# 품질 기준

작업량이 커져도 품질을 같은 수준으로 유지하기 위한 기준이다. 물류 관리 프로젝트(3조)의 같은 문서에서 빌드·프런트·계층 규칙 항목을 빼고 줄여서 옮겼다. 빌드와 테스트 명령은 모듈 구성이 정해진 뒤 추가한다.

## 1. 완료 기준
- 빌드와 테스트가 통과한다. 실패하면 실패 출력과 함께 보고한다.
- 변경한 동작에 대한 테스트가 있다. 테스트를 쓰지 못했다면 이유를 보고한다.
- 실행이 필요한 변경(설정, 라우팅, 기동)은 실제로 띄워서 확인한다. 확인하지 못했다면 "미확인"이라고 명시한다.
- 빌드 성공을 실제 API 동작 확인으로 대신하지 않는다.
- 검증 근거(실행한 명령과 결과) 없이 완료라고 말하지 않는다.
- 되돌리기 어려운 결정을 했다면 ADR을 남겼고, 질문과 AI 판단은 `docs/learning/`, `docs/ai-judgments/`에 남겼다.

## 2. 작업 흐름
1. 이해: SA MASTER의 해당 절과 기존 코드를 먼저 읽는다.
2. 계획: 파일 3개 이상 바꾸거나 설계 선택이 있으면 계획을 먼저 세운다. 사용자 확인이 필요한 선택은 묻는다.
3. 테스트 먼저: 도메인 규칙과 버그 수정은 실패하는 테스트로 시작한다.
4. 구현: 필요한 만큼만 쓴다. 과설계를 경계한다.
5. 검증: 1절 기준을 확인한다.
6. 리뷰: 스스로 diff를 다시 읽는다.
7. 기록: 학습 노트, 판단 기록, ADR을 갱신한다.

## 3. 디버깅
- 추측으로 고치지 않는다. 재현 → 원인 가설 → 확인(로그, 테스트) → 수정 → 회귀 테스트 순서로 진행한다.
- 같은 수정을 두 번 실패하면 멈추고 가설을 다시 세운다.
- 원인과 해결 과정은 학습 가치가 크다. 해결했다면 `troubleshooting` 스킬로 남긴다.
