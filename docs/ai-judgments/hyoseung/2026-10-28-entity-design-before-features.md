# 시드 데이터·API부터 시작하는 AI의 이슈 순서를 거부하고 도메인 엔티티 설계를 첫 이슈로 둔다

## 맥락
- 해결하려던 작업: 공연·좌석 조회 → 예매 흐름(SA 6-5)의 첫 이슈 구성.
- AI 활용 방식: 오늘 할 이슈를 나누고 Linear에 등록해 달라고 했다.

## AI 제안
- ISE-63 "공연장·좌석 배치 시드(Flyway)": `venue`·`venue_seat` 테이블 생성과 1.5만 석 데이터를 한 이슈로 묶음.
- ISE-64 "운영자 공연·회차 등록 API": `concert`·`schedule` 테이블·엔티티 생성과 API를 한 이슈로 묶음.
- 즉 테이블과 엔티티를 각 기능 이슈 안에서 필요할 때마다 만드는 순서였다. 도메인 전체(관계, 엔티티 책임, `schedule_seat`)를 먼저 확정하는 단계가 없었다.

## 판단
- 결과: 거부
- 판단자: 반효승
- 근거: 엔티티 설계부터 한 다음 기능을 만들어야 하는데 대뜸 API 구현, 시드 데이터부터 하면 안 된다. 순서대로 해야 한다.
- 검토한 대안: 없음(사용자가 순서를 지정).

## 반영
Linear 이슈를 다시 나눴다.
- ISE-63 → "공연·좌석 도메인 엔티티와 스키마 설계": `venue`·`venue_seat`·`concert`·`schedule`·`schedule_seat`의 Flyway DDL과 엔티티, 엔티티 책임, `schedule_seat.status` 소유·Flyway 버전 규칙 합의(권우 님).
- ISE-65 신규 "공연장·좌석 배치 시드 데이터": ISE-63에 막힘.
- ISE-64 "운영자 공연·회차 등록 API": ISE-63·ISE-65에 막힘. 테이블·엔티티 생성은 ISE-63으로 옮김.
- 작업 브랜치 이름을 `feat/ISE-63-venue-seed`에서 `feat/ISE-63-concert-domain-entities`로 바꿨다(push 전).

## 검증
구현 전.

## 판단 이력
- 2026-10-28 거부: 기능별로 테이블을 만드는 순서 대신 도메인 엔티티 설계를 먼저 한다.

## 발표·면접 포인트
- AI는 "빨리 동작하는 것"을 기준으로 기능 단위로 쪼갰지만, 여러 기능(시드, 운영자 등록, 조회, 다른 팀원의 좌석 선점)이 같은 도메인 모델을 공유하므로 모델을 먼저 확정해야 나중에 마이그레이션을 고쳐 쓰는 일이 줄어든다고 판단했다.
