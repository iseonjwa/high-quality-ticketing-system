# 좌석 배치 캐시(P4b)를 Redis가 아니라 서비스 메모리에 두되, AI 설명만으로 채택하지 않고 측정 뒤 확정함

## 맥락
- 해결하려던 작업: ISE-204(P4b). 회차 좌석 조회가 요청마다 15,000석을 읽어 객체로 만드는 것이 병목이었다(P4a 측정에서 초당 50건에 GC로 30초 중 8.3초 멈춤). 안 바뀌는 좌석 배치를 캐시하려 했고, SA MASTER는 캐시를 Redis에 두는 것으로 그려 두었다.
- AI 활용 방식: "Redis를 배우고 싶은데 P4b 캐시를 Redis에 둘까"라고 물었다(학습 노트 [2026-11-08-p4b-cache-lottery-grade-redis.md](../../learning/hyoseung/qna/2026-11-08-p4b-cache-lottery-grade-redis.md)).

## AI 제안
- 서비스 메모리에 둔다. 안 바뀌는 큰 덩어리를 요청마다 다시 쓰는 경우라, Redis에 두면 요청마다 약 1MB를 받아 객체 15,000개로 다시 만들어(역직렬화) P4a에서 줄인 객체 생성이 돌아온다. 서비스가 1대이고 값이 안 바뀌어 서버 간 공유·무효화가 필요 없다. 공용 Redis(Gateway·대기열)에 큰 값을 흘리지 않는다. 대기열 회차 캐시(`CachedScheduleReader`)라는 선례가 있다.
- 이 설명에는 측정 근거가 없었다. Redis로 해 보면 효과가 작거나 느려질 수 있다는 결과 자체도 배울 거리라고 덧붙였다.

## 판단
- 결과: 수용(서비스 메모리). 다만 ADR 0054를 "제안" 상태로 두고, 최권우의 같은 조건 비교 측정 뒤 채택하기로 했다.
- 판단자: 반효승
- 근거: Redis 캐시를 쓰면 매 요청마다 Redis에 바이트로 저장된 약 820KB를 서버가 받아 객체로 바꾸는 역직렬화를 하게 되고, 그러면 15,000개 객체가 매 요청마다 생겨 1차 개선(DTO 프로젝션)으로 객체 생성을 줄인 의미가 줄어든다. "바뀌는 값"을 "여러 서버"가 최신 값으로 같이 봐야 한다면 Redis를 쓰겠지만, 배치는 바뀌지 않고 서버가 한 대라서 네트워크 비용도 객체 생성도 없는 서비스 메모리 캐시를 골랐다. 바뀌는 값(회차 좌석 등급·상태)은 캐시에 넣지 않고 안 바뀌는 값만 넣어 무효화를 없앤다는 설명도 직접 정리해 확인했다(학습 노트 "효승 정리 확인").
- 검토한 대안: Redis(SA 원안), Redis에 응답 JSON 통째로 저장, 캐시 없음(P4a에서 멈춤). ADR 0054 "검토한 대안"에 적었다.

## 반영
- ADR [0054](../../decisions/0054-seat-layout-local-cache.md)(2026-11-08, 상태 제안)와 P4b 구현 PR #534(배치를 서비스 메모리에 캐시, 상태만 요청마다 읽음).
- 2026-11-13 보강: 최권우 측정 브랜치 구현과 비교해 커넥션 구간 축소·첫 요청 몰림 방지를 합쳤다(PR #603, ADR 0054 「보강」 절). 상태 1초 캐시(P4c)는 PR #605.

## 검증
- 로컬(2026-11-08, ADR 0054 결과 절): P4a → P4b에서 초당 150 postgres CPU 평균 136% → 21%, 커넥션 쥔 시간 21ms → 4.6ms. 초당 300에서 P4a는 p95 2.06s, P4b는 26ms.
- 로컬 대 Redis(최권우, 2026-11-12, 같은 커밋에서 설정 하나만 바꿈, 기록 [2026-11-12-verify-local-vs-redis-layout-cache-by-measurement.md](../kwonwoo/2026-11-12-verify-local-vs-redis-layout-cache-by-measurement.md)): Gateway 경유 초당 100명 좌석 조회 p95 로컬 7.0ms 대 Redis 38.3ms, 한 건당 CPU 약 5.5 대 25ms. Redis 쪽은 GC 약 17배, Redis 시한 초과 500, 공용 Redis `noeviction` 쓰기 거절 34건.
- AI 설명과 비교: 방향(로컬이 낫다)과 큰 값을 요청마다 옮기는 비용은 맞았다. 설명에 없던 원인(역직렬화가 키운 할당·GC, 공유 연결의 시한, 공용 Redis 메모리 거절)은 측정으로 드러났다.
- 배포 서버(2026-11-12·14, 회차 15,000석): 2차(P4b) 초당 100까지 실패 0(1차 초당 40). 3차(P4c)는 초당 200에서 실패 0, DB CPU 1~2%.

## 판단 이력
- 2026-11-08 수용(조건부): 서비스 메모리로 구현하고 ADR 0054는 측정 전까지 "제안"으로 둠.
- 2026-11-12 측정: 최권우 로컬 대 Redis 비교에서 세 조건 모두 로컬 우세.
- 2026-11-13 반영: 두 구현을 합쳐 PR #603, ADR 0054에 비교 수치를 더함.

## 발표·면접 포인트
- SA 원안(Redis)과 다른 결정을 AI 설명만으로 확정하지 않고, 팀원이 같은 커밋에서 설정 하나만 바꿔 잰 결과로 확정했다. 결과는 설명과 같은 방향이었지만, 원인은 설명보다 컸다(CPU 약 4.5배, GC 약 17배).
- Redis가 맞는 곳(여러 서버가 함께 봐야 하고 자주 바뀌는 값: 대기열 순번, 입장 토큰)과 서비스 메모리가 맞는 곳(안 바뀌는 큰 값을 요청마다 다시 쓰는 경우)을 데이터 성격으로 나눴다.
