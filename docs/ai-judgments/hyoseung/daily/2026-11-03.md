# 2026-11-03 hyoseung AI 판단 일지

- [수용] AI가 구현한 회차 좌석 조회 API(ISE-148, `GET /api/v1/schedules/{scheduleId}/seats`)를 구조 변경 없이 받아들이고 PR로 올리기로 했다. 회차 좌석 전체를 구역 → 열 → 번호로 보여 주고, 선점·추첨석은 `available=false`로 표시하는 방식이다. 엔티티 전체 조회의 성능, `serverTime`을 컨트롤러에서 만드는 위치, DTO 안 `add` 메서드는 비교해 본 뒤 그대로 두었다 — 근거: "이해된듯 저거 확인했으니 저거 먼저 sqaush하자" (Claude Code)
- [수용] 회차 좌석 조회 다음 작업으로 예매 조회 대신 payment.result 소비(ISE-73)를 먼저 하자는 AI 추천을 받았다. 결제 결과를 예매에 반영하는 쪽이 없어 M2 한 흐름이 끊겨 있고, 강민 님 ISE-150이 이 소비자를 기다리며, 예매 조회의 티켓이 이 작업에서 생기기 때문이다. 결제 토큰 발급은 권우 님 선점 API에 이미 있다는 설명도 받았다 — 근거: "그러면 이슈 73번인 payment->reservation 이벤트 처리하면 되는거지? ... 일단 한번 해보자" (Claude Code)
- [수용] ISE-73 결제 결과 소비 설계에서 AI가 제시한 기본안을 받아들였다. 확정·거절·늦은 승인 외의 이상한 결과는 "일단" 상태를 바꾸지 않고 `event=PAYMENT_RESULT_ANOMALY` 오류 로그로만 남긴다. 조건부 UPDATE가 0행이면 예외로 트랜잭션을 되돌리고 Kafka 재시도에 맡긴다. 추첨 예매 연결은 강민 님 ISE-150에 남긴다. ADR 0027을 "채택"으로 바꿀지는 AI에게 맡겼다. AI는 구현이 ADR 표를 따르고 SA 10-3에 사유 코드가 반영돼 있어 채택으로 바꾸고, 저장 위치(로그)와 0행 재시도를 결과 절에 적었다 — 근거: "일단 로그찍기로 하고 ... 재시도 하는 게 낫다면 그렇게 해. 강민님이 한다고 하신 부분은 남기고, adr 0027 ... 이건 너가 판단하고 알려주고 그대로 커밋해" (Claude Code)
- [수용] AI가 구현한 ISE-74(payment.result DLQ 처리기: 한 번 다시 처리하고 실패는 `dead_letters` OPEN·오류 로그)와 ISE-75(대사용 내부 조회 API, 변경 조회는 현재 상태 + `updated_at` 기준)를 실제 Kafka·결제 서비스로 돌려 본 결과와 함께 받아들이고 PR로 올리게 했다. ADR 0027·0022·0029와 결제 계약 문서의 반영분은 준현 님 리뷰를 받기로 했다 — 근거: "지금 너가 요구사항대로 정확하게 구현했다면 pr올려봐. 보고 squash할게. 준현님한테도 봐달라고 말씀드리고" (Claude Code)
- [수용] 준현 님의 #282·#283 리뷰를 AI가 정리해 "머지 전 수정 3개는 필수, 선택 사항도 작으니 같이"라고 추천했고, 선택 사항까지 모두 반영하기로 했다. #282는 DB 연결 실패(`CannotCreateTransactionException`)를 인프라 오류로 분류, `dead_letters` 저장 전 NUL 치환·길이 자르기, 로그에 예매·결제 ID 추가, 뒤늦은 재처리 성공 시 OPEN을 RESOLVED로 닫기다. #283은 ADR 0029 충돌 rebase와 취소 전이 때 `updated_at` 갱신 주의 주석이다 — 근거: "다 해줘. 그리고 준현님에게 변경사항 말씀드려줘."
