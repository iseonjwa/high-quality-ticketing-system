# 2026-11-04 hyoseung AI 판단 일지

- [수용] 예매 상세·내 예매 목록 조회 API(ISE-171)를 직접 구현하다가 AI에게 맡기고, AI 구현을 그대로 PR #318로 올렸다.
  - AI 구현 내용
    - 서비스는 `XxxResult`, 컨트롤러는 `XxxResponse`로 나눴다.
    - 좌석 표시 정보·티켓 번호는 네이티브 조인 한 번으로 읽는다.
    - 남의 예매는 404다.
    - 결제 토큰은 `HELD`이고 만료 10초 전까지만 준다.
    - `paymentTokenExpiresAt`은 SA에 없어 뺐다.
  - SQL은 이해하지 못한 채 흐름 정리 화면(계층·SQL 예시 행·고려 사항)을 보고 받아들였다. 테스트 7개와 예매 서비스 290개가 통과한 것을 근거로 삼았다.
  - 근거: "도저히 내 이해 밖이다. 날린 쿼리보고 포기했다." "전체 흐름을 화면으로 보기 편하게 ... 보여줘. 아무 문제없으면 squash하자" (Claude Code)
- [부분 수용] AI가 "데이터·상태 → 한 건 흘리기 → 실패 경로 → 말로 설명" 순서와 "#321 리뷰 → 한 건 흘리기 → k6" 진행 순서를 제안했다. 공부법 중 첫 단계(엔티티 구조)만 골라 먼저 하고, 콘솔 대신 HTML 화면으로 보기로 했다.
  - 근거: "엔티티 구조부터 다시 이해해보자. 기초를 알아야 나머지들의 흐름 정도는 파악하기 쉬워질 것 같아. 콘솔 말고 html 화면으로 볼 수 있음 좋겠어." (Claude Code)
- [거부] 회차 좌석 생성 질문에 AI가 서버 안에서 공연장·등급을 어떻게 읽고 검증하는지로 답했다. 묻고 싶었던 것은 요청을 보내는 쪽이 DTO 값을 애초에 어떻게 아느냐였다며 다시 물었다.
  - 다시 받은 답: 시스템이 알려 주지 않는다. venueId는 운영자가 직접 치고(공연장 1곳뿐), 등급은 프론트 `SEAT_GRADES`에 박혀 있으며, 가격은 운영자가 정한다.
  - 근거: "db에서 어떻게 조회하냐가 아니라 요청dto에 애초에 값을 어떻게 알고 넣어주냐고." (Claude Code)
