# 2026-11-08 hyoseung AI 판단 일지

- [거부] AI가 P4a 전에 RATE=40을 한 번 더 돌려 postgres·Gateway CPU와 노트북 전체 CPU를 함께 보고 병목이 DB인지 CPU인지 커넥션 풀인지 나누자고 제안했다. 기준선(RATE 20~50 표, 커넥션 대기, GC 비율)은 이미 있고 측정만 며칠째라 진도가 막힌다고 보고, 추가 측정 없이 DTO 직접 조회(P4a) 구현으로 넘어가기로 했다. DB와 자바 비중은 P4a 전후 비교에서 함께 드러난다.
  - 근거: "측정을 어디까지 해야 할지 정하자. 기준선은 이미 있고 DTO 프로젝션과 캐시도 해야 하니, 지금은 P4a 구현으로 넘어가는 게 맞지 않을까?" (Claude Code, 말투 다듬음)
- [거부] AI가 P4a 전후 측정을 위해 git stash, 서버 빌드, k6 실행을 사용자가 직접 하도록 명령을 안내했다. 긴 명령이 화면에서 줄바꿈돼 줄마다 실행하다 계속 실패했고, 무엇을 하는 명령인지도 따라가기 어렵다고 보고 서버 기동과 전후 측정을 AI가 직접 하도록 넘겼다.
  - 근거: "명령이 길어 따라가기 어려우니 서버 기동과 전후 측정은 직접 돌려 주고, 결과와 흐름을 설명해 줘." (Claude Code, 말투 다듬음)
- [선택] AI가 남은 P4b·P4c를 ISE-189 번호로 PR마다 다시 여는 방식과 서브 이슈로 나누는 방식을 제시했다. P4a는 전후 수치를 저장하고 squash로 먼저 합쳐 팀원이 쓰게 하고, P4b·P4c는 서브 이슈(ISE-204, ISE-205)로 나눠 하나씩 PR로 진행하기로 했다. 처음 생각한 "커밋 3개를 한 PR에서 squash"는 단계별 효과를 따로 잴 수 없어 PR 단위로 나눴다.
  - 근거: "현재 개선 전 수치들과 dto 프로젝션 개선 후 수치 잘 저장하고 sqaush까지 한 다음 서브이슈로 남은 2개 하나씩 진행하면 될듯" (Claude Code)
- [부분 수용] AI가 P4b 측정을 RATE 30·40·50·100·150으로 돌리고 P4a는 100·150만 다시 재서 비교하려 했다. 더 높은 부하를 준 것은 받아들이되, 비교 기준을 먼저 P4a가 버티는 한계(예: 초당 200)로 잡고 그 속도에서 P4b가 어떻게 달라지는지 봐야 한다고 고쳤다. 한계 찾기 → 같은 속도로 비교가 P4a 때와 같은 방법이다.
  - 근거: "P4a도 엄청나게 많이 부담을 덜었으니 이것도 얼만큼 더 버틸 수 있게 되었고(예를 들면 200까지 버텼다) 이 늘어난 초당 요청 수를 기준으로 똑같이 P4b를 테스트 해봤을 땐 어떤 차이가 있었다를 비교해야하지 않을까?" (Claude Code)
