# 2026-11-13 hyoseung AI 판단 일지

- [선택] 권우님 P4b(`experiment/ISE-79-k6-steps`)에는 상태 1초 캐시(P4c)와 첫 요청 몰림 때 DB를 한 번만 읽는 구조가 함께 들어 있다. AI가 "P4b끼리 비교(권우님 코드에서 P4c만 측정용으로 뺌)"와 "P4c까지 만든 뒤 비교"를 제시했고, 사용자는 P4b끼리 로컬에서 먼저 비교해 효율을 보고 P4c 방향을 정하기로 했다.
  - 근거: "그래 P4B만 비교하자. ... 로컬에서 P4B부분만 비교해보고 어떤 게 훨씬 효율적인지 보고 P4C어케할지 정하면 될듯" (Claude Code)
- [수용] 로컬 P4b 비교에서 Gateway 동시 처리 상한(64) 때문에 부하를 제대로 못 준다는 사용자 지적에, AI가 두 버전 모두 측정용 덮어쓰기(#571)로 상한을 끄고 Gateway 경유로 실패 1%까지 올리되 노트북 한계 구간은 따로 표시하자고 제안했고 사용자가 받아들였다.
  - 근거: "그래 상한 제한 끄고서 뭐가 더 나은지 보자." (Claude Code)
- [부분 수용] AI가 권우님 버전 응답이 같은지 "띄운 뒤 측정 직전"에 확인하겠다고 하자, 사용자가 시작 전에 응답 DTO가 같은 객체인지 코드로 보면 된다고 바로잡았다. AI가 바로 코드를 비교해 응답 클래스 3개의 필드는 그대로이고 값의 출처(구역 등급=공연장 좌석 등급, 가격 numeric 소수 0자리, 선점 가능 기준, 정렬)도 같음을 확인했다. 실제 응답 비교는 값 표기 차이(가격 소수점 등)까지 잡는 짧은 이중 확인으로만 남겼다.
  - 근거: "응답 형식이 다른 건 지금 시작하기 전에 확인하면 되잖아. 응답 DTO가 똑같은 객체인지 보면 되는 거 아님?" (Claude Code)
- [수용] AI가 코드로 비교한 P4b 차이 3가지(커넥션 쥐는 구간, 상태 쿼리, 캐시가 빈 순간 동시 요청)가 모두 권우님 구조 쪽이 낫다고 하자, 사용자는 P4b끼리 비교 측정을 하지 않고 P4b를 권우님 구조로 바꾸기로 했다. AI는 1번의 효과를 "응답 속도"가 아니라 "커넥션 점유 시간 단축"으로 바로잡고, 측정 브랜치 전용 코드(Redis 선택, 사전 거절, 엔티티 경로)는 빼고 구조만 가져와 P4c(ISE-205)와 한 PR로 하자고 제안했다.
  - 근거: "이게 맞다면 권우걸로 아예 다 바꿔야겠네 p4b를" (Claude Code)
- [수용·팀 의견 전달] 권우님이 측정 브랜치 P4b 코드는 dev에 올린 적이 없고, 금액을 `BigDecimal` 그대로 쓰는 부분과 네이티브 쿼리 부분은 효승 코드(Money, JPQL)로 맞추면 된다고 했다. 사용자는 권우님 구조를 가져가되 안정성·유지보수에서 효승 코드가 나은 부분을 찾아 합치는 방향으로 AI에게 트레이드오프 비교 분석을 맡겼다.
  - 근거: "안정성이나 유지보수 측면에서 효승띠 코드가 우세한 부분 찾아서 수정해달라해" (권우님 의견 전달)
- [선택] AI가 두 P4b의 트레이드오프(커넥션 범위, 상태 쿼리 방식, 행 변환, 첫 요청 몰림, 위치 맞추기, 테스트)를 정리하자, 사용자는 모두 이해하기보다 두 버전에서 안정성·성능이 나은 점만 골라 합치기로 했다. 선점 가능 기준이 자바와 SQL 두 곳으로 갈리면 함께 고쳐야 하는 위험, 네이티브 SQL은 오타를 요청이 와야 안다는 점은 사용자가 직접 정리해 확인했다.
  - 근거: "두 버전 중에서 안정성, 성능면에서 좋은 점들만 뽑아서 적용하자." (Claude Code)
- [위임] 사용자가 로컬(합친 P4b)·배포·P4c 측정과 Linear 할 일 파악을 맡기며, 알 필요 없는 답장은 AI가 하고 가장 효율적인 순서로 실행하라고 했다. AI는 끝난 이슈 2건(ISE-76, ISE-62)만 답하고 닫았고, 판단이 필요한 항목(ISE-237 풀 크기, ISE-196 문장·락 시한, ISE-270 판단 기록 공개, ISE-206 리뷰)은 답하지 않고 제안과 함께 넘겼다. 동시 처리 상한 조정은 값이 Gateway 메모리와 받는 쪽 속도에 달려 배포에서만 하자고 제안했다.
  - 근거: "답장해달라는 것 있으면 내가 알지 않아도 되는 거면 너가 알아서 답장하고 지금 해야되는 것들 순서대로 너가 가장 효율적인 게 뭔지 파악해서 실행해봐" (Claude Code)
- [위임] 사용자가 안정성과 성능을 함께 챙긴 구현(합친 P4b, P4c)과 부하 측정까지 AI가 끝내고 결과를 먼저 받은 뒤, 해석과 수정은 그다음에 하자고 했다.
  - 근거: "너가 생각했을 때 안전성, 성능 둘 다 챙겨서 만들고 부하테스트 하고 결과를 알려줘. 다 한 다음에 해석하고 그때 고치자." (Claude Code)
- [지적] AI가 코드 비교로 "합친 P4b가 커넥션·상태 쿼리 면에서 낫다"고 했지만, 로컬 측정에서 사용자가 기존 P4b와 합친 P4b가 거의 같고 낮은 부하에서는 오히려 조금 느리다는 점을 짚었다. AI는 이를 인정하고, 합친 P4b의 차이는 평소 속도가 아니라 캐시가 빈 순간의 500 제거와 높은 부하의 CPU 절감에서만 드러났고 큰 효과는 P4c에서 나왔다고 정리했다.
  - 근거: "기존 P4b와 합친 P4b의 비교가 거의 비슷한데? 400번대에서의 cpu, dbcpu 이것 빼면 오히려 쪼끔 더 걸려 보이기도 하는데" (Claude Code)
- [선택] 합친 P4b는 안정성 개선으로만 적기로 했다. 측정 결과는 하나씩 분석하지 않고, 배포 측정까지 모두 끝낸 뒤 한 번에 분석하기로 했다(상한 128·초당 800 실패 원인 등은 그때 본다).
  - 근거: "합친 P4B는 그냥 안전성 개선했다고만 하자. ... 전부 측정하고 하는 게 나을거같아. 하나하고 분석하고 하나하고 분석하면 너무 오래걸령" (Claude Code)
- [위임] 합친 P4b 코드 전체를 직접 검증하기 어렵다며, 테스트와 연결된 곳에 문제가 없으면 dev에 합치자고 AI에게 맡겼다. AI는 최신 dev로 옮긴 뒤 전 모듈 빌드·테스트(2,121개 실패 0), 지운 타입을 쓰는 곳(모듈·문서·k6) 검색, 기록 검사를 하고, 지운 클래스를 가리키던 주석 하나를 고친 뒤 PR #603을 올렸다. 배포 측정을 단계별로 하려고 P4c는 다음 PR로 나눴다.
  - 근거: "테스트까지 아무 문제 없고 다른 연결된 곳까지 문제 없다면 dev에 합치자" (Claude Code)
- [부분 수용] AI가 측정 단계를 촘촘하게(10·20·30…) 잡아 온 방식을, 사용자가 의미 있는 값만 고르게 고쳤다. 배포 측정은 상한 끔으로 이미 잰 개선 전·1차·2차는 다시 재지 않고, 단계마다 버티는 값과 깨지는 값만 3회씩 재는 계획으로 바꿨다.
  - 근거: "10/20/30 이런 거 넣으면 필요도 없고 오래 걸리니까 의미 있는 값들로 하자. 너무 촘촘하게 하면 너무 오래걸리자나." (Claude Code)
