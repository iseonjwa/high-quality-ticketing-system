# 2026-11-15 hyoseung AI 판단 일지

- [지적] 사용자가 "Gateway 동시 요청 상한은 서버가 감당 못 할 때 넘치는 요청을 바로 거절해 부담을 줄이는 것"이라고 정확히 말했는데, AI가 목적을 둘로 쪼개고 누가 도입했는지를 덧붙여 사용자가 틀린 것처럼 설명했다. 사용자가 다시 짚었고, AI는 사용자 정리가 맞다고 먼저 인정한 뒤 개선 단계 순서(2차는 DB 부하, 커넥션 대기는 3차가 해결)만 바로잡았다.
  - 근거: "누가 넣었든 간에 ... 바로 거절해서 부담을 줄여주는 거잖아. 아니야? ... 이 상태에 맞게 Gateway 동시 요청 상한 값을 찾은 거 아니야?" (Claude Code)
- [지적] 사용자가 자기 정리 방식(짧게, 따라가면 이해되는 흐름)을 예로 들며, 길게 설명하는 것보다 상대를 이해시키는 것이 핵심이라고 했다. AI는 설명 방식을 바꾸기로 하고, 이 흐름을 이력서 소재 06번(좌석 조회 포화점 5 → 200, 상한 64)으로 정리했다.
  - 근거: "내가 말하는 거 어때? 따라가다 보면 이해가 되잖아. 마냥 길게 얘기한다고 설명 잘 하는 게 아니야." (Claude Code)
- [부분 수용] 자기 측정만 보고 상한이 없는 게 낫다고 봤던 사용자에게, AI가 상한 끔의 "실패 거의 없음"은 k6가 15,000건을 못 보낸 착시이고 성공 수는 같다는 점, 기다림은 대기열에서 하고 Gateway 상한 64는 안전장치로 둬야 한다는 점을 보였다. 사용자는 "티켓팅은 기다리게 해야 한다"는 직관은 유지하되 시야가 좁았다고 인정하고, 상한이 만들어진 배경과 지금 처리 방식을 먼저 알아보기로 했다.
  - 근거: "내 것만 봤을 땐 상한제한 없는 게 좋아보였는데 현재 어떻게 처리되고 있고 왜 좋아서 적절한 수 찾아야 하는지 알아보자." (Claude Code)
- [거부] AI가 벌크헤드를 "Gateway가 Redis를 동시에 부를 수 있는 칸(예: 100칸)"이라고 설명했다. 사용자가 검색해 "한 작업이 동시에 쓰는 자원 제한"이 아니냐고 짚었고, 코드 확인 결과 우리 벌크헤드(`auth-redis`)는 로그아웃 토큰 조회 한 작업만, 동시 50개로 묶는 것이었다. AI 설명의 범위와 값이 틀렸다.
  - 근거: "Gateway가 Redis를 동시에 부를 수 있는 칸이 아니라 ... 한 작업당 최대 요청 수를 제한한다 라고 검색했을 땐 그렇게 나오는데 너는 Redis 자체에 가는 요청이라고 하네. 뭐가 맞는거지?" (Claude Code)
- [거부] 사용자가 확인 없이 틀린 정보를 말하지 말고 애매한 부분은 확실히 파악한 뒤 말하라고, 자기 말에도 맞장구치지 말고 항상 확인하라고 했다. AI는 "로그아웃 확인 벌크헤드가 차도 좌석 조회는 된다"는 사용자 정리를 코드로 확인해 틀렸음을 근거와 함께 답했다(좌석 조회는 Redis를 쓰지 않고, 로그인 필요 경로라 인증 필터의 로그아웃 조회를 거쳐 칸이 차면 503).
  - 근거: "정확하게 설명해달라고 요청을 해도 왜 거짓말을 하지? ... 내 말이 맞다고 하지말고 항상 확인하고 얘기해라" (Claude Code)
- [지적] 사용자가 "예를 들어" 가정으로 물은 질문(작업 두 개가 각자 벌크헤드를 가지면 한쪽이 차도 다른 쪽은 되나)을 AI가 우리 코드의 실제 동작 질문으로 읽고 "아니다"라고 답했다. 질문을 그대로 읽게 했고, AI는 가정대로 답(맞다, 벌크헤드는 인스턴스별로 따로 센다)을 다시 했다.
  - 근거: "내가 예를 들어라고 물어봤잖아." (Claude Code, 말투 다듬음)
- [부분 수용] 사용자가 커넥션 풀은 5로 충분하다고 답하자고 했다. AI는 좌석 조회 기준으로는 맞다고 확인했지만(3차 뒤 배포 초당 100~800 커넥션 대기 0), 이유 중 "클라이언트가 820KB를 다 받을 때까지 기다리는 일"은 커넥션과 무관하다고 바로잡고(#603 뒤 커넥션은 DB 읽는 순간만 쥠), 응모(L1) 쪽 근거가 남아 있어 "5로 충분" 대신 "좌석 조회는 풀 크기의 이유가 아니다, 크기는 응모 측정으로"로 ISE-237에 답했다. ISE-204는 완료 기준을 정리해 닫았다.
  - 근거: "커넥션 풀 크기는 지금으로 해도 충분하잖아 그치? ... 5로 해도 괜찮다 응답하면 되겠네. P4b는 이미 끝난 거고, 이것부터 처리해봐." (Claude Code)
- [거부] AI가 ISE-237(커넥션 풀 크기)에 좌석 조회만 보고 답했다. 사용자가 이 풀은 좌석 조회·좌석 선점·공연 관리·추첨·스케줄러가 모두 같이 쓰므로 풀 전체 관점으로 답해야 하고, 사용자가 잘못 말했어도 AI가 이슈를 읽고 파악해 답했어야 한다고 짚었다. AI는 댓글을 고쳐 사용처별로 아는 것(S1 대기 0, L1 대기 약 195, K1 로컬 커넥션 대기, 나머지 확인 못 함)과 섞어서 재는 측정 조건을 제안했다.
  - 근거: "이 DB에서 좌석 조회, 좌석 선점, 공연 관리, 추첨, 스케쥴러가 모두 일어나니까 이 DB의 풀을 써야하잖아. 그러면 그 관점에서 얘기를 해야지. ... 내가 잘못보냈어도 너가 한번 파악하고 대답해야지" (Claude Code, 말투 다듬음)
- [거부] 고친 ISE-237 댓글도 이슈와 코드를 제대로 읽지 않은 채 사용처를 "따로 잰 것 없음"으로만 채운 상태였다. 사용자가 새 세션에서 다시 읽고 파악하라고 했다. AI는 dev 코드에서 풀 사용처를 모두 찾았다. 동기형 선점이 잠금을 기다리는 최대 500ms 동안 커넥션을 쥐고, 스케줄러는 기본 스레드 1개를 나눠 쓰며 그중 추첨 실행이 최대 10초를 쥔다. 소비자는 결제 결과 1개와 접수형 선점 2개가 있다. 이를 근거로 좌석 조회의 대기 0은 좌석 조회만 걸었을 때의 값이고, 섞이면 좌석 조회도 기다린다고 정리했다. 사용자는 이 내용으로 댓글을 고치라고 했다.
  - 근거: "다른 기능들도 같은 DB를 사용해서 같이 커넥션을 기다리는지 생각을 못하고 있었던 거야. ... 너가 다시 읽어서 파악하라는거야", "너가 파악한 것들로 댓글 수정해." (Claude Code)
- [위임] AI가 대기열 입장과 추첨 실행이 스케줄러 스레드 1개를 나눠 쓰는 점을 따로 이슈로 올릴지 물었다. 사용자는 담당이 아니어서 판단하기 어렵다며 AI에게 맡겼다. AI가 확인해 보니 이 문제는 `open-peak-load-plan.md`에 이미 C1·Z5와 대안 C1-2로 적혀 있었다. 그래서 새 이슈는 만들지 않기로 했다. 대신 ISE-237 댓글에 그 문서를 출처로 달고, 추첨 실행 실측값(0.5초·4.5초, ISE-87)과 C1-2가 풀 측정에 미치는 영향을 덧붙였다.
  - 근거: "난 담당 아니여서 이해 안 된 상태라서 잘 모르겠어. 그건 너가 판단해서 얘기만해줘봐." (Claude Code)
- [보류] AI가 ISE-237에서 남은 일을 정리했다. 측정 조건 확정과 섞은 측정, 설정 PR과 ADR이 남았고, 이 일들은 강민·권우 님 답이 와야 시작할 수 있다고 했다. 사용자는 답이 올 때까지 ISE-237을 보류하고, 남은 전체 일을 먼저 보기로 했다.
  - 근거: "그럼 답변 오기 전까지 이 이슈에서 내가 할 일은 없는 거네? 이거 그럼 보류하고 나머지 내가 해야될 전체 일이 뭐야" (Claude Code)
- [보류] AI가 좌석 조회의 다음 개선 후보로 응답 크기 줄이기(gzip 압축, 배치·상태 분리)를 제시했다. 사용자는 발표 전에 시간이 없어 개선은 3차에서 끝내고, 응답 크기는 ISE-276의 "도입하지 않은 것"과 "알려진 한계"로 남기기로 했다. 이후에는 현재 개선 내용과 프로젝트 전체를 파악하는 데 집중한다.
  - 근거: "응답크기까진 아직 안 바꿨어. 현재 개선된 내용과 프로젝트 전체를 파악해야돼 이제는. 개선할 시간 없어서 이제 개선은 끝." (Claude Code)
- [수용] 사용자가 ISE-281(선점 사전 거절용 읽기 메서드)을 AI에게 만들게 했다. 사용자가 말한 순서는 Linear 이슈 만들기 → 최신 dev → 브랜치 → 구현 → dev에 squash였다. AI는 ISE-281이 이미 권우 님이 만들어 사용자에게 배정한 contract 이슈라 새로 만들면 중복이라고 알렸고, 그 번호로 브랜치 `feat/ISE-281-seat-hold-precheck-cache`를 땄다. 구현은 #603 때 들어왔지만 쓰이지 않던 `SharedLoadCache.peekFresh`를 써서 DB를 새로 읽지 않게 했다. 선점 쪽 연결은 권우 님 몫으로 남겼다. 커밋·push·PR은 사용자 검토 뒤에 한다.
  - 근거: "저거 만들어줘. 만들고 나서 이해하자. 그러기 위해서 리니어 이슈 만들어야 하고 최신 dev 받아서 이슈 번호를 기반으로 브랜치 파야하고 기능 만들고 dev에 squash 해야되는 거 알고 있어?" (Claude Code)
- [거부] AI가 남은 일 목록에서 ISE-205(권우 님 P4c 코멘트)를 "ISE-281로 대부분 답이 됐다"고 넘겼다. ISE-196(강민 님 문장·락 시한 질문)도 답장을 미뤘다. 사용자는 질문받은 곳에 답하지 않고 다른 이슈만 만들어 두면 안 된다고 짚었다. 최소한 그 이슈에 어떻게 했는지 정리하거나 확인을 부탁하는 답글을 달아야 한다는 것이다. AI는 두 이슈의 원래 댓글에 답글을 달았다. ISE-196에는 락 시한은 이미 경로마다 있다는 점(동기 선점 500ms·접수형 100ms·추첨 3초)과, 문장 시한은 추첨 실행(최대 10초) 때문에 이번에 두지 않는다는 점을 적었다. ISE-205에는 #605 구조, 배포 측정, ISE-281 #633으로 이어진 결과를 적었다.
  - 근거: "물어본 곳에 답장 안하고 다른 이슈 만들어서 알아서 확인해라 하면 안되지. 최소한에 그 이슈에다가 정리해둬서 확인 부탁드린다고 하거나 어떻게 했는지 답글을 달아야지" (Claude Code, 말투 다듬음)
