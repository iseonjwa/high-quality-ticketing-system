# 2026-11-16 hyoseung AI 판단 일지

- [팀 결정] AI는 15,000석이 SA MASTER 3-2의 설계 기준이고 Flyway 시드(`V20261030_2__venue_seed.sql`)로 만들어진다고 짚었다. 그래서 기존 기준을 지우지 않도록, 작은 공연장을 새 마이그레이션으로 하나 더 넣고 k6가 공연장 ID를 환경 변수로 받게 하자고 권했다. 사용자는 팀원들과 이야기해 측정용 회차 좌석 수를 줄이기로 했다고 전했다. 한 장비 사양에서는 15,000석 응답과 부하를 서버가 버티지 못해 의미 있는 부하 테스트를 할 수 없다는 이유였다. 처음 말한 1,000개는 1,500개로 바꿨다. 공연장을 새로 넣을지 기존 시드를 바꿀지는 아직 정하지 않았다.
  - 근거: "좌석이 너무 크니까 부하를 서버가 버티지 못해서 유의미한 테스트를 할 수가 없다고 팀원분들이랑 방금 말했어. 근데 1500건으로 다시 바꿨어." (Claude Code, 팀 논의)
- [선택] AI가 좌석을 1,500석으로 줄이는 방법 두 가지를 비교했다. A안은 기존 공연장 좌석을 새 마이그레이션으로 숨겨(soft delete) 1,500석으로 줄이는 것이고, B안은 1,500석 공연장을 새로 추가하는 것이다. AI는 A안을 권했다. A안은 25구역·등급 경계를 유지해 k6·프론트를 그대로 둘 수 있고, venueId 1과 이름 조회를 고칠 필요가 없다. 사용자는 A안을 골랐다. 기존 시드 파일을 고치는지 물었고, AI는 체크섬 오류 때문에 새 마이그레이션으로 3~20열을 숨긴다고 답했다(구역당 600석 → 60석).
  - 근거: "한 구역 당 600좌석이였는데 60개로 줄였구나. 기존 거 줄이자고. ... 일단 반영해봐" (Claude Code)
- [선택] ISE-237(reservation-service DB 커넥션 풀 크기)에서 두 의견을 AI가 비교했다. 강민 님 안은 개선 뒤 배포 O1에서 풀 5로 커넥션 대기가 0이었으니 5를 유지하고 재측정을 생략하는 것이고, 권우 님 안은 로컬에서 풀이 클수록 실패가 줄었으니 풀 5·8·10을 다시 재는 것이다. AI는 강민 님 안을 권했다. 배포의 X1(풀 10)에서 CPU 포화로 커넥션을 쥐는 시간이 두 배가 됐고, 로컬은 DB CPU가 넉넉해 배포를 재현하지 못하며, 재측정에는 릴리스와 측정 모드가 한 번 더 필요하기 때문이다. 사용자는 이해했다며 5 유지와 결정 기록(ADR 0064)을 골랐다. 권우 님 측정(ISE-296)에서 커넥션 대기가 다시 보이면 그때 풀 8을 재는 조건을 남겼다.
  - 근거: "이슈 237은 이해됐어. ... 그래 그럼 둘 다 처리해주고" (Claude Code)
- [수용] ISE-293(커넥션 대기 시한 초과를 500 대신 503으로)에 예매 담당으로 동의했다. AI가 코드로 확인한 내용은 세 가지다. 지금은 공통 예외 처리기의 마지막 처리기가 500을 준다. 예매 계약(`contracts.md` 225행)은 이미 503이다. 좌석 선점 화면은 503에만 같은 멱등키로 자동 재시도한다(`seatHold.ts`). 결제·사용자 서비스 계약 확인은 각 담당 몫으로 남겼다.
  - 근거: "293번은 단순히 커넥션 대기하다가 시간 지났을 때 응답을 500으로 줬던 걸 503으로 주자는 말인가? ... 그래 그럼 둘 다 처리해주고" (Claude Code)
