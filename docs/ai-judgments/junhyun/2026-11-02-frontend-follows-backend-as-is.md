# 공연 화면에 없는 필드를 백엔드에 먼저 요청하자는 AI 제안을 거부하고, 프론트는 백엔드 구현 그대로 쓰고 빈 곳은 나중에 고칠 것으로 기록

## 맥락
- 해결하려던 작업: ISE-113 공연 목록·상세 화면. 범위에 회차별 등급 가격과 추첨석 회차 안내가 있다.
- AI 활용 방식: Claude Code가 ISE-99로 머지된 공연 조회 API를 확인하고 화면을 구현했다.

## AI 제안
- 공연 상세 응답(ISE-99)에 등급 가격과 추첨 정보가 없고, 목록 응답에는 서버 시각이 없다.
- AI는 세 필드(회차 `prices`·`lotteryId`, 목록 `serverTime`)를 화면에서 선택 필드로 받게 만들었다. MSW 목에는 이 필드를 넣었다.
- 공연 API 담당(효승)과 추첨 담당(GGangMY)에게 필드 추가를 요청하는 `contract` 이슈 초안을 쓰고, 올릴지 물을 예정이었다.

## 판단
- 결과: 거부
- 판단자: junhyun
- 근거: "프론트는 수동적으로 가자! 먼저 요청하지 말고, 나중에 고쳐야할 부분으로만 기록해놓고 백엔드의 구현상태를 그대로 이용하는 방안으로 가줘. 구현이안됐으면 안된대로 남기고 됐으면 된대로 갖다쓰고!"
- 검토한 대안: 선택 필드로 받아 두고 목에서 먼저 보이기, `contract` 이슈로 필드 추가 요청(둘 다 하지 않음)

## 반영
- 화면 스키마·공연 상세 화면·목에서 제안 필드를 뺐다. 목은 실제 응답과 같은 모양이다.
- `docs/design/frontend/README.md`의 "공연 화면 규칙 (ISE-113)"에 "백엔드 구현 그대로" 규칙과 "나중에 고칠 것"(등급 가격, 추첨 안내, 목록 서버 시각)을 적었다.
- `contract` 이슈는 올리지 않았다.

## 검증
- `npm test` 228개 통과. 공연 상세는 실제 응답 모양으로 그린다.
- 로컬 compose 실서버로 서버 시각 카운트다운과 오픈 순간 [예매하기] 활성을 확인했다.

## 판단 이력
- 2026-11-02 거부: 백엔드에 필드를 먼저 요청하지 않고, 프론트는 구현된 API만 쓰기로 함

## 발표·면접 포인트
- 프론트가 백엔드 계약을 앞질러 가정하면 목과 실제 응답이 어긋나 시연에서 깨질 수 있다. 화면은 구현된 계약만 쓰고 빈 곳을 기록으로 남겨 백엔드 일정과 분리했다.
