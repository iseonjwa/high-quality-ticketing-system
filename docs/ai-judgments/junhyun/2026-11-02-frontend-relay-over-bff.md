# 프론트와 Gateway 연결을 BFF 대신 nginx 중계로 하고, 실서비스 구조는 학습 기록으로만 남김

## 맥락
- 해결하려던 작업: React SPA로 정한 프론트(ADR 0040)를 별도 컨테이너로 띄우고 서버 간 통신으로 API를 부르는 방식을 정한다.
- AI 활용 방식: 처음 제안한 nginx 같은 출처 구성을 이해하지 못해 설명을 요청했다. 이어서 중계와 BFF의 차이, 실제 티켓팅 사이트라면 어느 쪽이 맞는지, 앞단 대기실을 두면 서버 대기열 설계가 의미 없어지는지를 차례로 물었다.

## AI 제안
- nginx 컨테이너가 정적 파일을 내주고 `/api/`를 `gateway:8080`으로 중계한다. 브라우저가 한 출처만 보므로 CORS가 필요 없다.
- 실서비스라면 웹은 BFF가 맞다. RFC 10017(2026-08)은 결제·개인정보를 다루는 브라우저 앱에 BFF를 강하게 권한다. 몰림은 원 서버 앞단의 대기열이 받는다.
- 앞단 대기실이 하는 일(순번, 일정 속도 입장, 서명 토큰, 진입점 검증)은 이 프로젝트의 대기열 설계와 같고 위치만 다르다. 처음에 "실서비스는 대기실을 맨 앞에 둔다"고만 말해 서버 대기열을 대체하는 것처럼 들리게 한 표현은 고쳤다.
- 이 프로젝트에는 A(중계), B(중계 + Refresh 토큰만 httpOnly 쿠키), C(BFF) 중 A를 추천했다. 기간 한정 시연이고 화면 구현은 M4 한 주이며, 계약이 브라우저 토큰 보관을 전제로 한다.
- 상세: [중계와 BFF](../../learning/junhyun/qna/2026-11-02-reverse-proxy-vs-bff.md), [앞단 대기실과 서버 대기열](../../learning/junhyun/qna/2026-11-02-waiting-room-vs-server-queue.md)

## 판단
- 결과: 수용 (A 선택)
- 판단자: Junhyun An
- 근거: "이 프로젝트는 백엔드 중심이니까, A로 진행하자". 기록은 "이런 걸 학습했지만 백엔드에 집중하기 위해 간단하게 진행했다"로 남기라고 함. 앞단 대기실 이야기에는 "서버에서 요청을 대기시키는 건 백엔드 중심 프로젝트라서 그렇게 한 것이라, 앞쪽에 대기실 서비스를 두면 서버의 설계가 의미 없어질 것 같다"는 걱정을 먼저 밝혔다.
- 검토한 대안: B(중계 + Refresh 토큰 httpOnly 쿠키), C(BFF)

## 발표·면접 포인트
- 실서비스라면 BFF와 앞단 대기실이 맞다는 것을 확인했지만, 백엔드에 집중하려고 프론트 연결은 가장 단순한 중계로 갔다. 앞단 대기실이 푸는 문제는 우리가 서버 대기열로 직접 구현했고, 서비스 안에 둔 비용은 폴링 간격·jitter·읽기 전용 조회로 줄였다.
