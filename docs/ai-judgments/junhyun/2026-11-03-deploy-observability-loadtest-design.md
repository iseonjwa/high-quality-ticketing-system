# 배포·관측·부하 측정 설계에서 AI 추천 대부분을 받아들이고, Jenkins를 더하며 main 머지 자동 배포와 오픈 피크 전체 시나리오를 고름

## 맥락
- 해결하려던 작업: M3(11/11) 배포 1회와 시연, 사용자가 적은 남은 작업(로그 관측과 슬랙 알림, 로그를 함께 보는 시연 환경, 배포 환경 설계, 배포 환경 부하 테스트 설계)을 설계하는 일.
- AI 활용 방식: 사용자가 "결정 지점마다 질문 후 문서화"를 골랐다. AI가 SA 9-1~9-3·3-1과 로컬 측정(유휴 약 4.1GB)을 근거로 선택지와 추천을 냈고, 사용자가 고르거나 바꿨다.

## AI 제안과 사용자 판단

| 결정 | AI 추천 | 사용자 판단 |
|---|---|---|
| 설계 진행 위치 | 배포·관측·부하는 이 세션, 프론트 화면은 프론트 세션(접점은 docs/design) | 수용 |
| AWS 계정 | (선택지 제시) | 보류: 아직 모름, 만드는 단계에서 정함 |
| EC2 크기(SA U10) | 로컬 측정 뒤 결정 | 수용 |
| 배포 방식 | Actions가 이미지 빌드 → GHCR → EC2 pull | 부분 수용: 그대로 하되 Jenkins를 섞자고 제안("Jenkins도 넣어보면 좋을 것 같은데? 1번으로 하고 해당 방식을 섞어줄래?") |
| Actions·Jenkins 역할 | Actions는 CI·이미지, Jenkins는 배포 파이프라인 | 수용 |
| Jenkins 위치 | 별도 작은 EC2 | 수용 |
| 배포 시점 | 이미지는 자동, 배포는 Jenkins에서 수동 | 다른 선택: main 머지 때만 자동 배포 |
| 로그 수집 | Loki + Grafana Alloy | 수용 |
| 요청 로그(설계 중 "정상 요청은 로그가 없다"를 확인한 뒤) | 공통 요청 로그 필터 + Zipkin 링크(앱 로그를 바꾸지 않는다던 첫 안을 고침) | 수용 |
| 슬랙 | (선택지 제시) | 팀 워크스페이스에 새 채널 |
| 시연 로그 | 나란히 띄우기 먼저, 프론트 안 로그 패널은 다음 | 수용 |
| 부하 도구 | k6 | 수용 |
| 부하 발생기 | 같은 리전 임시 EC2 | 수용 |
| 부하 설계 범위 | 공통 측정 기반 + 결제 시나리오 | 다른 선택: 오픈 피크 전체 시나리오까지 |

## 발표·면접 포인트
- CI(검증·이미지)와 CD(배포·확인·되돌림)를 GitHub Actions와 Jenkins로 나눠, 배포된 버전을 커밋 SHA 이미지로 고정하고 실패하면 직전 태그로 되돌린다.
- 로그·트레이스·지표를 traceId 하나로 이어 Grafana 한곳에서 요청 하나를 끝까지 따라가게 했다.
