# 프론트 사용자가 API를 직접 쏘는 사람보다 대기열에 늦게 선다는 문제를 제기하고 AI 답을 받았으나, 구현·이슈 작성 없이 기록만 남김

## 맥락
- 해결하려던 작업: 오픈 시각에 새로고침 없이 [예매하기]가 켜지는 프론트 구현(서버 시각 보정 카운트다운)을 설명받던 중이었다.
- AI 활용 방식: 사용자가 세 번 이어서 물었다.
  1. 오픈 시각이 되면 버튼이 켜지는 것을 어떻게 구현했나.
  2. 그렇게 하면 API로 직접 요청을 쏘는 사람에 비해 프론트를 거치는 사람이 늦게 요청을 보내는 문제가 생기지 않나.
  3. 실제 운영 중인 서비스는 어떻게 구현하나. 프론트에서 온 요청만 받거나 rate limit을 두는 방법도 있을 것 같다.
- 2번과 3번의 문제 제기와 두 가지 대안(프론트에서 온 요청만 받기, rate limit)은 사용자가 먼저 떠올린 것이다.
- AI는 1번 답에서 "공정성은 서버가 지킨다"고 했다. 2번 질문으로 이 말이 과했다는 것이 드러났다. AI는 서버가 막는 것은 정각 전 입장뿐이고, 정각 직후 순번은 도착 순서라 직접 API를 쏘는 쪽이 앞선다고 바로잡았다.

## AI 제안
- 2번에 대한 답: 문제는 실제로 생긴다. 대기열 순번은 Redis 도착 순서(`INCR`)다. 프론트 사용자는 시계 보정 편향(수~수십 ms), 카운트다운 주기(0~250ms), 사람 반응(0.2~0.5초 이상)만큼 늦는다. 프론트 지연을 줄여도 사람 반응은 남으므로, 원인은 프론트가 아니라 "순번 = 도착 순서" 규칙이다. SA 1-1·1-2는 이 문제를 알고 추첨 배분·매수 제한·입장 토큰으로 대응했다. 사전 대기실 + 무작위 순번은 SA Could로 남아 있다. 사용자별 요청 제한(`ratelimit:{userId}`)은 SA에 설계만 있고 코드에는 없다.
- 3번에 대한 답: 실서비스는 여러 층을 쌓는다. 프론트에서 온 요청만 받기는 원리상 보장할 수 없다. 클라이언트 값은 위조할 수 있고, 매크로는 진짜 프론트를 headless 브라우저로 쓴다. 실서비스는 대신 서명 토큰(대기열 통과 증명)과 봇 점수로 판단한다. rate limit은 꼭 있어야 하는 기본 층이지만, 정각에 한 번 쏘는 스크립트와 다계정은 못 막는다. Queue-it·Ticketmaster·Cloudflare는 사전 대기실과 무작위 순번을 제공한다.
- 후속 제안:
  - 지금은 구현하지 않고 발표·면접에서 알려진 한계로 설명한다.
  - rate limit은 Gateway의 `RequestRateLimiter`(Redis 토큰 버킷)로 붙일 만하다. 그러려면 `contract` 이슈 초안을 쓴다.
  - 사전 대기실은 대기열 담당에게 제안한다.
  - 프론트에서 온 요청만 받기는 추천하지 않는다.
- 답 원문은 학습 노트 세 개에 있다.

## 판단
- 결과: 보류
- 판단자: junhyun
- 사용자가 한 말: "이런 생각을 했고, 이런 답변을 받았다는 것만 기록해줘". rate limit `contract` 이슈 초안, 사전 대기실 제안, 구현은 진행하지 않는다.
- 근거: 미기재
- 검토한 대안: 프론트에서 온 요청만 받기, 사용자별 rate limit, 사전 대기실 + 무작위 순번, 프론트 카운트다운 정밀화(오픈 시각 `setTimeout`, 왕복 시간 절반 보정)

## 반영
미반영. 학습 노트 세 개와 이 기록만 남겼다. 코드·SA·ADR·Linear는 바꾸지 않았다.

## 검증
구현 전. 2026-11-08 `origin/dev`에서 확인한 사실은 다음과 같다.
- `reservation-service/src/main/resources/redis/queue/enter.lua`: 오픈 판정은 Redis `TIME`, 순번은 `INCR` 도착 순이다.
- Gateway·nginx·서비스 어디에도 요청 제한기가 없다. 공통 오류 코드 `RATE_LIMITED`(429)만 있다.
- Gateway는 `spring-cloud-starter-gateway-server-webflux`와 reactive Redis 의존성을 쓴다.

## 판단 이력
- 2026-11-08 보류: 문제 제기와 AI 답만 기록하고 구현·이슈 작성은 하지 않음

## 발표·면접 포인트
- 서버 시각 보정 카운트다운을 설명받다가, 프론트 사용자는 API를 직접 쏘는 사람보다 대기열에 늦게 설 수밖에 없다는 공정성 빈틈을 스스로 찾았다. AI의 "공정성은 서버가 지킨다"는 과한 표현도 이 질문으로 바로잡혔다.
- 대기열은 서버를 보호하는 장치이고, 순번이 도착 순서면 매크로 대책이 아니다. 이 프로젝트는 일부 좌석을 추첨으로 배분해 보완했다. 다음 단계 후보는 사전 대기실 + 무작위 순번과 사용자별 rate limit이다.
