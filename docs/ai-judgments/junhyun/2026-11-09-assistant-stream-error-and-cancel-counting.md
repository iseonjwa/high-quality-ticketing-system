# 상담 스트림에 error 이벤트를 두지 않고, 사용자가 멈춘 요청도 요청 제한과 일일 예산에 넣기로 함

## 맥락
- 해결하려던 작업: 내부 AI 상담(ISE-126)의 스트리밍 답변 화면을 만들던 세션의 셀프 리뷰가 계약(`docs/design/assistant/README.md` 2-1절)에서 정해지지 않은 점 두 가지를 짚었다.
- AI 활용 방식: 머지 세션이 서버 코드로 지금 동작을 확인한 뒤, 두 가지를 선택지로 사용자에게 물었다.

## AI 제안
1. 스트림 중간의 서버 오류
   - 질문: `event: error`를 따로 둘지
   - 추천: 두지 않는다. 지금대로 `done` 없이 닫히면 답변 중단으로 본다는 규칙만 2-1절에 적는다.
   - 이유: 서버는 Claude 실패·시한 초과를 이미 `fallback`(또는 `meta`의 `SEARCH`) → `sources` → `done`으로 마무리한다. `done`이 없는 경우는 연결 끊김, 서버 중단, 검색 단계 예외, 응답 안전망(30초)뿐이다.
   - 대안: error 이벤트를 두면 화면이 끊김과 서버 오류를 구분할 수 있다. 대신 백엔드·화면·계약을 함께 고쳐야 한다.
2. [답변 멈추기]로 끊은 요청
   - 질문: 분당 5회 제한과 일일 예산에 넣을지
   - 지금 코드: 둘 다 넣는다. 분당 제한은 SSE를 열기 전에 세고, 일일 예산은 Claude를 부를 때 쓴다.
   - 추천: 넣는다(지금 동작 그대로 두고 계약에 적는다).
   - 이유: 멈춰도 Claude 호출 비용은 이미 들었다. 멈춤과 재질문을 반복하는 남용도 막는다.
   - 대안: 빼 준다. 사용자에게는 너그럽지만, 돌려주는 시점과 남용 대책이 따로 필요하다.

## 반영
- 상담 화면 PR(브랜치 `feat/ISE-126-assistant-stream-ui`)의 2-1절 문구를 확정 문구로 맞추도록 그 세션에 전달했다.
- 후속 백엔드 PR(ISE-221)은 이 결정에 맞춰 error 이벤트를 더하지 않는다.

## 검증
코드 동작 확인(`AssistantService.stream`의 예외 처리와 `prepareStream`의 요청 제한 위치). 동작을 바꾸지 않는 결정이라 새 테스트는 없다.

## 판단 이력
- 2026-11-09 수용: 두 가지 모두 지금 동작을 계약으로 확정함.

## 발표·면접 포인트
- 스트리밍 응답은 HTTP 상태를 도중에 바꿀 수 없다. 그래서 실패를 "검색 모드로 마무리한 정상 종료"와 "끝 표시(`done`)가 없는 비정상 종료" 두 가지로만 나눴다. 이벤트 종류를 늘리지 않고 화면 처리를 단순하게 유지했다.
