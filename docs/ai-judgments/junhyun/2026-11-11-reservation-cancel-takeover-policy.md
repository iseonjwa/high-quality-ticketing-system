# 결제 쪽 취소 환불을 위해 기다리던 예매 취소 API(ISE-206)를 직접 만들기로 하고, 취소 정책은 AI 추천안 네 가지를 그대로 받아들임

## 맥락
- 해결하려던 작업: 11/13 마감인 결제 취소 환불(ISE-46)이 예매 취소 API(ISE-206, 반효승 담당)를 기다리고 있었다. ISE-206은 11/8에 이슈로 올린 뒤 Backlog에 머물러 있었고, 코드는 없었다.
- AI 활용 방식: 오늘 할 일 브리핑에서 AI가 "ISE-206을 기다리지 않고 결제 쪽을 가정으로 먼저 만든다"를 추천했다. 사용자는 한 걸음 더 나가 예매 취소 API까지 만들기로 했다. AI가 그에 필요한 정책 선택지 네 가지를 추천과 함께 물었다.

## AI 제안
1. 담당 처리: ISE-206 담당을 안준현으로 바꾸고, 반효승 님을 멘션해 구현과 리뷰 요청을 알린다. PR 리뷰어도 반효승 님으로 둔다.
2. 취소 기한: 확정(`CONFIRMED`) 예매만, 회차 시작 시각 전까지 취소한다. 그 밖에는 409로 거절한다.
3. 추첨 예매: 추첨 당첨 예매(`source = LOTTERY`)는 취소를 막는다. 풀린 추첨석이 승계·종결 로직과 얽히기 때문이다. 범위 밖으로 문서에 적는다.
4. 환불 상태 표시: 예매 상세에 `paymentId`만 더하고, 화면은 기존 결제 조회 API(`GET /api/v1/payments/{paymentId}`)의 `status`·`refundedAt`으로 환불 상태를 본다. 예매 DB는 바꾸지 않는다.

대안: 담당은 그대로 두고 댓글만 단다, 취소 기한을 시작 24시간 전으로 둔다, 추첨 예매도 취소를 허용한다, 예매 테이블에 `refunded_at`을 더해 예매 상세에 환불 상태를 싣는다.

## 발표·면접 포인트
- 다른 담당의 API를 기다리면 마감 안에 결제 취소 환불을 끝낼 수 없어서 직접 만들었다. 대신 담당을 바꾸고 원래 담당에게 리뷰를 맡겨 팀 합의가 깨지지 않게 했다.
- 추첨 예매 취소를 막은 것은 기능 축소가 아니라 위험을 나눈 선택이다. 풀린 추첨석이 승계 배정과 엮이는 문제를 이번 범위에서 떼어 냈다.
