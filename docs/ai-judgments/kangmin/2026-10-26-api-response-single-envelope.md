# API 응답 형식: AI의 기존 형식 유지·6키 통일 제안 대신 성공·실패를 다른 형태로 감싸고 둘 다 traceId를 넣기로 했다

## 맥락
- 해결하려던 작업: SA v2 12장(API 명세)을 정리하던 중, 요청·응답 형태가 API마다 달라 보여 하나로 통일할 수 있는지 검토했다.
- AI 활용 방식: 응답 형태 총정리를 받은 뒤 "응답 형태를 통합되게 하면?", "최대한 균일한 형식으로 고정하고 싶다"고 물었다. 이어서 이전 프로젝트에서 쓰던 형식(성공 `ApiResponse`, 실패 `ErrorResponse`)을 보여 주고 의견을 물었다.

## AI 제안
1. 처음에는 기존 결정(결정 기록 #19, SA v2 12-1: 성공은 본문 그대로, 실패는 ProblemDetail)을 유지하고, 형식 대신 규칙(202 폴링 간격, 실패 사유 필드 이름 `reasonCode`, 202 본문 모양)만 통일하자고 추천했다.
2. "최대한 균일"을 목표로 하자, 모든 응답을 한 모양으로 고정하는 공통 래퍼 안을 냈다.
3. 이전 프로젝트의 두 형태 래퍼(`ApiResponse` / `ErrorResponse`)는 기반으로 쓸 만하다고 보고, 202 생성 수단, 실패 응답의 `traceId`, timestamp 시간대, 에러 코드 이름 맞추기, Gateway 에러 처리기를 고칠 점으로 들었다. 바깥 `status`와 업무 `data.status`가 헷갈린다는 점도 짚었다.
4. 하나의 래퍼로 통일해도 된다고 답하면서 조건을 붙였다: HTTP 상태 코드는 정확히 유지(오류 집계), Spring 기본 `/error`·필터 단계·Gateway 에러까지 처리기가 잡고 형식 검사 테스트로 확인, Actuator·Mock PG·Kafka 이벤트는 감싸지 않는다.
5. 최종안으로 성공·실패 공통 6키(`status, code, message, data, errors, traceId`)를 제안했다.

## 판단
- 결과: 부분 수용. AI의 첫 추천(기존 형식 유지)과 최종 제안(6키 한 형태)은 받지 않았다. 두 형태 래퍼를 기반으로 쓰고 `traceId`를 넣으라는 검토 의견, 그리고 함께 지킬 조건(HTTP 코드 유지, 형식 검사 테스트, 감싸지 않는 대상)은 받았다.
- 판단자: 팀 (전달: GGangMY)
- 근거: 한 형식으로 통합하면 개발자가 실수로 응답을 이상하게 처리했을 때 받는 쪽에서 판단하기 어렵다. kangmin: "신경 쓸 게 많아서 실수가 꽤 많이 나올 것 같다. 응답 형태를 성공·실패 따로 나누는 게 좋아 보인다". 결정: "추적 id 포함해서 성공 응답이랑 실패 응답 다르게 구성하기로 결정"
- 검토한 대안: 기존 형식(본문 그대로 + ProblemDetail), 성공·실패 공통 6키

## 반영
- 노션 결정 기록 #19에 반영됐다(10/26 결정, 수정 내역에 이전 결정). 성공 `{status, message, data, traceId}`, 실패 `{status, code, message, errors, traceId}`.
- SA 사본 [`docs/core/SA MASTER.md`](../../core/SA%20MASTER.md) 11-2에 반영.
- 본문이 없는 성공 응답(로그아웃, 대기 취소)도 204 대신 200 + `data: null`로 성공 형태를 유지한다.

## 검증
구현 전. 구현 시 없는 경로·깨진 JSON·인증 없음·업무 에러·처리 안 된 예외가 실패 형태로 나오는지 형식 검사 테스트로 확인한다.

## 판단 이력
- 2026-10-26 보류: 공통 형식 통일 방향은 택했으나, 한 형식과 성공·실패 두 형식 사이에서 팀 의견이 갈려 결정을 미룸
- 2026-10-26 보류 유지: 튜터 피드백 뒤 팀 대화에서 kangmin은 성공·실패를 다른 형태로 나누는 쪽을 지지했다
- 2026-10-26 부분 수용: 팀이 성공·실패를 다른 형태로 감싸고 둘 다 traceId를 넣기로 결정
- 2026-10-26 수용: 본문 없는 성공도 200 + `data: null`로 성공 형태를 유지 (AI가 6키 안에서 제안한 204 → 200 변경을 두 형태 안에도 적용). 근거: "본문 없는 성공도 200 + data null로 성공 형태 유지하자"

## 발표·면접 포인트
- 응답 형식은 정답이 없는 선택이라, 우리 팀의 위험(상태·예외가 많아 개발 중 실수가 잦음)에 맞춰 골랐다. 성공과 실패의 형태가 다르면 잘못 감싼 응답이 바로 드러난다.
- 추적 ID를 성공·실패 모두에 넣어 고객 문의나 장애를 어느 응답에서든 Zipkin·로그로 따라갈 수 있게 했다. 형식과 별개로 HTTP 상태 코드는 정확히 유지해 409(정상 거절)와 5xx(오류) 집계가 흔들리지 않게 했다.
- AI의 제안을 두 번 받지 않은 사례다(기존 유지, 6키 통일). 반면 두 형태 래퍼를 검토한 AI의 지적(실패 응답에 traceId, Gateway 에러 처리기, HTTP 코드 유지)은 받았다.
