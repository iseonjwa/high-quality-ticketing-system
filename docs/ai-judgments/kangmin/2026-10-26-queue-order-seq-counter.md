# 대기열 정렬 기준: 팀원이 지적한 진입 시각 동점 문제를 AI로 검증하고 순번 카운터(seq) 안을 택했다

## 맥락
- 해결하려던 작업: 대기열 담당이 SA v2 14-8 Redis 키 표에 노션 댓글로 "seq로"를 남겼다. `queue:{scheduleId}:waiting`(ZSET, 점수 = 진입 시각)이 같은 ms에 들어온 요청의 순서를 구분하지 못한다는 지적이다.
- AI 활용 방식: kangmin이 그 지적을 AI에 그대로 물었다. "완전히 ms 단위로 동일하게 입장하면 순서 구분이 되지 않는 것이 아닌가, seq로 큐 자료형처럼 순번 처리가 필요해 보인다."
- 문제를 찾고 seq를 제안한 것은 대기열 담당이다. AI는 그 제안이 맞는지 검증하고 대안과 비교했다.

## AI 제안
- 지적이 맞다고 보고, 진입 시각 점수의 문제를 세 가지로 정리했다.
  - 같은 점수면 ZSET이 멤버 문자열 사전순으로 정렬한다. 순번은 겹치지 않지만, 같은 ms에 들어온 사람끼리는 도착 순서가 아니라 userId 순서로 정해져 공정하지 않다.
  - 시각을 서비스 인스턴스가 찍으면 인스턴스마다 시계가 달라, 늦게 온 요청이 앞설 수 있다.
  - 오픈 정각에는 같은 ms에 요청이 몰리는 게 정상이라 동점이 드물지 않다.
- 선택지를 네 개로 비교했다: A 진입 시각 유지 / B 시각 + 난수 등 보조값 / C 순번 카운터(`INCR queue:{scheduleId}:seq` 값을 점수로) / D Redis List.
- C(대기열 담당의 seq 안)를 추천했다. Redis는 명령을 하나씩 처리하므로 INCR 값이 겹치지 않고 항상 증가하며, 기준이 Redis 도착 순서 하나라 서버 시계와 무관하다. ZSET의 순번 조회와 계정당 1자리 중복 방지는 그대로 유지된다.
- 덧붙인 주의점: 중복 확인·INCR·ZADD를 Lua 스크립트 하나로 묶어야 연타로 순번을 두 번 받지 않는다. 입장 판정을 ZRANK와 seq 중 무엇으로 할지 정해야 한다(이탈자가 빠지면 ZRANK는 당겨지고 seq는 그대로라 결과가 달라진다).

## 판단
- 결과: 수용 (선택지 C)
- 판단자: kangmin. 문제 제기와 seq 제안은 대기열 담당
- 근거: 같은 ms에 입장하면 순서를 구분할 수 없다는 대기열 담당의 지적 ("완전히 ms단위로 동일하게 입장해버리면 순서 구분이 되지 않는 것이 아닌가?"). 선택은 "c안으로 할게"
- 검토한 대안: A 진입 시각 유지, B 시각 + 보조값, D Redis List

## 발표·면접 포인트
- 팀원이 리뷰에서 찾은 문제를 AI로 검증한 사례다. ZSET 점수를 시각으로 두면 동점은 멤버 사전순으로 정렬되고 서버마다 시계가 달라서, Redis INCR로 받은 순번을 점수로 써 "Redis에 도착한 순서" 하나를 기준으로 삼았다.
- 확인·발급·등록을 Lua 스크립트로 묶어 같은 사용자의 동시 요청에도 순번이 하나만 나가게 했다.
