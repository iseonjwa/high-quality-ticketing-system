# 추첨 공정성은 시드 약속 없이 규칙 공개와 1계정 중복 차단으로 마무리하기로 함

## 맥락
- 해결하려던 작업: ISE-49 추첨 상세 설계의 결정 D7(순위 알고리즘과 공정성) 검토. 설계 문서는 `docs/design/lottery/options.md` D7이다.
- AI 활용 방식: D7 추천을 받은 뒤 "실제 운영 중인 서비스들은 어떤 식으로 공정성을 어필하는가"를 물어 검색 조사를 받았다(학습 노트 `docs/learning/kangmin/qna/2026-10-30-lottery-fairness-in-real-services.md`).

## AI 제안
- D7 추천: C(`SHA-256(seed ‖ entryId)` 오름차순) + 시드 약속(commit-reveal). 시드 해시를 응모 시작 전에 공개하고 추첨 뒤 시드를 공개해 누구나 순위를 검증하게 한다. 추가 비용은 컬럼 1개와 공개 조회 API 1개이고 발표에서 공정성 근거가 된다는 이유였다.
- 검색 조사: 실제 티켓·한정판 서비스(Nike SNKRS, Ticketmaster Verified Fan)는 난수 검증보다 "규칙 공개 + 봇·중복 차단"을 공정성으로 내세우고, 추첨 자체를 외부 검증 가능하게 공개한 티켓 사례는 찾지 못했다.

## 판단
- 결과: 부분 수용(C는 수용, 시드 약속은 이후 확장으로 미룸)
- 판단자: 이강민
- 근거: 추가 검증은 이후에 생각하고, 당장은 실제 서비스처럼 규칙 공개와 부정 참여 차단 정도로 마무리한다.
- 검토한 대안: C + 시드 약속, B(시드 셔플).
- 감수: 운영자가 응모를 본 뒤 시드를 바꾸지 않았다는 것을 외부에 증명하지 못한다. 부정 참여 차단은 1계정 기준 중복 차단까지이고 다중 계정·봇은 막지 못한다.

## 반영
- `docs/design/lottery/options.md` D7(결정, 규칙 공개 항목, 배정 규칙, 바꿀 조건)·D9(옆자리 판정), `details.md` 1·2·7절(`seed_hash` 제외, 공개 조회 API 내용, 배정 테스트), `README.md` 결정 목록·구현 4단계.
- SA는 바뀌지 않는다(시드 기록·재현은 SA 4-3 그대로).

## 검증
구현 전. 테스트 기준: 같은 시드·응모 → 같은 순위, 입력 순서를 섞어도 같은 순위(`details.md` 7절).

## 판단 이력
- 2026-10-30 부분 수용: C 유지, 규칙 공개 + 1계정 중복 차단. 시드 약속과 공개 검증 API는 확장안.

## 발표·면접 포인트
- 공정성을 "누가 추첨에 들어가는가"와 "추첨이 조작되지 않았는가" 두 층으로 나누고, 실제 티켓 서비스 사례를 조사해 이번 범위는 첫 층(규칙 공개, DB 제약으로 1계정 1응모)에 집중했다. 순위는 시드 기반 해시 정렬이라 재현할 수 있고, 시드를 처음부터 바뀌지 않게 저장해 검증 계층을 나중에 추가만 하면 되게 했다.
