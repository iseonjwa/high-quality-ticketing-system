# 추첨석 분리(D9)의 후속 공백 3건을 설정 시점 제한, 캐시는 DB 조건에 맡김, 알림은 조회 API 기본으로 정함

## 맥락
- 해결하려던 작업: ISE-49 추첨 상세 설계에서 D9(S석 일부를 `LOTTERY` 등급으로 전환)를 정한 뒤 남은 공백 정리. 이슈화 직전 마지막 확인이다.

## AI 제안
- 좌석 캐시(H2, SA Should, 좌석 1초·공연 5분 TTL): 전환·반환 직후 캐시가 이전 등급을 보여도 일반 선점 조건 `grade <> 'LOTTERY'`가 막아 409로 끝나고 잘못 팔리지 않는다. 별도 처리 없이, H2 도입 때 설정·반환 시점 캐시 삭제만 넣는다.
- 일반 판매 중 설정: A(`now() < LEAST(open_at, entry_start_at)`일 때만 설정·수정) 추천, B(언제든, AVAILABLE만 전환)는 판매 중 좌석이 사라진다.
- 알림(F7, SA Could): 기본은 응모 결과 조회 API 상태로 안내, F7을 만들면 `LotteryDrawn`과 당첨·예비자 결과 이벤트(약 3,000건)를 outbox로 낸다.

## 판단
- 결과: 수용
- 판단자: 이강민
- 근거: AI 제안의 근거(DB가 기준 저장소라 캐시 지연은 정합성 문제가 아님, 검증 한 줄로 판매 중 좌석 소실 방지, 알림은 Could 범위)를 받아들였다. 사용자 발언은 "추천대로 결정"이다.
- 검토한 대안: 설정 시점 B(언제든 허용), 캐시 즉시 무효화를 1단계부터 구현.
- 감수: 일반 판매를 연 뒤에는 추첨을 추가할 수 없다. 알림 전까지 사용자는 결과를 직접 조회해야 한다.

## 반영
- `docs/design/lottery/options.md` D9 후속 결정, `details.md` 1절 설정 시점·2절 PATCH와 결과 조회 API, `README.md` 이슈화 후보(설정 API, 4단계 확장안)·일괄 반영 대기(D9).
