# 커넥션 대기 1초(ISE-196) 동의와 추첨 시나리오 L1~L3 검토 의견(ISE-192)을 AI 초안 그대로 올림

## 맥락
- 해결하려던 작업: 11/8 결제 담당이 Linear를 정리하며 추첨 담당에게 검토 2건을 요청했다(마감 11/10). ISE-196은 reservation-service 커넥션 대기 시한을 30초에서 1초로 줄여도 추첨에 문제가 없는지, ISE-192는 오픈 피크 시나리오 명세의 추첨 부분(L1~L3)이 맞는지다.
- AI 활용 방식: 요청 내용을 파악해 설명해 달라고 했고, AI가 명세·k6 스크립트·소비자 재시도 코드·11/6 로컬 결과를 대조해 의견과 합니다체 댓글 초안을 만들었다.

## AI 제안
- ISE-196: 동의. 응모 API·스케줄러·outbox 릴레이는 재시도나 다음 주기로 이어진다. `payment.result` 소비자만 1·2·4초 3회 재시도 뒤 DLQ로 가므로, 풀 포화가 10초 넘게 이어지면 결제 결과가 DLQ로 갈 수 있다. L2·L3 측정에서 DLQ 건수를 함께 본다.
- ISE-192:
  - L1: 실제 사용자 수 약 10만 명, 중복 재요청의 201 재생, 수 ms 503의 출처로 `auth-redis` 차단기 상태 지표.
  - L2: Mock PG 빌링키가 메모리라 "재시작 → 안정 대기 → 등록 → 추첨" 순서. 완료 판정은 추첨 시각 당첨자 수를 분모로, 추첨 시각부터 PAID까지 `lottery_settlement_duration_seconds` 95%가 600초 안. 승계분은 따로. 소비자 동시 수 개선은 결제 담당과.
  - L3: 추첨 실행 시간 두 갈래, 커넥션 대기 시한을 환경 기록표에.
  - 공통: 명세의 배포 토큰 문구를 ISE-201 취소에 맞게.

## 검증
- `payment.result` 소비자의 재시도 후 DLQ 경로는 `PaymentResultKafkaConfiguration`, `ConsumerErrorHandlers`에서 확인했다.
- 11/6 로컬 수치(201 50,860건, 응모 행 48,553, 처리량 초당 3.10건)는 `docs/design/lottery/numbers-and-measurement.md` 3-2절 값이다.
- DLQ 처리기가 추첨 결과를 다시 처리하는지, `auth-redis` 차단기가 L1 503의 출처인지는 확인하지 못했다(측정에서 확인).

## 발표·면접 포인트
- 커넥션 대기 시한을 줄이면 사용자 요청은 빨리 실패해 좋지만, 같은 풀을 쓰는 메시지 소비자는 재시도 예산 안에 회복하지 못하면 DLQ로 간다. 설정 하나가 동기 요청과 비동기 소비에 다르게 작용한다.
