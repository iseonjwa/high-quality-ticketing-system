# herdr 지휘자 운영을 잠시 멈췄다가, 판단은 앱·실행은 herdr 지휘자로 나눠 다시 쓰기로 함

## 맥락
- 해결하려던 작업: 11/10 측정 전에 할 일 여러 개(L1/L2 ID 입력, F1 절차, Linear 답글, PR 정리)를 동시에 처리하려 했다.
- AI 활용 방식: herdr로 지휘자 Claude 하나를 두고 작업자 Claude를 단위마다 열고 닫는 방식을 제안받아, 작업자 2개를 실제로 돌렸다.

## AI 제안
- 지휘자가 `herdr agent start`·`agent prompt --wait`·`pane close`로 작업자를 운영하고, 사람은 지휘자 화면만 본다.
- 작업자는 결과 파일만 남기고, 동시에 2개까지 돌리며, 파일 범위를 나눈다.

## 판단
- 결과: 부분 수용(처음 보류, 같은 날 역할을 나눠 다시 채택)
- 판단자: kangmin
- 근거: "herdr에서 뭐 일부 하고 여기 앱에서 일부하고 이러니까 뭐가 어떻게 정리되고있는건지 너무 헷갈려", "일단 일을 하나씩 처리할거야"
- 검토한 대안: 지휘자 방식 계속, 사람이 herdr 페인마다 직접 지시

## 반영
- 작업자 두 개는 이미 끝났다. 결과는 k6 스크립트 4개 수정과 `docs/design/lottery/f1-fault-injection.md` 초안이다. 이 결과는 앱 세션에서 하나씩 검토한다.
- 길잡이 안내에도 실수가 있었다. 셸에서 실행할 명령(`herdr server stop`, `claude --resume`)을 어느 창에 넣는지 밝히지 않아, 사용자가 지휘자 Claude 입력창에 넣었다.

## 검증
작업 방식 판단이라 해당 없음.

## 판단 이력
- 2026-11-09 보류: 실행 위치가 두 곳(herdr, 앱)으로 나뉘어 상태를 따라가기 어렵다고 보고 하나씩 처리로 돌아갔다.
- 2026-11-09 부분 수용: 앱(길잡이)이 설명·추천을 하고, 사용자가 확인하면 앱이 herdr 지휘자에게 지시하고 결과를 확인하는 방식(B안)을 골랐다. 근거: "이거대로 진행하자". herdr 서버가 일반 권한으로 다시 떠서 앱이 상태를 직접 읽을 수 있게 된 것이 조건이었다. 사이에 L1/L2 마무리를 앱에서 직접 한 것은 실행 위치를 묻지 않은 길잡이의 실수로 남긴다.

## 발표·면접 포인트
- 병렬 에이전트의 병목은 실행 속도가 아니라 사람의 결정과 상태 파악이었다. 결정할 사람이 한 명이면 실행 위치도 하나로 모으는 편이 빠르다.
