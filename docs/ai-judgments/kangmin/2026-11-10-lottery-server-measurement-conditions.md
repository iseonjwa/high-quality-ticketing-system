# 추첨 배포 측정 전 점검에서 AI가 추천한 L1 503 메시지 태그 추가와 L2 측정 조건을 그대로 받아들임

## 맥락
- 해결하려던 작업: 11/10 배포 서버 추첨 측정(L2-a 3회, L2-b, L1) 직전에 준비가 끝났는지 점검했다.
- AI 활용 방식: "추첨 측정을 위한 사전 준비가 다 되었는가, 추가로 필요한 작업은 없는가"를 물었다. AI는 k6 시나리오, `seed-demo.sh lottery`, 측정 모드 스크립트, 발생기·배포 측정 문서를 대조했다.

## AI 제안
| # | 항목 | 제안 |
|---|---|---|
| 1 | L1 503 구분 | `l1-lottery-entry.js`가 503에 오류 코드만 붙여, Gateway 인증 벌크헤드 거절(동시 25, 대기 0)과 다른 원인의 503이 모두 `SERVICE_UNAVAILABLE`로 섞인다. 메시지 태그를 더하고 측정 중 `resilience4j_bulkhead_*{application="gateway",name="auth-redis"}`를 함께 본다 |
| 2 | L2-a 규모·시각 | 응모 30,000명(기본값, 당첨 약 2,000명, 서버 추첨 시간도 함께 잼). setup이 추첨 시각까지 기다리고 `setupTimeout`이 1200초이므로 응모 시작 +2분, 마감 +14분, 추첨 +15분으로 만들고 바로 k6를 시작한다 |
| 3 | 반복 조건 | 회마다 새 추첨, `USER_ID_BASE` 10000000·10100000·10200000, `DURATION_SECONDS=900`(로컬 외삽 95% 도달 약 10.4분이라 660초면 꼬리가 잘릴 수 있음) |
| 4 | L2-b 부하 | `PAY_RATE` 20(503 없을 수준)과 30(`pg-approve` 한계 초당 약 33건 근처) 두 번 |
| 5 | 진행 기록 | `watch-lottery.sh`는 로컬 DB 전용이라 판정은 Grafana `추첨` 대시보드와 600초 경계 비율로 한다 |
| 6 | 운영 확인 | 측정 모드 `on` 뒤 Mock PG 300ms를 다시 걸고 확인, 배포 커밋은 서버 `.deploy/current`, 마지막 `off` 뒤 한 번 더 `off`로 ISE-228 서버 동작 확인 |

## 판단
- 결과: 수용
- 판단자: kangmin
- 근거: "추천대로 진행할거야"
- 검토한 대안: 응모 2,000명·추첨석 3,000석(전원 당첨, setup 짧음, 예비·승계 없음)은 AI가 비교안으로 냈고 고르지 않았다.

## 반영
- L1 메시지 태그는 herdr 작업자에게 맡긴다(11/10). 나머지는 측정 명령과 측정 기록표에 반영한다.

## 검증
- 측정 전. 응모 30,000명의 setup 시간이 마감 안에 끝나는지는 서버에서 확인하지 못했다.

## 판단 이력
- 2026-11-10 수용: 측정 전 점검의 추천 6가지를 그대로 진행하기로 함
