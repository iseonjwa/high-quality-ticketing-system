# Gateway CPU의 약 24%를 쓰는 관측(추적·지표·로그 문맥) 축소를 위험하다고 보고 보류함

## 맥락
- 해결하려던 작업: 배포 서버 5차에서 Gateway가 CPU를 가장 많이 썼다(2,000/s에서 188%). 요청당 비용을 줄일 곳을 찾으려고 0b에서 JFR로 기능별 CPU를 쟀다.
- AI 활용 방식: JFR 표본을 기능별로 나누고, 줄일 수 있는 항목과 예상 이득을 물었다.

## AI 제안
- 관측 묶음(추적 6.7%, 지표 6.3%, 로그 MDC 약 2.2%, 문맥 전파 약 8.5% 등)이 Gateway CPU의 약 24%다. 이를 줄이면 한 건당 Gateway CPU 약 0.23ms, 서버 CPU 약 12%를 아낄 수 있다(계산값, [open-peak-scenarios.md](../../design/infra/open-peak-scenarios.md) "배포 서버 5차" 0b).
- 방법 후보는 요청 로그 줄이기(C1), 추적 샘플링 조정(C2), 경로별 관측 끄기다([설계 메모](../../design/infra/single-host-msa-resource-isolation.md) 2-3절).

## 판단
- 결과: 보류
- 판단자: kangmin
- 근거: 관측을 줄이는 것은 위험하다고 봤다(메인 세션 전달, 말 미기재). 대신 Gateway 맨 앞 동시 처리 수 상한을 먼저 한다([동시 수 상한 판단](2026-11-11-gateway-in-flight-limit-first.md)).
- 검토한 대안: 측정 모드에서만 요청 로그를 꺼서 비용만 재기

## 반영
- 동시 수 상한 필터는 관측 순서를 바꾸지 않는다. 추적(0)·요청 로그(1) 뒤인 -200에서 거절하므로, 거절된 요청에도 traceId와 요청 로그가 남는다.
- 설계 메모 "진행 상태" 표에 보류로 적었다.

## 검증
해당 없음(보류)

## 판단 이력
- 2026-11-11 보류: 관측 축소는 위험해 손대지 않고 동시 수 상한을 먼저 함

## 바꿀 조건
- 동시 수 상한을 넣고도 거절된 요청의 관측 비용 때문에 서버 CPU가 내려오지 않을 때
- 시연 추적 샘플링(1.0)과 측정 조건(0.01)의 처리량 차이를 재야 할 때(C2)

## 발표·면접 포인트
- 가장 큰 CPU 몫(약 24%)이라도 장애 분석과 시연 추적을 약하게 만드는 비용이 커서, 먼저 기능을 잃지 않는 장치(유입 제한)를 골랐다.
