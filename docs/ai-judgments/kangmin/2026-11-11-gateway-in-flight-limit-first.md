# Gateway CPU 포화와 OOM을 막는 첫 장치로 맨 앞 동시 처리 수 상한을 고르고, 설계안·프런트 표시·첫 상한 64를 AI 추천대로 정함

## 맥락
- 해결하려던 작업: 배포 서버 5차에서 서버 CPU가 1,500/s에 93%였고 굿풋은 약 1,470/s에서 멈췄다. Gateway는 활성 VU 약 5,300\~5,900에서 메모리 상한 768MiB로 OOM이 세 번 났다. 차단기는 느린 호출 기준을 20ms까지 낮춰도 열리지 않았다(B20). Gateway에는 동시 처리 수 상한이 없다.
- AI 활용 방식: 다음 장치를 무엇으로 할지 물었고, 고른 장치의 설계(필터 위치, 세는 단위, 상한값, 거절 응답, 예외 경로, 지표)를 구현 전에 받았다.

## AI 제안
- 첫 장치: 관측 축소(C1·C2)보다 Gateway 맨 앞 동시 처리 수 상한(A1)을 먼저 한다. 동시 수가 힙을 키우고, 리틀의 법칙으로 지연도 묶으므로 OOM과 CPU 포화를 함께 막는다([설계 메모](../../design/infra/single-host-msa-resource-isolation.md) 2-2·5절).
- 설계안: 인증 필터(-100)보다 앞의 `GlobalFilter` -200, 구독될 때 자리를 잡고 성공·오류·취소 어느 쪽이든 `doFinally`로 반납, 503 + `Retry-After: 2` + 새 오류 코드 `GATEWAY_OVERLOADED`, 운영자 경로 제외, 현재 수·상한 게이지와 거절 카운터. M1(메모리 상한 1,024MiB, 직접 메모리 128MB)을 같은 PR에 운영 반영.
- 프런트 표시: 프런트는 표에 없는 코드를 "예상하지 못한 오류"로 보인다. 그래서 같은 PR에서 `GATEWAY_OVERLOADED`를 `SERVICE_UNAVAILABLE`과 같은 문구로 한 줄 넣자(A안). 대안은 코드를 `SERVICE_UNAVAILABLE`로 두는 것(B안)이었다.
- 첫 상한값: 구현 세션 설계안은 500이었다(1,500/s × p95 152ms ≈ 228의 약 2배). 5차 실험 세션은 단계별 평균 응답으로 다시 셈해 64를 추천했다. p95 200ms에 맞는 평균 40\~45ms × 1,480/s ≈ 60\~67이고, 처리 중 수가 260을 넘은 단계는 p95가 이미 435ms 이상이었다. 500은 2,000/s에서도 거절하지 않아 OOM만 막는다.

## 판단
- 결과: 수용(네 가지 모두)
- 판단자: kangmin
- 근거: 첫 장치는 "A로 진행해", 설계안은 "진행해". 프런트 표시와 상한값은 메인 세션 질문 창에서 A안과 64를 골랐다(말 미기재, 메인 세션 전달).
- 검토한 대안: 요청률 상한(A2, 초당 도착 수), 관측 축소(C1·C2, 보류 기록 참고), 오류 코드 `SERVICE_UNAVAILABLE` 유지, 상한 500
- 두 세션 근거가 달랐던 점: 설계안의 500은 p95를 평균 체류 시간 자리에 넣어 크게 나왔다. 실험 세션의 64는 같은 단계의 평균 응답을 썼다. 리틀의 법칙은 평균에 대한 식이라 64 쪽이 식에 맞다. 다만 둘 다 k6에서 본 값이라 Gateway 앞 커널 대기가 섞여 있고, Gateway 안의 처리 중 수는 더 작을 수 있다.

## 바꿀 조건
- 32·64·128·500 비교에서 굿풋이 상한 아래로 떨어지거나 정상 부하(1,000/s)에서 거절이 나오면 값을 올린다.
- 거절 비용 때문에 서버 CPU가 내려오지 않으면 필터를 관측 앞으로 옮기거나 관측 축소를 다시 검토한다.
- Gateway를 여러 대로 늘리면 로컬 카운터라 상한이 대수만큼 커지므로 다시 잰다.

## 발표·면접 포인트
- 차단기는 의존성 장애를 감지하는 장치라 CPU 포화를 감지하지 못한다는 것을 측정(B20)으로 확인했다. 그다음 자기 과부하는 맨 앞 동시 수 상한으로 따로 막았다.
- 같은 리틀의 법칙이라도 p95를 넣으면 500, 평균을 넣으면 64가 나왔다. 식의 전제(평균)를 지키는 값을 첫 값으로 두고, 측정으로 확정하는 순서로 갔다.
