# Gateway 동시 처리 수 상한 기본값을 128로 올리자는 6차 세션 제안을 거부하고, p95 여유를 이유로 64 유지를 추천한 메인 세션 안을 받아들임

## 맥락
- 해결하려던 작업: 배포 서버 6차에서 Gateway 맨 앞 동시 처리 수 상한(`iseonjwa.gateway.in-flight.max-requests`) 32·64·128·500을 같은 G1 부하(1,000\~2,500/s)로 한 회차씩 쟀다([6차 결과](../../design/infra/open-peak-scenarios.md) "배포 서버 6차"). 그 결과로 배포 기본값(지금 64)을 정해야 했다.
- AI 활용 방식: 6차 실험 세션이 측정 결과와 함께 기본값 제안을 냈고, 메인 세션에 그 제안을 검토하게 했다.

## AI 제안
- 6차 실험 세션: 64 → 128. 판정 기준(같은 부하에서 굿풋이 0a·M1보다 낮지 않고 p95 200ms 안)을 지키는 가장 큰 값이다. 2,000/s·2,500/s 굿풋이 64보다 높다(L128b 1,721·1,732 대 L64 1,696·1,608). 감수할 점으로 p95 여유가 작고(2,500/s 180ms, p99 265ms), bulkhead 거절이 섞이며(2,500/s 1,966건, 64는 96건), 회차마다 한 번만 쟀다는 점을 적었다.
- 메인 세션: 64 유지. 2,000/s에서 64와 128의 굿풋 차이는 25건(1.5%)으로, 같은 128을 두 번 잰 차이(5%) 안이라 반복 변동과 구분되지 않는다. 반면 p95는 64가 약 절반이다(2,000/s 87ms 대 162ms). 128은 처리 중 수가 auth-redis bulkhead(동시 50) 위로 올라가 재시도 간격이 다른 두 종류 503이 섞인다.

## 판단
- 결과: 거부(6차 세션의 128 제안), 수용(메인 세션의 64 유지 추천)
- 판단자: kangmin
- 근거: "64 유지하고 다음 가설 진행해"(메인 세션 전달)
- 검토한 대안: 128(6차 제안), 96(중간값, 재지 않음), 32(1,000/s에서도 거절 392건이 나와 제외)

## 반영
- 코드·설정 변경 없음. `config-repo/gateway.yml`의 `iseonjwa.gateway.in-flight.max-requests: 64`를 그대로 둔다.
- 다음 가설은 상한값이 아니라 요청 한 건당 CPU 줄이기다. 첫 가설 H1은 상한 거절을 관측·요청 로그보다 앞에서 하기다.

## 검증
- 근거 수치는 6차 측정값이다(배포 `8b95fe68`, 회차마다 1회). 64와 128의 반복 측정은 아직 없다.

## 판단 이력
- 2026-11-11 거부: 상한 기본값 128 제안(6차 세션). 64 유지(메인 세션 추천 수용)

## 바꿀 조건
- 11/13 재측정에서 64·96·128을 회차마다 2번 이상 재서, 2,000/s 이상 굿풋 차이가 반복 변동보다 크고 p95가 200ms 안이면 더 큰 값으로 바꾼다.
- H1(거절 앞당기기)·H2(요청 로그 끄기)로 한 건당 CPU가 바뀌면 처리 중 수와 응답 시간 관계가 달라지므로 그 뒤에 다시 잰다.

## 발표·면접 포인트
- 굿풋이 1.5% 높은 값보다 p95가 절반인 값을 골랐다. 1.5%는 같은 값 두 번 측정 차이(5%)보다 작아 근거가 되지 못했다.
- 상한값 최적화보다 한 건당 비용을 먼저 줄이는 쪽으로 다음 가설을 옮겼다. 거절 비율이 25%에서 40%로 바뀌어도 한 건당 Gateway CPU가 0.66\~0.71ms로 같았기 때문이다.
