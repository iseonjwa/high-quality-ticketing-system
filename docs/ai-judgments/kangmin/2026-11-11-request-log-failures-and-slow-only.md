# 배포 서버 7차에서 요청 로그 비용이 확인되자, 운영 요청 로그를 실패·느린 요청만 남기는 안(B)을 고름

## 맥락
- 해결하려던 작업: Gateway 과부하 때 서버 CPU를 줄이는 가설을 한 번에 하나씩 쟀다. 배포 서버 7차 H2(요청 로그 끔)에서 서버 CPU가 1,000/s 78% → 66%, 1,500/s 93% → 85%로 내려갔고, 2,500/s 굿풋이 6차 L64 1,608 → 2,122였다. Gateway CPU는 거의 같았고(114% → 111%) 로그 수집기 Alloy(22% → 14%)와 컨테이너 밖 CPU가 줄었다([7차 결과](../../design/infra/open-peak-scenarios.md) "배포 서버 7차").
- AI 활용 방식: 측정 결과와 함께 운영 요청 로그를 어떻게 줄일지 선택지를 받았다.

## AI 제안
| 선택지 | 얻는 것 | 잃는 것 |
|---|---|---|
| A. 운영도 끔 | H2와 같은 절감, 코드 변경 없음 | 요청 흐름 로그가 사라짐(traceId·지표는 남음) |
| B. 실패·느린 요청만 남김 | 문제 요청은 남기고 대부분을 줄임 | 코드 변경 필요, 정상 요청 흐름은 못 봄, 절감 폭 재측정 필요 |
| C. 표본(1% 등) | 요청 흐름을 비율로 봄 | 특정 요청을 못 찾을 수 있음 |
| D. 측정 때만 끔 | 운영 관측 그대로 | 실제 오픈 때 절감 없음 |

추천은 따로 하지 않았다.

- 결과: 수용(B 선택)
- 판단자: kangmin
- 근거: "B 실패·느린 것만"
- 검토한 대안: A, C, D

## 반영
- 미반영. 기준(실패의 범위, 느린 기준 시간)과 적용 범위(Gateway만 또는 공통 `RequestLogFilter`까지)를 설계해 확인받은 뒤 구현한다.

## 검증
- 구현 전. 구현 뒤 배포 서버에서 H2와 같은 부하로 절감 폭을 다시 잰다.

## 판단 이력
- 2026-11-11 수용: 운영 요청 로그는 실패·느린 요청만 남긴다(B)

## 바꿀 조건
- 다시 잰 절감 폭이 H2(로그 끔)보다 크게 작으면, 남기는 기준을 좁히거나 A를 다시 검토한다.
- 장애 분석에서 정상 요청 흐름이 꼭 필요했던 사례가 나오면 C(표본)를 더한다.

## 발표·면접 포인트
- 프로파일러(JFR)는 JVM 안의 로그 비용 5.2%만 보여 줬다. 끄고 켠 비교로 재 보니 비용은 대부분 JVM 밖 로그 경로(표준 출력 → Docker → Alloy → Loki)에 있었다.
- 로그를 다 끄지 않고 문제 요청만 남겨, 관측과 비용 사이에서 고른 결정이다.
