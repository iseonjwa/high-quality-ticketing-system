# 선점 뒤 issued 정리를 리스너 대신 훅 메서드로 하자는 AI 추천을 바로 바꾸지 않고 담당 의견을 먼저 묻는다

## 맥락
- 해결하려던 작업: ISE-207(입장 토큰을 좌석 선점 성공 때 소모)에서 대기열 `issued`의 사용자를 지우는 처리를 동기·비동기 중 무엇으로 할지, 동기라면 리스너와 메서드 중 무엇으로 할지 정하려 했다.
- AI 활용 방식: 처리 방식을 물었고, AI가 `SyncSeatHoldService`·`LotteryHoldExpiryHook`·대기열 차단기 코드와 Spring의 `AFTER_COMMIT` 처리 소스를 읽고 비교했다.

## AI 제안
- 동기로 한다. 응답 전에 정리가 끝나 바로 다시 줄을 서도 새 번호를 받는다. 비용은 Redis 명령 1회다.
- 리스너(`@TransactionalEventListener(AFTER_COMMIT)`) 대신 seathold 응용 계층의 훅 인터페이스를 queue가 구현하고, `writeTransaction.execute`가 끝난 뒤 부른다. 근거는 두 가지다.
  - `SyncSeatHoldService`가 트랜잭션을 코드로 열어 `execute` 뒤 호출이 그 자체로 커밋 뒤다.
  - 같은 `jti` 거절은 롤백이라 `AFTER_COMMIT` 리스너가 돌지 않아, ADR 0053 초안의 "거절할 때 한 번 더 지운다"를 리스너 하나로 못 한다.
- 함께 짚은 사실: Spring 7.0.10에서 `AFTER_COMMIT` 리스너 예외는 `afterCompletion`에서 잡혀 로그만 남는다. 11/9 대기열 담당 의견의 "잡지 않으면 500"은 리스너가 아니라 직접 호출에 해당한다(소스 확인, 실행 확인 안 함).

## 판단
- 결과: 보류
- 판단자: kangmin
- 근거: 기존 합의(동기 리스너, ADR 0053 초안)를 바꾸는 일이라 ISE-207 댓글로 대기열·선점 담당 의견을 먼저 묻는다.
- 검토한 대안: 리스너 유지(기존 합의), 비동기(`@Async`·Kafka)

## 반영
미반영. ISE-207 댓글 초안만 작성했다.

## 검증
구현 전.

## 판단 이력
- 2026-11-12 보류: 훅 메서드 추천을 담당 의견을 받은 뒤 정하기로 함
- 2026-11-13 거부(일부): "리스너와 메서드 둘 다 처리할 수 있는 것 아닌가, 한계가 확실한가"라고 지적함. AI가 다시 확인해 보니 거절 경로도 `AFTER_ROLLBACK` 리스너로 처리할 수 있었다. "리스너로는 할 수 없다"는 과장이었다고 정정했다. 다시 비교해 보니 기능 차이는 없고, 차이는 DB 커넥션을 쥐는 시간(리스너는 `ZREM` 동안 반납 전), 새 선점과 재요청의 구분, 선례였다. 댓글 초안은 "둘 다 가능, 장단 비교" 형태로 고쳤다.

## 발표·면접 포인트
- 트랜잭션을 코드로 쥔 서비스에서는 `AFTER_COMMIT` 리스너의 장점이 이미 있고, 롤백 경로에는 리스너가 돌지 않는다는 점이 선택을 갈랐다.
