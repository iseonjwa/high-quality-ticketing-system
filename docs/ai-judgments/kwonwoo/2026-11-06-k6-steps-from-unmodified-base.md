# k6 단계별 개선을 수정 없는 기본 코드에서 시작해 병목을 직면하는 순서로 다시 설계

## 맥락
- 해결하려던 작업: 좌석 선점·좌석 조회의 k6 부하·스트레스 측정으로 성능 개선 사례를 만든다([k6-seathold-bottleneck-plan.md](../../design/reservation/k6-seathold-bottleneck-plan.md)).
- AI 활용 방식: Claude Code가 같은 날 1차 개정에서 단계 순서와 결정 항목 6~9를 제안했고, 사용자 요청으로 코드명(P4a, R1 등)과 결정할 것을 풀어 설명했다.

## AI 제안
- 1차 개정: P4a부터 R1(커넥션 대기 1초)과 G1을 켠 환경을 기준으로 재고, 비교 기준은 같은 이미지의 `ENTITY + R1`로 한다. S1~S4는 측정 브랜치로 옮겨 S0과 비교한다. 최종(F)은 배포 환경에서 1회 잰다. 워밍업은 30초.
- 설명 뒤 제안: 기준 환경은 배포 메모리·만료 스케줄러 끔·워밍업만 두고 G1·R1은 단계로 뺀다. 측정 브랜치를 현재 HEAD에서 다시 만들어 한 단계에 커밋 하나씩 쌓는다. S4는 기본 측정 뒤 대사 위반이 나오면 넣는다.

## 판단
- 결과: 부분 수용. 1차 개정의 "R1을 기준 환경에 미리 넣는다"(6절 6번)는 거부하고, 설명 뒤 제안은 받아들이되 두 가지를 바꿨다.
  - 워밍업 30초 → 1분.
  - 최종(F)도 local에서 잰다. 배포 환경 성능 테스트는 나중에 따로 한다.
  - 다른 이슈에서 다룰 코드(P4, R1, G1·P1)는 반영할 때 이슈마다 따로 브랜치를 판다.
- 판단자: 최권우
- 근거: 기본 상태에서부터 순차적·단계적으로 병목과 문제 상황을 직접 직면하면서 진행해야 개선 사례가 된다. 단계마다 워크트리에서 돌린 결과를 예상과 대조한 뒤 반영한다.
- 검토한 대안: R1·G1을 켠 환경을 기준으로 재기(1차 개정). 한 이미지에서 환경변수로 단계를 고르기(이전 측정 워크트리).
