# K1-H를 막은 Gateway 인증 차단기를 측정 환경에서만 완화하기로 함

## 맥락
- 해결하려던 작업: ISE-79 k6 단계 측정. 수정하지 않은 base 코드에서 K1-H(좌석 선점만 보내는 스트레스, 초당 50→800명)를 잤다.
- 결과: 초당 100명부터 Gateway가 즉시 503을 냈다(100명 10%, 800명 97%). 그동안 reservation-service는 한가했고 잠금 대기도 0이었다.
- 원인: Gateway는 요청마다 Redis에서 로그아웃 토큰 여부를 확인하고, 이 호출에 차단기 `auth-redis`를 건다(`config-repo/gateway.yml`: 느린 호출 50ms, 비율 50%, 열림 10초). Gateway CPU가 100~180%로 오르자 느린 호출 비율이 90~100%가 되어 차단기가 열렸다. Redis CPU는 10% 아래였다.
- AI 활용 방식: Claude Code가 base 측정을 분석해 원인을 찾고, K1-H를 어떻게 이어 갈지 선택지 넷을 냈다.

## AI 제안
선택지 넷과 추천은 다음과 같았다.
1. (추천) 측정 브랜치에서만 차단기 기준을 덮어써 완화한다. 이 덮어쓰기는 단계가 아니라 측정 환경으로 기록하고, 발견 내용은 Gateway 담당에게 contract 이슈로 알린다.
2. 직면한 병목으로 보고 단계로 넣는다. 실제 반영은 Gateway 담당 이슈로 한다.
3. K1-H만 Gateway를 우회한다.
4. 그대로 기록한다.

추천한 이유는 세 가지였다. K1-H의 목적은 선점 경로 개선을 재는 것이다. Gateway는 다른 담당 영역이다. 우회하면 실제 경로(JWT 검증, 헤더 주입)가 빠진다.

## 반영
측정 브랜치 `experiment/ISE-79-k6-steps`의 `add787e`에 넣었다. 공유 `config-repo/gateway.yml`은 고치지 않았다.
- `reservation-service/k6/config-measure/gateway-k6measure.yml`: `slow-call-duration-threshold`를 50ms에서 100ms로 올린다. 100ms는 코드의 호출 시한(`REDIS_TIMEOUT`)과 같다. 그래서 느린 호출 판정은 사실상 꺼지고, "시한 초과·오류가 절반 이상이면 연다"는 보호는 남는다. 완화 폭은 에이전트가 정했다.
- `reservation-service/k6/compose.measure-gateway.yml`: Gateway에 `k6measure` 프로필을 켜고, config-server가 측정 전용 폴더도 읽게 한다.
- `step-run.sh`: 기준 환경 목록에 이 파일을 넣었다. Gateway가 `k6measure` 프로필로 떠 있지 않으면 측정을 시작하지 않는다.
- `STEPS.md`: 기준 환경, 실행 방법, 결정, base H 재측정 예상을 적었다.
- 후속: 측정 브랜치 `b1cdefa`에서 `failure-rate-threshold`를 50%에서 100%로 올렸다. 최근 20번이 모두 실패할 때만 열리므로, Redis가 완전히 응답하지 못할 때의 보호는 남는다.
- 후속: 측정 브랜치 `c6bc026`에서 측정 환경의 Gateway `JAVA_TOOL_OPTIONS`에 `-XX:+UseG1GC`를 더했다. `step-run.sh`는 Gateway가 G1으로 떠 있지 않으면 측정을 시작하지 않는다. 진단 회 이름은 `g1gw`다.
- contract 이슈는 올리지 않았다. 관찰 셋은 계획 문서 `docs/design/reservation/k6-seathold-bottleneck-plan.md` 6절 13번에 측정 뒤 조율할 거리로 남기고, 측정 브랜치 `STEPS.md`의 차단기 처리 항목에도 조율 시점을 적었다.

## 검증
- config-server가 `gateway/local,k6measure`에 측정 전용 파일(100ms)을 공유 `gateway.yml`(50ms)보다 앞 순서로 내려주는 것을 확인했다.
- base H 재측정(측정 브랜치 `121cba7`, STEPS.md): 느린 호출 비율은 내내 0이었다. 선점 오류는 100명 0%, 200명 0%로, 공유 기준의 10%, 47%보다 줄었다. 400명 73%, 800명 97%→93%다. 400명부터는 Gateway가 시한 100ms 초과를 실패로 세어 차단기가 다시 열렸다. 완화로 Gateway 한계가 초당 100명에서 약 200명으로 올라갔지만, 선점 경로의 한계(커넥션·잠금 대기)는 200명까지 드러나지 않았다.
- 실패율 100% 뒤 base H(측정 브랜치 `396493b`): 선점 오류가 50명·100명·200명 모두 0%, 400명 41%(이전 73%), 800명 89%다. 200명까지 차단기는 열리지 않았다. 400명에서는 reservation-service의 Serial GC 정지(최대 532ms)와 Gateway의 Redis 확인 시한 초과(초당 18~20건, 20번 연속으로 몰려 차단기가 몇 차례 열림)가 겹쳤다.

## 판단 이력
- 2026-11-07 수용: 측정 환경에서만 느린 호출 판정을 끄고 base H부터 다시 잰다.
- 2026-11-07 수용: 400명부터 실패 기준으로 다시 열려, 측정 환경에서 실패율 기준도 100%로 올린다.
- 2026-11-07 수용: Gateway Serial GC 가설을 측정 환경에서 Gateway G1으로 진단한다.
- 2026-11-07 진단 결과: Gateway G1으로 정지가 최장 17ms로 줄었는데도 Redis 확인 시한 초과와 400명 오류(43%)가 남아 가설을 기각했다. Gateway G1은 측정 환경에서 되돌렸다(측정 브랜치 `8a315ff`).
- 2026-11-07 보류: Gateway 담당 contract 이슈를 지금 올리자는 제안을 보류했다. 측정 환경 전용 임시 설정이라 측정이 모두 끝난 뒤 조율할 거리로만 남긴다.

## 발표·면접 포인트
- 무거운 경로(좌석 조회)를 떼자 앞단 Gateway 차단기가 먼저 드러났다. 병목은 하나를 치우면 다음 것이 보인다.
- 차단기의 느린 호출 시간은 호출하는 쪽에서 잰다. 그래서 Redis가 멀쩡해도 Gateway CPU가 차면 열린다.
- 측정 목적(선점 경로 개선)을 지키려고 다른 담당의 설정은 측정 환경에서만 바꿨다. 공유 설정을 바꾸지 않았으므로 측정 중에는 이슈로 올리지 않고, 실제 반영 여부는 측정이 끝난 뒤 최종 수치를 들고 담당과 조율한다.
