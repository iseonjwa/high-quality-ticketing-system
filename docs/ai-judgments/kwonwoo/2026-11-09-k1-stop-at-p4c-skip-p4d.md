# P4d 조건이 맞았지만 K1 좌석 조회 개선을 P4c에서 마치고 K1-H로 넘어감

## 맥락
- 해결하려던 작업: ISE-79 k6 단계 측정. 새 기기(i9-14900HX, Docker VM 32코어·16GiB)에서 base부터 P4b까지 다시 재고, 좌석 조회(K1) 개선의 다음 단계를 고르던 중이었다.
- 경과: 새 기기 P4b가 기존 측정(L 초당 100명, S 320명)을 모두 통과해, S 단계를 1,280명까지 올려 한계를 찾았다(좌석 조회 초당 640~1,280건 사이, 커넥션 대기 최대 186건). 그 병목을 겨냥해 P4c(선점 가능 좌석 ID 1초 캐시)를 넣고 쟀다.
- AI 활용 방식: 측정 결과(서버 지표, Prometheus의 Gateway 차단기 지표, JFR)를 모아 P4d 조건을 판단하고 다음 단계 선택지를 내게 했다.

## AI 제안
- P4c 결과: 1,280명 단계에서 커넥션 대기 186 → 0, PostgreSQL CPU 약 3.6코어 → 거의 0. DB 병목은 사라졌다.
- 그런데 같은 단계 클라이언트 성공률은 44.2% → 21.6%로 떨어졌다. 응답이 빨라져 k6가 830KB 응답을 더 많이 받아 CPU를 약 17코어까지 썼고, Gateway 인증 차단기가 더 오래 열렸다(즉시 거절 42,200 → 56,100건).
- JFR에서 Jackson이 약 32%, 응답 만들기가 약 24.5%라 계획 3-4절의 P4d 조건(커넥션 대기 평균 1 아래, Jackson ≥ 30%)은 맞는다.
- 선택지: (1, 추천) K1을 P4c에서 마치고 P4d는 넣지 않은 이유를 기록한 뒤 P4 묶음 마지막 3회 → K1-H S1·S2 → P1로 간다. (2) P4d를 넣고 reservation-service CPU·서버 처리량으로만 효과를 본다. (3) 오늘은 멈춘다.
- 추천 이유: 남은 한계가 부하 생성기와 Gateway(다른 담당)라 P4d 효과가 클라이언트 수치로 보이지 않는다. 같은 시간을 선점 경로(K1-H)에 쓰는 편이 사례가 된다.

## 반영
- 측정 브랜치 `experiment/ISE-79-k6-steps`의 `reservation-service/k6/STEPS.md` "P4c 실측 (새 기기)"와 결정 문단.
- 계획 순서가 바뀐다: K1은 base → G1 → R1 → P4a → P4b → P4c로 마치고, P4d는 조건은 맞았지만 넣지 않은 단계로 남긴다.

## 검증
- P4c L: 좌석 조회·선점 100% 성공, 매진 전 좌석 조회 p95 6ms, PostgreSQL CPU 최대 약 0.2코어(`step-p4c-net-L-20261109-203716`).
- P4c S 확장: 1,280명에서 커넥션 대기 0, PostgreSQL 거의 0, k6 약 16~17코어, Gateway 차단기 즉시 거절 약 56,100건(`step-p4c-net-x1280-S-20261109-204441`, JFR 포함).
- `ScheduleSeatApiTest` 7건 통과(P4c 코드).
- P4 묶음 마지막 3회(측정 브랜치 `a6d59e3`): L 3회 모두 100%, 매진 전 좌석 조회 p95 6~7ms. S 확장 3회의 1,280명 좌석 조회 성공은 81.1%·15.5%·44.1%(중앙값 44.1%)로, 503 수가 회마다 Gateway 차단기 즉시 거절 수(약 13,000·59,900·38,700건)와 거의 같다.
- 정정: AI 제안의 "1,280명 성공 44.2% → 21.6%로 떨어졌다"는 P4b·P4c 각 1회(P4c는 JFR 회) 비교였다. 3회 범위 안이라 P4b와 차이를 말할 수 없어 "개선이 클라이언트 수치를 떨어뜨렸다"는 해석은 거둔다. 1,280명의 한계가 Gateway 차단기라는 판단과 결정은 그대로다.
- 정정 2(2026-11-10): k6 메모리 상한을 2.5GiB에서 6GiB로 올려 다시 재자(`step-p1-net-x1280-S-20261110-002047`, 측정 브랜치 `ff1aa79`) K1 S 1,280명이 좌석 조회·선점 100%, p95 32ms였고 Gateway 차단기는 한 번도 열리지 않았다. k6 CPU는 약 17코어 → 7.4코어. 결정의 전제였던 "남은 한계가 부하 생성기와 Gateway"는 k6 상한이 만든 것이었다. P4c는 1,280명(서버 좌석 조회 초당 약 1,280건)까지 버티므로 K1을 P4c에서 마친 결정 자체는 유지할 수 있지만, 근거는 "1,280명까지 병목이 없다"로 바뀐다. P4d를 다시 볼지는 판단자가 정한다.
- 정정 3(2026-11-10): F 3회(측정 브랜치 `9e9bcb8`)에서 K1 S 1,280명은 2회 100%, 1회 81.6%(Gateway 차단기 즉시 거절 약 12,900건)였고 p95는 32~33ms로 같았다. k6는 CPU 7.6~7.8코어, 메모리 약 4GiB로 여유가 있었다. 정정 2의 "차단기는 한 번도 열리지 않았다"는 1회 결과였다. k6가 충분해도 Gateway 차단기는 가끔 열리지만, 2.5GiB 때(15~81%)보다 훨씬 드물다. reservation-service는 1,280명에서도 5xx 0이다.

## 판단 이력
- 2026-11-09 수용: P4d 조건은 맞지만 남은 한계가 부하 생성기와 Gateway라 K1을 P4c에서 마치고 K1-H로 간다.

## 발표·면접 포인트
- 조건표만 보면 다음 단계(P4d)를 넣어야 했지만, 그 단계가 겨냥한 자원이 이미 한계가 아니었다. 병목이 서버 밖(부하 생성기, 다른 서비스)으로 나가면 서버 개선을 멈추고 측정의 한계를 기록했다.
- 측정 도구의 상한이 결과를 만든 사례다. 이전 기기에서 VM을 지키려 건 k6 메모리 상한이 새 기기에서는 k6를 GC로 멈추게 해 요청을 몰아 보냈고, 그것이 Gateway 차단기를 훨씬 자주 열어 "서버 밖 한계"를 실제보다 크게 보이게 했다. 부하 생성기의 CPU·메모리를 서버 지표와 같이 보지 않으면 병목을 잘못 짚는다.
- 1회 측정으로 "개선이 클라이언트 수치를 떨어뜨렸다"고 읽었다가, 3회를 재 보니 다른 서비스(Gateway 차단기)가 만드는 흔들림(15~81%) 안이었다. 한계가 서버 밖에 있으면 같은 조건에서도 결과가 크게 흔들리므로, 단계 비교는 반복 측정으로 범위를 봐야 한다.
