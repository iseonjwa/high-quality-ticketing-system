# 좌석 조회 경량화는 담당자(반효승)가 dev에 넣은 P4a를 살려 진행하고, 측정 브랜치 코드는 참고로만 둠

## 맥락
- 해결하려던 작업: ISE-79 K1 단계 측정에서 좌석 조회 경량화(P4a~P4c)를 측정 브랜치에 직접 구현해 쟀다. 그 사이 좌석 조회 담당(반효승, ISE-189)이 다른 방식으로 짠 P4a를 dev에 넣었다(`a40b01d`). 둘 중 어느 코드를 기준으로 이어 갈지 정해야 했다.
- AI 활용 방식: dev 코드와 측정 코드의 차이와 충돌을 분석하게 하고, 두 P4a를 local에서 같은 조건으로 재 성능 차이를 확인하게 했다.

## AI 제안
- 두 P4a는 엔티티를 만들지 않고 같은 15,000행을 읽는다는 점이 같다. 측정 브랜치는 네이티브 SQL로 선택 가능 여부를 DB에서 계산하고, dev는 JPQL 생성자 식으로 상태·등급을 받아 자바에서 판단한다.
- 같은 조건 L 3회 중앙값으로 dev가 좌석 조회 성공 -3.3%p, 서버 처리량 -6.3%다. S에서 버틴 단계는 같다. 측정 전에 정한 기준(5%p, 10%, 같은 단계) 안이므로 dev 코드를 채택해도 된다.
- 차이는 일관되지만 P4b부터는 좌석 배치를 캐시하므로 거의 사라질 것으로 본다. 측정 브랜치의 P4b·P4c는 dev의 `ScheduleSeatRow` 위에 다시 짜야 하며, 측정 코드와 결과를 ISE-204·205의 구현 근거로 넘길 수 있다.

## 판단
- 결과: 수용
- 판단자: 최권우
- 근거: 담당자가 효승인 만큼 효승의 작업 내용을 살리는 것이 맞다. 좌석 조회 쪽을 직접 구현한 것은, 효승이 아직 구현하지 못한 부분이 부하 테스트 영역에 들어 있었기 때문이다.
- 검토한 대안: 측정 브랜치 P4a(조금 더 빠름)를 기준으로 삼는 것. 담당 영역을 침범하게 되어 고르지 않았다.

## 반영
- 측정 브랜치 `experiment/ISE-79-k6-steps` STEPS.md "P4a 구현 대조 예상·실측"(`0993e7c`)
- [k6-seathold-story.md](../../design/reservation/k6-seathold-story.md) 10절
- P4b·P4c를 dev 코드 위에 다시 짜는 일은 ISE-204·205(반효승)에 남긴다. 측정 브랜치 코드는 머지하지 않고 참고로만 넘긴다(넘기는 방법은 미정).

## 검증
- local 대조 측정: 측정 브랜치 P4a L 82.4~83.1%·초당 169.2~170.5건, dev P4a L 78.5~80.3%·초당 157.1~159.0건. S는 둘 다 40명까지 100%. 대사 위반 0.

## 판단 이력
- 2026-11-10 수용: 담당자의 dev P4a를 살리고, 측정 브랜치 코드는 참고로만 둔다.

## 발표·면접 포인트
- 부하 테스트 범위에 아직 구현되지 않은 다른 담당 영역이 걸려 측정용으로 먼저 구현했지만, 본 구현은 담당자 코드를 살렸다. 같은 조건에서 두 구현을 재 미리 정한 기준 안인지 확인한 뒤 채택했다.
- 측정을 위해 대신 짠 코드와 담당자의 실제 코드가 다를 수 있다. 그래서 측정 결과를 담당자 코드로 다시 확인하는 단계를 넣었다.
