# 입장 토큰 소모 뒤 issued 정리를 AFTER_COMMIT 리스너 대신 트랜잭션 밖 메서드 호출로 바꾸는 데 동의함

## 맥락
- 해결하려던 작업: ISE-207(입장 토큰을 좌석 선점 성공 때 소모). 선점이 커밋된 뒤 대기열 Redis `issued`에서 그 사용자를 지워야 다시 줄을 설 수 있다.
- AI 활용 방식: ADR 0053 초안(AI와 함께 작성)이 정리 방법을 정했고, 이 세션에서는 대기열 담당이 "그 방식대로 하면 안 된다"고 한 이유를 코드로 분석했다.

## AI 제안
- ADR 0053 결정 3: 선점이 `SeatHeldEvent`를 발행하고 대기열이 `@TransactionalEventListener(AFTER_COMMIT)`로 받아 동기로 `ZREM`한다. 실패하면 로그를 남기고 거절할 때 한 번 더 지운다.
- 이 세션의 첫 분석은 동기 리스너의 비용을 "선점 응답이 대기열 Redis 시한(200ms)만큼 늦어질 수 있다"로만 봤고, DB 커넥션 점유는 짚지 못했다.

## 판단
- 결과: 거부(리스너 방식). 대신 선점 쪽이 트랜잭션이 끝난 뒤 `QueueService.discardEntryToken(scheduleId, userId, entryTokenJti)`를 부른다.
- 판단자: 대기열 담당 권영은 제안, KWON-WOO 동의(Linear ISE-207 11-13 댓글)
- 근거(대기열 담당): 동기 `AFTER_COMMIT` 리스너는 커밋 뒤 DB 커넥션을 반납하기 전에 실행돼, Redis 정리 동안 커넥션을 더 잡는다. 커넥션 대기 시한을 1초로 줄인 피크(ISE-196)에서 풀을 압박한다. 흐름이 선점 코드에 드러나고 거절 경로에서 부르기 쉽다.
- 검토한 대안: `TransactionSynchronization.afterCommit`에서 부르기(리스너와 같이 커넥션을 쥐어 제외).

## 반영
- 대기열: 11-13 PR 예정(메서드·테스트, SA 7-3, `docs/design/queue/contracts.md`). 메서드는 `issued`의 토큰이 넘겨받은 `jti`와 같을 때만 지운다.
- 좌석 선점: 미반영. 호출 위치·접수형 처리는 학습 노트 7절에 정리했다.
- ADR 0053 결정 3 수정: 이강민 담당과 조율 중.

구현 전.

## 판단 이력
- 2026-11-13 거부: 리스너 대신 트랜잭션 밖 메서드 호출로 바꾸는 대기열 담당 제안에 동의.

## 발표·면접 포인트
- `AFTER_COMMIT`은 "커밋 뒤"지만 "커넥션 반납 뒤"는 아니다. 커밋 후처리에서 외부 I/O를 하면 그 시간만큼 커넥션을 쥔다. 풀이 5개인 서비스에서는 Redis 지연이 DB 풀 고갈로 번진다.
- AI 초안과 AI 분석이 모두 놓친 점을 담당자가 프레임워크 동작으로 짚었고, 학습 노트에 Spring 커밋 순서를 근거로 확인해 남겼다.
