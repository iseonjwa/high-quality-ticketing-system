# 지표 비용은 시계열 수에서 나온다는 분석을 받아 ISE-277을 SLO 버킷 방식으로 ISE-17보다 먼저 처리함

## 맥락
- 해결하려던 작업: ISE-277(좌석 선점·공연 조회의 서버 쪽 지표 빈칸)은 담당이 정해지지 않았고, 이슈 작성자가 히스토그램 범위(reservation-service만 또는 전체)와 결과 카운터의 `outcome` 구분에 의견을 물었다. 같은 날 ISE-17(접수형 소비자)을 시작하려던 참이었다.
- AI 활용 방식: ISE-277을 하면 기존 대비 성능에 영향이 있는지 물었다.

## AI 제안
- 요청마다 드는 비용은 카운터·버킷 증가뿐이라 나노초 단위이고, 선점 요청(밀리초 단위)에 비해 무시할 수준이다.
- 비용은 시계열 수에서 나온다. `percentiles-histogram`은 태그 조합마다 버킷 약 70개, `slo` 버킷 몇 개는 조합마다 그 수만큼이다. 배포 서버에서 Prometheus가 앱과 같은 호스트에서 돌아 이 차이가 측정 중 자원에 닿는다.
- 그래서 `slo` 버킷 몇 개만, ID 없는 라벨로, 카운터는 기동 시 등록하는 방식을 권했다.

## 판단
- 결과: 수용
- 판단자: KWON-WOO
- 근거: "그럼 일단 ISE-277을 처리하고 ISE-17을 진행하자"(성능 영향 분석을 본 뒤)
- 검토한 대안: ISE-17 먼저, `percentiles-histogram` 전체 켜기
- 이어진 판단(같은 날): AI가 "이슈 작성자 답을 기다리는 동안 ISE-17을 시작하자"고 했으나, 사용자가 "답변을 기다릴 필요 없고 내가 결정하면 될 거 같아"라며 직접 정하기로 했다. AI가 항목별 추천(범위 reservation-service만, 버킷 8개, `outcome` 9개, 컨트롤러 응답 기준, 조회 Timer·알림 규칙 보류, 대시보드 4묶음)과 진행 순서(PR 뒤 배포 측정에서 값 확인 후 이슈 종료)를 내놓았고, 사용자가 "진행해줘"로 그대로 확정했다.

## 반영
- 브랜치 `chore/ISE-277-seathold-metrics`.
- 이슈 작성자의 두 질문에 대한 답
  - 히스토그램은 reservation-service에만, 버킷 8개(25ms~3s)로 켠다.
  - `outcome`은 이슈 제안 여섯 값에 `entry_token_used`(ISE-207의 403), `invalid`, `error`를 더해 아홉 값이다.
- 대시보드 패널은 선점, 회차 좌석 조회, 공연 목록·상세, 접수형 결과 폴링 네 묶음이다.
- 좌석 조회 전용 Timer와 알림 규칙은 하지 않았다. HTTP 히스토그램이 같은 값을 주고, 알림 기준은 측정 뒤에 정한다.
- 기준 문서: `docs/design/reservation/seathold-metrics.md`

## 검증
- `SeatHoldMetricsApiTest` 3건: 결과별 카운터 증가, 0부터 보이는 아홉 값, 대시보드가 읽는 다섯 API(선점 POST, 좌석·공연 목록·공연 상세·결과 폴링 GET)의 HTTP 타이머가 경로 템플릿 `uri` 라벨과 8개 버킷으로 기록됨.
- reservation-service 전체 테스트 474건 통과(패널 추가 전 기준).
- 배포 서버 측정에서 값이 나오는지는 미확인이다.

## 판단 이력
- 2026-11-13 수용: ISE-277을 SLO 버킷 방식으로 먼저 처리한다.
- 2026-11-13 수용: 이슈 작성자 답을 기다리지 않고 AI 추천안대로 확정한다. 공연 목록·상세와 접수형 결과 폴링 패널을 더한다. 이슈는 배포 측정에서 값이 나오는 것을 본 뒤 닫는다.

## 발표·면접 포인트
- 관측 비용은 요청 경로보다 시계열 수(카디널리티)에서 나온다. 히스토그램 버킷 수와 라벨 값의 종류를 정하는 것이 곧 비용을 정하는 일이다.
