# 배포 측정(ISE-296) 결과로 선점 동시 처리 상한은 켜지 않고 커넥션 풀은 5를 유지하자는 AI 추천을 받아들임

## 맥락
- 해결하려던 작업: ADR 0062는 선점 동시 처리 상한을 코드 기본값 끔으로 두고 "배포 단계 측정에서 값을 정해 켠다"고 했다. ADR 0064는 풀 5를 유지하되 "CPU 여유가 있는데 커넥션 대기가 주 병목이면 풀 8을 다시 본다"고 했다. 배포 서버 단계 측정(ISE-296) 1·2차가 끝나 두 후속을 정해야 했다.
- AI 활용 방식: 측정 지표를 근거로 풀을 유지할지 늘릴지 추천해 달라고 했고, 이어서 두 ADR 결정을 위한 상세 설명을 요청했다.

## AI 제안
- 배포 서버 Prometheus에서 커넥션 풀 지표를 단계 시각표대로 A0·K1-H 구간으로 나눠 다시 냈다(결과 문서 11절).
  - 상한 끔 + 풀 5(S1): A0 성공률 98.8%, 성공 처리량 521건/초, 커넥션 대기 최대 95(획득 최대 0.76초), 대기 시한 초과 0건.
  - 상한 4 + 풀 5(S2) 41.7%·323, 상한 7 + 풀 8(P8) 55.6%·361. 상한을 켜면 측정 구간 커넥션 대기는 풀 5·8 모두 0이었다. 그래서 2차의 처리량 증가는 풀이 아니라 상한 4 → 7에서 나왔다고 봤다.
- 상한은 풀보다 작아야 보호 장치가 된다(선점 하나가 커넥션 하나를 쥔다). 그래서 두 결정은 한 묶음이다.
- 배포 측정은 상한의 대가(A0 처리량 31~38% 손실)만 쟀다. 상한의 이득(과부하·잠금 장애 때 좌석 조회 보호, 로컬 L9에서 타임아웃 57~76% → 0%)이 나는 장면은 재지 못했다.
- 운영에는 다른 보호가 이미 있다: 게이트웨이 동시 처리 상한 64, 커넥션 대기 시한 1초와 503(ISE-196·ISE-293), 캐시 사전 거절.
- 선택지: A. 상한 끔 + 풀 5(추천), B. 상한 7 + 풀 8, C. 상한 4 + 풀 5. 추천은 A이고, 상한 코드는 비상 스위치로 남겨 켜는 조건과 값을 ADR에 적는다.

## 발표·면접 포인트
- 보호 장치(동시 처리 상한)를 로컬 측정으로 넣었지만, 배포 측정에서 대가만 보이고 이득이 나는 조건은 앞단 장치가 이미 막고 있어 기본값을 끔으로 두었다. 코드는 비상 스위치로 남기고 켜는 조건을 지표로 적었다.
- "처리량이 올랐다"를 풀 덕분으로 읽지 않고, 측정 구간 대기 0을 근거로 상한 값 차이에서 나온 것으로 갈랐다.
