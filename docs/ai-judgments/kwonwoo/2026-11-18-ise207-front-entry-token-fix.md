# 배포 환경 재선점 403의 원인 분석과 프런트 수정안(ISE-207)을 받아 프런트 담당 대신 직접 고치기로 함

## 맥락
- 해결하려던 작업: 배포 환경에서 "대기열 입장 → 좌석 선택 → 선점 → 결제 없이 5분 넘게 대기 → 좌석 다시 고르기 → 선점"이 오류로 끝났다. 프런트 담당(준현)이 토큰 한도로 작업할 수 없어 직접 처리하려 했다.
- AI 활용 방식: 로컬 전체 스택을 띄워 Playwright로 재현하고 원인과 고칠 곳을 정리하게 했다.

## AI 제안
- 원인: 선점 201에서 서버가 입장 토큰을 소모하는데(ADR 0053) 프런트가 토큰을 지우지 않는다. 재선점은 403 `ENTRY_TOKEN_USED`인데 프런트는 이 코드를 처리하지 않아 토큰이 남고, 대기열이 그 토큰을 보고 좌석 화면으로 되돌려 최대 10분 빠져나갈 수 없다. 결제 화면과 좌석 확보 대화상자 두 경로 모두 재현됐다.
- 수정안: 선점 201이면 보낸 토큰만 지운다, `ENTRY_TOKEN_USED`도 토큰을 지우고 대기열로 보낸다, [좌석 다시 고르기]를 [다시 줄 서기]로 바꾼다, 목 서버도 토큰 소모를 흉내 낸다.
- 열어 둔 쟁점: (1) 201 뒤 토큰을 지우면 좌석 확보 대화상자가 뜬 채 새로고침할 때 대기열로 간다. (2) 결제 토큰 만료 직후 옛 선점이 풀리기 전 10~15초 빈틈은 이번 범위 밖으로 두자고 권했다.

## 판단
- 결과: 수용
- 판단자: 최권우
- 근거: 미기재
- 검토한 대안: 프런트 담당에게 재현 절차만 넘기기(AI가 처음 권한 안). 담당이 작업할 수 없어 택하지 않았다.

## 반영
- "그냥 해"로 수정안 전체를 맡겼다. 쟁점 (1)은 AI가 저장한 선점의 결제 가능 시간이 남아 있으면 결제 화면으로 보내는 쪽으로 정했다. 쟁점 (2)는 고치지 않았다.
- 변경: `frontend/src/api/client.ts`(`consumesEntryToken`, `isEntryTokenRejected`), `pages/seats/*`, `pages/payment/PaymentPage.tsx`, `mocks/*`, `docs/design/frontend/README.md`, `design-system.md`, ADR 0053 후속.

## 검증
- Vitest 1,452건 중 1,447건 통과. 실패 5건 중 4건은 단독 실행에서 통과했고(전체 실행의 시간 초과), `MyPageLayout` 1건은 origin/dev에서도 실패하는 기존 실패다.
- lint·빌드·바꾼 파일 Prettier 통과. Playwright 시연 흐름(MSW) 3건 통과.
- 로컬 compose 스택(프런트 이미지만 이 변경으로 다시 빌드)에서 결제 가능 시간 1분 회차로 두 경로를 따라갔다. 좌석 확보 대화상자·결제 화면 모두 첫 선점 201 뒤 토큰이 지워졌고, [다시 줄 서기] → 대기열 → 새 토큰으로 좌석 화면 → 두 번째 선점 201이었다. 수정 전에는 같은 절차가 403 `ENTRY_TOKEN_USED`였다.

## 판단 이력
- 2026-11-18 수용: 원인 분석과 수정안을 받아 직접 구현하게 함

## 발표·면접 포인트
- 서버 계약(ADR 0053)이 바뀌었는데 목 서버가 그 동작을 흉내 내지 않아, 목 기반 테스트로는 버그가 보이지 않았다. 실제 스택 재현으로만 드러났다.
