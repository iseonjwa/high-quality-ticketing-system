# 대기열 입장 토큰을 토큰 API로 분리하고 READY 상태를 두며, 진입도 순번 조회와 같은 상태를 응답하게 했다

## 맥락
- 해결하려던 작업: ADR 0015(issued 키) 리뷰 반영 뒤, 대기열 진입(POST `/queue`)·순번 조회(GET `/queue/me`)의 역할과 응답을 구현 전에 정리하고 있었다.
- AI 활용 방식: 진입과 순번 조회를 나누는 이유, 진입 시 `issued`가 있으면 무엇을 응답할지, 토큰 API를 따로 둘지, `READY`가 필요한지, 진입이 상태를 줄지를 차례로 물었다. 각 안을 "백엔드 코드가 깔끔한 쪽", "대용량 트래픽 부하 분산 관점"으로 비교해 달라고 했다.

## AI 제안
- 진입·순번 조회를 나누는 이유로 "폴링이 실수로 줄을 세우면 안 됨, 부하 측정·제한 분리, GET은 상태를 안 바꿈"을 들었다. 사용자가 토큰 API 분리를 제안하자, 현재 SA의 순번 조회 GET이 차례가 되면 `waiting`·`issued`에 쓰기를 하는 점을 짚으며 분리가 더 깔끔하다고 평가했다. 비용은 SA 계약 변경이라 구현 전에 ADR(제안)로 올리라고 했다.
- `READY`(토큰을 받을 수 있음)를 두자고 추천했다. `READY` 없이 `WAITING` + `position: 0`이면 이미 토큰을 받은 사람도 `WAITING`이라 부르게 되고, 토큰 없는 `ADMITTED`를 쓰면 같은 상태가 API마다 모양이 다르다고 했다.
- 진입 응답: 처음에는 진입이 상태만(토큰 없이 `ADMITTED`) 주라고 추천했다가, SA 11-5 응답 예시를 확인한 뒤 SA 모양을 따르는 쪽으로 바꿨다. 백엔드만 보면 "진입은 줄 세우기만"이 가장 깔끔하지만, 부하 관점에서는 진입이 순번과 `nextPollAfterSeconds`까지 주는 쪽이 낫다고 했다(진입 직후 폴링이 일제히 따라오면 오픈 순간 요청이 두 배가 되고, 첫 폴링 시각을 서버가 정할 수 없음).
- 순번 조회는 읽기 전용으로 두라고 했다. 정리 쓰기를 넣어도 HTTP상 문제는 없지만, 나중에 폴링을 Redis 복제본으로 나누려면 쓰기가 없어야 한다고 했다.
- Lua는 Redis 값을 원자적으로 읽고 쓴 결과만 돌려주고, 상태 판단·순번 계산은 앱의 도메인 메서드 한 곳에서 하라고 했다.
- `jti`는 회차·사용자·발급 시각으로 계산해 넣으라고 했다. 되돌리기 쉬운 결정이라 가장 후회가 적은 안이라고 했다.
- 폴링 간격에 jitter를 섞고, 적용 전후를 부하 테스트로 비교하라고 했다.

## 판단
- 결과: 부분 수용
- 판단자: youngeun
- 근거:
  - 토큰 API 분리는 사용자가 먼저 제안했다("폴링 api 말고 입장 토큰 api를 따로 만들면 어때?").
  - `READY`: 사용자는 "READY가 없으면 입장 순서가 되었는지 확인하는 로직이 추가적으로 필요하니까 별로인가?"라고 물은 뒤 READY를 넣은 흐름으로 정리를 요청했다.
  - 진입 응답: 사용자가 "토큰 발급은 POST → GET을 거쳐 토큰 API까지 가야 하는데 순번 확인은 POST에서도 바로 가능하다는 게 이상하지 않나", "POST에서도 seq<=admitted를 계산하는데 position 계산은 GET만 할 수 있으니까 이상하지 않아?"라고 지적해, 진입이 상태 일부만 주는 중간 안은 버렸다. 백엔드·부하 관점 비교를 들은 뒤 진입이 순번 조회와 같은 상태를 주는 안으로 정리를 요청했다.
  - `jti`: "계산해서 일단 넣어놓을게".
  - 순번 조회 읽기 전용, Lua·앱 역할 나누기, jitter: 미기재 (설명을 듣고 이어서 진행).
- 검토한 대안: 순번 조회가 토큰 발급(SA 현재), 진입은 줄 세우기만(201 + Location, 중복 409), 진입은 위치만(`WAITING`/`READY`), `READY` 없이 `position: 0`, 진입 `ADMITTED`에 토큰 없음/있음, 순번 조회에서도 정리, `jti` 제거·무작위

## 발표·면접 포인트
- 폴링 GET이 차례가 된 순간 Redis에 쓰기를 하는 구조를 찾아, 토큰 발급을 별도 API로 떼어 폴링을 읽기 전용으로 만들었다. 가장 많이 불리는 API를 복제본으로 분산할 길을 남겼다.
- 진입 응답에 상태를 줄지를 "코드 깔끔함"과 "부하 분산" 두 기준으로 비교했다. 줄 세우기만 하는 쪽이 코드는 깔끔하지만 오픈 순간 요청이 두 배가 돼서, 진입부터 다음 폴링 시각을 서버가 정하는 쪽을 골랐다.
