# Q1-d 로컬 확인에서 출발 대기를 다시 계산하는 방식으로 고치고, Q1 ↔ Q1-d 수치 비교는 배포 서버로 넘겼다

## 맥락
- 해결하려던 작업: ISE-217에서 새로 만든 오픈 순간 몰림 시나리오 `loadtest/k6/scenarios/q1d-queue-burst.js`를 로컬(노트북 한 대, compose.yml + compose.local.yml)에서 작게 돌려 동작을 확인하고, Q1과 같은 조건으로 비교하려 했다.
- AI 활용 방식: Claude Code에 실행, 결과 해석, 실패 원인 조사를 맡겼다. 고칠 파일이 생기면 이유를 먼저 듣고 확인하기로 했다.

## AI 제안
Q1-d를 300명 / 0.1초, 300명 / 0.1초(Gateway 데운 뒤), 300명 / 1초로 돌렸고 세 번 모두 503 `SERVICE_UNAVAILABLE`이 68~93% 나왔다. AI가 확인한 원인은 두 가지다.

1. Gateway 인증 Redis 차단기(`auth-redis`)가 열렸다. 차단기 직전 20번의 블랙리스트 확인이 모두 50ms를 넘었고(느린 호출 비율 100%), 그 뒤 요청은 3ms 만에 거절됐다. Redis 자체 지연은 평균 0.15ms라 느려진 곳은 Gateway 안쪽이다. 같은 현상이 TS-42에 노트북 환경 영향으로 기록돼 있다. Q1 명세(`open-peak-scenarios.md`)는 한도 안에서 이 차단기가 열리지 않는 것을 합격 조건으로 둔다. 따라서 이 노트북의 한도는 순간 초당 600명보다 낮다.
2. send_lag가 모든 VU에서 똑같이 약 109ms였다. 서버 요청 없이 k6 `sleep`만 재는 탐침에서 5초 대기는 2ms 안, 40초 대기는 VU 1개여도 약 100ms 늦게 깼다. sleep이 쓰는 단조 시계와 출발 시각을 정하는 벽시계(Date.now)가 Docker Desktop에서 어긋나는 것으로 봤다. 몰림의 모양은 유지되지만 send_lag 판정이 매번 거짓으로 실패한다.

제안은 다음 셋이었다.
- 1번: 대기를 "목표 1초 전까지 자고 깨어나 남은 시간을 다시 계산해 짧게 더 잔다"로 바꾼다.
- 2번: 로컬에서는 차단기가 열리지 않는 약한 조건(100명 / 1초)으로 정상 경로만 확인하고, Q1 ↔ Q1-d 1,000명·5,000명 비교는 배포 서버 측정으로 넘긴다.
- 3번: Q1-c 연타 확인도 같은 이유로 낮은 조건에서 본다.

## 판단
- 결과: 수용
- 판단자: youngeun
- 근거: 미기재("응"으로 1번 수정 후 2·3번 진행을 승인)
- 검토한 대안: 계획대로 Q1 ↔ Q1-d 1,000명 / 1초 비교로 바로 넘어가기. 사용자가 "300명도 안 되는데 1000명을 어떻게 돌려?"라고 되물어 보류됐다. 측정용으로 차단기 기준을 완화하는 덮어쓰기는 Gateway 담당과 이야기할 문제라 고르지 않았다.

## 반영
- `loadtest/k6/scenarios/q1d-queue-burst.js`: `sleepUntil` 추가. 긴 대기 뒤 남은 시간을 다시 계산한다.
- Q1 ↔ Q1-d 수치 비교: 배포 서버 측정으로 넘김(미반영).

## 검증
- 탐침(40초 대기, VU 300): 수정 전 늦게 깬 시간 약 97ms, 수정 후 최대 2ms.
- Q1-d 100명 / 1초(회차 5): 판정 기준 4개 통과, 201 100건, send_lag p95 1.7ms, Redis seq / waiting 100 / 100.
- Q1-c 300명, DUP_RATIO 0.1, 초당 30명(회차 6): 판정 기준 통과, 첫 요청 201 301건, 연타 200 46건, Redis seq / waiting 301 / 301. k6가 반복을 301번 시작해 고유 사용자가 301명이었다. teardown이 안내하는 기대값(USERS=300)과 1 차이가 난다.
- 실패한 세 번도 Redis seq와 waiting은 201 수와 같았다. 진입한 사용자의 순번은 부하 중에도 빠짐·중복이 없었다.

## 판단 이력
- 2026-11-09 보류: 300명이 실패한 상태에서 1,000명 비교로 넘어가자는 권장에 의문 제기
- 2026-11-09 수용: 대기 방식 수정, 로컬은 동작 확인만, 수치 비교는 배포 서버

## 발표·면접 포인트
- 부하 발생기도 측정 대상이다. send_lag가 모든 사용자에게 똑같이 늦으면 CPU 부족이 아니라 시계 문제일 수 있고, 서버 없이 발생기만 재는 탐침으로 갈랐다.
- 같은 503도 출처가 다르다. 차단기 지표로 대기열 서버가 아니라 Gateway 인증 단계에서 거절됐음을 확인했고, 노트북 결과를 서버 한계로 읽지 않았다.
