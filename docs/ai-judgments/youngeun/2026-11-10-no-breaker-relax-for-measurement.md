# 배포 Q1에서 auth-redis 차단기가 열리자 측정용으로 차단기 기준을 완화하는 안은 거부하고, 워밍업 뒤 다시 재는 안을 골랐다

## 맥락
- 해결하려던 작업: ISE-202 배포 서버 부하 측정 1단계(Q1 대기열 진입). 측정 모드 전환으로 서비스가 다시 뜬 직후 Q1 초당 3,000명(B1)과 사이 값 초당 300명(B0m)을 쟀다(측정 2026-11-09 UTC).
- AI 활용 방식: Claude Code에 발생기 tmux에서 k6 실행, Prometheus 차단기 지표·Redis 순번 확인, 멈춤 기준 판정과 다음 방향 제안을 맡겼다. 측정 모드 켜고 끄기와 키 옮기기는 사용자가 했다.

## AI 제안
B1·B0m 모두 Gateway `auth-redis` 차단기가 열려 진입 대부분이 503이었다. 차단기 직전 호출이 50ms를 넘는 느린 호출이었고 Redis 서버 지연은 1ms 안이었다. AI는 세 가지 길을 냈다.

1. 워밍업(초당 100명 5분) 뒤 같은 초당 300명을 다시 재서, 재기동 직후 식은 Gateway 탓인지 가린다.
2. Gateway 담당에게 contract 이슈로 알린다.
3. 측정용 덮어쓰기로 차단기 기준(느린 호출 기준, 최소 호출 수)을 완화해 대기열 서버 자체의 한도를 잰다.

## 판단
- 결과: 거부(3번). 1번은 순서를 바꿔 수용, 2번은 문구만 만들고 올리기는 보류
- 판단자: youngeun
- 근거: Gateway 설정은 다른 담당의 영역이고, 기준을 풀어서 재면 실제 운영에서는 생기지 않을 숫자가 나온다. 지금 설정 그대로 한계를 기록하고 Gateway 담당에게 넘기는 게 맞다고 봤다. 지시 원문 "1번으로 하되 순서를 이렇게 해줘 … 그다음 2번 contract 이슈 문구도 만들어줘 … 3번은 하지 마." 뒤이어 "이슈는 아직 올리지 말고 측정을 더 하자."
- 검토한 대안: 1번의 순서를 사용자가 정했다. 워밍업 결과는 판정에 쓰지 않고, 워밍업 직후 초당 300명이 안 열리면 식은 서버 탓으로 보고 멈추고, 또 열리면 100·200명으로 경계를 좁힌다.

## 반영
- 측정 순서: 워밍업 → 초당 300명(R300) → 데운 상태로 B 이어서(초당 3,000명 실패, 사이 값 1,000명 통과).
- contract 이슈 문구: 저장소 밖 결과 폴더에 초안으로 둠(미게시).
- 차단기 기준은 측정 내내 운영 설정 그대로 두었다.

## 검증
- R300(워밍업 뒤 초당 300명): 오류 0, p95 5.51ms, 느린 호출 0. 같은 조건의 B0m(식은 상태)은 차단기가 열렸다. 식은 Gateway가 원인일 가능성으로 둔다(비교 1회).
- 데운 상태 Q1 한도는 초당 1,000명 통과, 3,000명 실패 사이다. 이후 bulkhead 비교(25·100)에서도 1,000명 통과, 2,000명 실패로 같았다.
- 결과 표: 저장소 밖 `loadtest-results-2026-11-09/summary.md`.

## 판단 이력
- 2026-11-09 선택: 1번(순서 지정) 수용, 2번 문구 작성, 3번 거부
- 2026-11-09 보류: contract 이슈 게시는 B 결과를 더 본 뒤로

## 발표·면접 포인트
- 보호 장치가 측정을 막을 때 기준을 풀어 숫자를 얻는 대신, 운영 설정 그대로 "언제 왜 열리는가"를 재서 한도로 삼았다. 열리는 조건 자체가 운영에서 사용자가 겪을 한도이기 때문이다.
- 재기동 직후와 워밍업 뒤를 나눠 재서, 같은 503이 식은 서버 때문인지 처리량 한계 때문인지 갈랐다.
