# 식은 Gateway 측정 결과 문서에서 "제한시간 1s 실패" 대신 "100ms 시한 초과가 1.0s로 기록됐을 가능성"으로 고쳐 쓰자는 AI 정정을 받아들임

## 맥락
- 해결하려던 작업: ISE-202·ISE-229. Gateway를 다시 띄운 직후 Q1 첫 몰림이 `auth-redis` 차단기에 막히는 원인을 찾았다. 느린 호출 기준을 100ms·101ms로 올려 예열 없이 초당 300명을 쟀고(측정 2026-11-10 UTC), Redis `CLIENT LIST`로 연결 시점(측정 A)과 JVM 지표(JIT·GC·CPU)를 확인했다.
- AI 활용 방식: Claude Code에 측정 실행, 지표 조회, 결과를 `open-peak-scenarios.md` 3절 "배포 서버 2차"로 옮기는 초안을 맡겼다. 사용자가 넣으라고 한 추정 원인은 "식은 JVM의 JIT와 CPU 경합 → 응답 지연 → 제한시간 1s 실패 → 차단기 열림", 후속은 "ISE-230(차단기 설정 변경 후 재측정)"이었다.

## AI 제안
초안을 쓰기 전에 두 군데를 요청과 다르게 쓰겠다고 했다.
1. 실패 호출 최대 1.0s를 "제한시간 1s 실패"로 쓰지 않는다. 같은 날 dev에 들어간 #463(017ae9d6)의 설명은 "안쪽 100ms 시한을 전용 예외로 바꿔, 같은 TimeoutException이 차단기에 1,000ms 실패로 한 번 더 기록되던 것을 없앴다"이다. 측정한 코드(`f06c7d08`)에는 이 변경이 없고 같은 구간 Lettuce 명령 최대가 120.9ms다. 그래서 1.0s는 실제 걸린 시간이 아니라 Redis 확인의 100ms 시한 초과가 1,000ms로 기록된 값일 가능성이 크다. 원인 사슬도 "응답 지연 → 100ms 시한 초과 실패(기록상 1.0s) → 차단기 열림"으로 쓰고, 직접 재현하지 않았으니 "확인 안 됨"으로 둔다.
2. ISE-230의 실제 내용은 "auth-redis 차단기의 실패 원인 기록과 bulkhead 끄는 설정 확인"(강민)이라 후속을 "원인 기록(dev #463) 배포 뒤 재측정"으로 쓴다.

## 검증
- 100ms 초당 300명: 실패 34건으로 열림, 느린 호출 최대 3, 실패 호출 최대 1.0s. 101ms(측정 A): 실패 21건으로 열림, 느린 호출 최대 2, 실패 호출 최대 1.0s. 50ms(11/9 B0m)는 느린 호출 12로 열림.
- 측정 A: Gateway의 Redis 연결은 기동 때 생긴 하나뿐이고 몰림 중 새 연결이 없었다. 연결 맺기는 원인 후보에서 뺐다.
- JVM: 식은 실행의 몰림 중 JIT 6.1·9.0s(데운 실행 0.34s), Gateway CPU 최대 45%, GC 최대 61ms.
- 1.0s가 100ms 시한 초과의 기록값인지는 확인 안 됨. #463 배포 뒤 실패 종류 지표로 확인한다(ISE-230).

## 발표·면접 포인트
- 지표 값(실패 1.0s)을 그대로 원인으로 읽지 않고, 그 값을 만드는 기록 방식(바깥 TimeLimiter가 안쪽 시한 초과를 다시 기록)을 먼저 의심했다. 측정 도구가 보여 주는 숫자도 검증 대상이다.
- 느린 호출 기준만 올리면 차단기는 느린 호출 대신 실패로 열렸다. 기준값 조정은 원인을 없애지 않고 열리는 이유만 바꿨다.
