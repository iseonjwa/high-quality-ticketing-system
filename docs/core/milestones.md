## M1. 공통 모듈 + 인증 기반 (10/27–10/29)

모든 팀원이 같은 기반 위에서 각자 서비스를 바로 시작할 수 있게 공통 모듈과 인증을 먼저 만든다.

진행 방식:
1. 10/27 계약 합의: 인증 헤더, 공통 응답·에러 형식, 이벤트 공통 필드, 패키지 구조
2. 합의한 계약을 기준으로 공통 모듈을 각자 만들어 본다
3. 서로의 구현을 비교해 장점을 뽑아 하나의 브랜치로 합친다
4. 합친 브랜치 위에 인증을 올리고 main에 반영한다. 이후 모든 서비스 브랜치는 여기서 딴다

| 구분 | 내용 |
|---|---|
| 공통 모듈 | 4계층 패키지 구조, 공통 응답·에러 형식(`common` 모듈의 `response`·`web` 패키지), 전역 예외 처리, 이벤트 공통 필드 |
| 인증 | 회원가입·로그인·토큰 재발급·로그아웃(블랙리스트), 내 정보 조회, 운영자 계정 시드 |
| Gateway | 라우팅, JWT 검증 후 `X-User-Id`·`X-User-Role` 전달, Eureka |
| Config 서버 | `config-server`(포트 8888, native 백엔드)와 `config-repo/`(공통·서비스·프로필별 설정), 서비스는 `spring.config.import`로 연결 (SA 9-6, 결정 기록 #30) |
| 실행 환경 | docker-compose(PostgreSQL·Redis·Kafka·Prometheus·Grafana·Zipkin), `.env.example` |

응답 형식은 결정 기록 #19로 정했다(성공·실패 다른 형태, 둘 다 `traceId`, SA 11-2). Config 서버는 #30으로 10/27 통합 회의에서 결정했다.

완료 기준:
- 통합 브랜치가 main에 머지되어 있다
- `docker compose up` 한 번으로 인프라와 Config 서버·Gateway·Eureka·User 서비스가 뜨고, 서비스가 Config 서버의 설정을 읽는다
- 회원가입 → 로그인 → Gateway를 거친 인증 요청에서 `X-User-Id`·`X-User-Role`이 서비스까지 전달된다
- 새 서비스가 공통 모듈을 의존성으로 가져다 쓰면 응답·에러 형식이 그대로 적용된다
- Prometheus·Zipkin에서 Gateway·User 서비스 지표와 트레이스가 보인다(걷는 뼈대)

담당은 다 같이다. 공통 모듈은 전원이 각자 만들고, 인증·Gateway·실행 환경은 이슈를 가져간 사람이 작업한다.

## M2. 일반 예매 한 흐름 연결 (10/30–11/3)

서비스마다 최소 기능만 만들고 입장 → 선점 → 결제 → 확정을 API 호출로 끝까지 연결한다(수직 슬라이스, 결정 기록 #6).

| 담당 | 영역 | 내용 |
|---|---|---|
| 반효승 | 공연·좌석 → 예매 흐름 | 공연·회차·좌석 등록·조회를 먼저 만든다(선점 테스트에 필요). 이어서 예매 상태, 결제 토큰 발급, 결제 결과 소비 → 확정·발권 |
| 최권우 | 좌석 선점 | 동기형 일괄 선점, 중복 판매 방지, 멱등키 |
| 권영은 | 대기열 | 진입·순번·입장 토큰 발급, Gateway 입장 토큰 검증 필터 |
| 안준현 | 결제 (Mock PG 포함) | 결제 승인(동기), 서버 금액 검증, Outbox·처리 이력 공통 모듈, `payment.result` 발행, Mock PG 승인·조회 API |
| 이강민 | User·공통 → 추첨 설계 | User 계층 정리(ISE-47), 추첨 방향 결정과 상세 설계 시작(ISE-49, 11/6까지) |

연동 순서는 공연·좌석 데이터 → 좌석 선점 → 예매 흐름 ↔ 결제이고, 대기열은 병렬로 진행한다.

완료 기준:
- 로그인 → 대기열 → 입장 토큰 → 좌석 선점 → 결제 → `payment.result` → 예매 확정·발권이 API 호출로 끝까지 돈다
- 동기형 선점 기준선을 한 번 측정해 기록한다

## M3. MVP 완성·배포 (11/4–11/6)

연결한 흐름에 실패 경로(거절·만료·PG 장애)를 붙이고, 배포 1회와 MVP 시연을 마친다.

| 구분 | 내용 |
|---|---|
| 보상·장애 처리 | 결제 거절 시 좌석 반환, 선점 만료 스케줄러, 타임아웃·Circuit Breaker, UNKNOWN → PG 조회, 만료 뒤 승인 자동 환불, 재확인 스케줄러 |
| Mock PG | 장애 주입(지연·거절·승인 후 응답 유실), 환불 |
| 측정 | Synthetic Data 1차본 |
| 배포 | EC2 + compose 1회, 보안그룹·SSH 터널 |
| 시연 | API 호출(HTTP 요청 파일·Swagger) + Grafana·Zipkin 화면 |

완료 기준:
- Mock PG 장애 주입으로 거절·타임아웃·만료 뒤 승인 환불이 재현되고, 좌석·결제 상태가 서로 맞는다
- EC2에 한 번 배포해 시연 흐름이 돈다
- 11/6 MVP 시연을 마친다

Mock PG 장애 주입과 환불은 결제 담당이 맡는다. 이강민은 이 기간에 추첨 설계(ISE-49)를 마치고 M4 구현 이슈를 나눈다(10/28 역할 변경, SA 6-7).

## M4. 고도화 (11/9–11/16)

MVP 위에 Should 항목을 얹고, 측정·장애 주입 결과를 발표 소재로 남긴다. Notion의 트러블 슈팅 일정(11/9–11/16)과 함께 간다.

| 담당 | 내용 |
|---|---|
| 최권우 | 접수형(Kafka 접수) 선점, 동기형 대비 재측정 |
| 권영은 | 대기열 고도화(이탈 판정·대기 취소), 부하 테스트·Synthetic Data 주관, 입장 속도 역산 |
| 반효승 | 예매 취소, 공연·좌석 캐싱 |
| 안준현 | 취소 환불, 토스 테스트 모드 어댑터, 최소 화면, 내부 AI 상담(Could) |
| 이강민 | 추첨 배분 + 빌링키 자동결제(안준현과 함께) |

완료 기준:
- 동기형과 접수형의 비교 수치가 나온다
- 추첨 응모 → 추첨 → 자동결제 → 발권이 한 번 돈다
- 장애 주입·대사 결과와 트러블슈팅 사례를 발표 자료로 옮길 수 있게 정리한다
