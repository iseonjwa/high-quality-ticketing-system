# 0005. 인증 Redis 장애 시 우선 요청 차단

- 상태: 제안 (잠정 구현, 팀 논의 필요)
- 날짜: 2026-10-26
- 결정자: Junhyun An (잠정 정책 지정)
- 관련 AI 판단: [인증 Redis 우선 차단과 팀 논의](../ai-judgments/junhyun/2026-10-26-auth-redis-fail-closed.md)

## 맥락

SA 9-5의 블랙리스트 조회 장애 시 허용 정책은 합의 전 제안이었다. 사용자는 "지금은 요청 차단으로 하는데, 팀원과 논의해볼 내용이긴하다!"라고 지시했다.

## 결정

Gateway는 Redis 블랙리스트 조회를 100ms로 제한하고 실패·타임아웃·서킷 OPEN이면 보호 API에 503과 Retry-After를 반환한다. 잘못된 JWT의 401, 역할 부족의 403과 구분한다. Redis 장애 동안 서명만 맞는 Access를 허용하지 않는다.

로그인·Refresh·로그아웃의 Redis 저장 실패도 성공으로 반환하지 않는다. Redis 명령 타임아웃은 서버 측 미실행을 보장하지 않으므로 503 뒤의 토큰 상태를 이전 상태 그대로라고 가정하지 않는다.

## 검토한 대안

- 장애 시 허용: SA의 이전 제안이다. 가용성을 유지하지만 로그아웃된 토큰도 남은 시간 동안 통할 수 있다.
- 장애 시 차단: 사용자가 우선 적용하도록 지정했다. Redis 장애가 보호 API의 가용성에 영향을 준다.

## 결과

관찰(2026-10-27, 미해결): Gateway를 새로 기동한 직후 첫 요청이 Redis 연결 수립 때문에 100ms를 넘어 503이 난 적이 있다. 재시도하면 정상이었다. fail-closed와 짧은 타임아웃의 부작용이라 기동 시 Redis 연결을 미리 맺어 두는 방법(준비 상태 전 PING)을 검토해야 한다.

실제 Redis pause로 503과 복구 뒤 새 로그인·인증을 검증한다. 팀이 최종 정책을 합의하면 이 ADR의 상태와 SA를 함께 갱신한다. 팀 전체 채택으로 기록하지 않는다.
