# 0007. 로그인 5회 실패 잠금과 관리자 비밀번호 초기화

- 상태: 제안 (사용자 지시 + AI 구현 선택, 팀 확인 필요)
- 날짜: 2026-10-27
- 결정자: Junhyun An (요구), 구현 방식은 AI 선택을 수용
- 관련 AI 판단: [코드 리뷰 후속 수정 방향 선택](../ai-judgments/junhyun/2026-10-27-review-followup.md)

## 맥락

AI 리뷰가 로그인 응답 시간으로 계정 존재를 알 수 있고 시도 횟수 제한이 없다고 지적했다. 사용자는 로그인 5회 제한, 성공 시 횟수 초기화, 관리자의 비밀번호 초기화를 제대로 구현하라고 지시했다.

## 결정

- 연속 5회 실패하면 계정을 잠근다(`auth.max-login-failures`). 잠긴 계정은 올바른 비밀번호도 거절하고 423을 반환한다. 로그인에 성공하면 횟수를 0으로 되돌린다.
- 실패 횟수와 잠금은 PostgreSQL `users`에 UPDATE 한 문장으로 기록한다. 동시 시도에도 정확하고 Redis를 잃어도 잠금이 풀리지 않는다.
- 잠금은 운영자의 비밀번호 초기화로만 푼다. 초기화는 임시 비밀번호를 만들어 한 번만 응답하고, 실패 횟수·잠금을 풀고 Refresh를 폐기하며 변경 필요 표시를 켠다.
- 임시 비밀번호로는 토큰을 발급하지 않는다. 공개 엔드포인트 `POST /api/v1/auth/password-change`에서 현재(임시) 비밀번호로 새 비밀번호를 정한 뒤 로그인한다. 토큰을 주지 않으므로 "변경 전까지 다른 API 사용 금지"를 따로 강제할 필요가 없다.
- 존재하지 않는 이메일도 BCrypt 비교를 해서 응답 시간으로 계정 존재를 알기 어렵게 한다.

## 검토한 대안

- Redis 카운터와 시간 경과 자동 해제: 구현이 단순하지만 Redis 장애·초기화로 잠금이 사라지고, 사용자가 요구한 "관리자 초기화"와 맞지 않는다.
- 임시 비밀번호로 로그인 후 토큰에 변경 필요 클레임을 넣고 Gateway에서 제한: 토큰 계약과 Gateway 규칙이 늘어난다.
- 관리자가 새 비밀번호를 직접 지정: 운영자가 사용자 비밀번호를 알게 된다.

## 결과

계정 기준 잠금이라 남의 이메일로 5회 실패시켜 계정을 잠글 수 있고(IP 기준 제한 없음) 잠금 여부가 응답으로 드러난다. 운영자 계정이 잠기면 다른 운영자가 초기화하거나 재기동 시 시드 운영자 잠금만 풀린다. 이 한계는 [ADR 0008](0008-internal-trust-and-auth-design.md)의 D6에서 다룬다. 이미 발급한 Access는 만료까지 유효하다.
