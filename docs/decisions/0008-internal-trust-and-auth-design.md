- 선행: [ADR 0005](0005-auth-redis-fail-closed.md), [ADR 0006](0006-gateway-single-access-policy.md), [ADR 0007](0007-login-lockout-admin-reset.md)

## 맥락

ADR 0006으로 경로별 인증 판정을 Gateway 한 곳에 모으면서 서비스 단독 방어가 약해졌다. 지금 서비스는 Gateway가 넣어 준 `X-User-Id`·`X-User-Role`을 그대로 믿는다. 이 헤더는 서명이 없어서 Gateway를 거치지 않고 서비스에 닿는 요청이 임의 사용자·ADMIN으로 행세할 수 있다.

SA MASTER v3.1의 현재 설계는 같은 모델이다. 7-2는 "Gateway가 JWT 검증 → 헤더 전달, 인증이 서비스 호출 없이 끝남"이고, 9-2는 차단 계층을 "보안그룹 → Gateway → 서비스(권한, 도메인 규칙) → DB"로 정한다. 7-3은 HMAC이 검증자도 서명할 수 있다는 한계를 인정하고 비대칭 서명은 MVP 이후로 미뤘다. 따라서 이 설계가 확정되면 SA 7장·9장 변경을 팀에 제안해야 한다.

## 위협 모델

| # | 위협 | 현재 상태 | 영향 |
|---|---|---|---|
| T1 | 내부망·SSRF·설정 실수로 서비스에 직접 도달한 요청이 헤더를 위조 | 서명 없음. 보호는 네트워크 격리뿐이다(Compose 비공개 포트, 보안그룹) | 임의 사용자·ADMIN 행세, 관리자 API 호출 |
| T2 | JVM 모드·로컬 포트처럼 격리가 약한 환경 | 서비스 포트를 loopback에 여는 개발용 구성이 있다 | 같은 기기의 다른 프로세스가 위조 |
| T3 | 대칭 서명(HS256): 검증 키로 서명도 가능 | Gateway가 Access 키를 가진다 | Gateway 침해 시 모든 사용자 토큰 위조 |
| T4 | Redis 무인증: 블랙리스트·Refresh 해시·대기열이 같은 Redis | 인증 없음, 내부망 의존 | 블랙리스트 삭제로 로그아웃 우회, 대기열 조작 |
| T5 | Kafka·서비스 간 호출에 신원이 없음 | 이벤트 payload의 userId를 그대로 믿는다 | 이벤트 위조로 결제·예매 조작 |
| T6 | Access가 비밀번호 초기화·잠금·역할 변경 뒤에도 만료까지 유효 | 30분 | 탈취된 토큰이 최대 30분 유효 |
| T7 | 계정 기준 잠금 | 남의 이메일로 5회 실패시켜 잠금 가능 | 서비스 거부, 운영자 잠금 |

## 결정할 것

- D1. 서비스가 사용자 신원을 어떻게 믿을지 (T1·T2)
- D2. 서명 방식과 키 배포 (T3)
- D3. 적용 범위: 사용자 Access만 / 입장·결제 토큰까지 (SA 7-3과 맞물림)
- D4. 폐기(블랙리스트) 확인을 어느 계층에서 할지 (T6)
- D5. Redis·Kafka·DB 접속 인증 (T4·T5)
- D6. 계정 잠금 남용 방어 (T7)

## D1 선택지

| | A. 네트워크만 신뢰 (현재) | B. Gateway가 서명한 내부 신원 | C. 서비스가 사용자 JWT를 직접 검증 |
|---|---|---|---|
| 방식 | 헤더를 믿는다 | Gateway가 짧은 내부 토큰을 붙이고 서비스가 검증 | `Authorization`을 서비스까지 전달하고 서비스가 서명·exp·aud 검증 후 속성 생성 |
| T1·T2 방어 | 없음 | 있음 (내부 키를 모르면 위조 불가) | 있음 (사용자 토큰 서명으로 위조 불가) |
| Gateway 침해 | 전부 위조 | 내부 키로 전부 위조 | 비대칭 서명이면 위조 불가 |
| 요청당 추가 비용 | 없음 | Gateway 서명 + 서비스 검증 | 서비스 검증(RS256 검증은 마이크로초대) |
| 구현량 | 없음 | 내부 키 관리와 토큰 형식이 더 생김 | 이미 있는 `TokenDecoders`를 서비스에서 재사용. 헤더 신뢰 코드 제거 |
| SA 변경 | 없음 | 7-2 변경 | 7-2 변경, "서비스 호출 없이 인증" 문구는 유지(검증이 로컬) |

## D2 선택지

- HS256 유지: 키 하나로 단순하지만 검증하는 모든 서비스가 서명도 할 수 있다. C와 같이 쓰면 서비스 수만큼 위조 지점이 늘어 C의 이점이 사라진다.
- RS256 비대칭: 발급자(User)만 개인키를 갖고 Gateway·서비스는 공개키로 검증한다. 서명은 로그인 때만, 검증은 매 요청이라 RS256의 "서명 느림·검증 빠름" 특성이 맞다. 공개키는 설정에 둬도 되고 개인키만 비밀값이다. 키 교체를 위해 `kid`를 둔다.

## AI 추천 (결정 대기)

C + RS256을 단계적으로 적용한다.

1. 사용자 Access를 RS256으로 바꾸고 서비스가 직접 검증한다. 요청 속성은 검증한 토큰에서 만들고 `X-User-*` 헤더 신뢰는 없앤다. Gateway는 그대로 경로 판정·블랙리스트·요청 제한을 맡는다.
2. 입장·결제 토큰도 같은 패턴(Reservation 개인키, Gateway·Payment 공개키)으로 맞춰 SA 7-3의 한계 문단을 해소한다. SA를 바꾸는 일이라 팀 합의가 필요하다.
3. Redis에 비밀번호를 설정하고 서비스별 키 접두사 ACL을 건다. Kafka·Mock PG 신원은 서비스 간 호출이 생기는 M2 이후에 다룬다.

D4는 Gateway의 fail-closed 확인(ADR 0005)을 유지하고, 서비스는 서명·만료만 검증한다. 서비스에서 폐기를 확인할지는 민감 API(비밀번호 초기화, 결제)에 한해 열어 둔다. D6은 IP·전역 시도 제한과 운영자 계정 예외 정책을 별도 후속으로 둔다.

## 열린 질문

- C로 가면 Gateway를 거치지 않은 직접 호출도 유효한 사용자 토큰이 있으면 통과한다. 이를 허용 범위로 볼지, 서비스에도 네트워크 허용 목록을 둘지.
- 키 교체 주기와 방법(재기동 교체 vs JWKS 엔드포인트).
- 2단계(입장·결제 토큰 비대칭화)를 이번 M1에 넣을지, SA 합의 뒤로 미룰지.
