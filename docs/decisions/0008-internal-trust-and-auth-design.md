- 선행: [ADR 0005](0005-auth-redis-fail-closed.md), [ADR 0006](0006-gateway-single-access-policy.md), [ADR 0007](0007-login-lockout-admin-reset.md)

## 선택 이력

- 2026-10-27: 사용자가 "일단 C로 했는데"라고 D1의 사용자 JWT 직접 검증 선택을 전달했다. D2는 HS256과 RS256의 차이를 설명해 달라고 요청한 상태다. 팀 확정이나 코드 반영 완료로 기록하지 않는다.

아래 위협과 선택지의 현재 상태는 설계 조사 시점의 코드 기준이다. C 적용 이후의 검증 결과를 뜻하지 않는다.

## 맥락

ADR 0006으로 경로별 인증 판정을 Gateway 한 곳에 모으면서 서비스 단독 방어가 약해졌다. 지금 서비스는 Gateway가 넣어 준 `X-User-Id`·`X-User-Role`을 그대로 믿는다. 이 헤더는 서명이 없어서 Gateway를 거치지 않고 서비스에 닿는 요청이 임의 사용자·ADMIN으로 행세할 수 있다.

SA MASTER v3.1의 현재 설계는 같은 모델이다. 7-2는 "Gateway가 JWT 검증 → 헤더 전달, 인증이 서비스 호출 없이 끝남"이고, 9-2는 차단 계층을 "보안그룹 → Gateway → 서비스(권한, 도메인 규칙) → DB"로 정한다. 7-3은 HMAC이 검증자도 서명할 수 있다는 한계를 인정하고 비대칭 서명은 MVP 이후로 미뤘다. 따라서 이 설계가 확정되면 SA 7장·9장 변경을 팀에 제안해야 한다.

## 위협 모델

| # | 위협 | 현재 상태 | 영향 |
|---|---|---|---|
| T1 | 내부망·SSRF·설정 실수로 서비스에 직접 도달한 요청이 헤더를 위조 | 서명 없음. 보호는 네트워크 격리뿐이다(Compose 비공개 포트, 보안그룹) | 임의 사용자·ADMIN 행세, 관리자 API 호출 |
| T2 | JVM 모드·로컬 포트처럼 격리가 약한 환경 | 서비스 포트를 loopback에 여는 개발용 구성이 있다 | 같은 기기의 다른 프로세스가 위조 |
| T3 | 대칭 서명(HS256): 검증 키로 서명도 가능 | Gateway가 Access 키를 가진다 | Gateway 침해 시 모든 사용자 토큰 위조 |
| T4 | Redis 무인증: 블랙리스트·Refresh 해시·대기열이 같은 Redis | 인증 없음, 내부망 의존 | 블랙리스트 삭제로 로그아웃 우회, 대기열 조작 |
| T5 | Kafka·서비스 간 호출에 신원이 없음 | 이벤트 payload의 userId를 그대로 믿는다 | 이벤트 위조로 결제·예매 조작 |
| T6 | Access가 비밀번호 초기화·잠금·역할 변경 뒤에도 만료까지 유효 | 30분 | 탈취된 토큰이 최대 30분 유효 |
| T7 | 계정 기준 잠금 | 남의 이메일로 5회 실패시켜 잠금 가능 | 서비스 거부, 운영자 잠금 |

## 결정할 것

- D1. 서비스가 사용자 신원을 어떻게 믿을지 (T1·T2)
- D2. 서명 방식과 키 배포 (T3)
- D3. 적용 범위: 사용자 Access만 / 입장·결제 토큰까지 (SA 7-3과 맞물림)
- D4. 폐기(블랙리스트) 확인을 어느 계층에서 할지 (T6)
- D5. Redis·Kafka·DB 접속 인증 (T4·T5)
- D6. 계정 잠금 남용 방어 (T7)

## D1 선택지

| | A. 네트워크만 신뢰 (현재) | B. Gateway가 서명한 내부 신원 | C. 서비스가 사용자 JWT를 직접 검증 |
|---|---|---|---|
| 방식 | 헤더를 믿는다 | Gateway가 짧은 내부 토큰을 붙이고 서비스가 검증 | `Authorization`을 서비스까지 전달하고 서비스가 서명·exp·aud 검증 후 속성 생성 |
| T1·T2 방어 | 없음 | 있음 (내부 키를 모르면 위조 불가) | 있음 (사용자 토큰 서명으로 위조 불가) |
| Gateway 침해 | 전부 위조 | 내부 키로 전부 위조 | 비대칭 서명이면 위조 불가 |
| 요청당 추가 비용 | 없음 | Gateway 서명 + 서비스 검증 | 서비스 검증(RS256 검증은 마이크로초대) |
| 구현량 | 없음 | 내부 키 관리와 토큰 형식이 더 생김 | 이미 있는 `TokenDecoders`를 서비스에서 재사용. 헤더 신뢰 코드 제거 |
| SA 변경 | 없음 | 7-2 변경 | 7-2 변경, "서비스 호출 없이 인증" 문구는 유지(검증이 로컬) |

## D2 선택지

- HS256 유지: 키 하나로 단순하지만 검증하는 모든 서비스가 서명도 할 수 있다. C와 같이 쓰면 서비스 수만큼 위조 지점이 늘어 C의 이점이 사라진다.
- RS256 비대칭: 발급자(User)만 개인키를 갖고 Gateway·서비스는 공개키로 검증한다. 서명은 로그인 때만, 검증은 매 요청이라 RS256의 "서명 느림·검증 빠름" 특성이 맞다. 공개키는 설정에 둬도 되고 개인키만 비밀값이다. 키 교체를 위해 `kid`를 둔다.

## 결정 (2026-10-27, Junhyun An)

- D1: C. 서비스가 사용자 JWT를 직접 검증한다. `X-User-*` 헤더 신뢰를 없앤다.
- D2: Access는 RS256 비대칭으로 바꾼다.
- D3: Access만 먼저 바꾼다. 입장·결제 토큰의 비대칭화는 SA 7-3 변경 제안으로 팀 합의 뒤에 한다.
- 세 질문 모두 AI 추천안을 선택했다. 선택 이유는 미기재다.

## 상세 설계 (구현 전 초안)

**토큰**
- Access: RS256, 헤더에 `kid`. claim은 지금과 같다(`iss=iseonjwa-auth`, `aud=iseonjwa-api`, `sub`, `role`, `jti`, `token_type=access`, `iat`, `exp`).
- Refresh: HS256과 별도 키를 유지한다. 검증자가 발급자(User)뿐이라 대칭이어도 위조 지점이 늘지 않는다.
- 입장·결제 토큰: 이번 범위 밖(D3). 지금 SA의 HMAC·분리 키 규칙을 그대로 둔다.

**키**
- 개인키는 User만 갖는다(환경변수 `JWT_ACCESS_PRIVATE_KEY`, PKCS#8 PEM을 한 줄로 인코딩). Config Server에는 전달하지 않는다.
- 공개키는 비밀이 아니지만 개발자마다 키 쌍이 달라 `.env`로 Gateway·서비스에 주입한다(`JWT_ACCESS_PUBLIC_KEY`). `init-local-env.py`가 키 쌍을 만든다.
- 교체는 `kid`로 구분한다. 첫 구현은 활성 키 하나만 쓰고, 교체 때 이전 공개키를 함께 허용하는 확장은 후속으로 둔다.

**검증 지점**
- Gateway: 지금처럼 `AccessPolicy` 판정, 서명·만료·claim 검증, Redis 블랙리스트(fail-closed, ADR 0005). 사용자 헤더를 더는 만들지 않고 `Authorization`을 그대로 전달한다. 클라이언트가 보낸 `X-User-*`는 어느 쪽에서도 읽지 않는다.
- 서비스(common-web): `GatewayIdentityFilter`를 토큰 필터로 바꾼다. `Authorization: Bearer`가 있으면 공개키로 서명·만료·issuer·audience·token_type·role을 검증하고 `currentUserId`·`currentUserRole` 속성을 만든다. 검증 실패는 401, 토큰이 없으면 속성 없이 통과하고 컨트롤러가 401을 낸다. 관리자 API는 서비스에서도 역할을 확인한다.
- 폐기(D4): 블랙리스트는 Gateway에서만 확인한다. 서비스는 서명·만료만 본다. Gateway를 우회한 직접 호출이 로그아웃된 토큰을 쓰는 경우는 만료까지 통할 수 있고, 이는 알려진 한계다. 민감 API에서 서비스가 블랙리스트를 확인할지는 열린 질문이다.

**코드 영향**
- common-auth: 비대칭 디코더·키 파서 추가, 대칭 Access 경로 제거.
- user-service: Access 발급을 RS256 + `kid`로 바꾼다. Refresh 경로는 그대로다.
- gateway: `withIdentity` 제거(요청마다 exchange 변환이 사라진다), 디코더 교체.
- common-web·reservation·payment: 토큰 필터와 공개키 설정을 연결한다.
- 테스트: 서비스 통합 테스트가 헤더 대신 실제 토큰으로 호출하도록 바꾼다. 위조 헤더가 무시되는지, 다른 키로 서명한 토큰이 거절되는지를 추가한다. 스모크의 서비스 직접 호출도 토큰을 쓰게 바꾼다.
- 문서: SA 7-2의 헤더 전달 문구와 11-1의 인증 헤더 행이 바뀐다.

**후속(결정 대기)**
- D4 서비스 폐기 확인, D5 Redis 비밀번호·ACL, D6 로그인 남용 방어(IP 기준 제한, 운영자 계정 예외)는 구현 순서와 함께 정한다.

## 열린 질문

- C로 가면 Gateway를 거치지 않은 직접 호출도 유효한 사용자 토큰이 있으면 통과한다. 이를 허용 범위로 볼지, 서비스에도 네트워크 허용 목록을 둘지.
- 키 교체 주기와 방법(재기동 교체 vs JWKS 엔드포인트).
- 서비스가 민감 API(비밀번호 초기화, 결제)에서 블랙리스트를 직접 확인할지(D4).
- Redis 비밀번호를 이번 구현에 함께 넣을지(D5).
