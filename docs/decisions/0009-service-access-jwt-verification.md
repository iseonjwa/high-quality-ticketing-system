# 0009. 서비스가 Access JWT를 직접 검증하는 방향 선택

- 상태: 철회 (2026-10-27 Junhyun이 SA 7-2·7-3 유지로 되돌림. 고민 기록으로 보존)
- 날짜: 2026-10-27
- 결정자: Junhyun An
- 관련 AI 판단: [D1의 C 선택](../ai-judgments/junhyun/2026-10-27-service-jwt-verification-choice.md)
- 관련 설계: [ADR 0008 내부 신뢰 모델](0008-internal-trust-and-auth-design.md)

## 맥락

기존 SA 7-2는 Gateway가 JWT를 검증한 뒤 `X-User-Id`·`X-User-Role`을 서비스로 전달한다. 서비스는 해당 헤더의 서명을 검증하지 않는다.
ADR 0008에서 서비스가 신원을 신뢰하는 방법과 서명 알고리즘을 D1·D2로 나누어 비교했다.

사용자는 "일단 C로 했는데"라고 D1 선택을 전달했다. 후속 답변에서 "헤더 위조를 막고, 게이트웨이를 전적으로 신뢰하지 않음으로서 보안을 보강하기 위해서"라고 선택 이유를 밝혔다.
D2는 HS256과 RS256의 차이를 질문한 상태다.

## 결정

D1의 사용자 선택은 C다. User가 발급한 Access JWT를 서비스까지 전달하고 서비스가 서명·발급자·유효 시간·audience·토큰 종류 등을 검증해 사용자 신원을 구성하는 방향이다.
일반 `X-User-*` 헤더만으로 사용자 신원을 만들지 않는 것을 목표로 한다.
사용자가 밝힌 선택 의도는 헤더 위조 방지와 Gateway에 대한 전적인 신뢰를 줄여 보안을 보강하는 것이다. 후속 질문에서 이 의도의 기술적 타당성 검토를 요청했다.

D2의 서명 방식·키 배포는 결정하지 않았다. 입장·결제·Refresh 토큰 변경이나 서비스별 폐기 조회 확대도 이 선택에 포함하지 않는다.
SA 변경에 대한 팀 합의는 확인되지 않았으므로 제안 상태로 둔다.

## 철회

같은 날 사용자가 "비대칭 서명은 MVP이후로 미루는 게 맞는 것같다. 일단 방금 논의한 부분은 SA대로 하자. 내가 고민했던 기록만 남기고"라고 지시해 이 선택을 철회했다. 서비스는 계속 Gateway가 전달한 `X-User-*`를 신뢰한다. 이 문서는 이후 재검토할 때의 근거로 남긴다. 철회 판단은 [판단 기록](../ai-judgments/junhyun/2026-10-27-auth-trust-follow-sa.md), 현재 결정은 [ADR 0008](0008-internal-trust-and-auth-design.md)에 있다.

## 선택 근거의 범위

일반 헤더를 신원 근거로 쓰지 않고 검증된 JWT에서 신원을 구성하면 Gateway 우회·내부 헤더 위조에 대비할 수 있다.
Gateway가 토큰을 새로 위조할 능력까지 줄이려면 User에만 서명 권한을 두어야 한다. HS256에서는 Gateway도 공유 비밀키를 갖기 때문에 C 선택만으로 그 목표가 충족되지는 않는다.
RS256을 사용해도 관찰한 유효 토큰의 재사용과 Gateway에만 둔 정책의 생략은 별도 문제다. 이 설명은 설계 검토이며 실행·성능 검증 결과가 아니다.
사용자의 원래 선택 의도와 AI의 기술 검토는 [판단 기록](../ai-judgments/junhyun/2026-10-27-service-jwt-verification-choice.md)에서 구분한다.

## 검토한 대안

- A. Gateway만 검증하고 일반 헤더를 전달한다. 검증·키 배포 부담이 적지만 서비스가 신원 전달 경로를 신뢰해야 한다. 사용자가 채택하지 않은 구체적인 이유는 미기재다.
- B. Gateway가 내부 토큰을 새로 서명하고 서비스가 검증한다. 내부 신원 계약과 키 운영을 추가한다. 사용자가 채택하지 않은 구체적인 이유는 미기재다.
- C. 서비스가 사용자 JWT를 직접 검증한다. 사용자가 선택한 방향이다. 비용과 방어 범위의 비교는 [학습 노트](../learning/junhyun/qna/2026-10-27-msa-service-identity-verification.md)에 있다.

## 결과

서비스 검증으로 유효한 토큰이 없는 호출자의 사용자 헤더 위조를 거절할 수 있다. 서비스별 CPU 비용과 검증 설정·키 배포가 추가된다.
서비스 직접 접근 차단, Gateway의 요청 제한·블랙리스트, 서비스의 도메인 인가는 계속 필요하다. JWT 검증이 이 정책을 모두 대신하지 않는다.

ADR 0006의 경로 정책 집중과 서비스의 신원 검증을 어떻게 함께 적용할지는 구현 전에 정리해야 한다. 기존 ADR이나 SA를 팀 확정 없이 대체하지 않는다.
D2 선택, 팀 합의, 구현과 실행 검증이 후속 작업이다. 이 기록 작성 시점에는 문서만 반영했다.
