# 0010. 인증 상태 확인과 세션 변경을 사용자 행 잠금으로 직렬화

- 상태: 채택 (사용자 보강 요청 범위의 브랜치 구현)
- 날짜: 2026-10-27
- 결정자: Junhyun An (보강 요청), 세부 구현은 Codex
- 관련 AI 판단: [인증 구현 보강 4개 수용](../ai-judgments/junhyun/2026-10-27-auth-hardening.md)

## 맥락

비밀번호를 비교하는 동안 초기화·변경이 끝나도 먼저 시작한 로그인이 이전 사용자 스냅샷으로 토큰을 발급하고 Refresh를 저장했다.
실제 PostgreSQL·Redis·HTTP 통합 테스트에서 초기화·변경 뒤 로그인 성공과 세션 재생성을 재현했다.

## 결정

BCrypt 비교는 DB 행 잠금 밖에서 수행한다. 세션을 발급하기 직전에 `TransactionTemplate` 안에서 현재 사용자 행을 `PESSIMISTIC_WRITE`로 읽고, 비교에 사용한 비밀번호 해시가 여전히 같은지와 현재 잠금을 확인한다.
로그인·Refresh 발급과 비밀번호 변경·초기화의 세션 저장·폐기는 같은 사용자 행의 잠금 안에서 수행한다. 이 경로들이 여러 User 인스턴스에 분산돼도 PostgreSQL 행 잠금을 공유한다.
로그인 실패 횟수 증가는 발급 트랜잭션 밖에 남겨 인증 예외로 롤백되지 않게 한다. 성공 횟수 초기화는 발급 트랜잭션 안에서 수행한다.

## 검토한 대안

- 메서드 전체에 트랜잭션을 건다: BCrypt 동안 DB 자원을 오래 점유하고 실패 횟수의 예외·롤백 처리가 복잡해진다.
- `synchronized`로 묶는다: 다른 User 인스턴스와는 조율되지 않는다.
- 버전 컬럼이나 Redis 잠금·폐기 키를 추가한다: 새 상태·스키마·키 계약이 필요하다. 이번 보강은 기존 사용자 행과 세션 키로 제한한다.

## 결과

초기화가 먼저 끝나면 이전 해시로 확인한 로그인은 401로 거절한다. 세션 발급이 먼저 사용자 행을 잠갔다면 초기화가 그 뒤 세션을 폐기한다.
비밀번호 비교 뒤 현재 잠금도 재확인하므로 이전 스냅샷으로 새 잠금을 풀거나 토큰을 발급하지 않는다.
발급 중 짧은 Redis 작업 동안 DB 행과 연결을 점유한다. 같은 계정의 경합은 대기하며 처리량 영향은 별도 부하 측정 대상이다.
DB와 Redis를 하나의 분산 트랜잭션으로 만든 것은 아니다. Redis 타임아웃 뒤 실행 여부와 DB 커밋 실패는 여전히 실패 응답으로 다루며 세션 성공을 보장하지 않는다.
기존 Access의 만료 전 유효함과 Gateway 인증·HS256 설계는 유지한다.

## 검증

`./gradlew :user-service:test --tests iseonjwa.user.AuthIntegrationTest --no-daemon`에서 수정 전 새 경합 테스트 2개가 실패했다. 수정 후 18개 통합 테스트가 모두 통과했다.
테스트는 로그인 비밀번호 비교를 멈춘 사이 실제 초기화·변경 HTTP 요청을 완료한 뒤 로그인을 재개하며, 401·Refresh 미저장을 확인한다.
