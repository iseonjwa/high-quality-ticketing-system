# 0011. 앱 검증은 Java·JUnit으로 관리한다

- 상태: 대체됨 (0012). 앱 JUnit 원칙을 유지하고 개발 도구까지 이관 범위를 확장했다.
- 날짜: 2026-10-27
- 결정자: Junhyun An (내부 테스트 선호 지적), 세부 이관은 Codex
- 관련 AI 판단: [Python 앱 검증 대신 내부 JUnit 테스트](../ai-judgments/junhyun/2026-10-27-junit-test-boundary.md)

## 맥락

이 문서는 앱 검증을 먼저 이관한 시점의 기록이다. 이후 사용자가 전체 도구 통일을 선택했으며 현행 결정은 [ADR 0012](0012-java-gradle-workspace-tools.md)다.

서비스 내부에는 Java 테스트가 있었지만, 전체 API·연동·설정 서버 장애 검증은 Python 스크립트에도 구현돼 있었다.
사용자가 "내부 테스트코드로 처리해야할 것 같은뎅 아닌가!"라고 지적했다. Python 도구 전체를 제거하라는 개별 확정과는 구분한다.

## 결정

앱의 동작 판정은 프로젝트 안의 Java·JUnit 테스트로 옮긴다. 검증 전용 `system-tests` 모듈을 추가하며 실행 서비스·공개 API·업무 모듈 경계는 바꾸지 않는다.
설정 서버 기동 실패는 기본 `test`·`build`에 포함한다. 실행할 JAR도 태스크 입력으로 선언해 JAR가 바뀌면 검사를 다시 수행한다.
실제 스택 검증은 `system` 태그를 사용하고 `:system-tests:systemTest`로 실행한다. 기본 CI 테스트는 전체 앱 스택이나 실제 `.env`에 의존하지 않는다.
환경·프로세스 준비 도구는 유지한다. JVM 실행 도구도 서비스 동작 판정은 같은 Java 시스템 테스트에 위임한다.

## 검토한 대안

- Python 스모크를 계속 유지한다: 구현은 가능하지만 Java 코드와 테스트 도구가 나뉘고 검증·리포트의 유지 경계가 늘어난다.
- 각 서비스의 테스트에서 전체 스택까지 모두 실행한다: 다른 서비스·관측 도구의 기동 상태가 일반 모듈 테스트에 결합된다.
- 모든 시스템 검사를 기본 `test`에 넣는다: CI와 로컬 단위 검증에 전체 스택·개인 환경변수가 필요해진다.

## 결과

기존 Python 검증 범위를 JUnit 시나리오와 리포트로 확인할 수 있다. Python 앱 스모크와 설정 서버 장애 스크립트는 제거한다.
시스템 테스트의 환경은 실제 local 스택이다. 재기동과 Redis pause는 선택 옵션으로 분리하고 복구를 수행한다.
Python 실행 준비·포트 검사 도구의 유지·전환은 별도 범위다. 새 업무 서비스나 운영 배포를 추가하는 결정이 아니다.

## 검증

이관한 시스템 테스트 13개가 실제 스택에서 통과했다. 설정 서버 기동 실패 JUnit 1개도 통과했다.
기본 전체 검사에서는 JUnit 106개·개발 도구 Python 14개가 통과했다. JVM 실행 모드에서도 소켓·등록 주소와 시스템 테스트 11개를 확인하고 Compose 스택을 복구했다.
태스크·실행 범위와 기존 검사 대응은 [테스트 가이드](../guides/testing.md)에 있다.
