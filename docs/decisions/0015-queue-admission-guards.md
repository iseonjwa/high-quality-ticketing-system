# 0015. 대기열 입장 처리와 입장 토큰 발급의 안전장치

- 상태: 제안 (결정 4번 일부는 [0031](0031-queue-token-api-and-ready-status.md)로 변경)
- 날짜: 2026-10-27
- 결정자: 권영은 (대기열 담당, 팀 합의 전)
- 관련 AI 판단: [대기열 입장 토큰 발급 방식과 안전장치](../ai-judgments/youngeun/2026-10-27-queue-admission-guards.md)

## 맥락

SA MASTER v3.2는 대기열을 Redis 키 세 개(`seq`, `waiting`, `admitted`)와 입장 판정 `seq <= admitted`로 정했다(12-8, 결정 기록 #27). `admitted`를 사용자 명단이 아니라 누적 카운터로 두면서 아래 빈틈이 남았다.

1. **입장 처리 중복**: 1차 AI SA 피드백의 Queue 유지 조건 3은 "인스턴스마다 스케줄러가 돌면 입장 속도가 배가 된다, 전역 카운터(Redis Lua)로 제어한다"였다. SA v3부터는 "전역 카운터"로만 요약돼, 카운터를 공유해도 인스턴스마다 `+N`을 하면 속도가 배가 되는 문제를 막는 장치가 없다.
2. **카운터가 번호표를 앞지름**: `admitted`가 초당 N씩 무조건 오르면, 줄이 빈 동안 커진 값 때문에 오픈 순간 몰린 사용자가 한꺼번에 입장한다.
3. **입장 토큰 재발급**: 입장한 사용자는 계속 `seq <= admitted`라서, 순번 조회를 다시 부르면 새 토큰을 받는다. 토큰 유효 시간 T(10분)를 무한히 늘릴 수 있고 "최대 동시 입장 = N × T"가 깨진다. 매크로가 API를 직접 부르면 프론트 저장 방식과 상관없이 생긴다.
4. **입장 토큰 넘겨주기**: 7-3 검증 규칙(서명, `typ`, `aud`, `exp`, 회차 ID)에는 사용자 확인이 없어, 한 사람이 받은 입장 토큰을 다른 계정이 써도 통과한다. 결제 토큰에는 이미 `sub` = `X-User-Id` 확인이 있다.

## 결정

1. Gateway의 입장 토큰 검증에 **입장 토큰 `sub` = JWT 사용자 ID** 확인을 추가한다. 다르면 403 `ENTRY_TOKEN_INVALID`.
2. Redis 키 **`queue:{scheduleId}:lastTick`**을 둔다. 입장 처리 Lua가 Redis `TIME`의 현재 초와 비교해 이미 처리한 초면 건너뛴다.
3. 입장 처리는 **`admitted = min(admitted + N, seq)`**로 올린다.
4. Redis 키 **`queue:{scheduleId}:issued`**(ZSET, 점수 = 발급 시각)를 둔다. 토큰 발급 시 `waiting`에서 빼고 `issued`에 기록한다. 재조회하면 같은 발급 시각으로 토큰을 다시 응답한다(만료 = 발급 시각 + T). T가 지난 기록은 정리하고, 그 뒤 진입하면 새 seq로 맨 뒤에 선다. 대기열 진입 Lua와 순번 조회 Lua는 모두 `issued`를 먼저 확인한다. T 안의 기록이 있으면 대기열 진입 요청에도 새 seq를 발급하지 않고 같은 발급 시각으로 토큰을 다시 응답한다. 토큰을 받으면 `waiting`에서 빠지므로, 이 확인이 없으면 토큰이 유효한 동안 대기열 진입 API를 다시 불렀을 때 새 seq가 생겨 한 사람이 입장 상태와 대기 자리를 동시에 갖게 된다.
   - 2026-10-29 변경: 입장 토큰은 토큰 API에서만 주고, 진입·순번 조회는 `issued`에 T 안의 기록이 있으면 `READY`를 응답한다. 발급 시 쓰기 순서는 `issued` 기록 → `waiting` 제거다. 만료 기록 처리도 [ADR 0031](0031-queue-token-api-and-ready-status.md)을 따른다.

## 검토한 대안

- **토큰 발급 후 `waiting`에 그대로 둠**: 키 추가가 없지만 재조회마다 새 토큰이 나가 3번 문제가 그대로 남고, 만료 뒤에도 줄 없이 재입장한다. `waiting`이 진입한 모든 사람으로 커져 대기열 길이 지표(`ZCARD`)가 의미를 잃는다.
- **발급 시 `waiting`에서 빼기만 함 + 프론트 `sessionStorage` 저장**: 키 추가 없이 3번 문제는 막는다. 다만 서버가 발급한 뒤 응답이 유실되면 차례가 된 사용자가 맨 뒤로 밀린다. 부하가 큰 오픈 순간에 응답 지연·타임아웃이 늘어 이 경우가 가장 자주 생긴다. 다른 탭·기기에서도 같다.
- **`admitted`를 사용자 명단으로 둠**: 재발급·상한 문제는 자연히 풀리지만, 꺼낸 뒤 명단에 넣기 전에 끊기면 사용자가 사라지는 문제가 생기고 Lua가 커진다. SA가 카운터를 고른 이유(#27)를 거스른다.

## 결과

- 얻는 것: 입장 속도가 인스턴스 수와 무관하게 N 이하, 오픈 순간의 몰림 입장 방지, 토큰 유효 시간 고정, 응답 유실·새로고침·다른 기기에서도 입장 기회 유지, 토큰 넘겨주기 차단. `issued` 크기가 곧 현재 입장 인원이라 입장 속도 역산(3-3)의 측정값으로 쓴다.
- 감수하는 것: Redis 키 2개, `issued` 메모리(최대 약 N × T개), 순번 조회 Lua의 `ZSCORE` 한 번, 만료 기록 정리 작업.
- 후속 작업: 팀 확인 후 상태를 채택으로 바꾸고 SA MASTER 12-8·7-3의 🆕 표시를 지운다. Notion 결정 기록 #27에 수정 내역을 남긴다. 구현은 대기열 이슈(진입·입장 처리·순번 조회와 토큰 발급·Gateway 필터)의 완료 기준에 넣는다.
