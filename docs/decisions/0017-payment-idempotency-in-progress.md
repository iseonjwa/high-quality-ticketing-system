# 0017. 같은 멱등키 요청이 처리 중이면 202와 기존 paymentId를 돌려준다

- 상태: 제안 (SA 변경 요청 필요. 2026-10-28 개정)
- 날짜: 2026-10-27
- 결정자: 안준현
- 관련 AI 판단: [결제 상세 설계 빈틈 결정](../ai-judgments/junhyun/2026-10-27-payment-design-gaps.md)
- 관련 결정: [0018](0018-payment-pg-permit-before-tx1.md), [0019](0019-payment-new-key-existing-payment.md), [0026](0026-payment-one-per-reservation.md)
- 불변 조건: INV-1([invariants.md](../design/payment/invariants.md))

## 맥락

SA 11-1과 12-5는 `Idempotency-Key`(UUID, 24시간)를 정한다. 같은 키와 같은 본문이면 저장된 응답을 재생하고, 같은 키에 다른 본문이면 409 `IDEMPOTENCY_KEY_REUSED`다. 결제는 "멱등 기록과 결제 저장을 같은 트랜잭션"으로 처리한다(#17).

그런데 결제 승인은 PG 호출이 트랜잭션 밖이라 요청이 세 구간으로 나뉜다.

1. TX1: 멱등 기록(`response_status` NULL)과 결제 `REQUESTED` 저장
2. PG 호출(트랜잭션 밖, 응답 2초)
3. TX2: 결제 `APPROVED`·`DECLINED`·`UNKNOWN`과 outbox, 멱등 응답 저장

SA는 1~3 사이에 같은 키 요청이 오거나 서버가 죽었을 때의 응답을 정하지 않았다. Gateway 타임아웃이 3초라서 클라이언트는 응답을 못 받고 같은 키로 재시도하는 일이 정상 경로에서도 생긴다. 이때 클라이언트는 `paymentId`를 모른다.

## 결정

- 같은 키 요청이 오면 멱등 기록을 **토큰 검증보다 먼저** 조회한다. 토큰이 이미 만료됐어도 재시도가 결과를 받을 수 있어야 하기 때문이다.
- 응답이 이미 저장돼 있으면(`response_status` 있음) 그대로 재생한다.
- 응답이 아직 없으면(처리 중이거나 서버가 죽은 건) 결제 행의 현재 상태로 응답을 만든다. 상태별 응답은 [api.md](../design/payment/api.md)의 표 A가 기준이다.
  - `APPROVED`·`DECLINED`·`REFUNDED`면 200과 그 결과를 돌려준다.
  - `REQUESTED`·`UNKNOWN`이면 202, `Location`, `nextPollAfterSeconds`로 돌려준다. 클라이언트는 UNKNOWN과 같은 폴링 경로(`GET /payments/{id}`)를 쓴다.
  - `NEEDS_MANUAL_CHECK`면 409 `PAYMENT_ALREADY_EXISTS` + `Location`이다(0019과 같은 응답).
- 멱등 기록에서 결제 행을 찾으려고 `idempotency_records`에 `resource_id`(결제 ID)를 추가한다. 기록은 결제와 함께 생기므로 NOT NULL이다. 새 키를 기존 결제에 연결한 기록과 구분하려고 `link_type`(ORIGIN·ALIAS)을 둔다(0019). SA 12-5 공통 테이블 변경이다.
- **같은 키 동시 요청**: 두 요청이 모두 TX1까지 가면 한쪽은 멱등 기록 PK 위반으로 실패한다. 이 위반은 500이 아니라 정상 흐름이다. 롤백하고 허가를 반환한 뒤 멱등 기록을 다시 읽어 위 규칙대로 응답한다. 같은 예매에 다른 키로 동시에 들어온 경우의 `reservation_id` 위반은 0026·0019이 같은 방식으로 처리한다.
- 서버가 PG 호출 중에 죽어 `REQUESTED`로 남은 결제는 SA 10-5의 재확인 스케줄러가 10초 경과 뒤 확정한다. TX1이 `next_check_at`을 저장 시각 + 10초로 채우고 CHECK 제약이 누락을 막는다. 멱등 응답은 확정 때 채우지 않아도 위 규칙으로 재생된다.
- 일시 실패 응답(PG_UNAVAILABLE 503 등 5xx)은 멱등 응답으로 저장하지 않는다. 같은 키로 다시 시도할 수 있어야 한다. 멱등 기록은 TX1까지 진행된 요청(ORIGIN)과 0019의 연결(ALIAS)에만 생기므로 저장되는 응답은 ORIGIN의 200(`APPROVED`·`DECLINED`)과 202(`UNKNOWN`)뿐이다. TX1 전에 끝나는 검증 실패(4xx)와 503은 기록이 없고, 같은 요청을 다시 보내면 같은 결과가 나온다.
- Gateway가 504를 돌려줘도 서버 처리는 계속된다. 같은 키 재시도가 이 규칙으로 결과를 받는다(0018).

## 검토한 대안

- **409 `IDEMPOTENCY_IN_PROGRESS`**: 구현이 가장 단순하고 흔한 방식이다. 새 에러 코드가 필요하고, 클라이언트가 paymentId를 얻을 길이 없어 UNKNOWN 폴링 경로로 이어지지 않는다. 결제는 "결과를 곧 알려 주는" 쪽이 사용자 경험이 낫다고 보고 채택하지 않았다.
- **완료될 때까지 대기**: 사용자는 항상 최종 결과를 본다. Gateway 3초 타임아웃과 충돌하고, PG가 느릴 때 재시도 요청이 스레드를 더 점유해 Bulkhead의 목적(PG 지연의 격리)과 맞지 않는다.

## 트레이드오프

| | 얻는 것 | 감수하는 것 |
|---|---|---|
| 202 + 기존 paymentId | 재시도가 안전하고 폴링 경로가 하나다. 새 에러 코드가 없다 | `idempotency_records.resource_id`·`link_type` 추가(SA 변경). 응답이 "현재 상태"라서 저장된 응답과 달라질 수 있다 |
| 토큰 검증보다 멱등 조회 먼저 | 만료된 토큰으로도 결과를 받는다 | 인증은 통과한 사용자만 조회하므로 안전하지만, 검증 순서가 SA 6-6 서술과 달라진다 |
| 5xx 미저장 | 일시 장애 뒤 같은 키로 재시도 가능 | 같은 키의 응답이 시도마다 다를 수 있다 |
| PK 위반을 정상 흐름으로 | 동시 요청도 500 없이 같은 결과를 받는다 | 제약별 예외 분기 코드가 필요하다 |

## 결과

- SA 변경 요청: S-4(12-5 `resource_id`·`link_type`, 11-1 처리 중 응답과 5xx 미저장).
- 승인 요청의 전체 처리 순서는 0018과 `api.md`가 기준이다.
- 테스트: N3(PG 호출 중·서버 중단 뒤 재시도, 만료 토큰 재시도), N14(같은 키 동시 2건), 5xx 뒤 같은 키 재시도, N29(504 뒤 재시도).

## 개정 이력

- 2026-10-28: (1) TX1의 멱등 기록 PK 위반을 정상 흐름으로 처리하도록 했다(검토 M1, 사용자 지정 수정). (2) 현재 상태 응답에 `REFUNDED`·`NEEDS_MANUAL_CHECK`를 넣었다. (3) `resource_id`를 NOT NULL로 하고 `link_type`을 추가했다(사용자 결정 7, 0019). (4) 이 ADR의 결과 항목에 있던 처리 순서 "인증 → 멱등 조회 → 토큰 검증 → 금액 대조 → TX1 → PG → TX2"는 0018의 순서로 대체됐다(검토 L6). (5) `next_check_at` CHECK와 504 뒤 재시도를 적었다.

## 면접에서 설명할 한 줄

PG 호출이 트랜잭션 밖인 결제 API에서는 "처리 중"이라는 중간 상태가 생기므로, 멱등키 재시도에는 저장된 응답이 아니라 결제 행의 현재 상태로 답하게 해서 타임아웃·서버 중단 뒤에도 클라이언트가 같은 폴링 경로로 결과를 받게 했고, 동시 요청의 유니크 위반도 에러가 아니라 같은 결과로 바꿨다.
