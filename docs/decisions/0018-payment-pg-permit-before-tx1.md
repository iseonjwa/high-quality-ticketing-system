# 0018. 신규 승인 시도만 PG 호출 허가를 TX1 앞에서 얻고, PG 호출 자원은 승인과 복구 두 그룹으로 나눈다

- 상태: 제안 (SA 변경 요청 필요. 2026-10-28 개정)
- 날짜: 2026-10-27
- 결정자: 안준현
- 관련 AI 판단: [결제 상세 설계 빈틈 결정](../ai-judgments/junhyun/2026-10-27-payment-design-gaps.md)
- 관련 결정: [0017](0017-payment-idempotency-in-progress.md), [0020](0020-payment-refund-dlq-manual-check.md), [0022](0022-outbox-retry-and-retention.md), [0023](0023-payment-pg-client-port.md), [0026](0026-payment-one-per-reservation.md)
- 불변 조건: INV-1, INV-4, INV-8([invariants.md](../design/payment/invariants.md))

## 맥락

SA 6-6은 PG 호출에 트랜잭션 밖 실행, 타임아웃, Circuit Breaker, Bulkhead를 건다고 하고, 11-3은 CB OPEN·Bulkhead 초과를 503 `PG_UNAVAILABLE`로 정한다. 그러나 REQUESTED 저장(TX1)과 허가 검사의 순서는 정해져 있지 않다.

REQUESTED를 먼저 저장하면 503 뒤에도 같은 예매의 결제 행이 남는다. 사용자가 다시 시도하면 기존 결제와 부딪히고, 실제로는 PG를 호출한 적이 없는 결제가 REQUESTED로 남아 10초 뒤 재조회 대상이 된다. 장애 때 요청이 몰릴수록 쓸모없는 행이 쌓인다.

2026-10-27 원안은 재확인 스케줄러의 조회·환불 호출이 신규 승인과 같은 CB·Bulkhead를 쓸지를 미결로 남겼다. 같은 CB를 쓰면 승인 실패로 OPEN이 됐을 때 이미 생긴 금전 의무(불확실한 승인, 환불)의 복구가 함께 막힌다. 또 TX1·TX2의 DB 연결 대기와 PG 호출 직전의 토큰 만료가 정해지지 않았고, 처리 시간 합계가 Gateway 3초를 넘을 수 있다(Opus 검토 M2·M3·L9).

## 결정

### 처리 순서
승인 요청 한 건은 다음 순서로 처리한다. 응답 표와 에러 코드는 [api.md](../design/payment/api.md)가 기준이다.

1. 인증을 확인한다.
2. 요청 형식(`method`는 `CARD`만, 토큰 길이 상한)을 검증한다.
3. **같은 멱등키의 기록을 조회한다**(허가 없이, 토큰 검증보다 먼저, 0017). 재시도는 만료된 토큰으로도 결과를 받아야 하기 때문이다.
4. 토큰 서명·`typ`·`aud`·`exp`·`sub`와 금액을 검증한다. `exp`가 지났으면 신규 승인은 할 수 없고 기존 결제 조회만 한다(0019).
5. **같은 예매의 기존 결제를 조회한다**(허가 없이). `DECLINED`·`REFUNDED`면 거절하고(0016), 그 밖이면 기존 결제로 응답한다(0019). CB가 OPEN이어도 3~5단계의 응답은 그대로 나간다.
6. **신규 승인 시도일 때만** `pg-approve` 그룹의 Bulkhead·CB 허가를 얻는다. 얻지 못하면 행도 멱등 기록도 만들지 않고 503 `PG_UNAVAILABLE`을 돌려준다.
7. TX1: 멱등 기록과 결제 `REQUESTED`를 저장하고 **커밋한다**. 실패하면 허가를 호출 결과로 세지 않고 반환한다. 유니크 위반은 3단계부터 다시 조회해 응답한다(0017, 0026). DB 연결 대기는 1초`[가정]`로 제한하고, 넘거나 DB 오류면 503 `SERVICE_UNAVAILABLE`이다(행 없음).
8. **PG 호출 직전에 토큰 `exp`를 다시 확인한다.** 2~7단계 사이에 만료됐으면 PG를 부르지 않고 `DECLINED(TOKEN_EXPIRED)`로 닫는다. PG에 보내지 않았음을 이 시점에 확신할 수 있는 유일한 경우다. 허가는 호출 결과로 세지 않고 반환한다.
9. PG 호출은 TX1 커밋 뒤에, 트랜잭션 밖에서 한다. 호출이 시작된 뒤에는 결과에 따라 허가를 정산한다(승인·정상 거절은 성공, 결과를 모르는 타임아웃·연결 실패·PG 5xx·처리 중 응답은 실패로 CB에 기록한다. 요청·인증을 거절한 4xx `CLIENT_ERROR`는 셈하지 않고 반환한다. Bulkhead 허가는 항상 반환한다).
10. TX2: 결제 상태와 outbox, 멱등 응답을 저장한다. 조건부 UPDATE가 1행일 때만 후속 쓰기를 하고(0022), DB 연결 대기 제한은 TX1과 같다. TX2가 실패하면 202로 응답하고 재확인 스케줄러가 복구한다.

PG 타임아웃처럼 승인 여부가 불확실하면 결제를 `UNKNOWN`으로 저장하고 202를 돌려준다. 이후 확정은 재확인 스케줄러가 맡는다(재조회 10초×6회→1분→5분→15분, 끝내 모르면 `NEEDS_MANUAL_CHECK`). 서버가 PG 호출 중에 죽어 `REQUESTED`로 남은 결제도 같은 대상이다.

허가의 획득과 정산은 한 곳(PG 호출 래퍼)에서 `try/finally`로 묶어 반환을 빠뜨리지 않게 한다. HALF_OPEN 상태에서 허가를 정산하지 않으면 CB가 닫히지 않기 때문이다.

### PG 호출 자원 그룹
호출 특성과 장애 영향을 기준으로 최소 두 그룹으로 나눈다. 기능별로 더 나누지 않는다.

| 그룹 | 호출 | 호출 특성 | 장애 영향 | 허가를 못 얻으면 |
|---|---|---|---|---|
| `pg-approve` | `approve` | 사용자가 기다리는 동기 호출, 새 금전 의무를 만든다 | 막혀도 돈이 움직이지 않는다(행 없이 503) | 503 `PG_UNAVAILABLE` |
| `pg-recovery` | `findPayment`, `preventLateApproval`, `refund`, `findRefund` | 배경 작업의 호출, 이미 생긴 금전 의무를 해소한다. 지연에 덜 민감하다 | 막히면 불확실한 승인과 환불이 오래 남는다 | 다음 주기로 넘기고 재조회 횟수를 세지 않는다 |

- 경계: "새 의무를 만드는 호출"과 "기존 의무를 해소하는 호출"로 나눈다. 승인 폭주로 `pg-approve`가 OPEN·포화여도 복구는 계속되고, 장애 뒤 복구 호출이 몰려도 신규 승인 용량을 빼앗지 않는다.
- 각 그룹은 별도 Bulkhead와 CB 인스턴스다. 값(동시 수, 실패율, OPEN 시간)은 [pg-integration.md](../design/payment/pg-integration.md) 5절의 `[가정]`이고 부하 측정 뒤 조정한다. 타임아웃(연결 0.5초·응답 2초)은 같다.
- `pg-recovery`의 동시 수는 복구 실행기 스레드 수(2`[가정]`)와 같게 둔다. 복구 실행기는 Outbox 릴레이와 다른 스레드다(0022).
- 같은 PG에 대한 두 그룹이라 PG 전체 장애면 둘 다 OPEN이 된다. 이때 복구 쪽은 시도 횟수를 세지 않으므로 PG가 돌아오면 자동으로 이어지고, 체류 시간은 최고령 알림이 본다.

### 시간 예산과 Gateway 504
TX1(연결 대기 1초 이내) + PG(최대 2.5초) + TX2(연결 대기 1초 이내)는 Gateway 응답 시한 3초(SA 9-4)를 넘을 수 있다. 넘으면 클라이언트는 504를 받는다. Payment의 처리는 계속되고 PG 호출·TX2는 취소되지 않는다`[가정, N29로 확인]`. 클라이언트는 같은 키로 다시 보내 결과를 받고(0017), 새 키로 보내도 기존 결제에 연결돼 PG를 다시 부르지 않는다(0019). 결제가 두 번 일어나지 않으므로 3초 기준은 바꾸지 않는다. Gateway에 POST 재시도 필터를 두지 않는다.

## 검토한 대안

- **TX1 먼저, 허가 실패 시 행 정리**: 흐름은 읽기 쉽다. OPEN 구간에 요청마다 쓰기·삭제가 일어나 DB 부하가 늘고, 결제 행을 삭제하지 않는다는 SA 12-1 규칙과 맞지 않는다. 삭제 대신 새 상태를 만들면 상태 머신이 커진다.
- **허가 실패를 `DECLINED(PG_UNAVAILABLE)`로 닫기**: 상태 전이는 단순하다. 0016의 규칙(DECLINED 뒤 재승인 차단, 예매 RELEASED)과 합쳐지면 PG 장애가 사용자의 좌석 유실로 이어진다.
- **CB·Bulkhead 하나 공유**: 설정이 단순하다. 승인 실패로 OPEN이 되면 복구가 함께 멈춘다.
- **기능별 그룹(승인·조회·환불·환불 조회·망취소)**: 가장 세밀하다. 같은 PG의 장애는 함께 오는데 상태가 다섯 개로 흩어져 판단과 설정이 늘고, 사용자가 무조건적인 세분화를 원하지 않았다.

## 트레이드오프

| | 얻는 것 | 감수하는 것 |
|---|---|---|
| 허가를 TX1 앞에서 획득 | 503 뒤 결제 행이 남지 않는다. OPEN 구간의 DB 부하가 없다 | 허가를 얻은 뒤 TX1이 실패하는 경우의 반환 로직이 필요하다 |
| 기존 결제·멱등 조회는 허가 없이 | CB OPEN이어도 재시도·기존 결제 응답이 막히지 않는다 | 조회와 신규 시도 경로를 분리해 구현해야 한다 |
| PG 호출은 TX1 커밋 뒤 | 커넥션을 PG 대기 동안 잡지 않는다. 죽어도 REQUESTED 행이 남아 복구된다 | 커밋과 호출 사이에 죽으면 PG는 모르는 결제가 REQUESTED로 남는다. `NOT_FOUND`를 망취소 후 `DECLINED(NOT_SENT)`로 닫는 정책(SA 10-5)이 필수다 |
| 호출 직전 만료 재검사 | 선점이 곧 끝날 결제를 PG에 보내지 않아 만료 뒤 승인·환불이 줄어든다 | 만료 직전 사용자는 거절 응답을 받는다(어차피 선점이 곧 만료된다) |
| 두 그룹 | 승인 장애가 복구를 막지 않고, 복구 폭주가 승인을 막지 않는다 | 설정·지표가 두 벌이다 |
| 504 허용 | 3초 기준과 PG 2초 타임아웃을 유지한다 | 일부 사용자는 504 뒤 재시도로 결과를 받는다 |

## 결과

- `pg-integration.md`에 PG 호출 래퍼와 두 그룹의 값, `api.md`에 처리 순서와 504 동작을 쓴다.
- Resilience4j 의존성이 `payment-service/build.gradle`에 없다. 추가한다.
- `config-repo/payment-service.yml`의 Hikari `maximum-pool-size: 5`를 SA 9-4의 20으로 맞추고 `connection-timeout` 1초`[가정]`을 둔다(S-21).
- SA 변경 요청: S-6(처리 순서), S-20(두 그룹), S-21(연결 풀), S-26(504 동작).
- 테스트: E10, N4, N5, N15, N25, N29, HALF_OPEN 시험 호출 정산, PG 타임아웃 뒤 UNKNOWN과 스케줄러 복구.

## 개정 이력

- 2026-10-28: (1) 미결이던 재확인·환불 호출의 자원을 사용자 결정 3에 따라 `pg-recovery` 그룹으로 분리하고 그룹 경계와 근거를 적었다(검토 M3). 제목을 바꿨다(이전: "신규 승인 시도만 PG 호출 허가를 얻고, 허가는 TX1 앞에서 획득한다"). (2) PG 호출 직전 토큰 만료 재검사와 TX1·TX2의 DB 연결 대기 제한을 넣었다(M2). (3) TX1 유니크 위반을 재조회 응답으로 처리하도록 했다(M1, 0026). (4) Gateway 3초와 처리 시간의 관계, 504 뒤 복구를 명시했다(L9).

- 2026-10-28(ISE-37 구현): CB 실패 분류를 정했다. 0018 9단계("타임아웃·연결 실패·5xx")와 `pg-integration.md`("`Unknown` 전부")가 어긋나 있었다. 결과를 모르는 `Unknown`(`TIMEOUT`·`CONNECTION_LOST`·`PG_ERROR`·`PROCESSING`)만 실패로 세고 `CLIENT_ERROR`는 셈하지 않는다(사용자 선택). 이유: 요청 형식·인증 거절은 PG 장애가 아니라 우리 쪽 요청·설정 문제인데, 한 사용자의 잘못된 요청 약 10건이 CB를 열어 10초간 모든 사용자의 신규 승인을 막을 수 있다. 대가: PG 키 오설정처럼 전체에 걸린 4xx에서는 CB가 열리지 않아 `UNKNOWN` 행이 쌓이므로 `CLIENT_ERROR`는 ERROR 로그와 알림(ISE-41)으로 알린다.

## 면접에서 설명할 한 줄

외부 PG 호출은 "호출할 수 있는지(허가)를 먼저 확인하고, 그 뒤에 기록하고, 호출 직전에 다시 유효성을 보고 호출"하는 순서로 짜서 장애 중에 쓸모없는 결제 행이 쌓이지 않게 했고, 새 의무를 만드는 승인과 기존 의무를 해소하는 복구의 호출 자원을 나눠 승인 장애가 환불을 막지 않게 했다.
