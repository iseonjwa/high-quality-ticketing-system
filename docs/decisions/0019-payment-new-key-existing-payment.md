# 0019. 같은 예매에 다른 멱등키로 재요청하면 기존 결제로 응답하고 새 키는 별칭으로 기록한다

- 상태: 제안 (SA 변경 요청 필요. 2026-10-28 개정)
- 날짜: 2026-10-27
- 결정자: 안준현
- 관련 AI 판단: [결제 상세 설계 빈틈 결정](../ai-judgments/junhyun/2026-10-27-payment-design-gaps.md)
- 관련 결정: [0016](0016-payment-declined-token-reuse.md), [0017](0017-payment-idempotency-in-progress.md), [0018](0018-payment-pg-permit-before-tx1.md), [0026](0026-payment-one-per-reservation.md)
- 불변 조건: INV-1, INV-9([invariants.md](../design/payment/invariants.md))

## 맥락

SA 11-3은 D3 부분 유니크(`reservation_id`, 진행·확정 상태 4개)에 걸린 두 번째 요청을 409 `PAYMENT_ALREADY_EXISTS`로 정한다. 같은 키의 재시도(0017)는 해결했지만, 사용자가 UNKNOWN(확인 중)에 결제 버튼을 다시 눌러 클라이언트가 새 `Idempotency-Key`를 만들면 여전히 409가 된다. 이때 클라이언트는 기존 `paymentId`를 모를 수 있다. 응답이 409뿐이면 사용자는 "이미 결제가 있다"는 말만 듣고 결과를 확인할 방법이 없다.

2026-10-27 원안은 새 키로 연결한 요청을 멱등 기록에 남기지 않고 로그로만 남겼다. 그러면 같은 새 키로 다시 오면 기록이 없어 토큰 검증부터 다시 하고, 토큰이 만료됐으면 403이 된다. 연결 사실도 로그 보관 기간에만 추적된다(Opus 검토 L3).

## 결정

같은 예매에 이미 결제가 있으면 새 PG 승인 호출을 하지 않고 기존 결제로 응답한다. 예매당 결제는 하나다(0026).

| 기존 결제 상태 | 응답 |
|---|---|
| `REQUESTED`·`UNKNOWN` | 202 + 기존 `paymentId`와 상태, `Location`, `nextPollAfterSeconds` |
| `APPROVED` | 200 + 기존 결제 결과 |
| `NEEDS_MANUAL_CHECK` | 409 `PAYMENT_ALREADY_EXISTS` + `Location` 헤더 |
| `DECLINED`·`REFUNDED` | 409 `PAYMENT_ALREADY_CLOSED`(0016), 연결하지 않음 |

기존 결제에 연결하기 전에 핵심 요청 정보가 일치하는지 검증한다.

- 인증 사용자(`X-User-Id`)가 결제의 `user_id`와 같다.
- 토큰의 예매 ID가 결제의 `reservation_id`와 같다.
- 요청 금액이 토큰 금액과 같고 결제의 `amount`와 같다.
- 통화가 결제의 `currency`(`KRW`)와 같다. 요청에 통화 필드는 없으므로 원화 요청으로 보고 결제 행과 대조한다.
- 결제 수단이 결제의 `method`와 같다.

하나라도 다르면 기존 결제 정보를 노출하지 않고 409 `PAYMENT_ALREADY_EXISTS`를 `Location` 없이 돌려준다.

### 새 키는 별칭 기록으로 남긴다
- 검증을 통과해 연결한 새 키는 `idempotency_records`에 `link_type=ALIAS`, `resource_id`=기존 `paymentId`, 새 요청의 `request_hash`로 저장한다. 응답은 저장하지 않는다(`response_status` NULL).
- 같은 새 키로 다시 오면 0017의 멱등 조회 단계에서 이 기록을 찾아 PG 호출 없이 결제의 현재 상태로 응답한다. 본문이 다르면 409 `IDEMPOTENCY_KEY_REUSED`다.
- 저장은 `INSERT … ON CONFLICT (user_id, idem_key) DO NOTHING`이다. 같은 새 키가 동시에 오면 한쪽만 저장되고 다른 쪽은 다시 읽어 같은 응답을 받는다.
- 보관·삭제는 ORIGIN과 같은 규칙이다(만료 24시간 + 연결 결제가 진행 중이 아님, 0022).
- 구조화 로그(INFO, `event=PAYMENT_LINKED_BY_NEW_KEY`, 새 키·`paymentId`·사용자 ID·`traceId`)도 함께 남긴다.

### 토큰 만료 뒤에는 조회만 허용한다
- 토큰 서명·`typ`·`aud`·`sub`·금액은 통과했지만 `exp`가 지난 요청은 "조회 전용"이다. 기존 결제가 있으면 위 검증과 응답을 그대로 하고, 없으면 403 `PAYMENT_TOKEN_INVALID`다. 신규 승인(허가 획득·TX1·PG 호출)은 하지 않는다.
- 만료 뒤 24시간(멱등 기록 보관 기간)이 지난 토큰은 조회에도 쓰지 않는다. 그 뒤에는 `GET /payments/{id}`로 확인한다.

이 규칙은 0018 순서의 5단계(같은 예매의 기존 결제 조회, 허가 획득 전)에 속한다. 토큰의 예매 ID가 필요하므로 토큰 검증 뒤에 온다. 그래서 CB가 OPEN이어도 같은 응답이 나가고 PG를 호출하지 않는다. TX1에서 `reservation_id` 유니크 위반이 나도 같은 단계로 돌아와 이 표로 응답한다(0026).

## 검토한 대안

- **항상 409 + `Location` 헤더**: SA 의미를 그대로 유지한다. 클라이언트가 에러 흐름에서 `Location`을 따라가는 처리를 해야 하고, 가장 흔한 중복 클릭 상황이 에러로 보인다.
- **예매별 조회 API(`GET /payments?reservationId=`) 추가**: 409는 그대로 둔다. API 목록과 소유자 검사 범위가 늘고, 클라이언트가 호출을 한 번 더 한다.
- **새 키를 로그로만 남김(2026-10-27 원안)**: 테이블 쓰기가 없다. 같은 새 키 재요청이 토큰 검증을 다시 거쳐 만료 뒤 403이 되고, 연결 이력이 로그 보관 기간에만 남는다.

## 트레이드오프

| | 얻는 것 | 감수하는 것 |
|---|---|---|
| 기존 결제로 응답 | 중복 클릭·키 재생성에도 사용자가 상태를 끝까지 따라간다. PG를 다시 부르지 않는다 | 409의 의미가 좁아져(NEEDS_MANUAL_CHECK, 정보 불일치) 클라이언트의 키 재생성 실수가 드러나지 않는다 |
| 핵심 정보 검증 후 연결 | 다른 사람의 결제나 다른 금액의 결제를 돌려주지 않는다 | 비교 항목을 코드와 테스트로 유지해야 한다 |
| ALIAS 기록 | 같은 새 키 재요청이 토큰 없이도 같은 결과를 받고, 연결 이력이 DB에 남는다 | 멱등 기록 쓰기가 연결마다 한 번 늘어난다 |
| 만료 토큰은 조회만 | 결과 확인은 막지 않으면서 만료된 토큰으로 새 승인은 못 한다 | 검증 경로가 "신규 가능"과 "조회 전용"으로 나뉜다 |

## 결과

- SA 변경 요청: S-4(`link_type`), S-7(`PAYMENT_ALREADY_EXISTS` 의미와 연결 응답).
- `api.md` 처리 순서 3·4·5단계와 표 B, `data-model.md`의 `idempotency_records`.
- 0016와의 관계: `DECLINED`·`REFUNDED`는 연결하지 않고 409 `PAYMENT_ALREADY_CLOSED`다.
- 테스트: N6(UNKNOWN 중 새 키, 불일치 409, NMC 409 + Location), N24(같은 새 키 재요청 PG 0회, 만료 토큰 조회 전용), APPROVED 뒤 새 키 재요청(200, PG 호출 0회), CB OPEN 중 새 키 재요청, N13(TX1 충돌 뒤 연결).

## 개정 이력

- 2026-10-28: 사용자 결정 7을 반영했다. (1) 새 키를 로그로만 남기던 것을 `idempotency_records`의 ALIAS 기록으로 바꿨다. 같은 키 재요청은 PG 호출 없이 현재 상태로 응답한다. (2) 통화를 검증 항목에 넣었다(결제 `currency` 컬럼 추가, 0023). (3) 토큰 만료 뒤에는 신규 승인 없이 기존 결제 조회만 하도록 나눴다. (4) TX1 유니크 위반도 이 표로 응답한다(0026). 제목을 바꿨다(이전: "같은 예매에 다른 멱등키로 재요청하면 기존 결제로 응답한다").

## 면접에서 설명할 한 줄

중복 요청에 에러만 돌려주지 않고 "이미 진행 중인 결제"로 안내하되, 사용자·예매·금액·통화·수단이 모두 같은 경우에만 연결해 다른 결제를 노출하지 않았고, 연결한 새 키를 별칭으로 기록해 토큰이 만료된 뒤에도 PG를 다시 부르지 않고 결과를 돌려주게 했다.
