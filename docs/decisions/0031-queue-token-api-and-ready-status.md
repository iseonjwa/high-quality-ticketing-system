# 0031. 대기열 입장 토큰은 토큰 API에서만 발급하고 READY 상태를 둔다

- 상태: 제안
- 날짜: 2026-10-29
- 결정자: 권영은 (대기열 담당, 팀 합의 전)
- 관련 AI 판단: [대기열 토큰 API 분리와 READY 상태](../ai-judgments/youngeun/2026-10-29-queue-token-api-ready.md), [대기열 설계 설명 중 AI 근거 두 가지를 바로잡음](../ai-judgments/youngeun/2026-10-29-queue-ai-reasoning-corrections.md)
- 관련 이슈: ISE-68

## 맥락

SA MASTER v3.3과 [ADR 0015](0015-queue-admission-guards.md)에서 입장 토큰은 순번 조회(GET `/queue/me`)가 발급하고, ADR 0015는 대기열 진입(POST `/queue`)도 `issued`에 기록이 있으면 같은 토큰을 다시 응답하게 했다. 구현 이슈를 나누면서 아래 문제가 보였다.

1. **폴링 GET이 상태를 바꾼다**: 차례가 된 사용자의 순번 조회가 `waiting`에서 빼고 `issued`에 기록한다. 사람당 수십~수백 번 불리는 폴링에 쓰기가 섞여, 폴링을 Redis 복제본으로 나눌 수 없고 폴링과 발급을 따로 세거나 제한하기 어렵다.
2. **토큰을 주는 곳이 두 군데다**: 진입과 순번 조회가 모두 토큰을 줄 수 있어 발급 규칙과 테스트가 두 곳에 생긴다.
3. **상태 이름이 하는 일과 맞지 않는다**: 토큰을 주지 않는 응답에서 이미 입장한 사람을 표현할 상태가 없다. `ADMITTED`를 토큰 없이 쓰면 같은 상태가 API마다 다른 모양이 된다.
4. **중간 실패 뒤 만료 시 재입장 틈**: 토큰 발급 Lua가 `issued` 기록 뒤 `waiting` 제거 전에 실패하면 두 곳에 모두 남는다. T 동안은 `issued`를 먼저 보니 문제없지만, 기록이 만료돼 정리되면 `waiting`의 옛 seq(`<= admitted`)로 줄을 다시 서지 않고 입장할 수 있다.
5. **ZSET 항목은 자동 만료가 없다**: Redis TTL은 키 단위라 `issued` 항목 정리를 직접 만들어야 한다.

## 결정

1. **입장 토큰 API를 분리한다**: POST `/api/v1/schedules/{scheduleId}/queue/token`. 처음 발급과 재발급 모두 200이고 응답 모양이 같다. 입장 토큰은 이 API에서만 준다.
2. **응답 상태를 셋으로 둔다**:
   - `WAITING`: 아직 차례가 아님 (`position`, `estimatedWaitSeconds`, `nextPollAfterSeconds`)
   - `READY`: 토큰 API를 부르면 토큰을 받을 수 있음 (차례가 됐거나 이미 발급됨)
   - `ADMITTED`: 토큰을 받음 (토큰 API 응답에서만, `entryToken`, `entryTokenExpiresAt`)
3. **진입과 순번 조회는 같은 상태를 응답한다**: 둘 다 `WAITING` 또는 `READY`를 같은 모양으로 준다. 판단(`issued` 유효 → `READY`, `seq <= admitted` → `READY`, 그 밖 → `WAITING`)과 순번 계산은 앱의 도메인 메서드 한 곳에서 하고 두 API가 같이 쓴다. 진입은 새로 섰으면 201(`Location: /queue/me`), 이미 있으면 200이다.
4. **순번 조회는 읽기 전용이다**: Redis에 쓰지 않는다.
5. **Lua와 앱의 역할**: Lua는 Redis 값을 원자적으로 읽고 쓴 결과(발급 시각, seq, admitted)만 돌려준다. 상태 판단, 순번 계산, 토큰 서명, HTTP 응답은 앱이 한다. 상태 변경을 모두 Lua 안에서 끝내므로, Lua 이후에 앱이 끊기거나 응답이 유실돼도 같은 요청을 다시 하면 같은 결과가 나온다.
6. **토큰 발급 쓰기 순서**: `issued`에 현재 시각을 기록한 뒤 `waiting`에서 뺀다.
7. **`issued` 기록의 유효·만료 판단과 정리**:
   - 모든 대기열 Lua는 현재 시각을 Redis `TIME`으로 정한다. T와 오픈 시각은 인자로 넘긴다.
   - 진입: T 안의 기록이면 `waiting` 잔여를 지우고 `READY`. T가 지난 기록이면 `issued`·`waiting`에서 지우고 새 seq로 줄 선다.
   - 토큰 API: T 안의 기록이면 `waiting` 잔여를 지우고 같은 발급 시각으로 재발급. T가 지난 기록이면 둘 다 지우고 `QUEUE_NOT_JOINED`.
   - 순번 조회: T가 지난 기록이 있으면 `waiting`을 보지 않고 `QUEUE_NOT_JOINED`. 다시 진입한 사용자는 진입 Lua가 기록을 지웠으므로 이 경우는 만료 뒤 다시 진입하지 않은 사용자뿐이다.
   - 입장 처리 Lua(1초마다)가 T가 지난 항목을 최대 500개 꺼내 `issued`·`waiting`에서 함께 지운다.
8. **에러 코드**: 차례 전 토큰 요청은 409 `QUEUE_NOT_READY`(신규). 줄에 없거나 만료됐으면 404 `QUEUE_NOT_JOINED`(기존).
9. **입장 토큰 `jti`**: `entry:{회차 ID}:{userId}:{발급 시각}`의 SHA-256 앞 16바이트(hex). 같은 발급 시각으로 다시 서명하면 글자까지 같은 토큰이 나온다. 검증에는 쓰지 않는다(7-3 "추적·로그용" 유지).
10. **폴링 간격**: 순번 기반 간격(3~10초)에 ±20% jitter를 섞는다.

## 검토한 대안

- **순번 조회가 토큰을 발급 (SA v3.3 현재)**: API가 둘이라 단순하지만 위 맥락 1·2가 남는다.
- **진입은 줄 세우기만 하고 상태를 주지 않음 (201 + `Location`, 중복은 409)**: 백엔드 코드는 가장 깔끔하다. 다만 오픈 순간 모든 사용자가 진입 직후 순번 조회를 한 번 더 불러 가장 붐비는 시점의 요청이 두 배가 되고, 첫 폴링 시각을 서버가 정할 수 없다. 새로고침 뒤 재진입 같은 정상 상황을 4xx로 다루게 된다.
- **진입은 "어디에 있는지"(`WAITING`/`READY`)만 주고 순번은 주지 않음**: 진입 Lua가 `seq`·`admitted`를 이미 읽어 순번이 뺄셈 한 번인데 일부러 빼는 셈이라 근거가 약하다.
- **`READY` 없이 `WAITING` + `position: 0`으로 신호**: 상태 수는 줄지만 이미 토큰을 받은 사람을 `WAITING`이라고 부르게 되고, 프론트가 숫자 값으로 행동을 정한다. 토큰 API를 분리하면서 어차피 계약이 바뀌어 `WAITING` 모양을 지키는 이득도 작다.
- **순번 조회에서도 만료·잔여 기록을 정리 (ZREM)**: 동작에는 문제없고 HTTP상 허용되지만, 폴링을 읽기 전용으로 둬야 복제본 읽기가 가능하다. 정리는 진입·토큰 API와 입장 처리 Lua로 충분하다.
- **`jti`를 빼거나 무작위로 둠**: 빼면 SA 7-3을 고쳐야 하고, 무작위면 재발급마다 토큰 문자열이 달라져 "같은 토큰"이라는 설명과 테스트가 어긋난다. 계산 비용은 해시 한 번이다.

## 결과

- 얻는 것: 폴링 읽기 전용(복제본 분산 가능), 진입·폴링·발급을 API별로 세고 제한 가능, 토큰 발급 규칙 한 곳, 상태마다 프론트 행동 하나, 중간 실패 뒤 만료 시 재입장 차단, 진입 응답부터 폴링 시각 통제, 재발급 토큰 동일성 테스트 가능.
- 감수하는 것: API 1개·상태 1개·에러 코드 1개 추가로 SA 계약 변경, 차례가 된 사람의 요청 1번 추가(초당 N명 수준), 만료 판단 코드가 진입·토큰 Lua 두 곳에 같은 조각으로 들어감(두 API 모두 테스트).
- 확인이 필요한 사람: Gateway(입장 토큰 필터는 그대로), 프론트(`READY` 처리, 토큰 API 호출, `sessionStorage`), 좌석 선점(입장 토큰 형식 그대로).
- 후속 작업: 팀 확인 후 상태를 채택으로 바꾸고 SA MASTER의 🆕 표시를 지운다. 구현 완료 기준은 ISE-52(진입 Lua), ISE-53(진입 API), ISE-54(입장 처리·정리), ISE-55(순번 조회), ISE-57(토큰 API), ISE-20(`jti`)에 넣는다. jitter 적용 전후 초당 폴링 요청 최댓값을 부하 테스트에서 비교한다.
- [ADR 0015](0015-queue-admission-guards.md) 결정 4번 중 "진입·순번 조회가 같은 토큰을 다시 응답"하는 부분과 쓰기 순서를 이 결정으로 바꾼다. `issued` 키와 나머지 결정은 그대로다.
