# 0039. 추첨 자동결제는 전용 토픽 payment.billing과 전용 PG 그룹 pg-billing으로 일반 결제·환불과 나눈다

- 상태: 제안 (추첨 담당 제안안, 결제 담당 확인 대기, ISE-89. 최종 구현은 결제 담당이 고른다)
- 날짜: 2026-10-31
- 결정자: 이강민 (추첨 담당)
- 관련 AI 판단: [자동결제 Bulkhead 제안](../ai-judgments/kangmin/2026-10-30-lottery-billing-bulkhead-proposal.md), [선반영 후 보고](../ai-judgments/kangmin/2026-10-31-lottery-sa-sync-apply-first-report-later.md)
- 상세: [`docs/design/lottery/options.md`](../design/lottery/options.md) D6, 학습 노트 [`2026-10-30-lottery-billing-bulkhead.md`](../learning/kangmin/qna/2026-10-30-lottery-billing-bulkhead.md)

## 맥락
- 결제 설계의 승인 그룹 `pg-approve`는 동시 10, 대기 0이다([0018](0018-payment-pg-permit-before-tx1.md)). 추첨 직후 자동결제 2,000건 `[가정]`이 이 자리를 채우면 다른 회차 일반 결제가 즉시 503이 된다(측정 시나리오 2, [0036](0036-lottery-direction-measurement.md)).
- SA 10-1은 자동결제 요청 `BillingPaymentRequested`를 환불 요청과 같은 `payment.command`에 두었다. 자동결제가 PG 허가를 기다리며 오프셋을 넘기지 않으면 그 뒤의 환불 요청도 밀린다.

## 결정
추첨 쪽 요구 조건은 확정한다.
1. 자동결제가 일반 결제의 동시 자리를 침범하지 않는다.
2. 당첨 자동결제 95%를 10분 안에 처리한다.
3. 허가를 기다리는 동안 요청이 유실되거나 DLQ로 가지 않는다.

이를 만족하는 구현으로 아래를 제안하고, SA 10-1·6-6·6-7에 토픽 분리를 먼저 반영한다(10/31 선반영).
- 자동결제 전용 Bulkhead `pg-billing` 동시 3(인스턴스당). 3 ÷ 0.3초 `[가정]` = 초당 약 10건, 2,000건에 약 3.3분.
- 전용 토픽 `payment.billing`(파티션 3 이상)과 전용 리스너. 리스너 동시성은 그룹 동시 수와 같게 둔다.
- 허가를 못 얻으면 오프셋을 넘기지 않고 잠시 뒤 다시 시도한다(백프레셔). DLQ로 보내지 않는다.
- Circuit Breaker 상태는 그룹별로 둔다. 빌링키 무효가 많다고 일반 결제까지 OPEN되면 안 된다.

## 검토한 대안
- **`pg-approve`를 같이 쓴다**: 변경이 없다. 일반 결제가 503을 맞고 막을 수단이 없다.
- **같은 그룹을 쓰되 일반 판매가 없는 시간에만 자동결제**: 자원 분리가 없다. 다른 회차·공연 판매는 언제든 열려 있을 수 있다. 추첨 시각은 저트래픽 시간대를 권장하되(D10 운영 정책) 이것만으로 막지 않는다.
- **`payment.command`를 그대로 쓴다**: 토픽이 늘지 않는다. 환불 요청이 자동결제 뒤에 밀린다.

## 결과
- 얻는 것: 자동결제 폭주가 일반 결제와 환불에 번지지 않는다. 처리 속도를 동시 수 하나로 조절하고 측정할 수 있다.
- 감수하는 것: 결제 쪽 설정·토픽·리스너가 하나씩 는다. PG에 걸리는 동시 수가 최대 13이 되므로 실제 PG 한도 확인이 필요하다.
- 확인할 것: 토스 빌링 API 응답 시간과 동시 호출 한도, payment-service 인스턴스 수.
- 바꿀 조건: 시나리오 2에서 10분 안 95%를 못 지키면 동시 수를 올린다. PG 전체 한도에 걸리면 시간대 분리를 섞는다. 결제 담당이 다른 구현을 고르면 요구 조건 3개를 만족하는지로 판단하고 이 ADR을 대체한다.
