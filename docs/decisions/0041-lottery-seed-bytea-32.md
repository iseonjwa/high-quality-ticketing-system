# 0041. 추첨 시드는 BIGINT가 아니라 BYTEA 32바이트로 저장한다

- 상태: 채택
- 날짜: 2026-11-02
- 결정자: 이강민 (추첨 담당)
- 관련 AI 판단: [11/2 일지](../ai-judgments/kangmin/daily/2026-11-02.md)

## 맥락
- SA 12-3은 `lotteries.seed`를 `BIGINT`(8바이트, NULL 허용)로 적었다.
- 머지된 순위 계산 `DrawRanker`(ISE-84)는 `SecureRandom` 32바이트 시드를 만들고 `SHA-256(seed ‖ entryId)`로 순위를 정한다. 해시 입력 형식은 공개 계산식이라 바꾸면 이미 진행한 추첨을 재현할 수 없다.
- 추첨 테이블 마이그레이션(ISE-85)을 쓰면서 이 차이를 발견했다.

## 결정
- `seed BYTEA NOT NULL`에 `CHECK (octet_length(seed) = 32)`를 둔다. 설정 때 채우므로 NULL을 허용하지 않는다.
- SA 12-3, ERD 그림 3, `docs/design/lottery/details.md` 1절을 같은 내용으로 고친다.

## 검토한 대안
- `BIGINT`로 SA를 따르고 `DrawRanker`를 8바이트 시드로 바꾸기: 시드 공간이 2^64로 줄고, 이미 테스트까지 마친 순위 계산 코드와 테스트를 다시 고쳐야 한다.
- 컬럼을 빼고 팀 확인 뒤 정하기: 추첨 담당 영역 안의 결정이라 다른 서비스에 영향이 없어 기다릴 이유가 작다.

## 결과
- 얻는 것: 코드와 스키마가 같은 시드 형식을 쓴다. 시드를 추측해 순위를 미리 계산하기가 사실상 불가능하다(256비트). 시드 약속(확장안 ISE-95)의 `SHA-256(seed)`도 그대로 쓸 수 있다.
- 감수하는 것: 시드를 사람이 읽으려면 hex로 바꿔 보여 줘야 한다(공개 조회 API에서 DRAWN 뒤 공개할 때).
