# 0042. 빌링키는 AES-256-GCM으로 암호화해 저장하고 키는 환경변수 BILLING_KEY_SECRET으로만 주입한다

- 상태: 제안 (결제 담당 리뷰 대기)
- 날짜: 2026-11-02
- 결정자: 이강민 (추첨 담당, 결제 영역 작업은 결제 담당 리뷰)
- 관련 AI 판단: [11/2 일지](../ai-judgments/kangmin/daily/2026-11-02.md)
- 관련 결정: [0025](0025-payment-token-secret-injection.md)(결제 토큰 키 주입), [0023](0023-payment-pg-client-port.md)(PG 포트)

## 맥락
- SA 12-4 `billing_keys.billing_key_enc`는 "암호화 저장"이라고만 적었고, 결제 설계(`data-model.md` 11절)는 암호화 키 관리를 M4로 미뤘다.
- 11/2 팀 합의로 추첨과 빌링키 자동결제(F5-4·5)가 M2 필수 기능이 되어 ISE-96에서 지금 정해야 한다.
- 빌링키는 그 값만으로 결제를 일으킬 수 있다. DB나 백업이 새도 원문이 드러나면 안 된다.

## 결정
1. **알고리즘**: AES-256-GCM. IV는 암호화마다 `SecureRandom` 12바이트, 태그 128비트. 저장 값은 Base64(IV ‖ 암호문 ‖ 태그)다. GCM 태그로 값이 바뀌었거나 다른 키로 암호화된 것을 복호화 단계에서 잡는다.
2. **키 형식과 주입**: 다른 비밀값과 같은 소문자 16진수 64자 문자열을 환경변수 `BILLING_KEY_SECRET`으로 payment-service에만 준다. `config-repo/payment-service.yml`에는 자리표시자만 둔다. `./gradlew initLocalEnv`가 `.env`에 없을 때 만든다.
3. **키 바이트 해석**: 0025(결제 토큰)와 달리 **16진수로 디코딩한 32바이트**를 쓴다. HMAC은 키 길이가 자유롭지만 AES-256은 정확히 32바이트여야 한다. 두 키는 용도가 달라 해석이 달라도 어긋날 상대가 없다(발급·검증이 한 서비스 안).
4. **기동 시 검증**: 값이 없거나, 64자가 아니거나, 소문자 16진수가 아니면 기동을 실패시킨다. 오류 메시지에 키 값을 넣지 않는다.
5. **원문 사용 범위**: 원문은 PG 자동결제 호출 직전에만 복호화하고 로그·응답에 남기지 않는다. 등록 응답에는 카드 끝 4자리만 준다.

## 검토한 대안
- DB 기능(`pgcrypto`)으로 암호화: 키를 SQL 파라미터로 넘겨야 해서 DB 로그·통계에 키가 남을 수 있다.
- AES-CBC + HMAC: 같은 보장을 얻으려면 두 단계를 직접 조합해야 한다. GCM은 한 번에 기밀성과 무결성을 준다.
- 외부 KMS(봉투 암호화): 운영 환경에는 맞지만 부트캠프 배포 1회 범위에서 인프라가 늘어난다. 키 교체 절차와 함께 M4 후보로 둔다.

## 결과
- 얻는 것: DB만 새서는 빌링키를 쓸 수 없다. 키가 틀리거나 값이 바뀌면 복호화가 실패하고, 자동결제는 `BILLING_KEY_MISSING`으로 거절돼 추첨 승계로 넘어간다.
- 감수하는 것: 키를 잃으면 저장된 빌링키를 모두 다시 등록받아야 한다. 키 교체(재암호화) 절차가 없다. 같은 IV가 반복되면 GCM 기밀성이 깨지므로 IV를 고정하면 안 된다(테스트가 막는다).
- 바꿀 조건: 실제 PG(토스) 연동과 운영 배포를 하면 KMS·키 교체를 검토한다(M4).
