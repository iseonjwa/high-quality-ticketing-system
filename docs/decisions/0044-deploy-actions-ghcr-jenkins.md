# 0044. 배포는 GitHub Actions가 이미지를 GHCR에 올리고, 별도 EC2의 Jenkins가 main 머지 때 배포 EC2에 반영한다

- 상태: 제안 (팀 공유 필요. AWS 계정과 인스턴스 크기는 미정)
- 날짜: 2026-11-03
- 결정자: 안준현(사용자 결정)
- 관련 AI 판단: [배포·관측·부하 측정 설계 선택](../ai-judgments/junhyun/2026-11-03-deploy-observability-loadtest-design.md)
- 관련 설계: [`design/infra/deployment.md`](../design/infra/deployment.md)

## 맥락

- M3 완료 기준은 EC2 배포 1회와 MVP 시연이다(ISE-6). SA 9-1은 EC2 한 대에 docker compose로 띄우는 구성이고, 9-2는 Gateway 8080만 공개한다.
- 지금 CI(GitHub Actions)는 빌드·테스트와 기록 검사만 한다. 배포용 이미지를 만드는 곳이 없다.
- EC2에서 직접 빌드하면 7개 앱의 Gradle 빌드에 5~10분과 별도 메모리가 들고, 떠 있는 서비스와 자원을 다툰다. 어느 커밋이 떠 있는지도 흐려진다.
- 사용자는 Jenkins로 배포 파이프라인을 다뤄 보기를 원했다.

## 결정

1. **CI와 이미지는 GitHub Actions**: main에 머지되면 서비스 이미지를 빌드해 GHCR(GitHub Container Registry)에 커밋 SHA 태그로 올린다. dev → main 머지가 릴리스다.
2. **배포는 Jenkins**: 배포 EC2와 분리한 작은 EC2(t3.small급 `[가정]`)에 Jenkins를 둔다. UI는 공개하지 않고 SSH 터널로만 연다(SA 9-2 방식). 배포 EC2는 Jenkins EC2의 SSH만 받는다.
3. **배포 시점은 main 머지 자동**: Jenkins가 main을 폴링으로 감지한다(Jenkins를 웹훅에 열지 않기 위해서다). 그 SHA 이미지가 GHCR에 있으면 배포 EC2에서 `docker compose pull`·`up -d` → 헬스 대기 → 스모크 테스트 → 슬랙(#이선좌-배포상태알림) 알림 순으로 진행한다. 실패하면 직전 성공 태그로 되돌린다. 태그를 골라 다시 배포하는 수동 실행도 둔다.
4. **스모크 테스트**: 기본은 가볍게 한다(Gateway 경유 헬스, 가입·로그인, 공연 목록). 회차마다 좌석 15,000석을 만드는 `BookingFlowSystemTest`는 파라미터로 고를 때만 돈다.
5. **비밀값**: 서버 `.env`는 서버에서 만든다(저장소에 올리지 않음). GHCR 읽기 토큰, 배포 SSH 키, 슬랙 웹훅은 Jenkins Credentials에만 둔다.
6. **인스턴스 크기(SA U10)**: 로컬에서 부하를 걸어 측정한 뒤 16GB급과 8GB급 중 고른다.

## 검토한 대안

- **EC2에서 직접 빌드**: 가장 단순하다. 빌드가 운영 자원과 시간을 쓰고, 배포된 커밋을 이미지로 고정하지 못한다.
- **로컬에서 빌드해 올림**: CI 설정이 없다. 사람마다 결과가 다르고 Mac(ARM)에서 EC2(x86)로 교차 빌드해야 한다.
- **Jenkins가 빌드부터 배포까지**: 도구 하나로 끝난다. Jenkins 서버에 빌드 자원이 더 필요하고, 이미 있는 Actions CI와 일이 겹친다.
- **Jenkins를 배포 EC2에 같이 둠**: 비용이 없다. 메모리 0.5~1GB가 더 들어 16GB급이 필요해지고 부하 측정에 끼어든다.
- **로컬(노트북) Jenkins**: 비용이 없다. 노트북이 켜져 있을 때만 배포할 수 있고 팀원이 쓰지 못한다.
- **이미지는 자동, 배포는 수동 실행**(AI 추천): 시연·측정 중에 환경이 바뀌지 않는다. 사용자는 main 머지를 릴리스로 삼아 자동 배포를 골랐다. 대신 측정·시연 중에는 main 머지를 멈추는 운영 규칙이 필요하다.

## 결과

- 얻는 것: 배포된 버전이 커밋 SHA 이미지로 고정되어 되돌리기가 쉽다. 빌드가 운영 자원과 분리된다. CI(검증·이미지)와 CD(배포·확인·되돌림)의 경계가 분명하다.
- 감수하는 것: Jenkins EC2의 비용과 관리, 폴링 간격만큼의 배포 지연, GHCR·SSH 자격 증명 관리, main 머지가 곧 배포라는 릴리스 규율.
- 후속: 이미지 빌드 워크플로, 배포용 compose(GHCR 이미지 참조, SA 9-3 상한), Jenkins EC2와 Jenkinsfile, 인스턴스 크기 측정, 배포 DB 시드, 프론트 nginx 컨테이너(ISE-109). ISE-6 하위 이슈로 진행한다.
- SA 변경 요청: SA 9-1·9-2에 Jenkins EC2와 그 보안그룹 규칙을 더한다.
