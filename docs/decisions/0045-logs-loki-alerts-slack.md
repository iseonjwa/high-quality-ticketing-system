# 0045. 로그는 Grafana Alloy로 모아 Loki에 두고 요청마다 한 줄을 남기며, Prometheus 알림은 Alertmanager로 팀 슬랙에 보낸다

- 상태: 제안 (팀 공유 필요. 슬랙 채널은 2026-11-04에 만듦)
- 날짜: 2026-11-03
- 결정자: 안준현(사용자 결정)
- 관련 AI 판단: [배포·관측·부하 측정 설계 선택](../ai-judgments/junhyun/2026-11-03-deploy-observability-loadtest-design.md)
- 관련 설계: [`design/infra/observability.md`](../design/infra/observability.md)

## 맥락

- 지금 스택에는 지표(Prometheus·Grafana)와 트레이스(Zipkin)만 있다. 로그는 컨테이너마다 `docker logs`로 따로 봐야 하고, 결제 알림 규칙 22개(ADR 0024)는 보낼 곳이 없다.
- 시연에서 "요청 하나가 서비스를 어떻게 지나가는지"를 로그로 보여 주고 싶다. 모든 응답 본문에 `traceId`가 있고, 로그 줄에도 traceId가 찍힌다.
- 그런데 예매 한 흐름(가입, 대기열, 선점, 결제, 확정)을 돌려도 서비스 로그에는 요청에서 나온 줄이 없었다(2026-11-03 확인). 서비스는 오류·업무 사건만 로그로 남기고 요청마다 남기는 접근 로그가 없다.
- SA 9-2는 Grafana 같은 관리 UI를 공개하지 않고 SSH 터널로만 연다.

## 결정

1. **로그**: Grafana Alloy가 컨테이너 로그를 모아 Loki에 저장하고, 기존 Grafana에서 본다. 로그 형식(패턴)은 바꾸지 않고 Alloy에서 traceId를 뽑는다. 라벨은 서비스 이름 정도로 적게 둔다. 보관은 7일 `[가정]`.
2. **공통 요청 로그**: Gateway(전역 필터)와 서블릿 서비스(common 필터)가 요청마다 한 줄을 남긴다. 메서드, 경로 템플릿, 상태, 처리 시간만 남기고 본문·헤더·토큰·쿼리 값은 넣지 않는다. `/actuator/**`는 남기지 않고 설정으로 끌 수 있다. 모든 서비스에 걸리는 변경이라 `contract` 이슈로 알리고 결제 담당이 구현한다.
3. **요청 로그 대시보드**: traceId 변수로 서비스별 로그를 시간순으로 보고, 같은 traceId의 Zipkin 트레이스로 가는 링크를 둔다.
4. **알림**: Alertmanager를 더해 Prometheus 알림을 팀 슬랙 워크스페이스의 새 채널 `#이선좌-성능-모니터링`으로 보낸다. 해결 알림도 보낸다. Jenkins 배포 결과는 `#이선좌-배포상태알림`으로 보낸다(0044). 웹훅 주소는 `.env`와 Jenkins Credentials에만 둔다. 결제 한 건에 묶이는 알림(유저·결제 시각을 담는 알림)은 결제 서비스의 건별 사건 로그를 Loki 규칙이 읽어 같은 Alertmanager로 보낸다(2026-11-04 사용자 결정, 결제 서비스가 슬랙에 직접 보내는 안은 고르지 않았다).
5. **시연은 나란히 띄우기부터**: M3에는 프론트와 Grafana(발표자 노트북의 SSH 터널)를 나란히 띄운다. 프론트가 요청마다 traceId를 보여 주면 대시보드가 그 traceId로 로그를 거른다. 프론트 안 로그 패널(관리자 전용 API가 traceId로 Loki를 조회)은 M4 후보로 둔다.

## 검토한 대안

- **ELK(Elasticsearch·Logstash·Kibana)**: 검색이 강하고 널리 쓰인다. 메모리가 2GB 안팎 더 들고, Grafana와 화면이 나뉜다.
- **docker logs만**: 설정이 없다. 서비스를 가로질러 한 요청을 따라가기 어렵고 시연에 쓰기 어렵다.
- **Zipkin 트레이스만으로 시연**: 코드 변경이 없다. 서비스 구간과 시간은 보이지만, 시연에서 보여 주려던 로그 자체는 오류·배경 작업만 남아 비어 보인다.
- **Gateway 접근 로그만**: 변경이 작다. 서비스 안쪽 흐름은 로그에 없고 Zipkin에만 보인다.
- **앱 로그를 JSON으로 바꾸고 Loki로 직접 보냄**: 파싱이 쉽다. 모든 서비스의 로그 설정을 바꾸는 팀 공통 변경이고, 수집기를 거치는 방식보다 앱이 Loki 장애에 묶인다.
- **프론트 안 로그 패널부터**: 시연 효과가 크다. 새 관리자 API와 화면이 필요해 M3 일정에 부담이 되어 M4로 미뤘다.

## 결과

- 얻는 것: 지표·트레이스·로그를 Grafana 한곳에서 traceId로 잇는다. 결제 알림이 실제로 사람에게 간다.
- 감수하는 것: Loki·Alloy·Alertmanager의 메모리(합계 약 0.9GB `[가정]`)와 설정 관리, 슬랙 웹훅 비밀값 관리. 요청 로그만큼 로그 양이 늘어 부하 측정 때는 끌 수 있어야 한다.
- 후속: 공통 요청 로그 필터(`contract` 이슈), Loki·Alloy·로그 대시보드, Alertmanager·슬랙 연결, 프론트의 traceId 표시(프론트 세션). SA 9-1·9-3에 세 구성 요소와 메모리를 더하는 SA 변경 요청.
