# 0046. 부하 측정은 k6를 같은 리전의 임시 EC2에서 돌리고, 오픈 피크 전체 시나리오와 공통 측정 기반을 함께 만든다

- 상태: 제안 (팀 공유 필요. ISE-25 담당과 분담 확인). 측정용 토큰 키는 2026-11-08에 변경(아래 "변경")
- 날짜: 2026-11-03
- 결정자: 안준현(사용자 결정)
- 관련 AI 판단: [배포·관측·부하 측정 설계 선택](../ai-judgments/junhyun/2026-11-03-deploy-observability-loadtest-design.md)
- 관련 설계: [`design/infra/load-test.md`](../design/infra/load-test.md)

## 맥락

- SA 3-1은 좌석 선점 API의 동기형 기준선 → 병목 확인 → 접수형 개선 → 재측정과 포화점을 목표로 둔다. 부하 도구는 다른 기기에서 돌리고 측정 환경 기록표를 남긴다. 도구는 정하지 않았다.
- 동기형 선점 기준선 측정은 ISE-25(권영은)다. 결제·대기열·예매가 이어진 오픈 피크 흐름을 재는 사람은 정해지지 않았다.
- 결과를 서버 지표(Prometheus·Grafana)와 같은 시간축에서 보고 싶다.

## 결정

1. **도구는 k6**: 스크립트를 저장소에 두고 CLI로 돌린다. 결과는 Prometheus remote write로 보내 서버 지표와 같은 Grafana에서 본다.
2. **발생기는 같은 리전 임시 EC2**: 측정할 때만 같은 VPC에 연산형 인스턴스(c6i.large급 `[가정]`)를 띄우고 끝나면 지운다. Gateway는 VPC 내부 주소로 부르고, 보안그룹은 발생기 보안그룹에서 8080만 허용한다.
3. **범위**: 결제 담당(안준현)이 공통 측정 기반과 오픈 피크 전체 시나리오를 설계한다.
   - 공통 측정 기반: 발생기, 가상 사용자·토큰 준비, 회차·좌석 초기화, loadtest 프로필, 결과 기록표, 대시보드
   - 오픈 피크 전체 시나리오: 대기열 폭주 → 순번 조회 → 입장 → 선점 경합 → 결제 → 확정
   - ISE-25의 기준선 측정은 같은 기반의 "선점 경합" 시나리오를 쓴다(분담은 ISE-25에서 확인).

## 변경 (2026-11-08, ISE-191)

배포 환경 측정에 필요한 준비를 정하면서 "감수하는 것"에 적은 운영 키 위험을 이렇게 푼다. 결정자는 안준현(사용자 결정)이다.

- **측정용 토큰은 측정 동안만 측정 전용 키로 바꿔 띄운다.** `script/loadtest/measure-mode.sh on`이 `JWT_ACCESS_SECRET`·`ENTRY_TOKEN_SECRET`을 새 무작위 값으로 만들어 서버의 `.env.measure`에 두고 스택을 다시 띄운다. k6(발생기)는 그 키로 토큰을 서명한다. 끝나면 `off`가 운영 키로 되돌리고 측정 전용 키를 버린다.
- **운영 키와 운영 관리자 비밀번호는 발생기에 두지 않는다.** 발생기에는 측정 전용 키만 간다. 회차는 서버에서 `seed-demo.sh`로 준비하고 Q1~Q3은 `SCHEDULE_ID`로 받는다.
- 결정 1번(결과를 Prometheus remote write로 보냄)의 구현: 측정 모드 동안만 Prometheus에 `--web.enable-remote-write-receiver`와 9090을 열고, 보안 그룹은 발생기 보안 그룹의 9090만 허용한다. 추적 샘플링은 측정 모드에서 0.01, Mock PG 기준 지연은 300ms다.
- 대안으로 ISE-69 발급 API를 기다리는 안을 두지 않았다. 그 API가 입장 토큰만 줄 뿐 Access 토큰 3만 개를 미리 만드는 문제는 풀지 못한다.
- 감수하는 것: 측정 모드 동안 기존 로그인이 끊기고, 측정 중 Jenkins 배포가 돌면 측정 모드가 풀린다. 그래서 측정 동안 main 머지를 멈추거나 Jenkins 잡을 끈다. `measure-mode.sh`는 "서버에서 직접 `docker compose up` 하지 않는다" 규칙의 예외이며 계정 주인만 쓴다.
- 구현·절차: [`design/infra/load-test.md`](../design/infra/load-test.md) 2-1, 5절, `loadtest/deploy/compose.measure.yml`.

## 검토한 대안

- **nGrinder**: 국내에서 많이 쓴다. 웹 UI와 컨트롤러·에이전트 구성이라 띄울 것이 많고, 결과가 Grafana와 따로 논다.
- **노트북에서 실행**: 비용이 없다. 집·카페 네트워크와 노트북 성능이 결과에 섞인다.
- **Jenkins EC2에서 실행**: 따로 띄우지 않아도 된다. t3.small은 부하를 만들기에 작고, 배포 도구와 측정이 섞인다.
- **공통 기반과 결제 시나리오만 맡음**(AI 추천): ISE-25와 겹칠 일이 적다. 사용자는 오픈 피크 전체 흐름까지 맡기로 했다.

## 결과

- 얻는 것: 서버 지표와 부하 결과를 한 화면에서 비교한다. 측정 환경을 같은 리전으로 고정해 다시 내기 쉽다.
- 감수하는 것: 측정마다 EC2 비용과 준비 시간이 든다. 입장 토큰 발급 API(ISE-69)가 없으면 측정용 토큰 서명이 필요해 운영 키를 측정 도구에 넣는 위험이 생긴다. 이 위험은 측정 전용 키로 푼다("변경" 절).
- 후속: k6 스크립트와 실행 방법, 발생기 EC2 절차, 데이터 준비 스크립트, Mock PG `local,loadtest` 덮어쓰기(ISE-71), 결과 기록표. 측정 결과로 EC2 크기(SA U10)와 컨테이너 상한을 정한다.
- SA 변경 요청: SA 3-1의 "다른 기기"를 같은 리전 임시 EC2로 구체화한다.
