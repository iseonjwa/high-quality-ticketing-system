# 0047. 배포는 EC2 한 대에 DB·캐시·브로커까지 띄워 시작하고, 서버를 멈춘 기간(11/7~11/12)에 RDS 등 매니지드 서비스 분리를 검토한다

- 상태: 채택(단일 EC2로 시작). 매니지드 서비스 분리는 검토 예정(11/7~11/12)
- 날짜: 2026-11-04
- 결정자: 안준현(사용자 결정)

## 맥락

- SA 9-1은 EC2 한 대에 docker compose로 모든 구성 요소를 띄운다. SA 9-3은 이 구성의 메모리 예산과 단일 EC2 한계(인스턴스 장애 시 전체 중단)를 적었다. 10/26 피드백 답변에서 "프로젝트 범위에서는 컨테이너 분리까지만 한다"고 정했다.
- 지금 배포 compose(`compose.deploy.yml`, ISE-174)는 앱 8개와 PostgreSQL 3개(user·reservation·payment), Redis, Kafka, 관측 도구를 모두 배포 EC2(16GB급) 한 대의 컨테이너로 띄운다. 데이터는 그 EC2 디스크(EBS)의 docker 볼륨에 있고 백업은 없다.
- 리허설이 금요일(11/6)이라 11/4~11/5에 배포를 끝내야 한다.
- 비용(시드니 온디맨드): 배포 EC2와 Jenkins EC2를 함께 켜면 하루 약 6.8달러다. 사용자는 11/6까지 켜 두고, 11/7~11/12는 중지하고, 11/13~11/19에 다시 켜기로 했다(11/19까지 약 65달러).
- AWS 계정은 새 가입 방식(Paid plan)이다. RDS와 ElastiCache는 쓸 수 있고, MSK(Kafka)는 Paid plan 서비스 목록에 있다.

## 결정

1. **지금은 단일 EC2로 배포한다.** 리허설 전 배포를 늦추지 않고, SA 9-1 구성 그대로 간다.
2. **운영 일정:** 11/6까지 켜 둔다 → 11/7~11/12 중지(데이터는 EBS에 남고 컨테이너는 재시작 정책으로 다시 뜬다) → 11/13~11/19 다시 켠다 → 그 뒤 인스턴스·EBS·탄력적 IP를 지운다. M3 마감(11/11)에 서버 확인이 필요하면 그날만 켠다.
3. **중지 기간(11/7~11/12)에 상태를 가진 구성 요소를 매니지드 서비스로 뺄지 검토한다.** 검토 항목은 아래와 같고, 정하면 이 ADR을 갱신하거나 새 ADR로 남긴다.
   - PostgreSQL 3개 → RDS for PostgreSQL. 인스턴스 하나에 DB 셋, 또는 서비스마다 인스턴스. 앱은 `DB_URL` 환경 변수만 바꾸면 되는지
   - Redis → ElastiCache. Kafka는 MSK 비용이 크므로 EC2에 남길지 함께 본다
   - 비용(11/13~11/19 7일 기준)
   - 옮기는 방법: `pg_dump`·복원, 또는 시드 스크립트로 다시 만들기
   - 보안 그룹: DB는 배포 EC2 보안 그룹에서만 허용
   - 부하 측정(ISE-181, M4)과의 순서. 분리하면 측정 대상 구성이 바뀌므로 측정 전에 정한다
   - SA 9-1·9-3 변경 요청

## 검토한 대안

| 안 | 고르지 않은 이유 |
|---|---|
| 처음부터 RDS·ElastiCache로 분리 | 리허설 전 이틀 안에 구성·보안 그룹·이전까지 끝내기 어렵다. 비용도 늘어난다 |
| 분리를 검토하지 않음 | 단일 장애점·자원 경쟁·백업 부재를 설명만 하고 끝난다. 서버를 멈추는 기간이 있어 검토할 시간이 생긴다 |

## 결과

- 얻는 것: 리허설 전 배포가 단순하다(compose 하나, 스크립트 하나). 서버를 멈춘 동안 비용이 디스크·탄력적 IP만 남는다.
- 감수하는 것: 인스턴스가 멈추면 전체가 멈춘다. 앱과 DB가 CPU·메모리를 나눠 써 부하 측정 값에 영향이 있다. 백업이 없어 인스턴스를 "종료"하면 데이터가 사라진다(시연 데이터는 `script/deploy/seed-demo.sh`로 다시 만든다).
- 후속: 11/7~11/12 매니지드 분리 검토(위 3번). 정하면 `deployment.md`와 SA 변경 요청을 갱신한다.
