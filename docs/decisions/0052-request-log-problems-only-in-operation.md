# 0052. 운영 요청 로그는 5xx·끊긴 요청·200ms 이상만 남기고, 정상 요청은 트레이스와 지표로 본다

- 상태: 채택 (2026-11-13, 1단계 Gateway. 마감 일정 때문에 결제 담당 확인 전에 선조치 후보고로 채택했다. 이견은 ISE-230에서 받는다. 2단계 공통 필터는 contract 이슈로 서비스 담당 확인 뒤)
- 날짜: 2026-11-12
- 결정자: 이강민(사용자 결정)
- 관련 AI 판단: [실패·느린 요청만 남기는 안(B) 선택](../ai-judgments/kangmin/2026-11-11-request-log-failures-and-slow-only.md)
- 관련 측정: [open-peak-scenarios.md](../design/infra/open-peak-scenarios.md) "배포 서버 7차" H2
- 대체하는 결정: [ADR 0045](0045-logs-loki-alerts-slack.md) 결정 2 "요청마다 한 줄"의 **운영 기본값만**. 필드(메서드·경로·상태·시간), 본문·헤더 제외, `/actuator` 제외, `enabled`로 끄기는 그대로다. 로컬은 지금처럼 모든 요청을 남긴다

## 맥락
- ADR 0045는 시연에서 요청 흐름을 로그로 보이려고 요청마다 한 줄을 남기기로 했다. 끄는 것은 부하 측정 때만 쓴다고 봤다.
- 배포 서버 7차 H2(2026-11-11)에서 Gateway 요청 로그만 끄자 서버 CPU가 1,000/s 78% → 66%, 1,500/s 93% → 85%로 내려갔고 2,500/s 굿풋이 1,814 → 2,122였다. Gateway CPU는 거의 같았고(114% → 111%) 로그 수집기 Alloy(22% → 14%)와 컨테이너 밖 CPU가 줄었다. 비용은 대부분 JVM 밖 로그 경로(표준 출력 → Docker → Alloy → Loki)에 있었다. 5차 JFR의 로그 몫 5.2%는 이 비용을 보지 못했다.
- 오픈 피크에 가장 많은 응답은 정상 업무 거절일 수 있다(좌석 `SEAT_ALREADY_HELD` 409, 대기열 `QUEUE_NOT_READY` 409). 이것까지 남기면 절감이 사라진다.
- 배포 서버는 추적 샘플링이 1.0이라 정상 요청도 Zipkin에서 traceId로 볼 수 있다. 개수와 지연은 `http_server_requests` 지표에 있다. Loki 경보 규칙(`infra/loki/rules/payment-events.yml`)은 결제 사건 줄만 읽고 요청 로그를 읽지 않는다.

## 결정
1. `iseonjwa.request-log.mode`를 더한다. `all`은 모든 요청, `problems`는 상태 `min-status`(기본 500) 이상, 클라이언트가 끊은 요청(Gateway `CANCELLED`), 처리 시간 `slow-threshold`(기본 200ms) 이상만 남긴다. 키가 없으면 `all`이다.
2. 느린 기준 200ms는 굿풋 정의("200 응답이면서 200ms 안")와 같게 둔다. 로그에 남는 요청은 굿풋에서 빠진 요청이다.
3. 운영(config-repo 기본) `problems`, 로컬(`application-local.yml`) `all`. 시연도 `problems`로 하고 "정상 요청은 트레이스, 문제 요청은 로그"로 보인다.
4. 줄 수준은 INFO 그대로다. WARN으로 올리면 요청 로그 대시보드의 "최근 경고·오류" 패널이 503 줄로 덮인다.
5. 판정 규칙은 common `RequestLogPolicy` 하나를 Gateway와 서블릿 필터가 함께 쓴다. 1단계는 Gateway(`config-repo/gateway.yml`), 2단계는 공통 필터와 `config-repo/application.yml` 기본값이며 2단계 전에 `contract` 이슈를 올린다.

## 검토한 대안
- A. 운영도 끔: 절감이 가장 크고 코드 변경이 없다. 실패 요청도 로그로 못 찾는다.
- C. 표본(1% 등): 요청 흐름을 비율로 본다. 특정 실패 요청을 못 찾을 수 있다.
- D. 측정 때만 끔: 오픈 순간 실제 운영에서는 절감이 없다.
- 4xx 전부 남김: 오픈 피크의 409·429가 대부분이라 절감이 사라진다. `min-status: 400`으로 켤 수 있게만 둔다.
- 느린 기준 100ms(G1 판정 p95 기준): 1,500/s p99 88ms라 피크 꼬리가 걸리기 시작한다.

## 결과
- 얻는 것: 문제 요청은 지금처럼 traceId로 로그에서 찾고, 정상 요청 줄의 로그 경로 비용을 뺀다.
- 감수하는 것: 요청 로그 대시보드의 "이 요청의 로그"·서비스별 패널이 정상 요청에서 빈다(트레이스 패널은 그대로). Gateway와 서비스의 기준이 2단계 전까지 다르다. 실패가 급증하면(차단기 열림 등) 줄 수가 실패율만큼 다시 는다.
- 바꿀 조건: 배포 측정에서 `problems`의 서버 CPU가 끔(H2 재측정)보다 4%p 넘게 높으면 기준을 좁히거나 A를 다시 본다. 실패 줄이 초당 수백 건을 넘어 CPU를 다시 잡으면 실패 줄 속도 제한을 더한다. 정상 요청 흐름이 꼭 필요했던 장애 사례가 나오면 표본(C)을 `mode`에 더한다.
- 후속: 2단계 contract 이슈, `docs/design/infra/observability.md` 정상 요청 로그 절 갱신, Notion 결정 기록에 0045 해당 항목이 있으면 대체 사실 기록.

## 검증
- 배포 서버 8차(2026-11-12, 배포 `eda80051`, [open-peak-scenarios.md](../design/infra/open-peak-scenarios.md) "배포 서버 8차"): 같은 날 같은 배포에서 Gateway `problems`(P, 덮어쓰기 없음)와 끔(O, `enabled=false`)을 P1 → O1 → P2 → O2로 번갈아 쟀다. G1, 상한 64, 7차와 같은 부하다.
- 서버 CPU(두 회차 평균): 1,000/s P 59.6% 대 O 56.7%(+2.9%p), 1,500/s 78.5% 대 79.1%(−0.5%p), 2,000·2,500/s ±0.6%p. 같은 설정 두 회차 차이는 1.3%p 이하다. 굿풋(2,500/s 2,237~2,275)과 성공 p95(50~54ms)는 같다.
- 판정: 1,500/s는 ±2%p 안이다. 1,000/s는 +2.9%p로 측정 전에 정한 보류 칸(2~4%p)이지만, 30초 평균 하나의 표본 표준오차(약 2.5%p)와 같은 크기라 실제 차이인지 가리지 못했다. 위 "바꿀 조건"(4%p 넘게 높음)에는 닿지 않으므로 결정은 그대로 두고, 상태도 제안 그대로였다(결제 담당 확인 대기). 2026-11-13에 선조치 후보고로 채택했다.
- 한계: 끔(O)이 7차 H2보다 6~9%p 낮아, 8차는 7차와 수치로 직접 비교하지 않았다. 요청 로그를 전부 남기는 회차(`all`)는 이번에 재지 않았다.
