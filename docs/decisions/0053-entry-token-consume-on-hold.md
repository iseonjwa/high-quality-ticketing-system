# 0053. 입장 토큰은 좌석 선점이 성공한 순간 소모하고, 소모 여부는 선점 트랜잭션의 DB 고유 제약으로 확인한다

- 상태: 제안 (ISE-207 contract. 결정 1은 11/12 팀 회의 확정, 결정 2~5는 담당 확인 뒤 채택)
- 날짜: 2026-11-12
- 결정자: 팀 회의(소모 시점), 이강민(처리 방식 초안)
- 관련 AI 판단: [팀 결정: A안(선점 성공 시 소모)](../ai-judgments/kangmin/2026-11-12-entry-token-consume-on-hold-team-decision.md), [11/9 선점 시 소모 수용](../ai-judgments/kangmin/2026-11-09-entry-token-consume-on-hold.md)
- 관련 노트: [소모 시점 비교와 결제 토큰 만료 동작](../learning/kangmin/qna/2026-11-12-entry-token-consume-timing-and-payment-token-expiry.md), [구현 방법](../learning/kangmin/qna/2026-11-12-entry-token-consume-on-hold-implementation.md), 대기열 담당 노트 `docs/learning/youngeun/qna/2026-11-09-one-time-entry-token.md`
- 대체하는 SA 항목: SA MASTER 7-3의 "jti는 추적·로그용, 폐기 목록은 만들지 않는다. 1회용이 될 수 없다"(`docs/core/SA MASTER.md` 622행) 중 **선점 API 부분만**. Gateway는 여전히 폐기 목록을 보지 않는다. Notion SA는 바꾸지 않았다(대전제 4)

## 맥락
- 입장 토큰은 발급 뒤 10분 동안 서명과 `exp`만으로 검증하는 무상태 JWT다. 소모 시점이 없어, 10분 안에서는 같은 토큰으로 "선점 → 만료 기다리기 → 다시 선점"을 반복해 좌석을 묶어 둘 수 있다. 막는 것은 회차별 1인 매수 한도뿐이다.
- 입장 토큰을 쓰는 곳은 좌석 조회와 선점 두 곳뿐이다(`EntryTokenPolicy`). 결제는 결제 토큰을, 추첨 응모는 Access 토큰만 쓴다. 그래서 결제 완료 시점에 소모해도 막는 것이 거의 없다.
- 대기열 입장 속도는 초당 고정(`admitted`, 설계값 50)이라 일찍 소모해도 다음 사람이 더 빨리 들어오지 않는다. 목적은 처리량이 아니라 남용 방지다.
- 결제 토큰은 선점 만료 10초 전에 끝나고(기본 4분 50초), 만료 뒤 결제하면 403 `PAYMENT_TOKEN_INVALID`이며 좌석은 선점 만료 뒤 풀린다(코드 확인, 노트 1-3절).

## 결정
1. **입장 토큰은 좌석 선점이 성공한 순간 소모한다**(11/12 팀 회의). 실패한 선점(이미 선점된 좌석, 매수 한도 초과 등)은 소모하지 않는다.
2. **소모 여부는 선점 API(reservation-service)가 DB에서 확인한다.** Gateway는 지금처럼 Redis 없이 서명·`exp`·사용자·회차만 본다.
   - Gateway `EntryTokenFilter`는 검증을 통과한 토큰의 `jti`를 `X-Entry-Token-Id` 헤더로 넘긴다. 클라이언트가 보낸 같은 이름의 헤더는 항상 지운다(`X-User-Id`와 같은 방식).
   - `seat_hold_requests`에 `entry_token_jti` 열과 고유 인덱스를 둔다. 동기형 선점은 성공한 선점만 행을 남기고, 추첨 선점은 `NULL`이라(입장 토큰 없음) 서로 막지 않는다.
   - `SyncSeatHoldService.hold`는 멱등 재요청(`replay`) 확인 **뒤**, 좌석 잠금 **전**에 같은 `jti`의 행이 있으면 거절한다. 동시 요청은 고유 인덱스 위반으로 거절하고, `request_id` 고유 위반과는 제약 이름으로 구분한다.
3. **소모 뒤에는 대기열 `issued`에서 그 사용자를 지운다.** 선점 커밋 뒤(`@TransactionalEventListener(AFTER_COMMIT)`) `ZREM queue:{scheduleId}:issued <userId>`를 부른다. 지우지 않으면 `enter.lua`·`issue-token.lua`가 같은(이미 쓴) 토큰을 다시 줘 최대 10분 동안 다시 줄을 설 수 없다. `ZREM`이 실패하면 로그를 남기고, 거절할 때 한 번 더 지운다.
4. **거절 응답은 403 `ENTRY_TOKEN_USED`(새 코드)다.** 상태 코드 403은 프런트의 기존 "입장 토큰 문제 → 토큰 지우고 대기열로" 흐름에 맞추고, 코드 이름으로 만료·위조(`ENTRY_TOKEN_INVALID`)와 원인을 구분한다.
5. **프런트는 선점 201을 받으면 저장한 입장 토큰을 지운다.** `ENTRY_TOKEN_USED`는 `ENTRY_TOKEN_INVALID`와 같이 처리하고, 결제 실패·시간 초과 화면의 [좌석 다시 고르기]는 "다시 줄 서기"로 안내한다.

## 검토한 대안
- 소모 시점
  - 결제 완료 시: 결제가 실패한 사람이 바로 다시 시도할 수 있다. 다만 매수 한도가 이미 막는 "두 번 구매"만 막고, 좌석 묶어 두기는 막지 못한다.
  - 선점 시 소모 + 결제 없이 끝난 선점은 1회 복원(A'): 결제 시간 초과·카드 거절에 한 번 더 기회를 준다. 복원 조건·횟수 저장이 더 필요해 규칙과 구현이 복잡해진다(AI 추천, 팀 회의에서 A 선택).
  - 지금처럼 10분 자연 만료: 바꾸는 것이 없다. 남용을 막지 못한다.
- 확인 위치
  - Gateway가 Redis 폐기 목록을 확인: 좌석 조회까지 막을 수 있다. 피크 때 Gateway 경로에 Redis 조회가 하나 더 붙고(11/9~12 Gateway CPU·차단기 측정 참고), 선점 성공과 기록이 원자적이지 않아 동시에 두 번 누르면 둘 다 통과할 수 있다.
  - 대기열 `issued`만 지움: Gateway가 `issued`를 보지 않아 이미 받은 토큰을 막지 못한다.
- 거절 코드
  - 403 `ENTRY_TOKEN_INVALID` 재사용: 프런트 변경이 없다. 로그·안내에서 만료·위조와 섞인다.
  - 409 `ENTRY_TOKEN_USED`: 의미는 맞지만, 프런트가 409를 토큰 문제로 보지 않아 처리를 빠뜨리면 같은 거절이 반복된다(대기열 담당 노트의 지적).

## 결과
- 얻는 것: "입장 한 번 = 선점 한 번"으로 좌석 묶어 두기를 막는다. Gateway 경로 비용은 늘지 않는다. 같은 토큰으로 동시에 두 번 눌러도 DB가 하나만 통과시킨다.
- 감수하는 것:
  - 결제 토큰 만료나 결제 거절로 선점이 풀린 사람은 대기열에 다시 서야 한다. 결제 화면의 남은 시간 안내가 더 중요해진다.
  - 좌석 조회는 소모 뒤에도 `exp`까지 된다(해롭지 않다고 본다).
  - 대기열 `issued` 정리는 DB 커밋과 따로 움직인다. 실패하면 그 사용자는 최대 10분 다시 줄을 못 선다.
  - 결제 토큰이 만료된 직후 옛 선점이 풀리기 전(약 10~15초)에는 같은 좌석이 여전히 선점 상태다(이 결정과 별개로 이미 있는 빈틈, 노트 1-3절).
- 바꿀 조건:
  - 결제 시간 초과로 다시 줄을 서는 사람이 많다는 지표가 나오면 A'(1회 복원)를 다시 본다.
  - 좌석 조회 남용(소모된 토큰으로 계속 조회)이 피크 부하에 보이면 조회도 막는 방법을 다시 본다.
- 후속:
  - 담당별 구현: Gateway 헤더(강민), 선점 마이그레이션·검사·거절(선점 담당), `issued` 정리·SA 7-3·`docs/design/queue/contracts.md`(대기열 담당), 프런트 토큰 삭제·안내(프런트 담당)
  - 테스트: ISE-207 완료 기준 7개 + `ENTRY_TOKEN_USED` 응답
  - 담당 확인 뒤 상태를 채택으로 바꾼다
