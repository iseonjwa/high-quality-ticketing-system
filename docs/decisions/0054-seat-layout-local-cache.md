# 0054. 회차 좌석 배치 캐시(P4b)는 Redis가 아니라 reservation-service 메모리에 둔다

- 상태: 제안 (최권우 측정 코드와 같은 조건으로 비교 측정한 뒤 채택 여부를 정한다)
- 날짜: 2026-11-08
- 결정자: 반효승(사용자 결정)
- 관련 이슈: ISE-189(좌석 조회 경량화), ISE-204(P4b)
- 관련 AI 판단: `docs/ai-judgments/hyoseung/daily/2026-11-08.md` (개인 기록, 저장소에 올리지 않음)

## 맥락

- SA MASTER는 캐시를 Redis에 두는 것으로 그렸다. 9-1 구성도의 "Redis(대기열·캐시)", 9-4 캐시 TTL "공연 정보 5분 · 좌석 상태 1초"(결정 기록 #45), 9-5 Redis 장애 정책의 "공연 정보·좌석 캐시", Redis 키 표의 `cache:concert:{id}`다.
- ISE-189 P4a(PR #377)를 측정해 보니 좌석 조회 병목은 DB가 아니라 요청마다 객체를 많이 만드는 일이었다. 초당 50건에서 GC로 30초 중 8.3초를 멈췄고, 그동안 커넥션을 쥐고 있어 커넥션 5개 앞에 평균 1.4초 줄이 섰다. 엔티티 대신 DTO로 읽자 p95 2.68s → 40ms, GC 멈춤 8.3초 → 0.18초가 됐다.
- P4b는 회차마다 안 바뀌는 좌석 배치(좌석 ID, 구역, 구역 등급, 가격, 열, 번호) 15,000건을 캐시한다. 이 값은 회차를 만들 때(`createFromVenueSeats`) 한 번 생기고 바꾸거나 지우는 코드가 없다. 추첨 설정이 바꾸는 회차 좌석 등급(LOTTERY)과 좌석 상태는 캐시에 넣지 않는다.
- 배포는 EC2 한 대에 서비스마다 컨테이너 하나다([ADR 0047](0047-single-ec2-first-managed-split-review.md)). Redis 하나를 Gateway(블랙리스트·요청 제한)와 대기열이 함께 쓴다(SA 9-5).
- 이미 같은 방식의 선례가 있다. 대기열의 회차 정보는 서비스 메모리 캐시(`CachedScheduleReader`, 30초 갱신)를 쓴다.

## 결정

좌석 배치 캐시는 reservation-service 메모리에 둔다. 회차마다 처음 한 번 DB에서 읽어 만든 객체를 그대로 다시 쓴다. 좌석 상태와 회차 좌석 등급은 요청마다 읽어 붙인다(P4c에서 1초 캐시로 바꾼다).

핵심 근거(현재 상황: 안 바뀌는 데이터, 서비스 1대, 병목은 객체 생성):

1. 캐시한 뒤 요청마다 하는 일이 다르다. 메모리 캐시는 만들어 둔 배치 객체를 그대로 쓴다(배치 부분 새 객체 0개). Redis는 요청마다 약 1MB를 받아 배치 15,000건을 객체로 다시 만든다(역직렬화). P4a에서 줄인 객체 생성과 네트워크 전송이 요청마다 돌아온다.
2. 서버 간 공유가 필요 없다. Redis의 장점은 여러 서버가 한곳의 같은 값을 보는 것이다. 지금은 서비스가 한 대이고, 여러 대로 늘려도 배치는 안 바뀌어 서버마다 따로 가져도 서로 어긋나지 않는다.
3. 무효화가 필요 없다. 바뀌는 회차 좌석 등급(추첨)과 상태는 넣지 않고 안 바뀌는 값만 넣었다.

덧붙는 근거:

4. 공용 Redis를 보호한다. 초당 50건이면 Redis로 초당 약 50MB가 오간다. Redis가 느려지면 Gateway와 대기열까지 느려진다(SA 9-5 "죽는 것보다 느려지는 것이 더 위험하다").
5. 장애 처리가 단순하다. Redis 타임아웃·서킷 브레이커·DB 대체 조회(9-5)를 이 캐시에는 둘 필요가 없다.

Redis가 맞는 경우: 값이 바뀌고 여러 서버가 같은 값을 봐야 할 때다(대기열 순번, 입장 토큰, 로그아웃 블랙리스트). 이 결정은 데이터 성격과 지금 구조에 따른 선택이고, 서버를 늘리면서 배치가 바뀌는 기능이 생기면 다시 본다.

## 검토한 대안

- Redis(SA 원안): 서버 여러 대가 같은 값을 보고 재시작해도 남는다. 이 데이터는 안 바뀌어 공유가 필요 없고, 요청마다 역직렬화와 네트워크 전송이 생긴다.
- Redis에 응답 JSON 통째로 저장: 역직렬화는 없지만 좌석 상태가 섞여 1초마다 바뀌어야 하고, 매 요청 약 1MB를 Redis에서 옮긴다.
- 캐시 없음(P4a에서 멈춤): 요청마다 DB에서 15,000행을 조인·정렬한다. P4c(상태 1초 캐시)와 나누려면 배치와 상태를 따로 읽어야 한다.

## 결과

- 측정(2026-11-08, 로컬 노트북 1대, 배포 메모리 + G1, 단일 사용자 좌석 조회 30초):

| 초당 | P4a p95 | P4b p95 | P4a → P4b |
|---|---|---|---|
| 150 | 37ms | 18ms | postgres CPU 평균 136% → 21%, 커넥션 쥔 시간 21ms → 4.6ms |
| 200 | 1.18s(처리 173건/초) | 21ms | P4a는 DB가 먼저 포화(postgres CPU 최고 408%) |
| 300 | 2.06s(실패 0.84%) | 26ms | P4a 커넥션 대기 1.16초, P4b 대기 없음 |

  P4b는 초당 400부터 실패했지만 서비스는 받은 요청을 모두 200, 처리 p95 14ms로 응답했다. 실패는 노트북 CPU 포화로 Redis가 느려져 Gateway의 `auth-redis` 서킷이 열린 503이다(ADR 0005). 좌석 조회의 다음 한계는 부하 발생기를 분리해 다시 잰다.
- 얻는 것: 좌석 조회에서 배치를 DB·Redis 없이 만든다. DB에서는 상태(와 회차 좌석 등급)만 읽는다.
- 감수하는 것: 재시작 직후 회차마다 첫 요청이 배치를 만든다. 회차마다 힙에 배치 한 벌(수 MB)을 둔다. 판매가 끝난 회차는 비울 기준을 정한다.
- 후속: P4b 전후 측정(P4a와 같은 조건)과 Redis 방식 비교 수치를 이 기록에 더한다. 측정 뒤 상태를 채택으로 바꾼다.
- SA 변경 요청: 9-1 "Redis(대기열·캐시)"와 9-5 "공연 정보·좌석 캐시"에서 좌석 배치 캐시는 서비스 메모리라고 적는다. Notion SA MASTER는 사용자가 요청할 때 고친다.

## 보강 (2026-11-13): 최권우 측정 브랜치 구현과 합침

같은 P4b를 최권우가 측정 브랜치(`experiment/ISE-79-k6-steps` `066944bc`, dev에는 올리지 않음)에 따로 만들었다. 코드를 항목별로 비교해 안정성·성능이 나은 쪽을 골라 합쳤다. 차이가 코드에서 분명해 두 P4b끼리의 비교 측정은 하지 않았다(사용자 결정).

| 항목 | 이전(#534) | 최권우 구현 | 합친 결과 |
|---|---|---|---|
| 커넥션을 쥐는 구간 | 조회 서비스 전체 트랜잭션 | DB 읽기 클래스에만 트랜잭션 | 최권우 방식(`ScheduleSeatReader`) |
| 바뀌는 값 쿼리 | 15,000행의 id·등급·상태, Java에서 거름 | 선점 가능 id만, 네이티브 SQL | 선점 가능 id만, JPQL + enum 파라미터 |
| 배치 행 변환 | JPQL 생성자 표현식, 가격 `Money` | `Object[]` 칸 번호 형변환, 가격 `BigDecimal` | 이전 방식 |
| 캐시가 빈 순간 동시 요청 | 몰린 요청이 각자 DB에서 읽음 | 한 요청만 읽고 나머지는 기다림(`SharedLoadCache`) | 최권우 방식 + 단위 테스트 |
| 배치와 맞추기 | `HashMap` 위치 찾기, `boolean[]` | `long[]` 이진 탐색(SQL `ORDER BY id`에 기댐), 요청마다 `SeatMapRow` 15,000개 | 이진 탐색 + Java에서 정렬(`HoldableSeatIds`), `boolean[]` |

- 커넥션: 배포 측정(2026-11-12) 2차의 병목이 커넥션 5개였다. 캐시 꺼내기와 15,000석 맞추기를 트랜잭션 밖으로 빼 커넥션을 DB를 읽는 동안만 쥔다.
- 선점 가능 기준은 `ScheduleSeat#isHoldable`, 선점 쿼리, 좌석 조회 쿼리 세 곳에 있다. 좌석 조회 쿼리는 네이티브 문자열 대신 JPQL과 enum 파라미터로 써서 이름이 틀리면 서버가 뜰 때 드러나게 했다. 같은 결과인지는 API 테스트(선점된 좌석과 추첨석은 고를 수 없음)가 확인한다.
- 정렬: 이진 탐색이 쿼리의 `ORDER BY`에 기대면 그 줄이 빠질 때 에러 없이 틀린 `available`이 나간다. 받은 id를 Java에서 정렬해 이 약속을 없앴다. DB 정렬도 빠진다.
- 가격은 `Money`를 유지한다. 원 단위·음수 금지 규칙을 결제·예매와 같은 곳에서 지킨다.
- 최권우 측정(2026-11-12, 로컬, 같은 커밋에서 저장소만 바꿈)에서 배치를 Redis에 두면 Gateway 경유 초당 100명 좌석 조회 p95가 38.3ms로 로컬 7.0ms보다 느렸고, 한 건당 CPU는 약 4.5배였다. 역직렬화가 키운 할당·GC와 공용 Redis 128MB `noeviction` 쓰기 거절(34건)이 원인이었다. 이 기록의 로컬 결정과 같은 방향이다(측정 브랜치 `docs/design/reservation/k6-p4b-local-vs-redis.md`).
- `SharedLoadCache`는 TTL을 받아 P4c(상태 1초 캐시)에도 쓴다.
