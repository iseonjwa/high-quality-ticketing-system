# 0058. 접수형으로 시작한 선점 요청은 동기형 서버가 같은 키로 다시 받아도 202로 답한다

- 상태: 채택
- 날짜: 2026-11-12
- 결정자: 최권우 (좌석 선점 담당)
- 관련 이슈: ISE-16, ISE-247(프론트 알림)
- 관련 AI 판단: [모드 전환 뒤 같은 키 재요청의 처리로 C안 선택](../ai-judgments/kwonwoo/2026-11-12-sync-replay-of-async-requests.md)
- 관련 학습 노트: [접수형 요청을 동기형 서버가 다시 받으면 왜 500이 나는가](../learning/kwonwoo/qna/2026-11-12-mode-switch-replay-gap.md)
- 바꾸는 계약: `docs/design/reservation/contracts.md` 3-2 표에 ⑦을 더한다. [ADR 0057](0057-async-seat-hold-intake-and-mode.md)의 결정 4(접수형 재요청은 결과와 상관없이 202)를 동기형 서버까지 넓힌다.

## 맥락
선점 API는 같은 멱등키 재요청에 첫 결과를 돌려준다. 동기형은 성공한 선점만 `seat_hold_requests`에 남기므로, 동기형 재요청 처리(`SyncSeatHoldService.replay`)는 `HELD`가 아닌 행을 "깨진 데이터"로 보고 예외를 던졌다. 그러면 공통 처리기가 500으로 바꿨다.

접수형(ADR 0057)이 생기면서 이 가정이 깨졌다. 접수형은 `REQUESTED`(처리 중)와 `REJECTED`(거절) 행도 남긴다. 모드는 재시작으로 바꾼다. 그래서 아래 순서로 500이 난다.
1. 접수형 서버가 키 K의 요청을 `REQUESTED`로 받는다.
2. 응답이 닿기 전에 서버가 동기형으로 재시작한다.
3. 재시작 동안 요청이 끊기거나 503·504가 나서, 프론트가 같은 키로 다시 보낸다(`frontend/src/pages/seats/seatHold.ts`, 최대 4회).
4. 동기형 서버가 `REQUESTED` 행을 보고 500을 준다.
5. 프론트는 500을 다시 보낼 대상으로 보지 않는다. 그런데 키는 "결과 미확인"으로 남아 [결과 확인하기]를 누를 때마다 또 500이다. 행이 `REJECTED`면 영원히 그렇다.

## 결정
동기형 서버가 같은 키 재요청에서 `REQUESTED`나 `REJECTED` 행을 만나면 `202 Accepted`와 `Location: /api/v1/reservations/requests/{requestId}`로 답한다. 본문은 접수형 202와 같다(`status: "REQUESTED"`, `nextPollAfterSeconds: 1`). 실제 결과는 조회 API가 알려 준다. 조회 API는 모드와 상관없이 열려 있다(ADR 0057 결정 3).

규칙으로 줄이면 "요청은 시작한 방식으로 끝까지 답한다"이다.

그대로 두는 것:
- 같은 키에 다른 본문이나 다른 사용자면 상태를 보기 전에 `409 IDEMPOTENCY_KEY_REUSED`다.
- `HELD` 행은 지금처럼 201(또는 `RESERVATION_NOT_PAYABLE`)이다.
- `HELD`인데 예매가 없으면 지금처럼 예외로 남긴다. 실제로 깨진 데이터이기 때문이다.
- 이 분기는 동기형이 만들지 않는 행에서만 실행되므로, 동기형만 쓰는 동안에는 동작이 바뀌지 않는다.

## 검토한 대안
- **A. 코드는 두고 운영 절차로 막기**(`REQUESTED`가 0일 때만 전환)
  - 채택하지 않은 이유: `REJECTED` 행은 비워도 남아 그 키의 재요청은 언제든 500이다. 사람이 지켜야 하는 규칙이라 한 번 잊으면 그대로 500이 난다.
  - 계획된 전환에서는 이 절차를 C와 함께 써서 측정 데이터를 깨끗하게 한다.
- **B. `HELD`가 아니면 `409 RESERVATION_NOT_PAYABLE`**
  - 고칠 곳이 가장 작다.
  - 채택하지 않은 이유: 처리 중인 요청을 실패로 안내한다. 사용자가 새 키로 다른 좌석을 고르는 사이 앞 요청이 `HELD`가 되면 사용자가 모르는 예매가 생긴다. 그 예매가 좌석과 매수를 선점 시간(기본 5분) 동안 묶는다. 이미 4매를 고른 사용자는 다음 요청에서 `PURCHASE_LIMIT_EXCEEDED`를 받을 수 있다. 선점 서비스가 막으려는 문제를 스스로 만드는 셈이다. `REJECTED`의 실제 사유도 하나로 뭉개진다.
- **D. `REQUESTED`는 202, `REJECTED`는 원래 사유의 409**
  - 거절을 조회 없이 바로 알린다.
  - 채택하지 않은 이유: `TIMEOUT`, `PROCESSING_FAILED`는 선점 API 에러 코드에 없어 사유 대응표를 새 계약으로 관리해야 한다. 아끼는 것은 조회 한 번(약 1초)뿐이다.
  - 성능 차이도 없다. 두 안이 갈리는 곳은 "모드 전환 직후, 접수형이 거절한 행의 같은 키 재요청" 하나다. 그 경우에도 한 건당 GET 1번(PK 조회 1번, Gateway 통과 1번)이다. 좌석 조회, 새 선점, 접수형 폴링 같은 피크 경로는 두 안이 같다. 비상 전환을 가정해 크게 잡아도(입장 초당 50명 × 재시작 30~60초) 해당 사용자는 많아야 수천 명이고, 각자 GET을 한 번 더 할 뿐이다(추정).

## C를 고른 근거
1. **정확하다.** 처리 중이면 처리 중이라고 답하고, 실제 결과는 조회가 알려 준다. 처리 중을 실패로 안내하지 않으므로 사용자가 모르는 예매가 생기지 않는다(B와의 차이).
2. **규칙이 하나다.** "접수형으로 시작한 요청은 202"는 ADR 0057 결정 4(접수형 서버의 재요청은 결과와 상관없이 202)와 같은 규칙이다. 서버 모드와 상관없이 같은 요청에 같은 모양의 답이 나간다. 사유를 바꾸는 표가 필요 없다(D와의 차이).
3. **사람에게 기대지 않는다.** 행이 어떤 상태로 남든 코드가 막는다(A와의 차이).
4. **성능 비용이 없다.** 피크 경로는 그대로고, 갈리는 경우도 한 건당 GET 1번이다.
5. **받는 쪽이 이미 준비돼 있다.** 접수형을 쓰려면 202 처리 화면(ISE-120)이 먼저 배포돼야 하므로, 이 경우를 만나는 프론트는 202를 이해한다.

## 결과
- 얻는 것: 모드 전환 직후의 500이 사라진다. 사용자는 조회로 진짜 결과(`HELD`면 결제, `REJECTED`면 좌석 재선택)를 받는다.
- 감수하는 것
  - 동기형 서버도 202를 줄 수 있어 "동기형은 201"이라는 그림이 깨진다.
  - 같은 요청이 서버 상태에 따라 202였다가 201이 될 수 있다. 예를 들어 `REQUESTED`였던 행을 소비자가 `HELD`로 만든 뒤에는 동기형 재요청이 201을 준다. 둘 다 같은 예매를 가리키므로 틀린 결과는 아니다.
  - `REJECTED`는 결과가 이미 났는데도 사용자가 알기까지 조회 한 번이 더 걸린다.
- 후속 작업
  - ISE-247로 프론트 담당에게 ③⑦을 알린다.
  - 비상 전환(오픈 중 장애로 동기형으로 급히 되돌리기)을 범위에 둘지는 ISE-255에서 정한다. 재시작 방식에서는 되돌리는 순간 reservation-service 전체가 30초~1분 멈춘다(학습 노트 7절). 어느 쪽으로 정하든 이 결정은 필요하다.
