# 0059. 구역·매수만 받아 서버가 좌석을 고르는 자동 배정 선점을 FOR UPDATE SKIP LOCKED로 더하고, 멱등은 조건 문자열로 비교한다

- 상태: 제안 (좌석 선점 담당 사후 확인 필요, ISE-264 contract 이슈. 강민 위임 야간 작업, 선조치 후보고)
- 날짜: 2026-11-16
- 결정자: 이강민(위임받은 에이전트가 구현, 좌석 선점 담당 확인 전)
- 관련 검토: 11/15 자동 배정 설계 비교(A 서버가 골라 바로 선점 / B 추천 후 확정 / C 409에 대안 좌석)의 A안. 비교 문서는 저장소에 없다

## 맥락

- 11/15 균일 O1(사용자 3,000명)은 좌석 충돌이 병목이었다. 선점 409가 2,298건, 409 뒤 830KB 좌석 재조회가 1,904건이고 확정은 1,973명이었다(`docs/presentation/performance/2026-11-15-o1-synthetic-vs-uniform-source.md`).
- 서버를 바꾸지 않고 k6만 바꿔 "충돌·재조회가 없으면 어디까지 가나"를 잰 상한 실험(11/16 00:33, `SEAT_MODE=partitioned`, 같은 조건의 균일과 비교. 원자료는 아직 저장소에 없다)에서 확정 1,973 → 2,638(+33.7%), 포기 394 → 0, 선점 p95 192 → 114ms, 확정 대기 p95 3.9 → 1.03s였다. 상한 실험은 서버가 좌석을 고르는 비용과 구역 매진을 뺀 값이다.
- 그래서 사용자가 좌석 대신 구역·매수만 정하고 서버가 고르는 API를 실제로 두고, 같은 시나리오(`SEAT_MODE=auto`)로 다시 잰다. SA 5-1에서 "좌석 자동 배정"은 Could였다.

## 결정

1. **API**: `POST /api/v1/schedules/{scheduleId}/reservations/auto`, 본문 `{ grade | section, quantity }`(둘 다 없으면 회차 전체). 헤더·입장 토큰·`201` 응답 본문은 기존 선점 API와 같다. Gateway `EntryTokenPolicy`에 경로를 더한다. 경로를 새로 둔 것은 기존 `seatIds` 본문 검증과 사전 거절 분기를 건드리지 않기 위해서다.
2. **고르기와 잠금**: 범위 안 `AVAILABLE`·비추첨 좌석을 `ORDER BY id LIMIT :quantity FOR UPDATE SKIP LOCKED`로 잠그고, 기존 조건부 UPDATE(`holdAvailableSeats`)로 HELD로 바꾼다. 잠금 순서는 매수 행 → 좌석(ID 오름차순) → 예매로 ADR 0034 3항·SA 8-4와 같다. 상태 전이·매수 한도·예매 저장은 `SeatHolding`의 기존 메서드를 그대로 쓴다.
3. **연석**: 보장하지 않는다. 좌석 ID가 구역·열·번호 순으로 만들어져 ID 오름차순이 대개 붙은 자리를 준다. 건너뛴 행이나 열 끝에서는 떨어질 수 있다.
4. **구역 매진**: 범위 안 남은 좌석이 매수보다 적으면 `409 ZONE_SOLD_OUT`(새 코드). 다른 구역으로 넘기지 않는다. 클라이언트가 고른다.
5. **멱등**: 멱등키 행을 좌석 잠금 전에 쓴다(기존과 같은 순서, 같은 키 연타를 PK로 줄 세움). 그때는 좌석을 모르므로 `seat_ids`를 빈 배열로 쓰고 같은 트랜잭션에서 고른 좌석으로 채운다. 커밋된 행에는 늘 좌석이 있어 `NOT NULL`과 다른 읽는 쪽(결과 조회, 대사)을 바꾸지 않는다. 같은 키 재요청은 새 열 `auto_criteria`(예: `section=A;quantity=2`)로 비교하고, 같으면 처음 고른 좌석·예매를 돌려준다.
6. **모드**: 접수형(`seat-hold.mode=async`)이어도 이 API는 동기형으로 답한다. 사전 거절(1초 캐시)은 하지 않는다. DB의 지금 상태로 고르기 때문이다.

## 검토한 대안

- **기존 경로에 본문만 달리 받기**: Gateway 변경이 없지만 `seatIds` 필수 검증·사전 거절·접수형 분기에 조건이 하나씩 늘어 읽기 흐름이 나빠진다.
- **그냥 `FOR UPDATE`(건너뛰지 않음)**: 정합성은 같지만(앞 사람이 커밋하면 다시 검사해 다음 행을 읽는다) 같은 구역의 앞 ID로 몰린 요청이 줄을 서서 기다리고, `lock_timeout` 500ms를 넘기면 409가 된다. 자동 배정의 목적(충돌·대기 제거)에 맞지 않는다.
- **Redis 좌석 풀 pop, 구역별 커서**: 좌석 상태가 두 곳에 생겨 만료·결제 거절·취소마다 되돌리고 대사해야 한다. 남은 기간에 맞지 않다.
- **연석 보장**: 후보를 넉넉히 잠근 뒤 같은 열 이웃을 찾아야 한다. 이웃 계산은 `lottery.SeatAllocator`에 있어 가져오면 `lottery → seathold`와 순환 의존이 생긴다(ADR 0034). 이번에는 측정 목적상 보장하지 않는다.
- **좌석을 먼저 고르고 멱등키 행을 나중에 쓰기**: 같은 키 연타가 서로 다른 좌석을 잠그고, 같은 사용자의 매수 행을 먼저 커밋한 쪽 때문에 두 번째가 재응답 대신 `PURCHASE_LIMIT_EXCEEDED`를 받을 수 있다.
- **`auto_grade`·`auto_section`·`quantity` 열 셋**: 비교는 같지만 열과 검사 조건이 늘어난다. 조건은 비교에만 쓰므로 문자열 하나로 둔다.

## 결과

- 얻는 것: 좌석 충돌 409와 409 뒤 좌석 재조회가 없어진다. 잠긴 좌석을 기다리지 않아 `lock_timeout` 409도 없다(같은 사용자의 다른 탭이 매수 행을 쥔 경우만 남는다). 같은 구역 동시 30명이 모두 서로 다른 좌석을 받는 것을 PostgreSQL 통합 테스트로 확인했다(`AutoSeatHoldConcurrencyTest`).
- 감수하는 것: 사용자가 정확한 자리를 고르지 못하고 같은 구역 안에서는 앞 ID부터 나간다. 인기 구역 부족은 `ZONE_SOLD_OUT`으로 이름만 바뀌어 남는다. 확정이 늘면 결제가 Gateway 자리를 더 쓴다. 모두 같은 구역 앞 ID부터 훑어 앞쪽 HELD 행을 매번 지나간다(구역당 600석).
- 후속 작업: 좌석 선점 담당 확인(contract 이슈), 프런트 "자동 배정" 화면 연결, 배포 뒤 `SEAT_MODE=auto`와 `map`·`partitioned`를 같은 세션에서 재측정, 결과에 따라 상태를 채택으로 바꾸거나 되돌린다.
- 배포 실측(11/16 06:41 KST, v2 `2fe3ed10`, 사용자 3,000명 오픈 피크): `SEAT_MODE=auto`는 확정 433명으로 같은 버전 `map`(2,162\~2,201명)보다 크게 나빴다. 선점 500 1,352건, 선점 p95 1.92초, postgres-reservation CPU 280%, Hikari 사용 시간 평균 785ms·대기 62였다. 정합성은 맞았다(확정 433건 = 658석, 중복 0).
- 원인과 수정(TS-72): 등급·회차 전체 요청은 `schedule_seats`에 회차 안 ID 순 인덱스가 없어 pk(id)를 처음부터 훑었고, `:p IS NULL OR col = :p` 모양 때문에 일반 계획에서는 구역 요청도 같은 계획이 됐다. 249만 행 로컬 재현에서 한 번에 300\~380ms, 버퍼 약 35,000개였다. `(schedule_id, id)`·`(schedule_id, section, id)`·`(schedule_id, grade, id)` 인덱스(V20261116_6)를 더하고 받은 조건만 SQL에 넣게 바꿔 같은 데이터에서 0.04\~0.21ms, 버퍼 8\~14개가 됐다. 배포 재측정은 아직 하지 않았다.
