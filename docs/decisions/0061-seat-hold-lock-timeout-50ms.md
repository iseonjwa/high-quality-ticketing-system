# 0061. 동기형 좌석 선점의 잠금 대기 상한을 500ms에서 50ms로 줄이고, SKIP LOCKED는 쓰지 않는다

- 상태: 채택
- 날짜: 2026-11-13
- 결정자: 최권우 (좌석 선점 담당)
- 관련 이슈: ISE-261 (ISE-79 후속)
- 관련 AI 판단: [SKIP LOCKED를 먼저 하기로 함](../ai-judgments/kwonwoo/2026-11-13-seathold-skip-locked-first.md), [측정 뒤 SKIP LOCKED를 거부하고 50ms를 택함](../ai-judgments/kwonwoo/2026-11-13-reject-skip-locked-choose-50ms.md)
- 관련 기록: [TS-73](../troubleshooting.md), [학습 노트](../learning/kwonwoo/qna/2026-11-13-seathold-senior-improvements.md)
- 번호: 처음에 0059로 썼으나 dev에 먼저 들어간 [0059(자동 배정)](0059-seat-auto-assign-skip-locked.md)와 겹쳐 0060으로, 다시 dev의 [0060(시드 1,500석)](0060-seed-venue-1500-seats.md)과 겹쳐 11/16 0061로 옮겼다.
- 적용 범위: 사용자가 고른 좌석을 잡는 선점(동기형, 접수형 소비자)이다. 서버가 좌석을 고르는 자동 배정은 고른 좌석을 다른 좌석으로 바꿀 수 있어 SKIP LOCKED를 쓴다(ADR 0059). 이 기록의 "SKIP LOCKED는 쓰지 않는다"는 자동 배정에 해당하지 않는다.
- SA와의 관계: SA 9-4 표의 "선점 DB `lock_timeout` 500ms"를 50ms로 바꾼다. "오래 기다리기보다 바로 이미 선택된 좌석 안내"라는 의도는 그대로 따른다. Notion 항목은 고치지 않았다. 이 기록이 SA 9-4의 값을 대체한다.

## 맥락
- 동기형 선점은 좌석 행을 `ORDER BY id FOR UPDATE`로 잠그고 조건부 UPDATE(`status = 'AVAILABLE'`)로 바꾼다. 다른 트랜잭션이 좌석을 쥐고 있으면 `lock_timeout`까지 기다린다. 이 상한은 잠금 시도마다 따로 걸려, 같은 행을 여럿이 기다리면 몇 배까지 늘어난다(`docs/design/reservation/concurrency-results.md` 4-3절).
- 기다리는 동안 요청은 DB 커넥션을 쥔다. 500ms면 풀 10개 ÷ 0.5초, 곧 초당 약 20건보다 많은 선점이 잠긴 좌석으로 가면 풀이 찬다. 그러면 상관없는 좌석 조회까지 실패한다. ISE-79 잠금 장애 주입 측정에서 이 번짐이 남았다(`docs/design/reservation/k6-seathold-story.md` 5·11절).
- 처음에는 대기를 0으로 만드는 `FOR UPDATE SKIP LOCKED`를 넣었다. 동시성 테스트에서 성공한 선점이 크게 줄어 되돌렸다(TS-73).

## 결정
- `SyncSeatHoldService.LOCK_TIMEOUT`을 500ms에서 50ms로 줄인다. 좌석 쿼리는 `FOR UPDATE`(기다림)를 그대로 둔다.
- 매수 행과 예매 좌석 유니크 인덱스 대기에도 같은 50ms가 걸린다. 같은 트랜잭션에서 `SET LOCAL` 한 번으로 거는 값이기 때문이다.
- 접수형 소비자(ISE-17)의 잠금 대기 상한(`seat-hold.consumer.lock-timeout`)도 100ms에서 50ms로 맞춘다(11/14 추가). 소비자는 동시성 2로 커넥션 번짐은 없지만, 기다리는 동안 그 스레드가 맡은 파티션(6개 ÷ 2 = 3개)이 모두 멈춘다. C2에서 50ms로도 짧은 롤백 잠금은 기다려졌으므로 더 기다릴 이유가 없다. 설정 키는 따로 두어 배포 측정(`seathold.consumer.result{outcome=lock_timeout}`)에서 따로 바꿀 수 있게 한다. 근거는 [학습 노트](../learning/kwonwoo/qna/2026-11-14-ise17-merge-verification-tradeoffs.md) 2절이다.
- 동시성 테스트 C3의 목표를 1,500ms에서 400ms로 줄인다. 잠긴 좌석 한 건을 확인하는 `SeatHoldLockWaitTest`를 기본 빌드에 더한다.

## 검토한 대안
같은 동시성 테스트로 비교했다. C3은 좌석 잠금을 2초 쥔 트랜잭션과 같은 좌석을 노린 5명이고, 3라운드를 돈다. C2는 10명이 좌석 4개를 서로 겹치게 동시에 요청하는 라운드를 50번 돈다(500건). 방식마다 1~3회씩 쟀다.

| 방식 | C3 최대 대기 | C2 성공(500건 중) |
|---|---|---|
| 500ms (기존) | 643ms (이전 기록 1,060~1,305ms) | 83 |
| **50ms (채택)** | 171~225ms | 78, 87, 83, 92 |
| `SKIP LOCKED` (대기 0) | 20~161ms | 56, 56 |

- `SKIP LOCKED`
  - 잠긴 좌석을 건너뛰어 갱신 행 수를 줄이므로 대기가 0이고 번짐의 원인이 없어진다.
  - 그러나 여러 좌석 요청이 겹치면 성공한 선점이 약 1/3 줄었다.
  - 여러 좌석 요청은 일부 좌석을 잠근 뒤 다른 좌석이 이미 잡혀 있으면 롤백한다. 그 몇 ms의 잠금까지 건너뛰기 때문에, 곧 비는 좌석에 409를 준다.
  - 결정자 의견: 선점에 실패할 사용자가 잠깐 잠근 행에 다른 사용자가 접근하지 못하는 것은 문제다.
  - 409를 받은 사용자는 좌석을 다시 조회하고 다시 시도하므로, 줄이려던 409 재시도가 오히려 늘어난다.
- `FOR UPDATE NOWAIT`: 잠긴 행에서 바로 오류를 내므로 `SKIP LOCKED`와 같은 문제가 있다.
- 500ms 유지: 성공 건수는 같지만 번짐이 초당 약 20건부터 생긴다.
- 선점 동시 처리 상한, 사전 거절: 커넥션을 잡기 전에 거절하는 장치라 이 결정과 함께 쓸 수 있다. 별도 작업으로 둔다.

## 결과
- 얻는 것
  - 롤백할 요청이 쥔 짧은 잠금(수 ms)은 기다려서 빈 좌석을 놓치지 않는다. C2 성공 건수가 500ms와 같은 범위다.
  - 오래 쥔 잠금은 C3 기준 최대 171~225ms 안에 409로 끊긴다.
  - 번짐이 시작되는 도착률은 계산상 초당 약 20건에서 45~150건으로 오른다. 풀 10개를 최대 대기 약 0.22초나 중앙값 약 0.065초로 나눈 값이며, 부하로 재지는 않았다.
  - 위 계산의 풀 10개는 측정 브랜치 값이다(P1, `k6-contract-proposals.md` 5절). dev `config-repo`는 아직 5개라 지금 배포에서는 시작점이 그 절반(초당 약 10건 → 23~75건)이다. 풀 크기는 ISE-237에서 정한다.
- 감수하는 것
  - 번짐이 없어지지는 않는다. 그보다 많이 몰리면 커넥션을 잡기 전에 거절하는 장치가 필요하다.
  - 잠금을 50ms보다 오래 쥔 트랜잭션이 결국 롤백하면, 그 좌석을 노린 요청은 빈 좌석에도 409를 받는다. 500ms일 때보다 이런 경우가 늘 수 있다.
  - 같은 사용자의 탭끼리 매수 행을 다투다 50ms를 넘기면 409 `SEAT_ALREADY_HELD`를 받는다. 매수 행 트랜잭션은 수십 ms 안에 끝나 드물 것으로 본다. C4(같은 사용자 탭 4개 × 30라운드)에서는 2회 모두 이 409가 0건이었다.
- 후속 작업
  - 측정 브랜치 Z 시나리오(잠긴 행 집중)와 K1 부하로 500ms와 50ms를 비교한다. (11/16 끝: 로컬 L9 잠금 장애 300/s에서 의도 실패 50ms 0% 대 500ms 77%, 정상 부하는 차이 없음. [부하 비교](../design/reservation/seathold-lock-timeout-load-compare.md))
  - 사전 거절(ISE-205 뒤)과 409 본문의 실패 좌석 ID는 별도 작업이다. (11/16: 사전 거절은 ISE-281로 들어왔다. 켠 회와 끈 회 비교는 [캐시 사전 거절 측정](../design/reservation/seathold-pre-reject-cache-measure.md). 실패 좌석 ID는 계약 변경이라 남아 있다)
