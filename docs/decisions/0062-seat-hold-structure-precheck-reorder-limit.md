# 0062. 동기형 선점은 읽은 좌석 상태로 먼저 거절하고, 좌석 UPDATE를 트랜잭션 끝으로 옮기고, 동시 처리 상한을 둔다

- 상태: 채택. 단, 동시 처리 상한은 코드 기본값을 끔(`seat-hold.max-concurrent: 0`)으로 두고, 배포 환경에서 값을 잰 뒤 켠다. 2(순서 변경)는 local에서 효과를 확인하지 못해 배포 측정으로 다시 본다.
- 날짜: 2026-11-13
- 결정자: 최권우 (좌석 선점 담당)
- 관련 이슈: ISE-261 (ISE-79 후속)
- 관련 AI 판단: [구조 개선 세 가지를 추천 순서대로 넣고 측정하기로 함](../ai-judgments/kwonwoo/2026-11-13-seathold-structure-three-fixes.md)
- 번호: 처음에 0060으로 썼으나 dev의 0059(자동 배정), 0060(시드 1,500석)과 차례로 겹쳐 11/16 dev 병합 때 0062로 옮겼다(잠금 대기 50ms 기록은 0059 → 0060 → 0061).
- 관련 기록: [측정 문서](../design/reservation/seathold-structure-improvements.md), [학습 노트](../learning/kwonwoo/qna/2026-11-13-seathold-structure-review.md), [TS-74](../troubleshooting.md)
- 바꾸는 계약: 없다. 응답 상태와 코드는 그대로다. 409 `SEAT_ALREADY_HELD`를 내는 시점이 앞당겨지고, 이미 계약에 있는 503 `SERVICE_UNAVAILABLE`의 발생 조건에 "선점 동시 처리 상한 초과"를 더한다(`contracts.md` 4절). 프론트는 503을 이미 일시 불안정으로 안내한다.

## 맥락
- 동기형 선점(`SyncSeatHoldService`)은 한 트랜잭션에서 멱등키 조회 → 회차 조회 → 좌석 조회 → 멱등키 INSERT → 매수 UPDATE → 좌석 UPDATE(잠금) → 예매·예매 좌석·이력 INSERT → 멱등키 UPDATE → 커밋 순서로 돌았다.
- 측정에서 선점 응답의 77~97%가 409다. 이 요청들도 쓰기 4번을 하고 롤백했다. 좌석 조회에서 상태를 이미 읽었는데 검사하지 않았다. 접수형(ADR 0057)은 같은 자리에서 검사한다.
- 좌석 잠금은 UPDATE부터 커밋까지 쥔다. 그 사이 INSERT가 "3 + 좌석 수"번 있었다. 예매 좌석 ID가 IDENTITY라 배치로 묶이지 않는다.
- 커넥션을 잡기 전에 막는 곳이 없어, 잠긴 좌석을 기다리는 선점이 풀(5개)을 다 쥐면 좌석 조회까지 막혔다. ADR 0061(50ms)로 시작점을 올렸지만 없애지 못했다.

## 결정
1. **읽은 좌석 상태로 먼저 거절한다.** 좌석 조회 직후 `SeatHoldRules.allHoldable`로 검사하고, 잡힌 좌석이나 추첨석이 섞이면 멱등키·매수·좌석을 건드리지 않고 409로 끝낸다. 접수형도 같은 함수를 쓴다. 같은 키의 첫 요청이 그 사이 커밋됐을 수 있어, 409 전에 멱등키를 한 번 더 읽어 있으면 재응답한다. (11/15 갱신: 판정 재료인 멱등키·입장 토큰·회차·좌석을 한 문장으로 읽게 바꿔 이 재조회를 없앴다. 한 문장은 한 시점의 데이터라 "멱등키는 안 보이는데 그 요청이 잡은 좌석만 보이는" 경우가 생기지 않는다. 근거와 측정은 [성능 개선 반복 기록](../design/reservation/seathold-perf-loop.md) 반복 3·4.)
2. **좌석 UPDATE를 뒤로 옮긴다.** 순서를 매수 UPDATE → 예매·이력 INSERT → 멱등키 HELD → 좌석 UPDATE → 예매 좌석 INSERT → 커밋으로 바꾼다. 좌석 잠금을 쥔 구간이 "UPDATE + 예매 좌석 INSERT + 커밋"으로 준다.
- 1·2는 접수형 소비자(ISE-17)에도 적용한다(11/14 추가). 2는 동기형과 소비자가 함께 쓰는 본체 `SeatHolding`에 두어 순서가 한 곳에서 정해진다. 1은 소비자에서 읽은 좌석 상태로 걸리면 아무것도 바꾸기 전이라 롤백하지 않고 같은 트랜잭션에서 `REJECTED(SEAT_ALREADY_HELD)`와 처리 기록을 쓴다. 오픈 순간에는 같은 좌석 요청이 첫 처리 전에 한꺼번에 접수되어 접수 검사를 통과하므로, 진 요청 대부분이 소비자에서 걸린다. 근거는 [학습 노트](../learning/kwonwoo/qna/2026-11-14-ise17-merge-verification-tradeoffs.md) 1절이다.
3. **선점 동시 처리 상한을 둔다.** `SeatHoldConcurrencyLimit`(공정 세마포어)이 동시에 처리하는 선점을 `seat-hold.max-concurrent`개로 묶는다. 자리가 없으면 `seat-hold.max-concurrent-wait`(기본 200ms)만큼 기다리고, 그래도 없으면 커넥션을 잡기 전에 503으로 거절한다. 거절 수는 `seathold.concurrency.rejected` 지표로 센다. 기본값은 0(끔)이다. local 풀 5개 측정에서는 4개·200ms가 맞았다.

## 검토한 대안
- 캐시 사전 거절(측정 브랜치 `HeldSeatPreCheck`): 커넥션도 안 잡아 1보다 싸다. P4c(ISE-205)가 dev에 없어 지금 못 한다. 들어오면 1과 함께 쓴다. 캐시가 먼저 거르고 놓친 것을 1이 거른다. (11/16 갱신: ISE-281로 dev에 들어왔다(#633 읽기 메서드, #648 사전 거절). 동기형은 캐시 판정 → 1(한 문장 사전 판정) 순서로 함께 쓴다. 캐시가 잡힘이라 할 때의 멱등키 재조회는 커넥션을 쓰므로 3의 상한 안에서 한다.)
- 2에서 예매 좌석 INSERT를 좌석 UPDATE 앞에 두기: 예매 좌석 부분 유니크 인덱스가 사실상 첫 잠금이 되어 잠금 구간이 줄지 않는다.
- 3에서 기다리지 않고 바로 거절(대기 0): p95는 56ms로 짧다. 그러나 순간 몰림까지 잘라, 상한 없이도 다 처리하던 초당 300건에서 16~19%를 거절했다. 200ms는 0~1.4%였다([측정 문서](../design/reservation/seathold-structure-improvements.md) 7절).
- 3 대신 커넥션 풀 늘리기: DB 쪽 동시 실행 수가 늘 뿐 잠긴 좌석 대기가 풀 전체를 쥐는 구조는 그대로다.

## 결과
측정 수치와 원인은 [측정 문서](../design/reservation/seathold-structure-improvements.md)에 있다.
- 얻는 것
  - 1: 인기 구역 쏠림(L7)에서 처리량 +65%, p95 198 → 124ms. 잠금 장애(L8)에서 처리량 +18%.
  - 2: 측정으로 효과를 확인하지 못했다. L7·L8은 차이가 오차 안이고, C2 성공도 1번만 넣은 상태 78~81건, 2번까지 넣은 상태 75~86건으로 범위가 겹친다. 잠금 구간이 짧아지는 것은 구조상 사실이라 남긴다. 효과가 날 조건(DB 왕복이 긴 배포 환경, 같은 빈 좌석을 겨루는 요청이 많은 오픈 첫 몇 초)은 배포 측정에서 본다.
  - 3: 처리 가능량을 넘는 초당 600건에서 타임아웃 57~76% → 0%, 좌석 조회 성공 29~47% → 100%, 유령 선점 204~289석 → 0석.
- 감수하는 것
  - 1: 잠그지 않고 읽은 상태라, 그 사이 풀린 좌석에도 409를 줄 수 있다. 커밋된 상태를 읽으므로 그 좌석은 읽는 순간 잡혀 있었다. 409는 "다시 고르세요"라 사용자 피해가 작다.
  - 2: 아직 커밋되지 않은 선점과 겹친 질 요청은 INSERT를 더 한 뒤 롤백한다. C2 응답 중앙값이 약 1ms 늘었다.
  - 3: 처리 가능한 부하(초당 300건)에서 p95가 56~62ms → 93~182ms로 늘고 0~1.4%를 503으로 거절했다. 값(4개·200ms)은 local 풀 5개 기준이라 배포 환경에서 다시 정해야 한다.
- 후속 작업
  - 배포 단계 측정에서 상한 값을 정하고 config-repo에서 켠다.
  - 커넥션을 1초 안에 못 받은 요청이 계약(503)과 달리 500으로 나간다. 공통 예외 처리기 담당과 확인한다(측정 문서 9절). (11/16 contract 이슈 ISE-293으로 올림)
