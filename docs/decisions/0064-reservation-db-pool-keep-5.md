# 0064. reservation-service DB 커넥션 풀은 5를 유지하고, 풀 크기 재측정은 커넥션 대기가 다시 주 병목일 때 한다

- 상태: 채택 (ISE-237)
- 날짜: 2026-11-16
- 결정자: 효승(예매 흐름 담당), 강민·권우 의견 반영
- 관련 AI 판단: [2026-11-16 판단 일지](../ai-judgments/hyoseung/daily/2026-11-16.md)

## 맥락
- reservation-service는 좌석 조회, 선점, 공연 관리, 추첨, 스케줄러, Kafka 소비자가 커넥션 풀 하나(`maximum-pool-size: 5`)를 나눠 쓴다. 커넥션 대기 시한은 1초다(ISE-196).
- ISE-237은 응모(L1)와 좌석 조회(S1) 측정이 서로 다른 방향을 가리켜 풀 5·10·20을 같은 조건에서 재자고 제안했다.
  - L1(11/10): 풀 5, 초당 1,200에서 커넥션 대기 최대 약 195. 풀 20과 다른 두 설정을 함께 바꾸자 한도가 올랐지만 풀의 몫은 따로 모른다.
  - S1(11/11): DB CPU가 이미 약 210%라 풀을 늘리면 무거운 쿼리가 더 동시에 돌 수 있다.
- 배포 서버 측정(강민, ISE-264 O1, 동기형 선점). 출처는 ISE-237 강민 댓글(11/15 14:58 UTC X1, 11/16 00:22 UTC v1~v3)이다:

| 실행 | Gateway 상한 | 풀 | 커넥션 대기 최대 | 결과 |
|---|---|---|---|---|
| E2(11/15, 회차 140, 개선 전) | 1000 | 5 | 115 | 시한 초과 약 476건, 선점 126·예매 조회 342건 500 |
| X1(11/15, 회차 142, 개선 전) | 1000 | 10 | 30 | 500 0건이지만 커넥션을 쥐는 시간 16.5 → 33.2ms, 선점 p95 1.06 → 1.83초. 호스트 CPU 포화. 1회 측정이고 발생기 지연 판정(V2) 무효(`action_lateness` p95 1.96초), 식은 JVM이 의심되는 실행이라 방향만 읽는다 |
| v2 현실 모드 ×2(11/16, 개선 뒤) | 64 | 5 | 0 · 0 | 커넥션 사용 30초 평균 최대 7.0 · 5.7ms |
| v3 현실 모드(11/16) | 64 | 5 | 0 | 커넥션 사용 30초 평균 최대 6.3ms(같은 v3의 자동 배정 실행은 10.0ms) |

- 개선 묶음(v2)은 요청 로그 축소, Kafka 헬스체크, JIT 예열, 좌석 응답·공연 상세 1초 캐시, 선점 사전 거절이다. 여러 변경이 함께 바뀌어 하나씩 가를 수는 없다.
- 예외: 인덱스 없는 자동 배정 쿼리(v2)가 한 건에 약 785ms 커넥션을 쥐자 풀 5가 바닥나 상관없는 조회까지 500이 났다. 인덱스를 더한 v3에서 대기 0으로 돌아왔다.
- 권우 로컬 측정(PR #661, `docs/design/reservation/seathold-pool-limit-sweep.md`)에서는 풀이 클수록 잠금 장애 부하의 실패가 줄었다(초당 900에서 풀 5 42.7%, 풀 10 1.8%). 로컬은 DB가 쓸 CPU가 넉넉한 조건이고, 풀이 커질수록 한 건 시간이 조금씩 늘었다.

## 결정
- 운영 풀은 5를 유지한다. `config-repo/reservation-service.yml`은 바꾸지 않는다.
- 풀 5·8·10(또는 20) 재측정은 지금 하지 않는다.
- 다시 볼 조건: CPU 여유가 있는데 `hikaricp_connections_pending`이 주 병목으로 남을 때. 좌석 선점 방식 배포 비교 측정(ISE-296)에서 커넥션 대기가 다시 보이면 그때 풀 8을 함께 잰다.
- 커넥션을 오래 쥐는 쿼리가 원인이면 풀을 늘리기보다 그 쿼리를 고친다(v3 인덱스 사례).

## 검토한 대안
- 풀 10으로 올리기: X1에서 500은 사라졌지만 커넥션을 쥐는 시간이 두 배가 되고 지연이 나빠졌다. 배포 서버 CPU가 먼저 차서 동시에 도는 쿼리가 늘면 다 같이 느려진다. 다만 X1은 1회 측정이고 발생기 지연 판정이 무효인 실행이라 방향만 근거로 쓴다. 풀 5를 고른 주된 근거는 개선 뒤(v2·v3) 풀 5에서 대기 0이었다는 점이다.
- 풀 5·8·10 재측정(권우 제안): #661이 아직 main에 없어 배포에서 재려면 릴리스와 측정 모드가 한 번 더 필요하다. 개선 뒤 풀 5에서 이미 대기 0이라 바뀔 판단이 적다고 보고 ISE-296 측정에 조건으로 얹기로 했다.
- 로컬 결과로 정하기: 로컬은 DB CPU가 넉넉해 배포의 CPU 포화를 재현하지 못한다.

## 결과
- 얻는 것: 측정된 배포 조건(풀 5, 상한 64)에서 커넥션 대기 0. 설정 변경과 재측정 비용이 없다.
- 감수하는 것: 풀 10이 나쁘다는 근거(X1)는 1회·방향만이다. 응모(L1)에서 풀의 몫은 여전히 모른다. 11/10 풀 20 결과는 세 설정을 함께 바꾼 값이다. 접수형 선점 소비자 2개와 추첨 실행이 겹치는 조합도 배포에서 재지 않았다.
- 후속: ~~ISE-296에서 `hikaricp_connections_pending`을 함께 본다.~~ 11/17 확인했고 풀 5를 유지한다(아래 "11/17 확인"). 커넥션 대기 시한 초과의 응답 코드는 ISE-293(500 → 503)에서 다룬다.

## 11/17 확인: 배포 단계 측정(ISE-296)에서 다시 볼 조건에 해당하지 않아 풀 5를 유지한다

- 기록자: 최권우(좌석 선점 담당). 이 ADR의 결정을 바꾸지 않는 확인 기록이다.
- ISE-296 측정에서 풀 8(P8·D-P8)을 함께 쟀다. 근거는 [배포 단계 측정 결과](../design/reservation/deploy-seathold-steps-results.md) 11절이다. 게이트웨이 상한은 끄고 쟀다.
- 측정 구간(A0·K1-H) 커넥션 대기는 선점 동시 처리 상한을 끈 단계의 A0 몰림(동시 100명)에서만 생겼다(S1 최대 95, 획득 최대 0.76초). 대기 시한(1초) 초과는 모든 단계에서 0건이었고, K1-H(초당 320까지)에서는 대기가 최대 2였다. 상한을 켠 단계는 풀 5·8 모두 대기 0이었다.
- postgres-reservation CPU 최대는 31~55%(코어 하나 기준)로 여유가 있었다. 그래도 커넥션 대기가 실패로 이어지지 않아 "주 병목"이 아니었다. 실패는 선점 상한의 503과 게이트웨이 앞단에서 났다.
- 풀 8 단계(P8·D-P8)의 처리량 증가는 측정 구간 대기가 0이라 풀이 아니라 상한 4 → 7에서 나온 것으로 본다.
- 선점 상한은 운영에서 켜지 않기로 했다(ADR 0062 "11/17 갱신"). 상한을 켜고 값을 7로 둔다면 그때 풀 8을 함께 올린다. 상한은 풀보다 작아야 보호가 되기 때문이다.
- 재지 않은 것: 풀 8 + 상한 없음, 응모(L1)·추첨 실행·접수형 소비자가 겹치는 조합.
