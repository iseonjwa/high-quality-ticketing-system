# 프론트(frontend) 설계

시연용 웹 화면의 설계를 둔다. 결정과 이유는 [ADR 0040](../../decisions/0040-frontend-react-spa-in-monorepo.md)에 있고, 이 문서는 팀원이 한 번에 볼 수 있게 결론을 모은다. 담당은 안준현이다(SA 6-8).

상태: 구조·스택 결정(2026-11-02). 디자인 시스템은 확정하고 구현했다([design-system.md](design-system.md), ISE-111). API 클라이언트와 목도 있다(ISE-110). 화면은 로그인·회원가입·비밀번호 변경·내 정보(ISE-112), 공연 목록·상세(ISE-113), 대기열(ISE-114), 좌석 선택·선점(ISE-115), 결제(ISE-116), 예매 결과·내 예매(ISE-117), 추첨 응모(ISE-121), 자동결제 카드(ISE-122), 운영자 공연·회차·좌석 등록(ISE-123), 운영자 추첨 설정·회원 비밀번호 초기화(ISE-124), 시연 장애 패널(ISE-134)까지 있다. 코드는 저장소 [`frontend/`](../../../frontend/README.md)에 있다.

원칙: **백엔드에 집중하기 위해 프론트는 단순하게 간다.** 실서비스 구조(BFF, 앞단 대기실, 서버 렌더링 + CDN)는 확인했지만, 기간 한정 시연이라는 조건에 맞춰 가장 적은 구성으로 만든다. 무엇을 알고 무엇을 하지 않았는지는 ADR 0040 4절의 "학습한 실서비스 구조와 이번 선택" 표에 있다.

## 결정 요약

| 항목 | 결정 | 이유 한 줄 |
|---|---|---|
| 코드 위치 | 이 저장소의 `frontend/` | API 계약과 화면을 한 PR로 고치고, 배포가 compose 하나로 끝난다 |
| 스택 | React SPA (Vite + TypeScript) | 디자인 시스템에 컴포넌트가 필요하고 화면이 늘었다. Notion 결정 #7(정적 HTML·JS)의 바꿀 조건을 근거로 바꿨다 |
| 함께 쓸 도구 | React Router, TanStack Query, 직접 쓴 `fetch` 래퍼, React Hook Form + Zod, Tailwind CSS + shadcn/ui, MSW, Vitest + Testing Library + Playwright, ESLint + Prettier, npm. Zustand는 화면 사이에서 나누는 값(로그인 토큰)에만 | 칸마다 이유와 대안은 ADR 0040 3절 |
| Spring Boot 내장 | 하지 않는다 | 토큰을 브라우저가 들고 다니는 구조라 서버 템플릿이 할 일이 없고, JVM이 늘거나 Gateway 재빌드에 화면이 묶인다 |
| 실행 | 별도 nginx 컨테이너 | Node로 빌드한 정적 파일을 nginx가 내준다. 다른 팀원은 Node 없이 compose를 띄운다 |
| API 연결 | nginx가 `/api/`를 `gateway:8080`으로 중계 | 브라우저는 한 출처만 본다. Gateway·백엔드 계약은 바뀌지 않는다 |
| CORS | 넣지 않는다 | 같은 출처라 필요 없다. 로컬은 Vite `server.proxy`가 같은 역할을 한다 |
| 토큰 | Access는 JS 메모리, Refresh와 입장 토큰은 탭 단위 `sessionStorage` | 새로고침에도 로그인이 유지되고, 서버가 사용자당 Refresh 토큰 하나를 재발급마다 바꾸는 구조와 맞는다(ADR 0040 4절, ISE-110) |

## 구조

```
브라우저
  ├─ http://<호스트>/            → frontend 컨테이너(nginx): React 빌드 결과, 없는 경로는 index.html
  └─ http://<호스트>/api/v1/...  → nginx → gateway:8080 → user / reservation / payment
부하 도구 ──────────────────────────────→ gateway:8080 (nginx를 거치지 않는다)
```

nginx는 `/api/`만 Gateway로 넘기고 서비스로 직접 넘기지 않는다. 서비스는 Gateway가 넣은 사용자 헤더를 서명 없이 믿기 때문이다(`docs/guides/workspace.md`).

## API 클라이언트 규칙 (ISE-110)

화면은 `fetch`를 직접 부르지 않고 `frontend/src/api/`의 함수를 쓴다. 아래 규칙은 그 안에 한 번만 구현돼 있다.

| 규칙 | 동작 | 화면이 할 일 |
|---|---|---|
| 공통 응답 | 성공은 `data`만 돌려주고, 실패는 `ApiError`(`status`·`code`·`fieldErrors`·`traceId`)로 던진다. 성공 `data`는 Zod 스키마로 검증해 계약이 어긋나면 `RESPONSE_SCHEMA_MISMATCH`로 멈춘다 | 안내 문구는 `describeError(error)`로 얻는다(design-system.md 6절 표를 코드로 옮긴 것) |
| 401 | Gateway는 만료에 `TOKEN_EXPIRED`, 위조·형식 오류에 `UNAUTHORIZED`, 로그아웃된 토큰에 `TOKEN_REVOKED`를 준다(SA 11-3, ISE-131). 코드와 상관없이 401이면 재발급을 한 번 하고 같은 요청을 다시 보낸다. 동시에 받은 401은 재발급 하나를 함께 기다린다 | 재발급도 실패하면 세션이 만료로 지워진다(`expireSession`). 로그인이 필요한 화면을 `RequireAuth` 아래에 두면 로그인 화면으로 보내고 돌아올 경로를 남긴다(아래 "인증 화면 규칙"). `logout()`은 서버 요청이 실패해도 던지지 않는다. 헤더는 처음 화면으로 옮긴 뒤 부르고 `queryClient.clear()`로 이전 사용자의 조회 결과를 지운다 |
| 멱등키 | 선점·결제 함수는 `Idempotency-Key`를 인자로 받는다. 401 뒤 재시도는 같은 키와 같은 본문(복사해 둔 값)을 쓴다 | 의도마다 `newIdempotencyKey()`로 하나 만든다. `isOutcomeUnknown(error)`(응답 없음·504)면 실패로 보이지 말고 같은 키와 같은 본문으로 다시 보내거나 결과를 조회한다. 고른 좌석이 바뀌거나 예매 조회로 결제 토큰을 다시 받았으면 새 키로 보낸다(결제 토큰 원문도 본문 비교에 들어간다) |
| 입장 토큰 | `issueEntryToken`이 회차별로 저장하고, 좌석 조회·선점이 `X-Entry-Token`으로 붙인다. 저장한 토큰이 없으면 요청 없이 403 `ENTRY_TOKEN_INVALID`, 서버가 403을 주면 그 요청이 보낸 토큰만 지운다. 브라우저 시계로는 지우지 않는다(시계가 빠르면 대기열과 좌석 화면을 끝없이 오간다) | 대기열 진입 전에 `readEntryToken(scheduleId)`가 있고 `isEntryTokenFresh`면 대기열을 건너뛴다(서버 시각으로 보정한 now를 넘기면 더 정확하다). 403이면 대기열로 보낸다 |
| 조회 재시도 | TanStack Query 기본값: 연결 실패와 5xx만 두 번까지, `Retry-After`가 있으면 그 초에 0~+20%를 더해 기다린다 | 변경 요청은 자동 재시도하지 않는다. 결제 202·504의 "확인 중" 처리는 결제 화면(ISE-116)이 한다 |
| 목 | `npm run dev:mock`이면 MSW가 계약대로 응답한다. 주소에 `?mock=seat-conflict,payment-unknown`처럼 실패 시나리오를 고른다 | 시나리오 목록은 `frontend/README.md` |

- 결제 `APPROVED`는 예매 확정이 아니다. 결과 화면은 `getReservation`이 `CONFIRMED`가 될 때까지 다시 조회한다(목도 승인 직후 한 번은 `HELD`를 준다).
- 접수형 선점(202 `REQUESTED`)은 M4 고도화 모드라 응답 스키마에 아직 없다. ISE-120에서 더한다.
- 목 핸들러는 일반 예매 흐름(SA 2-4)만 있다. 취소·추첨·운영자 API는 그 화면 이슈에서 더한다.

## 인증 화면 규칙 (ISE-112)

| 규칙 | 동작 | 이유 |
|---|---|---|
| 경로 보호 | 로그인이 필요한 화면은 `app/routes.tsx`의 `RequireAuth` 아래에 둔다. 로그인 전이면 `/login`으로 보내며 history state `from`에 지금 주소(경로·검색어·해시)를 넘긴다. 보던 중 세션이 끝나도 같은 길로 간다 | 화면마다 로그인 검사를 따로 쓰지 않고, 로그인한 뒤 보던 화면으로 돌아간다 |
| 돌아갈 곳 | 로그인하면 `from`으로 간다. 앱 안의 경로만 받고(`//다른-호스트` 거절) 인증 화면이면 처음 화면으로 보낸다(`auth/navigation.ts`) | history state는 새로고침·뒤로 가기에도 남는다. 다른 사이트로 보내는 주소와 로그인 화면으로 되돌아오는 고리를 막는다 |
| 세션 만료 안내 | 재발급이 거절돼 세션이 끝나면 로그인 화면에 "로그인이 끝났어요. 다시 로그인해 주세요"를 보인다. 사용자가 로그아웃한 경우는 보이지 않는다(세션 저장소 `expired`) | 왜 로그인 화면에 왔는지 알려 준다 |
| 가입·변경 뒤 로그인 | 가입과 비밀번호 변경이 끝나면 같은 값으로 바로 로그인한다. 비밀번호를 바꾸면 이 탭의 옛 토큰부터 지운다. 로그인이 실패해도 앞 단계는 끝났으므로 실패로 보이지 않고 이메일을 채운 로그인 화면으로 보낸다 | 가입 응답에는 토큰이 없고, 비밀번호를 바꾸면 서버가 Refresh 토큰을 폐기한다. 옛 토큰이 남으면 로그인 화면이 로그인 상태로 보고 돌려보낸다 |
| 조회 결과 | 로그인을 보내기 전에 TanStack Query 캐시를 비운다 | 세션이 끝난 뒤 다른 계정으로 로그인해도 이전 사용자의 조회 결과가 보이지 않는다 |
| 입력 검사 | `auth/formSchemas.ts`가 서버 검증 규칙(비밀번호 8자 이상·UTF-8 72바이트 이하·공백만은 안 됨, 닉네임 30자 이하)을 먼저 확인한다. 이메일은 가입만 서버보다 엄격하게(도메인에 점) 보고, 로그인·비밀번호 변경은 서버(`@Email`)만큼 느슨하게 본다. 서버의 칸별 오류(400)는 그 칸 아래에 공통 안내로 옮긴다(서버 문구는 영어 기본 문구라 보이지 않는다) | 요청 전에 칸 아래에서 고치게 한다. 서버가 받는 이메일로 만든 계정이 화면에서 로그인하지 못하는 일을 막는다. 정본은 서버라 규칙이 바뀌면 함께 고친다 |
| 목 계정 | `npm run dev:mock`에서 `temp@iseonjwa.dev` / `TempPass2345`는 임시 비밀번호 계정이다. 어느 계정이든 비밀번호를 5번 틀리면 잠긴다(새로고침하면 풀린다) | 잠금·비밀번호 변경 화면을 백엔드 없이 본다 |

확인한 것(2026-11-02): 실제 Gateway(로컬 compose)에 붙인 개발 서버에서 가입 → 자동 로그인 → 내 정보 → 비밀번호 변경(자동 재로그인) → 로그아웃 → 옛 비밀번호 거절(401) → 새 비밀번호 로그인 → 5번 실패 뒤 잠금(423)을 headless Chrome으로 따라갔다.

후속(ISE-113에서 처리):
- 번들 500 kB 경고: 라이브러리를 `react`·`vendor` 묶음으로 나눠 해결했다(아래 "공연 화면 규칙"). 경로별 지연 로딩은 하지 않았다.
- 로그아웃 캐시: 처음 화면에 공연 목록 조회가 붙어 `queryClient.clear()` 대신 사용자 조회만 초기화한다(`resetUserQueries`, 아래 표).

## 공연 화면 규칙 (ISE-113)

| 규칙 | 동작 | 이유 |
|---|---|---|
| 첫 화면 | `/`가 공연 목록이다(최근 등록순, 20개씩, 주소의 `?page=`는 1부터). 공연 상세는 `/concerts/{concertId}` | 시연 흐름(SA 2-4)이 공연 목록에서 시작한다 |
| 판매 상태 | 응답의 `saleStatus`를 그대로 쓰지 않고, 서버 시각으로 보정한 지금으로 서버와 같은 규칙(오픈 전·오픈부터 공연 시작 전·그 뒤)을 다시 적용한다(`lib/saleStatus.ts`). 서버가 `CLOSED`라고 하면 따른다 | 응답은 받은 순간의 값이라, 화면을 띄워 둔 채 오픈 시각이 지나면 새로고침 없이 [예매하기]가 켜져야 한다 |
| 오픈 순간 | 카운트다운이 0이 되면 `onComplete`로 고른 회차 부분(`ChosenSchedule`)을 다시 그리고, 그 부분은 그릴 때마다 서버 시계로 상태를 다시 정해 [예매하기]를 켠다. 다시 조회하지 않는다. 회차 배지는 패널이 1초마다 다시 그린다(ISE-187) | 같은 0을 보는 카운트다운이 다시 그리게 해서 "00:00"이 보이는 순간과 버튼이 켜지는 순간이 같다(design-system.md 7절 올림). 부모의 1초 갱신을 기다리면 최대 1초 동안 0인데 버튼이 꺼져 있었다 |
| 시각 읽기 | API 시각은 `lib/instant.ts`의 `instantMillis`로 읽는다. 표시는 보는 사람의 시간대와 상관없이 한국 시각 "2026.11.20 (금) 19:00"이다 | 서버 `Instant`는 나노초 9자리까지 온다. ECMAScript 날짜 문자열은 밀리초 3자리까지만 정해 3자리로 잘라 읽는다. 공연은 한국에서 열린다 |
| 목록 배지 | 목록 응답에는 서버 시각이 없어 배지만 브라우저 시계로 정한다. 다음 회차가 없으면(끝났거나 아직 등록 전) 배지 없이 "예정된 회차가 없어요"만 보인다 | 예매 가능 여부는 서버 시각이 있는 공연 상세에서 다시 정하므로 목록 배지가 어긋나도 잘못 예매되지 않는다 |
| 백엔드 구현 그대로 | 화면은 지금 백엔드가 주는 필드만 쓴다. 없는 기능은 프론트가 먼저 요청하거나 가정한 필드를 만들지 않고 아래 "나중에 고칠 것"에 남긴다. 목도 실제 응답과 같은 모양이다 | 프론트 담당 결정(2026-11-02, [판단 기록](../../ai-judgments/junhyun/2026-11-02-frontend-follows-backend-as-is.md)). 화면 때문에 백엔드 일정이 흔들리지 않게 한다 |
| 번들 | 운영 빌드에서 라이브러리를 `react`(React·React Router)와 `vendor`(그 밖)로 나눈다(`vite.config.ts`의 `codeSplitting`). 앱 코드는 47 kB다 | 500 kB 경고를 없애고, 앱 코드만 바뀐 배포에서 라이브러리 파일을 캐시에서 다시 쓴다. 경로별 지연 로딩은 첫 화면도 같은 라이브러리(React Query, Zod)를 써서 줄어드는 양이 작고, 화면 테스트가 모두 비동기가 돼 하지 않았다 |
| 로그아웃 캐시 | 로그아웃 뒤 `resetUserQueries`(`api/queryClient.ts`)로 사용자 조회만 초기화하고, 공개 조회(키 첫 칸 `concerts`)는 그대로 둔다. 사용자 조회의 키 첫 칸은 공개 목록에 넣지 않는다 | `clear()`는 처음 화면의 공연 목록을 캐시와 끊고, 전부 초기화하면 목록이 스켈레톤으로 깜빡인다. 지우지 않고 초기화해서 화면에 붙은 사용자 조회가 있어도 이전 데이터가 남지 않는다 |
| 다시 조회 실패 | 받은 데이터가 있으면 먼저 그린다. 다시 조회하다 실패해도 목록·카운트다운·[예매하기]를 오류 알림으로 바꾸지 않고, 오류는 데이터가 없을 때만 보인다. 공연 상세는 탭으로 돌아와도 다시 조회하지 않는다(`refetchOnWindowFocus: false`) | 오픈 직전 탭으로 돌아온 순간 재조회가 503으로 실패하면 버튼이 사라진다(리뷰에서 재현). 상태와 시계는 화면이 다시 계산하므로 재조회가 필요 없고, 그 순간 부하만 늘린다 |
| 열린 순간 알림 | 보는 중에 오픈하면 화면 낭독기에 "예매가 열렸어요"를 알린다(`aria-live="polite"`) | 카운트다운(`timer`)은 매초 읽지 않아 버튼이 켜진 것을 알 수 없다 |

나중에 고칠 것(백엔드가 제공하면 붙인다):
- 회차별 등급 가격: ISE-113 범위지만 공연 상세 응답(ISE-99)에 없다. 좌석 조회에는 가격이 있지만 입장 토큰이 있어야 해서 공연 상세에서 쓸 수 없다. 지금은 가격 없이 회차·공연장·1인 매수만 보인다.
- 추첨석 회차 안내: ISE-113 범위지만 공연 응답에 추첨 정보가 없다. 추첨 공개 조회(GET `/lotteries/{lotteryId}`)는 추첨 ID로만 부를 수 있다. 추첨 화면(ISE-121)도 운영자가 준 주소(`/lotteries/{번호}`)로만 들어온다(추첨 응모 화면 규칙).
- 목록 배지의 서버 시각: 목록 응답에 `serverTime`이 없어 배지를 브라우저 시계로 정한다(위 "목록 배지").
- 목록 배지의 기준 회차: 목록 응답은 공연마다 "다음 회차"(아직 시작하지 않은 가장 빠른 회차) 하나만 준다. 그래서 가장 빠른 회차가 오픈 전이고 뒤 회차가 이미 판매 중이면 "오픈 예정"으로 보인다. 정확한 상태는 공연 상세에서 회차마다 보인다.

확인한 것(2026-11-02): 관리자 API로 로컬 compose에 공연과 회차(95초 뒤 오픈)를 만들었다. 브라우저 시계를 1시간 빠르게 바꾼 headless Chrome에서 공연 상세를 열었더니, 카운트다운이 서버 기준(66초)으로 셌다. 오픈 순간에는 다시 조회하지 않고 [예매하기]가 켜졌다. 이슈 완료 기준 두 가지다.

## 서비스형 홈·공연 상세 규칙 (ISE-187)

화면 모양과 그림 에셋 규칙은 [design-system.md 10절](design-system.md#10-서비스형-레이아웃과-그림-에셋-ise-187)에 있다. 여기에는 데이터로 무엇을 보이는지를 둔다.

| 규칙 | 동작 | 이유 |
|---|---|---|
| 홈 묶음 | 목록 응답을 예매 중(공연이 가까운 순), 티켓 오픈 예정(오픈이 가까운 순), 다른 공연(다음 회차가 없거나 이미 시작)으로 나눈다(`pages/concerts/homeConcerts.ts`). 대표 배너는 예매 중 다음 오픈 예정 순으로 최대 4개이고 첫 페이지에만 둔다. 보일 공연이 없으면 서비스 소개 배너를 둔다 | 목록 응답(번호·제목·다음 회차 시각)만 쓴다. 인기순·장르는 응답에 없다 |
| 다시 나누기 | 브라우저 시계로 10초마다 다시 나눈다 | 목록 배지 규칙(위)과 같다. 예매 가능 여부는 공연 상세가 서버 시각으로 정하므로 1초마다 목록 전체를 다시 그리지 않는다 |
| 남은 날 | "오픈 D-3", "오늘 공연"처럼 한국 날짜로 센다(`kstDaysUntil`) | 해외 시간대에서도 같은 날짜가 보인다 |
| 예매 패널 | 티켓 모양이다([design-system.md 12절](design-system.md)). 위 칸에 고른 회차(일시·장소)와 그 회차의 카운트다운·[예매하기]·"판매가 끝났어요"를 두고, 절취선 아래 칸의 라디오 목록에서 회차를 바꾼다. 처음 고를 회차는 예매 중인 첫 회차(공연이 가까운 순), 없으면 오픈이 가장 빠른 회차, 그것도 없으면 첫 회차이고, 처음 그릴 때 한 번만 정한다. 넓은 화면(64rem 이상)에서도 패널을 배너 위로 끌어올리지 않고 배너 아래 오른쪽 열에 두며, 스크롤하면 위에 붙는다 | 오픈 순간 [예매하기]가 첫 화면 안에 있어야 한다. 그래서 넓은 화면에서 배너 높이를 묶는다(제목 2줄, 요약 표 숨김, 낮은 창에서 작은 포스터). 측정은 1440×780·1366×650·1280×600·1093×530·900×600·390×664·360×640에서 버튼 아래 끝이 438~582px이고 3줄 제목도 첫 화면 안이다([design-system.md 12절](design-system.md)). 끌어올리면 절취선 양 끝 홈이 그림 위에서 점으로 보인다. 기본 회차를 매초 다시 정하면 목록 앞 회차가 열리는 순간 고른 회차가 바뀌어 보던 회차가 아닌 대기열로 들어간다(셀프 리뷰) |
| 공연 요약 | 장소(여럿이면 "외 N곳"), 기간(첫·마지막 회차 날짜), 회차 수, 1인 최대(회차마다 다르면 "회차마다 달라요") | 상세 응답의 회차 목록으로 계산한다 |
| 탭 | 공연 정보(그림, 공연 소개, 회차 일정 표)와 예매 안내(예매 순서 4단계, 알아 두세요). 탭 앞에 화면 낭독기용 h2 "공연 안내"를 둔다 | 예매 안내에는 시스템 규칙(대기열, 결제하는 동안 좌석 잡기, 결제 가능 시간, 이선좌 뒤 다시 고르기, 회차별 1인 누적 매수, 확인 중)만 쓴다. 선점 5분 같은 숫자는 설정이 바뀔 수 있어 쓰지 않고, 화면이 서버 시각으로 남은 시간을 보인다. 추첨은 회차 전체가 아니라 일부 좌석이고 응모 화면으로 가는 길이 운영자가 준 주소뿐이라 "일부 좌석은 추첨, 운영자가 안내한 응모 화면"으로 쓴다 |

나중에 고칠 것(백엔드가 제공하면 붙인다):
- 공연 이미지: API가 주면 그림 대신 쓴다. 바꾸는 곳은 `components/ticketing/concertArt.ts` 하나다.
- 홈 묶음의 개수·정렬은 받은 한 쪽(20개) 안에서만 맞다. 목록이 최근 등록순 쪽 번호라 전체 정렬은 API가 필요하다.
- 홈은 10초마다 다시 나눠, 보는 중 오픈한 공연이 오픈 예정에서 예매 중으로 옮겨지며 아래 내용이 밀린다. 예매 가능 여부는 공연 상세가 정하므로 두었다(셀프 리뷰 낮음).
- 장르·가격·관람 시간·출연진: 응답에 없어 보이지 않는다.
- 공연 검색·인기순: API가 없다.

## 마이페이지·티켓·로그인 화면 규칙 (ISE-188)

ISE-187에 이어 로그인한 사용자가 오래 보는 화면을 실제 서비스형으로 바꿨다. 화면 모양 규칙은 [design-system.md 10절](design-system.md#10-서비스형-레이아웃과-그림-에셋-ise-187)에 있다.

| 규칙 | 동작 | 이유 |
|---|---|---|
| 마이페이지 틀 | `/me`·`/me/reservations`를 감싸는 경로(`pages/my/MyPageLayout.tsx`)다. 넓은 화면에서는 왼쪽에 프로필 카드와 메뉴를 두고, 좁은 화면에서는 위에 가로로 넘기는 메뉴를 둔다. 메뉴는 예매 내역, 내 정보·자동결제 카드, 비밀번호 변경, (운영자만) 운영 화면이다. 메뉴는 보조 내용(aside)으로 감싸지 않는다. 가로 메뉴는 키보드 초점이 간 항목을 보이게 넘기고(`scrollIntoView`), 위아래 여백으로 초점 고리가 잘리지 않게 한다. [비밀번호 변경]은 누른 화면(내 예매·내 정보)을 돌아올 곳으로 넘긴다 | 실제 서비스의 마이페이지 구조다. 내 정보 화면 아래에 있던 [비밀번호 변경]·[운영 화면]은 메뉴로 옮겼다. Chrome은 일부라도 보이는 요소면 초점만으로 넘기지 않아 360px에서 반쯤 가려진 메뉴가 그대로였다(셀프 리뷰) |
| 내 정보 조회 | 틀과 내 정보 화면이 같은 키로 `/users/me`를 부르고 5분 동안 다시 받지 않는다(`ME_STALE_MILLIS`). 메뉴로 오가도 한 번만 조회한다. 로그아웃·로그인·비밀번호 변경은 캐시를 비운다 | 헤더에 두면 모든 화면이 조회해 오픈 순간 부하가 늘어난다. 마이페이지에 왔을 때만 부른다. 신선도 0으로 두면 내 정보 화면으로 돌아올 때마다 다시 받았다(셀프 리뷰) |
| 내 예매 티켓 | 왼쪽 날짜 칸(공연 일시, 한국 시각), 절취선, 공연 제목·상태 배지·예매 번호·금액을 둔다. 날짜 칸 색은 예매 확정이 인디고, 결제 대기가 경고색, 끝난 예매가 회색이고, 작은 글자도 바탕마다 4.5:1을 넘는 색을 쓴다(흐리게 하지 않는다). 끝난 예매는 제목도 흐리게 둔다. 링크 안에 `<article>`을 두지 않고, 링크 이름은 "공연 제목, 일시, 상태, 예매 번호, 금액"으로 따로 준다(날짜 칸은 `aria-hidden`) | 색만으로 구분하지 않도록 상태 배지를 함께 둔다. 목록 응답에 공연 번호가 없어 포스터 그림을 붙이지 않는다. 공연 상세와 다른 그림이 붙으면 같은 공연인지 헷갈린다. Chrome은 링크 이름을 내용으로 계산할 때 article 안 글을 빼서 이름이 빈 링크가 됐다(셀프 리뷰, Chrome 접근성 트리로 확인. jsdom은 이름을 계산해 테스트로 잡히지 않는다). 내용으로 계산하면 브라우저마다 칸 사이 띄어쓰기가 달라 이름을 따로 준다 |
| 확정 티켓 | 좌석마다 어두운 티켓 카드에 "Ticket n/N", 등급, 구역·열·번호, 티켓 번호, 가격, 꾸밈 바코드를 둔다. 화면 이동 값이 있으면 공연 제목·일시도 둔다. 아래에 예매 번호·결제 금액을 따로 둔다 | 실제 모바일 티켓처럼 좌석 하나가 티켓 한 장이다. 바코드는 티켓 번호로 그린 모양일 뿐 읽을 수 있는 코드가 아니다(`aria-hidden`, 티켓 번호는 글자로 보인다) |
| 인증 화면 틀 | 로그인·회원가입·비밀번호 변경(`AuthCard`)은 넓은 화면(56rem 이상)에서 왼쪽에 공연 그림과 서비스 소개, 오른쪽에 폼을 둔다. 좁은 화면에서는 폼 카드만 둔다. DOM에서는 폼이 먼저라 화면 낭독기가 제목(h1)부터 읽는다 | 그림은 `loading="lazy"`라 숨긴 좁은 화면에서는 받지 않는다 |
| 자동결제 카드 | 등록됨이면 실물 카드 모양("시연용 카드", 끝 네 자리, 등록일)을 두고, 옆에 해지 안내와 [해지]를 둔다 | 카드사·카드 이름은 응답에 없어 "시연용 카드"로 쓴다 |

2026-11-09 ISE-211에서 마이페이지 현재 메뉴를 진한 칩에서 옅은 인디고(`primary-50`·`primary-700`)로, 내 예매 티켓 모서리를 20px로 바꿨다. 동작 규칙은 그대로다([design-system.md 13절](design-system.md)).

## 대기열 화면 규칙 (ISE-114)

공연 상세의 [예매하기]가 `/schedules/{scheduleId}/queue`로 보낸다. 로그인이 필요하다(`RequireAuth`). 생김새는 [samples/queue.html](samples/queue.html)이고(2026-11-04 사용자 확인), 흐름은 `pages/queue/queueAdmission.ts`, 화면은 `pages/queue/QueuePage.tsx`에 있다.

| 규칙 | 동작 | 이유 |
|---|---|---|
| 건너뛰기 | 이 회차의 입장 토큰이 저장돼 있고 만료 전이면 요청 없이 좌석 화면으로 간다 | SA 11-5. 좌석 화면에서 403을 받으면 그 토큰을 지우고 대기열로 돌아온다(API 클라이언트 규칙 "입장 토큰") |
| 곧 입장해요 | `estimatedWaitSeconds`가 1 이하이면 순번 대신 "곧 입장해요 / 좌석 선택 화면을 준비하고 있어요"를 보인다. 기다리는 카드의 생김새는 티켓 모양이다([design-system.md 12절](design-system.md)) | 혼자 줄을 서도 입장 처리(500ms 스케줄러)와 순번 조회 간격(poll-min 3s + 20% 흔들기) 때문에 3~3.6초 동안 "내 순번 1"이 보였다. 화면 쪽 완화이고, 서버 쪽 개선(작은 순번은 바로 입장하거나 짧은 조회 간격)은 별도 contract 이슈로 다룬다 |
| 진입 | 화면을 열 때마다 진입 요청(POST `/queue`)부터 보낸다. 새로고침·새 탭도 같다 | 이미 줄에 있으면 서버가 같은 자리를 200으로 준다(ADR 0031 결정 3). 순번 조회부터 보내면 처음 온 사용자는 404 뒤 진입을 또 보내 오픈 순간 요청이 두 배가 된다 |
| 순번 조회 | `WAITING`이면 응답의 `nextPollAfterMillis`만큼 기다렸다 순번 조회(GET `/queue/me`)를 보낸다. 값을 고치지 않는다 | 서버가 순번 기반 간격(3~10초)에 jitter까지 섞은 값이다(ADR 0031 결정 10) |
| 토큰과 이동 | `READY`면 바로 토큰 API(POST `/queue/token`)를 부르고, 받은 토큰을 저장한 뒤 좌석 화면으로 바꿔 들어간다(replace). 진입 응답이 `READY`여도 순번 조회 없이 바로 부른다. 받은 공연 요약(아래 "공연 줄")도 좌석 화면에 넘긴다 | 좌석 화면에서 뒤로 가면 대기열이 아니라 공연 상세로 간다. 대기열로 돌아가면 저장한 토큰 때문에 다시 좌석으로 튕긴다. 좌석 API에도 공연 제목이 없다 |
| 자동 재시도 | 응답이 없거나(0) 지나가는 장애(429, 502·503·504)면 단계를 그대로 두고 같은 요청을 다시 보낸다. 간격은 `Retry-After`에 0~+20%를 더한 값이고, `Retry-After`가 없으면 3·3·4초, 그 뒤로는 8초에 0~+20%다. 횟수 제한은 없다. 그동안 카드 위 표시가 "연결이 잠시 불안정해요. 곧 다시 시도할게요"(경고색)로 바뀌고 순번은 그대로 보인다. 500은 다시 보내지 않고 아래 "그 밖의 오류"로 보인다 | 세 요청 모두 다시 보내도 결과가 같고, 자리는 서버에 있다. 서버가 정하지 않은 간격은 SA 9-4의 최소 조회 간격 3초(폴링 부하 상한) 아래로 내리지 않는다. 500은 다시 보내도 같은 결과일 가능성이 커서 끝없이 기다리게 하지 않고 문의 번호를 보인다(Redis 지연은 503이다, SA E11). 사용자가 할 일이 없어서 알림 상자 대신 표시 한 줄만 바꾼다(샘플 확인). 이 표시는 처음부터 있는 알림 영역의 글자만 바꿔 화면 낭독기가 읽게 한다 |
| 줄에서 빠짐 | 순번 조회·토큰이 404 `QUEUE_NOT_JOINED`면 "입장 시간이 지나 줄에서 빠졌어요"와 [다시 줄 서기]. 누르면 진입부터 다시 한다 | SA 11-5. 발급 기록이 그 사이 만료된 경우다 |
| 오픈 전 | 진입이 409 `SALE_NOT_OPEN`이면 "아직 오픈 전이에요"와 공연으로 돌아가는 버튼 | 공연 상세는 서버 시각으로 [예매하기]를 켜므로 주소로 바로 열 때만 나온다 |
| 차례 전 토큰 | 토큰 API가 409 `QUEUE_NOT_READY`면 3초 뒤 순번 조회로 돌아간다 | SA 11-5 "받으면 순번 조회로 돌아간다". 정상 흐름에는 없다 |
| 그 밖의 오류 | 안내 문구의 앞 문장을 제목, 뒤 문장을 설명으로 보이고 [다시 시도](진입부터)를 둔다. 예상하지 못한 오류는 문의 번호를 보인다. 404 `NOT_FOUND`(없는 회차)는 다시 보내도 같아 [다시 시도] 없이 [공연 목록으로]만 둔다 | 문구 규칙이 "원인. 다음 행동" 두 문장이다(design-system.md 1절) |
| 공연 줄 | 카드 위에 공연 제목·일시·공연장을 보인다. 공연 상세의 [예매하기]가 화면 이동 값(history state)으로 넘긴 값이다. 주소만 새 탭으로 열거나 로그인 화면을 거쳐 오면 없다 | 대기열 API에는 공연 정보가 없다. 백엔드에 요청하지 않고 프론트가 가진 값만 쓴다 |
| 예매 단계 | 예매 흐름 경로는 handle에 단계 번호를 두고(`app/bookingStep.ts`), 헤더 가운데에 단계 표시를 그린다. 앱 화면이 60rem보다 좁으면 지금 단계 이름만 남기고, 48rem보다 좁으면 숨긴다. 워드마크와 메뉴는 줄어들지 않는다 | 좌석 샘플의 상단 바와 같은 자리다. 시연 패널을 켠 1280px 화면(앱 화면 900px)에서도 헤더 한 줄에 들어간다. 처음에 40rem으로 두었더니 앱 화면 640~673px(1024px 창에 시연 패널)에서 워드마크가 두세 줄로 접혔다(셀프 리뷰) |
| 초점 | 사용자가 눌러야 하는 단계(빠짐·오픈 전·실패)가 되면 제목으로 초점을 옮긴다. [다시 줄 서기]·[다시 시도]를 누르면 새 내용(줄을 서고 있어요)을 먼저 그린 뒤 초점을 카드로 옮긴다 | 바뀐 안내를 화면 낭독기가 읽고, 누른 버튼이 사라져도 초점이 페이지 맨 위로 가지 않는다. 먼저 그리지 않으면 카드가 방금 본 안내를 담은 채 초점을 받는다. 순번은 그 줄에만 `aria-live`가 있어 조회마다 순번만 읽힌다 |

나중에 고칠 것: 없음. 토큰 API(ISE-69)와 좌석 화면(ISE-115)이 생겨 코드 변경 없이 실제 백엔드에서 대기열 → 좌석까지 이어진다(아래 "좌석 화면 규칙"의 확인한 것).

알아 둘 것:
- 진행 막대는 이 화면에서 처음 받은 순번을 기준으로 한다. 새로고침하면 그 순번이 새 기준이라 0부터 다시 찬다.
- 다른 탭을 보는 사이에 차례가 되면 바로 토큰을 받아 입장 시간이 시작된다. 좌석 화면이 탭 제목으로 알린다(ISE-115).
- 세션이 만료(`expireSession`)돼도 입장 토큰은 지우지 않는다(로그아웃만 지운다). 같은 탭에서 다른 계정으로 로그인하면 이전 사용자의 토큰으로 좌석 화면에 갔다가 403으로 지우고 대기열로 한 번 돌아온다. 같은 사용자가 다시 로그인하면 토큰을 그대로 쓴다. 어느 쪽이든 왕복 한 번 차이라 그대로 둔다.

확인한 것(2026-11-04):
- 실제 백엔드: 로컬 compose Gateway에 붙인 개발 서버에서 공연 1의 [예매하기]를 눌렀다. 진입이 201 `WAITING`(순번 1, `nextPollAfterMillis` 3148)을 주고, 3.2초 뒤 순번 조회가 200 `READY`를 줬다. 이어 토큰 요청이 404 `NOT_FOUND`(ISE-69 전)로 끝나 위 안내가 보였다. 시연 패널에 세 요청의 traceId가 남았다.
- 목: headless Chrome으로 기본·`queue-unavailable`·`queue-expired`, 오픈 전 회차(32), 없는 회차(999)를 따라갔다. 입장하면 좌석 경로로 바뀌고 뒤로 가기는 공연 상세였다. 토큰이 남은 탭은 대기열을 건너뛰었다. 1280px·900px·360px에서 가로 넘침이 없었다.
- 헤더: 1280·960·959·900·800·768·767·700·672·640·639·360px에서 워드마크 높이가 모두 24px(한 줄)이고 가로 넘침이 없었다. 예매 단계는 960px 이상에서 이름 전부, 768~959px에서 지금 단계 이름만 보이고 767px 이하에서 숨는다.

## 좌석 화면 규칙 (ISE-115)

대기열이 입장 토큰을 받으면 `/schedules/{scheduleId}/seats`로 바꿔 들어온다(예매 단계 2). 생김새는 [samples/seat-sections.html](samples/seat-sections.html)이다(2026-11-04 "구역 먼저 고르기" 선택). 화면은 `pages/seats/SeatsPage.tsx`, 선점 요청은 `pages/seats/seatHold.ts`·`useHoldRequest.ts`에 있다.

2026-11-09 ISE-210에서 생김새를 구역 카드·좌석 카드와 티켓 모양 선택 요약으로 바꿨다([design-system.md 12절](design-system.md)). 동작 규칙은 그대로다.

| 규칙 | 동작 | 이유 |
|---|---|---|
| 들어오기 | 저장한 입장 토큰이 없으면 요청 없이 대기열로 바꿔 보낸다(공연 요약 유지). 서버가 좌석 조회를 403으로 거절하면 자동으로 보내지 않고 "입장 시간이 끝났어요"와 [대기열로 돌아가기]를 보인다 | 새 탭·주소로 들어오면 대기열이 줄을 세워 토큰을 받아 온다. 서버 거절까지 자동으로 보내면 토큰이 계속 거절될 때(Gateway 설정 오류 등) 대기열과 좌석 화면을 끝없이 오간다 |
| 구역 먼저 | 구역 배치도에서 구역을 고르면 그 구역 좌석만 그린다. 처음에는 남은 좌석이 있는 첫 구역이다. 매진 구역은 누를 수 없다. 고른 좌석은 구역을 옮겨도 요약에 남고 배치도에 구역별 고른 수가 보인다. 배치도는 radio 묶음이라 Tab 한 번에 들어가 화살표로 옮긴다 | 로컬 KSPO DOME이 25구역 × 600석 = 15,000석(응답 811KB)이라 한 번에 그리면 좌석 버튼이 15,000개다. 구역 하나(600석)만 그리니 좌석 누름 41ms, 구역 전환 21ms였다(실제 백엔드, 1280px). 구역마다 Tab 정지점을 두면 좌석까지 25번 눌러야 한다 |
| 매수 | 1인 최대 매수까지 고른다(기본 2매). 최대 매수는 공연 상세 응답의 회차 값이다. 공연 요약 없이 들어오면 서버 기본값 4매까지 보이고 "회차당 최대 N매"를 뺀다. 매수를 줄이면 앞에서 고른 좌석만 남는다. 다 고른 뒤 더 누르면 "먼저 고른 좌석을 해제해 주세요" | 좌석 API에 최대 매수가 없다. 백엔드에 요청하지 않고 공연 상세 캐시를 쓴다(공연 상세에서 왔으면 요청이 다시 나가지 않는다). 한 번에 최대 매수보다 많이 보내면 400 `SEAT_COUNT_MISMATCH`, 이미 가진 HELD·CONFIRMED 좌석과 합쳐 넘으면 409 `PURCHASE_LIMIT_EXCEEDED`이고 화면은 [내 예매 보기]를 보인다 |
| 선점 요청 | [N매 선택 완료]가 좌석 ID를 오름차순으로 보낸다. 멱등키는 고른 좌석 묶음마다 하나다. 응답 없음·504·503·429면 같은 키로 모두 4번까지 보내고, 그동안 요약의 버튼 자리에 "좌석을 확인하고 있어요"를 보인다. 응답 없음·504가 한 번이라도 있었던 키는 "결과 미확인"이다. 그 뒤 409면 3초 기다려 같은 키로 한 번 더 확인하고(201이면 확보, 또 409면 겹침), 그 밖의 실패로 끝나면 "좌석을 잡았는지 확인하지 못했어요"를 보이며 키를 남긴다. 키가 남은 동안 좌석·매수를 바꾸지 못하고 요약 버튼이 [결과 확인하기](같은 좌석·같은 키)로 바뀐다. [다른 좌석 고르기]는 키를 버린다. 결과가 정해진 요청 뒤에는 새 키다 | 서버가 같은 키 재요청에 처음 결과를 줘 좌석이 두 번 잡히지 않는다. 결과를 모른 채 새 키로 보내면 이미 잡힌 내 좌석 때문에 409를 받는다. 서버는 성공한 선점만 키를 기록하고 좌석 ID를 정렬해 비교한다(`SyncSeatHoldService`). 앞 요청이 서버에서 아직 처리 중이면 같은 키 재요청이 내 좌석과 겹쳐 409를 받을 수 있다([예매 계약](../reservation/contracts.md) 3-2 ⑥). 이 409를 "남이 가져감"으로 보이면 내가 잡은 좌석을 잃은 것으로 안내하게 된다(셀프 리뷰에서 재현). 3초는 Gateway 응답 시한이라 그때면 앞 요청이 커밋이나 롤백으로 끝나 있다 |
| 409 이선좌 | 좌석을 다시 받아 고를 수 없게 된 좌석만 빼고 나머지는 둔다. 그 좌석이 있는 구역으로 옮겨 1.6초 깜빡이고 "이미 선택된 좌석입니다 / A구역 1열 3번이 방금 다른 분께 선택됐어요. 남은 좌석은 그대로 두었어요"를 보인다. 다시 받는 동안 좌석·버튼을 막는다. 다시 받기에 실패하면 [좌석 다시 불러오기]를 보이고 다시 누르라고 하지 않는다. 줄을 다시 서지 않는다 | 409는 어느 좌석이 겹쳤는지 알려 주지 않는다([예매 계약](../reservation/contracts.md) 4절, SA E1). 다시 받는 동안 막지 않으면 그사이 고친 선택을 받은 뒤 옛 값으로 덮었다(셀프 리뷰에서 재현) |
| 좌석 확보 | 201 `HELD`면 닫을 수 없는 대화상자에 잡은 좌석과 결제 가능 시간(`paymentTokenExpiresAt`)을 보이고 [결제하러 가기]만 둔다. 누르면 결제 화면(`/reservations/{id}/payment`, ISE-116)으로 바꿔 들어가며 선점 응답·좌석·공연 요약을 화면 이동 값으로 넘긴다(`pages/payment/paymentNavigation.ts`). 결제 가능 시간이 지나면 [좌석 다시 고르기]로 대화상자를 닫고 좌석을 다시 받는다. 잡은 선점은 회차별로 sessionStorage(`auth/heldSeats.ts`)에 두고, 좌석 화면이 다시 열릴 때 결제 가능 시간이 남았으면 대화상자를 다시 띄운다. 로그아웃이 지운다 | 닫을 수 있으면 잡힌 좌석을 두고 같은 회차를 또 골라 매수 한도에 걸린다. 결제 가능 시각은 선점 응답에만 있다(예매 상세에 없다). 대화상자가 뜬 채 뒤로 가거나 새로고침하면 결제로 갈 길이 사라졌다(셀프 리뷰). 결제 화면에서 뒤로 가면 공연 상세로 간다 |
| 입장 시간 | 앱 화면이 62rem 이상이면 헤더 오른쪽(`HeaderSlot`), 그보다 좁으면 본문 맨 위에 "입장 유효" 시간 칩을 둔다. 좌석 응답의 `serverTime`으로 보정하고, 그 응답이 오기 전에는 만료를 재지 않는다. 0이 되거나 선점이 403이면 좌석을 잠그고(흐리게) 위험 알림과 [대기열로 돌아가기]를 보인다. 이 버튼은 저장한 토큰을 지우고 대기열로 바꿔 들어간다 | design-system.md 7절. 칩을 48rem부터 헤더에 두면 앱 화면 768~800px에서 헤더가 최대 46px 넘쳤고, 56rem부터 두면 단계 이름이 다 보이는 960~982px에서 오른쪽 여백을 22px 먹었다. 브라우저 시계가 빠르면 서버 시각이 오기 전에 만료가 먼저 발동해 시간이 남아도 잠겼다(셀프 리뷰에서 재현). 서버 시각으로 끝난 토큰을 지우지 않으면 브라우저 시계가 늦을 때 대기열이 아직 유효하다고 보고 좌석으로 되돌려 보낸다 |
| 초점 | 409·결과 모름·실패·입장 만료 알림이 뜨면 초점을 알림 자리로 옮기고, 알림을 닫으면 "좌석 선택" 제목으로 옮긴다. [해제]를 누르면 그 자리에 온 [해제], 없으면 앞 [해제], 다 비면 "선택한 좌석" 제목으로 옮긴다. 좌석 확보 대화상자는 [결제하러 가기]에 초점이 가고, 내려가면 "좌석 선택" 제목으로 온다 | [선택 완료]가 비활성으로 바뀌거나 누른 버튼이 사라지면 초점이 body로 떨어진다. 끼워 넣은 알림은 화면 낭독기가 읽지 않을 수 있어(ISE-114) 초점으로 읽힌다 |
| 탭 제목 | 다른 탭을 보는 사이에 차례가 돼 좌석 화면이 열리면 탭 제목을 "입장했어요 · 좌석을 골라 주세요"로 바꾸고, 탭으로 돌아오면 되돌린다 | 입장 시간 10분이 그때부터 줄어든다(ISE-114에서 미룬 것) |
| 다시 받기 | 좌석 응답은 창에 돌아올 때 다시 받지 않는다. 409 뒤, 결제 가능 시간이 지난 뒤, [다시 시도]에서만 받는다 | 응답이 811KB다 |

나중에 고칠 것(백엔드가 제공하면 붙인다):
- 좌석 응답에서 추첨석(`LOTTERY`)이 선택할 수 없음과 구분되지 않는다. 범례에서 추첨석을 뺐다.
- 응답에 구역 위치가 없어 구역 배치도는 실제 공연장 모양이 아니라 응답 순서다.
- 1인 최대 매수와 공연 제목이 좌석 응답에 없어 화면 이동 값과 공연 상세로 채운다. 주소로 바로 들어오면 공연 줄과 매수 안내가 없다.
- 409가 겹친 좌석을 알려 주지 않아 좌석 전체(811KB)를 다시 받는다.
- 접수형 202(`REQUESTED`)는 ISE-120에서 붙인다.

확인한 것(2026-11-04):
- 실제 백엔드: 로컬 compose에 붙인 개발 서버에서 샘플 사용자로 공연 10의 [예매하기] → 대기열 → 토큰 → 회차 9 좌석(25구역, 811KB, 319ms)까지 3.7초였다. A구역 두 석을 고른 사이 다른 계정(운영자)이 첫 좌석을 API로 먼저 잡게 하고 [2매 선택 완료]를 누르니 409 뒤 "A구역 1열 1번이 방금 다른 분께 선택됐어요"와 남은 한 석이 유지됐다. 한 석을 더 골라 보내니 201 `HELD`와 결제 가능 4분 50초 대화상자가 떴다.
- 목: headless Chrome으로 기본·`seat-conflict`·`hold-unknown`(재전송 표시 뒤 확보)·입장 만료(잠금 뒤 대기열로)를 따라갔다. 360~1440px 14폭에서 가로 넘침이 없고 워드마크는 한 줄이었다. 시간 칩은 1000px 이상에서 헤더, 991px 이하에서 본문에 있었고, 960~990px에서도 헤더 오른쪽 여백 24px가 유지됐다. 셀프 리뷰가 재현한 경우(결과 모름 뒤 503·409, 브라우저 시계가 빠름, 409 뒤 다시 받는 동안 고치기, 알림 닫은 뒤 초점)를 고친 뒤 같은 스크립트로 다시 따라가 확인했다.

## 결제 화면 규칙 (ISE-116)

좌석 화면의 [결제하러 가기]가 `/reservations/{reservationId}/payment`로 바꿔 들어온다(예매 단계 3). 생김새는 [samples/payment.html](samples/payment.html)이다. 흐름은 `pages/payment/paymentFlow.ts`(React 없는 실행기)와 `usePaymentFlow.ts`, 화면은 `PaymentPage.tsx`에 있다.

2026-11-09 ISE-210에서 생김새를 티켓 모양 결제 요약과 카드 그림 결제 수단 칸으로 바꿨다. 결제 가능 시간은 헤더 칩 하나만 둔다([design-system.md 12절](design-system.md)). 동작 규칙은 그대로다.

| 규칙 | 동작 | 이유 |
|---|---|---|
| 결제 대상 | 좌석 화면이 넘긴 값(선점 응답·좌석·공연 요약·서버 시계 차이)을 쓴다. 없으면(새 탭·주소) 예매 조회가 `HELD`이고 결제 토큰이 있을 때 그 값으로 만든다. 결제 가능 시각은 `holdExpiresAt` - 10초이고 공연 카드는 없다. 예매 조회는 화면을 열 때마다 한 번 하고, 열려 있는 동안 다시 받지 않으며 떠나면 버린다(결제 화면 전용 키) | 결제 가능 시각(`paymentTokenExpiresAt`)은 선점 응답에만 있다. 예매 상세는 조회마다 결제 토큰을 새로 서명하는데, 토큰 원문이 결제 멱등 본문에 들어가 다시 받으면 같은 키로 보낼 수 없다([결제 API](../payment/api.md) 구현 메모 "요청 해시") |
| 이미 끝난 예매 | 예매가 `CONFIRMED`면 예매 상세(`/reservations/{id}`)로 바꿔 들어간다(방금 결제한 것인지 몰라 "완료" 결과 화면이 아니다). `EXPIRED`·`RELEASED`·`CANCELED`면 "결제할 수 없는 예매예요"와 [좌석 다시 고르기]이고 결제 버튼을 막는다 | 결제 뒤 새로고침이나 뒤로 가기로 다시 열린 경우다 |
| 결제 요청 | [결제하기]가 `{paymentToken, amount, method: CARD}`를 보낸다. 멱등키는 결제 토큰마다 하나이고 sessionStorage(`auth/paymentAttempts.ts`)에 둔다. 응답 없음·504·503·429는 같은 키·같은 본문으로 8번까지 다시 보낸다. 결제사 장애(503 `PG_UNAVAILABLE`)·그 밖의 실패 뒤 [다시 결제하기], 결과 모름 뒤 [결제 결과 확인하기]도 같은 키다. 결제 중 새로고침하거나 뒤로 갔다 오거나 예매 상세의 [결제하기]로 다시 열면, 화면이 새로 받은 토큰이 아니라 저장한 토큰·키로 이어 보내 지금 상태를 보인다 | 서버가 같은 키에 처음 결과를 돌려줘 두 번 결제되지 않는다. 새 키로 보내도 같은 예매의 결제에 연결되지만(api.md 표 B), 같은 키라야 응답 없음 뒤 결과를 그대로 받는다. 결제사 장애는 결제 기록이 남지 않아 다시 보내도 된다(api.md 6단계). 화면 상태만 두면 새로고침 뒤 결제 중인 예매에 결제 버튼이 다시 보였다(셀프 리뷰). 예매 조회는 조회마다 토큰을 새로 서명하므로 새 토큰으로 바꾸면 같은 요청이 아니게 된다. 서버는 같은 키 재요청이면 토큰이 만료됐어도 결과를 준다(api.md 1절 3단계) |
| 확인 중 | 202 `REQUESTED`·`UNKNOWN`은 같은 "결제를 확인하고 있어요 … 화면을 닫아도 결제는 그대로 진행돼요"다. 응답의 `nextPollAfterSeconds`(서버 10초) 뒤 결제 조회를 보내고, 계속 확인 중이거나 조회가 실패하면 같은 간격으로 다시 본다. 2분이 지나면 "결제 결과를 아직 확인하지 못했어요"와 [결제 결과 확인하기]. 결제 ID를 받기 전(응답 없음·504)에는 "결제 요청을 보내고 있어요 … 화면을 닫지 말고 기다려 주세요" | 실패로 다루지 않는다(SA 11-1, E10). 간격은 서버 값을 그대로 쓴다. 서버 재확인은 22분까지 가지만 화면이 그동안 조회하지 않는다. 요청이 서버에 닿았는지 모를 때 "닫아도 된다"고 하면 결제가 없는 채 선점이 풀린다(셀프 리뷰) |
| 확정 확인 | `APPROVED`는 예매 확정이 아니다. 예매를 1초마다 조회해 `CONFIRMED`면 결과 화면으로 바꿔 들어간다. `EXPIRED`면 "예매가 확정되지 않았어요 … 결제 금액은 환불돼요", 30초가 지나도 `HELD`면 "결제는 승인됐어요 / 예매 확정이 늦어지고 있어요"와 [내 예매 보기]. 승인 뒤에는 조회 오류가 나도 실패로 보이지 않고 다시 조회한다 | 승인 결과는 이벤트로 2초 안에 반영된다(SA 9-4). 승인이 선점 만료 뒤 도착하면 예매가 `EXPIRED`가 되고 환불된다(결제 계약 1-4). 승인 뒤 조회 한 번 실패로 "다시 결제하기"를 보이면 결제된 사용자에게 실패로 안내하게 된다(셀프 리뷰) |
| 거절 | 200 `DECLINED`는 사유별 첫 문장(카드사 거절·한도 부족·시간 지남)과 "잡아 둔 좌석은 풀렸으니 좌석을 다시 골라 주세요", [좌석 다시 고르기]. 결제 조회로 거절을 알면 사유 문장이 없다 | 거절되면 예매가 `RELEASED`가 되고 같은 예매에 새 결제는 409 `PAYMENT_ALREADY_CLOSED`다. 결제 조회 응답에는 `reasonCode`가 없다 |
| 수동 확인 | 409 `PAYMENT_ALREADY_EXISTS`(`NEEDS_MANUAL_CHECK`)나 조회의 `NEEDS_MANUAL_CHECK`는 "결제 확인이 늦어지고 있어요 … 내 예매에서 확인해 주세요" | 운영자 Ops 명령으로만 풀린다(ADR 0028) |
| 결제 가능 시간 | 결제 전·요청 중·결제 ID 받기 전 확인 중·결제사 장애 동안 "결제 가능" 시간 칩(좌석 화면과 같은 헤더 자리). 서버에 결제가 생긴 뒤에는 숨긴다. 좌석 화면이 넘긴 서버 시계 차이가 있으면 0이 될 때 "결제 가능 시간이 지났어요"와 [좌석 다시 고르기]를 보이고 버튼을 막는다. 차이가 없으면(주소로 들어옴) 0이 돼도 막지 않고 서버의 403 `PAYMENT_TOKEN_INVALID`를 따른다 | 브라우저 시계로만 막으면 시계가 빠른 사용자가 시간이 남았는데 결제하지 못한다(ISE-115 셀프 리뷰와 같은 문제) |
| 좌석 화면과의 관계 | 서버에 결제가 생겼거나(결제 ID를 받음, 승인) 선점이 끝나면(거절·환불·시간 지남 등) 저장해 둔 선점(`auth/heldSeats.ts`)을 지워 좌석 화면이 좌석 확보 대화상자를 다시 띄우지 않게 한다. 결제사 장애·실패·결과 모름에서는 남긴다. [좌석 다시 고르기]는 지우고 대기열 경로로 바꿔 들어가며, 입장 토큰이 남았으면 대기열이 바로 좌석 화면으로 보낸다 | 결제가 생긴 선점으로 대화상자를 다시 띄우면 결제 중인 좌석을 또 결제하게 안내한다. 반대로 [결제하기]를 누르자마자 지우면 결제사 장애 뒤 좌석 화면으로 가서 살아 있는 선점을 두고 새 좌석을 또 잡았다(셀프 리뷰) |
| 초점 | 거절·수동 확인·시간 지남·실패처럼 읽고 행동해야 하는 단계가 되면 초점을 알림 자리로, 버튼이 확인 중 표시로 바뀌면 "결제 금액" 제목으로 옮긴다. 확인 중 단계 글자는 늘 있는 알림 영역(sr-only `role=status`)이 읽는다 | 버튼이 사라지거나 막혀 초점이 body로 떨어진다. 끼워 넣은 알림은 화면 낭독기가 읽지 않을 수 있다 |

나중에 고칠 것(백엔드가 제공하면 붙인다):
- 예매 상세에 결제 가능 시각(`paymentTokenExpiresAt`)과 결제 ID가 없어, 주소로 들어오면 `holdExpiresAt` - 10초로 계산하고 결제 상태를 따로 보이지 못한다.
- 결제 조회 응답에 거절 사유가 없어, 확인 중을 거쳐 거절되면 사유를 보이지 못한다.
- 토스 결제창(ISE-125)은 백엔드에 토스 어댑터가 없어 붙이지 않았다.
- 예매 상세에 예매 출처(일반·추첨, `source`)가 없다. 추첨 예매도 `HELD` 동안 결제 토큰을 주므로 주소로 결제 화면을 열면 자동결제 대상 예매를 카드로 결제하게 보인다(예매당 결제 하나라 먼저 들어온 쪽이 이긴다). 백엔드가 출처를 주면 추첨 예매에는 결제 버튼을 숨긴다.

확인한 것(2026-11-04):
- 실제 백엔드: 로컬 compose(Mock PG)에서 샘플 사용자로 회차 9 두 석을 잡고 [결제하러 가기] → [330,000원 결제하기]를 누르니 결제 승인 뒤 예매가 `CONFIRMED`가 되어 결과 경로로 넘어갔다(누른 뒤 1.2초). 처음에는 로컬 reservation-service가 예매 조회 API(ISE-171, #318) 전 이미지라 확정 확인 조회가 404였고, 최신 dev로 다시 빌드한 뒤 확인했다.
- 목: headless Chrome으로 승인, `payment-declined`(한도 부족 문장과 [좌석 다시 고르기]), `payment-unknown`(확인 중 뒤 승인), `pg-unavailable`([다시 결제하기]), `payment-manual`, `payment-slow-confirm`(30초 뒤 "결제는 승인됐어요")을 따라갔다.

## 예매 결과·내 예매 화면 규칙 (ISE-117)

같은 화면(`pages/reservations/ReservationPage.tsx`)이 두 경로로 열린다. 결제 화면이 확정을 보면 `/reservations/{id}/complete`(결과, 예매 단계 4 "완료")로 바꿔 들어오고, 내 예매 목록(`/me/reservations`)이나 주소로는 `/reservations/{id}`(상세)로 연다. 생김새는 [samples/reservations.html](samples/reservations.html)이다.

| 규칙 | 동작 | 이유 |
|---|---|---|
| 경로 둘 | 결과는 "예매가 확정됐어요"와 "예매 번호 …" 머리(카드 없이 가운데 정렬)와 가로 티켓 한 장, [내 예매 목록](주)·[다른 공연 보기](보조). 상세는 제목·상태 배지 머리와 티켓. 결제 화면에서 이미 확정된 예매를 열면(새로고침·뒤로 가기) 결과가 아니라 상세로 보낸다 | 예매 단계 표시는 경로의 handle로 정한다. 방금 결제를 끝낸 것인지는 경로로만 알 수 있다. 완료 직후 가장 먼저 찾는 것은 내 예매라 주 버튼으로 둔다 |
| 공연 제목 줄 | 결제 화면(공연 요약)이나 내 예매 목록(공연 제목·시작 시각)이 화면 이동 값(heading)으로 넘긴 제목·일시를 보인다. 없으면 "예매 {예매 번호}"가 제목이다 | 예매 상세 응답에 공연 제목·일시가 없다. 백엔드에 요청하지 않고 앞 화면이 가진 값만 쓴다 |
| 확정 | 좌석마다 티켓 번호를 보인다. 결제 화면이 확정 예매를 예매 상세 캐시에 넣고 오고, 확정은 1분 동안 다시 받지 않아 결과 화면이 그 값을 바로 그린다 | 티켓은 `CONFIRMED`일 때만 응답에 있다. 취소 API가 없어 확정은 끝난 상태다 |
| 완료 티켓 모양 | 한 장짜리 가로 티켓이다. 왼쪽 포스터, 가운데 ADMIT n·상태 배지·공연 제목·일시·공연장·좌석 줄(좌석, 금액, "등급석 · 티켓 번호")·예매 번호·결제 금액, 오른쪽 떼는 칸(공연 날짜·시각, 꾸밈 바코드)이다. 40rem 미만은 떼는 칸을 아래로 내리고 48rem 미만은 포스터를 숨긴다. 떼는 칸은 `aria-hidden`이고 바코드는 예매 번호로 그린다([design-system.md 12절](design-system.md)) | 예전에는 좌석마다 어두운 모바일 티켓 카드였다. 날짜는 일시 줄이 같은 내용을 가진다 |
| 포스터 조건 | 포스터는 화면 이동 값(`ReservationHeading`)에 `concertId`가 있을 때만 붙인다. 결제 화면이 공연 요약에서 넘길 때만 있다 | 내 예매 목록 응답에는 공연 번호가 없다. 백엔드에 요청하지 않고 앞 화면이 가진 값만 쓴다 |
| 결제 대기 | 이 브라우저에 결제 시도가 있으면 "결제를 확인하고 있어요"와 [결제 결과 확인]. 없고 결제 토큰이 있으면 "결제가 아직 확정되지 않았어요 / {시각}까지 확정되지 않으면 좌석이 풀려요. 이미 결제했다면 확정까지 잠시 걸릴 수 있어요"와 [결제하기]. 시각은 `holdExpiresAt` - 10초다. 토큰이 없으면(마지막 10초) "결제 가능 시간이 지났어요". `HELD` 동안 5초마다 다시 받아 확정·만료를 반영하고, `holdExpiresAt` + 30초가 지나면 멈춘다 | 예매 응답에 결제 상태가 없다. 승인 뒤 확정이 늦거나 운영자 확인을 기다리는 예매도 `HELD`라 "아직 결제하지 않았어요"라고 하면 결제한 사용자에게 틀린 안내가 된다(셀프 리뷰). 결제 화면은 저장한 시도가 있으면 그 토큰·키로 이어 보낸다(결제 화면 규칙) |
| 끝난 예매 | `EXPIRED`는 "예매가 확정되지 않았어요 … 결제한 금액이 있으면 환불돼요", `RELEASED`는 "좌석이 풀렸어요 … 결제가 거절돼", `CANCELED`는 "취소된 예매예요". 풀린 좌석과 [내 예매 목록]·[공연 보러 가기] | 결제 상태는 예매 응답에 없다. 승인이 만료 뒤 도착한 `EXPIRED`는 환불되므로 "결제한 금액이 있으면"으로 둘 다 덮는다 |
| 내 예매 | 서버가 최신순으로 20건씩 준다. `(쪽 + 1) × 크기 < totalElements`면 [더 보기]로 다음 쪽을 붙이고, 예매 번호로 중복을 거른다. 붙인 첫 항목으로 초점을 옮기고 "N건 더 불러왔어요"를 알린다. 항목은 공연 제목·상태 배지·일시·예매 번호·합계이고 누르면 상세로 간다. 비면 "아직 예매한 공연이 없어요"와 [공연 보러 가기] | 목록 API에 정렬·상태 필터가 없고 `totalPages`도 없다. 쪽 번호(offset) 방식이라 쪽 사이에 새 예매가 생기면 앞 쪽 마지막 항목이 다음 쪽에 또 온다 |
| 상태 배지 | 예매 확정(초록 점), 결제 대기(경고색), 기한 만료·좌석 반환·취소됨(회색) | 결제 대기만 사용자가 할 일이 남았다 |
| 다시 받기 실패 | 한 번 받은 예매·목록은 다시 받기나 [더 보기]가 실패해도 그대로 두고, 위나 버튼 옆에 오류와 [다시 시도]를 둔다. 처음 받기 실패만 전체 오류다 | TanStack Query는 다시 받기 실패에도 오류 상태가 된다. 오류 상태로 갈라 그리면 결제 직후 "예매가 확정됐어요"가 부하 중 429 한 번에 사라지고, [더 보기] 실패가 받은 목록을 지웠다(셀프 리뷰에서 재현) |

나중에 고칠 것(백엔드가 제공하면 붙인다):
- 예매 상세에 공연 제목·일시·공연장이 없어 주소로 열면 예매 번호가 제목이다.
- 예매 상세에 결제 ID·결제 상태가 없어 "결제 완료·환불 중·환불 완료"를 나눠 보이지 못한다.
- 내 예매 목록에 상태 필터가 없어 만료·해제된 예매도 함께 보인다.
- 예매 취소(ISE-119)는 취소 API가 없다.
- 예매 응답에 출처(일반·추첨)가 없어, 추첨 당첨 예매가 자동결제 중(선점 30분)일 때도 [결제하기]가 보인다. 예매당 결제는 하나라 두 번 결제되지는 않지만 한쪽은 "결제 확인이 늦어지고 있어요"로 끝난다. 결제 상태가 없는 것과 함께 문구로만 피해를 줄였다.

확인한 것(2026-11-04):
- 실제 백엔드: 로컬 compose에서 샘플 사용자의 내 예매(확정 2건, 기한 만료 여러 건)를 열고, 확정 예매 상세(좌석별 티켓 번호), 기한 만료 상세, 결과 경로(`/complete`, 주소로 열어 예매 번호 제목)를 확인했다. 375px에서 가로 넘침이 없었다.
- 목: 빈 목록 → 좌석 선점 → 내 예매(결제 대기) → 상세 [결제하기] → 결제 화면(예매 조회로 만든 결제 대상) → 결과 화면(헤더 예매 단계 "완료")까지 이어졌다.

## 추첨 응모 화면 규칙 (ISE-121)

`/lotteries/{추첨 번호}`(`pages/lotteries/LotteryPage.tsx`)다. 추첨 정보는 로그인 없이 보이고, 응모·결과·자동결제 카드는 로그인 뒤에 보인다. 대기열·입장 토큰을 거치지 않는다. 생김새는 [samples/lottery.html](samples/lottery.html)이다.

| 규칙 | 동작 | 이유 |
|---|---|---|

"알아 두세요"에 승계 안내를 늘 둔다 | 응모하는 곳이 스크롤해도 보인다. 승계 문장은 예비자 결과 카드와 같다. 시안의 공연 그림 배너는 추첨 응답에 공연 번호·제목이 없어 넣지 않았다 |
| 응모 티켓 | 응모 카드는 행동([n매 응모하기], [로그인하고 응모하기])을 절취선 아래에 둔다([design-system.md 13절](design-system.md)) | 티켓 모양을 흐름 전체에서 같게 한다 |
| 단계 | 응모 시작 전·응모 중·응모 마감·추첨 중·추첨 완료·종료. 상태가 `DONE`·`DRAWN`이면 그대로, 아니면 응모 기간과 추첨 시각을 브라우저 시계로 나눈다. 1초마다 다시 그려 시각을 넘는 순간 바뀐다 | 응모 시작 전에도 상태가 `OPEN`이다. 추첨 정보 응답에 서버 시각이 없다. 응모·취소 가능 여부는 서버가 정한다(`LOTTERY_NOT_OPEN`) |
| 응모 | 시작 전에는 버튼을 막고 "{시각}부터 응모할 수 있어요". 매수가 둘이면 고른다. 응모 한 번(매수)에 멱등키 하나다. 응답이 없거나 504면 내 응모를 다시 받고(있으면 결과 카드), 없으면 매수를 잠그고 [응모 결과 확인하기]로 같은 키를 다시 보낸다. 결과를 모르는 동안은 마감이 지나도 "응모하지 않았어요"라고 하지 않는다 | 서버 멱등키는 사용자별이 아니라 전역이고, 같은 키에 다른 매수는 409다. 서버는 같은 키를 기간 검사보다 먼저 봐서 마감 뒤에도 응모가 있었으면 그 상태를 준다. 마감 뒤 "응모하지 않았어요"로 바꾸면 응모가 된 사용자가 당첨돼 결제되는데도 응모하지 않았다고 읽힌다(셀프 리뷰에서 재현). 이미 응모했으면(다른 탭) 내 응모를 다시 받는다 |
| 자동결제 카드 | 이 브라우저에 카드 기록이 없으면 응모 폼에 "자동결제 카드를 확인해 주세요"와 [카드 등록하러 가기](아래 카드로 초점). 아래에 자동결제 카드(ISE-122)를 둔다. 안내 버튼은 카드의 [카드 등록]과 이름을 나눈다 | 당첨 때 카드가 없으면 서버가 거절(`BILLING_KEY_MISSING`)하고 당첨을 넘긴다. 응모 때는 서버가 카드를 보지 않는다. 다른 브라우저에서 등록했을 수 있어 "확인해 주세요"로 쓴다 |
| 응모함 | 매수와 결과 발표 시각. 응모 중이면 [응모 취소] → 확인 대화상자(닫으면 [응모 취소]로 초점). 취소 응답이 없거나 504면 내 응모를 다시 받고 대화상자에 "취소됐는지 확인하지 못했어요"(다시 눌러도 된다). 추첨 시각이 지나면 "추첨하고 있어요" | 취소하면 다시 응모할 수 없다(재응모 409). 이미 취소한 응모를 다시 취소해도 200이다. 마감이 지나 취소가 409면 대화상자에 알리고 두 조회를 다시 받는다 |
| 결과 | 당첨(자동결제 중), 당첨·결제 완료와 [예매 보기], 예비자("추첨 순위 N위"), 미당첨, 결제·배정 실패(사유별), 응모 취소. 예매 화면의 등급 배지는 추첨석(`LOTTERY`)을 "추첨"으로 보인다 | 당첨 예매는 자동결제가 끝날 때까지 결제 대기라 예매 화면에 [결제하기]가 보인다. 직접 결제하면 자동결제와 겹쳐 결제가 끝난 뒤에만 예매로 보낸다. 서버 `drawRank`는 예비 몇 번째가 아니라 전체 응모 중 추첨 순위라(당첨자 수보다 크고 건너뛴 번호가 있다) "예비 N번"이라 쓰지 않는다(셀프 리뷰) |
| 초점 | 응모·취소에 성공하면(결과를 모를 때 다시 받은 결과 포함) 누른 버튼이 사라진다. 그 뒤 10초 안에 처음 그린 카드만 한 번, 초점이 body로 떨어졌을 때 제목으로 초점을 옮긴다 | 다시 받기로 결과가 바뀔 때(응모함 → 당첨)는 사용자가 한 일이 아니라 초점을 옮기지 않는다(작업자 테스트에서 찾음) |
| 다시 받기 | 내 응모는 추첨 시각 뒤 `ENTERED`, 또는 `WON`·`WAITLISTED`일 때 10초(화면마다 0~3초를 더한다)마다 다시 받는다. 추첨 정보는 "추첨 중"일 때만. 추첨 + 90분이 지나면 멈춘다. 한 번 받은 결과는 다시 받기가 실패해도 그대로 두고 위에 오류를 둔다 | 서버 추첨·배정·승계 스케줄러가 1~10초 주기다. 승계 마감(추첨 + 30분)과 당첨 예매 선점(30분, 한 번 30분 연장)을 덮는다. 시계가 맞는 모든 화면이 추첨 시각에 함께 다시 받기 시작하므로 간격을 흩뜨린다(셀프 리뷰). 간격은 화면을 열 때 정한다. 매번 무작위로 정하면 1초마다 다시 그릴 때 타이머가 새로 시작돼 다시 받지 않는다 |

실패 사유 문구(`failReason`): `BILLING_KEY_MISSING`·`CARD_DECLINED`·`INSUFFICIENT_LIMIT`·`HOLD_EXPIRED`는 "자동결제가 되지 않았어요", `NO_SEAT`·`PURCHASE_LIMIT_EXCEEDED`는 "좌석을 배정하지 못했어요", 모르는 값은 "당첨이 다음 순번으로 넘어갔어요"다. 배정 실패는 서버가 받은 오류 코드를 그대로 남기므로 목록이 닫혀 있지 않다.

나중에 고칠 것(백엔드가 제공하면 붙인다):
- 공연·회차에서 추첨으로 가는 길: 회차 응답에 추첨 번호가 없다.
- 추첨 화면의 공연 제목: 추첨 정보에 회차 번호만 있다. 회차 번호로 공연을 찾는 API도 없다.
- 추첨 정보의 서버 시각: 단계를 브라우저 시계로 나눈다.
- 당첨 예매의 출처: 예매 응답에 출처가 없어 내 예매에서 연 당첨 예매에도 [결제하기]가 보인다(예매 결과 화면 규칙).
- 예비 몇 번째인지: 응답의 `drawRank`는 전체 추첨 순위라 승계까지 몇 명이 남았는지 보일 수 없다.

확인한 것(2026-11-04):
- 실제 백엔드: 운영자 API로 새 회차에 추첨(추첨석 4석, 응모 2분)을 만들고 QA 계정으로 따라갔다. 로그인 전 화면 → 응모 시작 전(버튼 막힘) → [카드 등록하러 가기](카드로 초점) → 카드 등록(안내 사라짐) → 응모 시작 순간 버튼 켜짐 → 2매 응모 → 추첨 중 → 추첨 10초 뒤 당첨 → 10초 뒤 결제 완료 → [예매 보기]로 확정 예매(추첨석 2매, 티켓 번호). 카드 없이 응모한 추첨은 "자동결제가 되지 않았어요 / 등록된 자동결제 카드가 없어…"로 끝났다. 당첨 예매의 좌석 등급은 `LOTTERY`라 등급 배지를 "추첨"으로 보이게 했다.
- 목: 추첨 1번(응모 중)에서 2매 응모 → 취소(초점이 새 카드 제목), 추첨 3번(추첨 완료)에서 카드 등록 뒤 당첨 → 결제 완료 → 예매 상세. 375px에서 가로 넘침이 없었다. 시나리오 다섯 가지로 예비·미당첨·실패·결과 모름·응모 기간 아님을 본다.

## 자동결제 카드 규칙 (ISE-122)

추첨에 당첨되면 등록한 카드(빌링키)로 자동결제된다. 같은 카드(`components/ticketing/BillingKeyCard.tsx`)를 내 정보(`/me`) 아래에 두고, 추첨 응모 화면(ISE-121)에도 둔다.

| 규칙 | 동작 | 이유 |
|---|---|---|
| 보유 표시 | 이 브라우저에서 등록에 성공하면 카드 끝 네 자리와 등록일을 사용자별로 기록해 두고 "등록됨 / 시연용 카드 •••• 4242 · 11.04 등록"을 보인다. 기록이 없으면 "기록 없음 / 이 브라우저에서 등록한 카드가 없어요"와 [카드 등록]만 두고 해지 버튼은 두지 않는다 | 빌링키 보유 여부를 묻는 API가 없다. 등록·해지 응답만 쓴다. 처음에는 다른 브라우저에서 등록한 카드를 위해 기록이 없어도 해지 버튼을 두었으나, 등록하지 않은 사용자에게 해지 버튼이 보여 혼란스럽다는 사용자 확인으로 없앴다(ISE-186). 다른 곳의 카드가 서버에 남아 있어도 다시 등록하면 앞 카드가 해지되고 새 카드로 바뀐다. 등록 결과를 모를 때만 안내에 [해지]를 둔다 |
| 등록 | 시연 결제(Mock PG)에 `demo-<UUID>`를 인증 값으로 보낸다. UUID는 멱등키와 같은 `newIdempotencyKey`로 만든다. 기록이 있으면 버튼이 [다른 카드로 바꾸기]다 | 실제 PG라면 결제창이 인증 값을 준다(ISE-125). `crypto.randomUUID()`는 http 배포 주소에서 없어 쓰지 않는다(localhost에서는 있어 로컬 확인으로는 드러나지 않았다, 셀프 리뷰). 서버는 사용자당 카드를 하나만 두고, 다시 등록하면 앞 카드를 해지한다 |
| 등록 실패 | 400 `BILLING_KEY_REJECTED` "카드사가 등록을 거절했어요", 503 `PG_UNAVAILABLE` "카드사 연결이 원활하지 않아요", 응답 없음·504 "등록됐는지 확인하지 못했어요 / 다시 등록하면 새 카드로 바뀌어요. 쓰지 않으려면 해지해 주세요"와 [해지], 그 밖은 공통 오류 안내. 해지하면 등록 실패 안내를 지운다 | 등록에는 멱등키가 없지만 다시 등록해도 새 카드로 바뀔 뿐이라 그대로 다시 누르게 한다. 503은 서버가 저장하지 않고 앞 카드도 그대로 두므로(`BillingKeyService`) "등록 안 됨"이 맞다 |
| 해지 | 확인 대화상자("자동결제 카드를 해지할까요? / 응모한 추첨에 당첨되면 결제되지 않아 당첨이 다음 순번으로 넘어가요")를 거친다. 요청 중에는 닫을 수 없고, 실패하면 대화상자 안에 오류를 둔다(다시 열면 지난 오류는 지운다). 닫으면 연 버튼으로, 그 버튼이 사라졌으면 등록 버튼으로 초점을 돌린다. `revoked: true`면 "자동결제 카드를 해지했어요", `false`면 "등록된 카드가 없었어요"이고 둘 다 기록을 지운다 | 당첨 때 카드가 없으면 서버가 결제를 거절(`BILLING_KEY_MISSING`)로 끝내고 당첨을 예비자에게 넘긴다(`BillingPaymentService`). 되돌릴 수 없는 결과라 한 번 더 묻는다 |
| 같은 화면·다른 탭 | 기록을 저장·삭제하면(`auth/billingKeyRecord.ts`) 같은 사용자의 카드가 모두 바로 바뀌고(`useSyncExternalStore`), 다른 탭의 변경은 `storage` 이벤트로 받는다. 카드마다 제목 id를 따로 만든다(`useId`) | 추첨 화면에서 등록하고 내 정보로 가거나, 한 화면에 카드가 둘일 때 어긋나지 않게 한다 |

나중에 고칠 것(백엔드가 제공하면 붙인다):
- 보유 조회 API가 없어 다른 브라우저에서 등록한 카드나 서버에서 해지된 카드는 이 화면이 모른다. 기록이 없으면 "기록 없음"과 [카드 등록]만 보이므로, 다른 브라우저에서 등록한 카드를 이 화면에서 해지할 수는 없다(다시 등록하면 바뀐다).
- 카드사·카드 이름이 응답에 없어 "시연용 카드"로 쓴다.

확인한 것(2026-11-04):
- 실제 백엔드: 로컬 compose에서 QA 계정으로 등록(•••• 4242와 토스트) → [해지] 확인 대화상자 → 해지(토스트, 기록 지워짐)를 확인했다.
- 목: 기본은 등록·해지 성공, `?mock=billing-unavailable`은 등록 503이다.

## 시연 모드 규칙 (ISE-180)

M3 시연은 브라우저와 Grafana를 나란히 띄우고(배포 서버에서는 Grafana를 바로 열고, 로컬은 compose의 3000번을 쓴다), 화면에서 보낸 요청 하나의 traceId로 서비스별 로그를 따라간다([observability.md](../infra/observability.md) 5절, ADR 0045).

| 규칙 | 동작 | 이유 |
|---|---|---|
| 켜고 끄기 | 주소에 `?demo=on`을 붙이면 그 탭에서 켜지고, `?demo=off`나 패널의 [시연 모드 끄기]로 끈다. 파라미터는 읽은 뒤 주소에서 지운다. 켜짐과 패널 너비·접힘은 탭 단위 sessionStorage(`iseonjwa.demo`)에 둬 새로고침해도 남는다. 기본은 꺼져 있다 | 사용자 결정(2026-11-03). 빌드·배포 이미지가 그대로라 시연 때 다시 빌드하지 않는다. 다른 사람이 켜도 보이는 것은 자기 요청의 traceId(이미 응답 본문에 있다)와 발표자 노트북 기준 localhost 링크뿐이다 |
| 기록 | `api/transport.ts`의 `send()`가 요청마다 한 건을 남긴다(메서드, `/api/v1` 경로, 상태, 걸린 시간, 응답 본문 `traceId`). 실패 응답, 응답 없음(상태 0), 재발급 요청도 남기고 TanStack Query가 취소한 요청은 남기지 않는다. 쿼리 값은 빼고 최근 50건만 메모리에 둔다. 꺼져 있으면 아무것도 남기지 않는다 | 응답 헤더에는 traceId가 없고 본문에는 성공·실패 모두 있다. 한 곳에서 남겨 화면마다 넣지 않는다. 쿼리 값을 빼는 것은 서버 공통 요청 로그(ISE-182)와 같은 규칙이다 |
| 패널 | 화면 오른쪽에 고정되고 앱 화면은 패널 너비만큼 비켜 선다(`--demo-panel-width`). 기본 380px이고 왼쪽 경계를 끌거나, 경계에 초점을 두고 화살표·Home·End로 바꾼다(280~720px, 앱 화면 360px은 남긴다). 경계를 두 번 누르면 기본 너비, [접기]는 44px 막대다. 640px보다 좁은 화면(휴대폰)에서는 그리지 않는다. 토스트는 패널을 뺀 앱 화면 가운데에 뜬다 | 사용자 결정(2026-11-03): 오른쪽 아래 떠 있는 패널 대신 오른쪽 일부를 쓰고 크기를 조절하며, 휴대폰에서는 숨긴다. 나란히 띄워 창이 절반(약 720px)이 돼도 앱 화면과 겹치지 않는다 |
| Grafana 링크 | traceId를 누르면 `<Grafana 주소>/d/iseonjwa-request-logs?orgId=1&var-traceId=<traceId>&from=<요청 시각-15분>&to=<요청 시각+15분>`(epoch ms)을 이름 붙인 탭(`iseonjwa-grafana`)에서 연다. 처음 한 번만 새 탭이 열리고 다음부터 그 탭을 다시 쓴다. 기준 주소는 화면을 연 호스트의 3000번이다(로컬 `http://localhost:3000`, 배포 `http://52.63.10.174:3000`). `VITE_GRAFANA_URL`로 바꾼다(http·https만). traceId가 16진수 16~32자가 아니면 링크 없이 글자만 보인다 | 로컬 compose는 Grafana를 `127.0.0.1:3000`에 열고, 배포 서버는 3000을 보안 그룹에서 팀원 IP에만 열어 익명 보기(Viewer)로 둔다. 어느 쪽이든 화면을 연 호스트의 3000번이라 빌드 때 주소를 넣지 않아도 된다. `_blank`는 누를 때마다 새 탭을 열어 나란히 띄운 앱 창을 가린다. 처음 열린 탭을 옆 창으로 옮겨 두면 앱 창은 그대로다. 이름으로 다시 찾으려면 `noopener`를 붙이지 않는다(여는 곳은 팀이 띄운 Grafana다). 앞뒤 15분은 브라우저·서버 시계 차이와 요청 뒤 Kafka 소비자가 남긴 로그까지 넣으려는 것이다. 대시보드 UID와 변수 이름은 ISE-178이 맞춘다(observability.md 5절) |
| 복사 | traceId 옆 [traceId 복사]는 `navigator.clipboard`가 있을 때만 보인다 | 브라우저는 보안 출처(https·localhost)에서만 클립보드를 준다. 배포 화면을 http로 열면 링크만 남는다 |
| 코드 분리 | 패널은 `React.lazy`로 따로 받는다(운영 빌드 7.9 kB). 켜지 않은 사용자는 받지 않는다 | 시연 도구 때문에 일반 사용자의 첫 화면이 무거워지지 않게 한다 |
| 디자인 시스템 예외 | 패널은 HTTP 상태, traceId 같은 기술 용어를 그대로 보인다 | 예매하는 사람의 화면이 아니라 발표용 관측 도구다([design-system.md](design-system.md) 1절 "기술 용어를 보이지 않는다"의 예외) |
| 앱 화면 반응형 | 앱 화면 안의 반응형은 화면 폭(`sm:`·`md:`)이 아니라 패널을 뺀 앱 화면 너비로 정한다. `AppLayout` 루트가 `@container`이고, 화면은 `@min-[40rem]:`(sm 자리)·`@min-[48rem]:`(md 자리)를 쓴다. 대화상자처럼 화면 전체에 뜨는 것은 화면 폭 그대로다. 메뉴 셋은 앱 화면이 28rem보다 좁으면 버튼 여백을 줄인다. 앞으로 만드는 화면도 이 규칙을 따른다 | 화면 폭 기준은 패널이 앱 화면을 좁힌 것을 모른다. 창 절반에 패널을 띄우면 360px 앱 화면에 넓은 배치가 그려졌다(리뷰에서 재현: 공연 상세 회차 카드가 본문을 넘치고 워드마크가 줄바꿈됨). 같은 이유로 360px 휴대폰의 로그인한 헤더도 깨졌다(고치기 전 워드마크 높이 72px, 고친 뒤 24px) |

남은 것:
- 이슈 완료 기준(Grafana에서 그 traceId로 서비스별 로그를 연다)은 ISE-178(Loki·Alloy·요청 로그 대시보드) 뒤에 확인한다. 정상 요청이 서비스 로그를 남기려면 ISE-182(공통 요청 로그 필터)도 있어야 한다.
- 같은 traceId의 Zipkin 트레이스는 대시보드가 잇는다(ISE-178). 프론트는 Zipkin을 직접 열지 않는다.

확인한 것(2026-11-03): 로컬 compose Gateway에 붙은 개발 서버를 `?demo=on`으로 열어 공연 목록 조회, 로그인 실패(401), 로그인 성공, 목록 재조회를 보냈다. 패널의 traceId 5건이 브라우저가 받은 응답 본문의 traceId와 모두 같았다. headless Chrome으로 1280px, 720px(창 절반), 360px을 캡처했고, 경계를 100px 끌면 너비가 380에서 480으로 바뀌어 새로고침 뒤에도 남았다. 접기 뒤 초점은 [펼치기]로 옮겨 갔다. 창 절반(720px)에서 공연 상세·목록·로그인 화면이 앱 화면(360px) 안에 들어가고(카드 오른쪽 끝이 본문 오른쪽 끝과 같다) 헤더와 본문 여백이 같다. traceId 링크를 두 번 눌러도 Grafana 탭은 하나만 열렸다.

## 운영자 화면 규칙 (ISE-123)

운영자가 시연 데이터를 화면에서 만든다. 공연 → 회차 → 회차 좌석 순서다. 입력 칸과 버튼뿐인 화면이라 HTML 샘플 없이 만들고 상태별 캡처로 확인했다(design-system.md 9절 5번 보완).

| 규칙 | 동작 | 이유 |
|---|---|---|
| 경로 | `/admin`(공연 목록), `/admin/concerts/new`(공연 등록), `/admin/concerts/{id}`(회차 목록·회차 추가·좌석 만들기). `RequireAuth` 아래 `RequireAdmin`이 내 정보 조회로 ADMIN인지 보고, 아니면 "운영자만 볼 수 있는 화면이에요"만 보인다 | 화면에서 막는 것은 안내용이다. 실제로 막는 곳은 Gateway(USER에게 403)와 서비스의 `@RequireRole`이다 |
| 들어가는 길 | 마이페이지 메뉴(`/me`·`/me/reservations`, ISE-188)에서 운영자에게만 [운영 화면] 링크를 보인다(ISE-123 때는 [내 정보] 화면 아래). 헤더 메뉴에는 두지 않는다 | 로그인 응답에 역할이 없어 헤더에 두려면 모든 화면이 내 정보를 한 번씩 더 조회해야 한다 |
| 공연 등록 | 제목(200자까지)과 설명(선택). 등록하면 그 공연 화면으로 바꿔 들어가고(replace) 공연 목록 조회를 새로 받는다 | 뒤로 가면 등록 화면이 아니라 운영 첫 화면이다 |
| 회차 추가 | 공연장 번호, 공연 시작·예매 오픈(`datetime-local`), 1인 최대 매수·선점 시간(선택, 비우면 서버 기본값 4매·5분). 오픈이 시작보다 늦으면 화면에서 막는다. 404는 공연장 번호 칸에 "이 번호의 공연장이 없어요"로 붙인다 | 서버 규칙(`ScheduleCreateRequest`, `Schedule.create`)을 화면에서 먼저 확인한다. 공연은 이 화면이 이미 조회했으므로 404는 공연장이다 |
| 시각 | 운영자가 넣는 시각은 보는 사람의 시간대와 상관없이 한국 시각으로 보고 `+09:00`을 붙여 보낸다(`lib/kstDateTime.ts`) | 공연은 한국에서 열린다. 화면 표시도 한국 시각이다(공연 화면 규칙 "시각 읽기") |
| 좌석 만들기 | 회차마다 [좌석 만들기]가 VIP·R·S 가격 대화상자를 연다. 비운 등급은 보내지 않는다. 등급 모음이 공연장과 다르면(400) "등급이 공연장 좌석과 맞지 않아요"를 대화상자 안에 보이고, 이미 만든 회차(409)는 "좌석이 이미 있어요"로 표시한다. 요청 중에는 대화상자를 닫을 수 없고, 닫히면 초점이 그 회차 줄(버튼, 만든 뒤에는 결과 글자)로 돌아간다 | 서버는 가격 등급이 공연장 좌석 등급과 정확히 같아야 받는다. `LOTTERY`는 공연장 등급이 아니라 칸이 없다. 좌석 15,000석을 만드는 동안 닫고 다른 회차를 열면 앞 응답이 새 대화상자를 닫았다(셀프 리뷰에서 재현). 트리거 없이 여닫아 Radix가 초점을 돌려줄 곳을 모른다 |
| 결과를 모를 때 | 공연·회차 등록이 응답 없음(0)·504면 실패 안내 대신 "등록됐는지 확인하지 못했어요. … 목록에 없을 때만 다시 등록해 주세요"를 보이고 목록을 다시 받는다. 좌석 만들기는 그냥 다시 보내도 된다 | 등록 API에 멱등키도 중복 검사도 없어, 504 뒤 다시 누르면 같은 회차가 둘 생기고 삭제 API가 없어 지울 수 없다(셀프 리뷰에서 재현). 좌석 만들기는 서버가 회차를 잠그고 이미 있으면 409를 준다 |

나중에 고칠 것(백엔드가 제공하면 붙인다):
- 공연장 목록 API가 없어 공연장을 번호로 넣는다. 로컬 시드는 KSPO DOME 하나(번호 1, VIP·R·S)다.
- 공연장의 좌석 등급을 알려 주는 API가 없어 가격 칸을 VIP·R·S 셋으로 두고, 맞지 않으면 서버 400으로 안다.
- 회차에 좌석을 만들었는지 조회할 수 없다. [좌석 만들기]는 늘 보이고, 이 화면에서 만들었거나 409를 받은 회차만 표시가 바뀐다.
- 운영자용 공연 목록 API가 없어 공개 목록(최근 등록순 50개)을 쓴다.
- 공연·회차 수정·삭제 API가 없다.

확인한 것(2026-11-04):
- 실제 백엔드: 로컬 compose에서 `.env`의 운영자 계정으로 [내 정보] → [운영 화면] → 공연 등록(공연 11) → 회차 등록(공연장 1, 회차 10, 한국 시각 그대로 표시) → 좌석 만들기(15,000석)를 따라갔다. 같은 회차에 다시 만들면 "이미 좌석을 만든 회차예요"였다. 사용자 공연 상세에 그 회차가 보이고, 샘플 사용자 토큰으로 운영 API를 부르면 Gateway가 403 `FORBIDDEN`을 줬다.
- 목: headless Chrome으로 일반 사용자 차단, 빈 제목, 오픈이 늦은 회차, 없는 공연장(99), 등급 불일치, 좌석 만들기를 따라갔다. 1280px·375px에서 가로 넘침이 없었다.

## 운영자 추첨 설정·비밀번호 초기화 규칙 (ISE-124)

운영자가 회차에 추첨을 설정·고치고, 회원 비밀번호를 초기화한다. 운영자 화면 규칙(ISE-123)처럼 HTML 샘플 없이 상태별 캡처로 확인했다.

| 규칙 | 동작 | 이유 |
|---|---|---|
| 경로 | `/admin/concerts/{공연}/schedules/{회차}/lottery`(설정), `/admin/lotteries/{추첨}`(보기·고치기), `/admin/users/password-reset`(비밀번호 초기화). 공연 화면 회차 줄의 [추첨 설정]은 오픈 전 회차에만, 이 브라우저에서 설정한 회차는 [추첨 #번호]다. 운영 첫 화면에 "추첨 번호로 열기"와 [비밀번호 초기화]를 둔다 | 설정 화면은 "추첨은 공연 시작 1시간 전까지"를 먼저 보려고 회차 시각이 필요해 공연 번호도 경로에 둔다(공연 상세 조회로 받는다) |
| 추첨 번호 기억 | 설정 응답의 추첨 번호를 회차별로 이 브라우저에 기억한다(`admin/adminLotteryRecords.ts`). 실제 API와 목의 기록을 나눠 두고, 쓰기 전에 공개 추첨 조회로 그 추첨이 있고 같은 회차인지 확인한다. 틀리면 기록을 지우고 [추첨 설정]을 보인다. 고치기 화면이 없는 추첨(404)을 만나도 지운다 | 운영자용 추첨 조회·목록 API가 없어 추첨 번호는 설정 응답에서만 나온다. 목은 새로고침하면 번호가 처음부터 다시 나가고 dev와 dev:mock이 같은 주소를 써서, 확인 없이 쓰면 새 회차가 남의 추첨 번호를 보이고 설정할 수 없었다(셀프 리뷰에서 재현) |
| 설정 칸 | 뗄 등급(VIP·R·S), 한 번에 응모할 매수(1·2), 추첨석 수, 예비 순번 수, 응모 시작·마감, 추첨 시각(한국 시각). 응모 시작 > 지금, 시작 < 마감 ≤ 추첨, 추첨 + 1시간 ≤ 공연 시작을 화면에서 먼저 본다. 예매 오픈이 지난 회차는 폼 대신 안내만 | 서버 규칙(`LotteryCreateRequest`, `Lottery.LotterySettings.validate`, 설정 시점 규칙)을 따른다. 예비 순번 수의 서버 기본값은 없어 "추첨석의 절반 정도"를 권한다 |
| 권장 시간대 | 추첨 시각이 한국 시간 03:00~05:00 밖이면 입력 중에 정보 알림을 보이고, 저장 뒤 서버 경고(`DRAW_AT_OUTSIDE_LOW_TRAFFIC_WINDOW`)도 보인다. 막지 않는다 | 추첨 직후 자동결제가 몰려 일반 결제와 결제사 자리를 다툰다(서버 `DrawTimeWindow`) |
| 설정 결과 | 추첨 번호, 설정 요약, 경고, 응모 화면 주소(복사), [응모 화면 열기]·[설정 고치기]·[공연으로 돌아가기]. 결과 제목으로 초점을 옮긴다 | 공연 화면에서 추첨으로 가는 길이 없어 주소를 응모할 사람에게 알려야 한다 |
| 오류 | 이미 있음(409)은 "이 화면에서는 그 추첨의 번호를 알 수 없어요 … "추첨 번호로 열기"에 넣어 주세요"와 [운영으로]. 설정 마감(409)은 안내, 좌석 모자람(409)은 추첨석 수 칸에, 칸별 오류 없는 400은 값 사이 규칙을 다시 알린다. 결과 모름은 "다시 설정했을 때 이미 있다고 나오면 설정된 거예요" | 설정 API에 멱등키가 없다. 다시 보내면 성공했던 경우 409 `LOTTERY_ALREADY_EXISTS`가 된다. 409 응답에 기존 추첨 번호가 없어 화면이 찾아 줄 수 없다 |
| 고치기 | 공개 추첨 조회로 지금 값을 채운다. 뗄 등급·예비 순번 수는 조회에 없어 비워 두고 "비우면 바꾸지 않아요". 바꾼 칸만 PATCH로 보낸다. 저장하면 응답 값(등급·예비 순번 수 포함)으로 다시 채운다. 응모가 시작됐거나 `OPEN`이 아니면 폼 대신 값만 보인다. 바꾸지 않은 시각 칸은 칸 값(분) 대신 저장된 값(초 포함)으로 비교한다 | 서버는 보낸 필드만 고치고, 응모가 시작되면 409로 막는다. 회차 시각을 모르므로 "추첨은 공연 1시간 전까지"는 서버가 본다 |
| 비밀번호 초기화 | 회원 번호를 넣고 확인 대화상자를 거친다. 내 계정이면 막고 비밀번호 변경으로 안내한다. 결과는 임시 비밀번호(복사)와 "이 화면을 떠나면 다시 볼 수 없어요", 회원이 할 일. 없는 회원은 대화상자를 닫고 칸에, 그 밖의 실패는 대화상자 안에 보인다. 임시 비밀번호는 화면 상태에만 두고 저장하지 않는다. 요청 캐시도 남기지 않는다(`gcTime: 0`, [다른 회원 초기화] 때 지움). [다른 회원 초기화]는 회원 번호 칸으로 초점을 옮긴다 | 회원을 찾는 API가 없어 번호로 부른다. 회원은 내 정보에서 자기 "회원 번호"를 본다. 응답은 한 번만 볼 수 있다(서버 `Cache-Control: no-store`). 요청 로그 패널은 본문을 남기지 않는다. 서버는 자기 계정 초기화를 막지 않는데, 하면 내 Refresh 토큰이 폐기돼 곧 로그아웃되고 결과 카드와 함께 임시 비밀번호도 사라진다(셀프 리뷰) |
| 복사 | 읽기 전용 칸과 [복사]. 칸에 초점이 가거나 칸을 누르면 전체를 고른다. http 주소처럼 `navigator.clipboard`가 없으면 [복사]를 숨긴다 | 보안 출처(https·localhost)에서만 클립보드 API가 있다(요청 로그의 traceId 복사와 같은 처리) |

나중에 고칠 것(백엔드가 제공하면 붙인다):
- 운영자용 추첨 조회·목록이 없어 다른 브라우저에서 설정한 추첨은 공연 화면이 모른다. 추첨 번호로 연다.
- 이미 있음(409) 응답에 기존 추첨 번호가 없다.
- 공개 추첨 조회에 뗀 등급·예비 순번 수가 없어 고치기 화면이 두 칸을 비워 둔다.
- 회원 검색(이메일)이 없어 회원 번호로 초기화한다.
- 추첨 삭제 API가 없다.

확인한 것(2026-11-04):
- 실제 백엔드: 로컬 compose에서 `.env`의 운영자 계정으로 새 회차(공연 17)에 [추첨 설정] → R석 4석·예비 2명·2매·응모 1~2시간 뒤·추첨 3시간 뒤(권장 시간대 밖 안내) → 추첨 #3과 서버 경고·응모 화면 주소 → [설정 고치기]: 등급·예비 순번 수는 빈칸, 바꾼 칸 없이 저장하면 "바꾼 칸이 없어요", 추첨석 수만 6으로 저장하면 응답 값(R석·예비 2)으로 다시 채워짐 → 공연 화면 회차 줄 "추첨 #3". 새로 가입한 회원의 번호로 비밀번호 초기화 → 16자 임시 비밀번호와 결과 제목으로 초점, 그 비밀번호로 로그인하면 403 `PASSWORD_CHANGE_REQUIRED`, 이전 비밀번호는 401.
- 목: 운영자 계정(회원 번호 1)으로 새 회차에 좌석을 만들고 추첨 설정 → 데모 계정이 응모. 데모 계정(회원 번호 42) 비밀번호 초기화 → 임시 비밀번호로 로그인하면 비밀번호 변경이 필요하다.

## 시연 장애 패널 규칙 (ISE-134)

운영자가 시연 중에 Mock PG에 장애를 걸어 결제 실패·지연 흐름을 보여 준다. 시나리오별 클릭 순서와 기대 화면은 [demo-scenarios.md](../../guides/demo-scenarios.md)에 있다.

| 규칙 | 동작 | 이유 |
|---|---|---|
| 경로 | `/admin/demo/faults`. 운영 첫 화면에 [시연 장애 패널] 카드를 둔다 | 운영자 화면 묶음 안에 둔다(ADMIN 보호 그대로) |
| API | Gateway 운영자 경로 `/api/v1/admin/demo/pg/faults`(조회·설정)와 `/ledger/summary`만 쓴다. Mock PG 응답은 공통 응답 형식이 아니라 `apiRequest`의 `envelope: false`로 받는다 | 2026-11-09 사용자 결정: 프론트 nginx 직접 중계는 인증이 없어 공개 시연 사이트에서 누구나 장애를 걸 수 있다. `reset`·결제 API는 열지 않는다 |
| 시나리오 | 결제 거절·PG 응답 지연(4초)·승인 응답 유실은 다음 결제 1건(`count: 1`), PG 서버 오류는 해제할 때까지 건다. 걸린 시나리오 카드에 "걸려 있음"을 단다 | 결제 서비스의 PG 읽기 시한이 2초라 지연은 그보다 넉넉히 길게 둔다. 서킷 브레이커는 최근 20건 중 절반 넘게 실패해야 열려 버튼 한 번으로 재현되지 않는다 |
| 지금 걸린 장애 | `NONE`이 아닌 설정만 호출 종류·모드·남은 횟수(또는 "해제할 때까지")·지연·확률·주문 한정으로 보인다. 패널을 띄워 둔 동안 3초마다 다시 받는다. [모두 해제]는 호출 종류 다섯 개 모두에 `NONE`을 보낸다. 시나리오의 "걸려 있음"은 모드뿐 아니라 지연·횟수·한정까지 같을 때만 단다 | 시연 뒤 장애가 남아 다른 사람의 결제가 실패하는 일을 막는다. 1건짜리 장애는 다른 창의 결제가 쓰므로 화면이 오래된 상태를 보이지 않게 한다. k6가 건 짧은 지연을 시나리오로 잘못 보이지 않게 한다 |
| 장애 주입이 닫힌 환경 | 설정 조회가 code 없는 404면(Mock PG가 `local` 프로필이라 Boot 기본 본문) 버튼과 다시 조회를 멈추고 "이 환경에서는 장애를 걸 수 없어요"를 보인다. 공통 형식 404(Gateway에 경로가 없어 예매 서비스가 받음)는 일반 오류로 보인다 | 로컬 compose는 Mock PG를 `local`로 띄운다. 배포 서버는 `loadtest`라 열려 있다(compose.deploy.yml) |
| 경고 | "이 서버의 모든 결제에 걸려요"를 늘 보인다 | `orderId`를 미리 알 수 없어 주문으로 한정하지 못한다. 다른 사람의 결제가 그 한 번을 가져갈 수 있다 |
| 목 | MSW는 설정을 기억해 보여 주기만 하고, 목 결제 흐름은 따르지 않는다(결제 시나리오는 `?mock=`으로 고른다) | 목 결제는 이미 시나리오 스위치가 있다 |

## 팀원이 알아 둘 것

- Notion 「SA 기획·설계 결정 기록」 #7은 "정적 HTML·JS"로 남아 있다. 프론트 결정은 이 문서와 ADR 0040을 따른다. 저장소 기록과 Notion이 어긋나면 저장소 기록을 따른다(`AGENTS.md` 대전제 4).
- Gateway와 백엔드 API 계약은 바뀌지 않는다. CORS 설정도 넣지 않는다.
- compose에 frontend 서비스가 생겨 공개 포트가 바뀌었다(ISE-109). `checkPortExposure` 공개 목록에 `frontend`를 더했고 로컬 화면은 `http://localhost:8000`이다. 배포 EC2는 nginx 80만 전체에 열고 8080은 부하 측정 때 발생기 보안그룹에만 연다([deployment.md](../infra/deployment.md), 배포 담당 안준현, ISE-6). 로컬 `docker compose up`에 frontend 이미지 빌드가 더해지는 점은 PR과 팀 공지로 알린다.
