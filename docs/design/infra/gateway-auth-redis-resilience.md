# Gateway `auth-redis` 레질리언스 설정을 정하기까지 (2026-11-09~10)

상태: 기록. 재측정 1·2회는 2026-11-10 UTC에 G1으로 쟀다(5-1절, 정본 [open-peak-scenarios.md](open-peak-scenarios.md) 3절 "배포 서버 4차"). 2회 값을 운영 기본값으로 옮기는 결정은 [ADR 0050](../../decisions/0050-gateway-auth-redis-breaker-bulkhead-split.md)(제안, 2026-11-11)이다. 배포 뒤 운영값으로 다시 재는 것은 아직이다.

이틀 동안 부하 측정에서 Gateway 인증 차단기가 먼저 열렸다. 이 문서는 그 원인을 찾으며 "무엇을 생각했고, 무엇이 틀렸고, 무엇으로 바꿨는지"를 시간 순서로 모은다. 트러블슈팅 정리와 발표의 원천이다. 숫자는 모두 아래 원천 문서에서 옮겼고, 원천에서 확인하지 못한 것은 "확인 못 함"으로 적었다.

## 0. 한 줄 요약
Redis는 멀쩡한데(Redis 컨테이너 CPU 8%, 조회 0.3~1.9ms) 차단기가 열렸다. 차단기가 재는 시간에는 Gateway 자신의 혼잡(CPU 대기, GC, Lettuce 스레드 대기)이 섞이고, 벌크헤드 거절도 차단기 실패로 세어지기 때문이었다. 그래서 숫자(기준값)를 풀기보다 **무엇을 셀지(실패의 뜻)와 어떤 순서로 끊을지(시한 > 느린 호출 기준)**를 다시 정했다.

## 1. 용어
| 말 | 풀어 쓴 말 | 이 문서에서의 뜻 |
|---|---|---|
| `auth-redis` | 인증 Redis 확인 | 인증이 필요한 요청마다 Gateway가 Redis에 "이 토큰이 로그아웃됐나"를 묻는 호출. 이 호출을 감싼 차단기·벌크헤드의 이름이기도 하다 |
| 차단기 | 서킷 브레이커(circuit breaker) | 최근 호출의 실패·느린 호출 비율이 기준을 넘으면 일정 시간 호출을 아예 막는 장치. 열리면(OPEN) 인증 요청 전체가 503이다 |
| 벌크헤드 | bulkhead, 동시 실행 상한 | 동시에 실행할 수 있는 호출 수를 세는 허가 카운터(세마포어). 스레드가 아니다. 넘치면 즉시 거절(`BulkheadFullException`) |
| 시간 제한 | TimeLimiter | 차단기 바깥에서 호출 전체에 거는 시한. Gateway는 1초다 |
| 필터 시한 | 인증 필터의 Redis 시한 | `GatewayAuthenticationFilter`가 Redis 조회에 거는 시한. 100ms(SA 9-4 `[가정]`) |
| Lettuce | Redis 클라이언트 라이브러리 | Gateway가 쓰는 비동기 Redis 클라이언트. 연결 1개를 공유하고, 응답 처리를 I/O 스레드에서 한다 |
| 느린 호출 기준 | `slow-call-duration-threshold` | 이 시간을 넘으면 성공해도 "느린 호출"로 센다 |
| 창 | sliding window | 차단기가 비율을 계산할 "최근 호출" 범위. 건수 기준(마지막 N건) 또는 시간 기준(마지막 N초) |
| 웜업 | warm-up | 본 측정 전에 낮은 부하로 JIT 컴파일(실행 중 기계어 변환)과 연결을 데우는 것 |
| 과수용 | 감당 못 할 부하를 거절하지 않고 받음 | 빨리 거절하는 대신 줄을 세워 지연이 폭증하는 상태 |
| fail-closed | 실패 시 닫힘 | Redis를 확인할 수 없으면 통과시키지 않고 503을 준다는 원칙([ADR 0005](../../decisions/0005-auth-redis-fail-closed.md)) |
| Q1 / L1 | 측정 시나리오 이름 | Q1은 대기열 진입 몰림(ISE-202, 대기열 담당), L1은 추첨 응모 몰림(ISE-94, 강민) |

| 순서 | 장치 | 값(운영) | 이 순서 때문에 생기는 일 |

| 4 | Redis 조회 | 필터 시한 100ms, Lettuce 명령 시한 100ms | 차단기가 재는 시간 = 구독 순간부터 응답 신호가 돌아온 순간까지. Redis 일한 시간이 아니다 |

## 4. 정리된 원칙
| 원칙 | 왜 | 근거 장면 |
|---|---|---|
| 클라이언트가 재는 시간은 클라이언트의 혼잡도 잰다 | 차단기 타이머는 Gateway 안에 있다. CPU 포화에 가까워지면 Redis 탓으로 열려 인증 전체를 막는다 | 5, 8 |
| 의존성 장애 감지(차단기)와 자기 과부하 차단(벌크헤드)은 집계를 나눈다 | 거절이 실패로 세어지면 과부하가 곧 "Redis 장애"가 되어 10초 전체 거절로 커진다 | 3, 5, 8 |
| 시한 > 느린 호출 기준 | 그래야 "느리지만 응답함"과 "응답 없음"이 나뉜다 | 8 |
| Lettuce 명령 시한 > 필터 시한 | 필터 시한이 먼저 걸려야 `lookup_timeout`으로 분류된다 | 6, 8 |
| 벌크헤드 = 목표 처리량 × 정상으로 볼 한 건 시간(리틀의 법칙) | 그 이상 머무는 호출은 혼잡으로 보고 빨리 거절한다. 25가 차려면 1,200/s에서 한 호출이 약 21ms 머물러야 한다(계산값). Redis 자체는 2ms 안이라, 벌크헤드 포화는 CPU 포화의 증상이다 | 3, 5 |
| 창은 처리량과 함께 정한다 | 건수 창 20은 1,000/s에서 0.02초다. 시간 창 10초·최소 500건으로 바꾸면 순간 지연에 덜 흔들린다 | 4 |
| 측정용으로 보호 장치를 풀지 않는다(운영 한도 판정에는) | 풀어서 얻은 숫자는 운영에서 나오지 않는다. 푼 측정(C3~E)은 "다음 병목 찾기"로만 쓴다 | 2, 5 |
| 비교 실험은 출발 상태부터 맞춘다 | 값을 바꿀 때마다 Gateway가 다시 뜨면 "식은 정도"가 두 번째 변수가 된다 | 2, 3 |

## 5. 지금 정한 값과 대가
아래 "운영" 칸은 ADR 0050 이전 값이다. 재측정 2회 값이 새 운영 기본값이 됐다([ADR 0050](../../decisions/0050-gateway-auth-redis-breaker-bulkhead-split.md)). 재측정은 덮어쓰기(`loadtest/deploy/compose.gateway-bulkhead.yml`, #470, main 반영 #471)로 했다.

| 값 | 운영 | 재측정 1회 | 재측정 2회 | 감수할 점 |
|---|---|---|---|---|
| 창 | 건수 20, 최소 20 | 시간 10초, 최소 500건 | 같음 | 초당 50건 미만이면 10초 창이 차지 않아 차단기가 판정하지 않는다 |
| 느린 호출 | 50ms·50% | 100ms·80% | 같음 | Redis가 실제로 느려져도 늦게 감지한다 |
| 실패율 | 50% | 50% | 50% | 2회에서는 실패의 뜻이 "Redis 응답 없음·연결 오류"로 좁아진다 |
| 열림·반열림 | 10초·5건 | 5초·20건 | 같음 | 진짜 장애 때 시험 호출이 더 많이 나간다 |
| 필터 시한 | 100ms | 200ms | 200ms | 진짜 Redis 멈춤 때 사용자가 503까지 최대 200ms 기다린다 |
| Lettuce 명령 시한 | 100ms | 300ms | 300ms | 반응형 호출에 이 시한이 걸리는지 확인 못 함 |
| 벌크헤드 | 25 | 100 | **50 + 거절을 차단기에서 제외** | 50은 1,000/s × 50ms로 낸 계산값이고 측정 근거가 없다. 1,200/s 이상에서는 거절 503이 보일 것이다 |

회를 나눈 이유는 한 번에 하나만 바꾸기 위해서다. 1회는 시한을 띄운 효과, 2회는 벌크헤드를 낮추고 차단기와 떼어 낸 효과를 본다.

### 5-1. 재측정 결과(G1, 2026-11-10 UTC)
L1은 요청마다 reservation·Postgres까지 가서 뒤쪽 비용이 Gateway 숫자를 흔든다. 그래서 인증 경로만 부르는 G1(`GET /schedules/{id}/queue/me`)으로 쟀다. 웜업은 1차 표준(100/s 2분 → 1,000 30초 → 3,000 10초)을 회마다 넣었다.

| 목표 | 1회 성공 / p95 | 2회 성공 / p95 |
|---|---|---|
| 2,000/s | 99.53% / 208ms | 98.90% / 157ms |
| 2,500/s | 98.16% / 497ms | 95.58% / 428ms |
| 3,000/s | 92.67% / 1.01s | 87.96% / 806ms |

- 두 회 모두 3,000/s까지 차단기가 열리지 않았다. 503은 모두 벌크헤드 거절(`bulkhead_full`)이고 Redis 시한 초과·연결 오류는 0건이다. 3절 장면 2·3의 "Redis는 멀쩡한데 인증 전체가 막힘"은 이 설정에서 재현되지 않았다.
- 2회에서 거절이 차단기 집계에서 모두 빠졌다(`failed` 0, `ignored` 16,024). 4절의 "집계를 나눈다" 원칙이 배포 경로에서 동작한다.
- 벌크헤드 50은 거절을 늘리고 p95를 줄였다. 성공 처리량은 두 회 모두 약 2,300~2,470/s에서 멈췄고 서버 CPU가 99%였다. 7절의 "장비 CPU가 한도"와 맞는다.
- 각 1회 측정이다. 운영 반영(벌크헤드 50 + 거절 제외 + 시한 200ms 등)은 SA 9-4의 100ms `[가정]`을 바꾸는 결정 기록과 함께 정한다.

### 5-2. 차단기 예민화 실험 0a와 Gateway OOM(배포 서버 5차, 2026-11-11 UTC)
강민은 CPU 포화를 맨 앞 유입 제한으로 막자는 추천 대신, 차단기 느린 호출 기준을 낮춰 포화 전에 열리게 해 보기로 했다([판단 기록](../../ai-judgments/kangmin/2026-11-11-breaker-first-for-gateway-cpu-saturation.md)). 기준선 0a(ADR 0050 값)의 결과는 아래와 같다. 자세한 표는 [open-peak-scenarios.md](open-peak-scenarios.md) "배포 서버 5차"에 있다.

- 서버 CPU 90%는 1,000/s(평균 75%)와 1,500/s(평균 93%) 사이에서 넘었다. 굿풋(200ms 안 성공)은 약 1,470/s에서 멈췄다.
- 2,500/s(서버 CPU 99%)에서 사용자 p95는 878ms였지만, 차단기가 잰 호출 시간은 평균 11~17ms였고 느린 호출 비율은 0.13% 이하였다. 기다린 시간 대부분이 차단기가 재는 구간 밖(구독 전 이벤트 루프 대기, CPU 차례 대기)에 있다(추정). 그래서 느린 호출 기준을 낮춰 CPU 포화를 잡으려면 기준이 정상 호출 시간에 가까워져야 한다. 1단계에서 확인한다.
- CPU 몫: gateway 50~55%, reservation 23%, alloy(로그 수집) 7~10%, kafka·redis 각 4~10%. Gateway 안에서는 HTTP 이벤트 루프가 약 70%, Lettuce 응답 처리 스레드가 약 20%다.
- 느린 호출 기준을 20ms로 낮춘 회차(B20)도 2,500/s까지 열리지 않았다(느린 호출 비율 최대 24%). 차단기로 CPU 포화를 잡는다는 가설은 닫았다. 차단기는 Redis 장애 전용으로 두고(ADR 0050 그대로), 과부하는 맨 앞 동시 수 상한(A1)으로 막는 쪽으로 간다.
- 0b JFR 기준 Gateway Java CPU 몫: 관측(추적·지표·MDC·문맥 전파) 약 24%, 헤더 처리 약 7%, JWT 6.6%, Redis·차단기 2.5%다.
- M1(Gateway 상한 1,024MiB, 직접 메모리 128MiB)로 OOM 조건을 다시 돌리자 OOM은 0건이었다(메모리 최대 849MiB). 하지만 동시 요청을 더 받아 2,000/s p95가 752ms로 나빠졌다. 죽는 실패가 느려지는 실패로 바뀌었을 뿐이라, 맨 앞 동시 수 상한(A1)과 함께 가야 한다. A1 첫 값은 리틀의 법칙으로 64(32·64·128을 재서 정함)를 추천한다(5차 절 "A1 첫 상한값 근거").
- **Gateway가 컨테이너 메모리 한도(768MiB)로 세 번 강제 종료됐다.** 동시에 처리 중인 요청이 많을수록 힙이 최대(512MB)로 커진다. 힙 최대에 비힙 약 158MB와 JVM 밖 메모리 약 130MB를 더하면 한도를 넘는다(계산값). Gateway에는 동시 처리 수 상한이 없다. 이 실패는 CPU 포화보다 먼저 서비스를 내리고, 차단기로는 막지 못한다(추정).

## 7. 그래도 남는 한계
- 차단기·벌크헤드는 Redis 조회 한 번(평소 1ms 안팎)만 감싼다. 인증을 통과한 뒤 reservation·DB에서 수백 ms를 쓰는 구간은 막지 않는다. 그래서 차단기를 정상화해도 약 1,200~1,600/s에서는 장비 CPU가 한도다.
- 실제 사용자는 503을 받으면 약 1초 뒤 다시 보낸다(`Retry-After: 1`). k6는 다시 보내지 않으므로 측정은 실제 오픈보다 낙관적이다(추정).
- 근본 후보(로그아웃 목록 로컬 캐시, fail-open, 장비 분리 [ADR 0047](../../decisions/0047-single-ec2-first-managed-split-review.md))는 보안 성질이나 비용이 바뀌어 이번 범위에서 고르지 않았다.

## 8. 트러블슈팅·발표로 쓸 때
- 한 문장: "Redis는 멀쩡한데 인증 차단기가 열렸다. 차단기가 Gateway 자신의 혼잡을 Redis 장애로 오해하는 구조여서, 기준을 푸는 대신 무엇을 실패로 셀지를 다시 정했다."
- 보여 줄 장면:
  - 3절 장면 3: 벌크헤드 가설을 25·100 비교로 반증했다.
  - 장면 5: 풀면 병목이 옮겨 간다(C2 → D, 1.5배와 CPU 100%).
  - 장면 6: 1.0s의 정체, 측정값을 만드는 기록 방식을 의심했다.
  - 장면 8: 직관(시한을 조이자)이 구조상 반대로 작동함을 소스로 확인했다.
- AI 판단 사례: 거부 2건(장면 1 "벌크헤드 없음", 장면 2 "측정용 완화"), 수용 2건(장면 6 기록값 해석, 장면 8 재측정 값).
- 예상 질문:
  | 질문 | 답의 요지 |
  |---|---|
  | 벌크헤드를 키우면 되지 않나 | 거절이 늦어질 뿐 한도는 같았다(25·100 비교). 장비 여유가 없으면 늦춘 만큼 대기가 쌓인다 |
  | 차단기를 끄면 되지 않나 | fail-closed라 Redis가 정말 멈추면 모든 요청이 시한만큼 기다린다. 차단기는 그때 빨리 거절하려고 둔다. 끄는 것이 아니라 Redis 탓인 실패만 세게 했다 |
  | 왜 시한을 100ms보다 늘렸나 | 시한은 느린 호출 기준보다 커야 두 판정이 나뉜다. 낮추면 Gateway 혼잡이 곧 실패가 된다 |
  | 운영에 반영했나 | 아직이다. 재측정 뒤 SA 9-4의 100ms `[가정]`을 바꾸는 결정 기록과 함께 정한다 |
