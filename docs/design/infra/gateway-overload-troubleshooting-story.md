# Gateway 과부하를 측정으로 좁혀 간 기록: 차단기 오탐에서 거절 위치까지 (2026-11-09~12)

상태: 기록(8차 결과 반영). 2026-11-11 작성, 2026-11-12 7·8차 결과 반영, kangmin. 트러블슈팅 항목은 [TS-56~59](../../troubleshooting.md)이고, 이 문서는 그 사이의 생각 흐름을 단계별로 모은다. 발표의 트러블슈팅 장면과 이력서 서사의 원천이다.

숫자는 모두 아래 원천에서 옮겼다. 측정 정본은 [open-peak-scenarios.md](open-peak-scenarios.md) 3절 "배포 서버 1~8차"이고, 11/9~10 판단 흐름은 [gateway-auth-redis-resilience.md](gateway-auth-redis-resilience.md)에 있다. 원천에서 확인하지 못한 것은 "확인 못 함", 원천이 추정으로 적은 것은 "(추정)"으로 그대로 옮겼다. 측정은 별도 표시가 없으면 회차마다 1회다.

## 팀원용 3분 요약

**문제**: 티켓 오픈처럼 인증이 필요한 요청이 몰리면 Gateway가 먼저 무너졌다. 모양이 세 번 바뀌었다.
1. Redis는 멀쩡한데 인증 차단기가 열려 모든 요청이 503이 됐다.
2. 그걸 고치자 CPU가 한계가 됐다. 4 vCPU 한 대에서 1,500/s에 서버 CPU 93%였고, 2,000/s 굿풋 1,469·p95 435ms에서 처리량이 멈췄다.
3. 더 몰리면 Gateway가 OOM으로 죽었다.

**해본 것**(한 회차에 하나만 바꿔 쟀다. 배포 서버 1~8차, 11/9~12)

| 순서 | 해본 것 | 된 것 | 안 된 것 |
|---|---|---|---|
| 1 | 차단기가 "무엇을 실패로 세나"를 바꿈(벌크헤드 거절 제외, ADR 0050) | 3,000/s까지 차단기가 열리지 않음 | 한도가 CPU로 옮겨 갔다 |
| 2 | 차단기를 예민하게(느린 호출 20ms) | — | CPU 포화를 막지 못함. 차단기가 재는 구간 밖에서 기다림이 생겼다(가설 실패) |
| 3 | Gateway 메모리 768 → 1,024MiB | OOM 0 | 동시 요청을 더 받아 오히려 느려짐(p95 752ms) |
| 4 | 맨 앞 동시 처리 수 상한 64 | 2,000/s p95 435 → 87ms, 메모리 평탄 | 서버 CPU는 그대로(1,500/s 93%) |
| 5 | 상한 거절을 관측·로그보다 앞(HttpHandler 데코레이터)으로 | 2,500/s 굿풋 +13%, 거절 한 건이 받은 요청의 2~8%로 싸짐(8차 R0) | 과부하의 서버 CPU는 그대로. 상한은 남은 CPU를 받은 요청으로 다시 채운다 |
| 6 | 요청 로그를 실패·느린 요청만 남김(`problems`, ADR 0052) | 7차에서 끄자 1,500/s 93 → 85%. 8차에서 운영 설정 `problems`가 같은 날 끔과 2%p 안팎(1,500/s 78.5% 대 79.1%) | 1,000/s는 +2.9%p로 판정 보류 칸(4%p 미만이라 바꿀 조건은 아님) |

**지금 운영 상태**(배포 `eda80051`, 2026-11-12)
- 차단기·벌크헤드는 ADR 0050 값이다. 벌크헤드 거절은 차단기 실패로 세지 않고, 거절 비율 경보로 본다.
- Gateway 메모리는 1,024MiB에 직접 메모리 128MiB다.
- 동시 처리 수 상한 64가 HttpHandler 데코레이터에 있다. 넘치면 503 `GATEWAY_OVERLOADED`(`Retry-After: 2`)를 준다.
- Gateway 요청 로그는 `problems`다(5xx·끊긴 요청·200ms 이상). ADR 0052는 제안 상태이고 서비스 쪽은 2단계 전이다.
- 8차 같은 G1 부하에서 1,500/s 서버 CPU 78.5%, 2,500/s 굿풋 약 2,250, p95 50~54ms다. 처음(5차 0a)과는 날이 달라 바로 빼지 않는다. 같은 설정도 날에 따라 6~9%p 달랐다(8차).

**남은 한계와 다음**
- 과부하(2,500/s)에서 서버 CPU는 96~97%다. 동시 수 상한은 지연·메모리를 지키지만 CPU를 남기지 않는다. 과부하에서 CPU를 남기려면 받는 양을 묶어야(요청률 상한) 하고, 그만큼 굿풋을 버린다. 그래서 목표를 둘로 나눴다(11/12 강민 결정): 평상(1,500/s)은 서버 CPU 90% 미만, 과부하(2,000/s 이상)는 p95·OOM 0·굿풋으로 판정한다. 과부하 판정에는 "모든 요청 한 건당 CPU" 대신 "성공 한 건당 CPU"를 쓴다. 포화 단계의 CPU ÷ 모든 요청은 몫이라 상수에 가깝기 때문이다(단계 7, 4절).
- 한 대의 한도다. 4 vCPU 한 대에 컨테이너 21개이고 Gateway가 약 2코어를 쓴다. 남은 큰 수단은 장비 분리([ADR 0047](../../decisions/0047-single-ec2-first-managed-split-review.md)의 검토 항목)다.
- 요청 수 자체를 줄이는 대기열 폴링 상한 30초 제안은 강민이 거부했다. 지금 10초도 느리다는 판단이다([판단 기록(거부)](../../ai-judgments/kangmin/2026-11-12-reject-poll-max-30s.md)).
- 다음: 요청 로그 2단계(공통 필터, contract 이슈), 상한 64·96·128 반복 측정(8차에서 뺐다), Gateway가 아닌 호스트 쪽 CPU(Docker 로그 경로 추정)를 프로세스별로 재기.

## 0. 한 줄 요약과 전체 흐름
Redis는 멀쩡한데 인증 차단기가 열리는 문제에서 시작해, "차단기로 CPU 포화를 막을 수 있나"를 실험으로 반증하고, OOM과 지연을 동시 처리 수 상한으로 묶은 뒤, 거절에도 CPU가 든다는 사실에서 "관측은 필터보다 앞에서 시작한다"를 소스로 찾아 거절 위치를 HttpHandler 데코레이터로 옮기고, 7차에서 서버 CPU를 실제로 내린 것은 거절 위치가 아니라 요청 로그 경로였다는 것을 찾고, 8차에서 그 결과를 운영 설정(`problems`)으로 옮겨 같은 날 끔과 비교하고 거절 한 건의 비용을 직접 재기까지의 기록이다.

| 단계 | 날짜(UTC) | 바꾼 것 하나 | 핵심 숫자 | 판정 |
|---|---|---|---|---|
| 1 | 11/9~10 | (원인 찾기) 실패 원인 지표 추가 | 열린 원인 대부분 `bulkhead_full` 10~17건 | 원인 확인 |
| 2 | 11/10 | 차단기 집계에서 벌크헤드 거절 제외 등(ADR 0050 값) | 3,000/s까지 차단기 닫힘, 거절 16,024건 모두 `ignored` | 성공. 한도가 CPU로 옮겨 감 |
| 3 | 11/11 | 없음(기준선 0a), JFR(0b) | 1,500/s 서버 CPU 93%, 2,000/s 굿풋 1,469·p95 435ms | 기준선 |
| 4 | 11/11 | 느린 호출 기준 100 → 20ms(B20) | 2,500/s까지 열림 0회, 느린 호출 비율 최대 24% | 가설 실패 |

## 1. 용어
| 말 | 풀어 쓴 말 | 이 문서에서의 뜻 |
|---|---|---|
| 차단기 | 서킷 브레이커(circuit breaker) | 최근 호출의 실패·느린 호출 비율이 기준을 넘으면 일정 시간 호출을 막는다. `auth-redis`가 열리면 인증 요청 전부가 503이다 |
| 벌크헤드 | bulkhead, 동시 실행 상한 | Redis 조회를 동시에 몇 개까지 하나 세는 허가 카운터. 차면 바로 거절(`bulkhead_full`) |
| 동시 처리 수 상한 | in-flight limit, 동시성 제한 | Gateway 전체에서 처리 중인 요청 수를 세어 넘치면 바로 503(`GATEWAY_OVERLOADED`). 설계 메모의 A1 |
| 부하 차단 | load shedding | 감당할 수 있는 양만 받고 넘친 요청을 일찍 싸게 거절하는 것 |
| 굿풋 | goodput, 유효 처리량 | 200 응답이면서 200ms 안에 끝난 요청 수/초. 받기만 하고 늦은 요청은 빼고 센다 |
| 리틀의 법칙 | Little's law, L = λW | 평균 처리 중 수 = 평균 도착률 × 평균 머문 시간. 평균에 대한 식이다 |
| 이벤트 루프 | event loop | Netty가 적은 수의 스레드로 많은 연결의 I/O를 번갈아 처리하는 구조. Gateway는 `reactor-http-epoll` 4개 |
| 관측 | Observation(Micrometer) | 요청 하나를 시작·끝으로 감싸 추적 스팬과 `http_server_requests` 지표를 함께 만드는 장치 |
| HttpHandler 데코레이터 | HttpHandler decorator | WebFlux 요청 처리의 가장 바깥 처리기(`HttpHandler`)를 한 겹 감싸는 것. 관측·WebFilter보다 앞이다 |
| run queue | 실행 대기 수 | `vmstat`의 `r`. 4 vCPU에서 4를 계속 넘으면 CPU 차례를 기다리는 스레드가 있다 |
| JFR | Java Flight Recorder | JVM 내장 프로파일러. 실행 표본으로 어느 코드가 CPU를 쓰나 본다 |
| OOM | out of memory | 여기서는 컨테이너 메모리 한도를 넘어 커널이 프로세스를 죽인 것 |
| 웜업 | warm-up | 본 측정 전 낮은 부하로 JIT 컴파일과 연결을 데우는 것. 판정에서 뺀다 |

## 2. 환경과 일하는 원칙
- 배포 서버는 `m7i.xlarge` 한 대(4 vCPU, 15.7GiB)에 컨테이너 21개가 함께 돈다. 발생기는 같은 VPC의 `c6i.xlarge`, k6 v1.0.0이다. Gateway는 CPU 제한이 없다.
- 4차부터는 인증 경로만 부르는 G1(`GET /api/v1/schedules/{id}/queue/me`)으로 쟀다. L1은 reservation·Postgres까지 가서 뒤쪽 비용이 Gateway 숫자를 흔들기 때문이다.
- 단계 무효 규칙(5차부터): 빠진 요청이 목표의 1%를 넘거나 발생기 CPU 유휴가 10% 미만이면 그 단계는 무효다. 발생기 한계를 서버 한계로 읽지 않으려는 것이다.
- 강민 원칙 세 가지다.
  - 한 회차에 값 하나만 바꾼다. 말씀: "원인 파악을 놓치지 않게 한 번에 적용하는 게 아닌 순차적으로 적용해 보면서 지표를 쌓는 게 더 정확할 것 같아"([일지](../../ai-judgments/kangmin/daily/2026-11-11.md)).
  - 회차마다 바꾼 값·이유·전후 차이를 누적 표에 쌓는다(6절).
  - 실패한 가설도 같은 형식으로 남긴다. 실패 이유가 다음 가설을 정한다.

## 3. 단계별 기록

### 단계 1. Redis는 정상인데 차단기가 열린다 (11/9~10, 배포 1~3차, 측정 youngeun)
| 칸 | 내용 |
|---|---|
| 현 상황 | 1차 데운 Q1 2,000/s에서 201 428건 / 503 19,573건. Q2 대기자 10,000명은 시작 3초 뒤 열려 600초 동안 회복 못 함. Redis 서버 지연 0.1~0.8ms |
| 목표 | 503의 출처와 차단기가 열린 이유를 가른다 |
| 가설 | (a) 벌크헤드 25가 한도다 (b) 느린 호출 기준 50ms가 너무 낮다 |
| 실험 | 1차 벌크헤드 25 대 100, 2차 느린 호출 50 → 100ms, 3차 원인 지표(#463) 뒤 설정 다섯 가지(R1·R2·R3·F·G) |
| 결과 | 25·100 모두 2,000/s에서 열림(한도 같음). 100ms로 올리자 "실패"로 열림(실패 최대 1.0s). 3차에서 열린 원인 대부분이 `bulkhead_full` 10~17건 |
| 성공·실패 이유 | (a)(b) 둘 다 틀렸다. 벌크헤드가 차단기 안쪽이라 거절이 차단기 실패로 세어졌고, 건수 창 20은 1,000/s에서 0.02초(계산값)라 순간 거절 10건이면 열렸다. 1.0s는 안쪽 시한 초과의 중복 기록이었다 |
| 다음 가설 | 기준값을 풀지 말고 "무엇을 실패로 셀지"를 바꾸면 Redis가 멀쩡할 때 차단기가 열리지 않는다 |

- 왜 그렇게 생각했나: 처음에는 숫자(벌크헤드 크기, 느린 호출 기준)가 한도라고 봤다. 25와 100의 한도가 같다는 결과가 "크기가 아니라 구조"로 시선을 옮겼다.
- 차단기가 재는 구간: 차단기 타이머는 Gateway가 구독한 순간부터 응답 신호가 돌아온 순간까지다. Redis가 일한 시간이 아니다. 그 사이 Lettuce I/O 스레드 대기(연결 1개를 모든 요청이 공유), GC 멈춤, CPU 차례 대기가 섞인다([학습 노트](../../learning/kangmin/qna/2026-11-10-gateway-threads-bulkhead-vs-server-spec.md) 10절, 라이브러리 소스로 확인).
- 측정 도구의 숫자도 검증 대상이었다. 2차의 "실패 1.0s"는 기록 방식이 만든 값이었고, 고친 뒤 R1의 실제 시간은 110~115ms였다.
- 이 단계의 자세한 장면 8개와 판단 기록은 [gateway-auth-redis-resilience.md](gateway-auth-redis-resilience.md) 3절에 있다. TS는 [TS-51](../../troubleshooting.md)(L1 콜드 시작), [TS-53](../../troubleshooting.md)(원인 기록 빈의 기동 실패), [TS-56](../../troubleshooting.md)이다.

### 단계 2. 차단기 역할을 Redis 장애로 좁힌다 (11/10, 배포 4차 G1)
| 칸 | 내용 |
|---|---|
| 현 상황 | 단계 1의 원인을 알았지만 고친 값이 배포 경로에서 동작하는지 모른다 |
| 목표 | Redis가 멀쩡하면 차단기가 열리지 않게 한다 |
| 가설 | 시한 순서(Lettuce 300 > 필터 200 > 느린 호출 100ms)를 지키고 벌크헤드 거절을 차단기 집계에서 빼면, 과부하가 Redis 장애로 보이지 않는다 |
| 실험 | 1회: 시간 창 10초·최소 500·시한 200/300ms·벌크헤드 100. 2회: 1회 + 벌크헤드 50 + `ignoreExceptions: [BulkheadFullException]`. 1,000~3,000/s |
| 결과 | 두 회 모두 3,000/s까지 닫힘. 2회 거절 16,024건 모두 `ignored`, `failed` 0. 2,000/s p95 208 → 157ms. 성공은 약 2,300~2,470/s에서 멈추고 서버 CPU 99% |
| 성공·실패 이유 | 실패의 뜻이 "Redis 응답 없음·연결 오류"로 좁아져 오탐이 사라졌다. 대신 한도가 장비 CPU로 드러났다 |
| 다음 가설 | CPU 포화를 막아야 한다. 무엇으로 막나(단계 3·4) |

- 운영 반영은 [ADR 0050](../../decisions/0050-gateway-auth-redis-breaker-bulkhead-split.md)(#487)이다. 거절을 차단기에서 빼면 과부하가 차단기 상태로 안 보이므로 거절 비율 경보 2개를 함께 넣었다.
- 강민이 먼저 낸 "시한은 더 빡빡하게, 느린 호출은 더 넓게"는 거뒀다. 시한과 느린 호출 기준은 같은 구간을 재므로, 시한을 낮추면 Gateway 혼잡이 곧 실패가 된다. 직관이 구조상 반대로 작동한 사례다.

### 단계 3. 기준선을 다시 재고 CPU를 나눈다 (11/11, 배포 5차 0a·0b)
| 칸 | 내용 |
|---|---|
| 현 상황 | 4차는 서버 CPU를 단계별로 기록하지 못했다. 어디가 CPU를 쓰는지 모른다 |
| 목표 | 같은 날 같은 조건의 기준선과 CPU 분해(서버·컨테이너·스레드·코드) |
| 가설 | (측정 단계) Gateway가 가장 많이 쓰고, 그 안에서 줄일 곳이 보일 것이다 |
| 실험 | 0a: ADR 0050 값 그대로, 1,000~3,000/s, 단계 사이 30초 쉼. 0b: 같은 값 + JFR. 수집은 `vmstat`·`mpstat`·`pidstat -t` 1초, `docker stats` 약 3초 |
| 결과 | 서버 CPU 평균 1,000/s 75% → 1,500/s 93%. 굿풋은 약 1,470/s에서 멈춤(2,000/s 1,469, p95 435ms). 컨테이너 몫 gateway 50~55%, reservation 23%. Gateway 스레드는 `reactor-http-epoll` 4개 합 130%, `lettuce-epollEventLoop` 39%(2,000/s) |
| 성공·실패 이유 | JFR(0b): 관측 묶음 약 24%, `HttpHeaders` 처리 6.9%, HTTP I/O 17.6%, JWT 6.6%, 로그 5.2%, Redis·차단기 2.5%. JFR 부담은 0.4~0.7%로 반복 변동 안이었다 |
| 다음 가설 | 강민 가설: 차단기 시간에 Gateway 대기가 섞인다면 기준을 낮춰 포화 전에 열 수 있다(단계 4) |

- 한 건당 Gateway CPU(계산값 = 쓴 코어 × 1,000 ÷ 달성 요청 수/초)는 2,000/s에서 0.95ms다. 서버 전체는 2.0ms다.
- 0a의 3,000/s는 VU 상한과 OOM으로 무효였다. OOM은 단계 5에서 따로 다뤘다.
- 이 단계에서 이미 "Redis·차단기 코드는 CPU의 2.5%"라는 숫자가 나왔다. 단계 4의 결과를 예고한 숫자였지만, 강민은 측정으로 닫기로 했다.

### 단계 4. 차단기를 예민하게 하면 CPU 포화를 막을 수 있나 (11/11, 배포 5차 B20, 가설 실패)
| 칸 | 내용 |
|---|---|
| 현 상황 | 1,500/s에서 서버 CPU 93%. AI는 맨 앞 유입 제한을 추천했고 강민은 거부했다 |
| 목표 | 서버 CPU 90% 미만(`[가정]`, 강민)에서 차단기가 열려 CPU를 지킨다 |
| 가설 | CPU 포화 때 Gateway 대기가 Redis 호출 시간에 섞여 늘어나므로, 느린 호출 기준을 낮추면 포화 직전에 열린다 |
| 실험 | 느린 호출 기준 100 → 20ms 하나만 바꿈. 0a에서 차단기가 잰 시간 평균이 2,500/s 11~17ms라 그 근처로 한 번에 낮춤(강민 B 선택, 50·30ms 단계 생략) |
| 결과 | 2,500/s까지 열림 0회(웜업 포함). 20ms 기준 느린 호출 비율 최대 24%(기준 80%). CPU 90%를 넘는 1,000→1,500/s 구간의 비율은 10% 안팎 |
| 성공·실패 이유 | 기다림이 차단기 구간 밖에 있었다. 0a 2,500/s에서 사용자 p95 878ms, Gateway 경로 시간 평균 200~240ms, 차단기가 잰 시간 평균 10.7~16.5ms |
| 다음 가설 | CPU 포화와 OOM의 공통 원인은 "받아 주는 동시 요청 수에 상한이 없다"이다. 맨 앞에서 동시 수를 묶는다 |

- 무엇이 틀렸나: "Gateway 대기가 차단기 시간에 섞인다"는 단계 1에서 맞았던 사실이다. 그러나 섞이는 것은 구독 뒤의 대기(Lettuce 스레드, GC)였다. 과부하에서 크게 늘어난 것은 구독 전의 대기, 즉 이벤트 루프와 CPU 차례에서 인증 필터까지 오기 전의 줄이다(추정, 학습 노트 10절 표의 D·C). 차단기는 그 줄을 보지 못한다.
- 기준을 더 낮추면: 차단기가 90% 전에 열리려면 기준이 정상 호출 시간(1,000/s 평균 1~5ms)까지 내려가야 한다(추정). 그러면 평소에도 열리고, 열리면 넘친 만큼이 아니라 인증 전부를 막는다. 단계 1의 전면 장애로 돌아간다.
- 결론은 처음 거부한 AI 추천과 같았다. 차이는 "그렇다더라"가 아니라 "B20에서 24%였다"를 근거로 갖게 됐다는 점이다. [판단 기록(거부)](../../ai-judgments/kangmin/2026-11-11-breaker-first-for-gateway-cpu-saturation.md), [TS-57](../../troubleshooting.md).

### 단계 5. Gateway가 OOM으로 죽고, 메모리만 늘리자 느려진다 (11/11, 배포 5차 0a·M1)
| 칸 | 내용 |
|---|---|
| 현 상황 | 0a 도중 Gateway가 컨테이너 OOM으로 세 번 죽음(08:18:53·08:25:46·08:35:11Z, anon-rss 757~758MB, 상한 768MiB). 활성 VU 5,309~5,938일 때와 3,000/s 본 측정 |
| 목표 | Gateway가 몰림에서 죽지 않게 한다 |
| 가설 | 힙 최대 + 비힙 + JVM 밖 메모리가 상한보다 크다. 상한을 키우면 OOM이 사라진다 |
| 실험 | M1: `mem_limit` 768m → 1,024m, `-XX:MaxDirectMemorySize=128m`(설계 메모 A안을 한 묶음). OOM이 났던 발생기 설정(`PRE_VUS` 3,000·`MAX_VUS` 6,000) |
| 결과 | OOM 0건, 메모리 최대 849MiB. 2,000/s 굿풋 1,469 → 1,315, p95 435 → 752ms. 2,500/s p95 2.46s, 3,000/s에서 504 |
| 성공·실패 이유 | 죽지 않게 됐지만, 동시 요청을 더 받아(최대 6,000) 줄이 길어졌다. "죽는 실패"가 "느려지는 실패"로 바뀌었다 |
| 다음 가설 | 메모리 예산(M1)과 동시 수 상한(A1)은 함께 가야 한다 |

- 계산: 힙 512MB + 비힙 약 158MB + JVM 지표 밖 약 130MB ≈ 800MB > 768MiB(계산값). 처리 중 요청 하나에 약 47KiB로 보면 (768 − 500) ÷ 0.047 ≈ 5,700개에서 죽고, 실제 OOM 때 VU 5,309~5,938과 맞는다(거친 계산값).
- 벌크헤드 50은 Redis 조회만 감싸고 차단기는 열려도 연결을 받는다. 그래서 단계 2·4의 장치로는 OOM을 막을 수 없다(추정).
- B안(`-Xmx384m`)은 첫 OOM 직전 힙 사용이 341MB라 GC가 잦아질 위험이 커서 고르지 않았다. [TS-58](../../troubleshooting.md).

### 단계 6. 맨 앞 동시 처리 수 상한 (11/11, 배포 6차, 측정 kangmin)
| 칸 | 내용 |
|---|---|
| 현 상황 | A1(`GlobalFilter` -200, 인증 -100 앞)과 M1이 운영에 들어감(#488, 배포 `8b95fe68`) |
| 목표 | 같은 부하에서 굿풋이 0a·M1보다 낮지 않고 p95 200ms 안 |
| 가설 | 맨 앞에서 동시 수를 묶으면 넘친 요청은 일찍 거절되고, 받은 요청의 p95와 메모리가 묶여 굿풋이 는다. p95 200ms를 지키는 처리 중 수는 60~67(계산값) |
| 실험 | 상한 64(기본값) → 32 → 128 → 500(대조군) → 128 재측정(L128b, 웜업 맞춤). 그 밖은 5차 M1과 같음 |
| 결과 | 2,000/s 굿풋 / p95: L32 1,575 / 49ms, L64 1,696 / 87ms, L128b 1,721 / 162ms, L500 1,304 / 571ms(0a 1,469 / 435ms). 메모리 511~540MiB 평탄, OOM 0. 상한이 있으면 2,500/s도 유효(L64 굿풋 1,608) |
| 성공·실패 이유 | 상한이 Gateway 안의 줄 길이를 끊었다(성공). 그러나 서버 CPU는 어느 상한에서도 1,500/s 91~93%, 2,500/s 99%(실패). L32는 1,000/s에서도 392건을 거절했고, L128은 처리 중 수가 벌크헤드 50 위로 올라가 `bulkhead_full`이 섞였다(2,500/s 1,966건, L64 96건) |
| 다음 가설 | 상한값이 아니라 요청 한 건당 CPU를 줄여야 한다. 첫째는 거절 한 건의 비용 |

- 첫 상한값이 64가 된 이유(리틀의 법칙): 굿풋이 멈춘 약 1,480/s에서 p95/평균 비가 약 4.5~5였다. p95 200ms에 맞는 평균은 약 40~45ms이고, L = 1,480/s × 0.040~0.045s ≈ 60~67이다(계산값). 구현 세션 설계안은 500이었다. 1,500/s × p95 152ms ≈ 228의 약 2배로, p95를 평균 자리에 넣은 값이다. 리틀의 법칙은 평균에 대한 식이라 64를 첫 값으로 두고 32·64·128·500으로 확정하기로 했다. L500은 실제로 2,000/s에서 571ms로, 식의 전제를 어기면 상한이 OOM만 막는다는 것을 보여 줬다.
- 왜 굿풋이 늘었나: 5차에서 사용자 대기의 대부분이 Gateway 이벤트 루프·CPU 차례였다. 그 줄이 상한 크기로 짧아졌다. 넘친 요청은 시한까지 기다리다 실패하지 않고 바로 503을 받아 발생기 VU도 빨리 돌아왔다(L64 최대 VU 208, M1 5,792).
- 기본값: 6차 세션은 128을 제안했고, 강민은 64를 유지했다. 2,000/s 차이 25건(1.5%)은 같은 128을 두 번 잰 차이(5%) 안이고, p95는 64가 약 절반이다. [판단 기록(거부)](../../ai-judgments/kangmin/2026-11-11-keep-in-flight-limit-64.md).

### 단계 7. 거절에도 비용이 든다 → 관측은 필터보다 앞에서 시작한다 → 데코레이터 (11/11, 설계·구현)
| 칸 | 내용 |
|---|---|
| 현 상황 | 2,500/s에서 거절 비율 25%(L500)~40%(L32)로 달라도 한 건당 Gateway CPU 0.66~0.71ms(계산값) |
| 목표 | 거절 한 건의 비용을 줄여 서버 CPU를 내린다 |
| 가설 | 관측 비용 가설: 거절된 요청도 서버 관측(스팬·지표)·요청 로그·라우트 매칭을 거치느라 CPU를 쓴다. 이보다 앞에서 거절하면 그 비용이 사라진다 |
| 실험 | (설계) 처음 안은 "관측 필터보다 앞의 WebFilter"(A안). 소스 확인 뒤 `HttpHandler` 데코레이터(B안)로 바꿈. 속성·지표·기본 64·응답·운영자 경로 예외·반납 방식은 그대로 |
| 결과 | #497로 dev, #498로 배포(`1e9b1c75`). 7차 H1(6차 L64와 같은 부하): 서버 CPU ±1%p, 2,000/s 굿풋 1,696 → 1,781·p95 87 → 73ms, 2,500/s 굿풋 1,608 → 1,814·p95 104 → 78ms. 한 건당 Gateway CPU 0.71 → 0.72ms(2,500/s, 계산값) |
| 성공·실패 이유 | 9절에 미리 적은 판정 기준(한 건당 Gateway CPU·서버 CPU가 내려감)으로는 실패다. 그런데 이 기준이 가설을 가리지 못한다는 것을 결과를 보고 알았다. 서버 CPU 98~99% 단계에서 한 건당 값은 비용이 아니라 "Gateway가 받은 CPU 몫 ÷ 처리량"이라 상수에 가깝다. 같은 몫으로 성공을 더 냈으므로 성공 한 건당 Gateway CPU는 1.10 → 0.99ms(−10%, 계산값)다. 거절이 싸져 남은 CPU를 상한이 받은 요청에 다시 썼다고 읽는다(추정). 동시 수 상한은 남는 CPU를 다시 채우는 작업 보존형이라, 거절을 공짜로 만들어도 과부하의 서버 CPU는 내려가지 않는다 |
| 다음 가설 | 받은 요청 한 건의 비용을 줄인다. 5차에서 미뤘던 요청 로그(C1)를 끄고 잰다(단계 8). 거절 한 건의 비용은 포화 전 단계에서 따로 잰다(R0, 계획) |

요청이 Gateway 안에서 지나는 순서(Spring Boot 4.1.2, spring-web 7.0.10 소스로 확인):

| 순서 | 층 | 하는 일 | 거절 위치 |
|---|---|---|---|
| 0 | Netty | HTTP 바이트를 요청으로 해석 | |
| 1 | HttpHandler 데코레이터 | 카운터 하나 | **H1(7차)** |
| 2 | `HttpWebHandlerAdapter` | 요청 객체(exchange) 생성, 서버 관측·추적 스팬·http 지표 시작 | |
| 3 | WebFilter `RequestLogWebFilter` | 요청 로그 한 줄 | A안이었다면 여기 앞 |
| 4 | 라우트 매칭 | 모든 라우트의 경로 조건 평가 | |
| 5 | GlobalFilter -200 | 동시 처리 수 상한 | 6차 |
| 6 | GlobalFilter -100 | 인증(JWT, Redis 조회) | |

- 발견: Boot 4에는 `ServerHttpObservationFilter`가 없다. 서버 관측은 2번 어댑터가 WebFilter 체인 전체를 감싸 연다. 그래서 상한을 맨 앞 WebFilter로 옮겨도 로그·라우트 매칭만 건너뛰고 관측은 남는다. `RequestLogWebFilter`의 주석 "트레이싱 관측 필터는 `@Order(0)`"도 Boot 4 기준으로 틀린 전제였다(5a75435c에서 고침). 강민 선택: "B로 진행하고 주석도 같이 고쳐"([일지](../../ai-judgments/kangmin/daily/2026-11-11.md)).
- 왜 관측이 의심되나: 0b JFR에서 관측 묶음이 약 24%로 가장 컸다. 측정 모드 샘플링이 0.01인데도 그렇다. 샘플링되지 않는 요청도 관측 처리 비용은 낸다는 뜻이다(추정). 다만 이 몫은 받은 요청과 거절된 요청을 합친 값이라, 거절만의 몫은 확인 못 함이다.
- 데코레이터의 대가: 거절된 요청은 traceId(본문 `traceId` null)·요청 로그·`http_server_requests` 503 집계에서 빠진다. 거절 수는 `gateway_in_flight_rejected_total`로 센다. 경보 규칙은 `http_server_requests`를 쓰지 않고, 프런트는 nginx 같은 출처라 CORS 영향이 없다(둘 다 확인). 관리 포트(9080)는 이 연결점을 쓰지 않아 액추에이터에 영향이 없다.
- "부담"이라는 말의 뜻: 처음 설계안에 데코레이터가 "부담스러우면"이라고 썼는데, 어렵다는 뜻이 아니라 위 대가와 "팀원에게 익숙한 필터 층보다 바깥이라 찾기 어렵다"는 뜻이었다([학습 노트](../../learning/kangmin/qna/2026-11-11-observation-cost-hypothesis-and-handler-decorator.md)).
- 관측을 통째로 줄이는 안(C1 요청 로그, C2 샘플링)은 장애 분석을 약하게 한다고 보고 보류했다. H1은 받은 요청의 관측을 그대로 두고 거절된 요청만 건너뛴다. [판단 기록(보류)](../../ai-judgments/kangmin/2026-11-11-defer-gateway-observability-reduction.md), [TS-59](../../troubleshooting.md).

- 7차 1,000/s에서 H1에만 상한 거절 242건이 나왔다(6차 L64·H2 0건). 처리 중 최대 표본은 5라 5초 표본 사이의 짧은 몰림으로 본다(추정, 원인 확인 못 함).
- 재해석은 [학습 노트](../../learning/kangmin/qna/2026-11-11-h1-reinterpret-netty-cost.md)에 있다. 6차 거절 한 건은 받은 요청의 약 5분의 1(약 0.15~0.21ms, 계산값)로 보이며, 6차의 "거절도 처리 비용의 대부분을 낸다"는 추정은 같은 지표 한계 때문에 과장이었다.

### 단계 8. 요청 로그를 끄자 서버 CPU가 처음 90% 아래로 (11/11, 배포 7차 H2, 측정 kangmin)
| 칸 | 내용 |
|---|---|
| 현 상황 | H1 뒤에도 1,500/s 서버 CPU 93%. 5차 JFR에서 로그는 Gateway Java CPU의 5.2%였다 |
| 목표 | 받은 요청 한 건의 비용을 줄여 평상 부하(1,500/s)에서 서버 CPU 90% 미만 |
| 가설 | 요청 로그는 요청마다 표준 출력 한 줄을 만든다. 이것을 끄면 요청마다 드는 비용이 빠진다 |
| 실험 | H1 위에 `iseonjwa.request-log.enabled=false`(측정 덮어쓰기)만 더함. 켠 뒤 100/s 웜업 동안 Gateway 로그 0줄로 꺼진 것을 확인 |
| 결과 | 서버 CPU 1,000/s 78 → 66%, 1,500/s 93 → **85%**. 2,500/s 굿풋 1,814 → **2,122**(6차 L64 대비 +32%), p95 60ms. 상한 거절 2,500/s 18,724 → 11,627건, auth-redis `bulkhead_full` 247 → 402건 |
| 성공·실패 이유 | Gateway CPU는 거의 같았다(1,000/s 114 → 111%). 줄어든 곳은 로그 수집기 `alloy`(22 → 14%)와 컨테이너 밖 호스트 쪽(약 35%p)이다. 비용은 Gateway JVM 안이 아니라 로그 경로(표준 출력 → Docker 로그 → Alloy → Loki)에 있었다. 호스트 쪽은 Docker 데몬으로 보지만 프로세스별로 재지 않아 확인 못 함이다. JFR의 5.2%는 JVM 안만 보므로 이 비용을 보지 못했다 |
| 다음 가설 | 운영에서 요청 로그를 줄이는 방식을 정한다(B: 실패·느린 요청만 남김을 골랐다). 그 위에서 상한 64·96·128을 회차마다 2번 이상 잰다(11/13) |

- `bulkhead_full`이 늘어난 것은 상한을 통과한 요청이 늘어 Redis 조회 동시 수가 벌크헤드 50에 더 자주 닿았기 때문으로 본다(추정).
- 4차 G1의 "성공 처리량 2,300~2,470/s"와 7차 "굿풋 2,122"는 정의가 다르다. 4차는 상한 없이 늦게라도 성공한 수(2,500/s p95 428ms)이고, 굿풋은 200ms 안 성공만 센다. 같은 줄에 놓지 않는다.
- 운영 반영: 강민은 A(운영도 끔)·C(표본)·D(측정 때만 끔) 대신 B(실패·느린 요청만 남김)를 골랐다. 실패 범위·느린 기준·적용 범위(Gateway만 또는 공통 필터)는 설계 확인 전이다. ADR 0045의 "요청마다 한 줄"과 요청 로그 대시보드에 영향이 있다. [판단 기록(수용)](../../ai-judgments/kangmin/2026-11-11-request-log-failures-and-slow-only.md).

### 단계 9. 요청 로그를 운영에 반영하고 같은 날 끔과 비교 + R0 (11/12, 배포 8차, 측정 kangmin)
| 칸 | 내용 |
|---|---|
| 현 상황 | 7차 H2(끔)는 측정 덮어쓰기였다. 운영 반영 B안(`problems`: 5xx·끊긴 요청·200ms 이상만 남김)을 #501로 넣고 #503으로 배포했다(`eda80051`). H1이 거절을 얼마나 싸게 만들었는지는 포화 단계 지표로 못 가렸다. 6·7차 스레드별 자료는 수집기 오류로 비어 있었다 |
| 목표 | (1) 운영 설정 `problems`가 끔과 같은 효과를 내는지 같은 날 같은 배포에서 가린다. (2) 거절 한 건의 CPU를 직접 잰다(R0) |
| 가설 | (1) problems의 서버 CPU는 끔과 ±2%p 안이다. 정상 요청(200·빠름)은 로그를 남기지 않기 때문이다. 4%p 넘게 높으면 ADR 0052 "바꿀 조건"으로 간다. (2) H1 뒤 거절 한 건은 받은 요청의 10분의 1 이하다 |
| 실험 | R0: 포화 전 부하(500·1,000/s 두 번씩)에서 상한 1(거절이 많음)과 1,000(전부 받음)을 쟀다. Gateway CPU = b + a × 받은 요청 + r × 거절을 14개 단계로 풀었다. P 대 O: 7차와 같은 G1 부하에서 problems(P, 덮어쓰기 없음)와 끔(O)을 P1 → O1 → P2 → O2로 번갈아 두 번씩. 수집기는 Gateway Java PID를 잡게 고쳐 저장소에 넣었다(#502) |
| 결과 | R0: a 1.063ms, r 0.021ms(pidstat)·0.080ms(docker stats), **r/a 0.020~0.075**. P 대 O(두 회차 평균): 1,000/s 59.6 대 56.7%(**+2.9%p**), 1,500/s 78.5 대 79.1%(−0.5%p), 2,000·2,500/s ±0.6%p. 굿풋·p95 같음(2,500/s 2,237~2,275, 50~54ms). 같은 설정 두 회차 차이 0.0~1.3%p. 새 수집기는 6회차 모두 Java·`reactor-http` 4개·`lettuce-epoll` 1개를 잡았다 |
| 성공·실패 이유 | (2) 성공: H1이 거절 경로에서 관측·요청 로그·라우트 매칭을 건너뛰어, 거절에 남은 것은 Netty 해석과 응답 쓰기 정도다(1-1절 순서 0·1). (1) 1,500/s 이상은 성공, 1,000/s는 판정 보류 칸(2~4%p)이다. 다만 2.9%p는 30초 평균 하나의 표본 표준오차(약 2.5%p)와 같은 크기라 실제 차이인지 가리지 못했다. 4%p 미만이라 바꿀 조건에는 닿지 않는다 |
| 다음 가설 | 받은 요청 한 건(약 1.06ms)을 더 줄이거나 장비를 나눠야 과부하 CPU가 움직인다. 거절을 Netty 단계로 더 앞당기는 안은 이득 상한이 약 0.02코어(서버의 0.5%, 계산값)라 하지 않는다 |

- 같은 설정 끔(O)이 7차 H2보다 6~9%p 낮았다(1,000/s 56.7 대 66%, 1,500/s 79.1 대 85%). 같은 값이라도 날·배포가 다르면 이만큼 달라진다. 그래서 8차는 7차와 수치를 직접 비교하지 않고, 같은 날 O를 대조군으로 판정했다. 요청 로그를 전부 남기는 회차(A)는 측정을 앞당기려고 뺐고(강민 결정), 7차 H1을 대조군으로 두되 수치 비교는 하지 않는다.
- R0 대기자는 1명(`USERS=1`)이었다. 상한 1에서는 setup의 대기자 진입(200건씩 동시)이 상한에 걸리기 때문이다. 짝인 상한 1,000 회차도 1명으로 맞췄다.
- 1,000/s 거절 비율은 46%로 계획 기준 50%에 조금 못 미쳤지만 r 오차 ±0.02ms로 판정에 충분했다.
- 측정 중 12:26에 "측정 모드가 꺼져 있다"는 문의가 있어 읽기 명령으로 확인했다. 켜져 있었고 배포 커밋도 그대로였다. 회차마다 측정 모드를 다시 적용할 때의 "설정 변경" 알림을 꺼짐으로 본 것으로 추정한다(확인 못 함).
- 측정 모드 켜기·끄기와 키 옮기기는 이번만 에이전트가 대신했다(강민 선택, `loadgen.md` 8절 예외).

| L128b | 상한 128(웜업 맞춤) | 더 느슨하면 | 1,721 | 162ms | 93% | 0 | `bulkhead_full` 섞임 |
| H1 | 거절 위치를 데코레이터로 | 거절 비용 | 1,781 | 73ms | 93% | 0 | 7차. 0a가 아니라 6차 L64와 같은 부하로 비교 |
| H2 | H1 + 요청 로그 끔 | 로그 비용 | 1,871 | 57ms | **85%** | 0 | 7차. 1,500/s에서 처음 90% 아래 |
| g8-P | 요청 로그 `problems`(운영 기본) | ADR 0052 운영 반영 확인 | 1,950·1,937 | 43·44ms | 78.5% | 0 | 8차, 2회 평균. 날이 달라 위 행들과 직접 비교하지 않는다 |
| g8-O | 요청 로그 끔 | 같은 날 대조군 | 1,954·1,937 | 43·44ms | 79.1% | 0 | 8차, 2회 평균. 7차 H2와 같은 값인데 6~9%p 낮음 |
| R0 | 상한 1 대 1,000(500·1,000/s) | 거절 한 건 비용 직접 측정 | — | — | — | 0 | 8차. r/a 0.020~0.075 |

## 7. 발표용
| 장면 | 보여 줄 숫자 | 무엇을 증명하나 |
|---|---|---|
| 1. Redis는 멀쩡한데 인증 전체 503 | Redis 0.1~0.8ms, 503 19,573건, 원인 `bulkhead_full` 10~17건 | 증상의 출처를 지표로 갈라야 원인이 보인다 |
| 2. 실패의 뜻을 바꿈 | 3,000/s까지 닫힘, `ignored` 16,024 / `failed` 0 | 기준값보다 "무엇을 세나"가 먼저다 |
| 3. 차단기 예민화 실패 | 20ms 기준 비율 최대 24%, 차단기 구간 십수 ms 대 사용자 p95 878ms | 실패한 가설도 측정으로 닫았고, 그 이유가 다음 장치의 위치를 정했다 |
| 4. 메모리만 늘린 결과 | OOM 3 → 0, p95 435 → 752ms | 자원을 늘리는 것은 실패의 모양만 바꾼다 |
| 5. 동시 수 상한 | 2,000/s 굿풋 1,469 → 1,696, p95 435 → 87ms, 대조군 500은 571ms | 리틀의 법칙으로 고른 값이 측정에서 맞았다 |
| 6. 거절에도 비용 | 거절 25~40%에도 0.66~0.71ms, 관측은 어댑터에서 시작 | 숫자의 이상함을 소스로 따라가 구조를 찾았다 |
| 7. 데코레이터 | 서버 CPU ±1%p, 2,500/s 굿풋 1,608 → 1,814, 성공 한 건당 1.10 → 0.99ms | 미리 정한 판정 지표가 포화 단계에서는 가설을 가리지 못한다는 것도 측정으로 알았다 |
| 8. 요청 로그 | 1,500/s 서버 CPU 93 → 85%, 2,500/s 굿풋 2,122(+32%), Gateway CPU는 같음 | 비용은 코드 밖(로그 경로)에 있었다. 프로세스 안 프로파일러만 믿지 않고 컨테이너·호스트까지 나눠 봐야 보인다 |
| 9. 운영 반영과 R0 | problems 대 끔 1,500/s 78.5 대 79.1%, 거절 한 건 0.02~0.08ms 대 받은 요청 1.06ms | 측정 덮어쓰기의 효과를 운영 설정으로 옮겨 같은 날 대조군으로 확인했고, 포화 단계에서 못 가린 비용을 비포화 실험으로 직접 풀었다 |

예상 질문과 답:

| 질문 | 답의 요지 |
|---|---|
| 차단기를 끄면 되지 않나 | fail-closed(ADR 0005)라 Redis가 정말 멈추면 모든 요청이 시한만큼 기다린다. 끄지 않고 Redis 탓인 실패만 세게 했다 |
| 왜 AI 추천을 거부하고 차단기부터 했나 | 차단기 시간에 Gateway 대기가 섞인다는 측정 근거가 있어 가능성이 있었다. 한 회차로 닫았고, 결론은 같아도 근거가 숫자가 됐다 |
| 왜 64인가, 128이 굿풋이 더 높지 않나 | 2,000/s 차이 1.5%는 같은 값 두 번 측정 차이 5%보다 작다. p95는 64가 절반이다. 11/13 재측정에서 회차당 2번 이상 재서 다시 판단한다 |
| 상한을 낮추면 CPU가 내려가지 않나 | 6차에서 32도 99%였다. 동시 수 상한은 남는 CPU를 받은 요청으로 다시 채우는 작업 보존형이라 과부하에서 CPU는 내려가지 않는다. CPU를 내리려면 받는 양을 묶거나 받은 요청 한 건 비용을 줄여야 하고, 7차 H2가 후자다 |
| 요청 로그를 끄면 장애 분석은 | 운영은 끄지 않고 실패·느린 요청만 남긴다(`problems`, ADR 0052). 정상 요청 흐름은 추적(traceId)·지표로 본다. 8차에서 이 설정이 끔과 2%p 안팎이었다 |
| 거절을 더 앞(Netty)에서 하면 | R0에서 거절 한 건이 받은 요청의 2~8%였다. 2,500/s 거절 약 250/s를 다 없애도 약 0.02코어(서버의 0.5%, 계산값)라 하지 않는다 |
| 폴링 간격을 늘리면 요청이 줄지 않나 | 계산상 30초면 약 −63%지만, 순번 갱신 간격은 사용자 경험의 핵심이라 거부했다. 서버 부하를 사용자에게 넘기는 것이다 |
| 거절된 요청의 추적이 사라지면 장애 분석은 | 거절 수는 `gateway_in_flight_rejected_total`로 남고, 받은 요청의 관측은 그대로다. 잃는 것은 거절된 요청 각각의 traceId·요청 로그다. 7차에서 서버 CPU 차이는 없었지만 굿풋·p95가 나아졌고, 지금 운영에 들어가 있다 |
| 처리량 3,000/s는 왜 못 내나 | 4 vCPU 한 대에 21개 컨테이너다. 상한은 처리량을 올리지 않고 모양만 바꾼다. 남은 길은 한 건당 CPU 줄이기와 장비 분리(ADR 0047)다 |
| 측정을 믿을 수 있나 | 발생기 한계를 무효 규칙으로 걸렀고, 회차마다 1회라 반복 변동(5%)을 함께 적었다. 0a 대 0b로 프로파일러 부담도 쟀다 |

## 8. 아직 확인 못 한 것
- (8차에서 해소) 거절 한 건만의 CPU 비용: R0에서 0.02~0.08ms, 받은 요청의 2~8%였다.
- (8차에서 해소) 관측 비용 가설: H1 뒤 거절이 관측·요청 로그·라우트 매칭을 건너뛰자 거의 공짜가 됐다. 6차 거절 비용(받은 요청의 약 5분의 1)은 직접 잰 값이 아니라 7차 노트의 계산값이라, 6차 대 8차는 계산값 대 측정값의 비교다.
- (8차에서 고침) 6·7차 `pidstat.log`가 `docker-init`만 잡은 문제. 8차부터 Java 스레드별 자료가 있다.
- H2에서 줄어든 서버 CPU 중 약 35%p가 컨테이너 밖 호스트 쪽이다. Docker 데몬으로 보지만 호스트 프로세스별로 재지 않았다(수집기 `HOST_PIDSTAT=1`로 잴 수 있지만 8차에서 쓰지 않음).
- 8차 1,000/s의 problems 대 끔 +2.9%p가 실제 차이인지. 30초 평균 하나의 표본 표준오차와 같은 크기다.
- 8차 끔(O)이 7차 H2보다 6~9%p 낮은 이유.
- R0를 대기자 1명으로 잰 것이 받은 요청 비용 a에 주는 영향(10,000명과의 차이).
- 7차 상한 거절 수가 Prometheus 30초 증가량과 k6 수에서 약 40% 다르다(H1 1,500/s 622 대 1,054건).
- H1 1,000/s 상한 거절 242건의 원인.
- Gateway 안에서 센 처리 중 수와 k6에서 본 L의 차이. k6 쪽 L에는 Gateway 앞 커널 대기열 시간이 들어 있다.
- 1,000/s p95가 5차(15ms)보다 6차(23~32ms)에서 높은 이유. 배포·회차 상태가 섞였다.
- OOM 때 JVM 지표 밖 메모리 약 130MB의 정체(Netty 풀 직접 메모리, GC 자료 구조, 스레드 스택 후보).
- alloy(로그 수집)가 부하와 상관없이 22~27%, Kafka가 쉬는 구간에도 최대 140%를 쓴 이유.
- 측정 샘플링 0.01과 운영·시연 1.0의 처리량 차이(C2). 운영에서는 스팬 전송 비용이 더해져 H1 효과가 측정보다 클 수 있다(H3, 이번에는 재지 않음).
- 실제 사용자는 503 뒤 `Retry-After`만큼 기다려 다시 보내지만 k6는 다시 보내지 않는다. 측정은 실제 오픈보다 낙관적일 수 있다(추정).
- 모든 회차가 1회 측정이다(3차 G 2,000/s만 4회). 7차 H1의 2,000/s 굿풋 +5%는 반복 변동(5%) 안이다.

## 9. 7차 판정 (기준은 측정 전에 적었고, 결과는 측정 뒤 채웠다)
| 가설 | 바꾼 값 하나 | 판정 기준 | 결과 |
|---|---|---|---|
| H1 거절 앞당기기 | 상한 거절을 HttpHandler 데코레이터로(상한 64, 6차 L64와 같은 웜업·부하) | 2,500/s 한 건당 Gateway CPU가 6차 0.71ms보다 낮고, 서버 CPU가 내려가며, 굿풋·p95가 L64보다 나쁘지 않다. 차이가 없으면 관측 비용 가설은 틀린 것이다 | 기준대로면 실패: 한 건당 0.71 → 0.72ms, 서버 CPU ±1%p. 굿풋 +13%·p95 104 → 78ms는 L64보다 낫다. 다만 포화 단계에서는 이 기준이 가설을 가리지 못한다(단계 7) |
| H2 요청 로그 끔 | H1 위에 `iseonjwa.request-log.enabled=false`(덮어쓰기) | H1 대비 한 건당 Gateway CPU·서버 CPU 차이. 0b JFR 로그 몫 5.2%와 비교 | Gateway CPU는 같고 서버 CPU 1,000/s −12%p·1,500/s −8%p. JFR 5.2%보다 훨씬 큰 감소가 JVM 밖에서 나왔다(단계 8) |
| 상한 64·96·128 | 값마다 2회 이상 | 2,000/s 이상 굿풋 차이가 반복 변동보다 크고 p95 200ms 안이면 더 큰 값으로 바꾼다 | 7차에서 재지 않음. 8차(11/12로 앞당긴 재측정)에서도 측정을 앞당기려고 뺐다(강민 결정). 남은 일 |

- 비교 주의: 6차 `http_server_requests` 수에는 거절이 들어 있고 7차에는 빠진다. 요청 수 비교는 k6 원자료와 `gateway_in_flight_rejected_total`로 한다.
- 6차 Prometheus 쿼리 식은 원자료에 없다(파일 이름만 있다). 7차는 17종 이름을 6차와 같게 두고 식을 새로 썼다.
