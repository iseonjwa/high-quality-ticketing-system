# 오픈 피크 흐름의 트래픽 집중 구간과 단계별 개선 계획 (ISE-181)

상태: 설계. 코드 조사와 계산으로 세운 가설이며 측정 전이다 (2026-11-05 작성, ISE-181 담당 최권우 요청으로 Claude Code가 작성). 좌석 조회·선점의 실측은 [k6-seathold-bottleneck-plan.md](../reservation/k6-seathold-bottleneck-plan.md)에 있다.

예매 흐름 전체(오픈 전 조회 → 대기열 → 입장 → 좌석 조회 → 선점 → 결제 → 확정 → 만료, 그리고 추첨)를 따라가며 트래픽이 몰리는 구간을 찾는다. 구간마다 측정 시나리오, 단계별 개선 방안, 적용 방법, 트레이드오프, 예상 결과를 적는다. 공통 측정 기반은 [load-test.md](load-test.md)와 ADR 0046을 따른다.

- 근거: SA 2-3(핵심 흐름), 3장(검증 기준), 3-1(측정 방식), 3-3(입장 속도 역산), 8-1(시퀀스), 9-4(숫자 기준), 9-5(Redis 정책). 현재 코드와 `config-repo` 값은 2026-11-05 기준이다(커밋 `aeb39ba` 이후 작업 트리).
- 숫자는 따로 적지 않은 한 `[가정]`이다. "예상 결과"는 계산과 local 실측에서 나온 가설이며, 측정으로 확인하고 고친다.
- 다른 담당의 영역도 측정 담당이 개선 방안과 시나리오 초안을 쓴다. 확정은 그 담당이 검토한 뒤 하고, 코드 변경은 측정 결과와 함께 contract 이슈로 제안한다(AGENTS.md 대전제 11). 담당은 7절 표에 있다.
- 시나리오별 상세 명세(준비, 부하 모양, 지표, 판정 기준)는 [open-peak-scenarios.md](open-peak-scenarios.md)에 있다.

## 0. 한눈에 보기

### 0-1. 오픈 피크의 트래픽 모양

가정: 회차 1개, 15,000석, 오픈 시각에 30,000명이 대기열에 들어온다. 초당 입장 수 N은 현재 설정값 50이다.

| Z3 대기열 진입 | 오픈 직후 약 10초 | 약 3,000 | 30,000명 ÷ 10초 |

| Z5 입장·토큰 발급 | 오픈 뒤 10분 | 50 | N = 50 |

| Z9 결제 결과 반영 | 승인 직후 | 최대 약 50 이벤트 | 승인 1건당 이벤트 1건 |

## 1. 측정 방법

### 1-1. 두 층으로 잰다

1. **구간별 단독 시나리오**: 한 구간에만 부하를 걸어 그 구간의 한계와 개선 효과를 잰다. 한 번에 변경 하나만 넣고 같은 조건에서 앞 단계와 비교한다. K1-H(선점만)가 이 방식의 예다.
2. **오픈 피크 한 흐름(O1)**: 모든 구간을 실제 순서대로 잇는다. 구간별 개선을 합친 뒤 서비스 전체가 버티는지 판정한다. ISE-181 완료 기준의 "오픈 피크 시나리오"다.

단독 시나리오가 필요한 이유: 한 흐름에서는 앞 구간이 막히면 뒤 구간까지 요청이 가지 않는다. 좌석 조회가 막힌 K1에서 선점 개선이 "0건 → 0건"으로 보였던 것과 같다([k6-seathold-bottleneck-plan.md](../reservation/k6-seathold-bottleneck-plan.md) 5-3절).

### 1-2. 모든 구간에 같이 적는 값

- 고정 부하 결과: p95·p99, 성공·정상 거절(409 등)·오류(5xx·타임아웃) 건수.
- **오류 없이 버틴 최대 속도**: 속도를 두 배씩 올려 60초씩 재고, 오류율 1% 미만인 가장 높은 속도를 적는다. 고정 부하에서 모두 실패하는 동안에도 단계 차이가 보인다.
- **부하 뒤 회복 시간**: 부하가 끝난 뒤 처리 중 요청 수와 커넥션 대기가 0이 되는 시간([k6-overload-recovery.md](../reservation/k6-overload-recovery.md)).
- 측정 환경 기록표([load-test.md](load-test.md) 7절).

### 1-3. 측정 전에 맞출 공통 조건 (공통 기반, ISE-181 범위)

| 항목 | 지금 | 맞출 값 | 이유 |
|---|---|---|---|
| 추적 샘플링 | 배포는 `prod` 프로필에 `TRACING_SAMPLE_RATE` 1.0 | 측정 때 0.01 | 100% 추적은 요청마다 구간을 만들어 Zipkin으로 보낸다. 폴링 초당 수천 건이면 측정 대상 자체가 바뀐다 |
| `loadtest` 프로필 | 샘플링 0.01만 있고, 배포에서는 mock-pg만 이 프로필로 뜬다 | 측정용 덮어쓰기 compose로 앱에도 적용 | 위와 같다 |
| 요청 로그 | Gateway와 서비스가 요청마다 한 줄씩 남긴다 | 측정마다 켬·끔을 기록표에 적는다. 기본은 켠 채로 잰다 | 운영에서도 켜져 있으므로 비용도 측정 대상이다. 꺼서 차이를 한 번 잰다 |
| Mock PG 지연 | 기본 0ms(즉시 응답) | 장애 주입 API로 `DELAY` 300ms(추첨 문서의 가정값) | 0ms면 결제 한도가 실제보다 10배 넘게 높게 나온다 |
| 대기열 지표 | 대기 인원·입장 수·토큰 발급 수 지표가 없다 | Redis 키를 측정 중 주기적으로 읽어 기록한다. 지표 추가는 대기열 담당에게 제안 | 대기열 길이는 SA 3장 관측성 항목이다 |
| 발생기 | 노트북(local) | 같은 VPC 임시 EC2 | ADR 0046. local에서는 Gateway Redis 차단기 503처럼 환경 잡음이 섞였다. local의 k6 컨테이너는 약 32초마다 3초씩 멈췄다(2026-11-05 확인, [loadtest/k6/README.md](../../../loadtest/k6/README.md) 4절) |
| 결과 보관 | 파일(요약 JSON, 원자료 CSV) | Prometheus remote write | ADR 0046. 수신 설정은 아직 없다 |

## 2. 구간별 계획

각 구간은 같은 틀로 적는다: 왜 몰리나, 지금 구현, 측정 시나리오, 단계별 개선(적용 방법·트레이드오프·예상 결과), 담당.

### C1. reservation-service 공통 자원 (모든 구간에 걸침)

**왜 문제인가**: 대기열(Z3~Z5), 공연 조회(Z2), 좌석 조회(Z6), 선점(Z7), 결제 결과 반영(Z9), 만료(Z10), 추첨(Z11)이 모두 reservation-service 한 프로세스에서 돈다. 다음 자원을 모두 나눠 쓴다.

| 자원 | 값 | 근거 |
|---|---|---|
| DB 커넥션 | 5개 | `config-repo/reservation-service.yml` `maximum-pool-size` |
| Tomcat 요청 스레드 | 200개(기본값) | 설정 없음 |
| `@Scheduled` 스레드 | 1개(Spring 기본값) | 스케줄러 풀 설정 없음. 입장·회차 캐시 갱신·만료·추첨 4종이 한 스레드를 나눠 쓴다 |
| 힙 | 768MB(배포), 자동으로 Serial GC | `compose.deploy.yml`, [k6-seathold-bottleneck-plan.md](../reservation/k6-seathold-bottleneck-plan.md) 5-2절 |

한 구간이 무너지면 나머지도 같이 무너진다. 예를 들어 좌석 조회가 스레드 200개를 다 쓰면 대기열 폴링도 스레드를 받지 못한다. 실측에서 좌석 조회 하나가 스레드 200개를 모두 묶었다([k6-overload-recovery.md](../reservation/k6-overload-recovery.md) 3-1절).

| 단계 | 적용 방법 | 트레이드오프 | 예상 결과 |
|---|---|---|---|
| C1-0 기준선 | 변경 없음. O1에서 구간별 지연을 같이 본다 | - | 좌석 조회가 무너질 때 폴링·진입 p95도 같이 오른다 |
| C1-1 빨리 거절 | 커넥션 대기 30초 → 1초, Tomcat 스레드·연결 상한 축소(B8 R1~R3) | 순간 몰림에도 바로 실패한다 | 과부하가 지나면 30초 안에 회복한다. 2026-11-05 local 측정: R1(커넥션 대기 1초)만으로 회복했고 R2·R3 시작값은 R1보다 나빴다. R1만 ISE-196으로 제안했고 R3는 P4 뒤 배포 환경에서 다시 잰다([k6-overload-recovery.md](../reservation/k6-overload-recovery.md) 7절) |
| C1-2 스케줄러 분리 | `spring.task.scheduling.pool.size`를 4로 늘리거나 입장 스케줄러만 전용 스레드로 둔다 | 스레드가 늘면 만료·추첨이 DB 커넥션을 더 동시에 쓴다 | 추첨 실행(최대 약 4.5초 실측)이 입장을 멈추지 않는다 |
| C1-3 경로별 격벽 | 좌석 조회처럼 무거운 경로에 동시 처리 상한(세마포어나 Resilience4j Bulkhead)을 둬, 넘치면 503을 준다 | 상한 값을 경로마다 정하고 관리해야 한다 | 좌석 조회가 막혀도 대기열·선점은 계속 응답한다 |
| C1-4 인스턴스 분리 | reservation-service를 2대로 늘리거나 대기열을 별도 서비스로 뺀다(SA 7-1) | 메모리 예산(SA 9-3), 서비스 경계 결정이 필요하다 | 대기열 폭주와 선점 처리가 서로 영향을 주지 않는다 |

담당: 설정은 공유 설정이라 contract 이슈. 경계 변경은 팀 결정(ADR).

### C2. Gateway 공통 경로 (모든 인증 요청)

**지금 구현**: 인증이 필요한 요청마다 다음 순서로 처리한다.
1. JWT를 로컬에서 검증한다.
2. Redis `EXISTS auth:blacklist:{jti}`를 한 번 부른다. 타임아웃 100ms이고, `auth-redis` 차단기로 감싼다.
3. 좌석 조회·선점이면 입장 토큰을 로컬에서 검증한다.
4. 요청 로그를 한 줄 남긴다.

차단기는 최근 20회 중 50% 이상이 50ms를 넘으면 10초 열린다. 그동안 인증이 필요한 요청은 모두 503이다(fail closed, ADR 0005). 요청 제한(rate limiter)은 없다.

**측정 시나리오 G1**: 인증만 거치는 가벼운 API(예: 순번 폴링)에 초당 1,000 → 2,000 → 4,000 → 8,000건을 건다. Gateway CPU, Redis 명령 지연, 차단기 상태를 본다.

| 단계 | 적용 방법 | 트레이드오프 | 예상 결과 |
|---|---|---|---|
| G-0 기준선 | 변경 없음 | - | local에서는 K1-H 중에도 차단기가 네 번 열렸다([k6-seathold-bottleneck-plan.md](../reservation/k6-seathold-bottleneck-plan.md) 5-4절). EC2에서는 Redis가 50ms를 넘는지부터 확인한다 |
| G-1 관측 | Redis 지연 p95, 차단기 상태·열림 횟수를 대시보드에 둔다(SA 9-5 지표) | 없음 | 503의 출처를 서버 오류와 나눠 셀 수 있다 |
| G-2 블랙리스트 확인 줄이기 | 로그아웃된 `jti`를 Gateway 메모리에 짧게 캐시한다. 예: 블룸 필터를 주기적으로 갱신하고, 걸릴 때만 Redis를 부른다 | 로그아웃이 반영되기까지 최대 갱신 주기만큼 늦다. 보안 결정(ADR 0005)과 같이 봐야 한다 | 인증 요청당 Redis 호출이 거의 0으로 준다. 차단기가 열릴 일이 줄어든다 |
| G-3 요청 제한 | 사용자별·경로별 요청 제한(Spring Cloud Gateway `RequestRateLimiter`)을 둔다. 폴링을 서버가 준 간격보다 자주 보내면 429를 준다 | Redis 기반이면 Redis 호출이 하나 늘어난다. 로컬 카운터면 인스턴스마다 따로 센다 | 폴링 간격을 지키지 않는 클라이언트가 전체 부하를 키우지 못한다 |

담당: Gateway는 공통 영역이다. G-2·G-3은 보안·인증 결정이라 팀 합의와 contract 이슈가 필요하다.

### Z2. 오픈 전 공연·회차 조회

**왜 몰리나**: 오픈 시각 전, 사용자들이 공연 상세 화면에서 카운트다운을 보며 새로고침한다. 서버 시각 전용 API가 없어 상세 응답의 `serverTime`으로 카운트다운을 맞춘다(`frontend/src/lib/serverClock.ts`).

**지금 구현**:
- `GET /api/v1/concerts`(공개 경로, 인증 없음): 읽기 전용 트랜잭션 안에서 쿼리를 3번 한다.
  - 페이지 조회
  - 공연 전체 `count()`(요청마다)
  - 다가오는 회차 IN 조회
- `GET /api/v1/concerts/{id}`: 공연 조회와 회차(공연장 join fetch) 조회.
- 캐시는 없다. 커넥션 5개를 좌석 조회·선점과 같이 쓴다.

**측정 시나리오 B1**: 오픈 10분 전부터 30,000명이 상세를 10~30초마다 새로고침한다. 초당 1,000 → 3,000건. 같은 시간에 Z3(대기열 진입)을 걸어, 조회 부하가 진입에 번지는지 본다.

| 단계 | 적용 방법 | 트레이드오프 | 예상 결과 |
|---|---|---|---|
| B-0 기준선 | 변경 없음 | - | 커넥션 5개가 한도다. 쿼리가 건당 수 ms라면 초당 수백 건에서 커넥션 대기가 생긴다. 좌석 조회처럼 스레드를 다 쓰면 대기열 진입까지 막힌다 |
| B-1 조회 다듬기 | 목록의 `count()`를 없애거나(Slice) 캐시한다. 상세는 쿼리 1번으로 줄인다 | 목록 화면이 전체 개수를 보여 주지 못한다(Slice) | 건당 DB 왕복이 3 → 1~2로 줄어 한도가 1.5~2배로 오른다 |
| B-2 응답 캐시 | 공연 정보를 로컬 캐시(Caffeine)에 TTL 5분으로 둔다(SA 9-4 "공연 정보 5분"). `serverTime`은 캐시하지 않고 응답할 때마다 붙인다 | 관리자가 공연 정보를 고치면 최대 5분 늦게 보인다. 인스턴스마다 캐시가 따로 있다 | 대부분 DB를 거치지 않아 한도가 수십 배로 오른다. 남는 비용은 JSON 직렬화와 Gateway다 |
| B-3 HTTP 캐시 | 공개 응답에 `Cache-Control: public, max-age=30`과 `ETag`를 붙인다. 앞단(nginx, CDN)에서 받는다 | 캐시 무효화를 시간으로만 한다. 앞단 구성이 필요하다 | 요청이 서비스까지 오지 않는다 |
| B-4 서버 시각 분리 | `serverTime`만 주는 가벼운 API를 두거나, 응답 헤더 `Date`를 쓴다 | 프론트와 API 계약이 바뀐다 | 카운트다운 새로고침이 상세 조회를 부르지 않는다 |

담당: 공연 조회는 반효승. 측정 결과로 contract 이슈를 올린다(ISE-189와 같은 방식).

### Z3. 대기열 진입

**지금 구현**: `POST /schedules/{id}/queue`.
1. 회차를 메모리 캐시(`CachedScheduleReader`, 30초마다 갱신)에서 찾는다.
2. Lua 한 번(`enter.lua`)으로 판매 시각 확인, 중복 진입 확인(`ZSCORE`), `INCR seq`, `ZADD waiting`을 한다.
3. 캐시에 맞으면 DB를 쓰지 않는다.

**위험**:
- 캐시에 없으면 요청마다 DB `findById`를 부른다. 캐시는 1시간 안에 열리는 판매 중 회차만 담는다. 오픈 직후 재시작하면 첫 갱신 전까지 비어 있다. 그러면 진입 요청 초당 3,000건이 커넥션 5개로 간다.
- `INCR seq` 키 하나에 모든 진입이 몰린다. Redis는 단일 스레드라 문제는 되지 않는다(명령 수십만/초).

**측정 시나리오 Q1**: 오픈 시각에 30,000명이 10초 안에 진입한다(초당 3,000건). 이어서 60,000 → 120,000명. 진입 p95, 중복 순번 0, Redis CPU를 본다. 변형으로 측정 도중 reservation-service를 재시작한다(캐시가 빈 상태).

| 단계 | 적용 방법 | 트레이드오프 | 예상 결과 |
|---|---|---|---|
| Q-0 기준선 | 변경 없음 | - | Redis는 여유 있다. 한도는 Gateway·서비스의 CPU와 스레드다 |
| Q-1 캐시 미스 보호 | 캐시 미스일 때 DB 조회를 한 건만 보내고 나머지는 기다리게 한다(single-flight). 기동 때 캐시를 먼저 채운 뒤 준비 완료(readiness)를 알린다 | 기동이 조금 늦어진다 | 재시작 직후에도 DB로 몰리지 않는다 |
| Q-2 진입 비용 줄이기 | 진입 응답에 다음 폴링 시각을 같이 주고, 진입 직후 폴링을 하지 않게 한다 | 프론트 계약 확인이 필요하다 | 진입 직후의 폴링 몰림이 준다 |

담당: 대기열은 권영은.

### Z4. 순번 폴링 (요청 수 1위)

**지금 구현**: `GET /schedules/{id}/queue/me`.
- DB를 쓰지 않는다. 읽기 전용 Lua(`position.lua`)로 `TIME`, `ZSCORE` 2번, `GET`을 한다.
- 순번은 `seq - admitted`로 계산한다.
- 다음 폴링 시각은 `clamp(대기 초, 3초, 10초) + 0~20% jitter`다. 대기자가 많으면 거의 모두 10~12초가 된다.

**부하 계산**: 대기자 30,000명 ÷ 평균 11초 = 초당 약 2,700건. 대기열이 비는 데 10분(30,000 ÷ 50)이 걸리므로 이 부하가 10분 동안 이어진다. 폴링 한 건마다 다음 일이 생긴다.
- Gateway: JWT 검증, Redis 1번, 요청 로그 1줄
- 서비스: Tomcat 스레드 1개, Redis 1번, 요청 로그 1줄, 추적 구간(배포 값 100%)

**측정 시나리오 Q2**: 대기자 30,000명을 만들고(진입만 미리 실행), 입장 속도를 0으로 둔 채 서버가 준 간격대로 폴링한다. 대기자를 60,000 → 120,000명으로 늘린다. Gateway·서비스 CPU, 폴링 p95, 차단기 상태, 로그 양(Loki 수집량)을 본다.

| 단계 | 적용 방법 | 트레이드오프 | 예상 결과 |
|---|---|---|---|
| Q2-0 기준선 | 변경 없음. 추적 샘플링 0.01 | - | 초당 2,700건은 Redis에는 가볍다. 먼저 Gateway CPU나 로그·추적 비용이 드러날 것이다 |
| Q2-1 부가 비용 확인 | 요청 로그를 끄고 한 번, 추적 1.0으로 한 번 더 잰다 | 측정만 바뀐다 | 로그·추적이 폴링 비용의 몇 %인지 숫자로 나온다. 크면 폴링 경로만 로그를 샘플링한다 |
| Q2-2 폴링 간격 조정 | `poll-max`를 10초 → 20~30초로 늘리고, 순번이 먼 사용자일수록 길게 한다 | 순번 갱신이 늦게 보인다. 입장 차례가 됐는데 폴링 간격만큼 늦게 알 수 있어, 그만큼 입장 토큰 유효 시간(10분)을 쓴다 | 폴링 부하가 간격에 반비례해 1/2~1/3로 준다 |
| Q2-3 READY 근처만 자주 | 대기 예상 시간이 폴링 간격보다 짧아진 사용자만 3초로 줄인다(지금 식은 이미 그렇다). 먼 사용자는 상한을 키운다 | 위와 같다 | 위와 같다 |
| Q2-4 밀어주기 | SSE나 WebSocket으로 순번을 밀어준다 | 연결을 계속 붙잡아 Gateway·서비스 연결 수가 대기자 수만큼 늘어난다. 구조가 크게 바뀐다 | 폴링이 사라지지만 연결 유지 비용으로 바뀐다. M4 범위에서는 비교 기록만 남긴다 |

담당: 대기열은 권영은. 폴링 간격은 SA 9-4 값이라 바꾸려면 SA 변경 요청이 필요하다.

### Z5. 입장 스케줄러와 입장 토큰 발급

**지금 구현**:
- 500ms마다 판매 중 회차를 돌며 `admit.lua`를 부른다. Redis 시각으로 같은 초에 두 번 실행하지 않으므로, 인스턴스가 여러 대여도 초당 한 번만 입장한다.
- 한 번에 `admitted`를 50 올린다. 지난 초를 따라잡지는 않는다.
- 만료된 입장 토큰 정리는 한 번에 최대 500건이다.
- 스케줄러 스레드 1개를 만료(Z10)·추첨(Z11)과 나눠 쓴다.
- 입장 토큰 발급(`issue-token.lua`)은 멱등이다. 같은 사용자는 같은 토큰을 받는다.

**위험**: 다른 작업이 스레드를 1초 넘게 쥐면 그 초의 입장이 사라진다. 추첨 실행은 한 트랜잭션에서 최대 약 4.5초가 걸렸다(ISE-87 실측). 그러면 그동안 약 200명분의 입장이 빠진다. 사용자에게는 대기열이 멈춘 것처럼 보인다.

**측정 시나리오 Q3**: Q2 상태에서 입장 속도 50으로 10분 동안 돌리고, 실제 입장 수가 초당 50인지 Redis `admitted` 값으로 1초마다 기록한다. 변형으로 같은 시간에 만료 대상 선점 5,000건이나 추첨 실행을 겹친다.

| 단계 | 적용 방법 | 트레이드오프 | 예상 결과 |
|---|---|---|---|
| Q3-0 기준선 | 변경 없음 | - | 단독이면 초당 50을 지킨다. 추첨·만료와 겹치면 빠지는 초가 생긴다 |
| Q3-1 스케줄러 분리 | C1-2 | C1-2와 같다 | 겹쳐도 초당 50을 지킨다 |
| Q3-2 따라잡기 | `admit.lua`가 지난 시각과의 차이(초)만큼 입장시킨다(상한 있음) | 밀린 만큼 한 번에 입장시켜 선점 쪽에 순간 몰림이 생긴다. 상한이 필요하다 | 실제 입장 속도가 설정값과 같아진다 |
| Q3-3 N 역산 | 선점·좌석 조회의 한도(μ)와 체류 시간(W)을 실측해 SA 3-3 식으로 N을 다시 정한다 | N을 낮추면 대기 시간이 길어진다 | 뒤쪽 구간이 버티는 속도로만 들여보내, 대기열이 뒤쪽을 보호하는 장치가 된다. 지금 실측(좌석 조회 한계 초당 10명)이면 N 50은 너무 크다 |

Q3-3이 이 문서에서 가장 중요한 연결이다. 대기열은 뒤쪽 구간이 감당할 만큼만 들여보내는 장치다. 따라서 N은 Z6~Z8 측정 결과에서 정해야 한다.

담당: 대기열은 권영은. N은 SA 9-4 값이라 팀이 정한다.

### Z7. 좌석 선점

자세한 내용은 같은 문서 3-1절과 1-5절(K1-H)에 있다. 2026-11-06 개정으로 K1-H 단계는 P0''+R1 → S4 → P1 → P3 → (P2) → (P5)이고, P2·P5는 조건부로 줄였으며 P6·P7은 범위 밖으로 뺐다. K1-H 기준선에서 선점 경로는 커넥션 5개로도 초당 100명을 버텼다. 첫 1분 이후 p95는 20ms 미만이었다(5-4절). 단계별 차이를 보려면 K1-H 속도를 초당 100 → 800명까지 올린다.

담당: 최권우.

### Z8. 결제 승인

**지금 구현**: `POST /api/v1/payments`.
1. 멱등 기록 조회, 결제 토큰 검증, 예매 조회.
2. **PG 허가 얻기**: Bulkhead 동시 10, 대기 0. 못 얻으면 즉시 503 `PG_UNAVAILABLE`.
3. TX1(결제 REQUESTED 저장).
4. 트랜잭션 밖에서 PG를 호출한다. 연결 0.5초, 응답 2초, 재시도는 없다.
5. TX2(승인 반영과 outbox 저장).
6. 커넥션 풀은 20개다.

**부하 계산**: 처리량 상한은 동시 수 ÷ PG 응답 시간이다.
- PG 300ms면 10 ÷ 0.3 = 초당 약 33건.
- 오픈 피크에서 선점 성공은 입장 속도(초당 50)에 가깝다. 사용자가 대부분 결제하면 초당 최대 약 50건이 온다. 그러면 약 3분의 1이 503을 받는다.
- 사용자가 다시 누르면 요청이 더 늘어난다.
- Mock PG는 기본 지연이 0이다. 지연을 주입하지 않으면 이 한도가 보이지 않는다(1-3절).

**측정 시나리오 P1(결제)**: 선점을 미리 만들어 두고(예매 HELD + 결제 토큰), 결제만 초당 20 → 40 → 80 → 160건으로 건다. Mock PG `DELAY` 300ms. Bulkhead 남은 자리, `payment_approve_seconds{outcome}`, 503 비율, PG 호출 지연을 본다. 변형으로 PG 지연을 1초, 2초(타임아웃 경계)로 늘린다.

| 단계 | 적용 방법 | 트레이드오프 | 예상 결과 |
|---|---|---|---|
| PAY-0 기준선 | 변경 없음, PG 300ms | - | 초당 약 33건에서 503이 생긴다 |
| PAY-1 동시 수를 근거로 정하기 | 리틀의 법칙으로 동시 수 = 목표 처리량 × PG 응답 시간이다. 초당 50건 × 0.3초 = 15, 여유 2배면 30이다. `pg.protection.approve.max-concurrent-calls`를 측정으로 정한다 | PG가 견디는 동시 수를 넘으면 PG가 느려진다. 실제 PG(토스)의 호출 제한을 확인해야 한다 | 초당 50건을 503 없이 처리한다. PG가 느려지면 다시 503으로 보호한다 |
| PAY-2 짧은 대기 | Bulkhead 대기 0 → 100~200ms | 대기 시간만큼 응답이 늦고 요청 스레드를 쥔다 | 순간 몰림에서 503이 줄어든다 |
| PAY-3 PG 지연 대응 | PG 지연이 1~2초로 늘 때 차단기 느린 호출 기준(현재 실패율만 본다)을 더한다 | 느린 PG를 일찍 끊어 결제가 실패한다 | PG가 느려져도 결제 서비스 스레드·커넥션이 묶이지 않는다 |
| PAY-4 자동결제와 분리 | 추첨 자동결제를 별도 Bulkhead로 나눈다(추첨 문서 D6 B) | 일반 결제와 자동결제 각각의 최대치가 줄어든다 | 추첨과 일반 판매가 겹쳐도 일반 결제 503이 늘지 않는다 |

담당: 안준현(결제). 값은 `config-repo/payment-service.yml`의 `[가정]` 값이고 "부하 측정 뒤 조정"으로 되어 있다.

### Z9. 결제 결과 반영 (outbox → Kafka → 예매 확정)

**지금 구현**:
- 결제 outbox 릴레이는 500ms마다 돈다. 한 번에 20건씩 최대 10묶음을 처리한다. 보낸 뒤에는 행마다 UPDATE를 한 번씩 한다.
- Kafka 토픽은 자동 생성이라 파티션이 1개다. 소비자는 동시 1개다.
- reservation-service 소비자는 이벤트 한 건마다 다음을 한 트랜잭션에서 한다.
  - 처리 이력 INSERT
  - 예매 조회와 조건부 확정
  - 예매 좌석 조회·UPDATE
  - 회차 좌석 SOLD UPDATE
  - 티켓 INSERT(IDENTITY라 좌석 수만큼 따로)
  - 이력 INSERT
- 목표는 결제에서 확정까지 2초 이내다(SA 9-4).

**부하 계산**: 이벤트 한 건이 DB 왕복 약 8~10번이다. 건당 10~20ms면 소비자 1개로 초당 50~100건이다. 오픈 피크 수요(최대 초당 약 50건)와 비슷하다. 더 느려지면 랙이 쌓여 확정이 늦어진다.

**측정 시나리오 R1**: 결제 승인 이벤트를 초당 25 → 50 → 100 → 200건으로 만든다. P1(결제) 부하를 그대로 쓰거나 outbox에 직접 넣는다. 승인 시각에서 확정 시각까지의 지연(대사 SQL), 소비자 랙, outbox 미발행 건수(`outbox.pending.oldest`)를 본다.

| 단계 | 적용 방법 | 트레이드오프 | 예상 결과 |
|---|---|---|---|
| R-0 기준선 | 변경 없음 | - | 초당 50건 근처까지는 2초 안에 확정된다. 넘으면 랙이 선형으로 쌓인다 |
| R-1 랙 지표 | Kafka 소비자 랙(`kafka_consumer_fetch_manager_records_lag` 등)과 확정 지연을 대시보드에 둔다 | 없음 | 병목이 릴레이인지 소비자인지 나눠 볼 수 있다 |
| R-2 파티션·동시 수 | `payment.result` 파티션 3개, 소비자 동시 3개. 키를 예매 ID로 두어 같은 예매의 순서를 지킨다 | 토픽을 직접 만들어야 한다(지금은 자동 생성). 파티션은 줄일 수 없다. 커넥션을 3개까지 더 쓴다 | 처리량이 약 3배가 된다. 이때는 커넥션 5개가 다음 한도다 |
| R-3 쓰기 줄이기 | 티켓 ID를 시퀀스로 바꿔 JDBC 배치 INSERT, 좌석 UPDATE를 한 문장으로 | 엔티티 ID 전략을 바꾼다 | 건당 왕복이 약 8~10번에서 5~6번으로 준다 |

담당: 소비자·확정은 반효승, 릴레이·토픽은 공통 모듈(안준현). 토픽 파티션은 공유 설정이라 contract 이슈다.

### Z10. 선점 만료 (오픈 5분 뒤의 두 번째 파도)

**왜 몰리나**: 오픈 직후 초당 약 50건씩 만들어진 선점 중 결제되지 않은 것이 5분 뒤 같은 속도로 만료된다. 결제 503(Z8)이 많을수록 만료도 많아진다.

**지금 구현**:
- 5초마다 만료 대상을 최대 100건 고른다. `SKIP LOCKED` 없는 SELECT다.
- 한 건씩 따로 트랜잭션으로 처리한다. 조건부 만료, 좌석 UPDATE 2번, 매수 UPDATE, 이력 INSERT.
- 스케줄러 스레드를 입장·추첨과 나눠 쓴다.

**부하 계산**: 최대 처리량은 100건 ÷ 5초 = 초당 20건이다. local에서 잰 실제 값은 초당 약 15.6건이었다. 주기가 처리 시간(약 1.4초)만큼 길어지기 때문이다([open-peak-scenarios.md](open-peak-scenarios.md) 3절). 미결제 비율이 40%를 넘으면(초당 50 × 0.4 = 20) 만료가 밀린다. 그러면 매진처럼 보이던 좌석이 늦게 다시 풀린다. 인스턴스가 두 대면 같은 행을 같이 집어 잠금 경합만 생긴다(S4 대상).

**측정 시나리오 X1**: 만료 시각이 같은 선점 5,000건을 미리 만들고, 만료가 끝나는 시간을 잰다. K1-H를 같이 걸어 선점 p95 변화를 본다(load-test-scenarios.md L5와 같다).

| 단계 | 적용 방법 | 트레이드오프 | 예상 결과 |
|---|---|---|---|
| X-0 기준선 | 변경 없음 | - | 5,000건에 약 250초(초당 20건) |
| X-1 묶음·주기 조정 | `seathold.expiry.batch-size`·`interval`을 늘린다 | 한 주기가 길어져 스케줄러 스레드를 오래 쥔다(C1-2와 같이) | 묶음 크기에 비례해 빨라진다 |
| X-2 S4 | 건별 트랜잭션 안에서 `FOR UPDATE SKIP LOCKED`로 집는다 | 잠금 순서를 결제 결과 소비자와 맞춰야 한다(contract) | 인스턴스 여러 대가 나눠 처리한다. 헛수고 0 |
| X-3 묶음 처리 | 만료 대상 좌석을 한 문장으로 되돌린다(집합 UPDATE) | 건별 이력·매수 반영을 같은 문장 묶음 안에 맞춰야 한다 | 왕복 수가 건수에 비례하지 않는다 |

담당: 최권우(좌석 선점).

### Z11. 추첨

수치는 [lottery/numbers-and-measurement.md](../lottery/numbers-and-measurement.md)를 따른다. 코드에서 확인한 사실을 더한다.

**응모 마감 직전(초당 100건)**:
- `POST /lotteries/{id}/entries`는 동기 처리다. 201을 돌려주며, 202 접수형이 아니다.
- 쿼리는 3번이고 커넥션 5개를 일반 예매와 같이 쓴다.
- 대기열·입장 토큰을 거치지 않는다.
- 요청 한 건이 가벼워 초당 100건 자체는 문제가 작을 것이다. 다른 회차의 일반 판매와 겹치면 C1의 공유 자원 문제가 된다.

**추첨 직후 배정·자동결제(2,000건)**:
- 배정 스케줄러는 1초마다 최대 100명을 처리한다. 당첨자마다 트랜잭션이 따로다.
  - 남은 추첨 좌석 전체를 다시 읽는다(당첨자 2,000명 × 좌석 3,000석).
  - 시스템 선점을 만든다.
  - `BillingPaymentRequested` outbox를 쓴다.
- 결제 쪽 소비자는 동시 1개이고 PG를 동기로 부른다. 그래서 일반 결제와 같은 Bulkhead 10개 중 실제로는 1개만 쓴다.
- 계산: PG 300ms면 초당 약 3.3건이다. 2,000건에 약 10분이 걸려 목표(10분 안에 95%)의 경계에 있다. 추첨 문서는 Bulkhead 10을 다 쓴다고 보고 약 1분으로 계산했는데, 지금 코드의 한도는 소비자 동시 수다.

**측정 시나리오 L1(응모)**·**L2(자동결제)**는 추첨 문서 2절의 시나리오 1·2와 같다. L2에서는 배정 시작부터 결제 완료까지의 시간과, 같은 시간대 일반 결제의 503 비율을 본다.

| 단계 | 적용 방법 | 트레이드오프 | 예상 결과 |
|---|---|---|---|
| LOT-0 기준선 | 변경 없음, PG 300ms | - | 자동결제 2,000건에 약 10분. 배정은 당첨자마다 좌석 3,000행을 읽어 더 느릴 수 있다 |
| LOT-1 배정 조회 줄이기 | 남은 좌석을 주기마다 한 번만 읽고 메모리에서 나눈다 | 동시에 도는 배정과 겹치지 않게 잠금 규칙이 필요하다 | 배정 시간이 당첨자 수에 비례하게 된다 |
| LOT-2 소비자 동시 수 | `payment.command` 파티션·소비자 동시 수를 3~5개로 늘린다 | 일반 결제와 Bulkhead를 더 나눠 쓴다. PAY-4와 같이 정한다 | 자동결제 시간이 동시 수에 반비례해 2~3분으로 준다 |
| LOT-3 전용 Bulkhead | PAY-4 | PAY-4와 같다 | 일반 결제 503 증가 없음 |

담당: 추첨은 이강민, 결제 소비자는 안준현.

## 3. 오픈 피크 한 흐름(O1)

구간별 개선을 합친 뒤 ISE-181 완료 기준으로 한 번 돌린다.

| 단계 | 사용자 행동 | k6 구성 |
|---|---|---|
| 1 | 오픈 10분 전부터 공연 상세를 10~30초마다 새로고침 | 공개 API, 열린 모델 |
| 2 | 오픈 시각에 대기열 진입(10초에 걸쳐 30,000명) | 같은 VU가 이어서 |
| 3 | 서버가 준 `nextPollAfterMillis`마다 순번 조회, READY면 입장 토큰 발급 | 간격은 응답 값을 따른다 |
| 4 | 좌석 조회 → 1~3초 고민 → 선점, 409면 재시도 2번 | K1과 같다 |
| 5 | 선점 성공이면 5~30초 뒤 결제. 일부(10% `[가정]`)는 결제하지 않고 떠난다 | Mock PG `DELAY` 300ms |
| 6 | 확정 확인(예매 조회)을 2초 간격으로 최대 5번 | 확정 지연 측정 |

판정: 중복 판매 0, 대사 불일치 0. 구간별 p95, 오류율, 대기 시간(진입 → 입장), 확정 지연, 부하 뒤 회복 시간을 적는다. 사용자 3만 명 토큰이 필요하다. 배포 환경의 측정용 서명 키는 측정 모드의 측정 전용 키로 정했다(load-test.md 5절).
