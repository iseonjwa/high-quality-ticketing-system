# 오픈 피크 부하 시나리오 명세 (ISE-181)

상태: 초안. 담당 검토 전 (2026-11-05 작성, ISE-181 담당 최권우 요청으로 Claude Code가 작성)

[open-peak-load-plan.md](open-peak-load-plan.md)에서 찾은 트래픽 집중 구간마다, k6 스크립트로 바로 옮길 수 있는 수준으로 시나리오를 적는다. 다른 담당의 영역도 측정 담당(최권우)이 먼저 초안을 쓴다. 각 시나리오의 "검토" 칸에 적힌 담당이 확인하고 고친다. 고친 내용은 이 문서에 PR로 반영한다.

- 숫자는 모두 `[가정]`이다. 판정 기준도 측정 전에 정한 초안이며, 담당 검토에서 바꿀 수 있다. 측정 결과를 본 뒤에는 바꾸지 않는다.
- 요청·응답 필드 이름은 2026-11-05 코드에서 확인했다. 스크립트를 만들 때 다시 확인한다.
- 개선 단계(각 시나리오의 "비교할 단계")의 이름은 계획 문서 2절 표를 따른다.

## 1. 공통 사항

### 1-1. 환경

- 기본은 배포 환경(EC2 한 대)과 같은 VPC의 임시 발생기다([load-test.md](load-test.md) 2-1절). 배포 측정 전에는 local 스택에서 배포 메모리 덮어쓰기(`reservation-service/k6/compose.deploy-memory.yml`, `compose.g1.yml`)로 먼저 잰다. local 결과에는 "local"을 붙인다.
- 측정용 덮어쓰기로 추적 샘플링을 0.01로 둔다. Mock PG에는 `DELAY` 300ms를 걸어 둔다([open-peak-load-plan.md](open-peak-load-plan.md) 1-3절).
- 매 실행마다 측정 대상 서비스를 재시작하고 새 회차를 만든다. 측정 전 30초 동안 목표의 10% 부하로 워밍업한다.

## 2. 시나리오

### G1. Gateway 인증 경로 한도

- 검토: Gateway 공통(팀)
- 목적: 인증이 필요한 모든 요청이 거치는 Gateway 경로(JWT 검증 → Redis 블랙리스트 확인 → 라우팅)의 한도와, Redis 차단기가 열리는 지점을 찾는다.
- 대상 API: `GET /api/v1/schedules/{id}/queue/me`. DB를 쓰지 않는 가장 가벼운 인증 API라, 서비스 쪽 비용이 작아 Gateway 한도가 드러난다.
- 준비: 회차 1개, 진입한 사용자 10,000명(Q2와 같은 방법, 입장 스케줄러 끔).
- 부하: 열린 모델(`ramping-arrival-rate`). 초당 1,000 → 2,000 → 4,000 → 8,000건, 단계마다 60초. 사용자는 10,000명을 돌려 쓴다.
- 지표: 단계별 p95, 503 건수와 그때의 차단기 상태, Gateway CPU, Redis 명령 지연, 서비스 CPU.
- 판정 `[가정]`:
  - 한도: p95 100ms 이하, 오류 1% 미만인 가장 높은 단계.
  - 차단기: 한도 안에서 `auth-redis` 차단기가 한 번도 열리지 않는다.
- 변형: 요청 로그 끔(`ISEONJWA_REQUESTLOG_ENABLED=false`), 추적 1.0.
- 비교할 단계: G-0 → G-2(블랙리스트 확인 줄이기) → G-3(요청 제한).

### B1. 오픈 전 공연 조회

- 검토: 반효승
- 목적: 캐시 없는 공연 조회가 오픈 전 새로고침을 몇 건까지 버티는지, 그 부하가 같은 서비스의 대기열 진입에 번지는지 본다.
- 대상 API: `GET /api/v1/concerts/{concertId}`(80%), `GET /api/v1/concerts?page=0`(20%). 둘 다 공개 경로라 토큰이 필요 없다.
- 준비: 공연 20개, 대상 공연에 회차 3개.
- 부하:
  - B1-a: 열린 모델로 초당 500 → 1,000 → 2,000 → 4,000건, 단계마다 60초.
  - B1-b(번짐 확인): B1-a의 2단계 부하를 유지한 채 Q1(진입 초당 1,000건)을 같이 건다.
- 사용자 행동: 30%는 10초, 70%는 30초 간격으로 새로고침한다(B1-a의 속도를 정할 때 쓴 가정).
- 지표: API별 p95, 커넥션 대기, 처리 중 요청 수, 쿼리 수(`pg_stat_statements`가 있으면, 없으면 Zipkin 1%).
- 판정 `[가정]`:
  - 한도: p95 300ms 이하, 오류 1% 미만인 가장 높은 단계.
  - 번짐: B1-b에서 진입 p95가 Q1 단독 대비 2배를 넘지 않는다.
- 비교할 단계: B-0 → B-1(조회 다듬기) → B-2(로컬 캐시) → B-3(HTTP 캐시) → B-4(서버 시각 분리).

### Q1. 대기열 진입 몰림

- 검토: 권영은
- 목적: 오픈 시각의 진입 몰림을 받는지, 순번이 정확한지, 재시작으로 회차 캐시가 빈 경우에도 버티는지 본다.
- 대상 API: `POST /api/v1/schedules/{id}/queue`.
- 준비: 오픈 1분 전 회차를 만들고, 30초 이상 기다려 회차 캐시가 채워진 것을 확인한다.
- 부하:
  - Q1-a: 오픈 시각에 30,000명이 10초 안에 한 번씩 진입한다(`ramping-arrival-rate`로 초당 3,000). 이어서 60,000명, 120,000명(초당 6,000, 12,000).
  - Q1-b(재시작): Q1-a의 30,000명 실행 중 5초 시점에 reservation-service를 재시작한다.
  - Q1-c(연타): 사용자의 10%가 같은 요청을 0.2초 간격으로 3번 보낸다.
  - Q1-d(오픈 순간 몰림): Q1-a는 1초 안에서도 고르게 보낸다. Q1-d는 사용자 수만큼 VU를 미리 두고 같은 출발 시각을 기다렸다가, 1초 안에 앞쪽이 붐비게(삼각 분포, 절반이 앞 약 0.3초 안) 한 번씩 진입한다(`per-vu-iterations`, `q1d-queue-burst.js`, ISE-217). 같은 사용자 수·같은 1초의 Q1-a(`ENTER_SECONDS=1`)와 비교해 1초 안의 몰림 모양이 결과를 바꾸는지 본다.
- 지표: p95, 201·200 건수, 오류, Redis CPU·명령 수, 커넥션 대기(캐시 미스면 DB로 간다), 처리 중 요청 수.
- 판정 `[가정]`:
  - 순번: Redis `queue:{sid}:seq` 값이 진입한 고유 사용자 수와 같다. `waiting`의 원소 수와도 같다.
  - Q1-a: p95 200ms 이하, 오류 1% 미만.
  - Q1-b: 재시작 뒤 30초 안에 오류율 1% 미만으로 돌아온다. 그동안 커넥션 대기가 쌓이지 않는다.
  - Q1-c: 연타한 사용자도 순번은 하나다.
  - Q1-d: Q1-a와 같은 기준이다. 발생기의 출발 지연(`send_lag`) p95가 50ms 이하일 때만 서버 결과로 읽는다. 넘으면 발생기 한계다.
- 비교할 단계: Q-0 → Q-1(캐시 미스 보호) → Q-2(진입 응답에 다음 폴링 시각).

### Q2. 순번 폴링

- 검토: 권영은
- 목적: 요청 수 1위 구간(폴링)의 한도를 재고, 로그·추적 같은 부가 비용의 비중을 숫자로 본다.
- 대상 API: `GET /api/v1/schedules/{id}/queue/me`.
- 준비: 입장 스케줄러를 끄고 30,000명을 진입시킨다(초당 1,000, 30초).
- 부하: 닫힌 모델에 가깝게, 대기자 한 명이 VU 한 개다. 각 VU는 응답의 `nextPollAfterMillis`만큼 쉬고 다시 부른다. 10분 동안 돌린다. 대기자를 60,000, 120,000명으로 늘려 다시 잰다.
- 지표: 초당 폴링 수(계산값 약 2,700건과 비교), p95, Gateway·서비스 CPU, 요청 로그 줄 수(Loki 수집량), 차단기 상태.
- 판정 `[가정]`:
  - 폴링 간격: 실제 간격 중앙값이 서버가 준 값과 ±10% 안에서 맞는다(클라이언트 행동이 맞는지 확인).
  - 한도: p95 100ms 이하, 오류 1% 미만인 최대 대기자 수.
- 변형: 요청 로그 끔, 추적 1.0, `poll-max` 20초·30초.
- 비교할 단계: Q2-0 → Q2-1(부가 비용 확인) → Q2-2(폴링 상한 늘리기). Q2-4(밀어주기)는 비교 기록만 남긴다.

### Q3. 입장 속도 유지

- 검토: 권영은
- 목적: 설정한 초당 입장 수(N=50)가 실제로 지켜지는지 본다. 같은 스케줄러 스레드를 쓰는 만료·추첨과 겹칠 때 입장이 빠지는지 본다.
- 준비: 입장 스케줄러를 켜고, 대기자 30,000명을 만든다(Q2와 같은 방법). 측정 중 1초마다 Redis `queue:{sid}:admitted`를 읽어 기록하는 보조 스크립트를 돌린다.
- 부하:
  - Q3-a: Q2의 폴링을 10분 동안 그대로 건다. READY가 된 VU는 입장 토큰을 받고 끝낸다.
  - Q3-b: Q3-a 중 2분 시점에 만료 대상 선점 5,000건을 만든다(X1 방법).
  - Q3-c: Q3-a 중 2분 시점에 다른 회차의 추첨(응모 30,000건)을 실행한다(L3 방법).
- 지표: 초당 입장 수(`admitted` 증가량), 입장 토큰 발급 p95, READY에서 토큰 발급까지 걸린 시간.
- 판정 `[가정]`: 10분 동안 초당 입장 수가 45~50인 초가 95% 이상이다. 0인 초가 2초 넘게 이어지지 않는다.
- 비교할 단계: Q3-0 → Q3-1(스케줄러 분리) → Q3-2(따라잡기). Q3-3(N 역산)은 K1·PAY1 결과로 계산한다.

### PAY1. 결제 승인

- 검토: 안준현
- 목적: PG 동시 수 10의 한도를 확인하고, PG가 느려질 때 결제 서비스가 어떻게 버티는지 본다.
- 대상 API: `POST /api/v1/payments`. 헤더는 `Authorization`(Access 토큰)과 `Idempotency-Key`(UUID). 본문은 `{"paymentToken", "method": "CARD", "amount"}`.
- 준비: K1-H로 선점 20,000건을 만들고 결제 토큰·금액·사용자 ID를 CSV로 저장한다. 결제 토큰 유효 시간(선점 5분 − 10초) 안에 써야 하므로, 단계마다 선점을 새로 만든다.
- 부하:
  - PAY1-a: 열린 모델로 초당 20 → 40 → 80 → 160건, 단계마다 60초. Mock PG `DELAY` 300ms.

  - `payment_approve_seconds{outcome}`(승인·거절·불명·`unavailable`)

  - 결제 서비스 커넥션 대기
- 판정 `[가정]`:
  - 계산과 맞는가: PAY1-a에서 503 `PG_UNAVAILABLE`이 나기 시작하는 속도가 초당 약 33건(10 ÷ 0.3초) 근처다.

  - PAY1-c: 장애가 끝난 뒤 차단기가 30초 안에 닫힌다.
- 비교할 단계: PAY-0 → PAY-1(동시 수 조정) → PAY-2(짧은 대기) → PAY-3(느린 호출 기준).

### R1. 결제 결과 반영

  - k6의 승인 → 확정 시간

  - Kafka 소비자 랙
  - reservation-service 커넥션 대기
- 판정 `[가정]`:

- 변형: reservation-service 2대(헛수고 확인, S4 전후).
- 비교할 단계: X-0 → X-1(묶음·주기) → X-2(S4) → X-3(묶음 처리).

- 비교할 단계: 추첨 담당이 정한다. 접수형(202) 전환을 검토하면 그 전후를 같은 시나리오로 잰다.

### L2. 자동결제 폭주

- 검토: 이강민(배정), 안준현(결제 명령 소비자)
- 목적: 추첨 직후 당첨자 2,000명의 배정·자동결제가 10분 안에 95% 끝나는지, 그동안 다른 회차의 일반 결제가 영향을 받는지 본다.
- 준비: L1 상태(응모 30,000건, 빌링키 등록)에서 추첨 시각을 측정 시작으로 둔다. 다른 회차에 PAY1용 선점을 미리 만든다.
- 부하:
  - L2-a: 추첨만 실행한다. Mock PG `DELAY` 300ms, 실패율 5%(`DECLINE`, rate 0.05).
  - L2-b: L2-a와 같은 시간에 다른 회차 일반 결제를 초당 20건 건다(PAY1 방법).
- 지표:
  - 배정된 당첨자 수와 결제 완료 수(10초마다 SQL)
  - `payment.command` 소비자 랙
  - Bulkhead 남은 자리
  - 일반 결제 503 비율과 p95
  - 승계 처리 수
- 판정 `[가정]`:
  - 완료 시간: 추첨 뒤 10분 안에 자동결제 95%가 확정된다.
  - 일반 결제 영향: L2-b에서 일반 결제 503 비율이 PAY1 단독 대비 늘지 않는다.
  - 계산과 맞는가: 소비자 동시 1개, PG 300ms면 2,000건에 약 10분이 걸린다. 결과가 이와 다르면 배정 쪽 병목(당첨자마다 남은 좌석 전체 조회)을 본다.
- 비교할 단계: LOT-0 → LOT-1(배정 조회 줄이기) → LOT-2(소비자 동시 수) → LOT-3(전용 Bulkhead).

### L3. 추첨과 일반 판매 간섭

- 검토: 이강민, 최권우
- 목적: 추첨 실행과 배정이 같은 서비스에서 도는 일반 판매(선점·입장)에 주는 영향을 잰다(추첨 문서 시나리오 3).
- 부하: K1-H를 초당 100명으로 300초 건다. 60초 시점에 다른 회차의 추첨을 실행한다(응모 30,000건). Q3-a를 같이 걸면 입장 속도 영향도 본다.
- 지표: 선점 p95(추첨 전·중·후), 초당 입장 수, 커넥션 대기, 추첨 실행 시간.
- 판정 `[가정]`:
  - 선점 영향: 선점 p95 증가 20% 이하(추첨 문서 기준). 넘으면 추첨 분리의 근거로 쓴다(SA 7-1).
  - 입장 영향: 초당 입장 수가 0인 초가 2초 넘게 이어지지 않는다.
- 비교할 단계: C1-2(스케줄러 분리) 전후.

### O1. 오픈 피크 한 흐름

- 검토: 팀
- 목적: 구간별 개선을 합친 뒤 오픈 피크 전체를 한 번에 판정한다. ISE-181 완료 기준이다.
- 준비: 회차 1개(15,000석), 사용자 30,000명, Mock PG `DELAY` 300ms. 입장 속도는 Q3-3에서 다시 정한 값을 쓴다.
- 사용자 행동(VU 하나 = 사용자 한 명):
  1. 오픈 10분 전부터 무작위 시각에 들어와 공연 상세를 10~30초마다 새로고침한다.
  2. 오픈 시각에 0~10초 무작위 지연 뒤 대기열에 진입한다.
  3. `nextPollAfterMillis`마다 순번을 조회하고, READY면 입장 토큰을 받는다.
  4. K1처럼 좌석 조회 → 1~3초 고민 → 선점한다. 409면 최대 2번 재시도하고, 매진이면 끝낸다.
  5. 선점에 성공하면 5~30초 뒤 결제한다. 10%는 결제하지 않고 떠난다.
  6. 결제 승인 뒤 예매 조회로 확정을 확인한다(0.5초 간격, 최대 10번).
- 지표: 단계별 p95와 오류율, 진입 → 입장 대기 시간 분포, 매진 시각, 확정 지연, 만료 처리, 부하 뒤 회복 시간, 구간별 서버 지표.
- 판정 `[가정]`:
  - 정합성: 중복 판매 0, 대사 불일치 0, 결제 승인 수 = 확정 예매 수.
  - 응답: 선점·결제 p95가 Gateway 3초 안이고 오류(5xx·타임아웃) 1% 미만이다.
  - 회복: 부하가 끝나고 30초 안에 회복한다.
  - 대기열: 대기자가 입장 순서를 건너뛰지 않는다(입장 순서 = 진입 순서).

- 503은 모두 Gateway `auth-redis` 차단기 거절이다. Redis 서버 지연은 0.1~0.8ms로 정상이었고, 모든 실행에서 Redis `seq` = `waiting` = 201 수였다(대기열 서버까지 간 요청은 정확히 처리).
- 재기동 직후에는 느린 호출로 열린다. Gateway까지 재기동한 경우는 차단기가 열렸고, reservation-service만 재기동한 경우는 차단기는 정상이고 진입 p95가 308ms였다. 각 1회라 가능성으로 둔다.
- 열린 순간의 원인(실패/느린 호출)과 실패 예외 종류는 확인하지 못했다. Prometheus 표본이 5초 간격이고, actuator에 `circuitbreakerevents`가 없으며, 필터가 오류를 로그 없이 503으로 바꾼다.
- 부하 뒤 회복 시간: 열린 뒤 요청이 없으면 계속 열려 있다(자동 반열림 꺼짐). 10초 뒤 첫 요청부터 반열림, 시험 호출 5건 성공으로 닫혔다.
- Q1-d(1초 안 몰림)와 Q1-c(연타)는 한도가 Q1-a보다 낮은 차단기에서 막혀 배포에서 재지 않았다.

**Q2 순번 폴링** (`q2-queue-poll.js`, 입장 스케줄러 끔, 10분, 표준 워밍업 뒤)

| 조건 | 판정 | 유효 | poll_duration p95 | 폴링 200 / 503 | 초당 폴링 | 계산값 | 준 간격 중앙값 / 실제 간격(추정) | poll_lateness p95 | `auth-redis` | Gateway CPU (서버 전체) |
|---|---|---|---|---|---|---|---|---|---|---|
| 대기자 3,000명, VUS 300 | 통과 | 유효(ready 0) | 2.79ms | 193,563 / 0 | 322 | 약 327 | 10,616ms / 약 10,618ms | 0ms | 아니오 | 19% (53%) |
| 대기자 10,000명, VUS 400 | 실패 | 유효(ready 0) | 33.76ms | 19,848 / 1,910,147 | 평균 3,181(재시도 포함) | 약 964 | 10,940ms / 판단 불가 | 4ms | 시작 3초 뒤 열려 끝까지 | 33% (90%) |

- 계산값: 간격이 `clamp(순번/50초, 3초, 10초) × (1 + 0~20%)`라 앞쪽 500명이 3~11초마다 부른다. 이를 반영한 값이다. 명세의 "대기자 ÷ 약 11초"(3,000명이면 약 270)는 앞쪽 대기자를 빼고 셈한 근사다. 설명은 [폴링 수 노트](../../learning/youngeun/qna/2026-11-10-queue-poll-rate-and-interval.md).
- 실제 간격은 raw CSV에 사용자별 ms 시각이 없어 "준 간격 + 응답 시간 + 늦게 보낸 시간"으로 추정했다(±10% 안).
- 대기자 10,000명: 첫 폴링(10초에 흩음, 초당 약 1,000건) 3초 만에 `auth-redis`가 열렸다. 503을 받은 대기자가 3초 뒤 다시 부르고 503이 빨리 돌아와 초당 2,300~3,800건으로 불었다. 차단기는 10초마다 반열림으로 일부를 통과시켰다가 다시 열려 600초 동안 회복하지 못했다. setup의 대기자 진입(10,000명 6초)은 성공했다. 차단기와 클라이언트 재시도(3초)가 맞물려 스스로 회복하지 못했다. 오류 뒤 재시도 간격을 점점 늘리는 방식(지수 백오프)을 검토할 거리로 둔다(ISE-59).
- 오류 없이 버틴 최대 대기자 수: 3,000명 통과, 10,000명 실패 사이. 명세의 30,000명은 재지 않았다.
