# 오픈 피크 부하 시나리오 명세 (ISE-181)

상태: 담당 검토 반영 중 (2026-11-05 작성, ISE-181 담당 최권우 요청으로 Claude Code가 작성. 2026-11-09 Q1·L1~L3 검토와 X1 자체 검토를 반영했다, ISE-192)

[open-peak-load-plan.md](open-peak-load-plan.md)에서 찾은 트래픽 집중 구간마다, k6 스크립트로 바로 옮길 수 있는 수준으로 시나리오를 적는다. 다른 담당의 영역도 측정 담당(최권우)이 먼저 초안을 쓴다. 각 시나리오의 "검토" 칸에 적힌 담당이 확인하고 고친다. 고친 내용은 이 문서에 PR로 반영한다.

- 숫자는 모두 `[가정]`이다. 판정 기준도 측정 전에 정한 초안이며, 담당 검토에서 바꿀 수 있다. 측정 결과를 본 뒤에는 바꾸지 않는다.
- 요청·응답 필드 이름은 2026-11-05 코드에서 확인했다. 스크립트를 만들 때 다시 확인한다.
- 개선 단계(각 시나리오의 "비교할 단계")의 이름은 계획 문서 2절 표를 따른다.

## 2. 시나리오

### G1. Gateway 인증 경로 한도

- 검토: Gateway 공통(팀)
- 목적: 인증이 필요한 모든 요청이 거치는 Gateway 경로(JWT 검증 → Redis 블랙리스트 확인 → 라우팅)의 한도와, Redis 차단기가 열리는 지점을 찾는다.
- 대상 API: `GET /api/v1/schedules/{id}/queue/me`. DB를 쓰지 않는 가장 가벼운 인증 API라, 서비스 쪽 비용이 작아 Gateway 한도가 드러난다.
- 준비: 회차 1개, 진입한 사용자 10,000명(Q2와 같은 방법, 입장 스케줄러 끔).
- 부하: 열린 모델(`ramping-arrival-rate`). 초당 1,000 → 2,000 → 4,000 → 8,000건, 단계마다 60초. 사용자는 10,000명을 돌려 쓴다.
- 지표: 단계별 p95, 503 건수와 그때의 차단기 상태, Gateway CPU, Redis 명령 지연, 서비스 CPU.
- 판정 `[가정]`:
  - 한도: p95 100ms 이하, 오류 1% 미만인 가장 높은 단계.
  - 차단기: 한도 안에서 `auth-redis` 차단기가 한 번도 열리지 않는다.
- 변형: 요청 로그 끔(`ISEONJWA_REQUESTLOG_ENABLED=false`), 추적 1.0.
- 비교할 단계: G-0 → G-2(블랙리스트 확인 줄이기) → G-3(요청 제한).
- 다른 측정에서 먼저 본 것: 아래 "Gateway 인증 차단기 관찰"에 모은다. G1을 재기 전에도 다른 시나리오의 503을 해석할 때 쓴다.

#### Gateway 인증 차단기(`auth-redis`) 관찰

G1을 재기 전에, 다른 시나리오 세 곳(Q1-d, L1, K1·K1-H)에서 서비스보다 이 차단기가 먼저 요청을 막았다. 같은 현상이 여러 담당의 결과에 섞이므로 여기에 모은다(2026-11-09까지, 모두 local).

**동작.** Gateway는 인증이 필요한 요청마다 Redis에서 로그아웃 토큰(`blacklist:{jti}`)인지 확인한다(`GatewayAuthenticationFilter`). 호출 시한은 100ms이고, 이 호출에 차단기 `auth-redis`를 건다. 차단기가 열려 있거나 호출이 실패하면 보호 API는 즉시 503이다(fail closed, [ADR 0005](../../decisions/0005-auth-redis-fail-closed.md)). 공개 API는 이 확인을 거치지 않는다.

| 설정(`config-repo/gateway.yml`) | 값 | 뜻 |
|---|---|---|
| `sliding-window-size` / `minimum-number-of-calls` | 20 / 20 | 최근 20번 호출로 판단한다 |
| `slow-call-duration-threshold` / `slow-call-rate-threshold` | 50ms / 50% | 50ms를 넘는 호출이 절반 이상이면 연다 |
| `failure-rate-threshold` | 50% | 실패(시한 100ms 초과 포함)가 절반 이상이면 연다 |
| `wait-duration-in-open-state` | 10s | 연 뒤 10초 동안 모두 거절한다 |

**관찰.**

| 측정 | 담당 | 조건 | 결과 |
|---|---|---|---|
| Q1-d | 권영은 | 300명을 0.1초·1초 안에 진입 | 503이 68~93%. 100명·1초는 오류 0. Redis 자체 지연 평균 0.15ms |
| L1 | 이강민 | 응모 초당 400건부터 | 1~2ms짜리 503. 거절 위치는 확인하지 못했지만 모양이 같다 |
| K1-H base | 최권우 | 선점만 초당 100명부터 | Gateway CPU 100~180%에서 느린 호출 비율이 90~100%가 되어 열렸다. 거절 약 6만 1천 건. Redis CPU 10% 아래 |
| K1-H, 느린 호출 판정 끔 | 최권우 | 400명부터 | Redis 확인 시한 초과가 몰려 실패율로 열렸다. 실패는 초당 1건 안팎인데 정상 요청까지 초당 300~750건 거절 |
| K1-H, Gateway GC를 G1로 | 최권우 | 400명 | Gateway를 통과하는 요청이 초당 약 600건을 넘자 Redis 확인 평균이 0.5ms에서 8~13ms로 늘고 시한 초과가 초당 5~45건. GC를 바꿔도 같아 Gateway GC는 원인이 아니다 |
| K1 S(P4b) | 최권우 | 좌석 조회와 선점 160명부터 | Gateway 503 10,366건 중 10,048건이 이 차단기의 즉시 거절 |

**지금까지의 해석.**
- Redis는 느리지 않았다. 호출 시간은 호출하는 쪽(Gateway)에서 재므로, Gateway가 바쁘면 Redis가 멀쩡해도 느린 호출이나 시한 초과로 세어진다.
- 판단 범위가 20번이라 순간적인 지연에도 쉽게 열리고, 열리면 10초 동안 정상 요청까지 모두 거절한다.
- Gateway가 초당 약 600건을 넘을 때 Redis 확인이 Gateway 안에서 왜 밀리는지는 아직 모른다. G1에서 가려야 할 질문이다.
- 모두 노트북 한 대(k6와 전체 스택이 CPU를 나눠 씀)에서 본 값이다. 배포 서버에서도 같은 지점에서 열리는지는 확인하지 않았다.

**측정 환경의 처리.** K1·K1-H 단계 측정은 선점 경로를 보려고 측정 브랜치에서만 느린 호출 판정을 100ms(호출 시한과 같음)로, 실패율 기준을 100%로 덮어쓴다(2026-11-07 결정). 공유 설정은 그대로다. 그래서 K1-H 결과는 공유 기준의 배포 환경과 다르다는 점을 함께 적는다. 공유 기준을 바꿀지는 측정이 끝난 뒤 Gateway 담당과 정한다(`docs/design/reservation/k6-seathold-bottleneck-plan.md` 6절 13번, ISE-79 브랜치에 있고 dev에는 아직 없다).

**시나리오별 약속.** 서비스가 낸 503과 구분하려고, 503이 나온 시나리오는 그 구간의 `resilience4j_circuitbreaker_state{name="auth-redis"}`와 Gateway 로그(`일시적으로 인증을 확인할 수 없습니다`)를 함께 적는다([troubleshooting.md](../../troubleshooting.md) TS-42).

### B1. 오픈 전 공연 조회

- 검토: 반효승
- 목적: 캐시 없는 공연 조회가 오픈 전 새로고침을 몇 건까지 버티는지, 그 부하가 같은 서비스의 대기열 진입에 번지는지 본다.
- 대상 API: `GET /api/v1/concerts/{concertId}`(80%), `GET /api/v1/concerts?page=0`(20%). 둘 다 공개 경로라 토큰이 필요 없다.
- 준비: 공연 20개, 대상 공연에 회차 3개.
- 부하:
  - B1-a: 열린 모델로 초당 500 → 1,000 → 2,000 → 4,000건, 단계마다 60초.
  - B1-b(번짐 확인): B1-a의 2단계 부하를 유지한 채 Q1(진입 초당 1,000건)을 같이 건다.
- 사용자 행동: 30%는 10초, 70%는 30초 간격으로 새로고침한다(B1-a의 속도를 정할 때 쓴 가정).
- 지표: API별 p95, 커넥션 대기, 처리 중 요청 수, 쿼리 수(`pg_stat_statements`가 있으면, 없으면 Zipkin 1%).
- 판정 `[가정]`:
  - 한도: p95 300ms 이하, 오류 1% 미만인 가장 높은 단계.
  - 번짐: B1-b에서 진입 p95가 Q1 단독 대비 2배를 넘지 않는다.
- 비교할 단계: B-0 → B-1(조회 다듬기) → B-2(로컬 캐시) → B-3(HTTP 캐시) → B-4(서버 시각 분리).

### Q1. 대기열 진입 몰림

- 검토: 권영은
- 목적: 오픈 시각의 진입 몰림을 받는지, 순번이 정확한지, 재시작으로 회차 캐시가 빈 경우에도 버티는지 본다.
- 대상 API: `POST /api/v1/schedules/{id}/queue`.
- 준비: 오픈 1분 전 회차를 만들고, 30초 이상 기다려 회차 캐시가 채워진 것을 확인한다.
- 부하:
  - Q1-a: 오픈 시각에 30,000명이 10초 안에 한 번씩 진입한다(`constant-arrival-rate`로 초당 3,000. 속도는 `USERS / ENTER_SECONDS`의 평균이다). 이어서 60,000명, 120,000명(초당 6,000, 12,000). 실제 오픈은 앞쪽에 몰리므로, 결과에는 평균 속도인지 최고 속도(`ENTER_SECONDS=1` 등)인지 적는다.
  - Q1-b(재시작, 추후): Q1-a의 30,000명 실행 중 5초 시점에 reservation-service를 재시작한다. 스크립트·README에 재시작 절차가 없어 이번 측정(ISE-202)에서는 뺀다. 다시 하면 수동 절차를 README에 적거나 `RESTART_AT_SECONDS` 같은 옵션을 둔다.
  - Q1-c(연타): 사용자의 10%가 같은 요청을 0.2초 간격으로 3번 보낸다.
  - Q1-d(오픈 순간 몰림): Q1-a는 1초 안에서도 고르게 보낸다. Q1-d는 사용자 수만큼 VU를 미리 두고 같은 출발 시각을 기다렸다가, 1초 안에 앞쪽이 붐비게(삼각 분포, 절반이 앞 약 0.3초 안) 한 번씩 진입한다(`per-vu-iterations`, `q1d-queue-burst.js`, ISE-217). 같은 사용자 수·같은 1초의 Q1-a(`ENTER_SECONDS=1`)와 비교해 1초 안의 몰림 모양이 결과를 바꾸는지 본다.
- 지표: p95, 201·200 건수, 오류, Redis CPU·명령 수, 커넥션 대기(캐시 미스면 DB로 간다), 처리 중 요청 수, Gateway `auth-redis` 차단기 상태(G1 "Gateway 인증 차단기 관찰").
- 판정 `[가정]`:
  - 순번: Redis `queue:{sid}:seq` 값이 첫 요청의 201 건수(`enter_results{result="joined", attempt="first"}`)와 같다. `waiting`의 원소 수와도 같다. `USERS`와 비교하지 않는다. k6가 반복을 `USERS`보다 한 번 더 시작한 실행이 있었다(Q1-c 300명 설정에 고유 사용자 301). 실패한 실행에서도 `seq`·`waiting`은 201 건수와 같았다.
  - Q1-a: p95 200ms 이하, 오류 1% 미만.
  - Q1-b(추후): 재시작 뒤 30초 안에 오류율 1% 미만으로 돌아온다. 그동안 커넥션 대기가 쌓이지 않는다.
  - Q1-c: 연타한 사용자도 순번은 하나다.
  - Q1-d: Q1-a와 같은 기준이다. 발생기의 출발 지연(`send_lag`) p95가 50ms 이하일 때만 서버 결과로 읽는다. 넘으면 발생기 한계다.
- 비교할 단계: Q-0 → Q-1(캐시 미스 보호) → Q-2(진입 응답에 다음 폴링 시각).

### L1. 응모 마감 직전 몰림

- 검토: 이강민
- 목적: 응모 마감 직전의 몰림(마지막 1분에 6,000건, 초당 100건)을 받는지와 중복 응모 0을 확인한다.

- 준비: 회차 1개, 추첨(좌석 3,000석, 예비 1,000명, 응모 마감 측정 종료 10초 뒤). 스크립트는 반복마다 새 사용자를 쓰므로 사용자 수는 단계 속도 × 단계 시간의 합이다. 기본 단계(100 → 800, 단계마다 60초)면 약 10만 명이다(2026-11-06 local 100,384건). 측정 전용 키로 서명하므로 가입은 필요 없다.

- 판정 `[가정]`:
  - 응답: 초당 100건에서 p95 300ms 이하(추첨 문서 합격 기준).
  - 정합성: 응모 행 수 = 고유 응모 사용자 수다. 중복 재요청은 같은 멱등키라 201을 다시 돌려주므로, 201 건수가 응모 행 수보다 많은 것이 정상이다(2026-11-06 local: 201 50,860건, 응모 행 48,553 = 고유 사용자 48,553).
  - 한도: 오류 1% 미만인 최대 속도를 적는다.
- 비교할 단계: 추첨 담당이 정한다. 접수형(202) 전환을 검토하면 그 전후를 같은 시나리오로 잰다.

### L2. 자동결제 폭주

- 검토: 이강민(배정), 안준현(결제 명령 소비자)
- 목적: 추첨 직후 당첨자 2,000명의 배정·자동결제가 10분 안에 95% 끝나는지, 그동안 다른 회차의 일반 결제가 영향을 받는지 본다.

- 지표:

### L3. 추첨과 일반 판매 간섭

- 검토: 이강민, 최권우
- 목적: 추첨 실행과 배정이 같은 서비스에서 도는 일반 판매(선점·입장)에 주는 영향을 잰다(추첨 문서 시나리오 3).
- 부하: K1-H를 초당 100명으로 300초 건다. 60초 시점에 다른 회차의 추첨을 실행한다(응모 30,000건). Q3-a를 같이 걸면 입장 속도 영향도 본다.
- 지표: 선점 p95(추첨 전·중·후), 초당 입장 수, 커넥션 대기, 추첨 실행 시간.
- 결과에 함께 적을 것: 추첨 실행 시간이 어느 쪽이었는지(local에서 0.5초·4.5초 두 갈래로 나왔다), ISE-196(커넥션 대기 1초) 적용 여부(간섭 모양이 달라진다. 환경 기록표에 적는다). 선점 p95의 기준점(K1-H 단독)은 ISE-79 k6 단계 측정의 결과를 쓴다.
- 판정 `[가정]`:
  - 선점 영향: 선점 p95 증가 20% 이하(추첨 문서 기준). 넘으면 추첨 분리의 근거로 쓴다(SA 7-1).
  - 입장 영향: 초당 입장 수가 0인 초가 2초 넘게 이어지지 않는다.
- 비교할 단계: C1-2(스케줄러 분리) 전후.

### O1. 오픈 피크 한 흐름

- 검토: 팀
- 목적: 구간별 개선을 합친 뒤 오픈 피크 전체를 한 번에 판정한다. ISE-181 완료 기준이다.
- 준비: 회차 1개(15,000석), 사용자 30,000명, Mock PG `DELAY` 300ms. 입장 속도는 Q3-3에서 다시 정한 값을 쓴다.
- 사용자 행동(VU 하나 = 사용자 한 명):
  1. 오픈 10분 전부터 무작위 시각에 들어와 공연 상세를 10~30초마다 새로고침한다.
  2. 오픈 시각에 0~10초 무작위 지연 뒤 대기열에 진입한다.
  3. `nextPollAfterMillis`마다 순번을 조회하고, READY면 입장 토큰을 받는다.
  4. K1처럼 좌석 조회 → 1~3초 고민 → 선점한다. 409면 최대 2번 재시도하고, 매진이면 끝낸다.
  5. 선점에 성공하면 5~30초 뒤 결제한다. 10%는 결제하지 않고 떠난다.
  6. 결제 승인 뒤 예매 조회로 확정을 확인한다(0.5초 간격, 최대 10번).
- 지표: 단계별 p95와 오류율, 진입 → 입장 대기 시간 분포, 매진 시각, 확정 지연, 만료 처리, 부하 뒤 회복 시간, 구간별 서버 지표.
- 판정 `[가정]`:
  - 정합성: 중복 판매 0, 대사 불일치 0, 결제 승인 수 = 확정 예매 수.
  - 응답: 선점·결제 p95가 Gateway 3초 안이고 오류(5xx·타임아웃) 1% 미만이다.
  - 회복: 부하가 끝나고 30초 안에 회복한다.
  - 대기열: 대기자가 입장 순서를 건너뛰지 않는다(입장 순서 = 진입 순서).

### 동작 확인 중 얻은 수치 (local, 1회, 참고용)

| 시나리오 | 관찰 | 쓰임 |
|---|---|---|
| X1 | 만료 스케줄러가 묵은 선점을 5초 주기·100건 묶음으로 처리하는 속도는 초당 약 15.6건이었다(35주기 3,500건 224초). 한 주기가 5초 간격에 처리 약 1.4초를 더해 약 6.4초다 | 계획 문서 Z10의 계산값(초당 20건)보다 낮다. X-0 기준선의 예상값을 이 값으로 둔다 |
