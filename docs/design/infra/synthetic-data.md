# Synthetic Data: LLM이 만든 가상 사용자로 오픈 피크 재기 (ISE-262)

발제 필수 항목 "가상 사용자 기반의 부하 테스트 시나리오 생성(Synthetic Data)"을 채운다. 발제가 요구하는 산출물은 셋이다: LLM에 쓴 프롬프트 원문, 생성한 Synthetic Data(CSV), 일반 부하 테스트 결과와 Synthetic Data 기반 결과의 비교. 재료와 도구는 [`loadtest/synthetic/`](../../../loadtest/synthetic/README.md)에 있다.

- 이력: ISE-28 "Synthetic Data 1차본"은 11/11에 취소됐다(대기열 담당 판단: 인기 회차 쏠림은 회차별 Redis 키가 따로라 Q1~Q3와 결과가 같고, 좌석 구역 쏠림은 좌석 담당 몫). 발제 필수 산출물이 저장소에 없어 11/13에 ISE-262로 다시 시작했다([판단 기록](../../ai-judgments/junhyun/2026-11-13-fill-presentation-gaps-restore-synthetic-data.md)).
- 지금까지의 k6 시나리오도 난수를 쓴다. 다만 모든 사용자가 같은 규칙으로 움직인다(예: O1은 진입을 오픈 뒤 10초 안에 고르게 흩고, 1석·2석 반반, 70%가 좌석 응답 앞쪽 10%에서 고른다). Synthetic Data는 사용자마다 행동이 다르다.

## 1. 트래픽 시나리오 (발제 Step 1, 팀 설계)

| 질문 | 우리 답 | 근거 |
|---|---|---|
| 언제 몰리나 | 평일 오후 8시 티켓 오픈 정각. 오픈 10분 전부터 상세 새로고침, 오픈 직후 몇 초 안에 대기열 진입이 몰림 | SA 2-2 P1(퇴근 후 PC로 대기) |
| 누가 어떻게 쓰나 | 퇴근 후 PC 팬, 친구와 2매, 새로고침 연타, 여러 기기 접속. 매크로는 범위 밖 | SA 1-1 문제 정의의 현재 대안(여러 기기, 새로고침 연타), 2-2 페르소나, 4-5 제외 범위(행동 기반 매크로 탐지) |
| 어디가 병목인가 | 좌석 배치도 조회(응답 약 830KB), 인기 구역 선점 경쟁(409와 재시도), 오픈 직후 대기열 진입, Gateway 인증 경로 | S1·K1·Q1·G1 배포 측정([`open-peak-scenarios.md`](open-peak-scenarios.md), [Gateway 발표 소스](../../presentation/2026-11-12-gateway-overload-source.md)) |

사용자 흐름은 O1과 같다: 상세 조회 → 대기열 진입 → 순번 폴링 → 입장 토큰 → 좌석 배치도 → 선점(1~4석) → 결제 → 확정 확인. 409면 대기열로 돌아가지 않고 좌석만 다시 고른다. 선점은 5분 유지된다.

## 2. LLM으로 만들기 (발제 Step 2)

- 프롬프트: [`o1-prompt.md`](../../../loadtest/synthetic/o1-prompt.md). 1절 시나리오, 시스템 조건(좌석 25구역·등급, 1인 4매, 입장 초당 50명, 측정 창 ±10분), CSV 열과 필드별 허용 범위, 분포를 적는 JSON 형식을 줬다. 공개 통계를 안다고 꾸며 내지 말고 추정은 추정이라고 밝히라고 했다.
- 응답: [`o1-response.md`](../../../loadtest/synthetic/o1-response.md)(원문). 모델·명령·해시는 [`loadtest/synthetic/README.md`](../../../loadtest/synthetic/README.md)의 생성 기록에 있다.
- 왜 LLM에게 행이 아니라 분포를 받았나: 측정에는 수천 명이 필요하고, 같은 데이터를 다시 만들 수 있어야 한다. LLM은 페르소나와 분포(JSON)와 표본 40행을 내고, 3,000명은 `generate.py`가 시드 고정으로 만든다. LLM도 응답에서 표본은 난수 생성기로 뽑은 것이 아니라며 생성기로 다시 뽑기를 권했다.

LLM이 낸 페르소나(비율과 성격 요약, 수치는 모두 LLM이 추정이라고 밝힘):

| 페르소나 | 비율 | 특징 |
|---|---|---|
| `office_pc_fan` 퇴근 후 PC 팬 | 28% | 오픈 5분 전쯤 접속, 정각 진입, VIP 45%, 409면 같은 등급에서 다시 |
| `pair_buyer` 친구와 2매 | 18% | 항상 2석, 고르는 시간과 결제가 느림, 409 뒤 등급을 바꾸는 비율이 높음 |
| `refresh_spammer` 새로고침 연타 | 12% | 3~6초 간격 새로고침, 진입 2~5번 연타, 재시도 4~5번 |
| `mobile_commuter` 퇴근길 모바일 | 12% | 오픈 직전·직후 접속, 느린 선택·결제, 대기가 길면 일부 떠남 |
| `late_casual` 오픈 뒤 일반 관심층 | 10% | 오픈 30초~10분 뒤 접속, 등급을 덜 가림, 쉽게 포기 |
| `vip_hunter` VIP 고집 팬 | 8% | VIP만, 4매 60%, 409 뒤에도 VIP에서 끝까지 |
| `multi_device` 여러 기기 접속 | 7% | 한 계정이 여러 기기에서 새로고침·진입 |
| `browse_only` 구경만 하는 사람 | 5% | 85%는 진입하지 않음 |

LLM이 계산해 둔 전체 성질: VIP(전체 좌석의 20%)를 노리는 사용자가 약 42%, 진입 요청이 사용자 수의 약 1.6배. 둘 다 아래 3절에서 생성 데이터로 다시 센다.

## 3. 검증

LLM 출력을 그대로 믿지 않는다. `validate.py`가 형식·범위·비율을 기계로 본다.

| 대상 | 검사 | 결과(2026-11-13) |
|---|---|---|
| `o1-personas.json` | 필드 12개, 분포 종류·키, 비율 합 1, 가중치 합 1, 필드별 허용 범위·값 | 문제 없음. 페르소나 8개, 비율 합 1.0 |
| `o1-sample-40.csv`(LLM이 쓴 표본) | 머리말, 행마다 범위·허용 값, 페르소나별 분포 범위 | 문제 없음. 페르소나마다 30명 미만이라 페르소나 안 비율 검사는 건너뜀 |
| `o1-synthetic-3000.csv`(생성, 시드 20261113) | 위와 같고, 비율 허용치 `max(1%p, 3σ)` 안. 같은 시드로 두 번 만들어 바이트 비교 | 문제 없음. 두 번 만든 파일이 같음 |

생성한 3,000명의 성질(LLM이 응답에서 계산한 값과 비교):

| 성질 | 생성 데이터 | LLM 계산 |
|---|---|---|
| VIP를 노리는 사용자 | 1,265명(42.2%) | 약 42% |
| 진입 요청 수 ÷ 사용자 수 | 1.59 | 약 1.6 |
| 오픈 전 접속 | 2,500명(83.3%) | — |
| 오픈 전 접속이면서 오픈 3초 안에 진입 | 2,307명(76.9%) | "진입 지연 0~2초에 몰림" |
| 진입하지 않음(`enter_clicks = 0`) | 169명 | — |
| 좌석 수 1·2·3·4석 | 999 · 1,613 · 84 · 304명 | — |
| VIP를 노린 사용자가 요청한 좌석 합 | 2,675석(VIP 좌석은 3,000석) | — |
| 선점 뒤 결제하지 않고 떠남 | 328명(10.9%) | — |

## 4. k6 연동 (발제 Step 3)

O1(`loadtest/k6/scenarios/o1-open-peak.js`)이 `USERS_CSV`를 받으면 행마다 다른 프로필로 움직이고, 없으면 지금과 같은 균일 프로필로 움직인다. 두 모드는 같은 상태 기계를 쓴다. 비교에서 다른 것은 사용자 행동뿐이다.

| CSV 열 | O1에서 쓰는 곳 |
|---|---|
| `arrive_s`, `refresh_s` | 첫 접속 시각(오픈 기준), 오픈 전 상세 새로고침 간격 |
| `enter_delay_ms`, `enter_clicks` | 진입 시각, 진입 요청 횟수(2 이상은 연타 태그 `click=dup`, 0은 진입 안 함) |
| `queue_patience_s` | 대기 중 이 시간이 지나면 폴링을 멈추고 떠남(`left_queue`) |
| `seats`, `zone`, `think_ms` | 한 번에 고를 좌석 수, 노리는 등급(VIP·R·S·ANY), 첫 선택까지 시간 |
| `max_retry`, `on_conflict` | 409 뒤 다시 고르는 횟수, 같은 등급·아무 곳·포기 |
| `abandon_after_hold`, `pay_delay_s` | 선점 뒤 결제하지 않고 떠남, 결제까지 시간 |

지표의 `step_duration`과 `o1_outcomes`에 `persona` 태그가 붙는다(균일 모드는 `uniform`).

## 5. 비교 측정 계획

| 항목 | 균일 O1 | Synthetic O1 |
|---|---|---|
| 대상 | 배포 서버(`m7i.xlarge` 1대, 측정 모드), 발생기 `c6i.xlarge`, 사설 IP | 같음 |
| 사용자 | 3,000명, VU 300 | `o1-synthetic-3000.csv` 3,000명, VU 300 |
| 시간 | 오픈 전 600초, 오픈 뒤 900초 | 같음 |
| 회차 | 실행마다 새 15,000석 회차(`seed-demo.sh open`) | 같음 |
| PG | Mock PG 승인 지연 300ms(서버 안에서 한 번 주입, 두 실행 사이 재시작 없음) | 같음 |
| 순서 | 먼저 | 다음 |

비교 지표: 구간별 p95(조회·진입·폴링·좌석·선점·결제), 선점 409 비율, 결과 분포(확정·매진·포기·이탈), 진입 요청 수와 초당 최대 요청 수, Gateway·서버 CPU(Grafana). 표는 `compare.py`가 만든다.

LLM이 응답 3-3절에 적은 예측도 측정으로 맞는지 본다: 오픈 직후 1~3초에 진입이 더 뾰족하게 몰린다, 409와 재시도가 VIP 구역에 몰린다, 선점 뒤 이탈한 좌석이 5분 뒤 풀리며 두 번째 파도가 온다, 오픈 전 상세 조회·인증 요청의 정점이 균일 부하보다 높다.

### 5-1. 실행 순서

약 70분 걸린다. 측정 모드 켜고 끄기와 측정 키 옮기기는 측정자 본인이 한다([`loadgen.md`](../../guides/loadgen.md) 4·5·8절). 발생기 명령은 [`loadtest/k6/README.md`](../../../loadtest/k6/README.md) "배포 서버 측정"의 O1·A0 명령이 정본이다.

| # | 어디서 | 할 일 |
|---|---|---|
| 1 | 팀 채널 | `[발생기 사용 시작] <이름> / O1 균일·Synthetic, A0 / 약 70분, 이 동안 배포 금지` |
| 2 | 배포 서버 | `script/loadtest/measure-mode.sh status`로 다른 사람이 켜지 않았는지 보고 `MEASURER=<이름> script/loadtest/measure-mode.sh on` |
| 3 | 노트북 | 서버 `~/iseonjwa/.env.measure`를 발생기 `~/<이름>/iseonjwa/.env`로 옮기고 `chmod 600`(예: `scp -3`). 키 내용은 열지 않는다 |
| 4 | 배포 서버 | Mock PG 승인 지연 300ms를 한 번 건다(k6 README "Mock PG 장애 주입"). 두 O1 사이에 앱을 다시 띄우지 않는다 |
| 5 | 배포 서버 | O1 균일용 회차: `script/deploy/seed-demo.sh open "$(date -u -d '+10 minutes' +%Y-%m-%dT%H:%M:%SZ)"`. 출력의 공연 id·새 회차 id와 OPEN_AT을 적는다 |
| 6 | 발생기 | O1 균일 실행(`USERS=3000 VUS=300`, `PRE_OPEN_SECONDS`는 OPEN_AT까지 남은 초, 오픈 뒤 900초). 약 25분 |
| 7 | 배포 서버·발생기 | 5·6을 새 회차로 한 번 더, `USERS_CSV=../data/o1-synthetic-3000.csv`를 더해 Synthetic 실행. 실행 전 `validate.py`로 CSV를 검증한다 |
| 8 | 배포 서버 | Mock PG 지연을 풀고(`mode: NONE`), A0용 이미 열린 회차: `seed-demo.sh open "$(date -u -d '-5 minutes' +%Y-%m-%dT%H:%M:%SZ)"` |
| 9 | 발생기 | A0 실행 → `a0-report.py`로 표 한 줄 |
| 10 | 발생기 | `compare.py --base <균일 raw> --synthetic <Synthetic raw>`로 비교표. 원자료(`results/`)는 커밋하지 않는다 |
| 11 | 배포 서버·발생기·팀 채널 | `measure-mode.sh off`, 발생기 `.env` 삭제, `[발생기 사용 끝] <이름> / O1·A0 / 결과 받음, .env 삭제함` |

결과는 6절에 측정 환경 기록표(서버·발생기 사양, 커밋 해시, 회차 id, 시각)와 함께 적고, 발표용 한 장은 `docs/presentation/performance/`에 둔다.

## 7. 한계

- 비율과 분포의 모수는 LLM 추정이다. 실제 서비스 로그로 맞춘 값이 아니다. LLM도 응답에서 그렇게 밝혔다.
- 같은 페르소나 안에서 필드는 서로 독립으로 뽑는다(예: 연타하는 사람이 결제도 빠르다는 상관은 페르소나를 나누는 것으로만 나타난다).
- 3,000명이면 대기열이 약 1분이면 비어 `queue_patience_s`가 거의 작동하지 않는다. LLM도 같은 점을 짚었다.
- 매크로 사용자는 넣지 않았다.
- 배포 서버가 EC2 한 대라 서비스·DB·Kafka가 같은 기기에서 CPU를 나눠 쓴다(ADR 0047).
