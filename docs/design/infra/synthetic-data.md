# Synthetic Data: LLM이 만든 가상 사용자로 오픈 피크 재기 (ISE-262)

발제 필수 항목 "가상 사용자 기반의 부하 테스트 시나리오 생성(Synthetic Data)"을 채운다. 발제가 요구하는 산출물은 셋이다: LLM에 쓴 프롬프트 원문, 생성한 Synthetic Data(CSV), 일반 부하 테스트 결과와 Synthetic Data 기반 결과의 비교. 재료와 도구는 [`loadtest/synthetic/`](../../../loadtest/synthetic/README.md)에 있다.

- 이력: ISE-28 "Synthetic Data 1차본"은 11/11에 취소됐다(대기열 담당 판단: 인기 회차 쏠림은 회차별 Redis 키가 따로라 Q1~Q3와 결과가 같고, 좌석 구역 쏠림은 좌석 담당 몫). 발제 필수 산출물이 저장소에 없어 11/13에 ISE-262로 다시 시작했다([판단 기록](../../ai-judgments/junhyun/2026-11-13-fill-presentation-gaps-restore-synthetic-data.md)).
- 지금까지의 k6 시나리오도 난수를 쓴다. 다만 모든 사용자가 같은 규칙으로 움직인다(예: O1은 진입을 오픈 뒤 10초 안에 고르게 흩고, 1석·2석 반반, 70%가 좌석 응답 앞쪽 10%에서 고른다). Synthetic Data는 사용자마다 행동이 다르다.

## 1. 트래픽 시나리오 (발제 Step 1, 팀 설계)

| 질문 | 우리 답 | 근거 |
|---|---|---|
| 언제 몰리나 | 평일 오후 8시 티켓 오픈 정각. 오픈 10분 전부터 상세 새로고침, 오픈 직후 몇 초 안에 대기열 진입이 몰림 | SA 2-2 P1(퇴근 후 PC로 대기) |
| 누가 어떻게 쓰나 | 퇴근 후 PC 팬, 친구와 2매, 새로고침 연타, 여러 기기 접속. 매크로는 범위 밖 | SA 1-1 문제 정의의 현재 대안(여러 기기, 새로고침 연타), 2-2 페르소나, 4-5 제외 범위(행동 기반 매크로 탐지) |
| 어디가 병목인가 | 좌석 배치도 조회(응답 약 830KB), 인기 구역 선점 경쟁(409와 재시도), 오픈 직후 대기열 진입, Gateway 인증 경로 | S1·K1·Q1·G1 배포 측정([`open-peak-scenarios.md`](open-peak-scenarios.md), [Gateway 발표 소스](../../presentation/2026-11-12-gateway-overload-source.md)) |

사용자 흐름은 O1과 같다: 상세 조회 → 대기열 진입 → 순번 폴링 → 입장 토큰 → 좌석 배치도 → 선점(1~4석) → 결제 → 확정 확인. 409면 대기열로 돌아가지 않고 좌석만 다시 고른다. 선점은 5분 유지된다.

## 2. LLM으로 만들기 (발제 Step 2)

- 프롬프트: [`o1-prompt.md`](../../../loadtest/synthetic/o1-prompt.md). 1절 시나리오, 시스템 조건(좌석 25구역·등급, 1인 4매, 입장 초당 50명, 측정 창 ±10분), CSV 열과 필드별 허용 범위, 분포를 적는 JSON 형식을 줬다. 공개 통계를 안다고 꾸며 내지 말고 추정은 추정이라고 밝히라고 했다.
- 응답: [`o1-response.md`](../../../loadtest/synthetic/o1-response.md)(원문). 모델·명령·해시는 [`loadtest/synthetic/README.md`](../../../loadtest/synthetic/README.md)의 생성 기록에 있다.
- 왜 LLM에게 행이 아니라 분포를 받았나: 측정에는 수천 명이 필요하고, 같은 데이터를 다시 만들 수 있어야 한다. LLM은 페르소나와 분포(JSON)와 표본 40행을 내고, 3,000명은 `generate.py`가 시드 고정으로 만든다. LLM도 응답에서 표본은 난수 생성기로 뽑은 것이 아니라며 생성기로 다시 뽑기를 권했다.

LLM이 낸 페르소나(비율과 성격 요약, 수치는 모두 LLM이 추정이라고 밝힘):

| 페르소나 | 비율 | 특징 |
|---|---|---|
| `office_pc_fan` 퇴근 후 PC 팬 | 28% | 오픈 5분 전쯤 접속, 정각 진입, VIP 45%, 409면 같은 등급에서 다시 |
| `pair_buyer` 친구와 2매 | 18% | 항상 2석, 고르는 시간과 결제가 느림, 409 뒤 등급을 바꾸는 비율이 높음 |
| `refresh_spammer` 새로고침 연타 | 12% | 3~6초 간격 새로고침, 진입 2~5번 연타, 재시도 4~5번 |
| `mobile_commuter` 퇴근길 모바일 | 12% | 오픈 직전·직후 접속, 느린 선택·결제, 대기가 길면 일부 떠남 |
| `late_casual` 오픈 뒤 일반 관심층 | 10% | 오픈 30초~10분 뒤 접속, 등급을 덜 가림, 쉽게 포기 |
| `vip_hunter` VIP 고집 팬 | 8% | VIP만, 4매 60%, 409 뒤에도 VIP에서 끝까지 |
| `multi_device` 여러 기기 접속 | 7% | 한 계정이 여러 기기에서 새로고침·진입 |
| `browse_only` 구경만 하는 사람 | 5% | 85%는 진입하지 않음 |

LLM이 계산해 둔 전체 성질: VIP(전체 좌석의 20%)를 노리는 사용자가 약 42%, 진입 요청이 사용자 수의 약 1.6배. 둘 다 아래 3절에서 생성 데이터로 다시 센다.

## 4. k6 연동 (발제 Step 3)

O1(`loadtest/k6/scenarios/o1-open-peak.js`)이 `USERS_CSV`를 받으면 행마다 다른 프로필로 움직이고, 없으면 지금과 같은 균일 프로필로 움직인다. 두 모드는 같은 상태 기계를 쓴다. 비교에서 다른 것은 사용자 행동뿐이다.

| CSV 열 | O1에서 쓰는 곳 |
|---|---|
| `arrive_s`, `refresh_s` | 첫 접속 시각(오픈 기준), 오픈 전 상세 새로고침 간격 |
| `enter_delay_ms`, `enter_clicks` | 진입 시각, 진입 요청 횟수(2 이상은 연타 태그 `click=dup`, 0은 진입 안 함) |
| `queue_patience_s` | 대기 중 이 시간이 지나면 폴링을 멈추고 떠남(`left_queue`) |
| `seats`, `zone`, `think_ms` | 한 번에 고를 좌석 수, 노리는 등급(VIP·R·S·ANY), 첫 선택까지 시간 |
| `max_retry`, `on_conflict` | 409 뒤 다시 고르는 횟수, 같은 등급·아무 곳·포기 |
| `abandon_after_hold`, `pay_delay_s` | 선점 뒤 결제하지 않고 떠남, 결제까지 시간 |

지표의 `step_duration`과 `o1_outcomes`에 `persona` 태그가 붙는다(균일 모드는 `uniform`). 선점(`step_duration{step:hold}`)에는 처음 노린 등급 `zone`(균일은 `ANY`)과 응답 코드 `code`가 더 붙는다. CSV에 축 열(4-1)이 있으면 두 지표에 `ax_*` 태그 6개가 더 붙는다.

### 4-1. 행동 축 (페르소나 세분화)

이름 붙은 페르소나 8개만으로는 결과를 "어느 유형이 안 됐나"까지만 읽을 수 있다. 한 페르소나 안에 여러 행동이 섞여 있어서, 409나 지연을 어떤 행동이 만들었는지 가를 수 없다. 그래서 필드 12개를 행동 축 6개로 묶고, 사용자마다 축별 점수(0~1)를 매겨 3구간(0 낮음, 1 중간, 2 높음)으로 나눈다. 3구간이면 조합은 3^6 = 729칸이다.

| 축(CSV 열) | 0점 쪽 | 1점 쪽 | 담당 필드와 0점·1점 기준 |
|---|---|---|---|
| 도착 이른 정도(`ax_arrival`) | 오픈 뒤 도착, 새로고침 없음 | 10분 전 도착, 3초 간격 | `arrive_s` +600 → −600, `refresh_s` 60 → 3(0은 0점) |
| 진입 공격성(`ax_entry`) | 늦게 한 번 | 즉시 연타 | `enter_delay_ms` 30,000 → 200(로그), `enter_clicks` 1 → 4(0번은 이 축에서 뺌) |
| 좌석 욕심(`ax_demand`) | 1석, 아무 등급 | 4석, VIP | `seats` 1 → 4, `zone` ANY 0 · S 0.25 · R 0.5 · VIP 1 |
| 결정 속도(`ax_speed`) | 느림 | 빠름 | `think_ms` 30,000 → 300(로그), `pay_delay_s` 280 → 3(로그) |
| 집착도(`ax_persistence`) | 409면 바로 포기 | 끝까지 재시도·대기 | `max_retry` 0 → 5, `on_conflict` give_up 0 · any_zone 0.5 · same_zone 1, `queue_patience_s` 30 → 900(0은 끝까지 기다림이라 1점) |
| 구매 의지(`ax_intent`) | 구경만 | 반드시 결제 | `enter_clicks` 0이면 0점, `abandon_after_hold` 1이면 0점 |

- 축 점수는 담당 필드 점수의 평균이다. 구간 경계는 1/3과 2/3이다.
- 필드 하나는 축 하나만 정한다. 그래야 축 구간별 차이를 그 축의 효과로 읽을 수 있다. 예외는 `enter_clicks` 하나다(구매 의지가 진입 여부를, 진입 공격성이 횟수를 본다). 이 규칙은 테스트가 지킨다.
- 시간 필드는 로그로 잰다. 수백 ms와 수십 초가 섞여 있어서, 직선으로 재면 짧은 쪽 차이가 모두 1 근처에 뭉친다.
- 행동은 바꾸지 않는다. 이미 뽑은 값에서 계산만 하고 난수를 쓰지 않는다. 그래서 축 열을 넣은 뒤에도 기존 14열은 넣기 전 CSV와 바이트 단위로 같다(2026-11-13 확인).
- 규칙의 정본은 `persona_spec.py`의 `AXES`다. k6는 CSV의 구간 값을 태그로 옮기기만 하고 다시 계산하지 않는다. `validate.py`는 축 열이 필드 값으로 다시 계산한 값과 같은지 본다.

`o1-synthetic-3000.csv`의 축별 인원(낮음/중간/높음, 2026-11-13 생성):

| 축 | 낮음 | 중간 | 높음 |
|---|---|---|---|
| 도착 이른 정도 | 480 | 749 | 1,771 |
| 진입 공격성 | 1,151 | 1,352 | 497 |
| 좌석 욕심 | 1,081 | 952 | 967 |
| 결정 속도 | 1,072 | 1,823 | 105 |
| 집착도 | 444 | 669 | 1,887 |
| 구매 의지 | 72 | 353 | 2,575 |

729칸 중 202칸이 채워졌다. 칸당 평균은 4명꼴이라 칸 하나하나는 분석 단위가 되지 못한다. 그래서 `compare.py`는 축별 구간(9절)과, 고른 2축인 좌석 욕심 × 집착도(10절)만 표로 낸다.

축 점수를 새 분포로 다시 뽑는 방식(원형 8개를 중심점으로 두고 잡음을 더하는 혼합 생성)도 검토했다. 시뮬레이션해 보니 잡음 표준편차 0.15일 때 채워진 칸이 200칸으로, v1을 점수화만 한 것과 비슷했다. 부족한 것은 데이터의 다양성이 아니라 분석 관점이라고 보고, 지금은 점수화만 한다([판단 기록](../../ai-judgments/kangmin/2026-11-13-synthetic-persona-six-factors.md)).

## 5. 비교 측정 계획

| 항목 | 균일 O1 | Synthetic O1 |
|---|---|---|
| 대상 | 배포 서버(`m7i.xlarge` 1대, 측정 모드), 발생기 `c6i.xlarge`, 사설 IP | 같음 |
| 사용자 | 3,000명, VU 300 | `o1-synthetic-3000.csv` 3,000명, VU 300 |
| 시간 | 오픈 전 600초, 오픈 뒤 900초 | 같음 |
| 회차 | 실행마다 새 15,000석 회차(`seed-demo.sh open`) | 같음 |
| PG | Mock PG 승인 지연 300ms(서버 안에서 한 번 주입, 두 실행 사이 재시작 없음) | 같음 |
| 순서 | 먼저 | 다음 |

비교 지표: 구간별 p95(조회·진입·폴링·좌석·선점·결제), 선점 409 비율(전체·등급별), 결과 분포(확정·매진·포기·이탈), 진입 요청 수와 API별 초당 최대 요청 수, 오픈 뒤 1분 구간별 선점 결과, Gateway·서버 CPU(Grafana). 표는 `compare.py`가 만든다(1~8절). 행동 축 구간별 결과와 좌석 욕심 × 집착도 409 비율은 9·10절이다(4-1).

LLM이 응답 3-3절에 적은 예측도 측정으로 맞는지 본다: 오픈 직후 1~3초에 진입이 더 뾰족하게 몰린다, 409와 재시도가 VIP 구역에 몰린다, 선점 뒤 이탈한 좌석이 5분 뒤 풀리며 두 번째 파도가 온다, 오픈 전 상세 조회·인증 요청의 정점이 균일 부하보다 높다.

### 5-0. 측정 전에 고정한 판정 기준

측정 결과를 보고 기준을 고르지 않도록 기준을 먼저 적는다. 기준값을 바꾸려면 측정 전에 이 표를 고치는 PR을 먼저 올린다. 기준값은 이 문서가 정한 초안이고, 근거가 없는 값은 근거 칸에 그렇게 적었다.

**측정 유효성**: 하나라도 어기면 그 실행은 버리고 다시 잰다. 버린 실행과 이유도 6절에 적는다.

| 조건 | 기준 | 보는 곳 | 근거 |
|---|---|---|---|
| 발생기 여유 | 발생기 CPU 80% 이하, 메모리 90% 이하 | 실행 중 발생기에서 `docker stats` | 발생기가 막히면 서버 한계와 섞인다([`loadgen.md`](../../guides/loadgen.md) 문제 표) |
| 행동 시각 지연 | `action_lateness` p95 1,000ms 이하 | O1 요약 | 한 VU가 여러 사용자를 차례로 돌려 느린 요청이 다른 사용자의 행동을 늦춘다. 1초는 초안 값이다 |
| 환경 고정 | 두 O1 사이에 배포·재시작 없음, 같은 Mock PG 지연 | 팀 채널 공지, `docker ps`의 시작 시각 | 비교에서 다른 것은 사용자 행동뿐이어야 한다 |
| A0 요청 수 | 정확히 `VUS × ITERATIONS`(1,000)건, 409 0건 | k6 임계값(종료 코드 99), `a0-report.py` 판정 열 | 409는 준비한 좌석·사용자가 겹쳤다는 뜻이다 |

**정합성**: 하나라도 어기면 성능 수치보다 먼저 원인을 찾는다.

| 조건 | 기준 | 보는 곳 |
|---|---|---|
| 중복 판매 | 0건(같은 좌석의 확정 예매가 둘 이상인 경우 없음) | O1 teardown이 출력하는 대사 SQL |
| 결제 승인 = 확정 | 확정 예매 수 = `SOLD` 좌석 수 = 결제 승인 수 | 대사 SQL, 결제 DB |
| 처리하지 못한 오류 | O1 `o1_outcomes{outcome:error}` 0건, A0 오류율 1% 미만 | k6 임계값 |

**비교**: 균일과 Synthetic의 차이에는 합격선을 두지 않는다. 같은 서버에서 무엇이 얼마나 달라졌는지가 결과다. 처리량에도 고정 목표를 두지 않는다(SA 3장, 결정 #47: 고정 200/sec 대신 같은 환경의 전·후 비교와 포화점).

**LLM 예측 판정**: 5절의 예측 네 가지를 지표 하나씩에 묶는다. 어느 쪽으로 나와도 결과다. 맞지 않으면 "LLM 예측과 다름"으로 적고 이유를 추정한다.

| LLM 예측 | 맞았다고 보는 조건 | 지표(`compare.py` 절) |
|---|---|---|
| 오픈 직후 진입이 더 뾰족하게 몰린다 | Synthetic `queue_enter` 초당 최대가 균일보다 크다 | 6절 API별 초당 최대 |
| 409와 재시도가 VIP에 몰린다 | 처음 VIP를 노린 선점의 409 비율이 전체 선점의 409 비율보다 크다 | 8절 처음 노린 등급별 선점 409 비율 |
| 선점 뒤 이탈한 좌석이 5분 뒤 풀리며 두 번째 파도가 온다 | 오픈 뒤 300~420초 구간의 선점 201이 240~300초 구간보다 많다 | 7절 1분 구간별 선점 결과 |
| 오픈 전 상세 조회 정점이 균일보다 높다 | Synthetic `concert_detail` 초당 최대가 균일보다 크다 | 6절 API별 초당 최대 |

Note: 두 번째 파도는 선점 만료 스케줄러가 돌아야 생긴다. 스케줄러는 설정이 없으면 켜진다(`seathold.expiry.enabled`, `matchIfMissing = true`). 측정 모드에서 끄지 않았는지 측정 전에 확인한다.

**반복**: A0는 1분 안에 끝나므로 세 번 재고, 처리량이 가운데인 실행을 대표값으로 쓴다(세 줄 모두 6절에 남긴다). O1은 한 번에 약 25분이라 균일·Synthetic 각 한 번이다. 반복이 없다는 점을 한계에 적는다.

### 5-1. 실행 순서

약 75분 걸린다. 시작 전에 5-0의 기준을 다시 읽는다. 측정 모드 켜고 끄기와 측정 키 옮기기는 측정자 본인이 한다([`loadgen.md`](../../guides/loadgen.md) 4·5·8절). 발생기 명령은 [`loadtest/k6/README.md`](../../../loadtest/k6/README.md) "배포 서버 측정"의 O1·A0 명령이 정본이다.

| # | 어디서 | 할 일 |
|---|---|---|
| 1 | 팀 채널 | `[발생기 사용 시작] <이름> / O1 균일·Synthetic, A0 / 약 70분, 이 동안 배포 금지` |
| 2 | 배포 서버 | `script/loadtest/measure-mode.sh status`로 다른 사람이 켜지 않았는지 보고 `MEASURER=<이름> script/loadtest/measure-mode.sh on` |
| 3 | 노트북 | 서버 `~/iseonjwa/.env.measure`를 발생기 `~/<이름>/iseonjwa/.env`로 옮기고 `chmod 600`(예: `scp -3`). 키 내용은 열지 않는다 |
| 4 | 배포 서버 | Mock PG 승인 지연 300ms를 한 번 건다(k6 README "Mock PG 장애 주입"). 두 O1 사이에 앱을 다시 띄우지 않는다 |
| 5 | 배포 서버 | O1 균일용 회차: `script/deploy/seed-demo.sh open "$(date -u -d '+10 minutes' +%Y-%m-%dT%H:%M:%SZ)"`. 출력의 공연 id·새 회차 id와 OPEN_AT을 적는다 |
| 6 | 발생기 | O1 균일 실행(`USERS=3000 VUS=300`, `PRE_OPEN_SECONDS`는 OPEN_AT까지 남은 초, 오픈 뒤 900초). 약 25분. 실행 중 다른 창에서 `docker stats`로 발생기 CPU·메모리를 본다 |
| 7 | 배포 서버·발생기 | 5·6을 새 회차로 한 번 더, `USERS_CSV=../data/o1-synthetic-3000.csv`를 더해 Synthetic 실행. 실행 전 `validate.py`로 CSV를 검증한다 |
| 8 | 배포 서버 | Mock PG 지연을 풀고(`mode: NONE`), A0용 이미 열린 회차: `seed-demo.sh open "$(date -u -d '-5 minutes' +%Y-%m-%dT%H:%M:%SZ)"` |
| 9 | 발생기 | A0를 새 회차로 세 번 실행 → `a0-report.py`에 요약 세 개를 넘겨 표 세 줄(판정 열 포함) |
| 10 | 발생기 | `compare.py --base <균일 raw> --synthetic <Synthetic raw>`로 비교표. 원자료(`results/`)는 커밋하지 않는다 |

## 6. 결과

측정 전이다. 측정은 ISE-264에서 한다(2026-11-13 사용자 결정: 이번에는 방법과 자료만 준비).

측정하면 이 순서로 채운다.

1. 측정 신뢰도 네 줄: 실행 횟수와 대표값 고르는 법, 측정 환경(서버·발생기 사양, 커밋 해시, 회차 id, 시각), 버린 실행과 이유, 5-0 유효성 조건 결과.
2. 정합성 표: 5-0 정합성 조건마다 기준과 실제 값.
3. `compare.py` 출력 1~10절과 `a0-report.py` 표.
4. LLM 예측 판정 표: 예측마다 맞음·다름과 실제 값.
5. 차이의 원인 추정과 대가: 수치가 왜 달라졌는지, 우리가 무엇을 바꿔야 하는지(또는 바꾸지 않는 이유).

## 7. 한계

- 비율과 분포의 모수는 LLM 추정이다. 실제 서비스 로그로 맞춘 값이 아니다. LLM도 응답에서 그렇게 밝혔다.
- 같은 페르소나 안에서 필드는 서로 독립으로 뽑는다(예: 연타하는 사람이 결제도 빠르다는 상관은 페르소나를 나누는 것으로만 나타난다).
- 행동 축의 0점·1점 기준과 묶는 방식(4-1)은 LLM이 아니라 사람이 정한 초안이다. 기준을 바꾸면 구간 인원이 달라진다. 축별 결과(`compare.py` 9·10절)는 사용자 단위 결과다. 한 축의 비율이 서버 지연을 얼마나 바꾸는지(시스템 효과)는 축 비율을 바꾼 실행을 여러 번 해야 가를 수 있다.
- 3,000명이면 대기열이 약 45초면 비어 `queue_patience_s`가 작동하지 않는다. 인내 시간이 있는 사람 중 가장 짧은 값이 30초이고, 그런 페르소나(`late_casual`, `browse_only`)는 줄이 빈 뒤에 들어온다. `o1-synthetic-3000.csv`로 입장 순서를 계산하면 이탈자는 0명(폴링 지연 10초를 더해도 2명)이다. 그래서 이번 비교에서는 대기 취소·이탈 판정이 없는 대가(떠난 사람이 쓰는 입장 자리)가 0이다. LLM도 같은 점을 짚었다. 줄이 더 길어도 이 대가는 작다. 입장은 매초 순번 커서(`admitted`)를 초당 입장 인원만큼 올리는 방식이라(`admit.lua`) 떠난 사람의 순번도 그대로 지나가고 그 자리만 빈다. 떠난 사람 한 명마다 뒤 사람의 입장이 1 ÷ 초당 입장 인원(50/s면 0.02초)만큼 늦어진다. 같은 CSV로 입장 속도를 10/s로 낮춰 계산해도 이탈 약 137명, 마지막 사람의 추가 대기는 최대 약 14초다. 그래서 입장 속도를 바꾼 별도 실행은 하지 않고 이 계산으로 갈음한다(2026-11-14, ISE-268 댓글).
- 매크로 사용자는 넣지 않았다.
- 배포 서버가 EC2 한 대라 서비스·DB·Kafka가 같은 기기에서 CPU를 나눠 쓴다(ADR 0047).
- O1은 균일·Synthetic 각 한 번만 잰다. 실행 사이 편차는 A0 세 번의 편차로만 짐작한다.
