## 1. 요약

추천 방향은 "추첨 당첨을 시스템이 대신 선점한 일반 예매로 다룬다"이다.

- 당첨자에게 일반 예매와 같은 예매(HELD, `source=LOTTERY`)를 만들고 같은 결제 경로로 보낸다. 확정·만료·늦은 승인 환불(E8)·예매당 결제 1개(ADR 0026)를 새로 만들지 않는다.
- 추첨에만 있는 로직은 응모, 순위 계산, 좌석 배정, 예비 승계 네 가지로 좁힌다.
- 모든 단계의 상태는 DB 행에 있고 조건부 UPDATE로 바꾼다. 서버가 죽어도 다음 주기의 워커가 이어받는다.
- 측정으로 고를 것은 단순한 안을 기준선으로 둔다. 응모는 동기 INSERT로 시작하고 접수형(접수 행 + outbox)과 비교 측정한다(측정 시나리오 1).

이 방향으로 SA와 달라지는 곳이 네 군데 있다. 팀 확인이 필요하다. SA 반영은 결정이 모두 끝난 뒤 일괄로 한다(5절).
1. 응모를 동기 INSERT로 시작하면 SA 4-2 ③과 AI 검증 `#4`의 "응모 동기 처리 거부"를 측정 뒤 다시 본다(D3).
2. 추첨을 등급별(`UNIQUE(schedule_id, grade)`)에서 회차당 1개로 바꾼다. 비인기석(기본 S) 일부를 좌석 등급 `LOTTERY`로 미리 떼어 두고, 종결 때 원래 등급으로 되돌린다(D9). 그래서 기존 `UNIQUE(lottery_id, user_id)`가 그대로 "1인 1회차 1응모"가 된다(D2).
4. 추첨석이 미리 분리되어, 일반 오픈을 추첨 뒤로 미루는 시간 규칙이 좌석 보호에는 필요 없다(D9).
3. 응모 상태에 `CANCELED`(마감 전 취소)와 `WAITLISTED → LOST`(승계 마감)가 없다(D5, D14).

## 2. 큰 틀

### 2-1. 무엇을 증명하나
추첨은 기능 완성과 함께 측정 시나리오 3종으로 숫자를 남긴다(ADR 0036). 각 결정이 어느 시나리오로 검증되는지는 6절에 있다.

| 시나리오 | 질문 |
|---|---|
| 1. 응모 마감 직전 몰림 | 동기 INSERT로 초당 100건을 버티나. 버티지 못하는 지점은 어디인가 |
| 2. 자동결제 폭주 | 2,000건 자동결제가 다른 회차 일반 결제를 503으로 만들지 않나 |
| 3. 일반 예매 간섭 | 추첨·자동결제 중에 다른 회차 선점 p95가 20% 넘게 늘면 lottery를 서비스로 분리한다(SA 7-1) |

### 2-2. 위치
lottery는 Reservation 서비스 안 모듈이다(SA 7-1, 결정 기록 `#18`). reservation 모듈은 직접 호출할 수 있다(`#14`). 결제는 `payment.command`·`payment.result` 이벤트로만 만난다.

```
[Gateway] ─ 응모·조회 API ─▶ [Reservation]
                               ├─ lottery 모듈: 응모, 순위, 배정 워커, 승계
                               ├─ reservation 모듈: 예매 HELD 생성(재사용), 확정·만료(재사용)
                               └─ outbox ─▶ Kafka ─▶ [Payment] 빌링키 결제 ─▶ PG
                                  ▲                       │
                                  └──── payment.result ◀──┘
```

### 2-3. 전체 흐름과 시간
`T` = 추첨 시각(`draw_at`).

| 시각 `[가정]` | 단계 | 누가 | 결과 |
|---|---|---|---|
| 응모 기간 3일 | 응모·취소 | 응모 API | `lottery_entries` ENTERED·CANCELED |
| `entry_end_at` | 마감 | 마감 스케줄러 | 추첨 OPEN → CLOSED. 응모 API는 DB `now()`로 늦은 응모를 막는다 |
| T ~ T+10초 | 추첨 | 추첨 스케줄러 | 시드로 순위 계산, WON·WAITLISTED·LOST, 추첨 DRAWN |
| T+10초~ | 배정 | 배정 워커 | 당첨자마다 예매 HELD + `BillingPaymentRequested`(outbox) |
| ~T+4분 | 자동결제 | Payment | 동시 3, 초당 약 10건 → 2,000건 약 3.3분 |
| ~T+25분 | 늦은 확정 | 결제 재확인 스케줄러 | UNKNOWN 재조회 최장 약 21분(SA 9-4) |
| 결제 결과마다 | 확정·실패 | `payment.result` 소비자 | PAID 또는 FAILED |
| 실패 뒤 1초 안 | 승계 | 승계 워커 | 남은 좌석만큼 다음 예비자를 WON으로(D13) |
| T+30분 | 승계 마감 | 승계 마감 스케줄러 | 남은 WAITLISTED → LOST, 새 승계 없음 |
| ~T+60분 | 종결 | 종결 스케줄러 | 마지막 당첨 예매의 선점 만료(30분)까지 끝나면 추첨 DONE |
| ~T+60분 | 종결·반환 | 종결 스케줄러 | 추첨 DONE과 같은 트랜잭션에서 `LOTTERY` 좌석을 원래 등급으로 되돌린다. 남은 좌석은 일반 판매로 나온다 |

추첨석은 설정 때 떼어 두므로(D9) 일반 오픈 시각은 이 표에 묶이지 않는다. SA 4-3의 순서(추첨 뒤 일반 오픈)를 운영 정책으로 둘지는 팀이 정한다. 근거 계산은 [details.md](details.md) 5절에 있다.

### 2-4. 상태
SA 8-2 기준에 제안을 더했다. 굵은 글씨가 추가분이다.

```
추첨   OPEN → CLOSED → DRAWN → DONE          (시작 전은 entry_start_at 시각으로 판정, 상태를 늘리지 않음)
응모   ENTERED → WON | WAITLISTED | LOST
       ENTERED → CANCELED                   (추가: 마감 전 취소, 재응모 불가, D5)
       WAITLISTED → WON                      (승계)
       WAITLISTED → LOST                     (추가: 승계 마감, D14)
       WON → PAID | FAILED
       WON → WON (새 예매로 1회 재시도)        (추가: NOT_SENT 실패, D12)
예매   일반 예매와 같다. source = LOTTERY, hold_expires_at = 생성 + 30분
```

SA의 `(REQUESTED: 응답 상태)`는 D3에서 동기 INSERT를 고르면 없어진다.

### 2-5. 설계 원칙
| 원칙 | 적용 | 감수하는 것 |
|---|---|---|
| 일반 예매 경로를 재사용한다 | 당첨 예매도 매수 한도·좌석 조건부 UPDATE·부분 유니크·만료·E8 환불을 그대로 거친다 | reservation 모듈에 "시스템 선점" 진입점과 `source` 분기가 필요하다. 예매 흐름 담당 코드에 손이 간다 |
| 상태의 기준은 DB 행이다 | 단계마다 조건부 UPDATE, 워커가 `SKIP LOCKED`로 이어받는다. 순위는 시드에서 결정적으로 계산된다 | 스케줄러·워커가 6개가 된다(details.md 4절) |
| 단순한 기준선부터 측정한다 | 응모 동기 INSERT, 빌링키 확인은 결제 시점부터 | SA와 다른 출발점이라 팀 확인이 필요하다 |
| 좌석은 할당으로, 결제는 자원으로 나눈다 | 추첨석을 설정 때 `LOTTERY` 등급으로 떼어 두고 일반 선점은 잡지 않는다. 자동결제는 전용 PG 자리(`pg-billing`)를 쓴다 | 일반 선점 쿼리에 조건이 하나 늘고 반환 작업이 생긴다. 결제 쪽 설정·토픽이 하나 늘어난다 |

## 4. 구현 순서
앞 단계는 좌석 선점·결제 코드가 없어도 만들 수 있다. "추첨 구현을 M2로 당길지"는 아직 정하지 않았다. 당긴다면 범위는 1단계다.

| 단계 | 내용 | 의존 | 검증 |
|---|---|---|---|
| 1 | 테이블 마이그레이션, 설정 API, 응모·취소·결과 조회 API, 순위·배정 계산(순수 도메인), 마감·추첨 스케줄러 | 공통 모듈만 | 단위 테스트(순위 재현, 매수 건너뛰기), 측정 시나리오 1 |
| 2 | 배정 워커(시스템 선점), `payment.result` 소비자 분기 훅 | 좌석 선점·예매 확정 코드(M2) | 통합 테스트: 당첨 → 예매 HELD → Mock 결제 결과 → PAID·FAILED |
| 3 | `BillingPaymentRequested` 발행, 승계, 승계 마감·종결 | 결제 빌링키·자동결제(M4) | 측정 시나리오 2·3, 장애 주입 |
| 4 | 빌링키 사본(D4 2단계), 확장안: 시드 약속(D7), 재응모 허용(D5) | 결제 빌링키 이벤트 | 시나리오 1 재측정 |

## 6. 측정과 결정의 연결
| 시나리오 | 검증하는 결정 | 바뀔 수 있는 것 |
|---|---|---|
| 1 | D2, D3, D4 | p95가 300ms를 넘거나 포화점이 초당 100건 아래면 접수 행 + outbox로 바꾼다 |
| 2 | D6, D10, D14 | 10분 안 95%를 못 지키면 `pg-billing` 동시 수를 늘린다. PG 전체 한도가 막으면 일반 결제와 시간 분리 |
| 3 | D8, D9, D10 | 추첨 시각 정책(저트래픽 시간대)을 어겨 겹친 경우를 잰다. 선점 p95가 20% 넘게 늘면 배정 워커 속도 제한, 그래도 넘으면 추첨 시간대 예매 차단 또는 lottery 분리(SA 7-1) |

## 7. 확인하지 못한 것
- PostgreSQL 단건 INSERT의 로컬 처리량. 초당 100건이 쉽다고 예상하지만 측정 전이다(시나리오 1에서 확인할 질문).
- 30,000행 순위 갱신을 한 트랜잭션으로 10초 안에 끝낼 수 있는지.
- 토스 테스트 모드의 빌링 API 동시 호출 한도와 실제 빌링키 결제 응답 시간. 측정은 Mock PG로 하므로 테스트 모드에 붙일 때 확인한다(D6).
- payment-service 인스턴스 수와 `payment.billing` 파티션 수. Bulkhead 동시 수는 인스턴스당이고 리스너 동시성은 파티션 수를 넘지 못한다(D6).
- 예매 흐름 담당의 `payment.result` 소비자 구조(아직 코드가 없다. reservation-service는 패키지 뼈대만 있다).
