# 추첨 숫자 기준과 측정 설계

상태: 숫자 기준 채택(2026-10-29, 사용자 결정 D1). 측정 시나리오 상세는 작성 중. 숫자는 모두 `[가정]`이며 기준선 측정 뒤 바꾼다. 바꿀 때는 이유를 이 문서 끝 이력에 남긴다.

설계 순서는 "숫자 기준 먼저"다. 타임아웃·용량·마감을 먼저 정해야 상태 전이와 실패 처리의 시간 조건을 쓸 수 있다.

## 1. 숫자 기준

### 1-1. 규모 (회차 1개 기준)

| 항목 | 값 `[가정]` | 근거 |
|---|---|---|
| 회차 좌석 | 15,000석 | SA 3-2, 12-9 (KSPO DOME 규모) |
| 추첨 배정 비율 | 20% → **3,000석** | 차별화 기능이지만 일반 예매(Must)가 주 판매 경로 |
| 1인 응모 매수 | 1–2매, 평균 1.5매 | SA 4-3 규칙 초안 "등급별 1–2매" |
| 당첨자 수 | 3,000 ÷ 1.5 = **2,000명** | |
| 응모자 수 | **30,000명** (사람 기준 경쟁률 15:1) | SA 3-2 참고 수치(동시 접속 수십만~백만)보다 작게, 로컬 측정 가능한 규모 |
| 예비자 수 | 당첨자의 50% = **1,000명** | 승계 대상. 실패율보다 충분히 크게 |
| 자동결제 실패율 | 5% → 약 **100건** | 카드 한도·빌링키 무효 등. Mock PG 장애 주입으로 조절 |

### 1-2. 시간

| 항목 | 값 `[가정]` | 근거 |
|---|---|---|
| 응모 기간 | 3일 | SA 4-3 "응모 기간 → 마감 → 추첨 → 일반 오픈" |
| 마감 직전 몰림 | 마지막 1분에 응모의 20%(6,000건) → **초당 100건** | 마감 직전에 몰린다는 SA 4-3·결정 기록 #39 근거를 숫자로 |
| 추첨 실행 시간 상한 | **10초** | 응모 30,000행 정렬·시드 셔플·배정. 넘으면 배치 쿼리 설계를 다시 본다 |
| 자동결제 완료 목표 | 추첨 후 **10분 이내** 95% 확정 | 사용자가 결과를 기다리는 시간 상한 |
| 승계 마감 | 추첨 후 **30분** | 이후 남은 좌석은 일반 판매로 반환 |
| 일반 예매 오픈 | 추첨석 분리로 시간 제약 없음(D9, 10/29) | 처음 값은 "추첨 후 1시간 이상"이었다. 추첨 뒤 오픈을 운영 정책으로 둘지는 팀이 정한다(SA 4-3) |

### 1-3. 결제 용량 (결제 설계 `pg-integration.md` 5절과 맞춤)

| 항목 | 값 `[가정]` | 근거 |
|---|---|---|
| Mock PG 승인 응답 | 평균 300ms | 측정 전 가정. 장애 주입으로 지연을 늘려 본다 |
| 일반 결제 `pg-approve` Bulkhead | 동시 10, 대기 0 | 결제 설계 확정값(가정). 허가를 못 얻으면 503 `PG_UNAVAILABLE` |
| 자동결제가 `pg-approve`를 같이 쓰면(기준선, D6 10/31) | 겹치지 않으면 동시 10 → 초당 약 33건 → 2,000건 약 **1분**. 다른 회차 일반 결제와 겹치면 자리 10개를 자동결제가 채워 **일반 결제가 즉시 503** | 측정 시나리오 2에서 재현할 문제 |
| 개선 후보: 자동결제 전용 동시 수 | 동시 3 → 초당 약 10건 → 2,000건 약 **3.3분** | 시나리오 2 결과로 도입 여부를 정한다(D6 B) |

계산: 처리량 ≈ 동시 수 ÷ 응답 시간. 공유 10 ÷ 0.3초 = 초당 약 33건(2,000건 약 60초), 전용 3 ÷ 0.3초 = 초당 10건(2,000건 200초).

### 1-4. 겹침에 대한 메모
같은 회차 안에서는 추첨·자동결제와 일반 선점이 시간상 겹치지 않는다(SA 4-3). 그래서 측정 시나리오 3의 "간섭"은 **다른 회차·다른 공연의 일반 판매가 진행 중일 때 이 회차의 추첨·자동결제가 도는 경우**다. 서비스·DB·PG가 공유되므로 이 경우가 실제 위험이다. 운영 정책은 추첨 시각을 저트래픽 시간대로 권장하므로(D10, 10/30), 이 시나리오는 정책을 어겨 겹쳤을 때 얼마나 나빠지는지를 재서 정책과 워커 속도 상한의 근거로 쓴다.

## 3. 측정 결과

### 3-1. 추첨 실행 시간 (ISE-87, 2026-11-02)
- 조건: 응모 30,000행(1매·2매 반반), 추첨석 2,000석, 예비 1,000명. 로컬 Windows PC, 테스트용 PostgreSQL 17 컨테이너(tmpfs), `LotteryDrawServiceTest`에서 `LotteryDrawService.draw` 한 번의 시간만 잰다(응모 적재 시간 제외).
- 결과 8회: 4,508 · 515 · 481 · 4,600 · 504 · 593 · 4,440 · 446ms. 모두 상한 10초 안이다.
- 값이 약 0.5초와 약 4.5초 두 갈래로 나뉜다. 원인은 확인 못 했다. 확인할 질문: 갓 넣은 3만 행의 통계 갱신(autovacuum·ANALYZE)이 배치 UPDATE와 겹치는가, 테스트 컨테이너가 다른 테스트와 자원을 나누는가.
- 판단: 최악값도 상한의 절반 이하라 한 트랜잭션(D8 A안)을 유지한다. 배포 환경(EC2)에서 다시 재고, 연속 시간 초과(`lottery.draw.consecutive.failures`)가 나면 청크(B안)로 바꾼다.
- 측정 시나리오 1(마감 직전 초당 100건)과 그 결과로 정할 D3 전환·SA 반영은 부하 도구와 배포 환경이 필요해 측정 이슈(ISE-94)로 옮겼다(11/2 결정).

### 3-2. 로컬 사전 측정 (ISE-94, 2026-11-06)
- 조건: 로컬 compose 스택, 이미지 커밋 `b6d3ffd`. k6와 서비스가 같은 PC를 쓴다. 병목 위치를 찾는 값이고 서버 수치와 비교하지 않는다. 최종 수치는 배포 서버 + 같은 VPC 발생기에서 낸다.

자동결제(L2-a, 응모 2,000명, 추첨석 600석, 예비 100명, PG 지연 300ms):

| 항목 | 값 |
|---|---|
| 결제 완료 | 396건(600석), 요청 실패 0 |
| 추첨 뒤 첫 완료 / 마지막 완료 | 11.1초 / 138.6초 |
| 추첨 뒤 p95 | 132.1초 |
| 처리량 | 초당 3.10건 |

- 코드 확인: `payment.command` 소비자는 키 기반 순서 때문에 동시성 1이다(`PaymentCommandKafkaConfiguration`, `ConsumerContainerFactories`). PG 300ms면 계산 상한은 초당 약 3.3건이다.
- 1-3절의 "자리 10개를 자동결제가 채운다"는 가정과 다르다. 소비자 1개는 허가 1개만 쓴다.
- 확인할 질문 1: 초당 3.10건을 2,000건에 그대로 적용하면 95%까지 약 10.4분이다. 외삽한 값이다. 2,000건 자동결제가 서버에서 10분 안에 95%를 넘는가.
- 확인할 질문 2: 동시성 1에서 자동결제와 겹친 일반 결제의 503이 늘어나는가(L2-b, 미실행). 늘지 않으면 ADR 0039의 개선안은 전제부터 다시 본다.

응모 몰림(L1, 초당 100 → 200 → 400 → 800건, 단계별 60초). 시간은 ms다:

| 단계 | 응모 성공 p50 | 성공 p95 | 성공 p99 | 503 |
|---|---|---|---|---|
| 100 | 7.7 | 16.6 | 41.2 | 0 |
| 200 | 6.9 | 20.2 | 56.4 | 0 |
| 400 | 7.6 | 35.2 | 118.7 | 4,239 |
| 800 | 58.9 | 478.6 | 581.3 | 44,943 |

- 표는 단계의 앞 5초(속도를 올리는 구간)를 뺀 값이다. 전체로는 요청 100,384건 중 201이 50,860건, 503 `SERVICE_UNAVAILABLE`이 49,519건, 시나리오를 시작하지 못한 반복이 4건이다.
- 판정: 합격 기준인 초당 100건 p95 300ms 이하는 로컬에서 넘었다. 응모 행 48,553건 = 고유 사용자 48,553명으로 중복은 없다.
- 503은 시작 144초 뒤부터 나왔다. 응답 p50이 1.3ms로 빨라 서비스 처리 전에 거절된 것으로 보이나, 어디서 거절했는지는 확인 못 했다. 측정 직후 reservation-service 메모리는 509.7MiB / 512MiB였고 Zipkin 전송이 밀려 구간 1,145개가 버려졌다. 둘이 원인인지도 확인 못 했다.
- 측정하지 않은 것: L2-a 2,000건, L2-b, L3, 장애 주입.

- 150ms 진행 조회(PAID 누적, 30초 간격): 152 → 341 → 528 → 715 → 903 → 1,091 → 1,279 → 1,467 → 1,656 → 1,844. 증가분은 187~189건이고 (1,844 − 152) ÷ 270초 = 초당 6.27이다(계산값).
- 50ms 진행 조회(PAID 누적, 20초 간격): 121 → 432 → 752 → 1,070 → 1,394 → 1,711. 증가분은 311~324건이고 (1,711 − 121) ÷ 100초 = 초당 15.9다(계산값).

- 처리 속도는 세 점 모두 1 ÷ (PG 지연 + 약 10~16ms)다(계산값). 속도가 PG 지연에 거의 반비례한다. 덧붙는 시간이 세 점에서 같지 않고 150ms가 가장 작은 이유는 확인 못 함이다.
- 150ms 구간 지표: payment-service CPU 최대 17%, `pg-approve` 남은 자리 최소 9/10, DB 풀 대기 0, payment-service Kafka lag 최대 1,106. CPU·PG 허가·DB는 남는데 lag가 쌓였다.
- 결론(확정): `payment.command` 소비자 1개가 PG 응답을 직렬로 기다리는 것이 병목이다. 동시성은 `common/src/main/java/com/iseonjwa/common/messaging/consumer/ConsumerContainerFactories.java:26`의 `factory.setConcurrency(1)`이고, `payment-service`의 `PaymentCommandKafkaConfiguration.java:30`이 이 팩토리로 `payment.command` 리스너를 만든다. 3-2·3-3의 동시성 1 가설을 이 스윕으로 확정했다.

- 결제 결과 지표는 커밋된 뒤에 기록한다. 트랜잭션 안에서 세면 롤백 뒤 Kafka 재처리 때 같은 결과가 두 번 집계된다.
