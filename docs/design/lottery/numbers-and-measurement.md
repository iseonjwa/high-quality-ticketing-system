# 추첨 숫자 기준과 측정 설계

상태: 숫자 기준 채택(2026-10-29, 사용자 결정 D1). 측정 시나리오 상세는 작성 중. 숫자는 모두 `[가정]`이며 기준선 측정 뒤 바꾼다. 바꿀 때는 이유를 이 문서 끝 이력에 남긴다.

설계 순서는 "숫자 기준 먼저"다. 타임아웃·용량·마감을 먼저 정해야 상태 전이와 실패 처리의 시간 조건을 쓸 수 있다.

## 1. 숫자 기준

### 1-1. 규모 (회차 1개 기준)

| 항목 | 값 `[가정]` | 근거 |
|---|---|---|
| 회차 좌석 | 15,000석 | SA 3-2, 12-9 (KSPO DOME 규모) |
| 추첨 배정 비율 | 20% → **3,000석** | 차별화 기능이지만 일반 예매(Must)가 주 판매 경로 |
| 1인 응모 매수 | 1–2매, 평균 1.5매 | SA 4-3 규칙 초안 "등급별 1–2매" |
| 당첨자 수 | 3,000 ÷ 1.5 = **2,000명** | |
| 응모자 수 | **30,000명** (사람 기준 경쟁률 15:1) | SA 3-2 참고 수치(동시 접속 수십만~백만)보다 작게, 로컬 측정 가능한 규모 |
| 예비자 수 | 당첨자의 50% = **1,000명** | 승계 대상. 실패율보다 충분히 크게 |
| 자동결제 실패율 | 5% → 약 **100건** | 카드 한도·빌링키 무효 등. Mock PG 장애 주입으로 조절 |

### 1-2. 시간

| 항목 | 값 `[가정]` | 근거 |
|---|---|---|
| 응모 기간 | 3일 | SA 4-3 "응모 기간 → 마감 → 추첨 → 일반 오픈" |
| 마감 직전 몰림 | 마지막 1분에 응모의 20%(6,000건) → **초당 100건** | 마감 직전에 몰린다는 SA 4-3·결정 기록 #39 근거를 숫자로 |
| 추첨 실행 시간 상한 | **10초** | 응모 30,000행 정렬·시드 셔플·배정. 넘으면 배치 쿼리 설계를 다시 본다 |
| 자동결제 완료 목표 | 추첨 후 **10분 이내** 95% 확정 | 사용자가 결과를 기다리는 시간 상한 |
| 승계 마감 | 추첨 후 **30분** | 이후 남은 좌석은 일반 판매로 반환 |
| 일반 예매 오픈 | 추첨석 분리로 시간 제약 없음(D9, 10/29) | 처음 값은 "추첨 후 1시간 이상"이었다. 추첨 뒤 오픈을 운영 정책으로 둘지는 팀이 정한다(SA 4-3) |

### 1-3. 결제 용량 (결제 설계 `pg-integration.md` 5절과 맞춤)

| 항목 | 값 `[가정]` | 근거 |
|---|---|---|
| Mock PG 승인 응답 | 평균 300ms | 측정 전 가정. 장애 주입으로 지연을 늘려 본다 |
| 일반 결제 `pg-approve` Bulkhead | 동시 10, 대기 0 | 결제 설계 확정값(가정). 허가를 못 얻으면 503 `PG_UNAVAILABLE` |
| 자동결제가 `pg-approve`를 같이 쓰면 | 자리 10개를 자동결제가 채워 **일반 결제가 즉시 503** | 측정 시나리오 2의 핵심 문제 |
| 자동결제 전용 동시 수(안) | 동시 3 → 초당 약 10건 → 2,000건 약 **3.3분** | 10분 목표 안. D6에서 정함 |

계산: 처리량 ≈ 동시 수 ÷ 응답 시간 = 3 ÷ 0.3초 = 초당 10건. 2,000 ÷ 10 = 200초.

### 1-4. 겹침에 대한 메모
같은 회차 안에서는 추첨·자동결제와 일반 선점이 시간상 겹치지 않는다(SA 4-3). 그래서 측정 시나리오 3의 "간섭"은 **다른 회차·다른 공연의 일반 판매가 진행 중일 때 이 회차의 추첨·자동결제가 도는 경우**다. 서비스·DB·PG가 공유되므로 이 경우가 실제 위험이다. 운영 정책은 추첨 시각을 저트래픽 시간대로 권장하므로(D10, 10/30), 이 시나리오는 정책을 어겨 겹쳤을 때 얼마나 나빠지는지를 재서 정책과 워커 속도 상한의 근거로 쓴다.
