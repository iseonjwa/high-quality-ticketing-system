# 결제 불변 조건

결제 설계의 뼈대다. 어떤 장애에서도 지켜야 할 조건을 먼저 정하고, 각 조건을 어떤 장치가 지키는지, 그 장치가 무너지면 무엇이 잡는지를 연결한다. 기준 원칙은 하나다. **금전적 의무가 추적 없이 사라지지 않는다.**

- 기술이 있다고 안전하지 않다. 장치마다 맡는 실패가 다르게 하고, 한 장치만 맡는 실패는 5절에서 보강한다(2026-10-28 사용자 원칙).
- 다른 문서와 ADR은 이 문서의 ID(INV-n)로 참조한다. 시나리오 번호(E·N·FT)는 [failure-scenarios.md](failure-scenarios.md), 대사 규칙(RC-n)은 [ADR 0028](../../decisions/0028-payment-reservation-reconciliation.md)에 있다.
- INV-1~INV-7은 사용자가 정한 조건이다. INV-8·INV-9는 기존 결정(0017·0022, 0020·0024)을 같은 형식으로 정리한 보조 조건이며 새 요구를 더하지 않는다.
- 아직 구현 전이다. 아래 테스트는 설계 기대값이다.

## 2. 정의와 방어 수단

표의 "무너지는 경우"는 그 수단이 실패를 놓치는 조건이고, "그때 잡는 것"은 다음 방어선이다.

### INV-1 예매 하나에 승인된 결제는 하나뿐이다

| 수단 | 맡는 실패 | 무너지는 경우 | 그때 잡는 것 |
|---|---|---|---|
| `UNIQUE(reservation_id)` 전체(0025) | 다른 키·동시 요청·토큰 재사용으로 두 번째 결제 행 생성 | 마이그레이션 누락 | 마이그레이션 테스트(인덱스 존재 확인), 대사 RC-4 |
| 멱등 기록 PK와 `resource_id`(0016) | 같은 키 재시도의 새 결제 시도 | 기록 정리 오류 | 위 UNIQUE |
| 기존 결제 연결(0018) | 새 키 재요청의 PG 재호출 | 조회 누락 | TX1에서 UNIQUE 위반, 재조회 응답 |
| 결제 행당 승인 호출 1회, 복구는 조회 API만(0017, 0022) | 같은 주문 재승인 | 코드가 `approve`를 다시 부름 | PG 멱등키 `pg_order_id`(토스는 M4 확인), `UNIQUE(pg_tx_id)` |
| 조건부 전이(SA 8-4) | 두 경로가 같은 결제를 동시에 확정 | 행 수 확인 누락 | 대사 RC-7·RC-8 |
| Reservation의 중복 승인 환불(0026) | 위 방어를 모두 뚫은 두 번째 승인 | Reservation 규칙 누락 | 대사 RC-4 |

테스트: E2, N1, N13, N14, N17, FT-1~FT-4의 V1.

### INV-2 같은 결제 이벤트·명령이 다시 와도 추가 확정·추가 환불이 없다

| 수단 | 맡는 실패 | 무너지는 경우 | 그때 잡는 것 |
|---|---|---|---|
| `processed_event`(SA 10-4) | 14일 안의 재전달 | 정리 뒤 재전달 | 아래 업무 규칙 |
| 영향 행 1일 때만 후속 쓰기(INV-5) | 이미 지난 전이의 반복 | — | — |
| Reservation의 paymentId 대조(0026) | `PaymentApproved` 재전달로 확정 티켓 환불(C1) | 규칙 누락 | 같은 결제의 환불은 한 건(아래), 대사 RC-3 |
| `refund.payment_id` UNIQUE와 `INSERT … SELECT … ON CONFLICT`(0019) | `RefundRequested` 중복·DLQ 재처리 | — | PG 환불 멱등키 |
| 환불 워커 claim과 재호출 전 조회(0019, 0022) | 응답 유실 뒤 재호출, 토스 멱등키 15일 만료 뒤 재시도 | PG 조회가 오답 | PG 멱등키 `pg_refund_id`, PG의 취소 완료 결제 재취소 거절`[가정]` |
| Ops 명령은 PG 환불을 직접 부르지 않고 워커로 넘김(0027) | 수동 환불 중복 | PG 콘솔 직접 환불 | 예외 절차(환불 NMC에서만, PG 확인 뒤 반영) |

테스트: E13, N11, N19, N22, N31, FT-1·FT-2의 V2.

### INV-3 PG 승인 금액·통화는 결제와 같고, 결제의 금액·사용자는 예매와 같다

| 수단 | 맡는 실패 | 무너지는 경우 | 그때 잡는 것 |
|---|---|---|---|
| 토큰 금액 = 요청 금액, 토큰은 Reservation이 서명(SA 7-3, 0024) | 요청 금액 조작 | 키 유출 | 아래 대조 |
| PG 결과 금액·통화 대조(0022) | PG가 다른 금액을 승인 | 코드 누락 | `chk_payment_approved`(DB) |
| `chk_payment_approved`: APPROVED면 `pg_approved_amount = amount` | 불일치 결제의 APPROVED 저장 | — | — |
| Reservation의 userId·amount·currency 대조(0026) | 예매와 다른 결제로 확정 | 규칙 누락 | 대사 RC-5·RC-6 |
| 환불 금액 = PG 승인 금액(`INSERT … SELECT`), 환불 결과 금액 대조(0019, 0022) | 부분·과다 환불 | — | 대사 RC-5, Mock PG 원장 검사(V2) |

테스트: N16, N22, N28, FT의 V3.

### INV-4 환불 의무는 완료 또는 명시적 미해결 상태로 추적된다

명시적 미해결 상태는 환불 `REQUESTED`·`UNKNOWN`·`NEEDS_MANUAL_CHECK`, 운영자 종결 `FAILED`(외부 조치 기록 필수), `dead_letter` `OPEN`이다. 모두 건수·최고령 지표와 알림이 있다([observability.md](observability.md)).

| 수단 | 맡는 실패 | 무너지는 경우 | 그때 잡는 것 |
|---|---|---|---|
| Reservation의 상태 변경 + `RefundRequested` Outbox(0026) | 상태 변경 뒤 발행 유실 | Reservation이 발행하지 못함(`payment.result` 소비 DLQ 처리기 부재 등) | 대사 RC-2 |
| 소비자는 환불 행만 영속화하고 PG를 부르지 않음, 실패 시 오프셋 미커밋(0019) | 소비 중 장애 | 재시도 3회 실패 | DLQ 처리기 |
| DLQ 처리기의 영속화, 실패 시 오프셋 미커밋·무한 백오프(0019) | DLQ 도착 메시지 유실 | `.dlq` 보관 7일 초과 | 대사 RC-2, DLQ 처리기 실패·랙 알림 |
| 환불 워커 재시도(PG 호출 9회, 약 21분) 뒤 NMC(0019) | PG 일시 장애 | 장기 장애 | NMC 알림, 환불 대기 최고령 알림 |
| 검증 실패 명령은 `dead_letter` OPEN + 알림(0019) | 위조·불일치 명령의 조용한 폐기 | — | dead_letter 최고령 알림, 대사 RC-2 |
| Ops 명령(0027) | 사람이 처리한 건의 이벤트 누락 | — | 대사 RC-7·RC-8 |

테스트: E8, N7, N8, N19, N20, N23, N28, FT-4, FT-5.

### INV-5 상태 변경과 이력·이벤트는 함께 성공하거나 함께 실패하고, 실제로 바뀐 전이만 이벤트를 만든다

| 수단 | 맡는 실패 | 무너지는 경우 | 그때 잡는 것 |
|---|---|---|---|
| 같은 DB 트랜잭션 + Outbox(SA 10-1) | 커밋 뒤 발행 전 중단 | — | 릴레이 재시도 |
| 조건부 UPDATE 영향 행이 1일 때만 이력·Outbox·멱등 응답(0021) | 경합에서 진 쪽의 중복 이벤트·이력 | 코드 규칙 누락 | 대사 RC-7·RC-8, N17 |
| 릴레이 임대와 전송 확인(0021) | 전송 중 중단 | 임대가 전송 시한보다 짧음 | 임대 ≥ 2 × `delivery.timeout.ms` 규칙, 소비 멱등 |
| CHECK 제약([data-model.md](data-model.md)) | 필수 값 없는 확정, 재조회 시각 없는 미확정 | — | — |

테스트: N10, N17, N18, N26, FT-3.

## 3. 단일 방어 점검

방어 수단 하나가 무너졌을 때 다른 수단이 같은 실패를 잡는지 확인했다. 한 수단만 남은 곳과 보강안이다.

| # | 불변 조건 | 단일 방어로 남았던 곳 | 보강(이번 설계에 반영) | 남는 위험 |
|---|---|---|---|---|
| 1 | INV-3 | PG 승인 금액 대조가 코드 한 곳 | `pg_approved_amount` 컬럼과 APPROVED CHECK, 대사 RC-5 | PG 정산 자료와의 대사 없음(후속) |
| 2 | INV-4 | Reservation이 `RefundRequested`를 내지 못하면 Payment는 알 수 없음 | 대사 RC-2 | 대사 정지 중에는 작업 정체 알림뿐 |
| 3 | INV-5 | "영향 행 1일 때만 후속 쓰기"가 코드 규칙 | 대사 RC-7(상태·이력), RC-8(전이·이벤트), N17 | 24시간을 넘긴 누락은 RC-8 범위 밖 |
| 4 | INV-7 | 직접 SQL 금지가 절차 규칙 | append-only 트리거, RC-7·RC-8 사후 탐지 | 앱과 같은 DB 계정이 트리거를 끌 수 있음. 마이그레이션 계정 분리는 후속 |
| 5 | INV-8 | 늦은 승인 방지가 PG 망취소 하나에 의존 | Mock 계약 테스트, 토스 `Prevented` 금지 | `DECLINED` 뒤 PG가 늦게 승인하면 Payment는 모른다. PG 정산 대사(후속) |
| 6 | INV-1 | 토스 승인 멱등 미확인 | 결제 행당 승인 호출 1회 구조, `UNIQUE(pg_tx_id)` | — |
| 7 | INV-2 | 환불 재호출 방어가 PG 멱등키 하나 | 재호출 전 조회, 환불 행 UNIQUE, 워커 claim | PG 조회가 오답이면 PG의 재취소 거절에 의존 |
| 8 | INV-6 | 대사가 예매 내부 API 하나에 의존 | 작업 정체 알림, 원인 쪽 지표 | API가 오래 멈추면 탐지가 늦다 |
| 9 | INV-9 | Kafka 브로커 무인증 | Kafka-UI READONLY, 소비자 교차 검증, 대사 | 내부망 침해 시 발행 가능. SASL은 MVP 밖([0008](../../decisions/0008-internal-trust-and-auth-design.md) T5) |
