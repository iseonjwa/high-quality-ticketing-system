# ISE-79 동시성 시나리오 검토

상태: 검토 완료, 결정 대기 (2026-11-03, 좌석 선점 담당 최권우 요청으로 Claude Code가 검토)

ISE-79 본문의 재현 전제와 해결안을 현재 코드(`SyncSeatHoldService`, `JpaSeatHoldInventoryRepository`, `SpringDataUserScheduleQuotaRepository`, `SeatHoldExpiryService`)와 대조했다. 결론은 네 항목 중 TS-2만 이슈에 적힌 대로 재현될 것으로 보이고, TS-1·TS-3·TS-4는 증상이나 해결안을 고쳐야 한다는 것이다. 아래 판단은 코드를 읽고 세운 가설이며 실행으로 확인하지 않았다(Docker 미기동). [concurrency-scenarios.md](concurrency-scenarios.md)의 S0 기준선 실행으로 확인한다.

## 2. 상세

### R1. TS-1 역순 데드락은 현재 코드에서 재현되기 어렵다
- 근거 1: `sortedDistinctSeatIds`가 요청 좌석을 오름차순으로 정렬한 뒤 모든 처리에 쓴다. `[1024, 1023]`으로 와도 DB에는 `[1023, 1024]`로 간다.
- 근거 2: 좌석 선점은 `UPDATE ... WHERE id IN (:ids) AND status = 'AVAILABLE'` 한 문장이다. 한 문장 안의 행 잠금 순서는 실행 계획의 스캔 순서를 따르고, 같은 계획을 쓰는 트랜잭션끼리는 순서가 같다. PostgreSQL B-tree 인덱스 스캔은 `= ANY(배열)`의 값을 정렬해 인덱스 순서로 읽는다(미확인: 실제 계획은 `EXPLAIN`으로 확인 필요).
- 근거 3: 같은 사용자의 요청은 좌석보다 먼저 매수 행(upsert)에서 줄을 선다. 다른 사용자끼리는 매수 행을 공유하지 않는다.
- 제안: C2를 기준선에서 돌려 데드락 0이면 "재현되지 않음, 이미 정렬과 단일 UPDATE로 막혀 있음"을 기록하고 C2는 회귀 테스트로 남긴다. TS-1의 개선 서사는 실제로 생기는 문제인 "핫 좌석 잠금 대기와 커넥션 점유"(C3, L2, L6)와 `lock_timeout` 빠른 실패로 옮긴다.
- 하지 말 것: 데드락을 보이려고 운영 코드에 정렬 제거나 좌석별 개별 잠금 같은 나쁜 구현을 일부러 넣지 않는다. 학습용으로 보이고 싶으면 테스트 코드 안에서 JDBC로 두 트랜잭션이 역순으로 `SELECT ... FOR UPDATE`를 하게 만들어 `40P01`을 재현하고, 그것이 "정렬하지 않으면 생기는 일"의 시연임을 밝힌다.
- 덧붙여: SA 12-7의 `UPDATE ... WHERE id IN (SELECT ... ORDER BY id FOR UPDATE)`는 지금의 단일 UPDATE보다 잠금 순서를 명시적으로 고정하는 장점이 있다. 실행 계획이 바뀌어도(예: 비트맵 스캔) 순서가 유지된다. 이것은 "데드락 해결"이 아니라 "순서 보장의 명시화"로 기록하는 것이 정확하다.

### R2. TS-3의 증상은 500이 아니라 자기 요청 409다
- 흐름: 두 요청이 모두 사전 조회(`seatHoldRequests.findById`)에서 빈 결과를 본다. 첫 요청이 매수 upsert로 매수 행을 잠근다. 두 번째 요청은 같은 행 upsert에서 기다린다. 첫 요청이 커밋하면 두 번째 요청이 이어서 좌석 UPDATE를 하지만 좌석이 이미 HELD라 0행이 되고 `SEAT_ALREADY_HELD`(409)로 롤백한다. `seat_hold_requests` INSERT까지 가지 않으므로 PK 충돌은 생기지 않는다.
- 이 추정은 [contracts.md](contracts.md) 3-2 ⑥에 이미 "구조상 추정, 미재현"으로 적혀 있다. ISE-79 본문은 이 내용과 다르게 500 재현을 목표로 적었다.
- 해결안 보완: `DataIntegrityViolationException`을 잡는 처리만으로는 이 경로를 타지 않는다. 멱등키를 트랜잭션의 첫 쓰기로 선점해야 두 번째 요청이 PK에서 기다렸다가 유니크 위반을 받는다. 그 뒤 롤백된 트랜잭션 밖에서 새 읽기 트랜잭션으로 재조회해 ADR 0032 규칙대로 응답한다. 선점 방법은 둘 중 하나다.
  - `seat_hold_requests`를 REQUESTED로 먼저 INSERT하고 성공 시 HELD로 바꾼다. 실패하면 같은 트랜잭션이 롤백되므로 "실패한 동기형 요청은 행을 남기지 않는다"(ADR 0032)를 지킨다.
  - `pg_advisory_xact_lock(키 해시)`로 같은 키를 줄 세운 뒤 사전 조회를 한다. 테이블 변경이 없지만 해시 충돌 시 다른 키도 줄을 선다.
- 재조회 위치: `@Transactional` 메서드 안에서 예외를 잡으면 트랜잭션이 rollback-only라 재조회가 같은 트랜잭션에서 안 된다. 트랜잭션 경계 밖(호출하는 쪽)에서 잡는다.
- 제안: ISE-79 TS-3 문구를 "동일 멱등키 동시 진입 시 자기 요청 409 재현 → 멱등키 선점 + 유니크 위반 재조회로 201 복구"로 고친다. 500은 멱등키 선점을 넣은 뒤 재조회가 없을 때의 중간 상태로 S2 기록에 남길 수 있다.

### R3. ID만 `SKIP LOCKED`로 뽑으면 중복 집기를 막지 못한다
- 현재 `findExpiredReservationIds`는 읽기 전용 트랜잭션에서 ID 목록을 돌려주고 트랜잭션을 끝낸다. 여기에 `FOR UPDATE SKIP LOCKED`를 붙여도 커밋과 함께 잠금이 풀리므로, 다른 인스턴스가 바로 같은 ID를 다시 집는다. SA 8-4의 "ID만 SKIP LOCKED로 뽑고 처리는 건별 트랜잭션"도 같은 문제가 있다.
- 제안: 건별 트랜잭션 안에서 `SELECT id FROM reservations WHERE status = 'HELD' AND hold_expires_at <= :now ORDER BY hold_expires_at FOR UPDATE SKIP LOCKED LIMIT 1`로 한 건을 잠가 집고 같은 트랜잭션에서 처리한다. 한 주기에 배치 크기만큼 반복한다. 잠금이 처리 끝까지 유지되므로 다른 인스턴스는 그 행을 건너뛴다.
- 측정: C6의 헛수고(wasted) 수가 개선 지표다. 정합성은 기준선에서도 조건부 UPDATE가 지키므로 "중복 반환 방지"가 아니라 "헛수고와 잠금 대기 제거"로 기록한다.
- 이 변경은 SA 8-4 문장을 바꾸므로 ADR로 남긴다.

### R4. 전역 잠금 순서는 회수 경로끼리 맞추는 것이 핵심이다
- 지금 만료는 예매 → 예매 좌석 → 회차 좌석 → 매수 순으로 잠근다. 결제 결과 소비자도 ADR 0027의 "후속 쓰기는 영향 행이 1일 때만" 규칙상 예매를 먼저 전이할 가능성이 크다. 이 둘은 같은 예매 행에서 먼저 줄을 서므로 교착이 생기지 않는다.
- ISE-79대로 만료만 SA 8-4 순서(매수 → 좌석 → 예매)로 바꾸면, 예매를 먼저 잠그는 소비자와 순서가 엇갈려 오히려 교착이 생길 수 있다. R3의 `SKIP LOCKED`도 예매 행을 먼저 잠근다.
- 선점(매수 → 좌석)과 회수(좌석 → 매수)는 순서가 반대지만, 선점의 좌석 UPDATE는 `AVAILABLE` 조건이라 회수 중인 좌석(커밋 전에는 HELD로 보임)을 건너뛰고 잠금을 기다리지 않는다. 그래서 교착이 생기지 않을 것으로 본다. C7로 확인한다.
- 제안: 회수 경로(만료, 결제 거절, 취소)의 공통 순서를 "예매(조건부 전이) → 회차 좌석 오름차순 → 매수"로 정하자고 결제 결과 소비자 담당(반효승)에게 contract 이슈로 제안한다. 합의되면 SA 8-4를 대체하는 ADR을 쓴다. [hold-expiry.md](hold-expiry.md) 2절 1번(반환 코드 위치 B안)과 함께 정하면 규칙이 한 곳에 모인다.

### R5. 기록 번호가 겹친다
`docs/troubleshooting.md`는 이미 TS-1~TS-31을 쓴다. 이슈 항목 TS-1~TS-4를 그대로 쓰면 다른 문제와 번호가 겹친다. 기록할 때 그 파일의 다음 번호를 쓰고, ISE-79 본문에 "이슈 항목 → 기록 번호" 대응을 적는다.

### R6. 커넥션 풀 크기가 문서와 설정에서 다르다
`config-repo/reservation-service.yml`은 `maximum-pool-size: 5`, SA 9-4는 서비스당 20이다. 풀 5에서는 핫 좌석 잠금 대기보다 커넥션 대기가 먼저 병목이 되어 `lock_timeout` 효과가 가려질 수 있다. 부하 측정 전에 측정에 쓸 값을 정하고 환경 기록표에 적는다. 운영 값을 바꾸는 것은 공유 설정 변경이라 contract 이슈로 알린다.

### R7. E1 완료 기준은 기준선에서도 통과한다
좌석 조건부 UPDATE와 `reservation_seats` 부분 유니크 인덱스가 이미 있어 "1명만 201, 99명 409, 중복 판매 0"은 기준선에서 통과할 것으로 본다. ISE-79 완료 기준에서 이 항목을 "회귀 기준"으로 표시하면, 개선 서사가 실제로 바뀐 지표(C3·C4·C5·C6)에 모인다.

### R8. 부하 시나리오는 ISE-25와 겹친다
가상 사용자 토큰, 좌석 초기화, 측정 환경 기록표는 ISE-25(권영은) 할 일이다. 좌석 선점 쪽에서 같은 것을 따로 만들지 않고, [load-test-scenarios.md](load-test-scenarios.md)의 L2~L6을 ISE-25 도구에 더해 달라고 요청한다.
