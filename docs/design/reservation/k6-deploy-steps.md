# K1 단계 개선을 배포 서버에서 다시 재기 (ISE-79, 측정 전 계획)

상태: 준비 끝, 측정 전. 작성: 좌석 선점 담당 최권우 요청으로 Claude Code. 실행 도구와 예상의 정본은 측정 브랜치 `experiment/ISE-79-k6-steps`의 `reservation-service/k6/deploy/`와 `reservation-service/k6/STEPS.md` "배포 단계 측정" 절이다.

## 1. 무엇을 재나

local에서 한 단계씩 쌓은 K1 개선(base → G1 → R1 → P4a → P4b → P4c → F → 사전 거절)을 배포 서버에서 같은 순서로 한 번에 다시 잰다. local 수치는 32코어 노트북이라 CPU가 남았고, 배포 서버(4 vCPU에 컨테이너 20개)에서는 같은 개선이 어디까지 버티는지가 다르다. 발표에 쓸 "실제 환경 수치"를 얻는 것이 목적이다.

- 단계마다 reservation-service 이미지와 설정만 바꾼다. 이미지는 그 단계를 측정한 커밋으로 만들어 서버에 직접 넣는다(GHCR에는 main 릴리스만 있다). 같은 방식은 `loadtest/deploy/compose.seat-before.yml`이 먼저 썼다.
- Gateway를 비롯한 나머지 서비스와 설정은 배포 그대로 둔다(2026-11-12 사용자 결정). Gateway에는 ADR 0050 운영값과 동시 처리 상한 64가 들어 있다.
- 측정 모드 켜기·끄기, 키 옮기기, 회차 만들기는 팀 절차(`docs/guides/loadgen.md`, `script/loadtest/measure-mode.sh`)를 따른다. 회차는 서버에서 만들고 관리자 비밀번호를 발생기에 두지 않는다.
- 단계마다 L(초당 100명 300초)과 S(초당 5~160명, 회복 120초)를 잰다. 8단계 약 2시간 40분이다. S를 160명에서 멈추는 이유는 발생기 네트워크 기준(1.562Gbps)으로 좌석 조회(응답 약 830KB)가 초당 약 180건에서 막히기 때문이다(계산값).

## 2. CPU·힙이 버티지 못할 것으로 보는 단계

local 측정(32코어, 그리고 서버를 4코어에 묶은 CPU 상한 측정)으로 예상했다. 배포 서버는 한 코어가 local보다 느리고 다른 컨테이너도 같이 돌아서 CPU 상한 측정보다 조금 나쁠 것으로 본다.

| 단계 | L(초당 100명) | S(5~160명) | 먼저 차는 것 |
|---|---|---|---|
| base | 못 버팀 | 5명 단계부터 흔들림 | 힙(Serial GC, 부하의 약 75%가 GC 정지) |
| G1 | 못 버팀 | 10~20명 | CPU(G1이 여러 코어로 큰 할당을 치운다) |
| R1 | 못 버팀 | 10~20명 | CPU, 컨테이너 메모리 경계(local에서 1.12GiB/1.125GiB까지 감) |
| P4a | 못 버팀 | 20~40명 | CPU(PostgreSQL이 15,000행 조인·정렬로 약 4코어) |
| P4b | 경계(성공하지만 느려짐) | 80~160명에서 무너짐 | CPU(local L에서 세 컨테이너 합 약 4.2코어) |
| P4c | 버팀 | 160명 경계 | CPU(CPU 상한 측정 160명 p95 149ms) |
| F | 버팀 | 160명 경계 | CPU |
| 사전 거절 | 버팀 | 160명을 버틸 가능성이 가장 큼 | CPU(CPU 상한 측정에서 선점 처리 시간 -47%) |

- 힙(768MB)이 먼저 무너지는 단계는 P4a 전뿐이다. P4a부터는 GC 정지가 3% 아래라 CPU가 먼저 찬다.
- Gateway 동시 처리 상한 64 때문에 실패 모양이 local과 다를 것으로 본다. 좌석 조회와 선점이 초당 약 200건일 때 응답이 0.3초를 넘으면 상한에 닿는다(리틀의 법칙, 계산값). 그래서 base~P4a는 local의 504·500 대신 Gateway의 즉시 503이 많고, 서버 적체가 덜 쌓여 회복은 빠를 수 있다.
- Gateway 메모리는 local CPU 상한 측정에서 본 OOMKilled(768MB)보다 위험이 낮다. 배포는 1,024MB에 직접 메모리 상한 128MB이고 동시 처리 상한이 쥐는 응답 수를 묶는다.

## 3. 팀에 미치는 것

- 측정하는 동안 배포 서버가 측정 모드다. main 머지를 멈추고, 단계마다 슬랙 측정 채널에 "설정 변경" 알림이 간다.
- base~P4a 단계는 서버 CPU를 오래 채운다. 다른 측정·시연과 시간이 겹치지 않게 팀 채널에서 시간을 잡는다.
- 끝나면 측정 모드를 끄고(배포 이미지로 돌아온다) 서버에 넣은 단계 이미지는 지운다.
