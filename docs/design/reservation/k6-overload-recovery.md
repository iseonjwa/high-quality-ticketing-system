# 과부하가 끝나도 좌석 서비스가 돌아오지 않는 문제(B8) 분석과 대응 설계 (ISE-79)

상태: 원인 분석 완료, 대응 후 1회 측정(7절). R1은 회복을 풀었고 R2·R3 시작값은 오히려 나빴다. 반복 측정과 R3 값 다시 정하기가 남았다 (2026-11-05 작성, 좌석 선점 담당 최권우 요청으로 Claude Code가 분석)

K1 부하 측정(초당 100명, 5분)에서 reservation-service는 부하가 끝난 뒤에도 몇 분에서 10분 넘게 응답하지 못했다. 재시작해야만 돌아왔다. 이 문서는 세 번의 측정(P0·P0'·P0'')에서 본 현상, 지표로 따라간 원인, 대응 설계와 검증 기준을 적는다. 측정 원자료와 단계 계획은 [k6-seathold-bottleneck-plan.md](k6-seathold-bottleneck-plan.md) 5절에 있다.

| 대응 | 서버 안의 대기 시한과 대기열 크기를 Gateway 시한보다 짧고 작게 둔다. 커넥션 대기 30초 → 1초, Tomcat 스레드·연결 상한 축소 |
| 결과 | R1(커넥션 대기 1초)만으로 부하가 끝나고 10초 안에 회복했다(대응 전은 340초 뒤에도 연결 4,344개가 남음). 사용자가 받은 좌석 조회 200은 7건에서 1,463건으로 늘었다. R2·R3 시작값(연결 200)은 Tomcat 안 대기가 Gateway 시한보다 길어 오히려 나빴다. 빠른 실패·처리량 기준은 못 넘었다(7절, 각 1회) |

## 1. 현상

| 측정 | 환경 | 부하가 끝난 뒤 |
|---|---|---|
| P0 (2026-11-04) | 힙 256MB, Serial GC | 10분 넘게 전체 503. 재시작해야 돌아왔다 |
| P0' (2026-11-05) | 힙 768MB, Serial GC | 3분 넘게 직접 호출(`localhost:8082`)에도 응답 없음. 메모리 1.115GiB(상한 1.125GiB), CPU 170%. 재시작했다 |
| P0'' (2026-11-05) | 힙 768MB, G1 GC | GC 정지는 짧아졌지만, 부하가 끝나고 6분 뒤에도 요청 스레드 200개가 모두 바빴다. 재시작했다 |

메모리를 3배로 늘려도, GC를 바꿔 정지를 1초 아래로 줄여도 회복하지 못했다. 그래서 메모리·GC가 아닌 다른 원인이 있다고 보고 P0'' 지표를 따라갔다.

## 2. 요청이 지나는 길과 각 단계의 한도

```text
k6 ──▶ Gateway ──────────────────▶ Tomcat(reservation-service) ──────────▶ Hikari ──▶ PostgreSQL
       연결 시한 1초                연결 상한 8,192 (기본값)                   커넥션 5개
       응답 시한 3초 → 504          OS 대기열 100 (accept-count 기본값)        대기 시한 30초 (기본값)
                                    요청 스레드 200 (기본값)
```

| 위치 | 설정 | 값 | 출처 |
|---|---|---|---|
| Gateway | `httpclient.connect-timeout` | 1,000ms | `config-repo/gateway.yml` |
| Gateway | `httpclient.response-timeout` | 3s | 같은 파일 |
| Tomcat | `server.tomcat.threads.max` | 200 | Spring Boot 기본값(설정 없음) |
| Tomcat | `server.tomcat.max-connections` | 8,192 | 기본값 |
| Tomcat | `server.tomcat.accept-count` | 100 | 기본값 |
| Hikari | `maximum-pool-size` | 5 | `config-repo/reservation-service.yml` |
| Hikari | `connection-timeout` | 30,000ms | 기본값(설정 없음) |

핵심은 단계마다 시한의 크기가 어긋난다는 점이다. 바깥(Gateway)은 3초면 포기한다. 안쪽(Tomcat 대기열, Hikari 대기)은 수천 건을 30초까지 기다리게 둔다.

## 3. 원인: 지표로 따라간 순서 (P0'' 기준)

측정: 2026-11-05 03:04:12~03:09:12(UTC), 요청 29,994건(좌석 조회 29,976, 선점 18). 지표는 Prometheus(`reservation-service`, `gateway`)와 k6 원자료다.

### 3-1. 요청 스레드 200개가 모두 커넥션 5개를 기다렸다

| 지표 | 부하 중 | 부하가 끝나고 6분 뒤(03:15) |
|---|---|---|
| 처리 중인 요청 수(`http_server_requests_active_seconds_count` 합) | 200 | 200 |
| Hikari 사용 중 커넥션(`hikaricp_connections_active`) | 5 | 5 |
| Hikari 커넥션 대기 스레드(`hikaricp_connections_pending`) | 197 | 197 |
| JVM 스레드 수 | 252 | 253 |

처리 중 200은 Tomcat 요청 스레드 상한(200)과 같다. 대기 197과 사용 중 5를 더하면 약 200이다. 요청 스레드 전부가 커넥션 5개 앞에 줄을 섰다는 뜻이다. DB 잠금 대기는 0이었다. DB가 느린 것이 아니라 커넥션 하나를 쥔 좌석 조회(15,000석을 엔티티로 읽고 변환)가 오래 걸린다.

### 3-2. 서버는 초당 약 14건을 처리했고, 한 건이 서버 안에서 평균 14초를 보냈다

- 서버가 끝낸 좌석 조회 200은 초당 9.4~18.7건(평균 약 14건)이었다.
- 리틀의 법칙(시스템 안의 수 = 도착률 × 머무는 시간)으로 보면 200건 ÷ 초당 14건 ≈ 14초다. 실제 서버 안 평균 지연 14.4초와 맞는다.
- 커넥션 대기 시한이 30초라 14초를 기다린 요청은 실패하지 않는다. 대기 시한 초과(`hikaricp_connections_timeout_total`)는 5분 동안 23건뿐이었다. 그래서 요청은 빨리 실패하지 않고, 기다렸다가 끝까지 처리된다.

### 3-3. Gateway는 3초에 포기하지만 서버는 그것을 모른다

- Gateway는 3초 안에 응답이 없으면 504를 돌려주고 연결을 끊는다.
- 서버의 요청 스레드는 응답을 쓰는 순간까지 상대가 떠났는지 확인하지 않는다. 대기열에 있던 요청도 스레드를 받으면 처음부터 처리한다.
- 결과: 서버가 끝낸 좌석 조회 200은 5,015건이었다. k6가 받은 200은 19건이었다. **서버가 한 일의 99.6%는 이미 아무도 기다리지 않는 요청이었다.**

### 3-4. 서버 앞 대기열이 가득 차자 새 연결조차 받지 못했다

k6가 받은 좌석 조회 응답을 시간대별로 나누면 모양이 바뀐다.

| 구간 | 주된 응답 | 지연 중앙값 | 뜻 |
|---|---|---|---|
| 0~2분 | 504 8,717건 | 3,010ms | 서버가 연결은 받았지만 3초 안에 답하지 못함 |
| 2~5분 | 500 15,786건 | 1,008ms | Gateway 연결 시한(1초)에 걸림. 서버가 새 연결을 받지 못함 |

처음 2분의 504는 서버 앞까지 들어간 요청이다. 그 수(8,717)가 Tomcat 연결 상한(8,192)과 비슷하다. 상한이 차고 OS 대기열(100)까지 차자, 2분 이후 요청은 연결 단계에서 1초 만에 끊겼다(Gateway 응답 500).

P0'' 때는 Tomcat 연결 수를 직접 재지 못해 504 수와 상한이 비슷하다는 점, 500이 연결 시한(1초)에 모인다는 점으로 추정했다. 7절의 R0 측정에서 Tomcat MBean 지표를 켜고 다시 재니 연결 수가 부하 중 정확히 8,192에서 멈췄다. 추정이 맞았다.

### 3-5. 부하가 끝나도 쌓인 일이 남아 있다

- 남은 일: Tomcat 연결 최대 약 8,192건과 처리 중 200건.
- 처리 속도: 초당 약 14건이고, 한 건마다 커넥션을 기다린다.
- 비우는 데 걸리는 시간: 약 8,400건 ÷ 초당 14건 ≈ 10분.

이 계산은 P0''에서 부하가 끝나고 6분 뒤에도 스레드 200개가 바빴던 것, P0에서 10분 넘게 회복하지 못한 것과 맞는다. 그동안 새 요청은 같은 대기열 뒤에 서므로 사용자에게는 서비스가 죽은 것처럼 보인다.

### 3-6. 원인 사슬

```text
좌석 조회 1건이 무겁다(B2)
 → 커넥션 5개로 초당 약 14건만 처리
 → 도착(초당 100건 이상)이 처리를 넘어 요청 스레드 200개가 모두 커넥션 대기
 → 커넥션 대기 시한(30초)이 Gateway 시한(3초)보다 길어 빨리 실패하지 않음
 → Gateway가 포기한 요청이 Tomcat 대기열(최대 8,192)에 쌓이고, 서버는 그것을 끝까지 처리
 → 부하가 끝나도 쌓인 일을 비우는 데 약 10분
```

B2(무거운 좌석 조회)는 "얼마나 처리하느냐"의 문제다. B8은 "처리하지 못한 요청을 어떻게 버리느냐"의 문제다. P4로 B2를 풀어도 언젠가는 처리 한도를 넘는 부하가 온다. 그때 서버가 스스로 돌아오려면 B8을 따로 풀어야 한다.

### 3-7. 503의 출처 두 가지

측정 중 Gateway의 503에는 출처가 둘 있었다. 서로 다른 문제라 나눠 본다.

| 출처 | 확인 방법 | 나온 측정 |
|---|---|---|
| Eureka에서 인스턴스가 빠짐 | Gateway 로그 `No servers available for service` | P0(긴 GC 정지로 갱신이 끊김) |
| Gateway 인증의 Redis 차단기(`auth-redis`) 열림 | `resilience4j_circuitbreaker_state{state="open"}`, 응답 0~5ms | P0'·P0'' 시작 직후, K1-H 중 네 번 |

Gateway는 요청마다 Redis에서 로그아웃 토큰 여부를 확인한다. 그 호출이 50ms를 넘는 비율이 높으면 차단기가 10초 열리고, 그동안 인증이 필요한 요청을 모두 503으로 돌려준다(`GatewayAuthenticationFilter`). 노트북 한 대에서 k6와 전체 스택이 CPU를 나눠 쓰는 측정 환경 영향이 크다. 측정 수치에서는 이 503을 서버 오류와 따로 센다. 차단기 값은 Gateway 담당 영역이라 이 문서에서는 바꾸지 않는다.

## 4. 대응 방향: 빨리 거절해서 스스로 비우게 한다

원칙: **서버 안에서 기다리는 시간과 대기열 크기를 바깥 시한(Gateway 3초)보다 짧고 작게 둔다.** 처리하지 못할 요청은 일찍 거절해야 한다. 거절은 사용자에게 오류지만, 서버는 다음 요청을 받을 수 있는 상태로 남는다.

| # | 변경 | 값(시작점) | 기대 효과 | 대가·위험 |
|---|---|---|---|---|
| R1 | Hikari `connection-timeout` | 30s → 1s | 커넥션을 1초 못 받으면 실패한다. 스레드가 14초씩 묶이지 않아, 쌓인 요청을 초당 수백 건씩 비운다 | 순간적인 몰림에도 실패가 바로 난다. 1초는 Gateway 3초 안에 실패 응답이 돌아가게 하는 값이다 |
| R2 | Tomcat `threads.max` | 200 → 50 | 커넥션 5개를 200개 스레드가 기다리는 상태를 없앤다. 동시에 메모리에 올라가는 요청도 줄어 GC 압력이 준다 | 커넥션이 필요 없는 요청(헬스체크 등)도 같은 스레드를 쓴다. 풀을 늘리는 P1과 같이 다시 정해야 한다 |
| R3 | Tomcat `max-connections`, `accept-count` | 8,192 → 200, 100 → 50 | 서버 앞 대기열을 "3초 안에 처리할 수 있는 양" 근처로 묶는다. 넘친 요청은 Gateway에서 1초 안에 실패한다 | 처리량이 바뀌면(P4 이후) 값을 다시 맞춰야 한다. 너무 작으면 처리할 수 있는 요청까지 버린다 |
| R4 | (후속 검토) 마감 시각 전달 | Gateway가 요청에 마감 시각을 붙이고, 서버는 스레드를 받았을 때 이미 지났으면 처리하지 않는다 | 대기열에 남은 "이미 버려진 요청"을 처리 직전에 건너뛴다 | Gateway와 서비스가 같이 지켜야 하는 규칙이라 contract 이슈가 필요하다 |
| R5 | (후속 검토) Gateway 입장 제한 | 경로별 동시 처리·초당 요청 상한 | 서버까지 오기 전에 넘친 요청을 거른다 | Gateway 담당 영역. 대기열(queue-service)의 입장 속도와 겹치는지 먼저 본다 |

R1~R3은 reservation-service 설정만 바꾼다. 측정은 측정 전용 덮어쓰기 파일(`reservation-service/k6/`)로 먼저 한다. 값을 실제로 넣을 곳은 `config-repo/reservation-service.yml`이다. 이 파일은 대기열·예매·공연 담당도 같이 쓰므로, 측정으로 효과를 확인한 뒤 contract 이슈로 제안한다(AGENTS.md 대전제 11). 계획 문서에서는 R1을 P1(커넥션 풀)과 같은 단계로 묶어 두었다.

R1~R3 값은 시작점이다. "Gateway 시한 3초 × 서버 처리량" 근처가 적정 대기열 크기다. 지금 좌석 조회 처리량(초당 약 14건)이면 40건 남짓이고, 선점(5-4절 K1-H)이면 수백 건이다. 그래서 P4 뒤에 다시 맞춘다.

## 6. 검증 계획과 판정 기준

판정 기준은 대응을 넣기 전에 정해 둔다. 결과를 보고 기준을 바꾸지 않는다.

- 같은 조건: P0'' 환경(배포 메모리 + G1), K1 초당 100명 300초, 새 회차, 깨끗한 JVM.
- 바꾸는 것: R1 → R1+R2+R3 순서로 두 번. 한 번에 바꾸면 무엇이 효과를 냈는지 가리지 못한다.
- 부하가 끝난 뒤 5분 동안 10초마다 좌석 조회 한 건을 보내 응답 시간을 적는다.

| 기준 | 통과 조건 |
|---|---|
| 회복 시간 | 부하가 끝나고 30초 안에 처리 중 요청 수와 커넥션 대기가 0이 되고, 좌석 조회 한 건이 1초 안에 200으로 온다. 재시작이 없다 |
| 버려진 일 | 서버가 끝낸 요청 중 서버 안 지연이 3초를 넘는 것이 전체의 5% 미만 |

성공 건수(초당 100명에서 좌석 조회 19건)는 이 대응으로 늘지 않을 수 있다. 요청 한 건의 비용은 P4가 줄인다. 이 대응이 바꾸는 것은 과부하가 지난 뒤 서비스가 스스로 돌아오는가다.

### 7-3. 해석

- **R1(커넥션 대기 1초)이 회복 문제를 풀었다.** 커넥션을 1초 안에 못 받은 요청이 바로 실패하니, 스레드가 14초씩 묶이지 않는다. Tomcat 연결도 157개를 넘지 않았다. 부하가 끝나자 10초 안에 비었고, 그 뒤 좌석 조회는 300ms 안팎으로 돌아왔다. R0은 340초가 지나도 연결 4,344개가 남아 있었다(초당 약 11건씩 비워 3-5절 계산 약 10분과 맞는다).
- **버려지는 일이 줄어 쓸모 있는 일이 늘었다.** R1에서 서버가 끝낸 200의 95%가 사용자에게 갔다. R0은 0.1%였다.
- **R2·R3 시작값(스레드 50, 연결 200, OS 대기열 50)은 R1보다 나빴다.** 사용자가 받은 200이 1,463건에서 172건으로 줄고 504가 다시 늘었다(874 → 11,721건).
  - 원인: 연결 200개 중 스레드를 못 받은 150개는 Tomcat 안에서 기다린다. 서버가 처리하는 속도가 초당 약 10건이므로 그 줄을 비우는 데 15초쯤 걸린다. Gateway 시한 3초보다 길다.
  - 리틀의 법칙으로 맞는 크기를 다시 계산하면 3초 × 초당 10건 = 연결 약 30개다. 4절이 "좌석 조회 처리량이면 40건 남짓"이라고 한 값과 같은 자리다. 시작값 200은 선점(처리량 수백 건) 기준이라 좌석 조회가 무거운 지금은 컸다.
  - 서버 안 지연(`http_server_requests`)은 스레드가 요청을 집은 뒤부터 잰다. Tomcat 안에서 스레드를 기다린 시간은 들어가지 않는다. 그래서 R1+R2+R3의 "3초 초과 0%"는 버려진 일이 없다는 뜻이 아니다. 실제로 서버가 끝낸 200 2,941건 중 사용자에게 간 것은 172건이다.
- **빠른 실패는 R1도 기준을 못 넘었다.** 오류의 대부분이 500(Gateway 연결 시한 1초나 커넥션 대기 1초)이라 중앙값은 1초 근처다. p95 1.7초는 스레드를 기다린 시간이 더해진 것으로 본다. 커넥션 대기 시한을 더 줄이거나(예: 500ms) 스레드 수를 커넥션 수에 맞추면 줄어들 수 있다. 다음 측정에서 확인한다.

### 7-4. 다음 단계

1. R1만 먼저 제안한다. 회복을 푼 것은 R1이고, R2·R3은 값을 다시 정해야 한다. 공유 설정(`config-repo/reservation-service.yml`)이라 contract 이슈로 올린다.
2. R3을 리틀의 법칙 값(연결 30~40, OS 대기열 작게)으로 다시 잰다. 스레드 수는 P1(커넥션 풀)과 같이 정한다.
3. 각 조건 3회 반복한다(8절). 이번에는 1회씩이다.
4. P4(ISE-189) 뒤에는 처리량이 바뀌므로 R3 값을 다시 계산한다.

## 8. 한계

- 노트북 한 대(16코어, Docker Desktop 7.6GB)에서 k6와 전체 스택이 같이 돌았다. Gateway Redis 차단기 503처럼 측정 환경에서 생긴 오류가 섞인다.
- P0''에서는 Tomcat 연결 수를 직접 재지 못했다. 7절 측정에서 MBean 지표를 켜 확인했다.
- 각 측정은 1회다. 무너지는 모양이 세 번 모두 같아 반복의 의미는 작다고 봤다. 다만 대응 후 측정은 기준을 아슬아슬하게 넘을 수 있어 3회 반복하기로 했다. 7절은 아직 1회씩이다. 첫 반복을 이어서 돌리던 중 노트북 메모리가 모자라 백그라운드 실행이 멈췄다.

## 9. 발표·포트폴리오 포인트

- "메모리를 늘리고 GC를 바꿔도 회복하지 못했다"에서 출발했다. 그래서 자원 부족이 아니라 시한 설계 문제라는 결론에 측정 근거가 있다.
- 지표 세 개(처리 중 요청 200 = 스레드 상한, 커넥션 대기 197, 서버 200 5,015건 대 사용자 성공 19건)로 "서버가 버려진 일을 하고 있다"를 보였다.
- 리틀의 법칙으로 서버 안 지연(14초)과 회복 시간(약 10분)을 계산했고, 실측과 맞았다.
- 대응 원칙은 "안쪽 시한을 바깥 시한보다 짧게"다. 타임아웃을 계층 사이에서 맞추는 일반 원칙으로 설명할 수 있다.
- 503을 출처별로 나눠(Eureka 이탈과 인증 차단기) 측정 환경의 잡음과 서버 문제를 섞지 않았다.
