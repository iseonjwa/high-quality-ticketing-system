# P4b 좌석 배치 캐시: 로컬 메모리 대 Redis 비교 (ISE-79)

상태: 측정 끝(각 조건 1회). 작성: 좌석 선점 담당 최권우 요청으로 Claude Code. 측정 정본은 측정 브랜치 `experiment/ISE-79-k6-steps`의 `reservation-service/k6/STEPS.md` "P4b 배치 캐시 로컬 대 Redis" 예상·실측 절이고, 코드는 같은 브랜치 `6f89bbbb`(`SeatLayoutCache`, `compose.layout-redis.yml`)다. 본 구현은 좌석 조회 담당(반효승)의 ISE-204이므로 이 문서는 근거로 넘긴다.

## 1. 결론

측정한 세 조건 모두에서 로컬 캐시가 앞섰다. Redis가 앞선 것처럼 보인 지표는 좌석 조회가 먼저 실패해 뒤 단계(선점·DB) 부하가 줄어든 결과라 장점이 아니다.

| 조건 | 대표 지표 | 로컬 | Redis |
|---|---|---|---|
| Gateway 경유 L(초당 100명) | 매진 전 좌석 조회 p95 | 7.0ms | 38.3ms |
| 같은 회 | 좌석 조회 한 건당 reservation-service CPU | 약 5.5ms | 약 25ms |
| 직접 호출 M(매진 피함) | 좌석 조회 99% 이상 버틴 단계 | 640명 | 160명(320명 64.9%) |
| 같은 회 | 서버 좌석 조회 200 최대 | 초당 1,244건 | 초당 397건 |
| Gateway 경유 CPU 4코어 S | 좌석 조회 99% 이상 버틴 단계 | 160명 | 40명 |

원인은 Redis 서버가 아니라 "바뀌지 않는 큰 값(1.3MB)을 요청마다 네트워크로 옮겨 15,000개 객체로 다시 만드는" 구조다. Redis 서버 CPU는 가장 바쁜 회에도 평균 0.16코어였다.

## 2. 무엇을 비교했나

- 로컬: P4b 그대로. 배치(구역·열·번호·등급·가격 15,000석)를 인스턴스 메모리(`ConcurrentHashMap`)에 만료 없이 둔다. 같은 회차를 동시에 처음 읽으면 한 요청만 DB에 간다.
- Redis: 배치를 Jackson JSON 문자열 하나(1,344,751바이트, TTL 1시간)로 공유 Redis에 두고 좌석 조회마다 `GET`해 역직렬화한다. 키가 없으면 DB에서 읽어 넣는다. Spring Data Redis에서 흔한 방식이다. 로컬 근접 캐시는 두지 않았다(두면 로컬과 같아진다).
- 공통: 1초 상태 캐시(P4c), 정합성 수정 S1~S4, G1·R1·풀 10, 측정 환경 Gateway 차단기 완화. 사전 거절은 껐다. 같은 커밋에서 설정 `seatmap.layout-cache`만 바꿨다. 좌석 조회 시험 7개는 두 모드 모두 통과했다(응답 JSON 동일).
- 환경: Redis는 Gateway 인증·대기열과 같은 인스턴스 하나다(`maxmemory 128mb`, `noeviction`, AOF). reservation-service는 Lettuce 연결 하나를 모든 Redis 명령이 함께 쓰고(Spring Boot 기본, 풀 설정 없음), 공통 Redis 명령 시한은 100ms다(`config-repo/application.yml`).

| 지표 | 로컬 | Redis | 실제 이유 |
|---|---|---|---|
| 4코어 S 320명 선점 성공 · p95 | 75.0% · 2,526ms | 99.8% · 166ms | 좌석 조회가 먼저 실패해 선점까지 온 요청이 적다(전체 선점 52,020건 대 35,857건) |

## 4. 원인

1. 요청마다 1.3MB를 옮기고 다시 만든다. 로컬은 이미 만든 객체를 참조한다. Redis는 한 건마다 1.3MB를 받아 문자열로 디코딩하고 15,000개 레코드로 역직렬화한다. L에서 한 건당 CPU가 약 5.5ms에서 25ms로, 할당이 초당 259MB에서 1.85GB로 늘었다.
2. 할당이 GC를 키웠다. 힙(768MB)이 짧게 사는 큰 객체로 빨리 차서 GC가 L에서 약 17배 잦아졌고 Full GC가 생겼다(L 최대 367ms, 직접 M Full 115회).
3. 공유 연결과 짧은 시한이 지연을 실패로 바꿨다. Lettuce 연결 하나에 큰 응답이 줄을 서고, GC로 멈춘 동안 기다린 명령이 시한 100ms를 넘겼다. 직접 M의 좌석 조회 500 중 95%가 100~150ms에 끝났다. L의 500 341건도 Full GC 직후 2초 안에 몰렸다.
4. 공유 Redis의 메모리 상한에 닿았다. 새 회차를 처음 읽을 때 여러 요청이 함께 1.3MB를 `SET`하고, 큰 응답 버퍼가 겹쳐 128MB를 넘었다. `noeviction`이라 쓰기가 거절됐다. 같은 Redis를 쓰는 대기열 입장·Gateway 인증 쓰기도 그 순간 거절될 수 있다.
5. CPU를 나눠 쓰면 더 일찍 무너진다. 4코어 S에서는 역직렬화·GC가 Gateway·DB와 같은 4코어를 먹어 80명부터 실패했다.

## 5. 예상과 대조

| 예상(측정 전) | 실측 |
|---|---|
| L 좌석 조회 p95가 5~15ms 오른다 | 31ms 올랐다(7.0 → 38.3ms). 예상보다 크다 |
| reservation-service CPU 1.5~2배 | 약 4.5배. 역직렬화 비용을 직렬화 수준으로 낮게 잡았고 GC 증가를 빠뜨렸다 |
| Redis 내보내기 초당 약 250MB | 초당 약 247MB로 맞다 |
| 직접 M 처리량 한계 30~50% 낮아짐 | 서버 좌석 조회 최대 68% 낮아졌다(1,244 → 397) |
| 4코어 S 한 단계 낮아짐 | 두 단계 낮아졌다(160명 → 40명) |
| Redis가 앞서는 지표 없음 | 맞다. 앞서 보인 지표는 부하가 깎인 효과다 |

## 6. ISE-204(본 구현)에 넘길 판단 근거

- 배치처럼 크고 판매 중에 거의 안 바뀌는 값은 로컬 캐시에 둔다. Redis에 통째로 두고 요청마다 읽는 방식은 피한다.
- 여러 대에서 무효화(좌석 생성·삭제, 추첨 설정·수정·종결 D9의 등급 변경)를 맞춰야 하면, 로컬 캐시를 그대로 두고 Redis는 무효화 알림(Pub/Sub)이나 버전 번호 확인에만 쓴다. 값 자체는 옮기지 않는다.
- 측정하지 않은 대안: 압축 형식(열 배열·이진)과 Redis 연결 풀은 차이를 줄이겠지만 요청마다 옮기고 역직렬화하는 일은 남는다. 이 측정에서 근거가 없으므로 수치로 말하지 않는다.
- 한계: 각 조건 1회이고 local Docker 측정이다. 방향은 세 조건이 같지만 절대 수치는 배포 측정에서 다시 본다. 직접 M의 로컬 1,280명은 k6 메모리 상한으로 재지 못했다.
