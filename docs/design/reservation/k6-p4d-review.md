# P4d(좌석 조회 응답 JSON 재사용)를 다시 볼지 (ISE-79, 의논 초안)

상태: **판단 전.** 2026-11-09에 조건이 맞았지만 넣지 않았고, 2026-11-10 측정으로 그 근거가 바뀌어 다시 정할 거리가 됐다. 작성: 좌석 선점 담당 최권우 요청으로 Claude Code. 측정 정본은 측정 브랜치 `experiment/ISE-79-k6-steps`의 `reservation-service/k6/STEPS.md`다.

## 1. P4d가 무엇인가

좌석 조회(`GET /api/v1/schedules/{id}/seats`)는 P4c 뒤에도 요청마다 15,000석의 응답 객체를 만들고 약 830KB JSON으로 직렬화한다. P4c는 선점 가능 좌석 ID를 1초 동안 함께 쓰므로, 1초 안의 요청은 같은 `sections` JSON을 만든다. 다른 것은 `serverTime`과 `traceId`뿐이다. P4d는 상태 스냅숏마다 `sections` JSON 바이트를 한 번만 만들어 두고, 요청마다 바깥 부분만 쓴다. 응답 만들기·직렬화가 초당 요청 수에서 초당 1번으로 준다.

- 대가: 공통 응답(`SuccessResponse`) 직렬화를 거치지 않는 경로가 생긴다. JSON이 한 글자라도 다르면 프론트와 K1 스크립트가 깨지므로, P4a 때처럼 기존 경로와 바이트가 같은지 묶는 테스트가 필요하다.
- 담당: 좌석 조회는 concert 모듈(반효승)이고 본 구현은 ISE-189다. P4a~P4c도 측정은 측정 브랜치에서 직접 했고 본 구현은 ISE-189에 맡겼다. P4d를 넣더라도 같은 방식이다.

## 2. 지금까지의 경과

| 날짜 | 사실 | 판단 |
|---|---|---|
| 2026-11-09 | P4c S 확장(JFR) 1,280명에서 커넥션 대기 0, JFR 상위 메서드 중 Jackson 약 32%, 응답 만들기 약 24.5%. 계획 3-4절 조건(대기 평균 1 미만, Jackson ≥ 30%)이 모두 맞음 | 넣지 않음. 1,280명 한계가 k6(CPU 약 17코어)와 Gateway 차단기라, P4d가 줄일 reservation-service CPU가 클라이언트 수치에 드러나지 않는다고 봄([판단 기록](../../ai-judgments/kwonwoo/2026-11-09-k1-stop-at-p4c-skip-p4d.md)) |
| 2026-11-10 | k6 상한을 6GiB로 올리자 K1 S 1,280명이 100%, p95 32ms. F 3회에서 2회 100%, 1회 81.6%(차단기). reservation-service CPU 최대 6.2~6.7코어, Gateway 6.8~7.0코어, k6 7.6~7.8코어 | "남은 한계가 부하 생성기와 Gateway"라는 전제는 k6 상한이 만든 것이었다(TS-48). 근거가 "1,280명까지 병목이 없다"로 바뀜 |

## 3. 다시 볼 이유와 그러지 않을 이유

**다시 볼 이유**
- 1,280명에서 reservation-service가 6.5코어 안팎을 쓴다. JFR로는 그 절반 이상(약 57%)이 응답 만들기·직렬화다. local은 VM 32코어라 여유가 있지만, 배포 서버는 `m7i-flex.xlarge`(4 vCPU, 전체 스택이 같이 씀)다. 배포에서는 좌석 조회 CPU가 훨씬 낮은 속도에서 먼저 한계가 될 가능성이 크다.
- 830KB 응답은 네트워크도 쓴다. 초당 1,280건이면 약 1GB/s다. 배포 측정에서 응답 압축(gzip)을 보게 되면, P4d로 만들어 둔 바이트를 1초에 한 번만 압축할 수 있어 압축 CPU도 요청 수와 떼어 낼 수 있다(계획 3-2절의 gzip 후보와 이어짐).

**그러지 않을 이유**
- local에서는 1,280명까지 클라이언트 수치가 이미 100%라, P4d 효과는 reservation-service CPU와 서버 처리량으로만 보인다. 그보다 위 단계(2,560명)를 재면 k6가 830KB 응답을 받는 비용이 커져 측정 도구가 다시 한계가 될 수 있다.
- 1,280명 위에서는 Gateway 인증 차단기가 가끔 열린다(F 3회 중 1회). 이 조율이 끝나기 전에는 높은 단계 결과가 흔들린다.
- 코드 대가(공통 응답을 거치지 않는 경로, 바이트 비교 테스트)가 있고, 본 구현이 다른 담당(ISE-189)이다.

## 4. 선택지

| 안 | 내용 | 비용 | 남는 것 |
|---|---|---|---|
| 1 | **넣지 않고 마친다.** "조건은 맞았지만 local에서는 1,280명까지 병목이 아니었다"로 기록한다 | 없음 | 배포 환경에서 CPU 한계가 나와도 근거 측정이 없다 |
| 2 | **배포 환경 측정 때 다시 본다(추천).** 지금은 넣지 않고, 배포 측정에서 좌석 조회가 reservation-service CPU로 먼저 막히면(커넥션 대기 평균 1 미만 + CPU 포화) 그때 P4d를 넣는다. 조건은 계획 3-4절 그대로 쓰고 "앱 CPU 포화"를 더한다 | 지금은 없음. 배포 측정 때 P4d 구현과 측정 1회 | 조건부 단계의 원칙(직면한 병목만 고친다)을 지키면서 배포 환경으로 판단을 넘긴다 |
| 3 | **지금 측정 브랜치에서 넣고 잰다.** K1 L 1회와 S 확장 1회(가능하면 2,560명 단계 추가)로 reservation-service CPU·서버 처리량을 P4c와 비교한다 | 구현과 바이트 비교 테스트, 측정 약 1시간 | "CPU를 얼마나 줄였나" 수치가 사례에 더해진다. 클라이언트 수치는 같을 가능성이 크다 |

추천 이유(2안): local 측정은 1,280명까지 서버 쪽 병목이 없다는 결론으로 닫혔고, P4d가 겨냥하는 자원(앱 CPU, 네트워크)은 배포 환경에서 훨씬 빨리 한계에 닿는다. 한계가 보이는 곳에서 재야 효과가 사례로 남는다. 다만 발표에서 "조건표대로라면 다음 단계였다"는 이야기를 숫자로 닫고 싶다면 3안이 낫다.
