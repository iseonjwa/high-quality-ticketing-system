# 좌석 선점 k6 부하 시나리오와 병목 단계별 개선 계획 (ISE-79)

상태: 새 기기에서 base부터 F까지 단계 측정 완료(2026-11-10, 결과는 5-5절). 아래는 이전 기록이다. P0(S0), 배포 메모리(P0'), G1(P0'') 측정 완료. 단계 순서를 P4 우선으로 바꿨고, 그동안 선점 경로만 재는 K1-H(1-5절)를 더해 기준선을 쟀다. 2026-11-06에 측정 종류(부하·스트레스·회복, 1-6절)를 나누고 단계를 다시 정했다(3절). 개선 단계 전 (2026-11-04 작성, 2026-11-05 재측정, 2026-11-06 개정, 좌석 선점 담당 최권우 요청으로 Claude Code가 작성·측정). 결과는 5-1~5-4절, 과부하 뒤 회복 문제(B8)는 [k6-overload-recovery.md](k6-overload-recovery.md)

대기열이 초당 100명씩 5분 동안 입장시키는 상황을 k6로 재현한다. 이 문서는 그때 좌석 선점 경로에서 예상되는 병목, 기본 방법부터 쌓아 가는 개선 단계, 단계마다의 트레이드오프를 정한다. 병목 순위는 코드를 읽고 세운 가설이다. 근거로 2026-11-03 JUnit 근사 측정([concurrency-results.md](concurrency-results.md))을 함께 쓴다. 단계별 실측은 P0 기준선을 잰 뒤 이 문서에 채운다.

- 근거: SA 3-1(측정 방식), 3-3(입장 속도 역산), 9-4(숫자 기준), 12-7(핵심 쿼리)
- 관련: 정합성 단계 S0~S4는 [concurrency-scenarios.md](concurrency-scenarios.md), 부하 시나리오 L1~L6은 [load-test-scenarios.md](load-test-scenarios.md)에 있다. 이 문서의 시나리오는 L1~L6에 더하는 K1이다.
- JUnit 근사(`SeatHoldLoadTest`)는 부하 생성기와 앱이 같은 JVM에 있고 Gateway를 거치지 않는다. 그래서 이번 측정은 Gateway를 지나는 실제 HTTP 경로로 k6에서 다시 한다.

## 1. 시나리오 K1: 대기열 입장 직후 선점

### 1-1. 가정

| 항목 | 값 | 근거·비고 |
|---|---|---|
| 입장 속도 | 초당 100명, 5분(300초), 총 30,000명 | 사용자 지정(2026-11-04, 1분에서 5분으로 바꿈). `config-repo`의 현재 `queue.admit-per-second`는 50(SA 9-4 임시값)이라 그 2배다 |
| 부하 모델 | 열린 모델(도착률 고정) | 대기열은 응답 속도와 상관없이 일정 속도로 사람을 들여보낸다. 서버가 느려져도 도착이 줄지 않아야 실제와 같다 |
| 사용자 1명의 흐름 | 좌석 조회 → 1~3초 고민 → 선점(1~2석). 409면 좌석을 다시 조회하고 최대 2번 더 선점. 조회 결과에 선택 가능한 좌석이 없으면 선점하지 않고 끝낸다 | 409 뒤 재시도가 요청 수를 불린다. 재시도 횟수는 `[가정]`. 매진 화면에서 선점 버튼을 누를 수 없는 프론트 동작을 따른다 |
| 좌석 | 회차 1개, 15,000석(SA 3-2) | 30,000명 × 평균 1.5석 = 약 45,000석을 원하므로 측정 중에 매진된다(1-2절) |
| 좌석 선택 | 70%가 앞 구역 10%(1,500석)에서, 30%는 전체에서 무작위 | 인기 좌석 쏠림. 비율은 `[가정]` |
| 인증 | local은 k6가 반복마다 Access 토큰과 입장 토큰(`X-Entry-Token`)을 직접 서명한다(`TOKEN_MODE=sign`). 배포 환경은 ISE-191에서 정한다 | 토큰 발급 부하는 이 시나리오에서 뺀다. 처음에는 ISE-25 도구로 미리 발급한 CSV를 쓰려 했다. 3만 명 입장 토큰을 10분 유효 시간 안에 미리 받을 수 없어 서명 방식으로 바꿨다([README](../../../reservation-service/k6/README.md) 5절) |
| 경로 | k6 → Gateway → reservation-service → PostgreSQL | Gateway 타임아웃 3초(SA 9-4)가 판정에 들어간다 |

"동시 사용자 100명이 1초 간격으로 들어온다"를 "VU 100명이 1초마다 요청한다"(닫힌 모델)로 읽을 수도 있다. 닫힌 모델에서는 서버가 느려지면 요청도 줄어 병목이 가려진다. 대기열 뒤의 상황에는 열린 모델이 맞아서 그것을 기본으로 둔다. 닫힌 모델은 비교용으로 한 번 돌린다.

### 1-2. 예상 요청량

사용자 한 명이 내는 요청은 `조회 (1 + k) + 선점 (1 + k)`다. k는 409로 다시 시도한 평균 횟수다.

| k | 좌석 조회 req/s | 선점 req/s | 합계 req/s |
|---|---|---|---|
| 0 (충돌 없음) | 100 | 100 | 200 |
| 0.5 | 150 | 150 | 300 |
| 1.0 | 200 | 200 | 400 |

고민 시간이 1~3초이므로 같은 순간 서버 안에 있는 사용자는 리틀의 법칙으로 약 100명 × 2초 = 200명이다.

5분 동안 수요가 좌석의 약 3배라 측정은 두 구간으로 나뉜다.

| 구간 | 시점(추정) | 요청 모양 | 보는 것 |
|---|---|---|---|
| 판매 구간 | 0초 ~ 약 100~150초 | 조회와 선점이 섞인다. 선점이 모두 성공해도 초당 약 150석(100명 × 1.5석)이 팔리므로 15,000석 소진에 최소 약 100초가 걸린다. 409와 실패가 있으면 더 길다 | 선점 p95·p99, 커넥션 대기, 잠금 대기 |
| 매진 뒤 구간 | 매진 ~ 300초 | 새로 들어온 사용자는 조회 1번으로 끝난다. 매진 직전에 들어온 사용자의 재시도가 잠깐 몰린다 | 조회 p95·p99, CPU·GC. 좌석 조회만 남은 부하를 버티는지 |

두 구간을 한 숫자로 합치면 매진 뒤의 가벼운 409·조회가 선점 지연을 희석한다. 그래서 결과는 구간을 나눠 적는다(5절). 매진 시각은 대사 SQL로 마지막 선점 성공 시각을 뽑아 정한다.

### 1-3. k6 구성

스크립트는 [`reservation-service/k6/k1-seathold.js`](../../../reservation-service/k6/k1-seathold.js)이고, Docker 이미지로 돌린다. 실행 방법과 준비 상태는 [그 폴더의 README](../../../reservation-service/k6/README.md)에 있다. 아래는 핵심 설정이다.

```javascript
export const options = {
  scenarios: {
    k1_admission: {
      executor: 'constant-arrival-rate', // 열린 모델: 응답이 느려져도 초당 100명씩 시작한다
      rate: 100, timeUnit: '1s', duration: '5m',
      preAllocatedVUs: 300, maxVUs: 1000, // 시작하지 못한 반복은 dropped_iterations로 남는다
    },
  },
  summaryTrendStats: ['avg', 'p(50)', 'p(95)', 'p(99)', 'max'], // 기본 요약에는 p(99)가 없다
  thresholds: {
    'http_req_failed{expected:false}': ['rate<0.01'], // 5xx·타임아웃만 실패로 센다. 409는 정상 거절이다
    'http_req_duration{api:hold}': ['p(95)<1000'],     // 목표값은 [가정], P0 측정 뒤 정한다
    'http_req_duration{api:seats}': ['p(95)<500', 'p(99)<1000'],
  },
};
```

- `responseCallback`으로 201·409를 `expected`로 표시한다. 409를 실패로 세면 인기 좌석 거절이 오류율에 섞인다.
- 요청에 `api:seats`, `api:hold` 태그를 붙여 두 API의 지연을 나눠 본다. 태그별 p99가 요약에 나오게 임계값을 태그마다 하나 이상 건다. k6는 임계값이 걸린 태그 조합만 따로 요약한다.
- 구간별 수치는 k6 요약만으로 나눌 수 없다. `--out json=k6-result.json`(또는 Prometheus 원격 쓰기)으로 요청별 시각을 남기고, 매진 시각 전후로 잘라 p95·p99를 다시 계산한다.
- `dropped_iterations`가 0보다 크면 부하 생성기가 도착률을 못 맞춘 것이다. 서버 병목과 구분하려고 따로 적는다.
- k6는 대상과 다른 기기에서 돌린다(SA 3-1). 같은 기기에서 돌리면 환경 기록표에 적는다. JUnit 근사에서 같은 S0의 처리량이 2배 넘게 흔들린 원인 후보가 부하 생성기와 앱의 CPU 공유였다.

### 1-4. 판정과 함께 볼 지표

| 지표 | 위치 | 병목 신호 |
|---|---|---|
| p95·p99, 201·409·5xx·타임아웃 건수 | k6 요약 | p95가 Gateway 3초에 가까워지면 타임아웃이 오류로 바뀐다 |
| `hikaricp_connections_pending`, `hikaricp_connections_acquire_seconds` | Prometheus | 대기 수가 0보다 크게 유지되면 풀 병목 |
| `http_server_requests_seconds` | Prometheus | k6 지연과 차이가 크면 Gateway·네트워크 구간 |
| `pg_stat_activity`의 `wait_event_type = 'Lock'` 수 | 10초마다 SQL | 수십 이상이면 좌석 행 잠금 병목 |
| 프로세스 CPU, GC 일시 정지, 응답 바이트 | Prometheus·k6 `data_received` | 좌석 조회 응답 직렬화 병목 |
| 중복 판매, `held_count` 불일치 | 측정 뒤 대사 SQL | 0이 아니면 그 실행의 처리량은 버린다 |

### 1-5. 보조 시나리오 K1-H: 선점 경로만 따로 재기 (2026-11-05 추가)

K1에서는 좌석 조회(B2)가 먼저 무너져 선점까지 가는 요청이 거의 없다(5-1~5-3절). 그러면 선점 쪽 개선(P1~P3)을 넣어도 "선점 0건 → 0건"이라 차이가 보이지 않는다. P4(좌석 조회 경량화)는 반효승 담당(ISE-189)이라 끝날 때까지 시간이 걸린다. 그래서 좌석 조회를 떼고 선점 경로만 재는 K1-H를 더한다.

| 항목 | K1 | K1-H |
|---|---|---|
| 좌석 조회 | 시도마다 1번 | 측정 시작 전 `setup`에서 1번. 선택 가능 좌석 ID를 응답 순서대로 기억한다 |
| 사용자 1명의 흐름 | 조회 → 1~3초 고민 → 선점, 409면 조회부터 다시 | 1~3초 고민 → 목록에서 골라 선점, 409면 0.5~1초 뒤 목록에서 다시 고름 |
| 같게 둔 것 | - | 열린 모델, 초당 100명, 300초, 재시도 2번, 인기 구역 쏠림(70%가 앞쪽 10%), 1~2석, 토큰 서명 방식, P0'' 환경 |
| 묻는 질문 | 서비스 전체가 버티는가 | 선점 경로가 단계마다 얼마나 좋아졌는가 |
| 실행 | `run.sh` | `SEAT_MAP=once`를 붙인다. 결과 파일 이름에 `holdonly`가 붙는다 |

해석할 때 주의할 점:
- 좌석 목록이 측정 시작 시점에 고정이다. 판매가 진행될수록 이미 잡힌 좌석을 골라 409가 K1보다 많다. 경합이 실제보다 세다.
- 좌석 조회가 커넥션을 나눠 쓰지 않아 실제보다 좋게 나온다. K1-H 수치는 선점 경로의 상한으로 읽는다.
- 매진을 응답으로 알 수 없다. 매진 뒤에는 모든 선점이 409다. 매진 여부와 시각은 측정 뒤 DB로 확인한다.
- K1-H 결과로 K1 통과를 말하지 않는다. 결과 표는 5-4절에 따로 두고, 최종 판정은 P4 뒤 K1로 한다.

단계별 측정 흐름은 3절 끝의 그림에 있다.

### 1-6. 측정 종류: 부하·스트레스·회복 (2026-11-06 추가)

단계마다 같은 세 가지를 잰다. 고정 부하만 재면 초당 100명에서 모두 실패하는 동안 단계 차이가 보이지 않는다(5-3절). 한계점만 재면 목표 부하를 버티는지 말할 수 없다.

| 종류 | 질문 | 부하 모양 | 판정 `[가정]` |
|---|---|---|---|
| 부하(L) | 목표 부하를 버티는가 | K1: 열린 모델 초당 100명, 300초. 시작 전 60초 동안 초당 10명으로 워밍업 | 오류(5xx·타임아웃) 1% 미만, 조회 p95 500ms·선점 p95 1,000ms 이하, 대사 불일치 0 |
| 스트레스(S) | 어디까지 버티고, 넘으면 어떻게 무너지는가 | 단계마다 60초씩 도착률을 두 배로 올린다. K1: 초당 5 → 10 → 20 → 40 → 80 → 160 → 320명. K1-H: 50 → 100 → 200 → 400 → 800명 | 오류 1% 미만이고 p95가 Gateway 시한(3초)의 절반 이하인 마지막 단계가 "버틴 최대 속도"다. 그다음 단계에서 무엇이 먼저 막혔는지(풀, CPU·GC, 잠금, 발생기)를 적는다 |
| 회복(R) | 한계를 넘긴 뒤 스스로 돌아오는가 | S가 끝난 뒤 120초 동안 10초마다 좌석 조회 한 건(`RECOVERY_SECONDS=120`) | 30초 안에 처리 중 요청·커넥션 대기 0, 탐침이 1초 안에 200([k6-overload-recovery.md](k6-overload-recovery.md) 6절) |

- **워밍업:** 오픈 시각에 서버는 이미 오픈 전 조회를 받으며 떠 있다. K1-H 기준선에서 느린 요청이 JIT 전인 첫 1분에 몰렸다(5-4절). 실제 상황에 맞추려고 부하·스트레스 모두 앞에 60초 워밍업을 두고, 워밍업 구간은 결과에서 뺀다(`WARMUP_SECONDS=60`). 처음 제안은 30초였다(2026-11-06 결정).
- **스트레스 실행:** `MODEL=ramp`로 한 번에 돌린다. 요청마다 `stage` 태그(그 단계의 초당 도착 수)가 붙어 단계별 p95와 오류율을 요약에서 바로 읽는다. 한계를 넘긴 뒤의 단계는 앞 단계의 적체가 섞이므로, 판정은 처음 무너진 단계까지만 쓴다.
- **잡음 분리:** 지연이 수 ms인 503은 Gateway 인증 Redis 차단기에서 나온 것이다(5-4절). 원자료 CSV에서 따로 세고 오류율에서 뺀 값과 뺀 사유를 같이 적는다. 노트북 경합이 결과를 크게 흔든다(B8에서 같은 조건의 사용자 성공이 1,463~3,432건). 측정 중에는 브라우저·IDE 빌드를 끄고 `docker stats`로 k6 컨테이너 CPU를 같이 기록한다.
- **반복:** 단계를 고르는 탐색 측정은 1회만 한다. 발표에 쓰는 비교점(기준선, 각 묶음의 마지막 단계, 최종)만 3회 반복하고 중앙값과 범위를 적는다. 모든 단계를 3회씩 하면 한 단계에 약 40분이 걸려 단계 수를 줄여야 하기 때문이다.
- **넣지 않는 것:**
  - 스파이크 테스트: 이 경로 앞에는 대기열이 있다. 사용자는 READY를 폴링(3초 + jitter)으로 알게 되므로 입장이 고르게 퍼진다. 오픈 순간의 폭주는 대기열 진입(Q1, ISE-181)이 받는다.
  - 장시간(soak) 테스트: 15,000석이 2~5분 안에 팔린다. 그 뒤의 두 번째 파도인 선점 만료는 X1(ISE-181)이 본다.

## 2. 예상 병목

요청 하나가 지나는 순서대로 적었다. "예상 순위"는 이 시나리오에서 먼저 막힐 것으로 보는 순서다. 측정으로 바뀐 순위는 굵게 표시했다.

| # | 위치 | 왜 막히나(코드 근거) | 예상 순위 | 확인 지표 |
|---|---|---|---|---|
| B1 | DB 커넥션 풀 | `config-repo/reservation-service.yml`의 `maximum-pool-size`가 5다. Tomcat 스레드는 기본 200이라 요청 대부분이 커넥션을 기다린다. JUnit 근사에서 풀 5의 처리량은 VU 50부터 멈췄고(S0 446~478 req/s), 커넥션 대기 스레드가 최대 196개였다 | 1 → **2 (실측)**: K1-H 초당 100명에서는 첫 30초만 대기가 생겼다(5-4절). 좌석 조회가 먼저 막는다 | `hikaricp_connections_pending` |

| B3 | 선점 트랜잭션 길이 | `SyncSeatHoldService#hold` 하나가 `@Transactional`이다. 커넥션을 쥔 채 DB 왕복을 약 12~14번 한다(멱등키 조회, 회차 조회, 좌석 조회, 매수 조회, 매수 반영, 좌석 UPDATE, 예매·예매 좌석·이력·선점 요청 INSERT, 커밋). 결제 토큰 HS256 서명도 트랜잭션 안에서 한다. 왕복 수는 코드를 읽고 센 값이다 | 2 | Zipkin 구간, 커넥션 점유 시간 |

| B5 | 인기 좌석 행 잠금 | 같은 좌석을 잡으려는 요청이 좌석 UPDATE에서 앞 트랜잭션의 커밋을 기다린다. 기준선에는 `lock_timeout`이 없어 그동안 커넥션도 쥐고 있다. JUnit 근사의 L2·L6에서는 잠금 대기 세션이 최대 0~6개로 B1보다 작았다. 풀을 늘려 B1이 풀리면 이 병목이 드러날 것으로 본다 | 3~4 | 잠금 대기 세션 수, `api:hold` 409 p95 |
| B6 | 409 재시도 증폭 | 거절된 사용자가 좌석을 다시 조회하고 다시 선점한다. 지연이 길어질수록 다른 사람이 그 좌석을 먼저 잡아 409가 늘고, 409가 다시 요청을 늘린다. 매진 직전에는 남은 좌석이 적어 409 비율이 가장 높다 | B1·B2가 생기면 함께 커진다 | 사용자당 요청 수, k |
| B7 | 정합성 수정의 비용 | ISE-79 S1~S3은 요청당 왕복을 3번 늘린다(매수 INSERT, 선점 결과 UPDATE, `set_config`). JUnit 근사에서 VU 400 처리량 중앙값이 S0 1,125에서 S3 669 req/s로 내려갔다(편차 큼) | 수정 뒤 B3을 키운다 | 단계별 처리량 |
| B8 | 과부하 뒤 회복 불가 | (P0 측정 뒤 추가) Gateway가 3초에 포기한 요청도 서버는 끝까지 처리한다. 서버 안의 대기 한도(Tomcat 연결 8,192, 커넥션 대기 30초)가 Gateway 시한보다 훨씬 커서 버려진 일이 쌓이고, 부하가 끝나도 비우는 데 약 10분이 걸린다. P0에서는 GC 정지로 Eureka 갱신이 끊겨 전체 503도 겹쳤다. 원인 분석과 대응 설계는 [k6-overload-recovery.md](k6-overload-recovery.md). 2026-11-05 대응 측정에서 커넥션 대기 1초(R1)만으로 10초 안에 회복했다(같은 문서 7절) | B2와 함께 1순위 | 처리 중 요청 수, `hikaricp_connections_pending`, 부하 뒤 회복 시간 |

병목이 아닐 것으로 보는 것도 적는다. 측정에서 다르게 나오면 이 판단을 고친다.
- 매수 행(`user_schedule_quotas`)은 사용자마다 따로라 다른 사용자끼리 경합하지 않는다.
- 데드락은 JUnit 근사의 C2·C7에서 0이었다. 좌석 ID 정렬과 UPDATE 한 문장 덕분이다.
- Gateway의 입장 토큰 검증은 HS256 서명 확인이라 요청당 비용이 작다. 다만 Gateway도 같은 기기에서 돌면 CPU를 나눠 쓴다.
- 만료 스케줄러: 선점 유지 시간이 5분이라 첫 선점이 측정 끝 무렵(약 5분 뒤)에야 만료된다. 측정 중에는 스케줄러를 끈다([load-test-scenarios.md](load-test-scenarios.md) 2절 3번). 그래서 매진 뒤 좌석이 다시 풀리지 않는다. 만료가 섞이는 상황은 L5에서 따로 본다.

## 3. 단계별 개선 계획

원칙은 [concurrency-scenarios.md](concurrency-scenarios.md) 1절과 같다. 한 단계에 변경 하나만 넣고, 단계마다 같은 조건으로 다시 잰다. 앞 단계일수록 바꾸는 범위가 작고 되돌리기 쉽다. 각 단계의 구체적인 변경과 대가는 4절에 있다.

### 3-1. 단계 (2026-11-06 2차 개정: 기본 코드에서 직면 순서로)

수정하지 않은 기본 코드에서 시작해, 측정에서 직면한 병목 하나를 고치고 다시 재는 순서로 쌓는다. 같은 날 1차 개정은 R1·G1을 미리 켠 환경을 기준으로 삼았는데, 그러면 회복 실패와 GC 정지를 겪는 과정이 사례에서 빠진다. 그래서 G1과 R1도 단계로 둔다.

- **기준 환경:** 배포 메모리(gateway 768MB, reservation-service 1,152MB), 선점 만료 스케줄러 끔, 60초 워밍업, 지표·GC 로그 켬. 코드와 그 밖의 설정은 dev 그대로다. 나머지는 1-6절의 측정 기준을 따른다.
- **측정 브랜치:** `experiment/ISE-79-k6-steps`(머지하지 않음). 한 단계가 커밋 하나다. 설정 단계는 `step-overlays.txt`에 덮어쓰기 한 줄을 더하는 커밋이다. 실행 도구와 단계 기록은 그 브랜치의 `reservation-service/k6/STEPS.md`에 있다.
- **반영:** 다른 이슈의 코드는 이슈마다 따로 브랜치를 파서 반영한다. P4는 ISE-189(반효승), R1은 ISE-196이고, G1·P1은 공유 설정이라 contract 이슈로 제안한다. ISE-79 브랜치에는 선점 모듈 코드와 측정 기록만 옮긴다.
- **순서는 예상이다.** 앞 단계 측정에서 실제로 막힌 곳이 다음 단계다. 실측이 예상과 다르면 실측을 따르고 이유를 이 문서에 적는다.
- **측정 환경:** 최종(F)까지 모두 local에서 잰다. 배포 환경 성능 테스트는 나중에 따로 한다.

### 3-2. 바꾼 점과 이유 (2026-11-06)

- **R1을 회복 단계로 뗀다.** (2차 개정에서 바뀜: 미리 켜 두지 않고 base·G1에서 회복 실패를 직면한 뒤 단계로 넣는다. 아래는 1차 개정의 이유다.) 처음 P1은 풀 확대와 커넥션 대기 시한 단축을 한 단계에 묶었다. 시한 단축은 B8 측정에서 처리량이 아니라 회복을 푸는 변경으로 확인됐다(R1). 둘을 묶으면 무엇이 효과를 냈는지 가릴 수 없다. R1 없이 스트레스를 걸면 한계를 넘은 단계의 적체가 10분 가까이 남아 다음 단계와 다음 실행을 오염시킨다. 그래서 P4a부터는 R1을 켠 채 잰다. 비교 기준은 같은 이미지로 다시 잰 `ENTITY + R1`이다. R1이 배포 설정에 들어가지 않으면(ISE-196) 측정 전용 덮어쓰기(`compose.b8-r1.yml`)로 켠다.
- **P4d를 더한다(조건부).** P4c까지 해도 요청마다 15,000석의 응답 객체를 만들고 약 830KB JSON으로 직렬화한다. 1초 안에 들어온 요청은 같은 상태 스냅숏을 보므로 JSON도 같다. 다른 것은 `serverTime`과 `traceId`뿐이다. 그 부분만 요청마다 쓰면 직렬화 비용이 초당 요청 수에서 초당 1번으로 준다. P4c 결과에서 CPU·GC가 여전히 한계일 때만 넣는다. 응답 압축(gzip)은 같은 자리의 다른 후보다. 네트워크 830KB를 크게 줄이지만 요청마다 압축 CPU가 든다. local에서는 네트워크가 병목이 아니므로 배포 환경 측정에서 발생기 대역폭이 한계일 때 본다(load-test.md 2-1절).
- **S4를 독립 단계로 둔다.** 처음 계획은 "K1을 S0과 S4에서 한 번씩 잰다"였지만 S4를 재지 않았다. 정합성 수정(S1~S4)은 처리량을 낮춰도 넣어야 하는 변경이다. "정합성을 고쳐 잃은 처리량을 P1·P3로 되찾았다"가 선점 쪽 사례의 줄거리라서, S0과 S4의 차이를 K1-H 스트레스로 먼저 잰다. S1~S4 코드는 측정용 워크트리 `ise-79-measure`에 커밋되지 않은 채 있어 측정 브랜치로 옮기는 일이 먼저다.
- **P2를 조건부로 줄인다.** K1-H 기준선에서 선점 p95는 첫 1분 뒤 20ms 미만이었다(5-4절). 결제 토큰 서명(HS256)은 마이크로초 단위로 예상되어 효과가 작다. Zipkin이나 서버 지표로 트랜잭션 안 비DB 작업 비율을 먼저 재고, 10% 미만이면 측정 없이 "효과 작음"으로 기록한다.
- **P5를 조건부로 줄인다.** Redis 거절은 좌석 상태를 두 곳에 두는 복잡도가 크다. K1-H의 409는 p95 16ms로 이미 싸다. 다만 201·409 중 409가 87%였으므로(5-4절), 한계점에서 409가 커넥션을 오래 쥐는 것이 보이면 그때 넣는다. 거절 판단에만 쓰고 허용 판단에는 쓰지 않는 원칙은 유지한다.
- **P1의 순서를 P4 뒤로 둔다.** 5-3절의 판단과 같다. 요청당 비용을 줄이기 전에 풀을 늘리면 동시에 처리하는 조회가 늘어 GC가 다시 병목이 된다. K1-H에서는 P1을 먼저 잰다. 좌석 조회가 없어 이 문제가 없기 때문이다.
- **P6·P7을 뺀다.** P6(2대, 읽기 복제본)은 local 노트북 메모리(Docker 7.6GB)로 띄울 수 없고, 배포도 EC2 한 대다. 서비스 대수를 늘리는 변경은 사례가 아니라 구성 변경이라 이 계획의 질문("요청당 비용을 어떻게 줄였나")과 다르다. P7은 ISE-18의 동기형·접수형 비교에서 다룬다.

목표를 못 맞추면 대기열 입장 속도 N을 낮추는 것도 답이다. 대기열의 역할이 뒤쪽이 감당할 만큼만 들여보내는 것이기 때문이다. SA 3-3 식(`L_max = μ / r`, `λ = L_max / W`)에 스트레스 측정의 "버틴 최대 속도"를 μ로 넣어 N을 역산한다. N을 바꾸는 것은 대기열 담당(권영은)과 정한다.

### 3-3. 이전 순서 (기록)

2026-11-04 처음 순서는 P0 → P1 → P2 → P3 → P4 → P5 → P6 → P7이었다. "P0 결과에서 B2가 B1보다 먼저 막히면 P4를 P2 앞으로 당긴다"는 조건을 두었고, 2026-11-05 측정에서 그 조건에 걸려 환경 단계 P0'·P0''를 넣고 P4를 P4a·P4b·P4c로 나눠 P1 앞에 두었다(5-3절). 2026-11-06 1차 개정은 그 위에서 R1·S4·P4d를 더하고 P2·P5를 조건부로, P6·P7을 범위 밖으로 옮겼다. 같은 날 2차 개정에서 기준을 수정 없는 기본 코드로 바꾸고 G1·R1을 단계로, S4를 대사 위반이 나올 때의 조건부 단계로 바꿨다([판단 기록](../../ai-judgments/kwonwoo/2026-11-06-k6-steps-from-unmodified-base.md)).

### 3-4. 정합성 단계와 조건부 단계 (2026-11-06)

#### 정합성 수정 S1~S4: 무엇을 직면할 수 있나

S1~S4는 ISE-79의 본 작업(좌석 선점 경쟁 조건)이다. k6 결과와 관계없이 ISE-79 브랜치에 들어간다. 결함은 JUnit 동시성 테스트 C1~C7로 찾았다([concurrency-results.md](concurrency-results.md)). 그래서 k6 단계에서 정할 것은 "넣을지"가 아니라 "단계 순서의 어디에, 무엇을 근거로 넣는가"다. 넷은 결함이 생기는 조건이 달라 K1에서 직면할 수 있는지도 다르다.

| 수정 | 고친 결함(동시성 테스트) | 결함이 생기는 조건 | K1·K1-H에서 직면하나 |
|---|---|---|---|
| S1 매수 한도 | C4: 같은 사용자가 탭 4개로 동시에 선점하면 한도 4매를 넘어 8매까지 잡힌다. 매수를 읽고 검사한 뒤 더하는 사이에 다른 요청이 끼어든다 | 같은 사용자의 선점 요청이 동시에 둘 이상 | **직면하지 않는다.** k6 사용자는 한 번에 요청 하나만 보내고, 201을 받으면 끝내고, 오류면 포기한다. 한도(4매)에 닿기 전에 끝난다 |
| S2 멱등키 동시 진입 | C5: 같은 멱등키로 3번 연타하면 자기 요청끼리 부딪혀 409를 받는다 | 같은 멱등키 요청이 동시에 둘 이상(더블 클릭, 네트워크 재전송) | **직면하지 않는다.** k6는 요청마다 새 멱등키를 쓰고 재전송하지 않는다 |
| S3 잠금 대기 상한 | C3: 좌석 잠금을 오래 쥔 트랜잭션이 있으면 같은 좌석을 노린 요청이 끝없이 기다린다(5명 모두 2초 넘게) | 같은 좌석을 동시에 노리는 요청 + 앞 트랜잭션이 느릴 때 | **직면할 수 있다.** K1은 사용자 70%가 앞쪽 10% 좌석을 고른다. 서버가 느려지는 단계(GC 정지, 커넥션 대기)에서 앞 트랜잭션이 길어지면 잠금 대기가 쌓인다. 다만 동시성 테스트의 부하 근사에서는 잠금 대기가 생기기 전에 커넥션 풀이 먼저 막혔다(concurrency-results.md 5절 3번) |
| S4 만료 `SKIP LOCKED` | C6: 인스턴스 2개의 만료 스케줄러가 같은 만료 건을 서로 집어 헛수고 100건 | 만료 스케줄러가 두 곳 이상에서 동시에 돎 | **직면하지 않는다.** 측정 중에는 만료 스케줄러를 끄고 인스턴스도 하나다 |

그래서 S1~S4를 한 묶음으로 두지 않고 나눈다.
- **S3은 직면 조건부 단계다.** `step-run.sh`가 10초마다 행 잠금 대기 세션 수(`pg_stat_activity`의 `wait_event_type = 'Lock'`)를 남긴다. K1-H 스트레스의 처음 무너진 단계에서 잠금 대기 세션이 커넥션 풀의 절반(풀 5면 3개) 이상 이어지면 직면한 것으로 보고 S3을 넣는다. 잠금 대기가 거의 없으면 "k6에서는 잠금 대기 전에 다른 병목이 먼저 막았다"로 기록하고, S3은 S1·S2·S4와 함께 들어간다.
- **S1·S2·S4는 "다른 측정으로 직면한 결함"으로 넣는다.** 측정 결과로 넣지 않는 것이 아니라, 들어가야 하는 수정의 비용을 재는 단계다. 넣지 않고 끝까지 쌓으면 최종(F)이 실제로 배포되지 않을 코드를 재게 된다. 그래서 P1 앞에 넣고 K1-H 스트레스로 처리량이 얼마나 줄었는지 잰다. "정합성을 고쳐 잃은 처리량을 P1·P3로 되찾았다"가 선점 쪽 사례의 줄거리다.
- **k6로 직면하지 않는 결함은 동시성 테스트로 확인했다(2026-11-06).** 측정 브랜치 base 코드에서 C4·C5·C6이 모두 실패했다. C4는 30라운드 모두 한도를 넘어 최대 8매를 잡았다. C5는 자기 요청에 409가 60건 나왔다. C6은 헛수고가 100건이었다. 이전 S0 값과 같다. 기록은 측정 브랜치 `STEPS.md`에 있다.
- **넣는 방식(추천):** S1·S2·S4는 ISE-79 브랜치에 수정마다 커밋 하나로 넣고, 측정 브랜치에는 P1 앞에 같은 순서로 cherry-pick한다. 측정은 수정마다 K1-H 스트레스를 한 번씩 한다. 동시성 테스트의 부하 근사에서 S2(멱등키 행 INSERT·UPDATE)가 처리량을 가장 많이 낮췄으므로, 어느 수정이 얼마를 잃었는지 나눠 보이는 것이 사례에 낫다. S4는 만료 경로만 바꾸고 측정 중에는 만료 스케줄러를 끄므로 K1-H 결과가 바뀌지 않는다. 그래서 커밋만 하고 재지 않는다. ISE-79 브랜치 커밋은 S1 `5b2a9b4`, S2 `4eaa6d3`, S3 `3b9b0bf`, S4 `c307621`이다. 동시성 테스트는 모두 통과했다. C3은 처음에 최대 1,099ms로 목표 1초를 넘었다. `lock_timeout`이 잠금 시도마다 걸려 실제 상한이 약 1초이기 때문이라 목표를 1,500ms로 고쳤다(concurrency-results.md 4-3절).
- 대사 SQL(`invariants.sql`)은 단계마다 돌린다. 위반이 나오면 위 판단과 관계없이 그 결함을 직면한 것이다. 위반이 난 회의 처리량은 쓰지 않는다(1-4절).

#### 조건부 단계 P4d, P2, P5: 왜 조건부이고 어떻게 정하나

세 단계는 효과가 측정 결과에 달려 있는데, 넣으면 코드가 복잡해지거나 위험이 생긴다. 직면하지 않은 병목을 미리 고치지 않는다는 원칙대로, 판단할 지표를 미리 정해 두고 그 단계에 닿았을 때 측정값으로 정한다. 넣지 않은 단계도 "왜 넣지 않았는지"를 측정값과 함께 STEPS.md와 이 문서 5절에 남긴다.

| 단계 | 왜 조건부인가(대가) | 판단 시점 | 판단 지표와 기준 `[가정]` | 넣지 않으면 |
|---|---|---|---|---|
| P4d 응답 JSON 재사용 | 공통 응답(`SuccessResponse`) 직렬화를 거치지 않는 경로가 생긴다. JSON이 한 글자만 달라도 프론트와 K1이 깨져 바이트 비교 테스트를 따로 둬야 한다. 직렬화가 병목이 아니면 효과가 없다 | P4c의 K1 스트레스 뒤 | 처음 무너진 단계에서 ① 커넥션 대기가 거의 없고(Hikari 대기 평균 1 미만) ② JFR 프로파일에서 Jackson 직렬화가 앱 CPU 표본의 30% 이상 | 대기가 남아 있으면 P1로 간다. 직렬화가 30% 미만이면 다른 핫스팟을 JFR로 보고 계획을 다시 정한다 |
| P2 비DB 작업을 트랜잭션 밖으로 | 결제 토큰 서명을 커밋 뒤로 옮기면 "좌석은 잡혔는데 토큰이 없는" 상태가 생긴다. 멱등 재요청으로 복구되는지 따로 확인해야 한다. HS256 서명은 마이크로초 단위라 효과가 작을 것으로 본다 | P3 뒤 K1-H 스트레스 | 선점 한 건의 트랜잭션 시간 중 DB를 쓰지 않는 시간(서명, 회차·판매 기간 검사)의 비율이 10% 이상 | 측정 없이 "효과 작음"으로 기록한다 |
| P5 Redis 선거절 | 좌석 상태가 Redis와 DB 두 곳에 생긴다. Redis가 뒤처지면 잡을 수 있는 좌석을 거절할 수 있고, 만료·취소 때 지우는 경로가 늘어난다. K1-H 기준선의 409는 p95 16ms로 이미 싸다 | P3(또는 P2) 뒤 K1-H 스트레스 | 처음 무너진 단계에서 선점 409 요청의 처리 시간 합이 선점 요청 전체 처리 시간 합의 50% 이상(`http_server_requests_seconds_sum`을 상태별로 나눔). 선점 요청은 처리 시간 대부분 커넥션을 쥐므로 커넥션 점유 시간의 근사로 쓴다 | 409가 싸서 DB에 보내도 된다고 기록한다 |

- P5의 원래 내용 중 `lock_timeout`은 S3에 들어 있어 P5에서는 Redis 선거절만 본다.
- **정해야 할 것과 추천(2026-11-06):**
  1. **기준값 30%·10%·50%:** 그대로 출발점으로 두고, 측정 전에 이 문서에 고정한다. 결과를 본 뒤 기준을 옮기면 판단이 결과에 맞춰진다. 값이 기준의 ±5%p 안이면 "경계"로 적고 넣을지는 측정값을 보고 정한다.
  2. **P4d의 JFR:** 측정 브랜치에 JFR 덮어쓰기(`-XX:StartFlightRecording`, 기본 설정)를 두되, 모든 회에 켜지 않고 판단하는 회(P4c의 K1 S, P3의 K1-H S)에만 켠다. 기본 설정의 부하는 작지만 단계 비교 회와 조건을 같게 두려는 것이다. 단계(`step-overlays.txt`)가 아니라 관찰 옵션으로 `step-run.sh`에 둔다. 분석은 로컬 JDK의 `jfr` 명령으로 한다(런타임 이미지 `eclipse-temurin:21-jre`에 JFR이 들어 있다).
  3. **P2의 비DB 시간:** JFR로 잰다. 확인해 보니 앱 모듈의 추적은 `spring-boot-starter-zipkin`뿐이고 JDBC 계측(`datasource-micrometer` 등)이 없어 Zipkin에 DB 구간이 찍히지 않는다. 전용 타이머는 측정하려는 코드를 고쳐야 하므로 쓰지 않는다. `SyncSeatHoldService#hold` 아래 표본 중 결제 토큰 서명(`PaymentTokenIssuer#issue`)과 회차·판매 기간 검사가 차지하는 CPU 시간을 선점 요청의 평균 처리 시간과 비교한다. JFR 실행 표본은 CPU를 쓰는 시간만 잡으므로, DB 대기를 뺀 순수 계산 시간이라 이 질문에 맞다.
  4. **P5 근사의 검증:** base의 K1-H 스트레스 회에서 한 번 대조한다. 선점 요청 처리 시간 합(`http_server_requests_seconds_sum`, 선점 URI)과 Hikari 사용 시간 합(`hikaricp_connections_usage_seconds_sum`)의 차이가 20% 안이면 근사를 쓴다. 더 벌어지면 P5 판단은 JFR의 409 경로 표본으로 대신한다.

## 4. 단계별 트레이드오프

"적용 내용"은 무엇을 어떻게 바꾸는지 적는다. 코드 위치는 `reservation-service` 기준이다. 3절 표가 단계의 목적을, 이 표가 구체적인 변경과 그 대가를 적는다.

| R1 | **커넥션 대기 시한 줄이기.** `spring.datasource.hikari.connection-timeout`(커넥션을 기다리는 최대 시간, 기본 30초)을 1초로 줄인다. 기다리는 시간이 Gateway 제한(3초)보다 길면 사용자는 504를 받는데 서버는 30초까지 계속 기다리고, 그 일이 쌓여 부하가 끝나도 회복하지 못한다(B8) | 과부하 뒤 10초 안에 회복한다. 버려지는 일이 줄어 사용자가 받는 성공이 는다(실측, k6-overload-recovery.md 7절) | 몰릴 때 500이 빨리 나온다. 처리량 자체는 늘지 않는다 | 측정 완료. 낮은 속도 시험은 실행마다 reservation-service를 재시작해 깨끗한 JVM에서 쟀다. 초당 1명 시험의 첫 실행은 판매 기간이 지난 회차(이전에 만든 회차 1)를 잘못 골라 선점이 전부 `SALE_NOT_OPEN` 409였다. 그 실행은 버리고 새 회차로 다시 쟀다. 초당 2·5명 실행은 같은 회차였지만 좌석 조회 단계에서 끊겨 선점까지 가지 않았으므로 조회 수치는 그대로 쓴다.

#### 무너진 순서 (본 측정)

1. 좌석 조회 한 건이 회차 15,000석 엔티티와 조인한 공연장 좌석 엔티티를 모두 만들고, DTO와 약 830KB의 JSON으로 바꾼다(초당 1명 실행에서 조회 60건에 받은 바이트 약 49.9MB). 동시 요청 몇 건이면 256MB 힙이 찬다.
2. 힙이 차서 Major GC가 연달아 돈다. 측정 구간 6분 중 Major GC 정지 합계가 101.5초였고, 한 번에 최대 29.1초 멈췄다. Serial GC라 정지 중에는 모든 요청 스레드가 멈춘다.
3. 멈춘 동안 커넥션을 쥔 요청도 같이 멈춰 Hikari 대기가 최대 197건까지 쌓였다. 이때 DB 쪽 활성 세션은 최대 2개, 잠금 대기는 0이었다. `idle in transaction`이 최대 5개(풀 전체)였다. DB가 일하는 것이 아니라 앱이 커넥션을 쥔 채 멈춰 있었다는 뜻이다.
4. 커넥션을 30초 기다린 요청이 `CannotCreateTransactionException` 500으로 끝났다. Gateway는 3초에 504로 끊었다.
5. 정지 때문에 Prometheus 수집과 Eureka 갱신이 끊겨 Gateway가 인스턴스를 잃었다(`No servers available for service: reservation-service`). 503 18,274건은 Gateway가 1~6ms 만에 바로 돌려준 것이다. 60~120초 구간에는 다시 등록돼 500·504가 나오고, 180초부터는 다시 503만 나왔다.
6. 부하가 끝나고 10분이 지나도 회복하지 못했다. Gateway가 포기한 요청을 서버는 끝까지 처리하므로, Tomcat에 쌓인 요청을 비우는 동안 계속 GC에 묶였다. 재시작해야 돌아왔다.

서버 안에서 끝난 좌석 조회 200은 172건뿐이었다. 그 지연은 중앙값 27.5초, 최대 54.4초였다. 모두 Gateway 3초를 넘겨 사용자에게는 오류로 보였다.

초당 1명에서도 60초 동안 GC 정지가 8.1초(시간의 약 11%), 힙 최대 206MB였다. 이 환경에서 좌석 조회의 한계는 초당 1~2건이다. 목표(초당 100명, 재시도 포함 최대 200건)와 두 자릿수 차이가 난다.

#### 2절 가설과 비교

| 가설 | 측정 | 판정 |
|---|---|---|
| B1 커넥션 풀 5가 1순위 | 대기 197건까지 쌓였지만 원인은 GC 정지 중 커넥션을 쥔 요청이다. DB는 한가했다 | 증상이다. 풀만 늘리면 멈춘 요청이 더 많은 커넥션을 쥘 뿐이라 P1 단독으로는 효과가 없을 것으로 본다 |
| B2 좌석 조회가 1~2순위(미측정) | 초당 2명부터 무너졌다. 메모리와 GC가 원인이다 | 1순위로 확정. 다만 예상한 DB 부하가 아니라 앱 메모리 문제였다 |
| B3~B5 선점 트랜잭션·잠금 | 초당 1명에서 선점 p95 89ms. 본 측정에서는 선점까지 간 요청이 없다 | 아직 측정 불가. B2를 풀어야 보인다 |
| 2절에 없던 것 | 서비스가 무너지면 Eureka에서 빠져 전체가 503이 되고, 스스로 회복하지 못한다 | 새 병목 B8로 더한다 |

#### 계획 수정 제안

3절의 "P0 결과에서 B2가 B1보다 먼저 막히면 P4를 P2 앞으로 당긴다"에 해당한다. 다음 순서를 제안한다. 확정은 최권우가 한다.

1. **P0' 실행 환경 맞추기.** 측정 대상의 힙과 GC를 배포 환경에 맞춘다(예: 컨테이너 1~2GB, G1). 지금 숫자는 local Compose의 기동용 메모리 제한에서 나왔다. 워크스페이스 가이드도 그 제한이 운영 수용량을 뜻하지 않는다고 적는다. 공유 설정이라 바꾸려면 contract 이슈가 필요하다. 측정 전용 override 파일로 따로 두는 방법도 있다.
2. **P4를 P1 앞으로.** 좌석 조회에서 엔티티를 만들지 않는 조회(필요한 열만), 배치 정보 캐시와 상태 캐시를 넣는다. 응답 크기(약 830KB)를 줄이는 방법도 본다. 예를 들어 구역별 조회, 상태만 비트맵으로 주기가 있다. 이는 프론트·API 계약 변경이라 SA와 프론트 담당 확인이 필요하다.
3. **B8 대응.** Tomcat 최대 스레드·대기열을 줄여 넘친 요청은 빨리 거절한다. 커넥션 대기 시간도 Gateway 3초보다 짧게 둔다. 이는 P1에 같이 들어간다. 이렇게 해야 과부하 뒤 스스로 회복한다.
4. 그 다음에 P1(풀) → P2·P3(선점 트랜잭션) 순서를 그대로 진행한다.

1번(P0')은 2026-11-05에 메모리만 배포 값으로 맞춰 다시 쟀다. 결과는 5-2절에 있다.

### 5-2. P0'(S0) 배포 메모리로 다시 측정 (2026-11-05)

5-1절의 결과가 local Compose의 작은 메모리 때문인지 가리려고, 측정 경로의 메모리만 배포 서버 값으로 바꿔 다시 쟀다. 나머지 조건(코드, 프로필, 풀 5, 노트북 한 대, k6 설정)은 5-1절과 같다.

#### 바꾼 것

| 서비스 | 5-1절 (local 기본) | 5-2절 (배포 값) | 근거 |
|---|---|---|---|
| reservation-service | 컨테이너 512MB, `-Xms64m -Xmx256m` | 컨테이너 1,152MB, `-Xms384m -Xmx768m` | `compose.deploy.yml`(SA 9-3 표, 16GB급 EC2) |
| gateway | 컨테이너 512MB, `-Xms64m -Xmx256m` | 컨테이너 768MB, `-Xms256m -Xmx512m` | 같은 파일 |
| 선점 만료 스케줄러 | 켜짐 | 꺼짐(`SEATHOLD_EXPIRY_ENABLED=false`) | 2절. 5분 측정과 `holdMinutes` 5가 겹친다 |

덮어쓰기는 측정 전용 파일 [`reservation-service/k6/compose.deploy-memory.yml`](../../../reservation-service/k6/compose.deploy-memory.yml)에 두었다. 공유 설정(`compose.yml`, `compose.deploy.yml`)은 고치지 않았다. 다른 서비스까지 배포 값으로 올리면 상한 합계가 13GB를 넘는다. 이 기기의 Docker Desktop 메모리(7.6GB)로는 띄울 수 없어서 측정 경로의 두 서비스만 바꿨다.

**배포 값에서도 GC는 Serial이다.** 컨테이너 안에서 `java -XX:+PrintFlagsFinal`로 확인한 결과 두 서비스 모두 `UseSerialGC = true {ergonomic}`이었다. JVM은 메모리가 약 1,792MB보다 작으면 서버급 기기가 아니라고 보고 Serial GC를 고른다. 배포 서버의 reservation-service(1,152MB)도 같은 이유로 Serial GC로 뜬다. 정지 중에는 모든 요청 스레드가 멈추는 방식이라, 배포 환경에서도 5-1절의 정지 문제가 그대로 남는다.

#### 실행 목록

| 실행 | 속도·시간 | 결과 | 좌석 조회(성공만) p50 / p95 / p99 | 선점 p50 / p95 / p99 |
|---|---|---|---|---|
| K1 본 측정 | 초당 100명, 300초 | 30,014건 중 좌석 조회 200은 12건. 500 18,574, 504 10,410, 503 1,005. 선점 12건은 503 5, 504 7 | 2,420 / 2,770 / 2,820ms | 성공 없음 |
| 낮은 속도 5 | 초당 5명, 60초 | 301명 모두 선점 성공(201 301, 409 5). 실패 0 | 178 / 347 / 415ms | 19 / 55 / 191ms |
| 낮은 속도 10 | 초당 10명, 60초 | 602건 중 좌석 조회 200은 42건, 504 560. 선점 201 14 | 1,990 / 3,010 / 3,370ms | 2,520 / 2,860 / 2,880ms |

낮은 속도 시험은 실행마다 reservation-service를 재시작해 깨끗한 JVM에서 쟀다. 세 실행 모두 회차 4(새로 만든 15,000석)를 썼다. 앞 실행에서 잡힌 좌석은 300석 남짓이라 뒤 실행의 좌석 경합에 주는 영향이 작다.

#### 본 측정에서 본 것

1. 서버 안에서 끝난 좌석 조회 200은 4,055건이다. 5-1절(172건)의 약 24배다. 그러나 평균 지연이 25.6초(최대 30.9초)라 모두 Gateway 3초를 넘겨 사용자에게는 오류였다. 이 실행에서 서버가 소화한 조회는 초당 약 10건이다.
2. 측정 시작부터 7분 동안 GC 정지 합계는 Major 약 108초, Minor 약 133초였다. 힙 사용은 최대 707MB(상한 768MB)였다. 정지가 시간의 절반을 넘었다.
3. 500 18,574건은 Gateway가 약 1초 만에 돌려준 것이다. Gateway의 `connect-timeout`(1,000ms)에 걸린 것으로, reservation-service가 정지 중이라 연결을 받지 못했다. 5-1절에서는 같은 상황이 Eureka 이탈 뒤의 503으로 나타났다. 이번에는 정지가 짧게 끊겨 Eureka 등록은 대부분 유지됐고(503은 처음 30초의 1,005건뿐), 대신 연결 시한에 걸렸다. [고침, 2026-11-05] 처음 30초의 503은 Eureka 이탈이 아니라 Gateway 인증 Redis 차단기에서 나왔다(5-4절 "503의 출처").
4. Hikari 대기는 최대 197건으로 5-1절과 같았다. DB 활성 세션은 최대 6, `idle in transaction` 최대 5, 잠금 대기 0이었다. DB가 한가한 것도 5-1절과 같다.
5. 부하가 끝나고 3분 넘게 지나도 회복하지 못했다. 컨테이너 메모리는 1.115GiB(상한 1.125GiB)에 붙어 있었고 CPU는 170%였다. 직접 호출(`localhost:8082`)도 응답하지 않아 재시작했다. B8은 그대로다.

#### 해석

- 메모리를 3배로 늘리자 한계가 초당 1~2명에서 초당 5~10명으로 올랐다. 목표(초당 100명)와는 여전히 한 자릿수 이상 차이가 난다. 메모리를 늘리는 것만으로는 B2를 풀 수 없다.
- 원인은 5-1절과 같다. 요청 하나가 15,000석 엔티티와 약 830KB JSON을 만든다. 힙을 늘리면 버티는 동시 요청 수는 늘지만, 요청당 할당량이 그대로라 처리 속도가 할당 속도를 따라가지 못하는 시점이 조금 늦어질 뿐이다.
- 배포 서버도 Serial GC로 뜨므로 "배포 환경에서는 괜찮다"고 볼 근거가 없다. 배포 서버에서 K1을 돌리면 같은 모양으로 무너질 가능성이 높다.

#### 다음 단계 제안

1. **P4(좌석 조회 경량화)를 바로 시작한다.** 5-1절 제안 2번과 같다. 이번 결과로 메모리 조정이 대안이 아니라는 점이 확인됐다.
2. **GC 선택은 배포 담당과 이야기한다.** `-XX:+UseG1GC`를 명시하면 Serial의 전체 정지는 줄일 수 있다. 다만 `compose.deploy.yml`은 공유 설정이라 contract 이슈로 알려야 한다(AGENTS.md 대전제 11). G1로 바꿔 한 번 재 보는 것은 측정 전용 파일에서 따로 할 수 있다. 메모리와 GC를 같이 바꾸면 무엇이 효과를 냈는지 가릴 수 없어서 이번에는 바꾸지 않았다.
3. **B8 대응(Tomcat 스레드·대기열 축소, 커넥션 대기 1초)은 P4와 별개로 필요하다.** 메모리를 늘려도 과부하 뒤 회복하지 못했다.

2번(G1)을 5-3절에서 먼저 쟀다.

### 5-3. P0''(S0) G1 GC로 다시 측정하고 단계 순서를 정함 (2026-11-05)

#### 왜 쟀나
계획은 P1(커넥션 풀)부터 한 단계씩 쌓아 지표가 어떻게 좋아지는지 순서대로 보려는 것이었다. 그런데 P0·P0'에서 좌석 조회가 GC 정지로 먼저 무너져, 선점 쪽 개선(P1~P3)의 효과를 잴 수 없었다. 이 정지가 컨테이너 메모리 때문에 JVM이 자동으로 고른 Serial GC 탓이라면, GC만 바꿔 기존 순서를 지킬 수 있다. 그래서 P4로 순서를 바꾸기 전에 G1을 먼저 쟀다(판단 기록 [2026-11-05](../../ai-judgments/kwonwoo/2026-11-05-g1-first-then-decide-p4-order.md)).

판정 기준은 측정 전에 정했다.
- **A, 기존 순서 유지:** 초당 100명에서 좌석 조회 오류율이 5% 미만이라 선점 단계까지 요청이 가서 P1 효과를 잴 수 있고, 부하가 끝난 뒤 재시작 없이 회복한다.
- **B, P4를 먼저:** A를 만족하지 못한다.

#### 바꾼 것
reservation-service에 `-XX:+UseG1GC`만 더했다(측정 전용 파일 [`reservation-service/k6/compose.g1.yml`](../../../reservation-service/k6/compose.g1.yml)). 메모리(1,152MB, `-Xmx768m`)와 나머지 조건은 5-2절과 같다. G1 리전은 1MB로 골라졌다. GC 로그(`-Xlog:gc,gc+heap`)를 남겼다.

| 오류 0으로 버틴 최대 속도 | 초당 5명 | 초당 10명 |

#### 해석
- **G1은 정지 문제를 풀었다.** 정지 합계가 3분의 1로 줄었고, 수십 초짜리 정지가 사라졌다. 초당 10명까지 오류 없이 버텨 한계가 한 단계 올랐다.
- **그래도 초당 100명에서는 똑같이 무너졌다.** 정지가 사라지자 다음 병목이 드러났다. 좌석 조회 한 건이 15,000석을 엔티티로 읽고 DTO로 바꾸는 동안 트랜잭션(`@Transactional(readOnly = true)`)이 커넥션을 쥔다. 풀이 5개라 동시에 5건만 처리되고 나머지는 Hikari에서 기다린다. 서버가 소화한 조회는 초당 약 12건이었다. 목표 요청량(초당 100~200건)의 10분의 1 아래다.
- 이 상태에서 P1(풀 확대)을 넣으면 동시에 처리하는 조회가 늘어난다. 그러면 할당량과 CPU가 같이 늘어 GC가 다시 병목이 될 가능성이 높다. 요청당 비용을 줄이지 않으면 어느 자원을 늘려도 한계가 조금씩만 오른다.
- 판정은 **B**다. 기존 순서(P1부터)로는 선점 쪽 개선 효과를 잴 수 없다.

#### 바뀐 단계 순서
P0 → P0'(배포 메모리) → P0''(G1) → **P4a → P4b → P4c** → P1 → P2 → P3 → P5 → P6 → P7

- P0'·P0''는 측정 환경을 배포 서버에 맞추는 단계다. 코드 변경이 없고, 이후 단계는 모두 P0'' 환경(배포 메모리 + G1) 위에서 잰다.
- P4는 셋으로 나눠 한 단계에 변경 하나만 넣는다. P4a는 엔티티 대신 필요한 열만 DTO로 읽기, P4b는 바뀌지 않는 배치 정보 캐시, P4c는 좌석 상태 1초 캐시다.
- G1을 배포 설정(`compose.deploy.yml`)에 넣을지는 공유 설정이라 배포 담당과 contract 이슈로 정한다. 정하기 전까지 측정은 측정 전용 파일로 G1을 켠다.
  - 정함(2026-11-08, ISE-193): 배포 설정의 앱 7개 `JAVA_TOOL_OPTIONS`에 `-XX:+UseG1GC`를 명시했다. 배포 서버 측정은 측정 전용 파일 없이 G1로 돈다. 배포 뒤 `jvm_gc_pause_seconds_count`의 `gc` 라벨로 확인한다.
  - 확인(2026-11-10): 배포 서버(main `0e779531`)의 앱 8개(7개와 assistant-service)가 모두 `gc="G1 Young Generation"`이다.
- 좌석 조회 코드(`concert/application/ScheduleSeatQueryService`)는 공연·좌석 담당(반효승) 영역이라 P4는 반효승이 구현한다. contract 이슈 ISE-189로 요청했다. 좌석 선점 담당은 단계마다 같은 조건으로 재고 이 문서에 결과를 더한다.
- S4 기준선(3절)은 아직 재지 않았다.
- P4를 기다리는 동안 선점 경로는 K1-H(1-5절)로 따로 잰다. 기준선은 5-4절에 있다.

- **선점 경로는 초당 100명을 버틴다.** 풀 5에서도 첫 1분을 지나면 p95가 20ms 아래다. 같은 환경에서 K1은 좌석 조회에서 무너졌다(5-3절). P0''의 병목은 선점이 아니라 좌석 조회라는 점이 다시 확인됐다.
- 느린 요청은 첫 1분에 몰렸다. 기동 직후 JIT 컴파일 전 상태와 커넥션 대기(최대 171)가 겹친 구간이다. 이 구간의 p99 1.7초가 전체 p99를 정한다.

#### 503의 출처
503 4,020건은 Gateway가 2ms 안에 돌려준 것이다. 같은 시간 Gateway 로그에 `No servers available`은 없었다. `resilience4j_circuitbreaker_state{name="auth-redis",state="open"}`이 05:48:40, 05:50:30, 05:51:00, 05:52:20(UTC)에 열려 있었다. Gateway는 요청마다 Redis에서 로그아웃 토큰을 확인하는데, 그 호출이 느려지자 차단기가 열려 10초씩 503을 돌려준 것이다. 노트북 한 대에서 k6와 전체 스택이 CPU를 나눠 쓰는 환경 영향으로 본다. 선점 경로의 오류로 세지 않는다.

같은 방법으로 앞 측정을 다시 보니 P0'(02:15:50)와 P0''(03:04:50~03:05:10)의 시작 직후 503도 이 차단기가 열린 구간과 겹쳤다. 두 측정 모두 그 시간에 `No servers available` 로그가 없었다. 5-2절 3번에서 Eureka 이야기와 함께 적은 503 1,005건은 Eureka 이탈이 아니라 이 차단기에서 나온 것으로 고친다. Eureka 이탈이 확인된 것은 P0(5-1절)뿐이다.

### 5-5. 새 기기 단계 측정 결과 (2026-11-09~10)
