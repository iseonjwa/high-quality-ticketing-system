# 좌석 선점 k6 부하 시나리오와 병목 단계별 개선 계획 (ISE-79)

상태: 계획, 측정 전 (2026-11-04, 좌석 선점 담당 최권우 요청으로 Claude Code가 작성)

대기열이 초당 100명씩 5분 동안 입장시키는 상황을 k6로 재현한다. 이 문서는 그때 좌석 선점 경로에서 예상되는 병목, 기본 방법부터 쌓아 가는 개선 단계, 단계마다의 트레이드오프를 정한다. 병목 순위는 코드를 읽고 세운 가설이다. 근거로 2026-11-03 JUnit 근사 측정([concurrency-results.md](concurrency-results.md))을 함께 쓴다. 단계별 실측은 P0 기준선을 잰 뒤 이 문서에 채운다.

- 근거: SA 3-1(측정 방식), 3-3(입장 속도 역산), 9-4(숫자 기준), 12-7(핵심 쿼리)
- 관련: 정합성 단계 S0~S4는 [concurrency-scenarios.md](concurrency-scenarios.md), 부하 시나리오 L1~L6은 [load-test-scenarios.md](load-test-scenarios.md)에 있다. 이 문서의 시나리오는 L1~L6에 더하는 K1이다.
- JUnit 근사(`SeatHoldLoadTest`)는 부하 생성기와 앱이 같은 JVM에 있고 Gateway를 거치지 않는다. 그래서 이번 측정은 Gateway를 지나는 실제 HTTP 경로로 k6에서 다시 한다.

## 1. 시나리오 K1: 대기열 입장 직후 선점

### 1-1. 가정

| 항목 | 값 | 근거·비고 |
|---|---|---|
| 입장 속도 | 초당 100명, 5분(300초), 총 30,000명 | 사용자 지정(2026-11-04, 1분에서 5분으로 바꿈). `config-repo`의 현재 `queue.admit-per-second`는 50(SA 9-4 임시값)이라 그 2배다 |
| 부하 모델 | 열린 모델(도착률 고정) | 대기열은 응답 속도와 상관없이 일정 속도로 사람을 들여보낸다. 서버가 느려져도 도착이 줄지 않아야 실제와 같다 |
| 사용자 1명의 흐름 | 좌석 조회 → 1~3초 고민 → 선점(1~2석). 409면 좌석을 다시 조회하고 최대 2번 더 선점. 조회 결과에 선택 가능한 좌석이 없으면 선점하지 않고 끝낸다 | 409 뒤 재시도가 요청 수를 불린다. 재시도 횟수는 `[가정]`. 매진 화면에서 선점 버튼을 누를 수 없는 프론트 동작을 따른다 |
| 좌석 | 회차 1개, 15,000석(SA 3-2) | 30,000명 × 평균 1.5석 = 약 45,000석을 원하므로 측정 중에 매진된다(1-2절) |
| 좌석 선택 | 70%가 앞 구역 10%(1,500석)에서, 30%는 전체에서 무작위 | 인기 좌석 쏠림. 비율은 `[가정]` |
| 인증 | 로그인 토큰과 입장 토큰(`X-Entry-Token`)을 미리 발급해 CSV로 넣는다 | 토큰 발급 부하는 이 시나리오에서 뺀다. 발급 도구는 ISE-25(권영은) 산출물을 쓴다 |
| 경로 | k6 → Gateway → reservation-service → PostgreSQL | Gateway 타임아웃 3초(SA 9-4)가 판정에 들어간다 |

"동시 사용자 100명이 1초 간격으로 들어온다"를 "VU 100명이 1초마다 요청한다"(닫힌 모델)로 읽을 수도 있다. 닫힌 모델에서는 서버가 느려지면 요청도 줄어 병목이 가려진다. 대기열 뒤의 상황에는 열린 모델이 맞아서 그것을 기본으로 둔다. 닫힌 모델은 비교용으로 한 번 돌린다.

### 1-2. 예상 요청량

사용자 한 명이 내는 요청은 `조회 (1 + k) + 선점 (1 + k)`다. k는 409로 다시 시도한 평균 횟수다.

| k | 좌석 조회 req/s | 선점 req/s | 합계 req/s |
|---|---|---|---|
| 0 (충돌 없음) | 100 | 100 | 200 |
| 0.5 | 150 | 150 | 300 |
| 1.0 | 200 | 200 | 400 |

고민 시간이 1~3초이므로 같은 순간 서버 안에 있는 사용자는 리틀의 법칙으로 약 100명 × 2초 = 200명이다.

5분 동안 수요가 좌석의 약 3배라 측정은 두 구간으로 나뉜다.

| 구간 | 시점(추정) | 요청 모양 | 보는 것 |
|---|---|---|---|
| 판매 구간 | 0초 ~ 약 100~150초 | 조회와 선점이 섞인다. 선점이 모두 성공해도 초당 약 150석(100명 × 1.5석)이 팔리므로 15,000석 소진에 최소 약 100초가 걸린다. 409와 실패가 있으면 더 길다 | 선점 p95·p99, 커넥션 대기, 잠금 대기 |
| 매진 뒤 구간 | 매진 ~ 300초 | 새로 들어온 사용자는 조회 1번으로 끝난다. 매진 직전에 들어온 사용자의 재시도가 잠깐 몰린다 | 조회 p95·p99, CPU·GC. 좌석 조회만 남은 부하를 버티는지 |

두 구간을 한 숫자로 합치면 매진 뒤의 가벼운 409·조회가 선점 지연을 희석한다. 그래서 결과는 구간을 나눠 적는다(5절). 매진 시각은 대사 SQL로 마지막 선점 성공 시각을 뽑아 정한다.

### 1-3. k6 구성

```javascript
export const options = {
  scenarios: {
    k1_admission: {
      executor: 'constant-arrival-rate', // 열린 모델: 응답이 느려져도 초당 100명씩 시작한다
      rate: 100, timeUnit: '1s', duration: '5m',
      preAllocatedVUs: 300, maxVUs: 1000, // 시작하지 못한 반복은 dropped_iterations로 남는다
    },
  },
  summaryTrendStats: ['avg', 'p(50)', 'p(95)', 'p(99)', 'max'], // 기본 요약에는 p(99)가 없다
  thresholds: {
    'http_req_failed{expected:false}': ['rate<0.01'], // 5xx·타임아웃만 실패로 센다. 409는 정상 거절이다
    'http_req_duration{api:hold}': ['p(95)<1000'],     // 목표값은 [가정], P0 측정 뒤 정한다
    'http_req_duration{api:seats}': ['p(95)<500', 'p(99)<1000'],
  },
};
```

- `responseCallback`으로 201·409를 `expected`로 표시한다. 409를 실패로 세면 인기 좌석 거절이 오류율에 섞인다.
- 요청에 `api:seats`, `api:hold` 태그를 붙여 두 API의 지연을 나눠 본다. 태그별 p99가 요약에 나오게 임계값을 태그마다 하나 이상 건다. k6는 임계값이 걸린 태그 조합만 따로 요약한다.
- 구간별 수치는 k6 요약만으로 나눌 수 없다. `--out json=k6-result.json`(또는 Prometheus 원격 쓰기)으로 요청별 시각을 남기고, 매진 시각 전후로 잘라 p95·p99를 다시 계산한다.
- `dropped_iterations`가 0보다 크면 부하 생성기가 도착률을 못 맞춘 것이다. 서버 병목과 구분하려고 따로 적는다.
- k6는 대상과 다른 기기에서 돌린다(SA 3-1). 같은 기기에서 돌리면 환경 기록표에 적는다. JUnit 근사에서 같은 S0의 처리량이 2배 넘게 흔들린 원인 후보가 부하 생성기와 앱의 CPU 공유였다.

### 1-4. 판정과 함께 볼 지표

| 지표 | 위치 | 병목 신호 |
|---|---|---|
| p95·p99, 201·409·5xx·타임아웃 건수 | k6 요약 | p95가 Gateway 3초에 가까워지면 타임아웃이 오류로 바뀐다 |
| `hikaricp_connections_pending`, `hikaricp_connections_acquire_seconds` | Prometheus | 대기 수가 0보다 크게 유지되면 풀 병목 |
| `http_server_requests_seconds` | Prometheus | k6 지연과 차이가 크면 Gateway·네트워크 구간 |
| `pg_stat_activity`의 `wait_event_type = 'Lock'` 수 | 10초마다 SQL | 수십 이상이면 좌석 행 잠금 병목 |
| 프로세스 CPU, GC 일시 정지, 응답 바이트 | Prometheus·k6 `data_received` | 좌석 조회 응답 직렬화 병목 |
| 중복 판매, `held_count` 불일치 | 측정 뒤 대사 SQL | 0이 아니면 그 실행의 처리량은 버린다 |

## 2. 예상 병목

요청 하나가 지나는 순서대로 적었다. "예상 순위"는 이 시나리오에서 먼저 막힐 것으로 보는 순서다.

| # | 위치 | 왜 막히나(코드 근거) | 예상 순위 | 확인 지표 |
|---|---|---|---|---|
| B1 | DB 커넥션 풀 | `config-repo/reservation-service.yml`의 `maximum-pool-size`가 5다. Tomcat 스레드는 기본 200이라 요청 대부분이 커넥션을 기다린다. JUnit 근사에서 풀 5의 처리량은 VU 50부터 멈췄고(S0 446~478 req/s), 커넥션 대기 스레드가 최대 196개였다 | 1 | `hikaricp_connections_pending` |
| B2 | 좌석 조회 API | `ScheduleSeatQueryService#getSeats`가 요청마다 회차 15,000석을 공연장 좌석과 조인해 전부 읽고 JSON으로 만든다. 캐시가 없고, 409 뒤 재조회로 호출 수가 늘어난다. 매진 뒤 구간에서는 이 API만 초당 100건 남는다. 이전 측정은 선점 API만 쟀기 때문에 이 비용은 아직 잰 적이 없다 | 1~2 (미측정) | `api:seats` p95, CPU, GC, `data_received` |
| B3 | 선점 트랜잭션 길이 | `SyncSeatHoldService#hold` 하나가 `@Transactional`이다. 커넥션을 쥔 채 DB 왕복을 약 12~14번 한다(멱등키 조회, 회차 조회, 좌석 조회, 매수 조회, 매수 반영, 좌석 UPDATE, 예매·예매 좌석·이력·선점 요청 INSERT, 커밋). 결제 토큰 HS256 서명도 트랜잭션 안에서 한다. 왕복 수는 코드를 읽고 센 값이다 | 2 | Zipkin 구간, 커넥션 점유 시간 |
| B4 | INSERT 묶음 처리 불가 | `Reservation`, `ReservationSeat`, `ReservationStatusHistory`가 `GenerationType.IDENTITY`다. Hibernate는 IDENTITY 엔티티를 JDBC 배치로 묶지 못해 좌석 수만큼 따로 왕복한다 | 3 | B3과 같음 |
| B5 | 인기 좌석 행 잠금 | 같은 좌석을 잡으려는 요청이 좌석 UPDATE에서 앞 트랜잭션의 커밋을 기다린다. 기준선에는 `lock_timeout`이 없어 그동안 커넥션도 쥐고 있다. JUnit 근사의 L2·L6에서는 잠금 대기 세션이 최대 0~6개로 B1보다 작았다. 풀을 늘려 B1이 풀리면 이 병목이 드러날 것으로 본다 | 3~4 | 잠금 대기 세션 수, `api:hold` 409 p95 |
| B6 | 409 재시도 증폭 | 거절된 사용자가 좌석을 다시 조회하고 다시 선점한다. 지연이 길어질수록 다른 사람이 그 좌석을 먼저 잡아 409가 늘고, 409가 다시 요청을 늘린다. 매진 직전에는 남은 좌석이 적어 409 비율이 가장 높다 | B1·B2가 생기면 함께 커진다 | 사용자당 요청 수, k |
| B7 | 정합성 수정의 비용 | ISE-79 S1~S3은 요청당 왕복을 3번 늘린다(매수 INSERT, 선점 결과 UPDATE, `set_config`). JUnit 근사에서 VU 400 처리량 중앙값이 S0 1,125에서 S3 669 req/s로 내려갔다(편차 큼) | 수정 뒤 B3을 키운다 | 단계별 처리량 |

병목이 아닐 것으로 보는 것도 적는다. 측정에서 다르게 나오면 이 판단을 고친다.
- 매수 행(`user_schedule_quotas`)은 사용자마다 따로라 다른 사용자끼리 경합하지 않는다.
- 데드락은 JUnit 근사의 C2·C7에서 0이었다. 좌석 ID 정렬과 UPDATE 한 문장 덕분이다.
- Gateway의 입장 토큰 검증은 HS256 서명 확인이라 요청당 비용이 작다. 다만 Gateway도 같은 기기에서 돌면 CPU를 나눠 쓴다.
- 만료 스케줄러: 선점 유지 시간이 5분이라 첫 선점이 측정 끝 무렵(약 5분 뒤)에야 만료된다. 측정 중에는 스케줄러를 끈다([load-test-scenarios.md](load-test-scenarios.md) 2절 3번). 그래서 매진 뒤 좌석이 다시 풀리지 않는다. 만료가 섞이는 상황은 L5에서 따로 본다.

## 3. 단계별 개선 계획

원칙은 [concurrency-scenarios.md](concurrency-scenarios.md) 1절과 같다. 한 단계에 변경 하나만 넣고, 단계마다 K1 전체를 다시 돌린다. 앞 단계일수록 바꾸는 범위가 작고 되돌리기 쉽다.

정합성 단계(S1~S4)는 처리량을 낮춰도 넣어야 하는 변경이다. 그래서 K1은 S0과 S4에서 각각 한 번 재고, P1부터는 S4 위에 쌓는다. 이렇게 해야 "정합성을 고쳐서 느려진 만큼을 어디서 되찾았는가"가 한 표에 나온다.

| 단계 | 변경 | 겨냥 | 기대 효과(가설) | 바꾸는 범위 |
|---|---|---|---|---|
| P0 | k6 K1 스크립트, 토큰 CSV, 지표 수집. 코드 변경 없음. S0과 S4에서 측정 | 기준선 | 병목 순위 확인 | 측정 도구만 |
| P1 | 커넥션 풀 5 → 20, `connection-timeout`을 Gateway 3초보다 짧게(예: 1초) | B1 | 처리량 약 2배(JUnit 근사 결과), 커넥션 대기가 3초 타임아웃 대신 빠른 실패로 바뀜 | 설정 |
| P2 | 트랜잭션 줄이기: 결제 토큰 서명을 커밋 뒤로, 회차 조회·판매 기간 검사를 쓰기 트랜잭션 앞으로 | B3 | 커넥션 점유 시간 감소 | 서비스 코드 |
| P3 | 왕복 줄이기: 좌석 조회와 UPDATE를 `UPDATE ... RETURNING` 하나로, 매수 반영을 조건부 upsert 한 문장으로, 예매 좌석·이력 ID를 시퀀스로 바꿔 JDBC 배치 INSERT | B3, B4, B7 | 왕복 약 12~14회 → 7~8회(추정) | 저장소 코드, 엔티티 ID 전략 |
| P4 | 좌석 조회 가볍게: 엔티티 대신 필요한 열만 읽는 조회, 변하지 않는 배치(구역·열·번호·등급·가격)와 상태를 나눠 배치는 캐시, 상태는 1초 TTL 캐시 | B2, B6 | 좌석 조회 DB 부하와 응답 크기 감소 | 조회 코드, 캐시 |
| P5 | 인기 좌석 빠른 실패: `lock_timeout` 500ms(S3에 포함), 이미 HELD인 좌석을 Redis 집합으로 먼저 거절 | B5, B6 | 409 p95 감소, 거절 요청이 커넥션을 쓰지 않음 | Redis 키 추가 |
| P6 | 수평 확장: reservation-service 2대, 좌석 조회를 읽기 복제본으로 | B1~B3 전체 | 처리량을 인스턴스 수만큼 늘림(DB가 받쳐 주는 데까지) | 배포 구성, DB |
| P7 | 구조 전환: 접수형(Kafka) 선점 | 스파이크 흡수 | 202로 받고 일정 속도로 처리 | ISE-18 범위 |

P0 결과에서 B2가 B1보다 먼저 막히면 P4를 P2 앞으로 당긴다. 순서는 측정으로 정한다.

목표를 못 맞추면 대기열 입장 속도 N을 낮추는 것도 답이다. 대기열의 역할이 뒤쪽이 감당할 만큼만 들여보내는 것이기 때문이다. SA 3-3 식(`L_max = μ / r`, `λ = L_max / W`)에 P0~P6에서 잰 포화 처리량 μ를 넣어 N을 역산한다. N을 바꾸는 것은 대기열 담당(권영은)과 정한다.

## 4. 단계별 트레이드오프

| 단계 | 얻는 것 | 잃는 것·위험 | 판단 기준 |
|---|---|---|---|
| P1 풀 20 | 설정 한 줄로 처리량이 가장 크게 오른다 | 인스턴스 수 × 풀 크기가 PostgreSQL `max_connections`(기본 100)를 넘으면 안 된다. 풀이 너무 크면 DB의 문맥 전환과 잠금 경합이 늘어 오히려 느려진다. `connection-timeout`을 줄이면 몰릴 때 5xx가 빨리 나온다 | 풀을 10·20·40으로 바꿔 가며 처리량이 멈추는 지점을 찾는다. 공유 설정이라 contract 이슈로 알린다(AGENTS.md 대전제 11) |
| P2 트랜잭션 줄이기 | 코드 이동만으로 점유 시간이 준다 | 커밋 뒤 서명이 실패하면 좌석은 잡혔는데 토큰이 없다. 멱등 재요청이 다시 서명하는 기존 흐름(`replay`)으로 복구되는지 확인해야 한다. 회차 조회를 트랜잭션 밖으로 빼면 그사이 판매 종료를 놓칠 수 있다. 판매 기간은 서버 시각 검사라 영향이 작다 | 서명이 요청 시간에서 차지하는 비율을 Zipkin으로 먼저 잰다. 1ms 미만이면 서명 이동은 효과가 작다 |
| P3 왕복 줄이기 | 커넥션 점유와 DB 부하가 같이 준다 | 네이티브 SQL이 늘어 JPA 변경 감지와 테스트 용이성을 일부 잃는다. 조건부 upsert 한 문장은 SA 12-7(조회 후 조건부 UPDATE)과 모양이 달라 SA 변경 요청이 필요하다. ID를 IDENTITY에서 시퀀스로 바꾸면 스키마 변경과 마이그레이션이 생긴다 | 하나씩 넣고 C1~C7 회귀를 같이 돌린다. 효과가 5% 미만이면 되돌린다 |
| P4 좌석 조회 캐시 | 가장 많이 불리는 API의 DB 부하가 크게 준다 | 상태 캐시가 1초 늦으면 이미 잡힌 좌석이 AVAILABLE로 보여 409가 는다. 최종 판정은 DB 조건부 UPDATE라 정합성은 깨지지 않지만 사용자 경험과 재시도 수가 나빠진다. 캐시를 무효화하는 경로가 늘어난다 | TTL을 0·1·3초로 바꿔 409 비율과 좌석 조회 p95를 같이 본다 |
| P5 Redis 선거절 | 거절될 요청이 DB에 가지 않는다 | Redis와 DB 두 곳에 좌석 상태가 생긴다. Redis가 뒤처지면 잡을 수 있는 좌석을 거절할 수 있다. 그래서 Redis는 "확실히 잡힌 좌석" 거절에만 쓰고 허용 판단에는 쓰지 않는다. Redis 장애 시에는 그냥 DB로 보낸다(서킷 OPEN 정책, SA 9-5) | 409 중 Redis에서 끝난 비율과 잘못 거절한 건수(대사)를 센다 |
| P6 수평 확장 | 앱 CPU와 풀 한계를 넘는다 | 총 커넥션이 늘어 DB가 다음 병목이 된다. 복제본은 복제 지연만큼 오래된 좌석 상태를 보여 준다. 운영할 구성 요소가 늘어난다 | DB CPU와 잠금 대기가 낮을 때만 의미가 있다. 높으면 P3·P4가 먼저다 |
| P7 접수형 | 순간 폭주를 큐가 흡수하고 처리 속도를 고정한다 | 사용자가 결과를 폴링해야 하고, 선점 확정까지 지연(SA 9-4 2초 이내)이 생긴다. 접수 요청 행, 시한, 고아 정리 같은 구성이 늘어난다 | 동기형을 P6까지 올려도 목표 미달일 때. ISE-18의 동기형·접수형 비교에서 정한다 |
