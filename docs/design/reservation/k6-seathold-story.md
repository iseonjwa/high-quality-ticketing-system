# 좌석 선점 k6 부하 측정 정리: 발표 준비용 (ISE-79)

상태: local 측정 완료(2026-11-10), 측정 회고 뒤 재측정 반영(2026-11-11). 작성: 좌석 선점 담당 최권우 요청으로 Claude Code. 팀원이 발표 자료를 만들 때 읽는 요약이다. 수치의 정본은 [계획 문서](k6-seathold-bottleneck-plan.md) 5-5절과 측정 브랜치 `experiment/ISE-79-k6-steps`의 `reservation-service/k6/STEPS.md`다. 이 문서는 그 내용을 이야기 순서로 다시 묶었고 새 수치는 없다.

## 1. 한 줄 요약

티켓 오픈 직후 초당 100명이 좌석 화면에 들어오는 상황을 k6로 재현했다. 수정하지 않은 코드는 좌석 조회의 0.13%만 성공했다. 병목을 하나씩 고쳐 마지막 조합(F)은 100% 성공, 좌석 조회 p95 7ms가 됐다. 조회와 선점이 섞인 오픈 부하는 초당 320명까지 버텼다(매진 뒤 좌석 조회만이면 1,280명). 배포와 같은 4코어로 묶으면 160명에서 느려지고 320명에서 실패가 시작된다. 정합성 수정(중복 판매·한도 초과 방지)은 측정 가능한 성능 비용 없이 들어갔다.

## 2. 시나리오

### K1: 대기열 입장 직후 선점 (서비스 전체)

| 항목 | 값 | 이유 |
|---|---|---|
| 입장 속도 | 초당 100명, 5분, 총 30,000명 | 대기열이 일정 속도로 입장시키는 상황. 현재 설정값(`config-repo/reservation-service.yml`의 `queue.admit-per-second`)은 50이다. 50은 기준선 측정 전에 둔 임시값이고(SA 3-3·9-4), 측정은 그 2배로 더 엄하게 했다 |
| 부하 모델 | 열린 모델(도착률 고정) | 실제 대기열은 서버가 느려져도 입장을 줄이지 않는다. 닫힌 모델(VU가 응답을 기다림)은 서버가 느려지면 요청도 줄어 병목이 가려진다 |
| 사용자 흐름 | 좌석 조회 → 1~3초 고민 → 1~2석 선점. 이미 잡힌 좌석(409)이면 다시 조회해 최대 2번 더 시도 | 실제 예매 화면 동작 |
| 좌석 | 회차 1개, 15,000석. 70%가 앞 구역 10% 좌석을 고름 | 실제 공연장 규모와 인기석 쏠림 |
| 경로 | k6 → Gateway → reservation-service → PostgreSQL | 실제 요청 경로. Gateway 시한 3초가 판정에 들어간다 |

수요(30,000명 × 평균 1.5석)가 좌석의 약 3배라 측정 중에 매진된다. 그래서 결과는 매진 전과 매진 뒤로 나눠 본다.

### K1-H: 선점 경로만 따로 재기

K1에서는 좌석 조회가 먼저 무너져 선점까지 가는 요청이 거의 없었다. 그래서 좌석 목록을 시작 전에 한 번만 받고 선점만 반복하는 보조 시나리오를 두었다. 선점 쪽 개선(커넥션 풀, 정합성 수정)의 효과는 K1-H로 본다.

### 측정 종류 세 가지

| 종류 | 묻는 질문 | 부하 |
|---|---|---|
| 부하(L) | 목표 부하(초당 100명)를 버티는가 | 초당 100명, 300초 |
| 스트레스(S) | 어디까지 버티고, 넘으면 어떻게 무너지는가 | 60초마다 도착률을 두 배로(K1 5→1,280명, K1-H 50→800명) |
| 회복(R) | 한계를 넘긴 뒤 스스로 돌아오는가 | 스트레스 뒤 120초 동안 10초마다 좌석 조회 한 건 |

이 문서의 "10명", "640명", "1,280명", "800명"은 모두 **1초에 새로 들어오는 사용자 수(도착률)**다. 동시 접속자 수가 아니다. 동시에 서버 안에 있는 사용자 수는 도착률 × 한 사람이 머무는 시간이다. 초당 100명이 평균 2초 머물면 약 200명이 된다. 자세한 설명은 [학습 노트](../../learning/kwonwoo/qna/2026-11-10-arrival-rate-vs-concurrent-users.md)에 있다.

모든 회에서 대사 SQL로 중복 판매와 매수 불일치를 확인했다. 위반이 나온 회는 처리량을 쓰지 않는다(전 회 위반 0).

## 3. 진행 방식과 그렇게 한 이유

1. **수정하지 않은 기본 코드(base)에서 시작한다.** 처음에는 GC 설정과 커넥션 대기 시한을 미리 고친 환경을 기준으로 삼으려 했다. 그러면 "GC 때문에 멈추고 부하 뒤 회복하지 못하는" 과정이 사례에서 빠진다. 그래서 그 둘도 단계로 두었다([판단 기록](../../ai-judgments/kwonwoo/2026-11-06-k6-steps-from-unmodified-base.md)).
2. **직면한 병목 하나만 고치고 다시 잰다.** 한 단계에 변경을 둘 넣으면 무엇이 효과를 냈는지 가릴 수 없다. 계획한 순서는 예상일 뿐이고, 실측에서 막힌 곳이 다음 단계다.
3. **측정 전에 예상을 먼저 적는다.** 결과를 본 뒤 해석을 맞추지 않으려는 것이다. 조건부 단계의 기준값(예: P4d는 "커넥션 대기 평균 1 미만 + JSON 직렬화가 CPU의 30% 이상")도 측정 전에 고정했다.
4. **한 단계 = 측정 브랜치의 커밋 하나.** `git diff <앞 단계> <이 단계>`가 곧 변경 기록이다. 측정 브랜치는 머지하지 않는다. 실제 반영은 담당 이슈별로 따로 한다(좌석 조회 P4 → ISE-189, 대기 시한 R1 → ISE-196, GC·풀 → contract 이슈).
5. **발표 비교점만 3회 반복한다.** 단계를 고르는 탐색 측정은 1회, 기준선(base)과 최종(F)은 3회 재고 중앙값과 범위를 적었다. 모든 단계를 3회씩 하면 한 단계에 약 40분이 걸린다.

## 4. 단계별로 직면한 문제와 해결 (K1)

| 단계 | 직면한 문제 | 해결 | 왜 이 방법인가 | 좌석 조회 성공(L) | 버틴 단계(S) |
|---|---|---|---|---|---|
| base | 좌석 조회 한 건이 15,000석을 엔티티로 읽어 메모리를 크게 쓴다. 컨테이너 메모리 1,152MB에서 JVM이 Serial GC를 골라, 부하 시간의 약 75%를 GC로 멈춘다 | - | - | 0.13% | 10명, 회복 실패 |
| G1 | GC 정지는 7%로 줄었다. 그러자 커넥션 대기가 드러났다. 기다리는 요청이 197건 쌓이고 부하가 끝나도 풀리지 않는다 | G1 GC 명시(`-XX:+UseG1GC`) | 설정 한 줄로 멈춤을 없애는 가장 작은 변경이다. 이게 먼저 풀려야 다음 병목이 보인다 | 0.7% | 20명, 회복 실패 |
| R1 | 처리량이 크게 늘었다. 하지만 1초 대기 초과 500이 28,613건 나온다. 좌석 조회 한 건이 엔티티 3만 개를 만들어 커넥션을 오래 쥔다 | 커넥션 대기 시한 30초 → 1초 | Gateway는 3초에 포기하는데 서버는 30초까지 기다리며 버려진 일을 계속 처리했다. 빨리 실패시키면 줄이 비워지고 커넥션이 성공할 요청으로 돌아간다 | 40.3% | 20명, 40초 뒤 회복 |
| P4a | PostgreSQL이 CPU 약 4.3코어를 쓴다. 커넥션 5개가 모두 15,000행 조인·정렬 쿼리에 묶인다 | 엔티티 대신 필요한 열만 DTO로 읽기 | 응답에 필요 없는 엔티티 생성(메모리·CPU)을 없애는 가장 작은 코드 변경이다 | 81.3% | 80명, 30초 뒤 회복 |
| P4b | 초당 100명에서는 병목이 사라졌다. 부하를 올려 보니 640~1,280명 사이에서 커넥션 대기가 생긴다 | 공연 중 바뀌지 않는 정보(구역·열·번호·등급·가격)를 회차마다 한 번 만들어 캐시 | 바뀌지 않는 15,000행을 요청마다 조인할 이유가 없다. 요청마다 읽는 것은 "선점 가능 좌석 ID"만 남는다 | 100% (매진 전 p95 11ms) | 640명 |
| P4c | DB 일은 거의 사라졌다. 남은 서버 비용은 응답 만들기·JSON 직렬화(JFR 기준 약 57%)다 | 좌석 상태를 1초 동안 공유 캐시 | 1초 안에 들어온 요청은 같은 상태를 봐도 된다. 낡은 상태로 이미 잡힌 좌석을 골라도 선점 UPDATE가 DB에서 최종 판정하므로 중복 판매는 생기지 않는다 | 100% (매진 전 p95 7ms) | 1,280명 |

- P4c의 걱정은 "1초 낡은 상태 때문에 409(이미 선점된 좌석)가 늘지 않을까"였다. 실측 409 비율은 76.6%에서 76.9%로 거의 같았다. 원래 인기석 쏠림으로 409가 많아 1초 낡음이 더하는 몫이 보이지 않았다.
- 병목이 옮겨 간 순서는 **JVM 메모리(GC) → 커넥션 대기 → DB 조인 → 응답 직렬화**다. 발표에서 "하나를 풀면 다음 병목이 드러난다"를 보여 주는 줄거리다.

## 5. 선점 경로 (K1-H)

### 커넥션 풀 (P1)

Gateway를 거치면 800명에서 Gateway 인증 차단기가 먼저 막아 선점 경로의 한계를 볼 수 없었다. 그래서 k6가 reservation-service를 직접 부르는 회로 풀 크기를 정했다. 이 값은 Gateway 경유 값과 섞지 않는다.

| 풀 | 800명 선점 성공 · p50 / p95 / p99 | 커넥션 대기 최대 |
|---|---|---|
| 5 (현재값) | 100% · 2 / 14 / 33ms | 40 |
| 10 | 100% · 2 / 3 / 6ms | 0 |
| 20 · 40 | 10과 같음 | 0 |

풀은 10으로 정했다. 20·40은 효과가 없었고, 풀이 크면 DB 연결 수 한도(`max_connections`)와 문맥 전환 부담만 는다. 풀을 P4(좌석 조회 개선) 뒤에 늘린 이유도 있다. 조회가 무거울 때 풀을 늘리면 동시에 도는 조회가 늘어 GC가 다시 병목이 된다.

### 정합성 수정 (S1~S4)

이 수정들은 ISE-79의 본 작업이고, 성능과 상관없이 들어가야 한다. 결함은 JUnit 동시성 테스트로 찾았다. k6 사용자는 요청을 하나씩만 보내서 이런 결함을 직면하지 않는다.

| 수정 | 결함 | 해결 |
|---|---|---|
| S1 매수 한도 | 같은 사용자가 탭 4개로 동시 선점하면 한도 4매를 넘어 8매까지 잡힘 | 검사와 반영을 조건부 UPDATE 한 문장으로 |
| S2 멱등키 | 같은 멱등키로 연타하면 자기 요청끼리 부딪혀 409 | 멱등키를 가장 먼저 기록해 같은 요청인지부터 정함 |
| S3 잠금 대기 | 잠긴 좌석을 노린 요청이 끝없이 기다리며 커넥션을 쥠 | `lock_timeout` 500ms, 좌석 ID 순서로 잠금 |
| S4 만료 | 만료 스케줄러 두 개가 같은 건을 서로 집어 헛수고 | `FOR UPDATE SKIP LOCKED`로 한 건씩 집음 |

S1·S2를 하나씩 넣고 K1-H를 쟀더니 선점 p95가 넣기 전과 같았다(400명까지 5ms 이하). 처음 계획한 줄거리는 "정합성을 고쳐 잃은 처리량을 풀 확대와 왕복 줄이기로 되찾는다"였다. 하지만 잃은 처리량 자체가 측정에 보이지 않았다. 그래서 줄거리를 **"정합성 수정은 측정 가능한 비용 없이 들어갔다"**로 바꿨다. 결함과 해결의 자세한 내용은 [트러블슈팅](../../troubleshooting.md) TS-55~58에 있다.

### 부하 상태의 동시성 (K2·X)

K1은 같은 좌석 경쟁만 만든다. 그래서 같은 사용자의 동시 요청과 만료 스케줄러를 켠 부하를 따로 쟀다. S1~S4 전(A)과 F(B)를 같은 설정(G1·R1·풀 10)으로 1회씩 쟀고, 차이는 S1~S4뿐이다(측정 브랜치 STEPS.md "동시성 부하 측정 실측").

| 측정 | A (S1~S4 전) | B (F) |
|---|---|---|
| 멀티 탭: 탭 4개가 2석씩 동시 선점, 초당 50명 120초 | 한도(4매)를 넘겨 잡은 사용자 293명(최대 8석) | 0명 |
| 연타: 같은 키로 3번 동시 선점, 초당 50명 120초 | 좌석을 잡은 2,418명 중 2,416명이 자기 요청에 409 | 0명. 세 응답 모두 같은 예매의 201 |
| 만료 켬: 선점 유지 1분, K1 L | 성공 100%, 잠금 대기 0, 기한 지난 HELD 약 9,100건 적체 | A와 같음(약 9,050건) |
| 대사 위반 | 0 | 0 |

- 동시성 테스트(C4·C5)로 찾은 결함이 부하 규모에서도 그대로 나오고, 고친 뒤 사라진다. 이 결함은 대사 검사로는 잡히지 않는다. 기록이 어긋나는 것이 아니라 한도와 응답이 틀리는 것이기 때문이다.
- 비용은 연타 p95가 약 5ms(9.6 → 14.6ms) 늘어난 것뿐이다. 멀티 탭 p95는 같다.
- 만료를 켜도 잠금 경합은 생기지 않았다. 대신 만료 처리 속도(5초 주기에 최대 100건, 초당 약 20건)가 기한이 도래하는 선점(초당 약 50건)을 따라가지 못했다. 결제하지 않은 좌석이 몇 분 늦게 다시 팔린다. 코드가 아니라 스케줄러 설정의 한계라 11절 남은 일에 넣는다.

이어서 세 가지를 더 쟀다(측정 브랜치 STEPS.md "동시성 부하 2차 실측").

| 측정 | A (S1~S4 전) | B (F) |
|---|---|---|
| 잠금 장애 주입(1차): 인기 구역 근처 약 2,200석을 33초 동안 다른 세션이 잠금. 인기 구역과 겹친 정도는 미확인이라 아래 재측정 값을 쓴다 | 잠금 중 좌석 조회 성공 **25%**. 잠금과 상관없는 조회까지 커넥션 대기로 500 | 잠금 중 좌석 조회 성공 **77.5%**. 잠긴 좌석 선점은 500ms 뒤 409. 그래도 500이 남음 |
| 2대 만료 경합: 인스턴스 2대가 만료를 같이 돌림 | 읽은 대상의 39%가 다른 쪽이 이미 처리한 건(헛수고). 처리량은 1대와 같음 | 헛수고 0. 처리량 1대의 2배 |
| 만료 한 주기 상한 100 → 1,000 (B만) | - | 적체 약 9,050건 → 57~269건. 누적 만료 4,400 → 17,144건. 선점 p95 그대로(8ms) |

- 잠금 하나가 시스템 전체로 번진다. 잠긴 행을 노린 요청이 커넥션 10개를 쥔 채 기다리면, 그 행과 상관없는 좌석 조회까지 실패한다. S3(`lock_timeout` 500ms)는 번짐을 크게 줄였다. 그래도 풀 10개 ÷ 0.5초, 곧 초당 약 20건보다 많이 몰리면 남는다. 없애려면 커넥션을 잡기 전에 거절해야 한다(선점 동시 처리 상한, Redis 사전 거절).
- S4(`SKIP LOCKED`)의 효과는 1대에서는 보이지 않고 2대에서 드러난다. 수평 확장했을 때 만료 처리량이 대수만큼 늘어나게 하는 수정이다.
- 만료 적체는 설정 한 줄로 풀렸다. 결제하지 않은 좌석이 약 5초 안에 다시 팔린다.

### 잠긴 행에 트래픽이 몰릴 때 (Z)

인기석 10석을 다른 세션이 측정 내내 잠그고, 선점을 그 10석에만 초당 10명부터 두 배씩 320명까지 보냈다. 같은 시간에 잠금과 상관없는 구경꾼 요청(같은 서비스의 공연 목록, user-service, payment-service)을 API마다 초당 10건 보냈다(측정 브랜치 STEPS.md "잠긴 행 집중 2차 실측").

| 선점 도착률/초 | A 공연 목록 실패 | B 공연 목록 실패 | user·payment 실패 (A·B) |
|---|---|---|---|
| 10 | 98.2% | 0% | 0% |
| 20 | 100% | 24.7% | 0% |
| 40 · 80 · 160 | 100% | 65 · 80 · 92% | 0% |
| 320 | 100% | 99.8% | 0.2~1.1% |

- 장애는 생긴다. 잠긴 행을 노린 요청이 커넥션을 쥐면 같은 서비스의 다른 API까지 무너진다. A는 첫 단계에서 바로, B는 계산한 한계(풀 10개 ÷ 대기 상한 0.5초 = 초당 20건)에서 무너지기 시작했다.
- 다른 서비스로는 번지지 않는다. user-service와 payment-service는 모든 단계에서 정상이었다. 서비스마다 커넥션 풀과 DB가 따로이고, Gateway는 reservation-service 경로만 504를 냈다. MSA로 나눈 효과가 장애 격리로 나타났다.
- 유령 선점이 생긴다. 잠금이 풀린 순간 A 9건, B 8건의 예매가 생겼지만 클라이언트는 201을 하나도 받지 못했다. 클라이언트가 3초에 504를 받고 떠난 뒤 서비스 앞에 쌓인 요청이 늦게 처리된 것이다. 정합성은 지켜지지만 아무도 모르는 좌석이 만료까지 묶인다.

### 측정 회고 뒤 재측정 (2026-11-11)

측정 회고([학습 노트](../../learning/kwonwoo/qna/2026-11-11-k6-seathold-scenario-retrospective.md))에서 고른 세 측정이다. 모두 1회씩이고 대사 위반은 0이다(측정 브랜치 STEPS.md "측정 회고 뒤 세 측정 실측").

**잠금 장애 주입 재측정.** 잠글 좌석을 응답 순서로 골라 인기 구역 3,000석을 정확히 잠갔다. 다른 조건은 1차와 같다.

| | A (S1~S4 전) | B (F) |
|---|---|---|
| 잠금 중 좌석 조회 성공 (1차 → 재측정) | 25% → **12.7%** | 77.5% → **53.5%** |

- S3는 번짐을 절반쯤 줄이지만, 인기 구역에 잠금이 걸리면 좌석 조회의 절반이 실패한다. 1차 값은 잠금이 인기 구역과 덜 겹쳐 좋게 나온 것이다. 커넥션을 잡기 전에 거절하는 장치가 필요하다는 근거가 더 강해졌다.

**매진을 피한 스트레스.** 단계마다 새 회차를 쓰고 회차 하나에 초당 100명까지만 보내, 모든 단계에서 조회와 선점이 섞이게 했다.

| 단계 | 좌석 조회 성공 · p95 | 선점 성공 · p95 |
|---|---|---|
| 5~160명 | 100% · 12ms 이하 | 100% · 17ms 이하 |
| **320명** | **100% · 34ms** | **100% · 27ms** |
| 640명 | 53.4% | 75.8% |
| 1,280명 | 13.2% | 13.0% |

- 640명부터 Gateway가 즉시 503을 냈고 reservation-service는 오류 0건이었다. 응답 모양이 인증 차단기 거절과 같다. 이 회는 Gateway 로그가 없어 미확인이다. 아래 차단기 값 비교에서 운영 값으로 다시 재니 차단기가 열렸다. 그래서 섞인 부하의 한계는 "320명 확인, 640명에서 Gateway가 먼저 막음"이다. "1,280명"은 매진 뒤 좌석 조회만 받은 한계다.

**CPU 상한 F.** 서버 컨테이너 전체를 같은 4코어에 묶어 배포 서버(4 vCPU 한 대)를 흉내 냈다. k6는 다른 코어에 두었다. 이유는 [학습 노트](../../learning/kwonwoo/qna/2026-11-11-why-cpu-limit-in-load-test.md)에 있다.

| 측정 | 상한 없음 F | CPU 상한 F |
|---|---|---|
| L 성공 · 매진 전 좌석 조회 p95 | 100% · 7ms | 100% · 18ms |
| S 160명 | 100% | 100%, p95 149ms |
| S 320명 | 100% | 좌석 조회 80.5% · 선점 72.3% |
| S 1,280명 (매진 뒤 조회만) | 3회 중 2회 100% | 12.9%, Gateway 메모리 초과 종료 |

- local 32코어에서 본 "1,280명까지 서버 병목 없음"은 CPU가 남아서 나온 결과다. 4코어에서는 CPU가 거의 차서 160명에서 느려지고 320명에서 실패가 시작된다. 배포 측정의 기대치는 이 근처로 잡는다.
- 1,280명 단계 끝에 Gateway가 메모리 상한(768MB)을 넘어 `OOMKilled`로 죽었다. CPU가 모자라 큰 좌석 응답(약 830KB)을 늦게 내보내는 동안 Gateway가 쥔 응답이 늘어난 것으로 본다. 상한 없는 3회에서는 생기지 않았다. 로그에 `OutOfMemoryError`가 없어, JVM이 아니라 컨테이너 상한에 걸려 커널이 죽인 것이다. 힙 512MB + 비힙 + Netty 직접 메모리(기본 상한 512MB)가 768MB를 넘을 수 있는 설정이다. 같은 조건으로 2회 더 재니 강제 종료는 3회 중 1회, 메모리 상한 도달은 3회 중 3회였다. 남은 2회는 커널이 JVM 메모리를 스왑으로 내보내 살았지만 크게 느려졌다(좌석 조회 p95 최대 5.8초). 메모리를 채운 것은 몰린 830KB 응답이다. Gateway가 아직 읽지 못한 커널 소켓 받기 버퍼(최대 약 590MiB)와 JDK 직접 버퍼(최대 183MB)에 쌓였다. 처음 회의 1,280명 단계 끝과 회복은 판정하지 않는다([원인 분석](../../learning/kwonwoo/qna/2026-11-11-gateway-oomkilled-under-cpu-limit.md)).

**Gateway 차단기 값 비교.** 위 측정은 측정 환경에서만 완화한 차단기 값으로 쟀다. 운영 값(P)과 Gateway 담당이 시험 중인 값(T, 벌크헤드 50 + 벌크헤드 거절 무시 등)을 같은 시나리오로 1회씩 비교했다(측정 브랜치 STEPS.md "Gateway 차단기 시험 값 비교 실측").

| 좌석 조회 성공률 | 4코어 P | 4코어 T | 상한 없음 P | 상한 없음 T |
|---|---|---|---|---|
| 320명 | 49.0% | 99.0% | 100% | 100% |
| 640명 | 100%(매진 뒤) | 100% | 38.7% | 88.6% |
| 1,280명 | 8.9% | 10.1% | 12.8% | 54.5% |
| Gateway | 생존(657MiB) | 상한 1,089회, 스왑으로 생존 | 생존(566MiB) | **OOMKilled** |

- P의 차단기는 Redis 오류 0건인데 열렸다. 벌크헤드(25) 거절이 실패로 세어져 창 20건의 절반을 채웠다. 앞 매진을 피한 스트레스(완화 값: 실패율 100%) 640명의 즉시 503은 원인 로그가 없어 미확인이다. 완화 값에서도 벌크헤드 25는 그대로라, 벌크헤드 거절이나 거절 20건 연속에 따른 차단기 열림일 가능성이 크다.
- T는 차단기가 열리지 않아 성공률이 크게 올랐다. 대신 통과한 830KB 응답이 Gateway에 쌓여 상한 없는 환경에서도 메모리 초과로 죽었다. 시험 값을 운영에 넣으려면 Gateway 동시 처리 상한이나 메모리 여유가 함께 필요하다. 근거를 ISE-230에 댓글로 넘겼다.

## 6. 최종 결과: base와 F 비교 (3회)

F = P4c + S1~S4 + G1·R1·풀 10.

| 측정 | base | F |
|---|---|---|
| K1 L 좌석 조회 성공 | 0.13% | 100% |
| K1 L 매진 전 p95 (좌석 조회 · 선점) | 거의 모두 3초 초과 | 7ms · 8ms |
| K1 L 선점 성공(201) · 매진 | 0건 · 매진 안 됨 | 약 10,100건 · 189초 |
| K1 S 버틴 단계 | 10명, 회복 실패 | 640명 3회 100%, 1,280명 2회 100%·1회 81.6% (p95 33ms) |
| K1 S GC 정지 비율 | 약 76% | 1% 안팎 |
| K1-H 800명 선점 p95 / p99 | 27 / 40ms | 11 / 16ms |
| K1-H Gateway 연결 실패(500) | 회마다 41~60건 | 0 |
| reservation-service 5xx · 대사 위반 | 0 · 0 | 0 · 0 |

- **K1 S 640명·1,280명 단계는 매진 뒤라 좌석 조회만 왔다.** 매진을 피한 스트레스로 다시 재니 섞인 부하는 320명까지 버텼다(5절 "측정 회고 뒤 재측정"). 매진은 160~320명 단계에서 일어난다. 그래서 조회와 선점이 섞인 오픈 부하를 버틴 것으로 확인한 범위는 L의 초당 100명과 S의 160명 단계까지다. "초당 1,280명"은 좌석 조회만 받은 한계다. 또 스트레스는 도착률을 7분에 걸쳐 올린 값이라, 0에서 한 번에 1,280명으로 뛰는 경우는 재지 않았다(8절 5번).
- K1 S 1,280명의 81.6% 회와 K1-H 800명의 실패(base·F 모두 80~99%)는 Gateway 인증 차단기의 즉시 503이다. reservation-service는 모든 회에서 5xx 0이다.
- 그래서 Gateway 경유 K1-H는 성공률로 base와 F를 가르지 못한다. 차이는 지연(p95 27 → 11ms)과 Gateway 연결 실패(41~60건 → 0)에 있다.

## 7. 넣지 않은 단계와 이유

"직면하지 않은 병목은 미리 고치지 않는다"는 원칙을 따랐다. 넣지 않은 단계도 측정값과 함께 이유를 남겼다.

| 단계 | 내용 | 넣지 않은 이유 |
|---|---|---|
| P4d | 1초 상태 스냅숏마다 응답 JSON을 한 번만 만들어 재사용 | 조건(대기 0, 직렬화 약 32%)은 맞았다. local에서는 1,280명까지 서버 병목이 없어 효과가 클라이언트 수치에 보이지 않는다. 4 vCPU 배포 환경에서 다시 볼지 의논 중이다([k6-p4d-review.md](k6-p4d-review.md)) |
| P3 | DB 왕복 줄이기(UPDATE RETURNING, upsert, 시퀀스 배치) | 선점 경로 800명(서버 초당 약 2,200건)에서도 커넥션 대기 0, p95 3ms라 한계에 닿지 않았다 |
| P2 | 결제 토큰 서명 등을 트랜잭션 밖으로 | 판단할 한계점이 없다 |
| P5 | 이미 잡힌 좌석을 Redis로 먼저 거절 | 판단할 한계점이 없다. 좌석 상태를 두 곳에 두는 복잡도가 크다 |
| P6·P7 | 서버 2대, Kafka 접수형 선점 | 구성 변경이라 "요청당 비용을 어떻게 줄였나"라는 이 측정의 질문과 다르다. P7은 ISE-18에서 비교한다 |

## 8. 측정하며 겪은 문제

측정 도구와 환경이 결과를 왜곡한 일도 있었다. 발표에서 "측정값을 어떻게 검증했나"로 쓸 수 있다.

1. **부하 생성기 한계를 서버 한계로 잘못 읽었다(TS-59).** k6 메모리 상한(2.5GiB)에 닿은 k6가 GC로 멈췄다가 요청을 몰아 보냈다. 그 몰림이 Gateway 차단기를 자주 열었다. 그래서 한때 "1,280명 한계는 Gateway와 부하 생성기"로 판단하고 K1 개선을 멈췄다. 상한을 6GiB로 올리자 같은 코드가 1,280명을 100% 처리했다. 이후 판단과 기록을 정정했다. 교훈은 부하 생성기의 CPU·메모리를 서버 지표와 함께 봐야 한다는 것이다.
2. **기기를 바꿔 처음부터 다시 쟀다.** 이전 노트북(Docker 메모리 7.6GiB)에서 메모리가 모자라 측정이 끊겼다. CPU 상한이 없어 처리량이 기기를 따라가므로, 기기가 다르면 단계끼리 비교할 수 없다. 그래서 새 기기에서 base부터 다시 쟀다. 병목이 옮겨 간 순서는 두 기기에서 같았다.
3. **무효 회를 걸러 냈다.** 모든 회에 유효 기준을 적용했다. 기준은 k6 비정상 종료(137·2) 없음, 지표 수집 간격 15초 이내, 대사 위반 0이다. 이전 기기의 P4b는 부하 생성기 한계, 메모리 부족, k6 스크립트가 응답 본문을 쥔 채 대기한 문제로 4번 무효가 됐다. 5번째에 유효했다.
4. **측정 환경에서만 Gateway 차단기를 완화했다.** 공유 기준(느린 호출 50ms)은 선점만 보내는 초당 100명에서도 열려 서버 개선을 볼 수 없었다. 측정 환경에서만 기준을 덮어쓰고 공유 설정은 고치지 않았다. 그래서 K1-H 결과는 배포 환경 기준과 다르다는 점을 함께 적는다([판단 기록](../../ai-judgments/kwonwoo/2026-11-07-k1h-relax-gateway-breaker-in-measurement.md)).
5. **오픈 순간의 몰림은 대기열 앞에서 받는다고 두었다.** 티켓 오픈 순간의 인파(예: 10초에 30,000명)는 대기열 진입이 받는다. 이 부분은 Q1(ISE-181, [open-peak-scenarios.md](../infra/open-peak-scenarios.md))이 잰다. 좌석 서비스에는 대기열이 정한 속도(초당 100명)만 들어온다. 그래서 K1 L은 시작부터 초당 100명을 고정으로 넣는다. 스트레스(S)는 도착률을 단계마다 올려 버티는 한계를 찾는다. 그 한계로 대기열 입장 속도를 얼마까지 올릴 수 있는지 정하는 것이 목적이다(SA 3-3). 실제 트래픽 모양을 흉내 낸 것은 아니다. 대기열을 거치지 않고 한꺼번에 몰리는 스파이크 테스트는 넣지 않았다.

## 9. 발표에 쓸 만한 AI 판단 사례

## 10. 좌석 조회 단독 측정(S1, ISE-189)과의 관계

좌석 조회 담당(반효승)은 P4a를 dev에 머지했다(#377, `a40b01d`). 그 전후를 좌석 조회 API 하나만 부르는 S1 시나리오(`loadtest/k6/scenarios/s1-seat-query.js`, #438)로 쟀다. 두 측정은 묻는 질문이 달라 서로를 대신하지 않는다.

| 항목 | S1 (ISE-189) | K1 (이 문서) |
|---|---|---|
| 질문 | P4a가 좌석 조회 API 하나를 얼마나 가볍게 했나 | 오픈 직후 사용자 흐름 전체를 버티는가, 어떤 병목이 차례로 나오나 |
| 요청 | 좌석 조회만. 사용자 한 명의 토큰으로 반복 | 사용자 30,000명이 조회 → 고민 → 선점, 409면 재조회·재선점 |
| 부하 | 초당 30·40·50건, 30초 | 초당 100명 300초(L), 초당 5 → 1,280명(S) |
| 커넥션 풀 | 좌석 조회만 씀 | 조회와 선점이 풀 5를 나눠 씀 |
| 비교한 코드 | P4a 전후 | base → G1 → R1 → P4a → P4b → P4c → F |
| 환경 | local 노트북, 배포 메모리 + G1. 배포 서버 측정은 준비만 됨(`compose.seat-before.yml`) | local i9-14900HX, 배포 메모리 |

- S1의 P4a 결과(ISE-189 댓글, 초당 50건 p95 2.68초 → 40ms, 실패 4 → 0)와 K1의 P4a 결과(L 좌석 조회 성공 40.3% → 81.3%)는 같은 방향이다. K1이 100%에 못 미친 것은 선점이 같은 풀을 쓰고, 409 재조회 때문에 좌석 조회가 초당 100건보다 많이 오기 때문이다.
- K1의 P4a 코드(측정 브랜치 `50a365d`)는 dev의 `a40b01d`와 같은 코드가 아니다. 엔티티를 만들지 않고 필요한 열만 읽는다는 원리는 같다. 구현은 다르다. 측정 브랜치는 네이티브 SQL로 7열을 읽고 선택 가능 여부를 SQL에서 계산한다. 비교용으로 엔티티 경로도 남겼다. dev는 JPQL 생성자 식으로 `ScheduleSeatRow` 레코드 8열(회차 좌석 등급·상태 포함)을 읽고, 선택 가능 여부는 `ScheduleSeat.isHoldable`로 자바에서 판단한다. 엔티티 경로는 지웠다. 응답 DTO의 필드와 정렬 기준은 같다.
- 두 P4a를 같은 조건(G1·R1, 풀 5, k6 상한 6GiB)으로 대조했다(측정 브랜치 STEPS.md "P4a 구현 대조 실측"). L 3회 중앙값으로 좌석 조회 성공은 측정 브랜치 82.7%, dev 79.4%(-3.3%p)였다. 서버 좌석 조회 처리량은 초당 169.4건과 158.7건(-6.3%)이었다. S에서 버틴 단계는 둘 다 40명이다. 측정 전에 정한 기준(5%p, 10%, 같은 단계) 안이라 dev 코드를 채택해도 된다. 다만 dev가 3회 모두 일관되게 약 6% 느렸다. 커넥션 5개가 병목인 상태에서 행마다 하는 변환(문자열 2열 추가, enum·`Money` 변환)이 커넥션 점유를 늘린 것으로 추정한다. P4b부터는 좌석 배치를 캐시하므로 이 차이는 거의 사라질 것으로 본다.
- 측정 브랜치의 P4b·P4c는 측정 브랜치 P4a(`SeatMapRow`) 위에 짰다. dev로 옮기려면 `ScheduleSeatRow` 위에 다시 짜야 한다. 그대로 병합하면 좌석 조회 파일 5개가 충돌한다.
- **dev에는 P4a만 들어 있다.** P4b(ISE-204)와 P4c(ISE-205)는 Backlog다. 이 문서의 F 결과는 측정 브랜치의 P4b·P4c 코드로 잰 것이다. 지금 dev를 배포하면 K1은 F가 아니라 P4a 수준에 가깝다고 봐야 한다. 발표에서 F를 말할 때 이 점을 함께 적는다.

## 11. 남은 일

- G1 GC는 dev 배포 설정에 이미 들어 있다(ISE-193). 남은 공유 설정(대기 시한 1초, 풀 10)과 Gateway 차단기 기준은 팀과 의논한 뒤 contract 이슈로 올린다([k6-contract-proposals.md](k6-contract-proposals.md)).
- P4d를 다시 볼지 정한다([k6-p4d-review.md](k6-p4d-review.md)). CPU 상한(4코어)에서는 160~320명에서 CPU가 거의 찼다. 다만 Gateway와 인증 차단기도 같은 구간에서 한계에 닿아, P4d만으로 한계 단계가 바뀔지는 배포 측정에서 본다.
- Gateway 메모리: 4코어로 묶은 스트레스의 1,280명 단계에서 Gateway가 메모리 상한 768MB를 넘어 죽었다(5절). 배포 서버에서도 생길 수 있어 Gateway 담당과 조율한다. 차단기 시험 값에서는 상한 없는 환경에서도 죽었다(5절). 근거는 ISE-230 댓글로 넘겼고, 동시 처리 상한·메모리 여유 적용 여부는 Gateway 담당이 정한다.
- 이 결과는 모두 local(Docker VM 32코어·16GiB)에서 쟀다. 배포 환경(4 vCPU에 전체 스택) 성능 테스트는 따로 한다. 절대 수치는 배포 환경에서 크게 낮아질 수 있다.
- 선점 만료 한 주기 상한: 100이면 초당 약 20건이 상한이라 부하 중 적체가 쌓였다. 1,000으로 올리자 적체가 수백 건 아래로 유지됐다(5절). `seathold.expiry.batch-size` 기본값을 올리거나, 주기 안에서 대상이 빌 때까지 처리하되 시간 상한을 두는 방식으로 feat 브랜치에 반영한다(선점 담당, ISE-13).
- 잠금 번짐: 커넥션을 잡기 전에 거절하는 장치(선점 동시 처리 상한, Redis 사전 거절)를 검토한다. 잠금 장애 주입에서 S3만으로는 번짐이 남았다(5절).
- 유령 선점: 클라이언트가 이미 포기한 요청을 서버가 처리하지 않게 한다(요청 기한 전달, Tomcat 대기열 상한, 서버 쪽 요청 시한). 잠긴 행 집중 측정에서 잠금 해제 순간 A 9건, B 8건이 아무 응답 없이 선점됐다(5절).
