# 좌석 선점 부하(스트레스) 시나리오 (ISE-79·ISE-18)

상태: 설계, L1·L2·L3·L6 로컬 근사 측정 완료 (2026-11-03, 좌석 선점 담당 최권우). 결과와 한계는 [concurrency-results.md](concurrency-results.md) 4절. 근사 구현은 `reservation-service`의 `SeatHoldLoadTest`(`SEATHOLD_LOAD=true`일 때만 실행)다

동기형 선점 API의 처리량·지연을 개선 전후로 같은 조건에서 비교하는 시나리오다. 동시성 정합성은 [concurrency-scenarios.md](concurrency-scenarios.md)의 C1~C7이 맡고, 이 문서는 지연·처리량·포화점을 맡는다. 동기형과 접수형(Kafka)의 비교는 ISE-18 범위이며 같은 시나리오를 다시 쓴다.

- 근거: SA 3장(검증 기준·오류 정의), 3-1(측정 방식), 3-2(숫자 근거), 9-4(숫자 기준)
- 부하 도구, 가상 사용자 토큰 사전 발급, 좌석 초기화 스크립트, 측정 환경 기록표는 ISE-25(동기형 기준선 측정, 대기열·부하 테스트 담당 권영은)의 산출물이다. 이 문서는 그것을 재사용하고 좌석 선점에 필요한 시나리오만 더한다. 도구가 아직 정해지지 않았으면 k6를 제안한다(시나리오 단계 설정과 p95 집계가 내장되어 있다). 도구 선택은 ISE-25 담당과 정한다.

## 1. 측정 대상과 판정

- 대상: `POST /api/v1/schedules/{scheduleId}/reservations`(동기형, 201).
- 성공은 201, 정상 거절은 409(`SEAT_ALREADY_HELD`, `PURCHASE_LIMIT_EXCEEDED`)다. 오류는 5xx와 타임아웃(Gateway 3초)만 센다(SA 3장).
- 지표: 평균·p95·p99 응답 시간, 처리량(초당 응답 수, 201·409 각각), 오류율, 포화점.
- 409 응답 시간을 201과 따로 본다. 잠금을 기다리다 거절되는 시간이 사용자가 "이미 선택된 좌석"을 보기까지의 시간이다.
- 측정 뒤 대사 쿼리(`SeatHoldFixture`의 불변식과 같은 SQL)로 중복 판매 0건, `held_count` 불일치 0건을 확인한다. 부하에서 정합성이 깨지면 처리량 수치는 의미가 없다.

## 2. 공통 준비

1. 데이터: 회차 1개, 좌석 1,000석과 15,000석(KSPO DOME 약 15,000석, SA 3-2) 두 규모. 가상 사용자 1,000명. 좌석·사용자 규모는 `[가정]`이며 기준선 측정 뒤 갱신한다.
2. 측정마다 초기화: 대상 회차의 `seat_hold_requests`, `reservation_status_histories`, `reservation_seats`, `reservations`, `user_schedule_quotas`를 지우고 `schedule_seats`를 AVAILABLE로 되돌린다. ISE-25 초기화 스크립트에 이 회차 범위를 넣는다.
3. 프로필: loadtest(요청 제한 완화, 추적 샘플링 1%). 만료 스케줄러는 L5만 켜고 나머지는 끈다. 켜 두면 측정 중 만료가 섞인다.
4. 워밍업: 본 측정 전에 30초 동안 낮은 부하(VU 10)를 준다. JIT·커넥션 풀 초기화가 첫 수치를 왜곡하지 않게 한다.
5. 부하 도구는 대상과 다른 기기에서 돌린다(SA 3-1). 같은 기기에서 돌렸으면 환경 기록표에 적는다.
6. 측정 환경 기록표(SA 3-1 항목)에 이번 측정에서 바뀌는 값을 더 적는다: Hikari `maximum-pool-size`, `lock_timeout`, 만료 스케줄러 켬·끔과 인스턴스 수, 커밋 해시, 적용 단계(S0~S5).

## 3. 시나리오

| # | 이름 | 부하 모양 | 좌석 선택 | 보는 것 |
|---|---|---|---|---|
| L1 | 기준선 (SA 3장 정의) | VU 100이 1초 안에 시작, 각 10회 | 사용자마다 서로 다른 무작위 좌석 1~2개(충돌 적음) | 평균·p95·처리량·성공률. 모든 단계의 공통 비교축 |
| L2 | 인기 좌석 쏠림 (Synthetic) | VU 200, 60초 유지 | 요청의 80%가 좌석 5%(앞 구역)에 몰림, 나머지는 무작위 | 409 비율과 409 p95, 잠금 대기 세션 수, 커넥션 대기 |
| L3 | 포화점 계단 | VU 50 → 100 → 200 → 400 → 800, 단계마다 60초 | 15,000석에서 무작위 | 처리량 증가가 멈추고 p95가 급증하는 VU. `hikaricp_connections_pending` |
| L4 | 오용 혼합 | L1 + 사용자 10%가 같은 멱등키로 2회 연타, 5%가 탭 3개 동시 선점 | L1과 같음 | 5xx 0, 한도 초과 0(대사). 자기 요청 409 비율 |
| L5 | 만료 동시 처리 | 만료 대상 HELD 5,000건을 미리 만들고 L1 실행, 스케줄러 2 인스턴스 | L1과 같음 | 선점 p95가 만료 처리 중 얼마나 느려지는지, 5,000건 소진 시간, 헛수고 수 |
| L6 | 핫 좌석 집중 (E1 확대) | VU 1,000이 1초 안에 시작, 각 1회 | 좌석 10개 중 하나 | 좌석당 성공 1, 나머지 409. 409 p95와 커넥션 대기 시간 |

L2·L6이 TS-1(lock_timeout) 개선을 드러내는 시나리오다. L4는 TS-2·TS-3, L5는 TS-4의 부하 상태 확인이다. L1·L3은 모든 단계에서 돌려 회귀를 본다.

## 4. 처리량 개선 후보

후보는 가설이다. 한 번에 하나만 적용하고 L1·L3과 목표 시나리오를 다시 잰다.

| 후보 | 가설 | 확인 | 주의 |
|---|---|---|---|
| H1 `lock_timeout` 500ms (S3) | 핫 좌석에서 잠금을 기다리는 요청이 커넥션을 오래 쥐지 않아 L2·L6의 409 p95와 커넥션 대기가 준다 | L2, L6 | 잠금 보유 시간이 원래 짧으면 효과가 작다. 그 경우도 결과로 기록한다 |
| H2 커넥션 풀 5 → 20 | 지금 `config-repo/reservation-service.yml`은 5, SA 9-4는 20이다. 풀이 먼저 막혀 DB 잠금 효과가 가려진다 | L3 포화점 이동 | 공유 설정이라 contract 이슈 대상이다(AGENTS.md 대전제 11). 측정은 loadtest 프로필 값으로 먼저 한다 |
| H3 트랜잭션 축소 | 결제 토큰 서명이 트랜잭션 안에 있어 잠금 보유 시간에 들어간다. 커밋 뒤로 옮기면 보유 시간이 준다 | Zipkin 구간, L2 | 커밋 뒤 서명 실패 시 응답 규칙을 정해야 한다(contracts.md) |
| H4 왕복 줄이기 | 좌석 조회 뒤 UPDATE를 하는 두 번 왕복을 `UPDATE ... RETURNING` 한 번으로 줄인다 | L1, L3 | 가격·회차 검증을 RETURNING 값으로 대신해야 한다 |
| H5 접수형 전환 | Kafka 접수형이 스파이크를 흡수한다 | ISE-18 | ISE-79 범위 밖이다 |

## 5. 수집 위치

- 응답 지표: 부하 도구 결과(평균, p95, p99, 상태 코드별 건수). Prometheus `http_server_requests_seconds`로 서버 쪽을 함께 본다.
- 커넥션 풀: Prometheus `hikaricp_connections_active`, `hikaricp_connections_pending`, `hikaricp_connections_acquire_seconds`.
- DB 잠금: Postgres 지표 수집기가 없어 측정 중 10초마다 [concurrency-scenarios.md](concurrency-scenarios.md) 3-4절의 `pg_stat_activity` 쿼리와 `pg_stat_database.deadlocks`를 SQL로 떠서 남긴다. 지표 수집기 추가는 인프라 공유 변경이라 이번 범위에 넣지 않는다.
- 구간 지연: Zipkin(loadtest는 1% 샘플링). 느린 요청의 DB 구간과 토큰 서명 구간을 본다.

## 6. 결과 표 형식

| 단계 | 시나리오 | VU | 평균(ms) | p95(ms) | p99(ms) | 처리량(req/s) | 201 | 409 | 5xx·타임아웃 | 대사 불일치 | 커밋 |
|---|---|---|---|---|---|---|---|---|---|---|---|
| S0 | L1 | 100 | | | | | | | | | |

포화점은 L3 단계별 행을 그대로 두고, 처리량이 직전 단계보다 5% 미만 늘면서 p95가 2배 넘게 뛴 첫 단계를 포화점으로 적는다. 이 판정 기준은 `[가정]`이며 기준선을 본 뒤 조정한다.
