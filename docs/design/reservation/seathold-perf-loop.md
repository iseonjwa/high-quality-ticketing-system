# 좌석 선점 성능 개선 반복 기록 (2026-11-15~)

- 담당: 최권우 (좌석 선점)
- 관련: ISE-261, [배포 전 개선 측정](seathold-pre-deploy-measurements.md), [선점 구조 개선(ADR 0062)](seathold-structure-improvements.md)
- 진행 방식: 개선안 작성 → 다른 에이전트 세션의 독립 검토 → 적용 → 정합성 관문(전체 테스트, 동시성 C1~C7) → 변경 전·후를 같은 시점에 번갈아 측정 → 기록. 최대 5회 반복한다.
- 판정: p95, 좌석 조회 성공률, 동시 처리 요청 수(처리량), 실패율을 함께 본다. 정합성(중복 판매·불일치·유령 좌석)과 멱등성은 절대 조건이다. 차이가 측정 편차 안이면 "효과 없음"이다. 효과 없는 변경은 비용·위험이 있을 때만 되돌리고 근거를 적는다.

## 공통: 먼저 알아 둘 말
| 말 | 뜻 |
|---|---|
| 요청 기준 / 의도 기준 | 요청 기준은 서버가 받은 HTTP 요청 하나하나(재시도 포함)다. 의도 기준은 사용자 한 명이 "이 좌석을 잡고 싶다"고 누른 한 번이다. 프론트가 503·응답 없음에 같은 멱등키로 최대 3번 더 보내므로, 의도 하나가 요청 여러 개가 될 수 있다 |
| 의도 실패율 | 재시도까지 다 하고도 201(성공)이나 409(이미 잡힘)를 받지 못한 의도의 비율. 소비자가 실제로 겪는 실패다 |
| 의도 p95 | 처음 누른 때부터 마지막 결과를 받을 때까지 걸린 시간의 p95. 재시도 대기(1·2·4초)가 들어간다 |
| 동시 처리 상한 | 선점을 동시에 N개까지만 처리하고, 자리를 못 얻으면 커넥션을 잡기 전에 503으로 거절하는 장치(ADR 0062) |
| 유령 좌석 | 사용자는 실패(타임아웃)로 봤는데 서버가 뒤늦게 잡은 좌석 |
| 잠금 장애 | 인기 구역 20석을 측정 내내 잠근 느린 트랜잭션(관리 작업이 오래 걸리는 상황을 흉내 냄) |

## 측정 환경
한 PC(32코어)에서 Spring Boot 앱과 Docker PostgreSQL에 HTTP로 부하를 준다(`SeatHoldLoadTest`). 풀 5개, 커넥션 대기 1초, Tomcat 기본(작업 스레드 200). 부하는 열린 모델(1초에 N건, 응답과 상관없이)이고, 소비자 재시도 모사(`SEATHOLD_LOAD_CLIENT_RETRY=true`)를 켠다. 같은 코드도 측정마다 15%까지 흔들린다.

## 반복 1: 동시 처리 상한에 대기 인원 상한 (커밋 `92ba4a47`)

### 1-1. 기존 방식과 문제점
- 동시 처리 상한(ADR 0062)은 자리 4개가 차 있으면 최대 200ms 기다리고, 그래도 못 얻으면 503이다. 기다리는 요청 수에는 제한이 없었다.
- 기다리는 동안 요청은 Tomcat 작업 스레드(기본 200개)를 쥔다. 잠금 장애가 없는 1,800/s에서는 거의 모든 요청이 자리를 기다려 스레드가 바닥났다. 스레드를 못 받은 요청은 시한 없는 Tomcat 작업 대기열에 쌓여 3초 뒤 TIMEOUT을 맞았고, 같은 스레드를 쓰는 좌석 조회도 함께 실패했다([배포 전 측정](seathold-pre-deploy-measurements.md) 11절).
- 그 측정은 재시도가 없는 부하였다. 실제 프론트는 503·응답 없음에 같은 멱등키로 최대 3번 더 보낸다(약 1·2·4초 뒤). 503이 부하로 되돌아오는 효과가 빠져 있었다.

### 1-2. 바꾼 것
- **대기 인원 상한:** 자리를 기다리는 요청이 `seat-hold.max-concurrent-queue`(기본 64)명 이상이면 기다리지 않고 바로 503. 스레드 점유가 "자리 4 + 대기 64" 안으로 묶인다. 자리 대기 시간(200ms)과 자리 수(4)는 그대로다.
- **줄 순서 유지:** 자리를 바로 얻는 경로도 `tryAcquire(0, 단위)`로 써서 공정 세마포어의 줄 순서를 지킨다(시한 없는 `tryAcquire()`는 기다리는 요청을 건너뛴다).
- **거절 이유 지표:** `seathold.concurrency.rejected{reason=queue_full|wait_timeout}`. 대기 인원 초과는 몰림이 처리 한계를 넘은 것, 대기 시간 초과는 자리를 쥔 요청이 오래 걸린 것(잠금 장애 등)이다.
- **측정 도구:** 부하 테스트에 소비자 재시도 모사(`SEATHOLD_LOAD_CLIENT_RETRY`)와 의도 기준 지표를 더했다.

### 1-3. 예상
- 잠금 장애 없는 1,800/s: TIMEOUT이 거의 0, 좌석 조회 100% 근처. 다만 자리 4개의 처리 한계(약 1,800/s)에 닿아 TIMEOUT이 503으로 옮겨 갈 뿐일 수 있고, 재시도로 503이 늘 수 있다(검토 세션 지적).
- 잠금 장애 300/s: 지금과 같음. 600/s: 503 비율은 비슷하고 p95는 감소.

### 1-5. 결과가 이렇게 나온 이유
- **C가 B보다 TIMEOUT·유령·조회 실패를 없앤 이유:** 대기 인원이 64명으로 묶여 Tomcat 스레드가 바닥나지 않는다. 넘친 요청은 수 ms 안에 503을 받고 빠진다. 스레드가 남으니 좌석 조회도 바로 처리된다. 3초 동안 서버 안에 갇혀 있다가 뒤늦게 처리되는 요청이 없어 유령 좌석도 0이다.
- **C의 의도 실패율이 B보다 높은 경우(600/s 잠금 장애, 1,200/s)가 있는 이유:** B는 넘친 요청을 Tomcat 대기열에 3초까지 붙잡아 두었다가, 그중 일부를 늦게라도 처리했다(그 대가가 TIMEOUT, 유령, 조회 실패다). C는 그 요청을 바로 503으로 돌려보내고, 재시도 4번이 모두 몰림 구간에 걸리면 최종 실패가 된다. 1,200/s에서는 순간 몰림이 대기 인원 64명을 넘어 실패가 1.6% 생겼다.
- **정상 피크에서 상한을 끈 A가 가장 좋은 이유:** A는 커넥션 5개를 모두 선점에 쓰고, 상한은 4개만 쓴다. 처리 한계가 20% 낮다. 1,800/s는 자리 4개의 한계 근처라 C에서는 503 → 재시도가 다시 몰려(요청 기준 실패 53.8%, 평균 1.9번 시도) 11.3%가 끝내 실패했다. A는 그 부하를 커넥션 대기로 흡수했다.
- **잠금 장애에서 A가 무너지는 이유:** 잠긴 좌석을 노린 요청이 50ms씩 커넥션을 쥐어 처리 한계가 초당 수백 건으로 떨어진다. 재시도까지 몰려 3초 타임아웃이 쌓이고, 유령 좌석 216석, 좌석 조회 성공 20%다. 상한은 이 상황을 막으려고 있다.
- **가상 스레드(D)를 채택하지 않은 이유:** 스레드 고갈이 없어져 C와 비슷한 결과였지만 나은 점이 없다(1,800/s 의도 실패 14.7% 대 C 11.3%, p95 208 대 54ms). 서비스 전체(다른 담당 모듈 포함)의 실행 방식을 바꾸는 변경이라 위험에 견줘 얻는 것이 없다.

### 1-6. 판정
- **C 유지.** 상한을 켰을 때의 실패 모양이 "3초 TIMEOUT·유령 좌석·조회 실패"에서 "빠른 503 + 재시도"로 바뀌었다. 정상 1,800/s에서는 의도 실패도 19.7% → 11.3%로 줄었다.
- **남은 문제(다음 반복):** 상한 4개가 커넥션 5개보다 좁아 정상 피크에서 처리 한계를 20% 깎는다. 1,200/s에서도 대기 인원 64명이 순간 몰림에 넘친다.

## 반복 2: 커밋 뒤 작업을 자리 밖으로, 대기 인원 128, 풀 6 참고 측정 (커밋 `e8b91bb7`)

### 2-1. 기존 방식과 문제점
- 반복 1 뒤에도 정상 피크에서는 상한을 끈 쪽이 나았다. 자리 4개의 처리 한계(자리 수 ÷ 자리 점유 시간)가 커넥션 5개보다 낮기 때문이다.
- 자리는 `syncService.hold` 전체 동안 쥐었다. 여기에는 커밋 뒤의 일도 들어 있었다. 입장 토큰 대기열 정리(Redis 호출)와 결제 토큰 서명(CPU, 약 0.11ms)은 커넥션을 쓰지 않는데도 자리를 쥔 채 했다.
- 독립 검토에서 세 가지를 지적받았다.
  - 좌석 조회 탐침은 1초 캐시라 커넥션을 회차당 초당 1번만 써서 "커넥션 보호"를 판정할 수 없다.
  - 자리 수를 풀 크기(5)와 같게 하면 같은 풀을 쓰는 배경 작업(접수형 소비자, 만료, 결제 결과 소비자, Outbox 릴레이)의 몫이 없어진다. 부하 테스트에는 이 부하가 없어 실제보다 좋아 보인다. → 자리 5 후보는 채택 후보에서 뺐다.
  - 자리 점유 시간은 커넥션 사용 시간보다 길 것이다. → 계측을 넣었다.

### 2-2. 바꾼 것
- **커밋 뒤 작업을 자리 밖으로(R2-b):** `SyncSeatHoldService.hold(command, gate)`. 서비스가 트랜잭션 단계만 문(`SeatHoldGate`, 컨트롤러가 동시 처리 상한을 넘김) 안에서 하고, 입장 토큰 정리와 결제 토큰 서명은 자리를 돌려준 뒤에 한다. DB를 다시 읽는 재응답 경로와 예외 경로의 정리는 문 안에 남긴다(검토 확인).
- **계측:** 자리 점유 시간 `seathold.concurrency.held`. 커넥션 획득 대기 `hikaricp.connections.acquire`를 조건별로 비교한다.
- **측정 도구:** 배포 경로처럼 입장 토큰 ID를 붙이는 옵션, 대기열 정리에 인위적 지연(이번 측정 1ms, 배포의 Redis 왕복을 흉내 낸 가정값)을 넣는 옵션, 매번 커넥션을 쓰는 탐침(접수 결과 조회, 없는 ID → 404) 옵션.

### 2-3. 예상
- R2-b: 자리 점유 시간이 대기열 정리 지연(1ms)만큼 줄어 처리 한계가 오른다.
- 대기 인원 128(F2): 재시도 파도(1·2·4초)를 더 흡수해 정상 1,200/s 실패가 준다. 잠금 장애 600/s에서는 p95가 나빠질 수 있다(검토 지적).
- 풀 6·자리 5(H2, 참고): 처리 한계가 25% 올라 정상 피크 실패가 준다.

### 2-5. 결과가 이렇게 나온 이유
- **R2-b가 효과가 없었던 이유(예상이 틀렸다):** 대기열 정리와 토큰 서명은 성공(201)한 요청에서만 돈다. 정상 피크 응답의 약 97%를 차지하는 409(사전 거절)는 예외로 끝나 이 일을 하지 않는다. 그래서 자리 밖으로 뺀 1ms는 요청 평균으로 약 0.02ms(성공 2% × 1ms)라 측정에 보이지 않는다. 실제로 C와 C2 모두 "자리 점유 − 커넥션 사용" 차이가 약 0.6ms로 같았다.
- **자리 점유 시간의 대부분은 409 경로의 DB 작업이다:** 409 요청 하나가 멱등키 조회 → 입장 토큰 사용 조회 → 회차 조회 → 좌석 조회 → 멱등키 재조회(같은 키 경합 확인) → 롤백으로 DB를 6번 오간다. 이것이 처리 한계를 정한다(다음 반복의 대상).
- **대기 인원 128이 도움이 안 된 이유:** 실패의 원인이 순간 몰림이 아니라 처리 한계 초과(ρ>1)였다. 대기 인원을 늘려도 같은 요청이 더 오래 기다린 뒤 503을 받을 뿐이라 p95만 두 배가 됐다. 잠금 장애 300/s에서는 대기 시간 200ms를 채우는 요청이 늘어 503이 늘었다.
- **풀 6·자리 5가 크게 나은 이유:** 처리 한계가 자리 수에 비례해 25% 오른다. 정상 1,800/s 의도 실패가 22.5% → 9.4%로 줄었다. 잠금 장애 300/s에서는 자리 하나가 더 있어 503이 0이 됐다. 이 조건은 배경 작업 부하가 없는 측정이고 풀 크기는 ISE-237(효승) 범위라 채택하지 않고 근거로 넘긴다.

### 2-6. 판정
- **R2-b 유지(효과 없음).** 되돌리지 않은 근거: 측정한 비용이 없다(모든 시나리오에서 편차 안). 위험으로 지적된 "Redis가 느릴 때 자리 밖에서 스레드를 쥔다"는 성공 요청(정상 피크의 약 2%)에만 해당해, 1,800/s × 2% × 200ms ≈ 스레드 7개 수준이다. 반대로 대기열 Redis가 느려지면 그 지연이 선점 자리를 잡아먹지 않는 이점이 남는다. 코드는 문 인터페이스 하나와 메서드 하나가 늘었다.
- **대기 인원 128 채택 안 함.** 기본 64 유지. 실패율 개선이 없고 p95가 나빠진다.
- **풀 6·자리 5는 ISE-237 근거로 전달(사용자 확인 뒤 댓글).**

## 반복 3: 409 경로의 조회를 합쳐 DB 왕복 줄이기 (커밋 `25fb338b`)

### 3-1. 기존 방식과 문제점
- 반복 2에서 자리 점유 시간의 대부분이 409 경로의 DB 작업이라는 것을 확인했다. 정상 피크 응답의 약 97%가 409(이미 잡힌 좌석)다.
- 409 한 건(입장 토큰 있음)이 DB를 6번 오갔다: ① 멱등키 행 조회 → ② 입장 토큰 사용 조회 → ③ 회차 조회 → ④ 좌석 조회 → 읽은 상태로 먼저 거절 → ⑤ 멱등키 재조회(같은 키 첫 요청이 그사이 커밋됐는지) → ⑥ 롤백.
- 처리 한계는 대략 자리 수 ÷ 자리 점유 시간이다. 409 경로가 가벼워지면 자리 수를 늘리지 않고도 한계가 오른다.

### 3-2. 바꾼 것
- **①+② 한 문장:** 멱등키 행이 있는지와 입장 토큰이 거절되지 않은 요청에 쓰였는지를 한 번에 읽는다(`SELECT EXISTS(멱등키), EXISTS(활성 토큰)`, PK와 부분 유니크 인덱스를 각각 탄다). 멱등키 행이 있을 때만 행을 읽어 재응답한다.
- **③+④ 한 문장:** 좌석을 회차와 함께 읽는다(`JOIN FETCH`). 지운 회차 조건(`deleted_at IS NULL`)은 쿼리에 직접 적었다. 결과가 비면(없는 회차나 모두 다른 회차의 좌석, 드묾) 그때만 회차를 따로 읽어 404와 좌석 수 불일치를 가른다.
- 동기형, 접수형 접수, 접수형 소비자(③+④만)가 같은 조회를 쓴다.
- **바꾸지 않은 것:** 검사 순서(멱등키 → 토큰 → 회차·판매 기간·좌석 → 잠금, `contracts.md` 1절)와 ⑤ 멱등키 재조회(같은 키 경합 보호, ADR 0062)는 그대로다.
- **버린 안:** 토큰 조회를 먼저 거절 뒤로 미루기. 계약의 검사 순서를 바꾸고, 쓴 토큰으로 온 사용자가 "줄 다시 서기"(403) 대신 "다른 좌석 고르기"(409)를 먼저 받아 잘못 안내된다.
- **덤으로 고쳐진 경합(검토 세션 지적):** 전에는 ①과 ②가 다른 문장이라, 같은 키 첫 요청이 그 사이에 커밋되면 재요청이 ①에서는 키 없음, ②에서는 자기 토큰이 쓰인 것으로 보여 403을 잘못 받을 수 있었다. 한 문장이면 같은 시점의 데이터를 읽어 이 경합이 없다.

### 3-3. 예상
- 409 경로 6번 → 4번, 성공 경로 14번 → 12번.
- 처음에는 문장 하나를 약 0.5ms로 보고 처리 한계 +40%로 잡았다. 검토 세션이 "자리 점유에는 왕복 말고도 커넥션 대여·반납, Hibernate 처리, 예외·롤백 비용이 있고 로컬 왕복은 0.1~0.3ms일 수 있다"고 지적해 +10~30%로 낮춰 잡았다.

### 3-4. 실측 (조건마다 4회 평균, 반복 2 코드 → R3 → R3 → 반복 2 코드 순서. 반복 2와 같은 옵션)

| 잠금 장애 600/s | 의도 실패율(회당) | 29.1%(29.6, 28.4, 29.6, 28.8) | 25.1%(22.1, 25.5, 26.4, 26.6) |

### 3-5. 결과가 이렇게 나온 이유
- **자리 점유가 약 1.1ms 줄었다:** 409 경로에서 문장 2개를 없앴더니 자리 점유가 3.58 → 2.40ms(1,800/s)로 줄었다. 문장 하나당 약 0.55ms다. 검토의 보수적 추정보다 컸다. 이 환경에서는 문장마다 붙는 비용(Hibernate 쿼리 처리와 엔티티 수화, 커넥션 드라이버, Docker 루프백 왕복)이 큰 것으로 본다. 특히 ③ 회차 조회는 엔티티를 따로 만들던 문장이라 없어진 비용이 컸다.
- **처리 한계가 약 50% 올랐다:** 자리 4개 ÷ 2.4ms ≈ 1,670/s(이전 4 ÷ 3.6ms ≈ 1,110/s). 그래서 1,500/s가 한계 아래로 들어와 실패 0%가 됐고, 1,800/s는 한계를 조금 넘어 2.4%만 실패했다. 한계 근처는 실패율이 절벽처럼 변하는 구간이라 한계가 조금만 올라도 실패가 크게 준다.
- **잠금 장애 300/s의 503이 거의 없어진 이유:** 잠긴 좌석을 노리지 않은 요청이 자리를 빨리 돌려줘, 잠긴 좌석 때문에 50ms를 쥐는 요청이 있어도 자리가 덜 찬다.
- **잠금 장애 600/s가 조금만 나아진 이유:** 이 상황의 병목은 잠긴 좌석을 노린 요청이 자리를 50ms씩 쥐는 것이다. 조회를 합쳐도 이 50ms는 그대로다.

### 3-6. 판정
- **유지.** 정상 피크의 의도 실패가 크게 줄고(1,800/s 22.6% → 2.4%), p95·조회·유령 지표가 모두 같거나 좋아졌다. 정합성 관문(전체 509건, 동시성 C1~C7, 지운 회차 404)을 통과했다.
- **다음 반복:** 남은 409 경로 문장은 멱등키·토큰 한 문장, 회차·좌석 한 문장, ⑤ 멱등키 재조회, 롤백이다. 검토 세션 제안대로 ①~④를 한 문장으로 읽으면 같은 시점의 데이터라 ⑤가 필요 없어진다.

## 반복 4: 사전 판정을 한 문장으로, 멱등키 재조회 제거 (커밋 `14cad0dd`)

### 4-1. 기존 방식과 문제점
- 반복 3 뒤 409 경로는 ⓐ 멱등키+토큰 한 문장 → ⓑ 회차+좌석 한 문장 → 먼저 거절 → ⑤ 멱등키 재조회 → ⑥ 롤백, DB 왕복 4번이었다. 문장 하나가 약 0.55ms(반복 3 실측)라 아직 2.4ms를 자리에 쥐었다.
- ⑤는 "같은 키 첫 요청이 ⓐ와 ⓑ 사이에 커밋되면, 재요청이 멱등키는 못 보고 자기 좌석만 잡힌 것으로 봐 409를 받는" 경합을 막으려고 둔 문장이다(ADR 0062).

### 4-2. 바꾼 것
- **한 문장 사전 판정:** 좌석(회차 JOIN FETCH)과 함께 멱등키 행 수, 활성 토큰 행 수를 선택절 하위 쿼리로 한 문장에서 읽는다. 결과가 비면(없는 회차·모두 다른 회차의 좌석, 드묾) 멱등키·토큰을 먼저 따로 읽어 재응답 여부를 정한다(회차가 지워진 뒤의 같은 키 재요청도 재응답).
- **⑤ 제거:** 한 문장은 한 시점의 데이터를 읽는다(READ COMMITTED에서 문장마다 스냅샷 하나). 동기형은 멱등키 행과 좌석 변경을 한 트랜잭션에 커밋하고, 접수형은 멱등키 행을 좌석보다 먼저 커밋한다. 그래서 한 스냅샷에서 "멱등키 없음 + 그 요청의 좌석 잡힘"은 나올 수 없다. 스냅샷 뒤에 커밋되면 좌석도 아직 비어 보여 쓰기로 가고, 멱등키 PK 충돌 → 재응답(TS-3)이 처리한다. 독립 검토가 동기형, 같은 키 연타, 접수형, 접수형으로 시작한 요청의 동기형 재요청(ADR 0058)에서 모두 성립한다고 확인했다. ADR 0061에 갱신을 적었다.
- **부분 인덱스 유지:** 토큰 조건의 거절 상태를 파라미터가 아니라 리터럴로 썼다. 부분 유니크 인덱스(`status <> 'REJECTED'`)는 조건이 리터럴이어야 계획기가 쓸 수 있다(검토 지적, EXPLAIN으로 인덱스 사용 확인).
- 접수형 접수도 같은 문장을 쓴다. 접수형 접수에는 원래 ⑤가 없어 두 문장 사이 경합으로 자기 좌석 409가 이론상 가능했는데, 이것도 닫혔다.

### 4-3. 예상
- 409 경로 4 → 2번. 합친 문장에 하위 쿼리 두 개가 붙어 조금 비싸므로 자리 점유 2.4 → 1.6~1.9ms(보수적), 처리 한계 약 2,100~2,500/s.

### 4-4. 실측 (조건마다 4회 평균, 반복 3 코드 → R4 → R4 → 반복 3 코드 순서. 같은 옵션, 정상 2,400/s 추가)

|---|---|---|---|
| 잠금 장애 300/s | 503 건수 / 요청 p95 / 의도 p95 | 249 / 173ms / 0.48초 | 1.5 / 114ms / 0.11초 |
| 잠금 장애 600/s | 의도 실패율(회당) | 25.6%(25.6, 26.8, 24.7, 25.5) | 21.4%(20.8, 21.1, 22.0, 21.8) |
| 정상 1,500/s | 의도 실패율 / 요청 p95 | 6.1% / 61ms | 0.0% / 30ms |

### 4-5. 결과가 이렇게 나온 이유
- **예상보다 더 줄었다(1.3ms):** 문장 2개를 없앴더니 자리 점유가 약 1.1ms 줄었다. 반복 3과 같은 "문장당 약 0.55ms"다. 합친 문장의 하위 쿼리는 PostgreSQL이 한 번만 계산해(상관 없는 스칼라 하위 쿼리) 추가 비용이 작았다.
- **2,400/s까지 실패가 0인 이유:** 처리 한계가 자리 4개 ÷ 1.3ms ≈ 3,000/s로 올라 2,400/s도 한계 아래다. 503이 거의 없으니 재시도 파도도 생기지 않는다(평균 시도 1.0번).
- **잠금 장애 600/s가 조금 나아진 이유:** 잠긴 좌석을 노리지 않은 요청이 자리를 더 빨리 돌려준다. 하지만 잠긴 좌석을 노린 요청이 50ms씩 자리를 쥐는 병목은 그대로라 21%가 남는다.

### 4-6. 판정
- **유지.** 정상 피크의 의도 실패가 측정한 모든 도착률(2,400/s까지)에서 0%가 됐고, p95도 크게 줄었다. 정합성 관문(전체 509건, 동시성 C1~C7)을 통과했다.
- **남은 것:** 409 경로의 롤백 왕복(문장 1개). 잠금 장애 때 잠긴 좌석을 노린 요청이 50ms씩 자리를 쥐는 문제(잠금 시한 50ms는 ADR 0061 결정이라 이번 루프에서 바꾸지 않는다).

## 반복 5: 트랜잭션 밖 빠른 거절 (실험 커밋 `3fe24936`, 되돌림 `b303b078`)

### 5-1. 기존 방식과 문제점
- 반복 4 뒤 409 경로는 쓰기 트랜잭션 안에서 사전 판정 한 문장 → 409 → 롤백, DB 왕복 2번이었다(자리 점유 약 1.3ms).

### 5-2. 바꾼 것(실험)
- 쓰기 트랜잭션을 열기 전에 JdbcTemplate 자동 커밋 한 문장으로 항상 한 행을 읽어 거절할 요청만 걸러 냈다(멱등키 존재, 활성 토큰, 회차 존재·매수 한도·판매 기간, 회차 소속 좌석 수, 선점 가능 좌석 수). 판정 순서는 계약대로, 같은 멱등키 재요청과 통과한 요청은 반복 4의 쓰기 트랜잭션 경로를 그대로 탔다. 매수 한도·판매 기간은 같은 함수를 쓰게 했다.
- 독립 검토 반영: 좌석 `deleted_at`은 거르지 않음(JPA 경로와 같게), 공연은 조인하지 않음, 시각은 `OffsetDateTime`으로 읽어 앱 시계로 비교.

### 5-3. 예상
- 409 경로 2 → 1번(롤백 왕복과 JPA 처리가 빠짐), 자리 점유 1.3 → 0.7~1.0ms. 성공 경로는 문장과 커넥션 대여가 하나씩 는다(검토 지적: 좌석을 잡을 요청에 커넥션 대기가 붙을 위험).

### 5-4. 실측 (조건마다 L9 4회·L1 6회, 반복 4 코드 → R5 → R5 → 반복 4 코드)
| 상황 | 지표 | 반복 4 코드 | R5 |
|---|---|---|---|
| 잠금 장애 300/s | 의도 실패 / 요청 p95 | 0% / 100ms | 0% / 109ms |

### 5-5. 결과가 이렇게 나온 이유
- **409가 대부분인 고부하에서 나아진 이유:** 409 요청이 트랜잭션을 열지 않고 문장 하나로 끝나 롤백 왕복과 JPA 처리가 빠졌다. 자리 점유가 약 0.35ms 줄어 처리 한계가 약 3,000 → 3,400/s 이상으로 올랐다. 3,600/s 의도 실패가 19.7% → 4.3%가 됐다.
- **성공 위주 부하에서 나빠진 이유:** 성공할 요청은 빠른 판정 문장을 먼저 하고, 그다음 쓰기 트랜잭션에서 같은 판정을 다시 한다. 문장 하나와 커넥션 대여 한 번이 늘어 성공 요청이 자리를 더 오래 쥔다. 성공 비율이 높으면 이 비용이 409 쪽 이득보다 커서 처리량이 17% 줄고 p95가 22% 늘었다.

### 5-6. 판정: 되돌림 (근거)
되돌린 이유를 누구나 확인할 수 있게 적는다.
1. **좌석을 잡는 요청이 손해를 본다.** 성공 위주 부하에서 처리량 977 → 807 req/s(-17%), 요청 p95 158 → 194ms(+22%), 성공 응답 p95 약 190 → 212ms였다. 회당 값이 거의 겹치지 않아 편차가 아니다. 실제 오픈에서 빈 좌석이 많은 첫 몇 초가 바로 이런 성공 위주 구간이고, 이 구간의 요청이 가장 가치 있다(좌석을 실제로 사는 사용자).
2. **이득이 보이는 구간이 좁다.** 이 PC에서 2,400/s 이상에서만 차이가 났고, 그 구간에서도 반복 4 코드의 의도 실패는 이미 0~6%(3,600/s에서 19.7%)였다. 배포 서버(4 vCPU, 여러 서비스가 함께 돎)에서 이 도착률까지 선점 서버가 받을지는 Gateway·대기열 입장 속도에 달렸다.
3. **검토가 지적한 위험이 남는다.** 성공 요청이 커넥션을 두 번 빌린다. 같은 풀을 쓰는 배경 작업(접수형 소비자, 만료, 결제 결과 소비자, Outbox 릴레이)과 겹치면 두 번째 대여에서 기다리고, 1초를 넘으면 좌석을 잡을 요청이 실패한다. 부하 테스트에는 이 배경 부하가 없어 측정에 드러나지 않았다.
4. **판정 규칙이 두 곳에 생긴다.** 엔티티 규칙(`ScheduleSeat.isHoldable`, 회차 소프트 삭제)과 원시 SQL 조건을 계속 함께 맞춰야 한다. 반복 5 검토에서도 "좌석 deleted_at을 거르면 결과가 달라진다"처럼 어긋나기 쉬운 지점이 나왔다.
- 구현은 커밋 `3fe24936`에 남겨 두었다. 나중에 "최근 409 비율이 높을 때만 빠른 거절을 켜는" 방식이나, 배포 측정에서 409 구간이 병목으로 확인되면 다시 꺼낼 수 있다.

### 남은 일
- **잠금 장애 600/s의 21%:** 잠긴 좌석을 노린 요청이 잠금 시한(50ms, ADR 0061)만큼 자리를 쥐는 것이 병목이다. 잠금 시한이나 잠금 감지 방식을 바꾸는 것은 ADR 결정이라 이번 루프에서 하지 않았다.
- **풀 크기(ISE-237, 효승):** 반복 2 참고 측정에서 풀 6·자리 5가 정상 1,800/s 의도 실패를 22.5 → 9.4%로 줄였다(최종 코드에서는 다시 재야 함). 댓글 전달은 사용자 확인 뒤.
- **캐시 사전 거절(ISE-281, 효승 contract):** 좌석 조회 1초 캐시로 409 대부분을 DB 없이 거르면 409 경로가 0번이 된다.
- **동시 처리 상한은 코드 기본값 끔이다.** 배포 측정에서 켤 값(자리 4·대기 인원 64)은 config-repo 공유 설정이라 사용자 확인 뒤 넣는다.
- **배포 측정에서 다시 볼 것:** 왕복 시간이 다른 환경에서 문장 줄이기 효과, 배경 작업이 있을 때의 커넥션 대기(`hikaricp.connections.acquire`), 자리 사용 중 수.
