# 선점 동시 처리 상한과 커넥션 풀을 함께 올렸을 때 (로컬 측정, ISE-237 근거)

- 날짜: 2026-11-16
- 브랜치: `fix/ISE-261-seat-hold-lock-timeout`(반복 4 코드, `e0b659e9`). 코드는 바꾸지 않고 설정만 바꿨다.
- 관련: ISE-237(풀 크기, 담당 반효승), ADR 0062 결정 3(동시 처리 상한), [성능 개선 반복 기록](seathold-perf-loop.md), [학습 노트: 상한은 왜 4인가](../../learning/kwonwoo/qna/2026-11-16-seathold-concurrency-limit-4.md)

## 1. 요약
- 상한은 늘 "풀 - 1"로 두고(다른 API 몫 1개) 풀을 5 → 16까지 올렸다. **로컬에서는 처리 한계가 상한 수에 거의 비례해 올랐고, 꺾이는 지점은 16까지 보이지 않았다.**
- 정합성은 모든 조합·부하에서 지켜졌다. 중복 판매, 좌석·원장 불일치, 유령 좌석, 500, 3초 타임아웃이 모두 0이다. 커넥션 탐침(짧은 요청)도 모두 100% 성공했다.
- 그러나 **이 결과로 운영 풀을 정하지 않는다.** 11/15 배포 측정(ISE-237 X1)에서 풀 10은 커넥션을 쥐는 시간이 두 배가 되고 선점 p95가 1.06s → 1.83s로 나빠졌다. 원인은 호스트 CPU 포화로 봤다. 로컬 PC는 DB에 쓸 CPU가 넉넉해서 그 벽이 드러나지 않는다. config-repo(풀 5, 상한 끔)는 그대로 둔다.
- 로컬에서도 신호는 있다. 풀이 커질수록 한 건이 자리를 쥐는 시간이 조금씩 늘고(잠금 장애 10.8 → 11.4ms, 정상 4,000/s 1.58 → 1.67ms), DB CPU가 오른다. DB가 동시에 처리하는 일이 늘어 한 건이 느려지기 시작했다는 뜻이다. CPU가 적은 배포 DB에서는 이것이 훨씬 일찍, 크게 나타난다.

## 2. 측정 방법
- `SeatHoldLoadTest` L9(열린 모델, 응답과 상관없이 초당 정해진 수를 보낸다). 반복 4와 같은 옵션을 썼다.
  - 입장 토큰, 정리 지연 1ms, 프론트 재시도 모사(503·타임아웃이면 같은 키로 최대 4번), 커넥션 탐침 초당 20건(요청 상태 조회), 커넥션 대기 시한 1초, 대기 인원 64
- 잠금 장애: 일부 좌석을 미리 잠가 둬서, 그 좌석을 노린 선점이 잠금 대기 50ms(ADR 0061) 동안 커넥션을 쥔다. 정상: 잠긴 좌석이 없다.
- 순서: 1차는 5·4 → 6·5 → 8·7 → 10·9 → 10·9 → 8·7 → 6·5 → 5·4, 2차는 10·9 → 12·11 → 16·15 → 16·15 → 12·11 → 10·9로 번갈아 쟀다. 실행마다 3회 반복하고 JVM 예열인 1회차는 버렸다(조건별 n=4).
- 의도 실패율: 사용자 한 명의 선점 시도(재시도 포함)가 끝내 201·409를 받지 못한 비율이다. 의도 p95는 그 시도가 결과를 받기까지 걸린 시간이다.
- DB CPU: `docker stats`로 postgres 컨테이너 CPU를 약 2초 간격으로 기록했다. 기동·정리 시간도 섞여 있어 평균보다 p90을 본다(100% = 1코어).
- 조건별 4회의 의도 실패율 범위는 ±2%p 안이었다(예: 5·4 잠금 600/s 19.1~20.9%).

## 4. 왜 이렇게 나왔나
- **처리 한계 ≈ 상한 ÷ 한 건이 자리를 쥐는 시간.**
  - 잠금 장애: 자리를 쥐는 시간이 평균 약 11ms다(잠긴 좌석을 노린 요청이 50ms씩 기다려 평균을 끌어올린다). 상한 4면 4 ÷ 11ms ≈ 초당 360건, 15면 ≈ 1,360건이다(계산값). 실측에서 0%를 유지한 최대 부하가 5·4는 300/s, 8·7은 600/s, 12·11은 900/s, 16·15는 1,200/s로 이 계산과 맞는다.
  - 정상: 자리를 쥐는 시간이 약 1.35ms라 상한 4면 약 2,960/s(계산값)다. 5·4가 3,000/s에서 처음 실패한 것과 맞는다.
- **상한을 풀보다 하나 작게 둬서 짧은 요청이 막히지 않았다.** 모든 조합에서 탐침 성공 100%, 탐침 p95 2~4ms, 커넥션 대기 최대 0~1건이었다.
- **로컬에서 꺾이지 않은 이유:** 정상 4,000/s에서도 DB CPU p90이 144~151%(1.5코어)였다. 이 PC의 DB 컨테이너는 그보다 많은 코어를 쓸 수 있어 CPU 벽에 닿지 않았다. 배포 DB는 좌석 조회만으로 약 210%를 쓴 기록이 있고(ISE-237 본문, S1), X1에서는 풀 10에서 이미 지연이 나빠졌다.

## 5. 판단
- **config-repo는 바꾸지 않는다.** 풀 크기는 ISE-237 범위이고, 담당 쪽이 배포 측정을 근거로 "운영 풀 5 유지, CPU 개선 뒤 재측정"으로 정했다. 로컬 결과는 CPU 벽이 없는 조건이라 그 결정을 뒤집을 근거가 아니다.
- 이 측정이 ISE-237에 보탤 수 있는 것
  - 상한은 "풀 - 1"이 맞다. 풀을 몇으로 정하든 짧은 요청 몫 하나를 남기면 탐침 실패와 500이 없었다.
  - 풀을 올릴 때의 이득은 잠금 장애 구간에서 크다(600/s 실패 19.9% → 8·7에서 0%). 정상 부하에서는 5·4로도 2,400/s까지 실패가 없다.
  - 배포에서 다시 잴 때는 의도 실패율과 함께 `seathold.concurrency.held`(자리 쥐는 시간)와 DB CPU를 본다. 풀을 올렸는데 자리 쥐는 시간이 같은 비율로 늘면 이득이 없다. X1이 그 경우였다.
- 처리 한계를 CPU 비용 없이 올리는 쪽은 "자리를 쥐는 시간"을 줄이는 것이다. 잠금 장애에서는 잠긴 좌석을 노린 요청의 50ms 대기가 대부분이다. 이를 줄이려면 ADR 0061(잠금 대기 50ms)나 캐시 사전 거절(ISE-281)을 다시 봐야 해서 이번 범위에 넣지 않았다.
