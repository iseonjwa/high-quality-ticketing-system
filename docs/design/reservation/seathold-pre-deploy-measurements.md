## 2. 먼저 알아 둘 말
| 말 | 뜻 |
|---|---|
| 처리량(throughput) | 1초에 끝낸 선점 요청 수(req/s). 201과 409를 모두 센다 |
| p95 | 요청을 빠른 순으로 줄 세웠을 때 95번째 백분위의 응답 시간. "느린 쪽 5%가 이것보다 느리다" |
| 커넥션 사용 시간 | 요청이 커넥션 풀에서 DB 연결을 빌려 돌려줄 때까지의 시간(Hikari `hikaricp.connections.usage`). 트랜잭션 안에서 한 일이 길수록 길다. 풀이 5개라 이 시간이 곧 처리 한계를 정한다 |
| 잠금 시한(`lock_timeout`) | 좌석 행 잠금을 이 시간(50ms, ADR 0061) 안에 얻지 못하면 포기하고 409로 돌려보내는 설정 |
| 동시 처리 상한 | 선점을 동시에 4개까지만 처리하고, 자리를 200ms 안에 못 얻으면 커넥션을 잡기 전에 503으로 거절하는 장치(ADR 0062) |
| 닫힌 모델 / 열린 모델 | 닫힌 모델은 가상 사용자(VU)가 응답을 받으면 다음 요청을 보낸다(L1·L7·L10). 열린 모델은 응답과 상관없이 1초에 N건씩 보낸다(L9) |
| 만료 회수 | 결제하지 않고 선점 시간이 지난 예매를 HELD → EXPIRED로 바꾸고 좌석을 AVAILABLE로 돌려놓는 일 |

## 3. 측정 방법

### 3-1. 환경
- 한 PC(32코어)에서 Spring Boot 앱(Tomcat·Hikari)과 Docker PostgreSQL에 HTTP로 부하를 준다. 부하 생성기와 앱이 같은 JVM이다(`SeatHoldLoadTest`).
- 풀 5개, 커넥션 대기 시한 1초(config-repo와 같은 값). Gateway·인증은 없다. 요청에 입장 토큰 헤더가 없어 토큰 사용 여부 조회는 나가지 않는다.
- 같은 장비에서 전후를 비교하는 용도다. 절대 수치는 배포 환경(4 vCPU, 여러 서비스가 함께 돎)과 다르다.

### 3-2. 시나리오
| 이름 | 내용 | 무엇을 보나 |
|---|---|---|
| L1 | 좌석 15,000석에서 VU 100명이 무작위 1~2석을 30번씩(3,000건). 거의 모두 201 | 성공 경로의 비용(6번) |
| L7 | 좌석 1,000석, VU 200명이 20초 동안. 요청의 80%가 앞 100석에서 이웃 좌석 1~4개를 고른다. 대부분 409 | 오픈 직후 인기 구역 쏠림 |
| L9 | L7과 같은 좌석 선택 + 인기 구역 20석을 측정 내내 잠근 느린 트랜잭션. 초당 300건(처리 가능) / 600건(넘침), 동시 처리 상한 4·대기 200ms | 잠금 장애 중 번짐, 상한의 동작 |
| L10 | 결제하지 않은 선점 3,000건의 기한을 지나게 한 뒤, 만료 스케줄러를 운영과 같은 `fixedDelay`로 돌려 모두 회수하는 시간. 회수하는 동안 다른 회차에 VU 50명의 L7식 부하 | 만료 주기(5번) |

- 모든 시나리오에서 좌석 조회 탐침(선점과 상관없는 다른 회차)을 함께 돌려 번짐을 본다.
- L7·L1은 3회 반복이다. 1회차는 JVM 예열(JIT 컴파일) 때문에 늘 20~30% 느려 비교에서 뺀다.
- 서버 지표는 시나리오 시작과 끝의 누적값 차이로 낸다.

### 3-3. 측정 편차
같은 코드(2번 반영)로 L7을 두 번 쟀을 때 2·3회차 처리량이 1,277·1,293 req/s와 1,492·1,501 req/s로 약 15% 달랐다. 부하 생성기와 앱, DB가 한 PC의 CPU를 나눠 쓰고, 다른 프로세스 상태에 따라 흔들린다. 그래서 이 문서에서 **15% 안쪽의 차이는 "차이 없음"으로 본다.** 효과가 그보다 작을 것으로 예상한 6번은 변경 전·후를 번갈아 두 번씩 쟀다.

## 4. 개선 2: 계측 보강

### 4-1. 기존 방식과 문제점
- 배포 측정에서 선점이 느려지면 원인은 셋 중 하나다. 커넥션을 못 받았거나(풀), 좌석 잠금을 기다렸거나(잠금), CPU가 모자랐다.
- 지금까지는 Hikari 대기 수(`hikaricp_connections_pending`)와 결과 카운터(`seathold.result`)만 있었다. 잠금 대기는 부하 테스트가 따로 `pg_stat_activity`를 표본으로 떠서 "잠금을 기다리는 세션이 최대 몇 개"만 알 수 있었다. 배포 환경에서는 이 표본 수집이 없다.
- 동시 처리 상한은 거절 수(`seathold.concurrency.rejected`)만 셌다. 503이 나올 때 "상한이 너무 작아서"인지 "처리 가능량을 넘어서"인지 가를 수 없었다.

### 4-2. 바꾼 것
| 지표 | 종류 | 버킷 | 위치 |
|---|---|---|---|
| `seathold.seat_lock` | Timer. 좌석 조건부 UPDATE 한 문장의 시간. 잠금 시한 초과로 실패해도 기록한다 | 1·5·10·25·50·100ms | `SeatLockMetrics`, `SeatHolding.holdSeats` |
| `seathold.concurrency.in_use` | Gauge. 상한에서 지금 쓰고 있는 자리 수. 상한을 켰을 때만 등록 | | `SeatHoldConcurrencyLimit` |
| `seathold.concurrency.wait` | Timer. 상한의 자리를 기다린 시간(얻었든 못 얻었든) | 1·10·50·100·200ms | `SeatHoldConcurrencyLimit` |

- 라벨은 없다. 시계열은 Timer 두 개의 버킷(6 + 5)과 count·sum, Gauge 하나만큼 는다.
- 좌석 UPDATE는 잠금을 기다리지 않으면 1ms 안팎에 끝나고, 기다리면 50ms까지 늘어난 뒤 실패한다. 그래서 이 Timer의 분포가 곧 잠금 대기 분포다.

### 4-3. 결과
**비용(L7, 2·3회차)**
| | 처리량(req/s) | p95 | 커넥션 사용 시간 평균 |
|---|---|---|---|
| 기준선 | 1,513 · 1,500 | 155 · 152ms | 2.73 · 2.77ms |
| 계측 반영, 1차 | 1,277 · 1,293 | 188 · 175ms | 3.37 · 3.33ms |
| 계측 반영, 2차(같은 코드 다시) | 1,492 · 1,501 | 162 · 151ms | 2.78 · 2.77ms |

**새로 보인 것**
| 시나리오 | `seathold.seat_lock` | `seathold.concurrency.wait` / `in_use` |
|---|---|---|
| L7 | 586~617건, 평균 0.92~1.25ms, 5ms 이하 99.1~99.4% | 상한 끔(기록 없음) |
| L9 300/s | 1,346~1,363건, 평균 36.5~36.8ms, **50ms 이하 31.7~32.2%** | 평균 57~96ms, 200ms 이하 96.7~99.8%, 최대 사용 4/4 |
| L9 600/s | 1,469~1,484건, 평균 37.2~37.6ms, **50ms 이하 30.4~30.9%** | 평균 198ms, 200ms 이하 42.8~45.7%, 최대 사용 4/4 |

### 4-4. 지표가 이렇게 나온 이유
- **비용이 보이지 않는다:** 1차에서 처리량이 15% 낮았지만, 같은 코드로 다시 재니 기준선과 같았다(3-3절). 새 Timer는 좌석 UPDATE까지 간 요청에서만 기록된다. L7은 20초에 약 600번이고, 상한을 끈 L7에서는 대기 Timer가 한 번도 불리지 않는다. 기록 한 번이 1µs보다 짧으므로 처리량 1,500 req/s에 견줄 크기가 아니다.
- **L7에서는 잠금이 병목이 아니다:** 좌석 UPDATE의 99% 이상이 5ms 안에 끝났다. ADR 0062의 사전 거절이 이미 잡힌 좌석을 앞에서 걸러, 좌석 UPDATE까지 가는 요청은 대부분 이기는 요청이기 때문이다. 이 시나리오의 병목은 커넥션 수다(Hikari 대기 최대 195).
- **L9에서는 잠금이 병목이다:** 좌석 UPDATE 중 50ms 이하로 끝난 것이 약 31%뿐이다. 나머지 약 69%는 50~100ms 버킷에 있다. 잠금 시한 50ms를 다 기다리고 실패한 요청이다. 인기 구역 20석을 쥔 느린 트랜잭션 때문이다. 이전에는 "잠금 대기 세션이 최대 4개"라는 표본만 있었는데, 이제 "좌석 UPDATE의 몇 %가 잠금에 막혔나"가 배포 환경에서도 지표로 나온다.
- **상한이 왜 4/4로 붙어 있나:** 잠금에 막힌 요청은 자리 하나를 최소 50ms 쥔다. 자리 4개로는 이런 요청을 초당 최대 약 80건(4 ÷ 0.05초)만 처리할 수 있다. 초당 300건 중 좌석 UPDATE까지 가는 요청이 초당 약 68건이고 그중 약 69%가 50ms를 쥐므로 자리가 늘 거의 찬다. 그래서 300/s에서도 자리 대기가 평균 57~96ms였고 12~160건이 503을 받았다. 600/s에서는 자리 대기가 200ms 상한에 붙어(200ms 이하가 절반 이하) 절반 가까이가 503이다.
- **배포 측정에서 쓰는 법:** 상한 사용 중 수가 상한에 붙어 있고 `seat_lock`의 50ms 초과 비율이 높으면, 상한을 늘려도 잠금에 막힌 요청만 늘어난다(원인은 잠금). 사용 중 수가 붙어 있는데 `seat_lock`이 짧으면 상한이 작은 것이다.

## 5. 개선 5: 만료 주기 5초 → 1초

### 5-1. 기존 방식과 문제점
- `SeatHoldExpiryScheduler`는 앞 주기가 끝나고 5초 뒤에(`fixedDelay`) 최대 100건을 한 건씩 트랜잭션으로 만료한다. 100건을 처리하는 데 1초가 안 걸리는데 다음 주기까지 5초를 쉰다.
- 회수 속도의 상한이 "100건 ÷ (5초 + 처리 시간)", 곧 초당 약 17건이다. 부하 측정처럼 결제하지 않는 선점이 수천 건 쌓이면, 선점 시간이 지난 뒤에도 몇 분 동안 좌석이 HELD로 남는다. 그동안 같은 회차로 다음 측정을 돌리면 "이미 잡힌 좌석"이 섞여 결과가 오염된다. 실제 오픈에서는 그 좌석을 다른 사용자가 늦게 고르게 된다.

### 5-2. 바꾼 것
- config-repo `reservation-service.yml`에 `seathold.expiry.interval: 1s`를 넣었다. 코드 기본값(5초)과 한 주기 건수(100건)는 그대로다.
- 커넥션은 지금처럼 한 번에 하나만 쓴다. 쉬는 시간만 줄었다.

### 5-3. 결과 (L10, 3,000건, 5초·1초·5초·1초 순서로 번갈아)
| 주기 | 회수 시간 | 회수 속도 | 동시 선점 부하 처리량 / p95 | 좌석 조회 탐침 성공률 |
|---|---|---|---|---|
| 5초 (1회) | 192.0초 | 16건/초 | 520 req/s / 164ms (첫 실행, 예열) | 100% |
| 1초 (1회) | 65.2초 | 46건/초 | 811 req/s / 78ms | 100% |
| 5초 (2회) | 179.5초 | 17건/초 | 871 req/s / 73ms | 100% |
| 1초 (2회) | 63.9초 | 47건/초 | 854 req/s / 77ms | 100% |

- 미리 계산한 값은 5초 약 17건/초, 1초 약 55건/초였다. 5초는 맞았고, 1초는 계산보다 약 15% 낮았다.

### 5-4. 지표가 이렇게 나온 이유
- **약 2.8배 빨라진 이유:** 한 주기에 하는 일(100건, 약 0.9~1.1초)은 같고 쉬는 시간만 5초에서 1초로 줄었다. 한 주기 길이가 약 5.9초에서 약 2.1초로 줄어 같은 시간에 주기가 약 2.8번 더 돈다.
- **1초가 계산(55건/초)보다 낮은 이유:** 계산은 동시성 테스트 C6의 건당 약 8ms를 썼다. L10에서는 다른 회차에 선점 부하가 함께 돌아 커넥션 5개를 나눠 쓰므로 건당 약 11ms(100건 ÷ 47건/초 − 1초 = 약 1.1초)가 걸렸다.
- **선점 부하에 영향이 없는 이유:** 만료는 커넥션 하나로 한 건씩 처리해 주기를 줄여도 동시에 쥐는 커넥션은 여전히 최대 하나다. 만료가 바꾸는 좌석은 HELD 좌석이고 선점이 잠그는 좌석은 AVAILABLE 좌석이라 같은 행을 두고 기다리지 않는다. 2·3·4회차의 처리량(811~871 req/s)과 p95(73~78ms)는 주기와 상관없이 같은 범위다. 1회차가 낮은 것은 예열이다.
- **대가:** 회수할 것이 밀린 동안에는 커넥션 하나를 시간의 약 절반(1.1초 일하고 1초 쉼) 쓴다. 풀이 5개인 지금, 동시 처리 상한(4개)을 켜면 만료가 일하는 동안 좌석 조회 몫이 0~1개로 줄 수 있다. 풀 크기(ISE-237)를 정할 때 함께 본다.

## 6. 개선 6: 결제 토큰 서명을 트랜잭션 밖으로

### 6-1. 기존 방식과 문제점
- 동기형 선점은 트랜잭션 안에서 응답 결과를 만들며 결제 토큰(ES256)을 서명했다. 서명은 좌석 UPDATE 뒤, 커밋 전에 일어나 그동안 좌석 잠금과 커넥션을 쥔다.
- 이 PC에서 서명 한 번은 약 0.11ms다(JDK `SHA256withECDSA`, P-256, 2만 번 × 3회 평균 113.6~119.8µs).

### 6-2. 바꾼 것
- `SyncSeatHoldService`의 트랜잭션은 "무엇으로 답할지"(`Decision`: 결제 가능 / 확정됨 / 접수형)만 정하고, 토큰 서명은 커밋 뒤 `respond`에서 한다. 같은 멱등키 재요청 경로(`replay`)도 같은 방식이다.
- 서명이 실패하면 지금은 선점이 이미 커밋된 뒤 응답만 500이 된다. 같은 멱등키로 다시 보내면 재응답 경로에서 토큰을 다시 받는다.

### 6-3. 측정 방법
- 서명은 성공(201) 경로에만 있어 대부분 409인 L7·L9로는 보이기 어렵다. 거의 모두 201인 L1(3,000건 × 3회)을 주 지표로 쓴다.
- 같은 PC의 편차(3-3절)보다 효과가 작을 것으로 예상해, 변경 전·후 코드를 번갈아 넣었다. "변경 전"은 커밋 전에 한 번 서명하고 응답 때 한 번 더 서명하는 측정용 코드다. 커넥션을 쥔 시간은 원래 코드와 같고, 응답 지연에는 서명 한 번이 더 붙는다. 그래서 비교 지표는 응답 지연이 아니라 커넥션 사용 시간이다.
- 첫날 전·후·전을 재고 중단했다가, 다음 날 후·전을 다시 쟀다. 날이 바뀌며 PC 상태가 달라져 전체 값이 약 20% 빨라졌으므로, 같은 시점에 잰 것끼리 짝 1(첫날)·짝 2(다음 날)로 묶어 비교한다.

### 6-5. 지표가 이렇게 나온 이유
- **줄어든 크기가 서명 비용과 같은 이유:** 바꾼 것은 서명을 커밋 앞에서 뒤로 옮긴 것뿐이다. 커넥션을 쥔 시간에서 빠지는 것은 서명 한 번이고, 직접 잰 서명 비용이 약 0.11ms다. 두 짝 모두 0.10~0.11ms 줄었다.
- **차이가 작은 이유:** 서명 한 번은 성공 트랜잭션 전체(6~8ms) 가운데 1.5% 정도다. 성공 트랜잭션은 DB 왕복 14번과 커밋(디스크 기록)이 대부분을 차지한다.
- **얼마나 믿을 수 있나:** 같은 코드의 회차 간 차이(예: 변경 전 1과 2의 3회차 7.34 대 7.55ms)가 0.1ms보다 크다. 그래서 한 번의 비교로는 판단할 수 없다. 다만 시점이 다른 두 짝에서 방향과 크기가 모두 예상(0.11ms)과 같게 나와, "서명 비용만큼 줄었다"고 보는 것이 맞다.
- **처리량·지연이 거의 같은 이유:** L1·L7 모두 병목은 풀 5개의 커넥션 대기다. 짝 2에서 L1 처리량이 1~2% 높고 p95가 7~9ms 낮았지만, 커넥션을 쥐는 시간이 1~2% 준 만큼이라 측정 편차 안이다.
- **s6 단독 L7 결과가 낮았던 이유:** 6번을 넣은 직후 L7만 잰 1차 측정에서 2·3회차가 1,135·1,204 req/s였다. 같은 코드를 번갈아 잰 이번 측정에서는 1,437·1,457 req/s로 변경 전과 같았다. 1차 측정의 하락은 편차였다.
- **남기는 이유:** 측정으로 효과를 확인하지는 못했지만, 서명 비용이 커지는 배포 환경(코어당 성능이 낮고 CPU를 여러 서비스가 나눠 씀)에서는 잠금 구간이 그만큼 짧아진다. 코드상 손해가 없다(같은 일을 순서만 바꿈).

## 8. 측정하며 발견한 것
- **같은 코드도 15%까지 흔들리고, 날이 바뀌면 전체 값이 20%쯤 옮겨 간다.** 한 PC에서 부하 생성기와 앱, DB가 함께 도는 구조의 한계다. 효과가 작은 변경은 같은 시점에 변경 전·후를 짝으로 재고, 짝을 여러 번 모아야 한다.
- **측정을 중간에 멈추면 테스트 데이터가 남는다.** `SeatHoldFixture.cleanUp`은 테스트 메서드가 끝날 때 돈다. 프로세스를 멈추면 돌지 않아, 남은 선점이 다음 L10을 오염시킨다(10-5절).
- **잠금 장애 중에는 동시 처리 상한이 잠금에 막힌 요청으로 찬다.** 상한은 번짐(좌석 조회 실패)을 막는 데는 성공했다(탐침 성공 100%). 하지만 처리 가능한 300/s에서도 0.2~3.5%(12~209건)가 503을 받는다. 잠금 장애가 길어지면 잠금 시한(50ms)과 상한 자리 수가 함께 처리 한계를 정한다.

## 10. 같은 시점 재측정 (11/15)

### 10-1. 왜 다시 쟀나
4~6절의 수치는 11/14 하루 동안 단계별로 쟀고, 6번 일부는 11/15에 쟀다. 날이 바뀌자 같은 코드의 값이 약 20% 옮겨 가, 단계마다 다른 시점의 값을 비교한 셈이 됐다. 그래서 같은 시점에 두 코드를 번갈아 다시 쟀다.

### 10-2. 방법
- **기준선:** 2·6번을 넣기 전과 같은 동작으로 잠시 되돌린 코드. 좌석 UPDATE Timer와 상한의 대기 Timer·사용 중 Gauge를 빼고, 결제 토큰을 커밋 전에 서명한다. 응답 때 한 번 더 서명하는 측정용 코드라, 응답 지연과 닫힌 모델 처리량에는 서명 한 번(약 0.1ms)이 더 붙는다. 커넥션을 쥔 시간은 원래 코드와 같다.
- **최종:** 2·5·6번을 모두 넣은 코드.
- 기준선 → 최종 순서로 2번씩, 매번 L1·L7(각 3회, 2·3회차만 집계)과 L9(300·600/s 각 2회)를 쟀다. L9 300/s는 차이가 커 보여 최종 → 기준선 순서로 3번씩(각 3회) 더 쟀다.
- L10은 최종 코드에서 주기만 바꿔 5초·1초·5초·1초로 쟀다.

### 10-4. 결과가 이렇게 나온 이유
- **L7·L9 600/s가 같은 이유:** 두 시나리오의 병목은 커넥션 수(L7)와 잠긴 좌석(L9)이다. 2번의 계측과 6번의 서명 이동은 둘 중 어느 것도 바꾸지 않는다. 계측 기록은 1µs보다 짧고, 서명은 성공 응답(L7은 약 2%)에만 있다.
- **L9 300/s의 503이 크게 흔들린 이유:** 처음 4회씩은 기준선 8건, 최종 52건으로 최종이 모두 많았다. 순서를 바꿔 9회씩 더 재니 기준선 27건, 최종 18건으로 뒤집혔다. 300/s는 상한 자리 4개가 거의 찬 상태라, 자리 대기가 200ms를 넘느냐 마느냐가 몇 ms 차이로 갈린다. 그래서 회당 503이 0~105건으로 흔들린다. 13회씩 모은 평균의 차이(21 대 29건, 요청 6,000건의 0.1%p)는 회당 편차보다 훨씬 작아 차이로 보지 않는다.
- **L1 커넥션 사용 시간이 0.2ms 준 이유:** 바꾼 것은 서명 한 번(약 0.11ms)을 커밋 뒤로 옮긴 것이다. 11/14·11/15 첫 비교(6절)의 0.10~0.11ms와 같은 방향이고, 이번 0.2ms는 그보다 조금 크다. 같은 코드의 회차 간 차이(예: 기준선 2·3회차 5.86~6.85ms)가 이보다 커서 "서명 비용만큼 준다"는 6절 결론을 바꿀 근거는 아니다.
- **L1 처리량 +2.9%를 효과로 보지 않는 이유:** 측정용 기준선은 응답 때 서명을 한 번 더 한다. 닫힌 모델에서는 응답이 늦은 만큼 다음 요청이 늦어지므로, 이 차이의 일부는 측정 코드 때문이다.
- **L10이 11/14와 같은 이유:** 5초 17건/초, 1초 49건/초로 11/14(16~17, 46~47)와 같다. 만료는 커넥션 하나로 한 건씩 처리해 PC 상태의 영향을 덜 받는다.

### 10-5. 이번 측정에서 버린 값
- **L10 첫째·둘째 회:** 첫째 회는 400초 상한까지 기다리고도 자기 회차 3,000건을 하나도 회수하지 못했고, 둘째 회는 25건/초였다. 11/14에 측정을 중간에 멈춘 회차들은 정리 코드가 돌지 않아, 기한이 지난 선점이 DB에 남아 있었다. 만료 스케줄러는 가장 오래된 것부터 집으므로 그것부터 회수했다. 셋째·넷째 회만 위 표에 썼다. 이때 회수된 이전 회차 예매는 테스트 DB에 EXPIRED로 남아 있다(회차 12개, 21,086건).

## 11. 동시 처리 상한의 503 점검: 잠금 장애가 없을 때 (11/15)

### 11-1. 왜 쟀나
ADR 0062 뒤 503 비율이 크게 늘었다(L9 600/s에서 0% → 39~43%). 그때 상한은 잠금 장애가 있는 L9에서만 쟀다. 정상 오픈 피크(잠금 장애 없음)에서 상한을 켜면 어떻게 되는지는 재지 않았다. 그래서 L9에서 좌석 잠금만 끈 조건(`SEATHOLD_LOAD_L9_LOCKED=false`)으로 상한 끔과 상한 4·대기 200ms를 쟀다. 도착률은 600·1,200·1,800/s, 각 2회다.

### 11-2. 결과
| 도착률 | 지표 | 상한 끔 | 상한 4·대기 200ms |
|---|---|---|---|
| 600/s | 실패(503·TIMEOUT) / p95 | 0% / 6~8ms | 0% / 6~10ms |
| 1,200/s | 실패 / p95 | 0% / 6~7ms | 0% / 11ms |
| 1,800/s | 처리량 | 1,800 req/s | 1,564~1,565 req/s |
| | TIMEOUT(3초 초과) | 0건 | 9,936~15,594건(28~43%) |
| | 503 | 0건 | 35~177건 |
| | p50 / p95 | 14~19ms / 228~283ms | 2,224~2,675ms / 3,009~3,010ms |
| | 좌석 조회 탐침 성공률 | 100% | 56.1~74.0% |

### 11-3. 왜 이렇게 나왔나
- **1,200/s까지는 차이가 없다.** 선점 한 건이 커넥션을 쥐는 시간은 약 2.2ms다. 자리 4개면 초당 약 1,800건(4 ÷ 0.0022초)까지 처리할 수 있어 자리를 거의 기다리지 않는다.
- **1,800/s에서 상한이 오히려 무너뜨린다.** 도착률이 자리 4개의 처리 한계(약 1,800/s)에 닿자 거의 모든 요청이 자리를 수십~200ms 기다린다. 그런데 자리를 기다리는 동안 그 요청은 Tomcat 작업 스레드(기본 200개)를 쥐고 있다. 초당 1,800건이 평균 100ms 남짓씩 스레드를 쥐면 스레드가 200개를 넘게 필요해 바닥난다. 스레드를 못 받은 요청은 Tomcat 접수 대기열에 쌓이는데, 이 대기열에는 시한이 없어 3초 뒤 클라이언트가 TIMEOUT을 받는다. 503이 적은 것은 요청이 상한까지 오지도 못하고 그 앞에서 막혔기 때문이다.
- **좌석 조회까지 실패하는 이유:** 좌석 조회도 같은 Tomcat 스레드를 쓴다. 상한은 커넥션은 지켜 주지만 스레드는 지켜 주지 못한다.
- **상한을 끄면 버티는 이유:** 커넥션 5개를 다 쓰면 처리 한계가 약 2,300/s(5 ÷ 0.0022초)라 1,800/s를 감당한다. 상한 4는 커넥션 하나를 남기는 대가로 처리 한계를 20% 낮춘다.
- **잠금 장애가 있을 때(ADR 0062)는 왜 괜찮았나:** 잠금에 막힌 요청 때문에 처리 한계가 초당 수백 건으로 낮아, 넘친 요청 대부분이 200ms를 채우고 503을 받았다. 600/s × 0.2초 = 120개라 스레드 200개 안이었다.

### 11-4. 정리
- 상한(코드 기본 끔, config-repo에서도 켜지 않음)은 지금 배포 설정에는 영향이 없다. **다음 주 배포 측정에서 켜기 전에 고쳐야 한다.**
- 고칠 방향(측정 전): ① 자리 대기를 짧게(예: 50ms, 1,800/s × 0.05초 = 90개로 스레드 안), ② 상한을 풀 크기에 맞게 키움(풀은 ISE-237에서 정함), ③ 503에 `Retry-After`를 붙여 재시도를 늦춤. 각각 잠금 장애(L9 locked)와 정상 피크(L9 unlocked) 두 조건에서 재고 고른다.
- 아직 재지 않은 것: 프론트는 선점 503을 같은 멱등키로 처음 요청 포함 최대 4번 보낸다(재시도 3번, 약 1·2·4초 간격, `Retry-After`가 있으면 그 값. 선점 503에는 지금 이 헤더가 없다)(`frontend/src/pages/seats/seatHold.ts`). L9는 재시도 없는 고정 도착률이라, 503이 부하로 되돌아오는 효과가 빠져 있다.

## 12. 재현 방법
`SeatHoldLoadTest`는 환경 변수가 있을 때만 돈다. Docker 테스트 DB(`compose.test.yml`)가 떠 있어야 한다.

```bash
# L7(3회)
SEATHOLD_LOAD=true SEATHOLD_LOAD_POOL=5 SEATHOLD_LOAD_CONNECTION_TIMEOUT=1000 SEATHOLD_LOAD_REPEAT=3 \
  ./gradlew :reservation-service:cleanTest :reservation-service:test --tests '*SeatHoldLoadTest.L7*' -i

# L9(상한 4, 300·600/s, 2회)
SEATHOLD_LOAD=true SEATHOLD_LOAD_POOL=5 SEATHOLD_LOAD_CONNECTION_TIMEOUT=1000 SEATHOLD_LOAD_REPEAT=2 \
  SEATHOLD_LOAD_PROBE_RATE=20 SEATHOLD_LOAD_RATES=300,600 SEATHOLD_LOAD_MAX_CONCURRENT=4 \
  ./gradlew :reservation-service:cleanTest :reservation-service:test --tests '*SeatHoldLoadTest.L9*' -i

# L10(만료 회수 3,000건, 5초·1초 번갈아)
SEATHOLD_LOAD=true SEATHOLD_LOAD_POOL=5 SEATHOLD_LOAD_CONNECTION_TIMEOUT=1000 \
  SEATHOLD_LOAD_EXPIRY_INTERVALS=5000,1000,5000,1000 SEATHOLD_LOAD_EXPIRY_TARGETS=3000 \
  ./gradlew :reservation-service:cleanTest :reservation-service:test --tests '*SeatHoldLoadTest.L10*' -i

# L1(성공 위주 3,000건 × 3회)
SEATHOLD_LOAD=true SEATHOLD_LOAD_POOL=5 SEATHOLD_LOAD_CONNECTION_TIMEOUT=1000 SEATHOLD_LOAD_REPEAT=3 \
  SEATHOLD_LOAD_L1_ITERATIONS=30 \
  ./gradlew :reservation-service:cleanTest :reservation-service:test --tests '*SeatHoldLoadTest.L1*' -i
```

결과는 표준 출력의 `[SEATHOLD-LOAD]` 줄에 나온다. 서버 지표(`hikaricp.connections.usage`, `seathold.seat_lock`, `seathold.concurrency.wait`)는 시나리오 동안의 건수·평균·버킷 이하 비율이다.
