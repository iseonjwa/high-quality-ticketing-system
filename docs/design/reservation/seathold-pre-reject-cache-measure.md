# 캐시 사전 거절(ISE-281)을 켠 회와 끈 회 비교 (로컬 측정)

- 날짜: 2026-11-16
- 브랜치: `fix/ISE-261-seat-hold-lock-timeout`(dev 병합 뒤 `c539fb9c` 코드). 코드는 그대로 두고 `seat-hold.pre-reject.enabled`만 바꿨다
- 관련: ISE-281(dev #633 읽기 메서드, #648 사전 거절), [ADR 0061](../../decisions/0061-seat-hold-structure-precheck-reorder-limit.md) 결정 1, [성능 개선 반복 기록](seathold-perf-loop.md), [풀·상한 측정](seathold-pool-limit-sweep.md)

## 1. 요약
- **유지한다.** 캐시 사전 거절은 이 브랜치의 한 문장 사전 판정(반복 4)과 함께 쓸 때 더 낫다. 손해 본 구간은 없었다.
- 정상 부하의 처리 한계에서 효과가 컸다. 3,000/s에서 의도 실패 5.5% → 0%, 503 42.7% → 5.5%, 의도 p95 7.8초 → 46ms.
- 그 이유는 409 대부분(정상 95~96%)이 쓰기 트랜잭션 대신 캐시와 멱등키 조회 한 번으로 끝나서다. 그만큼 상한 자리를 쥐는 시간이 1.30~1.53ms에서 1.05~1.11ms로 20~30% 줄었다.
- 잠금 장애(일부 좌석을 다른 트랜잭션이 쥐고 있음)에서는 차이가 측정 편차 안이었다. 잠긴 좌석은 상태가 AVAILABLE이라 캐시가 거르지 못하고, 그 좌석을 노린 요청이 잠금 대기(50ms, ADR 0060) 동안 자리를 쥐는 것이 병목이기 때문이다.
- 정합성: 모든 조건에서 중복 판매, 좌석·원장 불일치, 유령 좌석, 500, 3초 타임아웃이 0이었다. 좌석 조회와 커넥션 탐침도 모두 100% 성공했다.

## 2. 측정 방법
- `SeatHoldLoadTest` L9(열린 모델). 옵션은 [풀·상한 측정](seathold-pool-limit-sweep.md)과 같다: 풀 5·상한 4·대기 인원 64, 입장 토큰, 정리 지연 1ms, 프론트 재시도 모사, 커넥션 탐침 초당 20건, 커넥션 대기 시한 1초
- 새 옵션 두 개를 더했다
  - `SEATHOLD_LOAD_PRE_REJECT`(기본 true): `seat-hold.pre-reject.enabled`
  - `SEATHOLD_LOAD_SEAT_VIEW_RATE`: 선점 대상 회차의 좌석 조회를 초당 N건 보낸다. 캐시는 누군가 그 회차 좌석을 조회해야 채워진다. 이 옵션이 없으면 켠 회도 사전 거절이 한 번도 일어나지 않는다. 이번에는 두 조건 모두 50/s로 같게 줬다
- 순서: 끔 → 켬 → 켬 → 끔. 실행마다 3회 반복하고 JVM 예열인 1회차는 버렸다(조건별 n=4)
- 결과에 `preRejected`(사전 거절 수)와 `preRejectedOf409`(409 중 비율), 좌석 조회 성공률·p95를 더했다

## 3. 결과
### 정상 (잠긴 좌석 없음)
| 도착률 | 지표 | 끔 | 켬 |
|---|---|---|---|
| 1,800/s | 의도 실패 / 의도 p95 | 0% / 13ms | 0% / 15ms |
| | 409 중 사전 거절 | 0% | 94.7% |
| | 자리 쥐는 시간 | 1.36ms | 1.11ms |
| 2,400/s | 의도 실패 / 의도 p95 | 0% / 30ms | 0% / 25ms |
| | 자리 쥐는 시간 | 1.30ms | 1.05ms |
| 3,000/s | 의도 실패 / 의도 p95 | **5.5% / 7.8s** | **0% / 46ms** |
| | 503 비율(요청 기준) | 42.7% | 5.5% |
| | 409 중 사전 거절 | 0% | 96.2% |
| | 자리 쥐는 시간 | 1.53ms | 1.07ms |

- 3,000/s 의도 실패 범위: 끔 4.8~6.3%, 켬 0.0%(4회 모두). 범위가 겹치지 않는다.
- 1,800·2,400/s의 p95 차이는 편차 안이다(끔 1,800/s 의도 p95 8~23ms, 켬 6~37ms).

### 잠금 장애 (좌석 20석을 다른 트랜잭션이 쥠)
| 도착률 | 의도 실패 끔 → 켬 | 409 중 사전 거절 |
|---|---|---|
| 300/s | 0% → 0% (의도 p95 109 → 85ms, 범위 84~145 대 76~104로 겹침) | 79% |
| 600/s | 20.8% → 19.6% (범위 20.2~21.4 대 18.1~21.3) | 80% |
| 900/s | 43.4% → 41.8% (범위 42.0~44.3 대 40.0~42.9) | 80% |

- 모두 범위가 겹쳐 효과 없음으로 판정한다.

## 4. 왜 이렇게 나왔나
- **처리 한계 ≈ 상한 ÷ 자리 쥐는 시간.** 끔은 409 요청도 쓰기 트랜잭션을 열고 한 문장 사전 판정(왕복 1번)을 한 뒤 롤백한다. 켬은 캐시가 잡힘이라 하면 읽기 트랜잭션에서 멱등키만 찾고 끝난다. 같은 재응답을 놓치지 않으려는 조회다(dev #648). 그래서 409 경로가 0번이 되지는 않고, 한 건이 자리를 쥐는 시간이 20~30% 준다. 계산상 상한 4의 처리 한계는 정상 3,000/s 부근에서 약 2,600/s(4 ÷ 1.53ms)에서 약 3,700/s(4 ÷ 1.07ms)로 오른다. 3,000/s가 끔에서는 한계를 넘고 켬에서는 안에 든 이유다.
- **잠금 장애에서 효과가 없던 이유.** 잠긴 좌석은 DB 상태가 AVAILABLE이라 캐시도 "선점 가능"으로 본다. 그 좌석을 노린 요청은 캐시를 지나 잠금 대기 50ms까지 자리를 쥔다. 사전 거절이 거르는 79~80%는 이미 잡힌 좌석이고, 그 요청은 원래도 짧게 끝났다. 병목은 잠긴 좌석 쪽이라 변하지 않는다.
- **정합성.** 캐시는 거절에만 쓴다. 캐시가 비었거나 1초가 지나 모르면 지금처럼 DB가 판정한다. 같은 멱등키의 앞선 요청이 있으면 캐시가 잡힘이라 해도 그 결과로 재응답한다.

## 5. 판단
- 켠 채로 둔다(코드 기본값 켬, dev와 같음). 손해가 없고 정상 부하 처리 한계를 올린다.
- 배포에서 다시 볼 것: 좌석 조회가 실제로 회차 캐시를 1초 안에 채우는지. 오픈 순간에는 모든 사용자가 좌석을 보고 고르므로 채워질 것으로 보지만, 자동 배정(ISE-264)처럼 좌석 조회 없이 선점만 오는 경로는 캐시가 비어 효과가 없다(자동 배정은 원래 사전 거절을 하지 않는다).
- 이번 범위에서 하지 않은 것: 캐시가 잡힘이라 할 때의 멱등키 조회를 없애는 것. 같은 키 재시도에 409 대신 201을 주려면 필요해 손대지 않았다.
