# 좌석 선점 구조 개선 세 가지와 측정 결과 (ADR 0062)

상태: local 측정 완료(2026-11-13). 작성: 좌석 선점 담당 최권우 요청으로 Claude Code. 결정은 [ADR 0062](../../decisions/0062-seat-hold-structure-precheck-reorder-limit.md)에 있고, 이 문서는 무엇이 문제였고 무엇을 바꿨고 지표가 왜 그렇게 움직였는지를 처음 보는 사람도 따라올 수 있게 푼다.

## 1. 한 줄 요약

좌석 선점 API의 정합성 구조(중복 판매 방지)는 그대로 두고, 비용 쪽 구조 세 곳을 바꿨다.
1. **질 요청을 먼저 거절했다.** 인기 구역 쏠림 부하에서 처리량이 1,109건/초에서 1,827건/초로 65% 늘고, p95 응답 시간이 198ms에서 124ms로 줄었다.
2. **좌석 잠금을 트랜잭션 끝으로 옮겼다.** local 측정에서는 효과를 확인하지 못했다.
3. **선점 동시 처리 상한을 뒀다.** 서버가 감당할 수 있는 양을 넘는 초당 600건이 들어올 때 타임아웃이 57~76%에서 0%로, 상관없는 좌석 조회의 실패가 53~71%에서 0%로, 사용자가 모르는 채 잡힌 좌석(유령 선점)이 204~289석에서 0석으로 줄었다. 대가로 39~43%의 요청을 "잠시 뒤 다시 시도"(503)로 돌려보낸다.

## 2. 먼저 알아 둘 말

| 말 | 뜻 |
|---|---|
| 선점 | 사용자가 고른 좌석 1~4개를 결제 전까지 그 사용자 것으로 묶어 두는 일. 전부 잡거나 하나도 안 잡는다 |
| 409 `SEAT_ALREADY_HELD` | "이미 다른 사람이 고른 좌석입니다". 사용자는 좌석을 다시 고른다 |
| 503 `SERVICE_UNAVAILABLE` | "잠시 뒤 다시 시도해 주세요". 서버가 일부러 받지 않은 요청이다 |
| 커넥션 풀 | 서버가 DB와 미리 열어 둔 연결 묶음. 이 측정에서는 5개다(config-repo와 같은 값). 요청은 연결을 하나 빌려 DB 일을 하고 돌려준다. 다 빌려 갔으면 줄을 서서 최대 1초 기다린다 |
| 행 잠금 | 같은 좌석을 두 요청이 동시에 바꾸지 못하게 DB가 거는 잠금. 먼저 잡은 요청이 끝날 때(커밋·롤백)까지 다른 요청은 기다린다. 이 서비스는 최대 50ms만 기다리고 409로 끝낸다(ADR 0061) |
| p50·p95 | 응답 시간을 줄 세웠을 때 가운데 값과 95번째 백분위 값. p95 124ms는 "100명 중 95명은 124ms 안에 응답을 받았다"는 뜻이다 |
| 처리량 | 1초에 응답한 요청 수 |
| 유령 선점 | 사용자는 3초 시한이 지나 실패를 받았는데, 서버는 줄에 서 있던 그 요청을 뒤늦게 처리해 좌석을 잡은 것. 사용자는 모르는 좌석이 선점 만료(수 분)까지 묶인다 |
| 닫힌 모델 / 열린 모델 | 부하를 주는 두 방식. 닫힌 모델은 사용자 N명이 응답을 받으면 다음 요청을 보낸다. 열린 모델은 응답과 상관없이 1초에 N건씩 새 요청이 들어온다. 티켓 오픈의 실제 모습은 열린 모델에 가깝다 |

## 3. 기존 방식과 문제점

### 3-1. 선점 한 건이 하던 일

동기형 선점(`SyncSeatHoldService`)은 아래를 한 트랜잭션으로 묶는다. 하나라도 실패하면 전부 되돌린다.

| 순서 | 하는 일 | 다른 요청과 다투나 |
|---|---|---|
| 1 | 같은 멱등키 요청이 있었나 조회 | 아니다 |
| 2 | 회차 조회 | 아니다 |
| 3 | 좌석 조회(상태까지 읽는다) | 아니다 |
| 4 | 멱등키 행 INSERT | 같은 키끼리만 |
| 5 | 사용자 매수 UPDATE | 같은 사용자의 탭끼리만 |
| 6 | **좌석 UPDATE(AVAILABLE → HELD). 여기서 좌석 잠금을 잡아 커밋까지 쥔다** | **같은 좌석을 노린 모든 요청** |
| 7 | 예매 INSERT, 예매 좌석 INSERT(좌석 수만큼), 이력 INSERT | 아니다 |
| 8 | 멱등키 행 UPDATE(HELD) | 아니다 |
| 9 | 커밋 | |

### 3-2. 문제 1: 질 요청이 이길 요청과 같은 길을 끝까지 갔다
- 티켓 오픈 직후에는 인기 좌석이 금방 잡힌다. 그 뒤로 들어오는 선점 대부분은 이미 잡힌 좌석이 섞여 있어 409로 끝난다. 이번 측정에서는 선점 응답의 94~97%가 409였다(ISE-79 k6 측정에서는 77~87%).
- 그런데 3번에서 좌석 상태를 읽고도 검사하지 않았다. 그래서 409로 끝날 요청도 4~6번(쓰기 3번)을 다 하고, 6번에서 "갱신한 좌석 수가 모자라다"를 확인한 뒤 전부 되돌렸다.
- 쓰기와 되돌리기 동안 커넥션 하나를 쥔다. 커넥션은 5개뿐이라, 질 요청이 오래 쥘수록 다른 요청이 줄에서 오래 기다린다.
- 같은 서비스의 접수형 선점(ADR 0057)은 이미 3번 자리에서 검사하고 있었다. 두 경로가 다르게 걸러 동기형에만 헛일이 남아 있었다.
- 여러 좌석 요청은 더 나쁘다. 잡힌 좌석이 하나 섞여 있어도 나머지 빈 좌석은 6번에서 잠그고 바꿨다가 되돌린다. 그 몇 ms 동안 같은 빈 좌석을 노린 다른 사용자는 기다린다(TS-70에서 본 "질 요청의 짧은 잠금").

### 3-3. 문제 2: 좌석을 잠근 채 할 일이 많았다
- 좌석 잠금은 6번에서 잡아 9번 커밋까지 쥔다. 그 사이 7·8번, 곧 "3 + 좌석 수"번의 DB 왕복이 있다. 4석이면 7번이다.
- 예매 좌석 ID를 DB가 매기는 방식(IDENTITY)이라 여러 행을 한 번에 보내는 배치 INSERT가 안 된다.
- 같은 좌석을 노린 요청은 이 시간만큼 기다리고, 50ms를 넘기면 빈 좌석이 될 수도 있었던 좌석에 409를 받는다.

### 3-4. 문제 3: 커넥션을 잡기 전에 들어오는 양을 막는 곳이 없었다
- 선점이 한꺼번에 몰리면 모두 커넥션 줄에 선다. 줄은 길이 제한이 없다.
- 서버가 1초에 처리할 수 있는 양보다 많이 들어오면 줄이 계속 길어진다. 줄에서 1초를 넘기면 서버가 실패(500)로 끝내고, 3초를 넘기면 사용자 쪽에서 포기한다(타임아웃).
- 사용자가 포기한 뒤에도 서버는 줄에 남은 요청을 처리한다. 이때 좌석이 잡히면 유령 선점이 된다.
- 좌석 조회처럼 선점과 상관없는 API도 같은 커넥션 줄에 서므로 함께 실패한다. 이것을 "번짐"이라고 불렀다(ADR 0061, k6 측정 5절).

## 4. 측정 방법

### 4-1. 환경
- 실제 Tomcat, HikariCP(커넥션 풀 5개, 대기 상한 1초), PostgreSQL(Docker)에 HTTP로 부하를 준다. 부하 발생기는 같은 JVM의 가상 스레드다(`SeatHoldLoadTest`, 2026-11-04 판단 기록). Gateway는 거치지 않는다.
- 사용자 쪽 응답 시한은 3초다(Gateway 응답 시한과 같다). 넘으면 TIMEOUT으로 센다.
- 한 PC(local)에서 같은 조건으로 전후를 비교하는 용도다. 절대 수치는 배포 환경과 다르다.

### 4-2. 시나리오

| 이름 | 무엇을 흉내 내나 | 부하 | 겨누는 개선 |
|---|---|---|---|
| L7 여러 좌석 쏠림 | 오픈 직후. 요청의 80%가 인기 구역 100석에서 붙은 좌석 1~4개를 고른다(1석 30%, 2석 50%, 3·4석 각 10%) | 닫힌 모델 200명, 20초, 좌석 1,000석 | 1 |
| L8 잠금 장애 중 번짐 | L7과 같은 요청에, 인기 구역 20석을 측정 내내 잠근 느린 트랜잭션을 더한다 | 닫힌 모델 400명, 20초 | 1, 3 |
| L9 일정 도착률 | L8과 같은 좌석·잠금 장애에서 1초에 들어오는 요청 수를 고정한다 | 열린 모델 초당 300건(처리 가능한 양 아래)·600건(위), 20초 | 3 |
| C2 겹치는 여러 좌석 | 10명이 좌석 4개를 서로 겹치게 동시에 요청 | 50라운드, 500건 | 2 |
| C3 오래 잠긴 좌석 | 좌석 잠금을 2초 쥔 트랜잭션과 같은 좌석을 노린 5명 | 3라운드 | 2 |

- L7·L8에는 좌석 조회 탐침을 같이 돌린다. 다른 회차의 좌석 조회를 20명이 쉬지 않고 반복한다. L9의 탐침은 초당 20건 고정이다(7-3절에서 이유를 설명한다).
- L7·L8은 3회, L9는 조건마다 2~4회, C2·C3는 3회씩 쟀다. 표에는 범위나 평균을 적는다.

### 4-3. 지표
- **처리량, p50·p95:** 선점 요청 전체 기준.
- **201·409·503·TIMEOUT·500 건수:** 사용자가 받은 결과.
- **잡힌 좌석:** 측정이 끝났을 때 HELD인 좌석 수. 같은 시간에 얼마나 팔았나.
- **유령 좌석:** 잡힌 좌석 수에서 사용자가 201로 받은 좌석 수를 뺀 값.
- **좌석 조회 성공률·p95:** 선점 부하가 상관없는 API로 번졌나.
- **정합성:** 중복 판매 좌석, 좌석 상태와 예매 원장의 불일치. 모든 측정에서 0이었다.

## 5. 개선 1: 읽은 좌석 상태로 먼저 거절

### 5-1. 바꾼 것
- 3번(좌석 조회) 바로 뒤에서 모든 좌석이 선점 가능한지 본다(`SeatHoldRules.allHoldable`, 접수형과 같은 함수). 하나라도 잡혀 있거나 추첨석이면 4~8번을 하지 않고 409로 끝낸다.
- 예외가 하나 있다. 같은 멱등키의 첫 요청이 1번과 3번 사이에 커밋되면, 두 번째 요청은 자기 좌석을 "잡힌 좌석"으로 본다. 그래서 409 전에 멱등키를 한 번 더 읽고, 있으면 첫 요청의 결과를 그대로 돌려준다.
- 이 검사는 잠그지 않고 읽은 값이다. 여기서 AVAILABLE이어도 6번 조건부 UPDATE가 최종 판단이라 중복 판매는 생기지 않는다.

### 5-2. 결과

| 시나리오 | 지표 | 기존 | 개선 1 | 변화 |
|---|---|---|---|---|
| L7 | 처리량 | 1,109건/초 | 1,827건/초 | +65% |
| L7 | p50 / p95 | 175 / 198ms | 105 / 124ms | p95 -37% |
| L7 | 201 건수 | 평균 608 | 평균 621 | +2% |
| L7 | 잡힌 좌석(1,000석 중) | 949 | 978~981 | +30석 |
| L7 | 좌석 조회 p95 | 195ms | 123ms | -37% |
| L8 | 처리량 | 374건/초 | 443건/초 | +18% |
| L8 | p95 | 1,218ms | 1,036ms | -15% |
| L8 | 500(커넥션 1초 대기 초과) | 5~11건 | 0~6건 | 줄어듦 |
| C2 | 성공(500건 중) | 78~92 | 78~81 | 차이 없음 |

### 5-3. 지표가 이렇게 움직인 원인
- **L7 처리량 +65%:** L7은 커넥션 5개가 병목이다(줄에 선 요청 최대 195개). 요청의 97%가 409인데, 409 한 건이 커넥션을 쥐는 시간이 "읽기 3번 + 쓰기 3번 + 되돌리기"에서 "읽기 3~4번"으로 줄었다. 같은 5개로 1초에 더 많은 요청을 처리한다.
- **L7 p95 감소:** 닫힌 모델에서는 "응답 시간 ≈ 사용자 수 ÷ 처리량"이다(리틀의 법칙). 200 ÷ 1,827 ≈ 109ms. 응답 시간 대부분이 DB 일이 아니라 커넥션 줄 대기였고, 처리량이 오르니 줄이 짧아졌다.
- **잡힌 좌석 +30석:** 같은 20초에 더 많은 요청을 처리해, 인기 구역이 찬 뒤 남은 낱개 좌석까지 채웠다.
- **좌석 조회 p95 감소:** 좌석 조회도 같은 커넥션 줄에 서므로 줄이 짧아진 만큼 빨라졌다.
- **L8은 +18%로 작다:** L8의 병목은 잠긴 20석이다. 이 좌석은 잠근 트랜잭션이 상태를 바꾸지 않아 AVAILABLE로 보인다. 그래서 개선 1의 검사를 통과하고, 6번에서 50ms를 기다린 뒤 409가 된다. 그동안 커넥션을 쥔다. 개선 1은 커밋된 잡힌 좌석만 거르므로 이 대기는 줄이지 못한다. 이것이 개선 3이 필요한 이유다.
- **C2는 그대로:** C2는 라운드마다 새 좌석으로 10명이 동시에 시작한다. 앞서 커밋된 선점이 없어 개선 1이 거를 요청이 없다. 예상대로다.

### 5-4. 얻은 것과 잃은 것
- 얻은 것: 오픈 피크의 대부분인 409 요청이 싸졌다. 커밋된 잡힌 좌석이 섞인 요청은 쓰기 0번, 잠금 0개로 끝나 다른 사용자를 기다리게 하지 않는다. 동기형과 접수형이 같은 기준으로 거른다.
- 잃은 것: 트랜잭션과 커넥션은 여전히 잡는다(읽기 3번). 커넥션까지 아끼려면 좌석 조회의 1초 상태 캐시로 거르는 사전 거절(P4c 뒤)이 필요하다. 둘은 함께 쓸 수 있다.
- 위험: 읽은 뒤 그 좌석이 풀렸으면 빈 좌석에 409를 준다. 읽은 순간에는 정말 잡혀 있던 좌석이고, 409는 "다시 고르세요"라 피해가 작다.

## 6. 개선 2: 좌석 UPDATE를 트랜잭션 끝으로

### 6-1. 바꾼 것
순서를 아래처럼 바꿨다. 다른 요청과 다투지 않는 쓰기를 먼저 하고, 좌석 잠금은 커밋 직전에 잡는다.

| 기존 | 바꾼 뒤 |
|---|---|
| 매수 UPDATE | 매수 UPDATE |
| **좌석 UPDATE (잠금 시작)** | 예매 INSERT, 이력 INSERT |
| 예매 INSERT, 예매 좌석 INSERT, 이력 INSERT | 멱등키 행 UPDATE |
| 멱등키 행 UPDATE | **좌석 UPDATE (잠금 시작)** |
| 커밋 (잠금 끝) | 예매 좌석 INSERT |
| | 커밋 (잠금 끝) |

잠금을 쥔 구간의 DB 왕복이 "3 + 좌석 수"번에서 "좌석 수"번으로 준다. 예매 좌석 INSERT는 좌석 UPDATE 뒤에 둔다. 앞에 두면 예매 좌석의 부분 유니크 인덱스가 사실상 첫 잠금이 되어 구간이 줄지 않는다.

### 6-2. 결과

| 시나리오 | 지표 | 개선 1까지 | 개선 2까지 |
|---|---|---|---|
| L7 | 처리량 / p95 | 1,827건/초 / 124ms | 1,834건/초 / 123ms |
| L8 | 처리량 / p95 | 443건/초 / 1,036ms | 432건/초 / 1,063ms |
| C2 | 성공(500건 중, 3회씩) | 81, 78, 81 | 86, 85, 86 / 다시 잰 3회 75, 81, 80 |
| C2 | 응답 p50 | 12~13ms | 13~15ms |
| C3 | 최대 대기 | 224~239ms | 188~259ms |

### 6-3. 지표가 이렇게 움직인 원인
- **효과를 확인하지 못했다.** 모든 차이가 측정마다 흔들리는 범위 안이다. C2는 처음 3회에서 80 → 86건으로 좋아 보였지만, 최종 코드로 다시 3회 재니 75~81건이었다. 잠금 대기를 50ms로 바꾼 측정(ADR 0061)에서도 같은 코드가 78~92건으로 흔들렸다.
- **L7·L8에서 안 보이는 이유:** 개선 2는 "같은 빈 좌석을 동시에 노리는 요청"이 많아야 효과가 난다. L7은 잠금을 기다리는 세션이 측정 내내 0개였다(`maxLockWaiters`). 인기 구역이 첫 몇 초에 다 잡히고 나면 남은 요청은 대부분 개선 1에서 걸러져 잠금까지 가지 않는다. 병목은 잠금이 아니라 커넥션 수였다.
- **C2에서도 안 보이는 이유(추정):** local DB는 INSERT 한 번이 1ms보다 훨씬 짧다. 잠금 구간에서 뺀 왕복 3번이 수백 µs라, 잠금 구간 대부분을 차지하는 커밋(디스크 기록)에 비해 작다.
- **C2 p50 +1ms:** 아직 커밋되지 않은 선점과 겹쳐 결국 실패할 요청이 예매·이력 INSERT를 더 한 뒤 되돌린다.

### 6-4. 얻은 것과 잃은 것
- 얻은 것: 잠금 구간이 짧아지는 것은 구조상 사실이다. DB 왕복이 긴 환경(DB가 다른 서버에 있는 배포 환경)이나 같은 빈 좌석을 겨루는 요청이 많은 오픈 첫 몇 초에서는 효과가 날 수 있다.
- 잃은 것: 커밋 전 선점과 겹친 질 요청의 비용이 조금 늘었다(C2 p50 +1ms).
- 판단: 측정한 손해가 작고 되돌리기 쉬워 남긴다. 배포 단계 측정에서 다시 보고, 그때도 효과가 없으면 되돌린다.

## 7. 개선 3: 선점 동시 처리 상한

### 7-1. 바꾼 것
- 선점 API 앞에 "동시에 처리하는 선점은 최대 N개"라는 문을 뒀다(`SeatHoldConcurrencyLimit`, 순서를 지키는 세마포어).
- 자리가 없으면 최대 200ms 기다린다. 그래도 없으면 커넥션을 잡기 전에 503으로 돌려보낸다. 거절 수는 지표 `seathold.concurrency.rejected`로 센다.
- 설정 `seat-hold.max-concurrent`(기본 0, 끔), `seat-hold.max-concurrent-wait`(기본 200ms). 이 측정은 풀 5개에 상한 4개를 썼다. 커넥션 하나는 좌석 조회 같은 다른 API 몫으로 남는다.
- 503은 이미 선점 API 계약에 있는 응답이고, 프론트가 "일시 불안정"으로 안내한다. 계약은 바뀌지 않는다.

### 7-2. 결과 (L9, 인기 구역 20석이 잠긴 상태)

| 도착률 | 지표 | 상한 없음 | 상한 4·대기 200ms | 상한 4·대기 0 |
|---|---|---|---|---|
| 초당 300건 | 실패(503·TIMEOUT·500) | 0% | 0~1.4% | 16~19% |
| 초당 300건 | 선점 p95 | 56~62ms | 93~182ms | 56~57ms |
| 초당 300건 | 좌석 조회 p95 | 21~38ms | 3~5ms | 3~5ms |
| 초당 600건 | TIMEOUT(3초 초과) | 57~76% | 0% | 0% |
| 초당 600건 | 503 | 0% | 39~43% | 46% |
| 초당 600건 | 결과를 받은 선점(201+409) | 2,911~5,206건 | 6,853~7,322건 | 6,431~6,462건 |
| 초당 600건 | 201 건수 | 336~409 | 434~475 | 447~455 |
| 초당 600건 | 선점 p95 | 3,009ms | 253~254ms | 56ms |
| 초당 600건 | 유령 좌석 | 204~289석(잡힌 좌석의 23~33%) | 0석 | 0석 |
| 초당 600건 | 좌석 조회 성공률 / p95 | 29~47% / 3,011ms | 100% / 3~6ms | 100% / 4ms |

### 7-3. 지표가 이렇게 움직인 원인
- **상한이 없을 때 초당 600건이 무너진 이유:** 잠긴 좌석을 노린 요청은 50ms씩 커넥션을 쥔다. 이 상태에서 서버가 처리할 수 있는 양은 초당 약 430~520건이었다(L8 처리량과 L9 600건 때의 응답 속도). 600건이 들어오면 매초 수십~백여 건씩 줄이 길어진다. 몇 초 만에 줄 대기가 3초를 넘어 대부분이 타임아웃됐다. 좌석 조회도 같은 줄에 서서 절반 넘게 실패했다.
- **유령 선점이 생긴 이유:** 사용자는 3초에 포기했지만 요청은 서버 줄에 남아 있었다. 차례가 오자 서버는 그 요청을 처리해 좌석을 잡았다. 잡힌 좌석의 4분의 1 안팎이 아무도 결제하지 않을 좌석이었다. 이 좌석은 선점 만료(수 분) 뒤에야 다른 사람에게 돌아간다.
- **상한을 켜면 줄이 생기지 않는다:** DB까지 가는 선점은 최대 4개다. 나머지는 200ms 안에 자리를 얻거나 503을 받는다. 서버 안의 줄이 200ms를 넘지 않으므로 3초 타임아웃과 유령 선점이 없다. p95 253ms는 대부분 "자리를 200ms 기다린 뒤 거절된 요청"이다.
- **결과를 받은 선점이 오히려 늘었다:** 상한이 없을 때는 DB가 처리한 요청 상당수가 이미 사용자가 포기한 요청이었다. 헛일이다. 상한을 켜면 DB가 처리하는 모든 요청이 사용자에게 응답이 닿는 요청이다. 그래서 201도 336~409건에서 434~475건으로 늘었다.
- **좌석 조회가 살아난 이유:** 커넥션 5개 중 선점은 최대 4개만 쥔다. 좌석 조회는 줄을 거의 서지 않는다(커넥션 대기 0~1개).
- **대기 0과 200ms의 차이:** 초당 300건은 평균으로는 감당할 수 있는 양이지만, 도착이 순간순간 몰린다. 대기 0은 그 순간 몰림까지 503으로 잘라 16~19%를 거절했다. 200ms 대기는 자리가 곧 나는 몰림을 받아 줘 거절이 0~1.4%다. 대가로 기다린 요청만큼 p95가 늘었다.

### 7-4. 얻은 것과 잃은 것
- 얻은 것: 감당할 수 있는 양을 넘어도 서버가 무너지지 않는다. 모든 요청이 0.3초 안에 결과(성공·이미 잡힘·잠시 뒤 다시)를 받는다. 유령 선점이 없다. 선점 폭주가 좌석 조회로 번지지 않는다.
- 잃은 것
  - 초당 600건에서 39~43%가 503을 받는다. 그 사용자는 다시 눌러야 한다. 다만 상한이 없을 때는 같은 사용자들이 3초를 기다린 뒤 타임아웃을 받았고, 그중 일부는 모르는 좌석까지 잡혔다.
  - 감당할 수 있는 초당 300건에서도 p95가 56~62ms에서 93~182ms로 늘고 0~1.4%가 503을 받는다. 상한 4가 커넥션 5개보다 좁고, 200ms를 기다린 요청이 있기 때문이다.
  - 값(4개, 200ms)은 local 풀 5개에서 정했다. CPU·DB가 다른 배포 환경에서는 다시 재야 한다. 그래서 코드 기본값은 끔이다.

### 7-5. 측정을 바로잡은 과정 (TS-74)
처음에는 L7·L8(닫힌 모델)로 쟀는데 결과를 믿을 수 없었다.
- 503은 1ms 안에 끝나므로, 쉬지 않는 가상 사용자 200명이 1초에 1만 건 넘게 다시 보냈다. 같은 JVM의 부하 발생기가 CPU를 먹어 서버 처리량까지 떨어졌다.
- 503 뒤 1초 쉬게 하니 이번에는 보내는 요청 자체가 줄어 비교할 수 없었다.
- 좌석 조회 탐침도 쉬지 않는 20명이라, 선점이 비운 커넥션을 탐침이 차지해 선점이 더 거절됐다.

그래서 1초에 들어오는 요청 수를 고정하는 L9를 만들고, 탐침도 초당 20건으로 고정했다. 빨리 거절하는 장치는 열린 모델로 재야 한다.

## 9. 측정하며 발견한 것
- **커넥션 대기 초과가 500으로 나간다.** 커넥션을 1초 안에 못 받은 요청(`CannotCreateTransactionException`)을 공통 예외 처리기(`CommonExceptionHandler`)가 500으로 응답한다. 선점 API 계약은 이 경우를 503 `SERVICE_UNAVAILABLE`로 정해 두었다. 공통 모듈이라 고치지 않았다. 개선 3을 켜면 선점에서는 거의 생기지 않지만, 다른 API에는 남는다.
- **유령 선점의 크기를 처음 쟀다.** 과부하에서 잡힌 좌석의 23~33%였다. 학습 노트에서 4번으로 꼽은 "요청 기한 전달"은 Gateway를 바꿔야 하지만, 개선 3만으로도 이번 조건에서는 0이 됐다.

```bash

SEATHOLD_LOAD=true SEATHOLD_LOAD_POOL=5 SEATHOLD_LOAD_CONNECTION_TIMEOUT=1000 SEATHOLD_LOAD_REPEAT=3 \
  ./gradlew :reservation-service:cleanTest :reservation-service:test \
  --tests '*SeatHoldLoadTest.L7*' --tests '*SeatHoldLoadTest.L8*' -i

# L9 (열린 모델). 상한을 켜려면 SEATHOLD_LOAD_MAX_CONCURRENT=4, 대기를 바꾸려면 SEATHOLD_MAXCONCURRENTWAIT=0ms
SEATHOLD_LOAD=true SEATHOLD_LOAD_POOL=5 SEATHOLD_LOAD_CONNECTION_TIMEOUT=1000 SEATHOLD_LOAD_REPEAT=2 \
  SEATHOLD_LOAD_PROBE_RATE=20 SEATHOLD_LOAD_RATES=300,600 \
  ./gradlew :reservation-service:cleanTest :reservation-service:test --tests '*SeatHoldLoadTest.L9*' -i

# C2·C3 등 동시성 시나리오
SEATHOLD_CONCURRENCY=true ./gradlew :reservation-service:cleanTest :reservation-service:test \

```

결과는 표준 출력의 `[SEATHOLD-LOAD]`, `[SEATHOLD-CONCURRENCY]` 줄에 나온다.
