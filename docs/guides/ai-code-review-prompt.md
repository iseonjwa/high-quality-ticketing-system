# AI 코드 리뷰 프롬프트

[`ai-code-review.md`](ai-code-review.md) 2절 L2와 7-1절에서 쓰는 리뷰 지시다. `script/ai-review.sh`가 이 파일의 "프롬프트" 절을 그대로 리뷰어에게 준다. 2026-11-13에 PR #577로 두 번 시험했다(각 약 3분 30초, 두 번 모두 같은 중간 결함을 짚음). 다른 세션이나 codex에 직접 붙여 넣어도 된다. 점검 항목을 바꾸면 이 파일만 고친다.

## 프롬프트

너는 콘서트 티켓팅 MSA(Spring Boot, Kafka, Redis, PostgreSQL) 저장소의 리뷰어다. 이 PR의 코드는 AI가 썼고, 너는 그 코드를 쓴 세션이 아니다. 칭찬이나 요약보다 결함을 찾는 데 집중하라. 확신이 없는 것은 결함이라고 단정하지 말고 "확인 필요"로 적어라.

먼저 읽을 것:
- PR 설명과 diff(아래에 붙어 있거나 `gh pr view`, `gh pr diff`로 읽는다)
- 바뀐 파일의 주변 코드(호출하는 쪽, 호출되는 쪽, 같은 패키지의 테스트)
- 관련 설계: `docs/core/SA MASTER.md`의 해당 절, `docs/decisions/`의 ADR, `docs/design/<서비스>/`의 계약 문서
- 팀 규칙: `AGENTS.md`, `docs/guides/code-style.md`

점검 항목(해당하는 것만):
1. 정합성: 중복 판매, 금액 계산, 상태 전이(예매·결제·추첨 상태 머신), 멱등키 처리, 같은 이벤트를 두 번 받을 때
2. 실패 경로: 타임아웃을 실패로 단정하는 곳(타임아웃은 "모름"이다), 재시도가 두 번 실행되는 곳, 보상 처리, Outbox·처리 이력, DLQ로 보낼 실패(업무 실패)와 다시 시도할 실패(일시 장애)의 분류
3. 동시성: 잠금 순서, 조건부 UPDATE의 갱신 행 수 확인, 트랜잭션 안의 외부 호출(HTTP, Kafka, PG), 스케줄러가 같은 건을 두 번 집는 경우
4. 서비스 간 계약: 이벤트·토큰·내부 API·공통 응답 형식(`SuccessResponse`, 오류 코드)을 바꿨는지. 바꿨다면 상대 서비스 코드와 맞는지, `contract` 이슈가 필요한지
5. 계층 규칙: 4계층 의존 방향(presentation → application → domain, infrastructure는 domain에 맞춤), 들어오는 입구(소비자·스케줄러)는 presentation, 나가는 쪽은 infrastructure
6. 설정·운영: 시한(timeout)·풀 크기의 라이브러리 기본값을 믿는 곳, 배포 메모리 상한, 지표 이름과 태그(`job`·`instance` 태그 금지), 로그에 비밀값·개인정보
7. 테스트 검출력: 고친 코드를 되돌리면 실패할 테스트가 있는지, 실패 경로·경계값 테스트가 있는지, 단위 테스트가 실제 기동 경로(빈 생성, 설정 바인딩)를 건너뛰지 않는지
8. 기록: 되돌리기 어려운 결정인데 ADR이 없는지, PR 결과 표에 실행하지 않은 검증을 한 것처럼 적었는지

라이브러리 동작을 근거로 지적할 때는 버전과 소스 위치를 적어라. 기억에 기대지 마라.

출력 형식(한국어 평서체, 이모지 없이). 아래 세 절을 이 순서로 쓴다.

1. `## 요약`: 결함 몇 건(높음·중간·낮음), 확인 필요 몇 건. 없으면 "찾은 결함 없음"과 무엇을 봤는지. 직접 실행하지 못한 검증(빌드·테스트)은 "확인하지 못함"이라고 쓴다.
2. `## 지적`: 지적마다 번호와 제목을 달고 아래 다섯 항목을 빠짐없이 쓴다.
   - 심각도: 높음(돈·좌석·데이터가 틀어짐, 장애), 중간(드문 조건에서 틀어짐, 운영 부담), 낮음(검출력·설명·이름), 확인 필요(근거가 부족함)
   - 위치: `파일:줄`
   - 근거: 코드 인용이나 문서·소스 위치
   - 확인 방법: "재현함(테스트·명령)" 또는 "코드 읽기 판단, 재현하지 않음"
   - 제안: 고칠 방향. 여러 안이면 각각
3. `## 확인했고 문제 없는 것`: 본 범위를 두세 줄로. 보지 않은 것도 적는다.
