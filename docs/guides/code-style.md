# 코드 작성 가이드

코드를 작성·수정·리뷰할 때 적용한다. 다음 사람이 업무 흐름과 선택 이유를 이해할 수 있게 쓴다.
SA·ADR·기존 공통 계약을 따르며, 주석과 문서의 문체는 [문서 작성 가이드](writing.md)를 따른다. 검증 기준은 [품질 기준](../agents/quality-gates.md)에 있다.

## 1. 줄 수보다 읽는 흐름을 우선한다

- 중첩 삼항식이나 부수 효과가 섞인 긴 Stream 체인은 조건문·반복문·중간 변수로 풀어 쓴다.
- Stream·`var` 같은 문법은 문맥에서 이해하기 쉬운지를 기준으로 선택한다. 일괄 금지하거나 사용 자체를 목표로 삼지 않는다.
- 코드를 줄이면서 필요한 검증·실패 처리·자원 정리를 생략하지 않는다.

## 2. 메인 메서드에서 업무 흐름이 보이게 한다

- 예외 조건을 먼저 처리해 정상 흐름의 중첩을 줄인다.
- 메서드는 의미 있는 책임으로 나눈다. 메서드 이름을 따라가면 검증·처리·응답의 흐름을 이해할 수 있게 한다.
- 줄 수를 맞추려고 의미 없는 전달 메서드를 늘리지 않는다. 메서드 최대 줄 수를 일률적인 기준으로 삼지 않는다.
- 메서드를 추출하거나 순서를 바꿀 때 트랜잭션·상태 변경·외부 호출의 실행 순서를 보존한다.

## 3. 이름에 의미와 단위를 담는다

- `data`, `temp`, `process`처럼 용도가 넓은 이름보다 업무와 역할을 드러내는 이름을 쓴다.
- 시간·횟수·상태는 `expiresAt`, `timeoutMillis`, `maxLoginFailures`처럼 의미와 필요한 단위를 구분한다.
- 정책 값과 반복되는 계약 값은 설정·상수로 의미를 드러낸다. 단순한 `0`, `1`까지 모두 상수로 만들지는 않는다.
- 이름이나 코드 구조를 개선하면 설명이 필요 없어지는 경우에는 그 개선을 먼저 한다.

## 4. 합의된 계층과 기존 공통 기능을 먼저 사용한다

- 합의된 4계층과 필요한 도메인·인프라 경계를 유지한다.
- 응답·예외·사용자 컨텍스트·역할 인가 등은 [기존 공통 계약](common-modules.md)을 먼저 확인한다. 같은 정책을 별도 구현으로 늘리지 않는다.
- 예상 재사용만을 이유로 범용 인터페이스·유틸리티·설정 계층을 추가하지 않는다. 현재 책임과 변경 경계가 필요한 추상화인지 확인한다.
- 코드 모양이 비슷해도 서로 다른 도메인 규칙을 억지로 공통화하지 않는다.

## 5. `Note:`는 필요한 지점에만 남긴다

코드만으로 알기 어려운 이유·주의점·학습 포인트가 있을 때 선택적으로 쓴다. 설명할 내용이 없는 곳에는 붙이지 않는다.

### 붙일 만한 지점

- 선택 이유: 처리 순서나 구현 방식을 바꾸면 결과가 달라지는 이유.
- 주의점: 트랜잭션·동시성·멱등성·인증 경계처럼 놓치면 문제가 생기는 전제.
- 학습 포인트: 그 구현을 이해하는 데 필요한 혼동하기 쉬운 프레임워크 동작이나 기술적 제약.

현재 인증 정책을 설명하는 예시는 다음과 같다.

```java
// Note: Redis 조회 실패 시 로그아웃 여부를 확인할 수 없다.
// 로그아웃된 토큰의 통과를 막기 위해 인증을 중단하고 503을 반환한다.
```

```java
// Note: 로그인 실패 횟수를 늘린 뒤 예외를 던진다.
// 실패 횟수 갱신까지 롤백되지 않도록 트랜잭션 경계를 유지한다.
```

### 남발하지 않는 기준

- 모든 클래스·메서드·필드에 의무적으로 붙이지 않는다. `Note:`가 없어도 필요한 맥락을 이해할 수 있으면 충분하다.
- getter·setter·단순 조회·대입이나 코드 내용을 그대로 읽어 주는 설명에는 붙이지 않는다. 일반적인 Java 문법을 줄마다 설명하지 않는다.
- 같은 맥락의 설명은 핵심 적용 지점 한 곳에 모은다. 호출하는 메서드나 소비하는 클래스마다 복사하지 않는다.
- 필요한 맥락을 짧게 설명하고, 긴 원리 설명은 학습 노트·ADR로 연결한다. 주석 수나 비율을 채우는 목표를 두지 않는다.
- 기존 주석은 설명이 유효하면 유지한다. 접두어를 통일하려고 모든 주석을 `Note:`로 바꾸지 않는다.
- 동작이 바뀌면 해당 주석도 고친다. 오래되거나 자명해진 설명은 정리한다.

클래스·공개 메서드의 사용 계약은 필요할 때 Javadoc으로 쓴다. `Note:`는 구현 지점의 맥락을 설명한다.
미완료 작업은 `TODO:`로 구분하고 실제 이슈·문서나 처리 조건을 남긴다. `Note:`만으로 미구현 작업이 완료된 것처럼 보이게 하지 않는다.

## 6. 실패의 의미를 보존한다

- 예외를 무조건 잡아 `null`, 빈 목록, 정상 결과로 바꾸지 않는다. 복구나 기본값이 필요한 경우에는 해당 계약과 이유가 있어야 한다.
- 예상한 업무 거절과 의존 서비스 장애는 기존 에러 계약에 맞춰 구분한다.
- 장애 분석에 필요한 원인과 추적 정보는 유지한다. 비밀번호·토큰·개인키는 로그에 남기지 않는다.
- 메서드를 짧게 만들기 위해 예외·반환값의 의미를 바꾸지 않는다.

## 7. 변경한 코드와 설명을 함께 맞춘다

- 동작이 바뀌면 관련 주석·테스트·계약 문서도 확인하고 갱신한다.
- 버그 수정에 관련 없는 전체 포맷 변경·이름 변경을 섞지 않는다. 수정하는 주변의 기존 스타일을 따른다.
- 포맷터 같은 새 도구 도입은 별도 선택으로 다룬다.
- 리뷰에서는 이름과 흐름, 필요한 추상화, 실패 처리, 주석의 정확성과 과다 여부를 함께 확인한다.
- API·인증·업무 동작 검증은 프로젝트의 Java·JUnit 테스트로 관리한다. 환경·프로세스 준비 도구에 검증 로직을 중복 구현하지 않는다. 실행 범위는 [테스트 가이드](testing.md)를 따른다.

## 8. Lombok

Lombok은 모든 모듈에서 제한 없이 쓸 수 있다(2026-10-27 통합 회의 D13). 의존성은 루트 `build.gradle`에 있다. 기존 코드는 record와 명시적 생성자를 쓰므로 Lombok으로 일부러 바꾸지 않는다.
