# 서비스 간 접점(contract) 이슈 가이드

서비스 간 접점을 바꾸는 쪽과 받는 쪽이 따로 일하면, 상대가 할 일이 설계 문서에만 있을 때 놓친다. 접점 변경은 Linear 이슈로 올려 받는 쪽 담당에게 알리고, 받는 쪽은 작업 전에 자신에게 온 이슈를 확인한다. 2026-10-30에 결제 담당이 처음 쓴 방식(ISE-73~77)을 공통 규칙으로 정했다.

## 1. 무엇이 접점인가

다른 서비스가 읽거나 써야 하는 것이다. 아래에 해당하면 `contract` 이슈를 올린다.

| 종류 | 예 |
|---|---|
| 이벤트 | 토픽, 페이로드 필드 추가·삭제·의미 변경, 소비자가 해야 하는 처리 규칙, DLQ 처리 |
| 토큰 | 입장 토큰·결제 토큰의 claim 이름과 키 해석, 만료 규칙 |
| 내부 API | 서비스끼리 호출하는 API의 경로·요청·응답, 대사용 조회 API |
| 공유 설정 | `compose.yml`, `config-repo`, 프로필처럼 여러 서비스가 함께 쓰는 설정 |
| 정책 확인 | 한 서비스의 설계가 다른 서비스의 정책에 영향을 줘서 답이 필요한 질문 |

한 서비스 안에서 끝나는 변경은 접점이 아니다.

## 2. 문서와 이슈의 역할

| 곳 | 역할 |
|---|---|
| 저장소 문서(`docs/design/<서비스>/contracts.md`, `docs/decisions/`, SA 변경 요청) | 정본. 무엇을 왜 정했는지, 필드 정의, 트레이드오프 |
| Linear `contract` 이슈 | 알림과 추적. 누가, 무엇을, 언제까지 해야 하는지. 이견과 일정 답변 |

결정의 이유를 이슈에만 쓰지 않는다. 이슈 본문은 짧게 쓰고 정본 문서를 링크한다.

## 3. 올리는 쪽 (접점을 바꾸는 사람)

### 언제
접점을 바꾸기로 정한 직후, 코드를 쓰기 전에 올린다. 상대가 자기 일정에 반영할 시간이 필요하다. 이미 구현한 뒤라도 상대가 아직 모르면 바로 올린다.

### 형식

| 항목 | 규칙 |
|---|---|
| 제목 | `contract(보내는 쪽→받는 쪽): 요약`. 한쪽 방향이 아니면 `contract(영역): 요약`. 한국어 평서형으로 쓴다. 예: `contract(payment→reservation): payment.result 소비 DLQ 처리기` |
| 라벨 | `contract`와 관련 영역 라벨(`payment`, `queue` 등). 새 영역 라벨이 필요하면 만든다 |
| 담당 | **상대 서비스 담당자**. 알림은 담당이 되거나 멘션될 때 간다. 담당이 정해지지 않았으면 팀에 물어 정하고, 담당 없이 두지 않는다 |
| 멘션 | 본문 첫 줄에 상대 담당자를 `@표시이름`으로 멘션하고 부탁할 일을 한 문장으로 쓴다 |
| 우선순위 | 상대가 작업을 시작하기 전에 답이 필요하거나, 내 구현이 막히면 High. 그 밖은 Medium |
| 연결 | 내 쪽 관련 이슈를 `related`로 잇는다 |

### 본문 틀
```markdown
@상대표시이름 한 문장: 무엇을 확인·구현해 달라는 것인지, 언제까지 필요한지.

## 배경
* 근거: 문서·ADR·SA 변경 요청 링크
* 왜 필요한가 한두 문장

## <상대 서비스>가 할 일
1. 번호를 붙여 구체적으로 쓴다(필드 이름, 처리 규칙, 경로).

## 완료 기준
- [ ] 담당이 내용을 확인하고 이견이 있으면 이 이슈에 남긴다.
- [ ] 구현 일정을 이 이슈에 적는다.
- [ ] 테스트 기준(무엇이 통과해야 하는가)
```

### 올린 뒤
- 접점이 바뀌면 문서와 이슈 본문을 함께 고치고 댓글로 알린다.
- 접점을 취소하면 이슈를 `Canceled`로 닫고 이유를 댓글로 남긴다.
- 에이전트는 담당 지정과 멘션으로 다른 사람에게 알림이 가므로, 이슈를 만들기 전에 목록을 사용자에게 보여주고 확인받는다.

## 4. 받는 쪽 (나에게 contract가 온 사람)

### 작업 전에 확인한다
작업(이슈 착수, 새 기능, 연동 변경)을 시작하기 전에 다음을 본다.

1. 나에게 배정된 열린 `contract` 이슈. Linear에서 라벨 `contract`, 담당 `나`, 상태가 Done·Canceled가 아닌 것을 필터한다. Linear MCP를 쓰는 에이전트는 `list_issues`에 `label: contract`, `assignee: me`를 주고 완료·취소를 제외한다.
2. 오늘 하려는 작업 이슈에 `related`로 연결된 `contract` 이슈.
3. 이슈가 가리키는 정본 문서(ADR, SA 변경 요청, `contracts.md`).

에이전트는 사용자에게 작업을 시작하자는 요청을 받으면 위 1·2를 먼저 확인하고, 관련 있는 항목을 작업 계획에 반영한다. 관련이 없으면 한 줄로 "해당 contract 없음"이라고만 알린다.

### 처리한다
| 상황 | 할 일 |
|---|---|
| 내용에 동의 | 구현 일정을 이슈에 댓글로 남기고, 작업 이슈와 `related`로 잇는다. 구현 PR 본문에 contract 이슈를 링크한다 |
| 이견이 있음 | 구현하지 않고 이슈에 이견을 댓글로 남겨 올린 사람과 합의한다. 합의되면 정본 문서를 고친다. 팀 합의(SA, ADR)를 개인 판단으로 덮어쓰지 않는다 |
| 정보가 부족 | 이슈에 질문을 남긴다. 추측해서 구현하지 않는다 |
| 구현 완료 | PR 링크와 확인 결과를 댓글로 남기고 이슈를 `Done`으로 한다 |

## 5. PR에서 확인

PR 템플릿 체크 칸에 두 줄이 있다. 해당 없으면 "해당 없음"이라고 적는다.
- 서비스 간 접점을 바꿨다면 `contract` 이슈를 올렸다.
- 작업 전에 나에게 온 `contract` 이슈를 확인했다.
