# 배포 서버 접속과 부하 측정 안내 (팀원용)

배포 서버와 Jenkins 서버에 접속하는 방법, 서버에서 지킬 규칙, 부하 측정(k6) 계획을 팀원에게 알리는 문서다. 2026-11-05 기준이다. 서버 설계와 절차의 정본은 [`design/infra/deployment.md`](../design/infra/deployment.md), [`design/infra/load-test.md`](../design/infra/load-test.md)이고, 이 문서는 팀원이 쓰는 부분만 모은다. 담당은 안준현이다.

## 2. 접속 준비: 공개 키와 개인 키

`ssh-keygen -t ed25519`를 실행하면 `~/.ssh/`에 파일이 **두 개** 생긴다.

| 파일 | 무엇 | 어디에 |
|---|---|---|
| `id_ed25519.pub` | **공개 키**. `ssh-ed25519 AAAA... 이름` 한 줄. 이미 보내 준 것 | 서버에 등록됨. 남에게 줘도 된다 |
| `id_ed25519` (확장자 없음) | **개인 키**. 여러 줄 파일 | 내 컴퓨터에만 둔다. 누구에게도 보내지 않는다 |

- 공개 키는 서버 문에 다는 자물쇠, 개인 키는 그 자물쇠를 여는 열쇠다.
- 2026-11-05에 강민·권우·효승·영은의 공개 키를 배포 서버와 Jenkins 서버에 등록했다.
- 접속 명령의 `-i`에는 **개인 키 파일 경로**를 넣는다. 공개 키 문자열이 아니다.
  - 기본 위치(`~/.ssh/id_ed25519`)에 만들었으면 `-i`를 빼도 된다.
  - 다른 이름으로 만들었으면 그 경로를 넣는다.
  - 내 개인 키가 어디 있는지 모르면 `ls ~/.ssh/`(Windows는 `dir $HOME\.ssh`)로 `.pub`과 이름이 같고 확장자가 없는 파일을 찾는다.
- 서버는 등록된 **IP에서 오는 SSH만** 받는다(AWS 보안 그룹).
  - 집·카페·교육장마다 공인 IP가 다르다. 접속이 갑자기 안 되면 대개 IP가 바뀐 것이다.
  - `curl https://checkip.amazonaws.com`으로 지금 IP를 확인해 담당에게 보내 준다.

## 3. 접속 명령

```bash
# 배포 서버
ssh -i ~/.ssh/id_ed25519 ubuntu@52.63.10.174

# 매번 치기 번거로우면 ~/.ssh/config에 적고 `ssh iseonjwa`로 접속한다
Host iseonjwa
  HostName 52.63.10.174
  User ubuntu
  IdentityFile ~/.ssh/id_ed25519
```

- Windows는 PowerShell의 `ssh`(Windows 10 이상 기본)나 Git Bash를 쓴다. 키 경로는 `C:\Users\<이름>\.ssh\id_ed25519`다.
- 처음 접속할 때 서버 지문을 물으면 `yes`를 입력한다.

**Grafana는 바로 연다.** `http://52.63.10.174:3000`을 브라우저에 입력한다. 등록된 IP에서만 열리고 로그인 없이 보기만 된다. 화면에 `?demo=on`을 붙인 시연 모드의 traceId 링크도 이 주소로 온다.

**나머지 관리 화면은 SSH 터널로 연다.** 포트가 서버 밖에 열려 있지 않다. 터널 명령을 켜 둔 채 브라우저에서 `localhost`로 연다.

```bash
# 배포 서버 관리 화면
ssh -N -L 8085:127.0.0.1:8085 -L 9090:127.0.0.1:9090 \
  -L 9093:127.0.0.1:9093 -L 9411:127.0.0.1:9411 iseonjwa
```

| 화면 | 주소 |
|---|---|
| Grafana(터널 없이) | `http://52.63.10.174:3000` |
| Kafka-UI(읽기 전용) | `http://localhost:8085` |
| Prometheus | `http://localhost:9090` |
| Alertmanager | `http://localhost:9093` |
| Zipkin | `http://localhost:9411` |

```bash
# Jenkins 화면
ssh -i ~/.ssh/id_ed25519 -N -L 8081:127.0.0.1:8080 ubuntu@3.107.168.36
```

- 브라우저에서 `http://localhost:8081`로 연다.
- Jenkins 로그인 계정은 `admin` 하나다. 비밀번호는 담당에게 개인 메시지로 받는다.

## 4. 서버에서 지킬 것

`ubuntu` 계정은 `sudo`와 `docker` 권한이 있어 무엇이든 할 수 있다. 그래서 다음은 하지 않는다.

| 하지 않는다 | 이유 |
|---|---|
| `docker compose down -v`, `docker volume rm` | DB·Kafka 데이터가 지워진다 |
| 서버에서 직접 `deploy.sh`, `git checkout`, `docker compose up` | 배포는 main 머지 → Jenkins로만 한다. 손으로 바꾸면 기록(`.deploy/current`)과 실제 상태가 어긋난다. 예외는 부하 측정 날 그날 측정자가 쓰는 `script/loadtest/measure-mode.sh on/off`뿐이다(5-5절, ADR 0046 변경 2026-11-09) |
| `.env` 열기·복사·공유 | 운영 비밀값이 있다 |
| `~/.ssh/authorized_keys` 수정 | 다른 사람과 Jenkins의 접속이 끊길 수 있다 |
| 배포 서버에서 k6 실행 | 부하 도구가 서버 자원을 나눠 써서 측정이 왜곡된다(5절) |

- 해도 되는 것은 읽기 위주다.
  - `docker ps`
  - `docker logs -f iseonjwa-reservation-service-1`
  - `docker stats`
  - Grafana 보기, 터널로 Zipkin 보기
- 컨테이너 재시작이 필요하면 팀 채널에 먼저 알린다.

## 5. 부하 측정(k6) 계획

### 5-1. 누가 무엇을 재나
| 측정 | 담당 | 어디서 | 상태 |
|---|---|---|---|
| 좌석 선점 K1(초당 100명 입장 → 좌석 조회 → 선점)과 단계별 개선 | 최권우(ISE-79) | 지금은 로컬 스택(배포 메모리·G1 덮어쓰기) | 진행 중. G1으로 한계가 초당 5명 → 10명. 다음은 좌석 조회 경량화 P4(반효승, ISE-189) |
| 공통 측정 기반(발생기, 토큰 준비, 회차 초기화, 결과 기록)과 오픈 피크 전체 시나리오 | 안준현(ISE-181) | 배포 서버 + 발생기 EC2 | 준비 전 |
| 동기형 선점 기준선 | 권영은(ISE-25) | 공통 기반의 "선점 경합" 시나리오 | 공통 기반 뒤 |

### 5-2. 배포 서버 측정 방식
- **k6는 배포 서버에서 돌리지 않는다.**
  - 배포 서버와 같은 VPC·같은 가용 영역의 **팀 공용 발생기 EC2**(`iseonjwa-loadgen`, 2026-11-09 생성)에서 돌린다(ADR 0046). 측정 날 사이에는 중지하고 팀 마지막 측정 뒤 종료한다.
  - 쓰는 규칙(한 번에 한 명, 팀 채널 알림, 각자 폴더, 시작·끝 체크리스트)은 [`loadgen.md`](loadgen.md)에 있다.
  - AWS 콘솔은 계정 주인만 쓰므로 발생기 켜기·중지·종료는 안준현이 한다. 만드는 절차는 [`load-test.md`](../design/infra/load-test.md) 2-1절이다.
- **발생기에서 부르는 곳**
  - Gateway 사설 주소 `http://172.31.4.93:8080`을 부른다. 프론트 nginx는 거치지 않는다.
  - 배포 서버 보안 그룹은 측정 중에만 발생기 보안 그룹에서 오는 8080(Gateway)과 9090(결과를 Prometheus remote write로 받음)을 연다.
- **k6 실행 방식**
  - 설치하지 않고 Docker 이미지 `grafana/k6:1.0.0`으로 한 번 실행한다. K1 스크립트(`reservation-service/k6/run.sh`)와 같은 방식이다.
  - 발생기에서 `BASE_URL=http://172.31.4.93:8080`만 바꿔 쓴다. 공인 IP `52.63.10.174`로 보내면 전송 요금이 붙고 보안 그룹에도 막힌다([`loadgen.md`](loadgen.md) 2절).
- **노트북에서 배포 서버로 큰 부하를 쏘지 않는다.**
  - 한국–시드니 왕복이 약 0.27초라 결과에 네트워크가 섞인다.
  - 스크립트 확인이나 시연 수준의 작은 부하는 괜찮다.
- **측정하는 동안에는 main 릴리스를 하지 않는다.** Jenkins가 측정 중에 배포를 시작한다.

### 5-4. 서버 측정 전에 남은 것
- **토큰 준비**: 정함(2026-11-08). 측정 동안만 측정 전용 서명 키로 바꿔 띄우고(`measure-mode.sh`), k6가 그 키로 직접 서명한다. 운영 키는 발생기에 두지 않는다(ADR 0046 변경).
- **`loadtest` 프로필**: 추적 샘플링 0.01은 측정 모드 덮어쓰기가 맡는다. 배포 Mock PG는 이미 `loadtest` 프로필이다. 입장 속도·토큰 유효 시간 덮어쓰기는 필요할 때 측정 전에 정한다.
- **결과 보기**: 정함(2026-11-08). k6 결과를 Prometheus remote write로 보내 Grafana에서 본다. 결과 파일(요약 JSON, CSV)도 남긴다.
- **측정 환경 기록표**: [`load-test.md`](../design/infra/load-test.md) 7절 양식을 측정마다 채운다.

### 5-5. 측정 날 순서

배포 서버를 재는 날의 순서다. 서버·발생기 켜기와 중지(AWS 콘솔)는 AWS 담당이, 측정 모드 켜기·끄기와 키 옮기기(3, 4, 6번)는 그날 측정자가 한다(ADR 0046 변경 2026-11-09). 자세한 설계와 명령은 [`load-test.md`](../design/infra/load-test.md) 2-1, 5절과 [`loadtest/k6/README.md`](../../loadtest/k6/README.md) "배포 서버 측정"에 있다.

1. **서버 켜기**: 배포 서버와 Jenkins 서버를 켜고 스모크가 통과하는지 본다.
2. **발생기 켜기**: 팀 공용 발생기가 중지돼 있으면 켜고 새 퍼블릭 IP를 팀 채널에 올린다. 측정자는 시작 알림을 올린다([`loadgen.md`](loadgen.md) 4절).
3. **측정 모드 켜기**(측정자): 먼저 `script/loadtest/measure-mode.sh status`로 다른 사람이 켜 두지 않았는지 본다. 그다음 `script/loadtest/measure-mode.sh on`(Q2는 `loadtest/k6/compose.queue-hold.yml`을 인자로). 이때부터 기존 로그인이 끊긴다. 시작 알림에 **main 머지 금지**를 넣고, Jenkins 잡을 끌 수 있으면 끈다(배포가 돌면 측정 모드가 풀린다).
4. **키 옮기기**: 서버의 `~/iseonjwa/.env.measure`를 발생기 저장소 루트의 `.env`로 옮긴다. 측정 전용 키 두 개뿐이고 운영 키와 관리자 비밀번호는 옮기지 않는다.
5. **측정**: 서버에서 회차를 만들고(`seed-demo.sh open`) 발생기에서 `SCHEDULE_ID`와 `PROM_RW_URL`을 주고 `run.sh`를 돌린다. Mock PG 지연 300ms는 서버에서 건다.
6. **측정 모드 끄기**(측정자): `script/loadtest/measure-mode.sh off`. 운영 키로 돌아오고 스모크가 돈다. `status`로 꺼졌는지 확인하고, 껐던 Jenkins 잡을 켠다. 끝 알림에 "측정 모드 끔"을 적는다.
7. **발생기 정리**: 측정자는 결과 파일을 내려받고 자기 폴더의 `.env`를 지운 뒤 끝 알림을 올린다. 그날 측정이 모두 끝났으면 발생기를 중지하고, 팀 마지막 측정 뒤에는 종료하며 8080·9090 보안 그룹 규칙도 지운다([`loadgen.md`](loadgen.md) 5절).
