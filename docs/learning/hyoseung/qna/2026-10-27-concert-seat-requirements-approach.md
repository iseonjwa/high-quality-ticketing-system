# 공연·좌석 영역을 실제 프로젝트처럼 페르소나·요청 흐름·트래픽부터 잡고 DB를 보는 방법

## 질문
담당한 공연·좌석 조회 → 예매 흐름을 실제 프로젝트처럼 만들고 싶다. 페르소나를 정하고, 요청 흐름과 요청량을 바탕으로 데이터베이스까지 신경 쓰려면 무엇을 어떤 순서로 보면 되는가.

## 답
실무에서는 **누가 → 몇 명이 → 어떤 순서로 → 얼마나 자주 요청하나**를 먼저 정하고, 그 숫자에 맞춰 API와 DB를 정한다. SA에 이 틀이 이미 있다(2-2 페르소나, 3-2 계산 틀, U2 숫자 연결 미해결). 담당 영역 기준으로 채우면 팀 산출물이 된다.

### 1. 페르소나: 내 API를 누가 쓰나 (SA 2-2에서 추림)
| 페르소나 | 이 영역에서 하는 일 | 특징 |
|---|---|---|
| P1 직장인 팬 | 공연 상세를 새로고침해 오픈 시각 확인 → 입장 후 좌석 조회 → 좌석 선택 | 오픈 직전에 조회가 몰린다 |
| P3 공연 운영자 | 공연·회차·좌석 등록 | 요청은 적지만 한 번에 1.5만 행이 생긴다 |
| P4 플랫폼 운영자 | 예매 상태 이력으로 사고 추적 | 이력이 지워지면 안 된다 |

### 2. 요청 흐름과 트래픽: API마다 성격이 다르다
| API | 호출자 | 몰림 정도 | DB 관점 |
|---|---|---|---|
| 공연 목록·상세 | 로그인 안 한 사람 포함 전원(공개) | 가장 많다. 오픈 직전 새로고침 폭주 | 읽기 위주, 거의 안 바뀜 → 캐시 후보(`cache:concert:{id}`, 5분) |
| 회차 좌석 조회 | 입장 토큰을 받은 사람만 | 대기열이 들여보낸 만큼(SA 3-3 예시 동시 약 1,000명) | 값이 계속 바뀌고 한 번에 1.5만 행을 읽는다 |
| 운영자 등록 | 운영자 몇 명 | 거의 없다 | 한 번에 1.5만 행을 쓴다 |
| 예매 상세·내 예매 | 결제한 사람 | 중간 | `INDEX(user_id, created_at)` |

### 3. 직접 계산해 볼 질문
1. **좌석 조회 응답 크기**: 1.5만 석 × 좌석당 JSON 약 60바이트 ≈ 응답 하나 900KB. 입장자 1,000명이 5초마다 새로고침하면 초당 약 180MB가 나간다. 감당되는가, 구역 단위로 나눠야 하는가.
2. **좌석 생성 쓰기**: PK가 `IDENTITY`면 Hibernate는 INSERT마다 생성된 ID를 받아야 해서 JDBC 배치로 묶지 못한다. 1.5만 번 `save()`와 `INSERT INTO schedule_seat ... SELECT ... FROM venue_seat` 한 문장을 비교한다.
3. **`serverTime`이 왜 있나**: 사용자 PC 시계는 틀릴 수 있다. 판매 오픈 판정과 카운트다운은 서버 시각을 기준으로 해야 한다.

계산 결과 때문에 SA와 다르게 가야 하면(예: 좌석 조회를 구역 단위로 나눔) 팀에 확인하고 `docs/decisions/`에 남긴다.

### 4. DB: 새로 설계하기보다 "왜 이렇게 생겼나"를 설명할 수 있게
테이블은 SA 12-3에 정해져 있다(`venue`, `venue_seat`, `concert`, `schedule`, `schedule_seat`). 볼 포인트는 다음이다.
- `venue_seat`(공연장 좌석 배치, 변하지 않음)와 `schedule_seat`(회차별 판매 상태, 계속 바뀜)를 왜 나눴나.
- `schedule_seat`에 `section`·`grade`·`price`를 왜 복사해 두나(조회 때 조인을 없애고, 회차마다 가격이 다를 수 있다).
- `INDEX(schedule_id, section)`은 어떤 쿼리용인가(회차의 구역별 좌석 조회).
- 왜 `version`(낙관적 락)은 운영자가 고치는 공연·회차에만 있고, 논리 삭제는 공연에만 쓰고 예매에는 쓰지 않나(예매는 상태 전이로 남겨야 만료·거절·취소를 구분한다. SA 12-1).

## 핵심 정리
- 요구사항 → 숫자 → 설계 순서로 간다. 숫자가 있어야 "캐시를 왜 쓰나", "왜 한 문장 INSERT인가"를 설명할 수 있다.
- 같은 서비스 안에서도 API마다 트래픽 성격(공개 조회 폭주, 제한된 좌석 조회, 드문 대량 쓰기)이 다르고, 그에 맞는 해법이 다르다.

## 면접 포인트
- "좌석 1.5만 행을 어떻게 만들었나": IDENTITY PK에서는 Hibernate 배치 INSERT가 꺼진다는 점과, `INSERT ... SELECT`로 DB 안에서 한 번에 복사한 이유를 숫자와 함께 말한다.
- "좌석 조회 응답이 크지 않나": 응답 크기 × 요청 빈도로 초당 전송량을 계산하고, 그 결과로 구역 분할·캐시 여부를 정했다고 말한다.
