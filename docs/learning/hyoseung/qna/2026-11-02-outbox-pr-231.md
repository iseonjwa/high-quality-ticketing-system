# Outbox와 processed_events는 무엇이고, PR #231(ISE-147)은 예매 흐름에 무엇을 바꾸나

## 질문
강민 님 PR #231 "예매 서비스 outbox·처리 이력 테이블과 릴레이 설정"을 리뷰해 달라는데 무슨 내용인지 모르겠다.

## 답

### 1. 왜 Outbox가 필요한가
결제 결과를 처리하다 "예매를 EXPIRED로 바꾸고, 결제 서비스에 환불 요청(RefundRequested)을 보낸다"를 해야 한다고 하자.

```java
@Transactional
void handle() {
    reservation.expire();            // DB
    kafkaTemplate.send(환불 요청);     // Kafka
}
```

DB와 Kafka는 한 트랜잭션으로 묶이지 않는다.
- Kafka 전송 후 DB 커밋이 실패하면: 예매는 그대로인데 환불 요청만 나간다.
- DB 커밋 후 Kafka 전송 전에 서버가 죽으면: 예매는 바뀌었는데 환불 요청이 사라진다. 돈이 묶인다.

Outbox는 Kafka에 바로 보내지 않고 **보낼 메시지를 같은 DB의 `outbox_events` 테이블에 행으로 쓴다**.

```java
@Transactional
void handle() {
    reservation.expire();                                        // DB
    outboxWriter.write("payment.command", 키, "RefundRequested", 1, payload);  // 같은 DB, 같은 트랜잭션
}
```

둘이 같은 트랜잭션이라 함께 커밋되거나 함께 롤백된다. 그 뒤 **릴레이**(백그라운드 스케줄러)가 PENDING 행을 집어 Kafka로 보내고 SENT로 바꾼다. 실패하면 다시 시도한다. 메시지가 사라지지 않는다(최소 한 번 전달).

### 2. processed_events는 받는 쪽 장치다
최소 한 번 전달이라 같은 메시지가 두 번 올 수 있다. 받는 쪽은 처리한 이벤트 ID를 `processed_events(event_id, consumer_group)`에 기록하고, 이미 있으면 건너뛴다. PK가 (이벤트 ID, 소비자 그룹)이라 같은 이벤트를 같은 그룹이 두 번 넣으면 막힌다.

### 3. PR #231이 한 일
| 파일 | 내용 |
|---|---|
| 마이그레이션 `V20261102_2` | reservation DB에 `outbox_events`, `processed_events` 생성. payment-service V1·V2와 컬럼·제약·인덱스가 같다(공통 모듈이 이름과 컬럼을 고정해서 쓴다) |
| `ServiceConfiguration` | `CommonOutboxConfiguration`을 가져와 `OutboxWriter`와 릴레이를 켠다 |
| `config-repo/reservation-service.yml` | Kafka 프로듀서 시한과 릴레이 설정(payment와 같은 값). 시한 관계가 어긋나면 공통 모듈이 기동을 막는다 |
| 테스트 프로필 | 릴레이를 끈다. 켜 두면 테스트가 확인하기 전에 행을 집어 간다 |
| `ReservationOutboxTest` | 커밋되면 함께 남고, 롤백되면 함께 사라지고, 트랜잭션 밖이면 거절하는지 확인 |

실제로 이벤트를 쓰는 코드는 없다. 판을 깔아 둔 PR이다.

### 4. 예매 흐름 담당이 볼 점
- ISE-73 결제 결과 처리에서 `RefundRequested`를 보낼 때 이 `OutboxWriter.write(...)`를 업무 변경과 같은 트랜잭션 안에서 부르면 된다. ISE-73의 "상태 변경과 Outbox는 한 트랜잭션" 요구가 이것이다.
- `payment.result` 소비자는 `processed_events`로 중복 처리를 막는다.
- 이 PR이 없으면 ISE-73을 시작할 때 같은 테이블을 직접 만들어야 했다.
