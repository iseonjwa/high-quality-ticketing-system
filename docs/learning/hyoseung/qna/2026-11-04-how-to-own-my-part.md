# 내가 맡은 부분을 누구에게든 정확히 설명하려면 어떻게 공부하나

## 질문

맡은 부분은 누구에게든 확실하고 정확하게 설명할 수 있어야 한다. 코드 전부가 어렵다면 흐름을 정확히 이해하라고 하시는데 어떻게 해야 하나.

## 답

### "설명할 수 있다"의 기준

기능 하나마다 다섯 질문에 막힘없이 답하면 설명할 수 있는 것이다.

1. 누가, 언제 부르나 (사용자 API인지, 이벤트인지, 스케줄러인지)
2. 무엇이 들어오고 무엇이 나가나
3. DB에서 무엇이 바뀌나 (어느 테이블의 어떤 상태가 무엇에서 무엇으로)
4. 무엇이 실패할 수 있고, 그때 어떻게 되나
5. 왜 이렇게 했나 (버린 대안 하나)

코드는 3·4번의 근거로 "여기서 이렇게 한다"를 보여 줄 한 곳만 알면 된다. 전체 줄을 외울 필요는 없다.

### 순서

1. **데이터와 상태를 먼저 본다.** 흐름의 뼈대는 상태 변화다. 예매는 `HELD → CONFIRMED / RELEASED / EXPIRED`, 좌석은 `AVAILABLE → HELD → SOLD`다. 테이블 6개(concerts, schedules, schedule_seats, reservations, reservation_seats, tickets)가 어떤 순서로 채워지는지만 알아도 흐름 절반을 설명할 수 있다.
2. **예매 한 건을 실제로 흘려 본다.** 로컬 스택에서 공연 등록 → 좌석 선점 → 결제 → 확정을 한 단계씩 실행하고, 단계마다 DB를 SELECT로 본다. 읽기보다 눈으로 바뀌는 것을 보는 쪽이 오래 남는다.
3. **실패 경로를 따로 본다.** 정상 흐름은 하나지만 질문은 대부분 실패에서 나온다. 거절, 만료, 기한 뒤 승인, 같은 이벤트 재전달.
4. **말로 설명해 본다.** 듣는 사람(AI든 팀원이든)이 다섯 질문을 던지고, 막힌 곳만 코드로 내려간다.

### 범위 나누기

내 범위(SA 6-5)는 다섯 질문 모두 답한다. 남의 범위(대기열, 결제, 추첨)는 경계만 안다: 나에게 무엇을 주고 나에게서 무엇을 받는지. 예를 들어 결제는 "`payment.result`로 승인·거절·환불을 보내 준다", 추첨은 "당첨 예매가 끝나면 `LotteryPaymentResultHandler`로 알려 준다"까지다.

### 내 기능 한 문단 (2026-11-04 스스로 설명해 보고 고친 것)

1. **시드**: 공연장 1개(KSPO DOME)와 공연장 좌석 15,000석만 시드다. 공연·회차·회차 좌석은 날짜와 가격이 공연마다 달라 시드로 두지 않고 운영자 API로 만든다.
2. **운영자 등록 API**: 공연 등록 → 회차 생성(공연장·공연 시각·오픈 시각) → 회차 좌석 생성(공연장 좌석 15,000석 복사, 등급별 가격).
3. **공연 목록·상세 조회**: 상세에는 회차마다 판매 상태가 붙는다. 판매 상태는 저장하지 않고 조회 시각으로 계산한다. 오픈 전 `BEFORE_OPEN`, 오픈부터 공연 시작 전까지 `ON_SALE`, 그 뒤 `CLOSED`(`Schedule.saleStatusAt`). 화면은 이 값으로 예매 버튼을 열지 정한다.
4. **좌석 조회 API**: 대기열을 통과한 사용자(입장 토큰)가 회차 좌석 배치와 상태를 본다. 대기열은 내 몫이 아니다.
5. 좌석 선점(권우)과 결제(준현)는 내 몫이 아니다. 나는 결제 서비스가 보낸 `payment.result`를 받는 데서 다시 시작한다.
6. **결제 결과 반영**
   - 승인: 예매 확정, 좌석 SOLD, 티켓 발급.
   - 거절: 돈이 나가지 않았으니 환불이 아니라 좌석 반환(RELEASED)이다.
   - 확정할 수 없는 승인(기한 뒤, 중복, 금액 불일치): 나는 `payment.command`로 환불을 요청만 하고, 실제 환불은 결제 서비스가 한다.
   - 환불 완료: 상태를 바꾸지 않는다. 확정 예매의 결제가 환불됐으면 좌석을 풀지 않고 이상 로그만 남긴다(ADR 0027).
   - 처리 실패가 반복되면 DLQ와 `dead_letters`에 남긴다(ISE-74).
7. **대사 API**: 결제 서비스가 예매 상태와 결제 상태를 맞춰 볼 때 쓰는 내부 API(ISE-75).
8. **내 예매 조회**: 예매 상세와 내 예매 목록(ISE-171).
