# k6로 캐싱 개선 전·후를 어떻게 재나

## 질문

수치 개선을 보이려고 아무것도 안 했을 때와 개선했을 때를 재려고 한다. 부하 테스트를 k6로 한다고 했는데 어떻게 하나.

## 답

### 현재 상태 (2026-11-04 확인)

- 팀 결정은 ADR 0046(제안)과 `docs/design/infra/load-test.md`다. 도구는 k6이고, 공통 측정 기반(발생기 EC2, 가상 사용자·토큰, 좌석 초기화, remote write)은 준현 담당이다. 아직 스크립트는 저장소에 없다.
- 내 개선 대상은 SA 6-5 고도화의 캐싱(H2)이다. TTL은 공연 정보 5분, 좌석 상태 1초다(SA 9-5, 결정 기록 #45). 키는 `cache:concert:{id}`다.
- 로컬에는 k6가 설치되어 있지 않다.

### 전·후 비교의 원칙

전·후 비교에서 바꾸는 것은 캐시 하나뿐이어야 한다. 나머지가 달라지면 무엇 때문에 빨라졌는지 말할 수 없다.

| 같게 둘 것 | 이유 |
|---|---|
| 장비·Docker 상한·JVM 옵션 | 장비가 바뀌면 수치 차이가 장비 탓일 수 있다 |
| 데이터 규모(공연·회차·좌석 수) | 행 수가 바뀌면 DB 시간이 바뀐다 |
| k6 스크립트와 부하 단계 | 같은 부하를 줘야 비교가 된다 |
| 워밍업 | JVM은 처음 몇십 초가 느리다. 둘 다 워밍업 뒤에 잰다 |

캐시를 켜고 끄는 방법은 설정값(예: `cache.concert.enabled`) 하나로 두는 것을 권한다. 커밋을 오가며 재면 다른 변경이 섞인다. 설정 하나로 끄면 같은 빌드로 두 번 잴 수 있다.

### 순서

1. k6 설치: `winget install k6` 또는 설치 없이 `docker run --rm -i grafana/k6 run - <script.js`
2. 대상 API를 고른다. `GET /api/v1/concerts/{id}`는 인증이 없어 바로 잴 수 있다. 좌석 조회는 Access 토큰과 입장 토큰이 필요해 준비가 더 든다.
3. 개선 전 측정: 캐시 없이 스크립트를 2~3번 돌려 평균을 기록한다.
4. 캐시를 구현하고, 같은 스크립트로 개선 후를 잰다.
5. 비교표에 p95, 처리량(req/s), 오류율을 적고 Grafana에서 DB 쪽 변화(Hikari 연결 대기, DB CPU)를 같이 본다. 캐시의 효과는 응답 시간보다 "DB에 가는 요청이 줄었다"에서 더 분명히 보인다.

### 스크립트 예시

```javascript
import http from 'k6/http';
import { check } from 'k6';

export const options = {
  stages: [
    { duration: '30s', target: 50 },   // 워밍업
    { duration: '1m',  target: 200 },  // 본 측정
    { duration: '10s', target: 0 },
  ],
  thresholds: { http_req_failed: ['rate<0.01'] },
};

const BASE = __ENV.BASE_URL || 'http://localhost:8080';

export default function () {
  const res = http.get(`${BASE}/api/v1/concerts/1`);
  check(res, { '200': (r) => r.status === 200 });
}
```

- `stages`: 가상 사용자 수를 시간에 따라 바꾼다. 같은 값을 전·후 모두 쓴다.
- `check`: 응답이 200인지 센다. 실패가 섞이면 빠른 것이 아니라 틀린 것이다.
- 결과 요약의 `http_req_duration`의 p(95)와 `http_reqs`(초당 요청)를 비교한다.

### 주의

- 노트북 로컬 측정은 내 개선의 상대 비교용이다. 발표용 절대 수치는 공통 기반(같은 리전 EC2)에서 다시 잰다.
- 공연 상세는 이미 빠를 수 있다. 개선 전에 병목이 없으면 캐시를 넣어도 차이가 작다. 이것도 결과이니 그대로 적는다.
- 측정 환경 기록표(`load-test.md` 7절)를 결과마다 채운다.

### 공통 측정 기반이란 (2026-11-05 추가 질문)

여러 사람이 각자 부하를 재면 장비, 데이터, 토큰 준비가 사람마다 달라 수치를 서로 비교할 수 없다. 그래서 부하를 거는 데 필요한 공통 준비물을 한 사람(준현)이 한 번 만들어 두고, 각자는 그 위에 자기 시나리오만 얹는다. 이 공통 준비물이 공통 측정 기반이다(`load-test.md` 3절).

| 준비물 | 왜 필요한가 |
|---|---|
| k6 실행 구조, 스크립트 위치 | 모두 같은 방식으로 돌리고 결과를 같은 곳에 둔다 |
| 발생기 EC2 (같은 리전·VPC 임시 인스턴스) | 노트북 네트워크와 CPU가 수치를 흔들지 않게 한다 |
| 가상 사용자·Access 토큰·입장 토큰 준비 | 로그인과 대기열을 매번 통과하지 않고 측정 대상 API만 부른다 |
| 회차·좌석 초기화 | 측정마다 같은 데이터 규모에서 시작한다 |
| Prometheus remote write | k6 결과를 서버 지표(CPU, Hikari)와 같은 Grafana에서 겹쳐 본다 |
| 측정 환경 기록표 | 어떤 조건에서 잰 수치인지 남긴다 |

2026-11-05 기준 이 기반은 설계 문서만 있고 스크립트는 아직 저장소에 없다. 내 캐싱 전후 측정은 공연 목록처럼 인증이 필요 없는 API라 기반 없이 로컬에서 먼저 상대 비교를 할 수 있다. 다만 발표용 수치는 기반 위에서 다시 재야 다른 팀원 수치와 같은 조건이 된다.
