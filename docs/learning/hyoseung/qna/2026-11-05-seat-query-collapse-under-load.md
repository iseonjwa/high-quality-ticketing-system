# 좌석 조회 API는 부하 측정에서 왜 무너졌나 (ISE-189, GitHub #336)

## 질문

다른 팀원이 부하 측정을 하는데 타임아웃이 난다고 한다. 좌석 15,000개를 한 번에 조회하는 작업이 무거워 DB 커넥션이 기다리고, 다른 사람도 기다리다 타임아웃이 나고 스레드도 바닥난다는데, 무슨 상황인가.

## 답

### 무엇이 무너졌나

- 대상: 내 API `GET /api/v1/schedules/{id}/seats`(회차 좌석 조회, ISE-148). 회차 좌석 생성 API가 아니다. Redis와도 관계없다.
- 측정: 좌석 선점 담당 최권우가 ISE-79에서 k6 시나리오 K1(대기열이 초당 100명씩 5분 입장 → 좌석 조회 → 선점)을 돌렸다. 근거 문서는 `feat/ISE-79-seat-hold-race-condition` 브랜치의 `docs/design/reservation/k6-seathold-bottleneck-plan.md` 5-1~5-3절이다. 아래 수치는 모두 그 문서의 측정값이고 내가 잰 값이 아니다.
- 결과: 초당 100명에서 약 30,000건 중 좌석 조회 성공이 12~18건이었다. 선점까지 간 사용자는 사실상 없었다.

### 요청 하나가 하는 일

`ScheduleSeatQueryService#getSeats`는 `@Transactional(readOnly = true)` 안에서 `findByScheduleIdWithVenueSeat`(join fetch)로 회차 좌석 15,000개와 공연장 좌석 15,000개를 JPA 엔티티로 만든다. 컨트롤러는 이를 DTO로 바꾸고 약 830KB JSON으로 직렬화한다. 요청 한 건이 메모리에 객체 수만 개와 큰 문자열을 만든다.

### 무너진 순서

1. **메모리**: 동시에 몇 건만 들어와도 힙(local 256MB, 배포 값 768MB)이 찬다.
2. **GC 정지**: 힙이 차서 GC가 연달아 돈다. 컨테이너 메모리가 작아 JVM이 Serial GC를 골랐고, Serial은 정지 동안 모든 요청 스레드를 멈춘다. local 측정에서 6분 중 정지 합계 101.5초, 한 번에 최대 29.1초였다.
3. **커넥션을 쥔 채 멈춤**: 트랜잭션 안에서 멈춘 요청이 커넥션을 놓지 않는다. 풀은 5개라 나머지 요청은 Hikari에서 줄을 선다. 대기는 최대 197건이었다.
4. **스레드 고갈**: Tomcat 요청 스레드(기본 200)가 거의 전부 커넥션을 기다리며 묶인다. 새 요청을 받을 스레드가 없다.
5. **타임아웃**: Gateway는 3초에 504로 끊는다. 서버 안에서는 커넥션을 30초까지 기다리다 500(`CannotCreateTransactionException`)이 난다. Gateway가 포기한 요청도 서버는 끝까지 처리한다.
6. **회복 불가**: GC 정지로 Eureka 갱신이 끊겨 Gateway가 인스턴스를 잃고 503을 준다. 부하가 끝나도 쌓인 요청을 처리하느라 회복하지 못해 재시작해야 했다.

### 핵심: DB는 한가했다

같은 시간 DB 활성 세션은 최대 2~6개, 잠금 대기는 0이었다. 무거운 쪽은 SQL 실행이 아니라 앱이 15,000행을 객체와 JSON으로 바꾸는 일(메모리, GC, CPU)이었다. 커넥션 대기는 원인이 아니라 증상이다. 그래서 커넥션 풀만 늘려도 해결되지 않는다.

### 환경만 바꿔서는 안 됐다

| 단계 | 바꾼 것 | 오류 없이 버틴 최대 속도 |
|---|---|---|
| P0 | local 기본(힙 256MB, Serial GC) | 초당 1명 |
| P0' | 배포 메모리(힙 768MB) | 초당 5명 |
| P0'' | 배포 메모리 + G1 GC | 초당 10명 |

G1로 긴 정지는 사라졌지만, 요청당 비용이 그대로라 초당 100명에서는 똑같이 무너졌다. 서버가 소화한 조회는 초당 약 12건이었다. 그래서 요청당 비용 자체를 줄이는 P4를 선점 개선(P1~P3)보다 먼저 하기로 순서를 바꿨다.

### 내가 할 일 (ISE-189)

응답 JSON 모양은 그대로 두고, 단계마다 PR을 나눠 각 효과를 따로 잰다.

1. P4a: 엔티티 대신 응답에 필요한 열(좌석 ID, 구역, 열, 번호, 등급, 가격, 상태)만 DTO로 바로 읽는다.
2. P4b: 공연 중 바뀌지 않는 배치 정보(구역·열·번호·등급·가격)를 회차마다 한 번 만들어 캐시한다.
3. P4c: 자주 바뀌는 좌석 상태만 따로 읽어 1초 캐시한다. 이미 잡힌 좌석이 1초 동안 빈 좌석으로 보일 수 있지만, 최종 판정은 선점의 조건부 UPDATE라 이중 판매는 생기지 않는다.

단계마다 최권우가 같은 조건(배포 메모리 + G1, K1)으로 다시 재서 문서 5절 표에 더한다.

### 포트폴리오에 쓸 때 지킬 것

- 문제 발견과 측정은 최권우(ISE-79)다. 내 몫은 원인 이해, 개선(P4a~c) 구현, 단계별 효과 확인이다. 이 구분을 흐리지 않는다.
- 개선 전 수치는 위 문서 값을 인용하고, 개선 후 수치는 실제 재측정이 나온 뒤에만 쓴다.

### 이어진 질문 정리

- **join fetch**: 엔티티는 원래 매핑된 열을 전부 읽는다. join fetch는 연관된 `VenueSeat`까지 같은 쿼리로 엔티티로 만든다는 뜻이다(N+1 방지). 그래서 행마다 엔티티 2개, 요청당 3만 개다. 여기에 DTO 15,000개와 JSON 문자열이 더해진다.
- **GC가 못 비우는 이유**: 처리 중인 요청의 객체는 아직 참조되고 있어 쓰레기가 아니다. 동시 요청 수십 건의 객체가 살아 있으면 GC를 돌려도 비울 것이 적고, 힙이 다시 바로 찬다.
- **Serial GC를 고른 이유**: 컨테이너는 Docker 컨테이너다. JVM은 메모리 상한이 약 1,792MB보다 작으면 서버급이 아니라고 보고 스레드 하나로 도는 Serial GC를 고른다(측정 문서 5-2절에서 `UseSerialGC = true {ergonomic}` 확인).
- **커넥션 대기**: 커넥션 5개를 얻은 요청만 일하고 나머지는 트랜잭션 시작 지점에서 커넥션을 기다린다. Tomcat은 요청 하나에 스레드 하나를 쓰므로, 기다리는 요청 수만큼 스레드가 묶여 200개가 바닥난다.
- **30초 500**: Hikari `connection-timeout` 기본값이 30초다. 30초 안에 커넥션을 못 얻으면 `CannotCreateTransactionException`으로 500이다. Gateway는 이미 3초에 504를 줬으므로 사용자는 이 500을 보지 못하고, 서버는 버려진 요청에 시간을 쓴다.
- **GC 정지(Stop-the-World)**: 그 JVM의 애플리케이션 스레드 전부가 멈춘다. 처리 중이던 요청은 하던 곳에서 멈추고, 새 요청도 받아 처리하지 못한다.
- **Eureka가 끊기는 이유**: Eureka는 서비스가 스스로 "살아 있다"를 주기적으로 보내야 명단에 남는다(heartbeat). local 설정은 5초마다 보내고 15초 동안 없으면 뺀다(`config-repo/application-local.yml`). 보내는 스레드도 같은 JVM 안에 있어서 GC 정지 동안 같이 멈춘다. 최대 29.1초 정지는 15초를 넘는다.

- **heartbeat는 요청 스레드를 쓰지 않는다**: Eureka가 서비스에 묻는 헬스체크가 아니다. 서비스 안의 Eureka 클라이언트가 전용 스케줄러 스레드로 Eureka 서버에 먼저 보낸다. 그래서 Tomcat 스레드 200개가 다 차도 heartbeat는 나간다. 끊긴 원인은 스레드 고갈이 아니라 GC 정지(JVM 전체 정지)다.
- **자주 바뀌는 상태를 1초 캐시하는 이유**: 초당 100건이 같은 회차 좌석 상태를 묻는다. 1초 캐시를 두면 그 100건이 DB 조회 한 번의 결과를 같이 쓴다. 대가는 최대 1초 늦은 상태다. 이미 잡힌 좌석이 빈 좌석으로 보여 선점 409가 늘 수 있지만, 최종 판정은 선점의 조건부 UPDATE(`status = 'AVAILABLE'`일 때만 바꿈)라 이중 판매는 생기지 않는다. 화면은 원래 조회 순간에도 낡을 수 있는 정보다.
