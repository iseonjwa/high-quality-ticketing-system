# 좌석 조회는 같은 객체를 다시 쓰는가, 왜 겹치는 요청이 적은가, 하나만 재도 되나

## 질문

1. `docker stats`는 실행할 때마다 껐다 켜야 하나.
2. 내 테스트는 한 사용자가 좌석 조회만 하고, 권우 님은 사용자마다 여러 요청을 해서 무너진 것인가.
3. 서버가 같은 객체를 반복해서 들고 있어서 새 객체가 아니니 힙이 견딘 것인가.

## 답

### docker stats

끄지 않아도 된다. 1~2초마다 값을 새로 그린다. 복사한 순간이 k6를 돌리기 전이었을 뿐이다. 실행 중 30초 동안의 최고값을 봐야 한다.

### 같은 객체를 다시 쓰지 않는다

- 요청마다 새로 만든다. 좌석 조회 한 번에 DB에서 좌석 15,000행을 읽어 엔티티 약 30,000개와 DTO 15,000개를 만들고, 약 800KB JSON으로 바꾼다.
- JPA 1차 캐시는 요청(트랜잭션) 하나 안에서만 산다. 같은 사용자, 같은 회차여도 다음 요청은 처음부터 다시 만든다.
- 앱 수준 캐시가 없다. 같은 결과를 재사용하게 만드는 것이 P4b(배치 정보 캐시)·P4c(좌석 상태 1초 캐시)다. P4a는 엔티티 대신 필요한 열만 DTO로 바로 읽어 요청마다 만드는 객체를 줄인다(2026-11-07 정정: 처음에 P4a를 캐싱이라고 잘못 적었다).

### 힙이 견딘 이유는 동시에 살아 있는 요청 수다

- 요청이 끝나면 만든 객체는 쓰레기가 되고 GC가 치운다.
- 힙에 동시에 살아 있는 양 ≈ 동시에 처리 중인 요청 수 × 요청 하나가 만드는 객체 양.
- RATE=10에서는 응답이 약 125ms라 동시에 처리 중인 요청이 1~2건이었다(VU 최대 2). 살아 있는 양이 작아 GC가 따라잡았다.
- 사용자 수나 요청 종류보다 동시에 몇 건이 겹치느냐가 핵심이다. 겹치는 요청이 늘면 힙이 차고, GC가 자주 돌면서 응답이 느려지고, 느려지면 겹치는 요청이 더 늘어나는 악순환이 생긴다.

### 권우 님 측정과의 차이 (해석, 확인 필요)

권우 님 K1은 사용자마다 대기열·토큰·좌석 조회·선점을 했고, 사용자가 몰려 들어와 좌석 조회가 겹쳤을 가능성이 크다. 정확한 차이는 권우 님 스크립트(`feat/ISE-181-test-load-test-k6`)와 결과를 비교해 확인한다. RATE를 올려 동시 처리 수를 늘리면서 메모리를 보면 직접 확인할 수 있다.

## 이어진 질문 (같은 날)

1. docker stats 최고값은 그 순간을 어떻게 아나.
2. 1초에 10번씩 30초인데 왜 겹치는 조회가 1~2건인가.
3. 좌석 조회 하나만 테스트하는 것은 잘못된 방식인가.

### 최고값은 기록해 두고 나중에 고른다

눈으로 지켜보지 않는다. 다른 창에서 1~2초마다 한 줄씩 찍어 두고, k6가 끝난 뒤 가장 큰 줄을 고른다.

```powershell
for ($i = 0; $i -lt 30; $i++) { docker stats --no-stream --format "{{.CPUPerc}}  {{.MemUsage}}" iseonjwa-reservation-service-1 }
```

### 초당 요청 수와 동시에 겹친 요청 수는 다르다

- 초당 10건은 0.1초마다 1건씩 고르게 출발한다는 뜻이다. 10건이 한꺼번에 가지 않는다.
- 한 건이 약 0.125초에 끝나므로 다음 요청이 출발할 때 앞 요청은 0.025초만 남아 있다. 겹치는 시간이 짧다.
- 동시 처리 수 ≈ 초당 요청 수 × 응답 시간 = 10 × 0.125초 = 1.25건(리틀의 법칙). k6 VU 최대 2와 맞는다.
- 겹침을 늘리려면 초당 요청 수를 올리거나 응답이 느려져야 한다. 응답이 느려지면 겹침이 늘고, 겹침이 늘면 더 느려지는 것이 붕괴의 악순환이다.

### 하나만 테스트하는 것은 잘못이 아니다

- 좌석 조회 하나의 한계와 P4a 전후 비교를 보려면 격리 테스트가 맞다. 다른 API가 섞이면 무엇 때문에 느려졌는지 가릴 수 없다.
- 한계: 요청이 고르게 도착한다. 실제 티켓 오픈은 한꺼번에 몰린다(스파이크). 이 테스트로는 "얼마나 버티나"를 보고, 몰림 상황은 흐름 시나리오(O1, K1)가 맡는다.
- 한 사용자로 반복해도 좌석 조회 서버 부담은 같다. 서버는 사용자마다 결과를 따로 기억하지 않고 매번 새로 만든다.
