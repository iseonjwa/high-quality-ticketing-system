# 좌석 조회 RATE=50에서 난 실패 3건은 무엇이고 왜 느려졌나

## 질문

좌석 조회를 초당 50건 30초로 돌렸더니 실패가 나왔다. 무엇이 실패했고 왜인가.

## 답

### 측정값 (local, 단일 사용자, schedule 2, 15,000석)

| RATE | 실패 | 중앙값 | p95 | VU 최대 | CPU | MEM |
|---|---|---|---|---|---|---|
| 20 | 0 | 91ms | 128ms | 3 | 약 200% | 790MiB |
| 50 | 3 (504) | 1.64s | 2.62s | 118 | 약 800% | 1.12GiB / 1.125GiB |

### 실패 3건은 Gateway 3초 타임아웃이다

1. 서비스 로그: 좌석 조회 1399건 모두 200. 가장 느린 건 4.7초.
2. Prometheus: gateway의 504(Gateway Timeout).
3. `config-repo/gateway.yml` `response-timeout: 3s`. 서비스가 3초 안에 답하지 않으면 Gateway가 끊는다. 서비스는 끊긴 뒤에도 끝까지 일한다.

### 느려진 원인은 GC다

- GC 로그(`-Xmx768m`, G1): 32초 동안 GC 928회, 멈춘 시간 합 8.1초. 시간의 약 25%를 멈춰 있었다.
- `G1 Humongous Allocation`이 자주 나왔다. G1에서 영역 절반보다 큰 객체(큰 배열·버퍼)를 따로 할당할 때 찍힌다. 800KB 응답을 만드는 과정의 큰 버퍼로 본다(해석).
- 악순환: 겹친 요청(약 82건)마다 엔티티·DTO·JSON을 만들어 힙이 찬다 → GC가 자주 돌며 멈춘다 → 응답이 느려진다 → 겹침이 더 는다.

### dropped_iterations

출발 시각에 빈 VU가 없어 k6가 보내지 못한 요청 수(101)다. 서버가 느려 VU가 모두 붙잡혀 있었다는 신호다.

### 교훈

실패율 0.21%만 보면 작아 보인다. 응답 시간 18배, GC로 25% 멈춤이 더 큰 신호다. 이 지점(초당 20~50건 사이)이 단일 사용자 격리 테스트에서의 한계다. P4a 뒤 같은 RATE=50으로 다시 재서 비교한다.

## 출처

- 효승 노트북 `C:\Users\hyozz\k6-practice\K6_LOG.md` (RATE=20, RATE=50)
- `config-repo/gateway.yml`
- reservation-service 컨테이너 `/tmp/gc.log`

## 기준선 확정 (2026-11-07, RATE=30·40 추가)

| RATE | 중앙값 | p95 | 실패 | VU 최대 | dropped | GC 멈춘 비율 |
|---|---|---|---|---|---|---|
| 20 | 91ms | 128ms | 0 | 3 | 0 | - |
| 30 | 106ms | 141ms | 0 | 5 | 0 | 약 16% |
| 40 | 253ms | 558ms | 0 | 23 | 5 | 약 24% |
| 50 | 1.64s | 2.62s | 3(504) | 118 | 101 | 약 25% |

- 30까지 버티고, 40에서 느려지기 시작하고, 50에서 타임아웃이 난다.
- 처리량은 40에서 초당 38건, 50에서 초당 41건으로 초당 약 40건에서 멈췄다. 이것이 P4a 전 처리량 상한이다.
- P4a 뒤 같은 RATE 30·40·50으로 다시 재서 이 표와 비교한다.

## 정확한 원인: DB 커넥션 풀 대기 (2026-11-07 Prometheus 확인)

앞에서는 GC만 원인으로 적었다. Hikari 지표를 보니 줄이 실제로 선 곳은 DB 커넥션 풀이었다. GC와 CPU는 그 줄을 길게 만든 쪽이다.

- `config-repo/reservation-service.yml` `maximum-pool-size: 5`. 커넥션은 5개뿐이다.
- 좌석 조회는 `@Transactional(readOnly = true)` 서비스 메서드 동안 커넥션 하나를 쥔다. 그 안에서 쿼리, 15,000행 읽기, 엔티티 30,000개 만들기가 모두 일어난다.

| 구간 | 커넥션 쥔 시간 평균(`hikaricp_connections_usage`) | 커넥션 기다린 시간 평균(`hikaricp_connections_acquire`) |
|---|---|---|
| RATE=10 워밍업 | 40~66ms | 약 0.1ms |
| RATE=30 | 43~80ms | 약 0.1~0.4ms |
| RATE=40 | 92~109ms | 150~168ms |

RATE=40 구간 `hikaricp_connections_pending` 최대 15, `active` 최대 5(꽉 참).

### 느려지는 사슬

1. 요청이 늘면 CPU를 나눠 쓰고 GC 멈춤(24%)이 끼어 엔티티를 만드는 시간이 늘어난다. 그 시간 동안 커넥션을 쥐고 있으니 커넥션 쥔 시간이 약 50ms → 약 100ms로 늘었다.
2. 커넥션 5개가 처리할 수 있는 양 ≈ 5 ÷ 쥔 시간. 0.1초면 초당 약 50건이다. 초당 40건이면 80%를 쓰는 셈이고, 몰림이 조금만 생겨도 줄이 선다.
3. 사용률이 100%에 가까워질수록 기다리는 시간은 비례가 아니라 급격히 늘어난다(대기열의 성질). 그래서 보내는 양은 1.3배인데 p95는 4배가 됐다.
4. RATE=40 중앙값 253ms ≈ 커넥션 기다림 약 150ms + 쥔 시간 약 100ms.
5. RATE=50은 처리할 수 있는 양을 넘어 줄이 30초 내내 길어졌고, 3초를 넘긴 요청은 Gateway가 끊었다(504). 처리량이 초당 약 40건에서 멈춘 것도 5 ÷ 약 0.12초와 맞는다.

### P4a와의 관계

DTO 직접 조회는 엔티티를 만들지 않아 커넥션을 쥔 시간 자체를 줄이고, 만드는 객체가 줄어 GC 멈춤도 줄인다. 두 가지가 함께 준다. P4a 뒤에는 k6 숫자와 함께 커넥션 쥔 시간·기다린 시간도 비교한다.

### 효승 정리 확인 (같은 날)

- 커넥션 풀: 미리 DB와 연결해 둔 커넥션 5개를 두고, 트랜잭션이 시작할 때 빌리고 끝날 때 돌려준다. `open-in-view: false`라 서비스 메서드가 return할 때 돌려준다. 맞다.
- 쥐고 있는 동안 하는 일: 쿼리 → 15,000행 받기(행 하나에 회차 좌석·공연장 좌석 열이 같이 있다) → 엔티티 30,000개 만들기 → `List<ScheduleSeat>` return. 맞다(3만 개는 결과 행이 아니라 엔티티 수).
- 줄어든 것은 DB 처리량이 아니라 커넥션 5개의 회전율이다. 커넥션을 쥔 시간의 상당 부분이 DB 일이 아니라 자바 쪽 엔티티 생성(CPU)이다.
- 비유: 식당 테이블 5개(커넥션). 음식(DB 결과)은 빨리 나오는데 손님(요청)이 테이블에 앉은 채 오래 먹는다(엔티티 생성). 손님이 몰리면 종업원(CPU)을 나눠 쓰고 가끔 모두 멈추니(GC) 더 오래 앉아 있고, 회전이 떨어져 문 앞에 줄이 선다(pending 15).
- 한 줄: 좌석 조회는 엔티티 30,000개를 만드는 동안 커넥션을 쥐고 있어서, 부하가 커져 CPU 경쟁과 GC로 그 시간이 늘면 커넥션 5개의 회전이 떨어지고 커넥션을 기다리는 줄이 응답 시간을 키운다.

### 정정: DB 시간도 작지 않다 (2026-11-07 EXPLAIN ANALYZE)

앞에서 "커넥션을 쥔 시간의 상당 부분이 자바 쪽 엔티티 생성"이라고 했다. 재 보지 않고 한 말이었고, 재 보니 DB 시간도 크다.

- 같은 쿼리(`schedule_seats` join `venue_seats`, schedule 2, 구역·열·번호 정렬)를 부하 없이 `EXPLAIN (ANALYZE)`로 5번 돌렸다. 실행 시간 약 50~70ms. 15,000 × 15,000 해시 조인 약 27ms, 15,000행 정렬(quicksort, 2.6MB), 결과 전송이 들어간다.
- 부하 없을 때 커넥션 쥔 시간이 40~66ms였으니, 그때는 DB 시간이 대부분이다.
- RATE=40에서 쥔 시간이 약 100ms로 늘었을 때 DB 쪽이 늘었는지 자바 쪽이 늘었는지는 아직 나누지 못했다. DB 컨테이너도 같은 노트북 CPU를 나눠 쓴다. 다음 측정에서 postgres 컨테이너 CPU를 같이 본다.
- P4a 영향: DTO 직접 조회는 자바 쪽 엔티티 생성을 없애지만 DB의 조인·정렬은 그대로다(읽는 열이 줄어 전송량은 준다). DB 쪽이 크면 P4a 효과는 기대보다 작고, DB를 아예 안 가게 하는 P4b·P4c가 더 크게 작용한다.

### CPU가 하는 일

CPU는 명령을 실행하는 장치다. 좌석 조회 한 번에 CPU가 하는 일은 아래와 같다.

- postgres: 두 테이블 조인, 15,000행 정렬, 결과를 바이트로 보냄
- JDBC 드라이버: 받은 바이트를 행마다 Long, String 같은 자바 값으로 바꿈(15,000행 × 25열)
- Hibernate: 엔티티 30,000개를 만들고 필드를 채우고 영속성 컨텍스트에 등록
- 컨트롤러: DTO 15,000개 만들기
- Jackson: 800KB JSON 문자열 만들기
- GC 스레드: 살아 있는 객체 찾아서 옮기기
- 같은 노트북의 Gateway(응답 중계)와 k6(초당 30MB 받아 읽기)

일할 스레드가 코어보다 많아지면 OS가 코어를 잘게 나눠 돌려 쓴다. 한 요청이 받는 CPU 몫이 줄어 같은 일을 하는 데 걸리는 시간이 늘어난다.

## P4a(DTO 직접 조회) 전후 (2026-11-08, 같은 환경에서 다시 측정)

| RATE | 구분 | p95 | 실패 | 커넥션 쥔 시간 | 커넥션 기다린 시간 | GC 멈춤 합(30초) | 서비스 CPU 최고 |
|---|---|---|---|---|---|---|---|
| 30 | 전 → 후 | 135ms → 50ms | 0 → 0 | 74ms → 20ms | 0.3ms → 0.01ms | 4.6초 → 0.15초 | 532% → 68% |
| 40 | 전 → 후 | 651ms → 47ms | 0 → 0 | 106ms → 20ms | 226ms → 0.01ms | 7.3초 → 0.16초 | 849% → 61% |
| 50 | 전 → 후 | 2.68s → 40ms | 4(504) → 0 | 107ms → 18ms | 1,377ms → 0.01ms | 8.3초 → 0.18초 | 868% → 79% |

- 엔티티 30,000개를 만들지 않자 커넥션을 쥔 시간이 약 5분의 1로 줄고, 커넥션 5개 앞의 줄이 사라졌다.
- GC 뒤 살아남는 양이 약 400MB → 약 69MB로 줄어 GC 멈춤이 약 50분의 1이 됐다.
- 읽는 열이 25개 → 8개로 줄어 postgres CPU 평균도 낮아졌다(48~88% → 32~43%).
- 앞에서 "DB 쪽 비중이 크면 P4a 효과가 작다"고 했던 걱정은 맞지 않았다. 병목은 엔티티 생성과 그로 인한 GC·CPU 경쟁이 커넥션 점유를 늘린 쪽이었다.
