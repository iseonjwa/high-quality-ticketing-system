# 잘하고 싶은데 무엇부터 공부해야 하나

## 질문

잘하고 싶은데 도대체 무엇부터 공부해야 하나.

## 답

새 주제를 넓게 펼치지 않는다. 지금 직접 잰 좌석 조회 붕괴(RATE=50, GC 25% 멈춤, Gateway 504)가 교재다. 이 한 건을 끝까지 설명하고 고치는 데 필요한 것만 순서대로 판다.

| 순서 | 공부할 것 | 답할 수 있어야 하는 질문 | 어디서 쓰나 |
|---|---|---|---|
| 1 | 좌석 조회 코드 흐름 | 요청 하나가 Controller → Service → Repository → SQL → 엔티티 → DTO → JSON까지 어떻게 가고, 왜 객체가 3만 개 생기나 | 모든 개선의 출발점 |
| 2 | JPA 엔티티 조회 vs DTO 직접 조회 | fetch join으로 엔티티를 읽을 때와 필요한 열만 DTO로 읽을 때 무엇이 덜 만들어지나 | P4a |
| 3 | JVM 힙과 GC 기초 | 힙, Young/Old, G1, Humongous가 무엇이고 gc.log 한 줄(`610M->400M(768M) 12ms`)을 읽을 수 있나 | RATE=50 원인 설명 |
| 4 | 동시성 기초 | 초당 요청 수와 동시 처리 수는 왜 다르나(리틀의 법칙), Tomcat 스레드와 Hikari 커넥션 풀은 무엇인가 | 부하 결과 해석 |
| 5 | 캐시 | 무엇을 캐시해도 되나(안 바뀌는 배치 vs 자주 바뀌는 상태), TTL과 오래된 값 허용 범위 | P4b, P4c |

### 방법

- 순서 하나마다 위 질문에 노트 없이 말로 답해 본다. 막히면 그 부분만 다시 본다.
- 공부한 것을 바로 측정과 연결한다. P4a를 구현하고 같은 seats.js RATE=20·50으로 다시 재서 GC 횟수와 응답 시간이 얼마나 줄었는지 숫자로 남긴다.
- 지금은 Kafka, 쿠버네티스처럼 좌석 조회와 무관한 주제를 새로 펼치지 않는다.

### 목표 문장

면접에서 이렇게 말할 수 있으면 된다. "좌석 조회를 k6로 초당 20, 50건으로 올려 재 보니 50건에서 응답이 18배 느려지고 Gateway 504가 났다. GC 로그를 보니 시간의 25%를 GC로 멈춰 있었다. 원인은 요청마다 엔티티 3만 개를 만드는 조회였고, DTO 직접 조회와 캐시로 고친 뒤 같은 조건에서 다시 재 X건까지 버텼다."

## 첫 점검 (같은 날, 효승 답 → 보완)

| 순서 | 효승 답 | 보완 |
|---|---|---|
| 1 | fetch join으로 회차 좌석 15,000 + 공연장 좌석 15,000 | 맞다. 여기에 응답 DTO 15,000개가 더해진다. 30,000개 엔티티는 트랜잭션이 끝날 때까지 영속성 컨텍스트가 붙잡고 있다. |
| 2 | 필요한 열만 담아 네트워크 비용을 줄인다 | 네트워크는 작은 부분이다(DB가 같은 Docker 안). 핵심은 만드는 객체 수와 메모리다. 행마다 엔티티 2개 + DTO 1개(45,000개) 대신 DTO 1개(15,000개)만 만들고, 영속성 컨텍스트에 올리지 않는다. RATE=50의 병목이 GC였으므로 객체 수를 줄이는 것이 바로 효과로 이어진다. 안 쓰는 열(created_at, deleted_at 등)도 읽지 않는다. |
| 3 | gc.log 수치 위치를 모름, Humongous 모름 | 아래 한 줄 읽기만 알면 된다. Humongous는 "G1에서 영역 절반보다 큰 객체는 따로 큰 자리에 할당하고, 이게 잦으면 GC를 부른다" 정도면 충분하다. 우선순위는 낮다. |
| 4 | 동시 처리 = DB 자원에 동시에 접근, 조회는 괜찮고 수정이 문제 | 여기서 동시 처리는 서버가 같은 순간 붙잡고 있는 요청 수다. "동시성 문제"는 두 종류다. 자원 문제(동시에 처리 중인 요청이 많아 메모리·CPU·스레드가 바닥남, 조회만으로도 난다, RATE=50이 증거)와 정합성 문제(같은 데이터를 동시에 수정해 이중 판매 등, 선점의 조건부 UPDATE가 막는다). |
| 5 | 안 바뀌는 것(좌석 수, 등급, 가격, 배치)은 캐시, 선점 상태는 매번 DB | 앞부분은 맞다(P4b). 캐시는 DB 부하뿐 아니라 결과를 다시 만드는 CPU·메모리도 아낀다. 선점 상태도 P4c는 1초 캐시를 택했다. 화면에 1초 늦은 상태가 보여도 최종 판정은 선점의 조건부 UPDATE라 이중 판매가 없고, 초당 50건 조회를 DB 1번으로 줄인다. "화면은 조금 늦어도 되고, 판정은 반드시 최신"이라는 구분이 핵심이다. |

### gc.log 한 줄 읽기

```
[57938.319s] GC(2082) Pause Young (Mixed) (G1 Evacuation Pause) 610M->400M(768M) 12.136ms
```

- `57938.319s`: JVM이 켜진 뒤 지난 시간
- `GC(2082)`: 2082번째 GC
- `Pause Young (Mixed)`: 멈추고 젊은 영역(+일부 오래된 영역)을 치웠다
- `610M->400M(768M)`: 힙 사용량 610MB → 400MB, 최대 768MB
- `12.136ms`: 그동안 멈춘 시간

RATE=50 동안 이런 줄이 30초에 928번 나왔고, 멈춘 시간을 더하면 8.1초였다.

## 두 번째 점검 (같은 날)

### 엔티티는 언제까지 살아 있나 (코드 확인)

- `config-repo/application.yml` `open-in-view: false`라 영속성 컨텍스트는 `ScheduleSeatQueryService.getSeats()`(`@Transactional(readOnly = true)`)가 끝날 때 닫힌다.
- 서비스는 엔티티 목록을 돌려주고, DTO 변환은 트랜잭션 밖 `ScheduleSeatController.getSeats()`의 `ScheduleSeatsResponse.of(...)`에서 한다.
- 그래도 엔티티 30,000개는 컨트롤러 지역 변수 `seats`가 참조해 DTO 변환이 끝날 때까지 살아 있다. 변환이 끝나는 순간에는 엔티티 30,000 + DTO 15,000 + JSON 바이트가 동시에 힙에 있다.
- 원리: GC는 아무도 참조하지 않는 객체만 치운다. 트랜잭션 안에서는 영속성 컨텍스트가, 밖에서는 지역 변수가 붙잡는다.
- P4a 주의: 조회 DTO를 다시 다른 응답 DTO로 옮기면 다시 30,000개가 된다. 조회 결과를 응답 항목으로 바로 쓰거나 옮기는 비용을 작게 둔다.

### 선점 상태 1초 캐시는 어떻게 동작하나

- 사람마다 요청은 그대로 서버에 온다. 100명이 조회하면 HTTP 요청은 100번이다. 서버가 화면에 밀어 주는 방식이 아니다.
- 줄어드는 것은 서버 → DB 조회다. 처음 요청이 DB에서 읽어 1초 동안 저장해 두고, 그 1초 안의 다른 요청은 저장해 둔 결과를 그대로 받는다. 1초가 지나면 다음 요청이 다시 DB에서 읽는다. 회차마다 DB 조회가 대략 1초에 1번이 된다.
- 주의(캐시 스탬피드): 1초가 끝나는 순간 동시에 들어온 요청들이 함께 DB로 가는 현상. 구현할 때 한 요청만 읽게 막을지 정한다.

### GC는 언제 도나

- 객체가 참조를 잃는 순간 도는 것이 아니다. 메서드가 끝날 때 도는 것도 아니다.
- 새 객체를 넣을 자리(G1의 Young 영역, Eden)가 차면 돈다. 그때 아직 참조되는 객체만 골라 살리고 나머지 자리를 한꺼번에 비운다. 참조를 잃은 객체는 다음 GC까지 그냥 자리를 차지한다.
- 그래서 "참조를 잃은 시점"은 "치워질 수 있는 시점"이지 "치워지는 시점"이 아니다. JIT이 컴파일한 코드에서는 지역 변수를 마지막으로 쓴 뒤부터 참조로 치지 않을 수도 있어, 메서드가 끝나기 전에 치워질 수 있다.
- RATE=50에서는 GC가 30초에 928번, 약 35ms마다 돌았다. 요청 하나(1.6초) 도중에도 수십 번 돈다. 그때 아직 참조 중인 엔티티 30,000개는 치워지지 못하고 다른 영역으로 복사된다. 오래 붙잡힌 큰 객체 묶음이 GC 비용을 키우는 이유다.
