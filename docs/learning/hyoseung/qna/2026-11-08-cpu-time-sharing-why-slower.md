# CPU를 나눠 쓰면 왜 요청이 느려지나, 800%는 코어 8개를 준 것인가

## 질문

1. 코어 하나가 여러 프로그램을 번갈아 실행해 동시에 도는 것처럼 보이게 하는 것이 멀티태스킹인가.
2. reservation-service에 코어 8개가 할당돼 800%까지 나온 것인가.
3. 요청이 많아지면 왜 느려지나. 컨텍스트 스위칭 때문인가.

## 답

### 1. 멀티태스킹

맞다. OS가 아주 짧은 시간(수 ms) 단위로 실행할 스레드를 바꿔 가며 코어를 나눠 쓴다(시분할). 코어가 여러 개면 실제로 동시에 도는 것과 번갈아 도는 것이 섞인다.

### 2. 800%는 할당량이 아니다

- `docker inspect` 결과 CPU 제한이 없다(`NanoCpus=0`). Docker가 쓸 수 있는 논리 코어는 24개(`NCPU=24`, 컨테이너 `nproc` 24)다.
- 800%는 "코어 8개만큼 실제로 썼다"는 측정값이지 상한이 아니다.
- 40과 50에서 800% 근처에서 멈춘 이유 후보(해석, 확인 전):
  - 커넥션이 5개라 트랜잭션 안에서 일하는 스레드는 동시에 최대 5개다. 커넥션을 기다리는 스레드는 잠들어 있어 CPU를 쓰지 않는다. 일할 수 있는 스레드 수 자체가 막혀 CPU가 더 오르지 않았을 수 있다.
  - 같은 노트북의 k6, Gateway, postgres, Windows가 나머지 코어를 썼을 수 있다.

### 3. 느려지는 이유

- 핵심은 나눠 갖기다. 일할 스레드가 코어보다 많으면 각 스레드는 차례를 기다리는 시간이 생긴다. 코어 8개에 일할 스레드 16개면 각자 절반만 실행되고 절반은 대기열에서 기다린다. 일의 총량은 같아도 요청 하나가 끝나기까지 걸리는 시간(벽시계 시간)은 두 배가 된다.
- 컨텍스트 스위칭(어디까지 했는지 저장하고 다른 스레드 상태를 불러오기)은 맞는 개념이지만 한 번에 수 마이크로초라 주된 원인은 아니다. 바뀐 스레드가 CPU 캐시를 다시 채우는 비용이 더해지는 정도다.
- GC 멈춤은 직접 더해진다. RATE=40에서 시간의 약 24%를 GC로 멈췄다. 일하는 시간이 76ms인 요청이 멈춤 때문에 약 100ms가 된다(76 ÷ 0.76).
- 측정된 것: 커넥션 쥔 시간 약 50ms → 약 100ms, GC 멈춤 16% → 24%. 측정되지 않은 것: 노트북 전체 CPU가 꽉 찼는지. 다음 측정에서 모든 컨테이너 CPU와 작업 관리자의 전체 CPU를 같이 본다.
