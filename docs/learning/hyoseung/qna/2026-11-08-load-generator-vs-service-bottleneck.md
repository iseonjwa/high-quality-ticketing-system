# 부하를 주는 쪽과 받는 쪽이 같은 노트북이면 병목을 어떻게 가리나

## 질문

서비스 탓일 때는 커넥션 대기, GC, CPU, 메모리를 보면 된다. 노트북 탓이라는 것은 무슨 뜻인가.

## 답

### 노트북 탓이란

지금은 노트북 한 대가 세 가지 일을 같이 한다.

1. k6: 요청을 만들고, 응답(좌석 조회 한 건 약 800KB)을 받아 읽는다. 초당 200건이면 초당 약 160MB를 받는다.
2. Gateway: 요청과 응답을 서비스와 k6 사이에서 중계한다. 800KB 응답도 한 번 더 지나간다.
3. 서비스·DB·Kafka 등 컨테이너 20개.

CPU와 메모리는 셋이 나눠 쓴다. 속도를 올리면 서비스가 아니라 k6나 Gateway가 먼저 바닥날 수 있다. 그러면 k6 숫자는 나빠지는데, 원인은 우리 서비스가 아니라 측정 도구나 중계 쪽이다. 이것이 "노트북 탓"이다.

### 가리는 법: 시간을 나눈다

k6가 잰 응답 시간 = 서비스 안 처리 시간 + 서비스 밖 시간(Gateway, 네트워크, k6가 응답을 받는 시간)

| 볼 것 | 어디서 | 서비스 탓이면 | 노트북(서비스 밖) 탓이면 |
|---|---|---|---|
| 서비스 안 처리 시간 | 서비스 로그 `RequestLogFilter` | k6 시간과 같이 늘어난다 | 거의 그대로다. k6 시간만 는다 |
| 커넥션 대기, GC, 서비스 CPU | Hikari 지표, GC 로그, docker stats | 오른다 | 낮다 |
| Gateway CPU | docker stats(gateway) | - | 높다 |
| 노트북 전체 CPU | 작업 관리자 | - | 100%에 붙는다 |
| `dropped_iterations` | k6 | 서버가 느려 VU가 붙잡혀 생긴다 | k6가 VU를 못 돌려도 생긴다 |

예: k6 p95 500ms인데 서비스 안 처리 시간 p95가 30ms면, 나머지 470ms는 서비스 밖에서 쓴 시간이다.

### 확실히 가리려면 분리

부하 발생기를 다른 컴퓨터에 두면 노트북 탓이 사라진다. 팀 계획은 같은 리전 임시 EC2에서 k6를 돌리는 것이다(ADR 0046). 배포 서버는 11/7~11/12 멈춰 있다(ADR 0047). 노트북에서 배포 서버로 큰 부하를 주는 것은 금지다.

같은 노트북 결과와 분리한 결과를 같은 속도로 비교하면, 노트북이 숫자를 얼마나 깎았는지와 서버의 실제 한계를 나눠 볼 수 있다.
