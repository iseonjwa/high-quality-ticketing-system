# 추첨 설정이 좌석 등급을 바꾼다는 뜻, P4b 캐시를 Redis에 둘지 서비스 메모리에 둘지

## 질문

1. 추첨 설정이 좌석 등급을 바꾼다는 것은 무슨 말인가.
2. Redis를 배우고 싶은데 P4b 캐시를 Redis에 둘까.

## 답

### 추첨 설정과 좌석 등급

- 회차 좌석(`schedule_seats`)에는 등급이 두 곳에 있다. 공연장 좌석 등급(`venue_seats.grade`, VIP·R·S)은 바뀌지 않는다. 회차 좌석 등급(`schedule_seats.grade`)은 추첨석이 되면 `LOTTERY`로 바뀐다.
- 관리자가 추첨을 설정하면(`LotteryAdminService` → `convertToLottery`) 해당 등급의 AVAILABLE 좌석 일부가 `LOTTERY`가 된다. 수정(`revertFromLottery`)·종결(`LotteryFinishService` → `revertAllFromLottery`)하면 원래 등급으로 돌아온다(D9).
- 좌석 조회에서 `available`은 `status == AVAILABLE && grade != LOTTERY`다. 그래서 회차 좌석 등급은 바뀌는 값이고, 캐시에 넣으면 추첨 설정 뒤 오래된 값을 보여 준다.
- P4b 설계: 캐시에는 절대 안 바뀌는 것(좌석 ID, 구역, 구역 등급=공연장 좌석 등급, 가격, 열, 번호)만 넣는다. 회차 좌석 등급과 상태는 매 요청(P4c 뒤에는 1초 캐시) 가볍게 읽는다. 그러면 추첨 설정 때 캐시를 비울 필요가 없다. 좌석은 회차를 만들 때 한 번(`ConcertAdminService` → `createFromVenueSeats`) 만들어지고 지우는 코드가 없다.

### Redis와 서비스 메모리

| | 서비스 메모리(예: Caffeine) | Redis |
|---|---|---|
| 요청마다 하는 일 | 이미 만든 객체를 그대로 씀. 새 객체 0개 | Redis에서 약 1MB를 받아 다시 객체 15,000개로 바꿈 |
| P4a 원인(객체 생성·GC)에 대한 효과 | 크다 | 작다. DB 대신 Redis에서 읽을 뿐 객체는 또 만든다 |
| 서버 여러 대 | 서버마다 따로 가진다(안 바뀌는 값이라 문제없음) | 모두 같은 값을 본다 |
| 재시작 | 비워진다(첫 요청이 다시 만든다) | 남는다 |

- 안 바뀌는 큰 덩어리를 요청마다 다시 쓰는 경우는 서비스 메모리가 맞다. Redis가 맞는 곳은 여러 서버가 함께 봐야 하고 자주 바뀌는 값(대기열 순번, 입장 토큰)이다. 우리 대기열이 이미 Redis를 쓴다.
- Redis로 해 보고 전후를 재는 것도 배울 거리다. 다만 효과가 작거나 오히려 느려질 수 있다는 결과가 나올 수 있다.

## 이어진 질문 (같은 날)

### 효승 정리 확인

- 추첨 설정은 회차 좌석 등급만 바꾼다(예: S → LOTTERY). 조건은 상태가 AVAILABLE이고 등급이 고른 원래 등급(sourceGrade)인 좌석이다. 맞다.
- 바뀌는 값을 캐시에 넣으면 바뀔 때마다 캐시를 비우고 다시 채워야 한다(캐시 무효화). 안 하면 사용자는 바뀌기 전 값을 본다. 맞다.
- 그래서 절대 안 바뀌는 값만 캐시에 넣어 무효화를 아예 없앤다. 맞다.

### Redis가 무엇인가

- Redis는 우리 서비스와 따로 도는 서버 프로그램이다(컨테이너 `iseonjwa-redis-1`). 키 → 값을 메모리에 저장하고, 서비스는 네트워크로 묻고 받는다.
- Redis는 자바 객체를 모른다. 넣을 때 객체를 바이트(JSON 등)로 바꾸고(직렬화), 꺼낼 때 바이트를 다시 자바 객체로 만든다(역직렬화).
- 서비스 메모리 캐시는 이미 만든 자바 객체를 서비스 힙에 그대로 들고 있다가 다시 쓴다. 바꾸는 과정이 없다.
- 비유: 서비스 메모리 캐시는 내 책상 위 메모, Redis는 길 건너 공용 창고다. 창고는 모든 서버가 같이 쓰고 서버를 껐다 켜도 남지만, 쓸 때마다 가서 꺼내 와 포장을 풀어야 한다.
- 좌석 배치 15,000개를 Redis에 두면 요청마다 약 1MB를 받아 객체 15,000개를 다시 만든다. P4a에서 줄인 객체 생성이 다시 생긴다.

## 효승의 Redis 흐름 이해 확인과 "현재 상황"의 선택 근거 (같은 날)

- 맞다: 처음 한 번 DB에서 읽은 배치를 JSON으로 바꿔(직렬화) Redis에 키·값으로 저장하고, 그 뒤 요청마다 받아서 다시 객체로 바꾼다(역직렬화).
- 고칠 점: 바이트를 객체로 바꾸는 것은 Redis가 아니라 우리 서비스다. Redis는 바이트(약 1MB)를 보내 줄 뿐이다. 직렬화는 채울 때 한 번, 역직렬화는 요청마다다.
- 고칠 점: 메모리 캐시도 "그대로 응답"은 아니다. 배치에 매 요청 상태를 붙이고, 응답 JSON 변환(Jackson)은 요청마다 한다. 아끼는 것은 배치를 DB에서 읽고 객체로 만드는 일이다.
- 현재 상황 근거(ADR 0048): 병목이 객체 생성이었다, 서비스 1대이고 값이 안 바뀌어 공유·무효화가 필요 없다, 공용 Redis(Gateway·대기열)에 초당 약 50MB를 흘리지 않는다, Redis 장애 정책이 필요 없다, 대기열 회차 캐시(`CachedScheduleReader`)라는 선례가 있다.
- Redis가 맞는 경우: 값이 바뀌고 여러 서버가 같은 값을 봐야 할 때(대기열 순번, 입장 토큰, 로그아웃 블랙리스트).
