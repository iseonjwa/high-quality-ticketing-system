# 좌석 조회 성능 개선(ISE-189 P4a) 포트폴리오 요약

## 한 줄

15,000석 회차 좌석 조회를 JPA 엔티티 조회에서 DTO 직접 조회로 바꿔, 초당 50건에서 p95 2.68s(타임아웃 발생) → 40ms, 처리량 상한 초당 약 41건 → 50건 이상으로 개선했다.

## 상황 → 문제 → 해결 → 결과

- 상황: 티켓 오픈 때 몰리는 회차 좌석 조회 API. 팀 부하 측정(K1)에서 좌석 조회가 먼저 무너져 좌석 선점 개선을 잴 수 없었다.
- 문제(측정으로 찾음): k6로 초당 요청 수를 10 → 50까지 올리며 원인을 좁혔다.
  - 초당 40건부터 응답이 4배 느려지고, 50건에서 Gateway 3초 타임아웃(504).
  - Hikari 지표: 커넥션 5개 앞 대기 평균 226ms → 1.4초.
  - GC 로그: 30초 중 약 8초(25%)를 GC로 멈춤, 매 GC 뒤 약 400MB 생존.
  - 원인: 요청마다 엔티티 30,000개를 만드는 동안 트랜잭션이 커넥션을 쥐고, 부하가 커지면 GC·CPU 경쟁으로 그 시간이 늘어 커넥션 회전이 막힘.
- 해결: JPQL `select new`로 응답에 필요한 8열만 DTO로 바로 읽음(25열 → 8열, 엔티티 0개). 응답 JSON은 그대로.
- 결과(로컬, 같은 환경 전후):

| 초당 요청 | p95 | 커넥션 대기 | GC 멈춤(30초) | 서비스 CPU |
|---|---|---|---|---|
| 40 | 651ms → 47ms | 226ms → 0.01ms | 7.3초 → 0.16초 | 849% → 61% |
| 50 | 2.68s(504 4건) → 40ms(실패 0) | 1.4초 → 0.01ms | 8.3초 → 0.18초 | 868% → 79% |

## 면접에서 말할 것

- 실패율만 보지 않고 응답 시간, 커넥션 대기, GC 로그를 함께 봐서 병목이 DB가 아니라 커넥션 점유 시간이라는 것을 찾았다.
- 한 번에 하나만 바꾸고 같은 환경에서 전후를 쟀다.
- 처음에는 DB 비중이 크면 효과가 작을 거라 봤지만, 측정해 보니 엔티티 생성이 커넥션 점유와 GC를 함께 키우고 있었다.

## GC가 "할 일이 없어졌다"는 뜻

Young GC 비용은 살아 있는 객체를 옮기는 양에 비례한다. 쓰레기는 옮기지 않으므로 공짜다.

| | 전(RATE=50) | 후(RATE=50) |
|---|---|---|
| GC 한 번 | 약 600M → 400M, 평균 9.4ms | 약 297M → 69M, 평균 2.2ms |
| 옮길 생존 객체 | 약 400MB | 약 69MB |
| 30초 동안 횟수 | 887회 | 79회 |

- 한 번에 옮길 양이 줄었다: 동시에 처리 중인 요청이 적고(VU 2), 요청마다 엔티티를 만들지 않아 살아 있는 객체가 작다.
- 덜 자주 돈다: 생존 객체가 작으니 힙 안에 새 객체를 받을 자리가 넓고, 요청마다 만드는 객체도 적어 Eden이 천천히 찬다.
- 그래서 횟수 약 11분의 1, 한 번 멈춤 약 4분의 1, 합계 약 50분의 1이 됐다.

## 이어진 질문: GC 비용과 P4a가 줄인 것 (같은 날)

- 맞는 이해: Young GC 비용은 살아 있는 객체를 찾고 옮기는 일이다. 쓰레기는 손대지 않고 칸째 비운다. 그래서 앱 코드가 GC를 돕는 방법은 "살아 있는 객체를 적게, 짧게" 두는 것이다.
- 고칠 점: 만들어진 객체가 다 옮겨지는 것은 아니다. GC가 도는 순간 아직 처리 중인 요청의 객체만 옮겨진다.
- P4a가 줄인 것은 두 가지가 곱해진 결과다.
  1. 요청 하나가 만드는 좌석 객체 수: 엔티티 30,000개 + 응답 15,000개 = 45,000개 → 조회 row 15,000개 + 응답 15,000개 = 30,000개(+ 영속성 컨텍스트 관리 없음). Eden이 천천히 차서 GC 횟수가 887회 → 79회. (2026-11-08 정정: 처음에 "15,000개로 줄었다"고 적었는데 응답 객체를 빠뜨렸다.)
  2. 객체가 살아 있는 시간: 응답 1.5초 → 약 30ms. GC 순간 처리 중인 요청이 거의 없어 옮길 양이 약 400MB → 약 69MB.
- 그래서 1/3이 아니라 GC 멈춤 합계가 약 50분의 1로 줄었다. 느려짐 → 겹침 → 더 느려짐의 악순환이 반대로 돌았다.
- GC 멈춤은 CPU 일만이 아니라 모든 요청 스레드를 멈춘다. 멈춤이 줄어 커넥션을 쥔 시간도 함께 줄었다.

| 단계 | 버틴 한계(초당) | 무너진 곳 |

| P4b(배치 메모리 캐시) | 300, 서비스 자체는 600까지 p95 17ms | 서비스 밖: 노트북 CPU 100% → Redis 느려짐 → Gateway `auth-redis` 서킷 OPEN → 503 |

- 한 줄: 좌석 조회 한계를 초당 30 → 150 → 300(서비스는 600 이상)으로 올렸고, 단계마다 병목이 커넥션 → DB → Gateway로 옮겨 가는 것을 층별 시간(k6 / 서비스 로그 / 커넥션)으로 확인했다.
- 같은 속도 비교: 초당 200에서 P4a p95 1.18s → P4b 21ms. 초당 150에서 postgres CPU 평균 136% → 21%.
