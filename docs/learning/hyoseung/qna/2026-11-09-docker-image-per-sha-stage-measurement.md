# 도커 이미지와 단계별 이미지로 재는 방법

## 질문

도커 이미지는 어떤 운영체제에 어떤 프로그램을 띄울지 정한 미니 컴퓨터인가. k6를 같은 리전 별도 EC2로 분리해 개선 전·1차·2차를 재려면 dev를 롤백해야 하지 않나.

## 답

### 이미지는 미니 컴퓨터가 아니라 "실행할 파일 묶음 + 실행 명령"이다

- 이미지 = 프로그램을 돌리는 데 필요한 파일을 통째로 얼린 것(읽기 전용)과 "켜면 무엇을 실행하라"는 설정이다.
- 컨테이너 = 그 이미지로 실제 띄운 프로세스다. 이미지 하나로 컨테이너 여러 개를 띄울 수 있다.
- 미니 컴퓨터(가상 머신)와 다른 점: 운영체제의 핵심(커널)은 들어 있지 않다. 호스트(EC2)의 리눅스 커널을 같이 쓰고, 이미지에는 리눅스 배포판의 파일들(alpine의 기본 명령, 라이브러리)만 있다. 그래서 가볍고 빨리 뜬다.

우리 `Dockerfile`로 보면 reservation-service 이미지에는 다음이 들어 있다.

1. alpine 리눅스 기본 파일 + Java 21 실행기(JRE)
2. 그 커밋의 코드로 빌드한 `app.jar`
3. 실행 명령 `java -jar /app/app.jar`

즉 이미지는 "그 커밋 시점의 코드"가 jar로 굳어 있는 상자다. 한 번 만들면 안이 바뀌지 않는다.

### 태그 = 상자에 붙인 이름표, 우리는 main 커밋 SHA를 붙인다

- `images.yml`은 main에 커밋이 들어올 때마다(dev → main 릴리스 머지) 서비스 8개 이미지를 만들어 `ghcr.io/iseonjwa/<서비스>:<main 커밋 SHA>`로 GHCR에 올린다.
- dev 머지만으로는 이미지가 생기지 않는다. main에 들어가야 생긴다.
- 커밋마다 이미지를 따로 남기는 이유가 바로 "그 SHA로 배포하거나 되돌리기 위해서"다.

| 단계 | main 커밋 | reservation-service 이미지 안의 좌석 조회 코드 |
|---|---|---|
| 개선 전 | `4544d1a`(11/6) | 엔티티로 읽음 |
| 1차 개선 P4a | `2f607d1`(11/8) | DTO로 읽음 |
| 2차 개선 P4b | P4b가 main에 들어간 뒤 SHA | 배치 캐시 |

두 커밋 사이 서비스 코드 차이를 비교하면 P4a 파일 10개뿐이다(나머지는 테스트·문서). 그래서 `4544d1a` 이미지가 곧 개선 전이다.

### 그래서 롤백이 필요 없다

- 코드를 되돌리는 것(dev 롤백)과 실행할 버전을 고르는 것(이미지 태그 선택)은 다른 일이다.
- 측정에 필요한 건 "개선 전 코드가 돌아가는 서버"이지 "dev에 개선 전 코드가 있는 상태"가 아니다. 개선 전 코드는 이미 `4544d1a` 상자에 얼려져 있다.
- 배포 서버의 compose에서 reservation-service의 이미지 태그만 `4544d1a…` → `2f607d1…` → P4b SHA로 바꿔 다시 띄우고 그때마다 k6를 돌린다. 다른 서비스, DB, Redis, Gateway는 그대로라 좌석 조회 코드만 다른 같은 조건이 된다.
- dev를 되돌리면 공용 브랜치라 팀원 작업과 다음 릴리스에 영향이 가고, 다시 넣을 때 되돌림을 되돌리는 커밋이 쌓인다.

### 바뀐 서비스만 새 이미지가 생기나 (추가 질문)

아니다. main 커밋마다 8개 서비스 이미지를 모두 새로 만들고 모두 같은 SHA를 붙인다(`images.yml`은 main push에 paths 필터가 없다). 안 바뀐 서비스도 새 이름표가 붙지만 안의 코드는 이전과 같다. 이렇게 하는 이유는 "이 SHA로 배포"라고 하면 8개가 빠짐없이 그 이름표로 있어야 Jenkins가 한 번에 받을 수 있어서다.

그래도 reservation-service만 바꿀 수 있는 이유는 서비스마다 이미지와 컨테이너가 따로라서다. compose에서 서비스마다 어떤 이름표의 이미지를 띄울지 따로 정할 수 있다. 그래서 다른 서비스는 지금 이미지 그대로, reservation-service만 `4544d1a` → `2f607d1` → P4b 이미지로 바꿔 띄운다.

컨테이너는 미니 컴퓨터라기보다 다른 프로그램과 격리된 채 도는 프로세스다. 자기만의 파일·네트워크·프로세스 공간을 가져 따로 된 컴퓨터처럼 보이지만 커널은 EC2와 같이 쓴다.

### 개선 전으로 재는데 다른 사람의 변경이 필요하면 (추가 질문)

- 다른 서비스의 변경: 다른 서비스는 최신 이미지로 띄우므로 그대로 들어간다.
- reservation-service 안의 변경이지만 좌석 조회 측정과 무관: 옛 이미지로 잰다. 재는 것은 좌석 조회 하나다.
- 측정에 꼭 필요한 변경(DB 테이블이 바뀌어 옛 코드가 안 뜨는 경우 등): 최신 main에서 측정용 브랜치를 따고 그 브랜치에서만 P4a를 `git revert`해 이미지를 만든다. dev·main에는 합치지 않는다. 지금 워크플로는 main 커밋만 GHCR에 올리므로 올리는 방법은 배포 담당과 정한다.
- 11/9 확인: `2f607d1` 이후 dev에 reservation-service·common 코드와 마이그레이션 변경이 없다. 측정 첫날 세 단계를 같은 데이터로 한 번에 재면 끼어들 틈이 거의 없다.

### 주의

- 배포 서버는 Jenkins가 main SHA를 보고 띄우고, 서버에서 직접 바꾸는 건 금지다. 태그 바꿔 띄우기는 배포 담당 팀원에게 부탁하고 채널에 알린다.
- `4544d1a` 이미지가 GHCR에 실제로 있는지는 부탁하기 전에 확인한다.
- 단계 사이에 DB 데이터(선점·판매 상태)가 바뀌면 조건이 달라지므로 같은 시드 상태에서 잰다.

### 서버에 들어가는 방법과 measure-mode.sh (추가 질문)

- 컴퓨터는 세 대다. 내 노트북(명령을 치는 곳), 발생기 EC2(k6가 요청을 보내는 곳, 3.106.225.224), 배포 서버(요청을 받는 곳, 공인 52.63.10.174, 사설 172.31.4.93).
- ssh는 내 노트북 터미널에서 다른 컴퓨터에 로그인하는 명령이다. `ssh -i ~/.ssh/id_ed25519 ubuntu@<주소>`를 치면 프롬프트가 `ubuntu@ip-...:~$`로 바뀌고, 그때부터 치는 명령은 그 컴퓨터에서 돈다. `exit`로 돌아온다. `ssh iseonjwa`는 `~/.ssh/config`에 별명을 적어 둔 사람만 쓸 수 있는 줄임말이다.
- 배포 서버에 지금 떠 있는 버전은 서버의 `~/iseonjwa/.deploy/current` 파일에 커밋 SHA로 적혀 있다.
- "덮어쓰기"는 GHCR의 이미지를 바꾸는 것이 아니다. 이미지는 그대로 있고, 서버의 "어느 이미지를 띄울지" 설정에서 reservation-service 줄만 옛 SHA로 바꿔 그 이미지로 컨테이너를 다시 만든다.
- `measure-mode.sh`는 배포 서버를 측정 모드로 바꾸는 팀 스크립트다(측정 전용 키, Prometheus 수신, 추적 샘플링 0.01). 덮어쓰기 파일을 같이 주면 그 설정도 얹어 다시 띄운다. 서버 조작이라 계정 주인만 실행한다.
