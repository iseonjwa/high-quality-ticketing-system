# Gateway 동시 처리 상한의 목적

## 질문

상한은 서비스가 감당할 수 없을 때 추가로 들어오는 요청을 막기 위한 것인가. 정확한 목적은.

## 답

코드(`InFlightLimitHandlerDecorator`)와 설정(`config-repo/gateway.yml`) 주석에 적힌 목적은 두 가지다.

1. Gateway 자신을 지킨다. 처리 중인 요청이 많을수록 힙이 커지고, 배포 서버 5차 측정에서 Gateway가 OOM으로 죽었다. 넘친 요청은 로그·인증·라우팅 전에 맨 앞에서 503으로 바로 거절한다.
2. 응답 시간을 묶는다. 리틀의 법칙(처리 중인 수 = 초당 처리량 × 머무는 시간)으로, 처리량이 한계일 때 동시 수를 묶으면 기다리는 시간도 묶인다. 64는 작은 요청이 평균 40~45ms일 때 p95 200ms에 맞춘 계산값이다.

- 서비스 보호는 주목적이 아니라 결과적 효과다(2차 보강에서 상한 64가 500을 줄임).
- 상한은 서비스별이 아니라 Gateway 전체에 하나라, 큰 응답(좌석 조회 820KB)이 자리를 오래 잡으면 다른 API도 503을 받는다.
- 설정 주석에 "32·64·128·500을 측정 모드에서 비교해 확정한다"고 적혀 있다. 2026-11-14 배포 측정(끔·64·128·256)이 그 근거다.

## 이어진 질문: 동시에 처리 중인 수가 무엇인가

- 효승 정리: 목적은 서버가 더 받을 수 없을 때 추가 요청을 받지 않는 것이다. 맞다. 다만 Gateway는 서버 상태를 직접 재지 않고 "지금 처리 중인 요청 수"만 세서 64를 넘으면 막는다.
- 동시에 처리 중인 수: 지금 이 순간 들어와 있는데 아직 응답이 끝나지 않은 요청 수.
- 리틀의 법칙: 안에 있는 수 = 들어오는 속도 × 머무는 시간. 초당 100건이 들어오고 한 건이 0.1초 걸리면 어느 순간이든 평균 10건이 처리 중이다(효승 예시, 맞다).
- 서버가 한계를 넘어 한 건이 2초 머물면 같은 초당 100건에도 200건이 쌓인다. 쌓인 요청마다 Gateway 메모리를 쓰고(좌석 조회 한 건 820KB) 모두 오래 기다린다. 그래서 64가 차면 바로 503으로 돌려보낸다.
- 측정 대입: 3차에서 상한 128·256은 처리량은 같고 p95만 0.36s → 0.8s → 약 2s로 늘었다. 허용한 줄 길이만큼 기다림이 늘었다.

## 이어진 질문(2026-11-15): 무엇을 높였다고 부르나, 상한은 한계를 보고 도입한 것인가

- 용어: 요청 한 건이 쓰는 자원(DB·메모리·CPU)을 줄여 서버가 실패 없이 버티는 최대 처리량을 높였다. 처리량(throughput), HTTP API에는 TPS보다 RPS가 정확하다. 더 보내도 처리량이 안 늘고 실패·지연이 시작되는 지점은 포화점(SA 3장 결정 #47).
- 발표 문장: 요청 한 건이 쓰는 메모리·DB·커넥션을 단계별로 줄여 좌석 조회 포화점을 초당 5건에서 200건으로 높였다.
- 상한은 효승이 도입한 것이 아니다. 강민이 ISE-230(#497)으로 Gateway 전체를 지키려고 먼저 넣었고(배포 5차 OOM), 서버 한계가 아니라 동시 요청 개수(64)로 막는다. 효승이 한 일은 그 상한이 좌석 조회에 주는 영향을 끔·64·128·256으로 측정해 64 유지 근거를 만든 것이다.

## 이어진 질문(2026-11-15): 서버 한계에서 기다리게 할까, 바로 거절할까

- 효승 정리: 상한 끔은 느려도 실패가 거의 없고, 64는 넘치면 거절한다. 티켓팅은 바로 거절보다 기다리게 하는 게 맞지 않나. 커넥션 줄이 사라지면 이제 스레드를 얻으려고 줄을 선다.
- 상한 끔의 "실패 거의 없음"은 착시다. 3차 초당 800에서 상한 끔은 k6 VU 400이 응답을 기다리느라 묶여 회당 약 15,000건을 아예 보내지 못했다(dropped). 상한 64는 거의 다 보내고 약 15,000건이 503. 성공은 둘 다 약 8,900건으로 같다. 기다리게 해도 더 많이 성공하지 않는다.
- 줄이 생긴다는 이해는 맞지만, 쌓이는 것은 스레드를 기다리는 요청이 아니라 처리 중인 요청이다(2026-11-15 바로잡음, [820KB 한계 노트](2026-11-15-seat-query-820kb-remaining-limit.md)). Gateway는 WebFlux(Netty)라 요청마다 스레드를 잡지 않는다. 상한 없이 받으면 처리 중인 요청이 끝없이 늘어 Gateway 응답 시한(3초) 504, 메모리(OOM)가 나고, 로그인·결제도 같은 Gateway에 갇힌다.
- 결론: 티켓팅에서 기다리게 하는 직관은 맞지만 기다리는 곳은 Gateway 안이 아니라 대기열이다. 대기열이 좌석 조회 포화점보다 낮은 속도로 들여보내고, Gateway 상한 64는 넘쳤을 때의 마지막 안전장치로 둔다. 그러면 64에 걸리는 사람은 거의 없다.

## 이어진 질문(2026-11-15): 상한은 어떤 문제에서 시작했고 지금 어떻게 처리되나

- 시작(강민 11/9~12, `docs/design/infra/gateway-overload-troubleshooting-story.md`): 인증 요청이 초당 2,000씩 몰리면 Gateway가 먼저 무너졌다. 차단기 오탐 → 고치자 CPU 한계 → 더 몰리면 Gateway OOM.
- 메모리를 768 → 1,024MiB로 늘리자 OOM은 사라졌지만 더 많이 안고 있어 p95 435 → 752ms로 느려졌다. 상한 64는 p95 435 → 87ms, 메모리 평탄, 200ms 안 응답 1,469 → 1,696건/초로 늘었다. 거절 위치를 맨 앞(HttpHandler 데코레이터)으로 옮겨 처리량 +13%.
- 지금: Gateway 맨 앞에서 처리 중 요청이 64를 넘으면 인증·로그 전에 503 + Retry-After 3초(dev). 운영자 경로를 빼고 모든 API가 같은 64칸을 쓴다.
- 다시 찾는 이유: 64는 작은 요청(평균 40~45ms) 기준 계산값이다. 820KB 좌석 조회는 칸을 오래 잡아 다른 API까지 503을 받을 수 있다. 배포 측정에서 128·256은 처리량이 같고 기다림만 늘어 64 유지가 맞았다. 큰 응답이 칸을 잡는 위험은 대기열 입장 속도와 응답 크기 줄이기로 푼다.

## 이어진 질문(2026-11-15): 서비스가 아니라 Gateway가 어디서 왜 무너졌나

- Gateway는 요청마다 JWT 서명 검증 → Redis 로그아웃(블랙리스트) 조회 → 입장 토큰 검증 → 서비스 전달 순서로 처리한다.
- 강민이 잰 요청(`/queue/me`)은 서비스 일이 Redis 한 번 읽기라 가벼워, 모든 요청이 거치는 Gateway의 고정 비용이 더 컸다(좌석 조회는 반대로 서비스가 무거움).
- 무너진 순서: ① 인증 차단기 오탐(벌크헤드 거절을 Redis 실패로 세어 순간 10건에 열림, Redis는 0.1~0.8ms로 정상) → 세는 기준 수정. ② Gateway CPU(JFR: 관측 약 24%, HTTP 읽고 쓰기 17.6%, 헤더 6.9%, JWT 6.6%, 로그 5.2%, Redis·차단기 2.5%). ③ CPU가 차자 요청이 인증 전 이벤트 루프 줄에서 쌓여 메모리 OOM.
- 그래서 상한 64로 Gateway 안에 쌓이는 수를 막았다.

## 이어진 질문(2026-11-15): 사용자 흐름, 벌크헤드, 거절하는 순간

- 흐름: 공연 상세 → 예매하기(`POST /schedules/{id}/queue` 대기열 진입) → 대기 화면에서 `GET /queue/me`(내 대기 순번, 3~10초마다 반복) → READY면 `POST /queue/token`(입장 토큰) → `GET /schedules/{id}/seats`(좌석 배치도) → 선점 → 결제. `/queue/me`는 좌석 조회 거절 뒤가 아니라 그 전이며, 기다리는 전원이 반복 조회해 오픈 순간 가장 많이 몰린다. 상한은 좌석 조회가 아니라 이 Gateway 측정에서 나왔다.
- 벌크헤드: Gateway가 Redis를 동시에 부를 수 있는 칸 수. 차면 기다리지 않고 바로 거절한다. 차단기: Redis 호출 실패 비율이 넘으면 한동안 Redis를 안 부른다(열리면 인증 전부 503). 벌크헤드 거절까지 Redis 실패로 세던 것을, 진짜 Redis 실패(시간 초과·연결 오류)만 세도록 "실패로 보는 기준"을 바꿔 해결(ADR 0050).
- CPU → 메모리: 요청마다 붙는 일(관측·읽고 쓰기·헤더·JWT·로그)의 총량이 초당 2,000번에 4코어를 넘어, 요청이 CPU 차례를 기다리며 Gateway 안에 쌓이고 메모리가 터졌다.
- 거절하는 순간: 처리 중 요청이 64 이상이면 인증·Redis·로그·서비스 호출 없이 바로 `503 GATEWAY_OVERLOADED` + `Retry-After: 3`. 프론트는 "연결이 잠시 불안정해요. 곧 다시 시도할게요"를 띄우고 3초 뒤 자동으로 다시 보낸다(`queryClient.ts`). 504는 다른 것(Gateway가 서비스 응답을 3초 넘게 기다리다 포기).

## 이어진 질문(2026-11-15): 벌크헤드는 Redis 전체 요청 제한인가, 한 작업 제한인가

- 한 작업 제한이 맞다(효승 검색 결과). 벌크헤드는 배의 격벽처럼, 한 작업이 동시에 쓰는 자원을 제한해 그 작업이 몰려도 나머지가 멀쩡하게 하는 칸막이다.
- 우리 Gateway의 그 작업은 인증 필터의 로그아웃 토큰 조회 하나다(`GatewayAuthenticationFilter` `redis.hasKey("blacklist:" + jti)`). 설정 `resilience4j.bulkhead.instances.auth-redis`: `max-concurrent-calls: 50`, `max-wait-duration: 0`(넘치면 바로 거절).
- 동시 처리 상한(64)은 Gateway에 들어온 모든 요청, 벌크헤드(50)는 그중 로그아웃 토큰 조회 한 작업이다.
- 정정: 앞서 AI가 "Redis를 동시에 부를 수 있는 칸, 예: 100칸"이라고 한 것은 범위와 값이 틀렸다.

## 이어진 질문(2026-11-15): 로그아웃 확인 벌크헤드가 차도 좌석 조회는 되나

- 아니다(코드 확인).
- 좌석 조회는 Redis를 쓰지 않는다. 예약 서비스 `concert` 패키지에 Redis 코드가 없다(메모리 캐시와 DB).
- 좌석 조회는 로그인이 필요한 경로다(`AccessPolicy` 공개 목록에 없음, `EntryTokenPolicy` 18행). 로그인이 필요한 요청은 모두 Gateway 인증 필터 `isRevoked()`에서 로그아웃 토큰 조회(`redis.hasKey("auth:blacklist:" + jti)`)를 벌크헤드 `auth-redis`(50) 안에서 한다(`GatewayAuthenticationFilter` 91~110행). 칸이 차면 좌석 조회도 503 `SERVICE_UNAVAILABLE`("일시적으로 인증을 확인할 수 없습니다", Retry-After)로 서비스까지 가지 못한다.
- 벌크헤드와 상관없이 지나가는 것은 공개 경로(가입·로그인·재발급·비밀번호 변경, 공연 목록·상세, 추첨 공개 조회, `AccessPolicy` 20~31행)뿐이다.
- 덧붙임(같은 날, 효승이 "예를 들어"의 가정으로 물은 것): Redis를 쓰는 작업이 둘이고 각자 자기 벌크헤드를 따로 가지면, 한쪽 칸이 다 차도 다른 쪽은 된다. 그게 벌크헤드의 목적이다. Resilience4j는 벌크헤드를 인스턴스(이름)별로 따로 만들고 동시 실행 수도 따로 센다. 다만 같은 Redis 서버를 쓰므로 Redis 자체 장애는 둘 다 받는다. 우리 Gateway에는 지금 `auth-redis` 칸 하나뿐이다.

## 이어진 질문(2026-11-15): 강민 측정 상황 다시 정리(확인 결과)

- 측정 대상은 둘이다. 차단기 문제(1~3차)는 Q1 대기열 입장(`POST /queue`) 초당 2,000, CPU·상한 문제(4차부터)는 G1 내 대기 순번(`GET /queue/me`)이다. G1(`g1-gateway-auth.js`)은 시작 때 1만 명을 대기열에 넣어 두고 `/queue/me`만 초당 1,000 → 2,000 …으로 올렸다. 인증이 필요한 가장 가벼운 API라 Gateway 한도만 보려고 골랐다.
- 차단기: 벌크헤드가 차서 생긴 거절을 차단기가 Redis 실패로 세어 열렸고, 인증이 필요한 요청 전부가 Gateway에서 503(1차: 201 428건, 503 19,573건). 당시 건수 창 20은 초당 1,000에서 0.02초라 순간 10건에 열렸다.
- 고침: 벌크헤드 거절을 실패로 세지 않게(`ignore-exceptions`), 창을 시간 기준으로(ADR 0050). 넘친 요청은 여전히 그 요청만 바로 503.
- CPU: 초당 1,500에서 서버 CPU 93%, Redis·차단기는 2.5%, 나머지는 관측·읽고 쓰기·헤더·JWT·로그.
- 상한: 처리가 멈춘 초당 약 1,480 × 한 건 40~45ms = 60~67 → 64(`gateway.yml` 71~73행). 초당 몇 건이 아니라 동시에 들어와 있는 개수로 막는다. 직접 계기는 한계를 넘었을 때의 Gateway OOM.

## 이어진 질문(2026-11-15): 그래서 상한은 몇이 맞나

- 64. 강민 측정(작은 요청 `/queue/me`, 초당 2,000, `gateway-overload-troubleshooting-story.md` 단계 6)과 효승 측정(820KB 좌석 조회)이 따로 같은 답을 냈다.
- 강민: L32 1,575/49ms(초당 1,000에서도 392건 거절), L64 1,696/87ms, L128 1,721/162ms(차이 1.5%는 반복 차이 5% 안, 벌크헤드 50보다 커서 `bulkhead_full` 섞임: 초당 2,500 1,966건 대 L64 96건), L500 1,304/571ms. 강민이 64 유지로 결정(판단 기록 `kangmin/2026-11-11-keep-in-flight-limit-64.md`).
- 효승: 3차 초당 800 30초 성공 64·128·256 모두 약 8,900, p95 0.36s·0.8s·약 2s. 2차 보강에서 64가 500을 거의 없애고 성공 약 15% 증가.
- 이유: 낮추면 평소에도 거절, 올리면 처리량은 같고 기다림만 길어지며 벌크헤드 50보다 커져 안쪽 거절이 생긴다.
- 한계: 값마다 1~3회 측정, 날마다 6~9%p 흔들림. 큰 응답이 칸을 오래 잡는 위험은 상한 값이 아니라 대기열 입장 속도·응답 크기로 푼다.
