# 좌석 조회 병목: 커넥션에서 CPU로

## 질문

1. 2차에서 커넥션 대기 196, 약 50% 500이 난 이유가 맞나.
2. 커넥션 풀을 늘리려다 상태 1초 캐시(3차) 덕분에 늘릴 필요가 없어진 것이 맞나.
3. DB가 한가한데 Gateway·서비스 CPU는 왜 꽉 찼나. CPU는 연산, 메모리는 저장 아닌가.

## 답

1. 맞다. 다만 2차에서 요청마다 읽은 것은 바뀌는 값(좌석 상태 15,000행)이다. 안 바뀌는 배치는 캐시에서 꺼냈다. 그동안 커넥션을 쥐어 초당 200에서 5개가 모자라 줄이 섰고(대기 최대 196), 1초 넘게 기다린 요청은 커넥션 대기 시한(1초, #529)으로 500이 됐다.
2. 좌석 조회만 놓고 보면 맞다. 3차는 상태를 회차마다 1초에 한 번만 읽어 커넥션 대기 0, DB CPU 1~2%가 됐다. 2차에서 풀을 늘렸다면 무거운 쿼리가 동시에 더 돌아 DB CPU가 먼저 찼을 수 있다. 같은 풀을 좌석 선점·추첨 응모도 쓰므로 풀 크기 문제(ISE-237)는 그쪽 근거로 남는다.
3. 응답 한 건을 만들고 보내는 것도 연산이다. 서비스는 메모리의 좌석 15,000개를 JSON 글자(약 820KB)로 바꾸고 임시 객체를 GC로 치운다. Gateway는 820KB를 받아 버퍼에 담고 복사해 내보낸다. 초당 약 295건이면 서비스는 15,000석 JSON을 295번 만들고 Gateway는 초당 약 240MB를 중계한다. 그래서 DB가 한가해도 4코어가 찼다(측정 중 CPU 기록, 비중은 재지 않음). 최권우 측정에서도 3차 뒤 서버 비용의 약 57%가 응답 생성·JSON 변환이었다. 다음 개선은 응답 크기 줄이기(압축, 배치·상태 분리)다.

## 이어진 질문: 3차 뒤 한계 약 295건의 뜻

- 효승 정리: 상태 1초 캐시로 DB 조회가 확 줄었고, 이제는 서비스의 15,000석 JSON 만들기와 서비스 → Gateway → 사용자로 820KB를 두 번 넘기는 일이 남아, 그 한계가 초당 약 295건이다. 맞다.
- 다듬을 점: 1초마다 따로 도는 작업은 없다. 캐시가 만료된 뒤 처음 온 요청 하나가 DB에서 읽어 채우고, 그사이 온 요청은 그 결과를 기다려 같이 쓴다.
- 다듬을 점: 요청 하나가 느린 것이 아니라(초당 200에서 p95 43~125ms), 1초에 해야 할 일의 총량이 4코어를 넘는 것이다. 넘친 요청은 줄을 서거나(상한 끔) 503을 받는다(상한 64).
- 확인 범위: 그 순간 Gateway·서비스 CPU가 4코어를 채운 것은 봤다. 초당 약 240MB(약 1.9Gbps) 전송이라 인스턴스 기본 네트워크 대역폭도 같이 의심되며, 무엇이 먼저 막혔는지는 재지 않았다. 해결책(응답 크기 줄이기)은 같다.
