# PostgreSQL 자동 통계 갱신 기준과 새 회차가 통계에서 빠진 이유

## 질문

PostgreSQL은 바뀐 행 수가 50 + 표 전체 행 수 × 10%가 되면, 그 행 수를 보고 가장 좋은 조회 방법을 정하는 ANALYZE를 다시 하는 것인가. 처음에는 잘 됐는데 부하 테스트로 데이터가 지워지지 않고 쌓이면서 기준이 높아져 자동 ANALYZE가 돌지 않았고, 그래서 실행 계획이 최신이 아니었던 것인가. 그렇다면 기준을 낮추기보다 좌석을 만든 직후 시스템이 ANALYZE를 돌려야 하는가.

## 답

흐름은 맞다. 한 군데만 다듬는다.

- **ANALYZE는 통계를 모으는 명령이다.** 조회 방법(실행 계획)을 정하는 명령이 아니다. 표의 행 수와 열마다 자주 나오는 값·값의 분포를 표본으로 재서 저장한다. 실행 계획은 쿼리가 올 때마다 플래너가 이 통계를 보고 새로 고른다. 통계에 회차 104가 없으면 플래너는 그 회차 좌석을 최소 1건으로 짐작하고, 1건에 맞는 Nested Loop를 고른다.
- **기준은 맞다.** autovacuum은 표마다 "마지막 ANALYZE 뒤 바뀐 행 수(INSERT·UPDATE·DELETE) > `autovacuum_analyze_threshold`(50) + `autovacuum_analyze_scale_factor`(0.1) × 표 행 수"면 자동으로 ANALYZE를 돌린다. 이 서버는 기본값 그대로다.
- **쌓여서 기준이 높아졌다는 것도 맞다.** 표가 작을 때는 회차 하나(15,000행)로 기준을 넘었다. 156만 행이 되자 기준이 약 15만 6천 행이 되어 회차 하나(약 1%)로는 닿지 않았다. 11/12의 마지막 자동 갱신(06:47 UTC)은 좌석 상태 변경 등이 쌓여 돈 것이고, 회차 104는 그 뒤에 생겨 통계에 없었다.
- **운영에서도 같다.** 지난 회차를 지우지 않으므로 운영 데이터도 쌓인다. 테스트에서만 생기는 일이 아니다.
- **결론도 맞다.** 기준을 낮추는 안(Flyway로 표별 `autovacuum_analyze_*` 설정)은 autovacuum 주기(기본 1분)만큼 늦고, 기준보다 작은 공연장에서는 돌지 않으며, 오픈 중 좌석 상태 UPDATE로 자주 돈다. 좌석을 만든 직후(커밋 뒤) 시스템이 `ANALYZE schedule_seats`를 돌리는 쪽이 맞다. PostgreSQL 문서도 한꺼번에 넣은 뒤 ANALYZE를 권한다(Populating a Database).

## 이어진 질문 (2026-11-16)

ANALYZE는 회차 좌석 표 전체를 보고 요약 통계를 다시 쓰고, 특정 회차 좌석을 조회할 때마다 플래너가 그 통계로 몇 행 나올지 짐작하는 것인가. 좌석 생성 직후 ANALYZE를 돌렸는데 새 회차(1,500석)를 왜 15,000행 가까이로 짐작하나.

## 답 (2026-11-16)

흐름은 맞다. "전체"가 아니라 표본이다.

- **ANALYZE는 표본만 본다.** 기본 설정(`default_statistics_target` 100)에서 약 3만 행을 뽑아 요약한다. `schedule_id` 열에는 "표에 든 회차 수"(n_distinct)와 "유난히 많이 나오는 회차 번호 목록"(최빈값 목록)이 남는다. 회차마다 정확한 행 수는 남지 않는다.
- **목록에 없는 회차는 평균으로 짐작한다.** 플래너는 "목록 밖의 행이 목록 밖의 회차들에 고르게 나뉜다"고 본다. 11/16 배포 서버에서 표 259만 5천 행, 회차 174개, 목록 2개(빈도 합 0.0136)라 새 회차 174를 14,890행으로 짐작했다. 실제는 1,500행이다.
- **과대 추정은 이 쿼리에 해롭지 않다.** 플래너는 Hash Join을 골랐다. 문제였던 것은 15,000행을 1행으로 과소 추정해 Nested Loop로 빠지는 쪽이다.
- **11/12에 1행으로 짐작한 이유는 추정이다.** 회차 수가 목록 크기(100) 안쪽이면 모든 회차가 최빈값 목록에 들어가고, 목록에 없는 새 회차는 0에 가깝게 짐작된다. 지금 서버에서는 그 상태를 다시 만들 수 없어 확인하지 못했다. 로컬 테스트 DB(회차가 적음)에서는 고치기 전 8행, 좌석 생성 직후 ANALYZE 뒤 실제에 가까운 값이었다.
- **배포 서버 확인(11/16, ISE-284 배포 뒤):** 회차 생성 05:41:39.44, `last_analyze` 05:41:39.82로 시스템이 생성 직후 ANALYZE를 돌렸다. 259만 5천 행에서 ANALYZE 한 번은 203ms였다.
