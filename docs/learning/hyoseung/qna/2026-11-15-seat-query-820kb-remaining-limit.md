# 좌석 조회 3차 뒤 남은 한계는 820KB 응답을 받는 쪽 대기인가

## 질문

1~3차로 좌석 조회를 크게 개선한 뒤 남은 한계는 요청 하나의 응답이 820KB라는 점이다. 부하를 끝까지 주면, 상대가 이 응답을 다 받을 때까지 Gateway의 요청이 끝나지 않고, 그래서 뒤에 들어오는 요청이 기다리게 되는 것이 한계인가.

## 답

남은 한계가 응답 크기(820KB)라는 점은 맞다. 다만 배포 측정에서 확인된 막힘과 로컬에서 본 막힘은 서로 다르다. 그리고 넘친 요청은 기다리지 않고 바로 거절된다.

1. **배포에서 확인한 것: 응답을 만들고 옮기는 CPU.** 11/14 배포(4코어)에서 3차는 초당 400·800을 보내도 처리량이 초당 약 295건에서 멈췄다. 이때 Gateway CPU는 230~280%, 서비스 CPU는 약 220%로 4코어가 꽉 찼다. DB CPU는 1~2%, 커넥션 대기는 0이었다. 부하 발생기는 같은 망의 EC2라 받는 속도가 빠르다. 그래서 이 막힘은 받는 쪽이 느린 탓이 아니라, 820KB JSON을 만들고(서비스) 옮기는(Gateway) 일이 CPU를 다 쓴 것이다. 둘 중 어느 쪽이 더 큰지는 재지 않았다. 820KB × 295/s ≈ 240MB/s여서 네트워크 대역폭도 후보로 남아 있다(확인 전).
2. **로컬에서 본 것: 받는 쪽이 느리면 Gateway 자리를 오래 잡는다.** 11/12 로컬(노트북 1대)에서 성공 요청의 본문을 받는 데 1.73초가 걸렸다. Gateway 동시 처리 상한은 응답의 마지막 조각을 넘길 때(`doFinally`)까지 자리를 쥔다. 그래서 받는 쪽이 느리면 자리가 64개를 넘었고, 넘친 요청은 503이 됐다. 실제 사용자(휴대폰·와이파이)는 더 느리게 받으므로 이 위험이 커질 수 있다. 다만 배포 환경에서 이 현상을 따로 잰 적은 없다.
3. **넘친 요청은 기다리지 않는다.** 상한 64에서는 자리가 없으면 바로 503 `GATEWAY_OVERLOADED`를 받는다. 배포 초당 800에서 62%가 503이었고 p95는 0.36초였다. 상한을 128·256으로 올리면 넘친 요청이 줄을 서서, 성공 수는 같고 p95만 0.8초·약 2초로 늘었다.

그래서 한계를 한 줄로 쓰면 "820KB 응답을 만들고 옮기는 비용이 4코어를 채워 초당 약 295건에서 멈춘다. 받는 쪽이 느리면 Gateway 자리도 오래 잡는다"가 된다.

## 이어진 질문: Gateway 스레드를 얻으려고 줄이 쌓이고, 그래서 상한에 걸려 인증 전에 거절되나

절반만 맞다. 인증 전에 거절된다는 부분은 맞고, 스레드를 기다린다는 부분은 틀리다.

- **틀린 부분: 스레드를 기다리지 않는다.** Gateway는 WebFlux(Netty, `spring-cloud-starter-gateway-server-webflux`)라 요청마다 스레드를 하나씩 붙잡지 않는다. 적은 수의 이벤트 루프 스레드가 여러 요청을 번갈아 처리한다. 그래서 스레드를 얻으려고 서는 줄은 없다.
- **실제로 쌓이는 것: 처리 중인 요청 수.** 상한은 Gateway 전체에 카운터 하나(`inFlight`)를 두고, 요청이 시작될 때 1을 더하고 응답이 끝날 때 1을 뺀다. 요청 하나가 오래 머물수록 처리 중인 수가 늘어난다(처리 중 수 = 초당 요청 × 머무는 시간). 오래 머무는 이유는 CPU가 차서 느려지는 것(배포에서 확인)과 받는 쪽이 느린 것(로컬에서 확인)이다.
- **맞는 부분: 인증 전에 바로 거절한다.** 처리 중인 수가 64를 넘으면 새 요청은 기다리지 않고 바로 503 `GATEWAY_OVERLOADED`를 받는다. 이 검사는 HttpHandler 데코레이터에서 하므로 관측, 요청 로그, 라우팅, 인증 필터(Redis 로그아웃 토큰 조회)보다 앞이다(`InFlightLimitHandlerDecorator`). 그래서 거절된 요청은 Redis까지 가지 않는다.
- DB 커넥션은 이 병목과 관계없다. 3차 뒤 커넥션을 쥐는 시간은 1.5ms 이하였고, 커넥션 대기는 0이었다.

## 응답 크기는 아직 줄이지 않았다

1~3차는 모두 응답 JSON을 그대로 두고 만드는 쪽만 가볍게 했다. 각 단계에서 응답 바이트를 비교해 같다는 것을 확인했다(`serverTime`·`traceId` 제외).

| 단계 | 바꾼 것 | 줄인 곳 |
|---|---|---|
| 1차(P4a, #377) | 엔티티 대신 필요한 열만 DTO로 읽음(25열 → 8열) | 서비스 메모리·GC |
| 2차(P4b, #534·#603) | 안 바뀌는 좌석 배치를 서비스 메모리에 캐시, 커넥션은 DB 읽는 동안만 | DB 조인·정렬, 커넥션 쥔 시간 |
| 3차(P4c, #605) | 선점 가능 여부를 회차마다 1초 캐시 | DB 조회 자체 |

압축 설정이나 배치·상태를 나누는 코드는 저장소에 없다. 응답 크기를 줄이는 것(gzip 압축, 배치·상태 분리)이 다음 후보다.
