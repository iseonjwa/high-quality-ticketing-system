## 배운 것

### 시간: 브라우저 시계를 믿지 않는다
- **서버 시각 보정**: 사용자 PC 시계는 틀릴 수 있다. 응답의 `serverTime`과 그 응답을 받은 순간의 브라우저 시각으로 차이(offset)를 한 번 재고, 이후 "지금"은 `Date.now() + offset`으로 계산한다. 서버가 시각을 적은 뒤 응답이 오기까지의 시간만큼 늦게 잡히지만, 오픈 카운트다운에서는 허용할 만하다.
  - 이 프로젝트: `createServerClock(serverTime, dataUpdatedAt)`이다. 그린 순간이 아니라 응답 받은 순간(`dataUpdatedAt`)으로 재야 캐시 나이만큼 늦어지지 않는다 — `frontend/src/lib/serverClock.ts`
- **상태는 응답 값이 아니라 지금으로 다시 정한다**: 응답의 `saleStatus`는 응답한 순간의 값이다. 화면을 띄워 둔 채 오픈 시각이 지나면 바뀌어야 하므로, 서버와 같은 규칙(오픈 전/오픈~공연 시작/그 뒤)을 보정한 지금에 다시 적용한다. 카운트다운이 0이 될 때 카드를 다시 그려 "00:00"과 버튼 활성이 같은 순간이 되게 했다(남은 시간은 올림) — `frontend/src/lib/saleStatus.ts`, `docs/design/frontend/README.md` "공연 화면 규칙"
- **나노초 시각 파싱**: Java `Instant`는 소수점 아래 9자리까지 직렬화된다. ECMAScript 날짜 문자열 형식은 밀리초 3자리까지만 정하므로 3자리로 잘라 읽는다. 표시는 보는 사람의 시간대가 아니라 한국 시각으로 고정한다 — `frontend/src/lib/instant.ts`

### 인증: 토큰을 어디에 두고 어떻게 바꾸나
- **Access·Refresh 보관**: Access는 JS 메모리, Refresh는 탭 단위 `sessionStorage`에 둔다. 새로고침에도 로그인이 이어지고 탭을 닫으면 사라진다. 서버가 사용자당 Refresh 하나를 두고 재발급마다 바꾸므로(rotation), 같은 토큰을 다시 쓰면 401 `TOKEN_REVOKED`다. 그래서 동시에 받은 401은 재발급 하나를 함께 기다린다(single-flight) — ADR 0040 4절, [판단 기록](../../../ai-judgments/junhyun/2026-11-02-refresh-token-session-storage.md)
- **만료 코드를 나누는 이유**: `TOKEN_EXPIRED`와 `UNAUTHORIZED`를 나눠도 공격자가 얻는 정보가 거의 없다. 클라이언트는 재발급 여부를 정할 수 있다. 다만 클라이언트는 코드와 상관없이 401이면 한 번 재발급하게 만들어 서버 코드 변화에 덜 묶이게 했다 — [qna/2026-11-02-gateway-expired-token-error-code.md](../qna/2026-11-02-gateway-expired-token-error-code.md)
- **로그인 실패와 계정 정보 노출**: user-service는 없는 이메일에도 가짜 해시로 BCrypt 비교를 한다. 응답 시간으로 계정 존재 여부를 알 수 없게 하려는 것이다. 5회 실패하면 423 잠금이고, 운영자가 초기화하면 임시 비밀번호로는 토큰을 주지 않는다(403 `PASSWORD_CHANGE_REQUIRED`) — `user-service/.../AuthService.java`
- **BCrypt 72바이트 한도**: BCrypt는 비밀번호를 72바이트까지만 비교한다. 서버는 글자 수가 아니라 UTF-8 바이트로 거절하므로 한글은 24자까지다. 화면 검사는 사용자 경험용이고 정본은 서버다 — `frontend/src/auth/formSchemas.ts`
- **돌아갈 경로와 열린 리다이렉트**: 로그인 화면으로 보낼 때 지금 주소를 history state로 넘긴다. 받을 때는 앱 안의 경로만 허용한다(`//다른-호스트` 거절). 인증 화면으로 되돌아오는 고리도 막는다 — `frontend/src/auth/navigation.ts`

### 화면 상태와 캐시(TanStack Query)
- **clear·remove·reset·invalidate**: `clear()`·`removeQueries()`는 캐시에서 쿼리를 지운다. 화면에 붙은 조회는 캐시와 끊겨 다시 받지 않는다. `resetQueries()`는 데이터를 비우고 붙은 조회는 다시 받는다. 그래서 로그아웃은 사용자 조회만 초기화하고 공개 조회(공연 목록)는 둔다 — `frontend/src/api/queryClient.ts`
- **데이터가 있으면 먼저 그린다**: 다시 조회하다 실패하면 `isError`와 `data`가 함께 참일 수 있다. 오류를 먼저 검사하면 받아 둔 카운트다운과 버튼이 사라진다(리뷰에서 재현). 오픈 직전 탭 복귀에 따른 재조회는 그 순간 부하만 늘려 공연 상세에서 껐다.
- **테스트 함정: 알림은 다음 매크로태스크에 온다**: TanStack Query는 화면 갱신을 `setTimeout(0)`으로 모아 보낸다. 다시 조회한 직후 바로 검사하면 갱신 전 화면을 본다. 그래서 고장 난 코드에서도 통과하는 테스트가 2개 있었다.

### 빌드와 보안
- **빌드 상수 접기**: Vite는 `import.meta.env.DEV`를 빌드 때 상수로 바꾸고, `if (false)` 안 코드를 지운다. 함수 기본 인자로 `import.meta.env`를 넘기면 상수로 접히지 않아 목 계정 문자열이 운영 번들에 남았다. 운영 빌드에 들어가면 안 되는 값은 `dist`를 검색해 직접 확인한다.
- **배포 화면은 누구나 연다**: 관리자 계정을 채워 주는 빠른 로그인 버튼은 개발 서버 전용으로 만들었지만 결국 뺐다. 샘플 계정은 각자 로컬 `.env`에 둔다.
- **번들 나누기**: 앱 코드와 라이브러리를 한 파일로 내면 앱만 바뀌어도 사용자가 전부 다시 받는다. 라이브러리를 `react`·`vendor` 묶음으로 나눠 캐시를 살렸다. 경로별 지연 로딩은 첫 화면도 같은 라이브러리를 써서 이득이 작았다 — `frontend/vite.config.ts`

### 접근성
- **오류 문구는 `aria-describedby`로 칸에 잇고, 제출 실패 때 첫 오류 칸으로 초점을 옮긴다.** 문구마다 `role="alert"`를 달면 칸이 여럿일 때 한꺼번에 읽혀 시끄럽다.
- **처리 중 버튼은 `disabled`가 아니라 `aria-disabled`다.** `disabled`는 초점을 잃게 해 키보드 사용자의 위치가 사라진다.
- **상태 변화는 알려야 들린다.** 카운트다운(`role="timer"`)은 매초 읽지 않으므로, 예매가 열린 순간을 `aria-live="polite"`로 따로 알린다. 카드 전체 링크는 제목 링크의 누름 영역을 넓혀(`::after`) 링크 이름을 제목만으로 둔다.

### 테스트가 버그를 잡는지 확인하기
- **되돌림 검사**: 고친 코드를 하나씩 원래대로 되돌려 테스트가 실패하는지 본다. 오늘 인증·공연 화면에서 20곳을 확인했다. 앞의 테스트 함정 때문에 재조회 실패 테스트 2개가 처음엔 잡지 못했고, 고친 뒤 잡았다.
- **시계만 가짜로**: `vi.useFakeTimers({ toFake: ['Date', 'setInterval', 'clearInterval'] })`로 시계와 주기 타이머만 가짜로 돌린다. 목 서버와 조회 재시도가 쓰는 `setTimeout`은 그대로 둬서 "1시간 어긋난 시계 + 3초 뒤 오픈"을 몇 밀리초 만에 검증했다.

### 결제(다른 세션에서 다룬 것)
- **결과 모름은 실패가 아니다**: 승인 응답이 유실되면 PG는 승인했는데 우리는 모른다. Mock PG는 Tomcat Valve로 연결을 끊어 이 상황을 만든다. 결제 서비스는 `UNKNOWN`으로 두고 재확인 스케줄러가 PG 조회로 확정한다 — [docs/design/payment/mock-pg.md](../../../design/payment/mock-pg.md), [failure-scenarios.md](../../../design/payment/failure-scenarios.md)
- **실제 PG를 붙여도 Mock PG가 필요한 이유**: 둘은 쓰임이 다르다. 실제 PG 테스트 모드로는 결제창 흐름과 실제 응답 모양을 확인한다. Mock PG는 서버만으로 도는 결제, 부하 측정, 원하는 장애 재현, 호출 횟수 검증, CI를 맡는다. 그래서 PG 포트 하나에 어댑터 두 개를 두고 설정으로 바꾼다 — [qna/2026-11-02-mock-pg-with-real-pg.md](../qna/2026-11-02-mock-pg-with-real-pg.md), [qna/2026-11-02-toss-payments-test-setup.md](../qna/2026-11-02-toss-payments-test-setup.md)
- **깨진 메시지는 원문 그대로 DLQ로 보낸다**: `RefundRequested` 소비에서 역직렬화 실패를 리스너가 받아 원문을 DLQ로 보내도록 ADR 0020을 바꿨다 — [events-and-reliability.md](../../../design/payment/events-and-reliability.md)

### 프론트 설계 판단에서 배운 것
- **실서비스 구조를 알고 덜어 낸다**: BFF·앞단 가상 대기실·서버 렌더링을 확인한 뒤 시연 범위에 맞춰 nginx 중계만 두었다 — [qna/2026-11-02-reverse-proxy-vs-bff.md](../qna/2026-11-02-reverse-proxy-vs-bff.md), [qna/2026-11-02-waiting-room-vs-server-queue.md](../qna/2026-11-02-waiting-room-vs-server-queue.md)
- **필수 검사와 `paths` 필터는 부딪힌다**: 특정 폴더가 바뀔 때만 도는 워크플로는 필수 검사로 걸 수 없다. 필수인 `build`는 항상 돌리고 안에서 단계만 건너뛰었다 — [qna/2026-11-02-required-checks-and-paths-filter.md](../qna/2026-11-02-required-checks-and-paths-filter.md)
- **프론트는 백엔드 구현 그대로 쓴다**: 공연 상세에 등급 가격·추첨 정보가 없을 때 백엔드에 먼저 요청하거나 가정한 필드를 만들지 않고, 빈 곳을 "나중에 고칠 것"으로 남겼다 — [판단 기록](../../../ai-judgments/junhyun/2026-11-02-frontend-follows-backend-as-is.md)

## 헷갈렸던 것, 아직 모르는 것
- 클래스 합치기 함수(`cn`)가 사용자 글자 토큰 `text-body`를 글자 색으로 보고 함께 쓴 색 클래스를 지웠다. 원인을 찾기까지 시간이 걸렸고, 토큰 이름을 `type-*`로 바꿔 피했다.
- Safari가 소수점 아래 9자리 시각 문자열을 읽는지는 직접 확인하지 못했다. 표준 범위로 잘라 읽게 해서 피했다.
- 목록 응답은 공연마다 "다음 회차" 하나만 준다. 그래서 뒤 회차가 판매 중이어도 "오픈 예정"으로 보일 수 있다. 백엔드가 바뀌기 전까지는 그대로 둔다.
- 처음 화면이 휑하다. 시연 흐름을 다 이은 뒤 다듬기로 했다.
