## 배운 것

### 1. 메시지를 "적어도 한 번" 주고받을 때 생기는 일

**보내는 쪽: Transactional Outbox와 재시도**
- **왜 Outbox인가**: DB 커밋과 Kafka 전송은 한 트랜잭션으로 묶을 수 없다. 그래서 상태 변경과 "보낼 이벤트"를 같은 DB 트랜잭션에 쓰고(outbox 행), 별도 릴레이가 그 행을 읽어 보낸다. 커밋된 이벤트는 언젠가 반드시 나간다. 대신 같은 이벤트가 두 번 나갈 수 있어(at-least-once) 받는 쪽이 `eventId`로 중복을 거른다.
- **일시 오류와 영구 오류**: 브로커가 잠깐 죽은 것(일시)은 기다리면 풀린다. 직렬화 실패·메시지 크기 초과·잘못된 토픽(영구)은 백 번 다시 보내도 같다. 일시 오류는 무한 재시도하고, 영구 오류만 `FAILED`로 멈춘다. 모르는 예외는 일시 오류로 본다. 모르는 예외를 영구로 보면 정상 이벤트가 멈추기 때문이다.
- **지수 백오프와 Jitter**: 실패할수록 간격을 두 배로 늘리고(상한 60초) 무작위 흔들림을 섞는다. 흔들림이 없으면 같이 실패한 행들이 같은 순간에 다시 몰려든다. 이번에는 "equal jitter"를 썼다. 실제 대기는 기본 지연의 50~100%라서 0에 가까운 재시도가 나오지 않는다.
- **키 순서**: 같은 예매의 이벤트는 순서가 중요하다(승인 뒤 환불). 앞선 행이 `FAILED`로 멈추면 같은 키의 뒤 행도 집지 않는다. 운영자가 원인을 고치고 `outbox requeue`로 되살려야 뒤 행이 이어서 나간다.
- 이 프로젝트: `common`의 `OutboxBackoff`·`OutboxFailureClassifier`·`OutboxRepository.claimNext`(#229, ISE-145). compose에서 Kafka 컨테이너를 실제로 멈추고 승인했다. 승인은 200이었고, Outbox는 5분 동안 13번 재시도했다. Kafka를 다시 켜자 25초 안에 `SENT`가 됐다.

**받는 쪽: 재시도·DLQ·백프레셔**
- **DLQ(Dead Letter Queue)**: 계속 실패하는 메시지 하나가 파티션 전체를 막지 않게, 몇 번 재시도한 뒤 별도 토픽(`<토픽>.dlq`)으로 보내고 다음 메시지로 넘어간다. 내용이 틀린 메시지(검증 실패)는 재시도해도 같으니 바로 보낸다.
- **DLQ로 보내기가 실패하면**: 그 메시지를 건너뛰면 잃는다. 그래서 DLQ 전송 결과를 기다리고, 실패하면 오프셋을 커밋하지 않아 같은 메시지를 다시 처리한다(`failIfSendResultIsError`).
- **무한 재시도가 맞는 소비자**: DLQ를 읽는 처리기는 더 갈 곳이 없다. 건너뛰면 환불 의무가 사라진다. 그래서 복구기 없이 최대 60초 간격으로 끝없이 재시도한다.
- **백프레셔**: 추첨 자동결제는 PG 호출 허가를 못 얻으면 DLQ로 보내지 않고, 오프셋을 넘기지 않은 채 1초마다 같은 메시지를 다시 읽는다. 처리 속도를 PG 용량에 맞추는 방법이다. 대가로 같은 파티션의 뒤 메시지(환불 포함)도 기다린다.
- 이 프로젝트: `common.messaging.consumer`의 `ConsumerErrorHandlers`·`ConsumerContainerFactories`(#225, ISE-27). 팀원 PR(#237)의 백프레셔 규칙은 결제 설정이 공통 처리기에 `setBackOffFunction`으로 더하는 방식으로 옮겼다.

**보관 정리: 지워도 중복이 안 생기게**
- **처리 이력(`processed_events`)을 지워도 되나**: 이력은 "이미 처리한 eventId"의 기록이다. 지운 뒤 같은 이벤트가 다시 오면 처리 이력은 막지 못한다. 그래도 중복 환불이 없는 것은, 환불 테이블의 `UNIQUE(payment_id)`와 조건부 UPDATE가 마지막 방어선이기 때문이다. 그래서 이력 보관 기간은 토픽 보관 기간보다 길어야 한다. 짧으면 기동을 막는다.
- **advisory lock**: 두 인스턴스가 같은 배치를 동시에 지우지 않게 PostgreSQL의 이름 붙은 잠금을 쓴다. 세션 잠금(`pg_try_advisory_lock`)은 연결을 계속 쥐어야 해서 커넥션 풀과 맞지 않는다. 그래서 배치마다 트랜잭션 잠금(`pg_try_advisory_xact_lock`)을 썼다. 커밋하면 저절로 풀린다.
- 이 프로젝트: `RetentionCleanup`, `IdempotencyRecordCleanup`(#251, ISE-146). 미확정 결제(`REQUESTED`·`UNKNOWN`·NMC)의 멱등 기록은 남긴다. 같은 키로 다시 오면 그 기록으로 기존 결제를 돌려줘야 하기 때문이다.

### 2. 관측: 무엇을 재고, 언제 사람을 부르나

**지표의 종류와 수집 방식**
- **Counter·Gauge·Timer**: Counter는 늘기만 하는 누적 값이다(실패 수). Gauge는 지금 값이다(대기 건수, 최고령). Timer는 걸린 시간의 분포다. 백분위(p95·p99)는 히스토그램 버킷을 켜야 Prometheus에서 `histogram_quantile`로 구한다.
- **Prometheus는 당겨 간다(pull)**: 서비스가 `/actuator/prometheus`에 값을 내놓으면 Prometheus가 몇 초마다 긁어 간다. 그래서 잠깐 떴다 사라지는 프로세스(Ops 명령 JVM)의 Counter는 긁힐 틈이 없다. Ops 실행 수는 떠 있는 서비스가 감사 테이블을 세어 Gauge로 낸다(`payment_ops_actions`).
- **카디널리티**: 라벨 값 조합마다 시계열이 하나씩 생긴다. `paymentId`처럼 끝없이 늘어나는 값을 라벨에 넣으면 Prometheus 메모리가 터진다. 그래서 라벨 값을 enum으로만 받게 해 구조적으로 막았다.
- **0으로 미리 등록하는 이유**: 처음 일어난 사건은 시계열이 없다가 생긴다. 그러면 `increase()`가 "0에서 1로 늘었다"를 못 본다. 값이 정해진 라벨 조합은 기동 때 0으로 만들어 둔다.
- **DB 집계 Gauge**: "운영자 확인이 필요한 결제 수"처럼 DB를 세야 하는 값은 수집할 때마다 쿼리하지 않는다. 15초마다 집계해 메모리에 두고 Gauge는 그 값을 읽는다. 대신 갱신이 멈추면 값이 굳으므로 "갱신 작업 정체" 알림이 함께 있어야 한다.
- 이 프로젝트: `PaymentMetrics`, `MeteredPgClient`(PG 호출을 감싼 데코레이터), `DbAggregateGauges`(#256, ISE-156). 결제에서는 에러율보다 "돈이 확정되지 않은 채 남은 건과 그 나이"를 먼저 본다(ADR 0024).

**알림 규칙**
- **즉시 확인과 기준 초과**: 돈이 확정되지 않았거나 추적이 끊긴 상태(NMC, DLQ OPEN, Outbox FAILED)는 1건이라도 바로 부른다. 자동 복구가 진행 중이지만 늦어지는 상태(UNKNOWN 5분, Outbox 지연 5분)는 기준을 넘을 때 부른다.
- **`increase(x[5m]) > 0`**: 지난 5분 안에 Counter가 늘었으면 참이다. 더 늘지 않으면 5분 뒤 저절로 풀린다. "발생" 알림을 이렇게 만든다.
- **`time() - 마지막 성공 시각`**: 배경 작업이 멈췄는지 본다. 마지막 성공 시각은 기동 시각으로 시작해야 첫 주기 전에 거짓 알림이 울리지 않는다.
- **알림도 테스트한다**: `promtool test rules`에 가짜 시계열을 주고 "몇 분에 어떤 라벨로 울리는가"를 단정한다. 기준값을 일부러 바꾸면 테스트가 실패하는 것도 확인했다.
- **겪은 함정**: 테스트 파일을 규칙 폴더에 두자 Prometheus가 `rules/*.yml` 패턴으로 테스트 파일까지 규칙으로 읽어 기동에 실패했다. 테스트는 `tests/`로 옮겼다.
- 이 프로젝트: `infra/prometheus/rules/payment-alerts.yml`(21개), `infra/grafana/dashboards/payment.json`(#257, ISE-157). compose에서 Kafka를 멈추고 5분 9초 뒤 `PaymentOutboxDelayed`가 울렸고, 다시 켜자 50초 뒤 풀렸다.

### 3. 운영자 복구: 사람이 돈을 움직일 때의 안전장치
- **직접 SQL을 막는 이유**: `UPDATE payments SET status='APPROVED'` 한 줄은 알림을 끄지만 이벤트가 나가지 않는다. 예매는 확정도 환불도 되지 않아 돈이 묶인다. 상태 변경, 이력, Outbox, 감사를 한 트랜잭션으로 묶는 명령만 허용한다.
- **목표 상태는 사람이 아니라 PG가 정한다**: 운영자는 "승인으로 바꿔라"를 고르지 못한다. 명령이 실행 시점에 PG를 다시 조회하고, 그 결과에 맞는 전이만 한다. PG를 모르면(`Unknown`) 아무것도 바꾸지 않는다.
- **dry-run과 계획 해시**: 먼저 무엇이 바뀔지 보여 주고, 대상·현재 상태·PG 근거의 SHA-256 해시를 준다. 적용할 때 계획을 다시 만들어 해시가 같아야만 실행한다. 확인과 실행 사이에 상태가 바뀌는 문제(TOCTOU)를 막는다.
- **4-eyes와 감사**: 돈이 움직이는 명령은 실행자와 다른 승인자가 있어야 한다. 성공(APPLIED)은 상태 변경과 같은 트랜잭션에 쓰고, 거부(REJECTED)는 롤백 뒤 따로 쓴다. 감사 테이블과 상태 이력은 DB 트리거가 UPDATE·DELETE·TRUNCATE를 거부한다(append-only). 테스트 정리에서만 `SET LOCAL session_replication_role = replica`로 트리거를 건너뛴다.
- **일회성 JVM**: 같은 이미지를 `ops` 프로필로 한 번 띄워 명령 하나를 실행하고 끝낸다. 웹 서버, Kafka 소비자, 배경 작업, Eureka 등록을 모두 끈다. 새 HTTP 엔드포인트(공격 표면)를 만들지 않는 방법이다.
- **한계를 거부로 드러내기**: PG 콘솔에서 직접 환불한 건은 우리 환불 ID가 없어 지금 PG 포트로 확인할 수 없다. 그래서 `refund resolve`는 거부하고 NMC로 남긴다. 확인 못 한 것을 확인한 척 닫지 않는다.
- 이 프로젝트: `ops` 패키지의 `OpsRunner`, 명령 `inspect`·`outbox requeue`·`payment resolve`·`refund resolve`·`refund retry`·`dead-letter resolve`(#258·#259·#262, ISE-158~160). compose에서 "DLQ OPEN 알림 → `dead-letter resolve --no-obligation` → 알림 해제"를 실제로 돌렸다.

### 4. 장애를 테스트로 증명하기
- **불변식으로 검증한다**: 장애마다 결과를 따로 단정하기보다, 끝날 때 늘 같은 세 가지를 본다. V1 승인 중복 없음, V2 환불 중복 없음, V3 모든 결제가 정상 종결이거나 지표에 잡힌 미해결이다.
- **저장 횟수가 아니라 호출 횟수**: PG가 멱등이면 같은 주문을 두 번 보내도 저장은 한 번이다. 그래서 "중복 승인 없음"은 저장이 아니라 호출 수(`approveCalls`)로 봐야 한다. Mock PG에 호출 계수와 원장 조회를 더했다(#263, ISE-128).
- **장애 대상을 좁힌다**: 배경 작업도 PG를 부르므로 "다음 호출 한 번 실패"를 걸면 엉뚱한 호출이 그 한 번을 가져갈 수 있다. 장애는 `orderId`·`refundId`로 한정한다.
- **재시작은 "재시작 직후 상태"로 만든다**: 테스트에서 프로세스를 죽이는 대신, 죽었을 때 남는 DB·PG 상태(TX1만 커밋됨, PG만 승인됨, 임대가 남음)를 만들고 복구 경로를 돌린다.
- **변이 확인**: 일부러 버그를 넣어 테스트가 실패하는지 본다. 이번에 이 방법으로 "시나리오가 금액 불일치 경로를 한 번도 지나지 않는다"는 빈틈을 찾아 시나리오를 더했다.
- **실제 장애는 테스트와 다르게 보일 수 있다**: 테스트의 DB 스위치는 새 연결을 거절한다. compose에서 `docker pause`로 Postgres를 얼리면 연결은 살아 있고 쿼리만 멈춘다. 커넥션 풀 대기 시한(1초)은 빈 연결이 없을 때만 걸리므로, 요청은 Gateway 시한(3초)을 넘겨 504가 됐다. DB가 풀린 뒤 처리가 이어져 결제 1건이 승인됐고 같은 키 재시도가 같은 결과를 받았다. 안전했지만 스레드가 무한정 기다릴 수 있어 소켓·문장 시한을 후속 과제(ISE-163)로 남겼다.
- 이 프로젝트: `payment-service`의 `scenario` 패키지(#264·#266, ISE-161·162), 검증기 `ScenarioInvariants`. 시나리오 26개(FT-1~6)가 모두 끝에 V1~V3를 통과하고, 3회 반복해도 간헐 실패가 없다.

### 5. 글자 충돌 없는 충돌: Flyway 버전과 비엄격 필수 검사
- 두 PR이 각자 `V5__...sql`을 더했다. 파일 이름이 달라 Git은 충돌로 보지 않았지만, Flyway는 같은 버전 둘을 거부해 dev에서 결제 서비스가 뜨지 않았다.
- dev 보호 규칙의 필수 검사는 "최신 dev 기준"(strict)이 아니다. PR의 초록 CI가 다른 PR이 머지되기 전 기준일 수 있다.
- 배운 점: 머지 직전에 최신 dev를 브랜치에 합쳐 다시 테스트하고, 마이그레이션 번호를 대조한다. 이후 모든 머지를 이 방식으로 했다 — [TS-31](../../../troubleshooting.md)
