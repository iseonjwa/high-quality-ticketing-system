# 알림 기능을 넣으면 서비스를 새로 만들어야 하나, 범위는 어디까지 넓히나

## 질문
1. 알림을 기능에 추가하면 새로운 서비스가 생길까?
2. 알림 서비스를 추가하려면 기능 범위를 어떻게 넓히는 게 좋을까?

## 짧은 답
- 알림을 보내는 쪽이 하나(추첨 결과 알림, F6-8)뿐이면 새 서비스가 필요 없다. 보내는 서비스가 2개 이상이 되면 Notification 서비스로 떼는 것이 낫다.
- 분리 근거가 서려면 세 가지가 필요하다. 알림을 보내는 서비스가 여러 개이고, 알림 서비스가 자기 데이터를 갖고, 장애 격리를 시연할 수 있어야 한다.

## 자세히

### 언제 떼나
- 예매 확정(Reservation), 결제 실패·환불 완료(Payment), 추첨 당첨·예비 승계(Lottery)처럼 여러 서비스가 알림을 보내면 뗀다.
- 결합이 거의 없다. 다른 서비스는 이미 Kafka로 이벤트를 발행하고 있으므로 Notification은 구독만 하면 된다. 아무도 Notification을 동기로 호출하지 않으니 알림이 죽어도 예매·결제는 영향을 받지 않는다.
- 발제문의 비동기 예시("주문 완료 후 알림·집계·로그 적재 → Kafka")와 그대로 맞는다.
- 예외: "대기열 입장 차례 알림"은 몇 초 안에 떠야 하는 실시간 알림이라 연결을 들고 있는 Queue가 SSE로 직접 보낸다.

### 분리 근거를 세우는 최소 범위
- **F7-1 거래 알림 발송**: 기존 Kafka 이벤트(예매 확정, 취소·환불, 추첨 당첨·낙첨, 승계)를 구독해 보낸다.
- **F7-2 알림함**: 내 알림 목록 조회, 읽음 처리. 자기 데이터(notification 테이블)와 조회 API가 생겨 "구독만 하는 껍데기"가 아니게 된다.
- **F7-3 Mock 발송기**: Mock PG처럼 지연과 실패율을 설정하는 모의 이메일 발송기. 외부 채널 장애를 원하는 때에 재현한다.
- **H12 알림 고도화**: Notification을 내려도 예매·결제는 정상이고, 복구하면 밀린 메시지를 소진한다(Grafana Consumer lag로 시연). 멱등 발송, 재시도·DLQ는 H8 공통 모듈을 재사용한다.

### 여유 있을 때와 넣지 않을 것
- P2: 공연 오픈 알림 신청(대량 발송 fan-out, 거래 알림과 토픽 분리), 실제 이메일(Mailtrap 같은 SMTP 테스트 서비스).
- 넣지 않음: SMS·카카오 알림톡(비용·발신 심사), 모바일 푸시(앱 없음), 알림 설정 세분화·마케팅 알림(고도화와 무관한 CRUD).

## 이 프로젝트에서는
- 현재 SA MASTER는 "알림: F6-8 하나뿐이라 Lottery 안에서 처리한다"로 되어 있다. 알림 확장(F7·H12, Notification 서비스)은 SA에 반영하지 않았고, 추가할지는 정하지 않았다.
- 추가하면 서비스가 6개가 된다. 발제 체크리스트의 "서비스가 5개 이상이다 → 합칠 수 있는지 재검토"를 더 넘어가므로, 같은 날 교차 검토에서 제안된 Lottery 병합 여부와 함께 판단하는 것이 좋다.
- 분리할 때 쓸 한 문장: "여러 서비스의 이벤트를 한 곳에서 구독해 발송하고, 발송 채널의 지연·장애가 예매·결제에 번지지 않게 한다."

## 면접 포인트
- "알림을 왜 별도 서비스로 뗐나요(또는 안 뗐나요)?" → 보내는 주체가 하나면 그 서비스 안에서 처리한다. 여러 서비스가 보내고 외부 채널 장애를 격리해야 할 때 이벤트 구독형 서비스로 뗀다. 동기 호출이 없어서 알림 장애가 거래로 번지지 않는다.
