# 티켓팅 대기열에 RabbitMQ를 쓰면 안 되나, RabbitMQ는 필수 요구사항인가

## 질문
1. 대기열에 RabbitMQ를 쓰면 안 될까?
2. RabbitMQ는 이번 프로젝트의 필수 사항이 아닌가?

## 짧은 답
- 쓸 수는 있지만 대기열 자체에는 Redis Sorted Set이 맞다. 이름은 둘 다 "큐"지만 대기열(waiting room)과 메시지 큐는 하는 일이 다르다.
- RabbitMQ는 필수가 아니다. 발제문에서 지금까지 배운 학습 목표 목록에만 나오고, [필수] 항목에는 Kafka가 명시돼 있다.

## 자세히

### 대기열이 해야 하는 일
| 할 일 | Redis Sorted Set | RabbitMQ |
|---|---|---|
| 내 순번 조회 | `ZRANK`로 "나는 몇 번째"를 바로 안다 | 큐 전체 길이는 알지만 특정 사용자의 위치는 알 수 없다. 예상 대기시간도 계산할 수 없다 |
| 중복 진입 방지 | userId를 멤버로 쓰면 같은 사람은 한 자리만 남는다 | 메시지가 쌓이기만 해서 이미 줄 서 있는지 확인할 수 없다 |
| 이탈 처리 | `ZREM` 한 번으로 줄 중간에서 뺀다 | 중간 메시지를 지울 수 없어 맨 앞에 올 때까지 기다렸다가 버린다 |
| 초당 N명 입장 | 앞에서 N명을 꺼내 입장 토큰을 준다 | 컨슈머가 초당 N개를 꺼내면 된다 |

RabbitMQ는 "앞에서부터 꺼내 처리하는 작업 큐"이고, 대기열은 "줄 선 사람이 자기 위치를 계속 확인하는 줄"이다. 순번을 보여 줘야 하는 순간 RabbitMQ로는 부족하다.

### RabbitMQ가 잘 맞는 곳
- 5분 선점 만료: 메시지 TTL과 DLX(Dead Letter Exchange)로 지연 메시지를 만들 수 있다.
- 결제 재시도·DLQ: 재시도와 실패 격리가 기본 기능이다.

다만 Kafka는 발제 필수라 빠질 수 없고, RabbitMQ를 더하면 브로커 두 개를 운영해야 한다. 선점 만료는 Redis TTL이나 스케줄러로도 충분하다.

### 발제문에서 확인한 사실
- RabbitMQ: 학습 목표 "대규모 스트림 처리" 목록의 "RabbitMQ 를 사용하여 프로듀서 컨슈머간의 메세지 전달을 할 수 있습니다." 한 곳뿐이다.
- Kafka: [필수] 분산 트랜잭션("Kafka를 이용해 각 단계의 진행 상태를 이벤트로 발행/구독")과 [필수] 대용량 트래픽("Kafka를 이용해 요청 데이터를 지정된 Topic에 적재하고 바로 응답") 두 곳에 명시돼 있다.

## 이 프로젝트에서는
- 대기열은 Redis Sorted Set, 이벤트는 Kafka로 가고 RabbitMQ는 넣지 않는 방향이다. SA MASTER에도 RabbitMQ는 없다.
- 학습 목표의 "Redis Sorted Set으로 리더보드 만들기"를 대기열 순번 관리로 응용한 것이라, 발표에서 "배운 걸 이렇게 썼다"로 연결할 수 있다.
- 선점 만료를 Redis TTL로 할 때의 주의점(Redis와 DB 만료 시각이 따로 놀면 한쪽만 풀림)은 [sa-review/03](../../../sa-review/03-seat-hold-kafka-design.md)의 규칙 1에 있다.

## 면접 포인트
- "대기열을 왜 메시지 큐가 아니라 Redis로 만들었나요?" → 대기열은 순번 조회, 중복 진입 방지, 중간 이탈이 필요하다. Sorted Set은 셋 다 O(log N) 명령 하나로 되고, 메시지 큐는 위치 조회와 중간 삭제를 지원하지 않는다.
- "Kafka와 RabbitMQ는 어떻게 다른가요?" → Kafka는 로그를 보존하고 파티션 단위 순서와 재처리에 강하다. RabbitMQ는 라우팅, TTL·DLX 같은 메시지 단위 제어에 강하다. 이 프로젝트는 발제가 요구하는 이벤트 발행·재처리 때문에 Kafka를 쓴다.
