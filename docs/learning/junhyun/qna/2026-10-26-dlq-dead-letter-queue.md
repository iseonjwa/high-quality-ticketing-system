# DLQ(Dead Letter Queue)는 무엇이고 언제 쓰는가

## 질문
DLQ가 뭔지 알려줘.

## 짧은 답
처리에 계속 실패하는 메시지를 본 흐름에서 빼내 따로 보관하는 큐(Kafka에서는 토픽)다. 실패한 메시지 하나가 같은 자리에서 재시도되며 뒤의 정상 메시지를 막는 일을 막고, 버리지 않고 남겨 두었다가 원인을 고친 뒤 다시 처리할 수 있게 한다. 메시지 유실 방지 수단 중 하나다.

## 자세히
### 왜 필요한가
Consumer가 메시지를 처리하다 예외가 나면 선택지가 셋이다.

| 선택 | 결과 |
|---|---|
| 무시하고 다음으로 진행 | 메시지가 사라진다(유실) |
| 같은 메시지를 계속 재시도 | 형식이 깨진 메시지(poison message) 하나가 파티션 전체를 막는다 |
| 몇 번 재시도 후 DLQ로 보내고 다음으로 진행 | 흐름은 계속되고 실패 메시지는 보존된다 |

### 일반적인 구조
```text
orders 토픽 -> Consumer -> 처리 성공 -> offset 커밋
                   |
                   +-- 실패 -> 재시도(간격을 늘리며 N회)
                                   |
                                   +-- 계속 실패 -> orders.DLQ 토픽 발행 후 offset 커밋
                                                        |
                                                        +-- 알림·모니터링 -> 원인 수정 -> 재처리
```

- Kafka에는 DLQ가 기본 기능으로 없다. Consumer가 별도 토픽(예: `orders.DLT`)에 직접 발행하는 방식으로 구현한다. Spring Kafka는 `DefaultErrorHandler`와 `DeadLetterPublishingRecoverer`, `@RetryableTopic`으로 이 패턴을 제공한다(RabbitMQ·SQS는 DLQ가 브로커 기능이다).
- DLQ 메시지에는 원본 토픽·파티션·offset, 예외 메시지, 재시도 횟수를 헤더로 남긴다. 그래야 원인을 추적한다.

### 재시도해도 되는 실패와 안 되는 실패
- 일시적 실패(네트워크, DB 락 타임아웃): 재시도하면 성공할 수 있다. 간격을 늘려 재시도한다.
- 영구적 실패(역직렬화 오류, 검증 실패, 없는 ID 참조): 재시도해도 같다. 바로 DLQ로 보낸다.

### 함께 설계할 것
- **멱등 소비**: 재시도와 재처리는 같은 메시지를 두 번 처리할 수 있다. 처리 이력을 키(eventId)로 기록해 중복을 걸러야 한다.
- **순서**: 실패 메시지를 DLQ로 보내고 다음 메시지를 처리하면 같은 키의 메시지 순서가 뒤바뀔 수 있다. 순서가 중요하면 해당 키 흐름을 멈추는 등 정책을 정한다.
- **운영**: DLQ는 쌓이기만 하면 무의미하다. 누적 건수 알림, 확인 담당자, 재처리 절차(수동 재발행 도구)를 정한다.

## 이 프로젝트에서는
- 트랙 D가 멱등 소비와 DLQ를 맡는다(`docs/sa-review/01-sa-1st-review.md`의 Kafka 공통 모듈 분담).
- 같은 문서 M7: Outbox·멱등·DLQ가 이름만 묶여 있으므로 재시도 횟수·간격, DLQ 확인 담당자, 재처리 방법을 정해야 한다. 발제 요구는 유실 방지 "1개 이상의 기능 구현"이므로 필요한 최소 경로부터 검증한다.

## 면접 포인트
- DLQ를 왜 쓰는가: poison message가 소비를 막지 않게 하고, 유실 없이 실패 건을 보존·재처리하기 위해서다.
- 재시도와 DLQ의 관계: 일시적 실패는 재시도, 한도를 넘거나 영구적 실패는 DLQ.
- DLQ를 쓰면 생기는 문제: 중복 처리(멱등성 필요), 순서 깨짐, DLQ 방치.
- Outbox(발행 측 유실 방지)와 DLQ(소비 측 실패 보존)는 유실을 막는 위치가 다르다.
