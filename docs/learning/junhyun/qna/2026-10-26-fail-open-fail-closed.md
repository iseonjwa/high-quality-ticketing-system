# fail open과 fail closed는 무엇이고 어떻게 고르는가

## 질문
fail open fail closed가 뭐야??

## 짧은 답
보호·검사 역할을 하는 구성요소(인증, rate limiter, 재고 확인 등)가 고장 났을 때 어느 쪽으로 기울어질지의 정책이다. fail open은 검사를 못 하니 일단 통과시키는 것이고, fail closed는 검사를 못 하니 일단 막는 것이다. 가용성을 우선하면 open, 안전·정합성을 우선하면 closed다.

## 자세히
### 비유
출입 통제 시스템이 정전됐을 때 문이 열리면 fail open(화재 시 대피에 유리하지만 보안은 뚫림), 잠기면 fail closed(보안에 유리하지만 사람이 갇힘)다.

### 비교
| | fail open | fail closed |
|---|---|---|
| 장애 시 동작 | 검사 없이 통과 | 요청 거부 |
| 우선하는 가치 | 가용성 | 안전, 정합성 |
| 위험 | 막아야 할 것이 통과한다(중복 결제, 과다 트래픽, 무인증 접근) | 정상 사용자까지 막힌다(서비스 중단) |
| 어울리는 곳 | 부가 기능, 추천, 캐시, 로그 | 인증·인가, 결제, 재고·좌석 확정 |

### 선택 기준
- 잘못 통과시켰을 때의 피해가 큰가, 잘못 막았을 때의 피해가 큰가를 비교한다. 돈, 보안, 데이터 정합성이 걸리면 closed 쪽이다.
- 한 시스템 안에서도 구성요소마다 다르게 고른다. 전체를 하나로 통일하지 않는다.
- 검사기 자체가 단일 장애점이 되지 않도록, closed를 고르면 검사기의 이중화와 타임아웃을 함께 설계한다.
- 중간 정책도 있다. 장애 시 허용량을 낮춰 일부만 통과시키는 degraded 모드, 로컬 캐시나 로컬 카운터로 대체 판단하는 방식이다.

### 예시
- Rate limiter가 쓰는 Redis가 죽었을 때: open이면 제한 없이 통과해 뒷단이 폭주 트래픽을 그대로 받는다. closed면 전 요청이 거부된다. 실무에서는 대개 로컬 제한으로 낮춘 open을 쓴다.
- 인증 서버가 응답이 없을 때: closed가 기본이다. open이면 무인증 접근이 열린다.
- 보안 장비(방화벽, WAF)와 가용성이 우선인 CDN 앞단은 서로 기본값이 다르다.

## 이 프로젝트에서는
설계 문서에 아직 이 정책이 명시된 곳은 없다. 다음 지점에서 정해야 한다.
- 대기열·좌석 선점의 Redis 장애: 좌석 선점은 정합성이 우선이므로 closed(선점 거부)가 자연스럽다. DB 조건부 UPDATE가 2차 방어이므로 Redis 판정을 건너뛰는 open도 가능은 하지만, 폭주 트래픽이 DB로 직행한다.
- 대기열 입장 속도 제어(Redis 전역 카운터) 장애: 정책에 따라 결과가 크게 달라지므로 SA에서 결정하고 `docs/decisions/`에 기록한다.
- 결제·예매 상태 확인에 실패했을 때: 확정하지 않는 closed가 기본이다. PG 타임아웃을 실패로 단정하지 않는 논의(`docs/sa-review/02-pg-timeout-handling.md`)와 같은 맥락이다.

## 면접 포인트
- fail open과 fail closed의 차이와 각각을 고르는 기준: 오작동의 비용(보안·돈 대 가용성)을 비교해 구성요소별로 고른다.
- "Redis 기반 rate limiter가 죽으면 어떻게 하나": 기본 답은 정책을 명시하고, 가용성이 중요하면 로컬 제한으로 낮춘 fail open, 안전이 중요하면 closed로 답한다.
- closed를 고를 때 따라오는 설계: 검사기 이중화, 타임아웃, 서킷브레이커.

## 참고
- 일반 개념 설명이다. 특정 버전이나 제품 문서에 의존하지 않는다.
