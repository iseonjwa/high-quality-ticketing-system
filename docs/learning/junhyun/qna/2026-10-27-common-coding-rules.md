# 가독성과 학습을 위해 공통 코드 작성 규칙을 어떻게 보완하면 좋은가

## 질문

> 좋아 다른 세션에서 이것저것 많이 결정했는데, 더 넣으면 좋은 공통 규칙이 있을까? 예를 들어 코드를 더 간결하고 읽기좋게 작성한다던지, 이전처럼 보면 좋을 부분에 Note: 주석을 넣는다던지...

## 짧은 답

읽는 흐름, 책임 분리, 이름, 기존 공통 계약, 선택적인 `Note:`, 실패 의미, 코드와 설명의 일치를 공통 기준으로 보완했다.
사용자가 7개 추천을 모두 반영하되 `Note:`를 과도하게 쓰지 말라고 요청했다.
현재 규칙의 정본과 예시는 [코드 작성 가이드](../../../guides/code-style.md)에 있다. 이 노트는 제안과 수용의 맥락을 보존한다.

## 자세히

### 제안과 수용

처음에는 코드 가독성과 학습용 주석에 대한 7개 규칙을 추천했다. 이후 사용자가 다음과 같이 수용했다.

> 응ㅇ 이거 전부 넣어줘! Notes 를 너무 과도하게 남발하지 말도록 하고!

기존 계층·공통 계약과 필요한 실패 처리를 보존하면서 흐름을 읽기 쉽게 만드는 것이 목적이다. 메서드 줄 수나 특정 문법의 사용 횟수를 일률적인 목표로 정하지 않는다.
수용한 규칙과 주석 예시는 코드 작성 가이드로 옮겨 한 곳에서 관리한다. [AI 판단 기록](../../../ai-judgments/junhyun/2026-10-27-common-code-style-rules.md)에 수용 범위와 사용자 원문을 남겼다.

### 주석을 많이 쓰는 것과 학습을 돕는 것은 다르다

학습용 주석은 적용 지점에서 선택 이유와 실수하기 쉬운 전제를 떠올리게 해야 한다. 모든 메서드에 설명을 붙이면 중요한 정보가 묻히고 변경 때 맞춰야 할 설명도 늘어난다.
현재 [AuthService](../../../../user-service/src/main/java/iseonjwa/user/application/AuthService.java)의 로그인 실패 기록 트랜잭션 경계, Redis 폐기 순서 같은 설명이 참고할 만한 사례다.
자명한 코드에는 `Note:`가 없어도 되며, 상세 원리는 학습 노트·ADR로 연결한다. `Note:`·Javadoc·`TODO:`의 구분과 남발 방지 기준은 정본 가이드에서 확인한다.

## 이 프로젝트에서는

[AGENTS.md](../../../../AGENTS.md)는 주석의 한국어 평서체와 팀 설계 준수 등을 정한다. [문서 작성 가이드](../../../guides/writing.md)는 사실 기반·간결한 문서를, [품질 기준](../../../agents/quality-gates.md)은 테스트·실행 검증과 최소 구현을 다룬다.
사용자 요청으로 `AGENTS.md`에 핵심 원칙과 코드 작성 시 읽을 문서를 추가했다. 문서 지도와 작성 가이드에도 정본 링크를 연결했다.

최신 [ADR 0008](../../../decisions/0008-internal-trust-and-auth-design.md)은 SA의 Gateway 인증·헤더 전달·HS256을 유지하고, 내부 경로 차단·역할 인가 공통화·포트 공개 검사 적용을 기록한다.
따라서 코드 작성 규칙의 예시도 이 현재 계약을 기준으로 한다. 이전에 검토하고 철회한 서비스 직접 JWT 검증을 현재 구현으로 설명하지 않는다.

이번 변경은 코드 작성 규칙과 연결 문서에 한정한다. 인증 코드나 기존 설계 결정은 변경하지 않았다.

## 면접 포인트

- 간결한 코드와 짧은 코드는 어떻게 다른가: 필요한 검증·실패 처리를 보존하면서 흐름과 이름이 명확한 코드를 목표로 한다. 한 줄로 압축한 표현이 더 읽기 어려울 수도 있다.
- 주석을 언제 쓰는가: 코드에서 드러나는 동작보다 선택 이유, 안전성의 전제, 프레임워크 동작처럼 코드만으로 알기 어려운 맥락을 설명한다.

## 참고

- [Google Java Style 7.3.1](https://google.github.io/styleguide/javaguide.html#s7.3.1-javadoc-exception-self-explanatory): 단순하고 명백한 멤버는 자명한 설명을 반복할 필요가 없지만 필요한 정보는 생략하지 않는다.
- [Google Java Style 4.8.6](https://google.github.io/styleguide/javaguide.html#s4.8.6-comments): 구현 주석·Javadoc·TODO의 구분과 추적 가능한 TODO.
- Google의 포맷·언어별 문법 규칙 전체를 도입하는 제안은 아니다. 예시는 프로젝트의 Java 21과 기존 한국어 문서 규칙을 따른다.
