# 서비스가 Access JWT를 직접 검증할 때 HS256과 RS256은 무엇이 다른가

## 질문

> 일단 C로 했는데, D2: Access 토큰 서명 방식은요?
> 1. RS256 비대칭: User만 개인키를 갖고 Gateway·서비스는 공개키로 검증한다. 서명은 로그인 때만, 검증은 매 요청이라 특성이 맞다. 개인키만 비밀값이다.
> 2. HS256 유지: 구현은 단순하지만 검증하는 모든 서비스가 토큰을 위조할 수 있다. C와 같이 쓰면 이점이 줄어든다.
> 이것들 차이도 알려줘

후속 질문:

> 그리고 HS256과 RS256에서 말하는 공유키, 개인키는 서비스들 사이에서 공유된다는거지? 아예 외부로 공개되는게아니라?

D1의 C 선택은 사용자가 전달한 사실이다. D2의 선택지에 표시된 커서는 최종 선택으로 해석하지 않는다.

## 짧은 답

HS256은 발급과 검증에 같은 비밀키를 사용하므로 키를 받은 모든 검증 서비스가 토큰을 만들 수도 있다.
RS256은 User에 개인키를 두고 나머지 서비스에는 공개키를 배포해 발급 권한과 검증 권한을 분리한다.
HS256은 계산과 초기 구현이 단순하고, RS256은 키 운영과 계산 비용을 더 들여 다른 서비스의 침해가 사용자 토큰 발급 권한으로 번지는 것을 줄인다.
C처럼 여러 서비스가 검증한다면 AI는 Access에 RS256을 제안한다. 사용자는 아직 D2를 선택하지 않았다.

## 자세히

### HS256: 공유 비밀키로 생성하고 검증한다

HS256은 HMAC-SHA256을 사용한다. 검증자는 같은 키와 토큰 내용으로 MAC을 다시 계산해 수신한 값과 비교한다.
따라서 정상 서비스 코드에 발급 기능을 작성하지 않았더라도, 키를 읽을 수 있는 주체는 다른 프로그램으로 유효한 토큰을 만들 수 있다.

| 주체 | 보유한 키 | 가능한 일 |
|---|---|---|
| User | Access 공유 비밀키 | 토큰 발급·검증 |
| Gateway | 같은 Access 공유 비밀키 | 토큰 검증·생성 |
| Reservation·Payment | 같은 Access 공유 비밀키 | 토큰 검증·생성 |

예를 들어 공격자가 Payment에서 공유 Access 키를 읽으면, 임의의 `sub`와 `role=ADMIN`을 넣은 토큰을 만들 수 있다.
다른 검증 서비스는 같은 키로 만든 유효한 MAC만 보고 User가 만든 토큰과 구별할 수 없다.

HS256을 올바르게 사용하려면 충분히 무작위인 비밀키가 필요하다. RFC 7518은 HS256에 256비트 이상의 키를 요구한다.
키 길이 검사만 통과한 사람이 정한 문자열이 충분한 무작위성을 갖는다고 볼 수는 없다.

### RS256: 개인키로 서명하고 공개키로 검증한다

RS256은 RSA와 SHA-256을 사용하는 전자서명이다. RFC 7518은 RSA 키를 2048비트 이상으로 정한다.
User는 개인키로 서명하고 Gateway와 서비스는 그 개인키에 대응하는 공개키로 검증한다.

| 주체 | 보유한 키 | 가능한 일 |
|---|---|---|
| User | 개인키·공개키 | 토큰 발급·검증 |
| Gateway | 공개키 | 토큰 검증 |
| Reservation·Payment | 공개키 | 토큰 검증 |

Payment의 공개키가 노출되어도 그 키만으로 다른 사용자 토큰에 유효한 서명을 만들 수 없다.
User의 개인키가 침해되면 토큰 위조가 가능하고, 다른 서비스가 탈취한 기존 유효 토큰을 재사용하는 문제도 남는다.
보호 대상 서비스 자체가 침해된 경우까지 그 서비스의 서명 검증 코드로 해결할 수는 없다.

공개키는 비밀로 숨길 필요가 없지만 신뢰하는 경로로 배포해야 한다. 공격자의 공개키로 바뀌면 공격자가 만든 토큰을 신뢰하게 된다.
개인키는 User에만 주입하고 모든 서비스가 읽는 공용 설정·이미지·저장소에 넣지 않는다. 공개키 배포와 개인키 배포의 접근 범위를 분리한다.

### 내부 공유와 외부 공개를 구분한다

| 키 | 이 프로젝트에서 보유할 주체 | 외부 공개 |
|---|---|---|
| HS256의 공유 비밀키 | User와 Access를 검증하는 Gateway·서비스 | 금지 |
| RS256의 개인키 | User 발급 주체 | 금지. 다른 업무 서비스에도 배포하지 않는다 |
| RS256의 공개키 | Gateway·서비스 등 검증 주체 | 가능. 서명을 만들 능력을 주지는 않는다 |

HS256의 "공유"는 비밀키를 발급·검증 서비스 사이에서 나누어 갖는다는 뜻이다. 브라우저나 일반 사용자에게 공개한다는 뜻이 아니다.
RS256에서 서비스 사이에 배포하는 것은 공개키다. 개인키까지 모든 검증 서비스에 공유하면 발급 권한을 분리하는 목적을 잃는다.

공개키는 외부에서 조회할 수 있는 JWKS URL로 제공할 수도 있다. OpenID Connect Discovery는 공개 JWK Set에 개인키나 대칭 비밀키 값을 포함하지 않도록 정한다.
이 설명이 현재 프로젝트에 공개 JWKS API를 구현했다는 뜻은 아니다. 파일·설정으로 공개키를 배포하는 선택도 가능하다.
일반 클라이언트는 발급받은 Access 토큰을 제출하며, API 호출을 위해 HS256 비밀키나 RS256 개인키를 받을 필요가 없다.

### 성능과 운영의 절충

| 기준 | HS256 | RS256 |
|---|---|---|
| 발급·검증 권한 | 같은 키를 가진 주체가 모두 보유 | 개인키 보유자만 발급 |
| 계산 비용 | 일반적으로 상대적으로 작다 | 일반적으로 HMAC보다 크다 |
| 서명 크기 | 32바이트 | RSA 2048비트 키라면 256바이트 |
| 초기 구현 | 현재 코드의 방식 유지 | 키 쌍, 발급기·검증기 변경 필요 |
| 키 운영 | 모든 검증자에게 비밀 배포·교체 | 개인키 보호와 공개키 버전·배포 관리 |
| 검증 서비스의 키 노출 | Access 토큰 위조로 확산 가능 | 공개키만으로 Access 토큰 위조 불가 |

서명 크기는 JWT의 Base64url 인코딩 전 값이다. 전체 토큰 크기는 payload 등에도 영향을 받는다.
계산 비용은 알고리즘 구조에 따른 일반적인 비교이며, 현재 코드·장비에서 HS256과 RS256의 비용을 측정하지 않았다.
RS256의 RSA 검증이 RSA 서명보다 일반적으로 가볍다는 설명은 RS256 검증이 HS256 검증보다 빠르다는 뜻이 아니다.

선택지의 "서명은 로그인 때만"은 단순화한 표현이다. Access 토큰을 재발급할 때도 서명한다.
C에서는 발급할 때 서명하고, 보호 API 요청을 받을 때 Gateway와 서비스가 검증한다. User가 요청마다 새로 서명하는 구조는 아니다.
두 알고리즘 모두 검증 키를 로컬에 두면 매 요청마다 User에 확인할 필요가 없다.

키를 교체하려면 HS256과 RS256 모두 이전 토큰을 어떻게 처리할지 정해야 한다. RS256에서는 새 개인키로 발급하면서 필요에 따라 이전 공개키도 일정 기간 유지할 수 있다.
토큰의 `kid`로 신뢰하는 키 목록에서 검증 키를 찾는 방식을 사용할 수 있다. 키 침해로 긴급 폐기하는 경우는 일반적인 무중단 교체와 구분한다.

### C와 HS256을 함께 쓰면 어떤 이점이 남는가

C와 HS256도 키를 모르는 외부·내부 호출자의 위조 헤더를 거절할 수 있다. C의 방어 효과가 모두 없어지는 것은 아니다.
다만 키를 가진 다른 서비스를 침해한 공격자는 사용자 신원까지 위조할 수 있다. 검증 서비스와 발급자의 권한을 나누려는 목표에는 한계가 있다.

RS256에서는 서비스에 검증에 필요한 공개키만 배포할 수 있다. 여러 서비스가 검증하는 C 구조에서 AI가 RS256을 제안하는 이유다.
둘 다 JWT 내용의 무결성과 발급 근거를 확인하는 방식이며 payload를 비밀로 숨기는 암호화는 아니다.
로그아웃·탈퇴·역할 변경의 반영 시점은 여전히 폐기·상태 재조회 정책으로 정해야 한다.

## 이 프로젝트에서는

확인한 로컬 코드의 [TokenDecoders](../../../../common-auth/src/main/java/iseonjwa/common/auth/TokenDecoders.java)는 `withSecretKey`와 HS256을 사용한다. [JwtTokens](../../../../user-service/src/main/java/iseonjwa/user/infrastructure/security/JwtTokens.java)도 HS256으로 발급한다.
Access와 Refresh 키는 이미 구분한다. 이번 D2 질문은 Access 범위이며 Refresh·입장·결제 토큰의 변경까지 수용한 것으로 보지 않는다.

RS256을 선택하면 Access 발급을 개인키 기반으로 바꾸고 Gateway·서비스의 Access 검증을 공개키 기반으로 바꾸어야 한다.
기존 `iss`·시간·audience·토큰 종류·필수 claim 검증은 계속 적용하고 허용 알고리즘을 명시해야 한다. 공개키만 달면 검증 정책이 끝나는 것은 아니다.
Spring Security는 `NimbusJwtDecoder.withPublicKey(...)`를 제공하므로 RSA 연산을 직접 구현할 필요는 없다.

D1의 사용자 선택은 [판단 기록](../../../ai-judgments/junhyun/2026-10-27-service-jwt-verification-choice.md)과 [ADR 0009](../../../decisions/0009-service-access-jwt-verification.md)에 남긴다. 팀 합의 상태는 미확인이다.
D2는 설명·비교 중이며 RS256 추천은 AI 제안이다. 이 질문에서는 인증 코드나 키를 변경하지 않았다.

## 면접 포인트

- HS256에서 검증자가 토큰도 만들 수 있는 이유: 검증 시 원본과 같은 공유 비밀키로 MAC을 계산하므로 유효한 MAC을 생성할 능력도 갖는다.
- MSA에서 RS256을 선택하는 이유: 발급자에게만 개인키를 두고 검증 서비스에는 공개키만 배포해 침해 시 발급 권한의 확산을 줄인다.
- RS256의 비용: HMAC보다 일반적으로 계산과 토큰 크기 부담이 있고 키 쌍·교체 정책이 필요하다. 처리량과 지연 영향은 실제 배포 환경에서 측정해야 한다.
