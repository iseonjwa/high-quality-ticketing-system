## 짧은 답

C는 서비스가 User 발급 Access JWT를 검증하고, B는 Gateway 발급 내부 토큰을 검증한다. 둘 다 서명된 증거에서 사용자 신원을 얻는다.
이전 물류 프로젝트는 Gateway에서 JWT를 검증하고 사용자 상태를 재조회한 뒤, 업무 서비스에 일반 헤더를 전달했다.
신원 전달의 위조 방지와 최신 권한·탈퇴 상태 확인은 별개의 문제다. C나 B에 사용자 상태 재조회를 추가할 수 있다.
첫 답변에서는 C와 비대칭 서명의 조합을 우선 제안했다. 후속 비교에서는 이중 검증이 필수 조건이 아니며, 현재 MVP의 내부 신뢰 범위와 운영 비용을 함께 선택해야 한다고 보완했다.
사용자·팀의 설계 결정이나 구현 완료를 뜻하지 않는다.

## 자세히

### 인증과 인가를 나눈다

인증은 요청의 사용자 신원을 확인한다. JWT 서명 검증으로 신뢰하는 발급자가 그 신원을 담아 발급한 토큰인지 확인한다.
Bearer 토큰은 보유자가 사용할 수 있으므로, 탈취한 유효 토큰의 재사용까지 서명 검증만으로 막지는 못한다.

인가는 확인한 사용자가 요청한 행동을 해도 되는지 판단한다. ADMIN 여부뿐 아니라 예매 소유자와 요청 사용자가 같은지도 서비스에서 확인해야 한다.
JWT의 역할은 발급 당시의 값이므로, 서명 검증 성공이 현재 역할·탈퇴·로그아웃 상태까지 보증하지는 않는다.

### C. 서비스가 사용자 JWT를 직접 검증한다

1. User 서비스가 로그인 성공 시 Access JWT를 발급한다.
2. 클라이언트가 `Authorization: Bearer <Access JWT>`로 Gateway에 요청한다.
3. Gateway가 토큰을 검증하고 정책에 따라 블랙리스트 등을 확인한 뒤, 원본 Access JWT를 서비스에 전달한다.
4. 서비스가 서명, 허용 알고리즘, `iss`(발급자), `exp`·`nbf`(유효 시간), `aud`(허용 대상), 토큰 종류와 필수 claim을 검증한다.
5. 서비스가 검증 결과의 `sub`로 사용자 신원을 만들고, 해당 API의 권한·소유권을 판단한다.

서비스는 User의 서명을 신뢰한다. `X-User-Id`나 `X-User-Role` 값만 보낸 요청은 인증 근거가 되지 않는다.
HTTP 헤더 자체를 없애는 방식은 아니다. `Authorization` 헤더로 운반한 서명된 토큰을 검증하는 방식이다.

검증 키를 로컬에 가지고 있으면 서명·claim 검증마다 User 서비스에 호출할 필요가 없다. JWKS를 사용하면 초기 키 조회나 키 교체 때 통신이 생길 수 있다.
서비스에도 검증 CPU 비용이 생기므로 실제 부하로 확인해야 한다. 이 질문에서 성능을 측정하지는 않았다.

HS256은 발급자와 검증자가 같은 비밀키를 가진다. 검증 서비스가 키를 가지면 임의 토큰을 만들 능력도 생긴다.
RS256 같은 비대칭 서명에서는 User만 개인키를 가지고, Gateway와 서비스에는 검증용 공개키를 배포할 수 있다.
공개키만 가진 서비스는 임의 사용자 토큰을 새로 서명할 수 없다. 탈취한 기존 토큰의 재사용은 별도 문제다.

### B. Gateway가 서명한 내부 신원을 검증한다

1. 클라이언트가 User 발급 Access JWT로 Gateway에 요청한다.
2. Gateway가 Access JWT와 필요한 정책을 검증한다.
3. Gateway가 검증한 사용자 신원으로 수명이 짧은 내부 토큰을 새로 서명해 서비스에 전달한다.
4. 서비스가 Gateway의 서명, 내부 발급자, 자기 서비스에 맞는 audience, 만료와 내부 토큰 종류를 검증한다.
5. 서비스가 내부 토큰에서 신원을 만들고 해당 API의 권한·소유권을 판단한다.

서비스는 Gateway의 서명을 신뢰한다. 예를 들어 내부 토큰에 `iss=gateway`, `sub=42`, `aud=reservation-service`를 넣을 수 있다.
내부 토큰은 원본 Access 토큰의 남은 유효 시간을 넘지 않도록 제한하고, 외부에서 보내 온 내부 신원 헤더는 Gateway가 제거한 뒤 새로 설정해야 한다.
서비스도 일반 `X-User-*` 값 대신 검증한 내부 토큰의 claim을 신원 근거로 사용해야 한다.

사용자 토큰 형식을 내부 서비스와 분리하거나 서비스별 권한 범위를 줄이려는 경우에 유용하다. 범위를 실제로 줄이는 claim과 검증 정책이 있어야 이점이 생긴다.
반면 내부 토큰 규격, 발급 코드, 키 배포·교체, 만료 정책을 추가로 관리한다. Gateway에는 내부 토큰 서명 비용이 생긴다.

Gateway가 내부 토큰의 발급자이므로 Gateway의 서명 권한이 침해되면 내부 신원도 위조될 수 있다.
내부 검증 키로 HMAC 비밀키를 공유하면 검증 서비스도 내부 토큰을 만들 수 있으므로, 이 경우에도 키의 신뢰 범위를 정해야 한다.
수명이 짧아도 만료 전 탈취 토큰의 재사용이 자동으로 차단되지는 않는다.

### 이전 물류 프로젝트의 실제 흐름

2026-10-27에 `/Users/alloy/Desktop/bootcamp/logistics-management`의 로컬 소스를 읽어 확인했다. 실행 환경에서의 동작은 이번에 검증하지 않았다.

1. `UserHeaderSanitizingFilter`가 외부 요청의 `X-User-*` 헤더를 제거한다.
2. Gateway의 Spring Security와 JWT decoder가 JWT 서명·만료·필수 claim을 검증한다.
3. `UserVerifyingJwtConverter`가 검증된 JWT의 `sub`로 사용자를 조회한다. 저장된 역할과 JWT 역할을 비교하고, 조회되지 않거나 일치하지 않으면 거절한다.
4. 사용자 조회는 `UserServiceClient`의 `/internal/users/{userId}` 호출을 사용한다. 캐시 종류는 설정에 따라 local 또는 Redis이며, `AuthProperties`의 기본 TTL은 60초다.
5. `UserHeaderInjectionFilter`가 확인한 사용자 정보로 `X-User-*` 헤더를 다시 넣어 업무 서비스로 전달한다.

따라서 JWT 인증 뒤에 사용자 상태 재확인을 더한 구조다. 단순히 클라이언트가 제출한 `userId`로 권한만 조회한 구조는 아니다.
다만 Gateway와 업무 서비스 사이의 신원 전달은 일반 헤더이므로, 그 구간은 네트워크 격리 등으로 Gateway를 거치지 않은 요청을 막아야 한다.

권한 재조회는 `X-User-Role`만 위조하는 공격과, 탈퇴·역할 변경 뒤에도 토큰이 남아 있는 문제에 대응한다.
그러나 공격자가 `X-User-Id`를 관리자 ID로 바꾸어 서비스에 직접 도달할 수 있다면, 그 ID의 실제 역할을 조회해도 호출자가 그 관리자인지는 증명되지 않는다.
조회할 사용자 ID는 검증한 토큰 또는 인증된 전달 경로에서 얻어야 한다.

캐시된 조회는 TTL이나 무효화 정책만큼 변경 반영이 늦어질 수 있다. 캐시 미적중 시에는 User 서비스 통신 지연과 장애에 영향을 받는다.
이전 프로젝트의 사용자 ID 기반 상태 조회를 표준 OAuth 토큰 introspection과 동일시하지 않는다. RFC 7662의 introspection은 토큰 자체를 전달해 활성 상태와 메타데이터를 조회하는 프로토콜이다.

### 두 질문은 독립적으로 결정한다

| 질문 | 선택 예 |
|---|---|
| 서비스가 받은 사용자 신원이 진짜라는 근거는 무엇인가 | User 서명의 Access JWT(C), Gateway 서명의 내부 토큰(B) |
| 역할 변경·탈퇴·로그아웃을 언제 반영할 것인가 | 짧은 Access 유효 시간, 블랙리스트, 상태 재조회와 캐시 무효화 |
| 해당 예매에 접근할 수 있는가 | 서비스가 검증한 사용자 ID와 예매 소유자를 비교 |

C와 B 어느 쪽도 상태 재조회를 금지하지 않는다. B도 사용자 상태를 별도로 조회하지 않으면 오래된 원본 토큰의 역할을 내부 토큰에 복사할 수 있다.

### 두 번 검증하는 비용과 얻는 방어

MSA라고 JWT를 반드시 두 번 검증해야 하는 것은 아니다. Gateway에서만 사용자 인증을 수행하는 설계도 가능하다.
대신 서비스로 전달하는 신원의 무결성과 호출 경로를 다른 수단으로 보호해야 한다. NIST SP 800-204 4.1도 Gateway에 인증을 모으는 선택을 설명하면서 우회 연결을 막는 상호 인증 등의 보완을 함께 다룬다.

같은 알고리즘과 구현으로 비교하면 C에서는 JWT 검증 연산 횟수가 늘어난다. HTTP 처리, DB 쿼리, 업무 처리 전체가 두 배가 되는 것은 아니다.
두 번째 검증에는 JWT 파싱, 서명·claim 검증, 객체 할당 비용이 생긴다. 공개키를 로컬에 두면 검증 때문에 매 요청마다 인증 서버를 호출할 필요는 없다.
현재 제안은 Gateway의 블랙리스트 확인을 유지하고 서비스에는 로컬 JWT 검증을 추가하는 것이며, Redis 조회까지 두 번 하는 구성은 아니다.

추가 CPU 수요는 다음처럼 추산할 수 있다. 여러 서비스로 요청이 분기되면 추가 검증이 일어나는 서비스 요청을 합산한다.

```text
추가 CPU 코어 수 ≈ 추가 검증 횟수/초 × 검증 1회의 평균 CPU 시간(초)
```

예를 들어 서비스에 초당 10,000건이 도달하고 검증 1회의 CPU 시간이 0.05ms라면 추가 수요는 약 0.5코어다.
같은 트래픽에서 0.5ms라면 약 5코어다. 두 시간은 비용을 설명하기 위한 가정이며 현재 코드·장비의 측정값이 아니다.
실제 결과는 서명 알고리즘, 키 크기, JVM·라이브러리, 토큰 크기, 할당과 GC, 실행 장비에 따라 달라진다.

개별 검증 시간이 짧아도 CPU가 포화되면 요청 대기와 p95·p99 응답 시간이 크게 늘 수 있다. 따라서 추가 지연과 전체 처리량을 함께 확인해야 한다.
현재 HS256에서 RS256으로 바꾸는 비용과, 같은 토큰의 검증 위치를 늘리는 비용은 구분해서 측정해야 한다.

| 방식 | Gateway에서 할 일 | 서비스에서 할 일 | 얻는 것과 비용 |
|---|---|---|---|
| A. Gateway만 사용자 JWT 검증 | 사용자 JWT 검증·기존 정책 | 전달된 신원을 전제로 도메인 인가 | 토큰 검증과 키 배포가 적다. 내부 헤더 위조에 대한 방어는 호출 경로 보호에 의존한다 |
| C. Gateway와 서비스가 사용자 JWT 검증 | 사용자 JWT 검증·기존 정책 | 사용자 JWT 검증·도메인 인가 | 서비스에서 신원 위조를 거절한다. 서비스별 CPU·검증 설정·키 관리가 늘어난다 |
| B. Gateway 내부 토큰 | 사용자 JWT 검증·기존 정책·내부 토큰 서명 | 내부 토큰 검증·도메인 인가 | 내부 신원 형식과 범위를 분리한다. 추가 서명, 토큰 규격, 키 운영이 필요하다 |

B는 검증을 한 번으로 줄이는 대안이 아니다. 원본 검증, 내부 서명, 내부 검증이 필요하다.
어느 방식의 실제 CPU 비용이 큰지는 사용하는 알고리즘과 구현에 따라 다르므로, 연산 횟수만으로 단정하지 않는다.

A가 합리적이려면 내부 호출 주체를 어느 범위까지 신뢰할지 명시해야 한다. 외부 서비스 포트 비공개와 사용자 헤더 제거는 기본 조건이다.
다만 외부 포트가 닫혀 있어도 같은 내부망의 다른 서비스나 SSRF를 통한 연결 가능성은 남을 수 있다.
내부 구성원까지 신뢰하지 않으려면 네트워크 정책이나 mTLS 같은 호출 주체 인증으로 접근을 제한하거나 서비스에서 토큰을 검증해야 한다. 이런 대안에도 설정·운영 비용이 든다.

C는 유효한 서명 토큰이 없는 내부 요청의 사용자 사칭을 방어한다. 서명을 검증할 뿐, 탈취된 유효 토큰의 재사용이나 Gateway에만 둔 폐기·입장 정책을 모두 막지는 않는다.
공개키만 가진 다른 서비스는 사용자 토큰을 새로 위조할 수 없지만, 보호 대상 서비스 자체가 침해된 경우까지 해당 서비스의 검증 코드로 해결할 수는 없다.

Gateway의 JWT 검증을 제거하고 서비스에서만 검증하는 구조도 이론적으로 가능하다. 그러나 Gateway가 검증된 사용자 ID로 블랙리스트나 사용자별 정책을 수행해야 한다면 그대로 적용할 수 없다.
검증하지 않은 JWT의 사용자 ID를 신뢰해 요청 제한이나 권한을 판단해서는 안 된다.

현재 장비에서의 JWT 벤치마크와 A/C 부하 비교는 실행하지 않았다. 비교한다면 같은 알고리즘·키·트래픽·업무 흐름에서 서비스 검증 유무만 바꾸고, CPU·GC·처리량·p95·p99와 위조 헤더 직접 호출의 거절 여부를 함께 확인한다.

### 선택 근거의 기술적 타당성과 범위

"헤더 위조를 막는다"는 C의 설계 근거로 성립한다. 서비스가 일반 사용자 헤더를 무시하고 서명·claim 검증을 통과한 JWT에서만 신원을 구성해야 한다.
기존 Gateway도 외부의 사용자 헤더를 제거하므로, Gateway를 정상 통과하는 외부 헤더 위조에는 이미 방어가 있다.
C의 추가 효과는 Gateway를 우회해 서비스에 도달한 요청이나 Gateway가 전달하는 신원 값만으로 사칭하는 경우에도 서비스가 증거를 검사하는 것이다.

"Gateway를 전적으로 신뢰하지 않는다"는 신원 전달에 대한 신뢰를 줄인다는 범위에서 타당하다. Gateway의 모든 행위를 독립적으로 검증하거나 모든 침해를 막는다는 뜻은 아니다.
C와 HS256을 조합하면 Gateway도 Access 비밀키를 가져서 새 사용자 토큰을 위조할 수 있다.
C와 RS256을 조합하고 User만 개인키를 갖게 하면, 공개키만 가진 Gateway는 임의 사용자 토큰을 새로 서명할 수 없다.

RS256이어도 Gateway가 이미 관찰한 유효 Bearer 토큰을 재사용하거나 Gateway에만 둔 정책을 생략하는 문제는 남는다.
Bearer 토큰은 서명 키 없이도 보유한 토큰을 사용할 수 있는 방식이므로, 서명 키의 보호와 토큰의 보호를 나누어 생각한다.
이 검토는 사용자의 선택 의도가 기술적으로 어떤 조건에서 성립하는지 확인한 것이다. 현재 시스템의 방어 효과를 실행으로 입증하거나 비용 대비 최적성을 측정한 결과는 아니다.

AI가 제안하는 설명 문장은 다음과 같다. 사용자가 이 문장까지 채택한 것으로 기록하지 않는다.

> Gateway가 전달한 사용자 헤더만으로 신원을 신뢰하지 않고, 각 서비스가 발급자의 JWT를 직접 검증해 Gateway 우회와 내부 헤더 위조에 대비한다. 발급 권한까지 User에 한정하려면 비대칭 서명을 사용한다.

## 이 프로젝트에서는

현재 [SA MASTER 7-2](../../../core/SA%20MASTER.md)는 Gateway가 검증한 `X-User-Id`·`X-User-Role` 전달을 사용한다. 9-2는 서비스 포트를 내부 전용으로 두는 네트워크 정책을 전제로 한다.
[GatewayIdentityFilter](../../../../common-web/src/main/java/iseonjwa/common/web/GatewayIdentityFilter.java)는 헤더 형식을 확인해 요청 속성으로 옮기며, JWT 서명을 직접 검증하지 않는다.

[TokenDecoders](../../../../common-auth/src/main/java/iseonjwa/common/auth/TokenDecoders.java)는 이미 서명·발급자·유효 시간·audience·토큰 종류 등의 검증을 모아 둔다. 현재 생성 코드는 HS256에 고정되어 있다.
C의 claim 검증 규칙은 재사용할 수 있지만, RS256을 적용하려면 공개키 기반 decoder와 개인키 기반 발급 코드, 키 설정을 변경해야 한다.
보호 API에서 인증을 필수로 요구하고, 검증 결과로 신원과 권한을 구성하는 서비스 측 처리도 필요하다.

첫 답변의 AI 제안은 C와 비대칭 서명을 우선 검토하는 것이었다. 추가 내부 토큰 규격 없이 서비스가 발급자의 서명을 확인할 수 있기 때문이다.
HS256으로도 일반 헤더 위조에 대한 방어는 생기지만, 검증 서비스 전체에 발급 능력을 배포하는 한계가 남는다.
첫 설명 시점의 [ADR 0008](../../../decisions/0008-internal-trust-and-auth-design.md)은 결정 대기 상태였다.
후속 대화에서 사용자는 D1의 C 선택을 전달했다. [판단 기록](../../../ai-judgments/junhyun/2026-10-27-service-jwt-verification-choice.md)과 [ADR 0009](../../../decisions/0009-service-access-jwt-verification.md)에 남겼으며 팀 합의 상태는 미확인이다.
D2는 [HS256·RS256 비교 노트](2026-10-27-jwt-hs256-vs-rs256.md)에서 설명하며 아직 선택 전이다.

후속 질문으로 비용을 비교한 뒤에는 추천의 조건을 구분했다. 팀이 내부 구성원을 신뢰하고 해당 위험을 수용하는 부트캠프 MVP라면 현재 SA의 A를 유지하는 선택도 합리적이다.
내부 구성원의 헤더 위조까지 이번 범위에서 방어하려면 C와 비대칭 서명을 우선 검토한다. 내부 토큰으로 외부·내부 인증을 분리할 요구가 없다면 B를 성능 개선 목적으로 추가할 이유는 작다.
현재 기본 Compose는 업무 서비스 포트를 호스트에 공개하지 않지만, 같은 내부망의 호출자를 Gateway로 제한하는 증거가 되지는 않는다. `compose.local.yml`은 개발용으로 업무 서비스 포트를 loopback에 공개한다.

Gateway는 진입 정책·블랙리스트·요청 제한을 맡고, 서비스는 신원 검증과 자기 도메인의 인가를 맡도록 역할을 나눌 수 있다.
다만 C에서 유효한 사용자 JWT를 가진 직접 호출은 서명 검증을 통과할 수 있다. Gateway에만 둔 블랙리스트·입장 토큰·요청 제한까지 서비스 검증이 대신하지는 않는다.
따라서 서비스 직접 접근 차단을 유지하고, 폐기를 서비스에서도 확인할지 등은 별도 정책으로 결정해야 한다.

## 면접 포인트

- Gateway에서 검증했는데 서비스도 검증하는 이유: Gateway를 거치지 않고 서비스에 도달한 요청이나 내부 헤더 위조에도 사용자 신원을 검증하기 위해서다. 네트워크 방어도 함께 유지한다.
- JWT를 검증하면 권한이 항상 최신인가: 발급 당시 claim의 무결성과 유효 시간을 확인할 뿐이다. 최신 상태가 필요하면 폐기 정책, 상태 재조회, 캐시 무효화 등을 추가한다.
- 검증 서비스에 공개키만 배포하는 이유: 토큰을 검사하는 능력과 새 토큰을 발급하는 능력을 분리하기 위해서다.
- 이중 검증이 필수인가: 필수는 아니다. 내부 신원 전달을 어떤 경로와 주체까지 신뢰할지 정하고, 서비스의 토큰 검증 비용과 호출 경로 보호 비용을 비교한다.
