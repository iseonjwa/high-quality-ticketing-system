# 폴링 간격에 ±20% jitter를 섞는다는 것은 무슨 뜻인가

## 질문
PR #91(대기열 입장 토큰 API 분리, ADR 0031)을 리뷰하다가 "폴링 간격 ±20% jitter"라는 표현이 나왔다. 무슨 말인가.

## 짧은 답
jitter는 "일부러 섞는 무작위 오차"다. 서버가 "3초 뒤에 다시 물어봐"라고 알려주면 클라이언트는 정확히 3초가 아니라 2.4~3.6초(3초 ±20%) 사이의 무작위 값만큼 기다렸다가 요청한다. 같은 시각에 시작한 수만 명의 폴링이 같은 순간에 몰리지 않고 시간 축에 퍼지게 하려는 장치다.

## 자세히
### 문제: 요청이 박자를 맞춰 몰린다
티켓 오픈 순간 수만 명이 거의 동시에 대기열에 들어온다. 모두에게 "다음 폴링은 3초 뒤"라고 응답하면 모두가 3초 뒤에 동시에 요청하고, 그 응답을 받은 뒤 또 3초 뒤에 동시에 요청한다. 평균 요청 수는 같아도 1초 안에 몰리는 파도가 반복되어 서버가 받는 순간 최대치(peak)가 평균보다 훨씬 커진다. 이를 thundering herd(떼 몰림) 또는 동기화된 폴링 문제라고 부른다.

### 해법: 간격에 무작위 오차를 더한다
```java
// 기준 간격 3초, ±20% 무작위
long baseMillis = nextPollAfterSeconds * 1000L;
double factor = 0.8 + ThreadLocalRandom.current().nextDouble() * 0.4; // 0.8 ~ 1.2
long delayMillis = (long) (baseMillis * factor);                      // 2400 ~ 3600ms
```
- ±20%는 "기준값의 80%~120% 중 균등 무작위"라는 뜻이다. 비율은 팀이 정하는 값이고, 너무 작으면 분산이 약하고 너무 크면 순번 갱신 체감이 들쭉날쭉해진다.
- 한 번 흩어진 요청은 다음 주기에도 각자 다른 무작위 값을 더하므로 시간이 갈수록 더 고르게 퍼진다.

### 어디서 섞는가
- 클라이언트가 섞는 방식: 서버는 기준 간격만 주고 클라이언트가 타이머에 jitter를 더한다. 서버 부담이 없다.
- 서버가 섞는 방식: 서버가 응답의 `nextPollAfterSeconds`에 jitter를 더해 내려준다. 클라이언트 구현에 의존하지 않고 서버가 분산을 통제하지만, 초 단위 정수 필드라 ±20%가 거칠게 표현된다(3초면 2~4초 수준).
- 이 PR 문서(SA 9-4 제안 10번)에는 누가 섞는지가 적혀 있지 않다. 리뷰에서 확인할 만한 지점이다.

### 비슷한 개념
- 재시도 backoff에 섞는 jitter(AWS의 "exponential backoff and jitter")도 같은 원리다. 실패한 요청들이 같은 시각에 재시도해 서버를 다시 무너뜨리는 것을 막는다.
- 캐시 TTL에 섞는 jitter도 있다. 같은 시각에 만료되는 키들이 한꺼번에 DB로 몰리는 것(cache stampede)을 막는다.

### jitter가 입장 순서를 해치지 않는가
- 순서는 줄에 선 순간 붙는 순번(seq)이 정한다. `seq <= admitted`이면 `READY`이므로 먼저 선 사람이 항상 먼저 `READY`가 된다. 폴링은 이 상태를 확인할 뿐이라 jitter가 순번을 바꾸지 못한다.
- 남는 영향은 `READY`를 알아채는 시각이다. 순번이 앞선 사람이 간격 끝에 걸려 최대 +20% 늦게 확인하면, 순번이 뒤진 사람이 토큰 API를 먼저 불러 좌석 선택을 몇 초 먼저 시작할 수 있다. 고정 간격 폴링도 사람마다 폴링 위상이 달라 같은 현상이 있고, jitter는 오차 폭을 키울 뿐이다.
- 보장되는 것은 "좌석 선택 자격을 받는 순서"이고, "좌석 선택을 시작하는 정확한 순간"은 아니다.

### READY가 되면 프론트는 계속 요청해야 하는가
- 반복 요청은 `WAITING` 구간의 순번 조회 폴링뿐이다. `READY`를 받으면 폴링을 멈추고 `POST /queue/token`을 한 번 부른다.
- 토큰 요청을 다시 보내는 경우는 응답 유실·새 탭·다른 기기뿐이고, `issued` 기록 덕분에 같은 토큰과 만료 시각을 돌려받는다.
- 폴링 대신 서버 푸시(SSE, WebSocket)로 `READY`를 알릴 수도 있다. 동시 접속자가 많으면 연결 유지 비용이 커서 폴링을 택했다는 것은 문서에서 확인하지 못한 추정이다.

### 상용 티켓팅 서비스는 어떻게 하는가
- 내부 구조(폴링 간격, 토큰, 용량)는 공개되어 있지 않다. 아래는 공개 자료에서 확인한 범위(2026-10-29 웹 검색)다.
- Ticketmaster Smart Queue: 판매 시작 약 15~30분 전에 대기실을 열고, 대기실에 들어온 시각이 아니라 판매 시작 시점에 무작위로 순번을 배정한다고 공식 안내와 2018년 발언이 설명한다. 도착 순서(FIFO)가 아니라 사전 대기자를 섞는 방식이라, 일찍 오는 것의 이득이 없고 대기실 입장 전 폭주가 순번과 무관해진다.
- Queue-it(대기열 전문 업체, 여러 티켓·유통 사이트가 사용): 트래픽이 설정한 한도를 넘을 때만 방문자를 업체 인프라의 대기실로 보내고, 정해진 속도로 원 사이트에 들여보낸다. 연동은 클라이언트·서버·엣지·모바일 SDK 커넥터가 있다. 즉 대기열 자체를 원 서비스 밖에 둔다.
- Naver·인터파크의 내부 설계는 공식 자료를 찾지 못했다. 개인 블로그들은 Redis Sorted Set 순번 + 입장 토큰 구조를 추정·제안하지만 실제 구현의 증거는 아니다.
- 일반적으로 알려진 패턴(이 검색에서 확인한 것이 아니라 배경 지식)은 대기열을 앱 서버 밖(CDN 엣지, 별도 서비스)에 두어 본 서비스를 보호하고, 순번 조회는 캐시 가능한 가벼운 응답으로 만들고, 입장 속도를 서버가 제어하는 것이다.

### 정석 구현이 있는가
- 하나의 표준은 없고, 업계에서 반복해서 쓰는 패턴의 조합이 있다(배경 지식이며 이 검색으로 확인한 것은 아니다).
  1. 폭주 흡수와 입장 제어를 분리한다. 대기실은 가볍고 무상태에 가깝게, 본 서비스에는 정해진 속도로만 들여보낸다.
  2. 입장 증명은 서명된 토큰(JWT 등)으로 하고, 본 서비스는 토큰 서명·만료만 검증한다. 대기열 저장소를 직접 조회하지 않는다.
  3. 순번 알림은 폴링(+ 서버가 주는 다음 폴링 시각, jitter), 또는 SSE·WebSocket 푸시 중 하나를 쓴다. 규모가 크면 폴링 응답을 캐시·정적 파일 수준으로 가볍게 만들기도 한다.
  4. 순서 정책은 FIFO와 무작위 배정 중 서비스 성격에 맞게 고른다.
  5. 대기열이 죽어도 본 서비스가 열려 있지 않도록 fail closed를 기본으로 하고, 봇 방어(로그인, CAPTCHA, 계정당 1줄)를 앞단에 둔다.
- 이 프로젝트 설계(Redis 순번 + 입장 토큰 + 폴링)는 1~3번과 같은 계열이다.

### 프론트가 부하 분산에 협조해야 하는가
- 한다. 선량한 클라이언트가 폭주하지 않게 돕는 역할이다. 서버가 준 `nextPollAfterSeconds`를 지키고, ms 단위 jitter를 섞고, `READY`를 받으면 폴링을 멈추고 토큰 요청을 한 번만 보낸다. 실패와 과부하 응답(429, 503)에는 backoff + jitter로 물러난다. 백그라운드 탭은 `visibilitychange`로 폴링을 늦추고, 같은 사용자의 중복 탭 폴링은 한 탭으로 모은다.
- 프론트 코드는 신뢰할 수 없으므로 서버도 사용자당 요청 제한 등으로 방어해야 한다. 프론트는 협조, 서버는 방어다.

## 이 프로젝트에서는
- ADR 0031과 SA MASTER 사본 머리말 제안 표 10번이 "폴링 간격에 jitter를 섞는다"를 제안한다(9-4). 순번이 멀수록 간격을 길게(기본 3초, 최대 10초) 하는 정책과 함께 쓰면, 간격이 같은 그룹 안에서도 요청이 퍼진다.
- 진입 응답이 `nextPollAfterSeconds`를 내려주는 구조(11-5)라 서버가 첫 폴링 시각까지 정할 수 있다. 진입 직후 첫 폴링에 jitter를 주면 오픈 순간 요청이 두 배로 겹치는 문제를 줄인다.
- 적용 전후는 부하 테스트로 비교하라는 것이 PR의 제안이다. 비교 지표로는 초당 요청 수의 평균 대비 최대 비율과 p99 지연을 볼 수 있다.

## 면접 포인트
- 폴링을 쓰는 대기열에서 요청이 한 순간에 몰리는 이유와 해결책은? → 모두가 같은 기준 시각 + 같은 고정 간격이라 동기화된다. 간격에 무작위 오차(jitter)를 섞어 분산한다.
- jitter를 클라이언트와 서버 중 어디서 넣을까? → 클라이언트는 비용이 없지만 구현에 의존하고, 서버는 통제할 수 있지만 응답 필드 해상도와 계약에 제약이 있다.
- jitter 효과를 어떻게 검증하나? → 같은 시나리오로 적용 전후 부하 테스트를 돌려 초당 요청 수의 peak/평균 비와 지연 분포를 비교한다.

- jitter를 넣으면 입장 순서가 깨지지 않나? → 순서는 서버의 순번(seq)과 `admitted` 비교로 정해지므로 폴링 시각과 무관하다. 다만 자격을 확인하고 토큰을 받는 시각에는 폴링 간격만큼의 오차가 있다.
