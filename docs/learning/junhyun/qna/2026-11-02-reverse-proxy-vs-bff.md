# SPA와 API를 잇는 리버스 프록시 중계와 BFF는 무엇이 다른가

## 질문
프론트를 별도 컨테이너로 띄우고 서버 간 통신으로 API를 부르고 싶다. nginx 중계 방식과 BFF 방식의 차이를 알려 달라.

이어서 물은 것: 실제 티켓팅 사이트를 만든다면 어느 방식이 더 적절한가.

## 짧은 답
핵심 차이는 API를 실제로 부르는 주체가 누구고 토큰을 어디에 두느냐다. 중계는 브라우저 JS가 토큰을 들고 API를 부르며, nginx는 요청을 내용 그대로 Gateway에 넘기는 파이프다. BFF는 프론트 전용 서버가 토큰을 서버 세션에 두고 API를 대신 부르며, 브라우저는 세션 쿠키만 가진다. BFF는 토큰 탈취를 어렵게 하는 대신 서버 하나를 더 만들고 운영해야 하고, 쿠키를 쓰므로 CSRF 방어가 필요해진다.

실제 티켓팅 서비스라면 웹은 BFF가 맞다. 결제와 개인정보를 다루는 브라우저 앱에는 IETF RFC 10017(2026-08)이 BFF를 강하게 권한다. 대신 대기열을 BFF 앞 위치에 두어 몰림을 먼저 받고, BFF에는 입장한 사람만 들어오게 한다. 대기열이 하는 일 자체는 이 프로젝트가 서버에 만든 것과 같고 위치만 다르다. 이 프로젝트가 중계를 고르는 이유는 기간 한정 시연이라는 조건 때문이지, 중계가 더 좋은 구조라서가 아니다.

## 자세히

### 1. 요청이 지나가는 길

중계(리버스 프록시):
```
브라우저 JS ── Authorization: Bearer <access> ──▶ nginx ──(그대로)──▶ Gateway ──▶ 서비스
  토큰 보관: 브라우저 (메모리, localStorage, sessionStorage)
  nginx가 아는 것: "/api/로 시작하면 gateway:8080으로" 한 줄
```

BFF(Backend for Frontend):
```
브라우저 JS ── Cookie: SID=... ──▶ BFF 서버 ── 세션에서 토큰 꺼냄 ── Bearer <access> ──▶ Gateway ──▶ 서비스
  토큰 보관: BFF 서버 세션 (Redis 등). 브라우저는 httpOnly 쿠키만
  BFF가 아는 것: 로그인, 토큰 갱신, 화면별 API, 응답 가공
```

두 방식 모두 Gateway 입장에서는 Bearer 토큰이 붙은 요청이 들어온다. Gateway의 JWT 검증, 사용자 단위 요청 제한은 그대로 돈다.

### 2. 비교

| 기준 | 중계 | BFF |
|---|---|---|
| API를 부르는 주체 | 브라우저 JS | 프론트 서버 |
| 서버의 역할 | 요청을 내용 그대로 넘긴다. 업무 로직이 없다 | 세션, 토큰 갱신, API 호출, 여러 응답 합치기·가공 |
| 토큰 위치 | 브라우저가 JS로 읽을 수 있는 곳 | 서버 세션. 브라우저는 JS로 읽지 못하는 httpOnly 쿠키 |
| XSS(악성 스크립트 주입) | 스크립트가 토큰을 읽어 밖으로 보낼 수 있다. 공격자가 나중에도 그 토큰을 쓴다 | 토큰을 읽지 못한다. 다만 페이지가 열려 있는 동안 스크립트가 사용자 대신 요청을 보내는 것은 막지 못한다 |
| CSRF(다른 사이트가 요청을 위조) | `Authorization` 헤더는 브라우저가 자동으로 붙이지 않아 해당하지 않는다 | 쿠키는 브라우저가 자동으로 붙인다. `SameSite` 설정과 CSRF 토큰이 필요하다 |
| 만들 것 | nginx 설정 몇 줄 | 서버 앱, 세션 저장소, 로그인·갱신 흐름, API마다 전달 코드 |
| 요청 경로 부담 | nginx 전달만 한다. 지연이 거의 없다 | 요청마다 세션 조회 + 서버 처리 + Gateway 호출. BFF도 부하를 받아 내야 할 대상이 된다 |
| 여러 API 합치기 | 못 한다. 브라우저가 여러 번 부른다 | 화면 하나에 필요한 여러 API를 한 번에 모아 준다 |
| 관측 | nginx는 보통 추적에 끼지 않는다. 추적은 Gateway에서 시작한다 | 서비스가 하나 늘어 지표·추적 대상이 된다 |
| 메모리 | 수십 MB | Node 서버 수백 MB, Spring Boot면 compose 기준 512MB |

### 3. 같은 화면을 두 방식으로: 대기열 → 좌석

중계:
1. 브라우저가 `POST /api/v1/schedules/31/queue`를 Bearer와 함께 보낸다. nginx가 Gateway로 넘긴다.
2. 응답의 `nextPollAfterMillis`만큼 기다렸다가 `GET /queue/me`를 반복한다.
3. `READY`면 `POST /queue/token`을 불러 입장 토큰을 `sessionStorage`에 둔다.
4. 좌석 조회·선점에 `X-Entry-Token`을 붙인다.

BFF:
1. 브라우저가 `POST /bff/schedules/31/queue`를 쿠키와 함께 보낸다. BFF가 세션에서 Access 토큰을 꺼내 Gateway를 부른다.
2. 순번 폴링도 매번 BFF를 거친다. 폴링 한 번이 세션 조회 + Gateway 호출이다.
3. `READY`면 BFF가 토큰 API를 부르고 입장 토큰을 세션에 둔다. 브라우저는 입장 토큰을 보지 않는다.
4. 좌석 조회·선점 때 BFF가 세션의 입장 토큰을 `X-Entry-Token`으로 붙인다.

대기자 1만 명이 3초마다 순번을 조회하면 초당 약 3,300건이다. 중계에서는 이 요청이 nginx를 지나 Gateway에서 바로 처리된다. BFF에서는 BFF가 먼저 이만큼을 받아 내야 한다.

### 4. 어느 쪽이 맞는가
- BFF가 맞는 경우: 웹·모바일처럼 클라이언트마다 다른 응답 모양이 필요할 때, 토큰 탈취가 치명적인 서비스(금융 등)일 때, 화면 하나가 여러 마이크로서비스를 불러 합쳐야 할 때, 내부 API 구조를 밖에 숨기고 싶을 때다.
- 중계가 맞는 경우: 클라이언트가 웹 하나이고, API가 이미 화면 단위로 설계돼 있고, 서버를 더 늘리고 싶지 않을 때다.
- 토큰 보관은 중계 방식에서도 개선할 수 있다. Access 토큰은 JS 메모리에만 두고, Refresh 토큰은 인증 서버가 httpOnly 쿠키로 내려 주는 방식이 SPA에서 흔하다. 이 방식은 인증 서버의 응답 계약이 바뀐다.

### 5. 실제 티켓팅 서비스라면

실서비스는 둘 중 하나만 고르지 않고 층을 나눠 섞는다.

```
[CDN] 정적 파일, 공개 페이지 캐시
  │
[대기열]     오픈 순간의 몰림을 여기서 받는다. 직접 만들거나 산다. 통과한 사람에게 서명된 입장 토큰
  │  (입장 속도만큼만 아래로 내려보낸다)
[웹 BFF] 로그인 세션(httpOnly 쿠키), 토큰 보관, 화면용 API     [앱용 API] 토큰은 OS 보안 저장소
  │                                                               │
[API Gateway] ─────────────────────────────────────────────────────┘
  │
[서비스들]
```

| 층 | 실서비스에서 쓰는 방식 | 이유 |
|---|---|---|
| 웹 인증·API 호출 | BFF | RFC 10017(OAuth 2.0 for Browser-Based Applications, BCP 212, 2026-08)은 브라우저 앱 구조를 보안이 높은 순서로 BFF, 토큰 중개 백엔드, 브라우저 OAuth 클라이언트로 놓는다. BFF는 "업무용 앱, 민감한 앱, 개인정보를 다루는 앱"에 강하게 권한다. 티켓팅은 결제와 개인정보(이름, 연락처, 본인인증)를 다루고, 계정을 빼앗기면 표를 빼돌려 되파는 피해로 이어진다. 같은 문서는 BFF가 CSRF 방어를 반드시 갖춰야 한다고 적는다 |
| 몰림 | 대기열(가상 대기실)을 원 서버 앞에 | 대기 인원 전체가 BFF·Gateway를 두드리지 않게, 직접 만든 대기열 서비스나 상용 제품(Cloudflare Waiting Room, Queue-it 등)을 앞단에 두고 통과한 사람만 원 서버로 보낸다. 순번·일정 속도 입장·서명 토큰·진입점 검증은 이 프로젝트의 대기열과 같은 일이다([대기실과 서버 대기열 노트](2026-11-02-waiting-room-vs-server-queue.md)). 그러면 BFF가 받는 양은 대기 인원이 아니라 입장 속도로 정해진다 |
| 공개 페이지 | 서버 렌더링·정적 생성 + CDN 캐시 | 공연 목록·상세는 검색 노출과 SNS 링크 미리보기(Open Graph)가 필요하다. 오픈 전 새로고침 트래픽도 CDN이 받는다. Next.js 같은 프레임워크가 서버 렌더링과 BFF를 한 서버에서 함께 맡는 경우가 많다 |
| 예매 화면 | 브라우저에서 동작하는 화면 | 좌석 선택, 남은 시간, 결제 확인 중은 상호작용이 많아 SPA처럼 동작한다 |
| 모바일 앱 | 앱용 API 또는 앱 전용 BFF | 앱은 쿠키 대신 OS 보안 저장소(iOS Keychain, Android Keystore)에 토큰을 둔다. 클라이언트마다 BFF를 따로 두는 것이 BFF 패턴의 원래 동기다 |
| 매크로·암표 | 별도 방어 층 | BFF는 봇을 막지 못한다. 봇은 진짜 브라우저를 조종한다. 보안문자, 본인인증, 봇 관리·WAF, 사용자 단위 요청 제한, 1인 매수 제한을 따로 둔다 |

3절의 "BFF가 폴링을 다 받아야 한다"는 단점은 대기열이 Gateway 뒤 서비스 안에 있는 이 프로젝트 구조에서 생긴다. 대기열을 앞단 서비스로 떼어 내는 실서비스 구조에서는 이 단점이 대부분 사라진다. 이 프로젝트에서도 대기열 모듈을 떼어 앞에 두면 같은 구조가 된다.

## 이 프로젝트에서는
- 계약이 브라우저 보관을 전제로 한다. 로그인·재발급은 `refreshToken`을 JSON 본문으로 준다(SA 11-5). 입장 토큰은 프론트 `sessionStorage`에 둔다(`docs/design/queue/contracts.md` 2절). BFF로 가면 이 프론트 규칙이 바뀐다.
- API가 이미 화면 단위다. SA 11-2가 "한 응답으로 다음 화면을 정할 수 있게 한다"를 원칙으로 둬서, 선점 HELD 응답에 결제 토큰이 들어 있다. BFF의 합치기 이점이 작다.
- 대기열이 Gateway 뒤 Reservation 서비스 안에 있어 폴링이 Gateway까지 들어온다. Gateway는 "몰리는 순간 인증이 서비스 호출 없이 끝남"을 목표로 설계했다(SA 7-2). 이 구조에서 BFF를 더하면 그 앞에 병목 후보를 하나 더 두게 된다.
- 결정: 중계(A). 기간 한정 시연이고 화면 구현은 M4 한 주이며, 백엔드에 집중하기 위해 프론트는 단순하게 간다. Access 토큰은 메모리에만 두고 XSS 위험은 감수한다. 5절의 실서비스 구조는 학습한 내용으로 [ADR 0040](../../../decisions/0040-frontend-react-spa-in-monorepo.md) 4절 "학습한 실서비스 구조와 이번 선택" 표에 남겼다.

## 면접 포인트
- SPA에서 토큰을 어디에 두었나: 중계 방식에서는 브라우저에 둔다. XSS에 노출되는 대신 CSRF는 해당하지 않는다. httpOnly 쿠키로 옮기면 XSS 탈취는 막지만 CSRF 방어가 필요해진다. 둘은 맞바꾸는 관계다.
- BFF를 쓰지 않은 이유: 클라이언트가 웹 하나이고 API가 화면 단위로 설계돼 있었다. 대기열 폴링이 몰리는 경로에 서버를 하나 더 두는 비용이 이점보다 컸다.
- 실서비스라면 어떻게 하겠나: 결제·개인정보를 다루는 웹이라 BFF로 토큰을 브라우저에서 빼고(RFC 10017), CSRF는 `SameSite`와 CSRF 토큰으로 막는다. 대기열을 BFF 앞에 두어 BFF는 입장 속도만큼만 받게 한다. 대기열 설계는 그대로 쓰고 위치만 앞단으로 옮긴다. 공개 페이지는 서버 렌더링과 CDN 캐시로 검색 노출과 새로고침 트래픽을 처리한다.
