# 토스페이먼츠 테스트 연동을 위해 미리 준비해 둘 것은 무엇인가

## 질문
토스페이먼츠 개발자 설정을 미리 준비해 놓으면 좋을 게 있나. M4의 토스 어댑터(ISE-45), 결제창 화면(ISE-125), 빌링키 등록(ISE-122·96)을 앞두고 물었다.

## 짧은 답
사람이 직접 해야 하는 일은 세 가지다.
1. 개발자센터에 이메일로 가입하고 테스트 키를 확인한다. 사업자번호와 계약은 필요 없다.
2. 시크릿 키를 저장소 밖에 안전하게 보관한다. 팀원에게는 키를 메신저로 보내지 않고 개발자센터의 사용자 추가로 권한을 준다.
3. 그 키로 자동결제(빌링) 테스트가 되는지 확인한다. 문서가 보장하지 않는 유일한 부분이다.

라이브 키, 전자결제 계약, 웹훅 등록은 지금 필요 없다.

## 자세히

### 1. 가입과 테스트 키
- 가입은 이메일만으로 된다. 가입하면 "개발자용 테스트상점"(개발 연동 체험 상점)에 테스트 키가 발급된다.
- 테스트 환경에서는 실제 카드를 넣어도 승인이 가상으로 처리되고 돈이 빠지지 않는다.
- 키는 클라이언트 키와 시크릿 키가 한 쌍이다.
  - 클라이언트 키: 브라우저 SDK를 초기화한다. 공개돼도 되는 값이다.
  - 시크릿 키: 서버가 API를 호출할 때 인증에 쓴다. `시크릿키:`를 Base64로 인코딩해 Basic 인증 헤더에 넣는다. 끝의 콜론을 빠뜨리면 `INCORRECT_BASIC_AUTH_FORMAT`이 난다.
- 키 계열이 둘이다.
  - 주문서형·결제창형 연동 키: `test_gck_`·`test_gsk_`
  - API 개별 연동 키: `test_ck_`·`test_sk_`
  - 계열을 섞거나 테스트 키와 라이브 키를 섞으면 `INVALID_API_KEY`가 난다.

### 2. 우리에게 필요한 키 계열
결제창 v2 연동 가이드와 자동결제 가이드가 모두 **API 개별 연동 키**를 쓰라고 안내한다. 그래서 일반 결제(결제창 → 서버 승인)와 추첨 자동결제(빌링)를 `test_ck_`·`test_sk_` 한 쌍으로 맞출 수 있다. 개발자센터 API 키 메뉴에서 이 계열이 보이는지 확인한다.

### 3. 시크릿 키 보관
- 저장소, 프론트 코드, 로그에 넣지 않는다. 토스 문서도 같은 것을 요구한다. 우리 저장소에서는 대전제 8(비밀값 금지)에 해당한다.
- 당장은 비밀번호 관리자 같은 개인 보관소에 둔다. 서버에 넣는 방법(환경변수 이름, 설정 서버 주입)은 ISE-45에서 결제 토큰 키(ADR 0025)와 같은 방식으로 정한다.
- 시크릿 키는 재발급하면 7일 동안 옛 키와 새 키가 함께 유효하다. 노출이 확인되면 결제 중단에 동의하고 즉시 폐기할 수 있다.
- 팀원(프론트·배포 담당)에게 키를 공유해야 하면 개발자센터의 사용자 추가 기능을 쓴다. 문서는 메신저나 이메일로 평문 전송하지 말라고 권한다.

### 4. 자동결제(빌링) 테스트 가능 여부 확인
- 라이브 자동결제는 추가 리스크 검토와 계약이 필요하다. 계약이 없는 키로 부르면 `NOT_SUPPORTED_METHOD`가 난다고 문서에 적혀 있다.
- 개발자용 테스트상점 키로 빌링을 테스트할 수 있는지는 공식 문서에서 찾지 못했다(미확인).
- 확인 방법: 개발자센터에서 테스트상점의 키 목록과 결제수단을 보거나, 기술지원 채팅에 묻는다. 안 되면 문서에 공개된 테스트 키로 시험한다.
- 테스트 빌링은 카드번호 앞 6자리만 맞아도 등록되고, 본인인증 번호는 `000000`이다.
- 토스는 스케줄링을 제공하지 않는다. 언제 결제할지는 우리가 정한다. 추첨은 결과 발표 뒤 우리 서버가 승인 API를 부른다.

### 5. 지금 하지 않아도 되는 것
- 전자결제 계약과 라이브 키: 시연은 테스트 환경으로 충분하다.
- 웹훅 등록: 외부에서 접근할 수 있는 URL이 필요하다(로컬은 ngrok). 우리 설계는 결과를 조회 API로 확인하므로(재확인 스케줄러, ADR 0023) 필수가 아니다.

### 6. 구현할 때 쓸 것
- `TossPayments-Test-Code` 헤더에 오류 코드를 넣으면 테스트 환경에서 그 오류 응답을 그대로 재현한다. 테스트 시크릿 키일 때만 동작한다. 토스 어댑터의 오류 분류 테스트에 쓴다.
- 결제창에서 결제 요청이 끝난 뒤 10분 안에 승인 API를 불러야 한다. 넘기면 `NOT_FOUND_PAYMENT_SESSION`이다(결제창 v2 연동 가이드).

## 이 프로젝트에서는
- M4 토스 어댑터가 확인할 목록은 `docs/design/payment/pg-integration.md` 7절에 있다. 3번 항목(`paymentKey` 만료 10분과 30분이 엇갈림)은 결제창 v2 가이드에서 "10분 이내 승인"을 찾았다. ISE-45를 시작할 때 이 근거로 7절을 고친다.
- 10분 승인 제한은 좌석 선점 만료와 함께 봐야 한다. 결제 토큰 `exp`가 선점 만료 10초 전이고, 이 시각이 지나면 Payment는 신규 승인을 거절한다(`docs/design/payment/contracts.md` 1절). 토스 결제창을 거치면 "결제창 완료 → 10분 안에 승인"과 "토큰 만료 전에 승인" 두 시한을 모두 지켜야 한다.
- 키 주입 방식은 결제 토큰 키와 같게 맞춘다(`docs/decisions/0025-payment-token-secret-injection.md`).

## 면접 포인트
- PG 연동에서 클라이언트 키와 시크릿 키를 나누는 이유: 브라우저는 결제창을 띄우기만 하고, 돈을 움직이는 승인은 시크릿 키를 가진 서버만 한다. 금액 변조를 막으려고 승인 금액은 서버가 저장한 값과 대조한다.
- 웹훅 없이 결제 결과를 확정하는 방법: 승인 응답을 못 받으면 결과를 모르는 상태로 두고, 주문 식별자로 조회 API를 불러 확정한다. 웹훅은 보조 신호로 쓸 수 있다.
