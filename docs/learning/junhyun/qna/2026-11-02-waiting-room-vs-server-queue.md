# 앞단에 가상 대기실을 두면 서버에 만든 대기열 설계는 의미가 없어지는가

## 질문
실서비스는 가상 대기실을 맨 앞에 둔다고 들었다. 이 프로젝트는 백엔드 중심이라 서버에서 요청을 대기시키도록 설계했는데, 앞쪽에 대기실 서비스를 두면 서버 설계가 의미 없어지는 것 아닌가.

## 짧은 답
의미 없어지지 않는다. 앞단 대기실은 대기열을 어디에 두느냐의 문제다. 그 안에서 푸는 문제(순번 발급, 일정 속도 입장, 서명된 통과 증명, 진입점 검증, 대기 화면 갱신 부하 조절, 만료·재진입)는 이 프로젝트가 서버에 만든 대기열과 같다. 상용 제품을 쓰는 회사는 그 문제를 제품에 맡긴 것이고, 직접 만드는 회사는 이 프로젝트처럼 만든다. 게다가 대기실이 있어도 입장 속도를 얼마로 할지는 서버를 측정해서 정해야 하고, 입장한 뒤의 동시성·결제·장애 대응은 전부 서버 몫이다.

## 자세히

### 1. 가상 대기실이 하는 일과 이 프로젝트의 대응

| 대기실이 하는 일 | 이 프로젝트에서 만든 것 |
|---|---|
| 줄 세우기 | Redis `seq` 카운터로 순번 발급, `waiting` Sorted Set (결정 #27, SA 12-8) |
| 일정 속도로 들여보내기 | 전역 카운터 `admitted`를 1초에 한 번만 올림(`lastTick`), 상한은 발급된 `seq` (ADR 0015) |
| 통과 증명 | 서명된 입장 토큰, 토큰 API, `READY` 상태 (ADR 0031) |
| 원 서버 앞에서 증명 확인 | Gateway 입장 토큰 필터가 좌석 조회·선점 경로에서 회차까지 비교 (`docs/design/queue/contracts.md`) |
| 대기 화면 갱신 부하 조절 | 서버가 jitter를 섞은 `nextPollAfterMillis`, 쓰기 없는 순번 조회 (ADR 0031) |
| 응답 유실·새 탭·만료 | `issued` 기록으로 같은 토큰 재발급, 만료 뒤 재진입 (ADR 0015·0031) |

상용 대기실 제품도 이 표의 왼쪽 칸을 구현한 것이다. 이 프로젝트는 그것을 직접 설계하고 구현했다.

### 2. 다른 것은 위치다

| 기준 | 서비스 안 (이 프로젝트) | 원 서버 앞단 |
|---|---|---|
| 대기 중 트래픽 | Gateway와 Redis까지 들어온다 | 원 서버에 오지 않는다 |
| 업무 정보 | 회차, 사용자, 매수 제한을 바로 안다 | 원 서버와 연동해야 안다 |
| 운영 | 직접 만들고 측정한다 | 제품이면 설정만 한다. 직접 만들면 별도 서비스를 운영한다 |
| 비용 | 서버 자원 | 제품 비용 또는 별도 인프라 |

이 프로젝트의 설계에는 앞단으로 옮길 길이 이미 있다. 순번 조회를 읽기 전용으로 만든 이유가 나중에 폴링을 Redis 복제본으로 나누기 위해서다(SA 12-8). 대기열은 Reservation 안 모듈이라(결정 #10) 규모가 커지면 별도 서비스로 떼어 앞단에 둘 수 있다.

### 3. 대기실이 있어도 서버가 해야 하는 일
1. **입장 속도를 정한다.** 대기실은 "초당 몇 명"을 받아야 동작한다. SA 3-3은 이 값을 선점 API의 포화 처리량 μ, 입장자 한 명의 요청률 r, 평균 체류 시간 W로 `λ = (μ / r) / W`로 역산한다. 제품을 사도 이 숫자는 서버를 측정한 팀만 넣을 수 있다.
2. **입장한 뒤를 처리한다.** 중복 판매 0건, 멱등키, 예매↔결제 SAGA, 타임아웃·Circuit Breaker·Bulkhead, Outbox, 만료 뒤 승인 환불은 대기실과 관계없다. 이 프로젝트의 나머지 설계 대부분이 여기다.
3. **스스로도 막는다.** 원 서버 주소를 직접 부르는 우회, 대기실 설정 실수, 입장자들의 재시도 폭주는 대기실이 막지 못한다. Gateway의 입장 토큰 검증, 사용자 단위 요청 제한, Bulkhead가 서버 쪽 방어선이다. 앞단 방어가 있어도 뒤에서 다시 막는 것을 다층 방어라고 한다.

## 이 프로젝트에서는
- 발표에서는 "실서비스는 대기실을 앞단에 둔다. 우리 대기열이 바로 그 대기실이다. 백엔드 프로젝트라 직접 만들었고, 서비스 안에 둔 대가로 대기 트래픽이 Gateway까지 들어온다. 이 비용은 jitter와 읽기 전용 조회로 줄이고 부하 테스트로 쟀다. 규모가 커지면 순번 조회를 복제본으로, 대기열 모듈을 앞단 서비스로 떼어 낸다"로 설명할 수 있다.
- 프론트 구조 결정([ADR 0040](../../../decisions/0040-frontend-react-spa-in-monorepo.md)) 4절에 "대기열 기능은 같고 위치만 다르다, 앞단으로 떼어 내는 길은 열려 있다"로 적었다. 대기열 설계를 대체한다는 뜻으로 쓰지 않았다.
- 관련: [중계와 BFF 노트](2026-11-02-reverse-proxy-vs-bff.md) 5절

## 면접 포인트
- "상용 대기실 솔루션을 쓰면 되지 않나": 제품을 써도 입장 속도는 서버 처리량을 측정해 정해야 하고, 입장한 뒤의 동시성·결제 정합성은 서버가 책임진다. 이 프로젝트는 대기실이 푸는 문제(순번, 일정 속도 입장, 서명 토큰, 진입점 검증)를 직접 구현해 원리를 확인했다.
- "대기열을 서비스 안에 둔 단점은": 대기 중 폴링이 Gateway와 Redis까지 들어온다. 서버가 폴링 간격과 jitter를 정하고, 순번 조회를 쓰기 없이 만들어 복제본으로 나눌 수 있게 했다.
