# 부하 테스트 때문에 EC2를 flex 인스턴스에서 일반 인스턴스로 바꾸려면 어떻게 하나

## 질문
부하 테스트 때문에 배포 서버를 flex 인스턴스(`m7i-flex.xlarge`)에서 일반 인스턴스로 바꾸려 한다. 그냥 내렸다가 다시 올리면 되나.

## 짧은 답
된다. 순서는 중지(Stop), 인스턴스 유형 변경, 시작(Start)이다. 같은 크기의 일반 인스턴스는 `m7i.xlarge`(4 vCPU, 16GiB)다.

"내린다"를 종료(Terminate)로 하면 안 된다. 종료하면 인스턴스와 루트 디스크(EBS)가 지워져 DB·Kafka 데이터와 `.env`가 모두 사라진다.

중지했다가 시작해도 이 프로젝트에서는 바뀌는 것이 거의 없다.
- 공인 IP: 탄력적 IP라 그대로다.
- 사설 IP: 그대로다.
- 디스크: 그대로다.
- 컨테이너: 재시작 정책(`restart: unless-stopped`)으로 다시 뜬다.

## 자세히

### 1. flex 인스턴스와 일반 인스턴스는 무엇이 다른가
- **flex(`m7i-flex`)**: 평소에는 vCPU당 40%를 기준 성능으로 보장한다. 필요하면 "대부분의 시간" 최대 성능까지 올라간다. 대부분의 서비스는 CPU를 늘 꽉 쓰지 않으니 이 방식으로 값을 낮춘다.
- **일반(`m7i`)**: 항상 최대 성능을 쓴다. AWS도 CPU를 계속 높게 쓰는 작업에는 M7i를 권한다.
- **`t3` 같은 크레딧 버스트형과의 차이**: flex는 크레딧을 모았다가 쓰는 방식이 아니다. 그래서 짧은 테스트라면 flex에서도 대개 최대 성능이 나온다.
- **부하 테스트에서 일반 인스턴스가 나은 이유**: 측정값을 설명하기 쉽다. "그 순간 CPU가 기준 성능으로 묶였던 것 아니냐"는 의문이 생기지 않는다. 같은 조건으로 다시 재기도 쉽다.

요금 차이는 작다.
- 시드니 `m7i-flex.xlarge`는 시간당 0.2394달러다(11/4 요금 노트).
- 버지니아 북부(us-east-1)에서 `m7i.xlarge`는 0.2016달러, flex는 그보다 5% 싸다.
- 이 비율로 계산하면 시드니 `m7i.xlarge`는 시간당 약 0.252달러, 하루 차이는 약 0.3달러다. 나중에 AWS 가격 데이터에서 시드니 0.252달러를 확인했다(6절).

### 2. "내린다"에는 두 뜻이 있다
| 동작 | 콘솔 메뉴 | 인스턴스 | 루트 디스크(EBS) | 공인 IP | 요금 |
|---|---|---|---|---|---|
| 중지 | 인스턴스 상태 → 인스턴스 중지 | 남는다. 다시 시작할 수 있다 | 남는다 | 탄력적 IP면 그대로, 자동 할당이면 바뀐다 | 인스턴스 요금은 멈추고 디스크·탄력적 IP 요금만 나온다 |
| 종료 | 인스턴스 상태 → 인스턴스 종료 | 지워진다. 되돌릴 수 없다 | 기본 설정이면 함께 지워진다 | 반납된다(탄력적 IP는 연결만 풀린다) | 멈춘다 |

인스턴스 유형은 중지 상태에서만 바꿀 수 있다. 실행 중에는 "인스턴스 유형 변경" 메뉴가 비활성으로 보인다.

### 3. 바꾸는 순서(콘솔)
1. **시점을 고른다.** dev→main 릴리스나 Jenkins 배포가 돌고 있지 않을 때 한다. 서버가 꺼진 사이에 Jenkins가 배포를 시작하면 SSH가 실패하고 실패 알림이 간다.
2. **중지한다.** EC2 → 인스턴스 → 배포 서버 선택 → 인스턴스 상태 → **인스턴스 중지**(종료가 아니다). 상태가 "중지됨"이 될 때까지 1~2분 기다린다.
3. **유형을 바꾼다.** 작업 → 인스턴스 설정 → **인스턴스 유형 변경** → `m7i.xlarge` → 적용.
4. **시작한다.** 인스턴스 상태 → **인스턴스 시작**.
5. **확인한다.**
   - 콘솔: 인스턴스 유형이 `m7i.xlarge`이고 공인 IP가 `52.63.10.174` 그대로인지 본다.
   - 서버: `ssh ubuntu@52.63.10.174` 뒤 `docker ps`로 컨테이너가 모두 떴는지 본다.
   - 화면: `http://52.63.10.174/`가 열리는지 본다.

### 4. 이 프로젝트에서 그대로인 이유(근거)
| 항목 | 그대로인 이유 | 근거 |
|---|---|---|
| 공인 주소 `52.63.10.174` | 탄력적 IP를 붙였다 | `docs/design/infra/deployment.md` 5절 |
| Jenkins → 배포 서버 접속 | `DEPLOY_HOST`가 사설 IP(`172.31.4.93`)이고, 사설 IP는 중지·시작에도 바뀌지 않는다 | 같은 문서 `DEPLOY_HOST` 설명 |
| DB·Redis·Kafka 데이터, `.env` | 모두 루트 EBS 디스크에 있고, 중지해도 디스크는 남는다 | ADR 0047 운영 일정 |
| 컨테이너 | 모든 서비스가 `restart: unless-stopped`다. Docker가 부팅 때 자동으로 시작되면 컨테이너도 다시 뜬다 | `compose.deploy.yml`, `script/deploy/install-docker.sh`(Docker 공식 apt 패키지는 서비스를 부팅 자동 시작으로 등록한다) |
| 드라이버·OS | `m7i-flex`와 `m7i`는 같은 Nitro·Intel x86_64 계열이라 Ubuntu 이미지를 그대로 쓴다 | AWS 범용 인스턴스 표 |

### 5. 주의할 점
- **시작 직후 몇 분은 503이 날 수 있다.** 앱이 Eureka에 등록될 때까지 게이트웨이가 경로를 못 찾는다(TS-34). 스모크도 그래서 120초까지 재시도한다.
- **용량 부족 오류가 날 수 있다.** 시작할 때 `InsufficientInstanceCapacity`가 나오면 그 가용 영역에 해당 유형이 잠시 모자란 것이다. 몇 분 뒤 다시 시작하거나 원래 유형으로 돌린다. 흔하지는 않다.
- **아키텍처가 다른 유형으로는 못 바꾼다.** Graviton(`m7g` 등 ARM)으로 바꾸면 x86 이미지가 부팅되지 않는다.
- **지출 한도에 걸려 있으면 시작이 안 된다.** 11/5 오전에 확인했을 때 배포 서버는 SSH와 HTTP 모두 응답하지 않았다. 11/4 지출 한도로 멈춘 상태가 이어지는 것으로 보인다. 그렇다면 한도를 먼저 올린다. 이미 중지 상태라면 2단계는 건너뛴다.
- **바꾼 뒤에는 문서를 맞춘다.** `docs/design/infra/deployment.md`의 첫 배포 기록(서버 사양 줄)과 요금 계산의 인스턴스 유형을 `m7i.xlarge`로 고친다.

### 6. 실제로 바꾼 결과 (2026-11-05)
- 사용자가 콘솔에서 유형을 `m7i.xlarge`로 바꿨다. 지출 한도로 이미 중지된 상태여서 중지 단계 없이 바로 바꿨다.
- 시드니 `m7i.xlarge` 요금은 AWS 가격 데이터로 시간당 0.252달러임을 확인했다(1절의 비율 계산과 같다).
- 문서를 맞췄다.
  - `deployment.md` 첫 배포 기록과 7절 결정 표
  - [요금 노트](2026-11-04-deploy-cost-and-single-host-db.md) 1-2절
- 14시쯤 한도를 올리고 시작했다. 3절 5단계대로 확인한 결과는 다음과 같다.
  - 유형: `m7i.xlarge`
  - 공인·사설 IP: 그대로
  - 컨테이너: 20개가 다시 떴다
  - 스모크: 4개 항목 통과
  - 중지 → 유형 변경 → 시작이 문서대로 동작했다

## 면접 포인트
- **수직 확장(scale-up)에는 짧은 중단이 따른다.** EC2 인스턴스 유형 변경은 중지 → 변경 → 시작이라 그동안 서비스가 멈춘다. 무중단으로 하려면 새 유형의 인스턴스를 따로 띄우고 로드밸런서에서 트래픽을 옮긴다(블루·그린). 수평 확장(scale-out)은 인스턴스를 더하는 방식이라 이런 중단이 없다.
- **성능 측정 환경에서는 성능이 보장된 인스턴스를 쓴다.** 버스트형(`t3`)이나 flex는 평소 비용을 줄이려고 CPU 성능을 조건부로 준다. 그래서 같은 테스트도 실행할 때마다 결과가 달라질 수 있다. 측정 대상은 성능이 고정된 유형으로 맞춰야 결과를 비교할 수 있다.
- **중지와 종료의 차이**: 중지는 디스크가 남고 다시 켤 수 있다. 종료는 인스턴스가 지워지고 기본 설정이면 루트 디스크도 지워진다. 공인 IP는 탄력적 IP가 아니면 중지·시작 때 바뀐다.
