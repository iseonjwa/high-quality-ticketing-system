# 부하 테스트를 로컬(노트북)에서 배포 서버로 쏘면 안 되나

## 질문
관리자 권한이 있는 사람이 로컬에서 배포 서버로 부하를 쏘면 안 되나.

## 짧은 답
- **할 수는 있다. 권한 문제는 아니다.**
  - 배포 서버의 80번(nginx)은 이미 누구에게나 열려 있다.
  - gateway 8080을 직접 부르려면 보안 그룹에 그 사람의 IP만 더하면 된다.
- **다만 공식 측정 숫자(기준선, 포화점, 발표용)는 로컬에서 내지 않는다.**
  - 한국에서 시드니까지 네트워크 지연이 서버 처리 시간보다 훨씬 커서 결과에 섞인다.
  - 처리량 한계도 서버보다 집 회선·노트북에서 먼저 올 수 있다.
- 로컬은 스크립트 확인과 가벼운 시연에 쓰고, 숫자는 같은 VPC 발생기에서 낸다.

## 자세히

### 1. 실제로 재 본 네트워크 지연 (2026-11-05, 이 맥북에서)
| 대상 | TCP 왕복 시간 |
|---|---|
| AWS 시드니 리전(`ec2.ap-southeast-2.amazonaws.com`) | 약 0.27~0.28초(5회) |
| AWS 서울 리전(`ec2.ap-northeast-2.amazonaws.com`) | 약 0.01~0.017초(3회) |
| 같은 VPC 안 EC2끼리 | 보통 1ms 미만 |

- 잰 방법: `curl -w '%{time_namelookup} %{time_connect}'`에서 DNS 시간을 뺀 TCP 연결 시간으로, 왕복 한 번에 해당한다.
- 값은 그날의 회선과 경로에 따라 달라진다.

### 2. 로컬에서 쏘면 생기는 문제
1. **응답 시간에 네트워크가 섞인다.**
   - 요청 하나는 최소 왕복 한 번(약 0.27초)이 걸린다. 서버가 20ms에 처리해도 k6에는 약 300ms로 찍힌다.
   - k6의 p95·p99가 사실상 "한국–시드니 지연"을 잰다. 서버 개선 전후 10~20ms 차이는 이 흔들림에 묻힌다.
2. **포화점이 누구 것인지 모른다.**
   - 가상 사용자 하나가 왕복을 기다리는 동안 다음 요청을 못 보낸다. 그래서 초당 최대 약 3.6건(1 ÷ 0.275초)이다. 초당 1,000건을 만들려면 가상 사용자가 수백 명 필요하다.
   - 그만큼 연결이 늘면 공유기(NAT 연결 수), 업로드 대역폭, 노트북 CPU, macOS 파일 디스크립터 한도가 먼저 막힐 수 있다.
   - 처리량이 멈췄을 때 서버 한계인지 집 환경의 한계인지 가릴 수 없다.
3. **다시 내기 어렵다.**
   - 시간대, 와이파이, 사람마다 회선이 달라 같은 시나리오도 결과가 바뀐다.
   - 측정 환경 기록표(`load-test.md` 7절)의 "부하 도구 장비·네트워크"를 고정할 수 없다.
4. **경로가 달라진다.**
   - 80으로 쏘면 nginx를 한 번 더 거친다.
   - 8080으로 쏘려면 보안 그룹에 개인 IP를 열어야 한다. 집 IP는 바뀌기도 한다.
   - SSH 터널로 우회하면 연결 하나에 모든 요청이 몰려 터널이 먼저 병목이 된다.

### 3. 그래도 로컬이 쓸모 있는 경우
- **서버 쪽 지표는 네트워크와 무관하다.** Grafana에서 보는 서버 처리 시간(`http_server_requests`), CPU, DB 연결 대기, Kafka 랙은 서버 안에서 잰 값이다. "이 정도 부하에 서버가 버티나"를 눈으로 보는 정도는 로컬로도 된다.
- **추천 분담**
  | 단계 | 어디서 | 왜 |
  |---|---|---|
  | k6 스크립트 작성·디버깅 | 로컬 k6 → 로컬 docker 스택 | 비용 0, 빠른 반복 |
  | 배포 서버에서 시나리오 동작 확인, 리허설 시연 | 로컬 k6 → 배포 서버(작은 가상 사용자 수) | 대기열이 차는 모습처럼 정확도가 필요 없는 확인 |
  | 기준선·포화점·발표 숫자 | 같은 VPC 발생기 EC2 → gateway 사설 IP | 네트워크 영향을 빼고 다시 낼 수 있게 |
- 데이터 전송 요금은 걱정할 수준이 아니다. AWS로 들어오는 트래픽은 무료다. 나가는 응답도 매달 100GB까지 무료라 짧은 시험이면 범위 안이다.

### 4. 설계 기록과의 관계
- SA 3-1과 9-2는 "다른 기기에서 실행하고 측정 기기 IP를 허용"한다고 적었다. 노트북도 이 방식에 들어간다.
- 11/3에 사용자가 이를 "같은 VPC 임시 EC2"로 구체화했다(ADR 0046). 노트북 실행은 같은 이유(네트워크와 노트북 성능이 결과에 섞임)로 대안에서 뺐다.
- 공식 측정을 로컬로 바꾸려면 ADR 0046을 고쳐야 한다. 이 노트의 분담처럼 확인·시연에만 쓰는 것은 ADR과 충돌하지 않는다.

## 면접 포인트
- 부하 테스트의 응답 시간은 "서버 처리 시간 + 네트워크 왕복"이다. 측정 대상이 서버라면 네트워크 몫을 최소화해야 한다. 그래서 발생기를 대상과 같은 리전·네트워크에 둔다.
- 폐쇄형 부하 모델에서 가상 사용자 하나의 처리량은 왕복 시간에 묶인다(초당 최대 1 ÷ 왕복 시간). 지연이 큰 곳에서 쏘면 같은 처리량에 더 많은 연결이 필요하고, 발생기 쪽이 먼저 한계에 닿는다.
- 클라이언트 지표(k6)와 서버 지표(Prometheus)를 같이 본다. 둘의 차이가 네트워크와 발생기 몫이다.
