# 프론트 테스트의 "8×8 동시 실행"은 무엇이고 왜 메모리를 다 쓰나

## 질문
"프론트 테스트 중에 부하 테스트가 있어? 돌릴 때마다 컴퓨터 메모리를 다 잡아먹는 것 같네", "8*8 테스트 이거 뭐야"

## 짧은 답
- 프론트 테스트(`npm test`, CI)에는 부하 테스트가 없다. jsdom에서 화면·API 동작을 확인하는 테스트뿐이다.
- "8×8"은 저장소 규칙도 CI도 아니고, 에이전트가 PR 전에 덧붙여 돌린 확인이다. 바꾼 테스트 파일을 vitest 8개로 동시에 띄우는 일을 8번 되풀이해(64번) 컴퓨터가 느릴 때도 테스트가 통과하는지 본다.
- 메모리를 다 쓴 원인은 vitest가 프로세스마다 CPU 코어 수만큼 작업자(각자 jsdom을 띄운 Node 프로세스)를 만든다는 데 있다. 8개를 동시에 띄우면 12코어 맥에서 작업자가 수십 개(최대 약 80개) 생긴다. 하나가 수백 MB라 메모리와 CPU가 바닥난다(부하 평균 60을 넘겼다).

## 자세히

### 왜 이런 확인을 했나
- 시간에 기대는 테스트는 빠른 컴퓨터에서는 통과하고 느린 CI에서만 실패한다. 예를 들어 데이터가 오기 전에 화면을 찾는 테스트다.
- 실제로 #326(추첨 화면)에서 CI가 한 번 실패했다. 로컬에서는 응답을 200ms 늦춰야 재현됐다.
- 그 뒤로 "일부러 컴퓨터를 바쁘게 만들어도 통과하는지"를 보려고 동시 실행을 PR 결과 표의 "느린 환경" 줄에 남겼다.

### 왜 이번에는 너무 무거웠나
| 원인 | 설명 |
|---|---|
| 작업자 수 제한 없음 | `vitest run`은 기본으로 코어 수만큼 작업자를 만든다. 파일 10개를 8개 프로세스로 동시에 돌리면 작업자가 수십 개다 |
| 같은 시간에 겹친 일 | 메인 세션의 전체 테스트, Sonnet 작업자의 동시 실행, 리뷰 에이전트의 테스트·headless Chrome, 프론트 이미지 docker 빌드가 같은 시간에 돌았다 |
| 이미 큰 바탕 | Docker 가상 머신(compose 스택 19개 컨테이너)이 약 5GB를 쓴다 |

결과도 쓸모가 적었다. 작업자 제한 없이 돌린 첫 확인은 64번 중 41번이 5초 시간 초과로 실패했다. 같은 테스트가 혼자 돌 때는 가장 느린 것이 149ms였다. 코드 문제가 아니라 컴퓨터가 감당하지 못한 것이다. `--maxWorkers=2`(프로세스마다 작업자 2개, 동시 16개)로 줄이자 64번 모두 통과했다.

### 줄이는 방법
- 작업자 수 제한: `npx vitest run --maxWorkers=2 <파일>`. 전체 테스트도 로컬에서는 `--maxWorkers=4`처럼 줄일 수 있다.
- 파일을 하나씩: `--no-file-parallelism`
- 동시 실행 확인은 시간에 기대는 테스트(가짜 시계, 다시 받기, 화면 갱신 순서)를 바꿨을 때만, 가볍게(예: 2개 × 3번) 한다.
- 원인을 직접 재현하는 편이 더 정확하다. 응답을 일부러 늦추는(MSW 핸들러에 지연) 테스트가 동시 실행보다 싸고 결과가 분명하다.
