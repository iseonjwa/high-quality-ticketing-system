# 부하 테스트(k6)는 어디에서 돌리고, k6도 컨테이너로 띄우나

## 질문
배포 서버에 부하 테스트를 하려면 Jenkins와 같은 인스턴스에서 돌리나. k6도 컨테이너로 띄우나.

## 짧은 답
- Jenkins 서버에서 돌리지 않는다. 배포 서버에서도 돌리지 않는다. **측정할 때만 같은 리전·같은 VPC에 임시 발생기 EC2를 띄우고, 끝나면 지운다**(ADR 0046).
- k6는 서버처럼 계속 떠 있는 서비스가 아니라 **측정하는 동안만 도는 클라이언트 프로그램**이다. 그래서 배포 compose의 20개에 들어가지 않는다. 발생기에서 k6를 바이너리로 설치할지 Docker 이미지(`grafana/k6`)로 한 번 실행할지는 아직 정하지 않았다(스크립트 위치와 함께 구현 이슈에서 정한다). 추천은 버전을 고정한 Docker 이미지로 한 번 실행하고 끝나면 지우는 방식(`docker run --rm`)이다.

## 자세히

### 1. 부하 테스트의 두 역할: 발생기와 대상
- **대상(target)**: 부하를 받는 쪽이다. 여기서는 배포 서버(`m7i.xlarge`)의 gateway와 그 뒤 서비스들이다.
- **발생기(load generator)**: 가상 사용자(VU)를 만들어 요청을 쏘는 쪽이다. k6가 여기서 돈다.
- 두 역할은 다른 기계에 둔다. 같은 기계에 두면 발생기가 대상의 CPU·메모리를 빼앗아, 측정값이 서버 성능인지 발생기 탓인지 가릴 수 없다.

```
[발생기 EC2 (임시)]  --사설 IP:8080-->  [배포 EC2: gateway → user/reservation/payment → DB·Redis·Kafka]
   k6                                       Prometheus·Grafana가 서버 지표를 잰다
   └─ 결과(remote write) ─────────────→  Prometheus (경로는 미정)

[Jenkins EC2]  --SSH 배포만-->  [배포 EC2]       (측정과 무관)
```

### 2. 왜 Jenkins 서버가 아닌가
| 후보 | 장점 | 안 쓰는 이유 |
|---|---|---|
| Jenkins EC2(`t3.small`) | 따로 띄울 필요가 없다 | 2 vCPU·2GiB 크레딧 버스트형이라 부하를 만들다 발생기가 먼저 포화된다. 배포 도구와 측정이 섞인다(측정 중 배포가 돌면 결과가 엉킨다) |
| 배포 EC2 자신 | 네트워크 지연이 없다 | 발생기와 대상이 CPU를 나눠 써 측정이 왜곡된다 |
| 노트북 | 비용이 없다 | 한국 → 시드니 왕복 지연과 집·카페 네트워크가 결과에 섞인다 |
| **같은 VPC 임시 EC2** | 지연이 작고 일정하다. 측정 환경을 다시 만들기 쉽다 | 측정마다 띄우고 지우는 수고와 약간의 비용 |

- 발생기 후보는 연산형 `c6i.large`급(2 vCPU, 4GiB, 성능 고정)이다(`[가정]`). 시드니에서 시간당 0.111달러라 3시간 측정이면 약 0.33달러다(AWS 가격 데이터, 2026-11-05). 발생기 CPU도 같이 기록해, 발생기가 먼저 포화되지 않았는지 확인한다.
- 배포 서버를 flex에서 `m7i.xlarge`로 바꾼 것과 같은 이유로, 발생기도 버스트형·flex가 아닌 성능 고정 유형을 고른다.

### 3. 발생기는 어떻게 대상에 붙나
- gateway를 **VPC 사설 IP의 8080**으로 직접 부른다. 프론트 nginx(80)를 거치지 않는다(ADR 0040 4절, `load-test.md` 2절).
- 배포 compose는 gateway를 `8080:8080`으로 열어 두었고 지금은 보안 그룹이 외부를 막는다. 측정할 때 배포 서버 보안 그룹에 "발생기 보안 그룹에서 오는 8080"을 더한다. Jenkins → 배포 서버 SSH(22)를 보안 그룹 참조로 연 것과 같은 방식이다.

### 4. k6를 컨테이너로 띄우나
k6는 Go로 만든 실행 파일 하나라 설치가 가볍다. 두 방법 모두 된다.

| 방법 | 예 | 장점 | 단점 |
|---|---|---|---|
| Docker 이미지 1회 실행 | `docker run --rm --network host -v "$PWD/loadtest:/scripts" grafana/k6:<버전> run /scripts/open-peak.js` | 버전 고정이 쉽다(측정 환경 기록표에 그대로 적는다). 저장소의 `install-docker.sh`로 준비가 끝난다 | 처음 이미지를 받는 시간 |
| 바이너리 설치 | `apt install k6` 후 `k6 run open-peak.js` | 가장 단순하다 | 설치 시점마다 버전이 달라질 수 있다 |

- 어느 쪽이든 **배포 compose(`compose.deploy.yml`)에는 넣지 않는다.** 넣으면 배포 서버에서 돌게 되어 1절의 왜곡이 생긴다.
- `--network host`는 컨테이너 네트워크 변환을 거치지 않게 해서 발생기 쪽 오버헤드를 줄인다.

### 5. 아직 정하지 않은 것 (ISE-181 구현 때)
`docs/design/infra/load-test.md` 9절 기준이다.
- k6 스크립트 위치와 실행 방식(위 4절)
- k6 결과를 서버 Prometheus로 보내는 경로: Prometheus에 remote write 수신(`--web.enable-remote-write-receiver`)을 켜야 하고, 9090을 발생기 보안 그룹에만 열지, SSH 터널로 보낼지 정해야 한다
- 입장 토큰 확보 방식(ISE-69 발급 API 사용 / 측정용 서명 도구)
- 서비스별 자원 지표 도구(`docker stats` / cAdvisor)
- 시나리오별 가상 사용자 수·좌석 수
- ADR 0046의 상태는 아직 "제안"이다(ISE-25 담당과 분담 확인 필요)

## 면접 포인트
- 부하 발생기와 대상은 분리한다. 같은 기계에서 돌리면 서로 자원을 빼앗아 측정이 무의미해진다. 발생기 자원도 함께 기록해 "발생기가 먼저 포화됐는가"를 확인한다.
- 측정 위치는 대상과 같은 리전·같은 네트워크로 둔다. 인터넷 구간의 지연과 흔들림을 빼야 서버의 처리량·지연을 잴 수 있다.
- 부하 도구는 상주 서비스가 아니라 일회성 작업(job)이다. 운영 스택에 섞지 않고, 측정 환경(도구 버전, 장비, 커밋)을 기록해 다시 낼 수 있게 한다.
