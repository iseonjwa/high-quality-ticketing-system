# 접수형(async) 좌석 선점은 무엇이고, 왜 하며, 지금 어디까지 왔나

## 질문
- Linear의 접수형 선점(ISE-15~18)은 어떤 내용인가?

## 짧은 답
- **지금 방식(동기형)**: 좌석 선점 요청을 받은 서버가 그 자리에서 DB에 좌석을 잡고 결과(201과 결제 토큰)를 돌려준다.
- **접수형**: 서버는 "접수했다"만 기록하고 바로 `202 Accepted`와 접수 번호를 돌려준다.
  - 실제 선점은 Kafka 소비자가 줄을 세워 처리한다.
  - 사용자는 접수 번호로 결과를 조회한다.
- 목적은 두 가지다.
  1. 오픈 정각 몰림을 DB가 감당할 속도로 평탄하게 만든다.
  2. 발제 [필수] 요구를 채운다. 요구 문장: "API가 요청을 받으면 Kafka Topic에 적재하고 바로 응답한 뒤 Consumer가 처리"
- **지금 상태**
  - 네 이슈(ISE-15 상위, 16 접수·조회 API, 17 소비자·실패 처리, 18 재측정)가 모두 손대지 않은 상태다. 담당은 최권우다.
  - 토대 일부는 있다. `seat_hold_requests` 테이블은 동기형도 쓰고 있고, outbox도 공통 모듈에 있다.
  - 현재 main 코드에는 "API → Kafka → 바로 응답"을 하는 API가 없다. 202를 돌려주는 곳은 mock-pg의 장애 응답뿐이다.

## 자세히

### 1. 바탕 개념: 동기 처리와 접수 처리
- 은행 창구에 빗대면 이렇다.
  - **동기형**은 창구 직원이 그 자리에서 처리하고 결과를 준다. 손님이 몰리면 창구 앞 줄이 길어지고, 오래 기다리다 포기하는 손님(타임아웃)이 생긴다.
  - **접수형**은 번호표를 먼저 주고 뒤에서 순서대로 처리한다. 번호표는 바로 받지만, 결과는 조금 뒤에 확인해야 한다.
- 서버로 바꾸면
  - 동기형은 요청 스레드가 DB 작업이 끝날 때까지 커넥션을 쥔다. 동시 요청이 커넥션 풀(reservation-service는 5개)보다 많으면 줄이 서고, 응답 시한을 넘긴다.
  - 접수형은 API가 짧은 쓰기 한 번(접수 행 + outbox)만 하고 끝난다. 무거운 선점은 소비자가 정해진 속도로 처리한다. 순간 몰림이 Kafka에 쌓였다가 천천히 빠진다. 이것을 부하 평탄화(load leveling)라고 한다.

### 2. 이 프로젝트의 접수형 설계 (SA MASTER v3.3)
```
POST /api/v1/schedules/{scheduleId}/reservations
  └ 한 트랜잭션: seat_hold_requests(REQUESTED) + outbox_events 저장 → 202 + requestId
outbox 릴레이(500ms 폴링) → Kafka seat-hold.request (키 {scheduleId}:{section})
SeatHoldConsumer: 같은 구역 요청을 한 파티션에서 순서대로 소비
  └ 선점 시도(조건부 UPDATE) → seat_hold_requests HELD 또는 REJECTED
GET /api/v1/reservations/requests/{requestId} → HELD면 예약·결제 토큰
```
| 설계 요소 | 이유 |
|---|---|
| 접수 행과 outbox를 한 트랜잭션에 저장(설계 결함 D4) | "202는 줬는데 메시지가 사라진" 요청이 없게 한다. 바로 발행하면 DB 저장과 발행 중 하나만 성공할 수 있다 |
| 파티션 키 `{scheduleId}:{section}` | 같은 구역 요청이 한 줄로 처리돼 같은 좌석을 두고 다투는 잠금 경합이 준다. 구역이 여러 개라 인기 회차 하나라도 여러 파티션으로 나뉜다 |
| 정합성은 여전히 DB 조건부 UPDATE와 부분 유니크 인덱스 | Kafka 순서는 경합을 줄이는 장치일 뿐이고, 중복 판매 방지는 DB가 맡는다 |
| 실패 마감(E15) | 재시도 3회 뒤 DLQ로 가면 `REJECTED(PROCESSING_FAILED)`가 된다. 30초 넘게 REQUESTED면 `REJECTED(TIMEOUT)`이 되고, 늦게 온 메시지는 조건부 갱신이 0행이라 좌석을 잡지 않는다 |
| `seat-hold.mode` = `sync` / `async` | 같은 코드에서 두 방식을 바꿔 가며 같은 환경으로 비교 측정한다 |

### 3. 대가
- 결과를 아는 시점이 늦다. 목표는 접수 → 처리 완료 2초 이내다(outbox 폴링 500ms + 소비자 지연).
- 프론트에 "처리 중 → 결과 조회" 화면이 필요하다. 안준현 담당 ISE-120이며, ISE-16 API가 있어야 만든다.
- 상태가 하나 늘고(REQUESTED), 실패 경로(DLQ, 타임아웃, 늦은 메시지)를 모두 다뤄야 한다.
- Kafka가 멈추면 접수는 되지만 처리가 밀린다.

### 4. 왜 지금 중요한가
- **측정 이야기의 중심이다.**
  - SA 3-1과 10-5절의 발표 스토리는 "동기형 기준선 → 병목 확인 → 접수형 개선 → 재측정"이다.
  - 비교 대상은 세 가지다: 동기형, 직접 발행, outbox.
- **발제 [필수] 문장과 직접 이어진다.**
  - 지금 main 코드에서 이 모양을 하는 API는 없다.
  - 추첨 응모는 동기(201)이고, Kafka는 outbox 이벤트(결제 결과, 환불·자동결제 요청)에만 쓴다.
  - 이 요구를 무엇으로 채웠다고 말할지 팀이 확인해야 한다.
- **다만 K1 측정에서 먼저 무너진 것은 좌석 조회였다(ISE-189).**
  - 선점 경로 개선 효과를 재려면 좌석 조회 경량화(P4a 머지, P4b·P4c 남음)와 커넥션 대기 시한(ISE-196)이 먼저 정리돼야 한다.
  - 같은 서비스를 최권우·효승이 함께 고치고 있어 순서를 두 사람이 맞춰야 한다.

### 5. 팀이 정할 것 (11/12 중간 점검 전)
| 선택지 | 내용 | 비용 |
|---|---|---|
| 전부 | ISE-16·17 구현 + ISE-18 세 방식 비교 | 최권우 혼자는 측정 일과 겹쳐 빠듯하다 |
| 최소 | ISE-16·17(outbox 방식 하나) + ISE-18은 동기형 대 접수형 한 번 비교 | 발제 요구와 발표 스토리는 지킨다 |
| 미룸 | M4에서 빼고 발표에서 설계만 설명 | 발제 [필수] 요구를 무엇으로 채웠는지 따로 답해야 한다 |

## 면접 포인트
- 비동기 접수는 처리량을 늘리는 기술이라기보다 **몰림을 시간으로 펴는 기술**이다. 실제 처리 속도는 소비자와 DB가 정한다. 대신 API 응답이 빠르고 서버가 넘어지지 않는다.
- 202를 주는 순간 "요청을 잃지 않는다"는 약속이 생긴다. 그래서 접수 기록과 메시지 발행을 한 트랜잭션으로 묶는 Transactional Outbox가 필요하다.
- Kafka 파티션 순서는 경합을 줄이는 도구다. 정합성 보장은 DB 제약과 조건부 갱신에 맡긴다.
