# 오픈 시각이 되면 새로고침 없이 [예매하기]가 켜지는 것을 어떻게 구현했나

## 질문
프론트엔드에서 오픈 시각이 되면 자동으로 들어갈 수 있게 버튼이 새로고침되는 것을 어떻게 구현했나.

## 짧은 답
- 새로고침하지 않고, 그 순간 서버에 다시 묻지도 않는다. 화면을 처음 받을 때 서버 시각(`serverTime`)을 한 번 받는다. 그 뒤로는 화면이 "지금"을 스스로 계산하고, 그 값으로 판매 상태(오픈 전·예매 중·판매 종료)를 다시 정한다.
- "지금"은 브라우저 시계가 아니라 서버 시각으로 보정한 시계다. 차이(offset)는 응답을 받은 순간 한 번만 잰다.
- 카운트다운은 250ms마다 다시 그린다. "00:00"이 보이는 순간 `onComplete`가 예매 패널을 다시 그리고, 그때 상태가 예매 중으로 바뀌어 버튼이 켜진다.
- 자동으로 대기열에 들어가지는 않는다. 버튼이 켜지기만 하고 누르는 것은 사용자다. 오픈 여부의 최종 판정은 서버 대기열 진입 API다. 오픈 전이면 409 `SALE_NOT_OPEN`으로 거절한다.

## 자세히

### 1. 왜 오픈 순간에 서버에 다시 묻지 않나
"오픈 순간 상세를 다시 받아 `saleStatus`를 확인한다"는 방식은 맞는 값을 얻지만, 오픈 대기 중인 사용자 전원이 같은 초에 상세 API를 다시 부른다. 티켓 오픈 순간은 가장 부하가 큰 때다. 그 순간 예매와 상관없는 조회가 같이 몰린다. 상태를 정하는 규칙(오픈 시각 ≤ 지금 < 공연 시작)이 단순하므로, 시각만 정확하면 브라우저도 서버와 같은 답을 낼 수 있다. 같은 이유로 탭을 오갈 때 다시 조회하는 React Query 기본 동작(`refetchOnWindowFocus`)도 껐다.

### 2. 왜 브라우저 시계를 믿지 않나 (clock skew)
사용자 PC 시계는 몇 초에서 몇 분까지 틀릴 수 있다. 브라우저 시계로 세면 시계가 빠른 사용자에게는 버튼이 먼저 켜지고, 느린 사용자에게는 늦게 켜진다. 그래서 응답에 서버 시각을 함께 받아 차이를 잰다.

```text
offset = serverTime - 응답을 받은 순간의 Date.now()
지금   = Date.now() + offset
```

- 차이는 **응답을 받은 순간**으로 잰다. 화면을 그린 순간의 `Date.now()`로 재면, 캐시에서 꺼낸 응답이나 다시 그린 화면에서 캐시 나이만큼 시계가 늦어진다. 그래서 React Query의 `dataUpdatedAt`(응답을 받은 시각)을 넘긴다.
- 서버가 시각을 적은 뒤 응답이 도착하기까지 걸린 시간(왕복의 절반 안팎)만큼은 늦게 잡힌다. 왕복 시간까지 빼는 NTP식 보정도 있지만, 오픈 카운트다운에서는 수십 ms 오차를 허용했다.

### 3. 타이머로 다시 그리기와 숨긴 탭
React는 상태가 바뀔 때만 다시 그린다. 시간은 흘러도 상태가 아니므로, 주기 타이머(`setInterval`)로 일부러 다시 그리게 만든다.

- 시각을 상태로 들고 있지 않는다. 타이머는 "다시 그려라" 신호(카운터 증가)만 보내고, 그릴 때 `clock.now()`를 읽는다. 그래서 다시 조회해 시계가 바뀌면 다음 주기를 기다리지 않고 바로 새 시계로 그린다.
- 숨긴 탭에서는 브라우저가 타이머를 최대 1분까지 늦춘다. 오픈 직전에 다른 탭을 보다 돌아오면 숫자가 멈춰 있을 수 있어서, `visibilitychange`로 탭이 다시 보이는 순간 바로 다시 그린다.

### 4. 남은 시간은 초 단위로 올린다
0.9초 남았을 때 내림하면 "00:00"인데 아직 오픈 전이라 버튼이 꺼져 있다. 올림하면 "00:01"이고, "00:00"이 보이는 순간과 실제 오픈(남은 시간 ≤ 0)이 같아진다.

## 이 프로젝트에서는

흐름은 네 단계다.

1. 공연 상세 응답의 `serverTime`과 `dataUpdatedAt`으로 서버 시계를 한 번 만든다. `useMemo`로 고정해 다시 그릴 때마다 차이를 다시 재지 않게 한다.
   - `frontend/src/pages/concerts/ConcertDetailPage.tsx:47`, `frontend/src/lib/serverClock.ts:12`
2. `useNow(주기, clock)`가 주기마다 다시 그리고, 탭이 다시 보이면 즉시 그린다.
   - `frontend/src/lib/serverClock.ts:25`
3. 판매 상태는 응답의 `saleStatus`를 그대로 쓰지 않고 `saleStatusAt(openAt, startsAt, 지금)`으로 다시 정한다. 규칙은 서버 `Schedule.saleStatusAt`과 같다. 서버가 `CLOSED`라고 하면 시각과 상관없이 따른다.
   - `frontend/src/lib/saleStatus.ts:7`
4. 고른 회차 패널(`ChosenSchedule`)은 그릴 때마다 `clock.now()`로 상태를 정한다. 오픈 전이면 카운트다운과 꺼진 버튼을 보인다. 카운트다운(250ms 주기)이 0이 되면 `onComplete`로 패널을 다시 그리고, 상태가 예매 중으로 바뀌어 대기열로 가는 링크 버튼이 된다.
   - `frontend/src/pages/concerts/ConcertDetailPage.tsx:342`, `frontend/src/components/ticketing/Countdown.tsx:27`

고친 문제 두 가지(ISE-187).
- **"00:00"인데 버튼이 꺼져 있던 1초**: 처음에는 패널이 부모의 1초 주기 값을 받아 상태를 정했다. 카운트다운은 250ms마다 0을 보이는데 버튼은 다음 1초 주기까지 꺼져 있었다. 테스트 작업자가 찾았다. 패널이 그릴 때 직접 시계를 읽고, 카운트다운 `onComplete`로 다시 그리게 바꿨다.
- **`onComplete`가 두 번 불리는 경우**: 오픈 순간 다시 조회한 응답이 늦게 오면 새로 잰 차이가 조금 작아진다. 그러면 막 0을 넘긴 남은 시간이 다시 양수가 될 수 있다. 그래서 "이미 불렀다"는 기록은 남은 시간이 아니라 목표 시각(`targetAt`)이 바뀔 때만 지운다(`Countdown.tsx:38`).

접근성: 카운트다운은 `role="timer"`라서 화면 낭독기가 매초 읽지 않는다. 보는 중에 열렸을 때만 `aria-live` 영역에 "예매가 열렸어요"를 넣는다(`ConcertDetailPage.tsx:407`). 알림 영역은 처음부터 있어야 낭독기가 바뀐 내용을 읽으므로 빈 채로 미리 둔다.

최종 판정은 서버다. 화면 시계가 틀려 버튼이 일찍 켜져도, 대기열 진입 API가 오픈 전이면 409 `SALE_NOT_OPEN`으로 거절한다(`reservation-service/.../queue/application/QueueService.java:39`). 화면은 "아직 오픈 전이에요"를 보인다(`frontend/src/pages/queue/queueAdmission.ts:163`). 프론트 계산은 사용자 경험용이고, 오픈 시각은 서버가 지킨다. 다만 서버가 막는 것은 "정각 전 입장"뿐이다. 정각 직후 누가 먼저 서는지는 도착 순서라서, API를 직접 쏘는 사람이 버튼을 누르는 사람보다 앞에 선다([후속 질문](2026-11-08-queue-fairness-frontend-vs-direct-api.md)).

검증: 11/2에 브라우저 시계를 1시간 바꿔도 서버 기준으로 세고 오픈 순간 새로고침 없이 버튼이 켜지는 것을 실서버로 확인했다. 테스트는 `Date`와 `setInterval`만 가짜 타이머로 돌려 "1시간 어긋난 시계 + 3초 뒤 오픈"을 검증한다([11/2 하루 정리](../daily/2026-11-02.md)).

## 면접 포인트
- "오픈 시각에 버튼을 켜려면 서버를 폴링하나요?" → 아니다. 오픈 순간의 폴링은 가장 바쁠 때 부하를 더한다. 서버 시각으로 보정한 시계로 브라우저가 상태를 계산하고, 최종 판정은 진입 API가 한다.
- "클라이언트 시계가 틀리면?" → 응답의 서버 시각과 수신 시각으로 offset을 잰다. 남는 오차는 편도 지연 정도이고, 그래도 일찍 누르면 서버가 409로 거절한다.
- "숨긴 탭에서 타이머가 늦어지는 문제는?" → 브라우저가 백그라운드 타이머를 늦춘다. `visibilitychange`로 다시 보이는 순간 즉시 다시 계산한다. 시각을 상태로 쌓지 않고 그릴 때 읽으므로 밀린 틱을 따라잡을 필요가 없다.
