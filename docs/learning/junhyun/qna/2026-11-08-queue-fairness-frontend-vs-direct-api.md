# 프론트를 거치는 사람은 API를 직접 쏘는 사람보다 대기열에 늦게 서지 않나

## 질문
오픈 시각에 화면이 스스로 [예매하기]를 켜는 방식이면, API로 직접 요청을 쏘는 사람에 비해 프론트를 거치는 사람이 늦게 요청을 보내는 문제가 생기지 않나.
([앞 질문: 오픈 시각에 버튼이 켜지는 구현](2026-11-08-open-countdown-button-without-refresh.md)의 후속)

## 짧은 답
- 생긴다. 지금 대기열 순번은 Redis에 도착한 순서(`INCR`) 하나로 정한다. 그래서 오픈 정각에 진입 API를 바로 부르는 스크립트가 버튼을 보고 누르는 사람보다 앞에 선다.
- 차이의 대부분은 사람의 반응 시간이다. 프론트 쪽 지연(카운트다운 주기, 시계 보정 편향)은 줄일 수 있지만, 줄여도 사람은 스크립트를 이기지 못한다.
- 원인은 프론트가 아니라 "순번 = 도착 순서"라는 규칙이다. 근본 대책은 도착 속도가 순번을 정하지 않게 바꾸는 것이다. SA는 일부 좌석을 추첨으로 배분하는 것을 해법으로 골랐고, 사전 대기실과 무작위 순번은 Could로 남겼다.
- 서버가 이미 막는 것: 오픈 전 진입(409), 한 계정의 여러 순번, 입장 토큰 넘겨주기, 매수 초과. 아직 없는 것: 사용자별 요청 제한. 오픈 전 연타에 벌칙이 없다.

## 자세히

### 1. 어디서 늦어지나
프론트 사용자의 진입 요청은 오픈 시각보다 아래 시간만큼 늦게 출발한다(값은 추정, 측정하지 않음).

| 지연 | 크기 | 줄일 수 있나 |
|---|---|---|
| 시계 보정 편향: 상세 응답이 오는 데 걸린 편도 시간만큼 화면 시계가 늦다 | 수~수십 ms | 왕복 시간의 절반을 더해 보정하면 줄어든다 |
| 카운트다운 주기: 0이 된 뒤 첫 250ms 틱에 버튼이 켜진다 | 0~250ms | 오픈 시각에 맞춘 `setTimeout`으로 없앨 수 있다 |
| 사람 반응: 버튼이 켜진 것을 보고 누르기까지 | 보통 0.2~0.5초 이상 | 없다 |
| 클릭 → 대기열 화면 → 진입 요청 | 수 ms(화면 이동만 하고, 대기열 화면은 이미 번들에 있다) | 거의 없다 |

스크립트는 시계를 NTP로 맞춰 정각에 쏘거나, 오픈 전부터 짧은 간격으로 연타한다. 오픈 전 요청은 409로 끝날 뿐 벌칙이 없다. 그래서 오픈 직후 첫 요청이 바로 순번을 받는다.

### 2. 순번이 도착 순서라서 생기는 차이
진입 Lua는 이미 줄에 있으면 기존 순번을 돌려주고, 없으면 `INCR`로 다음 번호를 준다. 정렬 기준이 Redis 도착 순서 하나다. 서버 시계 차이와 같은 ms 동점 문제를 없애려고 고른 방식이다(SA 결정 기록 #27). 대신 먼저 도착한 사람이 무조건 앞이다.

예를 들어 오픈 첫 1초에 2만 명이 고르게 들어오면, 0.5초 늦은 사람은 약 1만 번 뒤에 선다. 입장 속도가 초당 N명이라 그만큼 늦게 입장하고, 그사이 좋은 좌석은 팔린다.

### 3. 프론트를 빠르게 해도 풀리지 않는 이유
- 줄일 수 있는 프론트 지연은 많아야 약 0.3초다. 사람 반응 시간은 남는다.
- 프론트가 오픈 정각에 진입 요청을 자동으로 쏘게 만들면 반응 시간도 없앨 수 있다. 하지만 그건 모든 사용자에게 매크로를 나눠 주는 것과 같다. 그래도 회선이 가깝거나 계정이 많은 쪽이 이긴다. 겨루는 대상이 사람과 스크립트에서 스크립트끼리로 바뀔 뿐이다.
- 결국 "누가 먼저 도착했나"로 순번을 정하는 한 속도 경쟁은 남는다.

### 4. 도착 속도가 순번을 정하지 않게 하는 방법
| 방법 | 내용 | 효과와 비용 |
|---|---|---|
| 추첨 배분 (이 프로젝트 F6, 구현됨) | 일부 좌석을 응모 기간에 받고 추첨한다 | 그 좌석은 속도와 무관하다. 일반 예매 좌석의 속도 경쟁은 그대로다 |
| 사전 대기실 + 무작위 순번 (SA Could) | 오픈 전 일정 시간 동안 대기실 입장을 받고, 오픈 순간 대기실 안 사람의 순번을 무작위로 섞는다. 그 뒤 도착자는 도착 순 | 오픈 전에 와 있기만 하면 ms 경쟁이 사라진다. Queue-it 같은 대기열 서비스의 사전 대기열 방식이다. 진입 Lua·오픈 전 409 규칙·대기열 화면이 바뀐다 |
| 사용자별 요청 제한 (SA 12-8 `ratelimit:{userId}`, 미구현) | 1초 안 요청 수를 세어 넘으면 429 | 연타 부하를 줄인다. 정각에 한 번 쏘는 스크립트는 못 막는다 |
| 보안문자 (SA Could) | 진입 전에 사람인지 확인한다 | 스크립트 비용을 올린다. 사람도 느려진다 |
| 계정 비용 올리기 (본인 인증, SA Won't) | 계정을 여러 개 만들기 어렵게 한다 | 사전 대기실과 함께 써야 효과가 크다. 무작위여도 계정이 많으면 당첨 확률이 오른다 |

무작위로 섞어도 계정을 여러 개 가진 사람은 여전히 유리하다. 그래서 사전 대기실은 계정당 1자리·매수 제한과 함께 써야 한다.

## 이 프로젝트에서는
- 순번: `reservation-service/src/main/resources/redis/queue/enter.lua`가 `INCR`로 도착 순서를 순번으로 준다. 계정당 1자리라 연타해도 순번이 늘지 않는다.
- 오픈 판정: 같은 Lua가 Redis `TIME` 하나로 판정한다. 인스턴스 시계나 사용자 시계와 무관하게 아무도 정각 전에 줄에 서지 못한다. 오픈 전이면 `QueueService`가 409 `SALE_NOT_OPEN`을 던진다.
- 입장 토큰: Gateway가 토큰의 `sub`와 로그인 사용자를 비교해 넘겨주기를 막는다(ADR 0015).
- 요청 제한: 공통 오류 코드 `RATE_LIMITED`(429)는 있다. 하지만 Gateway·nginx·서비스에서 제한기를 찾지 못했다(2026-11-08 `origin/dev` 기준). 오픈 전 연타도 Gateway 인증 → 서비스 → 회차 조회 → Lua까지 매번 간다.
- SA 1-1은 문제를 "매크로·회선 속도가 순서를 정한다"로 적었다. 1-2의 해법은 "좌석 일부를 추첨으로 배분, 매수 제한, 입장 토큰"이다. 일반 예매의 속도 경쟁은 알고도 남긴 범위다.

## 면접 포인트
- "대기열이 있으면 매크로를 막을 수 있나?" → 대기열은 서버를 보호하고 입장 속도를 조절한다. 순번이 도착 순서면 빠른 쪽이 앞에 서므로 매크로 대책은 아니다. 공정성은 순번 규칙(사전 대기실 무작위, 추첨)과 계정·요청 통제로 따로 다룬다.
- "프론트 타이밍을 정밀하게 맞추면 되지 않나?" → 줄일 수 있는 것은 수백 ms다. 사람 반응 시간은 남는다. 자동으로 쏘게 하면 모두가 매크로를 쓰는 셈이라 문제가 회선과 계정 수 경쟁으로 옮겨 갈 뿐이다.
- "왜 도착 순서로 정했나?" → 여러 인스턴스의 시계 차이와 같은 ms 동점을 피하려고 Redis 한 곳의 `INCR`을 기준으로 삼았다. 정확하고 단순한 대신 속도 경쟁을 그대로 반영한다. 이 trade-off를 추첨 배분으로 보완했다.
