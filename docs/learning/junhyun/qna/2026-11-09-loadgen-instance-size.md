# 부하 발생기 EC2는 얼마나 커야 하나 (c6i.large와 c6i.xlarge)

## 질문
"이렇게 큰 EC2 서버를 써야 해?" 팀 공용 k6 발생기 안내(ISE-94)가 `c6i.xlarge`(4 vCPU, 8GiB)를 쓰라고 해서 나온 질문이다.

## 짧은 답
- 모든 시나리오에 xlarge가 필요한 것은 아니다. Q2·Q3(VU 300개)는 `c6i.large`로도 충분하다.
- xlarge가 필요한 근거는 두 가지다. K1은 좌석 조회 응답이 커서 네트워크가 막히고, Q1은 VU를 2,000개 미리 만들어서 메모리가 빠듯하다.
- 두 유형의 차이는 시드니 기준 시간당 0.111달러다. 20시간을 써도 약 2.2달러다.
- 크기를 고르는 기준은 요금이 아니다. 발생기가 먼저 막히면 그 측정 결과는 쓸 수 없고 다시 재야 한다. 다시 재는 비용(배포 서버 요금, 측정 모드 재설정, 팀원 시간)이 요금 차이보다 크다.

## 자세히

### 발생기가 먼저 막히면 왜 문제인가
부하 측정은 "서버가 어디까지 버티나"를 재는 일이다. 발생기의 CPU·메모리·네트워크가 먼저 한계에 닿으면, 지연이 늘거나 요청을 덜 보낸 원인이 서버인지 발생기인지 가를 수 없다. k6에서는 정한 도착률을 못 맞춘 반복이 `dropped_iterations`로 남는다. 이 값이 0이 아니고 발생기 자원도 꽉 찼다면, 그 결과를 서버의 한계로 해석하면 안 된다.

k6 문서가 주는 발생기 기준은 다음과 같다(Running large tests).
- CPU: k6 사용률을 80% 이하로 두고 20%는 비워 둔다. 모든 코어가 100%면 결과가 나빠진다.
- 메모리: 사용률이 90%를 넘지 않게 한다. 간단한 스크립트는 VU 하나에 약 1~5MB를 쓴다(VU 1,000개면 1~5GB).
- 응답 본문: k6는 기본으로 응답 본문을 메모리에 올린다. 본문이 필요 없으면 `discardResponseBodies: true`로 메모리를 아낀다.
- 네트워크: 1Gbit/s 근처에서 일정하게 머물면 네트워크 카드가 한계일 가능성이 높다.

### 두 유형의 차이
| 항목 | `c6i.large` | `c6i.xlarge` |
|---|---|---|
| vCPU / 메모리 | 2 / 4GiB | 4 / 8GiB |
| 네트워크 기준 대역폭 | 0.781Gbps | 1.562Gbps |
| 시드니 시간당 요금 | 약 0.111달러 | 약 0.222달러 |

두 유형 모두 "최대 12.5Gbps"로 표기되지만, 그 속도는 네트워크 크레딧이 남아 있는 동안만 나는 순간 속도다. 크레딧이 얼마나 오래 가는지는 보장되지 않으므로, 측정 계획은 기준 대역폭으로 세운다.

`t3` 같은 버스트형은 더 싸지만 발생기로 쓰지 않는다. CPU 크레딧이 떨어지면 CPU가 기준치로 묶이거나(standard), 초과분 요금이 붙는다(unlimited). 측정 도중에 발생기 성능이 바뀌면 결과를 믿을 수 없다.

### 시나리오별로 필요한 것
기본값은 저장소의 k6 스크립트에서 읽었다(2026-11-09 dev 기준).

| 시나리오 | 기본 부하 | 먼저 막힐 자원 | large로 되나 |
|---|---|---|---|
| Q2 순번 폴링, Q3 입장 | VU 300개 | 없음 | 된다 |
| Q1 대기열 진입 | 30,000명을 10초에(초당 3,000건), VU 2,000개를 미리 만들고 최대 5,000개 | 메모리. 2,000개 × 1~5MB = 2~10GB | 빠듯하다. 4GiB에서 OS와 Docker 몫을 빼면 위쪽 범위에서 부족하다 |
| G1 Gateway 인증 | 초당 최대 8,000건 | CPU | 미확인. 발생기 CPU를 보며 판단한다 |
| K1 좌석 선점 | 좌석 조회 응답 약 830KB. 초당 100건이면 약 0.66Gbps, 기본 단계 끝(초당 320건)이면 약 2.1Gbps | 네트워크 | 안 된다. 0.781Gbps에 거의 바로 닿는다 |

VU 하나가 실제로 몇 MB를 쓰는지는 아직 재지 않았다. k6 문서는 VU 100개로 돌려 보고 메모리 사용량에 목표 VU 수를 곱하라고 권한다.

K1은 xlarge(1.562Gbps)로도 초당 320건 단계까지 보낼 수 없다. 배포 서버 `m7i.xlarge`의 기준 대역폭도 같은 1.562Gbps라 서버 쪽 네트워크도 비슷한 지점에서 막힌다. 그 단계까지 간다면 응답 크기를 줄이는 것(좌석 조회 응답 압축이나 분할)이 측정 대상이 된다.

### 고르는 방법
1. **xlarge 하나로 계속 쓴다**: 시나리오마다 유형을 바꿀 일이 없다. 콘솔은 계정 주인만 쓸 수 있으므로, 유형을 바꿔야 하면 그때마다 계정 주인이 해야 한다.
2. **large로 시작하고 필요하면 바꾼다**: 중지 → 인스턴스 유형 변경 → 시작에 몇 분이면 된다. 사설 IP는 그대로라 보안 그룹 규칙은 고칠 필요가 없지만, 퍼블릭 IP가 바뀌어 팀에 다시 알려야 한다. 바꾸는 기준은 k6 문서의 CPU 80%, 메모리 90%와 네트워크 0.78Gbps 근처다.

- 측정 중에는 발생기에서 `docker stats`로 k6 컨테이너의 CPU·메모리를 기록하고, k6 요약의 `dropped_iterations`를 같이 본다(`load-test.md` 2-1절 5번).

## 면접 포인트
- **부하 테스트 결과를 어떻게 믿을 수 있나?** 발생기와 대상 서버를 다른 기기에 두고, 발생기 CPU·메모리·네트워크와 `dropped_iterations`를 같이 기록한다. 발생기가 먼저 포화됐으면 서버 한계로 해석하지 않는다.
- **발생기 크기는 어떻게 정했나?** 시나리오별로 먼저 막힐 자원을 계산했다. 응답이 큰 시나리오는 네트워크(응답 크기 × 초당 건수), VU를 많이 미리 만드는 시나리오는 메모리(VU 수 × VU당 메모리)를 봤다. 요금 차이보다 측정을 다시 하는 비용이 커서, 가장 무거운 시나리오를 견디는 유형을 골랐다.
- **왜 버스트형(t3)을 안 썼나?** CPU 크레딧이 떨어지면 성능이 바뀌어 측정 조건이 흔들린다. 연산형(c 계열)은 성능이 고정이다.
