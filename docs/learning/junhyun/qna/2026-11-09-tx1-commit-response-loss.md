# ISE-169 결제 TX1 커밋 응답 유실은 무엇이고, 왜 "재시도가 이어받기" 원안으로는 풀리지 않나

## 질문
ISE-169 이슈를 자세히 설명해 달라.

## 짧은 답
- DB가 2초 넘게 멈춘 순간 TX1(결제 행 만들기)의 커밋 응답을 받지 못하면, 서버는 실패로 보고 503을 준다. 그런데 커밋은 DB가 풀린 뒤 실제로 끝날 수 있다.
- 그러면 "PG를 부르지 않은 `REQUESTED` 결제"가 남는다. 재시도해도 PG를 부르지 않고, 재확인 스케줄러가 이 결제를 `DECLINED(NOT_SENT)`로 닫는다.
- 그 예매는 다시 결제할 수 없다. 돈은 나가지 않는다(승인 0). 사용자는 좌석을 다시 잡아야 한다.
- 이슈 원안은 "재시도가 PG 호출 기록이 없는 `REQUESTED`를 이어받아 승인한다"이다.
  - 그런데 지금은 "PG를 안 불렀다"를 확정할 방법이 없다.
  - 확정하려고 호출 직전 표시를 커밋하면, 그 커밋의 응답도 똑같이 잃을 수 있다. 문제가 없어지지 않고 자리만 옮긴다.
- 추천은 원안을 거부하고 한계를 ADR로 기록하는 것(B)이다. 측정에서 실제로 관측되면 TX1 커밋에만 시한을 길게 거는 G안으로 간다.

## 자세히

### 1. 바탕 개념

**커밋과 커밋 응답은 다른 사건이다**
- 애플리케이션이 `COMMIT`을 보내면 DB는 WAL(변경 기록)을 디스크에 쓰고 나서 "끝났다"는 응답을 돌려준다.
- 네트워크에서 "보냈는데 답이 없다"는 성공인지 실패인지 모르는 상태다. 요청이 안 닿았을 수도, 처리는 됐는데 응답만 늦거나 사라졌을 수도 있다.
- 비유: 택배를 맡기고 송장 번호를 받기 전에 창구가 멈췄다. 택배가 접수됐는지는 창구가 다시 열려야 안다. "모르니까 또 보내자"고 하면 두 번 갈 수 있다.

**소켓 시한(socket timeout)**
- DB 연결에서 응답을 기다리는 최대 시간이다. 넘으면 클라이언트가 연결을 버리고 예외를 던진다.
- ISE-163(PR #278)에서 결제 DB 연결에 2초를 걸었다(`config-repo/payment-service.yml`의 `socketTimeout: 2`). DB가 멈췄을 때 요청 스레드가 끝없이 기다리지 않게 하려는 것이다.
- 시한은 "클라이언트가 그만 기다린다"일 뿐이다. 서버에 이미 닿은 커밋을 취소하지 않는다. 이슈는 PostgreSQL이 커밋 기록 중에는 문장 시한으로도 취소하지 않는다고 적었다. 이 전제는 아직 직접 검증하지 않았다.

**멱등키(Idempotency-Key)**
- 같은 요청을 여러 번 보내도 결과가 한 번 처리한 것과 같게 하는 키다.
- 우리 결제는 같은 키로 다시 오면 새로 처리하지 않고 기존 결제의 현재 상태로 답한다(ADR 0017).

### 2. 이 프로젝트의 결제 흐름 (payment-service)

**한 번의 결제 요청**
1. 같은 키 조회 → 토큰 검증 → 같은 예매의 기존 결제 조회 → PG 호출 허가 얻기
2. **TX1**: `REQUESTED` 결제 행과 멱등 기록(ORIGIN)을 한 트랜잭션에 저장한다(`PaymentTx.createRequested`).
3. PG 승인 호출. PG 멱등키는 주문 번호(`pg_order_id`)에서 만든다.
4. **TX2**: 결과(`APPROVED`·`DECLINED`·`UNKNOWN`)를 저장한다.

**안전장치 셋**
- TX1에서 DB 오류가 나면 "PG 호출 전이라 같은 키로 다시 시도할 수 있다"고 보고 503을 준다(`PaymentApprovalService.java:102-108`).
- 같은 키 재시도는 저장된 응답이 없으면 결제의 현재 상태로 답하고, PG를 부르지 않는다(`replay`). `REQUESTED`면 202다.
- **재확인 스케줄러**는 `REQUESTED`·`UNKNOWN` 결제를 10초 뒤부터 다시 본다(`PaymentRecheckService`).
  - PG에 주문을 조회한다.
  - PG가 주문을 모르면(NotFound) "늦은 승인 방지"(망취소)를 부른다.
  - 막았으면(Prevented) `DECLINED(NOT_SENT)`로 닫는다.

**규칙 셋(결정 기록)**
- 0017: 같은 키는 현재 상태로 응답하고 PG를 부르지 않는다.
- 0018: PG 호출 허가는 TX1보다 먼저 얻는다. 같은 키 응답은 허가 없이 나간다.
- 0023 결정 7: 승인은 결제 행 하나에 한 번, 승인 요청 스레드만 부른다. PG 쪽 멱등(특히 토스)이 확인되지 않아 거기에 기대지 않으려는 것이다.
- 0026: 결제는 예매당 하나다(`UNIQUE(reservation_id)`). 닫힌 결제가 있는 예매에 다시 결제하면 409 `PAYMENT_ALREADY_CLOSED`다.

### 3. 무슨 일이 생기나 (시간 순서)
1. t=0: TX1이 `COMMIT`을 보낸다. 그 순간 DB가 멈춘다(컨테이너 정지, WAL 기록 지연).
2. t=2초: 소켓 시한이 지난다. 서버는 TX1이 실패했다고 보고 503을 준다.
3. DB가 풀리면서 커밋이 끝난다. `REQUESTED` 결제와 멱등 기록이 남고, PG는 불리지 않았다.
4. 사용자가 같은 키로 다시 보낸다. 멱등 기록이 있으니 현재 상태 `REQUESTED`로 202를 받는다. 여기서도 PG는 부르지 않는다(0017).
5. 10초 뒤 재확인 스케줄러가 PG에 조회한다. PG는 이 주문을 모른다 → 늦은 승인 방지 → `DECLINED(NOT_SENT)`.
6. 이 예매는 결제가 닫혔다. 다시 결제하면 `PAYMENT_ALREADY_CLOSED`다(0026). 선점 시간이 끝나면 좌석이 풀리고, 사용자는 처음부터 다시 예매해야 한다.

- 돈은 안전하다. 승인 호출이 한 번도 없었다.
- 손해는 사용자 경험이다. 결제를 눌렀는데 실패하고 좌석을 잃는다.
- 같은 결말이 FT-3 "TX1 커밋 뒤 프로세스 중단"에도 있다. ISE-163 전에는 시한이 없어서 커밋 응답을 끝까지 기다렸고, 승인까지 갔다.

### 4. 이슈 원안과 그 문제
원안: 같은 키 재시도가 "PG 호출 기록이 없는" `REQUESTED`를 만나면 새 결제를 만들지 않고, 같은 주문 번호와 PG 멱등키로 승인을 이어 간다.

**(1) "PG 호출 기록 없음"을 지금은 판정할 수 없다**
- `payments` 테이블에는 PG를 불렀다는 기록이 없다. 환불에만 `refunds.pg_requested_at`이 있다.
- 그래서 `REQUESTED`에는 네 경우가 섞인다.
  - ① TX1 응답 유실: PG를 안 불렀다.
  - ② 원 요청이 지금 PG를 부르는 중이다.
  - ③ PG는 승인했는데 TX2가 실패했다.
  - ④ PG 승인 뒤 프로세스가 죽었다.
- ②③④는 PG를 이미 불렀다. 여기서 재시도가 또 승인을 부르면 같은 결제를 두 번 승인 요청하게 된다. 이중 승인(INV-1) 위험이다.
- 행이 만들어진 지 몇 초인지로 가르는 것은 시간 가정이지 확정이 아니다.

**(2) 판정하려고 표시를 두면 문제가 자리만 옮긴다**
- "PG 부르기 직전에 `pg_requested_at`을 커밋하고, 그 응답을 받은 뒤에만 호출한다"고 하면 "표시 없음 = 안 불렀음"이 성립한다.
- 그런데 이 표시 커밋의 응답도 2초를 넘길 수 있다.
  - 원 요청은 호출하지 않고 503을 준다. 표시는 나중에 커밋된다.
  - 재시도는 표시가 있으니 이어받지 못한다. 지금과 같은 `NOT_SENT` 결말이다.
- 반대로 응답 없이 호출을 강행하면, 표시가 끝내 안 닿았을 때 재시도도 호출해서 승인이 두 번 간다.
- 결국 "PG 호출 전 마지막 커밋의 응답 유실"은 구조적으로 남는다. 위치만 TX1에서 표시 커밋으로 옮긴다. 대가로 모든 결제 요청에 DB 왕복이 하나 는다.

**(3) 표시 없이 같은 PG 멱등키로 다시 부르면**
- 두 번 불러도 PG가 멱등키로 한 번만 승인해 준다면 안전하다.
- 하지만 그러면 "행당 승인 1회" 보장을 우리 코드가 아니라 PG 멱등에 맡기게 된다(0023 결정 7과 어긋남).
- 토스가 승인(confirm)에도 멱등키를 지키는지는 문서로 확인되지 않았다(ISE-45 조사).

**(4) 결정 세 개를 모두 바꿔야 한다**
- 0017(같은 키는 PG를 안 부름), 0018(같은 키 응답은 허가 없이), 0023(승인은 요청 스레드만 한 번)

### 5. 선택지
| 안 | 내용 | 효과 | 비용 |
|---|---|---|---|
| A 원안 | 호출 직전 표시 + 재시도 이어받기 | 거의 없음(문제 위치만 이동) | 스키마 변경, 승인마다 DB 왕복, ADR 3개 수정 |
| D | 표시 없이 같은 멱등키로 재승인 | TX1 유실·TX2 실패 모두 복구 | 행당 승인 1회를 PG 멱등에 맡김, 토스 미확인 |
| E | 원 요청이 "안 보냈다"는 포기 표시를 남기고, 재시도가 그때만 한 번 이어받음 | 안전하지만 효과가 좁음 | 컬럼 2개, 비동기 기록, ADR 3개 수정 |
| G | TX1 커밋에만 소켓 시한을 8초로 따로 건다 | 원 요청이 커밋 응답을 끝까지 받아 승인까지 감. 결정 3개 그대로 | 반나절. 느린 DB에서 요청 스레드가 최대 8초 묶임(동시 승인 10으로 제한). 8초를 넘으면 여전히 같은 결말 |
| **B (추천)** | 바꾸지 않고 ADR로 한계와 재검토 조건을 남김 | 판단과 근거 보존 | 약 1시간 |

- G의 8초는 첫 재확인(행 생성 10초 뒤)보다 짧게 잡은 값이다. 원 요청이 기다리는 동안 스케줄러가 먼저 손대지 않게 하려는 것이다.
- G를 하면 Gateway 3초 시한 때문에 사용자는 504를 받을 수 있다. 결제 처리는 계속되고, 같은 키 재시도로 결과를 받는다(S-26).

### 6. 추천 이유
- 돈은 안전하다(승인 0).
- 커밋 응답이 2초 넘게 늦을 때만 생기는 드문 경우다. 우선순위도 Low다.
- 원안이 효과가 없다는 판단 자체가 기록할 가치가 크다. AI(11/3 Opus 리뷰)가 낸 방안을 검토 끝에 거부한 사례라 발제의 "AI 설계 검증 로그(거부)"에 쓸 수 있다.
- 감시 신호가 이미 있다. 늦은 승인 방지가 실제로 막은 횟수(`payment_pg_call_seconds_count{operation="prevent_late_approval",outcome="prevented"}`)다. 부하 측정에서 이 값이 0이 아니면 G를 한다.

### 7. B로 갈 때 남길 것
- ADR(번호는 머지 때 확인): "TX1 커밋 응답 유실로 남은 `REQUESTED`는 재시도가 이어받지 않고, 재확인의 `DECLINED(NOT_SENT)` 종결을 한계로 둔다."
- 문서
  - `events-and-reliability.md` 7절의 "따로 다룬다"를 ADR 링크로 바꾼다.
  - `api.md`·`failure-scenarios.md`의 "503(행 없음)"에 "커밋 응답 유실이면 행이 남는다"를 덧붙인다.
- 선택: 응답 방향만 멈추는 프록시로 커밋 응답 유실을 재현하는 테스트. G를 하면 필수다.

## 면접 포인트
- "타임아웃은 실패가 아니라 모름이다." 커밋 응답을 못 받으면 커밋됐는지 모른다. 이런 모름을 재시도로 메우려면 "정말 안 보냈다"는 근거가 필요하고, 그 근거를 만드는 쓰기도 같은 모름을 겪는다.
- 그래서 이 설계는 이중 승인(돈 문제)을 막는 쪽을 택하고, 사용자 경험 손해(결제 실패)를 드문 한계로 받아들였다. 재검토 조건은 지표로 걸어 두었다.
