# 오픈 피크 부하 시나리오 PAY1·R1·L2는 각각 무엇을 재는가

## 질문
"PAY1, R1 같은 각각의 테스트가 뭔지 상세히 설명해 줘." 오픈 피크 시나리오 명세(ISE-192)의 결제 담당 몫을 검토하며 나온 질문이다.

## 짧은 답
- **PAY1(결제 승인)**: 결제 API 하나만 떼어 놓고 "PG를 동시에 10개까지만 부른다"는 문이 초당 몇 건까지 받는지 잰다. PG가 느려지거나 고장 날 때 서버가 어떻게 버티는지도 본다.
- **R1(결제 결과 반영)**: 결제가 승인된 뒤 예매가 "확정"되기까지(outbox → Kafka → 예매 서비스) 2초를 지키는 최대 속도를 잰다.
- **L2(자동결제 폭주)**: 추첨 직후 당첨자 2,000명의 카드 자동결제가 10분 안에 끝나는지 잰다. 그동안 다른 공연의 일반 결제가 피해를 보는지도 본다.
- 셋 다 계산으로 예상한 한도(결제 초당 약 33건, 확정 초당 50~100건, 자동결제 약 10분)가 실제로 맞는지 확인하고, 개선 전후를 비교하려는 측정이다.

## 바탕 개념

### 시나리오와 판정
부하 시나리오는 "구간 하나에, 정해진 모양의 부하를 걸고, 미리 정한 기준으로 합격·불합격을 가리는 측정"이다. 명세가 판정 기준을 측정 전에 `[가정]`으로 적어 두는 이유는, 결과를 본 뒤 기준을 맞춰 바꾸는 일을 막기 위해서다.

### 열린 모델과 단계별 속도
- **닫힌 모델**은 가상 사용자 수를 고정한다. 서버가 느려지면 사용자도 응답을 기다리느라 요청을 덜 보내서, 부하가 저절로 줄어든다.
- **열린 모델**은 "초당 몇 건이 도착한다"를 고정한다. 서버가 느려져도 요청은 같은 속도로 계속 온다. 티켓 오픈처럼 사람이 몰리는 상황은 열린 모델에 가깝다. k6의 `constant-arrival-rate`·`ramping-arrival-rate`가 이 방식이다.
- 속도를 20 → 40 → 80 → 160처럼 단계로 올리면 "어느 속도에서 무너지기 시작하는지"가 보인다.

### 리틀의 법칙
`동시에 처리 중인 수 = 처리량 × 한 건 처리 시간`이다. 거꾸로 쓰면 `처리량 상한 = 동시 처리 수 ÷ 한 건 처리 시간`이다. PG를 동시에 10개까지 부르고 PG가 0.3초 걸리면, 10 ÷ 0.3 ≈ 초당 33건이 한도다. PAY1과 L2의 계산이 모두 이 식에서 나온다.

### Bulkhead(격벽)와 Circuit Breaker(차단기)
- **Bulkhead**는 동시에 PG를 부를 수 있는 자리 수다(결제는 10). 자리가 없으면 기다리지 않고 바로 503 `PG_UNAVAILABLE`로 거절한다. PG가 느려져도 요청 스레드가 줄줄이 묶여 서버 전체가 멈추지 않게 하려는 장치다.
- **Circuit Breaker**는 최근 호출 20건 중 실패가 50% 이상이면 "열려서" 10초 동안 PG 호출 자체를 막는다. 10초 뒤 시험 호출 3건이 성공하면 다시 닫힌다. 고장 난 PG를 계속 두드리지 않으려는 장치다.
- 둘은 다르다. Bulkhead 거절은 "지금 자리가 꽉 찼다"이고 실패로 세지 않는다. 차단기는 "PG가 고장 났다"고 판단한 상태다.

### 결과 모름(UNKNOWN)과 재확인
PG 응답이 시한(2초) 안에 오지 않으면 돈이 나갔는지 알 수 없다. 이것을 거절로 닫으면 "돈은 나갔는데 예매는 안 된" 사고가 난다. 그래서 결제를 UNKNOWN으로 두고, 재확인 스케줄러가 10초 간격으로 PG에 "이 주문 어떻게 됐어?"라고 물어 승인이나 거절로 확정한다.

### Outbox와 Kafka 소비자 랙
- **Outbox 패턴**: 결제 상태 변경과 "결제 승인됨" 이벤트를 같은 DB 트랜잭션에 저장한다. 별도 릴레이가 그 이벤트를 Kafka로 보낸다. DB에는 승인됐는데 이벤트가 사라지는 일을 막는다.
- **소비자 랙**: Kafka에 쌓였지만 소비자가 아직 읽지 못한 메시지 수다. 랙이 늘면 확정이 늦어진다.
- **파티션과 키**: 토픽은 파티션으로 나뉘고, 파티션 하나는 소비자 하나가 차례로 읽는다. 파티션을 늘리면 병렬로 읽지만, 같은 키(예: 예매 ID)의 메시지는 늘 같은 파티션으로 가서 순서가 지켜진다.

### 단계 이름(PAY-0, R-0, LOT-0)
`-0`은 아무것도 바꾸지 않은 기준선이다. 숫자가 커질수록 개선을 하나씩 더한 상태다. 같은 시나리오를 단계마다 다시 재서 전후를 비교한다.

## 세 시나리오가 재는 곳

```text
[일반 예매]  좌석 선점 ─▶ (PAY1) 결제 승인 ─▶ (R1) 승인 이벤트 → 예매 확정
                              │
                              │  PG 동시 호출 자리 10개를 같이 쓴다
                              │
[추첨 예매]  추첨 → 당첨 배정 ─▶ (L2) 카드 자동결제 2,000건 ─▶ 추첨 결과 반영
```

## PAY1. 결제 승인

**재는 곳**: `POST /api/v1/payments`. 좌석을 선점한 사용자가 [결제하기]를 누르는 순간이다.

```text
요청 → 멱등키·결제 토큰 확인 → [허가: Bulkhead 10, 대기 0] → TX1(결제 REQUESTED 저장)
     → PG 호출(Mock PG, 300ms) → TX2(승인 반영 + outbox) → 응답
```

**왜 재나**: 오픈 직후 선점 성공자는 대기열 입장 속도와 비슷한 초당 약 50명이다. 대부분 바로 결제하면 결제도 초당 약 50건이 온다. 한도가 33건이면 약 3분의 1이 503을 받는다. 이 숫자가 맞는지 확인해야 대기열 입장 속도(뒤쪽 구간이 감당할 만큼만 들여보내는 값)도 근거를 갖고 정할 수 있다.

**변형**
| 변형 | 거는 것 | 묻는 것 |
|---|---|---|
| PAY1-a | 초당 20 → 40 → 80 → 160건, PG 300ms | 계산대로 초당 약 30건에서 503이 나기 시작하나 |
| PAY1-b | 40건 단계에서 PG 지연을 1,000ms, 1,900ms(시한 바로 아래), 2,500ms(시한 초과)로 | 느린 PG에 서버가 묶이지 않나. 시한을 넘긴 결제(UNKNOWN)를 재확인이 모두 정리하나 |
| PAY1-c | 승인 호출에 PG 서버 오류를 30초 | 차단기가 열리고, 장애가 끝나면 다시 닫히나 |

**보는 값**: 결과별 승인 시간(`payment_approve_seconds{outcome}`), Bulkhead 남은 자리, 차단기 상태, UNKNOWN 건수와 확정까지 걸린 시간, DB 커넥션 대기.

**합격 기준(가정)**: 503이 계산한 속도 근처에서 시작된다. 같은 결제가 두 번 승인되지 않는다(Mock PG 원장으로 대조). 측정이 끝나면 UNKNOWN이 모두 확정된다. 장애가 끝나면 차단기가 닫힌다.

**결과를 어디에 쓰나**
- PAY-1: 동시 수를 근거로 정한다. 리틀의 법칙으로 초당 50건 × 0.3초 = 15, 여유 2배면 30이다.
- PAY-2: 자리가 없을 때 100~200ms 기다려 보기.
- PAY-3: PG가 느릴 때 일찍 끊는 "느린 호출" 기준을 차단기에 더하기.
- PAY-4: 자동결제와 일반 결제의 자리를 나누기.

## R1. 결제 결과 반영

**재는 곳**: 결제 승인 응답은 바로 오지만, 예매 확정은 이벤트로 따로 일어난다. 그 사이가 사용자 화면의 "결제를 확인하고 있어요" 구간이다. 목표는 2초 안에 확정되는 것이다(SA 9-4).

```text
결제 TX2(승인 + outbox 저장) → outbox 릴레이(500ms마다, 20건씩 최대 10번)
  → Kafka payment.result(파티션 1) → 예매 서비스 소비자(동시 1)
  → 한 트랜잭션: 예매 CONFIRMED, 좌석 SOLD, 티켓 생성(이벤트 1건에 DB 왕복 8~10번)
```

**왜 재나**: 소비자 하나가 이벤트 한 건에 10~20ms를 쓰면 초당 50~100건이 한도다. 오픈 피크 수요(초당 약 50건)와 거의 같다. 이보다 느려지면 랙이 쌓이고 확정이 몇 초씩 밀린다.

**방법**
- 승인을 초당 25 → 50 → 100 → 200건 만든다.
- Mock PG 지연은 0으로 둔다. 결제 승인 쪽 한도(PAY1)가 섞이지 않게, 한 번에 한 변수만 보려는 것이다.
- 승인을 받은 가상 사용자가 예매 상태를 0.5초 간격으로 조회해, 확정까지 걸린 시간을 잰다.

**보는 값**: 승인 → 확정 시간(k6 조회와 DB 시각 차이), 결제 outbox에서 가장 오래 기다린 이벤트의 나이, Kafka 소비자 랙, 예매 서비스 커넥션 대기.

**합격 기준(가정)**: 확정 p95가 2초 이하인 최대 속도를 적는다. 승인된 결제 수와 확정된 예매 수가 맞고, 티켓 수와 확정 좌석 수가 맞으며, 같은 이벤트를 두 번 처리한 기록이 없다.

**나눠 보는 이유**: 2초 중 결제 쪽(릴레이 대기 최대 0.5초 + Kafka 전송)과 예매 쪽(소비·확정)이 각각 얼마를 쓰는지 알아야 어디를 고칠지 정한다. 결제 쪽은 안준현(릴레이·토픽), 예매 쪽은 반효승(소비자)이 검토한다.

**결과를 어디에 쓰나**: R-1(랙 지표 대시보드) → R-2(파티션 3개·소비자 3개, 키는 예매 ID) → R-3(티켓 일괄 INSERT 등 DB 쓰기 줄이기).

## L2. 자동결제 폭주

**재는 곳**: 추첨 예매는 응모 → 추첨 → 당첨자에게 좌석 배정 → 미리 등록한 카드(빌링키)로 자동결제 순서다. 당첨자가 2,000명이면 추첨 직후 결제 2,000건이 한꺼번에 생긴다. 결제가 거절되면 다음 대기자에게 넘긴다(승계).

```text
배정 스케줄러(1초마다 최대 100명) → BillingPaymentRequested(outbox)
  → Kafka payment.command → 결제 서비스 소비자(동시 1)
  → [허가: 일반 결제와 같은 Bulkhead 10] → PG(300ms) → payment.result → 추첨 결과 반영
```

**왜 재나**
- 소비자가 하나라 자동결제는 한 건씩 차례로 진행된다. 0.3초씩이면 초당 약 3.3건이고, 2,000건에 약 600초(10분)다.
- 목표가 "10분 안에 95%"라 기준선(LOT-0)은 경계에 걸리거나 넘을 것으로 본다.
- 자동결제와 일반 결제가 PG 자리 10개를 같이 쓴다. 자동결제를 빨리 하려고 소비자를 늘리면 일반 결제 자리가 줄어든다. 이 트레이드오프가 L2의 핵심이다.

**변형**
| 변형 | 거는 것 | 묻는 것 |
|---|---|---|
| L2-a | 추첨만. PG 300ms, 거절 5% | 10분 안에 95%가 결제 완료(PAID)되나 |
| L2-b | L2-a와 같은 시간에 다른 회차 일반 결제 초당 20건 | 일반 결제 503이 PAY1 단독일 때보다 늘지 않나 |

**보는 값**: 배정 수와 결제 완료 수(10초마다), `payment.command` 랙, Bulkhead 남은 자리, 일반 결제 503 비율과 p95, 승계 건수.

**준비할 때 주의할 점**: Mock PG는 빌링키를 메모리에 둔다. 빌링키를 등록한 뒤 Mock PG를 재시작하면 전원이 "빌링키 없음"으로 거절된다. 순서는 Mock PG 재시작 → 30초 대기 → 빌링키 등록 → 추첨이다.

**결과를 어디에 쓰나**
- LOT-1: 배정할 때 남은 좌석을 매번 다시 읽지 않기.
- LOT-2: 소비자 동시 수 늘리기. 동시 수를 몇으로 할지는 아래 계산 표로 정한다.
- LOT-3: 자동결제 전용 Bulkhead(PAY-4와 같음).

| 소비자 동시 수 | 자동결제가 쓰는 자리 | 일반 결제(초당 20 × 0.3초) | 합계 / 10 | 2,000건 소요(계산) |
|---|---|---|---|---|
| 1(지금) | 1 | 6 | 7 | 약 600초 |
| 3 | 3 | 6 | 9 | 약 200초 |
| 5 | 5 | 6 | 11(초과) | 약 120초 |

## 나머지 시나리오 한 줄씩
| ID | 재는 곳 | 핵심 질문 |
|---|---|---|
| G1 | Gateway 인증 경로 | 인증 요청의 Gateway 한도와 Redis 차단기가 열리는 지점 |
| B1 | 오픈 전 공연 조회 | 캐시 없는 공연 조회가 몇 건까지 버티고 대기열 진입에 번지는가 |
| Q1·Q2·Q3 | 대기열 진입·순번 폴링·입장 속도 | 진입 몰림을 받는가, 요청 수 1위 구간의 한도, 입장 속도를 지키는가 |
| K1·K1-H | 좌석 조회·선점 | 별도 계획 문서(`k6-seathold-bottleneck-plan.md`) |
| X1 | 선점 만료 | 만료 처리 속도와 그것이 선점 지연에 주는 영향 |
| L1 | 추첨 응모 마감 직전 | 응모 접수 한도, 중복 응모 0 |
| L3 | 추첨과 일반 판매 간섭 | 추첨이 도는 동안 선점 p95와 입장 속도가 유지되나 |
| O1 | 전체 흐름 | 개선을 합친 뒤 서비스 전체가 버티나 |

## 면접 포인트
- **결제 API 처리량 한도를 어떻게 정했나**: 리틀의 법칙으로 "PG 동시 호출 수 ÷ PG 응답 시간"을 계산하고, 열린 모델 부하로 503이 시작되는 속도를 재서 검증했다. 동시 수는 목표 처리량 × 응답 시간에 여유를 곱해 정한다.
- **Bulkhead와 Circuit Breaker의 차이**: Bulkhead는 동시에 쓰는 자원 수를 제한해 장애가 퍼지는 것을 막고, 차단기는 실패율로 상대가 고장 났다고 판단해 호출 자체를 끊는다. 포화 거절은 고장이 아니므로 차단기 실패로 세지 않는다.
- **승인 후 확정을 비동기로 한 이유와 지연을 재는 법**: 결제와 예매는 서비스가 달라 outbox와 Kafka로 결과를 넘긴다. 지연은 클라이언트 조회 간격에 묶이지 않게 DB의 승인 시각과 확정 시각의 차이로 잰다.
- **두 기능이 한정된 자원을 나눠 쓸 때**: 자동결제 소비자를 늘리면 처리 시간은 줄지만 일반 결제의 자리를 뺏는다. 동시 수를 계산으로 정하거나 자원을 따로 나눈다(전용 Bulkhead).
