# 부하를 늘려 가며 결제 단계별 시간과 임계치를 재는 법

## 질문
"인원수를 늘려 가면서 결제의 각 단계에서 시간이 얼마나 드는지, 임계치가 얼마인지 재고 싶다. 어떻게 해야 하나?"

## 짧은 답
- "인원 늘리기"와 "임계치"는 이미 있는 PAY1(`loadtest/k6/scenarios/pay1-payment.js`)이 잰다. 결제 요청을 초당 20 → 40 → 80 → 160건으로 올린다.
- 빠진 것은 "단계별 시간"이다. 서버는 결제 API 전체 시간(`payment_approve_seconds`, p95를 볼 수 있음)과 PG 호출 평균만 잰다. 사전 검사, TX1, TX2는 따로 재지 않는다.
- 그래서 순서는 (1) 승인 흐름에 단계 타이머를 더하고, (2) PAY1을 굵은 단계로 한 번 돌려 무릎을 찾고, (3) 무릎 근처를 촘촘한 단계로 다시 재서, (4) 단계 중 어느 것이 먼저 늘어나는지로 병목을 가린다.
- 이 결제 서버는 PG 자리(Bulkhead 10)가 차면 기다리지 않고 503을 준다. 그래서 임계치는 "느려짐"보다 "503이 나기 시작함"으로 먼저 보일 것으로 예상한다. 계산값은 초당 약 33건(10 ÷ 0.3초)이다.

## 바탕 개념

### "인원"은 두 가지로 셀 수 있다
- **동시 사용자 수(닫힌 모델)**: 가상 사용자(VU) N명이 요청 → 응답 → 다음 요청을 되풀이한다. 서버가 느려지면 사용자도 기다리느라 요청을 덜 보내서 부하가 저절로 줄어든다. 한계를 실제보다 좋게 보이게 만든다.
- **초당 도착 수(열린 모델)**: "초당 N명이 결제 버튼을 누른다"를 고정한다. 서버가 느려져도 요청은 같은 속도로 온다. 티켓 오픈은 대기열이 초당 몇 명씩 들여보내는 구조라 열린 모델이 맞다. k6의 `ramping-arrival-rate`다.
- 둘은 **리틀의 법칙**으로 바꿔 말할 수 있다. `동시에 처리 중인 수 = 초당 건수 × 한 건 시간`. 초당 30건이 0.33초씩 걸리면 동시에 약 10건이 처리 중이다. "몇 명까지 버티나"를 물으면 "초당 몇 건까지"로 답하고, 필요하면 이 식으로 동시 수로 바꾼다.

### 임계치는 "무릎"이다
부하를 올리면 처음에는 처리량이 부하만큼 늘고 지연은 거의 그대로다. 어느 지점부터 처리량은 더 늘지 않고, 지연이나 거절이 갑자기 늘어난다. 그래프가 꺾이는 그 지점이 무릎(knee)이고, 그 직전 속도가 임계치다.

무릎은 눈으로 고르지 않고, 측정 전에 판정 기준을 적어 두고 처음 깨지는 단계로 정한다.

| 기준(예시) | 깨지면 |
|---|---|
| 승인된 결제 p95 < 1초 | 느려짐이 시작됐다 |
| 503 `PG_UNAVAILABLE` 비율 < 1% | 자리가 모자라기 시작했다 |
| 처리한 건수 ≥ 보낸 건수의 99% | 서버가 받은 만큼 처리하지 못한다 |
| k6 `dropped_iterations` = 0 | 발생기가 모자라다(서버 한계가 아니다) |

### 단계별 시간을 재는 세 가지 방법

| 방법 | 무엇을 주나 | 장점 | 한계 |
|---|---|---|---|
| **서버 단계 타이머**(Micrometer 히스토그램 → Prometheus) | 부하 단계마다 각 단계의 p50·p95·p99 | 모든 요청을 센다. 부하와 시간 축으로 나란히 볼 수 있다 | 코드를 고쳐 배포해야 한다. 한 사람의 시간이 아니라 그 순간 요청들의 분포다 |
| **분산 추적**(Zipkin) | 요청 하나의 단계별 폭포 그림 | 한 요청 안에서 시간이 어디로 갔는지 바로 보인다 | 측정 모드 표본 비율이 0.01이라 일부만 남는다. 백분위를 내기 어렵다 |
| **DB 시각 차이**(사후 SQL) | `payments.created_at`(TX1)과 `approved_at`(TX2)의 차이 등 | 코드를 바꾸지 않아도 된다 | 굵은 구간만 보인다. 사전 검사·PG·TX2를 나누지 못한다 |

"각 단계가 부하에 따라 어떻게 변하나"에는 첫 번째가 맞다. 추적은 이상한 요청 몇 건을 들여다볼 때 쓴다.

### 히스토그램이어야 p95가 나온다
Micrometer 타이머는 기본으로 합계·건수·최대만 낸다. 그러면 평균은 구할 수 있어도 p95는 못 구한다. `publishPercentileHistogram()`을 켜면 구간별 건수(`_bucket`)가 나가고, Prometheus의 `histogram_quantile(0.95, …)`로 원하는 시간 창의 p95를 계산한다. 평균은 느린 소수를 가려서 임계치 판단에 쓰기 어렵다.

## 이 프로젝트에서는

### 결제 한 건이 지나는 단계와 지금 재는 것 (2026-11-11 dev `a32fd2dc`)

```text
k6 → Gateway → 결제 서비스
  ① 사전 검사: 멱등 기록 조회 → 결제 토큰 검증 → 같은 예매 결제 조회
  ② 허가: pg-approve Bulkhead 10, 대기 0 (못 얻으면 503)
  ③ TX1: 결제 REQUESTED 저장 + 멱등 기록
  ④ PG 호출(트랜잭션 밖, Mock PG 300ms)
  ⑤ TX2: 승인 반영 + outbox 저장 → 응답
  ⑥ outbox 릴레이(500ms 주기) → Kafka payment.result
  ⑦ 예매 서비스 소비 → 예매 CONFIRMED·좌석 SOLD·티켓 생성
```

| 단계 | 지금 있는 값 | 빠진 것 |
|---|---|---|
| k6가 본 전체 | k6 `payment_duration{result}`, `http_req_duration{api:payment}`. 선점은 `api:hold`로 따로 | 없음 |
| Gateway 체류 | Gateway·결제 서비스 `http_server_requests_seconds`(합·건수만) | 두 서버 시간의 차이로 어림한다 |
| ① 사전 검사 | 없음 | 단계 타이머 |
| ② 허가 | 거절 수 `payment_approve_seconds_count{outcome="unavailable"}`, 남은 자리 `resilience4j_bulkhead_available_concurrent_calls` | 대기가 0이라 시간은 재지 않고 거절률로 본다 |
| ③ TX1 | 커넥션 얻는 시간 `hikaricp_connections_acquire_seconds`(평균), 대기 `hikaricp_connections_pending` | 단계 타이머 |
| ④ PG 호출 | `payment_pg_call_seconds`(합·건수만, 평균) | 히스토그램 |
| ⑤ TX2 | 없음 | 단계 타이머 |
| ①~⑤ 전체 | `payment_approve_seconds{outcome}` 히스토그램(p95 가능) | 없음 |
| ⑥ 릴레이 | `outbox_pending_oldest_seconds`(가장 오래 기다린 이벤트) | 없음 |
| ⑦ 확정 | Kafka 랙 `kafka_consumer_fetch_manager_records_lag_max`, R1 k6 승인 → 확정 시간(0.5초 조회 간격만큼 올림) | 소비 처리 시간 타이머(예매 서비스, 반효승 담당) |

- 추적으로도 ③~⑤를 따로 보기 어렵다. DB 구간 span이 없고, `MockPgAdapter`는 `RestClient.builder()`로 클라이언트를 직접 만들어 관측 레지스트리가 붙지 않으므로 PG 호출 span도 따로 남지 않는다(코드로 확인, 실제 Zipkin 화면은 미확인).
- 커넥션 풀은 20, PG 호출은 트랜잭션 밖이라 PG를 기다리는 동안 커넥션을 붙들지 않는다(`config-repo/payment-service.yml`). 그래서 PG 자리 10이 커넥션 20보다 먼저 찬다고 예상한다.

### 재는 순서

1. **단계 타이머를 더한다.** `PaymentMetrics`에 `payment.approve.stage{stage=precheck|tx1|pg|tx2}` 타이머를 히스토그램으로 더하고, 라벨 값은 enum으로만 받는다(ADR 0024 라벨 규칙). `payment.pg.call`에도 히스토그램을 켠다. Grafana 결제 대시보드 "2. 승인 흐름"에 단계별 p95 패널을 둔다.
2. **local에서 굵게 돌린다.** `compose.mockpg-loadtest.yml`로 mock-pg를 `loadtest` 프로필로 띄우고, 다시 띄웠으면 30초 넘게 기다린 뒤 PAY1을 기본 단계(20, 40, 80, 160 / 단계마다 45초, PG 300ms)로 돌린다. 503이 처음 나는 단계를 찾는다.
3. **무릎 근처를 촘촘히 다시 잰다.** 예를 들어 20과 40 사이면 `STAGES=25,30,35,40 STAGE_SECONDS=60`. 결과가 흔들리는 것을 보려고 같은 조건을 3번 돈다. 한 번에 변수 하나만 바꾼다(PG 지연은 300ms로 고정, 지연을 바꾸는 것은 PAY1-b).
4. **단계별 p95를 부하 단계와 나란히 본다.** 어느 단계가 먼저 늘어나는지가 병목 위치다.
   - PG 시간은 그대로인데 503만 늘면 PG 자리(Bulkhead)가 한계다. 개선은 PAY-1(동시 수 조정)이다.
   - TX1·TX2가 먼저 늘고 `hikaricp_connections_pending`이 오르면 커넥션 풀이나 DB가 한계다.
   - 서버 시간은 그대로인데 k6 시간만 늘면 Gateway나 발생기 쪽이다.
5. **배포 서버에서 잰다.** 배포 측정은 지금 바로는 안 된다.
   - PAY1은 `setup()`에서 관리자 로그인으로 회차를 만들어 발생기에서 돌지 않는다(`docs/guides/loadgen.md` 9절). R1-d처럼 서버에서 만든 회차(`SCHEDULE_ID`)를 받는 판이 필요하다.
   - Mock PG 지연은 서버 안에서 일회용 curl 컨테이너로 건다(`loadtest/k6/README.md` "Mock PG 장애 주입").
   - 새 타이머는 main에 들어가 배포돼야 서버에서 보인다. 측정 중 main 머지는 금지라, 팀 측정 사이의 빈 시간에 배포를 잡는다.
   - 시작 전 팀 채널 알림, 측정 모드 켜기와 측정 전용 키 옮기기는 측정자 본인이 한다(`loadgen.md` 4·5절).
6. **결과를 적는다.** `docs/design/infra/open-peak-scenarios.md` 3절에 PAY1 결과 표와 측정 환경 기록표, "오류 없이 버틴 최대 속도"를 둔다.

## 면접 포인트
- **임계치를 어떻게 정의했나**: 열린 모델로 도착률을 단계적으로 올리고, 측정 전에 정한 기준(p95, 거절률, 처리량 비율) 중 하나가 처음 깨지는 단계를 임계치로 봤다. 결과를 본 뒤 기준을 바꾸지 않으려고 미리 적었다.
- **왜 VU가 아니라 도착률로 늘렸나**: 닫힌 모델은 서버가 느려지면 부하가 같이 줄어 한계를 가린다. 티켓 오픈은 대기열이 초당 몇 명씩 들여보내는 열린 상황이다.
- **병목을 어떻게 찾았나**: 결제 한 건을 사전 검사·TX1·PG·TX2로 나눠 단계별 히스토그램을 남기고, 부하를 올릴 때 어느 단계가 먼저 늘어나는지 봤다. 평균이 아니라 p95로 봤다.
- **거절이 먼저 나는 설계의 의미**: PG 자리에 대기를 두지 않아 과부하가 지연 증가가 아니라 503으로 나타난다. 요청 스레드가 PG를 기다리며 쌓이지 않게 하려는 선택이고, 그래서 이 구간의 임계치는 거절률로 잰다.
