# 스레드 풀 크기는 CPU 바운드와 I/O 바운드에서 어떻게 다르게 잡나

## 질문
아래 내용을 지식으로 저장하고 추가 설명을 붙여 달라.

> 1. CPU 바운드 작업(CPU 집중 작업): 권장 스레드 수는 CPU 코어 수 + 1개(이상적으로는 코어 수에 최적화)
> 2. I/O 바운드 작업(입출력 대기가 많은 작업): 권장 스레드 수는 CPU 코어 수보다 많은 개수

## 짧은 답
- **CPU 바운드는 코어 수 + 1이 출발점이다.** 계산만 하는 스레드는 코어 하나를 꽉 채우므로 코어보다 많이 띄워도 일이 빨라지지 않고 문맥 교환 비용만 는다. +1은 페이지 폴트 같은 잠깐의 멈춤 동안 코어가 노는 것을 메우는 여분이다.
- **I/O 바운드는 기다리는 비율만큼 늘린다.** 공식은 `스레드 수 = 코어 수 × 목표 CPU 사용률 × (1 + 대기 시간 ÷ 계산 시간)`이다. 계산 10ms·DB 대기 90ms인 작업은 4코어에서 4 × 1 × (1 + 9) = 40개가 출발점이다(계산값).
- **"많이"에는 상한이 있다.** 스레드가 기다리는 대상(DB 커넥션, 외부 API 동시 처리 수)이 더 작으면 그 앞에서 줄만 선다. 이 프로젝트에서 Tomcat 요청 스레드 200개가 Hikari 커넥션 5개 앞에 197개씩 줄을 선 측정이 그 예다.
- 두 규칙 모두 정답이 아니라 시작값이다. 실제 값은 부하 측정으로 맞춘다.

## 자세히

### 1. 용어
| 용어 | 뜻 |
|---|---|
| CPU 바운드 | 실행 시간 대부분을 CPU 계산에 쓰는 작업. 암호화, 해시, 압축, 이미지 처리, JSON 대량 변환, JWT 서명 검증 |
| I/O 바운드 | 실행 시간 대부분을 외부 응답을 기다리며 쓰는 작업. DB 조회, HTTP 호출, 파일·네트워크 읽기, Redis·Kafka 호출 |
| 코어 수 | 이 문서에서는 OS가 보는 논리 CPU 수다. Java에서는 `Runtime.getRuntime().availableProcessors()` 값이다 |
| 문맥 교환(context switch) | OS가 실행 중인 스레드를 멈추고 다른 스레드로 바꾸는 일. 레지스터 저장·복원과 CPU 캐시 손실 비용이 든다 |
| 스레드 풀 | 스레드를 미리 만들어 두고 작업을 나눠 주는 구조. 요청마다 스레드를 만들고 없애는 비용을 줄이고, 동시 실행 수에 상한을 둔다 |

### 2. CPU 바운드: 왜 코어 수 + 1인가
- 코어 하나는 한순간에 스레드 하나만 실행한다. 계산만 하는 스레드는 쉬지 않으므로 코어 4개에 스레드 4개면 CPU가 이미 100%다.
- 스레드를 8개로 늘려도 처리량은 그대로다. 4개씩 번갈아 실행될 뿐이고, 번갈아 바꿀 때마다 문맥 교환 비용과 캐시 손실이 생겨 오히려 느려진다.
- 그래도 계산 스레드가 가끔 멈출 때가 있다(페이지 폴트, GC 안전 지점 대기, 짧은 잠금). 그동안 코어가 놀지 않도록 한 개를 더 둔다. 이 +1 규칙은 Brian Goetz의 『Java Concurrency in Practice』 8.2절이 출처다.
- 원문 메모의 "이상적으로는 코어 수에 최적화"는 이 뜻이다. 코어 수 근처가 적정이고, +1은 보험이다.

### 3. I/O 바운드: 몇 개가 "코어보다 많이"인가
I/O를 기다리는 동안 스레드는 CPU를 쓰지 않는다. 그 시간에 다른 스레드가 코어를 쓰게 하려면 기다리는 비율만큼 스레드가 더 있어야 한다.

```
스레드 수 = N_cpu × U_cpu × (1 + W / C)

N_cpu : 코어 수
U_cpu : 목표 CPU 사용률(0~1). 같은 장비의 다른 일을 위해 남겨 둘 몫을 뺀다
W / C : 대기 시간 ÷ 계산 시간
```

| 작업 | 계산 C | 대기 W | 4코어, 사용률 1.0 기준 |
|---|---|---|---|
| 순수 계산 | 10ms | 0ms | 4 × (1 + 0) = 4 (CPU 바운드 규칙과 같다) |
| DB 조회 위주 | 10ms | 90ms | 4 × (1 + 9) = 40 |
| 느린 외부 API | 5ms | 495ms | 4 × (1 + 99) = 400 |

표의 값은 모두 공식에 넣은 계산값이다. W와 C는 추측하지 말고 APM·지표(요청 처리 시간과 CPU 시간)에서 잰다.

### 4. 리틀의 법칙으로 같은 답을 확인하기
동시에 처리 중인 일의 수 L은 도착률 λ와 머무는 시간 W의 곱이다(`L = λ × W`).
- 초당 200건이 들어오고 한 건이 0.1초 머문다면, 동시에 스레드 20개가 일하고 있어야 한다(200 × 0.1 = 20, 계산값).
- 스레드가 20개보다 적으면 요청이 큐에 쌓이고, 훨씬 많으면 놀거나 다른 자원 앞에서 기다린다.
- 3절 공식은 "CPU를 꽉 채우려면 몇 개", 리틀의 법칙은 "이 부하를 받으려면 몇 개"를 묻는다. 둘 중 작은 쪽, 그리고 뒤쪽 자원이 받을 수 있는 쪽이 실제 상한이다.

### 5. 스레드를 너무 많이 띄우면 생기는 일
| 문제 | 이유 |
|---|---|
| 메모리 | 플랫폼 스레드는 각자 스택을 갖는다. 64비트 HotSpot의 기본 스택 예약 크기는 1MB다(`-Xss`). 실제로 쓰는 만큼만 물리 메모리를 차지하지만 수천 개면 무시할 수 없다 |
| 문맥 교환 | 실행 준비된 스레드가 코어보다 훨씬 많으면 OS가 바꾸는 데 시간을 쓴다. 응답 시간 꼬리(p99)가 길어진다 |
| 뒤쪽 자원 포화 | 스레드가 늘수록 DB·외부 API에 동시에 더 많이 몰린다. 뒤쪽이 받지 못하면 스레드는 늘었는데 처리량은 같고 대기만 길어진다 |
| 과부하 회복 지연 | 큐와 스레드가 클수록 이미 사용자가 떠난 요청을 끝까지 처리하느라 부하가 지나간 뒤에도 회복이 늦다 |

반대로 너무 적으면 CPU가 놀고 있는데 요청은 큐에서 기다린다.

### 6. 공식이 맞지 않는 두 모델

**이벤트 루프(Netty, WebFlux, Node.js)**
- 스레드가 I/O를 기다리지 않는다. 소켓 여러 개를 스레드 하나가 돌아가며 처리하고, 응답이 오면 콜백으로 이어 간다.
- 그래서 I/O가 많아도 스레드 수는 코어 수 근처가 적정이다. 블로킹 호출을 하면 그 스레드가 맡은 연결 전체가 멈추므로 블로킹 일은 별도 스레드 풀로 뺀다.

**가상 스레드(Java 21)**
- JVM이 관리하는 가벼운 스레드다. I/O를 기다리면 캐리어 스레드(실제 OS 스레드, 기본값은 코어 수만큼)에서 내려오고, 응답이 오면 다시 올라간다.
- 스레드 수를 아껴야 할 이유가 거의 없어 "풀 크기"를 고민하지 않는다. 대신 뒤쪽 자원 보호는 세마포어나 커넥션 풀 같은 별도 장치로 한다.
- Java 21에서는 `synchronized` 안에서 블로킹하면 가상 스레드가 캐리어에 고정(pinning)되어 이 이점이 사라진다. JDK 24(JEP 491)에서 해결됐다.

### 7. 컨테이너에서 "코어 수"를 읽을 때 주의할 점
- JVM은 컨테이너의 CPU 제한(`cpus`, cgroup)을 보고 `availableProcessors()`를 정한다. 제한이 없으면 호스트 전체 CPU 수를 본다.
- 한 장비에 JVM 여러 개가 CPU 제한 없이 떠 있으면, 각 JVM이 "CPU 전부를 혼자 쓴다"고 보고 GC 스레드·이벤트 루프·ForkJoinPool 크기를 정한다. 장비 전체로는 코어보다 훨씬 많은 스레드가 CPU를 다툰다.
- 하이퍼스레딩 장비의 vCPU는 물리 코어 하나를 둘로 나눈 것이다. CPU 바운드 작업은 vCPU 수만큼 늘려도 물리 코어 수 이상으로는 잘 늘지 않는다.

### 8. 커넥션 풀 크기는 따로 본다
- 스레드 풀과 커넥션 풀은 같은 질문이 아니다. 커넥션 풀은 DB 서버의 코어·디스크가 동시에 처리할 수 있는 양에 맞춘다.
- HikariCP 문서는 출발점으로 `커넥션 수 = (DB 서버 코어 수 × 2) + 유효 디스크 수`를 제시한다. 커넥션을 늘릴수록 빨라지는 것이 아니라, 적은 커넥션을 빨리 돌려쓰는 쪽이 대개 더 빠르다는 것이 요지다.
- 요청 스레드가 커넥션보다 훨씬 많으면, 커넥션이 필요한 요청 기준으로는 남는 스레드가 대기 줄일 뿐이다.

## 면접 포인트
- **"스레드 풀 크기를 어떻게 정하나요?"** 작업이 CPU 바운드인지 I/O 바운드인지 먼저 본다. CPU 바운드는 코어 수 + 1, I/O 바운드는 `코어 수 × 목표 사용률 × (1 + 대기/계산)`이 시작값이다. 대기·계산 시간은 지표로 재고, 부하 테스트로 맞춘다.
- **"I/O 바운드면 스레드를 무한정 늘리면 되나요?"** 아니다. 스레드가 기다리는 뒤쪽 자원(커넥션 풀, 외부 API 한도)이 상한이다. 요청 스레드 200개가 커넥션 5개를 기다린 측정을 예로 든다.
- **"WebFlux는 왜 스레드가 적나요?"** 이벤트 루프는 I/O를 기다리지 않고 콜백으로 이어 가므로 코어 수만큼이면 된다. 대신 블로킹 호출을 하면 그 루프의 모든 연결이 멈춘다.
- **"가상 스레드를 쓰면 풀 크기 고민이 없어지나요?"** 스레드 수 고민은 줄지만 뒤쪽 자원 보호는 그대로 필요하다. 세마포어나 커넥션 풀로 동시 실행 수를 막는다. Java 21에서는 `synchronized` 안 블로킹이 pinning을 일으킨다.
- **"컨테이너에서 코어 수는?"** JVM은 cgroup CPU 제한을 읽는다. 제한이 없으면 호스트 전체 CPU를 보므로, 한 장비에 JVM이 여럿이면 스레드가 과하게 잡힌다.
