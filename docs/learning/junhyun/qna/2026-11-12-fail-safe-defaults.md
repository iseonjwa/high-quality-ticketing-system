# 기능 플래그의 기본값은 왜 꺼짐이어야 하나(안전한 기본값)

## 질문
결제 개선 방안을 하나씩 적용할 때마다 설계와 이론 문서를 남기기로 했다(11/12). 이 노트는 ISE-240(Mock 건너뛰기 기본값을 끔)의 이론이다. 다루는 물음은 "시연용 설정인데 왜 기본을 꺼 두는가"다.

## 짧은 답
- 설정을 **빠뜨렸을 때 어느 쪽으로 떨어지는가**가 기본값을 정하는 기준이다. 빠뜨림은 반드시 일어나므로, 떨어진 곳이 안전해야 한다.
- 시연 편의 기능은 켜졌을 때 위험(결제 없이 승인)이 생긴다. 그러니 꺼진 것이 기본이고, 필요한 환경에서 사람이 명시적으로 켠다.
- 이 설계 원칙의 이름이 안전한 기본값(fail-safe defaults)이다.

## 자세히

### 바탕 개념
- **안전한 기본값**: Saltzer와 Schroeder가 1975년 논문 "The Protection of Information in Computer Systems"에서 정리한 보호 설계 원칙 중 하나다. 접근 결정은 "허용되지 않으면 거부"를 기본으로 하고, 명시적으로 허용한 것만 통과시킨다.
- **허용 목록과 차단 목록**: 허용 목록은 적은 것만 통과시키고 나머지는 막는다. 차단 목록은 적은 것만 막고 나머지는 통과시킨다. 목록에서 항목을 빠뜨렸을 때 허용 목록은 "막힘"(불편하지만 안전), 차단 목록은 "뚫림"(위험)으로 실패한다. 기능 플래그의 "꺼짐이 기본"은 허용 목록과 같은 구조다.
- **기본값을 정하는 기준**: (1) 빠뜨렸을 때 안전한 쪽인가, (2) 틀렸을 때 눈에 띄는가. 꺼짐이 기본이면 빠뜨림은 "기능이 안 보임"이라는 눈에 띄는 불편으로 드러나고, 켜짐이 기본이면 아무도 모르게 위험이 열려 있다.

### 환경변수가 전달되지 않는 실수는 왜 흔한가
설정 한 값은 여러 층을 지나야 앱에 닿는다: 서버 `.env` → compose의 `environment` → 컨테이너 환경 → 설정 서버의 `${변수:기본값}` → 프로퍼티 바인딩. 어느 층에서든 이름이 빠지면 값은 조용히 기본값으로 떨어진다. 에러가 나지 않으므로 사람이 발견하지 못한다. 그래서 "전달이 끊겨도 기본값이 안전한가"를 층마다 확인하지 않고 기본값 한 곳에서 보장하는 쪽이 싸다.

## 이 프로젝트에서는
- 이 설정은 기본이 `true`였고 compose가 변수를 `payment-service`에 넘기지 않았다. 결과적으로 배포 서버에서 끌 수도 없고, 빠뜨리면 켜져 있는 상태였다(ISE-240). 기본을 `false`로 바꾸고 compose가 `${PAYMENT_PG_MOCK_BYPASS:-false}`로 넘기게 해 두 층 모두 안전한 쪽으로 맞췄다.
- 이미 같은 원칙을 따르는 곳이 있다. 토스 키가 라이브 키(`test_` 접두사가 아님)면 `payment-service`가 기동을 거부한다(허용 목록: 테스트 키만 통과). `PAYMENT_PG_PROVIDER`를 비우면 서버 기본 PG가 Mock이고, Anthropic API 키가 비면 AI 상담은 검색 모드로 동작한다(없을 때 더 약하지만 안전한 동작으로 떨어진다).
- 시연에서는 같은 이유로 "켜는 절차"가 문서에 있다. 켜는 일이 명시적이어야 켠 사람이 안다.

## 면접 포인트
- "설정 기본값을 어떻게 정하나"에는 "빠뜨렸을 때 안전한 쪽, 그리고 빠뜨림이 눈에 띄는 쪽"이라고 답한다. 편의 기능은 꺼짐, 보안 기능은 켜짐이 기본이다.
- 허용 목록과 차단 목록을 빠뜨림 관점으로 비교할 수 있어야 한다.
- 설정이 여러 층을 지나며 조용히 끊기는 사례(compose가 변수를 넘기지 않음)를 실제로 겪었다는 이야기가 근거가 된다.
