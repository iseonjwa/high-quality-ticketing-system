# 서버를 막 띄운 직후 첫 요청들은 왜 느리고 어떻게 줄이는가

## 질문
결제 개선 방안을 하나씩 적용할 때마다 설계와 이론 문서를 남기기로 했다(11/12). 이 노트는 ISE-243(기동 웜업)의 이론이다. 다루는 물음은 "서버를 막 띄운 직후 첫 요청들은 왜 느리고 어떻게 줄이는가"다.

## 짧은 답
- 첫 요청이 느린 것은 코드가 아직 "준비되지 않았기" 때문이다. 클래스를 처음 읽고, 코드를 아직 기계어로 컴파일하지 않았고, DB·HTTP 연결을 처음 맺고, 지연 초기화된 빈을 처음 만든다.
- 이 비용은 평균에는 잘 안 보이고 **p99에 나타난다**. 요청이 많으면 느린 소수(첫 몇 건)가 상위 1%에 들어간다.
- 줄이는 가장 단순한 방법은 트래픽을 받기 전에 읽기 전용 경로를 미리 실행하는 웜업이다. 더 무거운 방법으로 AppCDS, CRaC, 네이티브 이미지가 있다.
- 원인을 가르려면 첫 회, 둘째 회, 수천 회 뒤를 비교한다.

## 자세히

### 첫 호출이 느린 이유를 층으로 나누면
1. **클래스 로딩과 정적 초기화**: JVM은 클래스를 처음 쓸 때 파일에서 읽고 검증하고 정적 초기화를 한다. 프레임워크(Spring, Hibernate, Jackson)는 처음 쓰는 클래스가 매우 많다.
2. **JIT 컴파일 단계**: 처음에는 인터프리터가 한 줄씩 실행한다. 자주 쓰는 메서드는 C1(빠르게 컴파일, 덜 최적화)로, 아주 자주 쓰는 것은 C2(오래 걸리지만 많이 최적화)로 올라간다. 대략 수백~수천 번 호출·반복이 쌓여야 단계가 올라가고, 정확한 기준은 JVM 설정에 따라 다르다. 그 전의 코드는 느리다.
3. **DB 연결과 준비**: 커넥션 풀의 첫 연결 수립(TCP, 인증), 준비된 문장(prepared statement)과 Hibernate 쿼리 계획 캐시의 첫 생성.
4. **HTTP 연결 수립과 연결 풀**: 외부 PG 호출의 첫 연결(TCP, 필요하면 TLS)과 클라이언트 클래스 초기화.
5. **지연 초기화 빈**: 처음 쓰일 때 만들어지는 빈은 그 요청이 비용을 낸다.

### 원인을 가르는 방법
같은 호출을 되풀이하며 회차별 시간을 잰다.
- 첫 회만 크고 둘째 회부터 작다 → 1·3·4·5(한 번만 드는 초기화)가 원인이다.
- 둘째 회 이후도 느리다가 수십~수천 회에 걸쳐 서서히 줄어든다 → 2(JIT)가 원인이다.
- 웜업의 회차를 늘리면 어디서 안정되는지도 보인다. 회차별 시간은 평균 하나로 뭉개지 않고 첫 회, 둘째 회, 나머지 평균으로 나눠 본다.

### 웜업은 언제 끝나야 하나
트래픽을 받기 전이다. 웜업 중에 요청이 들어오면 웜업과 경쟁하고 첫 요청의 느림도 그대로다. 그래서 웹 서버가 연결을 받기 전(Spring에서는 웹 서버 시작보다 앞선 `SmartLifecycle` 단계)에 끝내고, 서비스 등록(Eureka)이나 readiness(준비 완료) 신호도 그 뒤에 나가게 한다. liveness(살아 있음)는 웜업 중에도 통과해야 오케스트레이터가 죽이지 않는다. 웜업은 최적화이지 기동 조건이 아니므로 실패해도 기동은 계속한다.

### 다른 방법과 비교

| 방법 | 내용 | 이 프로젝트에서 고르지 않은 이유 |
|---|---|---|
| 기동 웜업(선택) | 읽기 전용 경로를 미리 실행 | 코드 몇십 줄, 의존 없음. 쓰기 경로와 C2까지는 못 데운다 |
| AppCDS | 클래스 로딩 결과를 아카이브로 저장해 시작을 줄임 | 빌드·이미지 단계가 늘고, 줄이는 것은 클래스 로딩 부분뿐이다 |
| CRaC | 웜업된 JVM 상태를 스냅샷으로 저장해 복원 | 특정 JDK와 런타임이 필요하고 연결 같은 외부 자원 처리가 까다롭다 |
| GraalVM 네이티브 이미지 | 미리 기계어로 컴파일해 JIT가 없음 | 리플렉션·프록시가 많은 Spring/Hibernate와 빌드 시간·호환 비용이 크다 |
| slow start(트래픽을 조금씩 올림) | 새 인스턴스에 가는 요청을 서서히 늘림 | 로드 밸런서가 여러 인스턴스를 가질 때 쓴다. 지금은 결제 서비스가 한 대다 |

### 평균이 아니라 p99에 나타나는 이유
기동 직후 몇 건이 1초 이상 걸려도 그 뒤 수천 건이 0.3초면 평균은 거의 변하지 않는다. 하지만 백분위수는 "느린 순서대로 1%"를 보므로, 초당 20건에서 첫 몇 초 동안의 느린 요청이 단계 전체의 p99를 정한다.

## 이 프로젝트에서는
- 11/12 배포 측정에서 결제 서비스를 다시 띄운 직후 첫 단계(초당 20건)의 승인 p99가 세 번 모두 1.0~1.4초, 다음 단계는 약 0.33초였다. 첫 JPA 조회의 최대값이 0.6~0.9초로 가장 컸다(원인은 층 구분 전).
- ISE-243: 승인 흐름의 읽기 조각(DB 조회 세 가지, 가짜 결제 토큰 검증, Mock PG 조회)을 웹 서버 시작 전에 20회씩 미리 실행하고, 단계마다 첫 회·둘째 회·나머지 평균을 로그로 남긴다. 이 로그가 위 "원인을 가르는 방법"의 근거가 된다. 설계는 `docs/design/payment/events-and-reliability.md` 7절 "기동 웜업"이다.
- 로컬 테스트에서 잰 값(로컬 환경, 20회): DB 조회 첫 회 184ms, 둘째 회 4.4ms, 나머지 평균 2.1ms. 첫 회만 크고 이후는 작아 한 번만 드는 초기화 비용의 모양이다. 배포 서버 값은 측정 전이다.
- 쓰기 경로는 가짜 데이터로 돌리는 위험 때문에 데우지 않는다. 그래서 첫 `saveAndFlush`의 비용은 남는다.

## 면접 포인트
- "첫 요청이 왜 느린가"에 클래스 로딩, JIT(인터프리터 → C1 → C2), 연결 수립·캐시, 지연 초기화로 나눠 답한다.
- 원인을 추측하지 않고 회차별 시간을 첫 회·둘째 회·평균으로 나눠 재서 가른다는 방법을 말한다.
- 웜업을 트래픽 수신 전에 끝내고 실패해도 기동을 막지 않는다는 판단, 쓰기 경로를 일부러 데우지 않은 이유를 설명한다.
- 평균이 아니라 p99에서 기동 직후의 느림이 드러난다는 점.
