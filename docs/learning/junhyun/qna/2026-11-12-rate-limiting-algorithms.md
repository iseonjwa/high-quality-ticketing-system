# 요청 횟수 제한은 어떤 방식이 있고 어디에 두는가

## 질문
결제 개선 방안을 하나씩 적용할 때마다 설계와 이론 문서를 남기기로 했다(11/12). 이 노트는 ISE-241(빌링키 등록 횟수 제한)의 이론이다. 다루는 물음은 "요청 횟수 제한은 어떤 방식이 있고 어디에 두는가"다.

## 짧은 답
- 방식은 다섯 가지다: 고정 윈도 카운터, 슬라이딩 윈도 로그, 슬라이딩 윈도 카운터, 토큰 버킷, 누수 버킷. 정확도, 메모리, 순간 몰림 허용 정도가 다르다.
- 제한은 어디에(nginx·Gateway·서비스), 무엇을 기준으로(IP·사용자·전체) 둘지가 방식만큼 중요하다. 막으려는 대상이 "PG 호출 수"처럼 업무 의미를 가지면 업무를 아는 서비스 안에서 사용자 기준으로 둔다.
- 어떤 방식이든 "검사하고 기록"은 한 번에 일어나야 한다. 따로 하면 동시 요청이 모두 통과한다.
- 초과하면 429와 `Retry-After`로 답한다.

## 자세히

### 방식 비교

| 방식 | 동작 | 장점 | 단점 |
|---|---|---|---|
| 고정 윈도 카운터 | 시간을 칸(예: 1분)으로 나눠 칸마다 센다 | 가장 단순하고 메모리가 키당 숫자 하나 | 칸 경계에서 최대 2배가 통과한다(칸 끝에 N, 다음 칸 처음에 N) |
| 슬라이딩 윈도 로그 | 허용한 요청의 시각을 모두 저장하고 "지금부터 최근 W" 안의 수를 센다 | 정확하다 | 메모리가 상한(요청 수)에 비례한다 |
| 슬라이딩 윈도 카운터 | 지금 칸과 앞 칸의 수를 겹친 비율로 섞어 근사한다 | 메모리가 작고 경계 문제가 줄어든다 | 근사값이다 |
| 토큰 버킷 | 일정 속도로 토큰이 차고 요청마다 하나를 쓴다. 가득 차면 더 차지 않는다 | 평균 속도를 지키면서 순간 몰림(버킷 크기만큼)을 허용한다 | 평균과 몰림 두 값을 정해야 한다 |
| 누수 버킷 | 요청이 큐에 들어가 일정 속도로만 나간다 | 출력이 일정하다 | 큐가 차면 거절하고, 대기가 생긴다 |

### 어디에, 무엇을 기준으로
- **위치**: nginx나 Gateway는 서비스 앞에서 싸게 막지만 업무 의미를 모른다(예: "이 API의 PG 발급 시도"). 서비스 안은 업무 단위로 정확하지만 요청이 서비스까지 들어온 뒤라 자원을 조금 쓴다. 보통 거친 방어는 앞단에, 업무 상한은 서비스에 둔다.
- **기준**: IP는 로그인 전에도 쓸 수 있지만 공유 IP(회사·통신사 NAT)를 한 사람처럼 막고, 한 사용자의 여러 IP는 구분하지 못한다. 사용자 기준은 인증 뒤에만 가능하다. 전체 기준은 서비스 보호용 상한이다.

### 저장 위치
- **메모리**: 가장 빠르고 의존이 없다. 재시작하면 초기화되고 인스턴스마다 따로 센다.
- **Redis**: 인스턴스가 여러 개여도 한 곳에서 센다. 의존과 네트워크 호출이 늘고, 증가와 만료를 원자적으로(Lua·`INCR`+`EXPIRE`) 해야 한다.
- **DB**: 영속적이고 감사할 수 있지만 막으려는 요청마다 쓰기가 생겨 폭주할 때 DB가 먼저 부담을 진다.

### check-then-act 경쟁
"세어 보고(check) 상한 미만이면 기록한다(act)"를 두 단계로 나누면, 동시에 온 20개 요청이 모두 "아직 0개"를 보고 통과한다. 상한을 넘는 허용이 생긴다. 해결은 검사와 기록을 한 임계 구역에 넣는 것이다. 메모리라면 사용자별 `synchronized`나 `ConcurrentHashMap.compute`, Redis라면 Lua 스크립트나 원자 연산이다.

### 429와 Retry-After
HTTP 429 Too Many Requests는 "요청이 너무 많다"는 표준 상태다. `Retry-After`는 다시 시도할 수 있을 때까지의 초(또는 날짜)를 알려 주어 클라이언트가 무작정 재시도하지 않게 한다.

### 횟수 제한과 동시 수 제한은 다르다
- 횟수 제한: 일정 기간 안에 몇 번 했는지를 센다(끝난 요청도 센다).
- 동시 수 제한: 지금 진행 중인 것이 몇 개인지를 센다(끝나면 줄어든다). 느린 호출이 자원을 붙잡는 상황을 막는다.

## 이 프로젝트에서는
- **빌링키 등록(ISE-241)**: 사용자당 분 3회·하루 10회, 슬라이딩 윈도 로그, 메모리 보관. 막으려는 것이 PG 발급 호출 수라 허용된 시도는 PG 결과와 상관없이 세고, 검사와 기록은 `compute` 한 구역에서 한다. 설계는 `docs/design/payment/data-model.md` 11절이다.
- **AI 상담**: 사용자당 분 5회·일 30회. 같은 슬라이딩 윈도 로그를 쓴다(assistant-service). 외부 LLM 호출 비용을 묶는 것이다.
- **Gateway 맨 앞 동시 처리 상한**: 동시 수 제한이다. 지금 처리 중인 요청 수를 묶어 CPU·메모리 포화를 막는다.
- **PG 동시 허가**: 동시 수 제한이다. 결제 승인 PG 호출이 동시에 10개를 넘지 않게 한다(Bulkhead).
- 앞의 둘은 "기간 안의 횟수", 뒤의 둘은 "지금 진행 중인 수"를 센다. 호출 비용을 묶을 때는 횟수, 느린 자원이 붙잡히는 것을 막을 때는 동시 수가 맞는 도구다.

## 면접 포인트
- 고정 윈도의 경계 2배 문제와 슬라이딩 윈도 로그의 메모리 비용을 대비해 설명할 수 있어야 한다.
- 토큰 버킷은 순간 몰림을 허용하고, 누수 버킷은 출력을 고르게 한다.
- 분산 환경에서는 메모리 카운터가 인스턴스마다 따로라는 한계를 알고, Redis 원자 연산이 대안이라고 말한다.
- "check-then-act를 어떻게 막았나"에 `compute`로 검사와 기록을 한 구역에 둔 사례와, 동시 20스레드 테스트로 허용 수가 정확히 상한임을 확인한 근거를 든다.
