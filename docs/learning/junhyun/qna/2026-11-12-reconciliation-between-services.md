# 서비스마다 DB가 따로일 때 서로 어긋난 것을 어떻게 찾는가(서비스 간 대사)

## 질문
결제 개선 방안을 하나씩 적용할 때마다 설계와 이론 문서를 남기기로 했다(11/12). 이 노트는 ISE-239(예매↔결제 대사 켜기)의 이론이다. 다루는 물음은 "서비스마다 DB가 따로일 때 서로 어긋난 것을 어떻게 찾는가"다.

## 짧은 답
- 서비스마다 DB가 따로면 한 트랜잭션으로 묶을 수 없다. 서비스는 이벤트로 연결되고, 각 장치는 자기 쪽 실패만 본다. 그래서 어긋남은 반드시 생길 수 있다고 보고 **따로 찾는 장치(대사)**를 둔다.
- 막는 장치(Outbox, 멱등 소비, DLQ)는 어긋남이 생기는 확률을 줄이고, 찾는 장치(대사)는 그래도 생긴 어긋남을 발견한다. 서로 대신할 수 없다.
- 대사는 한쪽 서비스(여기서는 결제)가 주체가 되어 양쪽 데이터를 읽어 비교하고, 허용 지연 안의 차이는 보류하고, 기록과 알림만 남긴다. 자동으로 고치지 않는다.

## 자세히

### 왜 어긋나는가
- 예매와 결제는 DB가 따로이고 이벤트(Kafka)로만 이어진다. 결제가 승인돼도 "승인됨" 이벤트가 예매에 닿고 처리되기 전에는 예매가 아직 `HELD`일 수 있다(일시적).
- 장치마다 자기 쪽 실패만 본다. Outbox는 "결제 DB에 쓴 이벤트가 나간다"를 보장하지만 예매가 이벤트를 제대로 처리했는지는 모른다. DLQ는 처리하지 못한 메시지를 따로 모으지만 메시지가 아예 오지 않은 경우는 모른다. 그래서 둘이 맞아 보여도 양쪽 상태가 다를 수 있다.
- 사람이 직접 SQL로 상태를 바꾸거나 버그가 한쪽만 바꾸는 경우도 이벤트 경로 밖의 어긋남이다.

### 막는 장치와 찾는 장치
| 구분 | 장치 | 무엇을 막거나 찾나 | 못 보는 것 |
|---|---|---|---|
| 막는다 | Outbox | 내 DB에 쓴 변경이 이벤트로 빠짐없이 나감 | 받는 쪽이 처리했는지 |
| 막는다 | 멱등 소비 | 같은 이벤트가 두 번 와도 한 번만 반영 | 이벤트가 오지 않은 경우 |
| 막는다 | DLQ | 처리 못 한 메시지를 모아 사람이 확인 | 메시지 자체가 없는 경우 |
| 찾는다 | 대사 | 양쪽 현재 상태를 비교해 어긋난 것을 발견 | 비교 기준 밖(기간, 허용 지연 안)의 것 |

### 대사의 구성 요소
- **주체**: 누가 비교하나. 돈이 걸린 쪽(결제)이 예매 서비스의 읽기 전용 조회 API를 불러 대조한다. 예매 서비스는 읽기만 허용해 결제가 예매 DB를 건드리지 못한다.
- **무엇을 비교하나**: ID·상태·금액·사용자 같은 값만 비교한다(개인정보는 담지 않는다).
- **허용 지연(allowed lag)**: 정상적으로도 이벤트가 닿기까지 시간이 걸린다. 마지막 갱신이 허용 지연보다 가까운 대상은 판단하지 않고 다음 회차로 미룬다(이 프로젝트 기본 10분).
- **기록과 알림**: 어긋난 것은 `reconciliation_mismatches`에 `OPEN`으로 남기고, 다시 맞으면 `RESOLVED`로 닫고, `OPEN` 수를 지표로 내보내 0보다 크면 알린다.
- **자동 수정을 하지 않는 이유**: 어느 쪽이 맞는지 기계가 모른다. 잘못 고치면 환불·확정이 중복되거나 돈이 틀어진다. 사람이 원인을 확인하고 Ops 명령으로 고친다.

### RC-1~RC-8
| 규칙 | 조건 | 뜻 | 고객이 겪는 일 |
|---|---|---|---|
| RC-1 | 결제 승인, 환불 행 없음, 예매 `HELD` | 승인됐는데 확정되지 않음 | 돈은 나갔는데 예매가 안 잡힘 |
| RC-2 | 결제 승인, 환불 행 없음, 예매 `EXPIRED`·`RELEASED`·`CANCELED` 또는 없음 | 환불 의무가 등록되지 않음(가장 심각) | 돈이 나갔는데 표도 환불도 없음 |
| RC-3 | 결제 환불됨, 예매 `CONFIRMED` | 환불됐는데 확정 유지 | 환불받았는데 표가 살아 있음 |
| RC-4 | 예매 `CONFIRMED`인데 연결된 결제가 없거나 승인이 아님 | 승인 없는 확정 | 결제 없이 표를 가짐 |
| RC-5 | 결제 금액 ≠ 예매 금액(또는 환불 금액 ≠ 승인 금액) | 금액 불일치 | 잘못된 금액이 청구·환불 |
| RC-6 | 결제 사용자 ≠ 예매 사용자 | 사용자 불일치 | 남의 예매에 결제 |
| RC-7 | 결제·환불의 현재 상태 ≠ 이력의 마지막 상태 | 이력 없는 상태 변경 | 기록과 실제가 다름(감사 문제) |
| RC-8 | 확정 전이에 대응하는 Outbox 행이 없음 | 이벤트 없는 확정 | 다른 서비스가 변경을 영영 모름 |

RC-7·RC-8은 결제 DB만 보고, RC-1~RC-6은 예매 서비스를 불러야 한다.

### 오탐을 줄이는 방법
- **허용 지연**: 이벤트가 닿는 시간 안의 차이를 불일치로 세지 않는다.
- **조회 실패와 "없음"의 구분**: 예매 서비스가 죽었거나 404가 났을 때를 "예매가 없다"로 읽으면 모든 결제가 RC-2로 잘못 열린다. 그래서 200 응답에서 빠진 ID만 "없음"이고, 그 밖의 응답은 조회 실패로 그 규칙을 기록·닫기 없이 실패시킨다.
- **대량 누락 기준**: 200 응답이어도 한 묶음이 통째로 비었거나 회차 전체에서 5건 이상·10% 넘게 빠졌으면 조회 실패로 본다(일부 데이터를 못 받은 채 판단하지 않는다).

### "검사하지 않아서 0"과 "검사해서 0"
`OPEN` 불일치 수 지표는 규칙을 끄면 0이 된다. 켜져서 검사한 0과 꺼져서 검사하지 않은 0이 화면에서 똑같이 보이므로, 꺼진 규칙은 알림 문구나 문서에 밝혀야 한다. 이 프로젝트에서도 RC-1~RC-6이 꺼져 있던 동안의 지표 0은 "문제 없음"이 아니었다.

### 금융권의 정산 대사와의 비교
금융권은 하루 단위로 내부 원장과 카드사·VAN·은행의 정산 파일을 대조하고, 차이는 "미결 항목"으로 모아 사람이 처리한다. 방식은 같다(양쪽 기록 비교 → 차이 기록 → 사람이 확인). 이 프로젝트는 외부 정산 파일 대신 예매 서비스의 조회 API를 쓰고, 주기가 일 단위가 아니라 5분 단위이며, 허용 지연 안의 차이를 보류한다는 점이 다르다.

## 이 프로젝트에서는
- 설계는 `docs/decisions/0029-payment-reservation-reconciliation.md`와 `docs/design/payment/events-and-reliability.md` 10절이다. 5분마다 도는 `reconciliation` 작업이 RC-1~RC-8을 규칙별 한 트랜잭션으로 기록한다.
- RC-7·RC-8만 켜져 있다가 11/12에 로컬 전체 스택에서 실제 예매 서비스와 붙여 확인하고 RC-1~RC-6도 켰다(ISE-239). 정상 회차 불일치 0, 예매를 `EXPIRED`로 바꾸면 한 회차 뒤 RC-2가 열려 알림이 나가고, 되돌리면 한 회차 뒤 `RESOLVED`가 되고, 예매 서비스를 멈추면 RC-1~RC-6만 실패하고 RC-7·RC-8은 돈다는 것을 확인했다.
- 가짜 서버로 검증한 테스트와 실제 서비스를 붙여 본 확인은 다른 것이다. 가짜 서버는 우리가 이해한 응답 모양만 검증하고, 실제 연결은 필드 이름·시각 형식·서비스 발견 같은 어긋남을 드러낸다.

## 면접 포인트
- "MSA에서 데이터 정합성을 어떻게 보장하나"에 막는 장치(Outbox, 멱등, DLQ)와 찾는 장치(대사)를 나눠 답한다. 최종 일관성에서는 어긋남이 생긴다고 가정하고 발견·복구 경로를 둔다.
- 허용 지연, 조회 실패와 "없음" 구분 같은 오탐 방지 설계를 말한다.
- 자동 수정을 하지 않고 기록·알림·사람 확인으로 남긴 이유(어느 쪽이 맞는지 모름)를 설명한다.
- "검사하지 않아서 0" 문제와 가짜 서버 테스트의 한계를 실제 연결 확인으로 메운 경험을 든다.
