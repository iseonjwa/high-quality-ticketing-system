# 실패한 요청을 언제, 몇 번, 얼마나 기다렸다가 다시 보내야 하는가

## 질문
결제 개선 방안을 하나씩 적용할 때마다 설계와 이론 문서를 남기기로 했다(11/12). 이 노트는 ISE-242(결제 503 자동 재시도)의 이론이다. 다루는 물음은 "실패한 요청을 언제, 몇 번, 얼마나 기다렸다가 다시 보내야 하는가"다.

## 짧은 답
- **언제**: 다시 보내도 결과가 같거나 안전한 실패(멱등한 요청, 서버가 아무것도 만들지 않은 거절)일 때만 보낸다.
- **몇 번**: 적게 보낸다. 재시도는 서버가 이미 힘들 때 요청을 더 얹는 일이라 한도(횟수, 예산)가 필요하다.
- **얼마나 기다리나**: 서버가 알려 주면(`Retry-After`) 그 값을, 아니면 지수 백오프에 지터(무작위)를 섞어 같은 순간에 몰리지 않게 한다.
- 재시도는 **한 층에서만** 한다. 화면·Gateway·서비스가 모두 재시도하면 횟수가 곱해진다.

## 자세히

### 다시 보내도 되는 실패와 안 되는 실패
- **멱등성**: 같은 요청을 여러 번 보내도 한 번 보낸 것과 결과가 같으면 다시 보내도 안전하다. 같은 멱등키를 붙이면 결제 승인 같은 POST도 멱등하게 만들 수 있다.
- **결과를 아는 거절**: 서버가 "아무것도 만들지 않았다"고 확실히 말한 실패(이 프로젝트의 503 `PG_UNAVAILABLE`, ADR 0018)는 다시 보내도 된다.
- **결과를 모르는 실패**: 타임아웃·연결 끊김은 서버가 처리했는지 모른다. 멱등키가 없으면 다시 보내다 중복 처리가 생길 수 있다. 같은 키로 보내 서버가 중복을 걸러 주거나, 먼저 조회로 결과를 확인한다.
- **다시 보내도 소용없는 실패**: 400·403·409처럼 요청 자체나 상태가 문제인 실패는 다시 보내도 같은 답이다.

### 기다리는 방법: 고정, 지수 백오프, 지터
| 방식 | 대기 | 특징 |
|---|---|---|
| 고정 지연 | 늘 1초 | 단순하지만 같은 순간에 실패한 요청이 같은 순간에 다시 몰린다 |
| 지수 백오프 | 1초, 2초, 4초… | 서버가 회복할 시간을 점점 더 준다 |
| full jitter | 0 ~ (지수 값) 사이 무작위 | 몰림을 가장 잘 흩뜨린다. 대기가 매우 짧을 수도 있다 |
| equal jitter | (지수 값)/2 + 0 ~ (지수 값)/2 무작위 | 최소 대기를 보장하면서 흩뜨린다 |

**thundering herd(몰려드는 떼)**: 서버가 순간 실패해서 한꺼번에 거절된 1,000명이 모두 정확히 1초 뒤 다시 보내면 서버는 1초 뒤에 같은 크기의 충격을 또 받는다. 지터로 그 시점을 흩뜨린다.

### 재시도 폭주와 재시도 예산
서버가 과부하일 때 각 요청이 3번씩 다시 보내면 부하는 최대 4배가 된다. 그래서 재시도에는 한도를 둔다: 요청당 최대 횟수, 또는 전체 요청 대비 재시도 비율(재시도 예산, 예: 10% 이하)을 둔다. 층이 여럿이고 각각 3번씩 재시도하면 3×3×3 = 27배까지 곱해진다. 그래서 한 층(보통 가장 바깥, 멱등키를 아는 쪽)에서만 한다.

### Retry-After
서버가 "몇 초 뒤에 다시 와"라고 알려 주는 응답 헤더(429·503)다. 서버가 가장 잘 아는 값이므로 클라이언트의 추측보다 우선한다. 단, 너무 긴 값은 사용자 경험을 해치므로 상한을 둘 수 있다.

### 차단기와 재시도의 관계
차단기(circuit breaker)는 실패가 많으면 잠시 호출 자체를 막는다. 차단기가 열린 동안(이 프로젝트는 10초)에는 다시 보내도 또 거절이다. 그래서 재시도는 "순간 포화" 같은 짧은 실패에만 효과가 있고, 차단기가 열린 긴 장애에는 몇 번을 보내도 소용없이 부하만 더한다. 재시도 횟수를 적게 두는 이유다.

## 실패 종류별 처리

| 실패 | 서버가 만든 것 | 처리 |
|---|---|---|
| 503 `PG_UNAVAILABLE`(허가 못 얻음, 차단기 OPEN) | 없음 | 같은 키로 한 번 자동 재시도(1~2초 무작위, 누름 한 번당), 또 실패하면 사용자가 [다시 결제하기] |
| 응답 없음·504(결과 모름) | 모름 | 같은 키·같은 본문으로 최대 8회, 3초부터 늘려 가며 지터, 그동안 결제 조회로 확인 |
| 429·502 | 모름 또는 없음 | 결과 모름과 같은 재전송 |
| 400·403·409 | 없음 또는 이미 있음 | 다시 보내지 않고 단계별 안내(토큰 만료, 이미 있음 등) |

## 이 프로젝트에서는
- **이번 한 번 재시도(ISE-242)**: 11/12 배포 측정에서 PG 동시 허가가 찬 순간 포화는 수 ms~수백 ms 안에 풀렸다. 그래서 503 `PG_UNAVAILABLE`을 한 번만, 1초 + 무작위 0~1초 뒤 같은 멱등키·본문으로 자동으로 다시 보낸다. 서버가 이 503에서 행도 멱등 기록도 만들지 않으므로 안전하다. 차단기가 열린 장애에는 효과가 없으니 한 번으로 끝내고 사용자가 다시 누르게 한다. 설계는 `docs/design/frontend/README.md` 결제 절이다.
- **결과 모름 재전송**: 응답 없음·504·429·502는 같은 키·같은 본문으로 최대 8회, 3초부터 늘리고 지터를 섞는다(`queryRetryDelay`).
- **Gateway에는 POST 재시도 필터를 두지 않는다**(ADR 0018): 재시도는 멱등키를 아는 화면 한 층에서만 하고, 층이 겹쳐 곱해지는 것을 막는다.
- **대기열 폴링**: 순번 조회 간격에도 지터를 섞어 폴링이 같은 순간에 몰리지 않게 한다.

## 면접 포인트
- "재시도는 멱등할 때만"이라는 전제와, 멱등키로 POST를 안전하게 만든 방법을 말한다.
- 지수 백오프와 지터를 왜 같이 쓰는지(thundering herd) 설명한다.
- 재시도 폭주, 한 층에서만 재시도하는 이유(곱셈), 차단기가 열린 장애에서 재시도가 소용없는 이유를 든다.
- 결과를 아는 거절과 결과를 모르는 실패를 구분해 처리한 사례로 이 프로젝트의 결제를 든다.
