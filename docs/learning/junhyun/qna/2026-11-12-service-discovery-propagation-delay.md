# 서비스를 다시 띄우면 왜 한동안 503이 나나 (서비스 발견의 캐시와 전파 지연)

## 질문

결제 개선 방안을 하나씩 적용할 때마다 설계와 이론 문서를 남기기로 했다(11/12). 이 노트는 ISE-244(다시 띄운 뒤 서비스 발견 지연)의 이론이다. 다루는 물음은 "컨테이너는 healthy인데 왜 Gateway는 한동안 그 서비스를 못 찾는가"다.

## 짧은 답

- Gateway는 요청마다 Eureka에 묻지 않는다. 인스턴스 목록의 사본을 들고 있다가 주기적으로 갱신한다. 사본이 세 겹(Eureka 서버 응답 캐시, 클라이언트 레지스트리 사본, LoadBalancer 캐시)이라 새 인스턴스가 라우팅에 닿기까지 각 주기의 합만큼 걸릴 수 있다.
- 기본 주기는 30초·30초·35초다. 이 프로젝트는 배포 프로필에서 5초씩으로 줄였다.
- "컨테이너가 떴다"와 "다른 서비스가 그것을 찾을 수 있다"는 다른 사실이다. 배포 확인과 부하 측정은 이 차이를 기다려야 한다.

## 자세히

### 서비스 발견이 푸는 문제

컨테이너는 다시 만들어질 때마다 IP가 바뀐다. 인스턴스 수도 늘고 준다. 호출하는 쪽이 주소를 설정 파일에 적어 둘 수 없으므로 "이름 → 지금 살아 있는 주소 목록"을 알려 주는 등록소가 필요하다.

| 방식 | 누가 목록을 보고 고르나 | 예 |
|---|---|---|
| 클라이언트 쪽 발견 | 호출하는 쪽이 등록소에서 목록을 받아 직접 고른다 | Eureka + Spring Cloud LoadBalancer(이 프로젝트) |
| 서버 쪽 발견 | 호출하는 쪽은 고정 주소(로드밸런서, DNS 이름)만 알고 중간이 고른다 | AWS ALB, Kubernetes Service, Docker compose의 서비스 이름 |

클라이언트 쪽 발견은 중간 홉이 없고 호출하는 쪽이 분산 방식을 정할 수 있다. 대신 모든 호출자가 목록의 사본을 들고 있어 사본이 낡는 시간이 생긴다.

### 사본이 세 겹이다

```
서비스 기동 → Eureka 등록(즉시)
  → ① Eureka 서버의 읽기 전용 응답 캐시 갱신   (기본 30초)
  → ② 클라이언트가 레지스트리를 다시 가져옴      (기본 30초)
  → ③ LoadBalancer의 인스턴스 목록 캐시 만료    (기본 35초)
  → Gateway가 새 주소로 보냄
```

- ①은 Eureka 서버가 조회 부하를 줄이려고 둔 캐시다. 등록은 바로 반영되지만 클라이언트에 주는 응답은 주기적으로만 갱신된다.
- ②는 Eureka 클라이언트의 원래 동작이다. 등록소가 잠깐 죽어도 클라이언트는 가진 사본으로 계속 호출한다.
- ③은 Spring Cloud LoadBalancer가 요청마다 목록을 다시 만들지 않으려고 둔 캐시다.
- 세 주기는 서로 맞물리지 않으므로 운이 나쁘면 합(95초)에 가깝게, 평균으로는 그 절반쯤 걸린다.

### 왜 이렇게 느슨하게 만들었나

Eureka는 일관성보다 가용성을 고른 등록소다(CAP에서 AP). 등록소와 통신이 끊겨도 호출이 멈추지 않게 클라이언트가 사본을 믿고, 서버는 갱신(heartbeat)이 한꺼번에 끊기면 네트워크 문제로 보고 인스턴스를 지우지 않는다(자기 보호 모드). 그 대가가 "낡은 목록으로 잠깐 잘못 보낼 수 있다"이다. 그래서 호출하는 쪽에는 재시도, 시한, 차단기가 같이 있어야 한다.

### 내려가는 쪽도 같다

인스턴스가 정상 종료하면 Eureka에서 바로 빠지지만, 호출자들의 사본에는 같은 주기만큼 남는다. 그동안 죽은 주소로 보낸 요청은 연결 실패가 된다. 비정상 종료면 Eureka가 갱신이 끊긴 것을 알아채는 시간(기본 90초)까지 더해진다. 무중단 배포에서 "먼저 등록을 빼고, 사본이 갱신될 때까지 기다린 뒤, 프로세스를 내린다"는 순서를 지키는 이유다.

### 주기를 줄이면 무엇을 내는가

- 등록소 조회가 늘어난다. 서비스 수 × (1 ÷ 주기)다. 변경분만 받는 조회라 작은 규모에서는 부담이 없다.
- 등록소가 잠깐 흔들릴 때 그 흔들림이 더 빨리 호출자에게 전파된다. 캐시가 길면 흔들림을 덮어 주는 면이 있다.

## 이 프로젝트에서는

- 두 번 겪었다. 첫 배포의 스모크 실패(TS-34, 약 35초)와 11/12 결제 측정(다시 띄운 뒤 약 55초, 결제 176건 503).
- 처음에는 스모크가 기다리게 고쳤고(120초 재확인), 이번에 배포 프로필의 세 주기를 5초로 줄였다(`config-repo/application-prod.yml`, `config-repo/eureka.yml`). local 프로필은 처음부터 5초였는데 배포 프로필에는 빠져 있었다.
- 인스턴스가 하나라 앱이 뜨는 동안(약 25초)의 공백은 남는다.
- 단일 서버 compose에서는 Docker DNS(서비스 이름)로 바로 부르면 발견 지연이 없다. 그래도 Eureka를 쓰는 이유는 발제의 Spring Cloud 구성과, 인스턴스를 늘렸을 때의 분산 때문이다.
- 측정 절차에는 "서비스를 다시 만든 뒤 60초 넘게 기다린다"를 적었다(`loadtest/k6/README.md`).

## 면접 포인트

- "컨테이너 healthy"와 "라우팅 가능"의 차이를 실제 장애(스모크 실패, 측정 중 503)로 설명한다.
- 캐시가 어디에 몇 겹 있는지와 각 캐시가 왜 있는지(조회 부하, 등록소 장애 내성)를 말한다. 주기를 줄일 때 내는 것도 함께 말한다.
- 무중단 배포의 종료 순서(등록 해제 → 전파 대기 → 종료)와 연결한다.
