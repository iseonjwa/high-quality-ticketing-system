# 최종 발표에서 심사위원은 무엇을 보나, 우리는 무엇을 더 채워야 하나

## 질문
"발표 때 심사위원이 좋게 평가하려면 어떤 부분을 더 보완해야 할까?" 발표 자료에는 직접 겪고 해결한 경험을 기본으로 넣고, 우리의 판단 비중을 크게 둘 생각이다. 작업량은 다른 조에 뒤지지 않는다고 본다. 이어서 "AI가 만든 코드를 검토하는 방법도 만들어 넣어야겠다. 4조는 CodeRabbit을 달고 리뷰를 적극적으로 했다"는 말이 붙었다.

## 짧은 답
- 심사는 발제문이 정한 필수 산출물, "왜 그렇게 했나"에 대한 설명, AI 활용을 본다. 질문은 제출 자료를 보고 미리 쓴다. 그래서 작업량보다 제출 자료에서 필수 항목이 빠짐없이 보이는지가 먼저다.
- 2026-11-13 기준으로 비어 있는 필수 산출물이 있다. Synthetic Data(ISE-28 취소), 동기형과 접수형 비교 측정(ISE-18 Backlog), 발제 기준 형식(100명 × 10회)의 요약 표, Kafka-UI 캡처, AI 대표 사례 2건 정리다.
- 작업량은 숫자로 앞선다. 하지만 PR 316개 중 GitHub 리뷰가 남은 PR은 12개다. AI를 많이 썼다는 것이 드러날수록 "AI가 만든 코드를 누가 어떻게 검증했나"는 질문이 먼저 나온다. 검증은 해 왔지만 그 흔적이 PR에 남지 않았다. 지금 채울 수 있는 것은 검증 방법을 한 장으로 정리하고, 남은 PR부터 리뷰를 PR에 남기는 것이다.

## 자세히

### 발제문이 정한 평가 근거
Notion [발제문 원본](https://app.notion.com/p/4027bd823b758019a04dda70d6ae39ab)에서 확인했다(2026-11-13).
- 발표회(11/19, ZEP): 외부 심사위원이 참관한다. 질문은 "자료를 바탕으로 사전 작성"하고, AI 활용 부분도 랭킹에 반영한다. 서면 피드백은 없다.
- 필수 항목과 산출물
  - 분산 트랜잭션(SAGA): 대상 트랜잭션과 실패 시나리오 문서, 기술 선택 근거, 이벤트 흐름도, 실패 → 보상이 동작하는 로그·화면 캡처.
  - 대용량 트래픽: 측정 환경 기록표, 동시 100명 · 1초 안에 시작 · 각 10회(총 1,000회) 기준의 평균 응답 시간·처리량·성공률, 최적화 전·후 2회 이상, 개선 내역 1~3줄, Kafka-UI의 Topic·Consumer 그룹 캡처, 파티션 수·키를 고른 이유 한 줄. API가 요청을 Kafka에 넣고 바로 응답한 뒤 Consumer가 처리하는 구조가 필수다.
  - 모니터링: Prometheus와 Grafana 대시보드.
  - 최소 구현: 실패 정의 문서와 구현, Kafka 실패·중복 대응, 유실 방지 패턴 1개 이상, 부하 테스트(100명 × 10회 기준).
  - AI 설계 검증 로그: 계층형(4계층) 검증 필수, 거부 1건 이상.
  - Synthetic Data: LLM에 쓴 프롬프트 원문, 생성한 CSV, 일반 부하 결과와 Synthetic Data 기반 결과의 비교.
  - 발표 자료의 AI 대표 사례 2건 이상. 사례마다 해결하려던 작업, Claude Code 활용 방식, 채택·수정·기각 이유, 빌드·테스트·API 검증 결과, 팀이 직접 내린 MSA 설계 판단을 넣는다.
- 대용량 트래픽 항목의 핵심 문장: "특정 숫자를 찍는 것"이 아니라 "병목을 어떻게 찾고 무엇을 바꿨나"에 답할 수 있어야 한다.

리뷰 수는 GitHub GraphQL로 PR마다 리뷰를 모아 셌다. 4조 리뷰 384건에는 작성자가 CodeRabbit 코멘트에 답한 것도 들어 있다.

### 왜 리뷰가 PR에 적은가
팀 규칙이 그렇게 정했다. `docs/guides/git-workflow.md` 5절은 "필수 승인은 없다. 작성자가 AI 검증을 거친 뒤 머지하고 팀에 알린다"이고, 리뷰 대신 CI(`build`, `records-check`)를 필수 관문으로 둔다. 검증 자체는 로컬 세션에서 했다. 다른 모델로 diff를 다시 읽게 하거나(Opus, codex), 지적마다 수용·거부를 판단 기록에 남겼다. 그 결과가 PR 화면에 남지 않았을 뿐이다. 그래서 할 일은 새로 만드는 것보다, 해 온 방법을 적고 증거를 보이게 하는 쪽이다.

### AI가 만든 코드를 검토하는 방법 (정리 초안)
지금 쓰는 장치를 순서대로 묶으면 네 겹이다. 팀원마다 쓰는 도구가 달라 2번은 사람별로 모아야 한다.
1. **쓰기 전에 기준을 고정한다.** SA·ADR·계약(contract 이슈)을 먼저 정하고 AI는 그 안에서 구현한다. 설계를 AI가 정하지 않게 한다.
2. **쓴 모델과 다른 모델이 검토한다.** 지적마다 사람이 수용·부분 수용·거부를 고르고 이유를 `docs/ai-judgments/`에 남긴다. 거부 55건이 이 과정의 흔적이다.
3. **CI가 자동으로 막는다.** `verifyWorkspace`(격리 DB·Redis로 전체 빌드와 JUnit), `records-check`(기록 구조와 비밀값 흔적), Prometheus·Loki 규칙 검사, 프론트 lint·test·build.
4. **배포 환경에서 확인한다.** 배포 서버에서 시연 시나리오와 k6 측정을 돌리고 Grafana·Zipkin으로 본다.

남은 기간에 보탤 것:
- 남은 PR부터 2번의 결과를 PR에 남긴다. 방법은 둘이다. Claude Code의 `/code-review --comment`로 지적을 인라인 코멘트로 올리고 작성자가 수용·거부로 답한다. 또는 CodeRabbit을 단다. CodeRabbit 공식 문서는 공개 저장소를 무료(Team 기능)로 본다고 적는다. 설치는 GitHub 조직 관리자가 한다.
  - 이후 같은 날 결정: CodeRabbit은 리뷰 횟수의 시간당 한도 때문에 넣지 않고 프롬프트로만 리뷰한다([판단 기록](../../../ai-judgments/junhyun/2026-11-13-no-coderabbit-prompt-review-only.md)).
- 지난 기록에서 "AI 리뷰가 실제로 잡은 결함"과 "AI 리뷰 지적을 거부한 사례"를 각각 골라 대표 사례로 만든다. 사례에는 빌드·테스트·API 검증 결과가 들어가야 한다.
- 이 방법을 팀 규칙으로 바꾸려면 `git-workflow.md` 5절을 PR로 고치고 팀이 동의해야 한다.

### 판단을 발표에 넣는 형식
판단 비중을 크게 두려면 장마다 "문제 → 선택지 2~3개 → 고른 것 → 버린 것과 그 이유 → 결과 수치 → 치른 대가"를 한 장에 넣는다. 심사위원은 "그 판단이 맞았다는 근거는?"을 묻는다. 그래서 판단마다 측정이나 테스트 결과를 하나씩 붙인다. ADR 58개를 다 보여 주기보다 3~4개를 깊게 보여 주고, 나머지는 "판단 기록 170건, 거부 55건"처럼 숫자로 보인다.

## 면접 포인트
- **AI가 만든 코드를 어떻게 믿었나?** 쓰기 전에 설계와 계약을 사람이 정했고, 쓴 모델과 다른 모델이 검토했고, 지적마다 사람이 판단해 기록했다. CI가 통합 테스트와 비밀값 검사로 막았고, 배포 서버에서 측정으로 다시 확인했다.
- **리뷰 승인 없이 머지한 이유는?** 다섯 명이 서비스를 하나씩 맡아 리뷰 대기가 병목이 되는 것을 피하려고 승인 대신 CI를 필수 관문으로 뒀다. 대가는 리뷰 흔적이 PR에 남지 않는 것이다.
