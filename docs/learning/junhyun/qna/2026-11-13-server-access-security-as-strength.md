# 서버 접근을 보안 그룹·사람별 키·접속 기록으로 묶은 것이 발표에서 장점이 되나

## 질문
"서버 접속할 때 보안 그룹 설정하고, 팀원들만 접근할 수 있게 하고, 누가 접근했는지도 다 기록에 남도록 해서 보안도 챙긴 건데, 이것도 장점인가?"

## 짧은 답
장점이 맞다. 다만 "보안 그룹을 설정했다"는 기본기라 그것만으로는 점수가 크게 붙지 않는다. 장점이 되는 지점은 원칙이다. 꼭 필요한 것만 열고(최소 노출), 사람마다 따로 열쇠를 주고(사람별 추적), 측정 기기에도 그날 필요한 키만 두었다(최소 권한). 이 원칙을 SA 9-2에서 먼저 정하고 배포·측정 절차까지 이어서 지켰다는 점을 보여야 한다.

"누가 접근했는지 다 기록에 남는다"는 과장이다. 정확히는 **누가 언제 들어왔는지는 사람별로 남고, 들어와서 무엇을 했는지는 사람별로 남지 않는다.** 그리고 보안을 장점으로 내세우면 "서비스가 HTTP라 비밀번호가 평문으로 간다"는 질문이 먼저 나온다. 한계를 같이 적어야 장점이 산다.

## 자세히

### 바탕 개념
- **최소 노출(attack surface 줄이기)**: 밖에서 닿을 수 있는 포트와 화면을 줄인다. 열린 문이 적으면 설정 실수 하나가 사고로 이어질 길도 적다.
- **심층 방어(defense in depth)**: 한 겹이 틀려도 다음 겹이 막게 한다. 예를 들어 보안 그룹을 잘못 열어도 컨테이너가 `127.0.0.1`에만 묶여 있으면 밖에서 닿지 않는다.
- **최소 권한**: 필요한 사람에게 필요한 권한만, 필요한 동안만 준다.
- **인증과 추적은 다르다.** 인증은 "들어올 자격이 있나"이고, 추적(attribution)은 "누가 했나"다. 계정 하나를 여럿이 쓰면 인증은 되지만 추적은 약해진다.
- **기록의 무결성**: 감사 기록은 기록 대상이 지울 수 없는 곳에 있어야 증거가 된다. 같은 서버에 있고 그 서버의 관리자 권한을 모두가 가지면 증거로서 약하다.

### 이 프로젝트에서 실제로 한 것
2026-11-13 저장소 문서와 서버에서 확인했다.

| 원칙 | 한 것 | 근거 |
|---|---|---|
| 최소 노출 | 배포 서버는 80(프론트 nginx)만 전체에 연다. Gateway 8080은 닫았고 외부에서 막힌 것을 확인했다. DB·Redis·Kafka는 포트를 열지 않는다 | `design/infra/deployment.md` 3절·검증 |
| 최소 노출 | 관리 화면(Kafka-UI, Prometheus, Alertmanager, Zipkin, Jenkins)은 SSH 터널로만 연다. Grafana만 팀원 IP에 읽기 전용으로 열었다 | `guides/deploy-server-access.md` 3절, 11/5 판단 기록 |
| 심층 방어 | 관리 화면은 compose에서 `127.0.0.1`에만 묶고, 내부 서비스는 `ports` 없이 `expose`만 쓴다. 보안 그룹을 잘못 열어도 밖으로 안 나간다 | SA 9-2 |
| 심층 방어 | Kafka-UI를 읽기 전용으로 두어 관리 화면에서 `RefundRequested` 같은 이벤트를 위조하는 길을 닫았다 | SA 9-2, ADR 0020 |
| 사람별 키·IP 제한 | SSH 22번은 팀원 IP `/32`만 받는다. 공개 키를 사람마다 등록해 한 명을 빼거나 키가 새면 그 줄만 지운다 | 11/4 판단 기록, `deploy-server-access.md` 2절 |
| 서버끼리는 보안 그룹 참조 | Jenkins → 배포 서버 22, 발생기 → 배포 서버 8080·9090은 IP가 아니라 상대 보안 그룹을 소스로 허용한다. 9090은 측정 중에만 연다 | `deployment.md`, `load-test.md`, ADR 0046 |
| 최소 권한 | 발생기에는 운영 키와 관리자 비밀번호를 두지 않는다. 측정 모드를 켤 때마다 새로 만든 측정 전용 키만 그날 측정자 폴더에 두고 끝나면 지운다 | `guides/loadgen.md`, ADR 0046 변경 |
| 최소 권한 | AWS 콘솔은 계정 주인만 쓴다. Jenkins 관리자 비밀번호는 저장소가 아니라 서버 파일(권한 600)에 있다 | `deploy-server-access.md` |
| 추적 | sshd가 로그인마다 키 지문을 남긴다. 발생기는 키 지문 4개로 682번, Jenkins 서버는 2개로 43번의 공개 키 로그인이 남아 있었다(회전된 기록 포함, IP는 보지 않고 지문별로만 셈). 배포 서버는 이 세션에서 접속하지 못해 확인하지 않았다 | 서버 `/var/log/auth.log*` |
| 추적 | 측정 모드는 `MEASURER=<이름>` 없이 켜지지 않고, 켜고 끌 때 측정자·시각·커밋이 슬랙에 자동으로 남는다. 발생기 사용 시작·끝도 팀 채널에 이름을 붙여 알린다 | `script/loadtest/measure-mode.sh`, ISE-223·224·228 |
| 비밀값 | `.env`는 커밋하지 않고, PR마다 `records-check`가 비밀값 흔적을 검사한다 | AGENTS.md 대전제 8, CI |

### 한계 (발표에서 먼저 말할 것)
| 한계 | 왜 문제인가 | 지금 | 다음 단계라면 |
|---|---|---|---|
| 서비스가 HTTP다 | 로그인 비밀번호와 JWT가 평문으로 오간다 | 도메인·인증서 없이 짧은 기간 운영(배포 문서에 "https 아님"이라고 적음) | 도메인 + 인증서(ALB와 ACM, 또는 Let's Encrypt) |
| 계정 하나(`ubuntu`, sudo·docker 권한)를 같이 쓴다 | 들어온 사람은 키 지문으로 알지만, 들어와서 한 명령은 사람별로 남지 않는다 | "서버에서 하지 않을 것" 규칙과 배포는 Jenkins로만 | 사람별 계정, 또는 AWS Systems Manager Session Manager(세션 기록이 사람별로 남음) |
| 접속 기록이 같은 서버에 있다 | sudo가 있는 사람은 기록을 지울 수 있다 | 없음 | 기록을 서버 밖(CloudWatch Logs 등)으로 보냄 |
| IP 허용 목록을 손으로 고친다 | 집·카페마다 IP가 바뀌어 운영 부담이 있고, 같은 공인 IP를 쓰는 다른 사람도 통과한다(키가 있어야 들어오지만) | 바뀌면 담당에게 IP를 보냄 | Session Manager는 22번을 열지 않아도 된다 |
| Grafana 익명 보기 | 팀원 IP에서는 로그인 없이 지표를 본다 | 읽기 전용, 팀원 IP만 | 시연 뒤 닫거나 로그인 |

### 발표에 넣는 방법
- 보안을 따로 한 장으로 세우지 않는다. 배포 장표 한쪽에 "운영 원칙: 최소 노출·사람별 키·측정 잠금" 상자 하나와, 한계 표(ISE-276)에 위 다섯 줄을 넣는 정도가 맞다. 발제 요구사항과 짝지은 SA 3장 목표 표에 보안 항목은 따로 없다.
- 가장 설득력 있는 예는 측정 쪽이다. 발생기에는 운영 키를 두지 않고 측정 전용 키만 그날만 두며, 측정 모드를 누가 켰는지 슬랙에 자동으로 남는다. "공용 기기를 여럿이 쓰면서도 권한과 책임을 사람 단위로 나눴다"는 이야기가 된다.
- 말할 때는 "다 기록된다" 대신 "접속은 사람별 키로 추적되고, 서버 안의 행동은 계정을 같이 써서 추적이 약하다. 그래서 배포는 Jenkins로만 하게 막았다"처럼 한계까지 한 번에 말한다.

## 이 프로젝트에서는
- 설계: SA 9-2(외부 노출과 접근, 결정 #57). 실제 규칙은 `design/infra/deployment.md` 3절 표가 정본이다(Jenkins·발생기 행을 더함). SA 9-2 표는 이전 안(8080 공개, 3000 터널 전용)으로 남아 있고, 지금은 프론트 nginx 80이 진입점, Grafana 3000은 팀원 IP에만 열렸다(11/5 결정).
- 팀원 안내: `guides/deploy-server-access.md`, `guides/loadgen.md`.
- 한계 표는 ISE-276(도입하지 않은 것·알려진 한계)에 넣는다.

## 면접 포인트
- "보안 그룹으로 막았다"보다 "열린 포트를 80 하나로 줄이고, 관리 화면은 로컬 바인딩과 SSH 터널의 두 겹으로 막았다"가 낫다. 왜 두 겹인지(설정 실수 대비)를 말할 수 있어야 한다.
- 인증과 추적을 구분해서 말한다. 사람별 키는 추적의 시작이지만 공용 계정에서는 거기서 멈춘다. 다음 단계로 Session Manager나 사람별 계정을 말할 수 있으면 깊이가 보인다.
- 장점을 말할 때 한계(HTTP)를 먼저 꺼내면 질문을 미리 막는다.
