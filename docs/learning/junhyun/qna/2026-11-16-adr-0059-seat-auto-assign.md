# ADR 0059 자동 배정 선점은 무엇을 정했고 왜 아직 "제안"인가

## 질문
"59번 결정은 뭔데?" 프런트에 자동 배정 버튼을 붙이면서(ISE-304, PR #714) 머지 전에 확인할 결정으로 ADR 0059를 짚자 나온 질문이다.

## 짧은 답
- 사용자가 좌석 대신 **구역과 매수만** 고르면 서버가 좌석을 골라 바로 선점하는 API(`POST /schedules/{id}/reservations/auto`)를 더한 결정이다.
- 서버는 구역 안 빈 좌석을 좌석 ID 순으로 `FOR UPDATE SKIP LOCKED`로 잠근다. 남이 잠근 좌석은 기다리지 않고 건너뛰므로 "이미 선택된 좌석" 409와 그 뒤 830KB 좌석 재조회가 없어진다.
- 상태가 "제안"인 까닭은 두 가지다. 강민이 맡긴 야간 작업으로 먼저 만들고 좌석 선점 담당(권우)의 사후 확인을 받지 못했다. 그리고 배포 측정에서 한 번 크게 나빴고(확정 433명, 같은 버전 직접 선택 약 2,200명), 원인인 인덱스를 고친 뒤 재측정을 아직 하지 않았다.

## 자세히

### 왜 만들었나
11/15 균일 O1(사용자 3,000명) 측정에서 병목은 좌석 충돌이었다. 선점 409가 2,298건, 409 뒤 좌석 재조회가 1,904건이었고 확정은 1,973명이었다. 서버를 그대로 두고 k6만 "충돌 없이 나눠 둔 좌석"으로 고쳐 상한을 재 보니 확정이 2,638명(+33.7%)으로 늘었다. 충돌이 없으면 얼마나 나아지는지 확인했으니, 실제로 서버가 좌석을 골라 주는 API를 두고 다시 재기로 했다.

### 무엇을 정했나
| 항목 | 정한 것 | 이유 |
|---|---|---|
| API | 새 경로 `/reservations/auto`, 본문 `{grade 또는 section, quantity}`. 헤더·입장 토큰·201 응답은 기존 선점과 같다 | 기존 경로에 섞으면 `seatIds` 검증·사전 거절·접수형 분기마다 조건이 늘어 읽기 어렵다 |
| 잠금 | `ORDER BY id LIMIT :quantity FOR UPDATE SKIP LOCKED` 뒤 기존 조건부 UPDATE로 HELD | 그냥 `FOR UPDATE`면 같은 구역 앞 ID로 몰린 요청이 줄을 서 기다리다 `lock_timeout`(500ms)으로 409가 된다. 자동 배정의 목적(대기 없애기)과 맞지 않다 |
| 연석 | 보장하지 않는다 | 좌석 ID가 구역·열·번호 순이라 대개 붙지만, 이웃 계산을 가져오면 `lottery → seathold` 순환 의존이 생긴다 |
| 구역 매진 | `409 ZONE_SOLD_OUT`. 다른 구역으로 넘기지 않는다 | 어느 구역으로 넘길지는 사용자가 정한다 |
| 멱등 | 멱등키 행을 좌석 잠금 전에 쓰고(좌석은 빈 배열), 같은 트랜잭션에서 고른 좌석으로 채운다. 같은 키 재요청은 `auto_criteria` 문자열(예: `section=A;quantity=2`)로 비교한다 | 같은 키 연타가 서로 다른 좌석을 잡지 않게 PK로 줄 세운다 |
| 모드 | 접수형 설정이어도 동기형으로 답한다 | 고를 좌석이 정해지기 전에는 접수형 메시지 키(구역)를 정할 수 없다 |

`SKIP LOCKED`는 PostgreSQL이 다른 트랜잭션이 잠근 행을 기다리지 않고 결과에서 빼는 옵션이다. 작업 큐에서 "아직 아무도 안 가져간 일"을 꺼낼 때 흔히 쓴다. 좌석 배정도 "아직 아무도 안 잡은 좌석 N개"를 꺼내는 일이라 같은 패턴이다. 다만 잠긴 좌석을 "없는 것"으로 세므로, 그 요청이 롤백되면 좌석이 다시 생긴다. 그래서 프런트는 `ZONE_SOLD_OUT`을 "매진"이라 단정하지 않고 "지금 2석을 잡지 못했다"고 안내한다(PR #714 셀프 리뷰).

### 지금 상태
- 배포 실측(11/16 06:41, 사용자 3,000명): 자동 배정 모드는 확정 433명, 같은 버전 직접 선택은 2,162~2,201명이었다. 정합성은 맞았다(중복 0).
- 원인(TS-72): 회차 안 ID 순 인덱스가 없어 큰 테이블을 처음부터 훑었다. `(schedule_id, section, id)` 등 인덱스를 더하고 받은 조건만 SQL에 넣게 고쳐 로컬 재현에서 한 번에 300ms대 → 0.04~0.21ms가 됐다. 배포 재측정은 아직이다.
- 그래서 ADR의 후속 작업이 세 가지 남아 있다: 권우 확인, 프런트 연결(PR #714), 배포 재측정 뒤 채택 여부 결정.
