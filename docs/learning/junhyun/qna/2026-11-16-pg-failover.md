# 결제 PG 폴백(이중화)은 언제 하고 언제 하면 안 되나

## 질문
"토스나 우리가 단 Mock 둘 중 하나가 오류 나면 다른 쪽으로 폴백해야 한다는데 되어 있나?" 문서에 적힌 요구가 아니라 "결제를 구현할 때 그렇게 해야 한다"는 일반론으로 들은 것이다.

## 짧은 답
- 일반론은 맞다. 결제사(PG)가 하나뿐이면 그 PG 장애가 곧 우리 매출 중단이라, 규모가 있는 서비스는 PG를 둘 이상 붙이고 장애 때 다른 PG로 보낸다(PG 이중화, 멀티 PG 라우팅).
- 다만 폴백은 **새 결제를 어느 PG로 시작할지 고르는 순간**에만 한다. 이미 한 PG에 승인 요청을 보낸 결제를 다른 PG로 다시 승인하면 같은 주문이 두 번 결제될 수 있다.
- 이 프로젝트는 결제마다 PG를 하나로 고정하고(ADR 0023 11/10 개정) 자동 폴백은 없다. 토스 장애 때는 503 `PG_UNAVAILABLE`과 [다시 결제하기], 서버 설정이 켜져 있으면 사람이 누르는 [토스연동 건너뛰고 결제하기]만 있다.

## 자세히

### 왜 "시작 전"에만 바꾸나
결제는 "요청을 보냈는데 답을 못 받은" 상태가 있다(타임아웃, 504). 이때 PG에서는 승인이 됐을 수도, 안 됐을 수도 있다. 이 상태에서 다른 PG로 다시 승인하면:
- 첫 PG에서 실제로 승인됐다면 고객 돈이 두 번 나간다.
- 우리 DB에는 결제 한 건만 남아 대사(reconciliation)에서야 발견된다.

그래서 업계에서도 결과를 모르는 결제는 **같은 PG에 같은 멱등키로 다시 묻는다**(이 프로젝트의 재확인·늦은 승인 방지가 이것이다). 다른 PG로 넘기는 것은 "돈이 움직이지 않았다고 확실한" 경우뿐이다.

| 실패 시점 | 돈이 움직였나 | 다른 PG로 넘겨도 되나 |
|---|---|---|
| PG 결제창이 안 뜸, 결제 준비 API 장애 | 아니다 | 된다 |
| 서킷 브레이커가 열려 요청 자체를 보내지 않음 | 아니다 | 된다 |
| PG가 명확히 거절(한도 초과, 카드 오류) | 아니다 | 기술적으로는 되지만 보통 사용자에게 다른 수단을 고르게 한다 |
| 승인 요청 뒤 타임아웃·응답 없음 | 모른다 | 안 된다. 같은 PG에 다시 묻는다 |
| 승인 성공 | 그렇다 | 안 된다 |

### 이 프로젝트에서의 제약
- Mock → 토스 자동 전환은 불가능하다. 토스는 사용자가 결제창에서 카드 인증을 해야 한다.
- 토스 → Mock 전환은 시연용이다. Mock은 실제 결제가 아니므로 운영 서비스라면 "다른 실제 PG"가 그 자리에 들어간다. 발표에서는 "PG 포트(`PgClient`) 뒤에 PG를 결제마다 고르는 구조라 실제 두 번째 PG를 붙이면 같은 자리에서 장애 전환이 된다"로 설명할 수 있다.
- PG 하나 장애가 다른 PG까지 막지 않으려면 서킷 브레이커·벌크헤드를 PG별로 나눠야 한다. 지금은 두 PG가 같이 쓴다(ADR 0023 결과의 감수 항목).
