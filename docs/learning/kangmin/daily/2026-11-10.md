## 배운 것

### 측정 결과에서
- **병목은 단계마다 옮겨 간다**: 운영 설정에서는 Gateway `auth-redis` 차단기가 약 800~1,000/s에서 먼저 막았다. 차단기를 풀면 벌크헤드 25·DB 풀 5가, 그것도 풀면 서버 CPU(4 vCPU를 컨테이너 21개가 나눠 씀)가 약 1,600/s에서 막았다 — `docs/design/lottery/numbers-and-measurement.md` 3-4절
- **자동결제 한도는 CPU가 아니라 소비자 수다**: 처리 속도가 1 ÷ (PG 지연 + 약 10~16ms)로 PG 지연에 반비례했다. `payment.command` 소비자 1개가 직렬로 기다린다 — 같은 문서 3-4 A
- **일반 결제 한도는 PG 허가 수다**: 허가 10개 ÷ 약 0.31초 ≈ 초당 32건(계산값). CPU는 4%였다 — 같은 문서 3-4 B
- **측정 조건이 결과를 바꾼다**: 콜드 시작 800/s는 거절 55%, 웜업 뒤 800/s는 거절 0건이었다. 앞 추첨의 DB 처리와 겹친 단계는 p95가 올랐다 — `qna/2026-11-10-circuit-breaker-warmup-and-relaxing.md`, 3-4절 D·E

### Gateway와 차단기에서
- **설정값의 근거를 가려 본다**: 메모리는 서비스별로 계산했지만 CPU·스레드·연결 수는 기본값이거나 측정에서 막힌 곳을 올린 값이었다. reservation·user Hikari 5는 근거 기록이 없었다 — `qna/2026-11-10-gateway-threads-bulkhead-vs-server-spec.md` 1~5절
- **벌크헤드는 스레드가 아니라 세마포어다**: 숫자를 키워도 스레드는 늘지 않는다. 받아들이는 일이 늘어 같은 장비의 CPU를 더 쓴다. 벌크헤드가 차는 것은 CPU 포화의 증상이다(리틀의 법칙) — 같은 노트 3·6절
- **요청당 스레드 모델과 이벤트 루프 모델**: Tomcat은 요청마다 스레드 1개를 쥐고 Redis를 기다린다. Netty는 스레드 4개로 돌고 기다리지 않는다. 대기열 진입은 Redis만 쓰므로 Tomcat 200개는 여유가 크다 — 같은 노트 7절
- **처리량과 동시 요청 수를 나눈다**: 동시 수 = 처리량 × 한 건 시간. 800/s에서 처리 중인 요청은 평균 약 3건이라, 한도를 정하는 것은 요청당 CPU 시간이다 — 같은 노트 8절
- **무너지는 원인은 되먹임이다**: 도착 속도는 그대로인데 처리가 느려지면 처리 중인 요청이 불어나 메모리·GC가 CPU를 더 쓴다. 503마다 화면이 1초 뒤 다시 보내 재시도 폭풍이 된다. 줄 서서 기다리는 사용자는 자원을 붙잡지 않는다 — 같은 노트 9절, `qna/2026-11-10-queue-join-503-auto-retry.md`
- **클라이언트 시한은 클라이언트 자신의 혼잡을 함께 잰다**: 차단기의 시한·느린 호출은 Gateway 타이머가 재고, 그 안에 이벤트 루프 작업 큐 대기, Lettuce 응답 처리 대기(연결 1개 공유 → 머리 막힘), GC 멈춤, CPU 대기가 들어간다. Redis가 잰 시간(SLOWLOG)은 응답에 실려 오지 않는다 — 같은 노트 10·13절
  - 차단기가 시간을 늘려 보는 상황 표(가능한 상황 · 구간 · 차단기가 보는 것 · 가능성 · 확인 방법)는 같은 노트 10절 "시간이 늘어날 수 있는 상황"에 있다
- **시한을 낮추면 Redis가 아니라 Gateway 혼잡에 예민해진다**: 시한 초과는 실패로 세어지고, 시한이 느린 호출 기준보다 작으면 느린 호출 규칙이 죽는다 — 같은 노트 12절
- **auth-redis 요청 경로에는 재시도가 없다**: 실패하면 바로 503. 재시도는 클라이언트 화면이 한다 — 같은 노트 11절
- **벌크헤드 거절과 차단기 집계를 떼어 낸다**: 지금은 벌크헤드가 차단기 안쪽이라 거절이 실패로 세어진다. 그래서 25로 낮추면 실패율이 오른다. `ignoreExceptions`로 거절을 무시하면 성공도 실패도 아니게 되어 차단기는 Redis 장애만 본다 — 같은 노트 14~16절

### 배포·git에서
- **배포는 main 머지로만 일어난다**: dev 머지나 발생기 `git pull`로는 서버의 Gateway 이미지와 측정 덮어쓰기 파일이 바뀌지 않는다. PR을 여는 것도 배포하지 않는다 — `qna/2026-11-10-squash-merge-dev-main-conflict.md`, `qna/2026-11-10-deploy-method-ec2-compose-vs-k8s.md`, `qna/2026-11-10-when-jenkins-stops.md`
- **squash 머지는 오래 사는 브랜치의 공통 조상을 갱신하지 않는다**: dev→main을 squash로 넣으면 다음 반영 때 같은 파일에서 충돌이 날 수 있다. 내용이 아니라 이력 문제라 merge commit 동기화로 풀었다 — `qna/2026-11-10-squash-merge-dev-main-conflict.md`
- **발생기용 측정 도구는 측정 전에 커밋·푸시만 하면 된다**: 발생기는 아무 브랜치나 받을 수 있어 main에 넘길 필요가 없고, 측정 중 main 머지는 오히려 금지다 — `qna/2026-11-10-measurement-tool-branch-vs-main.md`
