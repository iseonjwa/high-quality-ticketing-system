# 좌석 선점 API의 v1·v2는 무엇이고, 응답을 가공 없이 바로 쓰게 하려면 어떻게 하나

## 질문
SA v2 API 목록의 `POST /api/v1/reservations` 설명에 "일괄 선점 (v1 201 / v2 202)"이라고 되어 있다. v1·v2가 무엇을 뜻하나. 공통 경로 `/api/v1`과 헷갈리는 표현이 아닌가. 또 응답 결과를 2차 가공하지 않고 바로 쓸 수 있는 응답으로 바꾸는 게 좋지 않나.

## 짧은 답
- 여기서 v1·v2는 API 버전이 아니라 좌석 선점 구현의 개선 단계다. v1은 DB 조건부 UPDATE로 바로 처리하는 동기 기준선(201), v2는 Kafka에 접수하고 202를 돌려주는 개선안이다. 경로는 둘 다 `/api/v1/reservations`로 같다.
- `/api/v1`과 혼동되므로 "기준선(동기) / 개선(접수형)"처럼 버전 숫자가 아닌 이름으로 바꾸는 편이 낫다.
- 바로 쓸 수 있게 하려면 두 가지를 나눠 본다. 선점 성공 응답에 결제에 필요한 값(결제 토큰 등)을 넣는 것은 비용이 작아 바로 할 만하다. 접수형(v2)에서 결과를 바로 주는 것은 발제 요구(접수 후 바로 응답)와 기준 저장소 결정에 걸려 있어 측정 후 팀이 정한다.

## 자세히

### v1·v2의 뜻
| 단계 | 처리 방식 | 응답 | 클라이언트가 할 일 |
|---|---|---|---|
| v1 (기준선) | 한 트랜잭션에서 매수 한도 → 좌석 조건부 UPDATE → 예매 저장 | 201 + `status: HELD` | 결과를 바로 사용 |
| v2 (개선) | API는 Kafka에 요청을 적재하고 바로 응답, 소비자가 DB에 반영 | 202 + `status: REQUESTED` + `Location` | `Location`을 다시 조회해 HELD·REJECTED를 확인 |

발제는 v2 방식(Kafka에 적재하고 바로 응답, 소비자가 처리)을 요구한다. 팀은 v1을 먼저 만들어 기준선을 재고, v2로 바꾼 뒤 개선 전·후를 비교하기로 했다. 그래서 같은 API에 두 단계가 적혀 있다.

### 헷갈리는 이유와 대안
API 경로의 `v1`은 외부 계약의 버전이다. 계약이 깨지는 변경이 있을 때 `v2` 경로를 새로 연다. 반면 선점의 v1·v2는 같은 계약 안에서 내부 구현을 바꾸는 것이다. 같은 기호를 다른 뜻으로 쓰면 "v2 API를 따로 만든다"로 읽힌다. API 목록의 단계 열에도 `v2`가 있어서 더 헷갈린다.

| 표기 후보 | 장점 | 단점 |
|---|---|---|
| 기준선 / 개선 | 발표 스토리(개선 전·후)와 바로 이어진다 | 처리 방식이 이름에 드러나지 않는다 |
| 동기 / 접수형 | 처리 방식이 드러난다 | 개선 순서가 드러나지 않는다 |
| 1단계 / 2단계 | 짧다 | 무엇이 다른지 알 수 없다 |

"기준선(동기) / 개선(접수형)"처럼 둘을 함께 쓰면 두 정보가 다 남는다.

### 응답을 바로 쓰게 하는 방법 1: 선점 응답에 다음 단계 값 넣기
지금 흐름은 선점 성공(201) 뒤에 `GET /reservations/{id}`를 한 번 더 불러 결제 토큰을 받는다. 결제 토큰은 선점 시점에 이미 정해지는 값(`reservationId`, `userId`, `totalAmount`, 만료 = 선점 만료)으로 만들기 때문에 선점 응답에 바로 넣을 수 있다.

- 얻는 것: 클라이언트 호출이 한 번 줄고, 선점 → 결제가 응답 하나로 이어진다.
- 대가: 선점 트랜잭션에서 HMAC 서명을 하나 더 만든다(가벼운 연산). 선점 담당과 결제 토큰 발급 담당이 다르면 응답 계약을 함께 정해야 한다.
- `GET /reservations/{id}`는 새로고침·재진입용으로 그대로 둔다.

### 응답을 바로 쓰게 하는 방법 2: 접수형에서 결과를 바로 주기
| 방식 | 동작 | 장점 | 대가 |
|---|---|---|---|
| A. 202 + 결과 조회 (현재 v2) | 접수만 답하고 클라이언트가 `Location`을 조회 | 서버 자원을 적게 쓰고 폭주를 흡수한다. 발제 요구에 그대로 맞는다 | 클라이언트가 두 단계로 처리해야 한다 |
| B. 결과를 기다렸다 응답 | Kafka에 적재한 뒤 소비자 결과를 최대 N초 기다렸다 응답하고, 넘으면 202 | 대부분 결과를 바로 받는다 | 기다리는 동안 스레드·커넥션을 잡아 폭주 때 v2의 목적과 부딪힌다. 인스턴스가 여럿이면 결과를 받을 경로가 필요하다. "적재하고 바로 응답"이라는 발제 요구와도 어긋난다 |
| C. 혼합형 | Redis에서 원자적으로 즉시 판정해 결과를 바로 주고, DB 기록만 Kafka로 넘긴다 | 결과를 바로 쓴다. 판정이 빠르다 | 판정 기준이 Redis가 되어 "판매 기준은 DB"라는 결정(기준 저장소)과 부딪힌다. Redis와 DB가 어긋날 때 맞추는 작업이 필요하다 |

어느 방식이든 v1과 v2의 응답 본문 모양을 같게 두면 클라이언트 코드는 `status`만 보고 분기하면 된다. 현재 SA v2도 "응답 형식은 v1·v2가 같다"로 정해 두었다.

## 이후 결정 (2026-10-26)
- 명칭: v1·v2 대신 동기형(sync)·접수형(async)으로 부르고, 경로의 `/api/v1`만 버전 표기로 남긴다. 설정 키는 `seat-hold.mode` (결정 기록 #19).
- 방법 1 채택: 선점 성공(HELD) 응답과 접수 결과 조회의 HELD 응답에 결제 토큰을 넣는다 (#33).
- 접수형은 API가 접수 요청 행(REQUESTED)과 outbox를 한 트랜잭션으로 저장하고, 결과 조회는 그 행을 읽는다. 동기형도 같은 행을 남긴다 (#33·#46). 방법 2의 B·C는 채택하지 않았고, 혼합형은 v3 후보로 남았다.

## 면접 포인트
- "API 버전과 구현 버전을 왜 구분했나": 경로의 버전은 외부 계약이 깨질 때만 올린다. 내부 처리 방식을 바꾼 것은 같은 계약 안의 개선이라 같은 경로를 유지했다.
- "비동기 접수 API에서 사용자는 결과를 어떻게 아나": 202와 결과 조회 위치를 주고 폴링하게 했다. 결과를 바로 줘야 하면 즉시 판정은 Redis가, 영속은 Kafka 소비자가 맡는 혼합형을 쓸 수 있지만, 기준 저장소가 둘이 되는 대가가 있다.
