# 회차당 매수를 4매에서 1인 1매로 바꾸면 무엇을 얻고 무엇을 치르나

## 질문
1인 1매로 바꾸게 되면 발생할 비용

## 짧은 답
- **코드 비용은 거의 없다.** 예매·선점 코드가 아직 없다(10/28 dev 기준). 결제는 예매 단위라 영향이 없다.
- **큰 비용은 세 가지다.** ① 팀 결정(10/23 "최대 인원수를 정해 놓고 좌석을 고른다", #35 회차당 4매)을 뒤집는 합의 비용 ② SA 여러 장의 수정 ③ 동시성 학습·발표 소재 일부가 사라지는 것(여러 좌석 전부 아니면 전부, 좌석 잠금 순서, D1의 형태).
- **매수 제한 자체는 사라지지 않는다.** 1매여도 같은 사용자가 동시에 두 번 요청하면 2매가 될 수 있어 D1 같은 방어는 여전히 필요하다. 구현만 단순해진다.
- 얻는 것: 선점 쿼리와 테이블이 단순해지고, 교착 위험이 없어진다.

## 자세히

### 1. 단순해지는 것 (얻는 것)

| 지금 (최대 4매) | 1인 1매 |
|---|---|
| 좌석 여러 개를 ID 오름차순으로 잠가 교착 방지 (8-4, 12-7) | 좌석 1개라 잠금 순서·교착 문제가 없음 |
| 바뀐 행 수 ≠ n이면 롤백 (전부 아니면 전부) | 0행 또는 1행 |
| `user_schedule_quotas` 행 보장 + `held_count + n <= max` 조건부 UPDATE (D1) | `reservations`에 `UNIQUE(user_id, schedule_id) WHERE status IN ('HELD','CONFIRMED')` 부분 유니크 하나로 대체 가능 |
| `reservations` 1 : N `reservation_seats` | 1 : 1이라 합칠 수 있음(합치지 않아도 됨) |
| `seatIds` 1~4개 검증, `SEAT_COUNT_MISMATCH` | `seatId` 하나 |

### 2. 치르는 비용

**① 합의 비용 (가장 큼)**
- 10/23 기능 흐름 팀 결정 "최대 인원수를 정해 놓고 좌석을 자유롭게 클릭해서 고름"(SA 4-4)과 결정 기록 #35(회차당 4매, 잠정)를 바꾼다. 개인 판단으로 바꿀 수 없고 회의·결정 기록 수정이 필요하다.
- 좌석 선점(최권우)·예매 흐름(반효승)·추첨(이강민) 담당의 설계가 모두 영향을 받는다.

**② 문서 수정 범위 (SA v3.3 기준)**

| 위치 | 바뀌는 것 |
|---|---|
| 2장 | P1 페르소나("친구와 2매")·시연 시나리오(매수 선택)·E3·E16 |
| 3장, 16장 #7 | 오류 정의의 "매수 초과", 설명 점검 "매수 제한" |
| 4장 | F4-1 "매수 선택 → 좌석 선택", 4-3 추첨 "등급별 1–2매", 4-4 팀 결정 표 |
| 6-4 | 좌석 선점 MVP 기능(매수 한도 행, 좌석 ID 정렬) |
| 8-3·8-4 | 전이 표의 "매수 한도 ±n", 잠금 순서 |

**③ 학습·발표 소재 감소**
- 발제 필수 "동시성 제어"의 대표 장면은 같은 좌석 경합(E1)이라 그대로 남는다.
- 줄어드는 것: 여러 좌석을 한 번에 잡는 "전부 아니면 전부", 좌석 ID 정렬로 교착을 막는 설명, D1 "같은 사용자의 동시 요청이 매수 한도를 넘는다"의 숫자 예(4매 한도에 2+3매)가 단순해진다.
- AI 검증 #8(D1~D4 자체 검수)의 D1 기록은 이력으로 남지만 설계 근거가 약해진다.

**④ 부하 특성 변화 (측정 전, 추정)**
- 같은 좌석 수를 팔려면 예매 수가 늘어난다. 12-9는 평균 2.5매로 확정 예매를 약 12,000건으로 잡았다. 1매면 약 30,000건이다. 결제 요청, `payment.result` 이벤트, 상태 이력, Outbox 행이 같은 비율(약 2.5배)로 늘어난다.
- 입장자 한 명이 사는 좌석이 줄어 같은 좌석 수에 더 많은 입장자가 필요하다. 입장 속도 역산(3-3)의 가정이 바뀐다.
- 반대로 한 요청이 잡는 좌석이 1개라 행 잠금 시간은 짧아진다. 처리량이 좋아질지 나빠질지는 측정해야 안다.

**⑤ 서비스 현실성**
- 실제 콘서트 예매는 보통 1인 여러 매(동행)를 허용한다. 1인 1매는 매크로·암표 대책으로 쓰이기도 하지만, 동행 예매가 필요한 사용자(P1)의 시나리오가 깨진다.

### 3. 1매로 바꿔도 남는 것
- 매수 제한(D1류 방어): 동시 요청 두 건이 각각 1매씩 잡으면 2매가 된다. 부분 유니크나 quota 행 둘 중 하나는 필요하다.
- 같은 좌석 경합(E1), 판매 여부 기준(D2), 결제·SAGA·만료 전부.

### 4. 판단 기준
- 바꿀 이유가 "구현을 줄이려고"라면 얻는 것은 선점 쿼리 일부뿐이고, 합의·문서 비용이 더 크다.
- 바꿀 이유가 "매크로·암표 대응"이나 "추첨과 규칙을 맞추려고"라면 기획 변경이므로 회의 안건으로 올린다.
- 중간안: `schedules.max_per_user`가 이미 회차별 설정값이다. 설계는 4매 그대로 두고 시연·측정에서만 1로 설정할 수 있다.
