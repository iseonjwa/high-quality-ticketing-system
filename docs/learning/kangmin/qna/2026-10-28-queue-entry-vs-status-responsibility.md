# 이미 입장 토큰을 받은 사용자가 대기열 진입(POST)을 다시 부르면 토큰을 누가 돌려줘야 하나

## 질문
대기열 담당과 대화 중. POST `/queue`로 진입하고 GET `/queue/me`로 순번을 조회하다가 차례가 되면 입장 토큰을 받는다. 토큰이 만료되지 않았으면 새로고침해도 빠르게 다시 입장할 수 있다. 그런데 POST 요청 때 이미 토큰이 있으면 POST에서 처리하게 되는데, 이걸 GET이 판단하고 처리하게 하는 것이 서로 기능 역할을 침범하지 않는 것 아닌가?

## 짧은 답
- 맞는 고민이다. ADR 0015(제안)는 **POST도 `issued`를 확인하고, 기록이 있으면 같은 발급 시각으로 토큰을 다시 응답**하게 했다. 그러면 토큰을 내주는 곳이 POST와 GET 두 곳이 된다.
- 나눠 볼 것은 두 가지다. ① **POST가 `issued`를 확인하는 것**은 꼭 필요하다(없으면 입장 상태인 사람이 새 순번을 또 받는다). ② **POST가 토큰까지 응답하는 것**은 선택이다.
- 추천: POST는 "새 순번을 만들지 않고 `ADMITTED` 상태만 알린다", 토큰은 GET `/queue/me`만 내준다. 진입 = 줄 서기, 조회 = 상태 확인·토큰 응답으로 역할이 하나씩 남고, SA 11-5의 POST 응답 형식(`WAITING`만)과도 맞는다. 대가는 새로고침 때 요청 1번이 더 드는 것이다.

## 자세히

### 1. 지금 흐름 (SA 12-8, ADR 0015)

| 요청 | Redis에서 하는 일 | 응답 |
|---|---|---|
| POST `/queue` | `issued` 확인 → 기록이 있고 T 안이면 **토큰 재응답**. 없으면 `waiting` 확인 → 없으면 seq INCR → ZADD | 처음: `WAITING` + 순번 / 이미 줄: 같은 순번 / 이미 입장: 토큰(ADR 0015) |
| GET `/queue/me` | `issued` 확인 → 있으면 같은 발급 시각으로 토큰 재응답. 없으면 `waiting`의 seq와 `admitted` 비교 → `seq <= admitted`면 `waiting`에서 빼고 `issued`에 기록 후 토큰 | `WAITING` + 순번 / `ADMITTED` + 토큰 |

POST가 `issued`를 보는 이유(ADR 0015 4번): 토큰을 받으면 `waiting`에서 빠진다. 확인이 없으면 토큰이 유효한 동안 POST를 다시 불렀을 때 새 seq가 생겨, 한 사람이 **입장 상태와 대기 자리를 동시에** 갖는다.

### 2. "확인"과 "토큰 응답"은 다른 문제다

| | 하는 일 | 빠지면 |
|---|---|---|
| POST의 `issued` 확인 | 입장한 사람에게 새 seq를 주지 않음 | 한 사람이 자리 2개 → 대기열 공정성이 깨짐. **반드시 필요** |
| POST의 토큰 응답 | 새로고침한 사람이 요청 한 번으로 토큰을 받음 | GET을 한 번 더 부르면 됨. **편의 기능** |

그래서 "POST가 판단하지 말고 GET이 해야 한다"는 절반만 맞다. 판단(새 seq 금지)은 POST에 남아야 하고, 옮길 수 있는 것은 토큰 응답이다.

### 3. 선택지

| 선택지 | POST가 이미 입장한 사람에게 | 장점 | 대가 |
|---|---|---|---|
| A. 지금 제안 (ADR 0015) | 토큰을 다시 응답 | 새로고침 후 요청 1번으로 입장 | 토큰을 내주는 경로가 2개(서명·만료 계산·응답 형식이 두 곳). POST 응답이 `WAITING`/`ADMITTED`+토큰 두 형태가 되어 SA 11-5와 어긋남 |
| **B. 상태만 알림 (추천)** | 새 seq 없이 `status: ADMITTED`, `nextPollAfterSeconds: 0` | 토큰 응답은 GET 하나. POST는 "줄 서기"만. 응답 형식이 단순 | 새로고침 시 POST → GET 두 번 |
| C. 409로 거절 | `ALREADY_ADMITTED` 같은 에러 | 역할이 가장 분명 | 정상 상황(새로고침)을 에러로 다룸. 409 집계가 늘어 측정 해석이 흐려짐 |

B를 추천하는 이유:
- 입장 토큰 발급은 서명 키(`ENTRY_TOKEN_SECRET`), 만료 = 발급 시각 + T 계산, claim 구성이 얽힌 민감한 코드다. 한 경로에만 있으면 실수할 곳이 줄고 테스트도 한 곳에서 끝난다.
- 클라이언트는 이미 GET을 반복 호출하는 흐름이라 "POST 다음에 GET" 한 번이 자연스럽다.
- 참고: B에서도 코드 수준에서는 같은 "토큰 응답" 메서드를 공유할 수 있다. "역할 침범"은 **API 계약** 문제이고, 내부 구현은 한 곳으로 모으면 된다.

### 4. 더 단순하게: 새로고침한 클라이언트는 GET부터
클라이언트가 새로고침 뒤 **GET `/queue/me`를 먼저** 부르면 된다.
- `issued`가 있으면 → 토큰 (입장 상태 복구)
- `waiting`에 있으면 → 순번
- 둘 다 없으면 → 404 `QUEUE_NOT_JOINED` → 그때 POST로 진입

이러면 POST는 "아직 줄에 없는 사람"만 부르게 되고, POST의 `issued` 확인은 클라이언트가 실수로 POST를 부른 경우를 막는 방어선이 된다.

### 5. 한 가지 더 볼 점: GET이 상태를 바꾼다
GET `/queue/me`는 `seq <= admitted`가 되는 순간 `waiting`에서 빼고 `issued`에 기록한다. HTTP에서 GET은 "안전한(상태를 바꾸지 않는)" 메서드로 보는 게 원칙이라, 엄밀히는 어긋난다.
- 지금 설계가 받아들일 만한 이유: 같은 GET을 몇 번 불러도 결과가 같다(멱등). 처음 한 번만 `waiting → issued`로 옮기고, 이후에는 같은 발급 시각으로 같은 만료의 토큰을 돌려준다.
- 대안: 입장 전환을 GET에서 하지 않고 스케줄러가 `admitted`를 올릴 때 함께 옮기는 방식. 하지만 스케줄러가 입장자 전원의 토큰 발급 시각을 기록해야 해서 일이 커지고, 1초마다 N명씩 ZSET을 옮겨야 한다.
- 결론: GET이 상태를 바꾸는 점은 "멱등이라 감수"로 문서에 적어 두면 리뷰나 발표에서 설명할 수 있다.

### 6. 추가 질문: 다른 방안은 없나, 지금 방안(A)이 좋은 방향인가

판단 기준을 먼저 둔다. 1·2는 반드시 지켜야 하고, 3~6은 비교 항목이다.

| # | 기준 | 뜻 |
|---|---|---|
| 1 | 공정성 | 입장한 사람이 새 순번을 또 받지 않는다 |
| 2 | 응답 유실 복구 | 토큰 응답을 못 받아도 차례를 잃지 않는다 |
| 3 | 토큰 발급 경로 수 | 서명·만료 계산이 몇 곳에 있나 |
| 4 | HTTP 의미 | POST는 만들기, GET은 상태를 바꾸지 않는 조회 |
| 5 | 오픈 순간 요청 수 | 새로고침 폭주 때 요청이 늘어나나 |
| 6 | 클라이언트 단순함 | 화면이 분기할 경우의 수 |

| 안 | 이미 입장한 사람이 POST를 부르면 | 1 | 2 | 3 | 4 | 5 | 6 |
|---|---|---|---|---|---|---|---|
| A. 토큰 재응답 (지금, ADR 0015) | 200 ADMITTED + 같은 만료의 토큰 | ○ | ○ | 2곳 | POST가 조회 역할도 함 | 1번 | POST 응답이 두 형태 |
| B. 상태만 알림 | 200 ADMITTED, `nextPollAfterSeconds: 0` | ○ | ○ | 1곳 | 나음 | 2번(GET 먼저면 1번) | 단순 |
| C. 409 거절 | 409 `ALREADY_ADMITTED` | ○ | ○ | 1곳 | 나음 | 2번 | 에러 처리 분기 + 측정에서 409 집계 증가 |
| D. 조회 위치 안내 | 200 ADMITTED + `Location: /queue/me` (SA 11-2의 202 `Location` 규칙과 같은 모양) | ○ | ○ | 1곳 | 나음 | 2번 | B와 같음. 다음 요청 주소를 서버가 알려 줌 |
| E. 토큰 발급 전용 API | GET `/queue/me`는 상태만(`WAITING`·`READY`), POST `/queue/me/entry-token`이 `waiting → issued` 전환과 토큰 발급 | ○ | ○ | 1곳 | 가장 맞음 (GET이 상태를 바꾸지 않음) | 차례가 될 때 1번 더 | API 1개 추가, Gateway 경로 1개 추가 |
| F. 한 번만 발급, 프론트 저장 | 재발급 없음 | ○ | **×** | 1곳 | 맞음 | 1번 | 오픈 순간 응답 유실 때 맨 뒤로 밀림 (ADR 0015가 기각한 안) |
| G. httpOnly 쿠키로 전달 | 쿠키가 이미 있으면 진입이 필요 없음 | ○ | **×** (Set-Cookie가 담긴 응답이 유실되면 같음) | 1곳 | — | 1번 | 쿠키 도메인·SameSite·부하 도구 설정 부담, MVP는 화면 없이 API로 시연 |

**지금 방안(A)이 틀렸나**: 아니다. 반드시 지킬 1·2를 모두 지키고, 같은 서비스 안이라 서명 키 경계 문제도 없다. 내부에서 토큰 발급 메서드 하나를 POST·GET이 함께 부르면 "2곳"의 실제 위험도 작다. 차이는 **API 계약을 얼마나 단순하게 두느냐**다.

**고르는 기준**
- 요청 수와 화면 흐름을 가장 줄이고 싶다 → A 유지. 대신 POST 응답 예시(SA 11-5)에 `ADMITTED` 형태를 추가하고, "POST도 토큰을 다시 줄 수 있다"를 계약에 적는다.
- 계약을 단순하게, 바꿀 곳은 최소로 → **B (추천)**. ADR 0015 4번의 "토큰을 다시 응답" 한 구절과 SA 12-8 한 줄만 바뀐다. 클라이언트가 새로고침 후 GET부터 부르면 요청 수도 A와 같다.
- HTTP 의미까지 깔끔하게(발표·면접 소재) → E. 5절의 "GET이 상태를 바꾼다"까지 함께 풀리지만 API가 하나 늘고 Gateway 경로 규칙, 테스트가 늘어 M1~M2 일정에는 부담이다.
- F·G는 2번(응답 유실 복구)을 못 지켜 제외한다. C는 정상 상황을 에러로 다뤄 측정 해석을 흐린다.

### 7. E 방식에서 세 API가 각각 하는 일

E에서 POST `/queue`는 **B와 똑같다**. 바뀌는 것은 GET이 상태를 바꾸지 않게 되고, 그 일을 새 API가 가져가는 것이다.

| API | 역할 | Redis | 상태를 바꾸나 |
|---|---|---|---|
| POST `/schedules/{id}/queue` | 줄 서기 | `issued`에 있으면 ADMITTED(새 seq 없음) / `waiting`에 있으면 같은 seq / 없으면 INCR seq + ZADD waiting | 처음 진입할 때만 |
| GET `/schedules/{id}/queue/me` | 내 상태 보기 | 읽기만. `issued` 있음 → ADMITTED / `seq <= admitted` → **READY** / 아니면 WAITING / 없음 → 404 | 안 바꿈 |
| 🆕 POST `/schedules/{id}/queue/me/entry-token` | 입장 토큰 받기 | `issued` 있음 → 같은 발급 시각 / READY → ZREM waiting, ZADD issued(지금) / WAITING → 409 / 없음 → 404 | 처음 받을 때만 |

- 새 상태 **READY**: "차례는 왔지만 토큰을 아직 안 받음". Redis에 따로 저장하지 않고 `seq <= admitted`로 계산한다.
- 클라이언트 흐름: POST 진입 → GET 반복 → READY → POST entry-token → 토큰. 새로고침하면 POST entry-token 한 번(이미 입장이면 같은 만료의 토큰, 아니면 409·404로 다음 할 일을 안다).
- entry-token은 같은 요청을 다시 보내도 결과가 같다(멱등). 응답이 유실되면 그대로 다시 부르면 된다.
- READY인데 토큰을 받지 않고 떠난 사람은 지금 설계의 이탈자와 같다. 그 번호만큼 실제 입장 속도가 N보다 낮아진다. READY에 받기 기한을 두려면 READY가 된 시각을 따로 기록해야 해서 키가 늘어난다(지금 설계에도 없는 기한이라 같은 수준의 한계).
- 추가로 필요한 것: 에러 코드 1개(예: `QUEUE_NOT_ADMITTED` 409, 차례 전 요청), Gateway 경로 규칙(인증 필요), API 명세·테스트.

## 이 프로젝트에서는
- 근거: ADR 0015 4번(제안), SA 12-8 🆕 "대기열 진입 시 입장 기록 확인", SA 11-5 대기열 응답 예시(POST는 `WAITING`만)
- 결정권: 대기열 담당. ADR 0015가 제안 상태라 B로 바꾸면 ADR 0015 4번과 SA 12-8 문장을 함께 고친다.

## 면접 포인트
- "같은 기능을 두 API가 하면 왜 문제인가": 민감한 로직(토큰 서명)이 두 경로에 있으면 한쪽만 고치는 실수가 생긴다. API 역할은 하나로, 내부 구현은 공유로.
- "GET이 상태를 바꿔도 되나": 원칙은 안전한 메서드. 멱등이면 실무에서 감수하기도 하고, 그 근거를 문서로 남긴다.

- 프론트(MVP 이후)의 새로고침 흐름을 GET 먼저로 둘 수 있는지
