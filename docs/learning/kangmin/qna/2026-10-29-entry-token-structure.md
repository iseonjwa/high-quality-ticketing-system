# 우리 입장 토큰은 어떻게 구성되어 있나

## 질문
우리 입장 토큰이 어떤식으로 구성되어 있는가

## 짧은 답
- 입장 토큰은 **HMAC-SHA256으로 서명한 JWT**다. Reservation(대기열 모듈)이 발급하고 Gateway가 검증한다(SA 7-3).
- claim은 `typ=entry`, `aud=gateway`, `sub`(사용자 ID), 회차 ID, `exp`(발급 후 10분), `jti`다. 회차 ID의 claim 이름(이전 안 `sid`)은 아직 정하지 않았다(ISE-20).
- 핵심은 "이 사용자가 이 회차에 지금부터 10분간 좌석 조회·선점을 해도 된다"를 **서비스 호출 없이 서명만으로** 증명하는 것이다.
- 10/29 기준 코드는 없다. 설계(SA 7-3, ADR 0015)만 있다.

## 자세히

### 1. 모양
JWT는 `헤더.본문.서명` 세 부분을 Base64URL로 붙인 문자열이다.

```
eyJhbGciOiJIUzI1NiJ9 . eyJ0eXAiOiJlbnRyeSIs... . 3q2+7w...
      헤더                     본문(claim)            서명
```

- 헤더: `{"alg":"HS256"}`. 서명 알고리즘
- 본문: 아래 claim. 암호화가 아니라 인코딩이라 누구나 읽을 수 있다. 비밀 정보를 넣지 않는다
- 서명: `HMAC-SHA256(헤더.본문, ENTRY_TOKEN_SECRET)`. 본문을 한 글자라도 바꾸면 서명이 맞지 않는다

### 2. claim과 각각의 이유 (SA 7-3)
| claim | 값 | 왜 있나 |
|---|---|---|
| `typ` | `entry` | 토큰 종류. 결제 토큰(`payment`)이나 액세스 토큰을 입장 토큰 자리에 넣는 것을 막는다 |
| `aud` | `gateway` | 이 토큰을 받을 쪽. `typ`와 함께, 키가 실수로 같아져도 다른 토큰과 섞이지 않게 하는 이중 방어 |
| `sub` | 사용자 ID | 누구의 입장권인지. Gateway가 JWT 사용자 ID(`X-User-Id`)와 같은지 확인해 **토큰 넘겨주기를 막는다**(ADR 0015, 제안) |
| 회차 ID | 예: `31` | 어느 회차의 입장권인지. 요청한 회차와 다르면 거절한다. A 회차 대기열을 통과한 토큰으로 B 회차 좌석을 잡는 것을 막는다 |
| `exp` | 발급 시각 + 10분 `[가정]` | 입장 유효 시간. 이 시간 안에 좌석을 선택해야 한다 |
| `jti` | UUID | 추적·로그용. 폐기 목록은 만들지 않는다(여러 번 쓰는 토큰이고 유효 시간이 짧아서) |

예시 본문(이름 확정 전, 회차 ID를 `sid`로 가정):

```json
{ "typ": "entry", "aud": "gateway", "sub": "42", "sid": 31,
  "exp": 1793176800, "jti": "7c1e..." }
```

### 3. 발급, 전달, 검증
| 단계 | 누가 | 무엇을 |
|---|---|---|
| 발급 | Reservation `queue` 모듈 | 순번 조회에서 `seq <= admitted`면 서명. 발급 시각을 Redis `queue:{scheduleId}:issued`에 기록하고, 다시 조회해도 **같은 발급 시각으로 다시 서명**해 만료가 늘지 않게 한다(ADR 0015) |
| 전달 | 클라이언트 | 좌석 조회(GET)·선점(POST) 요청에 `X-Entry-Token` 헤더로 보낸다. 대기열 API와 결제 API에는 쓰지 않는다 |
| 검증 | Gateway | 서명 → `typ` → `aud` → `exp` → 회차 ID = 요청 회차 → `sub` = `X-User-Id`. 하나라도 틀리면 403 `ENTRY_TOKEN_INVALID` |

Redis가 장애여도 입장 토큰 검증은 서명과 `exp`만으로 되므로 계속 통과한다(SA 9-5). 서명 토큰을 고른 주된 이유가 이것이다.

### 4. 다른 토큰과 비교
| | 액세스 토큰 | 입장 토큰 | 결제 토큰 |
|---|---|---|---|
| 발급 | user-service | Reservation(대기열) | Reservation(예매 흐름) |
| 검증 | Gateway | Gateway | Payment |
| 키 | JWT 키 | `ENTRY_TOKEN_SECRET` | `PAYMENT_TOKEN_SECRET` |
| 증명하는 것 | 누구인가 | 지금 좌석을 잡아도 되는가 | 이 예매를 이 금액으로 결제해도 되는가 |
| 유효 | 로그인 기간 | 10분 | 선점 만료 - 10초 |

키를 토큰마다 나눈 이유: Gateway는 결제 키를, Payment는 입장 키를 갖지 않아 서로의 토큰을 만들 수 없다.

### 5. 고른 방식과 감수한 점
| 선택지 | 장점 | 단점 |
|---|---|---|
| **서명 토큰(HMAC JWT), 채택** | Gateway가 Redis·서비스를 부르지 않고 검증. 오픈 순간 몰릴 때 검증 비용이 거의 0 | 발급 뒤에는 취소할 수 없다(폐기 목록 없음). 10분 동안은 유효 |
| Redis에 입장 명단을 두고 매 요청 조회 | 즉시 취소 가능 | 좌석 요청마다 Redis 조회가 붙고, Redis 장애가 곧 예매 장애 |
| 비대칭 서명(RSA 등) | 검증 쪽이 토큰을 만들 수 없다 | 키 관리가 늘어 MVP 이후로 미뤘다(SA 7-3) |

HMAC은 검증 키로 서명도 할 수 있다. 그래서 "Gateway도 입장 토큰을 만들 수 있다"는 한계가 있다. 이 한계는 SA에 그대로 적혀 있다.

### 6. `jti`는 실제로 어디에 쓰나 (추가 질문)
`jti`(JWT ID, RFC 7519)는 토큰 한 장마다 붙는 고유 번호다. 표준이 정한 원래 목적은 **재사용 방지와 폐기**, 즉 "이 번호의 토큰은 더 이상 받지 않는다"를 표현하는 것이다.

우리 코드에서 실제로 쓰는 곳은 액세스 토큰 하나다.
- 로그아웃하면 user-service가 `auth:blacklist:{jti}`를 Redis에 남긴다(`RedisSessionStore.logout`).
- Gateway는 요청마다 이 키가 있는지 확인해 로그아웃한 토큰을 막는다(`GatewayAuthenticationFilter`).
- 즉 액세스 토큰에서 `jti`는 **폐기 목록의 키**다.

#### 현재 설계 기준 (문서·코드로 확인한 것)
| 토큰 | 설계 문서 | 실제 코드 |
|---|---|---|
| 액세스 | SA 12-8 `auth:blacklist:{jti}` (로그아웃된 Access, TTL = 남은 시간) | 구현됨. 로그아웃 시 기록, Gateway가 매 요청 확인 |
| 입장 | SA 7-3 "추적·로그용으로만 쓰고 폐기 목록은 만들지 않는다" | 토큰 자체가 없음 |
| 결제 | SA 7-3, `contracts.md`·`api.md`·ADR 0025 "로그·추적용, 폐기 목록 없음". ADR 0016은 `jti` 폐기 목록으로 토큰을 1회용으로 만드는 안을 검토하고 **채택하지 않았다** | 필수 claim으로 검증만 함. 읽거나 로그에 남기는 코드는 찾지 못함 |

정리하면 현재 설계에서 `jti`가 실제 기능을 하는 곳은 **액세스 토큰의 로그아웃 차단** 하나다. 입장·결제 토큰의 "추적·로그용"은 용도의 방향만 적은 것이다. 어떤 로그에 어떤 이름으로 남기는지, 무엇을 집계하는지는 어느 문서에도 없다. 그래서 지금 상태로는 `jti`를 넣어도 쓰이는 곳이 없다.

#### 이후 활용 후보 (아래 표는 제안이며 설계에 없다)
입장 토큰은 폐기 목록을 만들지 않기로 했다(SA 7-3). 이유는 두 가지다.
- 좌석 조회·선점에 여러 번 쓰는 토큰이라 1회용으로 만들 수 없다.
- 10분이면 저절로 만료된다.

폐기 목록에 쓰지 않으면 `jti`에 남는 쓸모는 **"이 요청이 어느 토큰으로 들어왔나"를 식별하는 것**이다.

| 용도 | 어떻게 | 무엇을 알 수 있나 |
|---|---|---|
| 요청 묶기 | Gateway 접근 로그·Zipkin 태그에 `jti`를 남긴다 | 토큰 한 장으로 좌석 조회를 몇 번 하고 선점을 몇 번 시도했는지. 사용자 ID로는 "몇 번째 입장인지"가 구분되지 않는다 |
| 이상 사용 탐지 | 같은 `jti`가 짧은 시간에 여러 IP·기기에서 오는지 본다 | `sub` 확인은 **다른 계정**의 사용만 막는다. 같은 계정을 여러 기기·매크로가 나눠 쓰는 것은 `jti`로만 보인다 |
| 장애·민원 조사 | "입장했는데 좌석이 안 잡혔다" 문의에서 토큰을 특정한다 | 그 토큰의 검증 실패 사유(만료, 회차 불일치 등)와 시각 |
| 측정 | 발급 로그와 사용 로그를 `jti`로 이어 붙인다 | 입장자 중 실제로 선점까지 간 비율, 입장 후 첫 선점까지 걸린 시간. 입장 속도 N을 거꾸로 계산하는(SA 3-3) 근거가 된다 |
| 나중의 폐기 | 필요해지면 `jti`로 블랙리스트를 붙인다 | 지금 구조를 바꾸지 않고 확장할 수 있다 |

정해야 할 것(ISE-20에 넣을 만한 항목):
- **다시 서명할 때 `jti`를 유지할지.** ADR 0015는 재조회 때 같은 발급 시각으로 다시 서명한다. 이때 `jti`를 새로 만들면 재발급 횟수를 셀 수 있지만, 한 사람의 입장이 여러 `jti`로 쪼개진다. 같은 값(예: 회차와 사용자, 발급 시각으로 정하는 값)을 쓰면 "입장 1회 = `jti` 1개"가 되어 위 표의 집계가 쉬워진다.
- **어디에 남길지.** Gateway 로그에 남기지 않으면 위 용도는 모두 성립하지 않는다. 지금 코드에서 결제 토큰의 `jti`를 읽거나 로그에 남기는 곳은 찾지 못했다(검증 테스트에서 값을 넣기만 한다).

## 면접 포인트
- "입장 토큰을 왜 JWT로?" → 오픈 순간 모든 좌석 요청을 Gateway에서 서비스 호출 없이 검증하려고. Redis가 죽어도 검증은 계속된다
- "토큰을 남에게 넘기면?" → `sub`를 JWT 사용자 ID와 대조해 403
- "재조회로 토큰을 계속 새로 받으면?" → 발급 시각을 Redis에 기록하고 같은 시각으로 다시 서명해 만료가 늘지 않는다
