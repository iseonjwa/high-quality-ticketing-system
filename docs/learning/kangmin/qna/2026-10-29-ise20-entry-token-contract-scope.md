# ISE-20 입장 토큰 계약은 무엇을 기준으로 범위를 정했고, 누가 함께 정해야 하나

## 질문
ISE-20에서 각 이슈 담당자들이 고려해야 할 부분이 뭐가 있을까. 각 담당자가 임의로 결정하면 되는 것인지, 상호 고민해야 할 담당자가 있는 것인지. 입장 토큰 claim에서 고려해야 할 범위는 어떤 기준으로 책정된 것인지. 확인할 쪽이 왜 좌석 선점과 Gateway 두 곳인지.

## 짧은 답
- 범위의 기준은 "**만드는 쪽과 읽는 쪽이 똑같이 해석해야 하는 것**"이다. 토큰 자체(claim 이름·타입, 서명 키 해석, 만료), 검증 규칙(무엇과 무엇을 비교하나), 전달 방식(헤더 이름) 세 묶음이다. 한쪽 안에서 끝나는 것(Redis `issued`, Lua, jitter)은 뺐다.
- 대부분은 대기열 담당이 정해서 통보하면 된다(SA 6-9 "형식을 소유한 담당이 정하고 소비하는 쪽이 리뷰"). 함께 정해야 하는 것은 **"요청 회차를 어디서 읽나"** 하나가 크고, 헤더 이름·필터 순서·공통 `TokenType`이 작게 걸린다.
- 확인 대상이 Gateway와 좌석 선점인 이유는 SA 6-9가 입장 토큰 소비자를 그 둘로 적었기 때문이다. 다만 다시 보니 **좌석 조회(`GET /schedules/{id}/seats`, 공연·좌석 조회 담당)도 입장 토큰을 요구하는 API**라 빠져 있다. 프론트(헤더·`sessionStorage`)와 공통 모듈(`TokenType`)도 작게 걸린다.

## 자세히

### 1. 범위를 정한 기준
ISE-20의 "정할 것" 표는 통합 담당이 SA 7-3 토큰 규칙 표의 행을 그대로 가져와, 각 행에 "양쪽이 구현하려면 아직 모자란 것"을 붙여 만들었다.

| 묶음 | 왜 계약인가 | ISE-20 항목 |
|---|---|---|
| 토큰 자체 | 발급자가 쓴 바이트를 검증자가 읽는다. 이름·타입이 하나라도 다르면 검증이 모두 실패한다 | claim 이름(회차 ID `sid`?)·타입, 서명 키 해석(UTF-8 그대로, ADR 0025), 만료 10분, `jti` 계산식 |
| 검증 규칙 | 검증자가 토큰 값을 무엇과 비교하는지가 정해져야 발급자가 넣을 값이 정해진다 | 회차 ID = 요청 회차, `sub` = `X-User-Id`, 실패 시 403 `ENTRY_TOKEN_INVALID` |
| 전달 방식 | 클라이언트가 보내고 Gateway가 꺼낸다 | 헤더 이름 `X-Entry-Token` |

뺀 것: `issued` 기록, 토큰 API의 Lua, 폴링 jitter, READY 상태. 모두 대기열 안에서 끝나거나 ADR 0031(ISE-68)이 다룬다.
같은 방식의 앞선 사례가 결제 토큰 계약이다(`docs/design/payment/contracts.md`: claim 표 + 예시 + 검증 동작 + 확인 요청).

### 2. 혼자 정해도 되는 것과 함께 정할 것
| 항목 | 정하는 사람 | 함께 볼 사람 | 이유 |
|---|---|---|---|
| claim 이름·타입, `jti` 식, 만료 10분 | 대기열 | 없음(통보) | 형식 소유자가 정한다(SA 6-9, 7-3 마지막 문단) |
| 서명 키 해석 | 대기열 | 결제(참고) | 결제 토큰이 이미 `TokenDecoders.signingKey`(UTF-8 그대로)를 쓴다. 같게 두면 공통 도우미 하나로 끝난다 |
| **요청 회차를 어디서 읽나** | **대기열 + 좌석 선점 + 좌석 조회** | — | 아래 3절. API 경로나 Gateway 필터 구조를 바꿀 수 있다 |
| 헤더 이름 | 대기열 | 프론트, 좌석 선점·조회 | 보내는 쪽(프론트)과 문서(11장)가 같은 이름을 쓴다. 바꾸기는 쉽지만 어긋나면 403만 난다 |
| 필터 순서(JWT → 입장 토큰) | 대기열 | Gateway 공통 코드 | `sub` = `X-User-Id` 비교는 JWT 필터가 `X-User-Id`를 만든 뒤에야 가능하다. 지금 Gateway에는 JWT 필터(`GatewayAuthenticationFilter`)만 있다 |
| 입장 토큰 대상 경로 | 대기열 | 좌석 선점·조회 | 어느 경로에 필터를 걸지(좌석 조회·선점만, SA 6-3) |
| `TokenType`에 ENTRY 추가 여부 | 대기열 | User·공통 담당 | 공통 enum은 지금 ACCESS·REFRESH뿐이다. 결제 토큰처럼 따로 둘지 정한다 |

### 3. 함께 정해야 하는 핵심: 요청 회차를 어디서 읽나
검증 규칙 "토큰의 회차 ID = 요청 회차"에서 요청 회차의 위치가 API마다 다르다.

| API | 담당 | 회차 위치 |
|---|---|---|
| `GET /api/v1/schedules/{scheduleId}/seats` | 공연·좌석 조회 | 경로 |
| `POST /api/v1/reservations` | 좌석 선점 | 본문 `scheduleId` |

Gateway(WebFlux)는 경로는 쉽게 읽지만, 본문을 읽으려면 요청 본문을 메모리에 담아 두었다가 다시 흘려보내야 한다.

| 선택지 | 장점 | 단점 |
|---|---|---|
| A. 선점 경로를 `/schedules/{id}/reservations`로 바꿔 Gateway가 경로만 본다 | 검증이 Gateway 한 곳에서 끝난다 | 선점 API 계약(SA 11장)을 바꾼다. 접수형 결과 조회 등 관련 경로도 맞춰야 한다 |
| B. Gateway가 본문을 읽어 `scheduleId`를 꺼낸다 | API를 바꾸지 않는다 | 가장 붐비는 선점 요청마다 본문 버퍼링이 붙는다. 필터가 본문 형식을 알아야 한다 |
| C. Gateway는 서명·`typ`·`aud`·`exp`·`sub`만 보고, 토큰의 회차 ID를 헤더(예: `X-Entry-Schedule-Id`)로 넘긴다. 서비스가 자기 요청 회차와 비교한다 | API와 필터가 단순하다. 경로·본문 어디에 있든 서비스가 안다 | 검증이 두 곳으로 나뉜다. 서비스가 비교를 빠뜨리면 다른 회차 입장권이 통한다. 외부에서 같은 헤더를 보내면 Gateway가 지워야 한다 |

어느 안이든 좌석 선점·조회 담당의 코드나 계약이 바뀐다. 그래서 대기열 담당 혼자 정할 수 없다. 지금 문서만으로 보면 A가 가장 단순하다(검증 한 곳, 본문 버퍼링 없음). 대가는 좌석 선점 담당의 API 경로 변경이다. 세 담당이 같이 고를 문제다.

### 4. 왜 Gateway와 좌석 선점 두 곳이었나
- 근거: SA 6-9 "입장 토큰(대기열 → Gateway·좌석 선점)". 이슈 본문의 "소비자: Gateway, Reservation"도 같은 뜻이다.
- Gateway: 검증하는 곳이다(SA 7-3). 검증 필터는 대기열 담당이 만들지만(SA 6-3), Gateway는 공통 코드라 필터 순서·에러 형식·대상 경로를 공통 규칙과 맞춰야 한다.
- 좌석 선점: 입장 토큰이 지키는 대상 API이고, 요청 회차가 본문에 있어 3절 문제가 생긴다.
- 빠진 것: 좌석 조회도 입장 토큰이 필요한 API다(SA 6-5 "회차 좌석 상태(입장 토큰 필요)"). 경로에 회차가 있어 3절 문제는 작지만, 대상 경로와 헤더는 같이 확인해야 한다. 프론트(헤더 이름, `sessionStorage` 안내)도 확인 대상이다.

### 5. 대기열 담당의 선택별 할 일 (추가 질문)
검증 위치 선택지의 장단점은 [검증 위치 노트](2026-10-29-entry-token-verification-location.md)에 있다. 여기서는 선택에 따라 누가 무엇을 해야 하는지만 적는다.

모든 선택에 공통(ISE-20에 확정할 것): claim(`typ=entry`, `aud=gateway`, `sub` 문자열, `sid` 정수, `exp` 10분, `jti`는 ADR 0031 식), HS256 + `TokenDecoders.signingKey`, 헤더 `X-Entry-Token`, 실패 403 `ENTRY_TOKEN_INVALID`, 적용 API 2개(좌석 조회·선점), 발급은 `POST /queue/token`(ADR 0031, dev 머지됨).

| 담당 | A-1 Gateway 단독(선점 경로 변경) | A-2 Gateway 단독(본문 읽기) | B Reservation 단독 | C 양쪽 분담 |
|---|---|---|---|---|
| 대기열 | Gateway 필터(JWT 필터 뒤, 경로에서 회차) + Gateway 키 설정 + WebFlux 테스트 | Gateway 필터 + 본문 버퍼링·JSON 파싱 + 테스트 | Reservation `@RequireEntryToken`·인터셉터·`EntryPass` + MockMvc 테스트 | Gateway 필터(서명~`sub`) + 내부 헤더 `X-Entry-Schedule-Id` 설정·외부 값 제거 + Reservation `EntryPass` 리졸버 |
| 좌석 선점 | 경로를 `/schedules/{id}/reservations`로, 본문 `scheduleId` 제거(ISE-7·ISE-21) | 본문 필드 이름 `scheduleId`를 Gateway와의 계약으로 고정 | 컨트롤러 표시 + 서비스 회차 비교 + 403 테스트 | B와 같음 |
| 좌석 조회 | 없음(경로에 회차) | 없음 | 컨트롤러 표시 + 회차 비교 + 403 테스트 | B와 같음 |
| 프론트 | 선점 호출 경로 변경 | 없음 | 없음 | 없음 |
| User·공통 | Gateway 필터 순서·오류 형식 리뷰 | 같음 | 없음 | Gateway 필터·헤더 제거 리뷰, `IdentityHeaders`에 내부 헤더 추가 |
| 문서 | SA 11-4·11-5 선점 경로, 6-4 | SA 7-3 그대로, 측정 항목(본문 버퍼링 비용) | SA 7-3·6-3·9-5, 결정 기록 `#56` 수정 + ADR | SA 7-3 검증 규칙 분리, 내부 헤더 명시 |

결정이 늦으면 안 되는 이유: ISE-20은 ISE-7(동기형 선점)과 ISE-56(서명과 검증)을 막고 있다. 특히 A-1은 ISE-7 착수 전에 정해야 선점 경로를 두 번 만들지 않는다.

## 이 프로젝트에서는
- 이슈: Linear ISE-20(대기열 담당, 마감 10/30, M2), 하위 관계: ISE-56(서명과 검증)·ISE-7(동기형 선점)을 막고 있다
- 근거: SA 6-3·6-5·6-9·7-3·11-3·11-5, ADR 0015(`sub` 확인), 0025(키 해석), 0031(ISE-68, 토큰 API·`jti`)
- 코드(10/29): Gateway에는 JWT 필터만 있고 입장 토큰 필터는 없다. 공통 `TokenType`은 ACCESS·REFRESH뿐이다
- 관련 노트: [입장 토큰 구조](2026-10-29-entry-token-structure.md)

## 면접 포인트
- "서비스 간 토큰 계약은 어떻게 나눴나" → 만드는 쪽과 읽는 쪽이 똑같이 해석해야 하는 것(토큰 형식, 검증 규칙, 전달 방식)만 계약으로 묶고, 형식 소유자가 정해 통보하고 소비자가 리뷰했다.
- "Gateway에서 본문의 값을 검증해야 하면?" → 본문 버퍼링 비용 때문에 경로로 옮기거나, Gateway는 토큰만 검증하고 비교 값을 헤더로 넘기는 방법을 비교했다.
