# 추첨 자동결제를 위해 결제 담당과 무엇을 합의해야 하나

## 질문
결제 담당과 합의할 내용 상세히 설명

## 짧은 답
합의할 것은 다섯 가지다. 앞의 두 개가 측정 시나리오 2와 바로 이어져 가장 급하다.
1. **PG 용량 나누기**: 자동결제가 일반 결제의 `pg-approve` 자리(동시 10)를 같이 쓸지, 따로 둘지
2. **빌링키 경계**: 등록·보관·결제 실행은 결제, 응모 때 빌링키 확인은 누가 어떻게 할지
3. **실패 처리**: 결제 실패 사유(`reasonCode`)마다 같은 당첨자에게 다시 결제할지, 예비자에게 넘길지(U9). ADR 0026(예매당 결제 1개)과 맞물린다
4. **결과가 늦게 확정될 때**: `UNKNOWN`·`NEEDS_MANUAL_CHECK`가 승계 마감(30분)과 선점 만료를 넘길 때
5. **이벤트 계약**: `BillingPaymentRequested`의 필드, 중복 수신 방지, 금액 검증

## 자세히

### 1. PG 용량 나누기 (측정 시나리오 2)
현재 결제 설계(`pg-integration.md` 5절)는 PG 호출 자원을 두 그룹으로 나눈다. `pg-approve`(승인 API, 동시 10, 대기 0, 자리가 없으면 바로 503)와 `pg-recovery`(재조회·환불, 동시 2)다. 자동결제를 넣을 그룹은 아직 없다.

| 선택지 | 장점 | 단점 |
|---|---|---|
| A. 자동결제도 `pg-approve`를 같이 쓴다 | 코드 변경이 없다 | 자동결제 2,000건이 자리 10개를 채우면 다른 회차 일반 결제가 바로 503이 난다. 대기 0이라 막을 수단이 없다 |
| B. 자동결제 전용 그룹 `pg-billing`(동시 3 `[가정]`) | 일반 결제 자리가 보호된다. 자동결제 속도를 숫자로 정할 수 있다(3 ÷ 0.3초 = 초당 약 10건, 2,000건에 약 3.3분) | PG에 걸리는 전체 동시 수가 13이 된다. 실제 PG 한도를 넘지 않는지 확인해야 한다 |
| C. 같은 그룹을 쓰되 일반 예매가 없는 시간에만 자동결제 | 자원 분리가 없다 | 같은 회차는 SA 4-3에서 이미 시간이 나뉘어 있지만, 다른 회차·공연의 일반 판매는 언제든 열려 있을 수 있다 |

추천은 B다. 결제 설계가 "호출 특성과 장애 영향이 다르면 그룹을 나눈다"(ADR 0018)는 기준을 이미 쓰고 있다. 자동결제는 사용자가 응답을 기다리지 않는 배치형 호출이라 이 기준에 맞는다.

함께 정할 세부:
- **허가를 못 얻을 때의 동작**: 승인 API는 503으로 거절하지만, 자동결제는 Kafka 소비자라 거절하면 안 된다. 기다리거나(소비 일시 정지) 잠시 뒤 다시 시도해야 한다. 이게 백프레셔(소비 속도를 하류 용량에 맞추는 것)다. 소비자 동시성(파티션 수·리스너 스레드)을 Bulkhead 동시 수와 같게 두면 대기가 거의 생기지 않는다.
- **Circuit Breaker를 공유할지**: PG가 같으므로 PG가 실제로 죽으면 둘 다 막혀야 한다. 반대로 자동결제만 실패율이 높을 때(빌링키 무효가 많을 때) 일반 결제까지 OPEN되면 안 된다. 카드 거절 같은 명확한 거절은 지금도 성공으로 세므로 큰 문제는 아니지만, 상태를 공유할지는 정해야 한다.
- **PG 쪽 한도**: Mock PG는 우리가 정한다. 토스 테스트 모드의 동시 호출 한도는 확인 못 함.

### 2. 빌링키 경계
SA가 정한 것: `billing_keys`는 payment DB에 있다(사용자당 ACTIVE 1개, 암호화 저장). 등록 API는 `POST /api/v1/payments/billing-keys`(결제 담당)다. 응모 API의 에러 코드에는 `BILLING_KEY_REQUIRED`(409)가 있다. 즉 **응모(Reservation 안 lottery 모듈)가 빌링키 유무를 알아야 하는데, 데이터는 Payment에 있다.** 이게 경계 문제의 핵심이다.

| 응모 때 빌링키 확인 방법 | 장점 | 단점 |
|---|---|---|
| A. 응모 때 Payment를 동기 호출 | 항상 최신 상태다 | 마감 직전 초당 100건이 그대로 Payment로 간다. Payment가 느리거나 죽으면 응모도 막힌다(시나리오 1에 결제 장애가 섞임) |
| B. Payment가 `BillingKeyRegistered`·`Revoked` 이벤트를 내고, lottery가 사본(읽기 모델)을 둔다 | 응모가 Payment와 분리된다 | 이벤트·소비자·테이블이 늘고, 등록 직후 반영이 잠깐 늦을 수 있다 |
| C. 응모 때는 확인하지 않고, 자동결제에서 빌링키가 없으면 실패로 보고 승계 | 가장 단순하다 | 당첨 2,000명 중 빌링키 없는 사람이 많으면 실패와 승계가 늘고, 사용자는 응모가 됐는데 나중에 실패한다 |

추천은 B를 기본으로 하고 C를 안전망으로 두는 것이다. 응모 뒤에 빌링키를 해지할 수도 있어서, 사본이 있어도 자동결제 시점의 실패는 어차피 처리해야 한다. 일정이 빠듯하면 C만으로 시작하고 B는 측정 결과를 보고 붙인다.

함께 정할 세부:
- 빌링키를 해지할 때 "진행 중인 응모가 있으면 막을지"
- 빌링키 원문은 Payment 밖으로 나가지 않는다(lottery는 유무와 `card_last4`만 안다)

### 3. 실패 처리 (U9와 ADR 0026)
결제 쪽 확정 사항: 결제 행은 예매당 하나다(`UNIQUE(reservation_id)`, ADR 0026). 거절된 예매는 다시 결제할 수 없고, 다시 결제하려면 새 예매가 필요하다. 0026은 "U9가 같은 예매 재결제를 요구하면 다시 연다"는 조건을 달고 추첨 담당에게 넘겼다(S-15·S-16).

`PaymentDeclined.reasonCode`는 `CARD_DECLINED`, `INSUFFICIENT_LIMIT`, `TOKEN_EXPIRED`, `NOT_SENT`, `OTHER`다. 사유마다 누구 책임인지가 다르다.

| 사유 | 책임 | 처리안 |
|---|---|---|
| `CARD_DECLINED`, `INSUFFICIENT_LIMIT` | 당첨자 | 예비자 승계(SA 규칙대로) |
| `NOT_SENT` (PG에 보내지 않았음이 확인됨) | 우리 서버 | 이걸로 당첨자가 자리를 잃으면 불공정하다. 같은 당첨자에게 **새 예매를 만들어** 다시 요청하면 0026을 바꾸지 않아도 된다 |
| `TOKEN_EXPIRED` | 해당 없음 | 서명 결제 토큰은 일반 결제용이다. 자동결제에 토큰을 쓸지부터 정해야 한다 |
| `OTHER` | 불명 | 승계로 볼지 정한다 |

추천: 0026은 그대로 두고 "우리 책임 실패는 같은 당첨자에게 새 예매로 1회 재시도, 당첨자 책임 실패는 승계"로 결제 담당에게 답한다. Payment/PaymentAttempt 분리(0026 대안 2)는 필요 없게 된다. 대가는 lottery가 `reasonCode`로 분기해야 한다는 점이다. 지금 계약은 "Reservation은 사유별로 분기하지 않아도 된다"고 적혀 있으니, 추첨은 분기한다는 사실을 계약에 적어야 한다.

### 4. 결과가 늦게 확정될 때
결제 상태 중 `UNKNOWN`은 재조회로 확정되고, `REQUESTED`는 10초가 지나면 재조회 대상이 된다. `NEEDS_MANUAL_CHECK`는 운영자가 확정할 때까지 종결되지 않는다. 추첨 쪽 숫자는 "자동결제 10분 안에 95%"와 "승계 마감 30분"이다.

정할 것:
- **재조회가 끝나는 시점의 상한**: 재조회를 몇 번, 어떤 간격으로 하는지 결제 설계에서 확인해 30분 안에 결과가 나오는지 맞춘다(재조회 횟수·간격은 이 답에서 확인 못 함)
- **`NEEDS_MANUAL_CHECK`인 당첨 건**: 승계 마감까지 확정이 안 되면 좌석을 일반 판매로 돌릴지, 붙잡아 둘지. 돌렸다가 나중에 승인되면 환불해야 한다(0027의 "HELD가 아닌 예매에 온 PaymentApproved는 환불" 흐름)
- **당첨 예매의 선점 만료(`hold_expires_at`)**: 일반 선점 만료가 그대로 적용되면 자동결제가 밀릴 때 만료 뒤 승인이 되고 환불로 이어진다. 당첨 예매만 만료를 승계 마감까지로 길게 둘지 정한다. 이건 Reservation 담당과도 관련 있다

### 5. 이벤트 계약 (`BillingPaymentRequested`)
SA 10-3 페이로드는 `reservationId, userId, amount, lotteryEntryId`다. 토픽은 `payment.command`, 키는 `reservationId`, Reservation이 Outbox로 발행한다.

정할 것:
- **멱등성**: 승인 API는 멱등키 헤더를 쓰지만 이벤트에는 없다. `UNIQUE(reservation_id)`와 결제 쪽 `processed_event`로 중복 수신을 막을 수 있는지, 별도 키가 필요한지
- **금액 검증**: 일반 결제는 서명 결제 토큰으로 금액을 검증한다. 자동결제는 내부 이벤트를 믿을지, Payment가 예매 금액을 따로 검증할지
- **결과를 받는 쪽**: `payment.result`는 Reservation 소비자 그룹 하나가 받는다. lottery는 같은 서비스 안 모듈이라 `reservationId`로 `lottery_entries.reservation_id`를 찾아 `WON → PAID/FAILED`로 바꾸면 된다. 결제 쪽에 추가 요청은 없다. 나중에 lottery를 서비스로 떼어 내면(SA 7-1) 소비자 그룹이 하나 더 생긴다
- **`method`**: 승인 API는 `BILLING`을 자동결제 이벤트 전용으로 남겨 두었다. 같은 승인 로직(TX1 → PG → TX2)을 쓰는지 확인한다

## 면접 포인트
- "자동결제가 일반 결제를 막지 않게 어떻게 했나?" → 호출 특성(배치형 vs 사용자 대기형)이 달라 Bulkhead를 나눴고, 소비자 동시성을 Bulkhead 동시 수에 맞춰 백프레셔를 걸었다. 전용 자리 3개로 2,000건을 약 3.3분에 처리하는 계산을 측정으로 확인했다
- "결제 실패하면 당첨자는?" → 실패 책임으로 나눴다. 당첨자 책임은 예비자 승계, 서버 책임은 새 예매로 재시도. 예매당 결제 1개 제약을 깨지 않는다
