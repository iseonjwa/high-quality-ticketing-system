# 추첨석을 등급으로 구분하는 것과 추첨이 좌석을 먼저 선점해 두는 것은 무엇이 다른가

## 질문
추첨석을 별도 등급(`LOTTERY`)으로 구분하지 않고, 좌석 일부를 추첨이 먼저 선점해 가는 방식으로 풀면 어떤가. 추첨 좌석의 확보·배정을 관리자가 매번 동적으로 할당하게 하면 어떤가.

## 짧은 답
일반 선점 쿼리를 고치지 않아도 된다는 장점이 있다. 하지만 추첨석은 "선점"이 아니라 "재고 할당"에 가깝다. 선점은 주인(사용자)과 짧은 만료(5분)를 전제로 만든 개념인데, 추첨석에는 주인이 없고 3일 넘게 묶여 있어야 한다.
그래서 선점 구조에 맞추려면 가짜 시스템 예매, 매수 한도 예외, 긴 만료, 당첨자에게 좌석 넘기기, 만료 때 추첨 풀로 되돌리기 같은 예외가 예매 흐름 코드 곳곳에 생긴다. 등급으로 구분하는 쪽은 일반 선점 쿼리에 조건 하나와 종결 때 되돌리는 작업 하나로 끝난다.

## 자세히

### 선점 방식으로 풀면 생기는 일
SA 기준 선점은 `reservations`(HELD, `hold_expires_at`) + `reservation_seats`(HELD, `UNIQUE(schedule_seat_id) WHERE status IN ('HELD','CONFIRMED')`) + `user_schedule_quotas`(매수 한도)로 이뤄진다. 추첨이 3,000석을 먼저 선점하려면:

| 필요한 것 | 이유 | 손대는 곳 |
|---|---|---|
| 시스템 사용자 명의의 예매 1건 + 예매 좌석 3,000행 | 선점에는 예매(주인)가 있어야 한다 | 예매 데이터에 실제 고객이 아닌 예매가 섞인다. 내 예매·통계·대사에서 빼야 한다 |
| 매수 한도 예외 | 회차당 4매(`max_per_user`) 검사를 통과할 수 없다 | 매수 한도 로직 |
| 3일 이상의 만료 | 기본 5분이면 만료 스케줄러가 풀어 버린다 | 생성 시 `hold_expires_at`을 추첨 + 60분으로 지정 |
| 당첨자에게 좌석 넘기기 | 시스템 예매 좌석 RELEASED + 당첨 예매 좌석 HELD를 한 트랜잭션으로 | 배정 워커 |
| 당첨 예매 만료 시 추첨 풀로 되돌리기 | 그냥 만료되면 회차 좌석이 AVAILABLE이 되어, 일반 판매가 열려 있으면 예비자 몫을 일반 사용자가 잡는다 | 예매 만료 스케줄러 |
| 종결 때 남은 시스템 선점 해제 | 일반 판매로 돌려준다 | 기존 해제 흐름 재사용(이건 쉽다) |

### 세 방식 비교
| 방식 | 일반 선점 쿼리 | 예매 흐름 코드 변경 | 데이터 의미 |
|---|---|---|---|
| 미리 떼지 않음(시간 규칙) | 그대로 | 없음 | 깔끔. 대신 일반 오픈이 추첨 후 70분 이후로 묶인다 |
| 등급 `LOTTERY` | `grade <> 'LOTTERY'` 조건 추가 | 거의 없음(종결 때 S로 되돌리기는 추첨 쪽) | 등급 칸에 판매 경로가 섞인다 |
| 추첨이 먼저 선점 | 그대로 | 가장 많다(위 표) | 가짜 예매가 생긴다 |

### 일반화: 할당과 선점
- 재고 할당(allocation): 재고를 판매 경로별로 나눠 두는 것. 주인이 없고 기간이 길다. 예: 항공사 좌석의 마일리지 좌석 할당.
- 선점(hold): 특정 구매자가 결제할 때까지 짧게 잡아 두는 것. 주인과 짧은 만료가 있다.
두 개념을 한 구조에 넣으면, 짧은 개념에 맞춘 규칙(매수 한도, 짧은 만료)을 긴 개념이 매번 예외로 피해 가야 한다.

### 관리자가 추첨석을 매번 동적으로 할당한다면
"동적"의 수준을 나눠 봐야 한다.

| 수준 | 내용 | 평가 |
|---|---|---|
| 1. 추첨마다 등급·좌석 수 지정 | 설정 API가 `sourceGrade`, `seatCount`를 받는다 | 지금 설계(`details.md` 2절)가 이미 이 수준이다 |
| 2. 여러 등급·구역에서 골라 할당 | 예: VIP 200석 + S 2,800석, 또는 구역 지정 | 등급 `LOTTERY`로 덮어쓰면 원래 등급(가격, 화면 표시, 되돌릴 등급)을 잃는다. 좌석마다 원래 등급을 남겨야 하므로 등급 칸 대신 별도 구분 컬럼(`sales_channel`)이 맞다. 또 당첨자가 VIP와 S 중 무엇을 받는지(가격이 다르다) 응모 때 정해야 해서, 응모가 등급을 고르게 되고 1인 1회차 1응모 문제(D2)가 다시 생긴다 |
| 3. 설정 뒤에도 수시로 변경 | 응모 중이나 추첨 뒤에 좌석 수를 바꾼다 | 응모 중 변경은 이미 응모한 사람의 당첨 확률을 바꿔 공정성 설명이 깨진다. 추첨 뒤 변경은 순위·승계와 얽힌다. 응모 시작(`entry_start_at`) 전까지만 바꿀 수 있게 막는 것이 안전하다 |

할당 자체는 `UPDATE schedule_seats SET ... WHERE schedule_id = ? AND grade = ? AND status = 'AVAILABLE' ... LIMIT`처럼 조건부로 해야 일반 판매가 이미 잡은 좌석을 뺏지 않는다.

## 이 프로젝트에서는
- 설계 문서: `docs/design/lottery/options.md` D9. 추첨 담당은 S석 일부를 추첨석으로 미리 떼는 방향을 검토 중이고, 표시 방법으로 등급 Enum(`LOTTERY`)과 먼저 선점하는 방식을 비교했다.
- 예매 흐름·좌석 코드는 아직 없다(reservation-service는 패키지 뼈대). 어느 방식이든 좌석 담당·예매 흐름 담당과 합의해야 한다.

## 면접 포인트
- **일부 재고를 특정 판매 채널용으로 떼어 둘 때 기존 장바구니·선점 구조를 재사용하지 않은 이유는?** 선점은 주인과 짧은 만료를 전제로 한다. 채널 할당은 주인이 없고 기간이 길어, 재사용하면 매수 한도·만료·데이터 집계 곳곳에 예외가 생긴다. 할당을 별도 표시로 두고 선점은 원래 의미대로 남겼다.
