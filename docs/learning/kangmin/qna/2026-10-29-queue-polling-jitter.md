# 대기열 폴링 간격의 jitter는 무엇이고, 서버와 프론트 중 어디서 넣어야 하나

## 질문
대기열에서 서버측에서 시간을 보내주고 프론트가 처리하는 것에 있어서. jitter ?

## 짧은 답
- jitter는 대기 시간에 일부러 섞는 작은 무작위 값이다. 같은 순간 응답을 받은 사용자들이 같은 순간 다시 요청해 부하가 주기적으로 솟는 것(thundering herd, 몰림 현상)을 흩어 놓는다.
- ISE-68(ADR 0031 결정 10)은 "순번 기반 간격 3~10초에 ±20% jitter"만 정했고, **누가 섞는지와 값의 단위**는 정하지 않았다.
- 추천: 서버가 섞어서 `nextPollAfterSeconds`에 담고 프론트는 그 값대로만 기다린다.
- 단위(추가 질문 뒤 정정): 초당 최댓값을 낮추는 데는 정밀도보다 **퍼지는 폭**이 중요하다. 지금은 정수 초를 유지하고 첫 폴링의 폭을 넓힌다. 1초 안 순간 몰림이 측정되면 그때 공통 규칙 전체를 정수 밀리초로 바꾼다(3절).

## 자세히

### 1. 왜 몰리나
오픈 정각에 1만 명이 1초 안에 진입하면 모두 거의 같은 시각에 응답과 `nextPollAfterSeconds: 3`을 받는다. 그대로 따르면 3초, 6초, 9초 뒤에 1만 건씩 다시 몰린다. 응답 지연 차이로 조금씩 흩어지지만 수십 ms 수준이라 거의 유지된다.

±20%를 섞으면 첫 번째 재요청이 2.4~3.6초 구간(1.2초 폭)에 퍼진다. 각 사용자의 무작위 값이 회차마다 더해지므로 퍼짐은 폴링할수록 커진다(k번째 폴링의 퍼짐은 대략 √k배). 시간이 지나면 요청이 고르게 깔린다.

### 2. 어디서 섞나
| 선택지 | 장점 | 단점 |
|---|---|---|
| A. 서버가 섞어 응답에 담는다 | 규칙이 한 곳이다. 비율·간격을 프론트 배포 없이 바꾼다. 진입 응답(ISE-68에서 진입도 `nextPollAfterSeconds`를 준다)부터 첫 폴링 시각을 서버가 흩는다. 부하 테스트 스크립트도 서버 값을 따르기만 하면 된다 | 응답 값이 매번 달라 테스트에서 난수를 주입해야 한다(`RandomGenerator`를 생성자로 받기) |
| B. 서버는 기본 간격만, 프론트가 섞는다 | 서버 응답이 결정적이라 테스트가 쉽다 | 규칙이 프론트에 있어 서버가 보장하지 못한다. 부하 테스트 스크립트(k6 등)도 같은 규칙을 따로 구현해야 하고, 빠뜨리면 측정이 실제보다 나빠진다 |
| C. 둘 다 섞는다 | — | 무작위가 두 번 들어가 실제 퍼짐을 설명하기 어렵다 |
| D. 결정적 분산: 서버가 `seq`나 사용자 ID로 오프셋을 정한다(예: 기본 간격 × (0.8 + 0.4 × (seq mod 100) / 100)) | 난수 없이 고르게 퍼진다. 같은 입력이면 같은 값이라 테스트가 쉽다 | 같은 사용자는 늘 같은 쪽(빠른 쪽·느린 쪽)에 있어 회차가 지나도 퍼짐이 커지지 않는다. 설명이 하나 더 필요하다 |

추천: A. 폴링 간격을 서버가 정한다는 지금 계약(`nextPollAfterSeconds`)의 목적이 "부하를 서버가 통제"이므로 jitter도 그 안에 넣는 것이 일관된다. 테스트는 난수 주입으로 해결하고, 범위(기본값의 0.8~1.2배)와 대략의 분포만 검증한다. D는 A의 테스트가 번거로울 때의 대안이다.

감수하는 것: 응답 값이 비결정적이다. 프론트가 값을 무시하면 막지 못한다. 그래서 너무 이른 재요청은 사용자 요청 제한(`ratelimit:{userId}`, SA 12-8)이 막는다는 것을 함께 적어 둔다.

### 3. 단위: 정수 초인가 밀리초인가 (추가 질문 뒤 정정)
처음 답에서는 "정수 초로 반올림하면 3초 구간에서 83%가 같은 초에 몰려 jitter가 사라진다"고 했다. 이 계산은 모든 사용자가 **정확히 같은 순간** 응답을 받았다고 가정한 것이라 과장이었다. 실제로는 진입 자체가 1초 정도에 퍼져 들어온다. 아래는 측정이 아니라 계산이다(1만 명이 1초 동안 고르게 진입, 기본 간격 3초, 첫 재요청 기준).

| 방식 | 첫 재요청이 퍼지는 구간 | 초당 최댓값 |
|---|---|---|
| jitter 없음 | 3~4초 | 약 1만 건 |
| ±20%, 밀리초 정밀도 | 2.4~4.6초 | 약 8,300건 |
| ±20%, 정수 초로 반올림(2·3·4초가 8%·83%·8%) | 2~5초 | 약 8,300건 |
| 정수 초, 2·3·4초 균등(각 33%) | 2~5초 | 약 3,300건 |

- 초당 최댓값은 정밀도가 아니라 **폭**이 정한다. ±20%는 3초 기준 1.2초 폭이라, 이미 1초 퍼져 있는 진입에는 첫 회 효과가 작다. 폴링이 반복되면 퍼짐이 커지지만(한 번에 표준편차 약 0.35초, k번째에 약 0.35√k초) 1초 넘게 퍼지려면 9회, 약 30초가 걸린다.
- 정밀도가 차이를 내는 곳은 **1초 안의 순간 몰림**이다. 진입이 100ms 안에 몰렸다면 반올림 방식은 83%가 다시 100ms 안에 오고, 밀리초 방식은 1.2초에 퍼진다. 초당 집계로는 둘이 같아 보이고 100ms 단위로 봐야 차이가 보인다.
- 몰림이 가장 심한 때는 오픈 직후 첫 폴링이다. 그래서 진입 응답의 간격만 폭을 넓히는 것이 가장 효과가 크다(예: 1~5초 정수 균등). 그 뒤 폴링은 ±20%로 충분하다.

단위 선택지:

| 선택지 | 장점 | 단점 |
|---|---|---|
| a. 정수 초 유지 + 첫 폴링 폭 넓히기 | 계약이 그대로다. 결제(`PaymentView.nextPollAfterSeconds`는 `Integer`, 테스트 있음)와 접수형 선점을 건드리지 않는다 | 1초 안 순간 몰림은 못 푼다. 1초 간격은 더 줄일 수 없다 |
| b. 대기열만 `nextPollAfterMillis`(정수) | 정밀하고 타입이 정수라 `parseInt`로 잘릴 일이 없다 | 같은 뜻의 필드가 API마다 이름·단위가 달라 프론트가 두 규칙을 안다. SA 11-2 공통 규칙과 어긋난다 |
| c. 공통 규칙 전체를 `nextPollAfterMillis`로 | 이름·단위·타입이 하나다 | 결제 코드·테스트·문서, SA 11-2·11-5를 함께 고친다. 결제 담당 작업이 생긴다 |
| d. 이름 유지, 소수 초 허용(`2.73`) | 결제 정수 값과 호환된다 | 같은 필드가 정수일 때도 소수일 때도 있다. Java DTO 타입이 서비스마다 달라지고, 프론트가 정수로 읽으면 잘린다 |

추천: 지금은 a. 바꿀 조건은 부하 테스트에서 100ms 단위 최댓값이 초당 평균보다 크게 튀는 것이다. 그때는 c로 한 번에 바꾼다. b와 d는 같은 뜻의 값을 두 방식으로 남겨 나중에 비용이 더 크다.

HTTP 표준 헤더 `Retry-After`는 정수 초만 담는다(RFC 9110 delay-seconds). 밀리초가 필요하면 어차피 본문 필드여야 한다.

### 4. 확인할 것
- jitter 효과는 ADR 0031 후속 작업대로 "초당 폴링 요청 최댓값"을 적용 전후로 비교한다. 1초 단위 집계는 1초 안의 몰림을 가리므로 100ms 단위 최댓값도 함께 본다.
- 부하 테스트 스크립트가 응답의 `nextPollAfterSeconds`를 그대로 따르는지 확인한다. 스크립트가 고정 간격으로 폴링하면 jitter를 측정할 수 없다.

### 5. "Redis 장애 503은 ms를 못 주니 정수 초가 맞다"는 의견 검증 (추가 질문)
결론(정수 초 유지)은 맞지만, 근거는 절반만 맞다.

| 주장의 부분 | 검증 | 근거 |
|---|---|---|
| 503 재시도 시각은 ms로 줄 수 없다 | 맞다 | 표준 헤더 `Retry-After`는 HTTP 날짜 또는 정수 초만 담는다(RFC 9110 10.2.3). 실패 응답 형식(SA 11-2 `{status, code, message, errors, traceId}`)에는 `data`가 없어 본문에도 넣을 곳이 없다 |
| 그러므로 폴링 간격도 정수 초여야 한다 | 따라 나오지 않는다 | 둘은 다른 신호다. 정상 폴링 간격은 200 응답 본문 `data.nextPollAfterSeconds`(서버가 정하는 계약 필드)이고, 장애 재시도는 503 헤더(HTTP 표준)다. 헤더의 제약이 본문 필드의 단위를 정하지 않는다 |

남는 근거는 "프론트가 기다리는 시간을 한 단위로 다룬다"는 일관성이다. 타이머 함수 하나에 초를 넘기면 된다. 다만 프론트는 어느 쪽이든 변환 한 줄로 끝나므로 약한 근거다. 정수 초를 유지할 더 강한 근거는 3절이다. 결제가 이미 같은 필드를 정수로 구현했고, 초당 최댓값은 정밀도보다 폭이 정한다.

이 의견에서 더 중요한 점은 단위가 아니라 **장애 회복 순간의 몰림**이다.
- Redis 서킷이 OPEN이면 대기열 요청이 모두 503을 받는다. 같은 `Retry-After` 값을 받은 사용자는 같은 시각에 다시 온다. 서킷이 HALF_OPEN으로 시험하는 순간(OPEN 10초 뒤 5회 시험, SA 9-4)에 재시도가 한꺼번에 몰리면 시험이 실패해 다시 OPEN이 된다. 회복이 늦어진다.
- 그래서 503에는 정상 폴링보다 jitter가 더 필요하다. 헤더가 정수 초라도 할 수 있다.
  1. 서버가 `Retry-After`를 응답마다 정수 범위에서 무작위로 고른다(예: 5~15초). 정수라도 폭이 넓으면 3절 표처럼 최댓값이 크게 준다.
  2. 클라이언트는 `Retry-After` 이상 기다리면 된다. 표준상 더 늦게 오는 것은 문제가 없으므로, 받은 값에 0~1초 무작위를 더해 1초 안의 몰림까지 흩을 수 있다. 연속 503이면 간격을 늘린다(지수 백오프).
- 지금 코드: Gateway의 503(인증 Redis 장애, ADR 0005)은 `Retry-After: 1` 고정이다(`GatewayErrorWriter`). 서킷 OPEN이 10초라 클라이언트는 OPEN 동안 약 10번 재시도하고 모두 즉시 503을 받는다. 서킷 덕분에 Redis에는 가지 않지만 Gateway 요청은 그만큼 는다. 대기열 503의 `Retry-After` 값은 아직 정해지지 않았다.

정할 것(대기열 담당·공통):
- 대기열 503 `Retry-After`: 서킷 OPEN 시간(10초)에 맞춘 범위 + 무작위. Gateway의 고정 1초도 같은 규칙으로 맞출지
- 프론트의 503 처리 규칙: `Retry-After` + 무작위 지연, 연속 실패 시 백오프 상한

## 이 프로젝트에서는
- 근거: ADR 0031 결정 10(대기열 담당, 제안), ADR 0005(인증 Redis fail-closed), SA 9-4 폴링 간격·Redis 서킷, 9-5 Redis 장애 정책, 11-2 실패 응답 형식, 11-5 대기열 응답, 12-8 `ratelimit:{userId}`
- 같은 생각을 쓴 곳: Outbox 재시도의 지수 백오프 + jitter(ADR 0022). 그쪽은 재시도 간격, 이쪽은 주기적 폴링 간격이다
- 판단할 사람: 대기열 담당(서버 규칙), 프론트 담당(값을 그대로 따르는지)

## 면접 포인트
- "폴링 부하가 주기적으로 솟으면?" → 서버가 다음 조회 시각에 jitter를 섞어 보냈다. 같은 순간 응답받은 사용자들이 같은 순간 다시 오지 않게 하는 것이다.
- "왜 서버에서?" → 폴링 간격을 서버가 정하는 목적이 부하 통제라 규칙을 한 곳에 뒀다.
- "jitter 폭은 어떻게 정했나?" → 초당 최댓값은 정밀도가 아니라 퍼지는 폭이 정한다는 계산을 하고, 가장 몰리는 첫 폴링만 폭을 넓혔다. 단위 변경은 측정에서 1초 안 몰림이 보일 때로 미뤘다.
