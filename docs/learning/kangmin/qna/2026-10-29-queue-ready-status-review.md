# 대기열 응답 상태에 READY를 더하는 제안(ISE-68)을 어떻게 볼까

## 질문
ISE-68 PR 리뷰중.. 응답 상태 추가에 대한 분석이 필요함

## 짧은 답
- 제안: 입장 토큰 발급을 POST `/queue/token`으로 떼고, 상태를 `WAITING`(차례 전) · `READY`(토큰 API를 부르면 받음) · `ADMITTED`(토큰 받음, 토큰 API에서만) 셋으로 둔다(대기열 담당 ADR 0031, 제안).
- 판단: `READY` 추가에 찬성한다. 토큰 발급을 떼어 낸 순간 "토큰 없이 입장 가능을 알리는 상태"가 반드시 필요하고, 상태 하나가 프론트 행동 하나에 대응한다.
- 리뷰에서 짚을 것은 상태 자체가 아니라 주변 규칙이다. READY 뒤 받을 수 있는 에러, READY를 받고 토큰을 안 받는 사람, 줄 앞쪽의 폴링 간격, ADR 번호 충돌.

## 자세히

### 1. 바뀌는 것
| | 이전(SA v3.3, ADR 0015) | 제안(ADR 0031) |
|---|---|---|
| 토큰을 주는 곳 | 순번 조회 GET, 진입 POST(재응답) | 토큰 API POST만 |
| 순번 조회 | 차례면 `waiting` → `issued` 쓰기 + `ADMITTED`·토큰 | 읽기 전용. `WAITING` 또는 `READY` |
| 진입 | `WAITING`(순번) | 순번 조회와 같은 `WAITING`·`READY`. 새로 섬 201, 이미 있음 200 |
| 에러 | `QUEUE_NOT_JOINED` | + `QUEUE_NOT_READY`(409) |

READY의 출발점은 상태를 늘리고 싶어서가 아니다. 폴링 GET에서 쓰기를 없애려고 토큰 발급을 뗐더니, 토큰을 주지 않는 응답에서 "이제 받으러 가라"를 표현할 값이 없어졌다.

### 2. 선택지 비교 (READY 자리에 올 수 있는 것)
| 선택지 | 장점 | 단점 |
|---|---|---|
| A. `READY` 추가(제안) | 상태 = 프론트 행동이 1:1이다(WAITING → 폴링, READY → 토큰 API, ADMITTED → 좌석 화면). "차례 됨"과 "이미 발급됨"을 합쳐도 행동이 같아 문제없다 | 계약에 상태·API·에러가 하나씩 는다. 차례가 된 사람은 요청이 1번 늘어난다(초당 N명 수준) |
| B. `WAITING` + `position: 0` | 상태 수가 그대로 | 이미 토큰을 받은 사람도 WAITING이라 부른다. 프론트가 숫자 값으로 행동을 정한다 |
| C. 토큰 없는 `ADMITTED` | 이름이 하나로 끝난다 | 같은 상태가 API마다 모양이 다르다(토큰이 있다가 없다가) |
| D. 순번 조회가 계속 토큰 발급(현행) | 요청이 1번 적다 | 폴링 GET이 쓰기를 해 복제본 분산·별도 제한이 막힌다. 발급 규칙이 두 곳 |

A가 맞다고 본다. B·C는 ADR이 이미 검토하고 버렸고, 그 이유가 타당하다. D와의 차이는 "가장 많이 불리는 API를 읽기 전용으로"라는 구조 이득과 요청 1번의 교환인데, 요청 증가는 대기 인원이 아니라 입장 속도 N에 비례해 작다.

감수하는 것: 계약 변경(프론트 미구현이라 지금이 가장 싸다), 2단계 호출로 생기는 사이 틈(아래 3절).

### 3. 리뷰에서 짚을 점
| # | 내용 | 왜 | 제안 |
|---|---|---|---|
| 1 | READY 뒤 토큰 API가 받을 수 있는 응답이 명시돼 있지 않다 | READY(이미 발급) 뒤 T가 지나 정리되면 토큰 API는 404 `QUEUE_NOT_JOINED`다. 반대로 READY 뒤 409 `QUEUE_NOT_READY`는 `admitted`가 줄지 않으니 정상 흐름에 없다 | "READY 뒤 404면 다시 진입, 409는 정상 흐름에 없음(나오면 버그)"을 11-5에 한 줄 적기. 프론트 분기가 정해진다 |
| 2 | READY를 받고 토큰을 안 받는 사람의 규칙이 없다 | 토큰 유효 시간 T는 토큰 API를 부른 시각부터 센다. 차례가 된 뒤 한참 있다 받아도 10분을 새로 받는다. 백그라운드 탭에서 돌아온 사람들이 한꺼번에 받으면 순간 입장이 N을 넘을 수 있다. 이전 설계도 "차례 뒤 첫 조회 시각"에 발급해 성질은 같다. 새 위험이 아니라 2단계가 되며 드러난 것이다 | 이번 PR에서 막을 필요는 없다. 이탈 판정(6-3 "이후")에서 "READY 미수령"을 이탈로 볼지 정할 항목으로 남기기 |
| 3 | 줄 앞쪽 사용자의 대기 | 줄이 비어 있을 때 진입하면 201 `WAITING`(새 seq는 항상 `admitted`보다 크다)이고, 다음 폴링(기본 3초 ± 20%)까지 기다린다. 오픈 뒤 한산할 때 체감 지연이다 | `position <= N`이면 `nextPollAfterSeconds`를 1초로. 순번 기반 간격 규칙에 한 줄 추가 |
| 4 | 토큰 API 응답의 `status`는 늘 `ADMITTED`다 | 그 응답 안에서는 정보가 없다. 다만 "모든 대기열 응답은 `data.status`로 화면을 고른다"는 규칙이 유지된다 | 그대로 두는 데 찬성. 코멘트할 필요는 없다 |
| 5 | ADR 번호 충돌 | 이 PR이 0031을 쓴다. 추첨 담당의 `0031-lottery-direction-measurement.md`도 0031이었다(10/31 커밋 전에 0036으로 바꿈) | 이 PR이 먼저 올라왔으니 추첨 쪽을 0032로 바꾼다 |

참고로 이 PR의 `jti` 결정(회차·사용자·발급 시각의 해시)은 [입장 토큰 노트](2026-10-29-entry-token-structure.md) 6절의 "다시 서명할 때 `jti`를 유지할지" 질문에 "유지"로 답한 것이다. "입장 1회 = `jti` 1개"가 되어 이후 측정에 쓰기 좋다.

`data.status`와 공통 응답의 `status`(HTTP 숫자) 이름이 겹친다는 점은 작성자가 PR 리뷰 포인트로 이미 올렸다. 결제도 `data.status`를 쓰고 있어 대기열만 바꾸면 더 어긋난다. 바꾼다면 팀 전체로 따로 정할 일이다.

## 이 프로젝트에서는
- PR: iseonjwa/high-quality-ticketing-system `#91`(`docs/ISE-68-queue-token-api`), ADR 0031(대기열, 제안), ADR 0015, SA 6-3·8-1·9-4·9-5·11-3~11-5·12-8
- Redis 장애 때(9-5 closed): 진입·순번 조회·토큰 API가 모두 503이다. 이미 받은 토큰은 서명만으로 계속 통한다. READY 추가로 바뀌는 것은 없다.
- 판단할 사람: 대기열 담당(작성자), 프론트 담당(READY 처리)

## 면접 포인트
- "응답 상태를 어떤 기준으로 나눴나" → 상태 하나가 클라이언트 행동 하나에 대응하게 했다. 서버 내부 사정(차례 됨, 이미 발급됨)은 행동이 같으면 한 상태로 합쳤다.
- "폴링 API를 왜 읽기 전용으로" → 가장 많이 불리는 API에 쓰기가 섞이면 복제본 분산과 별도 제한이 막힌다. 그 대가로 입장 시 요청이 1번 늘지만 입장 속도에 비례해 작다.
