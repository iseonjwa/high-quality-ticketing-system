# 추첨 자동결제 전용 Bulkhead pg-billing의 동시 3, 전용 토픽, 백프레셔, 그룹별 Circuit Breaker는 무엇인가

## 질문
추첨 설계 D6의 B안(전용 그룹 `pg-billing`)에서 "동시성 3"은 무슨 뜻이고 왜 3인가. 전용 토픽, 백프레셔, 그룹별 Circuit Breaker도 자세히 설명해 달라.

## 짧은 답
"동시 3"은 자동결제가 PG에 동시에 걸어 둘 수 있는 호출 수다. 처리량은 동시 수 ÷ 응답 시간이라, PG 응답 0.3초 `[가정]`이면 3은 초당 약 10건, 2,000건에 약 3.3분이다. 목표(10분 안 95%)를 약 3배 여유로 지키는 가장 작은 정수라 3이다. 1이면 10분이 꼬박 걸려 여유가 없고, 늘릴수록 PG에 거는 부하가 커진다.
전용 토픽은 자동결제 2,000건이 환불 명령 앞을 막지 않게 하고, 백프레셔는 허가를 못 얻은 메시지를 버리지 않고 같은 자리에서 다시 시도하게 하며, 그룹별 Circuit Breaker는 한쪽 실패가 다른 쪽 결제를 끊지 않게 한다.

## 자세히

### 1. 동시 3: Bulkhead가 세는 것
Bulkhead(격벽)는 세마포어다. 허가가 3개 있고, PG 호출 전에 하나를 얻고 응답 뒤 돌려준다. 3개가 다 나가 있으면 네 번째 호출은 허가를 못 얻는다.

| 동시 수 | 처리량(0.3초 기준) | 2,000건 | PG에 걸리는 최대 동시 수(승인 10 + 복구 2 + 이것) |
|---|---|---|---|
| 1 | 초당 3.3건 | 약 10분 | 13 |
| **3** | **초당 10건** | **약 3.3분** | **15** |
| 5 | 초당 16.7건 | 약 2분 | 17 |
| 10 | 초당 33건 | 1분 | 22 |

- 계산은 리틀의 법칙(처리량 = 동시 처리 수 ÷ 처리 시간)이다. PG 응답 0.3초는 가정이고, 실제 토스 빌링 API 응답 시간은 확인하지 못했다.
- 3을 고른 기준은 "목표를 지키는 가장 작은 값"이다. 자동결제는 사용자가 화면 앞에서 기다리는 결제가 아니므로 빠를 필요가 없고, PG에 거는 부하를 줄이는 쪽이 낫다. 남는 여유(10분 - 3.3분)는 실패 재시도와 응답 지연에 쓴다.
- Bulkhead는 **인스턴스마다** 따로 센다. payment-service를 2대 띄우면 실제 동시 수는 6이다. 수평 확장할 때 같이 봐야 한다.
- 기존 `pg-approve`의 동시 10은 그대로 남는다. 자동결제가 아무리 몰려도 일반 결제 자리 10개는 건드리지 않는 것이 이 안의 목적이다.

### 2. 리스너 동시성도 3으로 맞추는 이유
자동결제 요청은 HTTP가 아니라 Kafka 메시지로 온다. Spring Kafka 리스너 동시성(`concurrency`)은 메시지를 처리하는 소비자 스레드 수이고, 스레드 하나는 메시지 하나를 동기로 처리한다.

| 리스너 동시성 | 결과 |
|---|---|
| 3보다 크다(예: 10) | 10개 스레드가 허가 3개를 놓고 다툰다. 7개는 매번 허가를 못 얻어 재시도만 반복한다 |
| **3과 같다** | 동시에 처리 중인 메시지가 최대 3개라 허가가 거의 항상 남는다. 허가 거절은 PG가 느려졌을 때만 생긴다 |
| 3보다 작다 | 허가가 남아도 쓰지 못한다 |

- 주의: 리스너 동시성은 토픽 파티션 수보다 클 수 없다(남는 스레드는 논다). `payment.billing` 파티션은 3개 이상이어야 한다.
- 같은 당첨자의 요청 순서는 신경 쓰지 않아도 된다. 예매 1건 = 결제 1건이고 결제 멱등이 `reservationId`로 막는다.

### 3. 전용 토픽: 앞 메시지가 뒤를 막는 문제
Kafka 파티션 안의 메시지는 순서대로 처리된다. 자동결제 요청과 환불 명령(`RefundRequested`)이 같은 `payment.command`에 섞이면, 2,000건 뒤에 들어온 환불은 앞의 자동결제가 다 빠질 때까지(약 3.3분) 기다린다. 이것을 head-of-line blocking이라 한다.

| | 같은 토픽 | 전용 토픽 `payment.billing` |
|---|---|---|
| 환불 지연 | 자동결제가 다 빠질 때까지 | 영향 없음 |
| 속도 조절 | 토픽 하나에 리스너 하나라 자동결제만 따로 늦출 수 없다 | 자동결제 리스너만 동시 3으로 조절 |
| 비용 | 없음 | 토픽·리스너·SA 10-1 변경 |

### 4. 백프레셔: 허가를 못 얻으면 어떻게 하나
일반 승인 API는 허가를 못 얻으면 바로 503을 준다(현재 코드 `maxWaitDuration(Duration.ZERO)`). 사용자가 앞에 있어서 다시 누를 수 있기 때문이다. Kafka 메시지는 다르다. 기다리는 호출자가 없어서 예외로 끝내면 재시도 → DLQ로 가고, DLQ의 메시지는 누군가 손으로 다시 넣기 전까지 결제가 안 된다. 당첨자는 결제 기회를 잃는다.

그래서 허가를 못 얻으면 실패로 다루지 않고 "지금은 받을 수 없다"로 다룬다.
1. 오프셋을 커밋하지 않는다(이 메시지를 처리한 것으로 치지 않는다).
2. 같은 메시지를 잠시(예: 1초) 뒤 다시 읽는다. Spring Kafka에서는 수동 커밋 모드의 `Acknowledgment.nack(Duration)`이 이 일을 한다.
3. PG가 회복되어 허가가 생기면 이어서 처리한다.

이렇게 소비자가 받을 수 있는 속도에 맞춰 생산 측(Kafka에 쌓인 요청)을 기다리게 하는 것이 백프레셔다. 대가는 대기 시간이다. PG가 오래 죽어 있으면 당첨 예매의 선점이 만료될 수 있는데, 이 경우는 D12의 "결과 미수신 만료 → 선점 1회 연장"이 받는다.

### 5. 그룹별 Circuit Breaker
Circuit Breaker는 최근 호출의 실패율이 기준(지금 50%)을 넘으면 일정 시간(10초) 호출을 아예 막는다(OPEN). 실패로 세는 것은 타임아웃·5xx 같은 PG 이상이고, 카드 거절 같은 명확한 거절은 정상 응답이라 성공으로 센다.

| | CB 하나를 같이 씀 | 그룹마다 CB |
|---|---|---|
| 빌링 API만 장애 | 일반 승인까지 OPEN, 일반 결제 전부 거절 | 자동결제만 멈춤 |
| 일반 승인 API만 장애 | 자동결제까지 멈춤 | 자동결제는 계속 |
| PG 전체 장애 | 함께 OPEN | 각자 실패율을 보고 각자 OPEN. 결과는 같다 |

토스는 일반 승인과 빌링 결제의 API 경로가 다르므로 한쪽만 아플 수 있다는 가정이다. 현재 코드(`Resilience4jPgGroup`)는 이미 그룹마다 Bulkhead와 CB를 한 쌍씩 만든다. `pg-billing`은 같은 클래스로 그룹 하나를 더 만드는 일이다.

## 면접 포인트
- **Bulkhead 크기는 어떻게 정하나요?** 목표 처리 시간과 호출 응답 시간으로 필요한 동시 수를 계산하고(리틀의 법칙), 하류(PG) 한도 안에서 목표를 지키는 가장 작은 값으로 잡는다. 인스턴스마다 센다는 점을 같이 본다.
- **메시지 소비자에서 자원이 부족하면?** HTTP처럼 바로 거절하면 메시지가 DLQ로 가서 사실상 유실된다. 오프셋을 넘기지 않고 다시 읽는 백프레셔로 처리하고, 리스너 동시성을 허가 수에 맞춰 헛도는 재시도를 줄인다.
