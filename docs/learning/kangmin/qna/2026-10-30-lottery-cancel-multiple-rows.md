# 응모 취소 뒤 재응모를 새 행으로 만들면 한 사용자에게 행이 여러 개 생기는데, 무엇이 불리한가

## 질문
추첨 응모 취소(D5) A안처럼 취소는 `CANCELED`로 남기고 재응모는 새 행으로 만들면 한 사용자에게 행이 여러 개 생긴다. 이게 무엇이 불리한가. 같은 회차에서 한 번 취소하면 다시 응모할 수 없게 하면 어떤가.

## 짧은 답
정합성은 잃지 않는다. 부분 유니크 `UNIQUE(lottery_id, user_id) WHERE status <> 'CANCELED'`가 "살아 있는 응모는 한 사람당 하나"를 DB에서 보장한다.
불리한 점은 운영 규칙이 늘어나는 것이다. 모든 조회·집계에 `CANCELED` 제외 조건을 빠짐없이 붙여야 하고, 취소된 행의 멱등키를 어떻게 다룰지 정해야 하고, 취소·재응모 반복으로 행이 불어나는 것을 막을지 정해야 한다.

## 자세히

| 불리한 점 | 구체적인 모습 | 대응 |
|---|---|---|
| 조회 조건 누락 | 내 응모 조회, 응모자 수 지표, 추첨 대상 조회에서 `CANCELED`를 빼먹으면 취소한 응모가 살아 있는 것처럼 보이거나 응모자 수가 부풀려진다 | 추첨 대상은 처음부터 `status = 'ENTERED'`로 고른다. 응모자 수는 행 수가 아니라 살아 있는 행 수로 센다. 조회 메서드를 하나로 모은다 |
| 멱등키 해석 | `request_id`는 행마다 UNIQUE다. 취소한 뒤 예전 키로 다시 요청하면 "같은 키 = 기존 행 반환" 규칙 때문에 CANCELED 행이 돌아온다 | 재응모는 새 키로 해야 한다는 규칙을 API 문서에 적는다. 화면은 응모 버튼을 누를 때마다 새 키를 만든다 |
| 행 증가·남용 | 취소·재응모를 반복하면 한 사용자 행이 계속 는다 | 응모 3만 명 규모에서는 부담이 작다. 필요하면 재응모 횟수 상한이나 요청 속도 제한을 둔다 |
| 집계 의미 | "응모 행 수"와 "응모자 수"가 달라진다 | 지표 이름을 구분한다 |

B안(같은 행을 되살림)도 공짜는 아니다. 이력이 덮이고, 새 멱등키로 온 재응모를 기존 행에 어떻게 맞출지 규칙이 필요하다. 그래서 행이 여러 개인 불편은 "이력을 남기는 값"으로 보고 감수할 만하다.

### 대안: 취소는 받되 재응모는 막는다
한 번 취소하면 같은 추첨(회차당 추첨 1개라 곧 같은 회차)에 다시 응모할 수 없게 하면, 제약을 부분 유니크가 아닌 전체 유니크 `UNIQUE(lottery_id, user_id)`로 둘 수 있다. 사용자당 행이 평생 하나다.

| 얻는 것 | 잃는 것 |
|---|---|
| 행이 하나라 멱등키 해석 문제, 행 증가·남용, 취소·재응모로 순위를 바꾸는 시도가 모두 사라진다 | 실수로 취소한 사용자가 되돌릴 수 없다. 화면에서 "취소하면 다시 응모할 수 없다"를 확인받아야 한다 |
| SA 기존 제약을 그대로 쓴다. 부분 유니크가 필요 없다 | 매수(1→2매)를 바꾸려는 사용자도 취소 후 재응모로 바꿀 수 없다 |
| SA 규칙 "마감 전 응모 취소 가능"과도 맞는다(재응모는 규칙에 없다) | 재응모 시 유니크 위반이 나므로 "이미 응모"와 "취소한 응모"를 구분해 안내하려면 기존 행 상태를 한 번 더 읽어야 한다 |

추첨 대상(`status = 'ENTERED'`)과 응모자 수 지표에서 `CANCELED`를 빼는 조건은 이 안에서도 여전히 필요하다.

## 이 프로젝트에서는
- 설계 문서: `docs/design/lottery/options.md` D5, `details.md` 1절(`lottery_entries` 부분 유니크, `request_id` 멱등).
- 같은 방식의 선례: 예매·결제는 soft delete 대신 상태 전이로 남긴다(SA 12-1). 판매 여부도 `reservation_seats`의 부분 유니크(`WHERE status IN ('HELD','CONFIRMED')`)로 판정한다.

## 면접 포인트
- **취소 이력을 남기면서 한 사람당 하나만 유효하게 하려면?** 상태 컬럼과 부분 유니크 인덱스를 쓴다. 대신 모든 조회가 유효 상태 조건을 지켜야 하므로, 조회를 한곳에 모으고 테스트로 취소 뒤 재응모와 중복 응모를 함께 검증한다.
