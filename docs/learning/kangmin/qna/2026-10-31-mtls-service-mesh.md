# 서비스 간 인증에서 mTLS와 서비스 메시는 무엇이고, 이 프로젝트에 왜 과한가

## 질문
서비스 간 인증 선택지(네트워크 격리, 공유 비밀 헤더, 서비스용 JWT, mTLS·서비스 메시) 중 D인 mTLS·서비스 메시를 더 자세히 설명해 달라. 팀원이 "내부 API를 부른 쪽이 우리 서비스가 맞는지 확인하느냐"고 물은 맥락이다.

## 짧은 답
mTLS(mutual TLS)는 TLS 연결을 맺을 때 서버뿐 아니라 클라이언트도 인증서를 내서 서로 신원을 확인하는 방식이다. 인증서 안의 이름이 곧 서비스 신원이 되므로 "누가 불렀는가"를 네트워크 계층에서 확인하고, 통신도 암호화된다.
서비스 메시(Istio, Linkerd 등)는 이 인증서 발급·교체와 mTLS 연결을 각 서비스 옆의 프록시(사이드카)가 대신 처리하게 해서, 애플리케이션 코드를 바꾸지 않고 전체 서비스에 mTLS와 호출 허용 정책을 적용하는 인프라다.
효과는 가장 강하지만 인증서 운영과 Kubernetes 같은 기반이 필요하다. docker-compose로 운영하는 부트캠프 프로젝트에는 비용이 크다.

## 자세히

### 일반 TLS와 mTLS의 차이

| | 일반 TLS (HTTPS) | mTLS |
|---|---|---|
| 서버가 인증서 제시 | 한다 | 한다 |
| 클라이언트가 인증서 제시 | 안 한다 | 한다 |
| 확인되는 것 | 클라이언트가 "진짜 서버에 붙었다" | 양쪽이 서로 "누구와 붙었는지" 안다 |
| 클라이언트 신원 확인 방법 | 애플리케이션 계층(비밀번호, 토큰) | 연결 단계의 인증서 |

핸드셰이크 흐름(요지):
1. 클라이언트가 접속하면 서버가 자기 인증서를 보낸다. 클라이언트는 신뢰하는 CA가 서명했는지 확인한다.
2. 서버가 클라이언트에게 인증서를 요구한다(CertificateRequest).
3. 클라이언트가 자기 인증서와, 그 인증서의 개인키를 가졌다는 서명을 보낸다.
4. 서버가 같은 CA 기준으로 검증한다. 실패하면 HTTP 요청이 오가기 전에 연결이 끊긴다.
5. 서버는 인증서의 이름(CN·SAN, 메시라면 `spiffe://cluster.local/ns/default/sa/reservation-service` 같은 SPIFFE ID)을 읽어 호출자를 안다.

공유 비밀 헤더와 비교하면, 비밀값은 요청마다 그대로 전송돼 한 번 새면 누구나 재사용할 수 있다. mTLS의 개인키는 전송되지 않고 서명에만 쓰이므로, 통신을 엿봐도 신원을 훔칠 수 없다.

### 직접 구성할 때 필요한 것
mTLS 자체는 Spring Boot만으로도 켤 수 있다.

- 내부 CA 하나를 만들고, 서비스마다 인증서·개인키를 발급한다.
- 받는 쪽: `server.ssl.client-auth=need`와 truststore(우리 CA)를 설정한다.
- 부르는 쪽: RestClient·WebClient에 자기 keystore를 붙인다. Spring Boot 3.1부터는 SSL Bundle(`spring.ssl.bundle.*`)로 묶어 설정할 수 있다.
- 받는 쪽 코드에서 인증서 이름을 읽어 "이 경로는 reservation-service만 허용" 같은 판단을 한다.

어려운 부분은 설정이 아니라 운영이다.

| 운영 항목 | 할 일 | 빠뜨리면 |
|---|---|---|
| 발급 | 서비스가 늘 때마다 인증서 발급 | 새 서비스가 통신하지 못함 |
| 교체(rotation) | 만료 전에 새 인증서로 바꾸고 재기동·재로딩 | 만료 시각에 전체 장애 |
| 폐기 | 개인키가 새면 해당 인증서를 무효화 | 탈취한 쪽이 계속 정상 서비스로 행세 |
| 비밀 보관 | 개인키를 이미지·저장소에 넣지 않고 주입 | 키 유출 |

인증서 만료로 인한 장애는 실무에서 흔한 사고 유형이다. 그래서 수작업 mTLS는 서비스 수가 적을 때만 버틸 만하다.

### 서비스 메시가 대신해 주는 것
서비스 메시는 위 운영을 자동화한다. Istio 기준 구조는 이렇다.

- 데이터 플레인: 각 서비스 옆에 Envoy 프록시가 붙는다. 앱은 평문 HTTP로 `localhost` 프록시에 보내고, 프록시끼리 mTLS로 통신한다.
- 컨트롤 플레인(istiod): CA 역할을 하며 워크로드마다 수명이 짧은 인증서를 자동 발급·교체한다.
- 정책: `PeerAuthentication`으로 mTLS를 강제하고, `AuthorizationPolicy`로 "payment의 `/internal/**`는 reservation 서비스 계정만 호출 가능"처럼 호출 허용 규칙을 선언한다.

얻는 것: 앱 코드 변경 없음, 인증서 운영 자동화, 서비스 단위 허용 정책, 재시도·타임아웃·트래픽 분할·관측(메트릭, 분산 추적) 같은 부가 기능.
치르는 것: Kubernetes가 사실상 전제다(Consul Connect처럼 VM에서 도는 메시도 있지만 구성이 더 복잡하다). 요청마다 프록시를 두 번 거치므로 지연과 CPU·메모리가 늘고, 장애가 나면 앱 문제인지 프록시 설정 문제인지 가리기 어려워진다. 이 프로젝트에서 이 지연을 측정한 적은 없다.

### mTLS가 해결하지 않는 것
- 사용자 신원: mTLS는 "reservation-service가 불렀다"까지만 알려 준다. "사용자 42의 요청이다"는 여전히 `X-User-*` 헤더나 사용자 JWT로 전달해야 한다.
- 정상 인증서를 가진 서비스의 침해: reservation-service가 뚫리면 그 인증서로 허용된 호출은 모두 할 수 있다. 피해 범위는 허용 정책(AuthorizationPolicy)을 얼마나 좁게 잡았는가로 정해진다.
- Kafka: HTTP 메시와 별개다. Kafka 브로커에 SSL 클라이언트 인증과 ACL(토픽별 쓰기·읽기 허용)을 따로 설정해야 한다. 이벤트 payload 안의 값이 맞는지는 여전히 애플리케이션이 확인한다.

## 이 프로젝트에서는
- 현재는 네트워크 격리만 쓴다. Gateway가 `/internal/**`, `/api/v1/internal/**`를 외부에서 404로 막고(`gateway/src/main/java/com/iseonjwa/gateway/security/AccessPolicy.java`), 서비스 포트를 열면 `script/check-port-exposure.py`가 CI에서 실패시킨다. 서비스 간 신원 확인은 SA 7-2·7-3에 따라 MVP 이후로 미뤘다(`docs/decisions/0008-internal-trust-and-auth-design.md`).
- 배포는 docker-compose라 Istio·Linkerd를 바로 쓸 수 없다. Spring SSL Bundle로 수작업 mTLS는 가능하지만, 서비스 수만큼 인증서를 만들고 교체를 직접 해야 하며, 내부 동기 HTTP 호출이 지금은 payment → Mock PG 하나뿐이라 얻는 것이 적다.
- 필요해지는 순서는 공유 비밀 헤더 또는 서비스용 JWT가 먼저이고, mTLS·메시는 Kubernetes로 옮기거나 서비스 간 동기 호출이 많아질 때 검토할 조건이다.

## 면접 포인트
- mTLS와 일반 TLS의 차이: 클라이언트도 인증서를 내고 서버가 검증한다. 신원 증명이 연결 단계에서 끝나고, 개인키는 전송되지 않는다.
- 왜 서비스 메시를 쓰나: mTLS의 진짜 비용인 인증서 발급·교체를 자동화하고, 앱 코드 밖에서 서비스 단위 호출 정책을 선언하기 위해서다.
- mTLS만 있으면 인가가 끝나나: 아니다. 서비스 신원(인증)만 주므로 허용 정책과 사용자 단위 인가가 따로 필요하다.
- 왜 이 프로젝트에선 안 했나: docker-compose 환경이라 메시 기반이 없고, 내부 동기 호출이 거의 없어 위험 대비 운영 비용이 크다. 대신 내부 경로 외부 차단과 포트 비공개 검사로 노출을 줄였고, 남은 위험(내부망 안의 위조)은 ADR 0008에 기록했다.
