# 세션을 Redis에 공유하는 구조에서 Redis가 죽으면 전체가 멈추는데, 어떻게 막을 수 있나

## 질문
다른 팀이 Spring Session + Redis로 세션을 모든 서비스가 공유하는 구조라고 한다. Redis가 죽으면 인증이 전부 멈추는데, 어떻게 방지할 수 있나.

## 짧은 답
"Redis가 절대 안 죽게"는 불가능하므로 세 겹으로 나눠 대응한다.
1. 죽는 시간을 줄인다: 복제본 + Sentinel(또는 매니지드 Multi-AZ)로 자동 장애 조치.
2. 죽었을 때 피해 범위를 줄인다: 세션용 Redis를 캐시·대기열용과 분리하고, 세션이 필요 없는 공개 API는 Redis 없이 돌게 한다.
3. 죽었을 때 빨리, 명확하게 실패한다: 짧은 타임아웃 + 서킷 브레이커 + 503 응답.
JWT로 바꾸면 인증 자체는 Redis 없이 되지만, 로그아웃 블랙리스트를 Redis에 두면 같은 선택(장애 시 허용 또는 차단)을 다시 해야 한다.

## 자세히

### 왜 전체가 멈추나
세션 공유 구조에서 각 서비스는 요청의 세션 쿠키로 Redis에서 세션을 읽어 사용자를 알아낸다. Redis가 하나뿐이면 단일 장애점(SPOF)이 된다. 세션 정보 없이 사용자를 안전하게 알아낼 방법이 없으므로, 장애 시 허용(fail-open)은 사실상 선택지가 아니다. 결국 질문은 "어떻게 덜 죽고, 죽었을 때 얼마나 좁게 멈추게 하나"다.

### 1. 죽는 시간을 줄인다 (고가용성)

| 방식 | 동작 | 장점 | 대가 |
|---|---|---|---|
| Replica + Sentinel | Sentinel이 Primary 장애를 감지하면 Replica를 승격하고, 클라이언트는 Sentinel에 물어 새 Primary로 붙음 | 세션 용도에 가장 흔한 구성. Spring Data Redis가 Sentinel 설정을 지원 | Sentinel 3대 이상(과반 투표) 필요. 감지·승격 동안 수 초 이상 실패. 복제가 비동기라 직전 쓰기(방금 만든 세션)가 사라질 수 있음 |
| Redis Cluster | 데이터를 여러 샤드로 나누고 샤드마다 Replica로 장애 조치 | 용량·처리량 확장 | 세션만 담기엔 과한 경우가 많음. 다중 키 명령 제약 |
| 매니지드(예: ElastiCache Multi-AZ) | 장애 조치를 클라우드가 처리 | 운영 부담이 가장 적음 | 비용, 로컬 docker-compose와 구성이 달라짐 |
| 영속화(RDB·AOF) | 디스크에 기록해 재시작 후 복구 | 재시작 뒤 전원 재로그인을 피함 | 가용성 대책이 아님. 죽어 있는 동안은 여전히 멈춤 |

세션 유실은 "다시 로그인"으로 끝나는 피해라, 비동기 복제의 유실은 보통 감수한다. 이것이 결제 데이터와 다른 점이다.

### 2. 피해 범위를 줄인다 (격리)
- Redis 분리: 세션, 캐시, 대기열, 분산락을 한 Redis에 두면 캐시 폭주나 대기열 부하가 로그인까지 멈추게 한다. 세션용을 따로 두면 서로 영향을 주지 않는다.
- 공개 API는 세션을 건드리지 않게: 공연 목록 조회처럼 로그인이 필요 없는 요청은 Redis 장애 중에도 응답해야 한다. 이 요청 경로에서 세션 조회가 일어나지 않는지는 실제로 Redis를 멈춰 놓고 확인해야 한다. 프레임워크 설정에 따라 공개 경로에서도 세션 쿠키가 있으면 조회가 일어날 수 있다(확인할 질문).
- 세션 내용 최소화: 세션에 사용자 ID·역할만 두고 큰 객체를 넣지 않으면 직렬화 비용과 메모리 압박이 줄어든다.

### 3. 빨리, 명확하게 실패한다 (장애 대응)
- 짧은 명령 타임아웃: 기본 타임아웃이 길면 요청 스레드가 Redis를 기다리며 쌓여서, Redis 장애가 애플리케이션 스레드 고갈로 번진다.
- 서킷 브레이커: 연속 실패하면 Redis를 부르지 않고 즉시 실패시켜 복구 중인 Redis에 부하를 더하지 않는다.
- 응답 구분: 인증 실패(401)와 저장소 장애(503 + `Retry-After`)를 구분하면 클라이언트가 로그인 화면으로 튕기지 않고 재시도를 안내할 수 있다.

### JWT로 바꾸면 해결되나
부분적으로만 해결된다. 서명 검증은 Redis 없이 되므로 "인증 전체 정지"는 피할 수 있다. 그러나 로그아웃·강제 만료를 위해 블랙리스트를 Redis에 두면, Redis 장애 때 "블랙리스트를 못 봤으니 허용할까(fail-open) 차단할까(fail-closed)"를 다시 정해야 한다. 차단을 고르면 세션 구조와 같은 증상이 나온다. 차이는 "선택할 수 있다"는 점이다. 세션은 허용이라는 선택지 자체가 없다.

## 이 프로젝트에서는
- 로그인은 JWT이고, Gateway가 Redis 블랙리스트를 100ms 제한으로 조회한다. 실패·타임아웃·서킷 OPEN이면 보호 API에 503 + `Retry-After`를 준다(`docs/decisions/0005-auth-redis-fail-closed.md`, SA 9-5). 2026-10-27 통합 회의에서 closed를 채택했다.
- 따라서 우리도 Redis 장애 동안 로그인 사용자의 보호 API는 503이 된다. ADR 0005가 이 대가를 "발견되는 대로 따로 고친다"고 남겼다. 위 1·2번(Sentinel, Redis 분리)은 아직 하지 않았고, ADR 0008 위협 T4는 블랙리스트·Refresh 해시·대기열이 같은 Redis에 있다고 기록한다.
- 실제 Redis pause로 503과 복구를 검증하는 일은 ADR 0005에 남은 작업으로 적혀 있다. 이 노트에서 장애 조치 시간을 측정한 결과는 없다.

## 면접 포인트
- 세션 공유 Redis가 SPOF라는 지적에: 고가용성(Sentinel·매니지드), 격리(용도별 Redis 분리, 공개 API의 세션 비의존), 빠른 실패(타임아웃·서킷·503)의 세 겹으로 답한다.
- Sentinel 장애 조치 중 세션이 사라질 수 있는 이유: 복제가 비동기라서다. 피해가 재로그인이라 보통 감수한다.
- JWT면 Redis 장애와 무관한가: 서명 검증은 무관하지만 블랙리스트를 쓰면 open·closed 선택이 다시 생긴다. 우리 팀은 closed를 골랐고, 그 대가를 ADR에 남겼다.
