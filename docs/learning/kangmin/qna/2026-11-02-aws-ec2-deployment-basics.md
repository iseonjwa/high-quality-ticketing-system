# 클라우드 배포는 왜 하고, EC2·AWS 가입·요금은 어떻게 다루며, 우리 프로젝트에는 어느 정도 규모가 맞나

## 질문
배포에 대해 아는 것이 없다. 클라우드 배포를 하는 이유, EC2가 무엇인지, AWS 가입과 요금제는 어떻게 고르는지, 우리 프로젝트 규모에 맞는 사양은 어느 정도인지, 필요할 때만 켜서 비용을 줄일 수 있는지 알고 싶다.

## 짧은 답
- 클라우드 배포는 "내 PC가 꺼져도 남이 인터넷으로 접속할 수 있는 서버"를 빌리는 일이다. 우리는 시연·심사·측정을 위해 한다.
- EC2는 AWS가 빌려주는 가상 서버(리눅스 컴퓨터 한 대)다. 우리는 EC2 1대에 docker compose로 전체를 띄운다(SA 9장).
- 우리 구성은 컨테이너 17개, 메모리 상한 합계 약 11.1GB라서 16GB급(예: t3.xlarge) 1대가 최소다(SA 9-3).
- EC2는 "중지(stop)"하면 서버 사용료가 멈추고 디스크 요금만 남는다. 시연·측정 때만 켜면 월 비용을 크게 줄일 수 있다.
- 숫자(요금, 무료 크레딧)는 바뀌므로 쓰기 전에 AWS 공식 요금 페이지와 Pricing Calculator로 다시 확인한다.

## 1. 클라우드 배포를 하는 이유
| 이유 | 설명 | 이 프로젝트에서는 |
|---|---|---|
| 항상 접속 가능 | 내 노트북은 꺼지고, 공유기 뒤라 밖에서 접속할 수 없다 | 튜터·심사위원이 URL로 시연을 본다 |
| 장비를 사지 않음 | 서버를 사지 않고 쓴 시간만큼 낸다 | 16GB 서버를 약 2주만 빌린다 |
| 같은 환경 재현 | 누구의 PC 사양에도 기대지 않는 고정 환경 | 측정 결과에 "EC2 타입"을 적어 비교할 수 있다(SA 측정 환경 기록표) |
| 측정 분리 | 부하 도구와 대상 서버를 다른 기기에 둔다 | 노트북에서 부하를 걸고 EC2를 측정하면 서로 자원을 빼앗지 않는다 |
| 실무 경험 | 보안그룹, SSH, 비용 관리는 백엔드 면접 단골 주제다 | 포트폴리오에 "EC2 배포·보안그룹·SSH 터널"을 쓸 수 있다 |

## 2. 핵심 용어
| 용어 | 뜻 |
|---|---|
| 리전(Region) | 데이터센터가 모인 지역. 서울은 `ap-northeast-2`. 사용자와 가까울수록 지연이 짧다 |
| EC2 인스턴스 | 가상 서버 한 대. "인스턴스 타입"(예: t3.xlarge)이 CPU·메모리를 정한다 |
| AMI | 서버를 만들 때 쓰는 OS 이미지(예: Ubuntu 24.04, Amazon Linux 2023) |
| EBS | 인스턴스에 붙는 디스크. 인스턴스를 중지해도 데이터가 남고, 요금도 계속 나온다 |
| 보안그룹 | 인스턴스 앞의 방화벽. 어떤 포트를 어느 IP에 열지 정한다 |
| 키 페어 | SSH 접속용 열쇠(.pem). 비밀번호 대신 쓴다. 저장소에 올리면 안 된다 |
| 퍼블릭 IP / 탄력적 IP | 밖에서 접속하는 주소. 일반 퍼블릭 IP는 중지 후 다시 켜면 바뀐다. 고정하려면 탄력적 IP를 쓰는데, 붙여 둔 동안 요금이 나온다 |
| IAM | 계정 안의 사용자·권한. 팀원마다 IAM 사용자를 만들고 루트 계정은 잠가 둔다 |

## 3. 가입과 요금제 (2025-07-15 이후 새 계정 기준, 확인 필요)
- 새 계정은 가입할 때 **Free 플랜**과 **Paid 플랜** 중 하나를 고른다. 2025-07-15부터 예전 "12개월 무료 사용량" 방식이 크레딧 방식으로 바뀌었다.
- Free 플랜: 크레딧(시작 $100, 온보딩 과제로 최대 $200이라고 소개됨)을 쓰고, 6개월이 지나거나 크레딧을 다 쓰면 계정이 닫힌다. 초과 요금이 청구되지 않는 대신 막힌다.
- Paid 플랜: 모든 서비스를 쓸 수 있고, 크레딧을 다 쓰면 사용한 만큼 청구된다.
- **확인할 질문**: Free 플랜에서 16GB급 인스턴스(t3.xlarge)를 띄울 수 있는가. Free 플랜은 쓸 수 있는 인스턴스 타입을 제한한다는 설명이 있어, 안 되면 Paid 플랜으로 바꾸고 크레딧을 쓰는 방식이 된다. 가입 직후 콘솔에서 확인한다.
- 가입에는 이메일, 휴대폰 인증, 해외 결제 가능한 카드가 필요하다. 카드 등록은 본인이 직접 한다.

### 가입 직후 꼭 할 일
1. 루트 계정에 MFA를 켠다. 루트로는 평소 작업하지 않는다.
2. IAM 사용자(팀원별)를 만들고 필요한 권한만 준다.
3. **예산 알림(AWS Budgets)**을 만든다. 예: 월 $30 초과 예상 시 메일.
4. 리전을 서울(`ap-northeast-2`)로 고정해 쓴다. 다른 리전에 실수로 만든 인스턴스는 놓치기 쉽다.
5. 액세스 키를 만들었다면 `.env`나 코드에 넣지 않는다. 이 프로젝트 배포에는 액세스 키가 필요 없다(SSH만 쓴다).

## 4. 우리 프로젝트에 맞는 규모
- 배포 구조: EC2 1대 + docker compose(SA 9장). 서비스 단위 다중 인스턴스나 매니지드 DB(RDS)·Kafka(MSK)는 쓰지 않는다. 비용과 범위 때문이며, "인스턴스가 죽으면 전체가 멈춘다"는 한계를 문서에 적어 두었다.
- 메모리: 컨테이너 상한 합계 약 11.1GB → 75% 여유를 두면 약 14.8GB → **16GB급이 최소**(SA 9-3, 값은 `[가정]`이고 `docker stats`로 측정해 바꾼다).
- 후보와 대략 요금(서울, 온디맨드, 출처마다 차이가 있어 확인 필요):

| 타입 | vCPU·메모리 | 시간당(대략) | 비고 |
|---|---|---|---|
| t3.large | 2·8GB | 약 $0.10~0.13 | 메모리 부족. zipkin·kafka-ui·prometheus를 빼야 한다(U10) |
| **t3.xlarge** | 4·16GB | 약 $0.21 | SA 기준을 맞추는 최소안 |
| t4g.xlarge | 4·16GB(ARM) | 약 $0.22로 소개됨 | ARM이라 모든 이미지가 arm64를 지원하는지 먼저 확인해야 한다 |

- t3는 "버스트형"이라 CPU를 오래 100% 쓰면 크레딧이 줄어 느려질 수 있다(무제한 모드는 추가 요금). 부하 측정 결과를 해석할 때 이 점을 함께 적는다.

## 5. 필요할 때만 켜서 비용 줄이기
| 상태 | 서버 요금 | 디스크(EBS) | 데이터 |
|---|---|---|---|
| 실행 중 | 나옴 | 나옴 | 유지 |
| **중지(stop)** | 안 나옴 | 나옴 | 유지(docker 볼륨도 디스크에 남는다) |
| 종료(terminate) | 안 나옴 | 기본 설정이면 디스크도 지워짐 | 사라짐 |

- 계산 예시(t3.xlarge 약 $0.21/시간, 확인 필요):
  - 24시간 내내 켜 두면: 0.21 × 24 × 30 ≈ **월 $150**
  - 시연·측정 때만, 예를 들어 하루 6시간 × 12일 켜면: 0.21 × 72 ≈ **$15** + 디스크 30GB 월 약 $3 + 켜 둔 동안 퍼블릭 IPv4 요금
- 주의할 점
  - 중지한 뒤 다시 켜면 퍼블릭 IP가 바뀐다. 시연 URL을 고정해야 하면 탄력적 IP를 쓰되, 붙여 두는 동안 시간당 요금이 나온다.
  - 탄력적 IP를 인스턴스에서 떼어 놓고 반납하지 않으면 계속 과금된다.
  - "중지"를 잊는 것이 가장 흔한 비용 사고다. 예산 알림, 그리고 시연 끝나면 끄는 사람을 정한다.

## 6. 배포 준비 순서 (이 프로젝트 기준 초안)
1. AWS 계정·IAM·예산 알림 준비(배포 담당 계정 1개를 팀이 같이 쓴다).
2. EC2 생성: 서울 리전, Ubuntu, t3.xlarge, 디스크 30GB 이상, 키 페어 생성.
3. 보안그룹(SA 9-2): 22는 팀원 IP만, 8080(gateway)만 공개, Grafana·Kafka-UI 등 관리 화면은 열지 않고 SSH 터널로 본다.
4. 서버에 Docker·Docker Compose 설치.
5. 코드 가져오기: `git clone`(또는 이미지를 레지스트리에 올려 `pull`).
6. 서버용 `.env` 만들기: 서버에서 생성하고 저장소·채팅에 값을 올리지 않는다.
7. `docker compose up -d` → 헬스 체크 → Gateway로 시연 흐름 확인.
8. 끝나면 `docker compose down`이 아니라 인스턴스 **중지**(데이터 유지) 또는 마지막에 **종료**.

## 면접 포인트
- "EC2 1대 compose 배포의 한계는?" → 인스턴스 장애가 곧 전체 장애이고, 서비스별 확장이 안 된다. 운영이면 서비스별 다중 인스턴스와 매니지드 DB·브로커로 나눈다. 범위와 비용 때문에 컨테이너 분리까지만 했다.
- "외부 노출은 어떻게 줄였나?" → 보안그룹으로 Gateway만 공개하고, 관리 화면은 SSH 터널로 접근하며, compose에서도 `127.0.0.1`에만 바인딩해 이중으로 막았다.
