# 구현은 메인 에이전트가 하고 코드 리뷰는 서브에이전트에 맡기면 무엇이 좋은가

## 질문
코드 작성과 구현은 메인 에이전트가 하고 서브에이전트가 코드 리뷰를 하면 어떤 이점이 있는가.

## 짧은 답
핵심 이점은 구현 과정의 맥락과 분리된 상태에서 결과물을 읽게 할 수 있다는 점과, 파일 충돌과 패널 관리 부담 없이 리뷰를 붙일 수 있다는 점이다. 대신 구현 자체는 빨라지지 않고, 사람의 최종 판단을 대체하지 못한다. 코드를 고치는 일이 하나일 때는 리뷰 패널을 따로 두는 것보다 이 구성이 단순하다.

## 자세히

### 이점
| 이점 | 이유 |
|---|---|
| 맥락 분리 | 일반 서브에이전트는 메인 대화를 이어받지 않고 새로 시작한다. 구현 중의 가정을 전달받지 않으면 코드와 완료 기준만 보고 판단한다 |
| 메인 대화 절약 | 리뷰 중 읽은 파일 내용은 서브에이전트에 남고 메인에는 결과만 돌아온다 |
| 충돌 없음 | 리뷰가 읽기만 하면 워크트리가 필요 없고 구현과 파일이 겹치지 않는다 |
| 지시·반영 단순화 | 메인이 리뷰를 요청하고 결과를 받아 고치므로 사람이 패널 사이에서 내용을 옮기지 않는다 |
| 관점 고정 | 리뷰어에게 완료 기준, 실패 경로, 팀 규칙만 보라고 역할을 좁힐 수 있다 |

### 한계
- 구현은 빨라지지 않는다. 구현을 병렬로 하려면 패널과 워크트리가 필요하다.
- 맥락 분리는 기계적으로 보장되지 않는다. 포크 방식은 대화를 이어받고, 프롬프트에 구현 의도를 길게 쓰면 편향이 그대로 전달된다.
- 같은 계열 모델이 같은 맹점을 공유할 수 있다. 독립된 사람의 리뷰를 대신한다고 볼 근거가 없다.
- 새로 시작하는 만큼 필요한 코드를 다시 읽어야 해서 토큰이 더 든다.
- 메인이 지적을 걸러 전달하면 반대 의견이 약해질 수 있다. 원문을 보고 사람이 판단해야 한다.
- 리뷰가 품질을 얼마나 올리는지는 이 프로젝트에서 측정하지 않았다.

### 구성 비교
| | 메인 구현 + 서브 리뷰 | 패널 리뷰 |
|---|---|---|
| 조작 | 메인에 요청 | 패널을 직접 지시 |
| 후속 질문 | 메인을 통해 | 리뷰어에게 직접 |
| 맞는 경우 | 구현이 하나이고 커밋 단위로 확인할 때 | 설계 쟁점을 사람이 리뷰어와 깊게 따질 때 |

### 잘 쓰는 방법
- 리뷰 요청에는 diff 또는 브랜치, 이슈 완료 기준, 볼 관점만 넣고 "이렇게 구현했으니 맞는지 봐 달라"는 설명은 뺀다.
- 지적마다 코드 위치와 실패 시나리오를 쓰게 한다. 스타일 의견과 동작 결함을 분리한다.
- 수정하지 말고 보고만 하라고 지시한다. 쓰기 도구를 뺀 전용 에이전트를 정의할 수도 있다. 다만 `Bash`를 주면 파일 변경 가능성이 남는다.

## 이 프로젝트에서는
- ISE-150처럼 구현이 하나인 작업에 맞다. 호출 위치, 트랜잭션 경계, 중복 이벤트 처리 같은 완료 기준을 리뷰 관점으로 줄 수 있다.
- 리뷰 지적을 수용하거나 거부한 판단은 `docs/ai-judgments/<이름>/`에 남긴다. 발제 필수인 AI 설계 검증 로그의 원천이 된다.
- 테스트는 고정 포트 테스트 DB를 쓰므로 메인 테스트와 리뷰 쪽 테스트를 동시에 돌리지 않는다.

## 면접 포인트
- AI에게 리뷰까지 맡기면 믿을 수 있는가: 맥락을 분리해 놓치는 것을 줄이려는 보조 수단이고, 지적의 사실 여부는 코드와 테스트로 확인해 사람이 수용·거부를 결정한다.
- 왜 구현자와 리뷰어를 나누는가: 구현 중 세운 가정에 묶이지 않고 완료 기준과 실패 경로로 결과물을 다시 읽기 위해서다.
