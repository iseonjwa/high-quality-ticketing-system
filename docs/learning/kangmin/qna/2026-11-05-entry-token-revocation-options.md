# 이탈이나 결제 완료 뒤 줄을 다시 서게 하려면 입장 토큰을 어떻게 폐기할 수 있는가

## 질문
입장 토큰을 받은 뒤 창에서 나가거나 결제를 마쳐도 만료 전이면 줄을 서지 않고 다시 들어온다. 입장과 동시에 폐기해 다시 줄을 서게 하려 할 때 블랙리스트, 빠른 만료, 전달한 토큰 삭제 등 현재 구조에서 쓸 수 있는 방법과 로직을 조금 바꿀 때 더 나은 방법은 무엇인가.

## 짧은 답
- 재입장 경로는 브라우저 저장 토큰, 서버 `issued` 기록, Gateway의 무상태 JWT 검증 세 곳이다. 한 곳만 막으면 나머지 경로로 다시 들어온다.
- 입장 토큰은 좌석 조회와 선점에 여러 번 쓰이므로 입장 즉시 폐기는 할 수 없다. 폐기 시점을 결제 확정이나 명시적 나가기로 잡아야 한다.
- 추천은 결제 확정과 [나가기] 때 `issued` 삭제와 프론트 토큰 삭제를 함께 하는 것이다. 저장한 JWT의 직접 호출까지 막아야 하면 Gateway에 `jti` 블랙리스트를 더한다.
- 폐기해도 다음 사람의 입장은 빨라지지 않는다. `admit.lua`가 인원과 무관하게 초당 N명씩 `admitted`를 올리기 때문이다.

## 자세히

### 지금 다시 들어올 수 있는 이유
| 층 | 동작 | 위치 |
|---|---|---|
| 프론트 | `sessionStorage`의 토큰이 만료 전이면 대기열을 건너뛴다 | `frontend/src/pages/queue/queueAdmission.ts:68` |
| 대기열 Redis | `issued`에 T 안의 기록이 있으면 진입 요청에 `READY`를 주고, 토큰 API가 같은 토큰을 다시 만든다 | `enter.lua:17`, `issue-token.lua:9` |
| Gateway | 서명·`exp`·`sub`·회차만 보고 Redis를 보지 않는다 | `EntryTokenFilter.java:54` |

`issued` 재발급은 응답 유실·새 탭·다른 기기에서 입장 기회를 지키려는 의도된 설계다(ADR 0015·0031). SA 7-3도 입장 토큰의 폐기 목록을 만들지 않는다고 정했다.

### 폐기 방법 비교
| 안 | 방법 | 다시 줄 서기 | 저장한 JWT 직접 호출 | 변경 범위 | 감수할 점 |
|---|---|---|---|---|---|
| A | TTL 단축 | 만료 뒤에만 | 만료까지 통과 | 설정·상수 | 폐기가 아니다. 좌석 고르는 사람도 쫓겨날 수 있다 |
| B | 프론트 토큰만 삭제 | 안 됨 | 통과 | 프론트 | `issued`가 남아 같은 토큰을 바로 다시 받는다 |
| C | `issued` 삭제 + 프론트 삭제 | 됨 | 만료까지 통과 | Lua 1개, 프론트, 호출 지점 | 직접 호출은 최대 T 동안 남는다 |
| D | C + Gateway `jti` 블랙리스트 | 됨 | 즉시 403 | C + Gateway 필터 | 요청마다 Redis 조회 1회. SA 7-3·계약 ① 변경 |
| E | C + Gateway가 `issued`를 직접 조회 | 됨 | 즉시 403 | C + Gateway 필터 | 키 추가는 없지만 Gateway가 대기열 키 구조를 알게 된다 |
| F | C + 선점 서비스에서 `issued` 확인 | 됨 | 조회만 통과, 선점은 거절 | C + 선점 서비스 | "서비스는 재검증하지 않는다"는 계약 변경. 선점 요청마다 Redis 조회 1회 |
| G | JWT를 불투명 토큰으로 교체 | 됨 | 즉시 403 | 발급·검증·계약 전체 | 삭제가 곧 폐기로 단순하지만 서명 검증의 이점을 잃고 변경이 가장 크다 |

- A: TTL은 `EntryTokenClaims.TTL` 상수(JWT `exp`)와 `queue.entry-token-ttl` 설정(Redis 판단)에 따로 있다. 설정만 바꾸면 두 값이 어긋난다.
- C: `issued`에서 지우면 `enter.lua`가 새 seq를 주므로 줄 맨 뒤로 간다. 다만 줄이 비어 있으면 바로 입장한다.
- C의 남는 위험: 직접 호출로 선점할 수 있지만 T 안이고 회차당 매수 제한(기본 4매)은 그대로 적용된다.
- D: 인증 필터가 이미 `auth:blacklist:{jti}`를 Redis로 조회하고 Redis 장애 때 503을 준다(`GatewayAuthenticationFilter.java:80`). 입장 토큰 필터까지 오는 요청은 이 조회를 통과한 요청이므로, 블랙리스트 추가로 생기는 새 비용은 가용성보다 조회 한 번의 지연과 부하다. 부하 증가량은 측정하지 않았다.
- D의 키: `jti`가 발급 시각에서 계산되므로 다시 줄을 서서 받은 새 토큰은 영향받지 않는다. 키 TTL은 토큰의 남은 시간으로 둔다.

### 폐기 시점 비교
| 시점 | 정확도 | 문제 | 판단 |
|---|---|---|---|
| 입장 즉시·첫 사용 | - | 좌석 조회와 선점에 여러 번 써서 바로 막힌다 | 불가 |
| 선점 성공 | 높음 | 응답을 잃으면 같은 멱등키 재요청이 403을 받는다. 결제 실패 뒤 다시 줄을 서야 한다 | 비추천 |
| 결제 확정(`CONFIRMED`) | 높음 | 없음에 가깝다. 결제는 결제 토큰을 쓰므로 영향이 없다 | 추천 |
| [나가기] 버튼 | 높음 | 버튼을 누른 사람만 처리된다 | 추천 |
| 창 닫기(`pagehide` + `fetch keepalive`) | 낮음 | 새로고침과 구분이 어렵고 요청이 유실될 수 있다. `sendBeacon`은 `Authorization` 헤더를 넣지 못한다 | 단독 사용 비추천 |
| 하트비트 무응답 | 중간 | 좌석 화면에 주기 조회가 없어 새 요청이 필요하다. 모바일 백그라운드 전환을 이탈로 오판할 수 있다 | 고도화 |
| 만료까지 둠(현재) | 해당 없음 | 조용히 떠난 사람의 재입장을 막지 못한다 | 나머지 경우의 안전망 |

하트비트 부하 계산: SA 상한 30,000명(50명/초 × 600초)이 15초마다 보내면 2,000건/초다. 상한과 임시값으로 계산한 수치이고 측정값이 아니다.

### 추천과 이유
1단계로 C를 결제 확정과 [나가기]에 연결한다.
- 고른 이유: 정상 사용자의 재입장을 막는 목적을 Gateway 변경 없이 달성한다. 응답 유실 대비 재발급(ADR 0015·0031)과 충돌하지 않는다.
- 감수할 점: 저장한 JWT의 직접 호출은 최대 T 동안 남고, 조용히 떠난 사람은 만료까지 재입장할 수 있다.
- 실패 처리: 결제 확정 뒤 폐기 실패가 결제 처리를 되돌리면 안 된다. 커밋 뒤 호출하고 실패는 로그만 남기며 T 만료를 안전망으로 둔다.

2단계로, 직접 호출까지 막기로 정하면 D를 더한다. E보다 D를 고르는 이유는 이미 있는 로그아웃 블랙리스트와 같은 방식이고 Gateway가 대기열 키 구조를 몰라도 되기 때문이다.

### 폐기와 처리량은 별개다
`admit.lua`는 안에 몇 명이 있든 `admitted`를 초당 N만큼 올린다. 폐기하면 시스템 안의 인원 L과 체류 시간 W는 줄지만 입장 속도 λ는 그대로다. 나간 만큼 다음 사람을 들이려면 "정원 − 현재 인원"만큼 입장시키는 슬롯 방식으로 바꿔야 한다.

슬롯 방식에서는 `issued` 크기만으로 현재 인원을 셀 수 없다. 차례가 됐지만 아직 토큰을 받지 않은(`READY`) 사람이 빠지기 때문이다. N의 의미와 기준선 측정도 바뀌므로 폐기와 별도 결정으로 다룬다.

## 이 프로젝트에서는
- 폐기 호출 위치 후보: `reservation-service`의 `PaymentResultService`. 대기열 모듈과 같은 서비스라 서비스 간 호출이 없다.
- 프론트: 결제 결과 화면과 [나가기]에서 `removeEntryToken(scheduleId)`를 부른다. `sessionStorage`는 탭 단위라 다른 탭의 토큰은 남는다.
- 선점 재요청 중 403은 프론트가 이미 `entryExpired`와 `maybeHeld`로 구분한다(`useHoldRequest.ts:106`).
- 기록·공유: D·E·F를 고르면 SA 7-3과 계약 ①을 바꾸므로 ADR과 Linear `contract` 이슈가 필요하다. 대기열 담당과 Gateway 담당 합의 대상이다.

## 면접 포인트
- JWT를 쓰는데 폐기는 어떻게 하는가: 무상태 검증과 즉시 폐기는 맞바꾸는 관계다. 짧은 TTL, 블랙리스트, 서버 저장 토큰 중 어느 수준까지 상태를 허용할지 정해야 한다.
- 블랙리스트를 쓰면 JWT의 이점이 사라지지 않는가: 사라지는 부분이 있다. 이 구조에서는 인증 필터가 이미 같은 Redis를 조회하므로 추가 비용을 조회 한 번으로 볼 수 있다. 결정 전에 측정해야 한다.
- 토큰을 폐기하면 대기열이 빨라지는가: 고정 속도 입장에서는 빨라지지 않는다. 내부 부하만 줄어든다. 빨라지게 하려면 슬롯 방식이 필요하다.
