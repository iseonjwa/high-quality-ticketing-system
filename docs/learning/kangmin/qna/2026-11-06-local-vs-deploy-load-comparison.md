# 부하 측정에서 로컬과 배포 서버를 어떻게 나눠 쓰는가

## 질문
로컬에서도 측정해 보고, 정확한 비교를 위한 수치화는 배포 서버에서 하는 것이 옳은가. 배포 서버 측정은 왜 11/13까지 기다려야 하는가.

## 짧은 답
옳다. 로컬은 시나리오 확인과 병목 탐색에 쓰고, 동기형과 접수형의 최종 비교 수치는 배포 서버에서 낸다. 11/13은 기술적 제약이 아니라 비용 때문에 정한 운영 일정이다(ADR 0047).

## 자세히

### 1. 측정 환경별 역할
| 환경 | 쓰임 | 말할 수 없는 것 |
|---|---|---|
| 로컬 | 스크립트 동작 확인, 병목 위치 찾기, 개선안 거르기 | 배포 서버의 처리량과 포화점 |
| 배포 서버 + 같은 VPC 발생기 | 개선 전후의 최종 수치 | 실제 운영 규모의 성능(서버 한 대 구성이다) |

로컬은 발생기와 대상이 같은 노트북에서 CPU와 메모리를 나눠 쓴다. B8 측정에서는 같은 비교의 차이가 PC 경합에 따라 약 1.5배에서 3%로 달라졌다(`k6-overload-recovery.md`, PR 349 브랜치).

### 2. 비교가 유효하려면
- 전후 측정의 인스턴스 유형, 메모리 상한, GC, 샘플링, 데이터 규모, 부하 조건을 같게 둔다.
- 커밋 해시와 측정 환경 기록표를 남긴다.
- 로컬 값과 서버 값을 서로 비교하지 않는다.

### 3. 11/13까지 서버가 없는 이유
- 배포 EC2와 Jenkins EC2를 함께 켜면 하루 약 6.8달러가 든다. 그래서 11/7~11/12는 중지하기로 했다(ADR 0047).
- 11/13 전에 켜는 것은 계정 주인이 결정할 수 있다. ADR 0047에도 필요한 날만 켜는 예외가 있다.
- 다만 서버만 켜서는 측정할 수 없다. ISE-191의 측정 방식과 ISE-193의 G1 반영이 먼저 필요하다.

### 4. 측정 환경을 세팅해 두면 배포 서버에서 바로 잴 수 있는가
배포 서버용 준비까지 끝나 있으면 잴 수 있다. local 세팅만으로는 부족하다.

| 구분 | 항목 |
|---|---|
| 그대로 쓴다 | k6 스크립트(`BASE_URL`을 바꾼다), 측정 환경 기록표 양식 |
| 배포용 준비가 더 필요하다 | 토큰(`TOKEN_MODE=sign`은 local 전용), 발생기 EC2, 추적 샘플링 0.01, 기록 도구, G1 반영 |
| 선점 기준선에서는 뒤로 미룰 수 있다 | remote write(결과 파일로 대신한다), Mock PG 장애 주입·지연 |

## 면접 포인트
- 개선 효과는 "같은 환경의 전후 비교"로 설명한다. 환경이 바뀌면 개선 효과와 환경 차이를 구분할 수 없다.
- 로컬은 빠른 반복에, 대상과 분리된 발생기를 쓰는 서버 측정은 발표할 수치에 쓴다.
