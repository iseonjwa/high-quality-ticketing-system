# 이 프로젝트의 AWS 배포는 어떤 구성 요소로 되어 있고, 코드가 서버까지 어떻게 가는가

## 질문
AWS 배포도 잘 모른다. (발생기 EC2를 어떻게 더하는지 설명을 들은 뒤의 질문)

## 짧은 답
- AWS 쪽은 "어느 땅(리전·가용 영역)에, 어떤 울타리(VPC·서브넷) 안에, 어떤 컴퓨터(EC2)를 두고, 어떤 문(보안 그룹)을 여는가"로 읽으면 된다.
- 코드는 **main 머지 → GitHub Actions가 이미지 빌드 → GHCR에 저장 → Jenkins가 감지 → 배포 서버에 SSH로 들어가 `docker compose pull`·`up`** 순서로 서버까지 간다. 사람이 서버에 들어가 빌드하지 않는다.
- 배포 서버 한 대 안에서 앱·DB·Kafka·관측 도구가 모두 컨테이너로 돈다(ADR 0047).
- 바탕 개념(클라우드를 쓰는 이유, EC2, 요금)은 `2026-11-02-aws-ec2-deployment-basics.md`에 있다.

## 자세히

### 1. AWS 구성 요소
| 용어 | 비유 | 뜻 | 이 프로젝트 값 |
|---|---|---|---|
| 리전 | 도시 | 데이터센터가 모인 지역 | 시드니 `ap-southeast-2` |
| 가용 영역(AZ) | 도시 안 건물 | 리전 안의 독립 데이터센터 | `ap-southeast-2a` |
| VPC | 우리 회사 전용 사설망 | 다른 계정과 분리된 가상 네트워크 | `vpc-08032543fc446b5c7` |
| 서브넷 | 사설망 안의 층 | VPC를 나눈 IP 대역. 한 AZ에 속한다 | 배포·Jenkins가 같은 서브넷 |
| EC2 | 빌린 컴퓨터 | 가상 서버 | 배포 `m7i-flex.xlarge`, Jenkins `t3.small` |
| EBS | 컴퓨터에 꽂은 디스크 | EC2 디스크. 중지해도 남고, 종료하면 지워진다(기본 설정) | 배포 서버 gp3 40GB. DB 데이터가 여기 있다 |
| 사설 IP | 내선 번호 | VPC 안에서만 통하는 주소 | 배포 `172.31.4.93`, Jenkins `172.31.38.150` |
| 탄력적 IP | 고정 대표 번호 | 중지·시작해도 안 바뀌는 공인 주소 | 배포 서버에 하나 |
| 보안 그룹 | 건물 출입문 규칙 | 포트별로 누가 들어올 수 있는지 정하는 방화벽 | 아래 표 |

**배포 서버 보안 그룹**
| 포트 | 누가 | 용도 |
|---|---|---|
| 80 | 전체 | 프론트(nginx). 사용자가 여는 화면 |
| 22 | 팀원 IP, Jenkins 보안 그룹 | SSH 접속. 팀원은 등록된 집 IP에서만 들어간다 |
| 3000 | 팀원 IP | Grafana. 로그인 없이 보기만 |
| 8080 | 평소 없음, 측정 중 발생기 보안 그룹 | Gateway 직접 호출 |

Grafana만 팀원 IP에 열고, Prometheus(9090)·Alertmanager(9093)·Zipkin(9411)·Kafka-UI(8085)는 열지 않는다. 팀원은 SSH 터널(내 PC의 포트를 SSH로 서버 포트에 이어 붙이는 방법)로 본다(`docs/guides/deploy-server-access.md`). 슬랙 경보의 "바로 가기"가 `localhost` 주소인 이유다.

첫 배포 때 막혔던 점: 보안 그룹은 들어오는 규칙(인바운드)과 나가는 규칙(아웃바운드)이 따로다. 아웃바운드 규칙이 없어 서버가 GitHub·GHCR로 나가지 못했다(TS-33).

### 2. 코드가 서버까지 가는 길
```
개발자 PR → dev → (릴리스) main 머지
  ① GitHub Actions: 테스트(build.yml) + 이미지 8개 빌드(images.yml)
  ② GHCR(GitHub 이미지 저장소)에 ghcr.io/iseonjwa/<서비스>:<커밋 SHA>로 저장
  ③ Jenkins EC2: main을 2분마다 확인 → 새 커밋이면 그 SHA 이미지가 다 올라왔는지 확인
  ④ Jenkins → 배포 EC2에 SSH(사설 IP) → .env·compose 반영 → docker compose pull → up -d
  ⑤ 헬스 확인 → 스모크 테스트(가입·로그인·공연 목록) → 실패하면 직전 성공 태그로 되돌림
  ⑥ 단계마다 슬랙 #이선좌-배포상태알림
```

| 선택 | 이유 | 감수한 점 |
|---|---|---|
| 빌드는 Actions, 배포는 Jenkins로 나눔 | 빌드 자원을 GitHub이 대고, Jenkins는 배포만 한다 | 도구가 둘이라 볼 곳이 둘이다 |
| Jenkins가 GitHub을 폴링(2분) | 웹훅을 받으려면 Jenkins를 인터넷에 열어야 한다 | 배포가 최대 2분 늦다. **측정 중 main 머지 금지**인 이유다 |
| 이미지 태그는 커밋 SHA 하나 | 서버에 무엇이 떠 있는지 커밋 하나로 말할 수 있고, 되돌릴 태그가 분명하다 | `latest`처럼 편한 이름이 없다 |
| 서버에서 빌드하지 않고 이미지만 받음 | 서버 CPU를 빌드에 쓰지 않고, 테스트를 통과한 같은 이미지를 배포한다 | 이미지 빌드를 기다려야 한다 |

### 3. 배포 서버 안
- `compose.yml` 위에 `compose.deploy.yml`을 덮어 쓴다. 앱 8개는 GHCR 이미지를 받고, 컨테이너마다 메모리 상한이 있다(SA 9-3).
- 비밀값은 서버의 `.env`와 Jenkins Credentials에만 있다. 저장소에는 자리표시자만 있다.
- 재배포하면 Mock PG가 새로 떠서 메모리에 둔 빌링키가 사라진다. 그래서 재배포 뒤 시드를 다시 넣는다.

### 4. 누가 무엇을 하나
| 할 일 | 누가 | 방법 |
|---|---|---|
| EC2 만들기·지우기, 보안 그룹 수정, 유형 변경 | 계정 주인(안준현) | AWS 콘솔. 팀원 콘솔 초대 없음 |
| 서버 켜기·끄기 | 계정 주인 | 콘솔(또는 서버 안에서 예약 종료 명령, 11/6 노트) |
| 배포 | 자동(main 머지) 또는 Jenkins에서 태그 골라 재실행 | |
| 서버 접속, 로그·DB 확인, 컨테이너 재시작, 장애 주입 | 등록된 팀원 | SSH(집 IP 등록 필요) |
| Grafana 보기 | 등록된 팀원 | 브라우저로 `:3000` 바로 |
| Prometheus·Alertmanager·Zipkin 보기 | 등록된 팀원 | SSH 터널 |

### 5. 중지와 종료
| 동작 | 서버 요금 | 디스크(DB 데이터) | 언제 |
|---|---|---|---|
| 중지(Stop) | 멈춤 | 남음(디스크 요금은 계속) | 배포 서버를 쓰지 않을 때 |
| 종료(Terminate) | 멈춤 | 지워짐 | 발생기처럼 지킬 데이터가 없는 임시 서버 |

## 이 프로젝트에서는
- 11/9 서버를 켜면 배포 서버는 중지 전 상태로 돌아온다(EBS 유지). 새 커밋을 반영하려면 main 머지로 재배포하고, 재배포 뒤 시드를 다시 넣는다.
- 측정 때 발생기 EC2를 같은 서브넷에 더하고 8080 규칙을 연다(`2026-11-08-load-generator-ec2-setup.md`).

## 면접 포인트
- 관리 화면은 시연에 필요한 Grafana만 팀원 IP에 열고 나머지는 SSH 터널로 보며, Gateway 직접 포트는 측정 중에만 보안 그룹 단위로 연다. 노출 면을 최소로 두는 방식이다.
- 이미지를 커밋 SHA로 고정하면 "지금 서버에 무엇이 떠 있나"와 "어디로 되돌리나"에 바로 답할 수 있다.
