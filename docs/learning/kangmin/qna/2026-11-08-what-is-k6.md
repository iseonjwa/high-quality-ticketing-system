# k6는 무엇이고, 이 프로젝트의 추첨 시나리오에서 어떻게 쓰는가

## 질문
k6 설명.

## 짧은 답
- k6는 Grafana Labs의 오픈소스 부하 테스트 도구다. 시나리오는 JavaScript로 쓰고, 실행 엔진은 Go라 한 장비에서 가상 사용자를 많이 돌린다.
- 이 프로젝트가 고른 이유(ADR 0046): 시나리오가 코드라 저장소에서 PR로 검토하고, CLI·Docker 한 줄로 돌리고, 결과를 Prometheus로 보내 서버 지표와 같은 Grafana에서 본다.
- 핵심 개념은 네 가지다. 가상 사용자(VU), 실행기(executor), 지표(metric), 합격 기준(threshold).

## 자세히

### 1. 도구 비교
| 도구 | 시나리오 작성 | 특징 | 이 프로젝트에서 안 고른 이유 |
|---|---|---|---|
| **k6** | JavaScript | CLI, Docker 이미지, Prometheus remote write | (채택) |
| JMeter | GUI + XML | 오래되고 플러그인이 많다. 스레드 하나가 사용자 하나라 무겁다 | 시나리오가 XML이라 PR 리뷰가 어렵다 |
| nGrinder | Groovy·Jython | 국내에서 많이 쓴다. 웹 UI, 컨트롤러·에이전트 | 띄울 것이 많고 결과가 Grafana와 따로 논다(ADR 0046) |
| Gatling | Scala·Java DSL | 보고서가 좋다 | 검토 기록 없음 |
| Locust | Python | 작성이 쉽다 | 검토 기록 없음 |

감수한 점: k6의 JavaScript는 Node.js가 아니라 npm 패키지를 그대로 못 쓴다. 장비 여러 대로 나눠 돌리려면 k6 Operator나 유료 클라우드가 필요해, 이 프로젝트는 발생기 1대의 한계 안에서 잰다.

### 2. 스크립트의 생명 주기
`loadtest/k6/scenarios/l1-lottery-entry.js` 기준이다.

| 단계 | 몇 번 | L1에서 하는 일 |
|---|---|---|
| init (파일 최상단) | VU마다 1번 | 환경 변수 읽기, `options` 정의, 사용자 지표 선언 |
| `setup()` | 전체 1번 | 관리자 로그인, 회차·추첨 생성, 응모 시작 시각까지 대기. 반환값이 모든 반복에 전달된다 |
| `default()` | 반복마다 | 사용자 한 명이 응모 1건(5%는 같은 멱등키로 2번) |
| `teardown()` | 전체 1번 | L1은 쓰지 않는다 |

### 3. 가상 사용자와 실행기: 닫힌 모델과 열린 모델
- **VU**: 스크립트를 반복 실행하는 가상 사용자. 반복(iteration) 하나가 `default()` 한 번이다.
- **실행기**: VU와 반복을 어떻게 돌릴지 정한다. 두 계열이 있다.

| 모델 | 대표 실행기 | 부하를 정하는 것 | 서버가 느려지면 |
|---|---|---|---|
| 닫힌 모델 | `constant-vus`, `ramping-vus` | 동시 사용자 수 | 응답을 기다리느라 요청이 줄어든다. 느려진 만큼 부하가 스스로 약해져 문제가 가려진다 |
| 열린 모델 | `constant-arrival-rate`, `ramping-arrival-rate` | 초당 도착 요청 수 | 느려져도 같은 속도로 계속 보낸다. 남는 VU가 없으면 반복을 시작하지 못하고 `dropped_iterations`로 센다 |

티켓 오픈·응모 마감처럼 사용자가 서버 속도와 상관없이 몰려오는 상황은 열린 모델이 실제와 같다. 닫힌 모델에서 생기는 이 왜곡을 coordinated omission(조율된 누락: 느린 응답 때문에 보냈어야 할 요청을 안 보내 지연이 작게 잡히는 현상)이라고 부른다.

L1은 `ramping-arrival-rate`로 초당 100 → 200 → 400 → 800건을 단계마다 5초 올리고 60초 유지한다. `preAllocatedVUs: 300`, `maxVUs: 3000`은 그 속도를 내는 데 쓸 VU 상한이다.

### 4. 지표
| 지표 | 종류 | 뜻 |
|---|---|---|
| `http_req_duration` | 내장 Trend | 요청 하나의 응답 시간 |
| `http_req_failed` | 내장 Rate | 실패 비율. L1은 `expectedStatuses(200, 201)`로 503을 실패로 센다 |
| `dropped_iterations` | 내장 Counter | 열린 모델에서 시작하지 못한 반복 수. 발생기 쪽 한계의 신호다 |
| `entry_duration` | 사용자 Trend | 응모 응답 시간. 태그 `result`로 성공·거절을 나눠 본다 |
| `entry_results` | 사용자 Counter | 결과·시도·오류 코드별 건수 |

응답 시간은 평균보다 백분위수(p95, p99)를 본다. 평균은 소수의 매우 느린 요청을 가린다. p95 300ms는 "요청 95%가 300ms 안에 끝났다"는 뜻이다.

### 5. check와 threshold
- **check**: 응답 하나를 검사하고 비율만 센다. 실패해도 테스트는 계속 간다(L1의 `'응모 201'`).
- **threshold**: 테스트 전체의 합격 기준이다. 넘으면 k6가 실패 종료 코드를 낸다. L1은 설계 기준을 그대로 옮겼다.
  - `entry_duration p(95)<300`: 시나리오 1의 기준(초당 100건 p95 300ms)
  - `entry_results{result:error} count<1`: 예상 밖 오류 0건
  - `dropped_iterations count<1`: 발생기가 속도를 못 낸 반복 0건. 이 값이 생기면 서버 한계인지 발생기 한계인지 구분할 수 없다

## 이 프로젝트에서는
- 실행은 설치 없이 Docker 이미지 `grafana/k6:1.0.0`으로 한다. 서버 측정 때는 `BASE_URL`만 Gateway 사설 주소로 바꾼다(발생기 노트 참고).
- 11/6 로컬 L1 결과의 "시나리오를 시작하지 못한 반복 4건"이 `dropped_iterations`다. 로컬은 k6와 서비스가 같은 PC라 이 값이 발생기 한계인지 확인할 수 없었다.
- 추첨 시나리오는 L1(응모 몰림), L2(자동결제), L3(일반 예매 간섭) 세 개가 `loadtest/k6/scenarios/`에 있다.

## 면접 포인트
- 부하 모델을 동시 사용자 수(닫힌)로 잡으면 서버가 느려질 때 부하도 줄어 병목이 가려진다. 몰림 상황은 도착률(열린 모델)로 잰다.
- 합격 기준을 threshold로 스크립트에 넣으면 측정이 "보고 판단"이 아니라 "통과·실패"가 된다.
