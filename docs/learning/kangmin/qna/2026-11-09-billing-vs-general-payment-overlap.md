# 추첨 자동결제와 일반 결제가 겹칠 때 쓰는 장애 대응 장치와 개선 후보

## 질문
추첨 자동결제와 일반 결제가 몰릴 때 장애 대응 방법이 어떤 것들이 있었나.

## 짧은 답
- 지금(ADR 0039 기준선)은 둘이 PG 승인 그룹 `pg-approve`(Bulkhead 동시 10, 대기 0, Circuit Breaker)를 같이 쓴다. 자리가 없으면 일반 결제는 즉시 503, 자동결제는 1초 간격으로 계속 다시 시도한다(백프레셔).
- 개선 후보는 세 가지다: 전용 그룹·토픽 분리, 자동결제 속도 상한, 추첨 시간대 예매 차단.
- 로컬 측정에서 `payment.command` 소비자 동시성이 1로 확인돼, 문제가 "일반 결제를 막는다"보다 "자동결제가 느리다"(2,000건 95%까지 약 10.4분, 외삽)일 가능성이 커졌다. 서버 L2-a·L2-b로 확인한다.

## 자세히

### 1. 지금 구현된 장치
| 장치 | 동작 | 근거 |
|---|---|---|
| Bulkhead `pg-approve` | 동시 10, 대기 0. 일반 결제·자동결제가 같이 씀 | `pg-integration.md` 5절, ADR 0018·0039 |
| Circuit Breaker | 최근 20회 중 실패율 50% 이상이면 OPEN 10초, HALF_OPEN 시험 3회 | 같은 표 |
| 타임아웃 | 연결 0.5초, 응답 2초 | SA 9-4 |
| 일반 결제가 허가를 못 얻으면 | 503 `PG_UNAVAILABLE`, 결제 행을 만들지 않음. 사용자가 같은 키로 다시 시도 | `pg-integration.md` |
| 자동결제가 허가를 못 얻으면 | `PgUnavailableException` → 1초(`PG_PERMIT_WAIT_MILLIS`) 간격 무제한 재시도. 오프셋을 넘기지 않아 유실·DLQ 없음 | `PaymentCommandKafkaConfiguration` |
| 결과를 모르는 승인(`Unknown`) | 재확인 스케줄러가 `pg-recovery`(동시 2)로 PG에 다시 묻는다 | `pg-integration.md` |
| 결과가 안 오는 추첨 선점 | 만료 때 1회 연장, 그래도 없으면 실패 처리 | ISE-149 |
| 결제 실패 당첨자 | 예비자 승계 | ISE-93 |
| 운영 정책 | 추첨은 저트래픽 시간대(03:00\~05:00 `[가정]`) 권장, 설정 API는 경고만 | D10 |

### 2. 기준선에서 일부러 남긴 문제
- 다른 회차 판매와 겹치면 자동결제가 자리를 차지해 일반 결제가 503을 맞는다(설계 가정).
- 같은 토픽 `payment.command`의 환불 요청이 자동결제 뒤에 밀린다. 동시성 1이면 허가를 기다리는 자동결제 한 건 뒤로 같은 파티션의 환불이 줄을 선다(head-of-line blocking, 코드 구조로 본 추론).

### 3. 개선 후보 (ADR 0039)
| 후보 | 효과 | 대가 |
|---|---|---|
| 전용 그룹 `pg-billing`(동시 3) + 전용 토픽 `payment.billing` | 일반 결제·환불과 완전 분리. 2,000건 약 3.3분(계산) | 설정·토픽·리스너 추가, PG 동시 호출 최대 13 |
| 자동결제 속도 상한(리스너 동시성 < 10) | 일반 결제 자리를 남긴다 | 완전 분리는 아님 |
| 시간 분리 강제(추첨 시간대 예매 차단) | 겹침이 없어진다 | 다른 공연 판매까지 멈춤. 최후 수단 |

### 4. 측정이 바꾼 전제 (11/6 로컬)
- 소비자 동시성 1이라 자동결제는 허가를 1개만 쓴다. 설계가 걱정한 "자리 10개를 다 채움"은 일어나지 않는다.
- 대신 처리량이 초당 3.10건이라 2,000건 95%가 약 10.4분(외삽)으로 목표 10분을 넘을 수 있다.
- 그래서 개선의 축이 바뀐다: 동시성을 올리면 빨라지지만 일반 결제 간섭이 늘어난다. 전용 그룹으로 나누면 둘을 같이 풀 수 있다.
- 동시성을 올리려면 파티션 수가 그 이상이어야 하고, 키 순서(같은 예매의 명령 순서)를 지켜야 한다. `payment.command` 파티션 수는 확인 못 함.

## 면접 포인트
- "왜 처음부터 Bulkhead를 나누지 않았나": 간섭을 먼저 재현해 측정값으로 고르려고 했다. 측정해 보니 예상한 간섭 대신 처리 속도가 문제로 드러났다.
- 같은 실패(허가 없음)라도 호출자에 따라 처리가 다르다. 사용자 요청은 빨리 실패(503)하고, 당첨 결제처럼 잃으면 안 되는 작업은 기다렸다 다시 시도한다.

### 5. 레이트 리미터는 겹침 대응 어디에 들어가나 (추가 질문)
- Bulkhead는 "동시에 몇 건"을, Rate Limiter는 "1초에 몇 건"을 제한한다. PG 지연이 300ms로 일정하면 둘은 거의 같은 효과지만, PG가 느려지면 다르다. Bulkhead는 느려진 만큼 처리량이 자동으로 줄고, Rate Limiter는 초당 건수를 그대로 밀어 넣어 대기가 쌓인다.
- 겹침 대응에서 쓸 곳:
  | 위치 | 방식 | 효과 |
  |---|---|---|
  | 자동결제 소비자 | Resilience4j `RateLimiter`로 초당 N건(개선 후보 B의 구체안) | 일반 결제 몫을 시간 단위로 남긴다 |
  | PG 호출 전체 | 토스 API 한도에 맞춘 초당 상한 | 외부 한도 초과(429)를 미리 막는다. 토스 한도는 확인 못 함 |
  | Gateway 사용자 요청 | `RequestRateLimiter`(ISE-5) | 봇·연타 차단. 자동결제 겹침과는 직접 관계 없음 |
- 자동결제에는 Bulkhead 쪽이 더 맞다고 본다. PG가 느려질 때 스스로 속도를 줄이기 때문이다. Rate Limiter는 외부 API 한도를 지켜야 할 때 더한다.

### 6. 레이트 리미터를 지금 도입할 수 있나 (추가 질문)
- 기술로는 바로 된다. `resilience4j-ratelimiter`는 이미 쓰는 `resilience4j-bom`이 버전을 관리하므로 `payment-service/build.gradle`에 한 줄 더하면 된다(로컬 Gradle 캐시에도 있다). `Resilience4jPgGroup`처럼 허가를 얻는 곳 앞에 `RateLimiter.acquirePermission()`을 두는 구조가 된다.
- 문제는 효과다. 지금 겹침 문제와 맞춰 보면 대부분 풀지 못한다.

  | 문제 | 레이트 리미터로 풀리나 | 이유 |
  |---|---|---|
  | 일반 결제 503 | 거의 아니다 | 자동결제는 동시성 1이라 이미 허가를 1개만 쓴다. 더 줄일 몫이 없다 |
  | 자동결제가 느림 | 더 나빠진다 | 처리량 = min(상한, 동시 수 ÷ 응답 시간). 지금 상한이 초당 약 3.3건이라 리미터는 속도를 낮추기만 한다 |
  | 환불이 뒤에서 막힘, PG 장애 때 토픽 정지 | 아니다 | 같은 토픽·같은 파티션 구조가 원인이다. 리미터로 기다리게 하면 오히려 막히는 시간이 늘어난다 |
  | CB 공유 | 아니다 | 장애 판정 단위(CB)가 그대로 하나다 |
  | 기한이 지난 결제 명령 | 아니다 | 대기가 길어지면 더 자주 생긴다 |
  | 외부 API 한도 초과(429) | 그렇다 | 리미터가 맞는 유일한 자리다. 토스 API 한도는 확인 못 함 |

- 그래서 순서는 "분리(A)로 동시성을 올린 뒤, 토스 한도가 그보다 낮으면 리미터를 더한다"가 맞다. 예를 들어 `pg-billing` 동시 3이면 초당 약 10건(계산)이다. 토스 한도가 이보다 낮을 때만 리미터가 일을 한다.
- 도입한다면 지킬 것
  - 소비자 스레드에서 기다리게 할 때는 대기 시한을 `max.poll.interval.ms`(기본 5분)보다 훨씬 짧게 둔다. 대기 시한을 0으로 두고 허가 거절과 같은 `PgUnavailableException`으로 던지면, 지금의 1초 재시도 경로를 그대로 쓸 수 있다.
  - Resilience4j 리미터는 인스턴스마다 따로 센다. payment-service가 2대면 실제 상한은 2배가 된다. 전체 한도를 지켜야 하면 Redis 기반 카운터가 필요하다.
  - PG가 느려져도 리미터는 초당 건수를 그대로 밀어 넣는다. 동시 수 상한은 Bulkhead가 계속 맡아야 한다(5절).
- Gateway 요청 제한(G-3, `open-peak-load-plan.md`)은 사용자 요청을 막는 다른 문제다. 지금 Gateway에는 요청 제한이 없다.

면접 포인트: "레이트 리미터를 왜 안 넣었나" → 병목이 초당 건수가 아니라 소비자 1개와 공유 파티션이었다. 리미터는 속도를 더 낮출 뿐이라 격리(Bulkhead·토픽 분리)를 먼저 하고, 외부 한도가 확인되면 리미터를 더하는 순서로 정했다.

### 7. 결제가 바쁠 때는 자동결제가 빠지고, 한가할 때 처리하게 할 수 있나 (추가 질문)
- 할 수 있다. 일반 결제에 우선권을 주고 자동결제는 남는 자리만 쓰게 하는 방식이다(우선순위 기반 부하 양보, work-conserving: 자원이 놀면 낮은 우선순위가 쓴다). 후보 D(공유 그룹 자리 예약)를 구체화한 것이다.
- "바쁜지"를 무엇으로 보느냐에 따라 세 가지가 있다.

  | 방식 | 바쁨 신호 | 동작 | 장점 | 단점 |
  |---|---|---|---|---|
  | ① Bulkhead 남은 자리 보기 | `pg-approve` Bulkhead의 남은 허가(`getMetrics().getAvailableConcurrentCalls()`) | 남은 자리가 K개(예: 4) 이하면 자동결제는 허가를 받지 않고 `PgUnavailableException` → 지금의 1초 재시도 경로 | 신호가 즉시이고 코드 몇 줄. 기존 백프레셔를 그대로 쓴다 | "확인 후 획득"이 원자적이지 않아 순간적으로 1~2개 어긋날 수 있다(허용 범위로 봄). 인스턴스마다 따로 본다 |
  | ② 지표 보고 소비자 멈추기 | 최근 10초 일반 결제 요청 수, 503 비율(Micrometer·Prometheus) | 기준을 넘으면 Spring Kafka 컨테이너 `pause()`, 내려가면 `resume()` | 긴 바쁜 구간에 잘 맞는다. 파티션 배정을 유지해 리밸런스가 없다 | 신호가 수 초 늦다. 기준값·흔들림 방지(이력 현상, hysteresis)를 정해야 한다 |
  | ③ 적응형 동시성 | PG 응답 시간 | 응답이 느려지면 자동결제 동시 수를 줄이고, 빨라지면 늘린다(AIMD, TCP 혼잡 제어와 같은 방식) | PG 상태까지 반영한다 | 이 프로젝트 규모에 비해 과하다 |

- 추천은 ①이다. 남은 자리 신호가 PG 앞 자원 경쟁을 가장 직접적으로 보여 주고, 기존 백프레셔 경로를 그대로 쓴다.
- 꼭 함께 정해야 할 것 세 가지
  1. **기아(starvation) 방지**: 일반 결제가 계속 바쁘면 자동결제가 영원히 기다린다. 선점은 30분 뒤 만료되므로 위험하다. 최소 몫(언제나 1자리는 쓸 수 있음)을 두거나, 선점 만료가 가까운 명령은 양보하지 않게 한다(에이징). 이때 결제 기한 필드(`payBefore`)가 기준이 된다.
  2. **같은 토픽에서는 역효과**: `payment.command`에서 자동결제가 빠져 있는 동안 같은 파티션 뒤의 환불도 멈춘다. `pause()`도 토픽 전체를 멈춘다. 양보 방식은 자동결제 토픽을 나눈 뒤(A의 토픽 부분)에만 쓸 수 있다.
  3. **동시성 1이면 효과가 작다**: 지금 자동결제는 허가를 1개만 써서 양보할 몫도 1개뿐이다. 이 방식의 가치는 자동결제 동시성을 올렸을 때 생긴다. 한가할 때는 10자리를 다 쓰고(2,000건 약 1분, 계산), 바쁠 때는 물러난다.
- A(전용 그룹)와 비교하면 다음과 같다.

  | | A 전용 그룹(동시 3 고정) | ① 공유 그룹 + 양보 |
  |---|---|---|
  | 한가할 때 속도 | 초당 약 10건(3 ÷ 0.3초) | 초당 약 33건(10 ÷ 0.3초) |
  | 바쁠 때 일반 결제 보호 | 완전 분리 | 예약한 K자리만큼 |
  | PG 동시 호출 최대 | 13 | 10(지금과 같음) |
  | CB | 분리됨 | 그대로 공유(따로 나눠야 함) |
  | 구현 | 그룹·토픽·리스너 추가 | 토픽·리스너 추가 + 양보 판단 + 기아 방지 |

- 바꿀 조건: L2-b에서 겹침 때 일반 결제 503이 늘지 않으면 양보 장치는 필요 없다. 자동결제 속도만 문제라면 A로 충분하다.

면접 포인트: "자동결제를 왜 고정 격리 대신 양보 방식으로 했나(또는 안 했나)" → 고정 격리는 단순하지만 한가할 때 자원이 논다. 양보 방식은 자원을 다 쓰지만 기아를 막는 장치가 필요하다. 같은 파티션을 쓰는 동안에는 양보가 환불까지 멈추게 해서 토픽 분리가 전제다.
