# 입장 토큰을 좌석 선점 시점과 결제 완료 시점 중 언제 만료시킬까

## 질문
입장 토큰을 언제 어디서 만료시킬지 회의 중이다. 좌석을 선점한 시점(결제하러 가기 전)이나 결제 완료 시점을 생각한다.

## 짧은 답
- 지금 입장 토큰은 서명과 `exp`(발급 10분)로만 검증하는 무상태 토큰이고 폐기 목록이 없다(SA 7-3, `queue/contracts.md`). 그래서 "어느 시점에 만료"를 하려면 상태(Redis 키 등)를 새로 둬야 한다.
- 입장 토큰은 좌석 조회·선점에만 쓰인다. 결제는 결제 토큰을 쓴다. 그래서 결제 완료 시점에 만료해도 막는 것이 거의 없다.
- 대기열 입장은 초당 고정 속도(`admitted`를 1초마다 올림)라, 토큰을 일찍 끝내도 다음 사람이 더 빨리 들어오지 않는다. 일찍 끝내는 이득은 처리량이 아니라 남용 방지다.
- 추천: 선점이 **성공한** 순간 그 토큰으로 선점을 더 못 하게 한다(좌석 조회는 `exp`까지 허용). 검사는 Gateway가 아니라 선점 API(reservation-service)에서 한다.

## 자세히

### 1. 지금 구조 (코드·문서로 확인)
| 항목 | 값 |
|---|---|
| 형식 | HMAC-SHA256 JWT, `exp` = 발급 + 600초 |
| 검증 위치 | Gateway, 좌석 조회(GET)·선점(POST)에서 서명·`exp`·`sub`·`scheduleId` |
| 폐기 | 없음. "입장 토큰은 좌석 조회·선점에 여러 번 쓰여 1회용이 될 수 없다"(SA 575행) |
| 피크 때 | 서명 검증은 Redis 없이 통과(SA 820행) |
| 입장 속도 | 초당 고정(`lastTick`, `admitted`) |
| 선점 | 한 요청에 좌석 여러 개(`SeatHoldRequest.seatIds`), 회차별 1인 누적 매수 제한 |

### 2. 선택지
| 안 | 얻는 것 | 대가 |
|---|---|---|
| A. 선점 성공 시점 | 선점 → 만료 → 다시 선점 반복(좌석 묶어 두기)을 막는다. 대기열 뒤 사람과 공정 | 좌석을 바꾸거나 선점이 만료되면 다시 줄을 선다. 선점 API에 Redis 확인 1회 |
| B. 결제 완료 시점 | 결제 실패·선점 만료 뒤에도 남은 시간 안에서 다시 고른다 | 지금의 10분 자연 만료와 차이가 작다. 결제 결과를 받아 토큰을 끝내는 서비스 간 연결이 는다 |
| C. 지금대로(10분 자연 만료) | 상태 없음, 피크에 Redis 호출 없음 | 10분 안에서 선점을 되풀이할 수 있다. 1인 누적 매수 제한이 일부만 막는다 |

### 3. 추천과 이유
- A를 고르되 "선점에 성공한 경우에만" 소모한다. 이선좌(409)·검증 실패는 소모하지 않는다. 실패마다 줄을 다시 서게 하면 몰릴 때 사용자가 대기열과 좌석 화면을 오간다.
- 결제 재시도는 같은 선점의 결제 토큰으로 하므로 입장 토큰이 없어도 된다. A가 결제 흐름을 깨지 않는다.
- 위치는 선점 API다. Gateway에 폐기 목록을 두면 피크 때 모든 좌석 조회에 Redis 호출이 붙는다. 선점은 이미 DB·Redis를 쓰는 요청이라 추가 비용이 작다.
- 구현 예: 선점 성공 트랜잭션 뒤 `SET entry:used:{jti} 1 NX EX 600`. 다음 선점에서 이 키가 있으면 거절한다. Redis 장애 때 통과시킬지(fail-open) 막을지는 정해야 한다.

### 4. 회의에서 정할 질문
1. 목적이 남용 방지인가, 대기열 회전인가. 회전이면 입장 방식을 "활성 사용자 수 기준"으로 바꿔야 효과가 있다.
2. 좌석을 바꾸려는 사용자(선점 취소 → 다시 선점)를 허용할 것인가.
3. 거절 응답 코드: 기존 403 `ENTRY_TOKEN_INVALID`를 쓸지, 새 코드(예: 409 `ENTRY_TOKEN_USED`)를 둘지. 프론트는 403이면 대기열로 보낸다.
4. 토큰 계약 변경이라 contract 이슈(대기열 담당 소유, 예매 흐름·Gateway·프론트 소비).
5. 추첨은 입장 토큰을 쓰지 않아 영향 없다.

### 5. 선점 성공 시점에 소모하는 구현 설계 (코드로 확인한 구조 기준, 미구현)
- 상태 저장 위치: Redis 대신 `seat_hold_requests` 테이블. 동기형 선점은 성공한 선점만 이 행을 남기므로(`SyncSeatHoldService.replay` 주석) "성공한 경우만 소모"가 자동으로 맞는다. 같은 트랜잭션이라 DB가 롤백되면 소모도 사라지고, Redis 장애 때 fail-open을 정할 필요가 없다.
- 변경 목록:
  | 위치 | 변경 |
  |---|---|
  | Gateway `EntryTokenFilter` | 검증 통과 뒤 `X-Entry-Token-Id: <jti>` 헤더를 붙인다. 클라이언트가 보낸 같은 헤더는 항상 지운다(`withIdentity`와 같은 방식) |
  | 마이그레이션 | `seat_hold_requests.entry_token_jti` 열과 고유 인덱스 |
  | `SeatHoldController` | 헤더를 받아 `HoldSeatsCommand`에 넣는다 |
  | `SyncSeatHoldService.hold` | 멱등 재요청(`replay`) 확인 뒤, 좌석 잠금 전에 같은 jti 행이 있으면 거절(빠른 실패). 동시 요청은 고유 인덱스 위반으로 거절 |
  | 오류 코드 | 새 코드(예: 409 `ENTRY_TOKEN_USED`) 또는 403 `ENTRY_TOKEN_INVALID`. 팀이 정한다 |
  | 프론트 | 거절 응답 안내("이미 좌석을 잡았어요" 또는 대기열로) |
- 지켜야 할 것: 같은 멱등키 재요청은 소모 뒤에도 성공해야 한다(응답 유실 대비). `replay`가 먼저 오므로 순서만 지키면 된다.
- 주의점: 고유 인덱스 위반이 `request_id` 고유 위반(TS-3, 같은 키 동시 요청)과 같은 예외로 올라온다. 제약 이름으로 구분해야 한다.
- 남는 문제: 입장 토큰 재발급은 같은 `jti`를 준다(ADR 0031 결정 9). 그래서 소모 뒤 좌석을 바꾸려는 사용자는 토큰 `exp`(최대 10분)까지 새 토큰을 받지 못한다. 바로 다시 줄을 서게 하려면 소모 때 대기열 `issued`에서 그 사용자를 빼야 한다(대기열 모듈 변경).
- 추첨의 시스템 선점(`SystemSeatHoldService`)은 `seat_hold_requests`를 쓰지 않아 영향이 없다.

### 6. 대기열 `issued`는 무엇인가 (추가 질문)
- Redis Sorted Set `queue:{scheduleId}:issued`. 값은 사용자 ID, 점수는 입장 토큰 발급 시각(ms, Redis `TIME`). "입장 토큰을 받은 사람과 언제 받았나" 목록이다.
- 대기열 키 다섯 개: `seq`(번호표 카운터), `waiting`(줄 선 사람, 점수 = 번호), `admitted`(지금 몇 번까지 들어와도 되나), `lastTick`(초당 한 번만 올리기), `issued`(토큰 받은 사람).
- 쓰임(`reservation-service/src/main/resources/redis/queue/*.lua`):
  | 스크립트 | `issued`로 하는 일 |
  |---|---|
  | `issue-token.lua` | 내 번호 ≤ `admitted`면 `issued`에 발급 시각을 넣고 `waiting`에서 뺀다. 이미 있으면 같은 시각을 써서 같은 토큰(같은 `jti`)을 다시 준다 |
  | `enter.lua` | 다시 진입할 때 `issued`에 있고 아직 유효하면 줄을 세우지 않고 `TOKEN_ISSUED`. 만료됐으면 `issued`에서 빼고 새 번호를 준다 |
  | `position.lua` | 순번 조회 때 `issued`에 유효하게 있으면 `TOKEN_ISSUED` |
  | `admit.lua` | 1초마다 만료된(발급 + T 지남) 사람을 `issued`에서 정리 |
- 그래서 토큰을 소모한 뒤 바로 다시 줄을 세우려면 `ZREM queue:{scheduleId}:issued {userId}`를 해야 한다. 안 하면 `enter`가 유효한 토큰이 있다고 보고 같은 토큰을 돌려준다.
