# L1 응모 몰림 로컬 측정(11/6)은 어떻게 돌렸고, 숫자는 무엇을 말하나

## 질문
L1 로컬 기록 상세히.

## 짧은 답
- 초당 100 → 200 → 400 → 800건으로 응모 속도를 올렸다. 200까지는 503이 0건이고, 400에서 503이 나기 시작했다(4,239건). 800에서는 요청 대부분이 503이었다(44,943건).
- 합격 기준(초당 100건에서 p95 300ms 이하)은 로컬에서 통과했다. 성공한 응모 기준 p95는 16.6ms다.
- 503은 응답 p50이 1.3ms로 매우 빨라, 서비스가 처리하기 전에 앞단에서 거절했을 가능성이 크다. 어디서 거절했는지는 확인 못 했다.
- 원본: `docs/design/lottery/numbers-and-measurement.md` 3-2절, `loadtest/k6/results/l1-lottery-entry-20261106-201021-*`, 스크립트 `loadtest/k6/scenarios/l1-lottery-entry.js`.

## 자세히

### 1. 측정 방법
| 항목 | 값 |
|---|---|
| 환경 | 로컬 compose 스택, 이미지 커밋 `b6d3ffd`. k6와 서비스가 같은 PC를 씀 |
| 실행기 | `ramping-arrival-rate`: 응답 속도와 상관없이 초당 요청 수를 고정한다. 서버가 느려져도 요청이 줄지 않는다 |
| 단계 | 각 속도마다 5초 동안 올리고 60초 유지. 단계 하나가 65초, 전체 260초 |
| 사용자 | 반복마다 새 사용자 ID(`userIdOf(iterationInTest)`). 토큰은 k6가 직접 서명(`TOKEN_MODE=sign`) |
| 응모 | 1매·2매 반반. 5%(`DUP_RATIO`)는 같은 멱등키로 0.2초 뒤 한 번 더 보냄 |
| 판정 기준 | 응모 p95 300ms 미만, 오류 0, 못 보낸 반복 0 |

### 2. 단계별 결과 (ms, 각 단계 앞 5초 제외)
| 단계(초당) | 성공 p50 | 성공 p95 | 성공 p99 | 503 |
|---|---|---|---|---|
| 100 | 7.7 | 16.6 | 41.2 | 0 |
| 200 | 6.9 | 20.2 | 56.4 | 0 |
| 400 | 7.6 | 35.2 | 118.7 | 4,239 |
| 800 | 58.9 | 478.6 | 581.3 | 44,943 |

- 200까지는 p50이 그대로다. 400에서 p99가 두 배가 되고 503이 생긴다. 800에서는 성공한 요청도 p50이 8배가 된다. 포화점은 200~400 사이다.
- 503은 시작 144초 뒤부터 났다. 단계 구간으로 계산하면 400 단계(130~195초)에 들어가 유지 구간이 시작된 지 약 9초 뒤다.

### 3. 전체 합계 (k6 요약)
| 항목 | 값 | 읽는 법 |
|---|---|---|
| 요청 | 100,384 | 반복 95,616 + 중복 재전송 약 4,768 |
| 201 | 50,860 | |
| 503 | 49,519 | 모두 `SERVICE_UNAVAILABLE` |
| 못 보낸 반복 | 4 | 판정 기준 실패 |
| 응모 행 | 48,553 = 고유 사용자 48,553명 | 중복 응모 0 |
| 전체 p95 | 51.2ms | 빠른 503이 섞여 낮아 보인다. 판정에 쓰면 안 된다 |
| 성공만 p95 | 141.1ms | |

- 201 50,860건과 행 48,553건의 차이 2,307건은 같은 멱등키 재전송이 기존 응모를 그대로 201로 돌려준 것으로 보인다(추론, 응답 코드 확인 못 함).
- `min=-242941ns`처럼 음수 응답 시간이 찍혔다. k6 시간 측정 오차로 보이나 원인은 확인 못 했다.

### 4. 503의 원인 후보
| 후보 | 근거 | 상태 |
|---|---|---|
| Gateway 인증 필터 | `GatewayAuthenticationFilter`가 로그아웃 확인(Redis)을 못 하면 503 `SERVICE_UNAVAILABLE` "일시적으로 인증을 확인할 수 없습니다"를 쓴다 | 코드 확인. 이번 503이 이것인지는 확인 못 함 |
| Gateway 일반 503 | `GatewayExceptionHandler`가 상태 503을 같은 코드로 바꾼다(서킷 브레이커, 대상 없음 등) | 코드 확인. 어떤 경로였는지는 확인 못 함 |
| reservation-service 메모리 | 측정 직후 509.7 / 512MiB(`mem_limit: 512m`) | 관찰. 원인인지 확인 못 함 |
| Zipkin 전송 밀림 | 구간 1,145개 버림 | 관찰. 원인인지 확인 못 함 |

응답 p50 1.3ms는 서비스 DB 처리(성공 p50 7ms 안팎)보다 훨씬 짧아 앞단 거절 쪽에 무게가 실린다.

### 5. 서버에서 확인할 것
- 503 응답 본문의 메시지를 k6에서 태그로 남겨 거절 위치를 가린다.
- 같은 시각 Gateway 로그와 reservation-service 힙·GC 지표를 본다.
- 로컬은 k6와 서비스가 CPU를 나눠 쓰므로, 포화점(200~400)은 서버 + 같은 VPC 발생기에서 다시 잰다.
