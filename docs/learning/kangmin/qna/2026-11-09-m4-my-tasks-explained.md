# M4 주간(11/9~11/16) 추첨 담당 할 일은 각각 무엇이고 왜 하는가

## 질문
위클리 스크럼에서 내 할 일만 정리하고 설명해 달라.

## 짧은 답
- 이번 주 일의 중심은 ISE-94다. 추첨이 장애와 폭주를 견디는지 서버에서 숫자로 증명한다.
- 순서는 장애 대응 → 기능 → 성능이다. 한 요청이 실패하는 경우부터 보고, 구성 요소 장애, 부하, 다른 기능과의 간섭으로 넓힌다.
- 숫자는 근거: `docs/context/handoff.md` 0-2절(11/8 정리), `docs/design/lottery/numbers-and-measurement.md` 3-2절(로컬 측정).

## 자세히

### 1. 날짜별 할 일
| 날짜 | 할 일 | 증명하려는 것 |
|---|---|---|
| 11/9 | 준현에게 확인 → 서버 기동·시드 재적재 → F1 장애 주입 | 결제 서버나 릴레이가 죽어도 돈은 한 번만 나가고 좌석은 사라지지 않는다 |
| 11/9~10 | ISE-196·ISE-192 검토 댓글(마감 11/10) | 다른 담당의 변경이 추첨을 깨지 않는다 |
| 11/10 | L2-a 자동결제 2,000건 → L2-b 일반 결제 겹침 | 당첨자 결제가 10분 안에 끝나고, 일반 결제를 막지 않는다 |
| 11/11 | L1 응모 몰림, 503 거절 위치, Slack 경보 도착 | 응모가 몰리면 어디서 얼마부터 거절되는지 안다 |
| 11/12 | 개선안 구현, F2 사유 분리 배포 | 측정으로 찾은 병목을 고친다 |
| 11/13 | 개선 뒤 재측정, 시간 되면 L3 | 고친 효과를 같은 조건에서 숫자로 비교한다 |
| 11/14~16 | 재현·문서화·ADR 0039 대체·발표 자료 | 발표에서 근거로 쓸 기록을 남긴다 |

### 2. 용어
| 용어 | 뜻 |
|---|---|
| 장애 주입(fault injection) | 일부러 구성 요소를 죽이거나 느리게 만들어 시스템 반응을 보는 것 |
| 기준선(baseline) | 개선 전 첫 측정값. 이게 있어야 개선 효과를 말할 수 있다 |
| 포화점(saturation point) | 처리량이 더 오르지 않고 지연·오류가 급증하기 시작하는 부하 |
| 외삽(extrapolation) | 작은 규모 측정값으로 큰 규모 결과를 추정하는 것. 실측이 아니다 |
| 소비자 동시성(consumer concurrency) | Kafka 소비자가 동시에 처리하는 스레드 수. 파티션 수를 넘지 못한다 |
| outbox 릴레이 | DB outbox 테이블에 저장한 이벤트를 Kafka로 내보내는 작업 |

### 3. 항목별 설명
- **시드 재적재**: Mock PG는 카드(빌링키)를 메모리에 둬서 재배포하면 사라진다. 자동결제 측정 전에 `script/deploy/seed-demo.sh`와 ISE-199 응모자 적재 스크립트로 다시 넣는다.
- **F1 장애 주입**: (1) 결제 서버를 PG 호출 전에 종료하면 `NOT_SENT`로 남아 재시도된다. (2) outbox 릴레이를 멈추면 결과가 안 와서 선점이 1회 연장된다. (3) 복구 뒤 결제가 정확히 1회만 일어나는지 본다. 장애 시작, Slack firing, 복구, resolved 시각을 적으면 탐지 시간과 복구 시간이 숫자로 남는다. 다만 경보 규칙이 `payment-service` outbox만 봐서 (2)는 Slack이 안 올 수 있다. 결제 담당과 먼저 정한다.
- **F2 사유 분리**: Mock PG를 재기동해 빌링키가 사라지면 `BILLING_KEY_MISSING`이 되고, 당첨자 책임 실패로 처리돼 승계로 넘어간다. 시스템 탓인 실패를 사용자 탓으로 처리하는 문제라 사유를 나눈다. 결제 사유 계약이 바뀌면 contract 이슈를 올린다.
- **L2-a**: 당첨자 2,000명 자동결제가 10분 안에 95% 끝나는지 본다. 로컬 외삽은 10.4분이라 넘을 수 있다. 원인 후보는 `payment.command` 소비자 동시성 1이다. 한 번에 한 건씩 처리하면 PG 응답 시간이 그대로 합산된다.
- **L2-b**: 자동결제와 일반 결제가 겹칠 때 일반 결제가 503을 받는지 본다. ADR 0039는 두 흐름이 서로 막지 않는다는 전제 위에 있어서, 동시성 1이 사실이면 전제가 달라진다.
- **L1**: 로컬에서는 초당 400건부터 503이 났고 응답이 1.3ms였다. 서비스까지 가기 전에 앞단에서 거절했다는 신호다. 메모리도 509.7/512MiB였다. 서버에서 어디서 거절하는지 확인한다.
- **F4**: 경보가 Prometheus 규칙에서 Slack까지 실제로 오는지 확인한다. 메시지 링크가 `localhost`라 서버에서는 SSH 터널을 열어야 한다.
- **개선·재측정**: L2 결과로 개선안을 고른다(동시성 조정이 후보). 같은 조건으로 다시 재서 전후를 비교하고, 결과가 ADR 0039와 다르면 대체 ADR을 쓴다.

### 4. 끝냈다고 말할 기준
- 측정마다 환경(서버 구성, 커넥션 대기 시한 1초 적용 여부, 시드 수)과 숫자를 함께 기록한다.
- 기준을 넘었는지는 실측으로 판정한다. 외삽값으로 판정하지 않는다.
