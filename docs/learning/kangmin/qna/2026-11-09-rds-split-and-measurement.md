# ADR 0047의 "RDS 분리"는 무엇이고, 왜 추첨 측정 전에 정해야 하나

## 질문
RDS 분리?

## 짧은 답
- 지금 배포는 EC2 한 대에 앱 8개, PostgreSQL 3개, Redis, Kafka, 관측 도구를 모두 컨테이너로 띄운다(`compose.deploy.yml`).
- "RDS 분리"는 DB를 이 EC2 밖의 AWS 매니지드 DB(RDS for PostgreSQL)로 옮기는 것이다. ADR 0047 결정 3은 서버 중지 기간(11/7~11/12)에 이것(Redis → ElastiCache 포함)을 할지 검토한다고 적었다. 결정자는 안준현이다.
- 측정과의 관계: 분리하면 DB가 앱과 CPU·메모리를 나눠 쓰지 않게 되고, 앱 ↔ DB 사이에 네트워크 왕복이 생긴다. 분리 전에 잰 값은 분리 뒤 구성과 비교할 수 없다. 그래서 측정 전에 할지 안 할지 정해야 한다.

## 자세히

### 1. 선택지
| 안 | 얻는 것 | 대가 |
|---|---|---|
| 지금대로(단일 EC2) | 구성이 단순하다. 지금 바로 측정할 수 있다 | 앱과 DB가 자원을 나눠 써 병목이 섞인다. 인스턴스 장애 시 전체 중단, 백업 없음 |
| DB만 RDS로 | 자원 경쟁이 줄고 백업·장애 조치가 생긴다. 앱은 `DB_URL`만 바꾸면 되는지 확인 필요 | 구성·보안 그룹·데이터 이전 시간, 비용 증가, 앱 ↔ DB 네트워크 지연 추가 |
| DB + Redis(ElastiCache) | 상태 저장소가 모두 EC2 밖으로 나간다 | 비용과 이전 작업이 더 든다. Kafka(MSK)는 비용이 커서 EC2에 남길 가능성이 크다 |

### 2. 추첨 측정에 미치는 영향
- L2-a·L2-b: 결제·예매 DB가 앱과 같은 장비에 있으면 CPU 경합이 처리량에 섞인다. 분리하면 숫자가 달라질 수 있다.
- L1: 로컬 503 원인 후보(Gateway·메모리)와 직접 관계는 약하다. 다만 DB 위치가 바뀌면 응답 시간 분포가 바뀐다.
- 그래서 측정 기록표에 "DB 위치(같은 EC2 / RDS)"를 환경 항목으로 적는다.

### 3. 지금 상태
- 11/9 기준 분리를 했는지, 하기로 했는지 저장소에 기록이 없다(ADR 0047 상태: "검토 예정"). 확인 못 함.
- 강민이 정할 일이 아니다. 준현에게 "하는지, 한다면 언제 끝나는지"만 확인하고 측정 순서를 맞춘다.
