# 튜터가 던진 세 이슈(NTP 시간 동기화, 레이트 리미터, 벌크헤드 격리)는 이 프로젝트 어디에 걸리나

## 질문
튜터가 던진 이슈 NTP 시간 동기화, 레이트 리미터, 벌크헤드 격리 패턴.

## 짧은 답
| 이슈 | 이 프로젝트에서 걸리는 곳 | 지금 상태 |
|---|---|---|
| NTP 시간 동기화 | 오픈 시각·응모 기간·추첨 시각 판정, 토큰 만료, 측정 시각 비교(발생기 ↔ 서버) | 브라우저 시계는 `serverTime`으로 보정(구현·시연 확인). 서버 시계 동기화는 확인 못 함 |
| 레이트 리미터 | 대기열 폴링, 추첨 응모 몰림(L1), 봇·연타 | 미구현. ISE-5(사용자 단위 요청 제한) Backlog, 담당 없음 |
| 벌크헤드 격리 | PG 호출(일반 결제 ↔ 자동결제), DB 커넥션 풀(좌석 선점 ↔ 추첨 워커) | PG는 `pg-approve` 공유(ADR 0039 기준선). DB 풀은 reservation-service 전체가 5개를 공유 |

## 자세히

### 1. NTP 시간 동기화
- 문제: 서버마다 시계가 다르면(clock skew) "오픈했다/안 했다", "응모 마감 전/후", "토큰 만료"를 서버마다 다르게 판정한다. 티켓팅은 초 단위 공정성이 핵심이라 1초 차이도 문제가 된다.
- 지금 구조에서:
  - 배포는 EC2 한 대라 모든 컨테이너가 같은 호스트 시계를 쓴다. 서비스 사이 시계 차이는 구조적으로 작다.
  - 브라우저 시계는 믿지 않는다. 공연 상세·좌석 응답의 `serverTime`으로 보정한다(`frontend/src/api/concerts.ts`, 시연 D-02에서 브라우저를 1시간 빠르게 두고 통과).
  - 남은 위험은 호스트 시계 자체와, 발생기 EC2와 서버의 시계 차이다(측정 시각을 서로 비교할 때).
- 할 일: 배포 서버와 발생기에서 `timedatectl`, `chronyc tracking`(있으면)으로 동기화 여부와 오프셋을 기록한다. AWS는 Amazon Time Sync Service(169.254.169.123)를 제공한다. Ubuntu 24.04 기본 설정이 이것을 쓰는지는 확인 못 함.
- 발표 답: "한 대라 서비스 간 차이는 없고, 사용자 시계는 서버 시각으로 보정한다. 여러 대로 늘리면 NTP(Amazon Time Sync)와 오프셋 경보가 필요하다."

### 2. 레이트 리미터
- 문제: 초당 요청 수를 제한하지 않으면 봇·연타·폴링이 정상 사용자 몫의 자원을 먹는다. 넘치는 요청을 "언제, 어디서, 어떤 응답으로" 거절할지 정하지 않으면 지금 L1처럼 원인 모를 503이 난다.
- 선택지:
  | 위치 | 방식 | 대가 |
  |---|---|---|
  | Gateway | Spring Cloud Gateway `RequestRateLimiter`(Redis 토큰 버킷), 사용자·IP 단위 | 요청마다 Redis 호출 1회 추가 |
  | 서비스 안 | Resilience4j `RateLimiter`(인스턴스 단위) | 인스턴스가 늘면 전체 한도가 같이 늘어남 |
  | 대기열 | 입장 속도 자체가 리미터 역할(일정 속도 입장) | 대기열 뒤 API만 보호 |
- 추첨에서: 응모는 대기열을 거치지 않는다. 그래서 마감 직전 몰림(L1)을 대기열이 막아 주지 않는다. 사용자당 응모는 1건이라(중복 0 확인) 정상 사용자에게 제한이 거의 걸리지 않고, 연타·봇만 429로 빨리 거절할 수 있다.
- 할 일: L1 서버 측정에서 503 위치를 먼저 확인하고, 응모 경로에 사용자 단위 제한을 둘지 정한다. 공통 Gateway 변경이라 contract 이슈다.

### 3. 벌크헤드 격리
- 문제: 여러 작업이 같은 자원(스레드, 커넥션, 외부 호출 자리)을 나눠 쓰면 하나가 몰릴 때 나머지도 같이 죽는다. 배의 격벽처럼 자원을 나눠 한쪽 침수가 번지지 않게 한다.
- PG 호출: 일반 결제와 자동결제가 `pg-approve`(동시 10)를 공유한다(ADR 0039). 개선 후보는 전용 그룹 `pg-billing`(동시 3)과 전용 토픽. 로컬에서는 소비자 동시성 1이라 자동결제가 자리 1개만 써서 간섭보다 속도가 문제로 보였다(L2-a·L2-b로 확인).
- DB 커넥션 풀: reservation-service 안의 좌석 조회·선점·공연·추첨·스케줄러가 HikariCP 5개를 같이 쓴다(ISE-196 검토 때 확인). 추첨 실행 트랜잭션이 0.5\~4.5초 커넥션을 쥔다(3-1절). 일반 판매 중 추첨이 돌면 선점이 커넥션을 기다린다. 이것이 L3 "간섭"의 실체다.
  - 선택지: 추첨 워커용 풀을 따로 두기(DataSource 분리), 추첨 워커 동시 실행 수를 1로 묶기, 추첨을 별도 서비스로 분리(SA 7-1의 분리 조건).
- 발표 답: "격리는 두 층이다. 외부 호출은 Bulkhead로, 내부 DB 자원은 풀·동시성으로. 처음에는 공유로 두고 간섭을 측정으로 확인한 뒤 나눈다."
