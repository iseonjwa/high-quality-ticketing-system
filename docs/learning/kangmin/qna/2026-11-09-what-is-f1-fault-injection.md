# M4 할 일 목록의 F1은 무엇이고 왜 하나

## 질문
"F1이 뭔데" (F1 절차 결정 4개를 안내받던 중)

## 짧은 답
F1은 11/8 M4 할 일 분류(handoff 0-2절)에서 장애 항목에 붙인 번호다. F는 Fault(장애)이고 F1~F5가 있다. F1은 그중 **장애 주입**(fault injection) 항목이다. 배포 서버에서 일부러 장애를 일으키고, 추첨 자동결제가 설계대로 복구되는지 확인한다. 범위는 Linear ISE-94이고, 절차 초안은 `docs/design/lottery/f1-fault-injection.md`에 있다.

## 자세히

### F 번호 목록 (handoff 0-2절)
| ID | 내용 | 처리 |
|---|---|---|
| **F1** | 장애 주입: 결제 서버 강제 종료, outbox 릴레이(Kafka) 정지, 복구 뒤 결제 1회 | 서버에서 직접 실행(11/11) |
| F2 | Mock PG 재기동으로 빌링키가 사라지면 당첨자 책임 실패로 처리되는 문제 | 실패 사유 분리 코드 |
| F3 | 로컬 L1에서 400건/초부터 나온 503 | 서버 측정으로 거절 위치 확인 |
| F4 | 경보가 실제 슬랙까지 가는지 | F1과 함께 확인 |
| F5 | 실패 표의 경합 행, 워커 중 종료 | 발표 예상 질문으로 파악만 |

L1·L2·L3(Load, 부하 측정)과는 번호 체계가 다르다. L은 "얼마나 버티나", F는 "깨졌을 때 바르게 복구되나"를 본다.

### F1의 세 장면
| ID | 일으키는 장애 | 증명하려는 것 |
|---|---|---|
| F1-a | 자동결제가 몰릴 때 결제 서버를 `docker kill`(SIGKILL) | PG에 보내지 않은 결제는 `DECLINED(NOT_SENT)`로 닫히고 추첨이 같은 당첨자에게 1회 재시도한다. PG가 받은 결제는 `APPROVED`로 수렴한다. 이중 승인이 없다 |
| F1-b | Kafka 정지로 결제 요청 발행을 막음 | 결제 요청이 나가지 못해 선점이 만료 시각에 이르면 1회 30분 연장된다 |
| F1-c | Kafka 복구 | 밀린 요청이 발행되고 예매당 결제가 1건만 생겨 확정된다 |

함께 장애 시작 → 슬랙 firing → 복구 → resolved 시각을 적어 탐지·복구 시간을 숫자로 남긴다(F4 겸용).

### 왜 하나
- 단위·통합 테스트는 "이 코드가 이렇게 동작한다"를 증명한다. 장애 주입은 "실제 배포 환경(컨테이너, Kafka, 경보 파이프라인)이 합쳐졌을 때도 그렇다"를 증명한다.
- 이 프로젝트의 핵심 주장인 SAGA·outbox·멱등은 정상 상황에서는 차이가 보이지 않는다. 장애가 나야 설계가 일을 한다.
- 발제의 장애 대응 요구와 발표의 "무엇을 증명하는가" 장면의 원천이 된다.

## 이 프로젝트에서는
- 절차 초안: `docs/design/lottery/f1-fault-injection.md` (미커밋, 결정 4개 남음)
- 근거 설계: `docs/design/lottery/details.md` 6절 실패 표, ADR 0018(결제 처리 순서), ADR 0038(실패 사유별 처리)
- 같은 경로의 결정적 테스트: `Ft3RestartScenarioTest`(결제), `LotteryAssignmentTest`의 `NOT_SENT` 재시도 테스트(추첨)

## 면접 포인트
- "장애 대응을 어떻게 검증했나": 테스트로 결정적 경로를 고정하고, 배포 서버에서 프로세스 강제 종료·브로커 정지를 주입해 DB 상태 수렴, PG 승인 수, 경보 도착 시각을 확인했다.
- "카오스 엔지니어링과 무엇이 다른가": 운영 트래픽에서 무작위로 장애를 내는 것이 아니라, 실패 표의 특정 행을 골라 가설(기대 결과)을 먼저 쓰고 한 번씩 주입하는 계획된 장애 주입이다.
