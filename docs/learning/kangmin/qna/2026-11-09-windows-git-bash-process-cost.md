# 같은 셸 스크립트가 Windows Git Bash에서 왜 훨씬 느린가(프로세스 생성 비용)

## 질문
기록 검사가 93초에서 3.6초가 됐다면 기존 검증 실행 시간이 25배 빨라졌다는 뜻인가. 토큰 사용량과는 어떤 관계인가.

## 짧은 답
- 그렇다. 검사 한 번이 약 25배 빨라졌다(92.8초 → 3.6초, 3회 중앙값). 이 검사는 에이전트가 응답을 끝낼 때마다(훅), 그리고 PR마다(CI) 돈다. 그래서 측정이 아닌 작업에서도 매번 효과가 난다.
- 토큰과는 거의 관계없다. 토큰은 에이전트가 읽는 출력의 양과 호출 수로 정해진다(ISE-219, 영은님 실측). 이번 개선은 시간을 줄인 것이다.
- 느렸던 이유는 계산이 아니라 프로세스를 띄우는 횟수였다.

## 자세히

### 0. 기록 검사(`records-check.sh`)는 무엇인가 (추가 질문)
- 앱 코드가 아니라 **팀 기록 문서**가 정해진 형식을 지키는지 보는 검사 스크립트다. 대상은 `docs/ai-judgments/`(AI 판단 기록)와 `docs/learning/`(학습 노트)이다. AGENTS.md 대전제 2·3(질문과 AI 판단은 모두 기록한다)을 사람이 매번 확인하지 않게 하려고 만들었다.
- 보는 것:
  | 항목 | 예 |
  |---|---|
  | 사람별 폴더와 파일 이름 규칙 | `docs/ai-judgments/<이름>/YYYY-MM-DD-<slug>.md` |
  | 필수 머리말 | `title`, `date`, `judge`, `verdict` 등 9개. `verdict`는 수용·부분 수용·거부·보류 중 하나 |
  | 색인 링크 | 새 기록이 사람별 README, 일지, 공통 표(`shared: 예`), 학습 노트 색인에 올라가 있는지 |
  | 비밀값 흔적 | `ghp_`로 시작하는 GitHub 토큰, AWS 키, 개인 키 같은 문자열 |
- 보지 못하는 것: 기록을 **남겼는지 자체**(내용)는 모른다. 구조만 본다.
- 언제 도는가:
  | 시점 | 방식 |
  |---|---|
  | 에이전트가 응답을 끝낼 때마다 | Claude Code `Stop` 훅(`.claude/settings.json`, `--hook`). 어긋나면 에이전트가 한 번 더 이어서 고친다 |
  | PR과 `dev`·`main` push마다 | GitHub Actions `records-check`. PR 머지에 필요한 필수 검사다 |
  | 손으로 | `bash script/records-check.sh` |
- 그래서 느리면 영향이 크다. 에이전트가 응답을 끝낼 때마다 93초를 기다리거나, 30초 시한에 걸려 검사가 잘렸다.

### 1. 프로세스 생성 비용
| 환경 | 프로세스 하나 띄우는 비용 | 근거 |
|---|---|---|
| Windows Git Bash | 약 26ms | `/usr/bin/true` 200번 평균(2026-11-09 이 PC) |
| Linux | 대개 1ms 안팎 | 일반적인 값. 이 프로젝트에서 재지 않았다 |

Git Bash는 Windows 위에서 Unix처럼 보이게 만드는 층(MSYS2)이라, 새 프로세스를 만들 때 Linux의 `fork`보다 일이 훨씬 많다.

### 2. 원래 스크립트가 띄운 프로세스 수 (추정)
| 검사 | 방식 | 대략 횟수 |
|---|---|---|
| 판단 기록 머리말 | 파일 138개 × 키마다 `awk`(약 12번) | 약 1,700 |
| 비밀값 | 파일 약 1,800개 × `grep` 한 번 | 약 1,800 |
| 합계 | | 약 3,500 × 26ms ≈ 90초 |

이 계산은 추정이고, 측정한 92.8초와 크기가 맞는다.

### 3. 바꾼 방식
| 검사 | 새 방식 | 횟수 |
|---|---|---|
| 머리말 | 파일당 `awk` 한 번으로 키 전부 | 약 140 |
| 색인 | 한 번 읽고 bash 문자열 검색 | 몇 번 |
| 비밀값 | `git grep --untracked` 한 번 | 1 |

### 4. 결과가 같다는 것을 어떻게 보였나 (변이 테스트)
- 기록 구조를 일부러 망가뜨린 입력 31가지를 만들었다. 머리말 없음, 필수 키 빠짐, 색인 누락, 비밀값 같은 경우다.
- 각 입력에서 원래 스크립트와 새 스크립트의 출력과 종료 코드를 바이트 단위로 비교했다.
- 30가지가 같았다. 1가지는 원래 스크립트가 한글 파일 이름의 비밀값을 놓치던 누락이 고쳐진 것이었다.
- 고친 에이전트가 아닌 다른 에이전트가 저장소 밖 복제본에서 검증했다.

### 5. 고르는 기준
- Windows에서 도는 셸 스크립트는 반복문 안에서 외부 명령(`grep`, `awk`, `sed`, `$(...)`)을 띄우지 않는다.
- 여러 파일은 한 번에 처리하는 도구로 본다(`git grep`, 파일 목록을 받는 `awk`).
- 검사 도구를 고칠 때는 성능 숫자와 함께 "결과가 같다"는 증거(변이 비교)를 남긴다.
