# Resilience4j 서킷 브레이커와 벌크헤드 설정 키는 각각 무엇을 정하나

## 질문
Gateway `auth-redis` 권장 설정 표에서 창 종류, 최소 호출 수 같은 키가 정확히 무엇인지 하나씩 자세히 알려 달라고 했다.

## 짧은 답
서킷 브레이커(circuit breaker)는 "최근 호출 기록"을 보고 실패나 느림이 기준 비율을 넘으면 호출을 막는다. 키는 네 묶음이다.
1. 무엇을 최근 기록으로 볼지: 창 종류, 창 크기
2. 언제부터 판정할지: 최소 호출 수
3. 무엇을 나쁘게 볼지: 실패율 기준, 느린 호출 시간·비율 기준
4. 막은 뒤 어떻게 다시 열지: 열림 시간, 반열림 시험 호출 수

벌크헤드(bulkhead)는 별개 장치로 "동시에 몇 개까지 실행할지"만 정한다.

## 설명

### 상태 세 가지
| 상태 | 호출 | 다음 상태로 가는 조건 |
|---|---|---|
| CLOSED(닫힘, 정상) | 모두 실행하고 결과를 창에 기록 | 창의 실패율이나 느린 호출 비율이 기준 이상이면 OPEN |
| OPEN(열림, 차단) | 실행하지 않고 즉시 `CallNotPermittedException` | 열림 시간이 지나면 HALF_OPEN |
| HALF_OPEN(반열림, 시험) | 정해진 수만 실행, 나머지는 즉시 거절 | 시험 호출 결과 비율이 기준 이상이면 OPEN, 미만이면 CLOSED |

### 1. 창 종류 `sliding-window-type`, 창 크기 `sliding-window-size`
"최근"을 무엇으로 셀지 정한다.

| 종류 | 창 크기의 단위 | 동작 | 1,000/s에서 창 20 |
|---|---|---|---|
| `COUNT_BASED`(건수, 기본값) | 건 | 마지막 N건만 기억한다. 새 호출이 오면 가장 오래된 1건이 빠진다 | 마지막 20건 = 0.02초 분량 |
| `TIME_BASED`(시간) | 초 | 마지막 N초의 호출을 1초 단위 칸으로 모아 합친다 | 마지막 10초 = 약 10,000건 |

- 건수 창은 트래픽이 많을수록 창이 덮는 시간이 짧아진다. 0.02초 동안 GC 멈춤 한 번이나 CPU 순간 포화가 있으면 그 20건이 한꺼번에 느려지고, 그것만으로 열린다.
- 시간 창은 트래픽과 상관없이 "최근 10초의 평균"을 본다. 짧은 튐은 평균에 묻히고, 몇 초 넘게 이어지는 문제만 기준을 넘긴다.
- 대가: 시간 창은 문제가 생긴 뒤 비율이 기준을 넘을 때까지 시간이 걸린다. 10초 창에서 그때까지 정상이던 호출이 섞여 있으므로, 실패율 50%가 되려면 장애가 대략 몇 초 이어져야 한다(정확한 시간은 확인 못 함, 트래픽 모양에 따라 다름).

### 2. 최소 호출 수 `minimum-number-of-calls`
창 안에 이 수만큼 호출이 쌓이기 전에는 비율을 계산하지 않는다. 표본이 너무 적을 때 나오는 우연한 비율로 열리지 않게 막는 장치다.

| 예 | 결과 |
|---|---|
| 최소 20, 창에 10건이 있고 10건 모두 실패 | 판정하지 않음(열리지 않음) |
| 최소 20, 창에 20건, 10건 실패 | 실패율 50% → 기준 50% 이상이라 OPEN |
| 시간 창 10초·최소 500, 초당 30건(10초에 300건) | 300 < 500이라 Redis가 죽어도 판정하지 않음 |
| 시간 창 10초·최소 500, 초당 1,000건 | 10초에 약 10,000건이라 늘 판정함 |

- 시간 창에서는 "창 시간 × 초당 호출 수 ≥ 최소 호출 수"일 때만 차단기가 일한다. 10초·500건이면 초당 50건이 경계다(계산값).
- 건수 창에서 최소 호출 수가 창 크기보다 크면 사실상 창 크기가 최소가 된다. 지금 설정(창 20, 최소 20)은 "20건이 꽉 차야 판정"이다.

### 3. 무엇을 나쁘게 볼지
| 키 | 지금 | 뜻 |
|---|---|---|
| `failure-rate-threshold` | 50 | 창 안 실패 호출 비율이 이 값(%) **이상**이면 연다. 실패는 기본적으로 모든 예외다. 시한 초과, 연결 오류, 그리고 안쪽 벌크헤드의 거절(`BulkheadFullException`)도 실패로 센다 |
| `slow-call-duration-threshold` | 50ms | 이 시간보다 오래 걸린 호출을 "느린 호출"로 센다. 성공했든 실패했든 시간만 본다 |
| `slow-call-rate-threshold` | 50 | 창 안 느린 호출 비율이 이 값 이상이면 연다 |

- 두 규칙은 따로 판정해 둘 중 하나만 넘어도 연다.
- `auth-redis`는 Redis 조회 시한이 100ms다. 그래서 느린 호출 기준을 100ms로 두면 100ms를 넘는 호출은 이미 시한 초과로 실패가 된다. 느린 호출 규칙이 걸릴 호출이 없어진다. 느림을 따로 감지하려면 시한보다 작은 값(예: 80ms)이어야 한다.

### 4. 막은 뒤 다시 여는 방법
| 키 | 지금 | 뜻 |
|---|---|---|
| `wait-duration-in-open-state` | 10s | OPEN으로 머무는 시간이다. 그동안 모든 호출을 즉시 거절한다. 지나면 HALF_OPEN이 된다 |
| `permitted-number-of-calls-in-half-open-state` | 5 | HALF_OPEN에서 실제로 실행해 보는 시험 호출 수다. 그동안 다른 호출은 계속 즉시 거절한다. 시험 호출이 모두 끝나면 그 결과만으로 비율을 계산한다 |

- 시험 5건, 기준 50%이면 3건(60%)이 느리거나 실패하면 다시 열고, 2건(40%)이면 닫는다. 표본이 작아 우연에 크게 흔들린다. 20건이면 같은 50% 판정이 더 안정된다.
- 열림 시간이 짧으면 거절 구간은 줄지만 부하가 원인일 때 열림 → 반열림 → 열림을 자주 반복할 수 있다. 503의 `Retry-After`도 열림 시간과 맞춰야 쓸데없는 재시도가 줄어든다(ISE-230 영은 코멘트).

### 5. 벌크헤드 `max-concurrent-calls`
- 같은 이름(`auth-redis`)의 Redis 조회를 동시에 몇 개까지 실행할지 정한다. 세마포어 방식이고, 자리가 없으면 기다리지 않고(대기 0) 즉시 `BulkheadFullException`을 낸다.
- 필요한 자리 수는 리틀의 법칙(Little's law)으로 어림한다: 동시 실행 수 = 초당 호출 수 × 호출 한 건 시간. 1,000/s × 1ms = 1자리, 1,000/s × 25ms = 25자리.
- 즉 평소에는 25로 충분하고, 서버 CPU가 차서 한 건이 길어질 때 자리가 모자란다. Spring Cloud CircuitBreaker에서는 벌크헤드가 차단기 안쪽이라 이 거절이 실패율에 더해져 차단기까지 연다.

### 지금 값과 권장 값
| 키 | 지금 | 권장 |
|---|---|---|
| 창 종류·크기 | 건수 20 | 시간 10초 |
| 최소 호출 수 | 20 | 500 |
| 실패율 | 50% | 50% |
| 느린 호출 | 50ms·50% | 100ms·80%(측정 E), 80ms는 재측정 필요 |
| 열림 시간 | 10s | 5s(영은 제안대로 10초와 비교 측정 뒤 확정) |
| 반열림 시험 호출 | 5 | 20 |
| 벌크헤드 | 25 | 100 |
