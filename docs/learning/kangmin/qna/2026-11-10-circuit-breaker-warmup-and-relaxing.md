# 웜업과 단계 크기는 결과를 바꾸나, auth-redis 서킷 브레이커는 어떻게 완화하고 Gateway는 어떻게 개선하나

## 질문
11/10 오후 L1 응모 몰림 병목 탐색(ISE-94) 중 나온 질문 세 개다.
1. 웜업(warm-up, 본 측정 전에 낮은 부하로 서버를 데우는 것)을 하고 진행하면 결과가 달라질까? 초당 요청을 더 잘게 쪼개 단계를 나누면?
2. 차단기(서킷 브레이커)를 크게 완화한다는 게 어떻게 한다는 것인가?
3. auth-redis 느린 응답 기준을 확 늘려 두고 조금씩 낮춰야 하나? Gateway는 어떻게 개선해야 하나?

## 짧은 답
- 웜업은 결과를 바꿨다. 콜드 시작 초당 800건은 거절 55%였고, 웜업 뒤 초당 800건은 거절 0건이었다. 단계를 잘게 쪼개면 한도 자체는 그대로이고, 포화점(saturation point, 처리량이 더 늘지 않고 실패나 지연이 급증하기 시작하는 부하)이 어디인지를 더 정확히 짚는다. 웜업 뒤 30초 단계로 재서 포화점이 초당 800~1,000 사이임을 찾았다.
- 완화는 "판정 창을 넓히고 느린 호출 판정을 사실상 끄는 것"이다. 건수 기반 20건 창을 시간 기반 10초 창(최소 1,000건)으로 바꾸고, 느린 호출 기준을 50ms에서 1초로 올렸다. 실패율 50%는 남겼다.
- "크게 늘린 뒤 조금씩 낮추기"보다 측정에서 기준을 정하는 편이 낫다. 목표 부하에서 잰 p99에 여유를 곱하되 Redis 명령 시한 100ms보다 작게 잡는다. 개선 후보는 기준 재설정, fail-open, 로컬 캐시, 용량 네 가지이고 각각 감수할 점이 다르다.

## 자세히

### 1. 웜업과 단계 크기 (질문 1)
수치는 `docs/design/lottery/numbers-and-measurement.md` 3-3절 L1, 3-4절 C1·C2에서 가져왔다.

| 측정 | 시작 상태 | 단계 | 초당 800 | 초당 1,000 | 초당 1,200 |
|---|---|---|---|---|---|
| 3-3 L1 | 100 → 200 → 400 → 800 차례로 올림 | 65초 | 503 0건, p95 15.8ms | — | — |
| C1 | 콜드 시작(800부터) | 65초 | `auth_unavailable` 55% | — | — |
| C2 | 웜업 100~400 뒤 | 30초 | 거절 0%, p95 17.4ms | 거절 19%, p95 46.5ms | 거절 83% |

- 웜업이 바꾸는 것: JVM은 처음 도는 코드를 해석 실행하다가 자주 쓰는 코드를 JIT 컴파일한다. 연결 풀과 Netty 이벤트 루프도 처음 부하에서 자리를 잡는다. 식은 상태에서 초당 800건을 바로 받으면 이 준비 시간 동안 응답이 느려진다.
- C1에서는 시작 15초 뒤 `auth-redis` 서킷 브레이커가 느린 호출 100%로 열렸고, 그 뒤 열림을 반복했다. reservation-service CPU는 2%였다. 거절은 요청이 서비스에 닿기 전 Gateway에서 났다.
- 다만 C1과 3-3 L1의 차이가 콜드 시작 때문인지 단계 길이 때문인지는 따로 떼어 재지 않았다. 원인 분리는 확인 못 함이다.
- 단계를 잘게 쪼개는 일의 효과: 서버 한도를 올리지는 않는다. 65초 단계(800 → 1600)로는 "800은 되고 1600은 안 된다"까지만 말할 수 있다. 30초 단계(800 → 1000 → 1200)로 재자 "800은 거절 0%, 1000에서 19%"라는 포화점이 나왔다.
- 감수한 점: 단계가 짧을수록 한 단계의 표본이 줄어 p99 같은 꼬리 값이 흔들린다. 30초 단계는 상승 5초를 빼면 25초 분량이다. 실무에서는 포화점 근처만 잘게 쪼개고 그 단계는 길게 잡는다.

### 2. 차단기가 왜 열렸나 (질문 2의 배경)
- 대상 코드: `GatewayAuthenticationFilter.isRevoked`(`gateway/src/main/java/com/iseonjwa/gateway/security/GatewayAuthenticationFilter.java:89-92`)가 로그인 요청마다 `redis.hasKey("auth:blacklist:<jti>")`를 부른다. 조회에는 `.timeout(REDIS_TIMEOUT)`(29행, 100ms)이 걸리고, `redisBreaker.run(lookup)`으로 서킷 브레이커에 감싼다(91행). 브레이커 이름은 `breakers.create("auth-redis")`(41행)다. 어떤 오류든 `onErrorMap`에서 `AuthDependencyUnavailable`로 바뀌어 503 `SERVICE_UNAVAILABLE`이 된다(84-86행).
- 설정: `config-repo/gateway.yml:58-65`
  | 키 | 값 | 뜻 |
  |---|---|---|
  | `sliding-window-size` | 20 | 최근 20건으로 판정한다. `sliding-window-type`이 없어 건수 기반 슬라이딩 윈도우(sliding window)다 |
  | `minimum-number-of-calls` | 20 | 20건이 쌓여야 판정을 시작한다 |
  | `failure-rate-threshold` | 50 | 실패가 50% 이상이면 연다 |
  | `slow-call-duration-threshold` | 50ms | 50ms를 넘으면 느린 호출로 센다 |
  | `slow-call-rate-threshold` | 50 | 느린 호출이 50% 이상이면 연다 |
  | `wait-duration-in-open-state` | 10s | 열리면 10초 동안 모든 호출을 거절한다 |
  | `permitted-number-of-calls-in-half-open-state` | 5 | 반열림(half-open) 때 시험 호출 5건 |
- 20건 창은 초당 1,000건에서 0.02초 분량이다(계산값). 0.02초 사이 순간 지연으로 50ms를 넘는 호출이 10건만 생겨도 10초 동안 인증 요청 전체가 503이 된다.
- 그 뒤 진동이 생긴다. 10초 뒤 반열림으로 바뀌어 5건을 시험한다. 그동안 밀린 요청이 한꺼번에 들어와 시험 호출도 느리면 바로 다시 연다(재열림). 열림 → 반열림 → 재열림이 되풀이되어 부하가 그대로인 동안 거의 계속 거절한다. C1의 "열림 반복"이 이 모양이다.
- C2에서 Redis 조회 평균은 0.3ms에서 열리기 직전 1.9ms로 올랐고, Redis 컨테이너 CPU는 8%였다. 같은 단계에서 gateway CPU는 119%였다. 느린 호출이 Redis 자체 지연인지 Gateway 쪽 대기(CPU 포화 등)인지는 확인 못 함이다.

### 3. 크게 완화한다는 것 (질문 2)
선택지:

| 안 | 바꾸는 것 | 장점 | 단점 |
|---|---|---|---|
| 창만 키움 | 건수 창 20 → 수백 건 | 순간 지연에 덜 민감 | 부하가 낮을 때 판정까지 오래 걸린다 |
| 시간 창으로 바꿈 | 10초 시간 창, 최소 호출 1,000건 | 부하가 변해도 같은 시간 분량으로 판정 | 실제 장애를 감지하는 데 최대 10초 안팎이 걸린다 |
| 느린 호출 판정 끔 | 느린 호출 기준 50ms → 1초 | 순간 지연으로는 열리지 않는다 | 느리지만 죽지 않은 Redis를 차단기가 못 잡는다 |
| 브레이커 제거 | 브레이커를 쓰지 않음 | 오탐이 없다 | Redis 장애 때 요청마다 100ms 시한까지 기다린다 |

- 고른 것(C3): 시간 창 10초 + 최소 1,000건 + 느린 호출 1초 + 실패율 50% 유지. 적용 여부는 `buffered_calls` 1,184(20보다 큼)로 확인했다.
- 느린 호출만 1초로 끈 이유: 조회에는 100ms 시한이 걸려 있다. 100ms를 넘는 조회는 시한 초과 오류로 끝나 실패로 세어진다. 그러니 1초 기준의 느린 호출은 생길 수 없고, 사실상 느린 호출 판정만 끈 셈이다.
- 실패율을 남긴 이유: Redis가 실제로 죽거나 시한을 넘기면 실패로 세어져 차단기가 연다. 장애 때 요청마다 100ms씩 기다리는 대신 빨리 거절하는 차단기 본래 역할은 그대로 둔다.
- 감수한 점: 시간 창이 10초라 실제 장애를 늦게 감지한다. 또 오탐을 없애자 다음 한계가 드러났다. C3의 초당 1,200 단계 거절은 4.8%로 C2의 83%에서 크게 줄었지만, 인증 벌크헤드(bulkhead, 동시 실행 수 제한) 25의 남은 자리가 0이었고 reservation DB 풀 5의 대기가 최대 약 195였다.

### 4. 기준은 어떻게 정하나 (질문 3 앞부분)
- "크게 늘려 두고 조금씩 낮추기"는 한 번에 하나씩 바꾸면 쓸 수 있다. 다만 회차마다 Gateway를 다시 만들어야 하고(환경변수는 컨테이너를 새로 만들어야 들어간다), 어느 값에서 멈출지 근거가 없다.
- 측정 기반으로 정하는 순서:
  1. 차단기를 완화한 상태로 목표 부하(예: 초당 1,000)에서 `auth-redis` 호출 시간 분포를 잰다.
  2. 느린 호출 기준 = 목표 부하의 p99 × 여유(예: 2~3배). 정상 부하에서는 열리지 않고, 평소보다 몇 배 느려지면 연다.
  3. 이 값은 Redis 명령 시한 100ms(`config-repo/application.yml:51` `timeout: 100ms`, 코드 상수 `REDIS_TIMEOUT` 100ms)보다 작아야 한다. 같거나 크면 느린 호출이 되기 전에 시한 초과 실패가 되어 느린 호출 판정이 의미를 잃는다.
  4. 창은 시간 기반으로, 최소 호출 수는 목표 부하에서 몇 초 분량으로 잡는다.
- 적용 예(E): 시간 창 10초, 최소 500건, 느린 호출 100ms·80%, 열림 5초, 반열림 20건. E의 느린 호출 100ms는 시한 100ms와 같은 값이라 3번 원칙대로라면 더 낮춰야 한다. 목표 부하에서 잰 `auth-redis` p99 값은 이번 기록에 없다(확인 못 함).

### 5. C3·D·E 결과 (질문 3 뒷부분의 근거)
모두 측정 모드 안 임시 덮어쓰기였고, 04:13 측정 모드 off로 운영 설정에 되돌렸다. 단계는 웜업 100·200·400 뒤 각 30초다.

| 측정 | 차단기 | 인증 벌크헤드 | reservation Hikari | 초당 1,200 p95 | p95 300ms 이하 한도 | 차단기 열림 |
|---|---|---|---|---|---|---|
| C2 | 원래 설정 | 25 | 5 | — (거절 83%) | 문서에 값 없음(초당 800 거절 0%, 1,000 거절 19%) | 1000 단계 끝에 열림 |
| C3 | 완화 | 25 | 5 | 367ms(거절 4.8%) | 약 초당 800 | — |
| D | 완화 | 100 | 20 | 238ms(거절 0.07%) | 약 초당 1,200 | 안 열림 |
| E | 측정 기반 | 100 | 20 | 339ms(거절 0.5%) | 약 초당 1,000 | 안 열림(오탐 없음) |

- D는 처리량이 약 초당 1,600에서 정체했다. 서버 vmstat CPU가 100%였고, 4 vCPU를 모든 컨테이너가 나눠 쓴다. 다음 한계는 서버 CPU로 보인다(추정).
- E는 D보다 초당 1,200의 p95가 높다(339ms 대 238ms). E는 차단기 설정만 D와 다르다. 이 차이가 차단기 설정 때문인지 측정 사이 변동인지는 확인 못 함이다. E의 웜업 구간은 앞 추첨의 DB 처리와 겹쳤다(Postgres CPU 200% 이상). 가리려면 같은 설정으로 D와 E를 번갈아 두 번 이상 재야 한다.
- E의 초당 1,200 이상 거절은 차단기가 아니라 벌크헤드가 넘친 요청을 바로 거절한 것이다(초당 1,400에서 남은 자리 0).

### 6. Gateway 개선 후보
| 후보 | 하는 일 | 얻는 것 | 감수할 점 |
|---|---|---|---|
| A 기준 재설정 | 4절 방식으로 차단기 기준을 정하고, 벌크헤드를 100으로 올려 `config-repo/gateway.yml`에 반영 | 코드 변경 없음. E에서 오탐 0 | 시간 창이 길어 실제 Redis 장애를 늦게 감지한다. 벌크헤드를 올리면 Gateway CPU를 더 쓴다. Gateway 공통 설정이라 `contract` 대상이다 |
| B fail-open | Redis를 확인할 수 없으면 거절 대신 통과시킨다 | Redis 장애가 인증 전체 장애로 번지지 않는다 | 로그아웃한 토큰(블랙리스트)을 그동안 막지 못한다. 보안 판단이 필요한 설계 결정이다 |
| C 로컬 캐시 | 블랙리스트 조회 결과를 Gateway 메모리에 짧게 둔다 | Redis 호출 수가 준다 | 로그아웃이 캐시 시간만큼 늦게 반영된다. Gateway가 여러 대면 인스턴스마다 다르게 보인다 |
| D 용량 | Gateway를 다른 장비로 분리하거나 장비를 키운다 | 서버 CPU 100% 정체(약 초당 1,600)를 푼다 | 비용과 배포 구성이 늘어난다. ADR 0047(EC2 한 대로 시작하고 매니지드 분리 검토)과 함께 본다 |

- 순서 제안: A는 측정으로 효과를 본 설정이라 먼저 할 수 있다. B·C는 보안과 일관성의 대가가 있어 팀 결정(ADR)이 필요하다. D는 A 이후에도 목표 부하가 모자랄 때 본다. 어느 것을 할지는 강민과 Gateway 담당이 정한다.

### 7. SPRING_APPLICATION_JSON 덮어쓰기와 겹쳐 쓰기 주의
- 측정 때는 `config-repo`를 고치지 않고 Gateway 컨테이너 환경변수 `SPRING_APPLICATION_JSON`으로 값을 덮었다. 키 `auth-redis`에 하이픈이 있어 일반 환경변수 이름으로는 맵 키를 맞추기 어렵기 때문이다(`loadtest/deploy/compose.gateway-bulkhead.yml` 12행 주석).
- config 서버 값보다 이기는가: config 서버 값은 일반 config data로 들어가고 `SPRING_APPLICATION_JSON`보다 순위가 낮다(바이트코드 확인, [Gateway 기본 벌크헤드 노트](2026-11-09-gateway-default-bulkhead.md) 4절). C3에서 `buffered_calls` 1,184로 config-repo의 20건 창 대신 덮은 값이 적용된 것을 확인했다.
- 주의 1(두 compose 파일이 같은 키를 쓸 때): `measure-mode.sh on`은 덮어쓰기 파일을 여러 개 받아 준 순서대로 `-f`로 얹는다(`script/loadtest/measure-mode.sh:186-188`, 205행). 기본으로 얹는 `loadtest/deploy/compose.measure.yml`에는 이 키가 없다(검색 확인). Compose는 `environment`를 키별로 합치고 같은 키는 뒤 파일 값으로 바꾼다(Docker Compose 병합 규칙. 이 저장소에서 실행해 확인하지 않음). `SPRING_APPLICATION_JSON`은 문자열 하나라 JSON 안쪽이 합쳐지지 않는다. 벌크헤드 파일과 차단기 파일이 둘 다 이 키를 쓰면 뒤 파일의 JSON만 남고 앞 파일 설정은 통째로 사라진다. 그래서 한 측정 조건의 값은 JSON 하나에 모아 쓴다.
- 주의 2(같은 키를 config-repo와 JSON이 둘 다 쓸 때): `compose.gateway-bulkhead.yml` 주석은 "config-repo에 없는 키만 바꾸므로 겹치지 않는다"고 적었다. 차단기 키는 config-repo에 이미 있어 이 설명이 맞지 않는다. 덮은 값이 이기는 것은 C3 지표로 확인했지만, config-repo의 `slow-call-duration-threshold`(케밥 표기)와 JSON의 `slowCallDurationThreshold`(카멜 표기)처럼 표기를 달리 쓸 때도 같은지는 확인 못 함이다. 켠 뒤 지표로 값이 바뀌었는지 먼저 보고 잰다.
- 주의 3: 측정 기록표에는 덮어쓴 JSON 전체를 그대로 적는다. 저장소 밖 파일로 덮은 값은 커밋 해시로 재현할 수 없기 때문이다.

### 8. 면접 포인트
- "서킷 브레이커가 정상 부하에서 열렸다면 무엇을 보나": 창 크기를 시간 분량으로 환산하고(20건 = 초당 1,000에서 0.02초), 느린 호출 기준과 시한의 관계, 열림 → 반열림 → 재열림 진동을 본다.
- "차단기를 완화하니 무엇이 드러났나": 다음 병목(벌크헤드 25, DB 풀 5, 서버 CPU)이 차례로 드러났다. 한 번에 하나만 바꿔야 어느 설정의 효과인지 말할 수 있다.
