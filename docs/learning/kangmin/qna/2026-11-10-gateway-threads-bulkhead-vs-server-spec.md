# Gateway 스레드·벌크헤드·연결 풀 수치는 배포 서버 사양을 고려해 정한 값인가

## 질문
지금 바뀐 기준(차단기 완화·벌크헤드 100·Hikari 20)으로 테스트하면 Gateway가 견디지 못하고 서버 CPU 100%로 무너진다. 사양이 부족해서인 것 같은데, 그건 그렇다 치고, 스레드 풀과 벌크헤드가 어떻게 되어 있는지 고려해서 구성한 것인가? 서버 사양을 분석하고 고려한 수치가 맞나?

## 짧은 답
- **아니다(일부만 근거가 있다).** 서버 사양(4 vCPU)을 보고 정한 값은 하나도 없다. 대부분 라이브러리 기본값이고, 기본값들이 JVM이 본 CPU 수(4)를 따라 자동으로 정해졌을 뿐이다.
- 측정으로 근거가 생긴 값은 차단기 기준·벌크헤드 100·reservation Hikari 20뿐이고, 이것도 아직 측정 모드 안의 임시 값이다. 운영 설정의 reservation·user Hikari 5는 초기 통합 커밋에서 들어온 값으로 근거 기록이 없고, SA 9-4의 "서비스당 20"과도 다르다.
- 컨테이너 21개(일회성 `kafka-init` 제외)가 CPU 제한 없이 4 vCPU를 나눠 쓴다. JVM 11개가 각자 "CPU 4개짜리 장비를 혼자 쓴다"고 보고 스레드 수를 정한다.
- 벌크헤드는 스레드가 아니라 동시 실행 개수를 세는 세마포어(허가 카운터)다. 숫자를 키워도 Gateway 스레드는 늘지 않는다. CPU에 주는 영향은 간접적이다. 거절하던 요청을 받아들여 뒤쪽(reservation·Postgres)까지 보내므로 같은 장비의 전체 일이 늘어난다.
- D와 E의 p95 차이(1,200/s에서 238ms 대 339ms)는 벌크헤드로 설명할 수 없다. 둘 다 벌크헤드 100·Hikari 20이고 차단기 설정만 다르며, 차단기는 둘 다 열리지 않았다. 각 1회 측정이고 E는 웜업이 앞 추첨의 DB 처리와 겹쳤다. 원인은 확인 못 함이다.

## 이 노트의 질문 순서
2026-11-10 하루 동안 한 주제로 이어서 물은 질문을 절마다 정리했다. 앞 절의 결론을 다음 질문이 이어받는다.

| 절 | 질문 | 한 줄 결론 |
|---|---|---|
| 1~5 | 스레드 풀·벌크헤드·연결 풀이 서버 사양을 고려한 값인가 | 일부. 메모리만 계산했고 CPU·스레드·연결 수는 기본값이거나 측정에서 막힌 곳을 올린 값이다 |
| 6 | 벌크헤드가 너무 커서 감당 못 할 부하까지 받다 터지는가 | 방향은 맞다. 다만 줄 서는 곳은 벌크헤드 하나가 아니라 여러 곳이다 |
| 7 | 대기열 진입의 Tomcat 스레드 1개가 병목인가 | 직접 원인일 가능성은 낮다. 첫 병목은 Gateway였다 |
| 8 | 지금 사양에서 초당 몇 건이 괜찮은가 | 통과선은 진입 1,000/s·응모 800/s, 여유를 두면 그 60~70% |
| 9 | 왜 CPU·메모리가 터지나, 대기 중 Gateway 스레드 풀이 차나 | 대기자는 자원을 붙잡지 않는다. 처리 중인 요청이 불어나는 되먹임과 재시도 폭풍이 원인이다 |
| 10 | 차단기가 재는 시간에 Gateway 쪽 대기가 섞이나 | 섞인다. Lettuce 연결 하나를 공유해 머리 막힘이 생길 수 있다 |

| 13 | 시한을 재는 주체가 Gateway인가, SLOWLOG가 응답에 실려 오나 | Gateway다. SLOWLOG는 Redis 안에만 남는다 |
| 14 | 느린 호출 100ms 고정 시 시한·벌크헤드·실패율 | 시한 200ms, Lettuce 300ms, 벌크헤드 50 + 거절 무시, 실패율 50% |
| 15 | 벌크헤드를 25로 낮추면 실패율이 줄지 않나 | 지금 구조에서는 오른다. 거절이 차단기 실패로 세어지기 때문이다 |
| 16 | 거절을 무시하면 실패율에 안 들어가나, 그다음 어떻게 반영했나 | 안 들어간다(성공도 실패도 아님). ISE-233으로 반영했다 |

## 용어
| 줄임말·용어 | 풀어 쓰기 | 한 줄 뜻 |
|---|---|---|
| vCPU | virtual CPU | EC2가 주는 논리 CPU 하나. m7i는 하이퍼스레딩이라 물리 코어 2개 = vCPU 4개 |
| 이벤트 루프(event loop) | Netty의 I/O 스레드 | 소켓 여러 개를 스레드 하나가 돌아가며 처리한다. 막히는(blocking) 일을 하면 그 스레드의 모든 연결이 멈춘다 |
| 벌크헤드(bulkhead) | 격벽 | 한 의존성에 동시에 들어갈 수 있는 호출 수를 제한한다. Resilience4j 반응형 경로는 세마포어 방식이다 |
| TimeLimiter | Resilience4j 시간 제한기 | 감싼 호출이 정해진 시간 안에 끝나지 않으면 `TimeoutException`으로 끊는다 |
| Hikari(HikariCP) | JDBC 연결 풀 라이브러리 | DB 연결을 미리 만들어 빌려준다. `maximum-pool-size`가 동시에 쓸 수 있는 DB 연결 수다 |
| Lettuce | Redis 클라이언트 | Netty 기반 비동기 클라이언트. 기본으로 연결 하나를 여러 호출이 함께 쓴다 |
| p95 | 95번째 백분위 응답 시간 | 요청 100개 중 95개가 이 시간 안에 끝났다는 뜻 |
| 리틀의 법칙(Little's law) | L = λ × W | 동시에 처리 중인 수 = 초당 도착 수 × 한 건 머무는 시간 |

## 2. 각 수치의 근거
| 수치 | 근거 종류 | 내용 |
|---|---|---|
| 4 vCPU 장비 | 결정 기록 있음 | 메모리 16GB급(사용자 결정 11/4), 성능 보장 때문에 flex → 일반 인스턴스(11/5). **CPU 수를 서비스 구성에서 계산한 기록은 없다** |
| CPU 제한 없음 | 근거 기록 없음 | ADR 0047은 "앱과 DB가 CPU·메모리를 나눠 써 측정 값에 영향"을 감수한다고만 적었다(`0047-single-ec2-first-managed-split-review.md:41`) |
| Netty 이벤트 루프 4 | 라이브러리 기본값 | 설정 없음. CPU 수를 따라 자동으로 정해져 결과적으로 장비와 맞는다 |
| HTTP 클라이언트 풀 ELASTIC | 라이브러리 기본값 | 근거 기록 없음 |
| 벌크헤드 25 | 라이브러리 기본값 | 저장소에 값이 없다(`compose.gateway-bulkhead.yml` 머리 주석, 3-4절) |
| 벌크헤드 100(측정 안) | 측정 근거 | C3에서 1,200/s 때 남은 자리 0 → 100으로 올림. CPU를 고려한 계산은 없다 |
| 차단기 20건·50ms | SA 9-4 `[가정]` | `SA MASTER.md` 9-4 표 "Redis 서킷 브레이커". 측정 전 가정값 |
| 차단기 E안 | 측정 근거 | 3-4 C1·C2의 진동 관찰과 `2026-11-10-auth-redis-breaker-bulkhead-tradeoffs.md` |
| Tomcat 200 | 라이브러리 기본값 | 근거 기록 없음 |
| Hikari 5(reservation·user) | **근거 기록 없음** | 초기 통합 커밋 `bc4e15af`(10/27)에서 들어왔다. SA 9-4는 "서비스당 20, 측정 후 조정"이다 |
| Hikari 20(payment) | SA 9-4 `[가정]` | "측정 후 조정"(`SA MASTER.md` 9-4 커넥션 풀 행) |
| Hikari 20(reservation, 측정 안) | 측정 근거 | C3에서 5일 때 대기 최대 약 195 |
| Postgres 100 | PostgreSQL 기본값 | 근거 기록 없음 |
| 메모리 상한·힙 | 결정 기록 있음 | SA 9-3 메모리 표, `deployment.md` |

정리: 메모리는 서비스별로 계산했고, CPU·스레드·연결 수는 계산하지 않았다. 지금까지는 "기본값으로 띄우고 측정에서 막힌 곳을 올린다"였다.

## 3. CPU 100%를 어떻게 읽나

### 3-1. 4 vCPU를 누가 쓰나(측정값)
1,200~1,600/s 구간(D) 컨테이너 CPU: gateway 135~170%, reservation 93~105%, Postgres 70~74%, 합계 약 300~350%(계산값). 서버 vmstat은 100%(4 vCPU 전부). 나머지 약 50~100%는 Redis, Kafka, Prometheus, Loki, Alloy 같은 다른 컨테이너와 OS 몫으로 보이나 컨테이너별 값은 기록이 없어 확인 못 함이다(`numbers-and-measurement.md` 3-4 D 결과).

- 한 요청이 같은 장비 안에서 Gateway → reservation → Postgres를 거치고, 응모마다 Redis·Kafka·로그·지표 수집도 함께 돈다. 장비 하나의 4 vCPU가 이 모든 단계를 나눠 처리하므로, "Gateway가 무너진다"기보다 "장비 전체의 일이 4 vCPU를 넘었다"가 측정과 맞는 설명이다.
- 스레드 수를 계산해 보면(기본값 기준, 계산값): Gateway 이벤트 루프 4 + Lettuce 4+4, reservation Tomcat 최대 200, Postgres는 연결마다 프로세스 1개(최대 20), 그 밖에 JVM 11개의 GC·JIT 스레드가 각자 CPU 4개 기준으로 정해진다. 실행할 준비가 된 스레드가 4 vCPU보다 훨씬 많으면 문맥 교환과 대기가 늘어 응답 시간이 길어진다.

### 3-2. 이벤트 루프 모델에서 벌크헤드를 키우면
| 선택지 | 스레드에 주는 영향 | CPU에 주는 영향 |
|---|---|---|
| 벌크헤드 25 | 없음(세마포어 카운터) | 넘친 요청을 바로 503으로 돌려 보낸다. 거절은 싸다 |
| 벌크헤드 100 | 없음 | 받아들인 요청이 뒤쪽까지 가서 reservation·Postgres CPU를 쓴다. 같은 장비라 Gateway도 CPU를 덜 받는다 |

- 벌크헤드 안에서 일어나는 Redis 조회는 비동기라 스레드를 붙잡지 않는다. 그래서 "벌크헤드 100 = 스레드 100"이 아니다.
- 리틀의 법칙으로 보면, 벌크헤드가 차는 것은 Redis가 느려서가 아니라 응답 처리 대기가 길어져서다. 1,200/s에서 동시 25가 차려면 한 호출이 약 21ms 머물러야 한다(25 ÷ 1,200, 계산값). Redis 자체는 0.3~1.9ms였다(C2). 나머지 시간은 이벤트 루프·Lettuce 스레드가 CPU를 기다린 시간으로 보인다(추정). 즉 벌크헤드 포화는 CPU 포화의 증상이다.
- 벌크헤드를 100으로 올리면 한 호출이 약 83ms(100 ÷ 1,200, 계산값)까지 머물러도 거절하지 않는다. 거절이 줄어드는 대신 대기가 길어진다. 3-4 C3·D의 p95 상승(60ms → 367ms 등)과 방향이 맞는다.
- Netty 이벤트 루프를 4보다 늘려도 CPU가 4개라 처리량은 늘지 않는다. 이벤트 루프는 막히지 않는 한 CPU 수만큼이 적정이라는 것이 이 모델의 전제다. 다만 JWT 서명 검증처럼 CPU를 쓰는 일이 이벤트 루프 위에서 돌므로, 요청당 CPU 비용이 곧 Gateway 한도를 정한다.

### 3-3. D와 E의 p95 차이
| 비교 | D | E |
|---|---|---|
| 벌크헤드 | 100 | 100 |
| reservation Hikari | 20 | 20 |
| 차단기 | 시간 창 10초, 최소 1,000건, 느린 호출 1초 | 시간 창 10초, 최소 500건, 느린 호출 100ms·80%, 열림 5초, 반열림 20 |
| 차단기 열림 | 없음 | 없음 |
| 1,200/s p95 | 238ms | 339ms |
| 겹친 일 | 800 단계가 앞 추첨(`LOTTERY_ID` 20) DB 처리와 겹침 | 웜업이 앞 추첨(`LOTTERY_ID` 21) DB 처리와 겹침(Postgres CPU 200% 이상) |

- 벌크헤드와 Hikari가 같으므로 이 차이를 벌크헤드로 설명할 수 없다.
- 차단기는 열리지 않으면 호출을 세기만 하므로 CPU 차이를 크게 만들 이유가 코드상 보이지 않는다(추정).
- 남는 후보는 앞 추첨 DB 처리가 1,200 단계까지 이어졌는지와 1회 측정의 변동이다. 어느 쪽인지 확인 못 함이다.

## 4. 결론과 바꿀 후보

### 4-1. "사양을 고려한 수치인가"
**일부.** 메모리는 사양을 보고 나눴다. CPU·스레드·벌크헤드·연결 풀은 사양을 보고 계산하지 않았다. 기본값이 CPU 4를 따라 자동으로 정해진 것과, 측정에서 막힌 곳을 올린 값이 섞여 있다. 특히 reservation·user Hikari 5는 근거 기록이 없다.

### 4-2. 선택지 비교
| 선택지 | 하는 일 | 기대 | 감수할 점 |
|---|---|---|---|
| A. 컨테이너별 CPU 제한(`cpus`)을 둔다 | Gateway·reservation·Postgres에 몫을 정하고 관측 도구는 작게 묶는다 | 관측 도구가 앱 CPU를 빼앗지 않는다. JVM이 제한값을 CPU 수로 보고 스레드를 맞춘다. 병목 위치가 지표로 분명해진다 | 총량 4 vCPU는 그대로라 한도는 늘지 않는다. 몫을 잘못 나누면 한 곳이 먼저 막힌다. 한도가 오히려 낮아질 수 있어 다시 재야 한다 |
| B. 벌크헤드를 "CPU가 감당할 동시 수"로 맞춘다 | 리틀의 법칙으로 목표 처리량 × 허용 대기(예: 1,200/s × 20~40ms ≈ 25~50)를 잡고 재측정 | 넘치는 요청을 싸게 거절해 장비 전체가 무너지기 전에 막는다(부하 차단) | 거절(503)이 늘어난다. 대기열이 입장을 이미 제한한다면 중복일 수 있다 |
| C. Hikari를 CPU 기준으로 정한다 | Postgres가 쓸 수 있는 vCPU 기준(통상 "코어 × 2 + 디스크 수" 경험식)으로 5~10을 재 본다 | 쿼리 동시 실행이 줄어 경합이 줄어든다 | 연결 대기가 늘어 Tomcat 스레드가 기다린다. 경험식은 전용 DB 서버 기준이라 이 장비에 맞는지 측정해야 한다 |
| D. 측정 때 관측 부하를 줄인다 | Zipkin 샘플링 0.01(이미 측정 모드), 요청 로그 끔(`iseonjwa.request-log.enabled`), 스크레이프 간격 확인 | 앱이 쓸 CPU가 늘어 숫자가 운영에 가깝게 나온다 | 운영 관측과 조건이 달라진다 |
| E. 장비를 키우거나 나눈다 | 인스턴스 확장 또는 DB·Kafka 분리(ADR 0047 재검토) | 한도 자체가 올라간다 | 비용과 배포 구성이 는다. 팀 결정 대상이다 |

### 4-3. 추천
1. 먼저 측정으로 "누가 CPU를 쓰나"를 확정한다(아래 확인할 질문). 근거 없이 숫자를 바꾸면 지금과 같은 상황이 반복된다.
2. 그다음 A(CPU 제한)와 B(벌크헤드를 CPU 기준으로)를 함께 한다. 4 vCPU라는 한계를 받아들이고, 넘치는 요청을 Gateway에서 싸게 거절하는 쪽이 "느려지다 무너지는" 것보다 낫다. 1,600/s에서 p99 8.8s(C3)는 사용자가 실패보다 나쁘게 겪는 결과다.
3. reservation·user Hikari 5는 근거가 없으므로, 바꾸든 두든 측정값으로 근거를 남긴다.

감수할 점: 한도 숫자(약 800~1,200/s)는 장비를 바꾸지 않는 한 크게 오르지 않는다. 이번 조정의 목표는 "더 많이"가 아니라 "한도를 넘어도 예측 가능하게 거절"이다. 장비 확장은 비용이 드는 팀 결정이라 따로 다룬다.

## 6. 추가 질문: 벌크헤드가 너무 커서 감당 못 할 부하까지 받아내다 터지는 것 아닌가

### 질문
벌크헤드 수치가 너무 커서 너무 많이 받아들여 오히려 무거워지거나 부하를 견디지 못하는 것은 아닌가. 장애 대응을 제대로 해야 하는데, 감당할 수 없는 부하를 전부 받아내려다가 터지는 것은 아닌가.

### 짧은 답
- **방향은 맞다. 다만 범인은 벌크헤드 100 하나가 아니다.** 지금 구조는 감당 못 할 부하를 빨리 거절하지 않고 여러 곳에 줄 세워 기다리게 한다. 벌크헤드 100은 그중 한 곳의 거절 기준을 늦춘 것이다.
- `auth-redis` 벌크헤드는 요청 전체가 아니라 **Redis 조회 한 번(평소 1ms 안팎)** 만 감싼다. 인증을 통과한 요청이 reservation·DB에서 수백 ms를 쓰는 구간은 아무것도 막지 않는다. 그래서 벌크헤드를 25로 둔 C3도 1,600/s에서 p99 8.8s까지 갔다.
- 측정 D는 "터짐"보다 "포화 뒤 지연 폭증"에 가깝다. 처리량은 약 1,600/s에서 정체했고(2,000/s 목표에 1,603/s), 넘친 부하는 거절보다 대기로 쌓여 p95가 1.1s가 됐다. 장애 대응의 목표 모양(처리량은 정체, 지연은 묶이고, 넘친 만큼 빨리 거절)과 다르다.

### 어디에 줄이 서나(코드·설정 기준)
| 위치 | 지금 값 | 넘칠 때 동작 | 출처 |
|---|---|---|---|
| Gateway 전체 요청 수 | 제한 없음(요청 단위 동시 제한·속도 제한 필터 없음) | 모두 받는다 | `config-repo/gateway.yml` 필터 목록 |
| `auth-redis` 벌크헤드 | 25(운영) / 100(D·E) | 즉시 거절(대기 0) → 503. 거절이 차단기 실패로 세어진다 | `BulkheadConfig.java:33-34`, 1-2절 순서 |
| Gateway → 서비스 연결 | ELASTIC(상한 없음) | 연결을 계속 연다 | `HttpClientProperties.java:173` |
| Gateway 응답 시한 | 3초 | 3초 뒤 504. **뒤쪽 처리는 계속될 수 있다** | `config-repo/gateway.yml:10`, SA 9-4 S-26 |
| reservation Tomcat | 스레드 200, 대기열 100, 연결 8,192 | 스레드가 차면 연결을 받아 둔 채 기다린다 | `TomcatServerProperties.java:108,114,635` |
| reservation Hikari 연결 대기 | **설정 없음 → 30초** | 연결을 30초까지 기다린다. D에서 대기 최대 112 | `HikariConfig.java:50`(HikariCP 7.0.2), `config-repo/reservation-service.yml:8-9` |
| CPU 실행 대기 | 4 vCPU 공유 | 모든 스레드가 CPU를 기다린다 | 3-1절 |

- 가장 눈에 띄는 것은 reservation Hikari 대기 30초다. Gateway가 3초에 포기한 요청도 reservation에서는 DB 연결을 30초까지 기다렸다가 처리할 수 있다. 사용자는 이미 떠났는데 서버는 그 일을 계속해 CPU를 쓴다(헛일). payment는 이 문제 때문에 1초로 줄였다(`config-repo/payment-service.yml:9-11` 주석). reservation에는 같은 조치가 없다.
- 응모 API는 대기열 입장 토큰 없이 들어오는 것으로 보인다. `LotteryController`에 입장 토큰 검증이 보이지 않고, 추첨 설계 문서도 "입장 토큰 검증이 응모 API를 제외하는지 확인"을 남겨 두었다(`docs/design/lottery/README.md:155`). 그렇다면 L1 응모는 앞단의 입장 제한 없이 Gateway에 그대로 닿는다(확인할 질문).

### 벌크헤드 숫자를 리틀의 법칙으로 보면
| 값 | 1,200/s에서 거절 없이 견디는 한 호출 시간(계산값) | 뜻 |
|---|---|---|
| 평소 필요량 | Redis 0.3ms × 1,200/s ≈ 동시 0.4 | 평소에는 1개도 다 안 쓴다 |
| 25 | 약 21ms | 평소의 수십 배 여유. 이 값이 차면 이미 CPU가 밀리고 있다는 신호 |
| 100 | 약 83ms | 신호를 4배 늦게 받는다. 그동안 받아들인 요청이 뒤쪽 일을 늘린다 |

- 25는 "작아서 문제"였다기보다 **차면 바로 차단기가 열려 인증 전체가 10초 동안 503**이 되는 연결 방식이 문제였다(3-4 C1·C2 진동). 벌크헤드가 차단기 안쪽에 있어 `BulkheadFullException`이 실패로 세어지기 때문이다.
- 그래서 100으로 올린 효과는 "더 견딘다"가 아니라 "거절·열림을 늦춘다"이다. 장비 여유가 없을 때 늦춘 만큼 대기가 쌓인다. 강민이 걱정한 현상이 이것이다.

### 선택지 비교
| 선택지 | 하는 일 | 기대 | 감수할 점 |
|---|---|---|---|
| A. 벌크헤드 100 유지 | 측정 E안 그대로 | 포화 전 구간(약 1,000~1,200/s)에서 거절이 적다 | 포화 뒤에는 거절 대신 지연이 커진다(D 1,600/s p95 1.1s) |
| B. 벌크헤드를 작게(25~50) 두고, 벌크헤드 거절은 차단기 실패에서 뺀다 | 차단기 `ignore-exceptions`에 `BulkheadFullException`을 넣는다 | 넘친 요청만 하나씩 빨리 503. 차단기가 인증 전체를 10초 막는 진동이 사라진다. 차단기는 Redis 자체 장애만 감지한다 | 포화 때 503 비율이 보인다. 키·동작은 테스트로 확인해야 한다(확인 못 함). `gateway.yml`은 ISE-230 범위라 그 작업과 맞춰야 한다 |
| C. reservation Hikari 연결 대기를 1초로 줄인다 | payment와 같은 기준 | Gateway 3초 안에 실패가 확정돼 헛일이 줄어든다 | 포화 때 DB 대기 실패(500/503)가 빨리 드러난다. 응답 코드 매핑을 확인해야 한다 |
| D. Gateway 앞단에 요청 수 제한을 둔다 | 경로별 동시 요청 제한 또는 속도 제한(Spring Cloud Gateway `RequestRateLimiter` 등) | 장비가 감당할 만큼만 받고 나머지는 입구에서 거절한다. 가장 싼 거절이다 | 한도 숫자를 측정으로 정해야 한다. 속도 제한은 Redis를 또 쓴다. 정상 몰림도 거절한다 |
| E. 응모를 대기열 뒤에 둔다 | 입장 토큰을 응모에도 요구 | 입장 수로 부하를 조절한다 | 추첨은 "줄 서지 않는다"는 설계 취지와 맞는지 팀 결정이 필요하다 |

### 추천
B + C를 먼저 본다. 둘 다 "감당 못 할 만큼은 빨리, 조금씩 거절한다"는 같은 원칙이고 설정 수준 변경이다. B는 벌크헤드 숫자 논쟁(25냐 100이냐)을 "작게 두되 차단기와 떼어 놓는다"로 바꾼다. C는 사용자가 떠난 요청에 CPU를 쓰지 않게 한다. D·E는 한도 숫자와 팀 결정이 필요해 그다음이다.

감수할 점: 포화 구간에서 503이 눈에 보이게 늘어난다. "다 받아 내는" 것처럼 보이던 D의 숫자보다 성공률은 낮게 나올 수 있다. 대신 지연이 묶이고 장비가 무너지지 않는다. 발표에서는 "한도를 넘으면 빨리 거절한다"를 증명하는 장면이 된다.

### 확인할 질문
| 질문 | 확인 방법 |
|---|---|
| 포화 때 Gateway가 3초에 끊은 요청을 reservation이 계속 처리하나 | 1,600/s 구간에서 Gateway 504 수와 reservation 처리 완료 수(요청 로그·`http_server_requests`)를 비교 |
| D 1,600/s에서 지연이 어디서 쌓였나 | 같은 구간의 `hikaricp_connections_pending`, `tomcat_threads_busy`, Gateway 쪽 응답 시간 분리 |
| B를 적용하면 진동 없이 넘친 만큼만 거절되나 | 벌크헤드 25 + 거절 제외로 C2와 같은 단계를 다시 재서 거절 비율·차단기 상태 전환을 본다 |
| 응모 API에 입장 토큰이 필요 없나 | 대기열 담당과 확인(`docs/design/lottery/README.md:155`) |

## 7. 추가 질문: 대기열 진입에서 "Tomcat 스레드 1개가 처리"가 병목이 되나

### 질문
Gateway와 대기열 Redis만 두고 단계적으로 보자고 한 뒤, 대기열 진입 경로의 "reservation에서 Tomcat 스레드 1개가 처리" 때문에 병목이 생기는지 물었다.

### 짧은 답
- "1개"는 스레드가 하나뿐이라는 뜻이 아니다. 요청 하나가 처리되는 동안 **스레드 풀 200개 중 1개를 붙잡는다**는 뜻이다(요청당 스레드 모델, thread-per-request).
- 대기열 진입은 DB를 타지 않고 Redis Lua 1회라 스레드를 짧게 쥔다. 계산상 2,000/s에서도 200개가 차려면 한 건이 100ms 넘게 걸려야 한다. **직접 원인일 가능성은 낮다**(추정, Q1에서 Tomcat 스레드 지표를 켜지 않아 확인 못 함).
- 다만 CPU가 포화돼 한 건이 길어지면 스레드가 2차 증상으로 차고, 그때 Tomcat은 거절하지 않고 연결 8,192·대기열 100으로 줄을 세운다. 앞 절의 "거절 대신 대기" 문제가 여기서도 생길 수 있다.

### 요청당 스레드 모델과 이벤트 루프 모델
| 항목 | reservation(Tomcat, 요청당 스레드) | Gateway(Netty, 이벤트 루프) |
|---|---|---|
| 동시 처리 수를 정하는 것 | 스레드 수(최대 200) | 스레드 수와 무관. CPU와 메모리 |
| Redis를 기다리는 동안 | 스레드가 멈춰 기다린다(`StringRedisTemplate`은 동기 호출) | 스레드를 놓고 다른 요청을 처리한다 |
| 기다리는 스레드의 비용 | CPU는 거의 안 쓴다. 스택 메모리와 문맥 교환 비용이 있다 | 해당 없음 |
| 풀이 차면 | 연결을 받아 둔 채 줄을 세운다(연결 8,192, OS 대기열 100) | 해당 없음 |

### 리틀의 법칙으로 본 필요 스레드 수(계산값)
바쁜 스레드 수 = 초당 요청 수 × 한 건이 스레드를 쥐는 시간.

| 초당 요청 | 한 건 2ms | 한 건 10ms | 200개가 차는 한 건 시간 |
|---|---|---|---|
| 1,000 | 2개 | 10개 | 200ms |
| 2,000 | 4개 | 20개 | 100ms |

- 한 건 시간 2ms·10ms는 가정이다. Redis 자체는 0.3~1.9ms였다(3-4 C2). 여기에 요청 로그·추적·JSON 처리 시간이 더해진다.
- 그래서 스레드 200개는 Redis만 쓰는 경로에서는 여유가 크다. 스레드가 차는 상황은 "CPU가 밀려 한 건이 100ms 이상 걸릴 때"뿐이고, 그때 진짜 원인은 스레드가 아니라 CPU다.

### 측정 기록과 맞춰 보면
- Q1이 2,000~3,000/s에서 실패한 방식은 Gateway `auth-redis` 차단기가 2ms 안의 빠른 실패로 열린 것이다(`loadtest/deploy/compose.gateway-bulkhead.yml` 머리 주석, 영은님 판단 기록 `2026-11-10-no-breaker-relax-for-measurement.md:39`). 요청이 reservation에 닿기 전 Gateway에서 막혔으므로, 첫 병목은 Tomcat이 아니었다.
- 스레드 풀이 실제 병목이 된 사례는 좌석 조회다(`docs/design/reservation/k6-overload-recovery.md` 3-1·7절, local). DB 연결 5개를 스레드 200개가 기다려, 한 건이 서버 안에서 평균 14초를 보냈다. 원인은 스레드 수가 아니라 DB 대기 30초였고, 연결 대기 1초(R1)로 회복 문제가 풀렸다.
- 같은 측정에서 스레드를 50으로 줄인 R2는 오히려 나빴다. Tomcat 연결 상한을 "Gateway 3초 × 처리량"(약 30)으로 맞춘 R3는 CPU 경합이 클 때만 이득이 있었다. 스레드 수를 줄이는 것보다 **안에서 기다리는 줄을 Gateway 시한 안으로 묶는 것**이 효과가 있었다.

### 선택지 비교
| 선택지 | 하는 일 | 기대 | 감수할 점 |
|---|---|---|---|
| A. 그대로 두고 먼저 잰다 | Q1 재측정 때 Tomcat 지표를 켠다(`reservation-service/k6/compose.b8-observe.yml`의 `server.tomcat.mbeanregistry.enabled`) | 스레드가 병목인지 숫자로 가린다 | 측정 한 번이 더 든다. 배포 측정 모드에 이 덮어쓰기를 얹는 방법을 정해야 한다 |
| B. Tomcat 연결 상한을 처리량에 맞춘다(R3 방식) | 3초 × 대기열 처리량으로 `max-connections`·`accept-count`를 정한다 | 넘친 요청이 Tomcat 안에서 3초 넘게 기다리지 않는다 | 좌석 조회처럼 무거운 요청과 서비스를 같이 쓰므로 한 값이 둘에 다 맞지 않는다. local에서 빠른 실패가 오히려 늦어졌다 |
| C. 가상 스레드를 켠다 | 기다리는 동안 OS 스레드를 놓는다 | 스레드 수 제한이 사라진다 | SA 9-1 결정(Java 21 고정 문제로 끔)을 바꾸는 일이다. 스레드 한도가 없어지면 거절 지점이 사라져 오히려 더 받아들인다 |
| D. 대기열 API를 반응형으로 바꾼다 | WebFlux·반응형 Redis로 다시 만든다 | 이벤트 루프 모델의 이점 | 구조 변경이 크다. 이번 범위가 아니다 |

A. 지금 기록으로는 대기열 진입의 첫 병목이 Gateway였고, Tomcat 스레드가 문제라는 증거가 없다. 바꾸기 전에 Q1 재측정에서 `tomcat_threads_busy_threads`를 함께 본다. 실패하는 단계에서도 바쁜 스레드가 수십 개 이하면 스레드는 병목이 아니고, 200에 붙으면 그때 B를 검토한다. C는 "더 받아들이는" 방향이라 강민이 앞에서 걱정한 과수용을 키울 수 있다.

## 8. 추가 질문: 지금 사양에서 초당 몇 건이 괜찮은 정도인가

### 질문
초당 동시 요청 수가 어느 정도면 지금 서버 사양에서 괜찮은 정도인지 물었다.

### 먼저 두 숫자를 나눈다
| 용어 | 뜻 | 단위 |
|---|---|---|
| 처리량(throughput, RPS) | 초당 도착·처리하는 요청 수 | 건/초 |
| 동시 요청 수(concurrency, in-flight) | 지금 이 순간 처리 중인 요청 수 | 건 |

둘은 리틀의 법칙으로 이어진다. 동시 요청 수 = 처리량 × 한 건 시간. 예: L1 800/s에서 p50 3.7ms면 처리 중인 요청은 평균 약 3건이다(계산값, 평균 대신 p50을 썼다). 동시 수는 생각보다 작다. 그래서 이 장비의 한도는 스레드·벌크헤드 숫자보다 **요청 하나가 장비 전체에서 쓰는 CPU 시간**이 정한다. D 측정에서 1,600/s에 4 vCPU가 100%였으므로 응모 한 건이 장비 전체에서 약 2.5ms의 CPU를 썼다(4,000ms ÷ 1,600, 계산값, 다른 컨테이너 몫 포함이라 상한값).

### 지금 사양(4 vCPU 한 대, 운영 설정)에서 측정한 한도
| 경로 | 목표(설계 기준) | 통과(측정) | 실패(측정) | 막는 곳 | 출처 |
|---|---|---|---|---|---|
| 대기열 진입 Q1 | 30,000명을 10초 안 = 초당 3,000, p95 200ms | 데운 뒤 초당 1,000 | 초당 2,000 | Gateway `auth-redis` 차단기(빠른 실패) | `open-peak-scenarios.md:105,112`, 영은님 판단 기록 `:39` |
| 추첨 응모 L1 | 초당 100, p95 300ms | 초당 800(p95 15.8ms) | 초당 1,000에서 거절 19% | Gateway `auth-redis` 차단기 | 3-3 L1 표, 3-4 C2 |
| 일반 결제 | 초당 20(L2) | 초당 30까지 503 0.31% | 초당 35에서 503 9.4% | `pg-approve` 허가 10개(CPU 4%) | 3-4 B |
| 자동결제 | 2,000건을 10분 안 = 초당 3.3 | 초당 3.17 | 10분 기준 미달 | 소비자 1개 | 3-3 L2-a, 3-4 A |
| (참고) 응모, 측정 D 설정 | — | 초당 1,200(p95 238ms) | 초당 1,600에서 정체 | 서버 CPU 100% | 3-4 D. 운영 설정 아님 |

- 결제 두 줄은 CPU가 아니라 PG 허가와 소비자 수가 한도다. 사양을 키워도 안 바뀐다.
- CPU 사양이 한도에 직접 걸리는 것은 Gateway를 거치는 몰림(대기열 진입·응모)이다. 운영 설정에서는 CPU보다 먼저 차단기가 막고, 차단기를 풀면 약 1,200~1,600/s에서 CPU가 막는다.

### "괜찮은 정도"를 어떻게 정하나
| 선택지 | 기준 | 지금 값으로 하면(계산값) | 감수할 점 |
|---|---|---|---|
| A. 통과선 그대로 | 측정에서 통과한 최대 단계 | 진입 1,000 · 응모 800 | 여유가 없다. 1회 측정이 많고 측정 사이 변동(D·E 차이)도 있다 |
| B. 통과선의 60~70% | 업계에서 흔히 쓰는 여유 관례(순간 몰림·GC·변동 흡수). 이 프로젝트에서 측정으로 정한 비율은 아니다 | 진입 약 600~700 · 응모 약 500~560 | 보수적이라 장비 여유를 덜 쓴다 |
| C. 혼합 부하로 다시 잰다 | 실제 오픈처럼 진입·순번 폴링·응모를 함께 건 통과선 | 측정 전이라 없음 | 측정이 한 번 더 든다 |

- 지금 숫자는 모두 **경로 하나씩 따로** 잰 값이다. 실제 오픈 때는 진입과 순번 폴링(대기자 30,000명이면 계산상 초당 약 2,700건, `open-peak-load-plan.md` Z4)이 같은 4 vCPU와 같은 Redis를 함께 쓴다. 그래서 함께 걸었을 때의 한도는 각각의 한도보다 낮을 것이다(추정, 측정하지 않음).
- 목표와 비교하면 응모는 목표(100)의 8배를 통과해 여유가 있다. 대기열 진입은 목표(3,000)의 1/3에서 멈춘다. "사양이 모자란다"는 느낌은 대기열 진입 몰림에서 맞는 말이다.

## 9. 추가 질문: 왜 병목이 생기고 CPU·메모리가 터지나, 줄 서서 기다리는 동안 Gateway 스레드 풀이 차는 것인가

### 질문
지금 왜 병목이 생기고 CPU·메모리 점유가 터지는지, 대기열에 바로 들어가지 못하고 줄 서서 기다리는 동안 Gateway 스레드 풀이 가득 차서 터지는 것은 아닌지 물었다.

### 짧은 답
- **줄 서서 기다리는 사용자는 Gateway 자원을 붙잡지 않는다.** 대기열은 Redis에 순번 한 줄로 남고, 화면이 3~12초마다 순번을 묻는 짧은 요청(폴링)을 보낼 뿐이다. 기다리는 동안 열린 연결이나 스레드는 없다.
- **Gateway에는 요청마다 쓰는 스레드 풀이 없다.** 이벤트 루프 4개가 늘 같은 수로 돈다. 차는 것은 스레드가 아니라 벌크헤드 허가(25)와 "처리 중인 요청·연결"이다.
- 무너지는 원인은 **도착 속도가 처리 속도를 넘는 순간부터 처리 중인 요청이 불어나는 되먹임**이다. CPU 부족 → 응답이 느려짐 → 처리 중인 요청이 늘어남 → 메모리·GC가 늘어남 → CPU를 더 씀. 여기에 503 자동 재시도가 도착 속도를 더 키운다.
- **메모리가 터졌다는 기록은 없다.** 확인된 것은 C3 1,600/s 구간의 Gateway GC 87ms/s(1초 중 87ms를 GC에 씀)뿐이고, OOM(메모리 부족 종료)·재시작 기록은 찾지 못했다.

### 기다리는 동안 무엇이 남나(코드 기준)
| 시점 | Gateway | reservation | Redis |
|---|---|---|---|
| 진입 요청 1번 | 처리 중인 요청 1개(수 ms) | Tomcat 스레드 1개(수 ms) | `enter.lua` 1회, 순번 저장 |
| 줄 서서 기다림 | 없음 | 없음 | 순번 한 줄(메모리 수십 바이트) |
| 순번 폴링(3~12초마다) | 짧은 요청 1개씩 | Tomcat 스레드 1개씩(수 ms) | `position.lua` 1회 |

- 출처: `QueueController.java:24-56`, `RedisQueueRepository.java:19-34`, 폴링 간격 `open-peak-load-plan.md` Z4.
- 그래서 "기다리는 사람 수"는 연결 수가 아니라 **폴링 처리량**으로 비용이 된다. 대기자 30,000명이면 계산상 초당 약 2,700건이다(Z4). 이 비용은 진입 요청과 같은 4 vCPU를 쓴다.

### 무너지는 순서(원인 사슬)
| 순서 | 일어나는 일 | 근거 |
|---|---|---|
| 1 | 도착 속도는 서버가 느려져도 줄지 않는다. k6는 열린 모델(`constant-arrival-rate`)이고, 실제 사용자는 503을 받으면 화면이 약 1초 뒤 자동으로 다시 보낸다 | `loadtest/k6/scenarios/q1-queue-enter.js:31`, `2026-11-10-queue-join-503-auto-retry.md` |
| 2 | 요청당 CPU × 초당 요청 수가 장비 몫(4 vCPU를 21개 컨테이너가 나눔)을 넘는다 | 3-1절, 서버 vmstat 100%(3-4 C3·D) |
| 3 | 스레드들이 CPU를 기다려 한 건 시간이 길어진다 | Redis 자체 0.3~1.9ms인데 벌크헤드 25가 참(7절 계산) |
| 4 | 처리 중인 요청 = 도착 속도 × 한 건 시간이므로, 한 건 시간이 늘면 처리 중인 요청이 불어난다. 예: 평소 800/s × 3.7ms ≈ 3건, 1,600/s × 1s ≈ 1,600건(계산값) | 리틀의 법칙, 3-4 D 1,600/s p95 1.1s |
| 5 | 처리 중인 요청마다 Gateway는 사용자 연결·뒤쪽 서비스 연결(상한 없음)·버퍼를 쥔다. 메모리가 늘고 GC가 CPU를 더 쓴다 | `HttpClientProperties.java:173`(ELASTIC), C3 GC 87ms/s. 메모리 증가량은 확인 못 함 |
| 6a | 운영 설정: 동시 Redis 조회가 벌크헤드 25를 넘어 거절 → 차단기가 실패로 세어 열림 → 10초 동안 인증 전체 503 | 3-4 C1·C2, Q1 2ms 빠른 실패 |
| 6b | 완화 설정: 거절하지 않으니 처리 중인 요청이 계속 쌓임 → p99 8.8s, 2,000/s 이상에서 연결 실패, 발생기 VU 3,000 상한 도달 | 3-4 C3 |
| 7 | 실제 사용자는 503마다 약 1초 뒤 재시도 → 도착 속도가 더 늘어 1로 돌아간다(재시도 폭풍) | `queueAdmission.ts`, `Retry-After: 1`(`GatewayErrorWriter.java:28`) |

- 운영 설정은 6a로 "빨리 전부 거절"해서 무너지지 않는 대신 정상 사용자까지 10초씩 막는다. 완화 설정은 6b로 "전부 받아 내려다" 느려진다. 강민이 앞에서 걱정한 과수용이 6b다.
- k6 측정은 재시도를 하지 않으므로(7번이 없다) 실제 오픈보다 낙관적이다(추정).

### 선택지 비교(Gateway·Redis 범위 안)
| 선택지 | 끊는 고리 | 기대 | 감수할 점 |
|---|---|---|---|
| A. 벌크헤드를 작게 두고 거절을 차단기 실패에서 뺀다(6절 B) | 6a·6b | 넘친 요청만 하나씩 빨리 거절, 처리 중인 요청 수에 상한 | 포화 때 503이 보인다. 동작은 테스트로 확인해야 한다 |
| B. `Retry-After`를 열림 시간·부하에 맞춰 늘리고 흩뿌린다 | 7 | 재시도 폭풍이 줄어든다 | 사용자가 다시 시도하기까지 오래 기다린다. ISE-230 범위(영은님 코멘트 1)와 맞춰야 한다 |
| C. Gateway 입구에서 요청 수를 제한한다 | 4·5 | 처리 중인 요청이 장비가 감당할 수를 넘지 않는다 | 한도 숫자를 측정으로 정해야 한다. 정상 몰림도 거절한다 |
| D. 요청당 CPU를 줄인다(요청 로그·추적, 폴링 간격) | 2 | 같은 장비로 처리량이 오른다 | 관측 정보가 줄거나 순번 갱신이 늦게 보인다 |

### 추천
A + B를 먼저 본다. 둘 다 "넘친 만큼만 빨리 거절하고, 거절된 사람이 한꺼번에 다시 오지 않게 한다"는 같은 목표이고 Gateway·Redis 범위 안에서 끝난다. C는 A를 적용한 뒤에도 처리 중인 요청이 불어나면 검토한다. D는 처리량 자체를 올리는 일이라 따로 잰다.

감수할 점: 몰림 구간의 503이 눈에 띄게 남는다. 목표는 "모두 받기"가 아니라 "넘쳐도 무너지지 않고, 되돌아오는 시간이 짧게"다.

## 10. 추가 질문: 차단기가 재는 "Redis 호출 시간"에 Gateway 쪽 대기가 섞이나

### 질문
Gateway가 Redis에 요청을 보내고 응답을 받아 처리하기까지의 시간으로 차단기가 열고 닫는데, Gateway에 일이 쌓여 있으면 응답을 처리하지 못해 시간이 늘어나는 것인지, 어떤 상황들이 가능한지 물었다.

### 짧은 답
- **그렇다. 차단기가 재는 시간은 "Redis가 일한 시간"이 아니라 "Gateway가 구독한 순간부터 응답 신호가 차단기에 돌아온 순간까지"다.** 그 사이 Gateway·Lettuce 스레드가 밀린 시간, GC로 멈춘 시간, CPU 차례를 기다린 시간이 모두 들어간다.
- 그래서 Redis가 0.3~1.9ms로 멀쩡해도 차단기는 50ms 초과(느린 호출)를 볼 수 있다. 3-4 C2에서 Redis 컨테이너 CPU 8%인데 차단기가 느린 호출로 열린 것과 맞는다(추정).
- 가장 의심되는 곳은 **Lettuce 연결 하나를 모든 요청이 함께 쓰는 구조**다. Netty에서 연결 하나는 평생 이벤트 루프 스레드 하나에 묶이므로, Gateway의 모든 Redis 응답이 스레드 하나에서 차례대로 처리된다(추정, 서버에서 스레드별 CPU를 재야 확정).

### 차단기가 시간을 재는 구간(라이브러리 소스로 확인)
| 시점 | 무엇이 일어나나 | 어느 스레드 | 출처 |
|---|---|---|---|
| 시작 | 차단기 연산자를 구독하는 순간 `start`를 찍는다 | Gateway 이벤트 루프(`reactor-http-epoll`) | `CircuitBreakerSubscriber.java:48`(resilience4j-reactor 2.3.0) |
| 1 | 벌크헤드 허가를 얻는다(대기 0) | 같음 | `BulkheadConfig.java:34` |
| 2 | Lettuce가 `EXISTS` 명령을 연결의 이벤트 루프 작업 큐에 넣는다 | 넘겨줌 → Lettuce I/O 스레드 | Netty 동작(채널은 이벤트 루프 하나에 묶인다) |
| 3 | 명령이 네트워크로 나가 Redis가 처리한다 | Redis(단일 스레드) | — |
| 4 | 응답을 읽고 풀어(디코딩) 신호를 낸다 | Lettuce I/O 스레드. 기본은 다른 스레드로 넘기지 않는다 | `ClientOptions.java:67`(`DEFAULT_PUBLISH_ON_SCHEDULER = false`) |
| 끝 | 응답 신호가 차단기에 닿으면 `현재 - start`를 기록한 뒤 다음 단계로 넘긴다 | Lettuce I/O 스레드 | `CircuitBreakerSubscriber.hookOnNext` |
| 그 뒤 | 인증 필터 다음 단계(라우팅, 뒤쪽 서비스 호출 시작)가 이어서 실행된다 | **Lettuce I/O 스레드에서 이어진다**(다른 스레드로 넘기는 연산자가 없다) | `GatewayAuthenticationFilter.java:84-87`의 `flatMap` |

- 연결 공유: Spring Data Redis 기본값 `shareNativeConnection = true`(`LettuceConnectionFactory.java:134`, 4.1.2)이고 저장소에 풀 설정이 없다(`config-repo/application.yml:47-52`). 그래서 Gateway의 모든 인증 조회가 연결 하나를 쓴다.
- 벌크헤드 허가도 같은 구간 동안 쥐고 있다. 시간이 늘면 허가가 빨리 차서 거절(`BulkheadFullException`)이 나고, 그것도 차단기 실패로 세어진다(6절).

### 명령 하나가 Lettuce 안에서 거치는 큐(Lettuce 7.5.2 소스)
대화 중 "Lettuce 전송 대기열"이라고 줄여 말한 것은 정식 용어가 아니다. 실제로는 아래 두 큐다.

| 순서 | 큐 | 표준 용어 | 무엇이 기다리나 | 출처 |
|---|---|---|---|---|
| 1 | Netty 이벤트 루프 작업 큐 | event loop task queue | Gateway 스레드가 보낸 쓰기 요청이, 연결을 맡은 Lettuce I/O 스레드가 집어 갈 때까지 기다린다. 연결이 하나라 모든 요청이 한 스레드의 이 큐를 지난다 | `DefaultEndpoint.java:445`(`writeAndFlush`), Netty 동작 |
| 2 | 응답 대기 명령 목록 | Lettuce `CommandHandler`의 command stack(in-flight 명령) | Lettuce I/O 스레드가 명령을 RESP 바이트로 바꿔 소켓에 쓴 뒤, 응답이 올 때까지 이 목록에 넣어 둔다 | `CommandHandler.java:101,520`(`stack.add`) |
| 3 | 응답 처리 | — | 응답이 오면 목록의 맨 앞 명령과 짝지어 완료시킨다. Redis는 받은 순서대로 답하므로 짝도 순서대로다 | `CommandHandler.java:661,686`(`stack.peek`·`poll`) |

- 한 연결에서 응답을 기다리지 않고 명령을 여러 개 연달아 보내는 방식을 **파이프라이닝(pipelining)**이라 한다. 덕분에 연결 하나로도 많은 요청을 처리한다.
- 대신 응답을 순서대로만 처리하므로, 앞 명령의 응답 처리가 늦으면 뒤 명령도 기다린다. 이것이 **머리 막힘(head-of-line blocking)**이다(아래 상황 A).
- `commandBuffer`(`DefaultEndpoint.java:94`)는 자동 전송(auto-flush)을 끈 경우에만 쓰는 버퍼이고, `disconnectedBuffer`(`:92`)는 연결이 끊긴 동안 쌓는 버퍼다(11절). 평소 경로에는 쓰이지 않는다.

### 시간이 늘어날 수 있는 상황
| 상황 | 구간 | 차단기가 보는 것 | 가능성 | 근거·확인 방법 |
|---|---|---|---|---|
| A. Lettuce I/O 스레드 하나가 밀림 | 2·4 | 느린 호출. 앞 응답이 처리될 때까지 뒤 응답이 기다린다(머리 막힘, head-of-line blocking) | 높음(추정) | 연결 1개 = 스레드 1개. 게다가 "그 뒤" 행처럼 라우팅 일부까지 이 스레드가 맡는다. 스레드별 CPU에서 `lettuce-epollEventLoop` 하나가 100%에 붙는지 본다 |
| B. GC로 JVM 전체가 멈춤 | 전 구간 | 멈춘 동안 처리 중이던 호출이 모두 한꺼번에 느린 호출 | 중간 | C3 GC 87ms/s. 한 번 멈춘 시간이 수십 ms면 50ms 기준을 바로 넘는다. `jvm_gc_pause_seconds_max`로 본다 |
| C. CPU 차례 대기 | 전 구간 | 느린 호출. 스레드는 실행할 준비가 됐는데 4 vCPU가 다른 컨테이너에 쓰이고 있다 | 높음 | 서버 vmstat 100%(C3·D). `vmstat 1`의 `r` 열이 4보다 계속 크면 해당 |
| D. Gateway 이벤트 루프 밀림 | 시작 전 | **차단기 시간에는 안 들어간다.** 구독 전에 기다린 시간이라 사용자 응답 시간만 늘어난다 | — | `start`가 구독 순간이다. 다만 C를 통해 간접적으로 영향을 준다 |
| E. Redis 자체 대기 | 3 | 느린 호출 | 낮음 | Redis는 명령을 하나씩 처리하고 Lua 스크립트(reservation의 `enter.lua` 등)가 도는 동안 다른 명령이 기다린다. 하지만 Redis CPU 8%, 조회 평균 최대 1.9ms(C2) |
| F. 컨테이너 사이 네트워크 | 3 | 느린 호출 | 낮음 | 같은 장비 안 Docker 네트워크다. CPU가 포화되면 커널 처리도 늦어질 수 있다(C에 포함) |
| G. 벌크헤드 거절 | 1 | 느린 호출이 아니라 **실패**(약 0~2ms) | 높음(운영 설정) | Q1 "2ms 빠른 실패로 열림"(`compose.gateway-bulkhead.yml` 머리 주석) |
| H. 안쪽 시한 100ms 초과 | 2~4 | 실패(`RedisLookupTimeout`) | 몰림 때 가능 | `GatewayAuthenticationFilter.java:29`. ISE-230 원인별 지표(`AuthRedisFailures`)로 나뉘어 보인다 |

- C2의 "Redis 조회 평균 0.3ms → 1.9ms"가 어느 지표인지는 기록에 없다(확인 못 함). 차단기 호출 시간 평균이면 평균은 낮아도 일부 호출이 50ms를 넘어 20건 창의 절반을 채웠다는 뜻이 된다. 짧은 순간에 몰리는 B(GC 멈춤)나 A(머리 막힘)가 이런 모양을 만든다(추정).

### 정리: 차단기가 오해하는 구조
차단기는 "Redis가 아프다"를 감지하려고 둔 것인데, 지금 재는 시간에는 Gateway 자신이 바쁜 신호가 섞인다. 그래서 Gateway가 CPU 포화에 가까워지면 차단기가 Redis 탓으로 열리고, 인증 요청 전체를 10초 동안 막는다. 3-4의 진동(열림 → 닫힘 → 다시 열림)은 이 오해로 설명된다(추정).

### 선택지 비교
| 선택지 | 하는 일 | 기대 | 감수할 점 |
|---|---|---|---|
| A. 먼저 잰다 | 몰림 구간에서 스레드별 CPU와 GC 멈춤 시간을 본다 | A·B·C 중 무엇인지 가린다 | 측정 한 번이 든다 |
| B. 느린 호출 기준을 넓힌다(E안 100ms·80%, 10초 창) | 짧은 Gateway 쪽 대기에는 열리지 않게 한다 | 오해로 열리는 일이 준다. 11/10 E에서 끝까지 안 열렸다 | Redis가 실제로 느려질 때도 늦게 감지한다. 원인은 그대로다 |
| C. Lettuce가 응답 신호를 다른 스레드로 넘기게 한다(`publishOnScheduler`) | I/O 스레드는 읽기·풀기만 하고 라우팅은 계산 스레드가 맡는다 | A(머리 막힘)를 줄인다 | 호출마다 스레드를 한 번 더 건너 CPU를 조금 더 쓴다. 효과는 재 봐야 안다 |
| D. 연결을 여러 개 쓴다(풀 또는 연결 수 늘리기) | 응답 처리를 여러 I/O 스레드로 나눈다 | A를 줄인다 | 설정과 연결 수가 늘어난다. 반응형 경로의 풀 설정 방법을 확인해야 한다 |
| E. 로그아웃 목록을 Gateway 메모리에 캐시한다 | Redis 조회 자체를 줄인다 | 차단기 문제가 근본적으로 줄어든다 | 로그아웃 반영이 캐시 시간만큼 늦다. 보안 성질이 바뀌어 ADR 대상이다 |

### 추천
A부터 한다. C·D는 "스레드 하나가 막힌다"가 맞을 때만 효과가 있으므로, 스레드별 CPU를 보기 전에 고르면 근거 없는 변경이 된다. B(E안)는 이미 측정 근거가 있어 영은님 재측정 결과와 함께 판단한다.

감수할 점: A만으로는 아무것도 나아지지 않는다. 원인을 가리는 데 측정 한 번을 쓴다.

### 확인할 질문과 서버 명령(강민이 실행)
| 질문 | 확인 방법 |
|---|---|
| Lettuce I/O 스레드 하나가 100%에 붙나 | 몰림 중 `docker top <gateway 컨테이너> -eLo tid,pcpu,comm`로 스레드별 CPU를 보고, 높은 tid를 16진수로 바꿔 `docker exec <gateway 컨테이너> jcmd 1 Thread.print`의 `nid=0x...`와 맞춰 이름(`lettuce-epollEventLoop-*`인지)을 본다 |
| GC 멈춤이 50ms를 넘나 | Grafana `jvm_gc_pause_seconds_max{application="gateway"}` |
| CPU 차례 대기가 있나 | 측정 중 `vmstat 1`의 `r` 열 |
| C2의 "Redis 조회 평균"은 어느 지표였나 | 3-4 C2를 적은 측정 기록이나 Grafana 패널 식 확인 |

## 11. 추가 질문: `auth-redis` 장애 처리에 재시도(retry)는 없나

### 짧은 답
**요청 처리 경로에는 재시도가 없다.** Redis 조회가 실패하거나 시한을 넘기면 한 번에 503 `SERVICE_UNAVAILABLE`로 끝난다. 다시 보내는 주체는 서버가 아니라 **클라이언트 화면**이다(503마다 `Retry-After: 1`을 보고 약 1~1.2초 뒤 자동 재시도, 9절 7번).

### 확인한 곳
| 위치 | 재시도 | 출처 |
|---|---|---|
| 인증 필터의 Redis 조회 | 없음. `redisBreaker.run(lookup)` 뒤 `onErrorMap`으로 바로 503 예외로 바꾼다 | `GatewayAuthenticationFilter.java:93-104` |
| Spring Cloud CircuitBreaker 감싸기 | 없음. 순서는 시간 제한 → 차단기 → 벌크헤드뿐이고 재시도 연산자가 없다 | `ReactiveResilience4JCircuitBreaker.run`(5.0.3 소스, 1-2절) |
| `resilience4j.retry` 설정 | 없음 | `config-repo/gateway.yml`, `config-repo/application.yml` 검색 |
| Gateway 라우트 `Retry` 필터 | 없음. SA 9-4 결정대로 POST 재시도 필터를 두지 않는다 | `config-repo/gateway.yml:12-44`, `SA MASTER.md` 9-4 S-26 |
| `@Retryable`·`RetryTemplate` | 없음 | `gateway/src/main` 검색 |
| 기동 때 Redis 연결 확인 | **있음, 요청 경로 아님.** 기동 시 `PING`을 2초 시한으로 보내고 200ms 간격 2번 더 시도한다. 실패하면 Gateway가 뜨지 않는다 | `GatewayConfiguration.java:19-21,35-45` |
| `spring-retry` 의존성 | 있음. Config 서버 연결 재시도(`spring.config.import`의 `max-attempts=6`)용이다 | `gateway/build.gradle:6`, `gateway/src/main/resources/application.yml` |

### 재시도처럼 보일 수 있는 것: Lettuce 재연결
- Lettuce는 연결이 끊기면 자동으로 다시 연결하고(`DEFAULT_AUTO_RECONNECT = true`, `ClientOptions.java:52`), 끊긴 동안 들어온 명령을 버리지 않고 큐에 쌓았다가 다시 연결되면 보낸다(`DEFAULT_DISCONNECTED_BEHAVIOR = DEFAULT`, 큐 크기 기본 `Integer.MAX_VALUE`, `ClientOptions.java:63,75`).
- 하지만 인증 필터의 안쪽 시한이 100ms라, 사용자 요청은 100ms 안에 503으로 끝난다. 큐에 남은 명령은 나중에 보내져도 결과를 받을 구독자가 없다(추정, 동작은 확인 안 함). Redis가 오래 끊기면 이런 명령이 메모리에 쌓일 수 있다는 점은 확인할 질문이다.

### 재시도가 없는 것이 맞나
| 선택지 | 기대 | 감수할 점 |
|---|---|---|
| A. 지금처럼 서버 재시도 없음 | 과부하 때 Redis 호출이 2배·3배로 늘지 않는다. 실패가 100ms 안에 확정된다 | 순간 끊김 한 번에도 503이 난다 |
| B. 짧은 재시도 1번(예: 10~20ms 뒤) | 순간 끊김을 사용자에게 숨긴다 | 원인이 과부하면 부하를 키운다. 100ms 시한·벌크헤드 허가를 더 오래 쥔다. 차단기가 열린 동안에는 의미가 없다 |

지금 문제는 순간 끊김이 아니라 과부하(9·10절)라서 A가 맞다고 본다. 재시도는 클라이언트 쪽 하나로 충분하고, 그쪽은 `Retry-After`를 늘리고 흩뿌리는 것(9절 선택지 B)이 손볼 곳이다.

## 12. 추가 질문(제안): Redis 시한을 더 빡빡하게, 느린 호출 기준은 더 넓게 하면 되지 않나

### 강민의 제안
Redis는 평균 약 2ms라 100ms에 닿을 일이 거의 없다. 그러니 Redis 시한을 낮춰 Redis 장애를 더 예민하게 잡고, Gateway 쪽 느린 호출 기준은 더 넓게 잡아 Gateway가 바쁠 때는 덜 열리게 하자.

### 판단: 목표는 맞고, 수단은 지금 구조에서 반대로 작동한다
- 목표 "Redis 장애에는 예민하게, Gateway 혼잡에는 둔감하게"는 10절에서 찾은 문제(차단기가 Gateway 혼잡을 Redis 탓으로 오해)를 정확히 겨냥한다.
- 하지만 **시한(100ms)과 느린 호출 기준(50ms)은 같은 시간을 잰다.** 둘 다 Gateway가 구독한 순간부터 응답이 돌아온 순간까지이고, 그 안에 Gateway 쪽 대기(Lettuce 스레드 밀림, GC 멈춤, CPU 차례 대기)가 들어간다(10절). 그래서 시한을 낮추면 "Redis에 예민"해지는 것이 아니라 **"Gateway 혼잡에 더 예민"**해진다.

### 시한을 낮추면 일어나는 일(코드 기준 추론)
| 순서 | 일 | 근거 |
|---|---|---|
| 1 | Gateway가 바빠 한 호출이 시한(예: 10ms)을 넘는다. Redis는 멀쩡하다 | 10절 상황 A·B·C |
| 2 | 시한 초과는 `RedisLookupTimeout`, 즉 **실패**로 세어진다(느린 호출이 아니다) | `GatewayAuthenticationFilter.java:95-96` |
| 3 | 그 요청은 차단기가 닫혀 있어도 **바로 503**이다 | `GatewayAuthenticationFilter.java:88-90` |
| 4 | 실패율이 50%를 넘으면 차단기가 열린다. 느린 호출 기준을 아무리 넓혀도 이 경로는 막지 못한다 | `config-repo/gateway.yml:61` |
| 5 | 시한이 느린 호출 기준보다 작으면 느린 호출 규칙은 **아예 작동할 일이 없다.** 시한에서 먼저 끊기기 때문이다 | 시한 10ms < 느린 호출 100ms면 100ms짜리 호출이 존재하지 않는다 |

- 예: GC가 한 번 20ms 멈추면(C3 GC 87ms/s) 그 순간 처리 중이던 호출이 모두 10ms 시한을 넘어 한꺼번에 실패가 된다. 지금 100ms 시한이면 살아남을 호출들이다(추정).
- 결국 제안대로 하면 판정이 "느린 호출"에서 "시한 초과 실패"로 옮겨 갈 뿐, 오해는 그대로이고 사용자 503은 늘어난다.

### "평균 2ms"에 대한 정정
- 1.9ms는 3-4 C2에서 **차단기가 열리기 직전, 몰림 중** 평균이고, 평소는 0.3ms였다. 어느 지표였는지는 기록에 없다(확인 못 함).
- 시한은 평균이 아니라 **꼬리(p99·p99.9, 가장 느린 1%·0.1%)**로 정해야 한다. 평균 2ms여도 일부가 50ms를 넘어 20건 창의 절반을 채울 수 있다. 지금 Gateway에는 이 꼬리를 보여 주는 히스토그램(분포 지표) 설정이 없다(`config-repo/*.yml`에 `percentiles`·`histogram` 없음). Redis 자체 지연을 따로 보는 수집기(redis_exporter)도 없다.

### 시한을 낮추는 것이 실제로 주는 이득
제안에 맞는 부분도 있다. Redis가 **정말 멈췄을 때**(응답 없음, 네트워크 끊김) 요청마다 시한만큼 벌크헤드 허가를 쥐고 기다린다. 시한 100ms·허가 25면 그동안 초당 약 250건만 시한까지 가고 나머지는 벌크헤드에서 거절된다(25 ÷ 0.1초, 계산값). 시한을 줄이면 진짜 장애 때 사용자가 503을 더 빨리 받고 허가도 빨리 돈다. 단, Redis가 아예 꺼진 경우(연결 거부)는 시한과 상관없이 즉시 실패라 이득이 없다.

### 선택지 비교
| 선택지 | 하는 일 | 기대 | 감수할 점 |
|---|---|---|---|
| A. 제안 그대로: 시한 낮춤 + 느린 호출 넓힘 | 시한 100 → 10~20ms, 느린 호출 100ms 이상 | 진짜 Redis 멈춤 때 빨리 실패 | Gateway 혼잡이 곧 실패·503이 된다. 느린 호출 규칙은 죽은 설정이 된다 |
| B. 판정을 하나로 합친다: 느린 호출 규칙을 끄고(기준 = 시한), 시한은 측정한 꼬리 + 여유로 정한다 | 차단기는 "시한 초과·연결 오류 실패율"만 본다 | 규칙이 하나라 설명이 쉽다. 강민 제안의 뜻("느린 건 너그럽게")을 그대로 담는다 | 시한 숫자가 꼬리 측정에 달려 있다. 측정 전에는 정할 수 없다 |
| C. Redis 탓인 실패만 센다 | 벌크헤드 거절(`BulkheadFullException`)을 차단기 실패에서 빼고, 연결 오류·시한 초과만 센다(6절 B) | Gateway 혼잡으로 생긴 거절이 차단기를 열지 않는다 | 시한 초과에는 여전히 Gateway 대기가 섞인다 |
| D. 판정에 쓰는 시간을 Redis에 가깝게 잰다 | Lettuce 명령 지연 지표(쓰기 → 응답 읽기)나 redis_exporter로 Redis 쪽 시간을 따로 본다 | 오해의 원인(섞인 시간) 자체를 줄인다 | 차단기 판정에 직접 쓰려면 사용자 정의 코드가 필요하다. 관측용으로만 쓰는 것이 현실적이다 |

### 추천
B + C. 강민 제안의 뜻("Redis에는 예민, Gateway 혼잡에는 둔감")은 시한을 낮추는 것보다 **센 대상을 고르는 것(C)**과 **규칙을 하나로 합치는 것(B)**으로 더 잘 이뤄진다. 시한 숫자는 낮출지 그대로 둘지 측정한 꼬리로 정한다. 지금 데이터로는 100ms보다 낮출 근거가 없다(꼬리 측정이 없다).

감수할 점: B는 꼬리 측정이 먼저라 바로 적용할 수 없다. C는 Gateway 혼잡을 차단기에서 떼어 내는 대신, 혼잡은 벌크헤드 거절 503으로 따로 드러난다(목표한 모양이다). 시한은 SA 9-4의 Redis 시한 100ms `[가정]`이고 `gateway.yml`·인증 필터는 ISE-230 범위라, 바꿀 때는 ISE-230 담당과 맞추고 `docs/decisions/`에 남긴다.

## 13. 추가 질문: Redis 시한을 재는 주체가 Gateway인가

### 짧은 답
**그렇다.** Redis 서버는 "이 요청이 100ms를 넘었다"를 모른다. 시한·느린 호출 판정은 모두 클라이언트인 Gateway JVM 안의 타이머가 잰다. 그래서 Gateway가 바쁘면 Gateway 타이머가 재는 시간에 그 바쁨이 섞인다(10절).

### Gateway 안의 타이머들
| 타이머 | 값 | 재는 구간 | 넘으면 | 출처 |
|---|---|---|---|---|
| 필터 안쪽 시한 | 100ms | 조회 구독 → 응답 신호 | `RedisLookupTimeout` 실패 → 503 | `GatewayAuthenticationFilter.java:29,95-96` |
| 차단기 느린 호출 기준 | 50ms | 차단기 구독 → 응답 신호(`CircuitBreakerSubscriber`의 `start`) | 느린 호출로 기록(요청은 통과) | `config-repo/gateway.yml:62`, 10절 |
| Spring Cloud TimeLimiter | 1초 | 차단기 바깥 전체 | 시한 초과 실패 | `TimeLimiterConfig.java:14` |
| Lettuce 명령 시한 | 100ms | Lettuce 명령 단위 | 명령 시한 초과 | `config-repo/application.yml:51`. 반응형 호출에도 걸리는지는 확인 못 함 |

- 지금 실제로 먼저 걸리는 것은 필터 안쪽 100ms다. 1초 TimeLimiter는 사실상 닿지 않는다.

### Redis가 스스로 재는 시간
| Redis 쪽 기능 | 재는 것 | 차이 |
|---|---|---|
| `SLOWLOG` | 명령 **실행** 시간만(기본 10ms 넘는 명령 기록) | 네트워크·대기·Gateway 쪽 시간이 빠진다 |
| `LATENCY` 모니터 | 서버 내부 지연 사건(fork, 디스크 쓰기 등) | 켜야 쓴다(`latency-monitor-threshold`) |
| `timeout` 설정 | 쉬는 연결을 끊는 시간(기본 0, 끊지 않음) | 요청 시한과 무관하다 |

- 그래서 "Redis가 느렸나"는 Redis 쪽(`SLOWLOG`, `redis-cli --latency`)으로, "Gateway가 기다렸나"는 Gateway 쪽(차단기 호출 시간, ISE-230 실패 로그의 `elapsedMs`·`thread`)으로 따로 봐야 가를 수 있다.

### 오해하기 쉬운 점: SLOWLOG는 응답에 실려 오지 않는다
- 강민이 확인한 이해: "Redis가 SLOWLOG로 잰 시간을 응답과 함께 Gateway에 보내고, 판단은 Gateway가 한다" → **아니다.**
- Redis의 응답(RESP 프로토콜)에는 결과값만 있다. `EXISTS`면 정수 `1` 또는 `0` 하나다. 실행 시간은 실려 오지 않는다.
- SLOWLOG는 Redis 서버 메모리 안에 따로 쌓이는 기록이다. 사람이나 수집기가 `SLOWLOG GET`으로 따로 물어봐야 보인다. 명령별 누적 실행 시간(`INFO commandstats`의 `usec_per_call`)도 같다.
- 그래서 Gateway는 Redis가 잰 시간을 한 번도 보지 못하고, 요청마다 **자기 스톱워치**(위 표의 타이머)로만 판단한다. Redis 쪽 시간을 쓰려면 redis_exporter 같은 수집기로 Prometheus에 모아 사람이 비교하는 관측용이 된다. 요청 하나하나의 차단기 판정에는 쓸 수 없다.

| 시간 | 누가 재나 | 어디에 남나 | 차단기 판정에 쓰이나 |
|---|---|---|---|
| 명령 실행 시간 | Redis | SLOWLOG, `INFO commandstats`(Redis 메모리) | 아니다 |
| 요청 → 응답 신호 시간 | Gateway 타이머 | 차단기 상태, ISE-230 실패 로그 `elapsedMs` | 그렇다 |

### Gateway 타이머 하나에 들어가는 구간
Gateway는 Redis가 실제로 일한 시간을 요청 단위로 알 수 없다. 아래를 모두 더한 한 숫자만 본다. 그래서 시간이 늘어도 어느 구간이 늘었는지 구별하지 못한다.

| 구간 | Gateway 타이머에 들어가나 |
|---|---|
| 조회를 시작한 뒤 쓰기 요청이 Netty 이벤트 루프 작업 큐에서 기다리는 시간 | 들어간다 |
| 소켓 쓰기와 컨테이너 사이 네트워크 | 들어간다 |
| Redis 안에서 차례를 기다리는 시간 + 실행 시간(Redis가 일한 시간은 이 일부) | 들어간다 |
| 응답이 도착한 뒤 Lettuce I/O 스레드가 읽어 풀기까지 기다리는 시간 | 들어간다 |
| 그 사이 GC 멈춤, CPU 차례 대기 | 들어간다 |

이것은 이 설정만의 문제가 아니라 클라이언트 쪽 시한의 공통 성질이다. HTTP 클라이언트 응답 시한, DB 연결 대기 시한도 모두 클라이언트가 체감한 시간을 잰다. 원인을 가리려면 Redis 쪽(`SLOWLOG`, `INFO commandstats`, `redis-cli --latency`)과 Gateway 쪽(차단기 호출 시간, ISE-230 실패 로그 `elapsedMs`·`thread`)을 같은 구간에서 나란히 본다. 몰림 때 Gateway 쪽은 큰데 Redis 쪽이 조용하면 시간을 쓴 곳은 Gateway 안이다.

### 서버 명령(강민이 실행)
| 질문 | 명령 |
|---|---|
| 몰림 때 Redis가 실제로 느린 명령을 냈나 | `docker exec <redis 컨테이너> redis-cli SLOWLOG GET 20` |
| Redis까지 왕복 지연(같은 장비 안 다른 클라이언트에서 본 값) | `docker exec <redis 컨테이너> redis-cli --latency-history -i 5` |

## 14. 측정 값 정하기: 느린 호출 100ms를 고정했을 때 시한·벌크헤드·실패율

### 정하는 원칙
| 값 | 원칙 | 근거 |
|---|---|---|
| 시한 | 느린 호출 기준보다 커야 한다. 그래야 "느리지만 응답한" 구간(느린 호출)과 "응답 없음"(실패)이 나뉜다 | 12절 5번 |
| Lettuce 명령 시한 | 필터 시한보다 커야 한다. 그래야 필터 시한이 먼저 걸려 `RedisLookupTimeout`으로 분류된다 | `AuthRedisFailures` 원인 분류 |
| 벌크헤드 | 목표 처리량 × "정상이라고 볼 한 건 시간"(리틀의 법칙). 이 이상 머무는 호출은 혼잡으로 보고 빨리 거절한다 | 6·7절 |
| 실패율 | 벌크헤드 거절을 빼면 실패는 시한 초과·연결 오류뿐이다. 측정에서 바꾸는 값을 줄이려고 지금 값을 유지한다 | 6절 B, 11절 |

### 추천 값
| 값 | 운영 | E안 | 추천 | 이유 | 감수할 점 |
|---|---|---|---|---|---|
| 느린 호출 기준 | 50ms | 100ms | **100ms(강민 고정)** | — | — |
| 느린 호출 비율 | 50% | 80% | 80% | E안 유지. 바꾸는 값을 줄인다 | — |
| 필터 시한 | 100ms | 100ms | **200ms** | 느린 호출(100ms)의 2배. 100~200ms를 "느린 호출" 구간으로 남긴다. GC 멈춤(수십 ms)이 겹쳐도 실패로 바로 넘어가지 않는다 | 진짜 Redis 멈춤 때 사용자가 503까지 최대 200ms 기다린다 |
| Lettuce 명령 시한 | 100ms | 100ms | 300ms | 필터 시한보다 크게 둬 원인 분류를 지킨다 | 반응형 호출에 걸리는지 확인 못 함이라 안전하게 둔 값이다 |
| 벌크헤드 | 25 | 100 | **50 + 거절을 차단기에서 제외** | 측정 통과선 1,000/s × 50ms = 50(계산값). 한 호출이 50ms(운영 느린 호출 기준)를 넘게 머물 만큼 밀리면 혼잡으로 보고 거절한다. 100의 과수용과 25의 잦은 거절 사이다 | 50은 측정 근거가 없는 계산값이다. 1,200/s 이상에서는 거절 503이 보일 것이다(C3의 25는 1,200/s에서 4.8%) |
| 실패율 기준 | 50% | 50% | 50% | 유지. 거절 제외로 실패의 뜻이 "Redis 응답 없음"으로 좁아진 것만 본다 | Redis 장애 감지가 더 빨라지지는 않는다. 30% 등으로 낮추는 것은 이번 결과를 보고 정한다 |
| 창·최소 호출·열림·반열림 | 건수 20·20·10s·5 | 시간 10s·500·5s·20 | E안 유지 | 바꾸는 값을 줄인다 | 초당 50건 미만이면 10초 창에 500건이 안 차 차단기가 판정하지 않는다(12절) |

진짜 Redis 멈춤 때 시한까지 기다리는 요청은 50 ÷ 0.2초 = 초당 250건이고 나머지는 벌크헤드에서 바로 거절된다(계산값).

### 측정 순서(한 번에 하나씩)
| 회 | E안에서 바꾸는 것 | 보는 것 |
|---|---|---|
| 1 | 필터 시한 200ms, Lettuce 300ms | 시한을 띄운 효과. 차단기 상태, 원인별 실패, p95 |
| 2 | 1회 + 벌크헤드 50 + `ignoreExceptions: BulkheadFullException` | 벌크헤드를 낮추고 차단기와 떼어 낸 효과. 거절 비율, p95·p99, Gateway CPU·GC |

- 단계는 E안과 같다(웜업 뒤 1,000·1,200·1,300·1,400/s). 앞 추첨의 DB 처리와 겹치지 않게 Postgres CPU가 내려간 뒤 시작한다(3-3절).
- 필터 시한 설정값과 `ignoreExceptions` 덮어쓰기는 ISE-230 범위의 코드·파일 변경이 먼저 필요하다. `ignoreExceptions`는 설정 키가 있음만 확인했다(`CommonCircuitBreakerConfigurationProperties.java:171-172,351`, resilience4j-framework-common 2.3.0). 이 경로에서 실제로 적용되는지는 테스트로 확인해야 한다.

## 15. 추가 질문: 벌크헤드를 25로 다시 낮추면 실패율이 줄지 않나

### 질문
벌크헤드를 높이는 것이 오히려 과수용으로 문제이니, 25로 다시 낮추는 편이 실패율을 낮추는 데 도움이 되지 않는지 물었다.

### 짧은 답
"높이면 과수용"은 맞다(6절). 하지만 **지금 구조 그대로 25로 낮추면 실패율은 오른다.** 벌크헤드가 차단기 안쪽에 있어 벌크헤드 거절(`BulkheadFullException`)이 차단기에 실패로 세어지기 때문이다(1-2절 감싸는 순서). 25가 도움이 되려면 거절을 차단기 집계에서 빼는 설정(`ignoreExceptions`)과 짝지어야 한다.

### 근거
| 측정 | 벌크헤드 | 결과 | 출처 |
|---|---|---|---|
| C2 | 25, 운영 차단기 | 1,000/s에서 차단기가 열리고 이후 열림·닫힘 반복 | 3-4 C2 |
| C3 | 25, 차단기만 완화 | 1,200/s에서 남은 자리 0, 거절 4.8% | 3-4 C3 |
| Q1 | 25와 100 | 둘 다 1,000/s 통과·2,000/s 실패. 대기열 진입 경로의 한도는 벌크헤드가 정하지 않았다 | 영은님 판단 기록 `:39` |

- 시한을 200ms로 올리면 한 호출이 허가를 쥐는 시간이 길어져 25는 더 빨리 찬다(리틀의 법칙).

### 25 + 거절 무시와 100 비교
| | 벌크헤드 25 + 거절 무시 | 벌크헤드 100(E안) |
|---|---|---|
| 몰릴 때 사용자 | 503이 빨리, 조금씩 | 503은 적지만 응답이 느려진다 |
| 처리 중인 요청 | 상한이 작아 덜 불어난다 | 더 받아 장비 전체의 일이 는다 |
| 차단기 | Redis만 본다 | 넘칠 때 거절이 실패로 쌓인다 |
| 진짜 Redis 장애 때(시한 200ms) | 초당 약 125건만 시한까지 기다린다 | 초당 약 500건 |

이 비교 뒤 14절처럼 중간값 50과 거절 무시를 짝지은 안으로 정했다.

## 16. 추가 질문: 거절을 무시하면 실패율에 안 들어가나, 그리고 어떻게 반영했나

### 짧은 답
**안 들어간다.** 무시 예외는 성공으로도 실패로도 세지 않고, 빌려 간 허가만 돌려준 뒤 "무시됨" 이벤트를 낸다. 창에도, 최소 호출 수에도 들어가지 않는다. 요청 자체는 사용자에게 여전히 503이다.

### 라이브러리 소스로 확인
| 확인 | 내용 | 출처 |
|---|---|---|
| 무시 예외 처리 | `ignoreExceptionPredicate`에 맞으면 `releasePermission()` 후 무시 이벤트만 내고 끝난다. 아니면 기록 대상이면 실패로, 그 밖이면 성공으로 센다 | `CircuitBreakerStateMachine.handleThrowable`(resilience4j-circuitbreaker 2.3.0) |
| 설정 키 | `ignoreExceptions` | `CommonCircuitBreakerConfigurationProperties.java:171-172,351`(framework-common 2.3.0) |
| 지표 | 호출 수 지표에 `kind` 이름표 `failed`·`successful`·`ignored`·`not_permitted`가 있다 | `AbstractCircuitBreakerMetrics.java:30-34`(micrometer 2.3.0) |

- 무시된 거절은 `resilience4j_circuitbreaker_calls_seconds_count{name="auth-redis",kind="ignored"}`, ISE-230 원인별 실패 수 `bulkhead_full`, 벌크헤드 남은 자리 `resilience4j_bulkhead_available_concurrent_calls`로 따로 본다.

### 반영 과정(ISE-233)
| 단계 | 결과 |

| 변경 | 인증 필터 시한을 `auth.redis-timeout`(기본 100ms) 설정으로 바꾸고, `loadtest/deploy/compose.gateway-bulkhead.yml`에 `AUTH_REDIS_TIMEOUT`·`AUTH_LETTUCE_TIMEOUT`·`AUTH_IGNORE_EXCEPTIONS`와 재측정 값 두 묶음을 더했다. 별도 세션·작업 공간·브랜치 `feat/ISE-233-auth-redis-timeout-config`에서 했다 |
| 검증 | Gateway 테스트 100건 → 105건 모두 통과. 일부러 틀리게 바꾼 4개를 테스트가 모두 잡았다(세션 보고, 이 노트 작성자가 다시 실행하지는 않음). `ignoreExceptions`가 켜지면 거절이 `ignored`로 세어지는지는 컨텍스트 테스트(`AuthRedisResilienceContextTest`)가 확인한다 |

## 확인 못 함
- 배포 서버 컨테이너 안 `availableProcessors()` 값과 실제 스레드 이름·수(저장소와 라이브러리 소스로 추론만 했다)
- Postgres `max_connections` 실제 값
- D 측정에서 gateway·reservation·Postgres 말고 다른 컨테이너의 CPU 사용량
- D와 E의 p95 차이 원인
- Gateway HTTP 서버와 클라이언트가 같은 이벤트 루프를 쓰는지(Reactor Netty 기본 동작으로 보이나 이 저장소 구성에서 확인 안 함)
- Lettuce 명령 시한(`spring.data.redis.timeout`)이 반응형 호출에도 걸리는지(14절에서 필터 시한보다 크게 둬 피해 갔다)
- Lettuce I/O 스레드 하나가 몰림 때 100%에 붙는지(10절 상황 A, 서버에서 스레드별 CPU를 재야 한다)
- C2의 "Redis 조회 평균 0.3ms → 1.9ms"가 어느 지표였는지
- 시한 200ms·벌크헤드 50·거절 무시를 배포 서버에서 잰 결과(ISE-233 재측정 전)
