# 측정 도구 변경은 언제 커밋·푸시하고, main에 넘겨야 하나

## 질문
11/10 ISE-94 배포 측정 중 k6 스크립트(L1 `msg` 태그)를 고친 뒤 나온 질문 두 개다.
1. 커밋·푸시를 지금 해야 하나? 나중에 몰아서 하면 안 되나?
2. 그럼 main에 넘겨야 한다는 소리인가?

## 짧은 답
- 부하 발생기에서 쓸 측정 도구는 측정 전에 커밋·푸시해야 한다. 발생기는 git으로 원격 저장소의 커밋을 받아 실행하므로, 푸시하지 않은 변경은 발생기에 없다. 측정 결과와 학습 기록 같은 문서는 나중에 몰아서 올려도 된다.
- main에 넘길 필요는 없다. 발생기는 아무 브랜치나 받을 수 있다. 오히려 측정 중에는 main에 머지하면 안 된다. Jenkins가 main의 새 커밋을 배포하면서 측정 모드가 풀리기 때문이다.

## 자세히

### 1. 발생기는 코드를 어떻게 받나
- 발생기에서는 각자 폴더 `~/<영문 이름>/iseonjwa`에 저장소를 clone하고 `git switch dev`로 받는다. 측정 날에는 `git pull`로 최신 `dev`를 받는다(`docs/guides/loadgen.md` 59-63행).
- git은 원격에 있는 브랜치면 무엇이든 받을 수 있다. 기능 브랜치(`test/ISE-...-...`)를 푸시하고 발생기에서 그 브랜치로 바꾸면 main·dev에 머지하지 않고도 쓸 수 있다. 문서에 적힌 기본 흐름은 `dev`이고, 기능 브랜치로 받는 절차는 문서에 없다. 실제 발생기에서 기능 브랜치로 바꿔 본 기록은 확인 못 함이다.
- 그래서 "지금 푸시해야 하나"의 답은 무엇을 올리느냐로 갈린다.
  | 변경 | 언제 올리나 | 이유 |
  |---|---|---|
  | 발생기에서 실행할 k6 스크립트·측정 도구 | 측정 전 | 발생기가 git으로 받아야 실행할 수 있다 |
  | 측정 결과, 학습 노트, 판단 기록 | 측정 뒤 몰아서 | 측정 실행에 영향이 없다 |
  | 서버 설정·애플리케이션 코드 | 측정 중에는 올리지 않음 | 배포 서버 코드가 바뀌어 측정 조건이 흔들린다(2절) |

### 2. main은 배포 서버 코드다
- `Jenkinsfile` 1행: "main의 새 커밋을 배포 서버에 배포하는 파이프라인(ISE-175)". Jenkins는 main을 2분마다 확인해 새 커밋이면 배포한다(`docs/guides/deploy-server-access.md` 10행, `docs/design/infra/deployment.md` 29행).
- 배포는 `compose.yml`과 `compose.deploy.yml`만으로 다시 띄운다(`script/deploy/deploy.sh` 48-58행, [Gateway 기본 벌크헤드 노트](2026-11-09-gateway-default-bulkhead.md) 4-2절). 측정 모드(`loadtest/deploy/compose.measure.yml`과 덮어쓰기 파일)가 그 순간 풀린다.
- 그래서 규칙이 있다. "측정하는 동안에는 main 릴리스를 하지 않는다. Jenkins가 측정 중에 배포를 시작한다"(`docs/guides/deploy-server-access.md` 123행), "측정 중 main 머지 금지 — Jenkins가 2분마다 main을 보고 배포하면 측정 모드가 풀린다"(`docs/guides/loadgen.md` 34행). 측정 모드 시작 알림에도 "main 머지 금지"를 넣는다(같은 문서 81행).
- 선택지 비교:
  | 안 | 발생기 반영 | 배포 서버 영향 | 판단 |
  |---|---|---|---|
  | main에 머지 | 됨 | Jenkins 배포로 측정 모드가 풀리고 앱 컨테이너가 새로 만들어진다 | 측정 중 금지 |
  | dev에 머지 | 됨(`git pull`) | 없다. Jenkins는 main만 본다 | 이번에 쓴 방식 |
  | 기능 브랜치만 푸시 | 됨(브랜치 전환) | 없다 | 가능. 문서화된 절차는 아니다 |

### 3. 측정 도구 커밋을 기록표에 따로 적는 이유
- 서버와 발생기는 서로 다른 커밋으로 돈다. 11/10 측정 기록표는 "측정 모드 on 커밋 `0e77953`"(배포 서버, main)과 "발생기 `6be2f2b`(L2-a 1회), `234a839`(L2-a 2·3회, L2-b, L1)"를 따로 적었다. 오후 병목 탐색은 발생기 `1abd8ab`이다(`docs/design/lottery/numbers-and-measurement.md` 3-3절 기록표, 3-4절 머리).
- 이유는 재현성(reproducibility, 같은 조건으로 다시 재면 같은 결과가 나오는 성질)이다. 같은 서버 코드라도 k6 스크립트가 다르면 요청 모양·태그·판정이 달라질 수 있다. 서버 커밋과 발생기 커밋이 둘 다 있어야 나중에 그 측정을 그대로 다시 돌릴 수 있다.
- 예: 기록표에는 `234a839`가 "L1 태그 PR 450이며 L2 동작과 무관"이라고 적혀 있다. 발생기 커밋이 회차 중간에 바뀌었지만 L2 결과 비교에는 영향이 없다는 판단을 기록으로 남긴 것이다.

### 4. scp로 파일만 옮기는 대안
- 방법: 고친 k6 파일을 커밋하지 않고 `scp`로 발생기 폴더에 복사해 실행한다.
- 얻는 것: 푸시·PR·머지를 기다리지 않는다. 시험 삼아 한 번 돌려 볼 때 빠르다.
- 감수할 점:
  - 발생기의 실제 파일이 어느 커밋과도 같지 않다. 기록표의 "발생기 커밋"이 실행한 코드를 설명하지 못해 커밋 해시로 재현할 수 없다.
  - 발생기 폴더에 커밋되지 않은 변경이 남아 다음 `git pull`이 충돌하거나, 다른 사람이 같은 파일로 착각할 수 있다.
  - 굳이 쓰면 기록표에 파일 경로와 내용(또는 파일 해시)을 그대로 적고, 측정 뒤 같은 내용을 커밋한다. 덮어쓰기 파일을 저장소 밖에 두고 쓸 때의 원칙과 같다(`docs/learning/kangmin/qna/2026-11-09-gateway-default-bulkhead.md` 4절).
- 이번에는 커밋·푸시 후 dev 머지(PR 450)로 받았다.

### 5. PR 450 제목에서 ISE 번호를 뺀 이유
- 이 저장소는 브랜치 이름과 PR 제목의 `ISE-번호`로 Linear 이슈를 PR에 연결한다(`docs/guides/git-workflow.md` 63행). 브랜치 이름 규칙도 `{type}/ISE-{번호}-{주제}`다(47행).
- 연결된 PR이 머지되면 그 이슈가 자동으로 Done이 된다. 이슈의 남은 항목과 상관없다(같은 문서 90행, 93행. 11/2 ISE-85~93, ISE-88에서 확인). 인수인계 문서에도 같은 주의가 있다(`docs/context/handoff.md` 189행).
- PR 450의 L1 `msg` 태그는 ISE-94 측정을 위한 도구 변경이었다. 제목에 `ISE-94`를 넣었다면 머지 순간 측정이 진행 중인 ISE-94가 Done이 됐을 것이다. 그래서 번호를 뺐다.
- 확인한 것: 세션 시작 때의 커밋 목록에서 PR 450 커밋 제목 `test(loadtest): L1 실패 응답을 메시지 종류별로 세는 msg 태그를 더함 (#450)`에 ISE 번호가 없다. 같은 목록의 PR 447은 `#ISE-229`를 달고 있다. PR 450의 브랜치 이름에 ISE 번호가 없었는지는 확인 못 함이다. 브랜치 이름에 번호가 있으면 제목에서 빼도 연결된다.
- 감수한 점: 번호가 없으면 Linear 이슈에 PR이 자동 첨부되지 않는다. ISE-94 이슈에서 이 도구 변경을 찾으려면 이슈 댓글이나 측정 문서 기록표(3-3절 커밋 해시 행)로 이어 줘야 한다. 대안은 이슈를 쪼개는 것이다. 도구 변경용 작은 이슈를 따로 만들어 그 번호를 달면, 그 이슈만 Done이 되고 ISE-94는 열린 채로 남는다.

### 6. 면접 포인트
- "측정 결과를 어떻게 재현 가능하게 남겼나": 서버 배포 커밋과 부하 발생기 커밋을 따로 적고, 저장소 밖 임시 설정은 내용을 그대로 기록했다.
- "배포 자동화가 측정을 방해한 적이 있나": main 폴링 배포가 측정 모드를 풀 수 있어, 측정 중 main 머지 금지와 측정 도구는 dev로 받는 흐름을 썼다.

## 확인할 질문
- 발생기에서 기능 브랜치로 바꿔 측정한 적이 있나. 쓰려면 `loadgen.md`에 절차를 더할지 팀과 정한다.
- PR 450의 브랜치 이름에 ISE 번호가 들어 있었나(Linear 연결 여부).
