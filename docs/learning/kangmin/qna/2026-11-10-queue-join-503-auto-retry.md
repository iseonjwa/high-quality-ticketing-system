# Gateway 벌크헤드·차단기에 걸려 대기열 진입이 503이면 사용자가 다시 눌러야 하나, 자동으로 들어가나

## 질문
벌크헤드에 걸려 대기열에 들어가지 못하면 사용자가 다시 요청해야 하나, 기다리면 자연스럽게 대기열에 들어가나?

## 짧은 답
- 사용자는 아무것도 하지 않아도 된다. 대기열 화면이 503을 "지나가는 장애"로 보고 같은 진입 요청을 자동으로 다시 보낸다(`frontend/src/pages/queue/queueAdmission.ts`, 다시 보내는 상태 코드 0·429·502·503·504). 화면에는 연결 불안정 표시만 뜬다.
- 하지만 "기다렸다가 자리를 받는" 것은 아니다. 거절된 요청은 대기열 서비스에 닿지 않아 순번이 없다. 순번은 재시도가 성공한 시점에 정해지므로, 거절당한 만큼 뒤로 밀린다.
- 재시도 간격은 서버 `Retry-After`를 따른다. Gateway가 503마다 1초를 주므로 약 1~1.2초마다 다시 보낸다. 차단기가 10초 열려 있으면 사용자 한 명이 8~10번 헛요청을 보낸다(ISE-230 영은 코멘트).

## 설명
### 흐름
1. 사용자가 대기열 화면에 들어오면 `runQueueAdmission`이 진입(join) → 순번 조회(poll) → 토큰(token) 순서로 요청한다.
2. 어느 단계든 503이면 `connectionError`를 화면에 알리고 `queryRetryDelay`만큼 기다린 뒤 같은 요청을 다시 보낸다. 횟수 제한은 없다.
3. 기다리는 시간: 서버가 `Retry-After`를 주면 그 초 × (1 + 0~20% 흩뿌림). 주지 않으면 1·2·4·8초(상한 8초) 지수 증가이되 최소 3초.
4. 진입·조회·토큰 요청은 여러 번 보내도 결과가 같게 설계되어 있다(ADR 0031). 재시도가 겹쳐도 줄이 두 번 서지지 않는다.

### 단계별로 달라지는 것
| 503이 난 단계 | 순번 | 사용자가 겪는 것 |
|---|---|---|
| 진입 전(join) | 없음. 재시도 성공 시점에 새로 받는다 | 늦게 성공할수록 뒤 순번. 먼저 들어온 사람이 뒤로 밀릴 수 있다(공정성 손실) |
| 줄 선 뒤 조회(poll) | 대기열(Redis)에 그대로 있다 | 화면 순번 갱신만 늦다. 자기 차례가 와도 조회가 막히면 토큰 요청이 늦어진다 |
| 토큰 요청(token) | READY 상태 | 토큰 발급이 늦어진다. READY 유지 시간을 넘기면 놓칠 수 있다(확인 못 함) |

### 왜 이것이 차단기 설정과 이어지나
- 벌크헤드·차단기 거절은 대기열 서비스 앞(Gateway 인증)에서 난다. 그래서 대기열이 공정하게 줄을 세워도, 그 앞에서 무작위로 거절당한 사람은 순서가 섞인다.
- `Retry-After`가 1초로 짧으면 거절된 사람들이 1초마다 다시 몰려 반열림 순간에 차단기를 다시 열게 할 수 있다. 열림 시간에 맞춘 `Retry-After`(ISE-230 코멘트 1)가 필요한 이유다.

## 확인 못 함
- 조회가 오래 막히면 대기열이 그 사용자를 이탈로 보고 지우는지(지우면 404 `QUEUE_NOT_JOINED` → 화면은 "다시 줄 서기"). 대기열 설계 문서에서 찾지 못했다.
- READY 뒤 토큰을 받지 못하고 버틸 수 있는 시간
