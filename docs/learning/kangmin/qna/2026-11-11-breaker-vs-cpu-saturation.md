# 장비 CPU가 한도에 닿기 전에 차단기가 열려야 하지 않나

## 질문
G1 `auth-redis` 재측정(배포 서버 3차, 2026-11-10 UTC)에서 3,000/s까지 차단기가 열리지 않았고, 성공 처리량은 약 2,300~2,470/s에서 서버 CPU 99%로 멈췄다. 장비 CPU가 한도에 다다르기 전에 차단기가 켜져야 하지 않는가?

## 짧은 답
- **"CPU 한도 전에 무언가가 거절해야 한다"는 맞다. 그 일을 차단기가 하면 안 된다.**
- 차단기(서킷 브레이커)는 **뒤쪽 의존성(여기서는 Redis)이 아플 때** 호출을 끊어 의존성과 호출자를 보호한다. Gateway 자신이 바쁜 것(과부하)은 다른 장치, 즉 부하 차단(load shedding)이나 유입 제어(admission control)가 막는다.
- 차단기가 CPU 포화로 열리면 Redis는 멀쩡한데 인증 요청 **전체**가 열림 시간 동안 503이 된다. 92% 성공하던 부분 저하가 0% 성공인 전면 장애로 바뀐다. 1차 Q1(운영 설정)에서 2,000/s에 열려 인증 전체가 503이 된 것이 이 모양이고, ISE-230·ISE-233은 이 오해를 없애려는 변경이었다.
- G1에서도 CPU 한도 전에 거절한 장치는 있었다. 벌크헤드 거절(`bulkhead_full`, 응답 0~1ms)이다. 다만 **너무 늦게** 거절했다. 2,500/s에서 p95가 428~497ms로, Q1 목표 p95 200ms를 이미 넘었다. 빠진 것은 "목표 지연을 지키는 선에서 거절하는 유입 제어"다.

## 1. 두 장치가 지키는 것
| 장치 | 무엇을 보고 | 무엇을 지키나 | 거절 범위 |
|---|---|---|---|
| 차단기 | 의존성 호출의 실패율·느린 호출 비율 | 아픈 의존성에 계속 매달려 스레드·시간을 버리는 것 | 열려 있는 동안 그 의존성을 쓰는 요청 **전부** |
| 부하 차단·유입 제어(벌크헤드, 요청률 제한, 적응형 동시성 제한) | 지금 처리 중인 수, 초당 도착 수, 지연 증가 | 자기 자신(CPU·메모리·스레드)이 감당할 양 | 한도를 **넘친 만큼만** |

차단기에 과부하까지 맡기면 "넘친 만큼만"이 아니라 "전부"를 거절한다. 그래서 장애 대응의 목표 모양(처리량은 한도에서 정체, 지연은 묶이고, 넘친 만큼 빨리 거절)과 다르다.

## 2. 왜 G1에서 차단기가 안 열린 것이 맞는가
- 3차 값은 거절(`BulkheadFullException`)을 차단기 집계에서 뺐다(`ignored` 16,024, `failed` 0). 차단기의 "실패"는 이제 Redis 시한 초과·연결 오류만 뜻한다. 그 둘은 0건이었다. Redis는 실제로 아프지 않았으므로 열리지 않은 것이 설계대로다.
- 느린 호출(100ms·80%)로도 열리지 않았다. 차단기가 재는 시간에는 Gateway 쪽 대기도 섞이므로(2026-11-10 노트 10절), CPU 포화가 심해지면 언젠가 느린 호출로 열릴 수 있다. 그것은 오탐이다. 측정 중 느린 호출 비율이 몇 %까지 올랐는지는 기록하지 않아 **확인 못 함**이다.

## 3. 그럼 무엇이 CPU 한도 전에 거절해야 하나(선택지)
| 선택지 | 하는 일 | 기대 | 감수할 점 |
|---|---|---|---|
| A. 차단기 기준을 좁혀 CPU 포화도 잡게 한다 | 느린 호출 기준·비율을 낮춘다 | 포화 전에 열린다 | 열리면 인증 전체 503, 열림·닫힘 진동(3-4 측정). Redis 문제와 Gateway 문제를 구별하지 못한다. 1·2차로 돌아간다 |
| B. 벌크헤드를 더 낮춘다 | Redis 조회 동시 수를 줄여 일찍 거절 | 2회에서 50으로 낮추자 p95가 줄었다(2,000/s 208 → 157ms) | Redis 조회 한 번만 감싼다. 다른 CPU 비용(JWT 검증, 라우팅, 로그·추적)은 막지 않는다. 숫자가 장비에 묶인다 |
| C. Gateway 입구 요청률 제한 | 인스턴스당 초당 N건을 넘으면 바로 429/503 | 운영점(예: 통과선 2,000/s × 0.6~0.7, 계산값)에서 지연을 묶는다 | 고정값이라 장비·코드가 바뀌면 다시 재야 한다. Spring Cloud Gateway 기본 `RequestRateLimiter`는 Redis를 쓰므로 Redis 부하가 늘어난다. 로컬 방식(Resilience4j RateLimiter, Bucket4j 등)을 골라야 한다. 지금 Gateway 설정에는 요청률 제한이 없다(`config-repo` 확인) |
| D. 적응형 동시성 제한 | 지연이 늘면 허용 동시 수를 자동으로 줄인다(예: Netflix concurrency-limits) | 장비가 바뀌어도 한도를 스스로 찾는다 | 새 라이브러리와 조정 시간이 든다. 남은 일정(11/16 M4 마감)에 비해 크다 |
| E. 유입 자체를 줄인다 | G1 경로는 순번 폴링이다. `Retry-After`·폴링 간격으로 클라이언트가 덜 묻게 한다 | 대기열 설계가 원래 의도한 유입 조절과 맞는다. ISE-230 3번(`Retry-After` 분리)과 이어진다 | 클라이언트가 지켜야 효과가 있다. 진입(Q1) 몰림처럼 첫 요청이 몰리는 경우는 못 줄인다 |

## 4. 추천
- A는 거부한다. 1·2차에서 본 오탐 열림을 다시 만든다.
- 지금은 B(벌크헤드 50 + 거절 제외, 측정 근거 있음)와 E(`Retry-After`)로 간다. Gateway 설정 결정 기록(ISE-230 4번)에 "차단기는 Redis 장애만, 과부하는 벌크헤드·유입 제어가 맡는다"는 역할 나눔을 적는다.
- C는 결정 기록의 "바꿀 조건"에 둔다. 혼합 부하(진입 + 폴링) 측정에서 B만으로 p95 목표를 못 지키면 그때 넣는다.

감수할 점: B와 E만으로는 2,500/s 이상에서 p95 목표를 지키지 못한다(측정값 428~497ms). 이 구간은 "빠르게 거절은 되지만 받아 준 요청도 느리다"로 남는다.

## 확인 못 함
- G1 측정 중 차단기의 느린 호출 비율 최댓값
- 3,000/s 2회 p99 7.2s의 원인(벌크헤드 밖 대기 후보)
- 요청률 제한을 넣었을 때 p95가 실제로 묶이는지(측정 안 함)
