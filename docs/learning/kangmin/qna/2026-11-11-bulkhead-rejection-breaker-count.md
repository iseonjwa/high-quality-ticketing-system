# 벌크헤드 거절(503)을 auth-redis 차단기에서 예외로 뺄까, 실패로 세어 차단기를 열게 할까

## 질문
G1 `auth-redis` 재측정은 1회(벌크헤드 100, 거절을 실패로 셈)와 2회(벌크헤드 50, `ignoreExceptions: [BulkheadFullException]`)로 나눠 쟀다. 앞 노트([차단기 vs CPU 포화](2026-11-11-breaker-vs-cpu-saturation.md))는 "차단기는 의존성 장애, 부하 차단은 자기 과부하를 지킨다"고 답했다. 그렇다면 벌크헤드가 가득 차서 생긴 거절을 차단기 집계에서 빼는 것(예외)이 맞나, 실패로 세어 차단기를 열게 하는 것이 맞나?

## 짧은 답
- **지금 구성에서는 예외로 빼는 쪽(A)이 맞다.** 이 Gateway에서 벌크헤드가 차는 원인은 Redis가 아니라 Gateway CPU다. Redis 서버 지연은 0.1~0.8ms였고 Redis CPU는 9~17%였다. 거절을 실패로 세면 과부하가 "Redis 장애"로 바뀌고, 차단기가 열리면 넘친 만큼이 아니라 인증 요청 **전부**를 막는다.
- 빼도 Redis의 진짜 장애는 놓치지 않는다. 벌크헤드를 통과한 호출이 시한 초과(`lookup_timeout`)·연결 오류·느린 호출로 계속 기록되기 때문이다. 잃는 것은 감지 속도 약 1~2초다(계산값).
- 업계 기본값은 반대다. Hystrix는 벌크헤드 거절을 오류율에 넣는다. Hystrix는 의존성마다 스레드 풀을 따로 두므로 "풀이 찼다 = 그 의존성이 느리다"가 성립한다. 이 Gateway는 그 전제가 맞지 않는다.
- 덧붙일 것: 거절 비율 경보(C2). 예외로 빼면 과부하가 차단기 지표에서 사라지므로 따로 봐야 한다.

## 1. 사실 확인

### 1-1. 감싸는 순서(라이브러리 소스로 확인)
`ReactiveResilience4JCircuitBreaker.run`(spring-cloud-circuitbreaker-resilience4j 5.0.3) 92~106행:

```
toRun → bulkheadProvider.decorateMono(...)        // 가장 안쪽: 벌크헤드
      → transform(CircuitBreakerOperator.of(...)) // 그 바깥: 차단기
      → timeout(TimeLimiter 시한)                  // 가장 바깥: TimeLimiter(기본 1초)
```

Gateway 필터(`GatewayAuthenticationFilter.java:97-106`)가 넘기는 `toRun`은 `redis.hasKey(...).timeout(redisTimeout, RedisLookupTimeout)`이다. 그래서 바깥부터 **TimeLimiter → 차단기 → 벌크헤드 → Redis 조회(필터 시한)** 순서다. 벌크헤드 거절(`BulkheadFullException`)은 차단기 안쪽에서 나므로 차단기가 받는다.

### 1-2. 거절이 차단기에 어떻게 세어지나
`CircuitBreakerStateMachine.handleThrowable`(resilience4j-circuitbreaker 2.3.0) 203~220행:
1. `ignoreExceptions`에 맞으면 허가만 돌려주고 "무시됨" 이벤트를 낸다. 창에도, 최소 호출 수에도 들어가지 않는다.
2. 아니면 기록 대상(`recordExceptions`, 기본은 모든 예외)이면 실패로 센다.
3. 그 밖이면 성공으로 센다.

Resilience4j 문서도 기본값을 "모든 예외를 실패로 기록, 무시하는 예외 없음"으로 적고 있다. 따라서 **아무 설정도 하지 않으면 B(실패로 셈)가 기본**이다. 운영 설정(`config-repo/gateway.yml:58-65`)에는 `ignoreExceptions`가 없으므로 지금 운영은 B다.

### 1-3. 차단기가 열리면 무엇을 아끼나(코드로 확인)
필터는 JWT 해독(`decoder.decode`)을 먼저 하고 그다음 차단기를 부른다(`GatewayAuthenticationFilter.java:69-80, 87`). 그래서 차단기가 열려도 아끼는 것은 Redis 조회 한 번뿐이다. 요청 받기, JWT 서명 검증, 오류 응답 쓰기는 그대로 CPU를 쓴다. CPU가 병목일 때 차단기를 열어도 병목은 거의 줄지 않는다(코드 기준 추론, 측정 안 함).

### 1-4. 숫자
| 측정 | 설정 | 거절이 차단기에 | 결과 | 출처 |
|---|---|---|---|---|
| 1차 Q1 2,000/s(11/9) | 건수 창 20, 벌크헤드 25·100, 운영 차단기 | 실패 | **열림**. 벌크헤드 25: 빠른 실패 33건, 201 428건 / 503 19,573건. 벌크헤드 100: 실패 7건, 201 503건 / 503 19,498건. 느린 호출 0 | `open-peak-scenarios.md` 배포 서버 1차 Q1 표 |
| 1차 Q1 3,000/s(11/9) | 같음, 벌크헤드 25 | 실패 | **열림**. 2ms 이하 빠른 실패 10건. 201 41건 / 503 29,959건 | 같은 표 |
| G1 1회(11/10 UTC) | 시간 창 10초·최소 500건, 벌크헤드 100 | 실패 | 3,000/s까지 **안 열림**. failed 8,027 / 전체 약 334,000(약 2.4%, 계산값) | 배포 서버 3차 |
| G1 2회(11/10 UTC) | 같음, 벌크헤드 50 + 무시 | 무시 | 3,000/s까지 **안 열림**. failed 0, ignored 16,024 | 배포 서버 3차 |

여기서 하나를 짚어야 한다. **1회도 거절을 실패로 셌는데 안 열렸다.** 열리지 않은 이유는 시간 창 10초·최소 500건 덕분에 실패율이 50%에 한참 못 미쳤기 때문이다(3,000/s 단계의 거절도 시도의 약 7%). 1차가 열린 것은 건수 창 20이라 거절 10건이면 50%에 닿았기 때문이다. 즉 G1의 측정 범위에서 A와 B의 차이는 아직 드러나지 않았다. 차이는 **거절이 시도의 50%를 넘는 과부하**에서 나온다. 성공 처리량 약 2,400/s를 기준으로 하면 그 지점은 대략 4,800/s다(계산값, 측정 안 함).

## 2. 선택지 비교

### 2-1. 두 원인을 차단기가 구별할 수 있나
벌크헤드가 차는 경우는 두 가지다.
- (가) **Redis가 실제로 느려져** 한 호출이 허가를 오래 쥔다.
- (나) **Gateway CPU가 포화돼** Redis는 빨리 답했는데 응답 신호가 늦게 처리된다. G1에서 벌크헤드 50이 0까지 찼다. 리틀의 법칙으로 2,000/s에 50개가 차려면 한 호출이 약 25ms 머물러야 한다(계산값). Redis 서버 지연은 1ms 안이었으므로 나머지는 Gateway 쪽 대기다.

| 선택지 | (가) Redis 느림 | (나) Gateway CPU 포화 | 구별하나 |
|---|---|---|---|
| A. 예외로 뺀다(2회) | 통과한 호출이 느린 호출(100ms 초과)·시한 초과로 기록돼 열린다 | 거절은 세지 않는다. 통과한 호출만 본다 | **한다.** 거절 자체는 판정에 안 쓰고, 통과한 호출의 실제 결과로 판정한다 |
| B. 실패로 센다(1회, 운영 기본) | 거절 + 시한 초과가 함께 쌓여 더 빨리 열린다 | 거절이 실패로 쌓여 50%를 넘으면 열린다 | **못 한다.** 두 경우 모두 같은 `BulkheadFullException`이다 |
| C1. 벌크헤드를 차단기 바깥으로 옮긴다 | A와 같다 | A와 같다 | 한다. 거절이 구조상 차단기에 닿지 않는다 |
| C2. A + 거절 비율 경보 | A와 같다 | 차단기는 그대로 두고 사람에게 알린다 | 한다. 과부하를 따로 보이게 한다 |
| C3. 거절만 보는 별도 차단기 | — | 거절이 많으면 그 차단기가 전부 막는다 | B와 같은 문제다. 과부하에 "전부 거절"로 답한다 |

### 2-2. 나머지 기준
| 기준 | A | B | C1 | C2 |
|---|---|---|---|---|
| 과부하 때 거절 범위 | 넘친 만큼(벌크헤드) | 50%를 넘으면 열림 시간(5초) 동안 **전부** | 넘친 만큼 | 넘친 만큼 |
| Redis 진짜 장애 감지 | 시한 초과·연결 오류·느린 호출로 잡힌다. 다만 통과한 호출만 세므로 최소 500건이 차는 데 더 걸린다. 예: Redis 멈춤, 시한 200ms, 벌크헤드 50이면 통과 약 250/s, 500건까지 약 2초(계산값) | 거절도 세므로 몰림에서는 500건이 바로 찬다(2,000/s면 약 0.25초, 계산값) | A와 같다 | A와 같다 |
| `Retry-After` | 지금은 모든 503이 `Retry-After: 1`이다(`GatewayErrorWriter.java:28`). ISE-230 3번을 반영하면 거절은 "단발 실패"라 짧은 값을 준다 | 과부하가 차단기 열림으로 바뀌어 모두 같은 열림 시간 값을 받는다. 같은 시각에 다시 몰려 반열림 시험 호출과 겹칠 수 있다(추론) | A와 같다 | A와 같다 |
| 바꿀 것 | 설정 한 줄(`ignoreExceptions`) | 없음(운영 기본) | Spring Cloud CircuitBreaker 대신 Resilience4j 연산자를 직접 엮는 코드 변경 | A + Prometheus 경보 규칙 하나 |
| 깨지기 쉬운 점 | 덮어쓰기 파일·설정에서 키가 빠지면 조용히 B가 된다(영은님 ISE-230 코멘트 "덮어쓰기 파일이 차단기 키 전부를 덮는다") | — | 구조로 막혀 설정 실수에 강하다 | 경보 기준을 측정으로 정해야 한다 |

### 2-3. 업계에서 흔히 쓰는 방식(문서·소스로 확인한 것만)
| 라이브러리 | 벌크헤드 거절을 차단기에 | 확인한 곳 |
|---|---|---|
| Hystrix | **오류로 센다.** 오류 수 = 실패 + 시한 초과 + 스레드 풀 거절 + 세마포어 거절 | `HystrixCommandMetrics.HealthCounts.plus`(GitHub master) |
| Resilience4j | 따로 정하지 않는다. 기본이 "모든 예외를 실패로 기록"이라 결과적으로 센다. 벌크헤드와 차단기를 함께 쓸 수 있다고만 적었다 | resilience4j.readme.io CircuitBreaker 문서 |

Hystrix가 거절을 오류로 세는 데는 전제가 있다. Hystrix는 의존성마다 스레드 풀을 따로 두고, 호출 스레드가 그 풀에서 의존성 응답을 기다린다. 그래서 풀이 차면 거의 항상 그 의존성이 느리다는 뜻이다(위 (가)). 이 Gateway는 이벤트 루프 모델이라 스레드가 기다리지 않는다. 벌크헤드는 세마포어(동시 수 세기)이고, 차는 원인이 (나)였다. 전제가 다르므로 기본값을 그대로 따를 이유가 약하다. "Hystrix가 이 전제 때문에 그렇게 설계했다"는 설명은 Hystrix 문서에서 직접 확인한 문장이 아니라 구조에서 끌어낸 해석이다.

## 3. 고른 것과 이유
**A(예외로 뺀다) + C2(거절 비율 경보)를 추천한다. C1은 바꿀 조건으로 둔다.**

1. 이 Gateway에서 벌크헤드 포화는 Redis 장애의 신호가 아니라 Gateway CPU 포화의 증상이다(1-4, 2-1).
2. B로 열리면 넘친 만큼이 아니라 전부를 막는다. 그런데 차단기가 아끼는 것은 Redis 조회 한 번뿐이라 CPU 병목은 그대로다(1-3). 막는 범위만 커지고 얻는 것이 적다.
3. A로도 Redis 진짜 장애는 시한 초과·느린 호출로 잡힌다. 잃는 것은 몰림 중 감지 약 1~2초다(계산값).
4. A는 배포 서버에서 동작을 확인했다(2회 ignored 16,024, failed 0).
5. C2는 A가 만드는 빈칸(과부하가 차단기 지표에서 사라짐)을 메운다. 비용이 작다.

## 4. 감수한 점
- 몰림 중 Redis가 실제로 멈추면 B보다 1~2초 늦게 열린다(계산값). 그동안 통과한 호출은 시한 200ms까지 기다렸다 503이 된다.
- 과부하는 차단기가 아니라 벌크헤드 거절로만 처리된다. 넘친 요청은 503을 받지만, 받아 준 요청은 여전히 느릴 수 있다(2,500/s p95 428ms). 이 부분은 앞 노트의 유입 제어(요청률 제한, `Retry-After`)가 맡는다.
- 설정 한 줄에 기대므로 덮어쓰기 파일에서 빠지면 조용히 B로 돌아간다.
- 남는 오탐 길이 하나 있다. 통과한 호출의 시간에도 Gateway 쪽 대기가 섞인다. 그래서 CPU 포화가 더 심해지면 느린 호출(100ms·80%)로 열릴 수 있다. G1 측정 중 느린 호출 비율은 기록하지 않아 **확인 못 함**이다.

## 5. 바꿀 조건
| 조건 | 바꿀 방향 |
|---|---|
| Redis를 다른 장비·매니지드(ADR 0047 결정 3)로 옮겨, 벌크헤드 포화가 Redis 지연 때문에 생기는 것이 측정으로 보일 때 | B 쪽으로 다시 검토한다(Hystrix 전제가 맞아짐) |
| 측정이나 운영에서 `ignoreExceptions`가 빠져 거절이 failed로 다시 세어진 적이 생길 때 | C1(구조로 분리) |
| 4,800/s 근처 이상 과부하 측정에서 A가 느린 호출 오탐으로 열릴 때 | 느린 호출 기준을 다시 정하거나 차단기가 재는 구간을 줄인다(앞 노트 10절 C·D) |
| 저부하(초당 50 미만)에서 Redis 장애를 감지해야 할 때 | 최소 호출 수를 낮춘다. A·B 공통 한계다 |

| 6 | Redis 장애, 초당 50 미만 저부하 | **틀림**: 최소 500건이 안 차 판정 안 함 | **틀림**: 같음 | 같음 |
| 7 | 식은 Gateway 첫 몰림(JIT) | 대체로 맞음. 통과한 호출이 느린 호출로 세어지면 오탐 가능 | 오탐 가능성이 더 큼(거절까지 실패로 셈) | A와 같음 |
| 8 | 덮어쓰기에서 `ignoreExceptions` 누락 | **틀림**: 조용히 B가 됨 | — | 맞음(구조로 분리) |
| 9 | 실패의 실패: 경보 규칙이나 Alertmanager가 죽음 | 과부하를 아무도 모름(503은 계속 남) | — | C2만 잃고 A로 돌아감 |
| 10 | 서버 종료(Gateway 재기동) | 차단기 상태가 사라지고 닫힘으로 시작. 1·2차의 "재기동 직후 열림"은 A와 무관하게 웜업 문제 | 같음 | 같음 |

## 확인 못 함
- G1 측정 중 차단기 느린 호출 비율의 최댓값
- 과부하 50% 초과(약 4,800/s 이상)에서 A·B가 실제로 어떻게 움직이는지(측정 범위 밖)
- Redis 멈춤 때 A의 실제 감지 시간(계산값만 있음)
- `Retry-After`를 같은 값으로 받은 클라이언트가 동시에 다시 몰리는지(추론)
- Hystrix가 거절을 오류로 세는 설계 이유가 문서에 적혀 있는지(소스 계산식만 확인)
