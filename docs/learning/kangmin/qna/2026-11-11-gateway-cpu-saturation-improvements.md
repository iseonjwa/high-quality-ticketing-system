# Gateway CPU 포화는 사양 문제일 뿐인가, 요청률 제한이 도움이 되나

## 질문
[벌크헤드 거절 노트](2026-11-11-bulkhead-rejection-breaker-count.md) 4절의 감수한 점 세 가지를 더 줄일 방법은 없나? CPU 포화는 그냥 사양 문제라 해결할 수 없는 것인가? 최적화할 방향이 있나? 요청률 제한(rate limiter)을 넣으면 도움이 되나?

## 짧은 답
- **반은 사양 문제이고, 반은 아직 모르는 문제다.**
  - 사양: 4 vCPU 한 대에 컨테이너 21개가 산다. 총량은 늘릴 수 없다.
  - 모르는 것: 요청 하나가 Gateway에서 CPU를 약 0.9ms 쓰는데(계산값), 그 시간이 어디에 쓰이는지 재 본 적이 없다. 그래서 "더 줄일 수 없다"고 말할 근거도 없다.
- 순서는 **재기 → 줄이기 → 묶기**다. 프로파일링으로 어디에 쓰는지 보고, 요청당 CPU를 줄이고, 그래도 넘치는 양은 입구에서 싸게 거절한다.
- **요청률 제한은 도움이 된다. 다만 종류와 위치를 골라야 한다.**
  - 도움이 되는 것: 인스턴스 전체 상한을 인증보다 **앞에** 두는 로컬 방식이다. 장비가 감당할 양만 받으면 받은 요청의 지연이 묶이고, 감수한 점 3(CPU 포화로 느린 호출 오탐)도 거의 사라진다.
  - 도움이 안 되는 것: 사용자별 제한(G-3)은 G1 부하를 줄이지 못한다. G1 사용자들은 설계 간격을 지키며 묻기 때문이다. Spring Cloud Gateway 기본 `RequestRateLimiter`는 Redis를 부르므로 오히려 부하를 늘린다.

## 1. 확인한 사실
| 항목 | 값 | 출처 |
|---|---|---|
| 장비 | 배포 서버 `m7i.xlarge`, 4 vCPU. 서비스 전체가 한 대에서 돈다. 컨테이너별 CPU 제한 없음 | `open-peak-scenarios.md` 3절 환경 표, 2026-11-10 노트 |
| G1 3차 Gateway CPU 최대 | 216%(1회), 213%(2회). 서버 전체는 2,500/s부터 99% | `open-peak-scenarios.md` 배포 서버 3차 |
| 성공 처리량 | 약 2,300~2,470/s에서 멈춤 | 같은 곳 |
| Redis CPU | 9~17%. 병목이 아니다 | 같은 곳 |
| JWT 검증 | HS256(HMAC) `NimbusJwtDecoder`. 차단기보다 먼저 돈다 | `common/.../TokenDecoders.java:37-40`, `GatewayAuthenticationFilter.java:71-82` |
| 요청마다 하는 일 | 요청 로그 한 줄(`RequestLogWebFilter`), 추적 표본 10%(`TRACING_SAMPLE_RATE` 기본 0.1), 지표 | `config-repo/application.yml:17-18`, `observability.md` |
| 이미 있는 계획 | G-2 블랙리스트 확인 줄이기(메모리 캐시), G-3 요청 제한. "보안·인증 결정이라 팀 합의와 contract 이슈가 필요" | `open-peak-load-plan.md` G 단계 표 |
| `ignoreException(Predicate)` | Resilience4j 2.3.0 `CircuitBreakerConfig.Builder`에 있다(클래스 대신 조건으로 무시) | jar `javap` 확인 |

계산값:
- Gateway 요청당 CPU는 약 0.9ms다(2,160ms ÷ 약 2,400건). 거절된 요청도 분모에 들어 있어 대략적인 값이다.
- 장비 전체로는 요청당 약 1.7ms다(4,000ms ÷ 약 2,400건). 나머지는 순번 조회를 처리하는 reservation, Redis, 관측 도구, OS가 나눠 쓴다.

## 2. "사양 문제인가"
| 관점 | 판단 |
|---|---|
| 총량 | 사양 문제가 맞다. 4 vCPU 한 대에서 Gateway·서비스·DB·관측 도구가 같이 돈다. 운영이라면 Gateway를 따로 두고 여러 대로 늘리는 것(scale-out)이 정답이다. 이 프로젝트는 장비 한 대가 전제라 이 길은 막혀 있다 |
| 요청당 CPU | 모른다. HMAC 검증과 Redis 조회 한 번은 보통 수십 µs 수준으로 알려져 있지만(일반론, 이 장비에서 재지 않음) 0.9ms의 대부분일 것 같지 않다. 나머지 후보는 HTTP 프록시(Netty 읽기·쓰기), 요청 로그 JSON 직렬화와 Loki 전송, 추적, 지표 태그, 필터 체인이다. 어느 것이 큰지는 **확인 못 함**이다 |
| 다른 컨테이너 몫 | 관측 도구(Prometheus·Loki·Alloy·Zipkin)가 같은 CPU를 쓴다. 측정 중에는 앱 CPU를 빼앗는다 |

결론: "사양이라 못 고친다"는 아직 이르다. 요청당 CPU를 재 본 뒤에야 사양 문제인지 코드 문제인지 나눌 수 있다.

## 3. 개선 방향 비교
| 선택지 | 하는 일 | 기대 | 감수할 점 | 비용 |
|---|---|---|---|---|
| P. 프로파일링 | G1 2,000/s 구간에서 Gateway에 JFR이나 async-profiler를 붙여 CPU 불꽃 그래프(flame graph)를 본다 | 0.9ms가 어디에 쓰이는지 안다. 아래 선택지의 우선순위가 정해진다 | 측정 1회가 더 든다. 프로파일러 자체 부하가 조금 있다 | 작음 |
| R1. 요청 로그 끄기·줄이기 | G1 변형에 이미 있는 `ISEONJWA_REQUESTLOG_ENABLED=false`로 한 번 잰다 | 로그 비용이 크면 처리량이 오른다 | 운영에서 끄면 요청 추적이 약해진다. 성공 요청만 표본으로 남기는 식의 절충이 필요하다 | 매우 작음(이미 있음) |
| R2. 추적 표본 비율 | 0.1 → 0.01로 줄여 비교한다 | 추적 비용만큼 준다 | 드문 오류의 트레이스를 놓칠 수 있다 | 매우 작음 |
| R3. 블랙리스트 확인 줄이기(G-2) | 로그아웃된 `jti`를 Gateway 메모리에 캐시하고, 걸릴 때만 Redis를 부른다 | 요청당 Redis 호출·벌크헤드·차단기 비용이 거의 0이 된다. 차단기 오탐 문제 자체가 대부분 사라진다 | 로그아웃 반영이 갱신 주기만큼 늦다. ADR 0005(fail closed)와 충돌하는지 팀 합의가 필요하다 | 큼(보안 결정) |
| R4. 컨테이너 CPU 몫 나누기(`cpus`) | Gateway·reservation·관측 도구에 몫을 정한다 | 관측 도구가 앱 CPU를 빼앗지 않는다. JVM이 받은 몫에 맞춰 스레드 수를 정한다 | 총량은 그대로다. 몫을 잘못 나누면 한도가 낮아진다 | 중간(다시 재야 함) |
| L1. 입구 요청률 제한(인스턴스 전체, 로컬) | 인증 필터보다 앞에서 초당 N건(예: 통과선 2,000/s의 60~70%, 계산값)을 넘으면 바로 503 + `Retry-After` | 받은 요청의 지연이 묶인다. 거절이 JWT 검증보다 먼저라 더 싸다 | 고정값이라 장비·코드가 바뀌면 다시 재야 한다. 진입과 폴링을 같은 상한으로 묶으면 한쪽이 다른 쪽 몫을 먹는다 | 중간 |
| L2. 사용자별 요청 제한(G-3) | `nextPollAfterMillis`보다 자주 묻는 사용자에게 429 | 간격을 안 지키는 클라이언트가 전체 부하를 키우지 못한다 | 설계 간격을 지키는 몰림은 못 줄인다. 사용자 키를 알려면 인증 뒤에 둬야 해서 JWT 비용은 이미 쓴 뒤다 | 중간 |
| L3. 적응형 동시성 제한 | 지연이 늘면 허용 동시 수를 자동으로 줄인다(예: Netflix concurrency-limits) | 장비가 바뀌어도 한도를 스스로 찾는다 | 새 라이브러리와 조정 시간이 든다. 11/16 M4 마감에 비해 크다 | 큼 |

요청률 제한을 고를 때 주의할 점:
- Spring Cloud Gateway 기본 `RequestRateLimiter`(`RedisRateLimiter`)는 요청마다 Redis 스크립트를 부른다. Redis 호출을 늘리므로 지금 목적에 맞지 않는다. 로컬 방식(Resilience4j RateLimiter, Bucket4j, 직접 만든 토큰 버킷)을 쓴다.
- Gateway 실행 경로에 `resilience4j-ratelimiter`가 들어 있는지는 **확인 못 함**이다. Gradle 캐시에 2.3.0 jar가 있지만 Gateway 의존성 트리는 보지 않았다.
- 거절 응답을 429로 할지 503으로 할지는 ISE-230 3번(`Retry-After` 분리)과 함께 정한다. 클라이언트가 둘을 다르게 다루는지가 기준이다.

## 4. 감수한 점별로 줄이는 방법
| 감수한 점(벌크헤드 거절 노트 4절) | 줄이는 방법 | 효과와 한계 |
|---|---|---|
| 1. 몰림 중 Redis가 멈추면 B보다 1~2초 늦게 열린다 | 시간 창을 10초에서 5초로 줄이면 늦는 시간도 대략 절반이 된다(계산값) | fail closed라 그 1~2초 동안에도 사용자는 어차피 503을 받는다. 차이는 Gateway가 요청을 시한(100~200ms)까지 붙잡는지뿐이다. Redis 연결이 끊기면 Lettuce가 바로 오류를 내므로 대부분 빨리 실패한다(코드 기준 추론, 장애 주입은 F1에서 잴 일). **원래 작은 대가**라 손대지 않아도 된다 |
| 2. 설정 한 줄이 빠지면 조용히 B로 돌아간다 | (a) 코드에서 `ignoreException(Predicate)`로 클래스 이름을 비교해 항상 무시하게 한다. `AuthRedisFailures`가 이미 이름으로 비교하므로 같은 방식이다. (b) `kind="failed"`이면서 `cause="bulkhead_full"`인 경우를 경보로 둔다. (c) 설정을 읽어 무시 목록을 확인하는 테스트를 둔다 | (a)가 가장 튼튼하다. 다만 Spring Cloud CircuitBreaker의 `Customizer`와 `config-repo` 속성 중 무엇이 이기는지는 **확인 못 함**이라 테스트로 먼저 본다 |
| 3. CPU 포화가 심해지면 느린 호출로 오탐해 열린다 | (a) 입구 요청률 제한(L1)으로 CPU 포화 자체를 막는다. (b) 느린 호출 비율을 대시보드에 올려 실제로 얼마까지 오르는지 잰다. (c) 느린 호출 기준을 Redis 시한에 가깝게 올려 "거의 시한 초과"만 세게 한다 | (a)가 원인을 없앤다. (c)는 Redis가 서서히 느려지는 초기 신호를 놓친다 |

## 5. 추천 순서와 이유
1. **R1·R2·P를 한 번의 측정에 묶는다.** 같은 G1에서 요청 로그 끔, 추적 0.01, 프로파일을 차례로 잰다. 비용이 거의 없고, 이후 선택의 근거가 된다.
2. **감수한 점 2의 (a)를 코드로 고정한다.** 설정 실수 하나로 1차 Q1의 전면 503으로 돌아가는 길을 닫는다. 변경이 작고 테스트로 확인할 수 있다.
3. **L1(입구 요청률 제한)을 결정 기록의 "바꿀 조건"에서 "다음 단계"로 올릴지 정한다.** 1번에서 요청당 CPU가 크게 줄지 않으면 넣는다. 그때 상한값은 측정한 통과선에서 정한다.
4. R3(G-2)은 효과가 가장 크지만 보안 결정이라 팀 합의가 먼저다. contract 이슈로 올릴지만 정한다.

고른 이유:
- 지금 모르는 것(요청당 CPU의 쓰임새)을 먼저 재야 나머지 선택이 추측이 아니게 된다.
- 요청률 제한은 효과가 확실하지만 숫자가 장비에 묶인다. 요청당 CPU를 줄인 뒤에 정해야 다시 재는 일이 한 번으로 끝난다.

감수한 점:
- 1번은 처리량을 바로 올려 주지 않는다. 측정 한 회가 더 든다.
- L1을 미루는 동안 2,500/s 이상에서는 "빨리 거절은 되지만 받아 준 요청도 느리다"(p95 428~497ms)가 그대로 남는다.

바꿀 조건:
- 프로파일에서 로그·추적이 Gateway CPU의 큰 몫으로 나오면 L1보다 그 비용부터 줄인다.
- 혼합 부하(진입 + 폴링) 측정에서 p95 목표를 못 지키면 L1을 바로 넣는다.
- 팀이 G-2에 합의하면 R3를 먼저 한다. 그러면 감수한 점 1·3이 대부분 의미를 잃는다.

## 실패 표(L1을 넣는다면)
| 실패 | 결과 | 대응 |
|---|---|---|
| 상한을 너무 낮게 잡음 | 장비가 감당할 수 있는데 거절한다. 처리량이 상한에서 멈춘다 | 상한을 측정한 통과선의 비율로 두고 지표(`allowed`·`rejected`)를 본다 |
| 상한을 너무 높게 잡음 | 지금과 같다. 벌크헤드가 뒤에서 거절한다 | 벌크헤드를 그대로 두어 두 번째 선으로 쓴다 |
| 진입과 폴링이 한 상한을 나눔 | 폴링 몰림이 진입 몫을 먹는다 | 경로별로 상한을 나눈다 |
| 제한기 자체가 느림(잠금 경합) | 모든 요청이 느려진다 | 로컬 원자 연산 기반 구현을 고르고 부하에서 잰다 |
| Gateway 재시작 | 로컬 카운터가 비어 잠깐 상한 전체를 받는다 | 1초 단위 버킷이라 영향은 1초 정도다(계산값) |
| 클라이언트가 `Retry-After`를 무시 | 거절이 늘 뿐 부하는 줄지 않는다 | 사용자별 제한(L2)으로 보완한다 |

## 확인 못 함
- Gateway 요청당 CPU 0.9ms의 쓰임새(프로파일 없음)
- 요청 로그·추적을 껐을 때의 처리량 변화(G1 변형으로 계획만 있고 측정 안 함)
- `Customizer`와 `config-repo` 속성 중 어느 쪽이 우선하는지
- Gateway 실행 경로에 `resilience4j-ratelimiter`가 있는지
- HMAC 검증·Redis 조회 한 번의 이 장비에서의 실제 CPU 시간
