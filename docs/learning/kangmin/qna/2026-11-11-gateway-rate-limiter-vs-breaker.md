# 요청률 제한으로 "차단기를 예민하게 세팅해 CPU 포화 전에 열기"의 약점을 줄일 수 있나

## 질문
`auth-redis` 차단기를 예민하게 세팅해 Gateway CPU가 99~100%에 닿기 전에 열리게 하는 방법이 있다(Gateway CPU 포화 실험에서 설계 중). 레이트 리미터(요청률 제한)로 이 방법의 약점을 완화할 수 있는지 생각해 보자.

## 짧은 답
- **완화된다. 정확히는 "차단기가 하던 과부하 보호를 요청률 제한이 넘겨받는다".** 차단기는 열리면 그 경로를 전부 거절하고, 요청률 제한은 한도를 넘친 만큼만 거절한다. 같은 2,500/s가 와도 차단기는 열림 5초 동안 성공 0%, 요청률 제한은 한도만큼 계속 성공한다.
- **역할 나눔:** 요청률 제한(인스턴스 전체, 로컬)이 1차 방어로 CPU를 지키고, 차단기는 Redis 장애 안전망으로만 남긴다. 이렇게 하면 차단기를 예민하게 만들 이유가 없어진다. 지금 설정(ADR 0050 제안)의 방향과 같다.
- **구현은 인증 필터(-100)보다 앞의 로컬 제한기다.** Spring Cloud Gateway 기본 `RequestRateLimiter`는 라우트 필터라 인증 뒤에 돌고, 요청마다 Redis Lua 스크립트를 한 번 더 부르며, Redis 오류면 통과시킨다(소스 확인). 지금 목적에 맞지 않는다.
- **숫자는 처음 상한 후보 1,500/s·1,800/s(계산값)다.** 측정에서 p95가 1,500/s 20~26ms, 2,000/s 157~208ms였으므로 무릎(지연이 급히 늘기 시작하는 점)이 그 사이에 있다. 둘 다 재서 고른다.
- **한계:** 장비 한도(성공 약 2,300~2,470/s)는 그대로다. 요청률 제한은 처리량을 올리지 않고, "받은 요청은 빠르고 나머지는 빨리 거절"로 모양만 바꾼다. 3,000/s 목표는 다른 길(요청당 CPU 줄이기)이 필요하다([CPU 포화 개선 노트](2026-11-11-gateway-cpu-saturation-improvements.md) 3·5절).

## 1. 넘친 만큼만 거절 vs 열리면 전부 거절
차단기와 부하 차단의 일반 비교는 [차단기 vs CPU 포화 노트](2026-11-11-breaker-vs-cpu-saturation.md) 1절에 있다. 여기서는 "차단기를 예민하게" 방법에 대고 비교한다.

| 상황(2,500/s 유입, 장비 한계 약 2,300/s 가정) | 예민한 차단기 | 요청률 제한(상한 1,800/s) |
|---|---|---|
| 거절 범위 | 열린 5초 동안 인증 경로 전부(약 12,500건, 계산값) | 넘친 약 700건/s만(계산값) |
| 받은 요청의 지연 | 닫혀 있는 동안은 포화 상태 그대로(p95 428~497ms, 측정) | 상한 아래라 1,500~2,000/s 측정 구간 수준을 기대(측정 안 함) |
| 시간 모양 | 열림 → 반열림 → 닫힘 → 다시 몰림 → 열림으로 진동(11/10 3-4 측정) | 상한에서 평평하다. 상태가 없어서 진동할 것이 없다 |
| 판단 근거 | 느린 호출 비율. Gateway 쪽 대기가 섞인 시간이라 원인을 구별하지 못한다 | 초당 도착 수. 원인을 따지지 않고 양만 센다 |
| Redis 장애 감지 | 과부하와 섞여 구별이 안 된다 | 하지 않는다. 차단기가 계속 맡는다 |
| 클라이언트에 주는 신호 | `Retry-After` 1초인데 실제로는 5초 열림 → 헛요청 4~5번(계산값) | 거절 원인이 하나라 `Retry-After`를 따로 정할 수 있다(4절) |

함께 쓸 때 역할:

| 장치 | 맡는 것 | 지금 값 | 요청률 제한이 들어오면 |
|---|---|---|---|
| 요청률 제한(새로) | 자기 과부하. 초당 도착 수가 장비가 감당할 양을 넘는 것 | 없음 | 1차 방어 |
| 벌크헤드 `auth-redis` 50 | Redis 조회 동시 수. 순간 몰림의 2차 방어 | 50, 거절은 차단기에서 무시 | 그대로 둔다. 상한이 너무 높게 잡혔을 때의 안전망 |
| 차단기 `auth-redis` | Redis 장애(시한 초과·연결 오류) | 시간 창 10초, 느린 호출 100ms·80% | 그대로 둔다. 예민하게 만들지 않는다 |

## 2. 구현 선택지
### 2-1. 비교
| 선택지 | 하는 일 | 확인한 동작 | 비용·위험 |
|---|---|---|---|
| (a) SCG `RequestRateLimiter` + `RedisRateLimiter` | 라우트 필터에서 키별 토큰 버킷을 Redis Lua 스크립트로 잰다 | 요청마다 `redisTemplate.execute(script)` 한 번(키 2개 `setex`). Redis 오류면 `[1, -1]`로 **허용**(fail open). 거절 기본 상태 코드 429. 키가 비면 `denyEmptyKey=true`로 403. 라우트 필터 순서는 선언 순서(1, 2, ...)라 인증 필터(-100) **뒤**에 돈다 | 지금 병목(Gateway CPU)에 Redis 왕복 하나를 더한다. JWT 검증을 이미 한 뒤 거절하므로 거절이 싸지 않다. 기본 키(`PrincipalNameKeyResolver`)는 `exchange.getPrincipal()`을 쓰는데, 이 Gateway는 사용자를 헤더로 넘기므로 키가 비어 403이 날 것으로 보인다(코드 기준 추론, 실행 안 함) |
| (a') SCG `Bucket4jRateLimiter` | 같은 라우트 필터, 저장소만 Bucket4j | `io.github.bucket4j` 클래스가 필요하다. Gradle 캐시에 bucket4j가 없다 | 새 의존성. 라우트 필터라 인증 뒤인 것은 (a)와 같다 |
| (b) 로컬 제한기, 인증 앞(Resilience4j `RateLimiter`) | `GlobalFilter` 순서 -100보다 앞(예: -200)에서 경로 묶음별로 허가를 받는다 | Gateway 실행 경로에 `resilience4j-ratelimiter` 2.3.0이 이미 있다(`:gateway:dependencies` 확인). `AtomicRateLimiter`는 `limitRefreshPeriod`마다 `limitForPeriod`개를 채우고, 남은 허가는 `limitForPeriod`를 넘겨 쌓이지 않는다(2-2). 기본 `timeoutDuration`은 **5초**이고, Reactor 연산자는 기다릴 시간이 있으면 `Mono.delay`로 구독을 미룬다. 0으로 둬야 바로 거절한다 | 새 의존성 없음. 상한이 장비에 묶인다. 허가는 `AtomicReference` 하나의 CAS(비교 후 교체)로 받고, 실패하면 `parkNanos(1)` 뒤 다시 한다. 이벤트 루프 4개에서 경합이 문제될지는 확인 못 함 |
| (b') 로컬 제한기, 직접 만든 토큰 버킷 | `AtomicLong` 몇 개로 같은 일 | - | 코드가 작지만 시간 계산·테스트를 직접 책임진다. (b)보다 나을 이유가 아직 없다 |
| (c) 동시 수 제한(Semaphore·Bulkhead), 인증 앞 | 처리 중인 요청 수를 N으로 묶는다 | 지금 벌크헤드는 Redis 조회 한 번만 감싼다 | 리틀의 법칙으로 동시 수 = 처리율 × 체류 시간이다. 체류 시간이 늘면 같은 N에서 처리율이 저절로 줄어 장비 변화에 덜 민감하다. 대신 "초당 몇 건"으로 말할 수 없어 목표(초당 3,000)와 맞대기 어렵고, 체류 시간이 짧은 경로에서는 몰림을 거의 못 막는다 |
| (d) 키 단위(사용자별·IP별) | 한 사람·한 주소의 빈도를 묶는다 | 계획에 G-3로 있다 | 목적이 다르다. 연타·봇 방어용이고 CPU 보호용이 아니다. G1·Q1 사용자는 설계 간격을 지키므로 전체 부하를 줄이지 못한다. 사용자 키는 인증 뒤에야 알 수 있다. IP 키는 같은 NAT 뒤 사용자들을 한꺼번에 막는다 |

### 2-2. 토큰 버킷과 Resilience4j `RateLimiter`의 관계
- 토큰 버킷은 초당 r개씩 채우고 최대 b개(버스트 크기)까지 쌓는다. 순간에 최대 b건을 받고, 길게 보면 초당 r건을 받는다.
- Resilience4j `AtomicRateLimiter.calculateNextState`는 주기 수 × `limitForPeriod`만큼 채우되 `limitForPeriod`를 넘기지 않는다. 즉 **r = `limitForPeriod` ÷ `limitRefreshPeriod`, b = `limitForPeriod`**인 토큰 버킷과 같고, 다만 채우는 일이 주기 경계에서 한꺼번에 일어난다.
- 그래서 같은 초당 1,800이라도 주기를 어떻게 자르는지가 버스트 크기를 정한다(3-3).

### 2-3. 고른 것
**(b) Resilience4j `RateLimiter`, `GlobalFilter` 순서 -200, 경로 묶음별 인스턴스 전체 상한.**
- 고른 이유: 거절이 JWT 검증·Redis 조회보다 먼저라 가장 싸다. 의존성이 이미 있다. 상태가 없어 진동하지 않는다. `GlobalFilter`라 라우트가 정해진 뒤 돌므로 경로별 상한을 라우트로 나누기 쉽다.
- `WebFilter`(라우트 매칭 전)로 두지 않은 이유: 경로를 직접 맞춰야 하고, 액추에이터 요청까지 거치게 된다. `RoutePredicateHandlerMapping` 순서는 기본 1이다(소스 확인). 액추에이터 매핑이 그보다 앞서 잡혀 `GlobalFilter`를 거치지 않는지는 Spring Boot 쪽 소스를 보지 않아 **확인 못 함**이다. 테스트로 확인한다.
- 감수한 점: 상한은 이 장비·이 코드에서 잰 값이다. 장비나 요청당 CPU가 바뀌면 다시 재야 한다. 진입과 폴링을 다른 묶음으로 나누지 않으면 한쪽이 다른 쪽 몫을 먹는다. 로컬 카운터라 Gateway를 여러 대로 늘리면 상한이 대수만큼 커진다(지금은 한 대).

## 3. 수치 정하는 법
### 3-1. 포화점 × 여유 비율
| 측정(배포 서버 4차, G1, 1·2회) | p95 |
|---|---|
| 1,500/s | 20ms / 26ms |
| 2,000/s | 208ms / 157ms |
| 2,500/s | 497ms / 428ms |

- p95 200ms에 닿는 처리량은 2,000/s 근처다. 여기에 여유 비율 0.75~0.9를 곱하면 **1,500~1,800/s(계산값)**다. 1,500/s는 이미 p95 26ms로 잰 점이라 안전 쪽 하한, 1,800/s는 잰 적 없는 점이다.
- 앞 노트는 0.6~0.7(1,200~1,400/s)을 적었다. 그 비율은 측정 변동과 다른 컨테이너 몫을 넉넉히 둔 값이다. 1,500/s에서 이미 p95가 목표의 1/8이므로 0.6까지 내릴 근거는 약하다고 본다. 실험으로 정한다.
- 주의: 이 측정은 G1(순번 조회, 뒤쪽 비용을 줄인 경로)이다. Q1 진입은 reservation에서 Redis Lua와 회차 캐시를 거쳐 장비 전체 CPU를 더 쓴다. 진입 묶음의 상한은 Q1으로 따로 재야 한다(확인 못 함).

### 3-2. 리틀의 법칙으로 벌크헤드와 맞추기
- 처리 중 수 L = 처리율 λ × 체류 시간 W다.
- 상한 1,800/s에서 Redis 조회가 차단기 안에서 머무는 시간을 1,500/s의 p95 26ms로 잡으면 L ≈ 1,800 × 0.026 ≈ 47(계산값)이다. 벌크헤드 50과 거의 같다.
- 뜻: 상한 1,800/s에서는 벌크헤드가 가끔 거절할 수 있다. 1,500/s면 약 39(계산값)라 여유가 있다. 두 장치가 같은 순간에 거절하면 어느 쪽 거절인지 원인 카운터로 나눠 본다(`gateway_auth_redis_failures_total{cause="bulkhead_full"}`와 새 제한기 카운터).
- p95를 평균 대신 쓴 것은 보수적으로 잡으려는 것이다. 차단기 안 체류 시간 분포는 기록하지 않아 확인 못 함이다.

### 3-3. 버스트 크기와 오픈 순간 몰림(Q1-d)
- Q1-d는 1초 안에서 절반이 앞 약 0.3초에 몰린다. 30,000명이면 앞 0.3초에 약 15,000건, 순간 초당 약 50,000건이다(계산값).
- 상한 1,800/s를 주기 1초·허가 1,800으로 두면, 주기 시작 몇 ms 안에 1,800건이 한꺼번에 들어간다. 그러면 뒤쪽(벌크헤드 50)이 대부분을 거절해 요청률 제한이 몰림을 고르게 펴 주지 못한다.
- 주기를 짧게 자르면 b가 작아진다.

| 주기 / 허가 | 초당 상한 | 버스트 b | 판단 |
|---|---|---|---|
| 1s / 1,800 | 1,800 | 1,800 | 몰림을 그대로 뒤로 넘긴다. 쓰지 않는다 |
| 100ms / 180 | 1,800 | 180 | b가 벌크헤드 50의 3.6배(계산값). 몰림이 100ms마다 180건씩 들어간다 |
| 50ms / 90 | 1,800 | 90 | 벌크헤드와 비슷한 크기. 첫 후보 |
| 10ms / 18 | 1,800 | 18 | 가장 고르다. 주기 경계마다 상태를 바꾸는 CAS가 늘어난다. 비용은 확인 못 함 |

- 추천 시작점: **50ms / 90(1,800/s), 50ms / 75(1,500/s)**. 버스트는 벌크헤드 크기 근처로 맞춘다는 규칙이다. 이 규칙이 맞는지는 Q1-d로 확인한다.
- 몰림을 "기다리게" 하지 않고 바로 거절한다(`timeoutDuration: 0`). 기다리게 하면 Gateway 메모리에 요청이 쌓이고, 응답 시한 3초 안에서 지연만 늘어난다.

## 4. 거절 응답
### 4-1. 429와 503
| 선택지 | 뜻 | 이 프로젝트에서 |
|---|---|---|
| 429 Too Many Requests | 이 클라이언트가 너무 많이 보냈다 | 사용자별 제한(G-3)에 맞다. 대기열 화면(`queueAdmission.ts` 147행)은 429도 다시 보내지만, 공통 조회 재시도(`queryClient.ts` 19~24행)는 429를 다시 보내지 않는다 |
| 503 Service Unavailable + `Retry-After` | 서버가 지금 감당하지 못한다 | 인스턴스 전체 상한은 사용자 잘못이 아니라 서버 용량이므로 503이 뜻에 맞다. 대기열 화면과 공통 재시도 모두 503을 다시 보낸다 |

- 고른 것: **전체 상한은 503 + 새 오류 코드(예: `GATEWAY_OVERLOADED`) + 원인별 `Retry-After`, 사용자별 상한은 429.**
- 감수한 점: 503이 벌크헤드·차단기·전체 상한 세 원인을 가진다. 상태 코드로는 못 나누고 오류 코드와 지표로 나눈다. k6 판정도 503을 모두 실패로 세므로 원인별로 다시 나눠 읽어야 한다.

### 4-2. `Retry-After`와 ISE-230 3번
- 지금은 `GatewayErrorWriter`가 503이면 원인과 무관하게 `Retry-After: 1`이다(`GatewayErrorWriter.java` 27~29행). ISE-230 3번은 이것을 원인별로 나누는 일이다.
- 요청률 제한이 들어오면 원인이 하나 더 는다. 원인별로 다르게 줄 값의 방향:

| 원인 | `Retry-After` 방향 | 이유 |
|---|---|---|
| 차단기 열림 | 남은 열림 시간(최대 5초) | 그 전에 오면 반드시 또 거절된다 |
| 벌크헤드 가득 | 1초 | 순간 몰림이라 금방 빈다 |
| 전체 상한 초과 | 1초보다 길게(예: 2~3초, 실험으로 정함) | 거절된 사람이 1초 뒤 다시 오면 다음 1초 몫을 다시 다툰다. 30,000명을 1,800/s로 받으면 다 받는 데 약 17초(계산값)라, 짧은 간격의 재시도는 헛요청만 늘린다 |

- 대기열 화면은 `Retry-After`에 0~20% 흩뿌림을 더한다([503 자동 재시도 노트](2026-11-10-queue-join-503-auto-retry.md)). 정수 초라 흩뿌림 폭이 작다. 재시도 몰림이 다시 생기는지는 실험에서 본다.
- 공정성: 거절된 진입은 순번이 없고 재시도가 성공한 때 순번을 받는다(같은 노트). 요청률 제한은 거절을 무작위로 흩뿌리므로 "먼저 누른 사람이 먼저"는 1초 단위로만 지켜진다. 이것은 차단기 방식에서도 같았던 문제다(차단기는 더 크게 섞는다).

### 4-3. 예외 경로
| 경로 | 처리 | 근거 |
|---|---|---|
| 액추에이터(헬스·Prometheus 수집) | 제한하지 않는다 | 과부하 중에 헬스 체크·지표가 거절되면 상태를 볼 수 없다. `GlobalFilter`면 거치지 않을 것으로 보이나 확인 못 함(2-3) |
| 운영자 `/api/v1/admin/**` | 별도 묶음(작은 상한) 또는 제외 | 장애 시연 패널이 과부하 중에도 동작해야 한다. 요청이 적어 제외해도 부하 영향이 거의 없다 |
| 로그인·토큰 갱신 | 별도 묶음 | 토큰 만료 사용자가 갱신을 못 하면 다음 요청이 모두 401이 된다 |
| 결제 콜백 | 해당 없음 | 지금 PG(Mock PG)는 payment-service가 직접 부르고 Gateway를 거치는 PG 콜백 라우트는 없다(`config-repo/gateway.yml`). 생기면 제외한다 |
| `INTERNAL` 경로 | 해당 없음 | 외부 요청은 인증 필터가 404로 막는다. 제한기를 앞에 두면 404보다 먼저 거절될 수 있으나 해가 없다 |

## 5. 실험으로 확인할 것
### 5-1. 비교 구성
같은 부하(G1 2,500·3,000/s, 단계마다 30초, 배포 서버 4차와 같은 웜업)에서 세 구성을 비교한다.

| 구성 | 내용 |
|---|---|
| K0 | 지금(배포 서버 4차 2회 값). 기준선 |
| K1 | 예민한 차단기(CPU 포화 실험 세션이 정하는 값) |
| K2 | K0 + 요청률 제한 1,800/s(50ms/90). 시간이 되면 1,500/s(50ms/75)도 |

### 5-2. 지표와 판정
| 지표 | 판정 `[가정]` |
|---|---|
| 받아 준 요청 p95·p99 | K2가 2,500·3,000/s 모두 p95 200ms 이하 |
| 성공 처리량(초당) | K2가 상한의 95% 이상. 상한보다 많이 낮으면 제한기 자체 비용이나 뒤쪽 거절을 의심한다 |
| 1초 단위 성공률의 최솟값 | K1은 열림 구간에 0%가 나올 것으로 본다. K2는 0%인 초가 없어야 한다 |
| 거절 원인 비율(새 제한기 카운터, `bulkhead_full`, `breaker_open`) | K2에서 거절의 대부분이 제한기. `bulkhead_full`이 많으면 버스트가 크다 |
| 거절 응답 시간 | 0~1ms 수준(지금 벌크헤드 거절과 같은 수준) |
| Gateway CPU·서버 CPU | K2에서 서버 CPU 99% 아래로 내려오는지. 내려오지 않으면 거절 비용 자체가 크다는 뜻이다 |
| 차단기 상태 전환 수 | K2에서 0 |

- 3,000/s에서 K2는 약 1,200/s를 거절한다(계산값). 거절된 요청도 Netty 읽기·응답 쓰기·요청 로그 비용을 쓴다. 이 비용이 얼마인지 모르므로 "CPU가 내려간다"는 확인할 질문이다.
- 발생기는 `Retry-After`를 따르지 않고 정해진 도착률로 보낸다. 재시도 몰림의 효과는 이 실험으로 보지 못한다. 따로 보려면 거절 시 `Retry-After`만큼 쉬는 VU 모델이 필요하다.

### 5-3. 크기
| 항목 | 예상 | 근거 |
|---|---|---|
| 코드 | 새 `GlobalFilter` 1개, 설정 클래스 또는 `config-repo` 키 1곳, `GatewayErrorWriter` 오류 코드·`Retry-After` 1곳, 테스트 1~2개(허용·거절·예외 경로·카운터). 파일 4~5개 | 지금 필터 구조(`GatewayAuthenticationFilter`, `GatewayErrorWriter`)를 따른다 |
| 작업 시간 | 반나절(구현·테스트), 측정 1시간(K0 재사용 시 K1·K2만) | 배포 서버 4차 1·2회 시작 간격이 약 15분이었다(16:19:41Z → 16:35:05Z). 배포 시간을 더한 추정 |
| 11/13 재측정 슬롯 | K1 실험과 같은 슬롯에 K2를 붙이는 것은 크기로는 들어간다. 다만 11/12까지 PR 검토·배포가 끝나야 한다 | 일정은 확인할 질문이다 |

- 측정 모드에서만 켜는 스위치(기본 꺼짐)로 두면 운영 설정을 바꾸지 않고 잴 수 있다. 4차의 `compose.gateway-bulkhead.yml` 덮어쓰기와 같은 방식이다.

## 6. contract 이슈와 합의
- **contract 이슈가 필요하다.** `config-repo/gateway.yml`은 공유 설정이고, 거절 응답(상태 코드·오류 코드·`Retry-After`)은 프론트 대기열 화면이 따라야 하는 접점이다([contract 이슈 가이드](../../../guides/contract-issues.md) 1절).
- 측정 모드 스위치로만 잴 때는 운영 접점이 바뀌지 않으므로 이슈 없이 진행할 수 있다고 본다. 운영 기본값으로 켜기 전에 올린다.

| 상대 | 합의할 것 |
|---|---|
| 대기열 담당 | 전체 상한 거절을 503 + 새 오류 코드로 할지, `Retry-After` 값(ISE-230 3번과 함께), 진입·폴링·토큰 묶음을 나눌지와 각 상한, 공정성 손실(1초 단위)을 받아들일지 |
| 인프라 담당 | 측정 모드 덮어쓰기 파일, 제한기 지표를 대시보드·경보(`gateway-alerts.yml`)에 넣을지, 액추에이터 예외 확인 |
| 프론트(대기열 화면 담당) | 새 오류 코드를 연결 불안정 표시와 구별할지. 지금 재시도 규칙(503 다시 보냄, `Retry-After` 따름)이면 코드 변경 없이 동작한다 |

## 정리: 선택지 비교 → 고른 이유 → 감수한 점 → 바꿀 조건
- 비교: 예민한 차단기(전부 거절·진동) / SCG Redis 제한(Redis 호출 추가·인증 뒤·fail open) / 로컬 초당 제한(인증 앞, 넘친 만큼만) / 동시 수 제한(장비 변화에 덜 민감, 초당 목표와 맞대기 어려움) / 사용자별 제한(목적이 다름).
- 고른 것: 인증 앞 로컬 초당 제한(Resilience4j `RateLimiter`, 짧은 주기)을 1차 방어로, 벌크헤드는 2차 방어로, 차단기는 Redis 장애 전용으로 둔다. 차단기는 예민하게 만들지 않는다.
- 고른 이유: 넘친 만큼만 거절해 성공 0% 구간이 없다. 상태가 없어 진동하지 않는다. 거절이 가장 싸다. 의존성이 이미 있다.
- 감수한 점: 상한이 장비·코드에 묶인 고정값이다. 처리량 한도(약 2,300~2,470/s)는 그대로이고 3,000/s 목표는 이 방법으로 못 채운다. 503 원인이 셋이 되어 오류 코드·지표로 나눠 읽어야 한다. 경로 묶음을 나누는 설계가 하나 더 든다.
- 바꿀 조건:
  - 프로파일링·요청당 CPU 줄이기로 무릎이 크게 오르면 상한을 다시 잰다.
  - 장비가 바뀌거나 Gateway를 여러 대로 늘리면 동시 수 제한(c)이나 적응형 동시성 제한으로 옮긴다.
  - K2에서 거절 비용 때문에 CPU가 내려오지 않으면, 거절을 더 앞(요청 로그 전)으로 옮기거나 클라이언트 유입 조절(`Retry-After`·폴링 간격)을 먼저 한다.
  - 클라이언트가 간격을 지키지 않는 사례가 나오면 사용자별 제한(G-3)을 더한다.

## 확인 못 함
- 상한 1,800/s에서 실제 p95(1,500·2,000/s 사이 측정 없음)
- 거절된 요청 하나의 CPU 비용, 그래서 K2에서 서버 CPU가 내려가는지
- Q1 진입 경로의 무릎(G1과 다를 것으로 본다)
- 액추에이터 요청이 `GlobalFilter`를 거치지 않는지
- `AtomicRateLimiter` CAS 경합과 `parkNanos(1)`이 이벤트 루프에서 문제되는지
- `PrincipalNameKeyResolver` 기본 키가 이 Gateway에서 비는지(실행 안 함)
- 짧은 주기(50ms)의 버스트가 벌크헤드 거절을 실제로 줄이는지
