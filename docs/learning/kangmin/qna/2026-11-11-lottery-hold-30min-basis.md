# 추첨 당첨 예매의 선점 만료는 왜 30분인가

## 질문
F1-b 장애 주입 준비 중, 추첨 당첨 예매의 선점이 생성 + 30분이고 결제 결과가 없으면 1회 30분 더 연장한다는 설계를 봤다. 왜 30분이고 무슨 기준으로 정했나.

## 짧은 답
- 30분은 "자동결제 한 건이 최악의 경우 결과가 확정되기까지 걸리는 시간 + 여유"로 정한 타임아웃 예산(timeout budget)이다(D10, 2026-10-30).
- 계산: Kafka 대기 최대 약 3.3분 + REQUESTED 판정 10초 + UNKNOWN 재조회 최장 약 21분 = 약 25분, 여유를 더해 30분.
- 일반 예매의 5분을 쓰지 않은 이유: 사람이 결제하는 일반 예매와 달리 자동결제는 대기열과 재조회 때문에 늦어질 수 있다. 5분이면 "선점 만료 뒤 승인 → 환불"이 자주 생긴다.
- 숫자는 모두 `[가정]`이고 측정으로 확인하지 않았다.

## 1. 30분을 이루는 항목
| 항목 | 값 | 출처 |
|---|---|---|
| Kafka 대기(자동결제 대기열) | 최대 약 3.3분 | 당첨 2,000건 ÷ 초당 10건(자동결제 전용 동시 3 ÷ PG 응답 0.3초). `numbers-and-measurement.md` 1-3 |
| REQUESTED 판정 | 10초 | 결제가 REQUESTED로 10초 넘게 남으면 재조회 대상 |
| UNKNOWN 재조회 | 최장 약 21분 | 10초 × 6회 → 1분 → 5분 → 15분(SA 9-4). `details.md` |
| 여유 | 약 5분 | 반올림 |

## 2. 연장 30분과 상한 60분
- 연장은 "결제 결과를 받지 못한 채 만료"(outbox·Kafka·결제 서버 장애)를 위한 두 번째 기회다. 새 예매를 만들지 않고 같은 예매를 1회 연장하므로 결제 멱등(`reservationId` 단위)이 이중 결제를 막는다(ADR 0038).
- 종결은 승계 마감(추첨 후 30분) + 선점 만료(30분) = 추첨 후 최장 60분이다. 연장 상한도 이 60분이다.
- 승계 마감 30분은 별개 값이다. 예비자에게 당첨이 넘어가는 기간으로 10/29 숫자 기준(D1)에서 정했다.

## 3. 감수한 점
- 길게 잡은 대가는 종결과 남은 추첨석 반환이 최장 60분 늦어지는 것이다. 추첨석은 `LOTTERY` 등급으로 분리돼 있어(D9) 일반 판매 좌석을 막지는 않는다.
- 장애 주입(F1-b)에서 연장을 보려면 30분을 기다려야 하는 원인이 이 값이다.

## 4. 선점을 왜 길게 잡아야 하나 (후속 질문)
선점 만료는 "이 당첨 예매를 실패로 보고 좌석을 다음 사람에게 넘기는 시각"이다. 결제 결과보다 먼저 오면 다음 문제가 생긴다.

| 만료가 결제보다 먼저 오면 | 결과 |
|---|---|
| 예매는 만료 → 응모 `FAILED`, 좌석은 승계 | 그 뒤 PG가 승인하면 돈은 빠졌는데 좌석이 없다 → E8 환불 |
| 사용자 입장 | 당첨됐는데 결제 후 취소·환불. 같은 좌석이 다른 사람에게 감 |

예매 서비스는 결제 서비스의 진행 상태를 모른다(서비스 분리). 그래서 "결제가 진행 중이면 만료하지 않는다"를 직접 판단하지 못하고, 결제가 최악의 경우에도 끝날 시간만큼 기한을 넉넉히 준다.

| 선택지 | 장점 | 대가 |
|---|---|---|
| 짧게(예: 10분, 자동결제 95% 목표) + 늦은 승인은 환불 | 종결이 빠르고 테스트가 짧다 | PG 장애 때 환불이 몰린다(당첨자 경험 나쁨, 환불 경로 부하) |
| 결제 진행 상태를 예매가 받아 만료를 미룸 | 기한을 짧게 둘 수 있다 | 서비스 간 이벤트·상태 추가(계약 변경), 결제 서버 장애 때 상태도 안 온다 |
| **길게 30분(채택)** | 환불 없이 끝날 확률이 높다. 상수 하나라 단순하다 | 종결이 최장 60분 늦다. 추첨석이 분리돼 일반 판매에는 영향 없다 |

긴 선점의 비용이 작은 이유가 핵심이다. 일반 예매의 선점은 다른 사람이 살 좌석을 막으므로 짧아야 하지만(5분), 추첨석은 당첨자 몫으로 정해진 좌석이라 오래 잡아도 막히는 사람이 없다.

## 5. 선점과 재조회를 둘 다 줄이면 (후속 질문)
- Kafka 대기 3.3분은 "자동결제 전용 동시 3"이라는 개선 후보 기준 값이다. 현재 코드는 결제 명령 소비자가 동시 1개이고 PG를 동기 호출한다(`PaymentCommandKafkaConfiguration`, events-and-reliability.md). PG 300ms면 2,000건에 약 10분이다(`open-peak-load-plan.md` Z11, 미측정). 즉 지금 코드 기준 예산은 10분 + 10초 + 21분이라 30분도 빠듯하다.
- 재조회만 줄여도 Kafka 대기 10분은 남는다. 선점을 15분 아래로 줄이려면 Kafka 대기(소비자 동시 수)부터 줄여야 한다.
- 재조회 간격(SA 9-4)은 추첨만이 아니라 일반 결제와 환불 워커가 함께 쓰는 결제 담당 값이다. 줄이면 PG 장애가 몇 분 이어질 때 결과 미확정(NMC, 수동 확인) 건이 는다. 바꾸려면 `contract` 이슈로 결제 담당과 합의해야 한다.
- F1-b 대기는 선점 길이 그대로라, 15분으로 줄여도 Kafka를 15분 넘게 멈춰야 한다. 테스트 시간 문제는 시각 앞당기기나 설정값 분리가 더 직접적이다.

## 확인할 질문
- 시나리오 2에서 자동결제 전용 동시 수를 도입하지 않으면 Kafka 대기는 약 1분으로 줄어든다. 그때 30분을 줄일지.
- UNKNOWN 재조회 21분은 PG 장애가 길 때의 최장값이다. 실제 배포 측정에서 재조회까지 가는 비율은 확인 못 함.
