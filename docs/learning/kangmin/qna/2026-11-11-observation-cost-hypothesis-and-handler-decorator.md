# H1의 "관측 비용 가설"은 무엇이고, HttpHandler 데코레이터는 왜 "부담"이라고 했나

## 질문
H1 설계안 "다른 방안"에 "데코레이터가 부담스러우면 A안(WebFilter)으로 요청 로그·라우트 매칭 비용만 먼저 볼 수 있다. 다만 관측 비용 가설은 시험하지 못한다"고 썼다. 관측 비용 가설은 무슨 뜻인가? 데코레이터가 부담스럽다는 것은 적용하기 어려운 개념이라는 뜻인가?

## 짧은 답
- **관측 비용 가설**: "거절된 요청도 서버 관측(추적 스팬 만들기, `http_server_requests` 지표 기록)을 거치느라 CPU를 쓴다. 거절을 관측보다 앞에서 하면 그 비용이 사라져 서버 CPU가 내려간다"는 가설이다. 관측(Observation)은 Micrometer가 요청 하나를 시작·끝으로 감싸 지표와 스팬을 함께 만드는 장치다.
- **"부담"은 어렵다는 뜻이 아니었다.** 코드 양은 GlobalFilter와 거의 같고, Spring Boot가 공식 연결점(`WebHttpHandlerBuilderCustomizer`)을 준다. 표현이 모호했다. 뜻한 것은 아래 두 가지 대가다.
  1. 거절된 요청이 추적·요청 로그·`http_server_requests`에서 사라진다(A안은 로그만 사라진다).
  2. 팀원이 익숙한 Gateway 필터 층이 아니라 그보다 바깥 층이라, 읽는 사람이 위치를 알기 어렵다.
- 이 두 대가는 거절된 요청에만 해당한다. 받은 요청의 관측은 그대로라서 B안으로 정했다.

## 1. 요청 하나가 Gateway 안에서 지나는 순서
Spring Boot 4.1.2, spring-web 7.0.10 소스로 확인했다.

| 순서 | 층 | 하는 일 | CPU를 쓰는 일 |
|---|---|---|---|
| 1 | Netty | HTTP 바이트를 요청으로 해석 | HTTP I/O |
| 2 | HttpHandler 데코레이터 | (B안의 상한 위치) | 카운터 하나 |
| 3 | `HttpWebHandlerAdapter` | 요청 객체(exchange)를 만들고 **서버 관측을 연다** | 스팬 생성, 지표 태그 계산, 문맥 전파 |
| 4 | WebFilter: `RequestLogWebFilter` | 요청 로그 한 줄 | 로그 문자열·출력 |
| 5 | `DispatcherHandler` | 모든 라우트의 경로 조건 평가 | 라우트 매칭 |
| 6 | GlobalFilter -200 | (6차까지의 상한 위치) | — |
| 7 | GlobalFilter -100 | 인증(JWT, Redis 조회) | — |

- 6차까지는 6번에서 거절했다. 그래서 거절된 요청도 3·4·5번 비용을 다 냈다. 6차에서 거절 비율이 25%에서 40%로 바뀌어도 한 건당 Gateway CPU가 0.66\~0.71ms로 거의 같았던 이유를 이렇게 본다(추정).
- 5차 JFR에서 관측 묶음은 Gateway CPU의 약 24%, 로그는 5.2%였다. 이 몫은 받은 요청과 거절된 요청을 합친 값이라, 거절만의 몫은 확인 못 했다.

## 2. 선택지 비교
| 선택지 | 거절 위치 | 거절 때 건너뛰는 것 | 시험하는 가설 |
|---|---|---|---|
| A. 맨 앞 WebFilter | 4번 앞 | 로그, 라우트 매칭 | 로그·라우팅 비용 |
| B. HttpHandler 데코레이터 | 2번 | exchange 생성, **관측**, 로그, 라우트 매칭 | 관측 + 로그·라우팅 비용 |

- 처음에는 "관측 필터보다 앞의 WebFilter"로 옮기면 된다고 봤다. 소스를 보니 Boot 4에는 관측 필터가 없고, 3번 어댑터가 WebFilter 체인 전체를 감싼다. 그래서 A안으로는 관측을 건너뛸 수 없다.

## 3. 고른 이유와 감수한 점
- 고른 이유: H1의 목적이 "거절 한 건의 비용 줄이기"이고, 그 비용에서 가장 클 것으로 보는 관측을 건너뛰는 위치는 B안뿐이다.
- 감수한 점
  - 거절된 요청에는 traceId가 없다. 응답 본문의 `traceId`가 null이다.
  - 거절된 요청은 요청 로그와 `http_server_requests` 503 집계에 없다. 거절 수는 `gateway_in_flight_rejected_total`로 본다. 경보 규칙은 `http_server_requests`를 쓰지 않는다(확인).
  - 6차와 7차의 `http_server_requests` 요청 수를 그대로 비교하면 안 된다. 7차에는 거절이 빠진다.
- 바꿀 조건: 7차에서 한 건당 Gateway CPU가 6차(0.71ms, L64 2,500/s)와 차이가 없으면 관측 비용 가설은 틀린 것이다. 그때는 B안의 대가를 다시 따져 A안 위치로 되돌리는 것도 검토한다.

## 4. 확인할 질문
- 거절 한 건의 CPU가 얼마나 줄까? 7차에서 같은 부하(L64, 1,000\~2,500/s)로 잰다.
- 측정은 추적 샘플링 0.01, 운영은 1.0이다. 운영에서는 스팬을 실제로 보내는 비용까지 있어 B안의 효과가 측정보다 클 수 있다(H3, 이번에는 바꾸지 않음).
