# 스케줄러 쪽 추적 스팬을 끄면 무엇을 못 보게 되나

## 질문
Zipkin 메모리 저장 한도(10만 건)가 빨리 차는 원인이 reservation 스케줄러의 배경 스팬이라면, 그 스팬을 끄면 무엇을 못 보게 되는가.

## 배경 수치 (배포 서버, 2026-11-11 UTC 10시대, 사용자 요청이 거의 없는 10분, Zipkin API로 셈)
| 스팬 | 건수 | 몫 |
|---|---|---|
| reservation `evalsha`(스케줄러 안의 Redis Lua 호출) | 22,610 | 87% |
| reservation 스케줄러 작업(입장 허가, 추첨 배정·승계, 선점 만료 등) | 약 2,800 | 약 11% |
| 액추에이터·eureka | 약 500 | 약 2% |

10분에 약 2.6만 건이라 한도 10만 건은 약 40분이면 찬다(계산값). 기동 뒤 받은 스팬은 약 359만 건이고, 힙 오래 묵은 영역은 90%까지 찼다.

## 답
### 끄는 범위에 따라 잃는 것이 다르다
| 끄는 범위 | 줄어드는 양 | 못 보게 되는 것 |
|---|---|---|
| 스케줄러 안의 Redis 호출 스팬만 | 약 87% | 스케줄러 실행 한 번 안에서 어느 Redis 호출이 느렸는지(호출 단위 시간). 실행 전체 시간과 로그의 추적 ID는 남는다 |
| 스케줄러 작업 스팬까지 전부 | 약 98% | 위의 것에 더해 (1) 실행 한 번의 시작·끝 시각과 걸린 시간, (2) 그 실행에서 찍힌 로그를 추적 ID로 묶어 보기(MDC의 추적 ID가 비게 된다), (3) 스케줄러에서 시작해 Kafka로 다른 서비스까지 이어지는 흐름을 한 추적으로 보기 |
| 관측(Observation) 자체를 끄는 방식 | 같음 | 위의 것에 더해 같은 관측에서 나오는 지표(스케줄러 실행 시간 지표, Lettuce 명령 지표)도 사라진다. 그래서 "처리 시간은 지표로 남는다"는 말이 틀려진다 |

### 왜 (3)이 중요한가
- Kafka 송신과 수신은 관측이 켜져 있다(`config-repo/application.yml`의 `spring.kafka.template.observation-enabled`, `listener.observation-enabled`). 그래서 송신하는 쪽 스팬이 추적의 뿌리가 되어 받는 서비스까지 한 줄로 이어진다.
- 추첨 배정 → 자동결제 명령 → 결제 서비스 같은 흐름이 스케줄러에서 시작한다면, 스케줄러 스팬을 끄면 결제 쪽 스팬이 부모 없는 별도 추적으로 떨어진다. 장애 분석(F1 같은)에서 "어느 추첨 실행이 만든 결제인가"를 추적으로 잇지 못한다.
- 어느 스케줄러가 실행 안에서 Kafka를 직접 보내는지는 확인 못 함이다(outbox 릴레이가 스케줄러인지, 다른 스레드인지 코드로 봐야 한다).

### 그래서 고를 만한 범위
| 안 | 줄어드는 양 | 대가 |
|---|---|---|
| 가. 스케줄러 안의 Redis 호출 스팬만 끈다(관측은 두고 스팬만 만들지 않음) | 약 87% → 보존 약 5~8배(계산값) | 실행 안의 Redis 호출 단위 시간. 지표로는 남는다 |
| 나. 스케줄러 추적만 낮은 비율(예 1%)로 샘플링 | 약 97% | 사용자 정의 샘플러가 필요하다. 문제가 난 바로 그 실행이 안 남을 수 있다 |
| 다. 스케줄러 스팬 전부 끔 | 약 98% | 위 (1)~(3) 전부 |

추천은 가다. 장애 분석에 쓰는 것(실행 단위 시간, 로그 묶음, 서비스 간 흐름)은 남기고, 양의 대부분인 호출 단위 스팬만 걷어 낸다. "관측을 끈다"가 아니라 "스팬만 만들지 않는다"로 구현해야 지표가 남는다. 구현 방법(관측 필터 `ObservationPredicate`로 이름과 부모를 보고 거를지, 추적 핸들러에서 거를지)은 코드로 확인하고 정한다.

## 확인할 질문
- 요청이 많을 때(사용자 요청 스팬이 늘 때) 보존 시간이 얼마나 되는가. 측정 모드(샘플링 0.01)에서는 문제가 안 된다.
- 스팬 한 건의 평균 크기(10만 건에 힙 약 240MB면 건당 약 2.4KB, 거친 계산값).

## 이어진 질문: 스팬이 정확히 무엇이고, Redis 호출 스팬을 끄면 무엇을 감수하나
### 용어
| 용어 | 뜻 | 이 프로젝트에서 |
|---|---|---|
| 추적(trace) | 하나의 일(요청 하나, 스케줄러 실행 하나)이 여러 단계·서비스를 지나간 전체 기록. 추적 ID 하나로 묶인다 | Zipkin 화면의 한 줄 |
| 스팬(span) | 추적 안의 한 단계 기록 한 건. 이름, 시작 시각, 걸린 시간, 서비스, 부모 스팬 ID, 태그(예: Redis 명령 이름), 오류 여부를 가진다 | 아래 예시의 21줄 각각 |
| 관측(Observation, Micrometer) | 코드에서 "여기부터 여기까지를 잰다"는 측정 지점. 끝날 때 붙은 처리기들에게 결과를 넘긴다 | Spring 스케줄러, Lettuce, Kafka, HTTP가 자동으로 만든다 |
| 지표(metric) | 관측 결과를 시간 구간으로 합친 숫자(횟수, 합, 최대). 실행 한 건 한 건은 남지 않는다 | Prometheus `lettuce_*` 등 |

- 관측 하나에 처리기가 둘 붙어 있다. 지표 처리기는 타이머 숫자를 올리고, 추적 처리기는 스팬을 만들어 Zipkin으로 보낸다.
- "스팬만 만들지 않는다"는 추적 처리기만 건너뛰고 지표 처리기는 그대로 두는 것이다.

### 실제 예(배포 서버, 입장 허가 스케줄러 실행 한 번, Zipkin에서 꺼냄)
```
추적 (스팬 20개)
└ task queueadmissionscheduler.admit   2.1ms   reservation-service
   ├ evalsha   0.48ms   → redis   태그 db.operation=EVALSHA
   ├ evalsha   ...
   └ ... (evalsha 19개)
```
이 실행 하나가 스팬 20개를 만든다. 이 스케줄러가 몇 초마다 돌기 때문에 10분에 약 2.6만 건이 쌓였다.

### Redis 호출 스팬(evalsha)만 끄면
남는 것
- 스케줄러 실행 스팬(`task ...admit 2.1ms`): 언제 돌았고 얼마나 걸렸는지, 그 실행의 로그 추적 ID, 그 실행에서 Kafka로 이어진 흐름
- Redis 명령 지표: `lettuce_*`(명령별 횟수·시간 합·최대, 배포 서버에서 노출 확인)

감수하는 것
| 잃는 것 | 생기는 일 |
|---|---|
| 실행 한 번 안의 호출별 시간과 순서 | 실행이 300ms 걸렸을 때, Redis 호출 하나가 느렸는지 호출 사이에 CPU를 기다렸는지를 그 실행에 대해서는 가리지 못한다. 지표의 명령별 최대·평균으로 짐작만 한다 |
| 실행 한 번에 Redis를 몇 번 불렀는지 | 호출 수가 늘어나는 회귀(예: 반복문 안에서 호출)를 추적 화면으로 못 본다. 지표 횟수 증가로 간접 확인한다 |
| 특정 호출의 오류 표시 | 어느 호출에서 실패했는지 스팬 오류 표시로는 못 본다. 예외 로그(추적 ID 포함)로 본다 |

- 실행 전체 시간과 Redis 지표가 남아 "느려졌다"는 알 수 있다. 잃는 것은 "실행 한 번 안 어디가 느렸나"를 바로 짚는 능력이다.
- 정상 실행은 2ms 안팎(위 예)이라 평소 호출 단위 스팬의 쓸모는 작다. 느린 실행을 파고들 때만 아쉽다. 그때는 그 기간만 다시 켜는(설정값으로 끄고 켜는) 방식이면 대가가 줄어든다.
