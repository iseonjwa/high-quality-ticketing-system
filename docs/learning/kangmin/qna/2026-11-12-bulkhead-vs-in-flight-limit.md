# 벌크헤드와 동시 처리 수 상한은 무엇이 다른가

## 질문
벌크헤드랑 동시 처리 수 상한이 뭐가 다른지 잘 모르겠다.

## 짧은 답
- **장치의 모양은 같다.** 둘 다 "지금 동시에 몇 개 하고 있나"를 세는 카운터이고, 차면 기다리지 않고 바로 거절한다(세마포어).
- **다른 것은 무엇을 감싸고, 무엇을 지키느냐**다.

| | 벌크헤드 `auth-redis` | 동시 처리 수 상한 |
|---|---|---|
| 감싸는 범위 | 인증 필터 안의 **Redis 조회 한 번** | Gateway가 받은 **요청 전체**(들어와서 응답이 나갈 때까지) |
| 위치 | 인증 필터(GlobalFilter -100) 안쪽, 차단기 안 | 맨 앞 HttpHandler 데코레이터(관측·로그·라우팅·인증보다 앞) |
| 지키는 것 | **한 의존성(Redis)** 에 몰리는 호출이 Gateway 자원을 다 잡아먹지 않게 격리 | **Gateway 자신**(CPU·메모리·지연)이 감당 못 할 양을 받지 않게 |
| 값 | 동시 50(ADR 0050, 처음엔 라이브러리 기본값 25) | 동시 64(#488) |
| 거절 응답 | 503 `bulkhead_full`(인증 실패 경로) | 503 `GATEWAY_OVERLOADED` + `Retry-After: 2` |
| 거절 한 건 비용 | 높다. JWT 검증까지 마친 뒤에 거절된다 | 낮다. 받은 요청의 2~8%(8차 R0) |
| 막지 못하는 것 | Redis가 아닌 곳(CPU·메모리)의 과부하 | 의존성 하나가 느려져 그 호출만 쌓이는 것(상한 안에서도 64개가 모두 Redis를 기다릴 수 있다) |

비유하면 **동시 처리 수 상한은 건물 정문의 입장 인원 제한**이고, **벌크헤드는 건물 안 엘리베이터 한 대의 정원**이다. 정문 제한은 건물 전체가 붐비지 않게 하고, 엘리베이터 정원은 엘리베이터가 고장 나거나 느려질 때 그 앞 줄이 건물 전체를 막지 않게 한다.

## 0. 세마포어란 (뷰어 코멘트로 덧붙임)
- **세마포어(semaphore)**: "동시에 들어갈 수 있는 자리 수"를 숫자 하나로 들고 있는 카운터다. 원래 철도 신호기를 뜻하는 말이고, 운영체제에서 여러 스레드가 공유 자원을 쓰는 순서를 정할 때 쓰는 기본 도구다(데이크스트라, 1960년대).
- 동작은 두 가지뿐이다.
  - **얻기(acquire)**: 남은 자리가 있으면 1을 빼고 들어간다. 없으면 기다리거나(대기형) 바로 실패한다(즉시 거절형).
  - **놓기(release)**: 일이 끝나면 1을 더해 자리를 돌려준다.
- 예: 자리 3짜리 세마포어에서 요청 A·B·C가 들어가면 남은 자리는 0이다. D가 오면 기다리거나 거절된다. A가 끝나 자리를 놓으면 D가 들어갈 수 있다.
- 이 프로젝트의 두 장치는 모두 **즉시 거절형 세마포어**다.
  - 벌크헤드: `max-concurrent-calls: 50`, `max-wait-duration: 0`(기다리지 않음). Resilience4j의 `SemaphoreBulkhead`가 Java `Semaphore`로 구현한다.
  - 동시 처리 수 상한: 자리 64. Java `Semaphore` 클래스 대신 `AtomicInteger` 카운터로 같은 일을 한다(`InFlightLimitHandlerDecorator.java:45`). 요청이 들어올 때 1을 더해 64를 넘으면 거절하고(`:86`), 응답이 끝나거나 끊길 때 `doFinally`로 1을 뺀다(`:93`). 이 놓기를 빠뜨리면 자리가 새어 결국 모든 요청이 거절되므로, 반납 위치가 구현의 핵심이다([데코레이터 노트](2026-11-11-gateway-httphandler-decorator-early-reject.md)).
- 락(lock)과의 차이: 락은 자리가 1개인 세마포어와 비슷하다(한 번에 하나만). 세마포어는 자리가 N개라 "N개까지 동시에"를 표현한다.

## 1. 이름의 뜻
- **벌크헤드(bulkhead, 격벽)**: 배 밑바닥을 여러 칸으로 나눠, 한 칸에 물이 차도 배 전체가 가라앉지 않게 하는 벽이다. 소프트웨어에서는 "의존성마다 쓸 수 있는 자원(스레드·동시 호출 수)을 나눠, 한 의존성이 느려져도 나머지가 살아 있게 하는 것"이다. 그래서 보통 의존성 이름별로 둔다(`auth-redis`).
- **동시 처리 수 상한(in-flight limit, concurrency limit)**: 서버가 한꺼번에 처리하는 요청 수 자체에 상한을 두는 부하 차단(load shedding)이다. 의존성과 상관없이 "나는 지금 이만큼만 받는다"를 정한다.

## 2. 요청 하나가 두 장치를 지나는 순서
```
요청 → [동시 처리 수 상한: 64칸] → 관측·요청 로그 → 라우트 매칭 → 인증 필터
                                                              └ JWT 검증 → [벌크헤드: 50칸] → 차단기 → Redis 조회
```
- 상한 64칸 안에 들어온 요청만 인증까지 간다. 그 가운데 **동시에 Redis를 조회하고 있는 것**이 50을 넘으면 벌크헤드가 거절한다.
- 그래서 바깥 상한이 안쪽 벌크헤드보다 너무 크면, 거절이 비싼 안쪽(JWT 검증 뒤)에서 일어난다. 6차에서 상한을 128로 올리자 처리 중 수가 50 위로 올라가 2,500/s `bulkhead_full`이 1,966건이 됐다(상한 64에서는 96건).
- 바깥 상한이 64여도 벌크헤드 거절이 0은 아니다. 8차 2,500/s에서 30초에 205~386건이 나왔다. 처리 중 요청 대부분이 동시에 Redis 단계에 있는 순간이 있기 때문으로 본다(추정).

## 3. 왜 둘 다 필요한가
| 상황 | 동시 처리 수 상한만 있으면 | 벌크헤드만 있으면 |
|---|---|---|
| 요청이 몰려 CPU가 찬다(5~8차) | 넘친 요청을 맨 앞에서 싸게 거절. 받은 요청의 지연과 메모리가 묶인다 | Redis 조회만 50으로 묶일 뿐, 요청 자체는 계속 받아 줄이 길어지고 OOM까지 갔다(5차). 벌크헤드는 연결을 받는 것을 막지 못한다 |
| Redis가 느려진다 | 64칸이 모두 Redis 대기로 찰 수 있다. 다른 경로(인증이 필요 없는 공개 API 등)도 자리를 못 얻는다 | Redis 쪽은 50칸까지만 쌓이고 나머지는 바로 거절돼, Gateway의 다른 일은 계속된다 |
| Redis가 멈춘다 | 같은 문제 | 벌크헤드는 동시 수만 센다. 멈춘 것을 알아채고 호출을 끊는 것은 **차단기**의 일이다 |

## 4. 차단기와도 구분하기
| 장치 | 세는 것 | 하는 일 |
|---|---|---|
| 동시 처리 수 상한 | 지금 처리 중인 요청 수 | 넘치면 맨 앞에서 거절(과부하 방어) |
| 벌크헤드 | 지금 진행 중인 Redis 호출 수 | 넘치면 그 호출만 거절(의존성 격리) |
| 차단기 | 최근 Redis 호출의 실패·느린 비율 | 비율이 기준을 넘으면 일정 시간 Redis 호출을 아예 막음(장애 감지) |

ADR 0050이 정한 역할 나눔이 이것이다. 차단기는 Redis 장애만 세고(벌크헤드 거절은 실패로 세지 않음), 넘친 양은 벌크헤드와 동시 처리 수 상한이 거절한다. 1차의 "Redis는 정상인데 전체 503"은 벌크헤드 거절을 차단기가 Redis 실패로 세서 생긴 일이었다.

## 5. 값 정하기
- 둘 다 리틀의 법칙(동시 수 = 도착률 × 한 건 시간)으로 첫 값을 잡았다.
  - 벌크헤드 50: 초당 1,000건 × 정상으로 볼 Redis 조회 한 건 50ms(`config-repo/gateway.yml` 주석, 계산값).
  - 상한 64: 굿풋이 멈춘 약 1,480/s × p95 200ms에 맞는 평균 40~45ms ≈ 60~67(계산값).
- 바깥(64)이 안쪽(50)보다 조금 큰 것은 자연스럽다. 처리 중 요청이 모두 동시에 Redis 단계에 있지는 않기 때문이다. 다만 바깥을 크게 올리면 안쪽 거절이 늘어 거절 비용이 비싸진다(2절의 128 사례).
