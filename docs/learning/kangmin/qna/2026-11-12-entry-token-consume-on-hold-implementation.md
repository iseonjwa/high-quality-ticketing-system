# 선점 성공 시 입장 토큰을 무효화하려면 어떻게 처리해야 하나

## 질문
팀 회의에서 입장 토큰을 "선점 성공 시(좌석 예매 버튼)" 소모하기로 정했다(A안, [판단 기록](../../../ai-judgments/kangmin/2026-11-12-entry-token-consume-on-hold-team-decision.md)). 그러려면 입장 토큰을 어떻게 무효화하거나 만료시켜야 하나?

## 짧은 답
- 입장 토큰은 **서명된 JWT라 한번 내준 토큰을 "만료"시킬 수는 없다.** `exp`는 토큰 안에 박혀 있고, Gateway는 서명과 `exp`만 보고 통과시킨다(Redis를 보지 않는다). 그래서 "무효화"는 **"이 토큰(jti)은 이미 썼다"는 기록을 어딘가에 두고, 다음 요청에서 그 기록과 비교해 거절하는 것**이다.
- 기록과 비교를 **어디서 하느냐**가 핵심이다. 추천은 **선점 API(reservation-service)에서 DB 고유 제약으로** 하는 것이다.
  1. Gateway는 검증한 토큰의 `jti`를 헤더(`X-Entry-Token-Id`)로 넘긴다. Gateway는 지금처럼 Redis 없이 서명만 본다.
  2. 선점 서비스는 선점을 저장할 때 그 `jti`를 `seat_hold_requests`에 함께 저장하고, `entry_token_jti`에 **고유 인덱스**를 둔다. 같은 `jti`로 두 번째 선점이 오면 DB가 막는다.
  3. 선점이 커밋된 뒤 대기열의 `issued`에서 그 사용자를 지운다(`ZREM`). 지우지 않으면 대기열에 다시 들어가도 **같은(이미 쓴) 토큰**을 돌려받아 10분 동안 갇힌다.
  4. 프런트는 선점 201을 받으면 저장한 입장 토큰을 지우고, 거절 응답을 받으면 대기열로 보낸다.
- 담당이 넷(Gateway 강민, 선점 권우, 대기열 영은, 프런트 준현)이라 ISE-207 contract로 나눠 맡고, SA 7-3("1회용이 될 수 없다")을 바꾸는 ADR이 필요하다.

## 1. 왜 "만료시키기"가 아니라 "쓴 기록과 비교"인가
| 방법 | 어떻게 | 문제 |
|---|---|---|
| 토큰의 `exp`를 앞당김 | 불가능 | JWT는 발급 뒤 내용을 바꿀 수 없다. 바꾸면 서명이 깨진다 |
| 짧은 `exp`로 다시 발급 | 선점 때 새 토큰을 내줌 | 옛 토큰은 여전히 `exp`까지 유효하다. 옛 토큰을 막는 장치가 결국 따로 필요하다 |
| **쓴 `jti`를 기록하고 비교** | 기록 위치를 정한다 | 기록을 어디서 읽느냐에 따라 비용과 정확도가 달라진다(2절) |

지금 `jti`는 `entry:{scheduleId}:{userId}:{발급ms}`의 해시라(`JwtEntryTokenIssuer.java:53-58`), 같은 사람이 새로 발급받으면 발급 시각이 달라져 새 `jti`가 된다. 그래서 "쓴 `jti` 기록"은 그 토큰 하나만 막고, 대기열에서 새로 받은 토큰은 막지 않는다.

## 2. 기록과 비교를 어디서 하나
| 선택지 | 비교 위치 | 장점 | 대가 |
|---|---|---|---|
| G. Gateway에서 Redis 폐기 목록(denylist) | Gateway가 선점 요청마다 Redis `used:{jti}`를 확인 | 좌석 조회(GET)까지 막을 수 있다 | Gateway 뜨거운 경로에 Redis 조회가 하나 더 붙는다(11/9~12에 Gateway CPU·차단기로 고생한 바로 그 경로). 선점 성공과 기록 사이가 원자적이지 않아, 동시에 두 번 누르면 둘 다 통과할 수 있다 |
| **S. 선점 API에서 DB 고유 제약** ✅ | `seat_hold_requests.entry_token_jti` 고유 인덱스 | 선점 저장과 같은 트랜잭션이라 **동시에 두 번 눌러도 하나만 성공**한다. Gateway·Redis 비용이 늘지 않는다. 기존 멱등 처리(같은 요청 다시 보내기)와 함께 쓸 수 있다 | 좌석 조회(GET)는 토큰 `exp`까지 계속 된다(조회는 해롭지 않다고 본다). Gateway가 `jti`를 헤더로 넘겨야 한다 |
| Q. 대기열 Redis `issued`에서만 지움 | 대기열 상태만 바꿈 | 가장 간단하다 | Gateway는 `issued`를 보지 않으므로 **이미 받은 토큰은 그대로 통과한다.** 막는 효과가 없다. S와 함께 써야 의미가 있다 |

추천은 **S + Q**다. S가 실제로 막고, Q는 "다시 줄 서면 새 토큰"을 보장한다.

## 3. S + Q 구현 순서 (담당별)

### 3-1. Gateway (강민)
- `EntryTokenFilter`가 검증을 마친 뒤 `jti`를 요청 헤더 `X-Entry-Token-Id`로 넘긴다. 사용자가 같은 이름의 헤더를 보내면 지우고 덮어쓴다(위조 방지, `X-User-Id`와 같은 방식).
- 대상은 선점(`POST /api/v1/schedules/{id}/reservations`)만이다. 좌석 조회는 넘기지 않아도 된다.

### 3-2. 선점 서비스 (권우)
- 마이그레이션: `seat_hold_requests`에 `entry_token_jti VARCHAR(64)` 컬럼과 **고유 인덱스**를 더한다. 동기형 선점은 성공한 선점만 이 표에 행을 남기므로(ISE-207 본문) 성공한 요청끼리만 부딪친다. 행이 실패 상태로도 남는 구조라면 `WHERE status = 'HELD'` 부분 인덱스로 바꾼다. `seat_hold_requests.status`는 `REQUESTED`·`HELD`·`REJECTED` 셋이다(`V20261030_3__seat_hold_tables.sql:91`). 요청 행의 `HELD`는 "선점에 성공한 요청"이라는 결과라, 예매가 나중에 만료돼도 그대로 남는다. 그래서 한 번 성공한 토큰은 계속 막힌다.
  - 실패를 막지 않는 이유: 실패한 선점(좌석 이미 선점됨, 한도 초과)은 토큰을 쓴 것으로 치지 않아야 한다. 회의 결정이 "선점 **성공** 시 소모"이기 때문이다. 실패한 요청까지 막으면 좌석 경쟁에서 한 번 진 사람이 대기열로 쫓겨난다.
  - 추첨 선점은 입장 토큰이 없으므로 `NULL`이고 영향이 없다.
- 처리 순서(`SyncSeatHoldService.hold`):
  1. 멱등키 재요청 확인(같은 요청이면 저장된 결과를 그대로 돌려준다) — **이것을 먼저** 해야 네트워크 재시도가 "이미 쓴 토큰"으로 거절되지 않는다.
  2. 좌석·한도 확인과 선점 저장, 이때 `entry_token_jti`도 저장.
  3. 고유 제약 위반이면 "입장 토큰 이미 사용"으로 거절한다. 다른 고유 제약(같은 좌석 중복 등, TS-3)과는 **제약 이름으로** 구분한다.
- 커밋 뒤 이벤트: `@TransactionalEventListener(AFTER_COMMIT)`로 대기열 정리를 부른다(3-3). 롤백된 선점은 소모하지 않는다.

### 3-3. 대기열 (영은)
- 선점 커밋 뒤 `queue:{scheduleId}:issued`에서 그 사용자를 `ZREM` 한다.
- 이유: `enter.lua`·`issue-token.lua`는 `issued`에 유효한 기록이 있으면 같은 토큰을 다시 준다(`issue-token.lua:9-14`, `enter.lua:17-19`). 지우지 않으면 소모된 사람이 다시 줄을 서려 해도 같은 토큰을 받아 10분 동안 아무것도 못 한다.
- 같은 서비스(reservation-service) 안이라 동기 호출로 충분하다. `ZREM`이 실패하면 로그를 남기고, 거절할 때 한 번 더 지우는 것으로 보완한다(대기열 담당 노트의 안).

### 3-4. 프런트 (준현)
- 선점 201을 받으면 저장한 입장 토큰을 지운다(`frontend/src/auth/entryTokens.ts`).
- 거절 응답을 받으면 토큰을 지우고 대기열로 보낸다. 지금은 403 `ENTRY_TOKEN_INVALID`일 때만 지운다(`frontend/src/api/client.ts:44`).
- 결제 실패·시간 초과 화면의 [좌석 다시 고르기]는 이제 **대기열로 다시 줄 서기**가 된다. 문구를 "입장 시간이 끝났어요. 다시 줄을 서 주세요"처럼 바꿔야 한다.

## 4. 거절 코드
| 선택지 | 프런트 처리 | 장점 | 대가 |
|---|---|---|---|
| 403 `ENTRY_TOKEN_INVALID` 재사용 | 지금 코드 그대로(토큰 지우고 대기열로) | 프런트 변경 없음 | "만료"와 "이미 사용"을 구분하지 못해 안내 문구가 하나다 |
| **403 `ENTRY_TOKEN_USED`(새 코드)** ✅ | `ENTRY_TOKEN_INVALID`와 같이 처리하는 줄 하나 + 문구 | 원인을 구분한 안내, 지표·로그에서 소모 거절을 따로 센다 | 프런트 한 줄 추가 |
| 409 `ENTRY_TOKEN_USED` | 새 처리 필요 | "자원 상태 충돌"이라는 의미에 맞다 | 프런트가 지금 409를 토큰 문제로 보지 않아, 처리를 빠뜨리면 같은 거절이 반복된다(대기열 담당 노트의 지적) |

추천은 **403 + 새 코드**다. 상태 코드는 기존 처리 흐름(403이면 입장 토큰 문제)에 맞추고, 코드 이름으로 원인을 구분한다. 문서끼리 403·409가 어긋나 있으니(11/11 답글 초안은 409) 이번에 하나로 정해 ISE-207에 적는다.

## 5. 테스트로 확인할 것
| 경우 | 기대 |
|---|---|
| 같은 토큰으로 두 번째 선점 | 403 `ENTRY_TOKEN_USED`, 좌석·매수 변화 없음 |
| 같은 토큰으로 동시에 두 번 선점(경합) | 하나만 201, 하나는 거절(고유 제약) |
| 같은 멱등키로 재요청(네트워크 재시도) | 저장된 201 그대로 |
| 좌석 이미 선점됨(409)으로 실패한 뒤 같은 토큰으로 다른 좌석 | 성공(실패는 소모가 아님) |
| 선점 성공 뒤 대기열 재진입 | 새 순번, 새 `jti` 토큰 |
| 선점 트랜잭션이 롤백 | 토큰 소모 안 됨, `issued` 그대로 |
| 추첨 선점 | 영향 없음 |

## 6. 결정한 것과 감수한 점
- 결정(팀 회의): 선점 성공 시 소모(A).
- 감수: 결제 토큰 만료·결제 거절로 선점이 풀리면 대기열에 다시 서야 한다. 결제 토큰은 선점 만료 10초 전에 끝나므로(기본 4분 50초), 결제 화면에 남은 시간 안내가 중요해진다.
- 바꿀 조건: 결제 시간 초과로 다시 줄 서는 사람이 많다는 지표가 나오면 A'(결제 없이 끝난 선점은 1회 복원)를 다시 본다.

## 7. 다음 할 일
1. ADR: "입장 토큰은 선점 성공 시 소모한다(S + Q, 403 `ENTRY_TOKEN_USED`)". SA 7-3의 "jti는 추적용, 폐기 목록은 만들지 않는다, 1회용이 될 수 없다"를 대체한다.
2. ISE-207 본문 갱신: 회의 결정, 담당별 할 일(3절), 거절 코드, 테스트(5절).
3. 담당별 구현 PR(Gateway 헤더는 강민).
