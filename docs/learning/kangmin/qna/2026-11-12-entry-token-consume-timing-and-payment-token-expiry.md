# 입장 토큰은 언제 소모해야 하나, 결제 토큰이 먼저 만료되면 어떻게 동작하나

## 질문
1. 입장 토큰을 언제 소모(무효화)해야 하나? 좌석 예매하기를 누를 때(선점 성공, 결제 토큰을 받는 시점)인가, 결제가 완료될 때인가?
2. 입장 토큰은 아직 유효한데 결제 토큰이 만료돼 결제가 실패하면 시스템은 어떻게 동작하나?

## 짧은 답
- **지금은 입장 토큰을 소모하는 시점이 없다.** 발급 후 10분이 지나면 자연 만료될 뿐이고, 그 안에서는 같은 토큰으로 여러 번 선점할 수 있다(1인 매수 한도만 막는다).
- **결제 토큰은 항상 선점보다 10초 먼저 만료된다.** 기본 선점 5분이면 4분 50초다. 만료 뒤 결제하면 403 `PAYMENT_TOKEN_INVALID`이고, 결제 행도 생기지 않고 PG도 부르지 않는다. 좌석은 선점 만료 뒤 스케줄러가 풀 때까지(약 10~15초) HELD로 남는다. 화면은 "결제 가능 시간이 지났어요 → 좌석 다시 고르기"로 안내하고, 입장 토큰이 살아 있으면 대기열 없이 좌석 화면으로 돌아간다.
- **소모 시점은 "남용을 얼마나 막을지"와 "실패한 사람이 얼마나 쉽게 다시 시도할지"의 교환이다.** 선점 성공 시 소모하면 결제 시간 초과·카드 거절을 겪은 사람이 대기열 맨 뒤로 돌아간다. 결제 완료 시 소모하면 10분 동안 좌석을 잡았다 놓기를 반복할 수 있다.
- 추천은 **선점 성공 시 소모하되, 결제 없이 끝난 선점(만료·결제 거절)은 토큰 유효 시간 안에서 한 번 더 기회를 주는 안(A')** 이다. 다만 팀 논의 중(ISE-207)이고, 정할 것은 3절 끝에 있다.

## 1. 지금 동작 (코드로 확인, 실행으로는 확인 안 함)

### 1-1. 세 가지 시간
| 무엇 | 길이 | 정하는 곳 | 끝나면 |
|---|---|---|---|
| 입장 토큰 | 발급 후 10분 | JWT `exp`는 코드 상수 `EntryTokenClaims.TTL`(`common/.../auth/EntryTokenClaims.java:11`), Redis `issued`는 설정 `queue.entry-token-ttl: 10m`(`config-repo/reservation-service.yml:29`) | 좌석 조회·선점 요청이 Gateway에서 403 `ENTRY_TOKEN_INVALID` |
| 좌석 선점 | 기본 5분(회차별 `hold_minutes`) | `SyncSeatHoldService.java:192`, `Schedule.java:61` | 만료 스케줄러(5초 주기)가 EXPIRED로 바꾸고 좌석·매수 반환 |
| 결제 토큰 | 선점 만료 10초 전까지 | `JwtPaymentTokenIssuer.java:51`(`exp = holdExpiresAt - 10초`) | 결제 승인·준비가 403 `PAYMENT_TOKEN_INVALID` |

- 입장 토큰 설정값(`10m`)만 바꾸면 JWT `exp`는 코드 상수라 두 값이 어긋난다. 코드상의 사실이다.
- 결제 토큰의 10초 여유는 Gateway 시한 3초 + 결과 반영 2초 + 여유 5초다(`PaymentTokenIssuer.java:7-8`). 결제가 승인됐는데 선점이 먼저 끝나는 일을 줄이려는 장치다.

### 1-2. 입장 토큰
- reservation-service 대기열이 발급하고(`QueueService.issueToken`), **Gateway만 검증한다**(`EntryTokenFilter`, 대상은 좌석 조회와 선점 두 경로). reservation-service는 다시 보지 않는다.
- 소모 시점이 없다. SA 7-3도 "jti는 추적용, 폐기 목록은 만들지 않는다, 1회용이 될 수 없다"고 적었다(`docs/core/SA MASTER.md:622`).
- 같은 토큰으로 여러 번 선점할 수 있다. 막는 것은 회차별 1인 매수 한도뿐이고, 선점이 만료되거나 결제가 거절되면 매수가 돌아오므로 다시 선점할 수 있다.
- 프런트는 403 `ENTRY_TOKEN_INVALID`를 받을 때만 저장한 토큰을 지운다. 선점에 성공해도 지우지 않는다.

### 1-3. 질문 2: 입장 토큰은 유효, 결제 토큰은 만료된 상태에서 결제
| 단계 | 일어나는 일 | 근거 |
|---|---|---|
| 결제 요청 | payment-service가 토큰 서명·내용을 확인한 뒤 만료면 403 `PAYMENT_TOKEN_INVALID` | `PaymentApprovalService.java:126-141` |
| 결제 기록 | 결제 행·멱등 기록이 생기지 않고 PG도 부르지 않는다(허가와 TX1보다 앞에서 끝남) | 테스트 `PaymentApprovalApiTest.java:279-290` |
| 좌석 | 이벤트가 나가지 않아 reservation은 모른다. HELD로 남았다가 선점 만료 뒤 스케줄러가 풀어 준다(결제 토큰 만료 후 약 10~15초) | `SeatHoldExpiryService.java:86-99`, 리허설 기록 `2026-11-06-rehearsal.md:27` |
| 화면 | "결제 가능 시간이 지났어요. 잡아 둔 좌석은 곧 풀려요. 좌석을 다시 골라 주세요." + [좌석 다시 고르기]. 저장한 결제 시도와 선점 정보를 지운다 | `PaymentPage.tsx:680-688`, `usePaymentFlow.ts:37-45` |
| 다시 고르기 | 대기열 경로로 가지만 입장 토큰이 살아 있으면 바로 좌석 화면 | `PaymentPage.tsx:333-340`, `queueAdmission.ts:68-72` |
| 결제 토큰 재발급 | 만료를 늘려 주는 길은 없다. 예매 조회·같은 멱등키 재요청도 같은 `exp`로만 다시 서명하고, 만료 뒤에는 주지 않는다 | `ReservationService.java:48-54`, `SyncSeatHoldService.java:119-127` |

예외 두 가지:
- 같은 멱등키로 다시 보내면 저장된 결과를 받는다.
- 같은 예매에 이미 결제가 있으면 그 결제로 이어진다(DECLINED·REFUNDED면 409 `PAYMENT_ALREADY_CLOSED`).

**발견한 빈틈(코드로 추론, 실행 확인 안 함)**: [좌석 다시 고르기]로 바로 돌아가면, 옛 선점이 풀리기 전 약 10~15초 동안 같은 좌석은 409 `SEAT_ALREADY_HELD`, 매수 한도는 `PURCHASE_LIMIT_EXCEEDED`가 날 수 있다. 자기 선점 때문에 자기가 막히는 모양이다. 결제 토큰 만료 때 선점을 바로 풀어 주는 경로(선점 취소 API 등)가 있는지는 확인하지 못했다.

### 1-4. 결제 도중에 만료되면
| 시점 | 동작 |
|---|---|
| 결제 행을 만든 뒤, PG 호출 전 | 다시 확인해 만료면 PG를 부르지 않고 DECLINED(`TOKEN_EXPIRED`)로 닫는다. `PaymentDeclined`가 나가 reservation이 선점을 RELEASED로 바꾸고 좌석을 바로 돌려준다 |
| PG 호출이 이미 시작된 뒤 | 다시 확인하지 않고 결과대로 간다. reservation은 PG 승인 시각을 선점 만료와 비교해, 안이면 확정하고 넘으면 EXPIRED + 환불 요청 |

## 2. 입장 토큰 소모 시점 선택지

이미 11/9에 "선점 성공 시 소모"를 수용했고(판단 기록 `2026-11-09-entry-token-consume-on-hold.md`), ISE-207로 대기열·선점 담당과 논의 중이다. 오늘 질문(결제 토큰 만료로 실패한 사람)을 넣어 다시 비교한다.

| 선택지 | 소모 시점 | 막는 것 | 결제 실패한 사람은 | 구현 |
|---|---|---|---|---|
| C. 지금(소모 없음) | 10분 자연 만료 | 없음. 10분 동안 매수 한도 안에서 선점·해제를 반복할 수 있다 | 바로 다시 선점(옛 선점이 풀린 뒤) | 없음 |
| A. 선점 성공 시 | 선점 201 | 한 입장 = 한 번의 선점. 좌석을 잡았다 놓기 반복("좌석 돌리기")을 막는다 | **결제 시간 초과·카드 거절이면 대기열 맨 뒤로 돌아간다** | 중간: Gateway가 `jti` 전달, `seat_hold_requests.entry_token_jti` 고유 인덱스, `issued`에서 제거, 거절 코드 |
| B. 결제 완료 시 | 예매 CONFIRMED | 같은 토큰으로 두 번 구매(매수 한도가 이미 막음) | 10분 안이면 바로 다시 시도 | 중간: 결제 결과 소비자에서 소모 |
| **A'. 선점 시 소모 + 한 번 더 기회** | 선점 201, 단 결제 없이 끝난 선점(만료·거절)은 토큰 유효 시간 안에서 1회 복원 | A와 거의 같다(돌리기는 2회까지) | 토큰 10분 안이면 한 번 더 선점 | A보다 조금 큼: 선점 횟수를 세거나(고유 인덱스 대신 횟수 2) 만료·거절 때 복원 |

### 고르는 기준
1. **소모의 목적이 무엇인가.** 남용(좌석 돌리기) 방지라면 A·A'이고, 대기열 회전(다음 사람을 더 빨리 들이기)이라면 소모와 입장 속도를 묶는 설계가 따로 필요하다. 지금 입장 속도는 초당 50명 고정이라 소모만으로 회전이 빨라지지는 않는다(Q3, 설계값 N=50).
2. **실패한 사람의 비용.** 결제 토큰은 4분 50초라 결제창에서 머뭇거리거나 카드 인증이 늦으면 만료될 수 있다. 티켓 오픈에서 대기열 맨 뒤로 돌려보내는 것은 사용자에게 큰 손해다.
3. **구현·검증 시간.** 발표(11/19)까지 남은 시간이 짧다. 서비스 경계를 넘는 변경(Gateway·대기열·선점·프런트)이라 contract 이슈와 테스트가 필요하다.

### 추천과 이유
- **A'를 추천한다.** 남용 방지(선점 한 번 = 입장 한 번)를 지키면서, 자기 잘못이 아닐 수도 있는 실패(결제 시간 초과, 카드 거절)에 한 번의 기회를 준다. 실제 예매 사이트들도 결제 시간 초과 뒤 일정 시간 안의 재시도를 허용하는 경우가 많다(일반론, 이 프로젝트에서 조사하지 않음).
- 시간이 모자라면 **"알려진 한계(C, 10분 자연 만료)"로 두는 것**도 합리적이다. 이미 정한 기한(이번 주 안에 답이 모이지 않으면 알려진 한계)과 같다.
- **B는 추천하지 않는다.** 결제 완료 시 소모는 매수 한도가 이미 막는 것(두 번 구매)만 막고, 좌석 돌리기는 막지 못해 소모하는 의미가 작다.

### 감수할 점
- A': 돌리기를 완전히 막지는 못한다(2회까지). 선점 횟수를 세는 저장 위치(DB 또는 Redis)와 복원 조건(EXPIRED·RELEASED만, 사용자 취소는 제외 등)을 정해야 한다.
- C: 남용을 막지 못한다. 대신 바꾸는 것이 없다.

### 정할 것 (팀 논의용)
1. 소모의 목적: 남용 방지인가, 회전인가.
2. A·A'·C 중 무엇으로 갈지, 기한(이번 주) 안에 못 정하면 C를 알려진 한계로 둘지.
3. 거절 코드: 403 `ENTRY_TOKEN_INVALID`(프런트가 토큰을 지우고 대기열로 보냄) 대 409 `ENTRY_TOKEN_USED`(새 코드, 프런트 처리 추가). 대기열 담당 학습 노트는 403을 주장하고, 11/11 답글 초안은 409로 적혀 있어 문서끼리 어긋난다.
4. 1-3의 빈틈(자기 선점에 자기가 막히는 10~15초)을 같이 고칠지: 결제 토큰 만료 시 선점을 바로 푸는 경로.
