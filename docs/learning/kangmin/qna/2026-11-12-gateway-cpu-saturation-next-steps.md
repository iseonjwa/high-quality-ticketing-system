# 동시 수 상한으로도 CPU 포화가 안 풀리면 어떻게 하나, 로드밸런서가 필요한가

## 질문
어제(11/11) Gateway 트러블슈팅은 더 손댈 곳이 없나? 요청이 몰리면 CPU가 99%까지 오르는데 이걸 어떻게 해결하나? 로드밸런서가 필요한가? 동시 처리 수 상한으로도 안 되면 무엇을 해야 하나?

## 짧은 답
- **트러블슈팅은 아직 끝나지 않았다.** 원인과 방향은 찾았고, 남은 것은 운영 반영과 확인 측정이다(1절).
- **과부하에서 CPU 99%는 그 자체로 실패가 아니다.** 들어오는 양이 장비 처리량보다 많으면 어떤 장치를 써도 CPU는 꽉 찬다. 막아야 하는 것은 "CPU 99%"가 아니라 그때 받은 요청이 느려지거나(p95) 죽는 것(OOM)이다. 동시 수 상한은 이 둘을 이미 막았다(6·7차).
- CPU 숫자 자체를 내리는 방법은 세 가지뿐이다. **요청 한 건을 싸게**(공급 쪽 효율), **요청 수를 줄이기**(수요 쪽), **장비를 늘리기**(용량)다.
- (강민 거부, 3-2절 끝) 계산상 효과가 가장 큰 것은 **수요 쪽**이다. G1 부하의 실체는 대기열 폴링이고, 폴링 수는 서버가 정하는 간격(`poll-max` 10초)으로 결정된다. `poll-max`를 30초로 올리면 대기자 30,000명 기준 폴링이 약 2,780 → 1,000/s로 준다(계산값, 3-2절).
- **로드밸런서는 장비가 여러 대일 때만 의미가 있다.** 4 vCPU 한 대 안에서 Gateway를 여러 개 띄우고 앞에 로드밸런서를 두면 CPU를 나눠 쓸 뿐이고, 로드밸런서 자신도 CPU를 쓴다. 장비를 늘리는 것(scale-out)은 정답이지만 이 프로젝트는 한 대가 전제라(ADR 0047) 발표에서 "확장 방향"으로 숫자와 함께 말하는 것이 맞다.

## 1. 트러블슈팅에서 남은 것
| 남은 일 | 왜 필요한가 | 상태 |
|---|---|---|
| 요청 로그 B안 운영 반영 | 7차 H2는 측정 덮어쓰기였다. 운영에는 아직 요청마다 한 줄이 나간다 | 설계 끝(상황판 D7), 구현 전 |
| R0 거절 비용 직접 측정 | H1이 거절을 얼마나 싸게 만들었는지 포화 단계 지표로는 못 가렸다 | 절차 준비 끝(D9), 11/13 |
| 상한 64·96·128 각 2회 | 기본값 64를 반복 측정으로 확정한다 | 11/13 |
| CPU 목표 다시 정하기 | "CPU 90% 미만"을 과부하에도 요구하면 어떤 장치로도 못 지킨다(2절) | 열린 결정 |
| 수요 쪽 줄이기(3-2절) | 아직 손대지 않은 가장 큰 수단 | 이 노트에서 처음 제안 |

서사 문서(`gateway-overload-troubleshooting-story.md`)에는 단계 9로 "요청 로그 운영 반영"과 11/13 결과가 붙을 자리가 있다.

## 2. 왜 상한으로는 CPU가 안 내려가나: 작업 보존형
- 동시 수 상한은 처리 중 요청이 64개를 넘으면 새 요청을 바로 거절한다. 처리 중 요청이 끝나면 그 자리는 바로 다음 요청이 채운다. 이렇게 남는 자원을 놀리지 않는 방식을 **작업 보존형(work-conserving)** 이라고 한다.
- 그래서 들어오는 양이 처리량보다 많으면 자리는 늘 차 있고, CPU도 늘 차 있다. 상한이 바꾸는 것은 CPU가 아니라 **줄의 길이**다. 줄이 짧으니 받은 요청은 빨리 끝나고(p95 435 → 87ms), 메모리도 묶인다(OOM 3 → 0).
- 거절을 싸게 만들어도(H1) 남은 CPU는 다시 받은 요청에 쓰인다. 7차 H1에서 서버 CPU는 그대로였고 굿풋만 올랐다(1,608 → 1,814/s).
- 비유: 계산대가 4개인 가게에 손님이 계속 몰리면 계산대 4개는 늘 바쁘다. 줄을 세우는 규칙(상한)은 줄이 가게 밖까지 늘어지지 않게 할 뿐, 계산원을 쉬게 하지는 못한다. 계산원이 쉬려면 손님이 덜 오거나(수요), 계산이 빨라지거나(효율), 계산대가 늘어야(용량) 한다.

그래서 목표는 이렇게 나누는 것이 맞다(열린 결정 1의 안).

| 구간 | 목표 | 이유 |
|---|---|---|
| 평상 부하(1,500/s 이하) | 서버 CPU 90% 미만 | 여유가 있어야 순간 몰림을 흡수한다 |
| 과부하(2,000/s 이상) | p95 200ms 안, OOM 0, 굿풋 유지, 넘친 요청은 빠른 503 | CPU 99%는 피할 수 없다. 받은 요청을 지키는 것이 목표다 |

## 3. CPU 숫자를 내리는 세 방향
### 3-1. 요청 한 건을 싸게 (공급 쪽 효율)
5차 JFR과 7차 결과에서 나온 후보다.

| 후보 | 근거 | 기대 | 대가 |
|---|---|---|---|
| 요청 로그 B안 | 7차 H2: 1,500/s 서버 CPU 93 → 85% | 운영 반영하면 비슷한 감소(실패·느린 줄만 남으므로 조금 덜, 추정) | 정상 요청 로그를 Loki에서 못 본다(트레이스·지표로 본다) |
| 관측(추적·지표) 줄이기 | 0b JFR 관측 묶음 Gateway Java CPU 약 24% | 운영 샘플링 1.0을 낮추면 일부 | 장애 분석이 약해진다. 11/11 보류 |
| JWT 검증 캐시 | JFR 6.6% | 작음 | 토큰 무효화 반영이 늦어질 수 있다 |
| 블랙리스트 확인 메모리 캐시(G-2) | Redis·차단기 2.5%, Lettuce 스레드 39%(2,000/s) | Redis 호출 자체가 줄어 차단기 문제도 줄어든다 | 로그아웃 반영 지연, ADR 0005와 팀 합의 필요 |

한계: 효율 개선은 처리량 상한을 몇십 % 올릴 뿐, 들어오는 양이 그보다 크면 다시 99%가 된다.

### 3-2. 요청 수를 줄이기 (수요 쪽) — 계산상 가장 크지만 강민이 거부함
- G1은 `GET /api/v1/schedules/{id}/queue/me`, 즉 대기자가 순번을 묻는 폴링이다. 실제 오픈에서 Gateway 요청의 대부분이 이것이다(Q2 "요청 수 1위 구간").
- 다음 폴링 간격은 서버가 정한다. `PollPolicy.nextPollAfterMillis`(`reservation-service/.../queue/application/PollPolicy.java:17`)가 예상 대기 시간을 3초~10초(`config-repo/reservation-service.yml` `poll-min`·`poll-max`)로 자르고 지터 0~20%를 더한다.
- 그래서 폴링 수 ≈ 대기자 수 ÷ 평균 간격이다. 맨 뒤 대기자도 예상 대기가 10분이든 1시간이든 10초마다 묻는다. 대기자 30,000명이면 약 2,700/s다(Q2 계산값). 이것이 G1 부하의 원천이다.
- 방법: 멀리 있는 대기자는 드물게 묻게 한다. 예를 들어 `poll-max`를 30초로 올리면, 입장 속도 50명/초에서 예상 대기 30초 이상(순번 1,500 이후)인 대기자는 약 33초마다 묻는다.

계산(대기자 30,000명, 입장 50명/초, 지터 평균 10% 포함, 모두 계산값):
| `poll-max` | 앞쪽(간격이 상한보다 짧은 대기자) | 뒤쪽(상한 간격으로 묻는 대기자) | 합계 | 지금 대비 |
|---|---|---|---|---|
| 10초(지금) | 순번 500 안, 약 95/s | 29,500 ÷ 11초 ≈ 2,680/s | 약 2,780/s(Q2 계산값 약 2,700과 맞음) | — |
| 30초 | 순번 1,500 안, 약 145/s | 28,500 ÷ 33초 ≈ 860/s | 약 1,000/s | 약 −63% |
| 60초 | 순번 3,000 안, 약 175/s | 27,000 ÷ 66초 ≈ 410/s | 약 590/s | 약 −79% |

앞쪽은 간격이 예상 대기 시간과 같아(순번 ÷ 50초, 최소 3초) 순번별 폴링률 50 ÷ (1.1 × 순번)을 더한 값이다. 지터는 평균 10%로 넣었다.

- 이렇게 되면 4차에서 장비가 멈춘 2,300/s 근처에 가지 않는다. 같은 장비에서 대기자를 2~3배 더 받을 수 있다(계산값, 재지 않음).
- 대가와 확인할 질문:
  - 화면의 순번 갱신이 느려진다. 멀리 있는 대기자에게는 큰 문제가 아니지만, 화면은 예상 대기 시간으로 순번이 줄어드는 것처럼 보여 줄 수 있다(프런트 작업).
  - 입장 직전에 간격이 길면 입장 알림이 늦어진다. 지금 식은 예상 대기가 짧을수록 간격이 짧아지므로 앞쪽은 3~10초가 유지된다. 입장 토큰 유효 시간과 맞는지는 확인 못 함이다.
  - 대기열은 영은님 담당이다. `poll-max`는 공유 설정이라 contract 이슈로 제안하고 Q2-2(이미 계획된 "폴링 상한 늘리기" 변형)로 재야 한다.
- 이 방법이 상한·효율보다 나은 이유: 요청을 받은 뒤 거절하는 비용(H1에서 본 것)도, 받은 요청의 비용도 아예 생기지 않는다. 가장 싼 요청은 오지 않은 요청이다.

### 3-3. 장비를 늘리기 (용량) — 로드밸런서는 여기서 나온다
| 구성 | 효과 | 이 프로젝트에서 |
|---|---|---|
| 한 대 안에 Gateway 여러 개 + 로드밸런서 | 없음에 가깝다. CPU 4개를 나눠 쓸 뿐이고 로드밸런서도 CPU를 쓴다. Gateway(Netty)는 이미 이벤트 루프 4개로 코어를 다 쓴다 | 하지 않는다 |
| Gateway를 다른 EC2로 분리 | Gateway가 쓰던 약 2코어(180%)가 본 서버에 돌아온다 | ADR 0047의 장비 분리와 같은 축. 비용·일정 판단 |
| Gateway 여러 대 + ALB(AWS 로드밸런서) | 대수만큼 처리량이 는다. 한 대가 죽어도 남는다 | 운영이라면 정답. 이 프로젝트는 발표 범위 밖 |
| ALB·CloudFront·WAF 요청률 제한 | 넘친 요청을 우리 장비에 닿기 전에 거절한다. 거절 비용이 0이 된다 | 운영 확장 방향으로 언급 |

규모 감각(계산값): 장비 전체로 요청 한 건에 약 1.7~2.0ms를 쓴다(4차·5차). 4 vCPU면 약 2,000~2,350/s가 한도다. 목표 3,000/s는 약 5~6코어가 필요하다. 그래서 같은 코드로는 장비 한 대에서 못 낸다. 요청 로그 B안으로 한 건 비용이 10% 남짓 줄면 한도는 약 2,300~2,600/s가 된다(계산값, 확인 못 함). 수요 쪽을 줄이면 3,000/s 자체가 필요 없어진다.

## 4. 추천 순서
1. **요청 로그 B안 운영 반영**(진행 중, D7). 근거가 이미 측정으로 있다.
2. ~~폴링 간격 정책을 대기열 담당과 논의~~ 강민 거부(3-2절 끝). 간격은 두고 폴링 한 건을 싸게 하는 쪽만 본다.
3. **CPU 목표를 평상·과부하로 나눠 확정**(2절 표). 발표에서 "CPU 99%를 왜 못 막았나"에 대한 답이 된다.
4. **장비 분리·로드밸런서는 발표의 확장 방향**으로 숫자와 함께 말한다(3-3절 규모 감각).

고른 이유: 효율 개선은 상한을 조금 올리고, 장비는 비용이 든다. 수요 쪽은 코드 한 줄 설정으로 요청 수를 절반 넘게 줄일 수 있다(계산값). 다만 대기열 담당의 설계 영역이고 사용자 경험 대가가 있어 측정과 합의가 먼저다.

감수할 점: 폴링 간격은 이 노트에서 계산만 했다. 실제 효과와 입장 지연은 Q2-2 측정 전까지 확인 못 함이다.

## 판단: 폴링 간격 늘리기는 거부 (2026-11-12)
- 강민 판단: "대기열 폴링 지금 10초도 느린데, 이걸 30초로 늘리는것은 말이 안된다". 순번 갱신 간격은 사용자 경험의 핵심이라, 서버 부하를 줄이려고 늘리면 문제를 사용자에게 넘기게 된다. [판단 기록](../../../ai-judgments/kangmin/2026-11-12-reject-poll-max-30s.md)
- 그래서 3-2절의 표는 "얼마나 줄일 수 있나"의 계산으로만 남긴다. 수요 쪽에서 간격을 건드리지 않는 방향은 다음이다(모두 검토 전).
  - 폴링 한 건을 싸게: 순번 조회 경로의 요청 로그·관측 비용 줄이기(요청 로그 B안이 이미 이쪽), 순번 응답을 짧게 캐시해 Redis 조회 줄이기.
  - 변할 때만 알리기(SSE·WebSocket 밀어주기): 폴링 수는 사라지지만 연결 수만큼 메모리가 들고 Gateway 구조가 바뀐다. Q2-4가 "비교 기록만"으로 둔 방향이라 이번 범위 밖이다.
- 남는 현실적인 길은 효율(3-1)과 장비 분리(3-3)다.
