# 긴 에이전트 세션의 할루시네이션을 막으려면 인수인계 없이 한 세션으로 이어가는 게 나은가

## 질문
AI 에이전트가 오래 이어진 세션에서 사실과 다른 말(할루시네이션)을 하는 것을 막으려면, 인수인계를 하지 않고 한 세션으로 계속 진행하는 편이 나은가.

## 짧은 답
- 아니다. 인수인계를 없애면 문제가 줄지 않고 오히려 커진다. 오래된 세션이 틀리는 주된 이유는 맥락이 너무 길어지는 것이고, 인수인계는 그 맥락을 끊어 주는 수단이다.
- 다만 인수인계 문서 자체가 틀린 말을 옮기는 통로가 될 수 있다. 그래서 문서는 짧게 "사실 + 확인 방법"만 남기고, 새 세션은 문서를 믿지 않고 git·gh·Linear로 다시 확인한다.
- 아래 원리는 일반적으로 알려진 에이전트 동작에서 정리한 것이다. 이 프로젝트에서 세션 길이별 오류율을 잰 적은 없다.

## 자세히

### 1. 긴 세션이 틀리는 이유
| 원인 | 일어나는 일 |
|---|---|
| 맥락 창(context window) 한도 | 대화가 길어지면 앞부분을 요약(compaction)해서 넣는다. 요약은 손실 압축이라 숫자·파일 이름·"확인 못 함" 같은 단서가 빠지거나 뭉개진다 |
| 오래된 사실과 새 사실의 공존 | 같은 대화 안에 "보류"와 "머지됨", "17"과 "30"이 함께 남는다. 어느 쪽이 지금 사실인지 헷갈린다(예: 11/12 하루에만 main 반영 보류 → 반영 → 문제 → 재반영) |
| 바깥 세상의 변화 | 팀원이 PR을 머지하고 IntelliJ로 커밋해도 세션 안 기억은 그대로다. 세션이 길수록 기억과 실제가 멀어진다 |
| 주의 분산 | 할 일이 수십 개 쌓이면 앞서 한 약속(예: #483 리뷰의 `serverTime` 약속)을 놓치기 쉽다 |

### 2. 선택지 비교
| 안 | 방법 | 장점 | 단점 |
|---|---|---|---|
| A. 한 세션으로 계속 | 인수인계 없이 이어감 | 문서 쓰는 비용이 없다 | 1절의 문제가 모두 커진다. 요약이 반복될수록 초기 사실이 흐려진다 |
| B. 새 세션 + 긴 서술형 인수인계 | 지금 `handoff.md`처럼 절을 계속 쌓음(430줄, 0-1~0-9절) | 기록이 남는다 | 낡은 절의 "이 절이 우선", "보류" 같은 문장이 그대로 남아 새 세션이 낡은 사실을 믿을 수 있다 |
| C. 새 세션 + 짧은 상태 인수인계 + 재확인 (추천) | 최신 상태만 한 쪽으로, 각 사실에 확인 시각과 확인 방법(`git log`, `gh pr view`, Linear 이슈)을 붙임. 새 세션은 시작하자마자 그 방법으로 다시 확인 | 문서가 틀려도 재확인에서 걸린다. 맥락이 짧아 주의가 흩어지지 않는다 | 세션 시작마다 조회 비용이 든다 |

### 3. 고른 이유와 감수한 점
- **고른 이유**: 할루시네이션을 줄이는 핵심은 "기억에 기대지 않고 원본을 다시 보는 것"이다. C는 인수인계를 기억이 아니라 "어디를 다시 볼지 알려 주는 색인"으로 쓴다. 이 저장소의 `CLAUDE.local.md`가 이미 "handoff를 읽고 git status·log로 새로 확인한다"를 규칙으로 두고 있어 방향이 같다.
- **감수한 점**: 세션 시작 때 조회가 몇 번 늘어난다. 문서를 짧게 유지하는 수고가 든다.
- **바꿀 조건**: 한 작업이 반나절 안에 끝나고 바깥 변화가 없으면 인수인계 없이 한 세션으로 끝내도 된다. 할루시네이션 위험은 세션의 길이와 바깥 변화의 양에 비례한다.

### 4. 실천 규칙(제안)
1. 인수인계는 최신 절 하나만 둔다. 이전 절은 날짜 이름의 별도 파일로 옮긴다.
2. 사실마다 "확인: 21:00 KST, `gh pr view 562`"처럼 근거를 붙이고, 확인 못 한 것은 "확인 못 함"으로 적는다.
3. 새 세션은 인수인계의 사실을 "주장"으로 읽고, 다음 행동에 쓰기 전에 원본으로 확인한다.
4. 작업 단위가 끝나면 세션을 바꾼다. 하나의 세션에 서로 다른 작업 여러 개를 쌓지 않는다(메인은 지휘, 작업은 하위 세션).
