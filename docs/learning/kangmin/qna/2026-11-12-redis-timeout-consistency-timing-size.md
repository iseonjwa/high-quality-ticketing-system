# Redis 시한은 한 값으로 맞춰야 하나, 시점마다 달리해야 하나, 지금 값은 너무 큰가

## 질문
Redis 시한이 공통 설정(100ms), Gateway 설정(300ms), 인증 필터(200ms), 코드 기본값(100ms) 등 여러 곳에 흩어져 있다. 기준을 맞춰 일관되게 처리해야 하지 않나. 시점(오픈 피크, 평시, 기동 직후)에 따라 차이를 둬야 하지 않나. Redis 응답이 1~2ms인데 지금 기준이 너무 큰 것 아닌가.

## 짧은 답
- **맞춰야 할 것은 숫자가 아니라 규칙과 정의 위치다.** Lettuce 명령 시한(클라이언트가 포기하는 시간)과 인증 필터 시한(사용자 요청을 끊는 마감)은 뜻이 다른 층이라 값이 달라야 정상이다. 다만 같은 값을 두 곳에서 정하는 것(필터 시한의 코드 기본 100ms와 설정 200ms)과 옛 값을 말하는 주석은 고칠 대상이다.
- **시점에 따라 시한을 바꾸지 않는 것이 낫다.** 시한은 "이 이상은 장애로 본다"는 기준이라 부하에 따라 움직이면 안 된다. 시점에 따라 달라지는 것(부하, 데워지지 않은 상태)은 유입 제어·bulkhead·웜업이 맡는다. 기동 직후만은 이미 따로 다룬다(기동 웜업 2초 시한).
- **Redis 처리 시간에 비하면 크다(약 100배). 하지만 이 시계가 재는 것은 Redis가 아니라 Gateway 대기까지 포함한 왕복 시간이다.** 그 기준으로 100ms는 측정에서 너무 빡빡했고 200ms는 시한 초과 0건이었다. 더 줄일지는 피크 때 왕복 시간의 꼬리(p99.9)를 재 봐야 판단할 수 있다. 이 값은 아직 확인 못 했다.

## 자세히

### 1. 지금 Redis 시한이 정의된 곳
| 사용처 | 층 | 값 | 정의 위치 |
|---|---|---|---|
| 모든 서비스 공통 | Lettuce 명령 시한 / 연결 시한 | 100ms / 1s | `config-repo/application.yml` 51·52행 |
| Gateway | Lettuce 명령 시한 | 300ms | `config-repo/gateway.yml` 53행 |
| Gateway 인증 필터 | 사용자 요청 마감 | 200ms | `config-repo/gateway.yml` 58행 |
| 같은 필터 | 코드 기본값 | 100ms | `GatewayAuthenticationFilter.java` 42행 `@Value("${auth.redis-timeout:100ms}")` |
| Gateway 기동 | 웜업 PING | 2s, 200ms 간격 2회 재시도 | `GatewayConfiguration.java` 19~21행 |
| 예매 서비스 대기열 | Lettuce 명령 시한만 | 100ms(공통) | `RedisQueueRepository` 쪽 별도 마감 없음 |
| 사용자 서비스 세션 | Lettuce 명령 시한만 | 100ms(공통) | `RedisSessionStore` 쪽 별도 마감 없음 |

### 2. 일관성: 선택지 비교
| 안 | 내용 | 장점 | 문제 |
|---|---|---|---|
| A. 모든 곳 같은 값 | 예: 모두 100ms | 외우기 쉽다 | 층이 다른 시계를 같은 값으로 두면 둘이 경쟁해 원인 이름이 섞인다. 3차 R3(필터·Lettuce 둘 다 100ms)에서 Gateway에 `redis_error`가 섞였다(ADR 0050) |
| B. 사용처마다 따로 정함 | 지금에 가까움 | 사용처 사정을 반영 | 규칙이 문서에 흩어지고 같은 값이 두 곳에 생긴다 |
| C. 규칙 하나, 값은 사용처별, 정의 위치는 한 곳 | 추천 | 값이 달라도 왜 다른지 설명된다 | 규칙을 문서·테스트로 묶는 일이 든다 |

C의 규칙 예:
1. Lettuce 명령 시한은 서비스마다 하나, `config-repo`에만 둔다. 공통 100ms에서 출발한다.
2. 사용자 요청을 Redis 때문에 끊어야 하는 곳만 사용처 마감을 따로 둔다(지금은 Gateway 인증 하나).
3. 마감을 두면 `Lettuce 명령 시한 > 사용처 마감 > 느린 호출 판정`을 지키고 테스트로 묶는다. Gateway는 이미 `AuthRedisResilienceContextTest`로 묶여 있다.
4. 코드 기본값은 설정과 같게 두거나 기본값 없이 필수 키로 만들어 "두 곳 정의"를 없앤다.

**지금 고칠 것(코드 변경, 이 노트에서는 하지 않음)**
- `GatewayAuthenticationFilter.java` 42행 기본 100ms ↔ 설정 200ms. 설정이 빠지면 100ms로 돌아가 Lettuce보다 작은 쪽 순서는 유지되지만, 느린 호출 기준 100ms와 같아진다. 39행 주석("운영 설정에는 키를 두지 않고")과 `AuthRedisFailures.java` 51행 "(100ms)"도 옛 내용이다.
- SA 9-4의 "Redis 100ms"는 Gateway 인증만 ADR 0050이 대체했다. 예매·사용자 서비스는 100ms이고 별도 마감·차단기가 없다. 이 사실이 한 문서에 모여 있지 않다.

### 3. 시점에 따라 바꿀까: 선택지 비교
| 안 | 내용 | 결과 |
|---|---|---|
| A. 고정 | 지금 | 장애 판정 기준이 늘 같다 |
| B. 피크에 늘림 | 예: 오픈 때 500ms | Redis가 멈추면 한 호출이 자리를 500ms 붙잡는다. bulkhead 50 기준 통과량이 50 ÷ 0.2 = 250건/s에서 50 ÷ 0.5 = 100건/s로 줄고(리틀의 법칙, 계산값), 사용자는 503을 더 늦게 받는다 |
| C. 피크에 줄임 | 예: 오픈 때 50ms | 피크에는 Gateway가 가장 바쁘다. Gateway 쪽 대기가 곧 실패가 되어 Redis가 멀쩡해도 차단기가 열린다. 시한이 아니라 느린 호출 기준의 예지만, 기준이 50ms였을 때 식은 Gateway 첫 몰림(Redis 0.1~0.8ms)에서 차단기가 열린 것이 같은 모양이다(ADR 0050) |
| D. 최근 지연에 맞춰 자동 조정 | 적응형 시한 | 장애 중에는 지연이 늘어 시한도 따라 늘어나 장애를 늦게 판정한다. 값이 매번 달라 측정·설명이 어렵다 |

**고른 이유(A)**: 시한의 뜻은 "이보다 오래 걸리면 사용자를 더 붙잡지 않는다"이다. 이 기준은 시각이 아니라 사용자 대기 예산(Gateway 3초 중 인증 몫)에서 나온다. 시점에 따라 달라지는 것은 부하인데, 부하는 시한이 아니라 유입 제어(동시 처리 수 상한 64), bulkhead(50, 대기 0), 웜업이 다룬다.

**이미 시점 차이를 둔 곳**: 기동 직후. 첫 연결 수립에 요청 시한을 쓰지 않게 기동 단계에서 2초 시한으로 PING을 먼저 보낸다(`GatewayConfiguration.java`). 부하 측정은 덤 몰림을 넣은 웜업을 표준으로 했다(설계 문서 `gateway-auth-redis-resilience.md`). 시점 문제는 시한을 바꾸지 않고 이 두 장치로 풀었다.

**감수한 점**: 피크 순간 Gateway가 극단적으로 바쁘면 200ms도 넘을 수 있다. 그때는 시한 초과가 Redis 탓으로 세어진다. 그 몫은 동시 처리 수 상한이 Gateway를 덜 바쁘게 만들어 줄인다.

### 4. 지금 값이 너무 큰가
**재는 대상을 먼저 본다.** 필터 시계는 bulkhead를 통과한 순간부터 응답 신호까지다. Redis가 일한 시간(평소 0.3ms, 몰림 중 평균 1.9ms)은 일부이고, 나머지는 Gateway 이벤트 루프 대기·CPU·GC다. "Redis가 1~2ms니까 200ms는 크다"는 비교는 다른 것을 잰 두 숫자를 비교한 것이다.

**크게 두었을 때의 비용은 진짜 Redis 장애 때만 생긴다(계산값).**
| 필터 시한 | 장애 중 bulkhead 통과량 | 차단기 최소 호출 500건을 채우는 시간 | 열리기 전 사용자 대기 |
|---|---|---|---|
| 50ms | 50 ÷ 0.05 = 1,000건/s | 약 0.5초 | 50ms 뒤 503 |
| 200ms(지금) | 50 ÷ 0.2 = 250건/s | 약 2초 | 200ms 뒤 503 |

장애 한 번마다 "느리게 실패하는 구간"이 약 0.5초에서 약 2초로 늘어난다. 그 뒤에는 차단기가 열려 5초 동안 바로 503이다. bulkhead 거절은 차단기 집계에서 빠지므로 통과한 호출만 센다고 보고 계산했다.

**작게 두었을 때의 비용은 평소에 생긴다(측정값).** 100ms에서는 식은 Gateway의 1,000명 단계에서 시한 초과가 실패로 세어졌고(3차 F 식은 1,000명: 최근 20건이 모두 느린 호출, 그중 10건이 실패), 200ms의 G1 재측정 2회에서는 시한 초과가 0건이었다(ADR 0050).

**판단**: 평소 잘못 503을 내는 비용(정상 사용자가 거절됨)이 장애 때 1.5초 더 느리게 실패하는 비용보다 크다고 보고 200ms를 쓴다. "너무 큰가"를 숫자로 답하려면 피크 때 필터가 본 왕복 시간의 p99·p99.9가 필요하다. 이 값은 아직 없다(확인 못 함). p99.9가 수 ms라면 100ms로 내려도 되고, 수십 ms라면 200ms가 맞다.

## 이 프로젝트에서는
- 숫자 출처: `config-repo/application.yml`, `config-repo/gateway.yml`, `docs/decisions/0050-gateway-auth-redis-breaker-bulkhead-split.md`(측정값과 장애 중 통과량 계산)
- 측정을 다시 한다면: G1 피크 단계에서 Lettuce 명령 지연 지표(`lettuce_*`, 수집 여부와 히스토그램 구간은 확인 못 함) 또는 필터 실패 로그의 `elapsedMs`로 꼬리 지연을 본다. 정상 호출 시간은 지금 필터가 따로 기록하지 않는다.
- 예매·사용자 서비스: Redis 100ms만 있고 차단기·마감이 없다. 대기열 진입이 Redis 지연 때 어떻게 실패하는지는 측정하지 않았다. 대기열 담당과 확인할 질문이다.

## 면접 포인트
- **"Redis는 1ms인데 왜 시한이 200ms인가?"** 시한이 재는 것은 Redis 처리 시간이 아니라 호출자 쪽 대기까지 포함한 왕복이다. 100ms에서는 Redis가 멀쩡한데 Gateway 혼잡이 실패로 세어졌다. 크게 둔 비용은 진짜 장애 때 차단기가 열리기 전 약 2초 동안 느리게 실패하는 것이고, 그 비용을 받아들였다.
- **"피크 때 시한을 바꾸면 되지 않나?"** 늘리면 장애 때 자원을 오래 붙잡아 통과량이 줄고, 줄이면 피크의 자기 혼잡이 장애로 판정된다. 시한은 고정하고, 피크는 유입 제어와 웜업으로 다룬다.
- **"설정이 여러 곳에 흩어져 있지 않나?"** 값이 다른 것은 층의 뜻이 달라서이고, 그 순서를 테스트로 묶었다. 고칠 것은 같은 값을 코드와 설정 두 곳에서 정의한 부분이다.
