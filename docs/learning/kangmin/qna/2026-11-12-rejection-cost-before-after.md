# 예전에는 거절 한 건도 받은 요청만큼 비쌌고, H1로 싸게 만든 것이 맞나

## 질문
이전에는 거절 비용이 일반적인 받은 요청처럼 높았는데, 낮은 비용으로 처리할 수 있도록 개선했다는 게 맞나?

## 짧은 답
- **방향은 맞지만, "받은 요청만큼 비쌌다"는 과장이다.**
- H1 전(6차) 거절 한 건은 받은 요청의 **약 5분의 1(약 0.15~0.21ms)** 로 추정된다. 이 값은 포화 구간 자료를 연립해 푼 계산값이라 오차가 크다.
- H1 뒤(8차 R0) 거절 한 건은 받은 요청의 **2~8%(0.02~0.08ms)** 다. 이 값은 포화 전 구간에서 거절을 일부러 만들어 직접 쟀다.
- 그래서 "거절 비용을 받은 요청의 약 5분의 1에서 10분의 1 이하로 줄였다"고 말하는 것이 맞다. 다만 전후 값을 얻은 방법이 다르므로 정확한 감소율(%)은 말하지 않는다.

## 1. 왜 "받은 요청만큼 비싸다"고 생각했었나
- 6차에서 상한 32·64·128·500으로 거절 비율이 25~40%까지 달라졌는데, 한 건당 Gateway CPU(쓴 코어 ÷ 모든 요청)는 0.66~0.71ms로 거의 같았다.
- 그래서 처음에는 "거절도 받은 요청과 거의 같은 비용을 낸다"고 읽었다(TS-59 원인 절).
- 그런데 이 지표는 서버 CPU 98~99%인 포화 구간에서 잰 값이다. 포화 구간에서 한 건당 값은 비용이 아니라 "Gateway가 받은 CPU 몫 ÷ 처리량"이라 거의 상수가 된다. 거절 비용이 달라도 숫자가 같게 나온다.
- 7차 뒤 같은 자료를 받은 요청·거절 두 미지수로 연립해 다시 풀자 거절은 받은 요청의 약 5분의 1로 나왔다([H1 재해석 노트](2026-11-11-h1-reinterpret-netty-cost.md) 2절).

## 2. H1 뒤 값은 어떻게 쟀나 (8차 R0)
- 상한을 1로 두고(거의 모든 요청을 거절) 500·1,000/s의 포화 전 부하를 걸었다. 같은 부하를 상한 1,000(거절 0)으로도 걸었다.
- 두 회차의 Gateway CPU 차이를 거절 수로 나눠 거절 한 건 비용을 풀었다(`loadtest/k6/tools/r0_solve.py`).
- 결과: 받은 요청 a = 1.063 ± 0.013ms, 거절 r = 0.021 ± 0.021ms(pidstat). docker stats로는 r = 0.080 ± 0.017ms. r/a = 0.020~0.075.
- 미리 정한 판정선(r/a 0.1 이하면 가설 맞음)을 오차 위쪽(0.04·0.09)까지 넣어도 지킨다.

## 3. 그런데 서버 CPU는 왜 그대로였나
- 동시 처리 수 상한은 자리가 비면 다음 요청이 바로 채우는 작업 보존형이다. 거절이 싸져 남은 CPU는 받은 요청이 다시 쓴다.
- 그래서 H1의 이득은 서버 CPU가 아니라 **굿풋**으로 나타났다. 2,500/s 굿풋 1,608 → 1,814/s(+12.8%), p95 104 → 78ms(7차 H1, 6차 L64 대비).

## 4. 이력서·발표에서 쓸 때
| 쓸 수 있는 말 | 쓰면 안 되는 말 |
|---|---|
| 거절 한 건 비용을 받은 요청의 약 1/5(추정)에서 2~8%(측정)로 낮췄다 | 거절 비용을 90% 줄였다(전후 측정 방법이 달라 정확한 비율이 아니다) |
| 같은 CPU로 2,500/s 굿풋을 12.8% 더 냈다 | 거절을 앞당겨 서버 CPU를 낮췄다(낮아지지 않았다) |
| 포화 구간의 한 건당 CPU가 비용을 가리지 못한다는 것을 알고, 포화 전 측정(R0)을 따로 설계했다 | 처음부터 거절 비용을 정확히 알고 있었다 |
