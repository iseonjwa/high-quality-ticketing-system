# 동기·비동기와 블로킹·논블로킹 네 조합은 우리 서비스 어디에 있나

## 질문
블로킹·논블로킹과 동기·비동기를 함께 생각하면 헷갈린다. 동기 블로킹, 동기 논블로킹, 비동기 블로킹, 비동기 논블로킹 네 경우가 우리 서비스에서는 각각 어디에 있나.

## 짧은 답
- 두 축은 묻는 것이 다르다. **블로킹·논블로킹**은 "호출한 스레드가 결과가 나올 때까지 멈춰 있나"(제어권을 바로 돌려받나)이고, **동기·비동기**는 "작업이 끝났는지를 누가 챙기나"(호출자가 직접 확인하나, 끝나면 콜백·이벤트로 알려 오나)다.
- 네 조합 모두 이 저장소에 있다. 동기 블로킹은 좌석 선점의 행 잠금 대기, 동기 논블로킹은 대기열 순번 폴링과 `pg_try_advisory_xact_lock`, 비동기 블로킹은 outbox 릴레이의 `send()` 후 `future.get()`, 비동기 논블로킹은 Gateway 인증 필터의 Reactive Redis 조회다.
- 같은 흐름도 어느 경계에서 보느냐에 따라 칸이 바뀐다. 접수형 좌석 선점은 서버 안에서는 비동기(Kafka 소비자가 나중에 처리)지만, 클라이언트는 결과를 폴링으로 직접 확인하므로 클라이언트 쪽에서는 동기 논블로킹이다.

## 자세히

### 두 축 나누기
| 축 | 질문 | 갈리는 지점 |
|---|---|---|
| 블로킹 / 논블로킹 | 호출한 스레드가 기다리며 멈추나 | 호출이 바로 돌아오나(논블로킹), 결과가 나와야 돌아오나(블로킹) |
| 동기 / 비동기 | 완료를 누가 챙기나 | 호출자가 결과를 받아 다음 줄에서 직접 처리(동기), 완료되면 콜백·Future·이벤트가 알려 줌(비동기) |

식당 비유로 쓰면 이렇다.
- 동기 블로킹: 카운터 앞에서 음식이 나올 때까지 서서 기다린다.
- 동기 논블로킹: 자리로 갔다가 몇 분마다 카운터에 "나왔어요?" 하고 직접 물어본다.
- 비동기 블로킹: 진동벨을 받았지만(완료 알림 수단이 있음) 벨만 쳐다보며 아무것도 안 하고 서 있다.
- 비동기 논블로킹: 진동벨을 받고 다른 일을 하다가 벨이 울리면 받으러 간다.

### 1. 동기 블로킹: 좌석 선점의 행 잠금 대기
- 위치: `reservation-service/.../seathold/application/SyncSeatHoldService.java:52` (`LOCK_TIMEOUT = 500ms`)
- 동작: 좌석 행을 `FOR UPDATE`로 잠근다. 다른 트랜잭션이 같은 좌석을 잡고 있으면 요청 스레드는 잠금이 풀릴 때까지 멈춰 기다린다(블로킹). 결과(선점 성공·실패)는 그 스레드가 받아 바로 응답을 만든다(동기).
- 왜 이 선택인가: 코드가 위에서 아래로 읽히고 트랜잭션 하나로 묶기 쉽다. Spring MVC + JDBC의 기본 모델이다.
- 감수한 점: 기다리는 동안 스레드와 DB 커넥션을 쥔다. 핫 좌석에서 대기가 길어지면 커넥션 풀이 마른다. 그래서 `lock_timeout` 500ms로 대기 상한을 두었다(SA 9-4).
- 같은 칸의 다른 예: 결제 서비스 대사(reconciliation)가 예매 서비스를 부르는 `RestClient` 호출(`ReservationLookupHttpClient`).

### 2. 동기 논블로킹: 대기열 순번 폴링, try-lock
- 위치 ①: `frontend/src/api/queue.ts:13-17`. 클라이언트가 순번을 물으면 서버는 기다리지 않고 바로 `WAITING`(순번·다음 조회 간격) 또는 `READY`를 돌려준다(논블로킹). 차례가 됐는지는 클라이언트가 `nextPollAfterMillis`마다 다시 물어 직접 확인한다(동기).
- 위치 ②: `payment-service/.../reconciliation/infrastructure/JdbcMismatchRepository.java:30`의 `pg_try_advisory_xact_lock`. 잠금을 못 잡으면 기다리지 않고 즉시 `false`가 오고, 호출자 `ReconciliationRecorder`가 그 값을 보고 "다른 인스턴스가 돌고 있으니 건너뛴다"를 직접 판단한다. 스케줄러·워커의 `FOR UPDATE SKIP LOCKED`도 잠긴 행을 기다리지 않고 건너뛴다는 점에서 같은 성격이다.
- 왜 이 선택인가: 대기열은 서버가 수만 명의 연결을 붙잡고 있지 않게 하려는 것이고, try-lock은 중복 실행을 막되 기다리느라 스레드를 묶지 않으려는 것이다.
- 감수한 점: 폴링은 "아직이에요" 응답도 요청 한 건이라 부하가 된다. 서버가 jitter를 섞은 조회 간격을 내려 주는 이유다.
- 주의: ②의 JDBC 호출 자체는 DB 응답을 기다리는 블로킹 I/O다. 여기서 논블로킹이라는 말은 "잠금 대기"에 대한 것이다. 블로킹·논블로킹은 항상 "무엇을 기다리는가"를 붙여서 말해야 정확하다.

### 3. 비동기 블로킹: outbox 릴레이의 send 후 get
- 위치: `common/.../messaging/outbox/OutboxRelay.java:84`(보내기), `:112`(기다리기), `KafkaOutboxEventSender.java:25`
- 동작: `kafka.send()`는 브로커 확인을 기다리지 않고 `CompletableFuture`를 바로 돌려준다(비동기). 그런데 릴레이는 그 Future에 `get(남은 시간)`을 불러 브로커 확인(acks=all)이 올 때까지 스레드를 멈춘다(블로킹).
- 왜 일부러 이렇게 했나: 확인을 받은 행만 `SENT`로 바꿔야 전송 실패를 놓치지 않는다. 다만 한 건 보내고 한 건 기다리면 왕복 시간 × N이 걸리므로, 묶음을 먼저 모두 보내 놓고(비동기 이점) 마지막에 차례로 확인한다(블로킹). 기다리는 스레드는 사용자 요청 스레드가 아니라 스케줄러 스레드라 막혀도 사용자 응답에 영향이 없다.
- 감수한 점: 릴레이 스레드 하나가 마감 시각까지 묶인다. 그래서 `sendTimeout` 마감을 둔다. 또 `send()` 자체도 메타데이터를 기다리며 `max.block.ms`만큼 막힐 수 있어(코드 주석 `KafkaOutboxEventSender.java:20-21`) "비동기 API라서 절대 안 막힌다"는 가정은 틀리다.
- 일반론: 비동기 API를 부르고 바로 `get()`·`join()`·`block()`으로 기다리면 비동기의 이점이 사라져 안티패턴으로 불린다. 여기서는 "여러 건을 동시에 띄워 놓고 한꺼번에 기다린다"는 이유가 있어서 쓴다. 같은 칸의 단순한 예는 `reservation-service/.../LocalMessagingProbe.java:44`의 `send(...).get(5, SECONDS)`다.

### 4. 비동기 논블로킹: Gateway 인증 필터
- 위치: `gateway/.../security/GatewayAuthenticationFilter.java:87-93, 98`
- 동작: 블랙리스트 확인 `redis.hasKey(...)`는 Reactive Redis라 `Mono<Boolean>`을 바로 돌려준다. 이벤트 루프 스레드는 기다리지 않고 다른 요청을 처리하러 간다(논블로킹). Redis 응답이 오면 `flatMap`에 넘긴 함수가 이어서 실행된다(비동기, 콜백).
- 왜 이 선택인가: Gateway는 모든 요청이 지나는 입구다. 스레드 몇 개(이벤트 루프)로 많은 동시 연결을 받으려면 I/O를 기다리며 스레드를 쥐면 안 된다. Spring Cloud Gateway가 WebFlux(Netty) 위에 있는 이유다.
- 감수한 점: 코드가 `flatMap`·`onErrorResume` 연쇄라 읽기 어렵고, 이벤트 루프에서 블로킹 호출을 하나라도 하면 전체가 멈춘다. 시한도 `timeout(...)` 연산자로 따로 걸어야 한다.
- 시스템 수준의 같은 칸: 예매↔결제 SAGA. 예매 서비스는 결제 요청 이벤트를 outbox로 남기고 요청 스레드를 바로 끝낸다. 결제 결과는 나중에 `PaymentResultListener`(`@KafkaListener`)로 도착해 처리된다.

### 경계에 따라 칸이 바뀌는 예: 접수형 좌석 선점
`AsyncSeatHoldService.accept()`는 좌석을 잠그지 않고 `seat_hold_requests(REQUESTED)`와 outbox 이벤트만 한 트랜잭션에 쓰고 요청 ID를 돌려준다. 실제 선점은 Kafka 소비자가 나중에 한다.

| 보는 경계 | 칸 | 이유 |
|---|---|---|
| 예매 서비스 내부 | 비동기 논블로킹 | 접수 스레드는 선점 완료를 기다리지 않고, 완료는 소비자가 처리한다 |
| 클라이언트 ↔ 서버 | 동기 논블로킹 | 접수 응답은 바로 오고, 선점 결과는 클라이언트가 폴링으로 직접 확인한다 |
| 접수 API 한 번의 HTTP 호출 | 동기 블로킹 | 접수 트랜잭션이 끝나야 응답이 온다(짧을 뿐 기다리긴 한다) |

동기형 선점(1번)과 비교하면, 접수형은 사용자 요청 스레드가 핫 좌석 잠금을 기다리지 않게 만든 대신 "결과를 나중에 확인해야 하는" 흐름과 소비자·폴링이라는 부품을 더 얻었다.

### 정리 표
| 조합 | 이 저장소 예 | 스레드 | 완료 확인 |
|---|---|---|---|
| 동기 블로킹 | 좌석 행 `FOR UPDATE` 대기, `RestClient` 호출 | 기다리며 멈춤 | 호출자가 바로 받음 |
| 동기 논블로킹 | 대기열 순번 폴링, `pg_try_advisory_xact_lock`, `SKIP LOCKED` | 바로 돌아옴 | 호출자가 다시 물어 확인 |
| 비동기 블로킹 | outbox 릴레이 `send()` 뒤 `future.get()` | 결국 `get()`에서 멈춤 | Future가 알려 주지만 기다리며 받음 |
| 비동기 논블로킹 | Gateway Reactive Redis `Mono` + `flatMap`, Kafka SAGA | 바로 돌아옴 | 콜백·이벤트로 알려 옴 |

## 면접 포인트
- "동기와 블로킹은 같은 말인가?" 아니다. 블로킹은 스레드가 멈추는가, 동기는 완료를 호출자가 직접 챙기는가다. 그래서 네 조합이 나온다.
- "비동기 블로킹은 왜 생기나, 언제 써도 되나?" 비동기 API를 부르고 바로 `get()`하면 생긴다. 보통은 이점이 없지만, 여러 작업을 먼저 띄워 놓고 한꺼번에 기다리면 총 대기가 줄어든다. outbox 릴레이가 그 예이고, 기다리는 스레드가 사용자 요청 스레드가 아니라는 점도 함께 말한다.
- "WebFlux를 쓰면 무조건 빨라지나?" 아니다. 스레드를 적게 쓰며 많은 동시 연결을 받는 것이 이점이고, 한 요청의 처리 시간이 줄지는 않는다. 이벤트 루프에서 블로킹 호출을 섞으면 오히려 전체가 멈춘다.
- "논블로킹이라고 말할 때 무엇을 조심하나?" 무엇을 기다리지 않는지 대상을 밝힌다. try-lock은 잠금 대기에 대해 논블로킹이지만 JDBC 호출 자체는 블로킹 I/O다.
