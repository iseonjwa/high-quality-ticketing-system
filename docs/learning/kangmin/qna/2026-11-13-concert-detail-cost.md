# 공연 상세 조회 한 건은 왜 CPU 약 3ms를 쓰고, 어떻게 줄이나

## 질문
11/13 O1(오픈 피크 한 흐름) 배포 측정에서 오픈 전 120초 동안 요청은 공연 상세(`GET /api/v1/concerts/{id}`) 초당 약 660건뿐이었는데 서버 4 vCPU 중 2.7~2.9코어를 썼다. 한 건당 CPU(계산값)는 Gateway 1.0~1.2ms, 예매 서비스 1.1~1.4ms, 예매 DB 0.68~0.71ms로 합쳐 약 3ms다. 왜 이렇게 크고, 무엇으로 줄이나.

## 짧은 답
- **한 가지 큰 원인은 없다.** 세 컨테이너가 비슷하게 나눠 쓰고, 그중 회차 수에 비례하는 몫이 있다. 시연 공연(공연 1)은 측정 때마다 회차가 늘어 지금 **91개**(77개는 끝난 회차)이고 응답이 **13,497바이트**다. 회차 1개짜리 공연은 433바이트다.
- **DB 쿼리 자체는 싸다.** 두 쿼리의 실행 시간은 합쳐 약 0.2ms(EXPLAIN ANALYZE)다. 그런데 DB 컨테이너는 한 건에 0.7ms를 쓴다. 차이는 쿼리 실행 밖(연결 프로토콜, 트랜잭션 시작·커밋, 91행 결과 전송)으로 보인다(추정).
- **Gateway는 공개 경로라 인증(JWT·Redis)을 건너뛴다.** 그래도 한 건에 약 1ms다. 다른 요청(작은 응답)에서도 Gateway 한 건 비용이 0.7~1.3ms였으므로 대부분 "요청 한 건을 중계하는 고정 비용"으로 읽는다(추정).
- **추천: 예매 서비스 안에 공연 상세 원자료(공연 + 회차 목록) 로컬 캐시를 두고, `serverTime`과 판매 상태는 요청마다 계산한다.** DB 몫(약 0.7ms, 전체의 약 23%)과 Hibernate 몫을 없애고, 오픈 순간 판매 상태가 늦게 바뀌는 문제를 만들지 않는다. 그 전에 회차 수 몫을 B1-d로 먼저 잰다(6절).

## 1. 요청 한 건의 흐름 (dev 코드 기준)

| 단계 | 하는 일 | 회차 수에 비례? |
|---|---|---|
| Gateway | `AccessPolicy.PUBLIC_GET`(`/api/v1/concerts/*`)에 걸려 JWT 검증과 Redis 블랙리스트 조회를 건너뛴다. `EntryTokenFilter`는 헤더만 정리한다. 요청 로그는 `problems` 모드라 정상 요청은 남기지 않는다. 그다음 라우팅 → LoadBalancer(Eureka 목록) → 예매 서비스로 HTTP 중계. `observability`·`metrics`가 켜져 있다 | 응답 본문 중계만(13.5KB) |
| 예매 서비스 필터 | `GatewayIdentityFilter`, `RequestLogFilter`(요청마다 INFO 한 줄, 약 220바이트), 관측(지표·추적, 측정 때 샘플링 0.01) | 아니다 |
| `ConcertQueryService.getConcert` | `@Transactional(readOnly = true)` 안에서 쿼리 2번: ① `concertRepository.findById` ② `findByConcertIdWithVenue`(회차 + 공연장 join fetch, 시작 시각 정렬) | ②의 행 수 |
| DTO 변환 | 회차마다 `ScheduleSummaryResponse.of`가 판매 상태를 `serverTime` 기준으로 계산 | 그렇다 |
| JSON 직렬화 | 공연 3필드 + `serverTime` + 회차마다 6필드(시각 두 개는 ISO 문자열) | 그렇다 |

- **캐시는 없다.** ISE-204 좌석 배치 캐시(`ScheduleSeatLayoutCache`)는 좌석 조회용이고 공연 상세에는 없다. 요청마다 DB를 2번 부른다.
- **N+1은 없다.** 공연장은 join fetch로 같이 읽고, `concert`는 LAZY인데 DTO가 회차의 공연을 건드리지 않는다. EXPLAIN에서도 공연장은 Memoize로 91번 중 1번만 실제 조회했다.
- 끝난 회차(CLOSED)도 모두 내려준다. 화면(`ConcertDetailPage.tsx`)은 CLOSED 회차를 "마감"으로 그린다.
- `open-in-view: false`라 트랜잭션은 서비스 메서드 안에서 끝난다.

## 2. 서버에서 확인한 것 (11/13 21:45~21:50 KST, 측정 모드 꺼짐, 조회만)

| 항목 | 값 |
|---|---|
| 공연 1 회차 | 91개(CLOSED 77, ON_SALE 14). 다른 공연은 1~3개 |
| 응답 크기 | 공연 1: 13,497바이트, 공연 16(1회차): 433바이트. gzip 없음, `Cache-Control`·`ETag` 없음 |
| 응답 시간(한가한 서버, 순차 15회 중앙값) | 예매 서비스 직접: 91회차 4.3ms, 1회차 2.9ms / Gateway 경유: 91회차 14.9ms, 1회차 10.2ms |
| 쿼리 ① 공연 | Index Scan, 실행 0.033ms |
| 쿼리 ② 회차 + 공연장 | Seq Scan(119행 중 91행) → Memoize → 정렬, 실행 0.16~0.18ms, 계획 0.11~0.46ms. 전부 메모리 적중 |

- 원자료: `docs/context/concert-detail-cost-2026-11-13.md`(git 제외).

## 3. 원인 판정: 3ms를 나누면

오픈 전 구간의 서버 바쁜 코어 2.7~2.9 중 공연 상세를 처리한 세 컨테이너(Gateway + 예매 서비스 + 예매 DB)의 합은 **1.85~2.10코어**다(계산값, 11/13 측정 11-1절 다섯 회차). 나머지 약 0.8코어는 부하와 거의 무관한 Kafka(0.23~0.30), 관측 도구(0.15~0.17), 컨테이너 밖(0.27~0.36)이다. 즉 "공연 상세만으로 거의 3코어"는 실제로는 **공연 상세 약 2코어 + 바탕 소비 약 0.8코어**다.

| 몫 | 한 건 CPU(계산값) | 무엇이 쓰나 | 판정 근거 | 확신 |
|---|---|---|---|---|
| Gateway | 1.0~1.2ms | 공개 경로라 인증 없음. 중계(Netty 수신 → 라우팅 → LoadBalancer → HTTP 클라이언트 → 응답 13.5KB 전달), 관측·지표 | 혼합 구간의 다른 요청(응답이 작은 순번 조회 등)도 Gateway 한 건이 0.7~1.3ms였다. 본문 크기보다 요청 수에 비례하는 고정 비용으로 읽는다 | 추정. 필터별·단계별 분해는 확인 못 함 |
| 예매 서비스 | 1.1~1.4ms | Tomcat·Spring MVC·필터, 트랜잭션, JDBC 2회, Hibernate가 91행을 엔티티로 만듦, DTO 91개, JSON 13.5KB, 요청 로그 한 줄 | 회차 91개가 1개보다 응답이 1.4ms 늦다(한가할 때). 회차 수 몫이 있다. 크기는 확인 못 함 | 추정 |
| 예매 DB | 0.68~0.71ms | 쿼리 실행은 약 0.2ms. 나머지는 프로토콜(BEGIN READ ONLY·쿼리 2개·COMMIT), 91행 결과를 문자열로 만들어 보내기, 계획 세우기(서버 준비문이 안 된 경우) | EXPLAIN 실행 시간 합 0.2ms와 컨테이너 CPU 0.7ms의 차이 | 차이가 있다는 것은 확인. 무엇이 얼마인지는 확인 못 함(pg_stat_statements 없음) |
| 요청 로그(JVM 밖 포함) | 서버 전체에서 약 0.2ms로 추정 | 예매 서비스 `RequestLogFilter`가 정상 요청도 매번 남긴다 → 표준 출력 → Docker → Alloy → Loki | Gateway에서 요청 로그를 끄자 1,500/s에서 서버 CPU가 93% → 85%(0.32코어 ÷ 1,500 = 0.21ms/건, 계산값). 같은 크기라면 660/s에서 약 0.14코어 | 추정(다른 서비스의 측정을 옮긴 값) |

정리
- **DB는 쿼리 계획 문제가 아니다.** 인덱스·통계·N+1 모두 문제없고, 실행은 0.2ms다. DB 비용의 대부분은 "요청마다 DB에 간다"는 사실 자체(왕복과 결과 전송)다.
- **예매 서비스와 DB의 일부는 회차 91개 때문이다.** 회차는 시연 시드(`seed-demo.sh open`)가 측정마다 더한 것이라 실제 공연(회차 몇 개)보다 응답이 약 30배 크다. 그리고 측정할 때마다 늘어나 **날짜가 다른 O1 결과끼리 오픈 전 비용이 같은 조건이 아니다.**
- **Gateway 몫은 요청 수에 비례한다.** 공연 상세를 싸게 만들어도 Gateway 1ms는 남는다. 이것을 줄이려면 요청이 Gateway까지 오지 않게 하거나(HTTP 캐시), Gateway 자체를 가볍게 해야 한다.

## 4. 줄일 방법 비교

효과는 모두 추정이다. "한 건"은 공연 상세 한 건, 기준은 약 3ms.

| 방법 | 줄어드는 몫(추정) | 대가 | 담당(코드 이력) |
|---|---|---|---|
| A. 예매 서비스 로컬 캐시: 공연 + 회차 목록을 불변 객체로 캐시, `serverTime`·판매 상태는 요청마다 계산. TTL 수 초 + 관리자 공연·회차 생성·삭제 때 비움 | DB 0.7ms → 거의 0, 예매 서비스의 트랜잭션·JDBC·Hibernate 몫. **합쳐 약 0.9~1.2ms(30~40%)** | 인스턴스가 여러 개면 다른 인스턴스는 TTL까지 옛 목록을 볼 수 있다(지금 배포는 1개). 캐시 비움 지점을 빠뜨리면 TTL까지 늦게 보인다. API 응답은 그대로라 화면 변경 없음 | 공연 모듈 @hyos1(주 작성), 강민 일부 |
| B. Redis 캐시 | A와 비슷하거나 작다. DB 대신 Redis 왕복과 역직렬화가 생긴다 | 여러 인스턴스가 같은 값을 본다. 대신 Redis 왕복·직렬화 비용, Redis 장애 경로가 하나 더 생긴다 | 위와 같음 |
| C. 응답 줄이기: 끝난 회차 빼기(91 → 14) 또는 회차 목록 분리·페이지 | 회차 수 몫(예매 서비스 직렬화·변환, DB 결과 전송). 크기는 확인 못 함(6절 M1로 잰다) | API 계약 변경이라 프론트 화면(마감 회차 표시)과 맞춰야 한다. 실제 공연은 회차가 적어 효과가 시연 데이터에서만 크다 | 예매 @hyos1 + 프론트(안준현 담당, contract 이슈) |
| D. 시연 데이터 정리: 지난 시연 회차 정리, 또는 `seed-demo.sh`가 측정마다 새 공연을 쓰게 | C와 같은 몫을 코드 변경 없이. 측정 조건도 날마다 같아진다 | 지난 측정 회차를 참조하는 예매·좌석 행이 있어 지우기 어려울 수 있다(소프트 삭제 규칙). 이 조사는 제안만 한다 | 시드 스크립트 안준현 담당 |
| E. 쿼리 합치기(공연 + 회차 한 쿼리) | DB 왕복 1번, 약 0.05~0.1ms | 쿼리가 복잡해지고 회차 0개 공연 처리 분기가 생긴다. 효과가 작다 | @hyos1 |
| F. HTTP 캐시(`Cache-Control: max-age`, nginx 1초 캐시) | 캐시가 맞으면 Gateway·예매 서비스·DB 전부(약 3ms → nginx 몫만) | **`serverTime`이 TTL만큼 늦는다.** 화면이 이 값으로 오픈 카운트다운을 맞추므로 오픈 순간에 어긋난다. k6는 Gateway 8080을 바로 치므로 측정에 효과가 안 보인다 | 프론트 nginx 안준현 담당 |
| G. 예매 서비스 요청 로그를 Gateway처럼 `problems` 모드로 | 약 0.2ms(서버 전체, 추정). 공연 상세만이 아니라 모든 서블릿 요청에 효과 | 정상 요청 로그가 사라져 요청 로그 대시보드가 빈다. 지표·트레이스로 본다(Gateway와 같은 결정). 이미 "2단계, contract 이슈 뒤"로 잡혀 있다(`gateway.yml` 주석) | 공통 모듈 안준현 담당 |
| H. Gateway 공개 경로 가볍게(관측·지표 일부 끄기 등) | 확인 못 함. 1ms 안에서 무엇이 큰지 모른다 | 모든 경로의 관측에 영향. 근거 없이 끄면 장애 때 볼 것이 줄어든다 | Gateway 강민 |

## 5. 추천: A(로컬 캐시, 판매 상태는 요청마다 계산)

고른 이유
- 3ms 중 **확실히 아는 몫(DB 0.7ms)을 통째로 없앤다.** DB는 쿼리 계획이 이미 최적이라 쿼리를 고쳐서는 더 줄지 않고, "부르지 않는 것"만 남았다.
- 공연·회차 목록은 관리자가 바꿀 때만 변한다. 변하는 것은 `serverTime`과 판매 상태뿐인데 이 둘은 캐시한 회차의 `openAt`·`startsAt`으로 요청마다 계산하면 된다. 그래서 **오픈 정각에 BEFORE_OPEN → ON_SALE이 늦게 바뀌는 일이 없다.** F(HTTP 캐시)가 크게 줄이지만 바로 이 점 때문에 고르지 않는다.
- API 응답이 같아 프론트·contract 변경이 없다. 공연 모듈 안에서 끝난다.
- 같은 모듈에 좌석 배치 캐시(ISE-204) 선례가 있어 모양을 맞출 수 있다.

감수하는 점
- Gateway 1ms와 직렬화 몫은 남는다. 기대 효과는 3ms → 약 2ms(추정)이고, 오픈 전 660/s 기준 약 0.6~0.8코어(추정)가 다른 경로로 간다.
- 캐시 비움을 관리자 API(`ConcertAdminService`)에 걸어야 한다. `seed-demo.sh`는 관리자 API로 회차를 만들므로 비움이 걸린다. DB를 손으로 고치면 TTL까지 늦게 보인다.
- 인스턴스를 늘리면 로컬 캐시끼리 어긋난다(TTL까지). 그때는 B(Redis)나 비움 이벤트를 다시 본다.

바꿀 조건
- 6절 M1에서 회차 1개 공연이 91개 공연보다 한 건 CPU가 크게 작으면(예: 1ms 이상), A보다 D(시연 데이터 정리)를 먼저 한다. 코드 변경 없이 같은 효과이기 때문이다.
- M3에서 요청 로그 몫이 크면 G를 앞당기자고 공통 모듈 담당에게 제안한다.

## 6. 측정 계획 (B1-d `loadtest/k6/scenarios/b1d-concert-detail.js`)

B1-d는 공연 상세 하나만 초당 `RATE`건 보낸다. 공개 API라 토큰이 필요 없다. 측정 모드(추적 0.01)에서 O1 오픈 전과 같은 **RATE=660, 120초**로 돌리고, `gw-collect`의 docker stats로 컨테이너별 CPU를 모아 11/13과 같은 방법(평균 코어 × 구간 ÷ 성공 수)으로 한 건 CPU를 낸다.

| 단계 | 조건 | 보는 것 | 코드 변경 |
|---|---|---|---|
| M0 기준선 | `CONCERT_ID=1`(91회차) | Gateway·예매 서비스·예매 DB 한 건 CPU. 11/13 오픈 전 값(1.0~1.2 / 1.1~1.4 / 0.68~0.71ms)이 재현되는지 | 없음 |
| M1 회차 수 몫 | `CONCERT_ID=16`(1회차) | M0와의 차이 = 회차 90개 몫. C·D의 효과 크기 | 없음 |
| M3 요청 로그 몫 | M0 + 측정 덮어쓰기에 예매 서비스 `ISEONJWA_REQUESTLOG_ENABLED=false`(`iseonjwa.request-log.enabled`의 환경변수 이름. 대시는 빠진다) | 서버 전체 바쁜 코어 차이(로그 비용은 JVM 밖에도 있어 컨테이너 합만으로는 안 보인다) | 없음(설정) |
| M2 캐시 | A를 구현한 이미지로 M0 반복 | 예매 DB 한 건 CPU가 거의 0이 되는지, 예매 서비스 몫이 얼마 줄었는지 | 있음 |

- 각 조건 2회. 11/13 다섯 회차의 컨테이너 값 흔들림이 약 ±10%였으므로 그보다 큰 차이만 효과로 본다.
- M0·M1·M3는 코드 없이 다음 측정 날 한 번에 할 수 있다(약 15분). M2는 main 반영 뒤 배포 서버에서 하거나, 로컬 compose에서 M0·M2를 같은 PC로 비교한다(로컬은 절대값이 아니라 비율만 본다).
- `BASE_URL`이 Gateway 8080이라 nginx를 거치지 않는다. F를 재려면 80번으로 따로 돌려야 한다.

## 7. 확인하지 못한 것
- Gateway 1ms 안의 단계별 분해(중계, 관측, LoadBalancer). JVM 프로파일러(async-profiler 등)나 스레드 CPU를 재지 않았다.
- 예매 서비스 1.1~1.4ms 중 Hibernate·Jackson·로그·Tomcat 각각의 몫. 회차 수 몫의 크기(M1로 잰다).
- 예매 DB 0.7ms 중 프로토콜·결과 전송·계획 세우기 각각의 몫. pg_stat_statements가 없어 부하 중 쿼리별 평균을 보지 못했다. 서버 준비문(prepared statement)이 실제로 쓰였는지도 보지 않았다.
- 한가한 서버에서 Gateway가 직접 호출보다 7~10ms 늦은 이유. 지금 배포는 추적 샘플링 1.0이라 측정 때(0.01)와 조건이 다르다. CPU 문제인지는 모른다.
- 요청 로그 비용 0.2ms/건은 Gateway 측정값을 옮긴 추정이다. 예매 서비스에서 직접 재지 않았다.
- 실제 사용자가 오픈 전에 상세를 얼마나 자주 새로 고치는지. O1의 초당 660건은 시나리오 가정(10~30초 간격 또는 Synthetic 프로필)이다.
