# Gateway 동시 처리 수 상한을 64·128·256·512처럼 2의 거듭제곱으로 고르는 데 기술적 이유가 있나

## 질문
동시 처리 수 상한을 64, 128, 256, 512처럼 2의 배수로 지정하는 데 철학이 있나?

## 짧은 답
- **기술적 이유는 없다.** 상한은 `AtomicInteger`를 올리고 `maxRequests`와 비교할 뿐이다(`InFlightLimitHandlerDecorator`). 60이든 500이든 성능 차이가 없다.
- 2의 거듭제곱이 된 이유는 두 가지다. **① 탐색 간격**: 값을 모를 때 두 배씩 늘려 가며 재면 적은 회차로 넓은 범위를 훑을 수 있다(로그 간격 탐색). **② 반올림 습관**: 계산값을 기억하기 쉬운 수로 올렸다.
- 값을 정하는 근거는 모양이 아니라 **측정값과의 관계**다. 512는 "끔에서 본 최대 482보다 위"라서 후보가 됐고, 500이나 480이 아니라 512가 된 것은 반올림일 뿐이다.

## 자세히

### 1. 각 값이 어디서 왔나
| 값 | 출처 | 2의 거듭제곱인 이유 |
|---|---|---|
| 64 | 리틀의 법칙 계산값 60~67(1,480/s × 40~45ms) | 범위 안에서 기억하기 쉬운 수를 골랐다(`config-repo/gateway.yml` 주석) |
| 32·128·500 | 6차 비교(11/11) | 64를 기준으로 절반·두 배. 500은 "사실상 끔"을 보려던 큰 값이라 2의 거듭제곱이 아니다 |
| 96 | 11/13 오전 비교 | 64와 128 사이를 좁히려고 넣은 중간값. 2의 거듭제곱이 아니다 |
| 256 | 11/13 저녁 안전망 후보 | 64의 4배. 탐색 간격 |
| 512 | 11/13 저녁 안전망 후보 | 끔에서 본 처리 중 최대 482 바로 위의 반올림 |

96과 500처럼 2의 거듭제곱이 아닌 값도 이미 썼다. 규칙이 아니라 편의였다는 뜻이다.

### 2. 두 배씩 늘리는 탐색이 왜 흔한가
상한처럼 적당한 값이 몇인지 자릿수부터 모를 때는 같은 간격(64, 74, 84, …)보다 같은 비율(64, 128, 256, …)로 재는 편이 효율적이다.
- 네 회차로 64~512, 8배 범위를 덮는다. 같은 간격 10씩이면 같은 범위에 45회차가 든다.
- 결과가 크게 바뀌는 경계를 찾으면 그 사이를 다시 좁힌다(64와 128 사이에 96을 넣은 것).
- 이분 탐색이나 지수 백오프와 같은 생각이다.

### 3. 2의 거듭제곱이 실제로 의미 있는 곳
| 곳 | 이유 |
|---|---|
| 해시 테이블 크기(`HashMap` 용량) | 나머지 연산을 비트 AND로 바꿀 수 있다 |
| 버퍼·메모리 할당 단위(Netty 버퍼 풀, 페이지 크기) | 정렬·분할이 쉽다 |
| 링 버퍼(LMAX Disruptor 등) | 인덱스 감기를 비트 마스크로 한다 |

동시 처리 상한은 이런 구조가 아니라 정수 하나와의 비교라 해당하지 않는다.

### 4. 그래서 어떻게 정하나
- 안전망 값은 "평소 최대 처리 중 수보다 위, 메모리 여유 안"이면 된다. 11/13 측정에서 끔 최대 482, 컨테이너 609MiB/1GiB, 힙 284/512MiB였다.
- 운영값을 512로 할지 500으로 할지는 결과에 영향이 없다. 설명할 때는 "482 위로 여유를 둔 값"이라는 근거를 말하고, 2의 거듭제곱인 것은 근거로 쓰지 않는다.
