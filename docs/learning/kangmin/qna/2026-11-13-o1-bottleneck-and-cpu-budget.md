# 11/13 O1 측정으로 병목을 짚을 수 있나, 무엇을 더 고치고, CPU가 먼저 차는 서버에서 사용자를 어떻게 감당하나

## 질문
측정 모드가 끝났다. 스크립트에 더 고칠 곳이 있는지, 그게 중요한지 알고 싶다. 지금 테스트로 병목이 어디서 생기는지 파악할 수 있는 상황인가? CPU에 여유가 없어 계속 CPU가 먼저 죽는데, 이걸 어떻게 풀 수 있나? 자원이 제한된 지금 감당할 수 있는 사용자 수를 어떻게 관리해야 하나?

## 짧은 답
- **병목은 "서버 CPU 전체"까지는 짚었고, 그 안에서 누가 왜 CPU를 먹었는지는 아직 못 짚었다.** 서버는 4 vCPU 한 대에 앱 9개, DB 3개, Redis, Kafka, 관측 도구가 같이 산다. 증상은 예매 서비스 쪽(Hikari 풀 5개 고갈 500, 메모리 930MiB)과 auth-redis bulkhead(503)에 나왔다. 컨테이너별 CPU를 시간대별로 나눈 표와 요청 종류별 CPU 비용은 아직 없다. 원자료(docker stats·pidstat)는 남아 있다.
- **가장 먼저 의심할 곳이 있다.** 오늘 회차 12개(108~119)는 모두 측정 직전에 새로 만들었다. 저장소에는 좌석을 만든 뒤 `ANALYZE`하는 곳이 없다(확인함). 같은 날 노트(`2026-11-13-stale-statistics-nested-loop-seat-query.md`)대로라면 좌석 조회가 Nested Loop로 돌아 DB CPU를 몇 배 썼을 수 있다. **확인 못 함.** 맞다면 오늘 "CPU가 먼저 죽는다"의 큰 몫은 앱 한계가 아니라 측정 준비의 빈틈이다.
- **고정된 CPU에서 감당할 사용자 수 = CPU ÷ 성공 한 건당 CPU.** 손잡이는 둘이다. ① 한 건당 CPU를 줄인다(낭비 제거). ② 처리할 수 있는 만큼만 들여보내고 나머지는 싸게 기다리게 한다(입장 제어). 우리 시스템에서 ②는 이미 있는 **대기열 입장 속도(초당 50명)**다. 이 값을 예매 서비스가 실제로 처리할 수 있는 양에 맞추는 것이 핵심이다.

## 자세히

### 1. 지금 무엇을 알고 무엇을 모르나
| 구분 | 내용 | 근거 |
|---|---|---|
| 안다 | 서버 CPU가 한계다. 15,000명 회차는 평균 80~84%, 90% 이상인 시간이 회차의 60% 안팎 | `safety-net-measure-2026-11-13.md` 3·3-1절 |
| 안다 | Gateway는 1코어 기준 74~85%로 자기 몫에는 여유가 있었다. 처리 중 수를 정한 것은 Gateway 상한이 아니라 사용자 수와 예매 서비스 응답 속도다(512에서 거절 0, 처리 중 486~490) | 같은 문서 6절, 3-1절 |
| 안다 | 증상은 예매 서비스 500(Hikari 풀 5개 고갈, 끔·512에서 4,500~5,300건), auth-redis 503(2만여 건), 예매 서비스 메모리 930MiB(상한 1.125GiB의 81%) | 같은 문서 |
| 안다 | 예매 서비스 CPU 최대 147~173%, 예매 DB 100~110% | 같은 문서 3절 |
| 모른다 | 4코어를 시간대별로 누가 얼마나 썼나(대기열 서비스, Redis, Kafka, 관측, 컨테이너 밖) | 원자료는 있고 집계를 안 했다 |
| 모른다 | 요청 종류별 성공 한 건당 CPU(순번 조회 한 건, 좌석 조회 한 건, 선점 한 건) | 재지 않았다 |
| 모른다 | 좌석 조회가 통계 문제로 Nested Loop를 탔나 | 재지 않았다. 아래 2절 |

"병목 = CPU"는 출발점일 뿐이다. 병목을 짚었다고 하려면 **"어느 컨테이너의 어떤 일이 CPU를 쓰고, 그 일이 성공으로 이어졌나"**까지 가야 한다.

### 2. 먼저 확인할 것: 새 회차 통계
| 항목 | 내용 |
|---|---|
| 오늘 조건 | 회차마다 `seed-demo.sh open`으로 좌석 15,000행을 새로 만들고 곧바로 부하를 넣었다 |
| 저장소 | `script/`, `reservation-service` 마이그레이션 어디에도 `ANALYZE`가 없다(`git grep`, 11/13 확인) |
| 일어났을 수 있는 일 | 플래너가 새 회차를 1행으로 추정 → Nested Loop → 좌석 조회 한 번에 인덱스 15,000번 → DB CPU·커넥션 점유 증가 → Hikari 고갈 500 |
| 확인 방법(조회만) | 회차 119로 `EXPLAIN (ANALYZE, BUFFERS)` 좌석 조회 쿼리, `pg_stat_user_tables`의 `last_autoanalyze`, `n_mod_since_analyze` |
| 맞다면 | 측정 준비 스크립트에 `ANALYZE schedule_seats`를 넣고 다시 잰다. 운영에도 같은 위험이 있다(회차 등록 직후 오픈) |

이것을 확인하기 전에는 오늘 CPU 숫자로 "서버가 몇 명까지 버틴다"를 말하지 않는 편이 안전하다.

### 3. 스크립트에서 더 고칠 것과 중요도
| 중요도 | 고칠 것 | 왜 중요한가 |
|---|---|---|
| **높음** | 회차를 만든 뒤 `ANALYZE`(측정 준비) | 2절. 측정이 앱이 아니라 통계 빈틈을 잴 수 있다 |
| **높음** | 결제 본문 `pgProvider: 'MOCK'`(dev O1, `booking.js`) | 없으면 배포에서 결제가 전부 400이다(오늘 확인) |
| **높음** | k6 요청 태그 `name`을 경로 이름으로 고정 | URL마다 태그가 달라 Prometheus 시계열이 71만 개로 늘어 OOM이 났다(오늘 확인) |
| **높음** | 503을 받으면 `Retry-After`를 따르기 | 지금은 실패하면 무조건 3초 뒤 다시 보낸다(`retryLater(user, 3000)`). 상한 64 회차의 순번 조회 32.9만 건 가운데 상당 부분이 거절 뒤 재시도였다. 실제 화면이 `Retry-After`를 따른다면 측정 부하는 실제보다 부풀려진 것이다. 화면 동작은 확인 못 함 |
| 중간 | 좌석 조회·선점이 503·500이면 바로 `error`로 끝냄 | 실제 사용자는 다시 누른다. 지금은 실패가 많을수록 부하가 줄어드는 쪽으로 왜곡된다 |
| 중간 | 실제 도착 모양 기록(진입 요청 시각 10ms 단위) | 계획한 몰림이 VU 구조 때문에 평평해졌는지 모른다(`2026-11-13-o1-uniform-vs-synthetic-analysis.md` 4절) |
| 중간 | 연석 보장, 등급 안 앞열 쏠림 | 409와 재시도 양이 실제와 다를 수 있다 |
| 낮음 | 닫힌 모델(사용자 수가 처리 중 수를 정함) | 이번 질문에는 오히려 맞는 모델이다. 결과 해석 때 적어 두면 된다 |

앞의 네 가지는 **측정이 맞는 것을 재는가**의 문제라 먼저다. 나머지는 **얼마나 실제와 닮았나**의 문제다.

### 4. CPU가 먼저 차는 서버에서 사용자를 감당하는 방법
식은 단순하다.

```
감당할 수 있는 처리율(초당 성공) ≈ 쓸 수 있는 CPU(코어·초) ÷ 성공 한 건당 CPU(코어·초)
```

손잡이는 분자를 늘리거나, 분모를 줄이거나, 들어오는 양을 분자에 맞추는 것이다.

| 방향 | 방법 | 우리 시스템에서 | 대가 |
|---|---|---|---|
| A. 분모 줄이기(낭비 제거) | 통계 문제 해결 | 2절. 맞다면 효과가 가장 클 것으로 본다(추정) | 측정 준비·운영 절차가 늘어난다 |
| | 좌석 조회를 싸게 | 응답 약 820KB를 사용자마다 DB에서 만든다. 배치(열·번호)는 안 바뀌므로 캐시하고, 상태만 따로 준다 | 상태 반영 지연을 설계해야 한다(좌석 조회 담당과 합의) |
| | 순번 조회를 싸게 | 요청 수가 가장 많은 경로다(15,000명에서 초당 최대 약 2,300건). 간격을 서버가 정하고(`nextPollAfterMillis`), 클라이언트가 `Retry-After`를 따르게 한다 | 순번 갱신이 늦게 보인다 |
| | 거절·재시도 낭비 | 거절된 요청도 CPU를 쓰고, 3초 뒤 다시 온다 | — |
| | Gateway 한 건당 CPU | 약 1.06ms(성능 청사진). JWT 검증·관측 중복이 후보 | 측정이 더 필요하다 |
| B. 들어오는 양 맞추기(입장 제어) | 대기열 입장 속도를 예매 서비스 처리량에 맞춘다 | 지금 초당 50명을 들여보내는데 예매 쪽이 포화해 Hikari 500이 난다. 들어온 사람이 실패하는 것보다, 대기열에서 조금 더 기다리게 하는 편이 성공 수가 많을 수 있다(추정) | 대기 시간이 늘어난다. 적정 값은 측정으로 찾는다 |
| | 적응형 입장 | 예매 서비스 지연·풀 사용률을 보고 입장 속도를 자동으로 조절한다 | 구현·설명 비용이 크다. 고정 값을 먼저 찾는다 |
| C. 몫 나누기(격리) | 컨테이너별 CPU 가중치·상한(`cpu_shares`, `cpus`) | `single-host-msa-resource-isolation.md` M2~M4. 대기열·Gateway가 예매 서비스 몫을 잠식하지 않게 한다 | 남는 CPU를 빌려 쓰지 못한다. 값을 잘못 잡으면 스스로 한도를 낮춘다 |
| D. 분자 늘리기 | DB를 RDS로 빼기, 인스턴스 키우기 | ADR 0047 3번. 앱 노드에서 postgres 몫이 빠진다 | 비용. 발표까지 범위 밖일 수 있다 |

### 5. 순서 제안
1. **2절 확인**(조회만, 서버 측정 모드 없이 가능). 결과에 따라 이후 해석이 달라진다.
2. **오늘 원자료로 컨테이너별 CPU 분해표**를 만든다(측정 없이 가능). 누가 4코어를 먹었는지가 나온다.
3. 스크립트 "높음" 네 가지를 고친다.
4. 다시 잴 때는 **대기열 입장 속도**를 바꿔 가며 확정 수(굿풋)가 가장 큰 값을 찾는다. 이것이 "제한된 자원에서 감당할 사용자 수를 관리하는" 손잡이다. 대기열 담당(영은님)과 합의할 일이다.
5. 그 뒤에 좌석 조회 캐시, 순번 조회 비용처럼 분모를 줄이는 개선을 고른다.

### 6. 확인할 질문
- 회차 119의 좌석 조회 계획이 Nested Loop인가, `ANALYZE` 뒤 Hash Join으로 바뀌나
- 15,000명 회차에서 4코어의 시간대별 분해(예매 서비스, 예매 DB, 대기열 서비스, Redis, Gateway, Kafka, 관측, 컨테이너 밖)
- 실제 화면은 503의 `Retry-After`를 따르나
- 입장 속도를 30·40·50명으로 바꾸면 확정 수가 어떻게 달라지나
