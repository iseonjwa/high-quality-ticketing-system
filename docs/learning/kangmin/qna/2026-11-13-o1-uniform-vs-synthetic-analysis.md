# O1 균일 모드와 Synthetic 모드는 요청을 언제, 어떻게 보내나

## 질문
요청 수가 초당 N회로 고르게 오는 게 아니라 오픈 직후에 대부분 몰려 있다는 말인가? O1 스크립트의 균일 모드와 Synthetic 모드를 둘 다 자세히 분석해 달라.

## 짧은 답
- **Synthetic 모드는 그렇다. 균일 모드는 아니다.** dev `o1-open-peak.js`(#583 반영) 기준 계획값이다.
  - **Synthetic**(CSV 3,000명): 진입하는 2,831명 중 **0~0.3초에 18%, 1초 안에 50%, 3초 안에 81%**가 진입한다. 가장 붐비는 100ms(0.1~0.3초)에 진입 요청 513건이 몰린다. 초당으로 바꾸면 약 5,100건 속도다(계산값).
  - **균일**: 오픈 **1초 뒤부터 10초 동안 고르게** 진입한다. 첫 1초에는 진입이 0이다. 3,000명이면 100ms마다 약 30건, 초당 약 300건으로 평평하다.
- **다만 이것은 CSV와 코드가 정한 계획 시각이다.** 실제로 서버에 닿는 모양은 VU 수와 응답 시간이 깎는다. VU 하나가 사용자 10명을 순서대로 진행하기 때문이다. 실제 모양은 측정으로 확인해야 하고, 아직 재지 않았다.

## 자세히

### 1. 공통 구조: VU 하나가 사용자 여러 명을 든다
| 항목 | 내용 | 근거(dev `o1-open-peak.js`) |
|---|---|---|
| 실행기 | `constant-vus`. VU 수 고정, `PRE_OPEN_SECONDS + AFTER_OPEN_SECONDS` 동안 | 54~58행 |
| 사용자 배정 | VU 하나가 `USERS ÷ VUS`명을 든다(ISE-264 계획 3,000 ÷ 300 = 10명) | 125~145행 |
| 진행 방식 | VU는 자기 사용자 중 다음 행동 시각(`nextAt`)이 가장 이른 사람을 골라 그 시각까지 잠든 뒤 한 단계만 진행한다 | 108~123행, `nextUser` 226행 |
| 늦어짐 기록 | 계획 시각보다 늦게 보낸 정도를 `action_lateness`로 남긴다 | 121행 |
| 단계 | browse → enter → wait(폴링) → token → seats → hold → pay → confirm | `STEPS` 252~388행 |

**중요한 결과**: 한 VU 안의 요청은 하나씩 순서대로 나간다. 같은 VU의 사용자 10명이 같은 순간에 진입하려 해도, 앞 요청의 응답이 와야 다음 요청이 나간다. 그래서 순간 동시 요청 수는 **VU 수가 상한**이다.

### 2. 균일 모드 (`USERS_CSV` 없음)
모든 사용자가 같은 확률 규칙을 따른다(`uniformProfile` 152~170행).

| 단계 | 규칙 |
|---|---|
| 첫 행동 | 측정 시작부터 최대 60초 안 무작위 |
| 오픈 전 browse | 공연 상세를 10~30초 간격 무작위로 새로고침 |
| 진입 시각 | `openAt + 1초 + U(0, 10초)`. **고른 분포** |
| 진입 횟수 | 1번(연타 없음) |
| 폴링 간격 | 서버가 준 `nextPollAfterMillis`(없으면 3초). 측정 세션 보고로는 순번/50초를 3~10초로 자르고 지터 20%를 더한 값이다 |
| 실패 뒤 | 진입·폴링·토큰이 실패하면 3초 뒤 다시 |
| 좌석 고르기 | 매수 1석·2석 반반. 70%는 좌석 응답 앞쪽 10%(A구역 앞쪽)에서 고르고, 둘째 석은 "다음 빈자리" |
| 고민 시간 | 첫 선택 1~3초, 409 뒤 재시도는 0.5~1초 |
| 409 뒤 | 같은 방식으로 최대 2번 다시(`MAX_RETRY`) |
| 선점 뒤 | 10%는 결제 없이 떠나고, 나머지는 5~30초 뒤 결제 |
| 확정 확인 | 0.5초 간격, 최대 10번 |

진입 모양(계산값)
| 사용자 수 | 오픈 0~1초 | 1~11초 | 100ms당 |
|---|---|---|---|
| 3,000 | 0 | 초당 약 300 | 약 30 |
| 15,000(오늘 안전망 측정) | 0 | 초당 약 1,500 | 약 150 |

균일 모드에서 "몰림"은 오픈 뒤 10초라는 **구간 단위**로만 있다. 그 10초 안은 평평하다.

### 3. Synthetic 모드 (`USERS_CSV=../data/o1-synthetic-3000.csv`)
CSV 한 행이 사용자 한 명의 대본이다(`csvProfile` 172~205행). 페르소나 8종의 분포(`loadtest/synthetic/o1-personas.json`)에서 시드 20261113으로 3,000행을 만들었다.

#### 3-1. 진입 시각 계산
- 오픈 전에 온 사람(`arrive_s ≤ 0`): `진입 = 오픈 + enter_delay_ms`
- 오픈 뒤에 온 사람(`arrive_s > 0`): `진입 = 접속 + enter_delay_ms`(상세를 한 번 보고 진입)
- `enter_clicks = 0`(169명, 구경만): 진입하지 않는다

#### 3-2. 진입 분포 (CSV로 계산한 계획값, 진입 2,831명)
| 오픈 뒤 | 사용자 | 비율 | 진입 요청(연타 포함) |
|---|---|---|---|
| 0~0.1초 | 54 | 1.9% | 194 |
| 0.1~0.2초 | 205 | 7.2% | 513 |
| 0.2~0.3초 | 256 | 9.0% | 513 |
| 0.3~0.5초 | 389 | 13.7% | 808 |
| 0.5~1초 | 518 | 18.3% | 876 |
| 1~2초 | 614 | 21.7% | 896 |
| 2~3초 | 272 | 9.6% | 402 |
| 3~10초 | 125 | 4.4% | 151 |
| 10~120초 | 148 | 5.2% | 164 |
| 120초 이후 | 250 | 8.8% | 254 |

- 누적: 0.3초 18%, 1초 50%, 3초 81%. 진입 시각 중앙값 0.99초.
- 첫 1초 100ms별 진입 요청: 194, 513, 513, 430, 378, 257, 202, 121, 137, 159. **0.1~0.3초가 꼭대기**다. 0~0.1초가 낮은 것은 페르소나마다 진입 지연에 최솟값(50~400ms, 사람 반응 시간)을 두었기 때문이다.
- 진입 요청은 4,771건으로 사용자 2,831명의 약 1.7배다. 연타(2~5번)를 하는 사람이 1,153명이다.

그래서 말씀하신 "0~0.3초에 대부분"과는 조금 다르다. **꼭대기는 0.1~0.3초에 있고, 대부분(81%)은 3초 안에 들어온다.** 지금 분포의 근거는 LLM이 낸 페르소나 추정이다(`o1-personas.json`의 각 `basis`).

#### 3-3. 사용자 행동 (CSV 3,000행 집계)
| 항목 | 분포 |
|---|---|
| 페르소나 | PC 팬 840, 친구와 2매 540, 퇴근길 모바일 360, 새로고침 연타 360, 오픈 뒤 일반 관심층 300, VIP 사냥꾼 240, 여러 기기 210, 구경만 150 |
| 매수 | 1석 999(33%), 2석 1,613(54%), 3석 84(3%), 4석 304(10%) |
| 노리는 등급 | VIP 1,265(42%), R 900(30%), S 441(15%), ANY 394(13%) |
| 진입 횟수 | 0번 169, 1번 1,678, 2번 660, 3번 269, 4번 154, 5번 70 |
| 409 뒤 | 같은 등급 다시(`same_zone`), 아무 곳(`any_zone`), 포기(`give_up`). 재시도 횟수는 페르소나마다 1~5 |
| 그 밖 | 고민 시간, 대기열 인내 시간(넘으면 떠남), 선점 뒤 이탈 확률, 결제까지 시간이 페르소나마다 다르다 |

#### 3-4. 균일과 다른 동작
| 단계 | 균일 | Synthetic |
|---|---|---|
| 오픈 전 | 10~30초 새로고침 | 페르소나 간격(연타형 3~6초, 0이면 새로고침 없음) |
| 진입 | 1번 | 0~5번, 쉬지 않고 이어 보냄(273~280행) |
| 대기 | 끝까지 기다림 | 인내 시간이 지나면 떠남(410~412행). 취소 API는 부르지 않아 서버에는 남는다 |
| 좌석 | 전체 앞쪽 10%에서 70% | 노리는 등급 구간 안 무작위 위치(`pickSeatsInZone`) |
| 409 뒤 | 같은 방식 2번 | 페르소나의 `on_conflict`, `max_retry` |
| 기록 | 단계별 | 단계별에 페르소나 태그, 선점에는 등급·응답 코드 태그(`compare.py`가 등급별 409 비율을 낸다) |

### 4. 계획과 실제가 갈리는 곳
| 원인 | 내용 | 확인 방법 |
|---|---|---|
| VU 수 | ISE-264 계획은 VU 300개다. 0.1~0.3초 꼭대기의 1,026건을 계획대로 보내려면 그 200ms 안에 VU가 평균 3.4건씩 보내야 한다. 응답이 60ms보다 길면 못 따라간다(계산값). 연타는 같은 VU에서 앞 응답을 기다린 뒤 나가서 더 뒤로 밀린다 | k6 raw CSV의 `queue_enter` 요청 시각을 10ms 단위로 묶어 3-2 표와 비교한다. `action_lateness{state:enter}` |
| 서버 응답 시간 | 응답이 느려질수록 VU가 다음 사용자를 늦게 진행한다. 오늘 15,000명 끔 회차에서 `action_lateness` p95가 약 10.4초였다(측정, 균일 모드) | 같은 지표 |
| 연석 | 둘째 석부터 "다음 빈자리"라, 붙은 자리인지 보장하지 않는다 | 선점한 좌석의 열·번호 |
| 등급 안 앞열 | 등급 구간 안에서 무작위라 VIP 앞열 쏠림은 없다 | 선점 좌석 위치 분포 |

### 5. 파일에서 두 모드를 찾아 읽는 법 (추가 질문: 파일을 열어 봐도 못 알아보겠다)

#### 5-1. 로컬 파일에는 Synthetic 모드가 없을 수 있다
Synthetic 모드는 #583(11/13 18:01 KST dev 머지)에 들어갔다. dev를 받지 않은 브랜치의 `loadtest/k6/scenarios/o1-open-peak.js`에는 `USERS_CSV`도 `csvProfile`도 없다. 11/13 20:25에 확인한 로컬 브랜치(`refactor/ISE-273-...`)의 파일이 그랬다. 이 경우 dev 버전은 이렇게 본다.

```bash
git fetch && git show origin/dev:loadtest/k6/scenarios/o1-open-peak.js
```

#### 5-2. 한 파일, 스위치 하나
두 모드는 파일이 따로 있지 않다. **환경변수 `USERS_CSV`를 주느냐 마느냐**가 스위치다. 갈리는 곳은 딱 한 줄이다(dev 131행).

```js
const profile = csvRows === null ? uniformProfile(data) : csvProfile(csvRows[first + i], data);
```

- `USERS_CSV` 없음 → `uniformProfile`(152행): 모든 사용자에게 **같은 규칙**을 준다. 비어 있는(`null`) 칸은 단계마다 주사위를 굴려 정한다(예: 매수는 좌석을 고를 때 1석·2석 반반).
- `USERS_CSV` 있음 → `csvProfile`(172행): 사용자 i에게 **CSV i번째 행**을 준다. 행에 적힌 값이 그 사람의 성격이다.

그 뒤의 단계 코드(`STEPS`, 252행 이후)는 두 모드가 같다. 단계 코드는 `user.profile`의 값만 읽는다. 그래서 **모드 차이는 "프로필을 어디서 가져오나" 하나뿐**이다.

#### 5-3. 프로필 칸 대조
| 프로필 칸 | 균일(`uniformProfile`) | Synthetic(`csvProfile`, CSV 열) |
|---|---|---|
| `enterAt` 진입 시각 | 오픈 + 1초 + U(0, 10초) | 오픈 + `enter_delay_ms`(오픈 뒤 접속자는 접속 + 지연) |
| `refreshMs` 새로고침 간격 | `null` → 매번 10~30초 무작위 | `refresh_s` |
| `enterClicks` 진입 횟수 | 1 | `enter_clicks`(0~5) |
| `seats` 매수 | `null` → 1·2석 반반 | `seats`(1~4) |
| `zone` 등급 | `null` → 좌석 전체 앞쪽 10%를 70% | `zone`(VIP·R·S·ANY) |
| `thinkMs` 고민 | `null` → 1~3초 | `think_ms` |
| `maxRetry` · `onConflict` | 2 · 같은 방식 | `max_retry` · `on_conflict` |
| `patienceMs` 대기 인내 | 0(끝까지) | `queue_patience_s` |
| `abandonRatio` 이탈 | 0.1 | `abandon_after_hold`(0 또는 1, 그 사람이 떠나는지) |
| `payDelayMs` 결제까지 | `null` → 5~30초 | `pay_delay_s` |

#### 5-4. CSV 한 행 읽기 예
`loadtest/k6/data/o1-synthetic-3000.csv`의 두 행이다.

```
user_no,persona,arrive_s,refresh_s,enter_delay_ms,enter_clicks,seats,zone,think_ms,max_retry,on_conflict,queue_patience_s,abandon_after_hold,pay_delay_s
2,refresh_spammer,-502,5,397,2,1,ANY,1825,5,same_zone,0,0,11
6,vip_hunter,-390,11,271,1,2,VIP,2466,5,same_zone,0,0,30
```

- 2번(새로고침 연타): 오픈 502초 전에 들어와 5초마다 상세를 새로고침한다. 오픈 0.397초 뒤 진입 버튼을 2번 누르고, 끝까지 기다린다. 아무 등급에서 1석을 1.8초 고민해 고른다. 409면 같은 등급에서 최대 5번 다시 고르고, 선점하면 11초 뒤 결제한다.
- 6번(VIP 사냥꾼): 오픈 390초 전에 들어와 11초마다 새로고침한다. 오픈 0.271초 뒤 한 번 진입하고, VIP에서 2석을 2.5초 고민해 고른다. 409면 VIP에서 최대 5번 다시 고르고, 30초 뒤 결제한다.

균일 모드라면 두 사람 모두 오픈 1~11초 사이 아무 때나 한 번 진입하고, 매수와 고민 시간은 그때그때 주사위로 정한다.

#### 5-5. 실행할 때
```bash

# Synthetic(USERS는 CSV 행 수와 같아야 한다, 77~79행)

```

### 6. 정리
- 오픈 직후 몰림을 **계획에 넣은 것**은 Synthetic 모드다. 균일 모드는 10초에 고르게 흩는다.
- 계획한 모양이 **실제로 나갔는지**는 두 모드 모두 아직 재지 않았다. 몰림이 클수록 VU 구조 때문에 평평해질 가능성이 크다(추정).
- 그래서 "균일 대 Synthetic" 비교(ISE-264)의 결과를 해석하려면, 먼저 두 모드의 실제 도착 모양을 같은 방법으로 그려 두어야 한다.
