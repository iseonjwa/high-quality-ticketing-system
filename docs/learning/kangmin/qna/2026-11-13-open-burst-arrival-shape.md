# 오픈 순간 "초당 2,000명"은 1초 안에 고르게 오지 않는데, 부하 시나리오는 그 모양을 어떻게 흉내 내야 하나

## 질문
오픈 직후 초당 N명이 몰리는 시나리오에서, 실제 사용자는 1초 동안 고르게 요청하지 않는다. 1초에 2,000명이어도 앞 0.1~0.2초에 더 많이 오는 것이 정상 아닌가? 스크립트가 실제와 비슷하려면 어떻게 해야 하나?

## 짧은 답
맞다. 오픈 시각이라는 같은 신호를 보고 움직이는 사람들의 도착은 앞쪽에 몰린다. k6의 `constant-arrival-rate`·`ramping-arrival-rate`는 1초에 N건을 그 1초 안에 거의 같은 간격으로 나눠 보내므로 평균 요청률은 맞아도 순간 몰림은 재현하지 못한다. 동시 처리 수 상한(64)이나 bulkhead(50)처럼 **순간 동시 수**에 반응하는 장치는 같은 평균에서도 몰린 모양일 때 더 일찍, 더 많이 거절한다. 그래서 "평상 처리량"은 고른 도착으로, "오픈 순간 견딤"은 앞쪽이 붐비는 도착으로 따로 재야 한다. 이 저장소에는 앞쪽이 붐비는 Q1-d가 이미 있지만 배포 서버에서는 아직 돌리지 않았다.

## 자세히

### 1. 왜 앞쪽에 몰리나
| 원인 | 설명 |
|---|---|
| 같은 신호 | 모두 "20:00:00"을 기다렸다가 누른다. 도착 시각 = 오픈 시각 + 반응 시간 + 네트워크 지연 |
| 반응 시간 분포 | 사람 반응 시간은 짧은 쪽에 몰리고 꼬리가 긴 모양(로그정규 분포가 흔한 모델)이다. 그래서 첫 수백 ms가 가장 붐빈다 |
| 시계 차이 | 사용자 기기 시계가 서버와 어긋나면 일부는 미리 누르고 일부는 늦게 누른다. 서버 시각(`serverTime`)으로 맞추면 오히려 더 날카롭게 몰린다 |
| 자동 새로고침·매크로 | 정확히 0ms에 맞춰 보내는 클라이언트가 섞이면 맨 앞이 더 뾰족해진다 |
| 재시도 | 503·타임아웃을 받은 사용자가 다시 누르면 두 번째, 세 번째 파도가 생긴다 |

### 2. 도착 모양 선택지 비교
| 모양 | k6 구현 | 장점 | 한계 |
|---|---|---|---|
| 고른 간격 | `constant-arrival-rate`, `ramping-arrival-rate` | 재현성이 좋고 처리량 한계를 깨끗하게 잰다 | 1초 안 몰림이 없다. 오픈 순간보다 낙관적이다 |
| 포아송(무작위) | 반복마다 지수 분포로 `sleep` | 서로 모르는 사람들의 평상 도착에 가깝다 | 같은 신호를 보는 오픈에는 맞지 않는다 |
| 앞쪽이 붐비는 유한 분포(삼각 등) | `per-vu-iterations` + 같은 출발 시각 + 사용자별 지연 | 끝이 있어 "몇 초 안에 전부"를 정확히 지정한다 | 사용자 수만큼 VU가 필요해 발생기 메모리가 한계다 |
| 반응 시간 분포(로그정규 등) | 위와 같고 지연을 로그정규로 뽑음 | 사람 행동에 가장 가깝다 | 매개변수 근거가 필요하다(실제 서비스 로그가 없으면 가정) |
| 계단 + 재시도 파도 | 위 방식 + 실패 시 Retry-After 뒤 재요청 | 재시도 폭풍까지 본다 | 결과 해석이 복잡하다 |

### 3. 같은 평균인데 왜 결과가 달라지나
리틀의 법칙(L = λW)은 **평균**에 대한 식이다. 1초 평균 2,000건이라도 앞 0.2초에 절반(1,000건)이 오면 그 구간의 순간 도착률은 초당 5,000건이다. 응답 시간이 10ms면 평균 처리 중 수는 20이지만, 그 0.2초 동안은 50 근처까지 오르고 처리가 밀려 응답 시간이 늘면 더 커진다. 상한 64나 bulkhead 50은 이 순간값으로 거절하므로, 고른 도착에서는 거절 0이던 요청률에서도 몰린 도착에서는 거절이 생긴다.

### 4. 시나리오를 실제에 가깝게 만들 때 볼 것
- 같은 사용자 수·같은 1초로 **고른 도착과 몰린 도착을 짝지어** 잰다. 차이가 "몰림 모양의 비용"이다.
- 분포를 바꿔 가며(예: 1초 안 / 0.2초 안) 거절이 시작되는 지점을 본다.
- 발생기가 정한 시각에 실제로 보냈는지(`send_lag`)를 같이 기록한다. 늦으면 서버가 아니라 발생기 한계다.
- 실제 사용자는 새 TCP 연결을 연다. k6 VU는 연결을 재사용하므로 연결 수립 폭주(SYN, TLS)는 재현하지 않는다. 앞단(nginx)을 거치는지도 결과를 바꾼다.
- 대기열이 있는 구조라면 몰림을 받는 것은 "대기열 진입" 하나다. 뒤쪽 API는 입장 속도로 평탄해지므로, 몰린 도착은 진입 API와 Gateway에만 걸면 된다.

## 이 프로젝트에서는
- 고른 도착: `loadtest/k6/scenarios/q1-queue-enter.js`(`constant-arrival-rate`), `g1-gateway-auth.js`(`ramping-arrival-rate`). Gateway 상한 64·96·128 비교와 CPU 목표(1,500/s 90% 미만)는 모두 이 방식으로 쟀다.
- 몰린 도착: `loadtest/k6/scenarios/q1d-queue-burst.js`(ISE-217). 사용자 수만큼 VU를 미리 만들고 같은 출발 시각부터 `ENTER_SPREAD_SECONDS` 안에 삼각 분포로 출발시킨다. 지연은 `(1 - Math.sqrt(Math.random())) * SPREAD`이고, 절반이 앞 약 29% 구간에 들어온다(1초면 앞 0.29초에 절반). `send_lag` p95 50ms 이하일 때만 서버 결과로 읽는다.
- Q1-d의 기록은 local뿐이다. 300명을 0.1초·1초에 몰자 Gateway `auth-redis` 차단기가 열려 503이 68~93%였고(11/9), 그 뒤 차단기 값이 바뀌었다(ADR 0050). 배포 서버에서는 "차단기에서 먼저 막힌다"는 이유로 재지 않았다(`docs/design/infra/open-peak-scenarios.md` 343행).
- 확인할 질문: 지금 배포(상한 64, bulkhead 50)에서 Q1(고른 2,000명/1초)과 Q1-d(같은 2,000명, 1초·0.2초)의 거절 수가 얼마나 다른가. 차이가 크면 상한 값 비교(오늘 재측정)는 오픈 순간에 대해 낙관적인 근거다.

## 면접 포인트
- "초당 N건 부하 테스트"를 했다고 하면 "도착 모양은?"이라는 질문이 온다. 고른 간격은 처리량 한계, 몰린 도착은 순간 견딤을 잰다고 나눠 답한다.
- 평균 요청률이 같아도 순간 동시 수가 다르면 동시성 상한·커넥션 풀·bulkhead의 거절이 달라진다. 리틀의 법칙은 평균에 대한 식이라는 점을 함께 말한다.
- 열린 모델(도착률을 정함)과 닫힌 모델(사용자 수를 정하고 응답 뒤 다음 요청)의 차이: 닫힌 모델은 서버가 느려지면 요청도 줄어 과부하를 숨긴다. 오픈 몰림은 열린 모델로 잰다.
