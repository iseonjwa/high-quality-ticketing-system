# 대기열 입장 속도를 예매 서비스가 처리할 수 있는 양에 맞추려면 어떤 방법이 있고, 무엇부터 해야 하나

## 질문
11/13 O1 측정에서 대기열이 초당 50명을 들여보냈지만 예매 서비스가 먼저 포화해 Hikari 풀 고갈 500이 수천 건 났다. "처리할 수 있는 만큼만 동적으로 들여보낼 수 있는지 생각해 보자", "적당한 수치를 천천히 찾아가는 과정이 필요하다."

## 짧은 답
- 방법은 셋이다. (A) 고정값을 측정으로 찾기, (B) 예매 서비스 지표를 보고 입장 속도를 자동으로 조절하는 적응형(AIMD, gradient), (C) 입장 속도 대신 "지금 좌석을 고르는 사람 수" 상한(동시 입장 슬롯)을 두기다.
- **먼저 A를 한다.** 30·40·50을 같은 시나리오로 비교해 확정 굿풋(성공한 확정 수)이 가장 큰 값을 고른다. A의 결과가 B·C의 시작값과 상·하한이 되므로 버리는 일이 아니다.
- A로 부족한 경우는 정해 둔다. 회차·공연에 따라 한 명당 비용이 달라지거나, 같은 시각에 여러 회차가 열려 고정값이 맞지 않을 때다. 이때 B(AIMD)를 먼저 보고, C는 대기열 계약을 바꾸는 일이라 대기열 담당과 맞춘 뒤에 본다.
- Hikari 500은 원인이 아니라 증상이다. 서버 CPU가 4코어 모두 찬 상태에서 쿼리가 늦어져 커넥션 5개를 오래 잡고 있었던 것이다. 풀만 키우면 같은 CPU를 더 많은 쿼리가 나눠 쓰게 되어 해결되지 않는다(1-3절).

## 1. 지금 구조

### 1-1. 입장 처리 코드

| 무엇 | 어디 | 동작 |
|---|---|---|
| 설정 | `config-repo/reservation-service.yml` `queue.admit-per-second: 50`, `admission-interval: 500ms`, `entry-token-ttl: 10m` | 초당 입장 수 N은 고정값 하나다 |
| 스케줄러 | `QueueAdmissionScheduler`(500ms 고정 지연) → `QueueAdmissionService.admitOnSale()` | 판매 중인 회차마다 같은 N으로 `admit.lua`를 부른다 |
| 입장 Lua | `reservation-service/src/main/resources/redis/queue/admit.lua` | `lastTick`으로 1초에 한 번만 `admitted = min(admitted + N, seq)`. 만료된 `issued` 기록을 정리한다 |
| 판정 | `AdmissionRule`, `issue-token.lua` | `seq <= admitted`면 READY. 토큰 API를 부르면 `issued`(ZSET, 점수 = 발급 시각)에 넣는다 |
| 예상 대기·폴링 | `PollPolicy` | 예상 대기 = 순번 / N, 다음 폴링 = 예상 대기를 3~10초로 자른 값 + 지터 20% |
| 입장 토큰 소모 | ADR 0053, `#593`(ISE-207) | 선점이 성공하면 입장 토큰을 소모하고 `issued`에서 그 사용자를 지운다 |

알아 둘 성질 네 가지(코드로 확인).

1. **`admitted`는 들어간 사람 수가 아니라 번호표 포인터다.** 줄을 떠난 사람의 번호도 `admitted`를 소모하므로 실제로 들어오는 사람은 N보다 적을 수 있다. 반대로 예매 서비스가 느려져도 `admitted`는 매초 N씩 오른다. 지금 구조에는 되먹임(feedback)이 없다.
2. **N은 회차마다 따로 적용된다.** `admitOnSale()`이 판매 중인 회차를 돌며 각각 N을 준다. 두 회차가 같은 시각에 열리면 예매 서비스에는 2N이 온다.
3. **입장과 실제 부하 사이에 지연이 있다.** `admitted`가 오른 뒤 사용자는 다음 폴링(3~10초)에서 READY를 보고, 토큰 API를 부르고, 좌석을 조회한다. 입장 속도를 바꾼 효과는 약 5~15초 뒤에 예매 서비스에 나타난다(계산값. 폴링 간격과 O1 고민 시간 1~3초로 낸 범위, 측정 안 함).
4. **`issued` 크기는 "토큰을 받고 아직 선점하지 않은 사람 수"다.** ADR 0053 뒤로 선점 성공 시 빠지므로, 좌석 조회를 내는 사람 수에 가깝다. 다만 선점 없이 떠난 사람은 토큰 유효 시간 10분 동안 남는다.

- N 변경 방법: `QueueProperties`는 `@ConfigurationProperties` record이고 `@RefreshScope`가 없다. 설정 서버 값을 바꾼 뒤 재기동 없이 반영되는지는 **확인 못 함**. 측정에서는 재기동하거나 Gateway처럼 `SPRING_APPLICATION_JSON`으로 덮는 방법을 쓸 수 있다(질문 1).
- SA MASTER 3-3(결정 #45 잠정)은 이미 "50명/초는 기준선 측정 전 임시값이고, 포화점 μ와 체류 시간 W를 측정해 역산한다"고 적어 두었다. 이 노트는 그 역산을 실제로 하는 방법이다.

- (예매 서비스 + 예매 DB) / (좌석 조회 + 선점 정상)은 18.5~20.5ms CPU/건이다. 그 구간의 순번 조회·확정 조회 몫까지 들어 있어 **위쪽 한계**로 읽는다.
- 확정 / 토큰 발급은 끔 30%, L512 31~32%(계산값)다. 15,000명이 모두 토큰을 받았지만 약 3분의 1만 확정했다.

### 1-3. 한 명당 비용으로 본 감당량 (계산값, 추정)

- 끔 회차에서 사용자 한 명은 좌석 조회·선점 정상을 평균 약 2.3건 냈다((18,982 + 15,329) / 15,000).
- 한 건 약 19ms(위쪽 한계)라면 들어온 한 명이 예매 서비스 + DB에서 쓰는 CPU는 약 44ms다.
- 4코어에서 Gateway·Kafka·컨테이너 밖·관측 도구·결제가 약 1.8코어를 쓰고 남는 약 2.2코어가 예매 서비스 + DB 몫이다. 포화 직전(사용률 70~80%)을 목표로 하면 약 1.6~1.8코어다.
- 1.6~1.8코어 / 44ms ≈ **초당 36~40명**. 50은 이 추정보다 크다. 다만 포화 상태에서 잰 한 건당 비용에는 500 재시도와 대기로 늘어난 몫이 섞여 있어, 부하가 낮으면 한 건당 비용이 더 작을 수 있다. 그래서 이 숫자는 측정 지점을 고르는 데에만 쓰고, 값은 측정으로 정한다.
- Hikari를 리틀의 법칙(Little's law, 평균 동시 수 = 도착률 × 평균 체류 시간)으로 보면 이렇다. 초당 약 100건이 커넥션을 잡는다고 할 때, 쿼리가 15ms 걸리면 평균 1.5개만 쓴다. CPU 경합으로 쿼리가 50ms를 넘으면 5개가 모두 찬다. 풀 고갈은 CPU 포화의 결과다.
- **변수**: 다른 세션(`seat-stats-analyze`)이 새 회차 좌석 통계 문제(예매 DB 좌석 조회 한 건 12.7~13.5ms)를 고치는 중이다. 이 수정이 배포되면 한 명당 비용이 바뀌어 감당량도 바뀐다. 고정값 측정은 그 수정이 반영된 상태에서 해야 결과가 바로 낡지 않는다(질문 9).

### 2-2. A. 고정값을 측정으로 찾기

- 방법: 같은 O1 시나리오에서 N만 30·40·50으로 바꿔 돌린다. 확정 굿풋이 가장 크고 500이 거의 없는 N을 고른다(3절).
- 지표: 측정 때만 본다. 운영 중에는 아무것도 보지 않는다.
- 실패하면:
  - **값이 낮으면** 서버는 여유가 있는데 대기가 길어진다. 대기 p95는 대략 사용자 수 / N에 비례한다(15,000명이면 N=30에서 약 500초, 50에서 약 300초, 계산값).
  - **값이 높으면** 지금처럼 예매 서비스가 포화해 500과 `error` 사용자가 늘고 확정 비율이 떨어진다.
  - **상황이 바뀌면**(좌석 수가 다른 회차, 통계 수정 반영, 동시에 여러 회차 오픈, 서버 사양 변경) 측정한 값이 맞지 않는다. 그런데도 알려 주는 장치가 없다.
- 구현 비용: 설정 한 줄. 측정 1회에 15~20분, N 하나당 2회.
- 장점: 결과가 그대로 B·C의 시작값과 상·하한이 된다. 발표에서 "측정으로 포화점을 찾았다"는 근거가 된다.

### 2-3. B. 적응형: AIMD

AIMD(Additive Increase, Multiplicative Decrease, 가산 증가·곱셈 감소)는 TCP 혼잡 제어가 쓰는 방식이다. 건강하면 조금씩 올리고, 나빠지면 크게 줄인다.

```
매 P초(제어 주기)마다:
  건강 = Hikari 대기(pending) 최대 == 0
         && Hikari 시한 초과 증가분 == 0
         && 좌석 조회 p95 < 목표(예: 1초)
         && 예매 5xx 비율 < 0.5%
  if 건강:   N = min(N_max, N + a)              # 예: a = 2
  else:      N = max(N_min, floor(N × b))       # 예: b = 0.7
  Redis queue:admitRate 에 N 저장 → admit.lua와 PollPolicy가 이 값을 쓴다
```

- 지표: 대기열 스케줄러가 예매 서비스 **안에서** 돈다. 그래서 Prometheus를 거치지 않고 같은 프로세스의 Micrometer 레지스트리(`hikaricp_connections_pending`, `hikaricp_connections_timeout_total`, `http_server_requests`)를 직접 읽을 수 있다. 수집 지연(5초 scrape)과 Prometheus 장애에 묶이지 않는다.
- 제어 주기 P는 입장 → 부하 지연(5~15초)보다 길어야 한다. 짧으면 아직 효과가 나타나지 않은 상태에서 또 올려 **과잉 입장(overshoot) → 급감 → 다시 증가**를 반복하는 진동이 생긴다. 들여보낸 사람은 되돌릴 수 없으므로 증가 폭 a는 작게, 감소 b는 크게 둔다.
- 실패하면:

| 실패 | 결과 | 대응 |
|---|---|---|
| 지표를 못 읽음 | N을 정할 근거가 없다 | 마지막 N을 유지하지 않고 A에서 잰 안전값으로 내린다 |
| 주기가 지연보다 짧음 | 진동, 500이 주기적으로 튄다 | P ≥ 15초, a 작게. 측정에서 N 시계열을 그려 확인 |
| 다른 부하가 CPU를 씀(오픈 전 공연 상세만으로 2.7~2.9코어) | 입장자 탓이 아닌데 N을 줄인다 | CPU는 함께 쓰므로 줄이는 것이 맞다. 다만 N_min 아래로는 내리지 않는다 |
| 인스턴스가 여러 개 | 각자 자기 Hikari만 본다 | 한 인스턴스만 제어하거나(Redis 락), 인스턴스별 판정을 Redis에서 합친다. 지금은 1개라 해당 없음(질문 8) |
| 여러 회차 동시 오픈 | 회차마다 N이면 합이 커진다 | 전체 예산 N을 회차 수로 나눈다(질문 2) |
| 예상 대기 시간이 흔들림 | `PollPolicy`가 N으로 예상 대기를 낸다. N이 바뀌면 화면의 시간이 들쭉날쭉하다 | 최근 실제 입장 속도의 이동 평균으로 계산(질문 4) |

- gradient 방식: 지연 비율로 N을 연속 조절한다. 예: `N = N × clamp(목표 p95 / 측정 p95, 0.5, 1.2)`. Netflix `concurrency-limits` 라이브러리의 Gradient2는 이 생각을 동시 처리 수 상한에 쓴다. AIMD보다 부드럽게 움직이지만 p95가 시끄러운 지표라(좌석 조회 p95는 회차 좌석 수에도 따른다) 평활화와 계수 조정이 더 필요하다. 설명 비용도 크다. 이 프로젝트에서는 AIMD를 먼저 보고, AIMD가 진동하면 gradient를 비교 후보로 둔다.

### 2-4. C. 동시 입장 슬롯

입장 "속도" 대신 "지금 안에 있는 사람 수"를 제한한다. 리틀의 법칙으로 C = λ × W(W = 토큰 받고 선점할 때까지 걸리는 평균 시간)다.

```
admit.lua 안에서 1초마다:
  active = issued 중 유효한 수 + (READY인데 아직 토큰 안 받은 수)
  admitted = min(admitted + min(N_max, C - active), seq)   # C - active가 0 이하면 이번 초는 입장 없음
```

- 지표: Redis `issued` 크기만 본다. 예매 서비스가 느려지면 사람들이 좌석 선택 단계에 오래 머물고 `issued`가 늦게 빠져 입장이 저절로 줄어든다. 지표 파이프라인 없이 되먹임이 생기는 것이 C의 장점이다.
- 실패하면:

| 실패 | 결과 | 대응 |
|---|---|---|
| 선점 없이 떠난 사람이 `issued`에 10분 남음 | 자리가 묶여 입장이 멈춘다. O1에서 `error`로 끝난 사용자가 7,883~8,463명이었다. 이 사람들이 10분씩 자리를 차지하면 C가 곧 찬다 | "좌석 선택 시간" 제한을 토큰 유효 시간(10분)보다 짧게 둔다(예: 2~3분). 프런트 안내와 정책 결정이 필요하다(질문 6) |
| READY인데 토큰을 아직 안 받은 사람을 못 셈 | 폴링 지연 동안 C를 넘겨 들인다 | `admitted − 발급 누계`를 함께 센다. 발급 누계 카운터가 새로 필요하다 |
| 선점이 실패(409)해도 `issued`에 남음 | 409를 반복하는 사람이 자리를 오래 쓴다 | 의도한 동작이다. 좌석 조회 부하를 내는 사람이기 때문이다 |
| 결제 단계는 세지 않음 | 결제 서비스 부하는 이 상한 밖이다 | 11/13에 결제는 0.10~0.18코어로 작았다. 결제가 병목이 되면 다시 본다 |
| Redis 장애 | 대기열 자체가 멈춘다(지금과 같다) | 기존 대기열 차단기 동작을 따른다 |

- 구현 비용: `admit.lua`에 인자·로직 추가, 발급 누계 키, 선택 시간 제한(Lua·Gateway·프런트), 대기열 계약(`docs/design/queue/contracts.md`) 변경. 대기열 담당 영역이고, 다른 서비스가 따라야 하면 `contract` 이슈다(대전제 11).
- ADR 0015가 이미 "`issued` 크기가 곧 현재 입장 인원이라 입장 속도 역산의 측정값으로 쓴다"고 적어 두었다. C는 그 값을 측정값이 아니라 제어값으로 쓰는 것이다.

|---|---|---|---|

| 1 | **고정값 측정**: N = 50(재현), 40, 30, 각 2회 | 3-1절 판정으로 N* 하나를 고른다 | 끝난 뒤 config-repo 값 변경을 대기열 담당과 맞춘다 |
| 2 | 경계 확인(필요할 때만): N*가 30이거나 40·50이 비슷하면 35·45 또는 25 1회 | 굿풋 곡선의 무릎(knee)을 찾는다 | — |
| 3 | 고정값을 운영값으로 반영하고 결정 기록(SA 3-3·결정 #45 잠정을 대체하는 ADR) | ADR 채택 | 아래 "바꿀 조건" 중 하나가 보이면 4 |

| 5 | 슬롯 방식(C)은 선택 시간 제한 정책이 정해지면 비교 후보로 | — | — |

적응형으로 넘어갈 조건(이것이 보이지 않으면 고정값으로 충분하다).
- 좌석 수나 구역 구성이 다른 회차에서 같은 N*를 썼을 때 500이 다시 나거나, 서버가 눈에 띄게 남는다.
- 같은 시각에 여러 회차가 열리는 시나리오를 다룬다.
- 좌석 통계 수정처럼 한 명당 비용을 바꾸는 변경이 이어져 다시 잴 일이 반복된다.

왜 적응형부터가 아닌가.
- 적응형은 "목표 지표가 무엇인지"(500 0건인지, p95 1초인지)와 "상·하한"을 먼저 알아야 한다. 그 숫자가 1단계에서 나온다.
- 측정 없이 적응형을 넣으면 진동인지, 원래 그런 부하인지 가를 기준이 없다.
- 남은 일정(M4 11/9~11/16)에 비해 1단계는 설정 변경과 측정만으로 끝난다.

### 3-1. 측정 계획

시나리오
- O1 `o1-open-peak.js`, `USERS=15000`, `VUS=500`, `PRE_OPEN_SECONDS=120`, `ENTER_SPREAD_SECONDS=10`, PG 300ms, 측정 모드(샘플링 0.01). 11/13과 같다.
- **`AFTER_OPEN_SECONDS`를 모든 N에서 660초로 맞춘다.** N=30이면 대기열이 비는 데 약 500초(15,000 / 30, 계산값)라 지금 값 420초로는 끝까지 못 간다. 세 N을 같은 길이로 돌려 "대기열이 다 빠졌는가"를 조건에서 없앤다.
- 회차마다 새 15,000석 회차. Gateway 상한 512. k6 결과는 Prometheus로 보내지 않는다(11/13 OOM). 시작 전 Prometheus CPU 50% 미만.
- 순서: 50 → 40 → 30 → 50 → 40 → 30(시간에 따른 서버 상태 변화가 한쪽에 몰리지 않게 번갈아). 11/13 L512 두 회차의 확정 차이는 74건(약 1.6%)이었다. 이보다 작은 차이는 같은 값으로 본다.

판정 지표

| 지표 | 어디서 | 왜 |
|---|---|---|
| **확정 굿풋**: 확정 수 합계, 오픈 ~ 대기열 빔 구간의 초당 확정 | 예매 DB(CONFIRMED, 결제 APPROVED), k6 | 최종 목표. 들인 사람 수가 아니라 끝까지 산 사람 수 |
| 확정 / 토큰 발급(전환율) | 위 / k6 토큰 정상 | 들인 사람 중 얼마나 성공했나. 50에서 30~32% |
| 예매 서비스 500 수, Hikari 대기 최대, 시한 초과 증가분 | k6 `o1_failures`, Prometheus `hikaricp_connections_pending`·`hikaricp_connections_timeout_total` | 포화 신호. 500이 0에 가까워지는 N을 찾는다 |
| `error`로 끝난 사용자, EXPIRED 수 | k6, 예매 DB | 사용자가 겪은 실패 |
| 대기(진입 → 토큰) 중앙값·p95 | k6 | N을 낮춘 대가 |
| 좌석 조회·선점 p95 | k6 | Gateway 응답 시한 3초 대비 여유 |
| 서버 CPU, 예매 서비스·예매 DB CPU | vmstat, docker stats | 1-3절 한 명당 비용 추정 검증 |
| 정합성: SOLD = 확정 좌석, 중복 0, 예매당 승인 2건 이상 0 | 예매·결제 DB | 매번 확인 |

고르는 규칙
1. 정합성이 깨진 회차는 버린다.
2. 예매 서비스 500이 좌석 조회 + 선점 요청의 0.1% 이하이고, 좌석 p95 < 1초인 N만 후보로 둔다.
3. 후보 중 확정 굿풋이 가장 큰 N을 고른다. 굿풋이 같은 수준이면(1.6% 안) 대기 시간이 짧은 쪽(큰 N)을 고른다.
4. 후보가 없으면(30에서도 500이 남으면) 25로 한 번 더 내린다. 그래도 남으면 입장 속도가 아니라 한 명당 비용(좌석 조회 쿼리 등)이 문제라고 보고 그쪽을 먼저 고친다.

확인할 질문(측정으로 답한다)
- N을 30~40으로 낮추면 확정 굿풋이 50보다 같거나 높은가? 전환율이 30%에서 얼마나 오르는가?
- 1-3절 추정(초당 36~40명)은 맞는가? 500이 사라지는 N은 어디인가?
- N을 낮춰도 Gateway CPU(순번 조회 몫)는 그대로인가? 대기 인원이 오래 남아 폴링 총량이 늘지는 않는가?

## 면접 포인트
- "대기열 입장 속도는 어떻게 정했나?" → 처음 50은 임시값이었다. 측정해 보니 예매 서비스가 먼저 포화해 커넥션 풀 고갈 500이 났다. 같은 시나리오에서 입장 속도만 바꿔 확정 굿풋을 비교해 포화점 아래 값을 골랐다. 기준은 처리량이 아니라 끝까지 산 사람 수다.
- "커넥션 풀을 늘리면 되지 않나?" → 풀 고갈은 CPU 포화의 결과다. 리틀의 법칙으로 쿼리가 15ms면 커넥션 1.5개면 되는데, CPU 경합으로 50ms를 넘어 5개가 찼다. 풀을 늘리면 같은 CPU를 더 많은 쿼리가 나눠 써 모두 느려진다.
- "왜 처음부터 동적으로 안 했나?" → 적응형은 목표 지표와 상·하한을 먼저 알아야 하고, 입장과 부하 사이 5~15초 지연 때문에 주기를 잘못 잡으면 진동한다. 고정값 측정이 그 숫자를 준다.
- "AIMD와 동시 수 상한의 차이는?" → AIMD는 지표를 보고 속도를 바꾸는 명시적 되먹임이다. 동시 수 상한은 안에 있는 사람 수를 제한해, 서비스가 느려지면 자리가 늦게 비어 저절로 덜 들어온다(리틀의 법칙). 대신 떠난 사람의 자리를 회수하는 규칙이 필요하다.
