# 503의 Retry-After는 무엇을 기준으로 2초·3초를 정하고, 최적값은 어떻게 찾나

## 질문
Gateway 동시 처리 수 상한 거절은 `Retry-After: 2`, auth-redis 한 번 실패는 3초, 차단기 열림은 5초로 했다. 무엇은 2초, 무엇은 3초로 하는 기준이 무엇인가. 최적화된 수치를 잡으려면 어떻게 하나.

## 짧은 답
- 지금 2초와 3초는 둘 다 **측정 근거가 없다**. 2초는 "그때 bulkhead 거절 1초보다 길게", 3초는 "대기열 최소 조회 간격(`queue.poll-min`)과 같게"로 정한 값이다.
- 근거가 있는 것은 차단기 열림 5초 하나다. 언제 다시 받을지 서버가 알기 때문이다(열림 시간).
- 기준은 세 가지로 세울 수 있다.
  1. 회복 시점을 서버가 아는가.
  2. 거절된 사람이 거절되지 않은 사람보다 빨리 돌아오면 안 된다.
  3. 원인이 같은 거절은 같은 값을 준다.
- 이 기준으로 보면 동시 처리 수 상한도 3초가 맞다. 최적값은 Retry-After를 따르는 부하 시험에서 2·3·5초를 비교해 고른다.

## 1. Retry-After가 실제로 바꾸는 것
동시 처리 수 상한은 줄 세우지 않고 넘치면 바로 거절한다. 처리량의 천장은 장비가 정하고, Retry-After로는 천장이 바뀌지 않는다. Retry-After가 바꾸는 것은 세 가지다.

| 바뀌는 것 | 짧게 주면 | 길게 주면 |
|---|---|---|
| 거절 처리 CPU | 다시 오는 요청이 늘어 거절 비용이 늘어난다 | 줄어든다 |
| 몰림이 끝난 뒤 빈 자리 | 빨리 채워진다 | 최대 Retry-After 동안 자리가 놀 수 있다 |
| 누가 자리를 얻나 | 거절된 사람이 더 자주 다시 와서 자리를 더 많이 가져간다 | 공평에 가깝다 |

## 2. 거절 비용으로 본 크기 (계산값)
- 8차 R0 측정: 받은 요청 한 건 1.06ms, 거절 한 건 0.02~0.08ms CPU(`open-peak-scenarios.md` 배포 서버 8차).
- 계산: 거절된 사용자 1만 명이 다시 시도한다고 하자. 프론트는 Retry-After에 0~20% 흔들림(jitter)을 더하므로 평균 간격은 약 1.1배다.

| Retry-After | 다시 오는 요청 | 거절 CPU(0.08ms 기준) | 4 vCPU 중 비율 |
|---|---|---|---|
| 2초 | 약 4,500/s | 약 0.36코어 | 약 9% |
| 3초 | 약 3,000/s | 약 0.24코어 | 약 6% |
| 5초 | 약 1,800/s | 약 0.15코어 | 약 4% |

- H1(거절을 맨 앞으로 옮김) 덕분에 거절이 싸져서, 2초와 3초의 CPU 차이는 약 3%p다. CPU만으로는 승부가 나지 않는다. 1만 명이라는 숫자는 가정이고, 측정하지 않았다.

## 3. 세 가지 기준

| 기준 | 내용 | 적용 |
|---|---|---|
| ① 회복 시점을 아는가 | 안다면 그 시점을 준다. 더 짧으면 거절될 요청이 확실히 온다 | 차단기 열림 → 열림 시간 5초 |
| ② 정상 속도보다 빨리 오지 않게 | 거절된 사람이 정상 사용자보다 자주 오면, 거절이 오히려 더 공격적인 재시도를 만든다 | 대기열 폴링은 3~10초 간격이다. 그러니 3초 이상 |
| ③ 원인이 같으면 같은 값 | ADR 0050에서 bulkhead 거절은 "Gateway 자기 과부하"로 정했다. 동시 처리 수 상한도 같은 원인이다 | 상한 거절 = bulkhead 거절 = 3초 |

## 4. 코드로 확인한 문제 (②번 위반)
- `frontend/src/pages/queue/queueAdmission.ts`는 폴링이 실패하면 `queryRetryDelay(failures, error, random, MIN_POLL_MILLIS)`로 기다린다.
- `frontend/src/api/queryClient.ts`의 `queryRetryDelay`는 Retry-After가 있으면 그 값을 그대로 쓰고, 최소 간격(`minBaseMillis`, 3초)은 Retry-After가 없을 때만 지킨다.
- 그래서 지금 상한 거절(2초)을 받은 대기자는 2.0~2.4초 뒤에 다시 폴링한다. 정상 최소 간격 3초보다 빠르다.
- 뒤쪽 대기자는 서버가 10초 간격(`nextPollAfterMillis`)을 줬어도, 한 번 거절되면 2초 뒤에 온다. 다섯 배 빠르다.
- Gateway 값을 3초로 맞추면 첫 문제는 사라진다. 두 번째 문제는 프론트가 "Retry-After와 직전 `nextPollAfterMillis` 중 큰 값"을 써야 사라진다.

## 5. 최적값을 찾는 방법
- **목표를 먼저 정한다.** 장비 천장 안에서 "사용자가 성공할 때까지 걸린 시간(p50·p95)"을 줄이되, 거절 처리 CPU가 서버 CPU의 5%p를 넘지 않게 한다(5%p는 [가정]).
- **실험 설계**

| 항목 | 값 |
|---|---|
| 부하 모델 | 닫힌 모델. 사용자 N명이 응답을 받으면 다음 요청을 보낸다. 거절되면 Retry-After × (1 + 0~20%)를 기다린다. 지금 k6가 Retry-After를 따르는지는 확인하지 못했다 |
| 비교 | Retry-After 2·3·5초. 상한 64와 나머지 설정은 같게 둔다 |
| 지표 | 굿풋(초당 성공), 들어온 요청 ÷ 새 요청(재시도 증폭), 서버 CPU, 성공 p95, 사용자별 첫 성공까지 걸린 시간, 몰림이 끝난 뒤 거절률이 0으로 돌아오는 시간 |
| 고르는 규칙 | 굿풋이 같다면(작업 보존형이라 거의 같을 것이라 예상하지만 확인할 질문이다), 사용자 대기 시간이 가장 짧으면서 거절 CPU가 상한 안인 가장 짧은 값 |

- 반복은 단계마다 3회 이상이다. 한 번 잰 값의 차이는 30초 평균 표본 오차(8차에서 약 2.5%p)와 같은 크기일 수 있다.

## 6. 지금 권하는 것
1. 동시 처리 수 상한 Retry-After를 2초에서 3초로 바꾼다. 기준 ②·③에 맞는다. 측정 전 기본값이다.
2. 프론트 대기열 폴링은 Retry-After와 직전 `nextPollAfterMillis` 중 큰 값을 쓴다. 프론트 담당 확인이 필요하다.
3. 5절 실험은 상한 64·96·128 반복 측정 때 같이 돌린다.
