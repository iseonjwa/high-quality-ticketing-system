# 좌석 조회 1차 CPU가 11/11 76%에서 11/13 340%로 늘었다는 비교는 무엇부터 확인해야 하나

## 질문
담당 팀원이 좌석 조회 1차(P4a)를 동시 처리 상한 없이 쟀더니 CPU가 11/11 76%에서 11/13 340%로 늘었다고 했다. 두 측정 사이의 세팅 차이는 Gateway로 보이는데, 왜 이런 결과가 나왔나. 추가로 받아야 할 지표는 무엇인가.

## 짧은 답
- 원인은 아직 확인 못 함이다. 다만 저장소 기록으로 보면 Gateway 변경만으로 5배를 설명하기 어렵고, 두 숫자가 같은 조건의 값인지부터 확인해야 한다.
- 11/11 기록(`docs/design/infra/open-peak-scenarios.md` "배포 서버: S1 좌석 조회·B1-d")에도 1차 초당 50건 한계 실행의 CPU가 postgres-reservation 약 210%, reservation-service 약 95%, gateway 약 45%로 합계 약 350%다. 340%와 거의 같다. 76%라는 값은 저장소 기록에서 찾지 못했다.
- 1차는 처리량 상한이 초당 약 46~47건이다. 상한 아래(10~30건)와 상한 근처(50건)는 CPU가 선형으로 늘지 않는다. postgres가 포화하면 CPU가 한꺼번에 오른다.
- 그래서 먼저 볼 것은 "같은 초당 요청, 같은 CPU 단위(서버 전체 합인지 컨테이너 하나인지), 같은 구간(평균인지 최대인지)"이다. 팀이 정한 판정 기준대로 성공 한 건당 CPU로 바꿔 비교한다.

## 11/11과 11/13의 차이 (저장소에서 확인한 것)
| 항목 | 11/11 측정(배포 `74f91ffb`) | 11/13(지금 main + 덮어쓰기) | CPU 영향 예상 |
|---|---|---|---|
| reservation-service 이미지 | `74f91ffb`의 1차 | `08b08e6`(#565, 1차·P4b 직전). 차이는 결제 토큰 키 설정뿐이라고 기록됨 | 거의 없음 |
| Gateway 동시 처리 상한 | 없음(#488은 11/11 18:44 머지, 측정은 10:16~14:10) | 덮어쓰기로 끔(#571)이면 11/11과 같다 | 끔이면 차이 없음. 64로 켜졌다면 초당 50건에서 거절이 생긴다 |
| Gateway auth-redis | 건수 창 20, 느린 호출 50ms | 시간 창 10초, 느린 호출 100ms, bulkhead 50(#487) | 작음 |
| Gateway 요청 로그 | 전부 | 문제 요청만(#501) | 오히려 줄어야 함 |
| Gateway 메모리 | 768m | 1024m, 직접 메모리 상한 128m(#488) | 확인 필요. 약 850KB 응답을 많이 동시에 들고 있으면 직접 메모리·GC 영향 가능 |
| 다른 서비스 | — | 결제 기동 웜업(#525), 대사 RC-1~6 켬(#530), 서비스 발견 5초(#526) 등 | 부하 없을 때 기본 CPU를 올릴 수 있음 |

## 받아야 할 지표
| 지표 | 왜 |
|---|---|
| 두 실행의 초당 요청(RATE), 30초 동안 200 건수, 실패 건수(503·504) | 분모가 같은지 본다. 성공 한 건당 CPU를 계산한다 |
| CPU를 컨테이너별로(gateway, reservation-service, postgres-reservation, kafka, 나머지) | 340%가 어디서 늘었는지 본다. Gateway 차이라면 gateway 칸만 커야 한다 |
| 76%·340%가 서버 전체 합인지, 한 컨테이너인지, 평균인지 최대인지 | 단위가 다르면 비교 자체가 성립하지 않는다 |
| 부하 없는 1분의 컨테이너별 CPU(11/13 기준선) | 다른 서비스 변경으로 기본값이 올랐는지 본다 |
| p95·중앙값, hikari 커넥션 대기 최대 | 11/11 표와 같은 칸으로 비교한다. 포화했는지 알 수 있다 |
| Gateway: `gateway_in_flight_limit` 유무(상한이 정말 꺼졌는지), JVM GC 멈춤, 힙·직접 메모리 | Gateway가 원인인지 직접 확인한다 |
