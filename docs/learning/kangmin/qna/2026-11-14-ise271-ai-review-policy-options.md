# 남은 기간 PR마다 AI 리뷰를 남길지, 계약 경계 PR을 상대 담당이 볼지 어떻게 정하나(ISE-271)

## 질문
ISE-271을 자세히 설명하고, 댓글 초안의 결정(1번 조건부 찬성, 3번 기한 붙은 찬성)을 왜 골랐는지 설득해 달라. 다른 대안도 함께.

## 짧은 답
- 문제는 검증을 안 한 것이 아니라 **검증 흔적이 PR에 없다**는 것이다. 머지된 PR 313개 중 GitHub 리뷰가 남은 것은 12개다(ISE-271 본문).
- 1번은 "모든 PR에 본문 한 줄(최소형), 위험 PR에만 코멘트 게시"를 추천한다. 흔적은 전부 남기고, 비용은 위험이 큰 곳에만 쓴다.
- 3번은 "상대 담당 확인 + 반나절 넘으면 사후 확인"을 추천한다. 계약 경계는 혼자 판단하면 틀리기 쉬운 곳이라 상대 확인이 필요하다. 다만 승인 대기로 측정 일정이 막히면 안 된다.

## 자세히

### 1. 무엇을 정하나
| 번호 | 안 | 상태 |
|---|---|---|
| 1 | PR마다 AI 리뷰를 PR 코멘트로 남긴다(작성 세션과 다른 세션, `script/ai-review.sh <PR> --post`). 지적마다 답글로 수용·거부, 반영 커밋 SHA. 최소형은 PR 본문 한 줄 | 찬반 받는 중 |
| 2 | CodeRabbit | 하지 않기로 함(시간당 한도, 우리 설계를 모르는 일반 리뷰) |
| 3 | `contract` 이슈가 걸린 PR은 상대 담당이 승인하거나 코멘트 | 찬반 받는 중 |

규칙은 `docs/guides/git-workflow.md` 5절의 "필수 승인 0명, AI 검증 + CI가 관문"이다. 심사에서 "AI가 만든 코드를 누가 어떻게 검증했나"를 물으면, 지금은 판단 기록과 PR 본문에 흩어진 흔적을 모아 보여 줘야 한다.

### 2. 1번 선택지 비교
| 안 | 흔적 | 비용 | 위험 |
|---|---|---|---|
| A. 지금처럼(규칙 없음) | 판단 기록·일부 PR 본문에 흩어짐 | 없음 | 심사 질문에 PR 단위로 답하기 어렵다 |
| B. 최소형만(모든 PR 본문 한 줄) | 모든 PR에 "도구·지적 수·수용·거부" | 리뷰 실행 + 한 줄 | 지적 내용 자체는 PR에 안 보인다 |
| **C. 최소형 전부 + 위험 PR만 코멘트(추천)** | 모든 PR에 한 줄, 위험 PR은 지적·답글·SHA까지 | 위험 PR만 답글 비용 | "위험 PR" 경계가 사람마다 다를 수 있다 |
| D. 모든 PR 코멘트 | 가장 많음 | 가장 큼 | 문서·측정 PR까지 답글을 달다 검증보다 형식에 시간이 간다 |
| E. 모든 PR Claude + codex 둘 다 | 가장 많음 | D의 두 배 | 발표 직전 PR이 몰리면 리뷰가 머지를 막는다 |

C를 고른 이유:
- **PR 양**: 11/12 하루에 dev로 머지된 PR이 47개였고, 그중 문서 PR이 17개다(`gh pr list --state merged`로 셈). D·E는 이 양에 답글 비용을 곱한다. 리뷰 한 번에 걸리는 시간은 재지 않았다(확인 못 함).
- **위험의 쏠림**: 이 프로젝트에서 실제로 문제가 된 곳은 동시성(선점 매수 한도, 멱등키 연타), 결제, Gateway 시한, 서비스 간 계약이었다. 문서·측정 스크립트 PR은 틀려도 다음 PR로 고치면 된다.
- **도구 차이**: #577에서 Claude와 codex가 짚은 곳이 달랐다(ISE-271 참고 절). 그래서 둘 다 돌리는 비용은 계약·동시성 PR에만 쓴다.
- **심사 대응**: B만 해도 "모든 PR에 검증 흔적"이라는 답은 된다. C는 대표 사례로 보여 줄 "지적 → 거부 → 판단 기록" 흐름을 위험 PR에서 얻는다.

감수한 점: 위험하지 않다고 본 PR의 지적 내용은 PR에 남지 않는다. "위험 PR" 목록이 흐려질 수 있어 경로 기준(예: `*/seathold/**`, `payment-service/**`, `gateway/**`, `contract` 라벨)으로 적어야 한다.

바꿀 조건: 위험하지 않다고 본 PR에서 사고가 나면 D로 넓힌다. 리뷰 때문에 머지가 하루 넘게 밀리면 B로 줄인다.

### 3. 3번 선택지 비교
| 안 | 장점 | 대가 |
|---|---|---|
| A. 지금처럼(작성자가 머지하고 알림) | 빠르다 | 계약을 혼자 해석하다 틀린다(#526, #483은 리뷰 전에 머지하고 사후에 알림) |
| B. 상대 승인 필수 | 가장 안전 | 상대가 측정·발표 준비 중이면 PR이 멈춘다. GitHub 보호 규칙을 바꿔야 한다 |
| **C. 상대 확인 + 반나절 넘으면 사후 확인(추천)** | 확인 흔적이 남고 일정이 막히지 않는다 | 사후 확인에서 문제가 나오면 되돌리는 PR이 생긴다 |
| D. 상대 대신 다른 AI 세션이 계약 문서와 대조 | 사람 시간이 안 든다 | 상대 서비스의 숨은 가정(예: 예외 처리 범위)을 AI가 모른다. ISE-207에서 영은 님이 `RuntimeException` 범위를 다시 짚은 일이 그 예다 |

C를 고른 이유:
- 계약 경계는 "내 쪽은 맞는데 상대 쪽 가정과 어긋나는" 버그가 나는 곳이다. 상대 담당만 그 가정을 안다.
- 필수 승인(B)은 지금 보호 규칙(필수 승인 0명)과 다르고, 마감 주간에 병목이 된다.
- 반나절 기한은 지금까지 해 온 "먼저 머지하고 이슈에 사후 확인 요청" 흐름을 규칙으로 적은 것이다. 새 비용이 거의 없다.

감수한 점: 사후 확인에서 문제가 나오면 dev에 이미 들어간 코드를 고쳐야 한다. main 반영(배포) 전에 사후 확인이 끝났는지만 보면 배포 서버까지는 가지 않는다.

바꿀 조건: 사후 확인에서 되돌림이 두 번 넘게 생기면 B로 바꾼다.

## 이 프로젝트에서는
- 리뷰 스크립트: `script/ai-review.sh <PR> [--post] [--engine claude|codex]`(PR 머리 커밋을 임시 worktree로 꺼내 읽기 전용으로 리뷰)
- 규칙 정본: `docs/guides/git-workflow.md` 5절, `docs/guides/ai-code-review.md` 7절
- 계약 이슈 절차: `docs/guides/contract-issues.md`

## 면접 포인트
- "리뷰 승인 없이 어떻게 품질을 지켰나": 필수 승인 대신 CI와 다른 세션의 AI 리뷰를 관문으로 두고, 위험 PR은 두 도구로 교차 리뷰했다. 지적마다 수용·거부와 반영 커밋을 남겨 검증을 추적할 수 있게 했다.
- "모든 PR을 똑같이 리뷰하지 않은 이유": 리뷰 비용을 위험이 쏠린 곳(동시성·결제·계약)에 쓰고, 나머지는 흔적만 남겼다. 바꿀 조건을 미리 정했다.
