# JVM 프로파일러가 5%로 본 요청 로그 비용이 왜 실제로는 서버 CPU 12%p였나, 같은 날 대조군으로 운영 설정 효과를 어떻게 확인하나

## 질문
TIL 25편 소개글 1번("요청 로그를 끄자 서버 CPU가 처음으로 90% 아래로 내려갔습니다. JVM 프로파일러가 5%로 본 비용이 왜 프로세스 밖에서 더 컸는지, 같은 날 대조군으로 운영 설정의 효과를 확인한 과정을 정리했습니다.")을 고른 뒤, 소개글이 던지는 두 질문에 답해 달라고 함.

## 짧은 답
- 프로파일러(JFR)는 **JVM 안의 메서드**만 표본으로 봅니다. 요청 로그 한 줄의 비용은 JVM 안(문자열을 만들어 표준 출력에 쓰기)보다 **JVM 밖**(컨테이너 로그 처리, 로그 수집기, 커널)에서 더 많이 들었습니다. 그래서 JFR은 5.2%로 봤지만 끄자 서버 CPU가 초당 1,000건에서 78% → 66%로 내려갔습니다.
- 같은 설정도 날마다 CPU가 6–9%p 달랐습니다. 그래서 운영 설정(B: 실패·느린 요청만 남김)과 "끔"을 **같은 날, 같은 배포에서 번갈아 두 번씩** 재서 비교했습니다. 초당 1,500건에서 78.5% 대 79.1%로 같은 효과로 봤습니다.

## 자세히

### 1. 프로파일러 사각지대
| 보는 도구 | 보이는 것 | 보이지 않는 것 |
|---|---|---|
| JVM 프로파일러(JFR) | 메서드별 CPU, 할당 | 커널, 다른 프로세스, 컨테이너 런타임 |
| 컨테이너별 CPU | 서비스·수집기별 몫 | 컨테이너 밖 데몬 |
| 서버 전체 CPU | 모든 몫의 합 | 어디에 쓰였는지 |

로그를 끈 전후의 몫(원고 2절, 같은 날 측정):
- 게이트웨이 컨테이너 CPU: 114% → 111%(100% = 1코어). 거의 그대로
- 로그 수집기: 22% → 14%
- 가장 많이 준 곳: 컨테이너 밖 호스트 쪽(Docker로 추정, 호스트 프로세스별로는 재지 않아 확인 못 함)

교훈: 프로세스 안 프로파일러가 작게 본 비용이 실제로도 작은지는 **서버 전체 → 컨테이너별 → 프로세스 안** 순서로 나눠 봐야 압니다. 위에서부터 나누지 않으면 "JFR 5%니까 로그는 원인이 아니다" 같은 결론이 나옵니다.

### 2. 같은 날 대조군
| 질문 | 쉬운 방법 | 고른 방법 | 감수한 점 |
|---|---|---|---|
| 운영 설정이 끔과 같은 효과를 내나 | 전날 끔 결과와 비교 | 같은 날 B → 끔 → B → 끔 번갈아 두 번씩 | 측정 시간이 두 배 |
| 거절 한 건은 얼마인가 | 포화 부하에서 평균을 나눔 | 포화 전 부하에서 거절 많음(상한 1)·없음(상한 1,000)을 짝지어 풂 | 실제 몰림과 다른 조건이라 한도로 쓰지 않음 |

- 번갈아 재는 이유: 시간에 따라 바뀌는 조건이 한쪽 설정에만 몰리지 않게 하려는 것입니다(무엇이 날마다 다르게 했는지는 확인 못 함).
- 판정을 미리 정함: 측정 전에 "2–4%p 차이는 보류"로 정했습니다. 초당 1,000건에서 B가 끔보다 2.9%p 높았는데, 이 범위이고 30초 평균 하나의 표본 오차와 같은 크기라 "가리지 못함"으로 남겼습니다.
- 거절 비용: "게이트웨이 CPU = 바탕 + 받은 수 × a + 거절 수 × r"을 풀어 a = 1.06ms, r = 0.02–0.08ms. 거절을 Netty 단계로 더 앞당겨도 아낄 몫은 서버 CPU의 약 0.5%로 계산돼 하지 않기로 했습니다.

## 이 프로젝트에서는
- 운영 요청 로그는 B 방식(`request-log.mode: problems`, ADR 0052 채택): 5xx, 클라이언트가 끊은 요청, 200ms 이상 걸린 요청만 남깁니다. 4xx는 오픈 순간 정상 업무 거절이 가장 많아 넣지 않았습니다.
- 측정 기록: `docs/design/infra/open-peak-scenarios.md` 7차(H1·H2)·8차(P/O·R0), `docs/context/s-r0-prep-2026-11-12.md`(git 제외)
- 글: TIL 25편 원고 `docs/til/til25-draft.md`(git 제외) 2절

## 면접 포인트
- Q. 프로파일러에 5%로 나온 걸 왜 의심했나? → 서버 전체 CPU 변화와 컨테이너별 몫을 함께 봤기 때문입니다. JFR은 JVM 밖(컨테이너 로그, 수집기, 커널)을 보지 못합니다.
- Q. 하루 차이로 6–9%p가 흔들리는데 효과를 어떻게 믿나? → 같은 날·같은 배포에서 번갈아 두 번씩 재고, 같은 설정 두 번 차이(1.3%p 이하)보다 큰지만 효과로 봤습니다. 보류 범위는 측정 전에 정했습니다.
