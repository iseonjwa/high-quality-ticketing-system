# 대기열 입장 속도를 뒤쪽 여유에 따라 동적으로 조절하면 어떨까

## 질문
1. 전체 CPU 부하와 뒤에서 처리할 양을 보고, 여유가 있으면 빨리, 없으면 천천히 들여보내도록 대기열 입장 속도를 동적으로 정하면 총 처리 속도가 나아지고 앞에서 생기는 장애도 줄지 않을까.
2. "대기열 진입 초당 최대: 균일 353 / Synthetic 2,792(약 7.9배)"를 자세히 설명해 달라.

## 1. 입구 몰림 7.9배는 어떻게 나온 숫자인가
- **센 것**: k6 원자료(`C:\Users\Ptah\ise264-results\o1-open-peak-*-raw.csv.gz`)에서 `api=queue_enter` 요청을 초 단위로 묶어 센 최댓값이다. 응답 코드와 상관없이 "그 1초에 보낸 진입 요청 수"다. 353 ÷ 2,792가 아니라 2,792 ÷ 353 ≈ 7.9(계산값).
- **균일이 353인 이유**: 3,000명이 오픈 뒤 1~11초 사이에 고르게 진입한다(`uniformProfile`, `ENTER_SPREAD_SECONDS` 10). 평균 초당 약 300명이고, 무작위라 가장 많은 1초가 353이었다. 사람마다 진입은 1번이다.
- **Synthetic이 2,792인 이유**
  - 2,500명이 오픈 전에 와서 기다리다 오픈 직후 누른다. 오픈 1초 안에 1,423명, 3초 안에 2,308명이 진입했다(`o1-synthetic-3000.csv`의 `arrive_s`·`enter_delay_ms`).
  - 진입을 여러 번 누른다(연타). 1번 1,678명, 2번 660, 3번 269, 4번 154, 5번 70. 연타는 `http.batch()`로 거의 동시에 나간다.
  - 그래서 진입 요청 합계가 균일 3,016건, Synthetic 5,614건(201 2,831 · 중복 진입 200 1,267 · 503 1,516)이고, 그 대부분이 오픈 직후 1~2초에 몰렸다.
- **뜻**: 실제 티켓 오픈처럼 "정각에 일제히, 그것도 여러 번 누른다"를 넣으면 입구 순간 부하가 8배 가까이 된다. 503 1,516건은 모두 이 순간에 Gateway 상한 64가 거절한 것이고, 사용자는 3초 뒤 다시 와서 결국 2,831명 모두 진입했다.

## 2. 동적 입장 속도: 좋은 방향이고, 효과가 나는 곳과 안 나는 곳이 갈린다

### 지금 방식
- 고정 속도: 0.5초마다 Lua로 `admitted = min(admitted + N, seq)`, N은 초당 50명(`QueueAdmissionScheduler`, ADR 0015, `config-repo/reservation-service.yml:50`).
- SA 3-3은 이 값을 "선점 포화 처리량에서 리틀의 법칙으로 역산"하게 되어 있다. 한 번 계산해 고정하는 정적 방식이다.

### 제안의 정체
뒤쪽 상태를 보고 입장 속도를 바꾸는 **피드백 제어(적응형 입장 제어, adaptive admission control)**다. 네트워크의 TCP 혼잡 제어(AIMD: 여유 있으면 조금씩 늘리고 막히면 크게 줄임)나 서비스 메시의 적응형 동시성 제한과 같은 계열이다.

### 오늘 숫자로 본 기대 효과
| 구간 | 오늘 관측 | 동적 입장이면 |
|---|---|---|
| 오픈 뒤 15~70초 | 호스트 CPU 0.99, Hikari 대기, 거절이 모두 이 구간(그림 `host-cpu-122-123.png`, `rejected-rate-122-123.png`) | 속도를 **낮춰** 뒤쪽 포화를 줄인다 → 거절·지연 감소(추정) |
| 70초 뒤 | 거절 0, CPU 여유. 그런데 3,000명 ÷ 50 = 60초라 줄은 거의 비어 있다 | 올릴 대상이 없다 |
| 더 큰 줄(예: 3만 명) | 측정 안 함 | 여유 구간에 속도를 **올려** 대기 시간을 줄인다(추정) |

- 오늘 규모(3,000명)에서는 "빨리 들여보내기"보다 **"막힐 때 늦추기"** 효과가 주로 날 것으로 본다. 총 처리 시간은 비슷하거나 조금 길어지고, 거절과 p95가 줄어드는 쪽이다(추정).

### 효과가 나지 않는 곳: 앞에서 생기는 장애
- 오늘 Synthetic의 입구 503 1,516건은 **대기열에 들어가기 전**(진입 요청)에서 났다. 입장 속도는 진입 뒤의 일이라 이 거절은 줄지 않는다.
- 입구 몰림은 다른 손잡이로 다룬다: Gateway 경로별 상한(진입 API는 가벼우니 따로), 진입 연타를 클라이언트에서 막기(버튼 잠금), 진입 처리 자체를 더 싸게(Lua 한 번).

### 무엇을 신호로 쓸까
| 신호 | 장점 | 단점 |
|---|---|---|
| 현재 입장 인원(발급된 유효 토큰 수, `#620` 지표) | 같은 서비스 안에서 바로 읽는다. SA 3-3의 `L_max`와 바로 연결 | 무거운 사용자·가벼운 사용자를 구분 못 한다 |
| 선점 p95·Hikari 대기(reservation 내부) | 실제 병목을 직접 본다 | 신호가 늦고(수 초) 흔들린다 |
| 호스트 CPU | 전체를 본다 | 다른 서비스 부하까지 섞인다, 서비스가 장비 지표에 기대게 된다 |

- 가장 단순한 형태는 **속도 대신 "동시 입장 인원 상한"**이다. 유효 토큰 수가 `L_max` 아래일 때만 들여보낸다. 사람이 결제를 끝내고 나가면 자리가 나서 자동으로 속도가 맞춰진다(닫힌 고리). 이것도 SA 3-3의 `L_max = μ / r`과 같은 식에서 나온다.

### 대가와 위험
- 흔들림(진동): 신호가 늦으면 늘렸다 줄였다를 반복한다 → 변경 폭 제한, 최소·최대 속도, 평활(이동 평균)이 필요하다.
- 예상 대기 시간 안내가 부정확해진다(지금은 순번 ÷ 50으로 계산할 수 있다).
- 공정성은 그대로다(순번 순서는 바뀌지 않고 속도만 바뀐다).
- 대기열은 영은님 담당이라 바꾸려면 `contract` 이슈와 ADR이 필요하다.

### 근거를 만드는 방법(적용 전)
- 입장 속도를 30·50·80으로 고정해 같은 O1을 재면 "속도 대비 확정·p95·거절" 곡선을 얻는다. 그 곡선이 꺾이는 점이 동적 제어의 목표점이고, 고정 50이 그 점에서 얼마나 떨어져 있는지가 동적 입장의 기대 효과다(11/14 PR `#611`에서 입장 속도 덮어쓰기 파일이 빠져서 PR로 다시 추가해야 한다).

## 정리
- 앞(입구) 장애는 입장 속도로는 못 줄인다. 뒤(선점·결제) 포화와 지연은 줄일 수 있다.
- 오늘 규모에서는 "막힐 때 늦추기"가 주효과, 큰 줄에서는 "여유 있을 때 당기기"까지 효과가 난다(추정).
- 구현은 "동시 입장 인원 상한(닫힌 고리)"이 가장 단순하고, 근거는 입장 속도 고정값 비교 측정으로 만든다.
