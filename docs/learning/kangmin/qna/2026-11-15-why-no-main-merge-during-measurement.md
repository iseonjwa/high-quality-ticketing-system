# 배포 서버 측정 중에는 왜 main 머지를 막아야 하나

## 질문
S3(dev → main 뒤 재측정) 전까지 main 머지를 금지하는 이유를 자세히 알려 달라.

## 답
### 1. main 머지 = 배포다
- 이 프로젝트는 main에 머지되면 GitHub Actions가 이미지를 GHCR에 올리고, Jenkins가 배포 EC2에 반영한다(ADR 0044). 사람이 따로 배포 버튼을 누르지 않는다.
- 그래서 누군가 dev → main PR을 머지하는 순간, 측정 중인 서버의 컨테이너가 새 이미지로 다시 뜬다.

### 2. 측정 도중 배포가 일어나면 생기는 일
| 일 | 결과 |
|---|---|
| 컨테이너 재시작 | 진행 중이던 요청이 끊기고 503·연결 오류가 생긴다. 이 오류는 시스템 성능이 아니라 배포 때문이다 |
| JVM이 다시 차가워짐 | JIT·커넥션 풀·캐시가 비어 첫 몇 분 지연이 크다. "데운 서버" 조건이 깨진다 |
| 서비스 발견 지연 | 다시 뜬 뒤 Gateway가 새 인스턴스를 알기까지 503 구간이 있다(ISE-244, 갱신 주기 5초로 줄였지만 0은 아니다) |
| 측정 모드 덮어쓰기 해제 | 배포 스크립트가 운영 compose로 다시 띄우면 측정 모드 설정(`compose.measure.yml`, Mock PG 지연 등)이 사라질 수 있다 |

### 3. 오늘 측정이 특히 민감한 이유
- **두 O1을 같은 환경에서 재야 비교가 된다.** 판정 기준 V3(`synthetic-data.md` 5-0)은 "O1 균일과 O1 Synthetic 사이에 재시작·배포가 없음"이다. 사이에 배포가 끼면 두 실행을 **둘 다** 다시 재야 한다(한쪽만 다시 재면 같은 환경이었다는 증명이 안 된다). O1 한 번이 약 25분이라 최대 약 55분이 날아간다.
- **main과 dev의 서버 코드가 다르다.** 지금 main(`e109c11c`)에 없는 `#609`(선점 리팩터링·접수형 소비자), `#620`(대기열 지표), `#627`(대기열 재진입 규칙)이 dev에 있다. 측정 도중 배포되면 앞 실행은 옛 코드, 뒤 실행은 새 코드가 되어 "무엇 때문에 숫자가 달라졌나"를 가를 수 없다.
- **오늘 dev에 `#627`이 막 들어왔다(16:21).** 기능이 들어오면 누가 "main에도 올리자"며 dev → main PR을 열기 쉬운 시점이다. 그래서 시작 알림에 명시한다.
- Jenkins 잡을 우리가 끌 수 있는지 확인하지 못했다(C8, 11/13에는 콘솔 접근이 없었다). 막을 수 있는 수단이 사실상 팀 공지뿐이다.

### 4. 왜 "S3 전까지"인가
- S3는 일부러 dev → main을 머지해 새 코드로 다시 재는 단계다. 그때는 main 기준 측정(S1·S2·S2b)이 모두 끝나 있으므로, 배포가 앞 측정을 망치지 않는다.
- 같은 날, 같은 발생기 커밋, 같은 시나리오로 재면 차이를 코드 변경(`#609`·`#620`·`#627`) 탓으로 좁힐 수 있다.

## 선택지 비교
| 선택지 | 장점 | 대가 |
|---|---|---|
| 측정 중 main 머지 금지 공지(지금) | 바로 할 수 있다 | 공지를 못 본 사람이 머지하면 막을 수단이 없다 |
| Jenkins 잡 잠시 끄기 | 확실히 막는다 | 콘솔 권한이 없다(배포 담당 필요) |
| 측정 전에 dev → main 먼저 | 한 번만 재면 된다 | main 기준 결과를 잃어 `#609` 등의 영향을 가를 수 없다(11/14 거부한 안) |

## 한 줄 요약
main 머지는 곧 배포라서 측정 도중에 끼면 재시작·식은 JVM·코드 변경이 숫자에 섞이고, O1 두 번을 통째로 다시 재야 한다. 그래서 main 기준 측정이 다 끝나는 S3까지 막는다.
