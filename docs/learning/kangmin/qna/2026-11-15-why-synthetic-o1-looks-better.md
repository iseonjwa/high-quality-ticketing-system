# 오픈 직후에 더 몰리는 Synthetic O1이 왜 균일 O1보다 지표가 좋게 나왔나

## 질문
균일 모드와 Synthetic 모드가 제대로 설정된 것이 맞나? 현실에 가까운 Synthetic이면 요청이 오픈 직후에 몰릴 텐데, 왜 오히려 지표가 좋게 나왔나.

## 답 한 줄
**입구(대기열 진입)에서는 Synthetic이 8배 더 몰렸다. 직관이 맞다.** 그런데 대기열이 초당 50명씩만 들여보내서 그 뒤 부하는 두 모드가 비슷하다. 그 뒤에서 갈린 것은 **좌석 고르는 방식**이다. 균일은 사용자의 70%가 앞쪽 10% 좌석을 노리게 되어 있어 좌석 충돌(409)이 48%였고, Synthetic은 구역별로 흩어져 12%였다. 충돌이 재조회(약 830KB 응답)와 재선점을 부르고, 그것이 Gateway 칸과 DB를 채웠다.

## 1. 설정 확인(코드 근거, `loadtest/k6/scenarios/o1-open-peak.js`)
| 항목 | 균일(`uniformProfile`, 155행) | Synthetic(`csvProfile`, 176행 + `o1-synthetic-3000.csv`) |
|---|---|---|
| 대기열 진입 시각 | 3,000명 전원이 **오픈 +1~11초 사이에 고르게**(`ENTER_SPREAD_SECONDS` 10) | 2,500명이 오픈 전 도착. 진입은 **1초 안 1,423명, 3초 안 2,308명**, 10초 안 2,433명. 진입 안 하는 사람 169명 |
| 진입 연타 | 1번 | 1번 1,678명, 2번 660, 3번 269, 4번 154, 5번 70 |
| 좌석 고르기 | `zone` 없음 → `pickSeatsFromMap`: **70% 확률로 전체의 앞 10% 좌석 범위**에서 무작위 시작점(`lib/booking.js` 40행) | 구역 지정: VIP 1,265명, R 900, S 441, 아무 곳 394 |
| 409 뒤 행동 | 같은 구역으로 다시(최대 2번) | 같은 구역 1,487, 다른 구역 1,125, 포기 388 |
| 매수 | 무작위 | 2매 1,613, 1매 999, 4매 304, 3매 84 |

설정은 설계 문서(`docs/design/infra/synthetic-data.md`)대로 들어가 있다.

## 2. 실제로 몰린 양(k6 raw 데이터, 11/15 회차 122·123)
| API | 균일 합계 / 초당 최대 | Synthetic 합계 / 초당 최대 | 읽는 법 |
|---|---|---|---|
| 대기열 진입 | 3,016 / **353** | 5,614 / **2,792** | 입구는 Synthetic이 8배 몰렸다. 503 1,516건이 여기서 났다 |
| 순번 조회 | 8,659 / 404 | 7,306 / 636 | |
| 좌석 조회(약 830KB) | **4,904** / 123 | 3,182 / 104 | 균일은 409 뒤 재조회로 1.5배 |
| 선점 | 4,781(201 2,315 · **409 2,298** · 503 168) | 3,178(201 2,802 · **409 372** · 503 4) | 충돌률 48% 대 12% |
| 결제 | 2,053 / 51 | 2,547 / 39 | |
| 확정 상태 조회 | **4,899** / 236 | 2,687 / 41 | 균일은 확정이 늦어(p95 3.9초 대 1.0초) 더 자주 물어봤다 |

## 3. 왜 이렇게 되나
1. **대기열이 뒤쪽 부하를 평평하게 만든다.** 입장은 초당 50명이다. 입구에 2,792명이 오든 353명이 오든, 좌석 조회·선점으로 넘어가는 속도는 같다. 입구 몰림의 차이는 대기열 진입 503과 순번 조회에만 드러난다.
2. **뒤쪽 부하를 정한 것은 좌석 충돌이다.** 균일은 같은 규칙으로 앞쪽 10%에 몰려 두 번에 한 번 꼴로 409를 받았다. 409마다 좌석 조회(큰 응답)와 선점을 다시 하고, 그동안 Gateway 칸을 오래 잡는다. 그래서 균일에서 상한 64 거절이 좌석 조회·선점·확정 조회에 퍼졌다.
3. **Synthetic의 입구 거절이 오히려 흩뜨렸다.** 진입 503을 받은 사용자는 `Retry-After` 3초 뒤 다시 온다(`retryLater`). 상한이 입구에서 몰림을 몇 초씩 밀어낸 셈이다.
4. 포기·이탈 페르소나(포기 388, 진입 안 함 169)도 뒤쪽 요청을 줄였다.

## 4. 그래서 이 비교를 어떻게 말해야 하나
- "현실적인 사용자일수록 서버가 편하다"고 말하면 틀린다. 두 실행은 **도착 모양**과 **좌석 수요의 쏠림**이 동시에 다르다. 균일은 "모두가 앞자리를 노리는 최악의 쏠림", Synthetic은 "구역별로 흩어진 수요 + 더 날카로운 입구 몰림"이다.
- 말할 수 있는 것: ① 입구 몰림은 Synthetic이 8배 컸고, Gateway 상한이 입구에서 걸렀다. ② 대기열 뒤 병목은 도착 모양보다 **좌석 쏠림(충돌률)**이 정한다. ③ 같은 서버에서 충돌률 48% → 12%면 확정이 1,973 → 2,547.
- 대가: 두 요인을 한 실행으로는 가를 수 없다. 가르려면 Synthetic의 도착 모양에 균일의 좌석 규칙(앞 10%에 70%)을 붙인 실행이 하나 더 필요하다(오늘 하지 않음, 다음 측정 후보).

## 5. 오늘 측정에 주는 영향
- 상한 개선(B1·B2)은 **좌석 충돌이 많은 균일**에서 효과가 크게 보인다(B1 상한 1000에서 확정 +9%).
- Synthetic은 거절이 입구에 몰렸으므로, 상한을 올리면 입구 몰림(초당 2,792)이 대기열 Redis와 인증 Redis bulkhead(동시 50)로 넘어간다. B2 Synthetic에서 auth-redis 503이 늘어나는지 본다.
