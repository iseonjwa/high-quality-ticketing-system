# 오픈 순간 Gateway에서 대기열 진입이 거절되는 현상을 장비를 늘리지 않고 어떻게 풀 수 있나

## 질문
대부분의 부하와 병목이 Gateway에서 생긴다. 대기열 쪽에 부하가 더 실리게 바꾸거나, 모든 요청이 계속 거절되는 현상을 어떻게 다뤄야 할까. 로드밸런싱이나 쿠버네티스 같은 기술적 방안도 생각해 보자. "서버 비용을 늘리면 된다"로 끝나지 않는 방향도 찾자. 구현 여부는 나중에 정한다.

## 먼저 사실(측정으로 확인한 것)
| 사실 | 숫자 | 출처 |
|---|---|---|
| 남은 거절의 대부분이 오픈 순간 대기열 진입 | v2 R 상한 거절 5,571·4,494 중 진입 4,926·3,927(약 87~88%, 계산값) | ISE-264 측정 기록 v2 절 |
| 같은 코드에서 진입을 10초에 펴면 거절이 사라짐 | v2 균일(오픈 +1~11초 고르게): 상한 거절 0, 확정 2,236, HTTP 실패 0 | v2 균일(회차 166) |
| 가장 바쁜 30초 CPU 1위가 Gateway | v2 균일 gateway 77.0%, reservation 49.3% | 같음 |
| 진입을 여러 번 누름(광클) | Synthetic 진입 요청 5,614건 중 같은 사람의 중복 진입 200 응답 1,267건 | [11/15 노트](2026-11-15-adaptive-queue-admission.md) |
| 오픈 전 요청이 이미 많음 | 전체의 73.8%가 공연 상세, 그중 98.1%가 오픈 전 | 공연 상세 분석(ISE-285) |
| 장비는 4 vCPU 한 대 | 모든 서비스가 같은 CPU를 나눠 씀 | 배포 구성 |

**핵심**: 처리할 일의 총량이 넘치는 것이 아니라 **같은 1초에 몰리는 것**이 문제다. 같은 요청 수를 10초에 펴면(균일) 지금 서버로도 거절이 0이었다.

## 선택지: 네 방향
### A. 몰림을 시간으로 편다(가장 효과가 크다고 본다)
| 안 | 내용 | 기대(근거) | 대가 |
|---|---|---|---|
| A1. 오픈 전 사전 대기 등록 | 상세 페이지에 머무는 오픈 전 10분 동안 "대기 등록"을 받아 서명된 등록 토큰을 준다. 오픈 순간에는 등록 순서 또는 오픈 시각 이후 무작위로 섞은 순번으로 입장시킨다. 오픈 0~1초에 진입 요청을 보낼 이유가 사라진다 | 진입 요청이 오픈 전 10분에 퍼지면 균일(거절 0)보다 더 넓게 퍼진다(추정, 균일 결과가 근거) | 순번 공정성 규칙(선착순 대 무작위)을 정해야 함. 화면 변경. 등록 토큰 위조 방지 |
| A2. 진입 시각 슬롯 | 오픈 시각에 서버가 사용자별로 0~5초 안의 진입 시각을 정해 주고, 클라이언트는 그때 보낸다. 순번은 슬롯과 무관하게 서버가 정함 | 같음 | 클라이언트 시계·악성 클라이언트는 무시하고 서버가 늦게 온 것만 받도록 해야 함 |
| A3. 클라이언트 지터·백오프 | 503 뒤 재시도를 `Retry-After` + 무작위 지터로 흩고, 버튼을 누른 뒤 응답까지 다시 못 누르게 함 | 재시도 몰림 감소. 첫 1초 몰림은 그대로 | 가장 싸지만 악성·직접 호출에는 효과 없음 |

A1은 이미 있는 데이터와 맞물린다. 오픈 전 상세 조회가 요청의 73.8%라는 것은 사용자가 오픈 전에 이미 페이지에 와 있다는 뜻이고, 그 시간을 진입에 쓰지 않고 있다.

### B. 진입을 Gateway를 거치지 않거나 아주 싸게 처리한다(대기열 쪽에 싣기)
| 안 | 내용 | 기대 | 대가 |
|---|---|---|---|
| B1. 진입 경로 분리 | 앞단 L7 로드밸런서(ALB·Nginx·Envoy)의 경로 규칙으로 `queue enter·poll`을 Gateway가 아니라 대기열 서비스로 바로 보낸다. 대기열 서비스가 토큰 서명을 스스로 확인 | 진입이 Gateway 동시 처리 자리 64를 쓰지 않음. 무거운 경로만 Gateway가 맡음 | 인증 로직이 두 곳. 대기열 서비스가 바로 노출됨. 한 장비라 CPU 총량은 같음(자리 다툼만 사라짐) |
| B2. 경로별 상한(격리) | Gateway 안에서 진입·순번 조회 자리와 좌석·선점·결제 자리를 나눔 | 무거운 요청이 진입 자리를 빼앗지 않음 | 경로별 값 계산(λ×W) 필요. ISE-288 |
| B3. 진입 중복 합치기 | 같은 사용자의 1초 안 진입을 Gateway 맨 앞에서 하나로 합치거나 바로 같은 응답을 돌려줌 | Synthetic에서 중복 진입 1,267건만큼 줄어듦(그 실행 기준) | 사용자 식별이 인증 뒤라 맨 앞 처리와 순서가 충돌. 캐시 키 설계 |
| B4. 순번 조회를 밀어 주기 | 폴링 대신 SSE·WebSocket으로 순번을 서버가 밀어 줌 | 순번 조회 요청 수 감소 | 연결을 오래 쥠(메모리·연결 수), 재연결 몰림 |

### C. 거절을 똑똑하게 한다(같은 거절 수라도 덜 아프게)
| 안 | 내용 | 기대 | 대가 |
|---|---|---|---|
| C1. 단계별 우선순위 거절 | 자리가 찰 때 새 진입부터 거절하고, 이미 결제·확정 조회 중인 사용자는 통과 | 굿풋(확정) 보호. 지금은 확정 조회·결제도 같이 거절됨 | 우선순위 판단 비용, 경로 분류 규칙 |
| C2. 적응형 동시 처리 상한 | 고정 64 대신 지연을 보며 상한을 자동 조절(Netflix concurrency-limits의 Gradient·Vegas 방식) | 순간 몰림과 평시 모두 맞는 값을 스스로 찾음 | 새 의존성, 진동 위험, 검증 비용 |
| C3. 거절 대신 짧은 대기 | 자리가 없으면 바로 503 대신 최대 수백 ms 기다리는 대기열을 Gateway에 둠 | 0~1초 몰림을 흡수 | 대기가 길어지면 메모리·지연이 늘어 결국 안전망 역할을 잃음. 상한 필요 |

### D. 인프라로 넓힌다(로드밸런싱·쿠버네티스)
| 안 | 내용 | 정직한 평가 |
|---|---|---|
| D1. Gateway 여러 개 + 로드밸런서 | 같은 장비에 Gateway를 둘 띄우고 나눠 보냄 | 한 장비 4 vCPU를 나눠 쓰므로 총 처리량은 거의 그대로다(추정). 장비를 늘려야 효과가 난다 = 비용 |
| D2. 쿠버네티스 HPA | 처리 중 요청 수 같은 지표로 Gateway 파드를 자동 증설 | 파드가 뜨는 데 수십 초가 걸려 오픈 0~1초에는 늦다. 오픈 시각을 아니까 미리 늘리는 예약 증설(스케줄 스케일링)이 맞다. 결국 장비가 있어야 함 |
| D3. 엣지에서 대기실 | CDN·엣지 함수(예: 클라우드 대기실 제품)가 오픈 순간 요청을 받아 순번을 주고, 원 서버에는 정해진 속도로만 보냄 | 원 서버 앞에서 몰림을 끊는 업계 방식. 비용·외부 의존이 생기지만 "서버를 늘리지 않고 앞에서 줄 세운다"는 이야기가 된다 |

## 추천(발표 이야기로서)
1. **A1 오픈 전 사전 대기 등록**을 중심 안으로 본다. 이유
   - 측정이 직접 근거를 준다. 같은 v2 코드에서 진입을 10초에 펴면 거절 0(균일), 0~1초에 몰면 거절 4,494~5,571(현실 모드). 문제는 양이 아니라 시점이라는 것을 숫자로 보였다.
   - 버려지던 오픈 전 시간(요청의 73.8%가 오픈 전 상세 조회)을 진입에 쓴다는 점이 새롭다.
   - 장비를 늘리지 않는다.
2. 보조로 **C1 단계별 우선순위 거절**을 둔다. 그래도 몰리는 순간에 이미 결제 중인 사람을 지킨다.
3. **D(쿠버네티스·로드밸런서)**는 "한 장비에서는 총 CPU가 같아 효과가 작고, 오픈 시각을 아는 서비스라 자동 증설보다 예약 증설이 맞다"는 판단까지를 이야기로 남긴다.

## 증명하려면(측정 설계 초안)
- A1 흉내: k6 현실 모드에서 진입 시각을 "오픈 전 등록 + 오픈 뒤 서버가 정한 슬롯"으로 바꾼 모드를 더해 같은 v3에서 2회. 기대는 상한 거절이 균일 수준(0~299)으로 떨어지고 확정이 균일(2,236)에 가까워지는 것(추정).
- 주의: 11/16 자동 배정에서 본 것처럼 흉내는 서버 쪽 비용(등록 토큰 발급·검증)을 빼므로, 효과를 말하려면 실제 구현으로 다시 재야 한다.

## 확인 못 한 것
- Gateway CPU 77% 중 인증(토큰 검증·auth-redis)과 프록시 몫이 각각 얼마인지는 재지 않았다.
- D1·D2의 효과는 계산·추정이고 재지 않았다.
