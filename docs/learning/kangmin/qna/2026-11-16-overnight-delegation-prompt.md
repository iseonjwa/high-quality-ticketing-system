# 밤새 AI에게 측정·개선을 맡기는 위임 프롬프트를 어떻게 다듬으면 같은 성과를 다시 낼 수 있나

## 질문
11/15 밤에 쓴 위임 프롬프트(아래 "원문")를 더 깔끔하게 다듬어, 같은 성과를 내면서 팀원들도 쓸 수 있게 하려면 어떻게 고치면 될까.

## 원문에서 잘 된 것
- 목표가 분명했다: 측정 → 병목 → 개선 → 재측정 반복, 최종은 서비스 전체 성능.
- 멈추지 않게 했다: 결정은 AI 추천대로, 확인이 필요한 것은 문서에 쌓기.
- 기록을 조건으로 걸었다.
- 시작 전에 모르는 것과 필요한 권한을 한 번에 묻게 했다.

## 원문에 없어서 밤사이 생긴 일
| 빠진 것 | 밤사이 실제로 생긴 일 | 다듬은 프롬프트에서 |
|---|---|---|
| 끝나는 시각과 정리 | 09:00 전 정리 시각을 AI가 따로 정하고 시간 예산을 계산해야 했다 | 시작·끝 시각, 정리 시작 시각, 정리 항목을 적음 |
| 버전 고정 규칙 | 개선이 dev에 일찍 머지돼 "dev 그대로 배포"하면 전후 비교가 깨질 뻔했다(D10·D16·D19) | 개선 전·후를 커밋으로 고정한 브랜치로만 배포 |
| 반복 측정 기준 | 같은 설정 두 번(B1·E2)이 크게 달라 1회 결론이 흔들렸다 | 결론에 쓰는 비교는 같은 조건 2회 이상 |
| 측정 오염 확인 | payment가 cgroup OOM으로 5번 죽었는데 `docker inspect`에는 exit 0으로 보여 v0 결과 대부분이 "방향만"이 됐다 | 실행마다 재시작 수·커널 OOM 로그 확인 |
| 흉내 실험의 한계 | 좌석 나눔 흉내 +33.7%였지만 실제 자동 배정은 확정 433(인덱스 없음) | 흉내로 근거를 만든 개선은 실제 구현으로 다시 잰다 |
| 병렬 작업의 충돌 | 같은 폴더에서 다른 세션이 브랜치를 바꿔 커밋이 엉뚱한 브랜치에 들어갔다(D6) | 코드 작업은 워크트리로 격리, 측정 세션은 하나 |
| 금지 목록 | 권한이 "모든 것"이라 AI가 스스로 선을 그어야 했다(강제 push·비밀값·남의 브랜치 삭제 등) | 하지 않을 것을 명시 |
| 점검 주기·잠들기 방지 | 메인이 크론으로 30분마다 점검하고 절전 방지를 따로 켰다 | 점검 주기와 절전 방지를 조건으로 |
| 아침에 받을 것 | 보고서 모양을 AI가 정했다 | 아침 보고서 항목을 적음 |
| 표기("herdr 혹은 하위 섹션") | 하위 세션으로 이해했다 | 용어를 바로잡음 |

## 다듬은 프롬프트(템플릿)
`< >`는 각자 채운다. 이번 프로젝트 값은 예시로 둔다.

```text
[야간 위임] <시작 시각>부터 <끝 시각>(KST)까지 이 작업의 지휘를 맡긴다.

## 1. 목표
- 배포 서버 측정으로 CPU·처리 속도 병목을 찾고, 고치고, 다시 재서 서비스 전체 성능을 올린다.
- 성공 기준: <예: 현실 시나리오 O1 확정 예매 수, 선점 p95, 거절 수>를 개선 전 버전과 같은 조건으로 비교한 표.

## 2. 권한(허용)
- 결정은 네 추천대로 한다. 내 확인을 기다리지 않는다.
- dev 머지, 버전 브랜치로 main 배포(여러 번), Linear 댓글·이슈 생성, 다른 담당 영역 코드 수정을 허용한다. 다른 영역은 "선조치 후보고"로 이슈에 알린다.
- 측정 시나리오가 실제 사용과 다르다고 판단되면 고쳐도 된다. 고친 이유를 남긴다.

## 3. 하지 않을 것
- 강제 push, 남의 머지 안 된 브랜치 삭제, 비밀값(.env·키·토큰) 커밋·출력.
- 저장소 밖 서버 설정 수정(덮어쓰기는 <예: ~/<이름>-overrides/>에만), 데이터 일괄 삭제(`docker system prune` 등).
- 측정 도중 main 머지(버전 경계에서만).
- 커밋·PR의 AI 작성 표시.

## 4. 일하는 방식
- 메인 세션은 지휘·결정·기록만 한다. 서버 측정은 측정 세션 하나가 순서대로 맡는다.
- 코드 개선은 하위 세션이나 에이전트에 병렬로 맡기되, 각자 워크트리에서 dev 최신을 기준으로 한다.
- 반복: 측정 → 병목 후보(근거 숫자) → 개선 구현(테스트·변이 확인·CI) → dev 머지 → 버전 고정 배포 → 같은 조건 재측정.
- 이미 확정된 측정은 다시 하지 않는다. 오염됐거나 1회뿐인 결론은 다시 잰다.

## 5. 측정 규칙
- 개선 전·후는 커밋으로 고정한 브랜치(<예: deploy/v1-날짜, v2-날짜>)로 배포해 비교한다. dev를 그대로 배포하지 않는다.
- 결론에 쓰는 비교는 같은 조건 2회 이상. 1회 결과는 "방향만"으로 적는다.
- 재기동 뒤에는 예열하고 잰다.
- 실행마다 확인: 서비스 재시작 수와 커널 OOM 로그(`docker inspect`만 믿지 않는다), 컨테이너별 CPU, 측정 유효성(<예: 발생기 CPU, 예정 시각 지연>), 정합성(<예: 확정 = 결제 승인, 중복 0>).
- 흉내 실험으로 근거를 만든 개선은 실제 구현으로 다시 잰다.
- 정리 시각(<끝 시각 - 30분>)에는 진행 중 실행을 끝내거나 중단 표시하고, 측정 모드 끄기·덮어쓰기 삭제·서버 상태 확인을 한다.

## 6. 기록
- 결정 로그 한 파일(<예: docs/context/overnight-<날짜>-plan.md>)에 쌓는다: 시각 · 결정 · 이유 · 버린 대안 · 되돌릴 조건.
- 실험마다 원기록(명령·결과 숫자·원자료 위치)을 남긴다. 숫자는 원기록에 있는 것만 쓰고, 계산값·추정·확인 못 함을 표시한다.
- 내 확인이나 팀 합의가 필요한 것은 "아침 확인 목록"에 쌓고 일은 계속한다.
- 발표·트러블슈팅에 쓸 만한 장면(가정이 뒤집힌 순간 등)은 그때그때 문서에 남긴다.
- Linear·GitHub 글은 게시 전에 검증 에이전트로 원천과 대조한다.

## 7. 멈추지 않기
- <30>분마다 스스로 점검한다(하위 세션 상태, 측정 진행, 열린 PR·CI). 멈춘 세션에는 다음 일을 준다.
- 절전 방지를 켠다.
- 실험이 끝날 때마다 한두 줄로 보고한다. 모든 출력은 한국어.

## 8. 아침에 받을 것
- 한 쪽 보고서: 한 줄 결론, 버전별 핵심 숫자 표, 들어간 개선(PR·효과), 발표 장면 후보, 내가·팀이 확인할 것, 정리 결과(서버 상태).

## 9. 시작 전에
위 내용 중 이해가 안 되는 것, 미리 받아야 할 권한, 팀 규칙과 어긋나는 것을 지금 한꺼번에 물어 줘. 답을 받은 뒤에는 끝 시각까지 묻지 않고 진행한다.
```

## 왜 이렇게 나눴나
- 원문은 한 덩어리 문장이라 AI가 권한·금지·규칙을 스스로 나눠 읽어야 했다. 절로 나누면 AI가 판단할 때 해당 절만 다시 볼 수 있다.
- "모든 권한"보다 허용 목록과 금지 목록을 함께 주는 편이 오히려 멈추지 않는다. 경계가 분명하면 AI가 "이건 해도 되나"를 묻지 않는다.
- 측정 규칙(5절)이 이번 밤 결과의 신뢰도를 가장 크게 바꿨다. 버전 고정과 2회 측정이 없었으면 "+10.7%"를 말할 수 없었다.

## 확인 못 한 것
- 다듬은 프롬프트로 실제로 밤을 돌려 보지는 않았다. 각 규칙은 11/15~16 밤의 사건에서 거꾸로 뽑은 것이다.

## 구어체 버전(팀 공유용, 강민 말투)
강민 요청: 위 템플릿은 AI 문서처럼 읽혀 본인 요청문 같지 않다 → 원문 말투로 다시 씀. 내용은 템플릿과 같다.

```text
지금부터 <끝 시각>까지 이 작업 지휘를 전부 너한테 맡길게.

목표는 배포 서버에서 측정해서 CPU 부하나 처리 속도 병목을 찾고, 고치고, 다시 재서 서비스 전체 성능을 끌어올리는 거야.
아침에 개선 전이랑 후를 같은 조건으로 비교한 표가 있으면 성공이야.

결정은 네 추천대로 해도 되고 내 확인 기다리지 마.
dev 머지, main 배포(여러 번 해도 됨), 리니어 댓글이나 이슈 만들기, 다른 사람 담당 영역 코드 고치는 것까지 다 허용할게.
다른 사람 영역 건드리면 선조치 후보고로 이슈에 남겨 줘.
측정 시나리오가 실제 서비스랑 다르다 싶으면 고쳐도 되는데 왜 고쳤는지는 남겨.

대신 이건 하지 마.
강제 push, 남의 안 머지된 브랜치 지우기, .env나 키 같은 비밀값 커밋하거나 출력하기,
저장소 밖 서버 설정 직접 고치기(덮어쓰기는 <전용 폴더>에만), 데이터 통째로 지우기,
측정 돌아가는 중에 main 머지하기, 커밋이나 PR에 AI 작성 표시 넣기.

일은 이렇게 나눠서 해 줘.
메인은 지휘하고 결정하고 기록만 하고, 서버 측정은 측정 세션 하나가 순서대로 맡아.
코드 개선은 하위 세션이나 에이전트로 병렬로 돌리되 각자 워크트리에서 dev 최신 기준으로 작업해.
측정하고, 병목 찾고, 고치고(테스트·변이 테스트·CI까지), dev 머지하고, 버전 고정해서 배포하고, 같은 조건으로 다시 재는 걸 계속 반복하면 돼.
이미 확실한 측정은 다시 안 해도 되는데, 오염됐거나 한 번밖에 안 잰 결과는 다시 재.

측정할 때 꼭 지킬 것.
개선 전이랑 후는 커밋 고정한 브랜치로 배포해서 비교해. dev를 그대로 배포하면 비교가 깨져.
결론에 쓸 비교는 같은 조건으로 최소 두 번 재고, 한 번 잰 건 "방향만"이라고 적어.
서버 재시작한 다음엔 예열하고 재.
실행할 때마다 서비스 재시작 수랑 커널 OOM 로그(docker inspect만 믿지 말고), 컨테이너별 CPU, 측정이 유효한지, 정합성이 맞는지 확인해.
흉내 실험으로 근거 만든 개선은 실제로 구현한 다음에 다시 재.
<끝 시각 30분 전>부터는 정리해. 돌고 있는 건 끝내거나 중단 표시하고, 측정 모드 끄고, 덮어쓰기 지우고, 서버 상태 확인까지.

기록은 무조건 남겨서 나중에 내가 다시 확인할 수 있게 해.
결정은 한 파일에 시각, 결정, 이유, 버린 대안, 되돌릴 조건까지 쌓고,
실험마다 명령이랑 결과 숫자, 원자료 위치를 남겨. 숫자는 원기록에 있는 것만 쓰고 계산한 값이나 추정은 표시해.
내 확인이나 팀 합의가 필요한 건 아침 확인 목록에 쌓아 두고 일은 멈추지 마.
가정이 뒤집힌 순간 같은 건 발표나 트러블슈팅 자료가 되니까 그때그때 적어 두고,
리니어나 깃허브에 올리는 글은 올리기 전에 검증 에이전트로 원본이랑 한 번 대조해.

중간에 멈추지 않게 <30>분마다 스스로 점검해 줘. 하위 세션 상태, 측정 진행, 열린 PR이랑 CI 보고 멈춘 데 있으면 다음 일 줘.
절전 모드 안 되게 꼭 켜 두고, 실험 하나 끝날 때마다 한두 줄로 보고해 줘. 출력은 전부 한국어로.

아침엔 한 쪽짜리 보고서로 받고 싶어.
한 줄 결론, 버전별 핵심 숫자 표, 들어간 개선(PR이랑 효과), 발표에 쓸 장면, 나랑 팀이 확인할 것, 서버 정리 결과까지.

여기까지 보고 이해 안 되는 거, 미리 받아야 할 권한, 팀 규칙이랑 안 맞는 거 있으면 지금 한꺼번에 물어봐.
답 받고 나면 끝날 때까지 묻지 말고 쭉 진행해. 밤새 할 수 있겠어?
```

### 팀 공유 문구(초안)
> 어젯밤에 측정·개선을 AI한테 통째로 맡겨 봤는데 생각보다 잘 돌아갔어요. 처음엔 "결정은 네 추천대로, 권한 다 줄게, 대신 기록은 무조건 남겨" 정도로만 보냈고, 그것만으로도 버전 3개 배포하고 개선 9개 넣고 재측정까지 밤새 진행됐습니다.
> 해 보니까 처음부터 적어 뒀으면 좋았을 게 몇 개 있어서(끝나는 시각, 하지 말 것, 버전 고정, 두 번 재기, OOM 확인, 아침 보고서 모양) 그걸 넣어서 다시 정리해 봤어요. 아래처럼 보내 보시면 됩니다. 꺾쇠 칸만 각자 바꾸시면 돼요.
