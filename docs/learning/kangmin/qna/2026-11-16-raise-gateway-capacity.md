# 장비를 늘리지 않고 Gateway가 받을 수 있는 양을 더 늘릴 수 있나

## 질문
Gateway 한도를 어떻게 더 늘릴 수는 없을까.

## 먼저: "한도"가 무엇인가
- 설정 한도는 동시 처리 상한 64다. 처리량은 리틀의 법칙으로 `64 ÷ 요청 한 건 머무는 시간(W)`이다.
- 64를 올리는 것은 이미 해 봤다(11/15 B1·B2·E2). 거절은 줄었지만 줄이 DB 풀 앞으로 옮겨 가고 지연이 늘었다. 4 vCPU를 모두가 나눠 쓰기 때문이다.
- 그래서 진짜 한도는 **Gateway가 요청 한 건에 쓰는 CPU**와 **Gateway로 들어오는 요청 수**다. 둘 중 하나를 줄이면 같은 장비에서 더 받는다.

## 지금 아는 숫자
| 사실 | 값 | 출처 |
|---|---|---|
| 작은 요청 한 건 Gateway CPU | 1.063ms | 8차 R0(`open-peak-scenarios.md`) |
| 거절 한 건 | 0.02~0.08ms | 같음 |
| 1코어당 작은 요청 | 약 940건/초(계산값, 1 ÷ 1.063ms) | 계산 |
| Gateway CPU 중 관측 묶음(추적·문맥 전파) | 약 24%. 그중 `ContextPropagation` 5.8%, `ContextWriteRestoringThreadLocals` 2.7% | 11/11 0b JFR(`gateway-overload-troubleshooting-story.md`) |
| Gateway CPU 중 인증 Redis·차단기 | 약 2.5% | 같은 JFR |
| 요청의 73.8%가 공연 상세 | 98.1%가 오픈 전 | ISE-285 분석 |
| 좌석 응답 | 845,255바이트, 비압축으로 Gateway 통과 | 11/15 실측 |
| v2 균일 가장 바쁜 30초 CPU 1위 | gateway 77.0% | 11/16 측정 |

## 방법: 두 갈래
### A. 요청 한 건을 싸게(같은 요청 수를 더 적은 CPU로)
| 안 | 기대 | 근거 | 대가 |
|---|---|---|---|
| A1. 관측 묶음 줄이기: 자동 문맥 전파(`spring.reactor.context-propagation: auto`)를 끄거나 필요한 곳만 수동으로 | Gateway CPU 최대 약 24% 절약(상한 추정) | 11/11 JFR 몫 | 로그의 traceId 연결이 끊길 수 있음. 관측 담당 확인 필요 |
| A2. 좌석 응답을 압축 바이트로 캐시해 통과 | Gateway가 나르는 바이트 약 1/5~1/20(압축률 추정, 재지 않음) | 845KB 비압축 실측 | reservation 코드 변경, 클라이언트 `Accept-Encoding` 확인 |
| A3. 응답 크기 자체 줄이기(구역별 조회·비트맵) | 좌석 경로 비용 큰 폭 감소(추정) | 같음 | API 계약 변경 |
| A4. 경로별로 필요 없는 필터 빼기 | 공개 GET(공연 상세)은 인증·입장 토큰 필터가 필요 없음 | 공연 상세는 `PUBLIC_GET` | 필터 순서·보안 검토 |

### B. Gateway로 오는 요청을 줄이기(Gateway 앞에서 끝내기)
| 안 | 기대 | 근거 | 대가 |
|---|---|---|---|
| B1. 공연 상세를 Gateway 앞에서 캐시(프론트 nginx 또는 CDN, 1초) | 요청의 73.8%가 Gateway에 오지 않음 | ISE-285 분석 | 화면 시계가 응답 `serverTime`을 써서 시간 값 분리 합의가 먼저(ISE-285 2단계) |
| B2. 대기열 폴링을 "예상 입장 시각 직전"에 하게 | 1인당 조회 3.2 → 2~3회(추정) | 폴링 모델(11/16) | 대기열 담당 계약 |
| B3. 진입 광클 합치기 | Synthetic 기준 중복 진입 1,267건 감소 | 11/15 집계 | 맨 앞 사용자 식별 순서 |
| B4. 오픈 전 사전 대기 등록 | 오픈 0~1초 진입 몰림 자체를 없앰 | 같은 코드에서 10초에 펴면 거절 0 | 화면·순번 규칙 |
| B5. 가벼운 경로를 더 가벼운 프록시로(Nginx·Envoy가 대기열 조회를 대기열 서비스로 바로) | Spring Cloud Gateway 한 건 1.06ms를 안 거침 | 위 숫자 | 인증 로직이 두 곳 |

## 추천 순서
1. **A1 관측 묶음 측정**: 측정 덮어쓰기로 자동 문맥 전파만 끄고 같은 현실 모드 R을 잰다. 설정 하나라 가장 싸고, 효과가 크면 상한 64 그대로 처리량이 오른다. 효과 크기는 11/11 JFR 몫(24%)이 상한이다.
2. **B1 공연 상세 앞단 캐시**: 오픈 전 부하의 거의 전부라, 규모가 커질수록 이득이 크다(20만 명이면 오픈 전 초당 약 9,500건, 계산값).
3. **B2·B4**: 대기열 쪽 계약 변경이라 팀 논의(ISE-288)로.
- 상한 값을 올리는 것은 추천하지 않는다(11/15 실측: 줄이 DB 앞으로 옮겨 감).

## 확인 못 한 것
- 관측 묶음 24%는 11/11 G1(순번 조회만) JFR 기준이다. 지금 v3와 섞인 부하에서의 몫은 재지 않았다.
- 인증 토큰 서명 검증 비용, 지표 태그 비용은 따로 재지 않았다.
