# 오픈 순간 몰리는 사람 수를 크게 늘리면 서버 전체가 마비될까

## 질문
지금 상태에서 몰리는 사람 수를 확 늘리면 서버 전체가 마비될까.

## 짧은 답
- 바로 마비되지는 않을 가능성이 크다. Gateway 동시 처리 상한(64)이 넘친 요청을 싸게 거절해서, 뒤쪽 서비스는 일정량만 받는다.
- 대신 거절이 늘어 "대부분이 503을 받는" 상태가 된다. 처리되는 양(굿풋)은 천장에서 평평해진다.
- 더 늘리면 거절하는 일 자체와 연결 수, 재시도가 같은 장비 CPU를 먹어 굿풋이 떨어지는 구간이 올 수 있다. 지금 코드로 그 지점이 어디인지는 재지 않았다.

## 근거 1: 상한이 없을 때는 실제로 무너졌다(11/11, 배포 `74f91ffb`, G1 순번 조회만)
| 목표 | 성공률 | 굿풋(200ms 안 200 응답/초) | 성공 p95 | 서버 CPU 평균 |
|---|---|---|---|---|
| 1,500/s | 99.04% | 1,440 | 152ms | 93% |
| 2,000/s | 94.97% | 1,469 | 435ms | 99% |
| 2,500/s | 88.31% | **136** | 878ms | 99% |
| 3,000/s | 23.26% | **33** | 2.38s | 94%, **Gateway OOM** |

- 2,000/s에서 2,500/s로 25% 늘리자 굿풋이 1,469에서 136으로 약 1/11이 됐다(계산값). 요청은 다 받아 두고 하나도 제때 끝내지 못하는 상태, 즉 **혼잡 붕괴**다. 3,000/s에서는 Gateway가 메모리 초과로 죽었다.
- 2,500/s·3,000/s 단계는 발생기 VU 상한에 닿아 측정 규칙상 "무효"로 표시했다. 그래도 방향은 분명하다.
- 출처: `docs/design/infra/open-peak-scenarios.md` "단계별 결과" 표.

## 근거 2: 상한을 넣은 뒤 같은 부하에서는 버텼다
- 11/11 맨 앞 동시 처리 상한(`#488`)과 거절을 맨 앞으로 옮긴 변경(`#497`)이 들어갔다.
- 8차(11/12): 거절 한 건 비용은 받은 요청의 2~8%(받은 요청 1.06ms, 거절 0.02~0.08ms). 2,500/s에서 굿풋 약 2,250/s, p95 50~54ms, 서버 CPU 96~97%.
- 11/13 G1 반복: 2,500/s 굿풋 2,092~2,145, Gateway OOM·재시작 0, 힙 최대 229MiB.
- 즉 같은 2,500/s에서 굿풋 136 → 약 2,100~2,250. 상한이 "처리량을 늘리는 장치"가 아니라 **붕괴를 막는 장치**라는 직접 근거다.

## 그래도 무너질 수 있는 곳(추정, 재지 않음)
| 위험 | 왜 | 지금 아는 것 |
|---|---|---|
| 거절 자체의 CPU | 거절이 싸도 0은 아니다. 초당 수만 건이면 연결 받기·TLS·거절 응답이 4 vCPU를 채운다 | 거절 한 건 0.02~0.08ms. 몇 건/초에서 CPU를 채우는지는 계산·측정 안 함 |
| 같은 장비의 자원 다툼 | Gateway가 거절에 CPU를 쓰면 같은 장비의 reservation·payment가 덜 받는다 | v2 균일에서 이미 CPU 1위가 gateway(77.0%) |
| 재시도 폭주 | 거절된 사람이 3초마다 다시 오면 사람 수에 비례해 요청이 계속 쌓인다 | `Retry-After: 3`, 프론트는 그 값을 그대로 씀 |
| 연결 수·메모리 | 동시 연결이 수만 개면 Netty 버퍼·소켓 메모리가 늘어난다 | 상한 64가 응답 버퍼는 묶지만, 받아 둔 연결 수는 묶지 않는다(확인 못 함) |
| 다른 서비스 메모리 | reservation(1152m)·user(640m)는 계산상 상한을 넘을 수 있다 | 죽은 기록은 아직 없음(TS-71) |
| 오픈 전 공연 상세 | 사용자 수에 비례. 20만 명이면 오픈 전 초당 약 9,500건(계산값) | 장비 한 대 Gateway 한도 초당 약 2,000~2,300건 |

## 확인하려면
- 현실 모드 O1 사용자 수를 3,000 → 6,000 → 12,000처럼 단계로 늘려, 굿풋(확정 수)이 평평해지는지 꺾여 떨어지는지 본다. 꺾이는 지점이 "마비" 경계다.
- 발생기 장비(c6i.xlarge)가 3,000명에서 CPU 146~168%를 썼다. 12,000명이면 발생기가 먼저 한계일 수 있어 발생기 CPU 기준(V1 320%)을 같이 본다.
- 실행 중 멈출 조건(서비스 OOM, 정합성 깨짐)을 미리 정한다.
