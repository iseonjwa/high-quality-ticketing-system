# 부하 테스트 종류와 진행 현황

목차: [README](README.md)

2026-11-11 기준이다. 측정 결과는 모두 개인 노트북(i7-11800H, 16GB, Docker VM 7.6GiB) local에서 나왔다. 배포 서버 본 측정은 0회이고, 2026-11-13~18이 측정 기간이다.

## 1. 부하 테스트 종류

> 비유: 다리 안전 검사. 차 몇 대로 다리가 서 있는지 보고(smoke), 평소 교통량을 올리고(load), 다리가 휘어질 때까지 늘리고(stress), 갑자기 차 수천 대를 한꺼번에 올리고(spike), 하루 종일 차를 올려 둔다(soak). 차를 내린 뒤 다리가 원래대로 돌아오는지도 본다(recovery).

| 유형 | 묻는 질문 | 이 프로젝트의 시나리오 |
|---|---|---|
| Smoke | 돌아가기는 하나 | 발생기 연결 확인(VU 2·20초) |
| Load | 예상 부하에서 목표를 지키나 | K1(L), S1, B1-d, X1, L3 |
| Stress | 어디서 무너지나 | K1(S), K1-H, G1, B1, PAY1, R1, L1 |
| Spike | 순간 폭주를 받나 | Q1(초당 3,000), Q1-d(1초 버스트) |
| Soak | 오래 버티나 | 전용 스크립트 없음. 가장 긴 것은 O1 25분 |
| Recovery | 부하가 끝나면 돌아오나 | K1(S) 회복 탐침, B8 |

### 부하 모델: 열린 모델과 닫힌 모델

> 비유: 닫힌 모델은 손님 100명이 각자 음식을 받아야 다음 주문을 한다. 가게가 느려지면 주문도 줄어 문제가 가려진다. 열린 모델은 손님이 가게 사정과 상관없이 초당 100명씩 들어온다. 실제 티켓 오픈은 열린 모델이다.

그래서 대부분 `constant-arrival-rate`, `ramping-arrival-rate`(도착률 고정·증가)를 쓴다. 가상 사용자(VU)가 모자라 못 보낸 요청은 `dropped_iterations`로 남아, 서버가 아니라 발생기가 한계인지 판단하는 근거가 된다.

### 왜 K1에서 spike와 soak를 뺐나

대기열이 입장을 초당 50명으로 고르게 퍼뜨리므로 좌석 선점에는 스파이크가 오지 않는다. 오픈 순간의 폭주는 대기열 진입(Q1)이 받는다. soak는 15,000석이 2~5분 안에 다 팔려 의미가 없고, 그 뒤 선점 만료는 X1이 본다(`docs/design/reservation/k6-seathold-bottleneck-plan.md` 1-6절).

## 2. 도구와 환경

- k6: Docker `grafana/k6:1.0.0`. `run.sh`가 요약 JSON과 원자료 CSV를 남긴다.
- 배포 측정: 같은 VPC의 발생기 EC2 `iseonjwa-loadgen`(c6i.xlarge)에서 Gateway 사설 IP로 보낸다. 한 번에 한 명만 쓰고, 시작·끝에 `measure-mode.sh on/off`로 측정 모드를 바꾸면 슬랙에 알림이 간다(`docs/guides/loadgen.md`).
- 지표: Prometheus가 5초마다 앱 8개를 수집하고, k6 결과도 remote write로 보낸다(ADR 0046). Grafana 대시보드는 bootstrap, payment, lottery, request-logs가 있고 k6 전용은 없다.
- 보조 도구: GC 로그 분석(`gc_pause.py`), 10초 간격 `docker stats`, 정합성 검사(대사 위반 수), 회복 탐침.

## 3. 시나리오 목록

### 좌석 선점 단계 측정 (ISE-79, `reservation-service/k6/`)

|---|---|---|
| K1 (L) | 초당 100명 고정, 300초 | 실패율 <1%, 좌석 조회 p95 <500ms, 선점 p95 <1000ms |
| K1 (S) | 5→10→20→40→80→160→320명, 단계마다 60초 + 회복 120초 | 단계마다 오류 <1%, p95 <1500ms |

## 4. 측정 결과: 좌석 조회 병목을 하나씩 걷어낸 과정

> 비유: 막힌 하수관을 뚫는 일. 한 곳을 뚫으면 물이 다음 막힌 곳까지 가서 또 막힌다. 그래서 한 번에 하나씩 고치고 매번 다시 잰다.

### 4-1. GC가 첫 병목 (2026-11-04~05)

초당 100명에서 좌석 조회가 전부 실패했다. 좌석 15,000개를 JSON으로 만들 때 생기는 객체가 많아 GC가 계속 돌았다.

| 단계 | 변경 | 오류 없이 버틴 최대 속도 |
|---|---|---|
| P0 | 힙 512MB | 초당 1~2명 (Major GC로 최대 29.1초 정지) |
| P0' | 힙 1,152MB, Serial GC | 초당 5명 |
| P0'' | G1 GC | 초당 10명 (GC 정지 합계 241초 → 81.8초) |

Stop-the-World: GC가 도는 동안 애플리케이션 스레드가 전부 멈추는 것이다. Serial GC는 스레드 하나로 청소해 오래 멈추고, G1은 힙을 구역으로 나눠 조금씩 청소해 정지가 짧다.

### 4-2. 과부하 뒤 회복 못 하는 문제 B8 (2026-11-05)

> 비유: 손님(Gateway)은 3초 기다리다 떠났는데, 주방은 떠난 손님 주문까지 끝까지 만든다. 그사이 새 손님 주문은 밀린다.

Gateway가 3초에 포기한 요청을 서버는 DB 커넥션을 30초까지 기다리며 붙잡고 있었다.

| 대응 | 성공한 좌석 조회 | 회복 |
|---|---|---|
| R0 (대응 전) | 7건 | 340초 뒤에도 연결 4,344개 남음 |
| R1 (커넥션 대기 30초→1초) | 1,463건 | 10초 안에 회복 |
| R1+R2+R3 (연결 200) | 172건 | 오히려 악화 |

빨리 실패하는 편이 전체로는 더 많이 처리한다는 결과다. R1만 contract 이슈 ISE-196으로 제안했고 아직 공유 설정에는 반영되지 않았다.

### 4-3. K1 단계 측정 (2026-11-06~09)

| 단계 | 변경 | L: 성공률 / 서버 처리 | S: 버틴 단계 | 다음 병목 |
|---|---|---|---|---|
| base | 시작점 | 0.02% / 초당 3.9건, GC 정지 65.7% | 5명도 74% 실패 | Serial GC |
| G1 | G1 GC 명시 | 0.1% / 초당 14.7건 | 10명 | 커넥션 대기 |
| R1 | 커넥션 대기 1초 | 7.7% / 초당 7.1건 | 10명 | 조회가 커넥션을 오래 쥠 |
| P4a | 좌석 조회 경량화 1차 | 55.3% / 초당 58.0건 (내부망) | 20명 | DB CPU(15,000행 조인) |
| P4b | 좌석 조회 경량화 2차 | **92.6% / 초당 163.3건**, p95 1.3초 | **80명** | 커넥션 수, JSON 생성 |

P4a와 P4b를 매진 전 구간으로 비교하면 처리량이 약 2.9배, PostgreSQL CPU는 4.5코어에서 2.65코어로 줄었다. 모든 회에서 대사 위반(좌석 이중 판매 등)은 0건이다.

선점만 떼어 잰 K1-H는 200명까지 오류 0%, p95 약 17ms였다. 400명부터는 Gateway의 `auth-redis` 차단기 때문에 오류가 30~43%였다. 선점 로직이 아니라 Gateway 인증이 다음 병목이라는 뜻이다.

### 4-4. 측정에서 겪은 함정

- P4b 1~4차는 무효다. k6 메모리가 3.3GB까지 늘어 Docker VM이 멈췄다. 서버 한계가 아니라 발생기 한계였다. 그래서 k6에 메모리 상한(`--memory 2560m`)을 걸었다.
- Docker 포트 전달이 처리량을 약 40% 깎았다. k6를 compose 네트워크에 붙여 Gateway를 직접 부르도록 바꿨고, 이전 단계를 내부망으로 다시 재기로 했다.
- 원자료 집계에서 요청 수를 잘못 2로 나눠 절반으로 적은 적이 있어 2026-11-09에 고쳤다.

> 교훈: 부하 테스트의 첫 질문은 "서버가 느린가"가 아니라 "내가 잰 것이 서버인가"다.

### 4-5. 오픈 피크 시나리오 동작 확인 (2026-11-05, 작은 규모)

15개 시나리오를 작은 규모로 돌려 스크립트가 동작하는지만 확인했다. 예: Q2 1,000명 p95 10ms, PAY1 결제 p95 560ms, X1 500건이 약 33초에 모두 만료, O1 200명 중 180명 확정이고 좌석 조회 p95 4.15초가 가장 느렸다. Q1-d는 100명은 성공, 300명은 Gateway 차단기 때문에 503이 68~93%였다(2026-11-09).

## 5. 진행 현황

| 유형 | 준비 | 측정함 | 남은 일 |
|---|---|---|---|
| Smoke | 완료 | 2026-11-09 발생기→배포 Gateway 40건, p95 16.35ms | 측정 날마다 연결 확인 |
| Load | 완료 | K1(L) base~P4b, local | 새 기기에서 base부터 재측정, 배포 서버 S1 |
| Stress | 완료 | K1(S) 80명, K1-H 200명, local | 배포 서버에서 G1 1,000~8,000 등 본 측정 |
| Recovery | 완료 | B8 R0·R1·R3, local | 배포 환경 재확인 |
| Spike | 완료 | Q1 300명, Q1-d 100명 | 배포 서버에서 Q1 본 규모 |
| Soak | 없음 | 없음 | 배포 서버에서 Q2·O1 기본값으로 대신 |
| 전체 흐름 | 완료 | O1 200명, local | 구간 개선을 합친 뒤 30,000명으로 최종 판정 |

ISE-79의 남은 단계는 새 기기에서 base·G1·R1·P4a·P4b를 내부망 경로로 다시 잰 뒤, P4c → 선점 단계(S1~S3) → 정합성 묶음 → 커넥션 풀(P1) → P3 → 최종(F) 순이다. 약 47회, 9시간 분량으로 추정한다. 새 기기에서 잰 결과는 아직 저장소에 없다.

막힌 것:

- B1, G1, PAY1, R1, X1, O1은 `setup()`에서 관리자 계정으로 공연을 만든다. 운영 관리자 비밀번호를 발생기에 두지 않는 규칙 때문에 배포 서버에서 그대로 돌지 않는다.
- Gateway `auth-redis` 차단기 설정은 측정 뒤 Gateway 담당과 조율한다.

## 면접 포인트

- "부하 테스트에서 찾은 병목과 개선 수치" → 좌석 조회가 GC(Serial)와 15,000행 조인에서 막혔다. G1 GC, 커넥션 대기 단축, 조회 경량화로 성공률 0.02%→92.6%, 처리량 초당 3.9건→163.3건이 됐다. 단, 노트북 한 대에서 잰 상대 비교다.
- "커넥션 풀을 늘리면 되지 않나" → 연결을 200으로 늘리자 오히려 성공이 172건으로 줄었다. DB CPU가 이미 포화라 동시 쿼리만 늘었다. 풀 크기는 DB 코어 수에 맞춰야 한다.
- "부하 테스트 결과를 어떻게 믿나" → `dropped_iterations`, k6 메모리, 송신 지연 지표로 발생기 한계를 먼저 걸러 내고, 매회 대사 위반 0을 함께 확인했다.
