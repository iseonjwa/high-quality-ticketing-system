# 이선좌 티켓팅 시스템 종합 학습자료

콘서트 티켓 오픈 순간의 폭주를 견디는 예매 서버를 한 번에 훑어보는 자료다. 2026-11-11 `dev` 병합 시점(커밋 `ff1223e6`)의 코드와 문서를 기준으로 썼다. 각 항목에 "구현됨"과 "설계만"을 구분해 적었으니, 발표나 면접에서 말할 때 둘을 섞지 않는다.

## 한 문장 요약

> 놀이공원 인기 놀이기구 앞에 번호표 줄(대기열)을 세우고, 차례가 온 사람에게만 탑승권(입장 토큰)을 주고, 자리를 잠깐 맡아 둔 뒤(선점) 매표소(결제)에서 돈을 내면 표를 확정해 주는 시스템이다. 매표소 기계가 멈추거나 직원이 쪽지를 잃어버려도 돈과 좌석이 어긋나지 않게 하는 장치를 겹겹이 둔 것이 이 프로젝트의 핵심이다.

## 비유 사전

문서 전체에서 같은 비유를 쓴다.

| 시스템 요소 | 비유 |
|---|---|
| Gateway | 건물 1층 보안 데스크. 출입증(JWT)을 보고 어느 층으로 갈지 안내한다 |
| Eureka | 사내 전화번호부. 서비스가 지금 어느 주소에 있는지 알려 준다 |
| Config Server | 본사 공지 게시판. 모든 지점이 같은 설정을 여기서 읽는다 |
| 대기열(Redis) | 놀이공원 번호표 발급기와 전광판 |
| 입장 토큰 | 차례가 된 사람에게 주는 10분짜리 탑승권 |
| 좌석 선점(HELD) | 식당 자리에 가방을 올려 두는 것. 5분 안에 주문(결제)하지 않으면 치운다 |
| 결제 토큰 | 매표소에 내미는 "이 자리 맡은 사람 맞음" 확인증 |
| PG | 카드사와 연결된 외부 매표 대행사 |
| Kafka | 부서 간 사내 우편함. 보낸 쪽은 넣고 끝, 받는 쪽은 자기 속도로 꺼내 본다 |
| Outbox | 우편물을 바로 부치지 않고 먼저 장부에 적어 두는 발송 대장 |
| Inbox(processed_events) | 받은 우편 접수 대장. 같은 편지가 두 번 와도 한 번만 처리한다 |
| DLQ | 반송함. 처리 못 한 우편을 버리지 않고 따로 모은다 |
| 서킷 브레이커 | 누전 차단기. 계속 실패하면 잠시 전기를 끊어 불이 번지지 않게 한다 |
| 대사(Reconciliation) | 가게 마감 정산. 장부와 금고를 맞춰 보고 다른 곳을 찾는다 |

## 아직 없는 것 (자주 헷갈리는 곳)

- 좌석 선점은 PostgreSQL 조건부 UPDATE로 하는 동기형만 있다. Redis 선점과 Kafka 접수형 선점은 설계만 있다.
- 사용자 예매 취소와 취소 환불은 없다. 지금 있는 환불은 시스템이 거는 자동 환불뿐이다.
- Gateway 사용자 요청 제한(rate limit)과 공연·좌석 Redis 캐시는 없다.
- 배포 서버 본 부하 측정은 아직 0회다. 측정 결과는 모두 개인 노트북(local)에서 나왔다.

## 면접 포인트 (전체)

- "티켓 오픈 폭주를 어떻게 견뎠나" → 대기열로 입장 속도를 초당 50명으로 고정하고, 좌석은 DB 조건부 UPDATE로 한 명만 성공하게 했다. 분산락은 DB 제약과 이중이 되어 쓰지 않았다.
- "결제가 타임아웃 나면" → 실패가 아니라 "결과 모름"으로 두고 202를 준 뒤 재확인 스케줄러가 PG에 다시 묻는다. 좌석은 그동안 잡아 둔다.
- "부하 테스트로 무엇을 개선했나" → 좌석 조회가 GC와 DB 조인에서 막혔고, GC 교체와 조회 경량화로 성공률 0.02%에서 92.6%, 처리량 초당 3.9건에서 163.3건이 됐다(local 측정).
