# 입장 토큰의 회차 ID와 요청 회차 ID 비교를 Gateway와 서비스 중 어디서 할까

## 질문
대기열 입장 토큰의 회차 ID와 요청의 회차 ID 비교를 서비스가 맡는 게 좋을까, Gateway에 넘기는 게 좋을까?

## 짧은 답
나눠 맡는다. 토큰 자체 검증(서명, `typ`, `aud`, `exp`, `sub == X-User-Id`)은 Gateway가 하고, 회차 비교는 **요청의 회차 ID가 어디 있느냐**로 가른다. 경로에 있으면(`GET /schedules/{scheduleId}/seats`) Gateway가 바로 비교한다. 본문에 있으면(`POST /reservations`) Gateway는 토큰의 회차 ID를 내부 헤더 `X-Entry-Schedule-Id`로 넘기고, 본문을 어차피 파싱하는 Reservation 서비스가 비교한다. 어느 쪽이 하든 다르면 `403 ENTRY_TOKEN_INVALID`로 같은 의미를 낸다.

## 자세히

### 무엇을 막는 검사인가
회차 31(인기 공연)에 줄을 서는 대신 한산한 회차 32에서 입장 토큰을 받은 뒤, 그 토큰으로 회차 31 좌석을 선점하는 우회를 막는다. 서명·만료·사용자는 맞으므로 회차 비교가 빠지면 대기열이 무력해진다. 그래서 "어디서 하느냐"보다 "반드시 어딘가에서 하고 테스트로 고정하느냐"가 먼저다.

### Gateway에서 다 할 때
- 장점: 몰리는 순간 잘못된 요청을 서비스 호출 없이 끝낸다(SA 7-2의 취지). 검증 규칙이 한 곳에 모인다.
- 단점: `POST /reservations`는 회차 ID가 JSON 본문에 있다. Spring Cloud Gateway(WebFlux)에서 본문을 읽으려면 스트림을 메모리에 캐시(`cacheRequestBody`, `ModifyRequestBodyGatewayFilterFactory`)하고 다시 흘려보내야 한다. 오픈 순간 요청마다 버퍼가 생기고, Gateway가 예매 API 본문 스키마를 알게 된다. 본문 필드 이름이 바뀌면 Gateway도 같이 바뀌어야 한다.

### 서비스에서 다 할 때
- 장점: 서비스는 이미 본문을 파싱하고 도메인 규칙(회차, 좌석)을 안다. 결합이 없다.
- 단점: 입장 토큰 서명 키(`ENTRY_TOKEN_SECRET`)와 검증 코드가 서비스에도 필요하고, 위조 토큰 요청도 서비스까지 들어온다. 좌석 조회처럼 경로만 보고 막을 수 있는 요청까지 서비스로 보내게 된다.

### 나눠 맡을 때 (권장)
- Gateway: 토큰 자체가 유효한지, 이 사용자 것인지를 본다. 경로에 회차가 있으면 회차까지 비교한다.
- 서비스: 본문에만 있는 회차를 `X-Entry-Schedule-Id`와 비교한다. 정수 비교 한 줄이다.
- 전제: Gateway가 외부에서 들어온 같은 이름의 헤더를 반드시 지우고 새로 넣는다. 이 헤더에는 서명이 없으므로 `X-User-Id`와 같은 신뢰 모델(ADR 0008: 서비스 포트를 외부에 열지 않음)을 따른다.

### 다른 선택지: 경로에 회차를 넣기
`POST /schedules/{scheduleId}/reservations`로 바꾸면 Gateway가 본문 없이 전부 처리한다. REST 관점에서도 자연스럽다. 다만 API 경로 변경이라 팀 합의가 필요하고 영향 범위가 크다.

### 방식별 트레이드오프

비교 대상은 네 가지다.

- ① Gateway 전담(본문 파싱)
- ② 서비스 전담(서비스가 토큰 재검증)
- ③ 분담(Gateway가 토큰 검증, 본문 회차는 서비스가 `X-Entry-Schedule-Id`로 비교)
- ④ 경로 변경(`POST /schedules/{scheduleId}/reservations`)

| 기준 | ① Gateway 전담 | ② 서비스 전담 | ③ 분담 | ④ 경로 변경 |
|---|---|---|---|---|
| 잘못된 요청을 막는 위치 | 모두 Gateway | 모두 서비스(위조 토큰도 서비스까지 감) | 위조·만료·타인 토큰은 Gateway, 회차 불일치만 서비스 | 모두 Gateway |
| Gateway 복잡도 | 높음(본문 캐시, JSON 파싱, 파싱 실패 처리, 필터 순서) | 낮음(JWT만) | 중간(헤더 제거·주입 한 단계) | 낮음(경로 변수 비교) |
| 서비스 복잡도 | 없음 | 중간(토큰 검증기, 키 설정) | 낮음(정수 비교 한 줄) | 없음 |
| API 스키마 결합 | Gateway가 예매 본문 필드를 앎 | 없음 | 헤더 이름 하나만 공유 | 경로 규칙만 공유 |
| 검증 규칙의 위치 | 한 곳 | 한 곳 | 두 곳으로 나뉨 | 한 곳 |
| 신뢰 전제 | 없음 | 없음(서비스가 직접 검증) | 서명 없는 내부 헤더를 믿음(ADR 0008 전제) | 없음 |
| 바꾸는 범위 | Gateway 필터 | Reservation 설정·검증 코드 | Gateway 필터 + 선점 컨트롤러 | API 경로, SA·계약 문서, 클라이언트, 부하 테스트 스크립트 |
| 이후 회차 기반 API가 늘 때 | 엔드포인트마다 본문 위치를 Gateway에 등록 | 서비스마다 검증 | 서비스마다 비교 한 줄 | 경로 규칙만 지키면 자동 |

#### ① Gateway 전담
- 얻는 것: 검증이 한 곳에서 끝난다. 서비스는 입장 토큰을 전혀 몰라도 된다.
- 잃는 것: 선점 요청 본문은 100바이트 안팎이라 메모리 비용 자체는 크지 않다. 실제 비용은 복잡도와 결합이다.
  - WebFlux에서 본문은 한 번만 읽히는 스트림이다. 그래서 캐시 필터를 앞에 두고, 파싱하고, 같은 바이트를 다운스트림에 다시 흘려야 한다.
  - 잘못된 JSON이 들어왔을 때 Gateway가 400을 낼지 403을 낼지 정해야 한다.
  - 예매 API 본문이 바뀌면 Gateway도 함께 배포해야 한다.
- 맞는 경우: 회차 기반 POST가 한두 개뿐이고, 검증을 한 곳에 모으는 가치가 가장 클 때.

#### ② 서비스 전담
- 얻는 것: 내부 헤더를 믿지 않아도 된다. Gateway를 우회한 요청도 막는다(ADR 0008이 다루는 T1 위협).
- 얻는 것: Reservation은 입장 토큰 발급자라 키를 이미 갖고 있다. HMAC 검증은 마이크로초 단위라 성능 부담도 작다.
- 잃는 것: 좌석 조회처럼 경로만으로 막을 수 있는 요청도 서비스까지 들어온다. 오픈 순간 매크로가 위조 토큰으로 두드리면 그 부하를 서비스와 DB 커넥션 풀 앞단이 받는다.
- 잃는 것: "인증은 Gateway에서 끝낸다"는 SA 7-2 원칙과 어긋나 팀 합의가 필요하다.
- 맞는 경우: 내부망 신뢰를 낮추는 보강(ADR 0009 방향)을 MVP 범위에 넣기로 했을 때.

#### ③ 분담
- 얻는 것: 비용이 큰 검사(서명)는 앞단에서 걸러낸다. 본문 비교는 본문을 이미 가진 쪽이 한다. 변경 범위도 가장 작다.
- 잃는 것: 규칙이 두 곳에 나뉜다. 한쪽만 테스트하면 구멍이 생기고, 같은 403 의미를 양쪽이 지켜야 한다.
- 잃는 것: 내부 헤더를 위조할 수 있는 환경이면 회차 비교가 무력해진다. 다만 같은 환경이면 `X-User-Id`도 위조되므로 새로 생기는 위험은 아니다.
- 맞는 경우: 지금 SA의 신뢰 모델을 유지하면서 API를 바꾸지 않을 때. MVP 기본값.

#### ④ 경로 변경
- 얻는 것: 회차가 리소스 경로에 드러나 Gateway가 본문 없이 끝까지 판단한다. "회차 하위의 예매"라는 REST 구조로도 자연스럽다.
- 얻는 것: 이후 회차 기반 API가 늘어도 규칙 하나로 덮는다.
- 잃는 것: 본문의 `scheduleId`를 없애야 한다. 남겨 두면 경로와 본문을 다시 비교해야 해서 ③과 같아진다.
- 잃는 것: 접수형 `Location`, 결제 흐름 문서, 부하 테스트 스크립트까지 경로가 퍼져 있어 문서·계약 수정 범위가 가장 크다.
- 맞는 경우: 아직 클라이언트와 부하 테스트가 경로에 묶이기 전이고, 팀이 API 정리를 함께 하기로 했을 때.

#### 덧붙임: 클라이언트가 `X-Schedule-Id` 헤더를 보내는 안
이 안으로는 Gateway가 토큰 회차와 헤더만 비교할 수 있다. 하지만 헤더와 본문이 같다는 보장이 없어서 서비스가 다시 본문과 비교해야 한다. 결국 ③에 헤더 하나를 더한 것이라 얻는 것이 없다.

### 선택 기준 요약
- 신뢰 모델을 지금처럼 유지하고 변경 범위를 최소로 하려면 ③이다.
- 검증을 한 곳에 모으고 API 정리 비용을 감수할 수 있으면 ④다.
- 내부 헤더 신뢰를 줄이는 보안 보강이 목표면 ②, 또는 ③에 서비스 재검증을 더한다.
- ①은 다른 안보다 나은 점이 "한 곳"뿐인데, 그 장점은 ④가 더 싸게 준다.

## 이 프로젝트에서는
- 설계 검토 [07-reservation-system-review.md](../../../sa-review/07-reservation-system-review.md) G2에서 같은 결론(방안 A)을 냈고 팀 확인 대기 중이다.
- 계약 문서 [design/reservation/contracts.md](../../../design/reservation/contracts.md) 5-2가 대기열·Gateway 담당(권영은)과의 경계로 두 방식을 열어 두었다. 방안 A로 확정하면 Gateway 필터 구현과 Reservation 선점 컨트롤러의 403 처리가 각각 완료 기준에 들어간다.
- 입장 토큰은 Reservation(대기열 모듈)이 발급하므로 Reservation이 키를 갖고 직접 재검증하는 것도 가능하다. 다만 MVP에서는 헤더 신뢰 모델과 맞추는 쪽이 단순하다.

## 면접 포인트
- Gateway에 무엇을 두고 무엇을 서비스에 두는가: 요청의 형태(헤더, 경로)만 보고 판단할 수 있는 횡단 관심사는 Gateway, 본문과 도메인 지식이 필요한 규칙은 서비스. 이유로 WebFlux 본문 버퍼링 비용과 스키마 결합을 든다.
- 내부 헤더를 믿어도 되는가: 서명이 없으므로 Gateway가 외부 헤더를 제거하고 서비스가 외부에 노출되지 않는다는 전제에서만 믿는다. 더 강하게 하려면 서비스가 토큰을 직접 재검증하거나 내부 서명 토큰을 쓴다.
