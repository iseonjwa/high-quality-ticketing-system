# 좌석 선점 API에서 멱등 재요청(Idempotency Retry)이 뜻하는 것과 케이스별 응답 설계

## 질문
ISE-21(좌석 선점 결과 형식 정의)에서 말하는 "멱등 재요청"에 대해 상세히 설명해 달라.

## 짧은 답
멱등 재요청은 사용자가 `[선택 완료]` 버튼을 연타하거나 네트워크 지연(타임아웃)으로 응답을 못 받아 **같은 `Idempotency-Key` 헤더를 달고 선점 요청을 두 번 이상 보내는 상황**을 뜻한다. 서버는 이 재요청을 새 선점 시도로 처리하지 않고, 첫 번째 요청의 처리 결과(성공·거절·처리 중)를 그대로 돌려주어 중복 예매 생성과 `409 SEAT_ALREADY_HELD` 오판정을 막아야 한다.

## 자세히

### 1. 왜 좌석 선점에 멱등키와 재요청 처리가 필요한가?
티켓 오픈 정각에는 서버 응답이 느려지기 쉽다. 사용자가 좌석 `[1023, 1024]`를 고르고 `[선택 완료]`를 눌렀을 때 다음 두 가지 일이 흔히 벌어진다.

1. **네트워크 타임아웃 후 재시도**: 서버는 좌석 `[1023, 1024]`를 정상적으로 선점(`HELD`)하고 커밋했는데, 응답이 가는 도중 네트워크가 끊기거나 Gateway 타임아웃(3초)이 났다. 클라이언트는 실패한 줄 알고 같은 요청을 다시 보낸다.
2. **버튼 연타(따닥)**: 답답한 사용자가 버튼을 연속으로 두 번 누른다.

만약 멱등 처리가 없다면 두 번째 요청이 도착했을 때 다음과 같은 문제가 생긴다.
- 이미 첫 번째 요청이 좌석 `[1023, 1024]`를 `HELD`로 바꿔 놓았기 때문에, 두 번째 요청은 **내가 방금 잡은 좌석인데도 `409 SEAT_ALREADY_HELD`(이선좌)를 받고 튕겨 나간다.** 사용자는 선점에 성공해 놓고도 실패 화면을 보게 되어 결제 화면으로 넘어가지 못한다.
- 또는 다른 좌석으로 요청이 중복 처리되면 한 사람의 매수 한도(`user_schedule_quotas`)가 두 번 차감된다.

이를 막기 위해 클라이언트는 `[선택 완료]` 시점에 고유한 UUID(`Idempotency-Key`)를 만들어 헤더에 넣고, 재시도할 때도 같은 UUID를 보낸다.

### 2. 멱등 재요청에서 정해야 하는 4가지 세부 시나리오
단순히 "같은 키면 같은 응답"이라고만 정하면 실제 구현에서 빈틈이 생긴다. 다음 4가지 경우를 나눠서 규칙을 정해야 한다.

| 시나리오 | 조건 | 기대 동작과 이유 |
|---|---|---|
| **① 본문 위변조·오용** | 같은 `user_id` + 같은 `Idempotency-Key`인데 `scheduleId`나 `seatIds`가 첫 요청과 다름 | **`409 IDEMPOTENCY_KEY_REUSED`**. 클라이언트가 새 요청인데 키를 새로 안 만들었거나 잘못 재사용한 경우다. 좌석 배열은 순서만 다를 수 있으므로 정렬(`sort`) 후 비교한다. |
| **② 다른 사용자의 우연한 키 충돌 또는 도용** | `Idempotency-Key`(`request_id`)는 같은데 요청한 `user_id`가 다름 | UUID v4라 우연히 겹칠 확률은 없지만, 남의 `request_id`를 넣은 경우다. 다른 사람의 예매 정보를 노출하면 안 되므로 **`409 IDEMPOTENCY_KEY_REUSED`**(또는 `403 FORBIDDEN`)로 거절한다. |
| **③ 첫 요청이 완료된 뒤 재요청** | 같은 `user_id` + 같은 키 + 같은 본문이고 첫 요청이 이미 끝남 | 첫 요청이 `HELD`로 성공했다면 DB에서 기존 예매를 읽어 **`201 Created`와 동일한 선점 응답(결제 토큰 포함)**을 다시 내려준다. (단, 이미 선점 시간이 지나 `EXPIRED` 등 다른 상태로 바뀐 뒤에 재요청이 오면 어떻게 할지 정해야 한다.) |
| **④ 첫 요청이 아직 처리 중일 때 동시 도착** | 버튼 연타로 첫 요청의 트랜잭션이 끝나기 전에 두 번째 요청이 도착 | **동기형**: 첫 요청의 행 잠금이나 PK 제약이 풀릴 때까지 잠깐 대기한 뒤 완료된 결과를 읽어 반환하거나, PK 충돌 시 재조회해 결과를 돌려준다.<br>**접수형(M4)**: `seat_hold_requests` 상태가 아직 `REQUESTED`이므로 **`202 Accepted`**와 폴링 경로(`Location`)를 그대로 돌려준다. |

### 3. 동기형 선점에서 "실패(409) 요청의 멱등 기록" 딜레마
가장 주의해야 할 설계 포인트는 **첫 요청이 `409 SEAT_ALREADY_HELD`(이선좌)로 실패했을 때**다.
- **방식 A (실패 시 전체 롤백 — 추천)**: 동기형 선점에서 좌석 경합으로 실패하면 트랜잭션을 롤백한다(`seat_hold_requests` 행도 함께 롤백됨). 만약 같은 키로 재요청이 오면 다시 선점을 시도하고 여전히 팔린 좌석이면 똑같이 `409 SEAT_ALREADY_HELD`가 나온다. 실패 건까지 DB에 커밋하지 않아 쓰기 부하가 줄고 SA 12-7절("0행 → 롤백, 409")과 정확히 일치한다.
- **방식 B (실패도 `REJECTED`로 커밋)**: 별도 트랜잭션(`REQUIRES_NEW`)으로 `seat_hold_requests(REJECTED)`를 남긴다. 접수형(M4)에서는 비동기 소비자가 결과를 기록해야 하므로 필수지만, 동기형(M2)에서는 실패할 때마다 DB INSERT가 남아 오픈 정각 이선좌 폭주 때 DB 쓰기 부하만 늘어난다.

## 이 프로젝트에서는
[SA MASTER.md](../../core/SA%20MASTER.md) 11-1절, 11-5절, 12-3절에서 좌석 선점의 멱등성을 일반 `idempotency_records` 테이블 대신 **`seat_hold_requests` 테이블의 PK(`request_id = Idempotency-Key`)**로 처리하도록 설계했다(결정 기록 #17, #33).

- 테이블: `reservation` DB의 `seat_hold_requests` (`request_id UUID PK`, `user_id`, `schedule_id`, `seat_ids BIGINT[]`, `status`, `reservation_id`, `reason_code`)
- 또한 `reservations` 테이블에도 `request_id UUID NOT NULL UNIQUE` 컬럼이 있다.
- 따라서 ISE-21에서는 위 표의 **①~④ 시나리오별 상태 코드와 응답 형식**, 그리고 **동기형에서 실패(409) 시 `seat_hold_requests`를 롤백할지 여부**를 확정해 문서에 적으면 된다.

## 면접 포인트
- **Q. 왜 조회나 삭제가 아닌 좌석 선점(POST)에 멱등키(`Idempotency-Key`)를 도입했나요? 이미 좌석 중복 방지 제약(부분 유니크 인덱스)이 있지 않나요?**
  - **A.** 부분 유니크 인덱스(`D2`)와 조건부 UPDATE는 **"한 좌석이 두 번 팔리는 것(서버 정합성)"**은 막아주지만, **"네트워크 타임아웃으로 응답만 못 받은 정상 사용자가 재시도했을 때 자기가 잡은 좌석 때문에 `409 이선좌`를 받고 결제 화면으로 못 넘어가는 문제(사용자 경험)"**와 **"한 사용자가 따닥 연타로 다른 좌석을 중복 선점해 매수 한도를 소진하는 문제"**는 막지 못합니다. 그래서 클라이언트가 생성한 `Idempotency-Key`(`requestId`)를 기준으로 기존 선점 결과를 그대로 재응답하도록 설계했습니다.
- **Q. 결제 멱등성(`idempotency_records`)과 선점 멱등성(`seat_hold_requests`)의 테이블을 나눈 이유가 있나요?**
  - **A.** 선점은 M4에서 Kafka 비동기 접수형(`202 Accepted` → 폴링 조회)으로 전환할 때 "접수 요청의 현재 상태(`REQUESTED`·`HELD`·`REJECTED`)"를 조회하는 접수 원장이 필요합니다. 멱등키를 그대로 `request_id(PK)`로 쓰면 별도 멱등 테이블 없이 접수 요청 테이블 하나로 동기형 멱등 처리와 비동기형 상태 조회를 동시에 해결할 수 있어 테이블과 쓰기 횟수를 줄였습니다.
