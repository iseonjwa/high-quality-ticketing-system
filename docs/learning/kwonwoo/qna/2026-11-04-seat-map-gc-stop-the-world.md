# K1 측정의 Stop-the-World는 부하 테스트 환경 탓인가, 실제 환경에서도 생기는가

## 질문
그럼 이게 부하테스트라서 stop the world가 발생한 거야? 아니면 실제 환경에서도 동일하게 발생할 수 있는 문제인 거야?

## 짧은 답
부하 테스트라서 생긴 문제가 아니다. 부하 테스트는 티켓 오픈 때 실제로 들어올 트래픽을 흉내 낸 것뿐이다. 같은 트래픽이 실제로 오면 같은 일이 생긴다.

다만 이번 측정 환경이 증상을 더 빨리, 더 심하게 만든 것은 맞다. 나눠 보면 다음과 같다.
- 원인(코드): 좌석 조회 한 번이 15,000석을 엔티티로 다 만들고 약 830KB JSON으로 바꾼다. 요청이 늘면 메모리 사용이 그만큼 같이 는다. 실제 환경에서도 같다.
- 증폭(환경): 힙 256MB, 단일 스레드 Serial GC, 노트북 한 대. 실제 배포에서는 한계점이 더 높아지지만 사라지지는 않는다.

## 자세히

### 1. Stop-the-World는 언제 문제가 되나
GC는 종류와 상관없이 잠깐씩 애플리케이션 스레드를 멈춘다(Stop-the-World). G1 같은 GC는 평소 이 정지를 수 ms로 짧게 유지한다. 그래서 STW가 있다는 것 자체는 문제가 아니다.

문제는 **살아 있는 객체가 힙보다 커질 때**다. 처리 중인 요청이 들고 있는 객체는 GC가 치울 수 없다. 요청이 몰려 그 양이 힙을 채우면 다음 일이 반복된다.
1. GC가 돌아도 공간이 거의 안 생긴다.
2. 곧 다시 Full GC가 돈다.
3. 앱이 일할 시간이 없어진다.
4. 요청이 더 느려져 더 오래 메모리를 쥔다.

이 악순환을 GC thrashing(GC 폭주)이라고 한다. 이번 측정에서 6분 중 101초가 정지였고, 한 번에 29초까지 멈춘 것이 이 상태다.

### 2. 왜 실제 환경에서도 생기나
필요한 메모리는 대략 `요청 하나가 쓰는 메모리 × 동시에 처리 중인 요청 수`다.
- 요청 하나가 쓰는 메모리는 코드가 정한다. 좌석 엔티티 15,000개, 공연장 좌석 엔티티 15,000개, DTO 15,000개, 830KB 문자열이 들어간다.
- 동시 요청 수는 트래픽이 정한다. 티켓 오픈 때 대기열이 초당 수십~100명을 들여보내고 조회 한 번이 1초 걸리면, 동시에 수십~100건이 처리 중이다.

정확한 요청당 메모리는 아직 재지 않았다. 요청당 수~수십 MB로만 잡아도 100건이면 수백 MB~수 GB가 된다. 힙을 1~2GB로 올리면 한계점이 초당 1~2건에서 몇 배 오르겠지만, 목표인 초당 100~200건에는 여전히 못 미칠 가능성이 크다. 이 부분은 다음 측정(P0')에서 확인할 추정이다.

### 3. 이번 환경이 키운 부분
| 요인 | 이번 측정 | 실제 배포에서 |
|---|---|---|
| 힙 | 256MB(로컬 기동용 값) | 보통 더 크게 잡는다. 한계점이 오른다 |
| GC | Serial. 컨테이너 메모리가 작아 JVM이 자동 선택했다. 정리를 스레드 하나로 하므로 정지가 길다 | G1(JVM 기본값). 여러 스레드로 정리해 정지가 짧다 |
| 같은 기기 | k6, Gateway, DB, Kafka 등이 노트북 CPU를 나눠 쓴다 | 서버가 분리된다 |
| 프로필 | `local`(추적 100%, 요청 로그) | 추적 10% |

이 요인들은 "몇 명부터 무너지나"를 바꾼다. "트래픽이 늘면 메모리가 같이 늘어 결국 무너진다"는 구조는 바꾸지 못한다.

### 4. 뒤이은 연쇄 실패도 실제에서 흔하다
앱이 멈추면 헬스 체크와 Eureka 갱신도 같이 멈춘다. 그러면 Gateway가 "살아 있는 서버가 없다"고 보고 503을 낸다. Gateway가 포기한 요청도 서버는 끝까지 처리하므로, 부하가 끝나도 쌓인 요청을 비우느라 회복이 늦다. 운영 장애에서 자주 보이는 모양이고, 쿠버네티스 같은 환경에서는 헬스 체크 실패로 재시작이 반복되기도 한다.

### 5. 어떻게 확인하나
힙과 GC를 배포 수준(예: 1~2GB, G1)으로 맞추고 같은 K1을 다시 잰다(계획 문서 5-1절의 P0').
- 한계점이 조금만 오르면 코드(좌석 조회) 문제가 확정된다.
- 목표를 넘으면 이번 결과는 환경 탓이었다고 고쳐 적는다.

어느 쪽이든 좌석 조회가 요청마다 전체를 새로 만드는 구조는 트래픽에 비례해 비싸다. 그래서 P4(엔티티 없이 조회, 캐시, 응답 줄이기)는 해야 하는 개선이다.
