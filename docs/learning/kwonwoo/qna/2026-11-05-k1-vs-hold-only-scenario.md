# 기존 K1 부하 테스트는 어떻게 진행됐고, 선점만 떼어 재는 방식(K1-H)은 무엇이 다른가

## 질문
그럼 기존 방식은 부하테스트가 어떤 식으로 진행이 됐었고 지금 방식은 어떻게 다른거야?

맥락: K1(초당 100명)에서 좌석 조회가 먼저 무너져 P4(좌석 조회 경량화)를 먼저 하기로 했다. P4는 반효승 담당(ISE-189)이라 시간이 걸린다. 그동안 선점 경로만 따로 재서 P1~P3의 효과를 수치화하자는 제안(K1-H, 가칭)이 나왔다.

## 짧은 답
- 기존 K1은 실제 사용자 흐름을 그대로 흉내 낸다. 사용자마다 좌석 조회 → 고민 → 선점을 하고, 409가 나면 좌석 조회부터 다시 한다. 요청 대부분의 비용이 좌석 조회(15,000석, 약 830KB)에 있어 결과가 좌석 조회 한계로 정해진다.
- K1-H는 좌석 조회를 측정 시작 전에 한 번만 한다. 반복에서는 그 목록에서 좌석을 골라 선점만 보낸다. 서버에 가는 부하가 선점 경로뿐이라 P1~P3의 효과가 숫자로 보인다.
- 둘은 묻는 질문이 다르다. K1은 "서비스 전체가 버티는가", K1-H는 "선점 경로가 단계마다 얼마나 좋아졌는가"다. K1-H 결과를 K1 통과로 쓰면 안 되고, 최종 확인은 P4 뒤에 K1로 한다.

## 자세히

### 1. 기존 K1의 흐름 (`reservation-service/k6/k1-seathold.js`)

부하 모양: 열린 모델(`constant-arrival-rate`). 응답 속도와 상관없이 초당 100명이 새로 들어오고 300초 동안 이어진다. 총 3만 명이며, 한 사용자는 한 번만 쓴다.

사용자 한 명(반복 하나)의 흐름:

```text
GET /schedules/{id}/seats          ← 15,000석 전체, 약 830KB
  매진이면 끝
sleep 1~3초 (고민)
좌석 1~2개 고름 (70%는 앞쪽 인기 구역)
POST /schedules/{id}/holds
  201 → 끝(성공)
  409 → sleep 0.5~1초, GET seats부터 다시 (최대 2번 재시도)
```

- 한 사용자가 시도할 때마다 좌석 조회를 한 번씩 한다. 초당 좌석 조회는 최소 100건이고, 409 재시도가 늘수록 더 늘어난다.
- 좌석 조회 한 건은 15,000개 엔티티를 읽고 변환하는 동안 커넥션 5개 중 하나를 쥔다. 측정에서 서버는 초당 약 12건만 처리했다.
- 그래서 선점 요청은 거의 서버까지 가지 못했다. P1(풀)이나 P2·P3(선점 트랜잭션)을 넣어도 "선점 0건 → 0건"이라 효과를 볼 수 없다.

### 2. K1-H의 흐름 (제안)

```text
[setup, 측정 전 1회] GET seats → 좌석 ID 목록을 기억
[반복]
sleep 1~3초 (고민)
목록에서 좌석 1~2개 고름 (인기 구역 쏠림은 그대로)
POST /schedules/{id}/holds
  201 → 끝
  409 → sleep 0.5~1초, 목록에서 다른 좌석을 골라 다시 (최대 2번)
```

같게 두는 것: 열린 모델, 초당 100명, 300초, 토큰 서명 방식, 재시도 횟수, 인기 구역 쏠림, P0''(배포 메모리 + G1) 환경, 선점 지표(`hold_duration`, `hold_results`).

바뀌는 것: 반복 안의 `GET seats`가 빠진다. 서버 부하는 선점 경로(입장 토큰 확인 → 트랜잭션 → 좌석 잠금·갱신 → 매수 반영 → 결제 토큰)뿐이다.

### 3. 차이에서 생기는 주의점

| 항목 | K1 | K1-H | 해석할 때 |
|---|---|---|---|
| 보는 대상 | 좌석 조회 + 선점 | 선점만 | K1-H 수치는 선점 경로의 상한이다 |
| 좌석 정보의 신선도 | 시도마다 최신 | 측정 시작 시점에 고정 | 판매가 진행될수록 이미 팔린 좌석을 고르는 409가 K1보다 많아진다 |
| 매진 판단 | 응답에 선택 가능 좌석이 없음 | 알 수 없음 | 매진 뒤에는 모든 요청이 409다. 409 경로의 비용을 잴 수 있지만, 매진 시각은 DB의 마지막 선점 성공 시각으로 정한다 |
| 커넥션 경쟁 | 좌석 조회와 선점이 같은 풀을 나눠 씀 | 선점이 풀을 독차지 | 실제보다 좋게 나온다. P4 뒤 K1에서 둘이 섞일 때 다시 확인해야 한다 |
| 결과의 용도 | 서비스 전체 판정 | 단계별 비교(P1 → P2 → P3) | K1-H 표와 K1 표를 따로 둔다 |

- 409가 늘어나는 것은 단점이면서 장점이다. 경합이 K1보다 세져 잠금·충돌 처리(정합성 단계 S1~S4의 대상)를 더 강하게 시험한다.
- 이미 팔린 좌석을 고르는 비율을 줄이고 싶으면, 선택을 목록 전체에 퍼뜨리거나 VU마다 목록의 다른 구간에서 시작하게 할 수 있다. k6 VU끼리는 상태를 나누지 않아 "팔린 좌석 빼기"는 할 수 없다.

### 4. 두 시나리오를 함께 쓰는 순서

```text
K1-H : P0''(기준) → P1 → P2 → P3        선점 경로 개선을 단계별로
K1   : P0'' → P4a → P4b → P4c → (P1~P3 반영 상태) 전체 판정
```

이렇게 하면 "좌석 조회 병목은 P4로 넘기고, 그동안 선점 경로는 조회와 떼어 단계별로 쟀다. 마지막에 둘을 합쳐 K1로 확인했다"는 흐름이 된다.

## 실무 팁
- 부하 테스트에서 한 경로가 먼저 막히면 뒤 경로는 측정되지 않는다. 경로를 나눠 재는 시나리오를 두면 병목이 겹쳐 생기는 "0 → 0" 비교를 피할 수 있다.
- 나눠 잰 결과는 그 경로의 상한일 뿐이다. 발표나 면접에서는 "따로 쟀다"와 "합쳐서 확인했다"를 같이 말해야 설득력이 있다.
