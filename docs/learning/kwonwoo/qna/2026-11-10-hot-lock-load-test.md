# 잠금이 걸린 데이터에 트래픽을 몰아 보내는 부하 테스트로 무엇을 얻을 수 있나

## 질문
지인이 "락이 걸려 있는 데이터에 트래픽을 쏴도 재미있는 결과를 뽑을 수 있다"고 했다. 그런 테스트를 하면 얻을 수 있는 것이 있을까?

## 짧은 답
있다. 이 테스트로는 잠금 하나가 시스템 전체로 얼마나 번지는지(폭발 반경)를 볼 수 있다. 지금 K1은 같은 좌석을 두고 경쟁은 많이 하지만(409 약 77%), 선점 트랜잭션이 수 ms라 잠금을 오래 기다리는 일이 거의 없다. 그래서 "오래 잡힌 잠금"은 아직 재지 않은 영역이다. 오래 잡힌 행에 요청이 몰리면 다음 일이 차례로 생긴다.
1. 기다리는 요청이 DB 커넥션을 쥔 채 멈춘다.
2. 커넥션 풀이 비면 그 행과 상관없는 요청(좌석 조회, 다른 좌석 선점)까지 실패한다.

이 테스트로 얻는 것은 세 가지다. 첫째, S3(`lock_timeout` 500ms)가 이 번짐을 어디까지 막는지 수치로 보여 줄 수 있다. 둘째, 500ms라는 값을 데이터로 정할 수 있다. 셋째, "커넥션을 잡기 전에 거절해야 한다"는 다음 개선의 근거가 된다.

## 자세히

### 왜 K1에서는 이 현상이 안 보였나
- 선점 트랜잭션 하나는 수 ms 안에 끝난다. 같은 좌석을 노린 요청은 앞 트랜잭션이 커밋할 때까지만 기다리고, 커밋 뒤 행을 다시 확인해 409로 끝난다.
- 그래서 측정 중 잠금 대기 세션 수(`stats.txt`의 `lock_waits`)가 작았고, S3는 K1에서 직면하지 않았다.
- 잠금이 오래 잡히는 경우는 따로 만들어야 한다.

### 실제로 잠금이 오래 잡히는 경우
- 인기석에 오픈 첫 1초 동안 요청이 몰려, 같은 행 앞에 줄이 길게 선다.
- 만료 스케줄러나 대사가 여러 좌석 행을 잡고 있는 동안 선점이 같은 행을 노린다.
- 느린 트랜잭션(GC 정지, 외부 호출, 관리자 작업)이 행을 잡은 채 멈춘다.

### 무엇을 얻을 수 있나
| 얻는 것 | 내용 |
|---|---|
| 폭발 반경 | 잠긴 행을 노린 요청이 커넥션을 쥐고 기다리면, 풀 10개가 차는 순간 상관없는 좌석 조회·선점도 대기 시한(1초) 초과 500이나 Gateway 504로 실패한다. 잠금 하나가 전체 장애로 번지는지를 본다 |
| S3의 효과와 한계 | S3 전에는 잠금이 풀릴 때까지 기다린다. S3 뒤에는 500ms에서 409로 끝난다. 다만 계산하면 한계가 보인다. 풀 10개가 각각 최대 0.5초씩 묶이면, 잠긴 행으로 가는 요청은 인스턴스당 초당 약 20건(10 ÷ 0.5)만 받아도 풀이 다 찬다. 그보다 많이 몰리면 S3가 있어도 다른 요청이 커넥션을 못 받는다 |
| `lock_timeout` 값의 근거 | 100·500·1,000ms로 바꿔 가며 잰다. 잠긴 행 요청의 성공률과, 상관없는 요청의 성공률·p95가 어떻게 바뀌는지 보고 값을 정한다. 지금 500ms는 SA 9-4의 값이다 |
| 잠금 방식 비교 | 기다림(`FOR UPDATE`), 즉시 실패(`NOWAIT`), 잠긴 행 건너뛰기(`SKIP LOCKED`)를 비교한다. 사용자에게 주는 의미가 다르다. 기다림은 "늦게라도 될 수 있음", 즉시 실패는 "다른 좌석을 고르세요", 건너뛰기는 "옆자리로 자동 배정"이다 |
| 데드락 | 여러 좌석을 서로 반대 순서로 잡는 요청을 부하로 섞어, `pg_stat_database.deadlocks`가 느는지 본다. S3의 `ORDER BY id`가 부하 상태에서도 데드락을 막는지 확인한다 |
| 다음 개선의 근거 | 잠긴 행 요청이 커넥션을 쓰기 전에 거절되면 번짐이 사라진다. Redis로 이미 잡힌 좌석을 먼저 거절하는 방안, 동시 처리 상한(벌크헤드)이 그 방법이다. 이 테스트가 그 효과를 숫자로 보여 준다 |

### 해 볼 만한 설계 (K3 안)
1. **잠금 쥐기:** 측정 중 별도 세션에서 좌석 100개를 30초 동안 잠근다(`BEGIN; SELECT ... FOR UPDATE; SELECT pg_sleep(30); COMMIT;`). 동시에 K1 L(초당 100명)을 건다. 일부 사용자는 그 좌석을 노리게 한다.
2. **인기석 집중:** 모든 사용자가 같은 좌석 10개만 노리게 해 초당 200명을 보낸다. 커밋 직후 다시 줄이 서는 상황이다.
3. **비교:** S3 전(A)과 뒤(B)를 같은 조건으로 잰다.
4. **볼 값:**
   - 잠긴 좌석 요청: 409까지 걸린 시간
   - 상관없는 요청: 좌석 조회와 다른 좌석 선점의 성공률·p95
   - 서버 쪽: 커넥션 대기, `lock_waits`, 5xx, 데드락 수

예상(가설): A에서는 잠금을 쥔 30초 동안 풀이 차서 상관없는 요청까지 실패한다. B는 잠긴 좌석 요청이 500ms에 409로 끝나 번짐이 줄어든다. 다만 잠긴 좌석으로 초당 20건 넘게 몰리면 B도 풀이 찬다. 이 한계가 드러나는 지점이 발표에서 가장 재미있는 결과가 될 것이다.

### 실제로 재 본 결과 (2026-11-10, K3 안 1번)
부하 30초 뒤 인기 구역 약 2,200석을 33초 동안 잠갔다. S3 전(A)과 뒤(B)를 1회씩 쟀다(측정 브랜치 STEPS.md "동시성 부하 2차 실측").

| 잠금 중 | A (S3 전) | B (S3) |
|---|---|---|
| 좌석 조회 성공 (잠금과 상관없는 요청) | 25.0% | 77.5% |
| 처리한 선점 요청 | 1,235건 | 4,310건 |
| 500 (커넥션 대기 시한 초과) | 3,171건 | 2,161건 |

- 예상대로 잠금 하나가 상관없는 좌석 조회까지 무너뜨렸다. S3는 번짐을 크게 줄였지만, 풀 ÷ 대기 상한(초당 약 20건)보다 많이 몰려 500이 남았다.
- 잠금이 풀리자 둘 다 30초 안에 회복했다.

### 주의할 점
- "잠금을 30초 쥔다"는 인위적인 조건이다. 만료 스케줄러를 켠 X 측정(2026-11-10)에서는 잠금 대기 세션이 A·B 모두 0이었다. 만료 트랜잭션이 짧아 실제 운영 흐름만으로는 긴 잠금이 생기지 않았다. 그래서 K3은 "평소에는 없지만 느린 트랜잭션 하나가 생기면 어디까지 번지나"를 보는 장애 주입 테스트로 설명해야 한다.
- Gateway 차단기가 먼저 열리면 서버 안의 번짐이 가려진다. 측정 환경의 차단기 완화(`k6measure`)를 그대로 두고 잰다.

## 덧붙인 질문: 잠금이 걸린 테이블에 트래픽을 집중시켜 쏴 봤나

일부만 했다. 2026-11-10 측정(K)은 테이블 전체가 아니라 **행 잠금**이었다. 앞쪽 3,000석 중 선택 가능한 약 2,200석을 `FOR UPDATE`로 잡았다. 트래픽도 그 좌석에 일부러 몰지 않았다. K1의 원래 쏠림을 그대로 썼다. 사용자 70%가 앞쪽 10%(약 1,500석, 잠금 범위 안)를 고르고, 30%는 전체에서 고른다.

| 해 본 것 | 아직 안 한 것 |
|---|---|
| 행 잠금(약 2,200석, 33초) + 자연 쏠림(70%가 잠금 범위) | 트래픽을 잠긴 좌석에 100% 몰기(예: 인기석 10개에 초당 200명) |
| 초당 100명 | 도착률을 올려 가며 번짐이 시작되는 지점 찾기 |
| | 테이블 잠금(`LOCK TABLE schedule_seats ...`) |

**측정에서 함께 보인 것:** 좌석 조회는 행 잠금에 막히지 않는다. PostgreSQL은 읽기에 잠금을 걸지 않기 때문이다(MVCC). 그런데도 A에서 잠금 중 좌석 조회 성공이 25%로 떨어졌다. 원인은 잠금 자체가 아니었다. 잠금을 기다리는 선점이 커넥션 풀을 다 썼기 때문이다. 그래서 "잠긴 행 → 커넥션 고갈 → 상관없는 요청 실패"가 번짐의 경로다.

**더 하면 얻는 것:**
- 100% 집중: 잠긴 좌석으로 가는 요청 비율을 올리면, B(S3)도 풀이 차는 지점(초당 약 20건)을 뚜렷하게 넘긴다. 계산한 한계를 실측으로 확인할 수 있다.
- 테이블 잠금: 잠금 모드에 따라 결과가 갈린다. `EXCLUSIVE`는 쓰기만 막아 선점 전체가 기다린다. `ACCESS EXCLUSIVE`는 읽기까지 막아 좌석 조회도 기다린다. 운영에서 마이그레이션(DDL)이나 `VACUUM FULL`이 판매 중에 돌면 생기는 상황이다. 행 잠금보다 번짐이 훨씬 크고 빠를 것이다(가설). 운영 규칙("판매 중 DDL 금지", `lock_timeout`을 건 마이그레이션)의 근거가 된다.

## 덧붙인 결과: 잠긴 행에 트래픽을 100% 몰아 도착률을 올린 스트레스 (2026-11-10)

인기석 10석을 측정 내내 잠그고 선점을 그 10석에만 초당 10 → 320명으로 보냈다. 같이 잠금과 상관없는 요청을 보냈다(측정 브랜치 STEPS.md "잠긴 행 집중 2차 실측").
- **장애는 생긴다.** A(대기 상한 없음)는 초당 10명에서 바로 같은 서비스의 공연 목록까지 98% 실패했다. B(S3)는 초당 10명은 버티고 초당 20명부터 무너지기 시작했다. 위에서 계산한 한계(풀 10 ÷ 0.5초 = 초당 20건)와 같다.
- **다른 서비스로는 번지지 않는다.** user-service와 payment-service는 모든 단계에서 실패 0~1.1%, p95 4ms 이하였다. 서비스마다 커넥션 풀과 DB가 따로라 장애가 reservation-service 안에 갇혔다.
- **유령 선점:** 잠금이 풀린 순간 A 9건, B 8건의 예매가 생겼는데 클라이언트는 201을 받지 못했다. 클라이언트가 포기한 뒤 서비스 앞에 쌓인 요청이 늦게 처리됐다.
- 처음 회는 잠금을 ID 순서로 골라 k6가 노린 10석 중 1석만 잠겼다. 좌석 ID가 응답 순서와 다르기 때문이다. 이것이 오히려 "요청의 10%만 잠긴 행으로 가는" 조건이 되었고, B가 초당 160명까지 버텨 같은 한계 계산을 다시 확인했다.

## 이 프로젝트에서는
- 잠금 대기 상한과 잠금 순서: S3(`3b9b0bf`), 트러블슈팅 TS-67.
- 잠금 대기 세션 수는 `step-run.sh`가 10초마다 `stats.txt`에 남긴다(`lock_waits`).
- 동시성 테스트 C3이 잠금을 2초 쥔 상태에서 같은 좌석을 노린 5명의 대기를 잰다. 위 K3은 그것을 부하 규모로 키운 것이다.

## 면접 포인트
- **`lock_timeout`만으로 충분한가?** 대기 시간에 상한을 둘 뿐, 기다리는 동안 커넥션을 쥐는 것은 같다. 풀 크기 ÷ 대기 상한보다 많이 몰리면 풀이 찬다. 커넥션을 쓰기 전에 거절하는 장치(캐시 사전 확인, 동시 처리 상한)가 함께 있어야 한다.
- **잠금 경합 테스트에서 무엇을 봐야 하나?** 잠긴 행 요청만 보지 않는다. 그 행과 상관없는 요청이 영향을 받는지(폭발 반경)를 본다. 장애는 대개 그 번짐에서 커진다.
- **`NOWAIT`, `SKIP LOCKED`, 기다림은 어떻게 고르나?** 성능보다 사용자에게 주는 의미로 고른다. 좌석 선점처럼 "그 좌석"이어야 하면 짧게 기다리다 실패하고, 작업 큐처럼 아무 행이나 되면 `SKIP LOCKED`를 쓴다(S4 만료가 그 예다).
