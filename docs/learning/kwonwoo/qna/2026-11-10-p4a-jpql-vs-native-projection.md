# 좌석 조회 P4a에서 dev 코드와 측정 브랜치 코드는 무엇이 다른가

## 질문
dev에 있는 좌석 조회 코드(P4a, `a40b01d`)와 측정에 쓴 코드(`50a365d`)는 무엇이 다른가?

## 짧은 답
두 코드 모두 엔티티를 만들지 않고, 공연장 좌석과 조인한 15,000행을 같은 순서로 읽는다. 응답 JSON도 같다. 다른 것은 행을 읽어 자바 객체로 만드는 방식이다. 측정 브랜치는 네이티브 SQL로 읽고, 선택 가능 여부를 DB에서 참·거짓 한 열로 계산한다. dev는 JPQL 생성자 식으로 읽고, 좌석 상태와 등급 두 열을 받아 자바에서 판단한다. DB가 쿼리를 처리하는 시간은 거의 같다(약 17.8ms 대 18.3ms). 차이는 DB가 보내는 데이터 양과 JVM이 행마다 하는 변환에 있다.

## 자세히

### 코드 차이

| | 측정 브랜치 (`50a365d`) | dev (`a40b01d`) |
|---|---|---|
| 쿼리 | 네이티브 SQL, `List<Object[]>` | JPQL `select new ...ScheduleSeatRow(...)` |
| 읽는 열 | 7열. 마지막 열 `available`은 `status = 'AVAILABLE' AND grade <> 'LOTTERY'`을 DB가 계산 | 8열. 회차 좌석 `grade`, `status`를 그대로 받음 |
| 선택 가능 판단 | DB | 자바 `ScheduleSeat.isHoldable(status, grade)` |
| 행 객체 | `Object[]`를 손으로 옮김. `SeatLayoutRow`와 `SeatMapRow` 두 개 | `ScheduleSeatRow` 하나 |
| 값 변환 | 구역 등급만 `SeatGrade.valueOf`. 가격은 `BigDecimal` 그대로 | Hibernate가 등급 2개를 enum으로, 가격을 `MoneyConverter`로 `Money`로 바꿈 |
| 엔티티 경로 | 비교용으로 남김(JSON 동등성 테스트) | 지움 |

### DB에서 잰 것
측정 회차(15,000석)에 두 쿼리를 3번씩 직접 돌렸다. 캐시가 데워진 뒤에는 측정 브랜치가 약 17.8ms, dev가 약 18.3ms였다. dev는 문자열 두 열을 더 보내므로, 한 번 조회할 때마다 약 84KB를 더 보낸다(측정 브랜치 열 합계는 약 366KB).

### 왜 작은 차이도 처리량에 보일 수 있나
P4a 단계는 커넥션 5개가 병목이다. JDBC 결과를 읽어 객체로 만드는 동안에는 커넥션을 쥐고 있다. 그래서 한 행에 쓰는 시간이 조금만 늘어도 15,000행에 곱해지고, 그만큼 커넥션을 반납하는 시점이 늦어진다. 같은 조건으로 L을 3회씩 재 보니 dev의 서버 좌석 조회 처리량이 중앙값으로 6.3% 낮았다(초당 169.4건 대 158.7건). 좌석 조회 성공률은 3.3%p 낮았다. 두 쪽 3회의 범위가 겹치지 않아 회 사이 편차가 아니다. 원인은 위처럼 추정하며, JFR 등으로 검증하지는 않았다. 측정 전에 정한 기준(5%p, 10%) 안이라 dev 코드를 채택한다. P4b부터는 좌석 배치를 캐시해 행 변환을 회차마다 한 번만 하므로 이 차이는 거의 사라질 것으로 본다.

### 이 대조가 재지 않는 것
이 대조는 좌석 조회 파일 10개만 바꿨다. 나머지 코드(선점 등)와 설정(G1, 커넥션 대기 1초, 풀 5)은 두 쪽이 같다. 그래서 dev 배포 전체와 측정 브랜치 전체를 비교한 결과가 아니다. dev에는 커넥션 대기 1초(R1)가 없고, 선점에 대사(ISE-14) 같은 다른 변경도 들어가 있다.

## 면접 포인트
- **DTO 프로젝션을 JPQL 생성자 식과 네이티브 SQL 중 무엇으로 하나?** JPQL 생성자 식은 타입이 안전하고 엔티티 매핑(enum, 변환기, 조인)을 그대로 따른다. 네이티브 SQL은 계산을 DB로 넘기고 열을 줄일 수 있지만, 열 순서와 형변환을 손으로 맞춰야 하고 DB에 묶인다. 둘 다 영속성 컨텍스트에 엔티티를 올리지 않는다는 점은 같다.
- **커넥션 풀이 병목일 때 자바 쪽 변환 비용이 왜 중요한가?** 결과를 읽는 동안 커넥션을 쥐고 있기 때문이다. 행마다 드는 작은 비용이 큰 결과 집합에 곱해지면 커넥션 점유 시간이 늘고, 풀 크기가 같으면 처리량이 줄어든다.
