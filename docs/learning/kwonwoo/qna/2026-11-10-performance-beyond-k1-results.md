# K1 단계 측정(F)까지 끝낸 뒤 성능을 더 끌어올릴 방법은 무엇인가

## 질문
테스트한 내용들(G1, R1, P1, P4a~P4c, S1~S4) 말고도 성능을 더 끌어올릴 방법은 없을까?

## 짧은 답
있다. 다만 F 뒤에는 local에서 reservation-service와 DB가 먼저 막히지 않는다(K1 S 초당 1,280명, 커넥션 대기 0). 그래서 남은 개선은 그 바깥에서 먼저 막히는 곳을 겨냥해야 효과가 보인다. 측정 결과로 보면 다음 세 곳이다.
1. **응답 크기(830KB).** 배포 환경에서는 네트워크와 직렬화가 먼저 막힌다. 압축, 배치와 상태 분리, 상태 비트맵이 가장 큰 효과를 낼 것으로 본다.
2. **Gateway 인증 차단기.** K1-H 800명과 K1 S 1,280명에서 서버보다 먼저 열렸다.
3. **409 재시도.** 매진 전 선점 처리 시간의 약 77%가 409(이미 잡힌 좌석)에 쓰인다.

이 셋은 대부분 다른 담당 영역(좌석 조회, Gateway, 프론트 계약)에 걸린다. 내 영역(선점) 안에서 할 수 있는 것은 409 본문 개선, Redis 사전 거절, 접수형 선점 쪽이다.

## 자세히

### 지금 어디가 한계인가 (F 기준)
| 측정 | 결과 | 먼저 막힌 곳 |
|---|---|---|
| K1 L 초당 100명 | 100%, p95 7ms, 189초에 매진 | 없음 |
| K1 S 초당 1,280명 (매진 뒤 좌석 조회만) | 3회 중 2회 100%, 1회 81.6% | Gateway 인증 차단기 |
| K1-H 800명 (Gateway 경유) | 80.5~91.4% | Gateway 인증 차단기 |
| K1-H 800명 (Gateway 우회) | 100%, p99 6ms | 없음 |
| P4c 좌석 조회 CPU (JFR) | Jackson 약 32%, 응답 만들기 약 24.5% | 앱 CPU(직렬화) |
| 배포 발생기 대역폭 | 1.562Gbps ÷ 830KB ≈ 초당 230건 | 네트워크 |

### 1. 좌석 조회 응답을 작게 만든다 (담당: 좌석 조회, 프론트 계약)
| 방법 | 내용 | 기대 효과 | 비용 |
|---|---|---|---|
| 응답 압축(gzip) | `server.compression.enabled` 또는 Gateway에서 압축 | 같은 구조가 15,000번 반복되는 JSON이라 크게 줄 것으로 본다(비율은 재야 안다). 배포 대역폭 한계가 바로 올라간다 | 설정 한 줄. 압축 CPU가 든다. 그래서 아래 P4d와 같이 해야 1초에 한 번만 압축한다 |
| P4d 응답 바이트 재사용 | 1초 캐시에 객체 대신 직렬화(와 압축)를 마친 `byte[]`를 둔다 | JFR의 Jackson 약 32%와 응답 만들기 약 24.5%가 1초에 한 번으로 준다 | 좌석 조회 내부 변경. 조건은 이미 맞았다(`k6-p4d-review.md`) |
| 배치와 상태 분리 | 배치(구역·열·번호·가격)는 따로 주고 ETag로 304를 준다. 상태만 자주 받는다 | 배치는 판매 중에 바뀌지 않아 거의 항상 304다 | API 계약 변경이라 프론트와 contract 이슈가 필요하다 |
| 상태 비트맵 | 상태를 좌석 순번별 1비트로 준다. 15,000석이면 약 1.9KB | 830KB가 수 KB로 준다. 직렬화 비용도 사실상 없어진다 | 계약 변경. 프론트가 비트맵을 풀어야 한다 |

### 2. Gateway 인증 차단기를 손본다 (담당: Gateway)
측정 환경에서만 완화한 기준(느린 호출 판정 끔, 실패율 100%)을 실제로 어떻게 둘지 정해야 한다. 차단기가 열리면 서버가 멀쩡해도 503이 나온다. contract 초안 A안이다(`k6-contract-proposals.md`). 벌크헤드 기본 동시 25도 함께 본다(강민 기록 2026-11-09).

### 3. 409 재시도 증폭을 끊는다 (담당: 선점, 내 영역. 응답 계약은 프론트와 합의)
매진 전 사용자는 "조회 → 선점 → 409 → 다시 조회 → 다시 선점"을 반복한다. L에서 409 비율이 약 77%다.
- **409 본문에 이미 잡힌 좌석 ID를 담는다.** 좌석 UPDATE를 `RETURNING id`로 바꾸면 잡지 못한 좌석을 알 수 있다. 프론트가 그 좌석만 빼고 바로 다시 고르면, 좌석 조회 한 번(830KB)이 빠진다.
- **Redis로 이미 잡힌 좌석을 먼저 거절한다.** 선점 성공 때 Redis 집합(또는 비트맵)에 좌석을 넣고, 선점 요청이 오면 DB 트랜잭션 전에 그 집합으로 거절한다. 409의 대부분이 커넥션을 쓰지 않게 된다. 정본은 DB 그대로 두고, Redis가 틀려도 DB 조건부 UPDATE가 막는다. 대신 만료·해제 때 Redis를 같이 지워야 한다.
- **접수형 선점(ISE-16, Kafka).** 몰림을 큐로 받아 일정 속도로 처리한다. 응답이 "접수됨 → 결과 조회"로 바뀌어 사용자 경험과 계약이 달라진다. 대기열이 이미 입장 속도를 정하므로, 동기형이 버티는 한 우선순위는 낮다.

### 4. 수평 확장과 DB
- **reservation-service를 2대로.** 앱 CPU가 한계일 때 가장 단순하다. 풀 10 × 2 = 커넥션 20개가 PostgreSQL `max_connections` 안인지 보고, S4(만료 `SKIP LOCKED`)가 여러 대에서 겹치지 않는 것은 이미 C6으로 확인했다.
- **fillfactor와 HOT 업데이트.** `schedule_seats`는 상태 열만 계속 바뀐다. fillfactor를 낮추면 인덱스를 건드리지 않는 갱신이 늘어 쓰기와 vacuum 비용이 준다.
- **부분 인덱스.** P4b는 선점 가능 좌석 ID만 읽는다. `WHERE status = 'AVAILABLE'` 부분 인덱스면 매진에 가까울수록 읽는 행이 준다.

### 효과가 없거나 낮다고 본 것
- **가상 스레드:** P4a 단계의 병목은 스레드 수가 아니라 커넥션 수였다. F 뒤에는 둘 다 병목이 아니다.
- **커넥션 풀을 더 키우기:** 우회 K1-H 800명에서 풀 20·40은 풀 10과 같았다.
- **P2·P3(선점 트랜잭션 줄이기, 시퀀스 배치):** 선점 경로가 800명까지 한계에 닿지 않아 넣지 않았다. 더 높은 도착률을 재면 다시 볼 수 있다.

## 추천 순서
1. **배포 측정에서 실제로 먼저 막히는 곳부터 확인한다.** local의 한계와 배포의 한계가 다를 가능성이 크다(대역폭, 서버 자원 공유).
2. **응답 압축 + P4d.** 좌석 조회 담당과 함께 정한다. 배포 대역폭 한계를 직접 올리는 가장 싼 방법이다.
3. **Gateway 차단기 기준.** contract A안을 Gateway 담당과 정한다.
4. **409 본문의 좌석 ID.** 내 영역에서 할 수 있는 가장 효과가 큰 것이다. 응답 계약이 바뀌므로 프론트 담당에게 contract 이슈로 먼저 알린다.
5. **Redis 사전 거절, 배치·상태 분리, 비트맵.** 효과는 크지만 정합성(Redis와 DB 일치)과 계약 변경 비용이 커서 측정으로 필요가 확인된 뒤에 한다.

## 덧붙인 질문: 진행한 것 중 효과를 본 방법은 무엇이었나

수치는 [k6-seathold-story.md](../../../design/reservation/k6-seathold-story.md) 4~6절이다. 효과는 "그 단계에서 막혀 있던 것을 풀었는가"로 본다.

| 방법 | 효과 | 근거 수치 |
|---|---|---|
| R1 커넥션 대기 30초 → 1초 | 큼. 과부하 뒤 회복이 생겼다 | L 좌석 조회 성공 0.7% → 40.3%, S 회복 실패 → 40초 뒤 회복 |
| P4a 엔티티 대신 필요한 열만 읽기 | 큼 | L 40.3% → 81.3%, S 20명 → 80명 |
| P4b 바뀌지 않는 배치 캐시, 선점 가능 ID만 읽기 | 가장 큼. 초당 100명에서 병목이 사라졌다 | L 81.3% → 100%(매진 전 p95 11ms), S 80명 → 640명 |
| P4c 좌석 상태 1초 공유 캐시 | 큼. DB 일이 거의 없어졌다 | S 640명 → 1,280명, 매진 전 p95 11ms → 7ms, 409 비율은 그대로 |
| P1 커넥션 풀 5 → 10 | 선점 지연에 효과 | Gateway 우회 K1-H 800명 p99 33ms → 6ms, 커넥션 대기 최대 40 → 0. 20·40은 10과 같음 |
| G1 GC 명시 | 클라이언트 수치는 작지만 다음 병목을 드러냈다 | GC 정지 약 75% → 7%, L 0.13% → 0.7%, S 10명 → 20명 |
| S1~S4 정합성 수정 | 성능 개선이 아니라 정합성. 측정 가능한 비용이 없었다 | K1-H 400명까지 선점 p95 5ms 이하로 넣기 전과 같음 |

- 측정 도구 쪽 수정(k6를 compose 네트워크로 직접 연결, k6 메모리 상한 6GiB)은 서버를 빠르게 한 것이 아니다. 측정값을 바로잡았다. 포트 전달을 거치던 P4a는 처리량을 약 40% 덜 쟀고, 2.5GiB 상한은 Gateway 차단기 열림을 부풀렸다(TS-64).
- P4a의 81.3%는 측정 브랜치 코드로 잰 값이다. dev 코드(반효승 `a40b01d`)는 같은 조건에서 약 3%p, 처리량 약 6% 낮았다(측정 브랜치 STEPS.md "P4a 구현 대조 실측").

## 덧붙인 질문: 동시성 부하 측정에서 기존 문제는 무엇이었고, 무엇을 해결했으며, 다음 일의 근거는 무엇인가

| 기존 문제 | 이번에 한 것 | 상태 |
|---|---|---|
| S1·S2 결함(멀티 탭 한도 초과, 연타 자기 409)을 JUnit으로만 확인했다 | 부하 상태에서 재현(A: 한도 초과 293명, 자기 409 2,416명)하고 F에서 0명임을 확인 | 확인 끝. 코드는 PR #458 |
| S4(`SKIP LOCKED`)의 효과를 부하에서 본 적이 없다 | 2대 실행에서 A 헛수고 39%, B 0, 처리량 2배 | 확인 끝. 코드는 PR #458 |
| 만료 스케줄러를 켠 부하를 잰 적이 없다 | 만료 처리 상한(초당 약 20건)이 병목이라 적체 약 9,000건. 상한 1,000으로 적체 57~269건 | 측정 브랜치 덮어쓰기로만 확인. 실제 코드·설정 반영 전 |
| 긴 잠금이 생기면 어떻게 되는지 몰랐다 | 잠금 33초 동안 A 좌석 조회 25%, B 77.5% | 원인과 한계 확인. 해결 전 |

다음 일의 근거:
- **만료 상한 반영:** 상한 100에서 적체가 부하 끝까지 늘었고(9,051건), 1,000에서는 수백 건 아래로 유지됐다. 선점 p95(8ms)와 5xx(0)는 그대로라 부작용이 보이지 않았다. 내 영역(ISE-13)이라 바로 고칠 수 있다.
- **커넥션 전 거절:** S3가 있어도 잠금 중 좌석 조회 500이 1,220건 남았다. 풀 10개 ÷ 대기 상한 0.5초 = 초당 약 20건보다 많은 선점이 잠긴 좌석으로 가면 풀이 찬다는 계산과 맞다. 대기 상한을 줄이는 것만으로는 한계를 옮길 뿐이라, 잠긴·잡힌 좌석 요청이 커넥션을 쓰지 않게 해야 한다.
- 모든 측정은 1회씩이라 수치는 방향을 보여 주는 값이다. 발표 수치로 쓰려면 반복 측정이 필요하다.

## 면접 포인트
- **병목을 하나 없애면 다음 병목이 보인다.** GC → 커넥션 대기 → DB 조인 → 좌석 상태 조회를 차례로 없앤 뒤에는 서버 밖(Gateway, 네트워크)이 먼저 막혔다. 개선은 지금 먼저 막히는 곳을 겨냥해야 수치로 보인다.
- **큰 응답은 CPU와 네트워크를 함께 쓴다.** 직렬화 결과를 캐시하면 CPU가, 압축하거나 응답 모양을 바꾸면 네트워크가 준다. 계약을 바꾸는 개선은 효과가 크지만 다른 팀과 합의가 먼저다.
- **캐시로 빠르게 거절하되 정본은 DB에 둔다.** Redis 사전 거절은 409를 싸게 만들지만, 마지막 판단은 DB 조건부 UPDATE가 하게 해 Redis가 어긋나도 중복 판매가 생기지 않게 한다.
