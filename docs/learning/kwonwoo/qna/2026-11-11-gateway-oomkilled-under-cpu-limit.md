# CPU 상한을 건 스트레스에서 Gateway가 OOMKilled로 죽은 원인은 무엇인가

## 질문
CPU 상한(4코어)을 건 F 스트레스의 1,280명 단계 끝에서 Gateway가 죽었다. 왜 죽었는지 원인을 분석해 줘.

## 정정 (재현 측정 뒤, 2026-11-11)
같은 조건으로 관찰을 붙여 2회 다시 쟀다(측정 브랜치 STEPS.md "Gateway OOMKilled 재현과 원인 확인 실측"). 아래 "짧은 답"과 "자세히"의 일부가 틀렸다. 틀린 부분은 남겨 두고 여기서 바로잡는다.
- **반복 여부:** 강제 종료는 3회 중 1회다. 메모리 상한(768MiB) 도달은 3회 중 3회다. 나머지 2회는 커널이 JVM 메모리를 스왑으로 내보내 살아남았지만, 대가로 크게 느려졌다(GC 멈춤 최대 6.9초, 좌석 조회 p95 5.8초).
- **원인(확인):** 몰린 830KB 응답이 두 곳에 동시에 쌓였다.
  - 커널 소켓 받기 버퍼: reservation-service에서 받았지만 Gateway가 아직 읽지 않은 바이트다. cgroup `sock`이 최대 약 590MiB였고 TCP 받기 대기열 합과 같이 움직였다.
  - JDK 직접 버퍼: 읽었지만 아직 내보내지 못한 바이트다. NMT `Other`가 3MB에서 183MB로 올랐다.
  - JVM 평시 크기가 약 520MiB라 상한까지 여유가 약 250MiB뿐이었다.
- **틀렸던 것:**
  1. "JVM 지표에 안 보이는 Netty 직접 메모리가 가장 그럴듯하다"는 틀렸다. 이 환경의 Netty는 JDK 직접 버퍼를 쓰고(`direct buffer constructor: unavailable`), 그 양은 JDK 지표와 NMT에 잡힌다. 앞 분석의 3~19MB는 5초 간격 수집이 몇 초짜리 급등을 놓친 값이다.
  2. JVM 밖 메모리의 주인은 Netty가 아니라 커널 소켓 받기 버퍼였다. 이것은 JVM이 볼 수 없다.
  3. "응답을 클라이언트에 늦게 내보내 쌓인다"도 방향이 반대였다. 보내기 대기열은 0이었고, 쌓인 곳은 reservation-service에서 받는 쪽이었다.
- **맞았던 것:** CPU가 모자라 큰 응답이 오래 걸리면 동시에 쥔 바이트가 늘어 메모리가 찬다는 방향은 맞았다. 리틀의 법칙으로 낸 약 300MiB도 실제 급등(소켓 290~590MiB + 직접 버퍼 최대 183MB)과 크기가 비슷하다.
- **대책에 주는 변화:** 직접 메모리 상한(`MaxDirectMemorySize`)만으로는 커널 소켓 버퍼를 막지 못한다. 근본 대책은 응답 크기를 줄이는 것과 Gateway가 동시에 받는 큰 응답 수를 제한하는 것이다. 또 JVM 평시 크기 대비 상한 여유를 키워야 한다.
- **미확인:** 배포 서버에 스왑이 있는지. 없으면 느려지는 대신 바로 강제 종료될 것으로 본다. 배포 Gateway는 G1이라 평시 크기가 다를 수 있다.

## 추가 (차단기 값 비교 뒤, 2026-11-11)
Gateway 담당이 시험 중인 `auth-redis` 값(벌크헤드 50, 벌크헤드 거절 무시 등)으로 다시 쟀다(측정 브랜치 STEPS.md "Gateway 차단기 시험 값 비교 실측", 각 1회).
- 시험 값에서는 CPU 상한이 없어도 Gateway가 OOMKilled로 죽었다. 매진을 피한 스트레스 1,280명 단계 끝이었고, 소켓 받기 버퍼 최대 355MiB, 직접 버퍼 최대 105MB로 위와 같은 모양이다.
- 운영 값에서는 상한에 닿지 않았다. 차단기가 일찍 열려(벌크헤드 거절이 실패로 세어짐) 큰 응답이 Gateway까지 오지 않았기 때문이다. 즉 지금까지는 차단기가 우연히 메모리를 지켜 왔다.
- 그래서 차단기를 덜 민감하게 하면 Gateway 동시 처리 상한이나 메모리 여유가 함께 있어야 한다. 근거는 ISE-230 댓글로 Gateway 담당에게 넘겼다.

## 짧은 답
죽인 것은 JVM이 아니라 커널이다. Gateway 프로세스 전체 메모리가 컨테이너 상한 768MiB를 넘어 cgroup OOM killer가 죽였다(`OOMKilled=true`, 종료 코드 137, 로그에 `OutOfMemoryError` 없음).

넘친 이유는 두 겹이다.
1. **설정:** 힙 상한(512MB) + 비힙(약 164MB) + Netty 직접 메모리 기본 상한(힙 상한과 같은 512MB)이 컨테이너 상한보다 크다. JVM이 스스로 막기 전에 커널이 먼저 죽이는 구성이다.
2. **촉발:** CPU가 모자라 큰 좌석 응답(약 830KB)이 오래 걸렸다. 그래서 Gateway가 동시에 쥔 응답 수가 평소 10~30개에서 250~370개로 늘었다. 응답 하나를 통째로 쥔다고 치면 최대 약 300MiB다. 이 동안 컨테이너 메모리가 520~640MiB에서 771MiB로 올랐다.

Netty 직접 메모리를 지표로 내보내지 않아, 실제로 얼마였는지는 확인하지 못했다. 위 계산은 응답 전체를 쥔다고 본 상한값이다.

## 자세히

### 1. 누가 죽였나: 커널(cgroup) vs JVM
| 구분 | JVM이 막을 때 | 커널이 죽일 때 |
|---|---|---|
| 조건 | 힙이나 직접 메모리가 JVM 상한(`-Xmx`, `MaxDirectMemorySize`)에 닿음 | 프로세스 전체(힙 + 비힙 + 직접 메모리 + 스레드 스택 + 네이티브)가 컨테이너 상한에 닿음 |
| 결과 | 그 요청에 `OutOfMemoryError`. 프로세스는 대개 산다 | 프로세스가 즉시 죽음. 종료 코드 137, `OOMKilled=true`. 로그를 남길 틈이 없다 |
| 이번 회 | 해당 없음(`OutOfMemoryError` 0건) | **이것.** 마지막 로그는 04:40:12의 평범한 요청 로그다 |

### 2. 설정이 커널 종료를 허용한다
`compose.deploy-memory.yml`(배포 값과 같음)은 Gateway에 `mem_limit: 768m`, `-Xms256m -Xmx512m`을 준다.
- 힙은 최대 512MB까지 커밋될 수 있다. 이번에는 248MB 커밋이었다.
- 비힙(메타스페이스, 코드 캐시 등)은 약 164MB 커밋이었다.
- `MaxDirectMemorySize`를 지정하지 않으면 직접 메모리 상한은 힙 상한(512MB)과 같다. Netty는 기본으로 이 값을 자기 직접 메모리 상한으로 쓴다.
- 합치면 이론상 1.2GB 가까이 쓸 수 있는데, 컨테이너는 768MiB다. 직접 메모리가 크게 늘면 JVM이 막기 전에 커널이 먼저 죽인다.

이번 회에서 JVM이 보고한 값은 커밋 힙 248MB, 커밋 비힙 164MB, 스레드 34개였다. 스레드 스택을 1MB로 잡아도 약 450MB다. 컨테이너는 부하 중 520~640MiB였으니 70~190MiB는 JVM 지표에 보이지 않는 메모리다. Netty는 직접 메모리를 JDK 버퍼 풀을 거치지 않고 할당한다. 그래서 `jvm_buffer_memory_used_bytes{id="direct"}`(3~9MB)에 잡히지 않는다. 이 보이지 않는 부분의 주인으로 가장 그럴듯한 것이 Netty 직접 메모리다.

### 3. 촉발: 리틀의 법칙
동시에 처리 중인 요청 수 = 처리율 × 처리 시간이다(리틀의 법칙). Gateway 요청 로그의 응답 시간을 10초 구간마다 더해, 동시에 처리 중이던 좌석 조회 200 응답 수를 구했다.

| 구간 (UTC) | 단계 | 동시에 처리 중인 좌석 응답 | × 830KB |
|---|---|---|---|
| 04:38:00~04:39:10 | 640명(매진 뒤 조회만) | 1~31개 | 25MiB 이하 |
| 04:39:20~04:39:30 | 1,280명 | 246~262개 | 200~212MiB |
| 04:39:50 | 1,280명 | **371개** | **약 301MiB** |
| 04:40:00 | 1,280명 | 263개 | 약 213MiB |
| 04:40:09 | 컨테이너 메모리 마지막 수집 | | **770.9MiB** |
| 04:40:12 | Gateway 종료 | | |

1,280명 단계에서는 Gateway 인증 차단기가 대부분을 즉시 503으로 돌려보냈다(10초에 약 1만 건). 통과한 좌석 조회 200은 1초 넘게 걸렸다(10초에 1,000~1,700건). 4코어를 reservation-service(약 2.2코어)와 Gateway(약 1.7코어)가 나눠 써 CPU가 찼기 때문이다. 처리 시간이 수 ms에서 수 초로 늘자, 같은 처리율에서도 동시에 쥔 응답이 10배 넘게 늘었다.

CPU 상한이 없을 때는 같은 단계 p95가 33ms였다. 그래서 동시에 쥔 응답이 수십 개, 수십 MiB에 그쳐 죽지 않았다.

### 4. 확인하지 못한 것
- **Netty 직접 메모리 실제 값.** Reactor Netty 할당자 지표를 내보내지 않고, 네이티브 메모리 추적(NMT)도 꺼져 있었다.
- **응답을 얼마나 쥐는지.** Gateway는 응답을 조각으로 흘려보낸다. 그래서 830KB를 통째로 쥐지 않을 수 있다. 위 표의 MiB는 상한이다.
- **호스트 메모리 부족의 영향.** 같은 시간대에 호스트 메모리가 부족했다. 종료 자체는 컨테이너 상한 때문이지만, 호스트 부족이 지연을 키웠을 가능성은 배제하지 못한다.

### 5. 대책 후보 (Gateway 담당이 정할 일)
| 대책 | 효과 | 비고 |
|---|---|---|
| `-XX:MaxDirectMemorySize`(또는 `io.netty.maxDirectMemory`)로 직접 메모리 상한을 두고, 힙 + 비힙 + 직접 메모리 합을 컨테이너 상한 아래로 맞춤 | 넘칠 때 프로세스가 죽지 않고, 그 요청만 실패한다 | 예: 힙 384MB + 직접 128MB + 비힙 약 170MB. 값은 측정으로 정한다 |
| 큰 응답 줄이기: 좌석 응답 압축(gzip), 응답 재사용(P4d), 구역별 조회 | 응답 하나당 메모리와 CPU가 같이 준다 | 830KB JSON은 압축률이 높을 것으로 본다(미측정) |
| Gateway가 동시에 처리하는 요청 수 상한 | 늘어날 수 있는 동시 응답 수 자체를 막는다 | 넘는 요청은 빠르게 거절한다 |
| Reactor Netty 메모리 지표 내보내기 | 다음에 같은 일이 생기면 원인을 숫자로 본다 | `reactor_netty_bytebuf_allocator_*` |
| 요청마다 남기는 INFO 로그 줄이기 | 과부하 때 503 로그에 쓰는 CPU를 덜어 준다 | 1,280명 단계는 10초에 로그 약 1.2만 줄 |

## 면접 포인트
- "컨테이너에서 자바 앱이 137로 죽었는데 OutOfMemoryError 로그가 없다. 왜인가?" → JVM 상한이 아니라 컨테이너(cgroup) 상한에 걸려 커널이 죽였다. 힙만이 아니라 직접 메모리·메타스페이스·스레드 스택을 합친 값이 컨테이너 상한 아래인지 봐야 한다. Netty 같은 프레임워크의 직접 메모리 기본 상한은 힙 상한과 같다.
- "부하가 같은데 왜 메모리가 갑자기 늘었나?" → 리틀의 법칙. 처리 시간이 늘면 같은 처리율에서도 동시에 쥔 요청과 버퍼가 늘어난다. CPU 부족이 메모리 부족으로 번진 사례다.
