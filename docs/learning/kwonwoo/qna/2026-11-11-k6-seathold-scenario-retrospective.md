# 좌석 선점 k6 부하 측정을 돌아보면 불필요한 단계와 빠진 개선은 무엇이었나

## 질문
진행했던 부하 테스트 시나리오를 다시 검토해 줘. 불필요한 단계가 들어 있지 않았는지, 이것 말고 다른 개선 방안은 없었는지 보고 싶다.

대상은 ISE-79 측정 전체다. K1 단계 측정(base~F), K1-H, P4a 구현 대조, 동시성 부하(T·D·X), 2대 만료 경합, 만료 상한(E), 잠금 장애 주입(K), 잠긴 행 집중(Z)을 본다. 근거는 측정 브랜치 `experiment/ISE-79-k6-steps`의 `reservation-service/k6/STEPS.md`와 [발표 정리 문서](../../../design/reservation/k6-seathold-story.md)다.

## 짧은 답
뼈대는 맞았다. 수정 없는 base에서 시작해 병목 하나씩 고치고, 측정 전에 예상을 적는 방식은 그대로 두는 것이 좋다. 다만 다음 세 갈래는 고칠 만하다.
1. **결과가 미리 정해진 비교가 있었다.** Gateway 경유 K1-H 3회, 1대 X의 A·B 비교, Z의 A 전 단계가 그렇다. 이 회들은 측정 전에 결과를 알 수 있었다.
2. **무효 회가 여러 번 나왔다.** P4b 1~4차, Z 1차, 이전 기기 측정이 버려졌다. 원인은 모두 사전 점검이 없었던 것이다. 부하 생성기 용량, 장애 주입 대상, CPU 상한을 측정 전에 확인했어야 했다.
3. **시나리오가 실제 오픈 상황을 덜 닮은 곳이 있었다.** 스트레스 상위 단계는 매진 뒤라 좌석 조회만 받았다. 결제 흐름이 빠졌고, 측정이 5분 이하로 짧았다. CPU 상한 없이 32코어에서 재서, 배포 환경(4 vCPU)에서 나올 병목은 가려졌다.

## 자세히

### 1. 줄이거나 뺄 수 있었던 단계

| 측정 | 왜 줄일 수 있었나 | 대신 했으면 좋았을 것 |
|---|---|---|
| Gateway 경유 K1-H (base·F 3회씩) | 실패의 80~99%가 Gateway 인증 차단기의 즉시 503이었다. 그래서 성공률로 base와 F를 가르지 못했다(정리 문서 6절). 남은 차이는 p95와 Gateway 연결 실패뿐이다 | 선점 경로 비교는 Gateway 우회 K1-H로 하고, Gateway 경유는 1회만 재서 "차단기가 먼저 막는다"를 보이면 충분했다 |
| X(만료 켬) 1대의 A·B 비교 | S4(`SKIP LOCKED`)는 스케줄러가 둘일 때 생기는 경합을 고친다. 1대에서는 차이가 날 수 없다. 예상 단계에서 이미 "두 구현 모두 적체"라고 계산했고(상한 초당 20건 < 도래 초당 50건), 실측도 그대로 나왔다(4,417 대 4,400건) | B 1회로 적체를 확인하고, 바로 2대 경합(A·B)과 상한 1,000(B)으로 갔으면 한 회를 아꼈다 |
| Z(잠긴 행 집중) A의 6단계 전부 | A는 `lock_timeout`이 없어 첫 단계에서 무너질 것이 K에서 이미 보였다. 실측도 초당 10명에서 공연 목록이 98% 실패했다. 나머지 5단계는 모두 100% 실패라 정보가 없다 | A는 첫 단계 하나(또는 두 단계)만 재고 멈추는 조건을 두면 된다 |
| P4b 1~4차, Z 1차 | 무효였다. P4b는 부하 생성기 한계, 메모리 부족, k6가 응답 본문을 쥔 채 대기한 문제였다. Z 1차는 잠근 10석 중 k6가 노린 좌석이 1석뿐이었다 | 아래 3절의 사전 점검으로 대부분 막을 수 있었다 |
| 이전 기기에서 잰 base~P4b | 기기를 바꾸자 단계끼리 비교할 수 없어 처음부터 다시 쟀다. CPU 상한이 없어 처리량이 기기를 따라갔기 때문이다(STEPS.md "측정 기기 이동") | 처음부터 서버 컨테이너에 CPU 상한을 걸었으면 기기가 바뀌어도 수치를 이어 쓸 수 있었다 |

필요했던 단계도 분명하다. base부터 단계를 쌓은 것, P4a 구현 대조(dev 코드 채택의 근거), T·D(결함이 부하에서도 나오는지), 2대 만료 경합(S4 효과가 처음 보인 곳), 상한 1,000(설정 한 줄로 적체 해소)은 모두 결론을 바꾸거나 근거가 됐다.

### 2. 해석을 약하게 만든 설계

- **스트레스 상위 단계가 매진 뒤였다.** 수요가 좌석의 약 3배라 160~320명 단계에서 매진되고, 640·1,280명 단계는 좌석 조회만 받았다. 발표 문구 "초당 1,280명까지 버텼다"는 조회만의 한계다. 정리 문서 6절에 이 한계를 적어 두었지만, 시나리오에서 막을 수 있었다. 방법은 둘이다. 단계마다 새 회차로 옮겨 가거나, 단계 사이에 좌석을 되돌리면 된다. 그러면 단계마다 조회와 선점이 섞인 부하가 된다.
- **K의 잠금 대상이 인기 구역과 얼마나 겹쳤는지 모른다.** 좌석 ID 순서로 잠갔는데, k6의 인기 구역은 응답 순서(구역 → 열 → 번호)다. Z 1차에서 같은 어긋남이 드러났다. 그래서 K의 25%·77.5%는 "인기 구역 근처를 잠갔을 때"로만 읽어야 한다. 발표에 이 수치를 쓰려면 응답 순서로 잠가 다시 재야 한다.
- **동시성·잠금 측정은 모두 1회다.** T·D는 결과가 거의 결정적이라(293명 대 0명, 2,416명 대 0명) 1회로 충분하다. K·Z는 단계별 비율이 회마다 흔들릴 수 있다. 발표 수치로 쓸 값만 3회로 늘리면 된다.
- **2대 측정에서 Prometheus가 한 대만 긁었다.** 그래서 서버 지표를 판정에 쓰지 못했고, B 2대의 선점 500 108건 원인도 미확인으로 남았다.

### 3. 무효 회를 줄였을 사전 점검

| 점검 | 막았을 일 | 방법 |
|---|---|---|
| 부하 생성기 보정 | TS-64(k6 메모리 상한을 Gateway 한계로 잘못 읽음), P4b 1·2차 무효 | 측정 대상 없이 k6만 가벼운 엔드포인트에 최고 단계 도착률로 돌려 CPU·메모리 여유를 본다. 기기를 바꿀 때마다 다시 한다 |
| 장애 주입 대상 확인 | Z 1차 무효, K 해석 제한 | 잠금 세션이 잠근 좌석 ID와 k6 목표 좌석 ID의 겹침 수를 측정 시작 전에 출력하고, 기대와 다르면 멈춘다(Z 2차의 `locked 10`을 미리 확인하는 셈) |
| CPU 상한 | 기기 이동 재측정, P4d 판단 보류 | 서버 컨테이너 전체를 같은 4코어에 묶는다(`cpuset`). 배포처럼 4 vCPU를 함께 나눠 쓰게 하는 것이다. 컨테이너마다 `cpus`를 따로 주는 방식은 배포와 덜 닮았다([CPU 상한 노트](2026-11-11-why-cpu-limit-in-load-test.md)). local 32코어에서는 직렬화 비용(JFR 약 32%)이 병목이 되지 않아 P4d 효과가 보이지 않았다. 상한이 있으면 local에서 판단할 수 있었다 |

### 4. 시나리오에 없던 개선 방안

1. **K1에 결제를 섞는다.** 지금 K1은 선점까지만 하고 결제하지 않는다(`k1-seathold.js`에 결제 요청이 없다). 실제로는 선점한 사용자 일부가 결제하고, 확정·취소가 같은 좌석 행과 커넥션 풀을 쓴다. 예를 들어 선점의 30~50%를 결제로 이어 보내면, 결제 확정 이벤트 처리와 선점의 경합을 볼 수 있다. 결제 쪽은 다른 담당 영역이라 측정 브랜치에서만 섞는다.
2. **CPU 상한을 걸고 F를 다시 잰다.** 배포 측정(약 2~2.5시간) 전에 local에서 배포와 같은 코어 비율로 F L·S를 1회씩 잰다. P4d를 넣을지 이 결과로 미리 정할 수 있다.
3. **오래 도는 측정(soak).** 모든 회가 5분 안팎이었다. 30분~1시간 L을 1회 돌리면 다음을 볼 수 있다. 캐시·Outbox·만료 적체가 시간이 지나며 쌓이는지, 메모리가 새는지, GC가 점점 길어지는지.
4. **대기열 입장의 실제 모양.** 입장 스케줄러는 500ms 주기로 돈다(`QueueAdmissionScheduler`, `queue.admission-interval`). 입장이 0.5초마다 묶음으로 열리면, 좌석 서비스에 들어오는 요청도 고르게 퍼지지 않고 몰릴 수 있다. 클라이언트 폴링 간격이 이를 퍼뜨리는지는 확인하지 않았다(미확인). 묶음 도착(0.5초마다 50명) 시나리오로 짧은 몰림을 한 번 재 볼 만하다.
5. **회차 여러 개 동시 오픈.** 측정은 회차 하나(15,000석)였다. P4b 배치 캐시와 P4c 1초 캐시는 회차별이라, 여러 공연이 동시에 열리면 캐시 메모리와 첫 요청 비용이 회차 수만큼 는다.
6. **잠금 번짐·유령 선점 대책을 넣은 뒤 Z를 다시 잰다.** 정리 문서 11절의 대책을 넣으면, 같은 Z로 "초당 20건 한계가 사라지는지"와 "유령 선점이 0이 되는지"를 바로 비교할 수 있다. 대책은 두 가지다. 하나는 선점 동시 처리 상한이나 사전 거절이고, 다른 하나는 요청 기한 전달이다. 이미 만든 시나리오를 다시 쓰는 것이라 비용이 작다.

### 우선순위 제안
발표 수치를 지키는 데 가까운 것부터 둔다.
1. CPU 상한을 건 F 1회(2번). P4d 판단과 배포 측정 해석에 쓴다.
2. 매진을 피한 스트레스(2절 첫 항목). "1,280명" 문구를 조회와 선점이 섞인 수치로 바꿀 수 있다.
3. K를 응답 순서 잠금으로 다시 잰다. 발표에 K 수치를 쓸 때만 한다.
4. 결제 섞기, soak, 묶음 도착은 배포 측정 계획과 함께 정한다.

## 진행 결과 (2026-11-11)
우선순위 1~3을 1회씩 쟀다(측정 브랜치 STEPS.md "측정 회고 뒤 세 측정 실측", 정리 문서 5절 "측정 회고 뒤 재측정").
- **CPU 상한 F:** L은 100%(매진 전 좌석 조회 p95 7 → 18ms)였다. S는 160명에서 p95가 149ms로 오르고 320명에서 실패가 시작됐다. 1,280명 단계에서는 Gateway가 메모리 상한을 넘어 죽었다. local 32코어의 "1,280명까지 병목 없음"은 CPU가 남아서 나온 결과였다.
- **매진을 피한 스트레스:** 조회와 선점이 섞인 부하는 320명까지 100%였다. 640명부터 Gateway가 즉시 503으로 막았다. "1,280명"은 좌석 조회만 받은 한계다.
- **K 재측정:** 잠금 중 좌석 조회 성공이 A 25 → 12.7%, B 77.5 → 53.5%였다. 1차 값은 잠금이 인기 구역과 덜 겹쳐 좋게 나온 것이다.
- 세 측정 모두 회고에서 짚은 해석 문제를 실제 수치로 바꿨다. 1회씩이라 발표에는 방향으로 쓰고, 배포 측정에서 다시 확인한다.

## 면접 포인트
- "부하 테스트를 설계할 때 무엇을 먼저 확인하나?" → 부하 생성기의 여유를 먼저 확인한다. 생성기가 한계에 붙으면 요청 모양이 바뀌어 서버 한계처럼 보인다. 실제로 k6 메모리 상한 때문에 Gateway 한계로 잘못 읽은 적이 있다(TS-64).
- "A·B 비교를 언제 생략하나?" → 고친 결함이 생길 수 없는 조건이면 비교해도 차이가 없다. 예를 들어 다중 인스턴스 경합 수정은 1대에서 재지 않는다. 측정 전에 예상을 적어 두면 이런 회를 미리 거를 수 있다.
- "스트레스 테스트 결과를 읽을 때 주의할 점은?" → 단계가 오르는 동안 시스템 상태가 바뀌는지 본다. 매진처럼 상태가 바뀌면 상위 단계는 다른 부하를 잰 것이다.
