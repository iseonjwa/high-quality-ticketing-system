# 큰 좌석 응답 때문에 Gateway 메모리가 차는 문제를 다른 기술로 극복할 방법은 무엇인가

## 질문
CPU 상한 스트레스에서 Gateway가 OOMKilled로 죽은 원인을 봤다. 그럼 이걸 다른 기술로 극복할 수 있는 방법은 없을까?

## 정정 (재현 측정 뒤)
재현 측정에서 메모리를 채운 것은 커널 소켓 받기 버퍼(최대 약 590MiB)와 JDK 직접 버퍼(최대 183MB)였다([원인 분석 정정](2026-11-11-gateway-oomkilled-under-cpu-limit.md)). 그래서 3번 묶음의 "직접 메모리 상한"만으로는 커널 소켓 버퍼를 막지 못한다. 동시에 받는 큰 응답 수를 제한하거나 응답을 작게 하는 1·2번이 근본 대책이다. 추천 순서에서는 Gateway 쪽을 "동시 처리 상한 + 메모리 상한 여유"로 읽는다.

## 짧은 답
문제의 뿌리는 830KB 좌석 응답이다. CPU가 모자랄 때 Gateway가 이 응답을 동시에 약 370개 쥐면서 메모리가 찼다([원인 분석](2026-11-11-gateway-oomkilled-under-cpu-limit.md)). 극복 방향은 세 겹이다.
1. **응답 자체를 작게 한다.** 고정 배치와 좌석 상태를 나누고, 상태는 비트맵으로 보낸다. 830KB가 약 2.5KB가 된다.
2. **같은 응답을 싸게 낸다.** 1초마다 한 번 만든 응답을 압축해 두고 모두에게 같은 바이트를 보낸다. 바뀐 것만 밀어주는 방식(SSE)도 있다.
3. **Gateway가 죽기 전에 거절한다.** 직접 메모리 상한을 맞추고, 동시에 처리하는 요청 수에 상한을 둔다.

## 자세히

### 1. 응답을 작게: 배치와 상태 분리 + 비트맵
지금 응답은 좌석마다 구역·열·번호·등급·가격·선택 가능 여부를 담는다(좌석당 약 55바이트, 15,000석에 약 830KB). 이 중 공연 중에 바뀌는 것은 "선택 가능 여부" 하나뿐이다.
- **고정 배치:** 회차마다 한 번 만드는 정적 데이터다. 객체 저장소와 CDN(S3 + CloudFront)에 두거나, HTTP 캐시(`ETag`, `Cache-Control: max-age`)로 브라우저가 한 번만 받게 한다. 다시 받는 요청은 서버까지 오지 않는다.
- **좌석 상태:** 15,000석을 좌석 순서대로 1비트씩 표현하면 1,875바이트(base64 약 2.5KB)다. 830KB의 약 330분의 1이다.
- **Redis 비트맵:** 선점·만료·확정 때 `SETBIT`으로 해당 좌석 비트를 바꾸고, 조회는 `GET` 한 번으로 끝낸다. DB를 읽지 않는다. 최종 판정은 지금처럼 선점 때 DB의 조건부 UPDATE가 하므로, 비트맵이 잠깐 낡아도 중복 판매는 생기지 않는다. P4c가 이미 1초 낡은 상태를 허용한 것과 같은 논리다.
- **효과(리틀의 법칙):** 동시에 처리 중인 응답 370개 × 2.5KB ≈ 1MB다. Gateway 메모리, 직렬화 CPU, 네트워크가 함께 준다.
- **비용:** 외부 API 계약이 바뀐다. 프런트엔드가 배치와 비트맵을 합쳐 그려야 하고, 좌석 상태를 바꾸는 모든 경로가 비트맵도 바꿔야 한다. 두 저장소의 일관성 관리도 생긴다.

### 2. 같은 응답을 싸게 내기
- **미리 압축한 공유 응답(P4d + gzip):** 회차마다 1초에 한 번 응답 JSON을 만들고 gzip으로 압축해 둔 뒤, 모든 요청에 그 바이트를 보낸다(`Content-Encoding: gzip`). 요청마다 압축하면 모자란 CPU를 더 쓰지만, 1초에 한 번이면 비용이 거의 없다. 반복이 많은 JSON은 보통 크게 줄지만, 이 응답의 압축률은 재지 않았다. 브라우저가 자동으로 풀어 주므로 외부 계약은 바뀌지 않는다.
- **바뀐 것만 밀어주기(SSE, WebSocket):** 409를 받은 사용자는 지금 좌석 전체를 다시 읽는다. 서버가 바뀐 좌석만 이벤트로 보내면 다시 읽기가 사라진다. 대신 수만~수십만 연결을 유지하는 메모리와 운영 부담, 재연결 처리가 생긴다.

### 3. 죽기 전에 거절하기
- **메모리 상한 맞추기:** `-XX:MaxDirectMemorySize`(또는 `io.netty.maxDirectMemory`)를 두어 힙 + 비힙 + 직접 메모리를 컨테이너 상한 아래로 맞춘다. 넘치면 프로세스 대신 그 요청만 실패한다.
- **동시 처리 상한:** Gateway에 벌크헤드나 요청 속도 제한(`RequestRateLimiter`, Redis 기반)을 두거나, Reactor Netty 연결 수와 대기 수를 제한한다. 늘어날 수 있는 동시 응답 수 자체를 막는다.
- **엣지 프록시 교체(Nginx, Envoy):** C/C++ 기반이라 연결당 메모리가 작고 예측 가능하다. 다만 인증 필터(토큰·입장 토큰 검사)를 `auth_request`나 `ext_authz`로 옮겨야 해 범위가 크다.
- 이 묶음은 한계를 올리지 않는다. 실패 방식을 "프로세스 종료"에서 "요청 거절"로 바꿀 뿐이다.

### 비교
| 방법 | 응답 크기 | 서버 CPU | 외부 계약 변경 | 범위 |
|---|---|---|---|---|
| 배치·상태 분리 + 비트맵 | 약 330분의 1 | 크게 줆(DB·직렬화 없음) | 있음 | 큼 |
| 미리 압축한 공유 응답 | 압축률만큼(미측정) | 줆(1초에 한 번) | 없음 | 중간 |
| SSE로 변경분 전송 | 변경분만 | 다시 읽기 제거 | 있음 | 큼 |
| 메모리 상한 + 동시 처리 상한 | 그대로 | 그대로 | 없음 | 작음 |

## 이 프로젝트에서는
- 추천 순서는 다음과 같다. 1, 2번은 다른 담당 영역이라 근거와 함께 넘긴다.
  1. **메모리 상한 + 동시 처리 상한:** Gateway 담당. 작은 설정 변경으로 프로세스 종료를 막는다.
  2. **미리 압축한 공유 응답:** 좌석 조회 담당(반효승, P4). 외부 계약 변경이 없고, CPU 상한 측정으로 효과를 바로 확인할 수 있다.
  3. **배치·상태 분리 + 비트맵:** 좌석 조회 담당과 프런트엔드가 함께 하는 설계 변경이다. `contract` 이슈로 제안한다.
- 측정 근거: 측정 브랜치 `reservation-service/k6/STEPS.md` "측정 회고 뒤 세 측정 실측", [Gateway 종료 원인 분석](2026-11-11-gateway-oomkilled-under-cpu-limit.md).

## 면접 포인트
- "대용량 응답이 병목일 때 어떻게 하나?" → 먼저 무엇이 바뀌는지 나눈다. 바뀌지 않는 부분은 CDN·HTTP 캐시로 서버 밖에서 내보내고, 바뀌는 부분만 작은 형식(비트맵 등)으로 보낸다. 크기가 줄면 메모리·CPU·네트워크가 같이 준다.
- "압축은 언제 도움이 되나?" → CPU가 남고 네트워크가 병목일 때다. CPU가 모자라면 요청마다 압축하는 것은 해가 된다. 미리 한 번 압축해 재사용하면 이 단점이 사라진다.
- "과부하 보호와 성능 개선의 차이는?" → 벌크헤드·속도 제한은 실패 방식을 바꿀 뿐 한계를 올리지 않는다. 한계를 올리는 것은 요청당 비용을 줄이는 쪽이다.
