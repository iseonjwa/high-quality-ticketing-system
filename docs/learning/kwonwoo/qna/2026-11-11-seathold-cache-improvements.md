# 좌석 선점과 부하 경로에서 로컬 캐시·Redis 캐시로 더 개선할 부분은 무엇인가

## 질문
Gateway 말고, 부하 테스트나 동시성 제어 쪽에서 더 개선할 부분은 없을까? 로컬 캐시나 Redis 캐시를 쓰는 방식으로.

## 짧은 답
가장 효과가 클 후보는 **선점 요청을 DB에 가기 전에 로컬 상태 캐시로 거절하는 것**이다. 선점 요청의 약 77%가 409(이미 잡힌 좌석)로 끝난다. 그런데 지금은 409로 끝날 요청도 트랜잭션을 열고 문장 7개를 실행한 뒤 롤백한다. 좌석 조회가 이미 만들어 둔 1초 상태 캐시(P4c)로 "이미 잡힌 좌석이 섞였는지"를 먼저 보면, 그 요청 대부분이 커넥션을 쓰지 않는다.

그다음은 회차 정보와 좌석 가격을 로컬 캐시에서 읽는 것이다. 선점 한 건의 DB 왕복이 둘 준다. Redis로 좌석을 먼저 잡는 방식(Redis 선점 게이트)은 효과가 크지만, DB와 Redis 두 곳의 정합성을 관리해야 하고 설계 결정(ADR)이 바뀐다. 그래서 로컬 사전 거절로 부족할 때 꺼낸다.

## 확인한 사실 (feat 브랜치 코드)
409로 끝나는 선점 한 건(`SyncSeatHoldService.hold`)이 DB에서 하는 일은 다음과 같다.
1. `seat_hold_requests` 멱등키 조회
2. 회차 조회(`findSchedule`): 판매 기간, 1인 한도, 선점 시간
3. 좌석 조회(`findSeats`): 회차 소속과 가격
4. 멱등키 INSERT(`saveAndFlush`)
5. `set_config('lock_timeout', '500ms')`
6. 매수 조건부 UPDATE: 사용자의 매수 행을 잠근다
7. 좌석 조건부 UPDATE: 갱신 행 수가 모자라 409, 그리고 전체 롤백

- 측정에서 선점 요청의 409 비율은 약 77%였다(P4c 전후 76.6%, 76.9%). 인기석으로 몰리기 때문이다.
- 좌석 조회의 P4c(측정 브랜치)는 회차마다 선점 가능 좌석 ID를 정렬한 배열(`long[]`)로 1초 동안 들고 있다. 이분 탐색으로 좌석 하나를 마이크로초 단위로 확인할 수 있다.
- 커넥션 풀은 10개이고, 잠금 장애 주입에서는 커넥션을 쥔 채 기다리는 요청이 좌석 조회까지 실패시켰다(잠금 번짐).

## 자세히

### 1. 로컬 상태 캐시로 선점 사전 거절 (추천 1순위)
- **방법:** 선점 서비스가 트랜잭션을 열기 전에 회차의 상태 스냅숏을 본다. 1초 안에 만든 스냅숏이 있고, 요청 좌석 중 하나라도 선점 가능 목록에 없으면 바로 409 `SEAT_ALREADY_HELD`를 준다. 스냅숏이 없거나 1초보다 낡았으면 지금처럼 DB로 간다.
- **정합성:** 판정을 바꾸는 것이 아니라 "확실히 질 요청"만 미리 돌려보낸다. 낡은 방향은 두 가지다.
  - 스냅숏은 비어 있는데 지금은 잡힌 좌석: DB로 가서 지금처럼 UPDATE가 막는다. 중복 판매는 생기지 않는다.
  - 스냅숏은 잡혀 있는데 1초 안에 풀린 좌석(만료·취소): 잘못된 409가 난다. 좌석 조회 화면도 같은 1초 낡은 상태를 보여 주므로, 사용자가 볼 수 없던 좌석을 고를 일은 드물다. 다시 누르면 DB로 간다.
- **효과(예상, 미측정):** 409 요청의 대부분이 트랜잭션·문장 7개·롤백 없이 끝난다. 이미 커밋된 HELD 좌석을 노린 요청은 지금도 잠금을 기다리지 않고 빨리 끝나므로, 아끼는 것은 잠금 대기보다 **커넥션 점유 시간과 DB CPU**다. 매수 행 잠금도 덜 잡는다. 1초 안에 막 잡힌 좌석(진행 중인 트랜잭션이 쥔 행)은 스냅숏에 아직 비어 있어 잠금 대기는 그대로 남는다. 이 부분은 잠금 번짐 대책(동시 처리 상한)으로 따로 다룬다.
- **비용:** 선점 모듈이 좌석 조회 모듈(concert, 반효승)의 캐시를 읽는 포트가 필요하다. dev에는 아직 P4c가 없다(ISE-205 Backlog). 측정 브랜치에서 P4c 위에 먼저 재 보고, 효과가 있으면 P4c 이관과 함께 제안한다.
- **여러 대일 때:** 인스턴스마다 자기 스냅숏을 1초에 한 번 만든다. 대수만큼 조회가 늘지만 초당 몇 건이라 Redis로 공유할 이유가 없다.

### 2. 회차·좌석 가격 로컬 캐시
- 회차 정보(판매 기간, 1인 한도, 선점 시간)는 판매 중에 거의 바뀌지 않는다. 대기열 모듈의 `CachedScheduleReader`처럼 30초 안팎으로 로컬에 둘 수 있다. 좌석의 회차 소속과 가격은 P4b 배치 캐시에 이미 있다.
- 효과는 선점 한 건당 SELECT 두 번이다. 1번보다 작고, 성공하는 선점에도 적용된다.
- 주의할 점은 관리자가 오픈 시각이나 한도를 바꾸는 경우다. 캐시 시간만큼 늦게 반영된다. 판매 시작 직전에 시각을 바꾸면 위험하므로, 바꿀 때 캐시를 비우는 경로가 있으면 좋다.

### 3. Redis 선점 게이트 (보류)
- **방법:** 좌석마다 Redis 키를 `SET NX PX`(또는 Lua로 여러 좌석을 한 번에)로 먼저 잡는다. 이긴 요청만 DB 트랜잭션으로 가고, 진 요청은 Redis에서 바로 409다.
- **효과:** 인기석 경합이 DB 행 잠금이 아니라 Redis 안에서 끝난다. 1번과 달리 "방금 잡힌 좌석"의 잠금 대기까지 없어진다.
- **대가:** 좌석 상태의 주인이 둘이 된다. DB 트랜잭션이 실패하면 Redis 키를 풀어야 하고, 만료·취소·결제 확정 때도 함께 바꿔야 한다. 한쪽만 바뀌면 팔 수 있는 좌석이 안 팔리는 일이 생긴다. Redis가 죽었을 때 어떻게 할지(DB로 우회할지 거절할지)도 정해야 한다. 지금 설계는 DB 조건부 UPDATE가 최종 판정이다(SA 12-7). 바꾸려면 ADR이 필요하다.
- **언제:** 1번을 넣고도 배포 측정에서 선점 경로가 DB 잠금이나 커넥션으로 막힐 때 꺼낸다.

### 4. 좌석 조회 쪽 (다른 담당, 근거만 넘긴다)
- 가장 큰 남은 일은 P4b·P4c를 dev로 옮기는 것이다(ISE-204, 205). 지금 dev는 P4a뿐이라 배포하면 F 결과가 나오지 않는다.
- 그다음은 P4d(1초 스냅숏마다 JSON 바이트를 한 번만 만들기)다. CPU 4코어 측정에서 160~320명에 CPU가 찼고, JFR로는 좌석 조회 CPU의 약 57%가 응답 만들기·직렬화였다. 미리 압축한 바이트까지 두면 Gateway를 지나는 바이트도 준다.
- 좌석 상태를 Redis에 두는 것은 지금 응답 모양(830KB)에서는 이득이 작다. Redis가 830KB를 내보내는 네트워크 비용이 생기고, 로컬 1초 캐시로 DB 조회는 이미 초당 한 번이다. 응답을 배치와 비트맵으로 나누는 설계 변경을 할 때 Redis 비트맵(`SETBIT`)이 의미가 있다.

### 5. 캐시가 아닌 것 중 함께 볼 것
- **선점 만료 한 주기 상한 100 → 1,000(ISE-13):** 측정으로 적체가 줄어드는 것을 이미 봤다. 반영만 남았다.
- **선점 동시 처리 상한:** 진행 중인 선점 수를 세마포어로 커넥션 수보다 작게 묶는다. 1번이 못 줄이는 "방금 잡힌 좌석"의 잠금 대기가 풀 전체로 번지는 것을 막는다. 잠금 장애 주입 K로 효과를 볼 수 있다.

측정값(측정 브랜치 `step-f-cpu4-S-20261111-133015`, `step-m-f-M-20261111-130646`의 서버 지표와 k6 건수)과 자료 구조 크기로 추정했다. 효과는 구현 전 예상이다.

### 비용
| 항목 | 로컬(P4c 배열 재사용) | 로컬(전용 비트셋) | Redis 좌석 키(`SET NX PX`) | Redis 비트맵 |
|---|---|---|---|---|
| 회차 하나(15,000석) 메모리 | 추가 0(이미 P4c가 최대 약 117KB를 듦) | 약 1.9KB | 잡힌 좌석마다 약 70~100바이트, 전부 잡히면 약 1~1.5MB | 약 1.9KB |
| 갱신 비용 | 추가 0(P4c가 회차마다 1초에 한 번 조회) | 1초에 한 번 조회 | 선점·만료·확정마다 쓰기 | 상태가 바뀔 때마다 `SETBIT` |
| 확인 비용 | 이분 탐색 약 14번, 1마이크로초 안팎 | 같음 | 네트워크 왕복 1번(같은 망 0.2~0.5ms) | 왕복 1번 |

- 메모리는 어느 쪽도 크지 않다. 좌석 조회 응답 한 건(약 830KB)이 요청마다 만드는 쓰레기가 P4c 배열 하나보다 7배 크다. 지금 Redis는 local에서 약 7MB를 쓰고 상한은 192MiB다. 회차 10개를 좌석 키로 다 잡아도 15MB 안팎이라, 메모리 때문에 서버 비용이 오르지는 않는다.
- Redis의 진짜 비용은 메모리가 아니라 요청마다 하는 왕복과, 좌석 상태 주인이 둘이 되는 정합성 관리다.

### 효과 (서버에서 선점 요청을 처리한 시간, 초당 합)
| 단계 | 지금 선점 처리 시간 | 그중 409 | 409 한 건 평균 | 사전 거절 뒤 예상 |
|---|---|---|---|---|
| 상한 없음 M 320명 | 3.57초/초 | 1.39(39%) | 약 3.8ms | 2.2~2.6초/초(-27~37%) |
| CPU 4코어 S 160명 | 3.10초/초 | 2.29(74%) | 약 7.2ms | 0.9~1.5초/초(-50~70%) |
| CPU 4코어 S 320명(매진 직후) | 9.56초/초 | 9.43(99%) | 약 220ms | 1초/초 아래(-90% 이상) |

- 가정: 409 가운데 사전 거절로 걸러지는 비율을 70~95%로 잡았다. 1초 안에 막 잡힌 좌석을 노린 409는 스냅숏에 아직 안 보여 DB로 간다. 매진 뒤에는 선점 가능 목록이 비므로 거의 100%가 걸러진다.
- 사전 거절 한 건의 비용은 마이크로초 단위라, 409 한 건(3.8~220ms)과 비교하면 수천 배 이상 싸다.
- 아끼는 것: DB 문장(S 160명 기준 초당 약 316건 × 7문장 ≈ 2,200문장), 커넥션 점유, 매수 행 잠금이다.
- 아끼지 못하는 것: 좌석 조회의 응답 만들기·직렬화(JFR 기준 좌석 조회 CPU의 약 57%)다. 그래서 CPU 4코어에서 끝단 성공률이 얼마나 오를지는 장담하지 않는다. 선점 p95, 커넥션 여유, 잠금 번짐은 확실히 좋아지고, 성공률은 몇 %p 수준으로 본다(미측정).
- 대가: 1초 안에 풀린 좌석에 잘못된 409. 만료는 한 주기에 몰아서 풀리므로 그 직후 1초 동안 생길 수 있다. 측정에서 409 비율이 늘었는지로 본다.

## 측정 결과 (1번 사전 거절, 각 1회)
측정 브랜치 STEPS.md "선점 사전 거절 비교 실측"(`26edc87d`)이다.
- 거른 비율은 409의 73~84%로 가정(70~95%) 안이었다. 409 비율은 켠 회와 끈 회가 같았다(만료를 끈 측정이라 잘못된 409는 판정하지 못함).
- CPU 4코어, Gateway 경유: 160명 선점 처리 시간 -47%, 커넥션 사용 -51%. 매진 직후(320명) -95%, 좌석 조회 성공률 79.6% → 99.9%. 끝단 성공률이 예상(몇 %p)보다 크게 올랐다.
- CPU 4코어, 직접 호출: 한계 단계(320명, 커넥션 10개 포화)는 그대로다. 320명 선점 p95 -44%, 처리량 +5~11%.
- 상한 없음: 409가 원래 2~4ms로 싸서 차이가 거의 없다.
- 예상과 다른 점: 걸러진 요청도 멱등키 PK 조회(읽기 트랜잭션)를 하므로 비용이 0이 아니다. 상한 없는 환경에서 효과가 작은 이유 중 하나다.

## 추가 질문: 측정 뒤 다음 후보를 구체적으로
### 1. 잘못된 409를 만료를 켠 측정으로 확인
- **언제 생기나:** 사전 거절이 쓰는 스냅숏이 "잡힘"이라고 하는데 실제로는 풀린 좌석일 때다. 그런데 사용자는 좌석 조회 화면에서 "선택 가능"으로 본 좌석만 고른다. 그 화면도 같은 스냅숏에서 나왔다. 인스턴스가 하나면, 사용자가 본 스냅숏보다 사전 거절이 보는 스냅숏이 같거나 더 새롭다. 그래서 사용자가 "선택 가능"으로 본 좌석을 사전 거절이 "잡힘"으로 볼 일은 거의 없다(그 사이 다른 사람이 잡았다면 진짜 409다).
- **위험한 경우는 여러 대일 때다.** 인스턴스마다 스냅숏을 따로 만든다. 사용자가 A 인스턴스에서 막 풀린 좌석을 보고, 선점 요청이 B 인스턴스로 가면, B의 스냅숏은 최대 1초 더 낡아 아직 "잡힘"일 수 있다. 이때가 잘못된 409다.
- **어떻게 재나:** 측정 종류 X(만료 스케줄러 켬, 선점 유지 1분 회차, 초당 100명 300초)를 `SCALE=2`로 끔·켬 1회씩 잰다.
  - 409 비율을 비교한다. 다만 비율 차이는 작아서 1회 비교로는 가리기 어렵다.
  - 그래서 측정 브랜치에서만 표본 검증을 더한다. 사전 거절한 요청 중 1%를 골라 그 순간 DB에서 해당 좌석 상태를 읽고, 전부 `AVAILABLE`이면 "잘못된 거절"로 센다. 잘못된 거절 비율을 직접 얻는다.
- **판정:** 잘못된 거절이 사전 거절의 1% 아래면 받아들일 만하다. 사용자는 다시 누르면 된다. 넘으면 여러 대일 때는 스냅숏 시간을 줄이거나, 사전 거절을 "1초보다 오래 잡혀 있던 좌석"에만 쓰는 식으로 좁힌다.

### 2. 걸러진 요청의 멱등키 조회를 트랜잭션 없이
- **지금:** 걸린 요청은 `readTransaction`(읽기 전용 트랜잭션) 안에서 `seat_hold_requests`를 PK로 찾는다. 커넥션을 빌리고, JPA 세션을 열고, `BEGIN READ ONLY` + `SELECT`, `COMMIT`, 커넥션 설정 되돌리기까지 한다. 왕복 2번 이상과 JPA 비용이다.
- **바꾼 모습:** 자동 커밋으로 `SELECT 1 FROM seat_hold_requests WHERE request_id = ?` 한 문장만 보낸다(JdbcTemplate). 없으면 바로 409다. 있을 때(같은 멱등키 재요청, 드묾)만 지금의 재응답 경로(읽기 트랜잭션)로 간다.
- **효과(추정):** 걸린 요청 한 건이 커넥션을 쥐는 시간이 왕복 1번으로 준다. 커넥션 10개가 꽉 찬 직접 호출 측정(320명 이상)에서 효과가 보일 곳이다. 상한 없는 환경에서는 원래 작다.
- **더 줄이는 안과 기각 이유:** 최근 성공한 멱등키를 로컬 캐시에 두면 조회를 없앨 수 있다. 하지만 여러 대일 때 다른 인스턴스가 받은 첫 요청을 모르므로 재응답 대신 409가 나간다. 멱등키 계약을 깨므로 쓰지 않는다.

### 3. feat 브랜치에 넣으려면
- **막는 것:** 사전 거절은 좌석 조회의 1초 상태 캐시(P4c)에 기댄다. dev에는 P4c가 없다(ISE-205 Backlog, 담당 반효승). 측정 브랜치의 P4b·P4c는 측정 브랜치 P4a(`SeatMapRow`) 위에 짰고, dev는 `ScheduleSeatRow`라 그대로 옮기면 좌석 조회 파일 5개가 충돌한다.
- **순서:**
  1. 효승에게 P4b·P4c 측정 근거와 사전 거절 결과를 넘긴다(남은 일 목록의 "효승 전달"과 같은 묶음).
  2. 효승이 dev의 `ScheduleSeatRow` 위에 P4b·P4c를 구현한다(ISE-204, 205). 이때 선점 모듈이 읽을 공개 메서드 하나를 같이 둔다. 캐시를 새로 읽지 않고, TTL 안의 상태로만 "선점 불가 좌석이 섞였는가"를 답하는 메서드다. 모듈 간 접점이므로 `contract` 이슈로 맞춘다.
  3. 내가 feat 브랜치에 `HeldSeatPreCheck`를 넣는다. 설정 기본값은 끔이다. 1번 측정에서 잘못된 거절이 기준 안이면 켠다.
- **함께 고칠 것:** 지금 측정 코드는 회차에 속하지 않는 좌석 ID도 스냅숏에 없으니 409로 거른다. 원래는 400(`SEAT_COUNT_MISMATCH`)이다. 배치 캐시(P4b)로 회차 소속을 먼저 확인하면 원래 응답을 지킬 수 있다.

### 후속 측정 결과 (측정 브랜치 `0d38d570`, 각 1회)
- 후보 2(가벼운 멱등키 조회): 차이를 가를 수 없었다. L과 P의 차이(처리량 ±5%, p95 ±12%)가 같은 조건을 두 번 잰 차이와 비슷하다. 커넥션이 찬 구간에서 커넥션을 쥐는 것은 걸린 요청이 아니라 걸리지 않은 409와 201의 쓰기 트랜잭션이기 때문으로 본다. 넣지 않는다.
- 후보 1(잘못된 409): 2대, 만료 켬(측정 중 약 8,700건 만료)에서 표본 407건 중 0건이었다. 95% 신뢰 상한 약 0.7%로 기준(1% 미만)을 만족한다. 409 비율도 72.5%와 72.4%로 같다.

## 이 프로젝트에서는
- 추천 순서: 5의 만료 상한 반영(이미 측정함) → 1번을 측정 브랜치에서 P4c 위에 구현해 K1 S(CPU 4코어)와 잠금 장애 주입 K로 측정 → 효과가 있으면 2번과 함께 feat 브랜치에 넣고, P4c 이관(ISE-205)을 효승과 맞춘다.
- 1번의 측정 판단 기준: CPU 4코어 S에서 선점 p95, 320명 단계 성공률, reservation-service CPU, DB 커넥션 활성 수가 나아지는지 본다. 409 비율은 같아야 한다(잘못된 409가 늘면 1초 낡음의 대가가 보이는 것이다).
- 3번은 발표 질문("왜 Redis로 좌석을 잡지 않았나")에 답할 거리로 남겨 둔다. 답은 "최종 판정을 DB 한 곳에 두고, 확실히 질 요청만 캐시로 먼저 거절했다"다.

## 면접 포인트
- "캐시로 동시성 제어를 대신할 수 있나?" → 캐시는 판정이 아니라 거절에만 쓴다. 낡은 캐시가 '팔렸다'고 하면 잘못된 거절이 생기고, '비었다'고 하면 DB가 막는다. 어느 쪽도 중복 판매로 이어지지 않게 방향을 정한다.
- "Redis 분산 락이나 Redis 선점이 왜 바로 답이 아닌가?" → 상태의 주인이 둘이 되면 실패·만료·확정마다 두 곳을 맞춰야 한다. 성능 이득이 그 비용보다 클 때만 쓴다.
- "실패할 요청을 싸게 만드는 것"은 성공할 요청을 빠르게 만드는 것만큼 중요하다. 티켓 오픈처럼 실패가 다수인 부하에서는 더 그렇다.
