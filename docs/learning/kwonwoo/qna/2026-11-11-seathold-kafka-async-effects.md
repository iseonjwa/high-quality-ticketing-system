# 좌석 선점에 Kafka 접수형을 도입하면 어떻게 동작하고 무엇이 좋아지나

## 질문
카프카가 도입된다면 어떤 식으로, 어떤 개선 효과가 있을까? 좌석 선점 부분에 한해서.

## 짧은 답
- 동작: 선점 API가 바로 좌석을 바꾸지 않고 "선점 요청"을 저장한 뒤 202를 준다. 요청은 회차+구역 키로 Kafka에 들어가고, 구역마다 소비자 하나가 순서대로 같은 선점 로직을 실행한다. 사용자는 결과 조회 API로 HELD 또는 REJECTED를 받는다.
- 기대 효과는 처리량보다 **경합과 과부하를 다루는 방식**에서 나온다. 같은 인기 좌석을 동시에 잠그려는 싸움이 사라지고, DB 커넥션 사용량에 상한이 생기고, 몰린 요청이 서버 스레드 대신 Kafka에 쌓인다.
- 대신 결과를 늦게 알게 되고(outbox 폴링 + 소비 + 클라이언트 폴링), 인기 구역 하나는 소비자 하나의 속도에 묶이며, 구현할 것이 많다.
- 지금 측정만 보면 선점 경로는 병목이 아니다. K1-H에서 선점은 초당 200명까지 오류 0%, p95 약 17ms였다. 대기열이 입장을 초당 50명으로 막고 있어 선점에 스파이크가 오지 않는다. 그래서 지금 조건 그대로 도입하면 K1 수치는 거의 좋아지지 않고 응답이 느려질 수 있다. 효과를 보이려면 선점이 병목이 되는 조건에서 비교해야 한다.

## 자세히

### 1. 지금(동기형)과 접수형의 흐름 차이

> 비유: 동기형은 손님이 주방에 직접 들어가 재료를 집는 식당이다. 인기 재료 앞에서 손님끼리 부딪히고, 주방이 붐비면 문밖까지 줄이 막힌다. 접수형은 주문서를 레일에 꽂는 식당이다. 구역(코너)마다 요리사 한 명이 자기 레일의 주문서를 순서대로 처리한다. 손님은 번호표를 받고 기다린다.

동기형(구현됨, `SyncSeatHoldService`):

```
POST /schedules/{id}/reservations
  └ 한 트랜잭션: 매수 한도 UPDATE → 좌석 AVAILABLE→HELD UPDATE → 예매 저장 → 201 + 결제 토큰
```

접수형(설계, SA 10-1, ISE-15~18):

```
1. POST /schedules/{id}/reservations  (seat-hold.mode=async)
   └ 한 트랜잭션: seat_hold_requests(REQUESTED) + outbox_events 저장 → 202 + requestId
2. Outbox 릴레이(500ms 주기) → 토픽 seat-hold.request, 키 {scheduleId}:{section}
3. SeatHoldConsumer(그룹 reservation.seat-hold)
   └ processed_events로 중복 차단 → 동기형과 같은 선점 로직 → 요청 HELD 또는 REJECTED
4. GET /reservations/requests/{requestId} 폴링 → HELD면 예매 ID와 결제 토큰
5. 예외: 30초 안에 처리 못 하면 REJECTED(TIMEOUT), 재시도 3회 실패면 DLQ → REJECTED(PROCESSING_FAILED)
```

소비자는 파싱과 중복 차단만 하고 선점 규칙은 동기형과 같은 application 코드를 부른다. 그래야 재측정에서 차이가 접수 방식에서만 나온다. 소비자 위치는 ADR 0043(2026-11-03)에 따라 `presentation/messaging`이다. 2026-11-03 노트([seathold-kafka-placement](2026-11-03-seathold-kafka-placement.md))의 "infrastructure에 둔다"는 이 ADR로 바뀌었다.

### 2. 기대 효과

| 효과 | 왜 생기나 | 확인할 지표 |
|---|---|---|
| 같은 좌석 잠금 경합 감소 | 같은 구역 요청이 한 파티션에서 한 줄로 처리된다. 인기 구역(측정 가정: 70%가 앞 10%)에 몰린 요청이 동시에 같은 행을 잠그지 않는다 | 잠금 대기 수, 데드락, 409 처리 시간 |
| 데드락 위험 감소 | 같은 구역 안에서는 동시 트랜잭션이 없다. 구역을 넘는 다중 좌석 선택은 여전히 겹칠 수 있어 좌석 ID 오름차순 잠금은 계속 필요하다 | 데드락 로그(TS-1) |
| DB 커넥션 사용 상한 | 선점이 쓰는 커넥션 수가 "소비자 동시성"으로 고정된다. 지금은 요청 수만큼 커넥션을 다투고, 풀이 5개라 선점과 좌석 조회가 서로 굶긴다 | 커넥션 대기(pending), 좌석 조회 성공률 |
| 과부하 뒤 회복 | B8에서 본 문제는 Gateway가 3초에 포기한 요청을 서버가 끝까지 붙잡는 것이었다. 접수형은 접수 응답이 짧고, 밀린 일은 Kafka에 쌓여 소비자 속도로 빠진다 | 부하 후 회복 시간, 소비자 랙 |
| 진 요청의 빠른 정리 | 앞 요청이 이미 좌석을 잡았으면 뒤 요청은 잠금 대기 없이 조건부 UPDATE 0행으로 바로 REJECTED가 된다 | 소비 처리 시간 p95 |
| 발제 요구 충족 | "요청을 Topic에 적재하고 바로 응답, Consumer가 처리"를 선점에 적용 | - |

### 3. 비용과 한계

| 비용 | 내용 |
|---|---|
| 결과를 아는 시점이 늦어짐 | outbox 폴링 최대 500ms + 소비 처리 + 클라이언트 폴링 간격. 선점 5분 타이머는 HELD가 된 시점부터 세야 사용자가 손해를 보지 않는다 |
| 접수도 DB에 쓴다 | outbox 방식은 접수 때 `seat_hold_requests`와 `outbox_events` 두 행을 쓴다. 잠금 경합은 줄지만 DB 쓰기 자체가 사라지지 않는다. DB가 멈추면 접수도 실패한다 |
| 인기 구역 상한 | 한 파티션은 소비자 하나가 순서대로 처리한다. 선점 한 건이 10~17ms라면 구역 하나는 대략 초당 60~100건이 상한이다(K1-H p95로 어림한 추정, 미측정) |
| 구현량 | 결과 조회 API, 30초 타임아웃 스케줄러, DLQ 처리, 프론트 폴링 화면, reservation-service에 outbox·processed_events 테이블과 설정 추가(같은 서비스의 다른 담당과 조율 필요) |
| 직접 발행안의 문제 | outbox 없이 바로 발행하면 접수가 빠르지만, 발행 뒤 소비 실패를 저장할 곳이 없어 "처리 중"으로 남는다(설계 결함 D4) |

### 4. 지금 측정으로 본 현실

| 관찰 | 근거 | 해석 |
|---|---|---|
| 선점만 떼어 재면 초당 200명까지 오류 0%, p95 약 17ms | K1-H, 2026-11-07~09 local | 선점 로직 자체에는 여유가 있다 |
| 초당 400명부터 오류 30~43% | K1-H | 원인은 Gateway `auth-redis` 차단기다. 선점 쪽이 아니다 |
| K1의 주 병목은 좌석 조회(15,000행 조인, JSON 생성)와 DB CPU | K1 base~P4b | Kafka 접수형은 좌석 조회를 건드리지 않는다 |
| 대기열이 초당 50명만 입장시킨다 | `admit-per-second: 50` | 선점 도착률이 이미 평탄하다. Kafka가 하려던 "줄 세우기"를 대기열이 먼저 하고 있다 |
| JUnit 동시성 측정에서 병목은 DB 잠금이 아니라 커넥션 풀 | `concurrency-results.md` | 커넥션 상한 효과는 기대할 만하다 |

정리하면, 지금 조건에서 접수형의 이득은 "커넥션 사용 격리"와 "경합 안정성" 정도다. 처리량이 크게 오르는 그림은 아니다.

### 5. 효과를 보이려면 어떻게 측정하나

ISE-18과 SA 10-1은 "동기형 / 직접 발행 / outbox" 세 방식을 같은 환경에서 비교하는 것으로 계획되어 있다. 선점이 실제 병목이 되는 조건을 만들어야 차이가 보인다.

1. 선행: Gateway `auth-redis` 차단기 문제를 정리해 K1-H 400명 이상에서 선점까지 요청이 닿게 한다.
2. 조건: 입장 속도를 올리거나(예: 초당 500명) 대기열 없이 선점만 때리는 K1-H로, 인기 구역 쏠림을 강하게 둔다.
3. 지표:
   - 접수 응답 p95
   - 요청부터 HELD까지 걸린 시간 p95(사용자 체감)
   - 잠금 대기, 데드락, 커넥션 대기
   - 소비자 랙, 부하 후 회복 시간
   - 같은 시간에 돌린 좌석 조회의 성공률(커넥션 격리 효과)
   - 대사 위반 0
4. 예상: 동기형은 경합이 커질수록 잠금·커넥션 대기로 무너지고, 접수형은 접수 응답은 평탄하지만 HELD까지 시간이 늘어난다. 이 교환 관계를 수치로 보여 주는 것이 결론이다.

### 6. 다른 선택지: 혼합형

`docs/sa-review/03-seat-hold-kafka-design.md` 5절의 혼합형은 Redis Lua로 좌석을 즉시 판정해 200을 주고, DB 기록만 Kafka로 넘긴다. 진 요청 대부분이 Redis에서 끝나 DB에 오지 않고, 사용자는 결과를 바로 본다. 대신 Redis와 DB 두 곳의 상태를 맞추는 규칙(만료 기준은 DB, Redis TTL을 조금 길게)이 필요하다. 팀은 이 안을 v3 후보로 내렸다(SA M1 반영 표).

- 이슈: ISE-15(상위), ISE-16(접수·조회 API), ISE-17(소비자·DLQ·타임아웃), ISE-18(재측정). 모두 M4 Backlog
- 범위 결정: ADR 0035(접수형 전환을 M4 트러블슈팅 TS-5로 분리)
- 측정 근거: `docs/design/reservation/k6-seathold-bottleneck-plan.md`, `concurrency-results.md`, 측정 브랜치 `experiment/ISE-79-k6-steps`의 STEPS.md

## 면접 포인트
- "좌석 선점에 왜 Kafka를 썼나(또는 안 썼나)" → 같은 구역 요청을 한 파티션에서 순서대로 처리해 잠금 경합과 커넥션 사용을 제한하려는 목적이다. 그런데 대기열이 이미 입장 속도를 제한하고 있어서, 동기형 기준선을 먼저 재고 선점이 병목이 되는 조건에서만 전환 효과를 비교하기로 했다.
- "파티션 키를 회차로 하면" → 인기 회차 하나가 파티션 하나에 몰려 소비자 하나만 일한다. 그래서 구역까지 넣었다. 정합성은 파티션 순서가 아니라 DB 조건부 UPDATE가 지킨다.
- "비동기로 바꾸면 무엇을 잃나" → 결과를 즉시 못 본다. 그래서 선점 타이머를 HELD 시점부터 세고, 30초 타임아웃과 DLQ로 "처리 중"에 영원히 남는 요청을 없앤다.
