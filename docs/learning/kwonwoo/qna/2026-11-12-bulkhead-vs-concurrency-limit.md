# 벌크헤드(Bulkhead)와 동시 처리수 상한(Concurrency Limit)의 차이

## 질문
벌크헤드랑 동시처리수 상한이랑 어떻게 다른 거야?

## 짧은 답
- **벌크헤드 (Bulkhead, 격벽):** 자원을 방수 구역처럼 쪼개어 특정 작업의 장애나 지연이 다른 작업으로 번지지 않게 막는 **장애 격리(Partitioning / Isolation)** 패턴이다.
- **동시 처리수 상한 (Concurrency Limit / In-flight Limit):** 시스템이 감당할 수 있는 최대 요청 수에 천장을 두어, 메모리 폭사(OOM)나 CPU 포화를 막기 위해 초과분을 빠르게 거절하는 **과부하 보호(Overload Protection / Load Shedding)** 패턴이다.
- **비유:**
  - **동시 처리수 상한**은 건물의 **"최대 정원 100명"**(101번째 손님은 문밖에서 입장 제한).
  - **벌크헤드**는 배의 **"방수 격벽"** 또는 식당의 **"예약석 20석 / 일반석 80석 구역 분리"**(일반석이 꽉 차거나 불이 나도 예약석 손님은 영향을 받지 않음).

## 자세히

### 1. 벌크헤드 (Bulkhead)
선박에 물이 찼을 때 배 전체가 침몰하지 않도록 공간을 독립된 방수 구역(격벽)으로 나누는 데서 유래했다.

- **목적:** 한 기능이나 특정 의존성(DB, 외부 API, 특정 라우트)의 지연·장애가 전체 스레드나 커넥션을 독점하여 시스템 전체가 마비되는 **자원 고갈(Resource Starvation)**을 막는 것이다.
- **동작 방식:**
  - 스레드 풀 격리: A 작업용 스레드 10개, B 작업용 스레드 10개로 분리.
  - 세마포어 격리: 공유 풀 안에서 A 작업이 동시에 쓸 수 있는 퍼밋을 N개로 제한.
- **핵심 질문:** "어떤 한 녀석이 고장 나더라도 다른 녀석들이 살아남을 수 있는가?"

### 2. 동시 처리수 상한 (Concurrency Limit / In-flight Limit)
시스템(또는 프로세스) 전체가 동시에 처리 중인 요청(In-flight requests)의 총합을 제한한다.

- **목적:** 수용 용량을 넘는 트래픽이 쏟아져 들어올 때 버퍼 급증, 메모리 초과(OOM), CPU 스래싱, GC 지옥으로 시스템이 강제 종료되는 것을 막는 **자기 보호(Self-defense)**다.
- **동작 방식:**
  - 현재 처리 중인 요청 수가 임계치(예: 200개)에 도달하면, 추가 요청은 큐에서 무한정 대기시키는 대신 즉시 `503 Service Unavailable`이나 `429 Too Many Requests` + `Retry-After`로 탈락(Drop/Shed)시킨다.
- **핵심 질문:** "우리 시스템이 물리적으로 버틸 수 있는 한계를 넘어 터지지 않게 막고 있는가?"

### 3. 비교 요약

| 구분 | 벌크헤드 (Bulkhead) | 동시 처리수 상한 (Concurrency Limit) |
|---|---|---|
| **핵심 목적** | **장애 격리 (Fault Isolation)** | **과부하 방어 (Overload Protection)** |
| **관점** | 자원의 **분할 / 할당 (Partitioning)** | 전체 용량의 **천장 / 상한선 (Ceiling)** |
| **막는 문제** | 특정 경로가 지연되어 다른 정상 경로까지 굶어 죽는 현상 | 트래픽 폭주로 메모리(OOM)나 CPU가 터져 프로세스가 죽는 현상 |
| **구현 방식** | 작업/경로별 세마포어, 전용 스레드 풀, 전용 커넥션 풀 | 전체 요청 세마포어, Netty 연결 상한, 리액티브 배압 제어 |
| **설정 형태** | "A 기능 최대 25개, B 기능 최대 10개" | "서버 전체 in-flight 최대 200개" |

## 이 프로젝트에서는

우리 시스템에서 실제로 겪은 측정 사례로 보면 둘의 차이가 분명해진다.

### 1. 벌크헤드가 필요한 순간 (Z 시나리오)
- **문제:** 인기 좌석 10석에 트래픽이 몰리자, 선점 요청들이 500ms `lock_timeout` 동안 커넥션 10개를 모두 쥐고 늘어졌다. 그 결과 잠금과 아무 상관없는 **공연 목록·좌석 조회 API까지 커넥션을 얻지 못해 성공률이 53.5%로 반토막** 났다.
- **해결 (벌크헤드 적용):** 선점 경로에 `Semaphore(8)`을 두어 선점이 커넥션을 최대 8개까지만 쓰게 막으면, 잠금 지연이 발생해도 **남은 커넥션 2개는 좌석 조회/공연 조회가 항상 쓸 수 있게 격리**된다.

### 2. 동시 처리수 상한이 필요한 순간 (Gateway OOMKilled)
- **문제:** 4코어 환경에서 830KB 좌석 응답이 초당 수백 건 들어오자, Gateway가 응답을 미처 다 내보내지 못하고 동시에 370개의 응답을 쥐게 되었다. 커널 소켓 버퍼(590MiB) + Netty 직접 버퍼(183MB)가 768MB 상한을 넘어 **Gateway가 OOMKilled로 강제 종료**됐다.
- **해결 (동시 처리수 상한 적용):** Gateway가 동시에 중계하는 큰 응답 수를 최대 150~200개로 제한하여, 초과하는 요청은 들어오기 전에 즉시 503으로 거절함으로써 메모리 폭사를 막고 정상 요청 200개를 살린다.

## 면접 포인트
- **"벌크헤드와 Rate Limiter / Concurrency Limit의 차이는 무엇인가요?"**  
  → Rate Limiter나 Concurrency Limit은 들어오는 트래픽의 **양(처리율/동시성)을 제한해 시스템 전체가 다운되는 것을 막는 방어선**입니다. 반면 벌크헤드는 자원을 내부적으로 **구획화(Partitioning)하여 한 도메인/경로의 지연이나 장애가 다른 정상 도메인의 자원을 고갈시키지 않도록 격리**하는 패턴입니다.
- **"동시 처리수 상한은 왜 큐잉(Queueing) 대신 거절(Dropping)을 택하나요?"**  
  → 대기열(Queue)에 요청을 계속 쌓아두면 지연 시간이 누적되어 클라이언트 타임아웃을 초과하게 되고, 결국 서버는 이미 떠난 클라이언트를 위해 헛된 작업을 처리하는 악순환이 발생합니다. 버틸 수 없는 요청은 즉시 빠르게 실패(Fail-fast)시키는 것이 살아있는 요청의 성공률과 시스템 안정성을 지키는 길입니다.
