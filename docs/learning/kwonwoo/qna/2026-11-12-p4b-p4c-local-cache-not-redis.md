# 좌석 배치 캐시를 로컬 메모리에 둘까 Redis에 둘까 (개념부터 측정·원인까지)

이 노트는 캐시, Redis, GC, 부하 테스트를 처음 보는 사람도 끝까지 따라올 수 있게 썼다. 1~2절은 결론과 배경, 3절은 필요한 기초 개념, 4~6절은 무엇을 어떻게 쟀는지, 7~9절은 결과를 읽는 법과 원인, 10절 이후는 응용과 면접 준비다. 수치 원본은 [k6-p4b-local-vs-redis.md](../../../design/reservation/k6-p4b-local-vs-redis.md)와 측정 브랜치 STEPS.md에 있다.

## 질문

1. 측정 브랜치의 P4b(좌석 배치 캐시)는 로컬 캐시인가, Redis를 쓴 것인가?
2. 그럼 P4b를 Redis로도 만들어 성능을 재고, 어느 쪽이 어떤 지표에서 앞섰는지와 그 원인을 정리해 달라.

## 1. 짧은 답

- P4b와 P4c는 둘 다 **로컬 캐시**다. reservation-service 프로세스(JVM) 메모리 안의 맵에 값을 둔다. Redis는 쓰지 않았다.
- 같은 배치를 Redis에 두는 방식으로도 구현해 세 조건에서 재 보니 **모든 조건에서 로컬이 앞섰다.** 좌석 조회 p95가 7.0ms 대 38.3ms였고, 버틴 부하 단계는 640명 대 160명이었다.
- 원인은 Redis가 느려서가 아니다. **바뀌지 않는 큰 값(1.3MB)을 요청마다 네트워크로 옮겨 다시 객체로 만드는 구조**가 CPU와 메모리를 먹었다. 그 결과 GC가 잦아졌고, 짧은 Redis 시한(100ms)에 걸려 요청이 실패했다.
- Redis가 이긴 것처럼 보인 지표도 있었다. 하지만 그것은 앞 단계가 먼저 실패해 뒤 단계로 온 요청이 줄어든 착시였다(8절).

## 2. 배경: 좌석 조회 API가 하는 일

콘서트 예매 화면에서 사용자는 먼저 좌석 지도를 본다. 서버의 `GET /api/v1/schedules/{회차}/seats`가 그 지도를 준다. 한 회차에는 좌석이 15,000석 있고, 응답 JSON은 약 830KB다.

응답에 들어가는 정보는 성격이 다른 두 가지다.

| 구분 | 내용 | 바뀌는 빈도 |
|---|---|---|
| 배치(layout) | 좌석 ID, 구역, 열, 번호, 구역 등급, 가격 | 판매 중에는 거의 안 바뀐다 |
| 상태(state) | 지금 고를 수 있는 좌석인가 | 누가 선점할 때마다 바뀐다 |

티켓 오픈 순간에는 수많은 사용자가 이 API를 동시에 부른다. 처음에는 요청마다 DB에서 15,000행을 조인해 읽었고, 초당 10~80명에서 서버가 무너졌다(단계별 수치는 [k6-seathold-story.md](../../../design/reservation/k6-seathold-story.md) 4절). 그래서 단계별로 고쳤다.

- P4a: 엔티티 대신 필요한 열만 읽는다.
- P4b: **배치를 캐시**한다. 요청마다 DB에서는 "고를 수 있는 좌석 ID"만 읽는다.
- P4c: **상태도 1초 동안 캐시**한다. 회차마다 DB 조회가 1초에 한 번이 된다.

이 노트가 다루는 것은 P4b의 배치 캐시를 **어디에 두느냐**다.

## 3. 먼저 알아야 할 개념

### 3-1. 캐시

캐시는 비싸게 만든 결과를 저장해 두었다가 다시 쓰는 것이다. 좌석 배치처럼 DB에서 여러 테이블을 조인해 만드는 결과는 비싸다. 한 번 만든 결과를 두고 다음 요청에 그대로 주면 그 비용을 아낀다. 대가는 두 가지다. 원본이 바뀌면 캐시가 낡는다(무효화 문제). 그리고 저장할 공간이 필요하다.

### 3-2. 로컬 캐시와 원격 캐시

캐시를 어디에 두느냐에 따라 둘로 나뉜다.

```
로컬 캐시                              원격 캐시(Redis)
┌────────────── reservation-service ┐   ┌──── reservation-service ┐      ┌── Redis ──┐
│ 요청 → 메모리의 맵에서 객체를 꺼냄    │   │ 요청 → 네트워크로 GET ──────┼────→ │ 값(바이트) │
│        (참조만 넘김, 복사 없음)      │   │      ← 1.3MB 바이트 받음 ←───┼───── │           │
│                                    │   │      → 바이트를 객체로 복원   │      └───────────┘
└────────────────────────────────────┘   └─────────────────────────┘
```

| 기준 | 로컬 캐시 | 원격 캐시(Redis) |
|---|---|---|
| 꺼내는 비용 | 메모리 참조. 거의 0 | 네트워크 왕복 + 바이트 전송 + 객체 복원(역직렬화) |
| 서버가 여러 대일 때 | 대마다 따로 가진다 | 모든 대가 하나를 같이 본다 |
| 원본이 바뀌었을 때 | 모든 대의 캐시를 비워야 한다 | 키 하나만 지우면 된다 |
| 캐시 저장소 장애 | 상관없다 | Redis가 느려지면 같이 느려진다 |

원격 캐시의 장점은 **공유**와 **무효화가 한 곳**이라는 점이다. 단점은 **꺼낼 때마다 옮기고 복원하는 비용**이다. 값이 작으면 이 비용이 작고, 값이 크면 커진다. 이 노트의 측정은 결국 이 비용이 얼마나 되는지를 잰 것이다.

### 3-3. 직렬화와 역직렬화

자바 객체는 JVM 메모리 안에서만 의미가 있다. 네트워크로 보내거나 Redis에 넣으려면 바이트(여기서는 JSON 문자열)로 바꿔야 한다. 이것이 **직렬화**다. 꺼낼 때는 반대로 바이트를 읽어 객체를 다시 만든다. 이것이 **역직렬화**다.

```java
// 직렬화: List<SeatLayoutRow>(15,000개) → JSON 문자열(1,344,751바이트)
String json = objectMapper.writeValueAsString(layout);
// 역직렬화: JSON 문자열 → 새 List<SeatLayoutRow>(15,000개 객체를 새로 만든다)
List<SeatLayoutRow> rows = objectMapper.readValue(json, ROWS);
```

역직렬화는 공짜가 아니다. 문자를 하나씩 읽어 필드를 맞추고, 객체 15,000개와 그 안의 문자열·숫자 객체를 **새로 할당**한다. 좌석 조회 한 건마다 이 일을 하면 CPU와 메모리를 크게 쓴다.

### 3-4. JVM 힙, 할당, GC

자바에서 `new`로 만든 객체는 **힙**이라는 메모리 영역에 놓인다. 다 쓴 객체를 치우는 일은 **GC(가비지 컬렉터)**가 한다. 이 서비스는 G1 GC를 쓰고 힙은 768MB다.

- **할당률**: 초당 새로 만드는 객체의 양이다. 높을수록 힙이 빨리 차고 GC가 자주 돈다.
- **GC 정지(pause)**: GC가 일하는 동안 애플리케이션 스레드가 잠깐 멈춘다. 보통 수 ms이고, 힙이 거의 꽉 차면 길어진다.
- **Full GC**: 힙 전체를 한 번에 정리하는 무거운 GC다. 수백 ms 동안 서비스 전체가 멈출 수 있다. G1에서 Full GC가 나면 힙이 감당하지 못하고 있다는 신호다.
- **Evacuation Failure**: G1이 살아 있는 객체를 옮길 빈 공간을 찾지 못한 상태다. 대개 Full GC로 이어진다.

정리하면, 요청마다 큰 객체 묶음을 새로 만드는 코드는 할당률을 올리고, GC를 잦게 하며, 심하면 서비스 전체를 멈추게 한다.

### 3-5. Redis 클라이언트 연결과 명령 시한

Spring Boot는 Redis 클라이언트로 **Lettuce**를 쓴다. 기본 설정에서는 서비스 안의 모든 Redis 명령이 **TCP 연결 하나를 같이 쓴다**(`LettuceConnectionFactory`의 공유 연결). 명령은 그 연결에 차례로 실려 가고, 응답도 들어온 순서대로 처리된다. 응답 하나가 1.3MB면 그것을 다 받아 처리하기 전까지 뒤 응답들이 기다린다.

**명령 시한**은 "이 시간 안에 응답이 안 오면 포기한다"는 설정이다. 이 프로젝트는 공통 설정 `config-repo/application.yml`의 `spring.data.redis.timeout`이 100ms다. 대기열·인증처럼 작은 명령에 맞춘 값이라 짧다. 시한을 넘기면 `QueryTimeoutException`이 나고, 처리하지 않으면 500 응답이 된다.

### 3-6. Redis 메모리 상한과 noeviction

이 프로젝트의 Redis는 한 대이고, Gateway 인증·대기열·(이번 시험의) 배치 캐시가 함께 쓴다. 설정은 `maxmemory 128mb`, `maxmemory-policy noeviction`이다.

- `maxmemory`: Redis가 쓸 수 있는 메모리 상한이다. 저장한 값뿐 아니라 클라이언트로 내보내는 중인 응답 버퍼도 메모리를 쓴다.
- `noeviction`: 상한에 닿으면 기존 키를 지우지 않고 **새 쓰기 명령을 거절**한다. 대기열 입장이나 인증 같은 다른 기능의 쓰기도 함께 거절된다.

### 3-7. 부하 테스트 용어

| 용어 | 뜻 |
|---|---|
| k6 | 가상 사용자를 만들어 API를 부르는 부하 생성 도구 |
| p50 / p95 / p99 | 응답 시간을 정렬했을 때 50%·95%·99% 지점 값. p95가 38ms면 요청 95%가 38ms 안에 끝났다는 뜻이다 |
| 성공률 | 의도한 응답(좌석 조회 200, 선점 201·409)의 비율. 409는 "이미 잡힌 좌석"이라는 정상 응답이다 |
| L(부하) | 초당 100명을 300초 동안 일정하게 보낸다. 평소 지연을 본다 |
| S·M(스트레스) | 초당 5명에서 시작해 60초마다 두 배로 올린다(5, 10, 20 … 1,280명). 어디서 무너지는지 본다. M은 단계마다 새 회차를 써서 매진을 피한다 |
| 버틴 단계 | 성공률이 99% 이상 유지된 가장 높은 단계 |
| Gateway 경유 / 직접 호출 | 실제처럼 Gateway를 거치는 경로 / Gateway를 빼고 서비스만 재는 경로 |
| CPU 4코어 | 배포 서버(4 vCPU)처럼 모든 컨테이너를 같은 4코어에 묶은 조건 |
| 대사 | 측정 뒤 DB에서 이중 판매·매수 불일치가 없는지 확인하는 검사 |

## 4. 무엇을 만들었나

측정 브랜치에 `SeatLayoutCache`를 만들었다. 설정 `seatmap.layout-cache` 하나로 저장소를 고른다.

```java
public List<SeatLayoutRow> get(Long scheduleId) {
    if (!useRedis) {
        // 로컬: 메모리 맵에서 꺼낸다. 처음 한 번만 DB를 읽는다
        return localCache.get(scheduleId, () -> seatMapReader.readLayout(scheduleId));
    }
    // Redis: 요청마다 GET → JSON을 객체로 복원한다
    String cached = redis.opsForValue().get(KEY_PREFIX + scheduleId);
    if (cached != null) {
        return objectMapper.readValue(cached, ROWS);
    }
    // 없으면 DB에서 읽어 넣는다(TTL 1시간)
    List<SeatLayoutRow> layout = seatMapReader.readLayout(scheduleId);
    redis.opsForValue().set(KEY_PREFIX + scheduleId, objectMapper.writeValueAsString(layout), REDIS_TTL);
    return layout;
}
```

- Redis 방식은 "값 하나를 JSON으로 넣고 꺼낸다"는, Spring에서 가장 흔한 사용법으로 만들었다.
- Redis 앞에 로컬 캐시를 한 겹 더 두는 방식(근접 캐시)은 일부러 넣지 않았다. 넣으면 대부분의 요청이 로컬에서 끝나 로컬 방식과 같아지고, 비교가 되지 않는다.
- 두 방식이 같은 응답을 내는지 기존 좌석 조회 시험 7개를 Redis 설정으로 한 번 더 돌려 확인했다(`ScheduleSeatRedisLayoutApiTest`, 모두 통과).

## 5. 어떻게 공정하게 쟀나

성능 비교는 조건이 하나라도 다르면 의미가 없다. 그래서 아래를 지켰다.

1. **같은 코드, 설정 하나만 다르게.** 같은 커밋(`6f89bbbb`)에서 `compose.layout-redis.yml`을 얹었는지 여부만 다르다.
2. **나머지 조건은 그대로.** 1초 상태 캐시(P4c), 정합성 수정, GC·커넥션 풀 설정이 같다.
3. **측정 전에 예상을 적었다.** 결과를 보고 해석을 맞추지 않으려는 것이다(9절에서 대조).
4. **세 조건으로 쟀다.** 평소 부하(L), 서비스 자체의 한계(직접 호출 M), 배포 서버와 비슷한 제약(CPU 4코어 S).
5. **Redis 쪽 지표도 함께 남겼다.** 회 앞뒤로 Redis `INFO`(내보낸 바이트, 명령 수, CPU, 메모리)를 저장했다.

## 6. 결과

### 6-1. 평소 부하: Gateway 경유, 초당 100명

| 지표 | 로컬 | Redis |
|---|---|---|
| 좌석 조회 성공률 | 100% | 99.4%(500 341건) |
| 좌석 조회 p50 / p95 / p99 | **4.0 / 7.0 / 10.0ms** | 17.3 / 38.3 / 131.9ms |
| reservation-service CPU 평균 | **0.99코어** | 4.43코어 |
| 좌석 조회 한 건당 CPU | **약 5.5ms** | 약 25ms |
| 메모리 할당 | **초당 약 259MB** | 초당 약 1.85GB |
| GC 정지 | **527회, 합 1.5초, 최대 16ms** | 8,797회, 합 21.8초, 최대 367ms, Full GC 2회 |
| Redis가 내보낸 데이터 | 0 | 74.1GB(초당 약 247MB) |

한 건당 CPU는 "평균 CPU ÷ 초당 처리 건수"로 셌다. 로컬은 0.99코어 ÷ 초당 179건 ≈ 5.5ms, Redis는 4.43코어 ÷ 초당 177건 ≈ 25ms다. 같은 양의 일을 하는 데 CPU를 약 4.5배 썼다.

### 6-2. 서비스 자체의 한계: 직접 호출, 단계적으로 올림

| 단계 | 로컬 성공률 · p95 | Redis 성공률 · p95 |
|---|---|---|
| 80명 | 100% · 4.3ms | 100% · 21.8ms |
| 160명 | 100% · 4.9ms | 99.0% · 37.6ms |
| 320명 | **100% · 8.7ms** | 64.9% · 124.6ms |
| 640명 | **100% · 639ms** | 15.1% · 180.9ms |

서버가 처리한 좌석 조회는 로컬이 최대 초당 1,244건, Redis가 397건이었다. Redis는 메모리가 132.68MB까지 올라 상한(128MB)을 넘었고, 쓰기 34건을 거절했다. 로컬 회는 1,280명 단계에서 부하 생성기(k6)가 자기 메모리 상한에 닿아 멈췄다. 그래서 640명까지만 비교한다.

### 6-3. 배포 서버 흉내: Gateway 경유, CPU 4코어

| 단계 | 로컬 성공률 | Redis 성공률 |
|---|---|---|
| 40명 | 100% | 99.6% |
| 80명 | **100%** | 94.3% |
| 160명 | **99.9%** | 54.2% |
| 320명 | **77.9%** | 25.7% |

버틴 단계는 로컬 160명, Redis 40명이다.

## 7. 원인: 무슨 일이 연쇄로 일어났나

숫자를 순서대로 이으면 하나의 사슬이 보인다.

1. **요청마다 1.3MB가 오간다.** Redis에서 꺼낸 배치 JSON은 1,344,751바이트다. 초당 177건이면 1.34MB × 177 ≈ 초당 237MB다. 실측 Redis 내보내기는 초당 247MB로 맞는다.
2. **받은 1.3MB를 객체 15,000개로 다시 만든다.** 이 역직렬화가 한 건당 CPU를 5.5ms에서 25ms로 늘렸다. 할당은 초당 259MB에서 1.85GB로 약 7배가 됐다.
3. **할당이 늘자 GC가 폭증했다.** 768MB 힙이 짧게 쓰고 버리는 큰 객체로 금방 찼다. GC가 약 17배(527회 → 8,797회) 잦아졌다. 부하 131초쯤에는 Evacuation Failure(181ms)에 이어 Full GC(367ms)가 났다.
4. **멈춘 동안 Redis 요청이 시한을 넘겼다.** 서비스가 0.5초 가까이 멈추는 동안, 공유 연결 하나에 줄 선 응답들이 처리되지 못했다. 시한 100ms를 넘긴 요청이 `Redis command timed out`으로 500이 됐다. L의 500 341건은 모두 그 2초 안에 몰렸다. 직접 호출 M에서는 500 114,385건 중 95%가 100~150ms에 끝났다. 시한 100ms에 걸렸다는 뜻이다.
5. **공유 Redis의 메모리 상한에 닿았다.** M은 단계마다 새 회차를 쓴다. 새 회차를 처음 읽는 순간 여러 요청이 동시에 1.3MB를 `SET`했고, 내보내는 중인 큰 응답 버퍼도 겹쳤다. Redis 메모리가 128MB를 넘자 `noeviction` 정책에 따라 쓰기를 거절했다. 같은 Redis를 쓰는 대기열 입장과 Gateway 인증의 쓰기도 그 순간 거절될 수 있었다.
6. **CPU가 부족하면 더 일찍 무너진다.** 4코어 조건에서는 역직렬화와 GC가 Gateway·DB와 같은 4코어를 나눠 먹었다. 그래서 80명 단계부터 실패가 나왔다.

반대로 Redis 서버 자체는 한가했다. 가장 바쁜 회에도 Redis CPU는 평균 0.16코어였다. 병목은 Redis가 아니라 **값을 받아 다시 만드는 클라이언트 쪽**에 있었다.

## 8. 함정: Redis가 이긴 것처럼 보인 지표

4코어 조건의 320명 단계만 떼어 보면 Redis가 더 좋아 보인다.

| 지표 | 로컬 | Redis |
|---|---|---|
| 선점 성공률 | 75.0% | 99.8% |
| 선점 p95 | 2,526ms | 166ms |
| DB 커넥션 대기 최대 | 123 | 0 |

하지만 이것은 Redis가 선점을 잘 처리했다는 뜻이 아니다. 사용자는 좌석 조회에 성공해야 선점을 시도한다. Redis 쪽은 좌석 조회가 먼저 대량으로 실패했다. 그래서 선점 단계까지 온 요청이 적었다(전체 선점 35,857건 대 52,020건). 일이 적으니 선점이 빠르고 DB도 한가했다.

식당에 비유하면, 입구에서 손님을 대부분 돌려보낸 식당의 주방이 한가한 것과 같다. 주방 성능이 좋아진 것이 아니다. 지표를 비교할 때는 **두 쪽이 같은 양의 일을 처리했는지**를 먼저 확인해야 한다.

## 9. 예상과 무엇이 달랐나

| 측정 전 예상 | 실측 | 배운 점 |
|---|---|---|
| p95가 5~15ms 오른다 | 31ms 올랐다(7.0 → 38.3ms) | 꼬리 지연은 GC 정지가 키운다 |
| CPU가 1.5~2배 | 약 4.5배 | 역직렬화를 직렬화 정도로 봤고, GC 증가를 계산에서 빠뜨렸다 |
| Redis 내보내기 초당 약 250MB | 초당 247MB | 전송량은 단순 곱셈으로 맞힐 수 있다 |
| 직접 호출 처리량 30~50% 감소 | 68% 감소(1,244 → 397) | 시한 실패가 겹쳐 더 떨어졌다 |
| 4코어에서 한 단계 낮아짐 | 두 단계 낮아짐(160 → 40명) | CPU를 나눠 쓰면 비용이 더 크게 드러난다 |

방향은 예상과 같았지만 크기는 모두 예상보다 컸다. "Redis는 네트워크 비용이 있다" 정도의 설명으로는 GC와 시한까지 이어지는 연쇄를 내다보기 어렵다. 측정이 필요한 이유다.

## 10. 그럼 Redis 캐시는 언제 쓰나

Redis가 나쁜 것이 아니다. 값의 성격이 맞지 않았다.

| 값의 성격 | 알맞은 곳 | 예 |
|---|---|---|
| 작고(수 KB 이하) 여러 대가 같은 값을 꼭 봐야 한다 | Redis | 로그인 세션, 대기열 순번, 입장 토큰 |
| 원자적으로 바꿔야 한다(동시에 여럿이 고침) | Redis | 카운터, 분산 락, 선착순 재고 |
| 크고 거의 안 바뀌며 매 요청 읽는다 | 로컬 | 좌석 배치, 코드표, 설정 |
| 만드는 비용이 매우 커서 전체에서 한 번만 만들어야 한다 | Redis(또는 둘 다) | 무거운 집계 결과 |

좌석 배치는 세 번째에 해당한다. 서버가 여러 대일 때 배치가 바뀌면(좌석 생성·삭제, 추첨 설정으로 등급이 바뀜) 모든 대의 로컬 캐시를 비워야 한다. 이때는 값을 Redis에 두지 말고, Redis를 **알림 통로**로만 쓰는 방식이 맞다.

```
배치 변경 → Redis Pub/Sub로 "회차 572 배치 바뀜" 발행
         → 각 서버가 받아 자기 로컬 캐시에서 572를 지움 → 다음 요청이 DB에서 새로 읽음
```

이 방식은 요청마다 옮기는 일이 없고, 무효화는 한 곳에서 시작된다. 로컬과 Redis의 장점만 쓰는 구성이다.

측정하지 않은 개선 방법도 있다. 압축 형식(열 단위 배열, 이진 형식)은 전송량과 역직렬화 비용을 줄인다. Redis 연결 풀은 공유 연결 하나의 줄 서기를 줄인다. 다만 둘 다 "요청마다 옮기고 다시 만드는 일" 자체는 없애지 못한다. 근거가 없으니 수치로 말하지 않는다.

## 12. 한계

- 조건마다 1회씩 쟀다. 세 조건의 방향은 같지만 수치의 오차 범위는 모른다.
- 노트북의 Docker에서 쟀다. 절대 수치는 배포 서버와 다르다.
- Redis 방식은 JSON 한 덩어리로만 구현했다. 압축 형식이나 연결 풀을 쓴 Redis는 재지 않았다.
- 직접 호출 조건의 로컬 1,280명 단계는 부하 생성기의 메모리 상한 때문에 재지 못했다.

## 면접 포인트

- **"캐시를 Redis에 두지 않고 로컬에 둔 이유는?"** → 좌석 배치는 1.3MB로 크고 판매 중에 안 바뀌며 매 요청 읽는다. Redis에 두면 요청마다 그만큼을 옮기고 15,000개 객체로 역직렬화해야 한다. 같은 조건에서 재 보니 한 건당 CPU가 약 4.5배, p95가 약 5배가 됐다. 스트레스 한계는 640명에서 160명으로 내려갔다.
- **"Redis가 느렸던 것인가?"** → 아니다. Redis CPU는 평균 0.16코어 아래였다. 역직렬화로 할당이 7배가 되며 GC가 약 17배 잦아졌다. GC로 멈춘 사이 공유 연결에 줄 선 명령이 시한 100ms를 넘겨 500이 됐다.
- **"서버가 여러 대면 로컬 캐시 무효화는 어떻게 하나?"** → 값은 로컬에 두고, 변경 알림만 Redis Pub/Sub로 보내 각 서버가 자기 캐시를 비우게 한다.
- **"성능 지표를 볼 때 주의할 점은?"** → 앞 단계가 실패하면 뒤 단계 지표가 좋아 보인다. 이 측정에서 Redis 쪽 선점 p95가 166ms로 좋아 보였지만, 선점까지 온 요청이 31% 적었다. 같은 양의 일을 처리했는지부터 본다.
