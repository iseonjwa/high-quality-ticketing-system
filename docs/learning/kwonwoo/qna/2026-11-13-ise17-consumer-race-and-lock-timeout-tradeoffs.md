# ISE-17 접수형 소비자에서 30초 시한과 겹칠 때, 좌석 잠금을 못 얻었을 때 어떻게 할까

## 질문
1. ISE-17 시작 전에 정할 두 가지(소비자와 30초 시한 스케줄러가 겹칠 때, 소비자가 좌석 잠금을 못 얻었을 때)의 추천안을 처음 보는 사람도 이해할 수 있게 트레이드오프 관점에서 정리해 달라.
2. (같은 날 이어서) 추천안과 대안의 성능 지표 예상치를 함께 놓고 종합적으로 다시 정리해 달라. 선점은 오픈 시점에 대기열을 지나온 트래픽이 몰리는 지점이라 성능도 고려해야 한다.

## 1. 배경
### 1-1. 접수형 선점의 흐름
접수형 선점(`seat-hold.mode=async`)은 요청을 두 단계로 나눈다.

```
사용자 ─POST─▶ 접수(ISE-16) ─▶ seat_hold_requests(REQUESTED) + Outbox 행 ─▶ 202
                                     │
              Outbox 릴레이 ─▶ Kafka seat-hold.request ─▶ 소비자(ISE-17) ─▶ HELD / REJECTED(사유)
                                                            ▲
사용자 ─GET 1초마다─▶ 결과 조회                30초 시한 스케줄러 ─▶ REJECTED(TIMEOUT)
```

- **접수:** 좌석을 잠그지 않는다. 이미 잡힌 좌석이면 그 자리에서 409를 준다(ADR 0057).
- **소비자:** 동기형과 같은 순서로 좌석을 잡는다. 매수 행(`user_schedule_quotas`) `FOR UPDATE` → 좌석 행을 ID 오름차순으로 `FOR UPDATE`하며 `AVAILABLE→HELD` → 예매 저장 → 요청 행 `HELD`. 잠금 대기 시한(`lock_timeout`)은 500ms다.
- **30초 시한 스케줄러:** 만든 지 30초 넘게 `REQUESTED`인 행을 `REJECTED(TIMEOUT)`으로 닫는다.
- 모든 상태 변경은 `UPDATE ... WHERE status = 'REQUESTED'`라 이미 닫힌 요청은 0행으로 끝난다.

### 1-2. 성능 추정에 쓰는 숫자
| 항목 | 값 | 출처 |
|---|---|---|
| 대기열 입장 속도 | 설정 초당 50명, 측정 목표 초당 100명 | `config-repo/reservation-service.yml`, `k6-seathold-bottleneck-plan.md` 1절 |
| 사용자당 선점 요청 | 약 2.4건(K1-H 30,001명 / 72,208건) | 같은 문서 5-4절 |
| 동기형 선점 트랜잭션 | p95 7~11ms(F 단계, 로컬), K1-H 초당 800명 p95 11ms | 같은 문서 5-5절 |
| 동기형 409(이미 잡힌 좌석) | p95 16ms, 201·409 중 87% | 같은 문서 5-4절 |
| DB 커넥션 풀 | 5개(현재 설정) | `config-repo/reservation-service.yml` |
| Outbox 릴레이 | 같은 키의 PENDING은 한 건씩. 키가 20개 미만으로 몰리면 키당 초당 약 2건(코드로 계산, 미측정) | `2026-11-12-ise16-remaining-decisions-tradeoffs.md` |
| `seat-hold.request` 파티션 | **선언이 없다.** 자동 생성되면 브로커 기본값(1개)이다. 소비자 스레드도 1개가 된다 | `NewTopic` 선언은 payment-service에만 있다 |
| 인기 구역 쏠림 | 요청 70%가 앞쪽 10% 좌석 | K1 시나리오 가정 |

모든 숫자는 로컬 측정이거나 코드로 계산한 추정이다. 배포 서버 값이 아니다.

### 1-3. 오픈 피크에서 생기는 일(추정)
결정을 비교하기 전에, 오픈 직후 접수형 줄이 어떻게 움직이는지 먼저 본다. 두 결정의 성능 차이는 이 상황에서 갈린다.

- 입장 초당 100명, 그중 70%가 인기 구역 몇 개에 몰린다. 접수 단계 409가 걸러도, 소비자가 아직 처리하지 않은 좌석은 `AVAILABLE`로 보여 같은 좌석을 노린 요청이 줄에 함께 들어간다.
- 인기 구역 키 하나에 초당 20건이 들어오는데 릴레이가 키당 초당 2건만 보내면, 줄이 초당 18건씩 길어진다. 30초 시한 안에 처리되는 것은 앞쪽 약 60건(2건 × 30초)뿐이다. **뒤의 요청은 대부분 소비자에 닿기 전에 시한이 지난다.**
- 릴레이 제약을 풀어도 파티션이 1개면 소비자 한 스레드가 모든 구역을 처리한다. 트랜잭션 8ms 기준 초당 약 125건이 상한이고, 입장 초당 100명 × 2.4건에서 접수 409를 뺀 양과 비슷하거나 넘는다.

정리하면, 오픈 피크에서는 **"시한이 지난 메시지가 많이 도착하는 상황"과 "소비자 한 줄이 처리량 상한인 상황"이 실제로 일어날 수 있다.** 두 결정은 이 두 상황에서 차이가 난다.

## 2. 결정 1: 소비자와 30초 시한 스케줄러가 같은 요청을 동시에 만질 때

### 2-1. 문제
요청이 29.9초에 소비자에게 도착했다.

```
t=29.9s  소비자: 요청 확인 → 매수·좌석 잠금 → 좌석 HELD, 예매 저장 ...
t=30.0s  스케줄러: UPDATE ... SET REJECTED(TIMEOUT) WHERE status='REQUESTED' AND 30초 지남 → 1행
t=30.1s  소비자: markHeld(WHERE status='REQUESTED') → 0행
```

0행을 무시하고 커밋하면 좌석·예매는 잡혔는데 요청은 `TIMEOUT`인 상태가 남는다. 사용자는 실패로 알고 다른 좌석을 고르는데, 좌석과 매수 한도는 결제 시한까지 묶인다.

### 2-2. 선택지
- **A. 결과만 보고 되돌리기:** 끝에서 `markHeld`가 0행이면 트랜잭션 전체를 롤백하고, 새 트랜잭션에 `processed_event`만 남긴다.
- **B. 시작할 때 요청 행을 잠그고 시한 확인(추천):** 첫 쿼리를 `SELECT created_at ... WHERE request_id = ? AND status = 'REQUESTED' FOR UPDATE`로 하고, 접수 뒤 30초가 지났는지 앱 시계로 본다. 아니면 바로 건너뛴다. 스케줄러는 `FOR UPDATE SKIP LOCKED`로 고른 행만 닫는다.
- **C. 시작할 때 시한만 확인(잠금 없음):** 첫 조회에서 30초가 지났으면 건너뛴다. 확인과 갱신 사이 경합이 남아 A의 롤백 처리도 같이 해야 한다.

### 2-3. 성능 예상치
메시지 하나 기준이다. "제때 온 메시지"는 30초 안에 소비자에 닿은 것, "늦은 메시지"는 30초가 지난 뒤 닿은 것이다.

| 지표 | A | B | C |
|---|---|---|---|
| 제때 온 메시지의 트랜잭션 시간 | 동기형과 같음(약 8ms, p95 11ms) | 같음. 재요청 확인 조회(`findById`)를 잠금 조회로 바꾸는 것이라 쿼리 수가 같다. 요청 행은 소비자와 스케줄러만 만져 잠금 대기가 거의 없다 | 같음 |
| 늦은 메시지의 트랜잭션 시간 | 약 8ms. 매수·좌석 잠금, 예매·좌석·이력 INSERT를 다 하고 롤백 | **약 1ms.** 기본키 조회 한 번 | 약 1ms. 경계 몇 ms 안의 메시지만 A처럼 |
| 늦은 메시지가 쥐는 좌석 잠금 | 수 ms 동안 인기 좌석 행을 잠근다. 다른 키 줄(섞인 구역 요청)과 만료 작업이 그만큼 기다린다 | 없음 | 거의 없음 |
| 늦은 메시지 1,000건이 쓰는 커넥션 시간 | 약 8초 | 약 1초 | 약 1초 |
| 소비자 한 줄 처리량(파티션 1개, 늦은 메시지 비율 50% 가정) | 초당 약 125건 | 초당 약 220건(8ms·1ms 평균 4.5ms) | B와 비슷 |
| 스케줄러가 기다리는 시간 | 소비자가 쥔 행에 걸리면 그 트랜잭션이 끝날 때까지(수 ms) | 0(`SKIP LOCKED`). 건너뛴 행은 다음 주기에 닫힌다 | A와 같음 |
| 롤백이 남기는 DB 부산물 | 늦은 메시지마다 예매·좌석 행 INSERT 뒤 롤백(죽은 튜플, WAL) | 없음 | 거의 없음 |

- 풀이 5개라 커넥션 시간은 오픈 피크에서 가장 귀한 자원이다. 접수 POST, 결과 조회 GET, 좌석 조회, 만료 스케줄러가 같은 풀을 나눠 쓴다. A는 늦은 메시지가 많을수록 이 자원을 헛되이 쓴다.
- 1-3절대로 릴레이가 키당 초당 2건에 묶이면, 소비자 처리량 차이는 바로 드러나지 않는다(소비자가 릴레이를 기다린다). 차이는 커넥션 시간과 좌석 잠금으로 나타난다. 릴레이 제약을 풀거나 파티션을 늘리면 소비자 처리량 차이로도 나타난다.

### 2-4. 종합
| 관점 | A | B | C |
|---|---|---|---|
| 정확성(묶인 좌석이 남지 않음) | 맞음 | 맞음 | A를 같이 해야 맞음 |
| 오픈 피크 성능 | 늦은 메시지가 많을수록 나빠짐 | 늦은 메시지가 늘어도 비용이 거의 그대로 | B에 가까움 |
| 결과 경계 | 끝나 봐야 앎 | "처리 시작이 30초 안이면 끝까지 처리" 한 줄 | 경계 근처에서 A |
| 구현 복잡도 | 낮음 | 중간(잠금 조회, 스케줄러 `SKIP LOCKED`) | 중간(두 경로를 다 둠) |
| 사용자에게 보이는 것 | 29.9초에 시작한 처리가 결국 TIMEOUT일 수 있음 | 30초를 조금 넘겨 `HELD`가 될 수 있음 | A와 같음 |

**추천은 B다.**
- 정확성은 A와 같고, 오픈 피크에 늘어나는 늦은 메시지를 8ms가 아니라 1ms에 흘려보낸다.
- 30초 비교는 앱 시계로 한다. 처음에는 DB `now()`를 권했으나 구현하며 바로잡았다. `created_at`은 DB가 아니라 앱 시계(`commonAuditingClock`)로 쓴 값이라, DB `now()`와 비교하면 앱과 DB의 시계 차이(이미 1초쯤 겪었다, `2026-11-09-host-clock-drift-test-failures.md`)만큼 시한이 어긋난다. 쓴 시계와 같은 시계로 비교해야 한다. 시한 정리 작업도 같은 앱에서 같은 시계를 쓴다.
- 감수하는 것: 30초를 수 ms 넘겨 `HELD`가 커밋될 수 있다. 시한의 뜻을 "결과를 정하기 시작하는 마감"으로 `contracts.md` 2-2에 적는다. 스케줄러 쿼리에 `SKIP LOCKED`가 더해진다.
- A를 고를 조건: 측정에서 늦은 메시지가 거의 없을 때. 그때는 단순함이 낫다.

## 3. 결정 2: 소비자가 잠금 대기 시한(500ms)을 넘겼을 때

### 3-1. 언제 일어나나
같은 구역 메시지는 같은 키라 한 줄로 처리되므로 소비자끼리는 대부분 부딪치지 않는다. 남는 경우는 다음과 같다.
- **섞인 구역 요청:** A·B 구역을 같이 고르면 `A` 키로 들어간다(ADR 0056). 이 요청의 B 구역 좌석은 `B` 키 줄과 동시에 잠길 수 있다. 파티션이 1개면 줄이 하나라 이 경우도 생기지 않는다.
- **소비자 밖 작업:** 선점 만료 스케줄러(5초마다 만료 좌석 해제), 예매 취소, 결제 확정, 추첨 배정.
- **같은 사용자의 다른 구역 요청:** 매수 행이 사용자·회차당 하나라 다른 줄의 같은 사용자 요청과 부딪칠 수 있다.

상대 트랜잭션은 보통 수십 ms 안에 끝난다. 500ms를 넘기는 것은 상대가 비정상적으로 오래 쥘 때라 드물다. 발생 비율은 측정 전이라 모른다. 아래는 "메시지 1%에서 일어난다"를 넉넉히 잡은 가정이다.

### 3-2. 선택지
- **A. 바로 `REJECTED(SEAT_ALREADY_HELD)`로 닫기(추천):** 동기형과 같이 잠금 시한 초과를 좌석 충돌로 본다.
- **B. 예외를 던져 Kafka 재시도에 맡기기:** 1·2·4초 간격 3회 재시도, 그래도 실패하면 DLQ → `REJECTED(PROCESSING_FAILED)`.
- **C. 소비자만 잠금 시한을 길게(예: 2초).**
- **D. 소비자만 잠금 시한을 짧게(예: 100ms)하고 A처럼 닫기.**

### 3-3. 성능 예상치
| 지표(한 번 일어날 때) | A(500ms 후 거절) | B(Kafka 재시도) | C(2초) | D(100ms 후 거절) |
|---|---|---|---|---|
| 그 줄(파티션)이 멈추는 시간 | 0.5초 | 최대 약 9초(시도 4번 × 0.5초 + 대기 7초) | 최대 2초 | 0.1초 |
| 커넥션을 쥐는 시간 | 0.5초 | 최대 2초(시도마다 0.5초) | 최대 2초 | 0.1초 |
| 멈추는 동안 처리 못 하는 메시지(8ms 기준) | 약 60건 | 약 1,100건 | 약 250건 | 약 12건 |
| 사용자 결과 | 빠른 거절. 상대가 풀던 좌석이면 놓침 | 다음 시도에서 잡을 수 있음. 끝내 실패하면 `PROCESSING_FAILED` | 놓치는 경우가 줄어듦 | 놓치는 경우가 A보다 늘어남 |

1% 가정에서 1초 동안 들어온 메시지 125건 중 1.25건이 걸리면 그 줄이 멈추는 시간의 합은 다음과 같다.
- A: 초당 약 0.6초 → **처리량이 약 40% 준다.**
- B: 초당 10초 이상 → 줄이 사실상 멈추고, 뒤 요청이 30초 시한에 걸리기 시작한다.
- C: 초당 약 2.5초 → 줄이 멈춘다.
- D: 초당 약 0.13초 → 처리량이 약 11% 준다.

이 계산은 1% 가정이 크게 좌우한다. 0.1%면 A는 약 6%, D는 약 1%만 준다(처리량 = 1 / (8ms + 비율 × 멈춤 시간)). 그래서 발생 비율을 재는 것이 먼저다.

### 3-4. 종합
| 관점 | A | B | C | D |
|---|---|---|---|---|
| 오픈 피크 처리량 | 드물면 영향 작음 | 한 번만 나도 줄이 멈춤 | 줄이 멈춤 | 가장 작음 |
| 커넥션(풀 5개) | 0.5초 | 2초 | 2초 | 0.1초 |
| 거짓 거절 | 드묾 | 가장 적음 | 적음 | A보다 많음 |
| 거절 사유의 정확성 | `SEAT_ALREADY_HELD`(동기형과 같음) | 끝내 실패하면 `PROCESSING_FAILED`라 오해 | 정확 | A와 같음 |
| 동기형과의 일관성 | 같음 | 다름 | 다름 | 시한만 다름 |
| 구현 | 동기형 코드 재사용 | 오류 처리기 설정 + 사유 매핑 | 설정 하나 | 설정 하나 + 문서 |

**추천은 A다. 측정에서 잠금 시한 초과가 자주 나면 D로 내린다.**
- 접수형을 쓰는 이유가 "줄을 세워 많이 처리한다"이다. B와 C는 드문 경합 하나로 줄 전체를 수 초씩 멈춘다. 오픈 피크에서 그 사이 들어온 요청 수백~천 건이 밀리고, 일부는 30초 시한에 걸린다. 한 건의 거짓 거절보다 손해가 크다.
- A는 동기형과 같은 값(500ms)과 같은 결과(409 `SEAT_ALREADY_HELD`)라 두 모드를 같은 기준으로 비교하고 설명할 수 있다.
- D가 더 빠르지만 근거 없이 시한을 바꾸면 동기형과 기준이 갈린다. 잠금 시한 초과 횟수를 따로 세어(로그 또는 지표) 많을 때 D로 내린다.
- 감수하는 것: 드문 거짓 거절. 매수 행에서 시한이 넘은 경우(같은 사용자의 동시 요청)도 `SEAT_ALREADY_HELD`가 된다. 동기형도 지금 그렇다. 사유를 새로 만들면 `reasonCode` 값이 늘어 프론트가 처리할 것이 생긴다.

## 4. 결정보다 성능에 더 큰 것: ISE-17에서 함께 다룰 두 가지
1-3절에서 보듯, 오픈 피크의 처리량은 위 두 결정보다 아래 두 가지가 더 크게 정한다.

| 항목 | 지금 | 영향 | 제안 |
|---|---|---|---|
| `seat-hold.request` 파티션·소비자 동시성 | 선언 없음 → 자동 생성 시 1개 | 모든 구역이 소비자 한 스레드에 줄을 선다. 트랜잭션 8ms 기준 초당 약 125건이 전체 상한 | 결제처럼 `NewTopic`으로 파티션 수를 선언하고 소비자 동시성을 같게 둔다. 동시성 하나가 커넥션 하나를 쓰므로 풀 5개 안에서 정한다(예: 3) |
| Outbox 릴레이의 키당 한 건 | 키당 초당 약 2건(추정) | 인기 구역은 30초에 약 60건만 처리되고 나머지는 TIMEOUT | ADR 0057 결정 5대로 접수→처리 지연과 구역별 PENDING을 먼저 재고, 나쁘면 접수형 토픽만 키별 순서를 푸는 contract 이슈를 올린다 |

두 결정(B, A)은 이 병목이 풀린 뒤에도 유지되는 선택이다. 병목이 풀릴수록 늦은 메시지 비용(결정 1)과 줄 멈춤(결정 2)의 차이가 처리량에 직접 드러난다.

## 5. 정리
| 결정 | 추천 | 오픈 피크에서 얻는 것 | 감수하는 것 | 다시 볼 조건 |
|---|---|---|---|---|
| 1. 시한과 겹침 | 요청 행 `FOR UPDATE` + 앱 시계로 30초 확인, 스케줄러 `SKIP LOCKED` | 늦은 메시지 비용 8ms → 1ms, 좌석 잠금·커넥션 낭비 없음 | 30초를 수 ms 넘긴 `HELD`, 쿼리 복잡도 | 늦은 메시지가 거의 없으면 A도 됨 |
| 2. 잠금 시한 초과 | 500ms 뒤 `REJECTED(SEAT_ALREADY_HELD)` | 줄이 0.5초 넘게 멈추지 않음, 동기형과 같은 기준 | 드문 거짓 거절 | 초과가 잦으면 D(100ms) |

측정에서 볼 것은 다음과 같다. 늦은 메시지 비율, 잠금 시한 초과 횟수, 접수→처리 지연(p95), 구역별 Outbox PENDING, 소비자 처리량. ISE-277 대시보드의 결과 폴링 패널과 `accepted` 수도 함께 본다.
