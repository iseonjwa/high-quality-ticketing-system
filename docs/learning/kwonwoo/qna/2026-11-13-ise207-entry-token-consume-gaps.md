# ISE-207(입장 토큰을 선점 성공 때 소모) 초안대로 구현하면 어디서 어긋나나

## 질문
대기열 담당이 ISE-207에 적힌 방식대로 하면 안 된다고 했다. 왜 그런지 원인을 파악해 달라.

## 짧은 답
- (11-13 추가) 담당자가 밝힌 실제 이유는 6절이다. `AFTER_COMMIT` 리스너는 DB 커넥션을 반납하기 전에 실행돼, Redis로 `issued`를 지우는 동안 커넥션을 쥔다. 풀이 5개라 Redis가 느리면 선점 전체가 커넥션 대기로 막힌다. 그래서 트랜잭션이 끝난 뒤 메서드로 부르기로 했다. 아래 1~5절은 담당자 답을 받기 전에 코드로 찾은 어긋남이다.
- 대기열 담당의 그 발언은 Linear ISE-207 댓글, GitHub 이슈 #385, PR #524·#558·#574 어디에도 없다. 글로 남은 대기열 담당 의견(11-09 댓글)은 `issued` 정리에 찬성한다. 그래서 발언의 정확한 근거는 확인하지 못했고, 아래는 코드와 ADR 0053 초안을 맞대어 찾은 어긋남이다.
- 가장 유력한 것은 **거절할 때 `issued`를 다시 지우는 규칙에서 조건이 빠진 것**이다. 대기열 담당은 "발급 시각이 같은 경우에만 다시 정리"를 제안했는데, ADR 0053 결정 3은 조건 없이 "거절할 때 한 번 더 지운다"로 적었다. 조건이 없으면 옛 토큰을 가진 탭 하나가 새로 받은 정상 입장을 지운다.
- 그 밖에 초안의 전제 두 가지가 지금 코드와 맞지 않는다. 하나는 거절 경로가 롤백되므로 `AFTER_COMMIT` 리스너가 불리지 않는다는 점이다. 다른 하나는 ISE-16 접수형이 `REQUESTED`·`REJECTED` 행을 남겨 "성공한 선점만 행을 남긴다"는 전제가 깨졌다는 점이다.

## 자세히

### 1. 현재 대기열 코드에서 알아야 할 사실
- `issued`는 회차별 Sorted Set이다. 멤버는 사용자 ID, 점수는 발급 시각(ms)이다.
- 입장 토큰의 `jti`는 무작위가 아니다. `JwtEntryTokenIssuer`가 `sha256("entry:" + 회차 + ":" + 사용자 + ":" + 발급 시각ms)`의 앞 16바이트로 만든다. 같은 발급 시각이면 같은 토큰과 같은 `jti`가 나온다.
- `enter.lua`·`issue-token.lua`는 `issued`에 유효한 점수가 있으면 그 점수로 같은 토큰을 다시 준다. 그래서 소모 뒤 `issued`를 지우지 않으면 이미 쓴 토큰을 10분 동안 계속 받는다. 대기열 담당이 정리를 "사실상 필수"라고 한 이유다.

### 2. 어긋남 1: 거절 때 다시 지우기에 조건이 빠졌다 (유력)
대기열 담당 의견(11-09): "같은 토큰으로 거절할 때 **발급 시각이 같은 경우에만** 다시 정리한다."
ADR 0053 결정 3: "`ZREM`이 실패하면 로그를 남기고, 거절할 때 한 번 더 지운다." 조건이 없다.

조건이 없을 때 생기는 일:
1. 사용자가 토큰 A(발급 t1)로 선점에 성공한다. 커밋 뒤 `issued`에서 지워진다.
2. 사용자가 다시 줄을 서서 토큰 B(발급 t2)를 받는다. `issued` 점수는 t2다.
3. 열어 둔 다른 탭이나 늦게 도착한 재시도가 토큰 A로 새 선점을 보낸다. 403 `ENTRY_TOKEN_USED`로 거절된다.
4. 거절 경로가 조건 없이 `ZREM`하면 t2 기록이 지워진다.
5. 프론트는 `ENTRY_TOKEN_USED`를 `ENTRY_TOKEN_INVALID`처럼 처리해 그 회차의 저장 토큰(이제 B)을 지우고 대기열로 보낸다. 대기열은 `issued`가 없으니 새 번호로 맨 뒤에 세운다.

정상적으로 받은 입장이 사라지고, 사용자는 다시 처음부터 기다린다. 조건을 지키려면 대기열 쪽이 "지금 `issued` 점수로 만든 `jti`가 거절된 `jti`와 같을 때만" 지워야 한다. `jti`가 결정적이라 대기열 쪽에서 다시 계산해 비교할 수 있다. Lua 하나로 `ZSCORE`와 `ZREM`을 묶으면 원자적이다.

### 3. 어긋남 2: 거절 경로에서는 `AFTER_COMMIT`이 불리지 않는다
- 대기열 담당이 제안한 구조는 "선점은 `SeatHeldEvent`만 발행하고, 대기열이 `@TransactionalEventListener(AFTER_COMMIT)`로 받는다. 선점 코드가 대기열 코드를 직접 부르지 않는다"이다.
- 성공 경로는 이 구조로 된다.
- 거절 경로(이미 쓴 `jti`)는 예외를 던져 트랜잭션이 롤백된다. `AFTER_COMMIT` 리스너는 불리지 않는다. 그래서 "거절할 때 한 번 더 지운다"를 같은 구조로는 구현할 수 없다. 선점 코드가 대기열을 직접 부르거나, 별도 이벤트(`AFTER_ROLLBACK` 또는 트랜잭션 밖 발행)를 새로 정해야 한다. 초안은 이 부분을 정하지 않았다.

### 4. 어긋남 3: 접수형(ISE-16) 뒤로 "성공한 선점만 행을 남긴다"가 깨졌다
- ADR 0053 결정 2는 `seat_hold_requests.entry_token_jti`에 고유 인덱스를 두면서 "동기형 선점은 성공한 선점만 행을 남긴다"를 전제로 한다.
- ISE-16(ADR 0057) 뒤로 접수형은 접수 때 `REQUESTED` 행을 쓰고, 소비자가 실패하면 `REJECTED`로 바꾼다. 테이블 제약도 `REQUESTED`·`HELD`·`REJECTED` 셋이다.
- 접수 때 `jti`를 저장하고 고유 인덱스를 전체에 걸면, 소비자가 거절한 요청(`REJECTED`)도 토큰을 쥔다. 결정 1의 "실패한 선점은 소모하지 않는다"와 어긋나고, 사용자가 다른 좌석으로 다시 요청하면 `ENTRY_TOKEN_USED`를 받는다.
- 고칠 방향: `status <> 'REJECTED'`인 행에만 거는 부분 고유 인덱스로 바꾼다. 처리 중(`REQUESTED`)인 동안은 같은 토큰의 두 번째 요청을 막고, 거절되면 토큰을 돌려준다. `issued` 정리는 접수 커밋이 아니라 소비자가 `HELD`로 커밋할 때 한다.
- 이 부분은 좌석 선점 담당 몫이다.

### 5. 함께 볼 비용: 동기 리스너가 선점 응답을 대기열 Redis에 묶는다
- 대기열 담당은 리스너를 동기로 두자고 했다. 선점 응답이 나갈 때 정리가 끝나 있게 하려는 것이다.
- 대신 대기열 Redis가 느리면 선점 응답도 그만큼 늦는다. PR #574(ISE-59)로 Redis 명령 시한이 200ms가 됐고, `queue-redis` 차단기가 생겼다. 리스너의 `ZREM`도 이 차단기 안에서 부르고 예외를 잡으면, 최악은 선점 한 건에 200ms가 더해지는 정도다. 차단기가 열리면 바로 실패하고 로그만 남는다.
- 이것은 막는 이유라기보다 측정에서 확인할 비용이다.

### 6. 담당자 답변으로 확인한 실제 이유: 리스너가 DB 커넥션을 쥔 채 Redis를 부른다
대기열 담당의 요약(11-13): 동기 이벤트 리스너는 커밋 뒤지만 커넥션을 반납하기 전에 실행돼 `issued`를 지울 때까지 커넥션을 쥔다. 메서드로 부르면 트랜잭션이 끝나 커넥션을 반납한 뒤 지운다. 그래서 메서드 방식을 쓴다.

5절에서 "응답이 늦어지는 비용"으로만 본 것을 담당자는 "커넥션을 쥐는 비용"으로 봤다. 이쪽이 맞고 더 중요하다.

- Spring의 커밋 순서(`AbstractPlatformTransactionManager.processCommit`): `doCommit` → `triggerAfterCommit`(여기서 `AFTER_COMMIT` 리스너 실행) → `triggerAfterCompletion` → `finally`의 `cleanupAfterCompletion`(여기서 EntityManager를 닫고 커넥션을 풀에 돌려준다). DB 커밋은 끝났지만 커넥션은 아직 풀로 돌아가지 않았다.
- reservation-service의 Hikari 풀은 5개다(`config-repo/reservation-service.yml`). 선점 한 건이 Redis 시한(200ms)만큼 커넥션을 더 쥐면, 대기열 Redis가 느린 순간 5개가 금방 묶인다. 그러면 좌석 조회·선점 전체가 커넥션 대기 시한(1초, ISE-196)에 걸려 실패한다. Redis 장애가 DB 풀 고갈로 번지는 셈이다.
- `open-in-view: false`(`config-repo/application.yml`)라서 트랜잭션이 끝나면 커넥션이 실제로 돌아간다. 그래서 메서드 방식이면 Redis 호출 동안 커넥션을 쥐지 않는다.

메서드 방식을 쓸 때 지켜야 할 것:
- 트랜잭션 **밖**에서 불러야 한다. `@Transactional`인 `SyncSeatHoldService.hold` 안에서 부르면 리스너보다 나쁘다(커밋 전이라 롤백돼도 지워진다). 트랜잭션 메서드가 끝난 뒤 컨트롤러나 트랜잭션 없는 바깥 메서드에서 부른다. 같은 클래스 안의 자기 호출은 프록시를 타지 않으니 주의한다.
- 예외를 잡아 로그만 남긴다. 선점은 이미 커밋됐으므로 정리 실패로 500을 주면 안 된다.
- 선점 코드가 대기열 코드를 직접 부른다. 리스너로 피하려던 의존이 생기므로, 선점 쪽은 대기열이 내놓은 작은 인터페이스(예: `releaseIssued(scheduleId, userId, jti)`)만 알게 한다.
- 거절 경로에서 다시 지울 때도 같은 메서드를 쓸 수 있어 3절의 문제는 풀린다. 2절의 "같은 발급일 때만 지운다" 조건은 여전히 필요하다.
- 접수형은 HTTP 요청이 아니라 소비자가 `HELD`를 커밋한 뒤 부른다. 소비자 쪽도 트랜잭션 밖에서 부르는 같은 규칙을 따른다.

### 7. 대기열 담당의 변경안(ISE-207 11-13 댓글) 검토
변경안: 선점 쪽이 트랜잭션 밖에서 `QueueService.discardEntryToken(scheduleId, userId, entryTokenJti)`를 부른다. `issued`의 토큰이 넘긴 `jti`와 같을 때만 지우고, 아니면 아무 일도 하지 않는다. 성공 뒤와 `ENTRY_TOKEN_USED` 거절 뒤 모두 부르고, `QueueStorageUnavailableException`은 잡아 로그만 남긴다.

해결된 것: 2절(조건 없는 재정리), 3절(거절 경로), 6절(커넥션 점유)이 모두 풀린다.

남은 점:
1. **예외 타입이 `queue.domain`에 있다.** "선점 쪽은 `QueueService`만 import한다"와 맞지 않는다. 메서드가 저장소 예외를 안에서 잡아 로그를 남기고 끝내면(대기열 쪽 책임), 선점 쪽은 대기열 내부 예외를 몰라도 된다. 선점 쪽은 그래도 `RuntimeException`을 한 번 더 감싸 응답을 지킨다.
2. **`jti` 비교가 원자적인지.** `jti`는 SHA-256이라 Redis Lua(`redis.sha1hex`만 있음)에서 다시 계산할 수 없다. Java에서 `ZSCORE` → `jti` 계산 → `ZREM`을 따로 부르면 그 사이 기록이 바뀔 수 있다. 창은 매우 좁다(유효한 기록이 있는 동안은 새 발급이 생기지 않는다). 그래도 마지막 단계를 "점수가 읽은 값과 같을 때만 지운다" Lua로 하면 비용 없이 닫힌다.
3. **접수형(ISE-16)은 변경안에 없다(선점 담당 몫).** 접수형의 성공은 HTTP 요청이 아니라 소비자에서 난다.
   - `SeatHoldRequested` 페이로드에 `entryTokenJti`를 더해야 소비자가 부를 수 있다. 생산자와 소비자가 모두 reservation-service라 바깥 계약은 아니지만 이벤트 형식 변경이라 `contracts.md`에 적는다.
   - 소비자는 `HELD` 커밋이 끝난 뒤 트랜잭션 밖에서 부른다.
   - 고유 인덱스는 `status <> 'REJECTED'`인 행에만 건다(4절).
4. **호출 위치는 이미 마련돼 있다.** `SyncSeatHoldService.hold`는 `@Transactional`이 아니고 안에서 `TransactionTemplate`으로 트랜잭션을 연다. `writeTransaction.execute(...)`가 돌아온 뒤가 트랜잭션 밖이다. 자기 호출이나 프록시 문제가 없다. 거절은 같은 메서드에서 `BusinessException(ENTRY_TOKEN_USED)`를 잡아 부르고 다시 던진다.
5. **`claimRequest`의 고유 위반을 나눠야 한다.** 지금은 `seat_hold_requests` 저장의 `DataIntegrityViolationException`을 모두 같은 멱등키 경합(`ConcurrentSameKeyException`)으로 본다. `jti`를 같은 행에 쓰면 `jti` 고유 위반도 여기로 들어와 재조회 경로로 잘못 간다. 제약 이름으로 나눈다(ADR 0053 결정 2에 이미 적혀 있다).
6. **지연은 남는다.** 커넥션은 쥐지 않지만, Redis가 느리면 선점 응답이 최대 200ms 늦고 Tomcat 스레드도 그만큼 쓴다. 차단기가 열리면 바로 끝난다. 측정에서 확인할 값이다.

### 8. 덧붙인 질문: 그럼 좌석 선점의 Kafka를 없애야 하나
아니다. 대기열 담당이 바꾼 것은 "`issued`를 지우는 함수를 어디서 어떻게 부르나"(리스너 → 트랜잭션 밖 메서드)뿐이다. 선점을 처리하는 방식(동기형 DB 처리, 접수형 Outbox → Kafka → 소비자)과는 상관없다.

| | 동기형 | 접수형(Kafka) |
|---|---|---|
| 선점이 성공하는 곳 | HTTP 요청 안의 `writeTransaction` | Kafka 소비자의 트랜잭션 |
| `discardEntryToken`을 부르는 곳 | `hold`에서 트랜잭션이 끝난 직후 | 소비자에서 `HELD` 커밋이 끝난 직후 |
| 필요한 값 | 헤더 `X-Entry-Token-Id` | 메시지에 `entryTokenJti`를 실어 소비자까지 전달 |

접수형에 더할 것은 세 가지다. 메시지 필드 하나, 소비자의 호출 한 줄, `REJECTED`를 뺀 부분 고유 인덱스. 메서드 방식은 오히려 접수형에 더 맞는다. 리스너 방식이었다면 소비자 트랜잭션의 커밋 후처리에서 커넥션을 쥔 채 돌았을 것이다.

### 9. 덧붙인 질문: ISE-17(소비자)보다 ISE-207을 먼저 하면 무엇이 달라지나
전제: dev에는 아직 `SeatHoldRequested` 소비자가 없다. `AsyncSeatHoldService`가 접수와 Outbox까지만 하고, 실제 선점은 ISE-17이 만든다.

| | ISE-207 먼저 | ISE-17 먼저 |
|---|---|---|
| 이벤트 형식 | 소비자가 없을 때 `entryTokenJti`를 더한다. 읽는 쪽이 없어 호환을 신경 쓸 필요가 없다 | 소비자가 생긴 뒤 필드를 더한다. 필드 없이 이미 쌓인 메시지를 소비자가 받아 줘야 한다 |

## 면접 포인트
- 결정적 ID(`jti` = 해시(회차, 사용자, 발급 시각))는 "같은 발급"을 다시 계산해 확인할 수 있게 한다. 상태를 지울 때 "내가 지우려는 것이 지금 있는 것과 같은 세대인가"를 비교하지 않으면, 늦게 온 요청이 새 세대를 지운다. 낙관적 잠금의 버전 비교와 같은 원리다.
- 트랜잭션 이벤트는 커밋 단계에 묶인다. 거절(롤백) 경로에서 후처리가 필요하면 `AFTER_COMMIT`으로는 안 되고 따로 설계해야 한다.
