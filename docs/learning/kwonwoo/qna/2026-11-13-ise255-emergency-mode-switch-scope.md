# ISE-255 접수형 장애 때 동기형 비상 전환을 범위에 둘지, 무엇을 보고 정하나

## 질문
ISE-255(접수형 장애 때 동기형으로 급히 되돌리는 비상 전환을 범위에 둘지)를 자세히 설명해 달라.

## 짧은 답
- 정할 것은 "오픈 피크 중 접수형(Outbox·Kafka·소비자)이 고장 나면, 서비스를 멈추지 않고 동기형으로 되돌릴 수단을 만들 것인가"다.
- 지금은 모드를 기동할 때 한 번 읽는다(ADR 0057 결정 2). 바꾸려면 reservation-service를 재시작해야 하고, 한 대뿐이라 30초~1분 동안 대기열·좌석·선점·예매 API가 모두 멈춘다(추정).
- 그런데 배포 기본값이 `seat-hold.mode: sync`다(`config-repo/reservation-service.yml`). 접수형은 측정할 때만 켠다. 평소 사용자가 접수형을 쓰지 않으니, 접수형이 고장 날 때 되돌릴 대상도 없다.
- 그래서 실제 질문은 "발표·시연·운영에서 접수형을 기본으로 켤 계획이 있나"다. 없으면 범위 밖이 자연스럽고, 있으면 범위 안으로 두고 재시작 없는 전환을 만들어야 한다.

## 자세히

### 1. 지금 구조
| 항목 | 현재 |
|---|---|
| 모드 결정 | 기동 때 `seat-hold.mode`를 한 번 읽는다. `@RefreshScope`를 쓰지 않는다(ADR 0057 결정 2) |
| 기본값 | `sync`. 접수형은 측정 모드에서 덮어쓰기 파일(`SEATHOLD_MODE=async`)로만 켠다 |
| 소비자 | 모드와 상관없이 항상 돈다 |
| 결과 조회 API | 모드와 상관없이 열려 있다(결정 3) |
| 재시작 비용 | 인스턴스 한 대(ADR 0047). 기동·Eureka 등록·Gateway 목록 갱신까지 30초~1분 전면 중단(추정, 실측 아님) |

### 2. "비상 전환"이 필요한 장면
접수형을 켜고 오픈했는데 Kafka 브로커가 죽거나, Outbox 릴레이가 밀리거나, 소비자가 예외로 멈춘다. 사용자는 202를 받고 폴링하지만 결과가 `REQUESTED`에서 움직이지 않는다. 이때 동기형으로 바꾸면 새 요청은 DB에서 바로 처리된다.

재시작으로 바꾸면 그 순간 전면 중단이 생긴다. 접수형 장애는 선점 한 기능의 장애인데, 고치려다 대기열 입장까지 멈추는 셈이다. 그래서 "재시작 방식으로는 비상 전환이 사실상 안 된다"가 출발점이다.

### 3. 선택지
**범위 밖 (어제 AI 추천)**
- 모드 전환은 측정 도구로만 쓴다. ADR 0057에 "비상 전환은 범위 밖, 운영 기본값은 sync"라고 한 줄 덧붙인다.
- 이익: 할 일이 문서 한 줄이다. ISE-17·18과 ISE-79 측정에 시간을 쓴다.
- 근거: SA에서 접수형의 목적은 동기형과의 비교 측정이다. 비상 전환은 요구사항에 없다. 기본값이 sync라 장애 장면 자체가 측정 중에만 생기고, 측정 중에는 사용자가 없다.
- 손실: 나중에 "접수형을 운영 기본으로 쓰자"고 정하면 이 결정을 다시 열어야 한다. 면접에서 "접수형이 죽으면 어떻게 하나"는 질문에 "운영은 동기형으로 둔다, 접수형은 측정으로 효과를 확인했다"로 답해야 한다.

**범위 안: 재시작 없는 전환**
- 방법 1. `@RefreshScope` + `/actuator/refresh`
  - 모드를 읽는 빈을 갱신 범위에 두고, config-repo 값을 바꾼 뒤 refresh를 부른다.
  - 공통 Actuator 노출(`config-repo/application.yml`)에 `refresh`를 더해야 한다. 모든 서비스에 영향이 가는 공유 설정이라 contract 이슈 대상이다(대전제 11). 관리 포트(9080)를 밖에 열지 않는지도 확인해야 한다.
  - refresh 순간 빈이 다시 만들어진다. 그 사이에 들어온 요청이 옛 빈과 새 빈 중 어느 쪽을 타는지 경계가 흐리다.
- 방법 2. 운영자용 전환 API
  - 모드를 `AtomicReference` 같은 값으로 들고, 관리자 인증된 내부 API로 바꾼다. 요청은 POST 처리 시작 때 한 번 모드를 읽는다.
  - 경계가 분명하다(요청 시작 때 읽은 값으로 끝까지 간다). 대신 새 운영 API, 인증, 테스트가 필요하다.
  - 한 대라 상태를 공유할 필요는 없지만, 재시작하면 config 값으로 돌아간다. 이 점을 운영 절차에 적어야 한다.
- 어느 방법이든 따라오는 일
  - 전환 직후 남은 `REQUESTED` 행은 소비자가 계속 처리하거나 30초 시한(ISE-17)이 닫는다. 같은 키 재요청은 ADR 0058의 202로 답한다. 그래서 ISE-17의 시한이 먼저 있어야 비상 전환이 안전하다.
  - 장애를 언제 판단하고 누가 전환하는지(지표, 알림, 담당) 운영 절차가 필요하다.
  - 전환이 실제로 되는지 측정(전환 중 실패율, 남은 요청이 닫히는 시간)을 한 번은 해야 발표에서 말할 수 있다.

### 4. 비교
| 기준 | 범위 밖 | 범위 안(방법 1) | 범위 안(방법 2) |
|---|---|---|---|
| 남은 작업 | ADR 한 줄 | 공통 설정 변경·contract 이슈·경계 처리·측정 | 운영 API·인증·테스트·측정 |
| 다른 담당 영향 | 없음 | 모든 서비스의 Actuator 노출 | 없음(reservation 안) |
| 전환 경계 | 해당 없음 | 흐림 | 분명 |
| 운영에서 접수형을 쓸 수 있나 | 쓰지 않는다고 정함 | 쓸 수 있음 | 쓸 수 있음 |
| ISE-17·18 일정 | 영향 없음 | 밀림 | 밀림 |

### 5. 결정 기준
1. 발표·시연·운영 기본값을 접수형으로 둘 계획이 있는가. 없으면 범위 밖이다.
2. 있다면 남은 일정에 방법 2를 넣을 여유가 있는가. 없으면 "운영은 sync"로 정하고 접수형은 측정 결과로만 보여 준다.
3. ISE-18 측정 결과 접수형이 동기형보다 확실히 낫다면 그때 이 결정을 다시 연다. 범위 밖 결정에 "재검토 조건: ISE-18에서 접수형을 운영 기본으로 쓰기로 할 때"를 적어 두면 된다.

## 이 프로젝트에서는
- 기본값: `config-repo/reservation-service.yml`의 `seat-hold.mode: sync`
- 결정: ADR 0057 결정 2와 검토한 대안(`@RefreshScope`), ADR 0058 후속 작업
- 근거 노트: [2026-11-12-mode-switch-replay-gap.md](2026-11-12-mode-switch-replay-gap.md) 7·8절

## 면접 포인트
- 설정을 실행 중에 바꾸는 기능은 공짜가 아니다. 바뀌는 순간 처리 중인 요청의 경계, 공유 설정 노출, 누가 언제 바꾸는지까지 함께 설계해야 한다.
- 대안 경로(fallback)를 둘지는 "그 경로가 실제로 쓰이는 장면이 있는가"로 정한다. 기본값이 이미 안전한 쪽이면 전환 장치는 범위 밖으로 두고 재검토 조건을 적는다.
