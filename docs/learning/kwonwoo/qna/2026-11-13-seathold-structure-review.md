# 좌석 선점 구조 자체에 문제는 없나, 구조에서 개선할 부분은 무엇인가

## 질문
잠금 대기를 50ms로 줄였고 다음 개선안(사전 거절, 409 실패 좌석 ID)은 다른 일이 먼저 끝나야 한다. 그렇다면 시니어 백엔드 개발자 시점에서 선점 구조 자체에는 문제가 없나. 구조에서 개선할 부분이 있나.

## 짧은 답
정합성 뼈대는 맞다. 좌석의 정본이 DB 한 곳이고, 마지막 판단을 조건부 UPDATE가 한다. 중복 판매를 막는 장치가 여러 겹이다. 이 부분은 바꿀 이유가 없다.

구조 문제는 비용 쪽에 셋 있다.
1. **질 요청이 이길 요청과 같은 비싼 길을 끝까지 간다.** 동기형은 좌석 상태를 이미 읽어 놓고 검사하지 않는다. 접수형은 같은 자리에서 검사한다.
2. **좌석 잠금을 쥔 채 INSERT를 여러 번 한다.** 잠금 구간에 왕복이 "4 + 좌석 수"번 있다.
3. **커넥션을 잡기 전에 들어오는 양을 막는 곳이 없다.**

1이 가장 작고, 담당 영역 안에서 끝나고, 계약을 바꾸지 않는다. 1 → 2 → 3 순서를 추천한다.

## 설명

### 지금 동기형 선점 한 건이 하는 일
`SyncSeatHoldService.holdInTransaction` 한 트랜잭션 안에서 이 순서로 돈다.

| 순서 | 문장 | 잠금 |
|---|---|---|
| 1 | 멱등키 조회 (`seat_hold_requests`) | 없음 |
| 2 | 회차 조회 | 없음 |
| 3 | 좌석 조회 (`findSeats`, 상태까지 읽는다) | 없음 |
| 4 | 멱등키 INSERT (`claimRequest`) | 멱등키 행 |
| 5 | `lock_timeout` 설정 | - |
| 6 | 매수 조건부 UPDATE | 사용자·회차 매수 행 |
| 7 | 좌석 조건부 UPDATE (`ORDER BY id FOR UPDATE`) | **좌석 행** |
| 8 | 예매 INSERT | |
| 9 | 예매 좌석 INSERT × 좌석 수 (ID가 IDENTITY라 한 건씩 나간다) | 부분 유니크 인덱스 |
| 10 | 이력 INSERT | |
| 11 | 멱등키 행 HELD로 UPDATE | |
| 12 | 커밋 | 여기서 모든 잠금이 풀린다 |

### 잘된 부분 (바꾸지 않는다)
- 좌석 정본이 DB 한 곳이다. 7의 `WHERE status = 'AVAILABLE'` 조건부 UPDATE가 마지막 판단이라, 앞에서 무엇을 캐시하든 중복 판매가 생기지 않는다.
- 좌석 ID 오름차순으로 잠가 교착이 없다. 멱등키를 좌석보다 먼저 써서 같은 키 연타가 자기 좌석에 409를 받지 않는다. 예매 좌석 부분 유니크 인덱스가 마지막 방어선이다.
- 모드(동기형·접수형)를 한 API에서 설정으로 고른다. 핫 좌석 경합을 구조로 없애는 길(접수형, 구역 키로 줄 세우기)이 이미 설계돼 있다.

### 구조 문제 1. 동기형은 이미 읽은 좌석 상태를 버린다
- **상황:** 3에서 좌석 엔티티를 상태까지 읽는다. 그런데 동기형은 개수만 보고 상태는 보지 않는다. 접수형(`AsyncSeatHoldService.requireAllHoldable`)은 같은 자리에서 `isHoldable`을 검사해 잡힌 좌석이 섞이면 바로 409를 준다(ADR 0057).
- **왜 문제인가:** 측정에서 선점 응답의 77~87%가 409다. 이 요청들이 4~7을 모두 한다. 멱등키 INSERT, 매수 행 잠금, 좌석 UPDATE를 한 뒤 롤백한다.
- 7이 특히 나쁘다. 요청에 잡힌 좌석이 하나 섞여 있어도 나머지 빈 좌석은 잠그고 HELD로 바꾼다. 그다음 갱신 행 수가 모자라 롤백한다. 그 사이 같은 빈 좌석을 노린 다른 사용자는 기다린다. SKIP LOCKED를 넣었을 때 C2 성공이 줄어든 원인(TS-73)이 바로 이 "질 요청의 짧은 잠금"이다.
- **개선:** 3 바로 뒤에서 접수형과 같은 검사를 한다. 이미 읽은 값이라 문장이 늘지 않는다. P4c 캐시가 필요 없고, 응답은 그대로 409 `SEAT_ALREADY_HELD`라 계약도 바뀌지 않는다.
- **주의할 점:** 같은 멱등키의 첫 요청이 1과 3 사이에 커밋되면, 두 번째 요청은 자기 좌석을 HELD로 보고 409를 받는다. 검사에 걸렸을 때 멱등키를 한 번 더 조회해, 있으면 409 대신 재응답(replay)한다. 409 경로에서만 한 번 더 읽으므로 싸다.
- **얻는 것:** 커밋된 잡힌 좌석이 섞인 요청은 쓰기 0번, 잠금 0개로 끝난다. 다른 사용자가 이 요청의 짧은 잠금을 기다리는 일이 준다.
- **잃는 것:** 트랜잭션과 커넥션은 여전히 잡는다(읽기 3번). 커넥션까지 아끼려면 캐시 사전 거절(P4c 뒤)이 필요하다. 둘은 겹치지 않고 함께 쓴다. 캐시가 먼저 거르고, 캐시가 놓친 것을 이 검사가 거른다. 아직 커밋되지 않은 선점과 겹친 경우는 이 검사로 못 거른다. 그건 지금처럼 7에서 판단한다.

### 구조 문제 2. 좌석 잠금을 쥔 채 INSERT를 여러 번 한다
- **상황:** 좌석 잠금은 7에서 잡고 12에서 푼다. 그 사이 8~11, 곧 "4 + 좌석 수"번의 왕복과 커밋이 있다. 4석이면 8번이다. 예매 좌석은 ID가 IDENTITY라 JDBC 배치로 묶이지 않는다.
- **개선:** 8~11을 먼저 하고 좌석 UPDATE를 마지막에 둔다. 잠금 구간이 "UPDATE 한 번 + 커밋"으로 준다. 좌석 잠금을 짧게 쥐면 50ms 안에 끝나는 경우가 늘어, 기다리는 쪽의 409도 준다.
- **얻는 것:** 핫 좌석 처리량이 오른다. 같은 좌석을 연달아 노린 요청이 앞 요청의 INSERT를 기다리지 않는다.
- **잃는 것:** 질 요청이 INSERT를 다 한 뒤 롤백한다. 409가 대부분인 지금 이것만 하면 손해다. **문제 1로 409 대부분을 앞에서 거른 뒤에야 이득**이다. 그래서 1 다음에 한다.
- 예매 좌석 ID를 시퀀스로 바꿔 배치 INSERT로 묶는 일은 엔티티 공통 규칙과 닿아 있어 따로 본다.

### 구조 문제 3. 커넥션을 잡기 전에 막는 곳이 없다
- **상황:** 좌석이 하나도 잠기지 않아도, 동시에 들어온 선점이 풀(10개)보다 많으면 나머지는 커넥션을 최대 1초 기다린다. 그동안 톰캣 스레드도 쥔다. 50ms로 번짐 시작점을 올렸지만 없애지는 못했다(ADR 0061).
- **개선:** 선점 API 동시 처리 상한(벌크헤드). 상한을 넘으면 커넥션을 잡기 전에 503으로 거절한다.
- **얻는 것:** 선점이 몰려도 좌석 조회 같은 다른 API가 커넥션을 받는다.
- **잃는 것:** 상한 값을 잘못 잡으면 처리할 수 있던 요청도 거절한다. 측정으로 값을 정해야 한다.

### 더 큰 구조 선택: 접수형
- 핫 좌석 경합을 구조로 없애는 답은 접수형이다. 같은 구역 요청을 Kafka 파티션 하나로 보내 한 소비자가 차례로 처리하면 잠금 다툼이 없다.
- 접수(ISE-16)는 있지만 소비자(ISE-17)는 아직 없다. 응답이 202와 결과 조회로 바뀌어 프론트 흐름도 달라진다. 동기형의 1~3을 먼저 하고, 그래도 모자랄 때 꺼낸다.
- Redis를 좌석 정본으로 쓰는 구조는 앞선 노트([시니어 개선안](2026-11-13-seathold-senior-improvements.md))처럼 하지 않는다.

## 예시
4석 요청 A(그중 1석이 이미 HELD로 커밋됨)와 1석 요청 B(A의 빈 좌석 중 하나)가 동시에 온다.
- 지금: A가 빈 3석을 잠그고 HELD로 바꾼 뒤 롤백한다. 그동안 B는 기다린다. A의 INSERT가 길면 B는 50ms를 넘겨 빈 좌석에 409를 받는다.
- 문제 1 반영 뒤: A는 3에서 HELD 좌석을 보고 바로 409를 받는다. B는 기다리지 않고 좌석을 잡는다.

## 실무 포인트
- 같은 판단을 하는 두 경로(동기형·접수형)가 서로 다르게 거르면 한쪽에 헛일이 남는다. 경로가 둘이면 공통 규칙(`SeatHoldRules`)으로 모아 차이를 없앤다.
- 잠금 최적화는 "얼마나 오래 기다리나"(대기 상한)와 "얼마나 오래 쥐나"(보유 시간)와 "누가 쥐나"(질 요청을 빼기) 셋으로 나눠 본다. 지금까지는 첫째만 손댔다.
- 개선안 사이에 순서가 있다. 잠금 보유 시간을 줄이는 일은 질 요청을 먼저 걸러야 이득이다.

## 측정 결과
세 가지를 모두 넣고 단계마다 쟀다. 자세한 내용은 [측정 문서](../../../design/reservation/seathold-structure-improvements.md)에 있다.
- 1: 예상대로 효과가 컸다. 인기 구역 쏠림(L7)에서 처리량 +65%, p95 198 → 124ms.
- 2: 위 "얻는 것"과 달리 local에서는 효과를 확인하지 못했다. 병목이 잠금이 아니라 커넥션 수였고, local DB의 INSERT가 짧아 줄어든 잠금 구간이 작았다.
- 3: 처리 가능량을 넘는 부하에서 타임아웃·번짐·유령 선점이 모두 0이 됐다. 대가로 39~43%가 503을 받는다. 기다림 없이 바로 거절하면 평시 부하도 16~19% 거절해 200ms 대기를 뒀다.

## 더 알아볼 것
- 문제 1을 넣은 뒤 C2 성공 건수와 C3 대기가 어떻게 바뀌는지 잰다. C2는 같은 라운드 안 동시 요청이라 커밋 전 겹침이 많아 효과가 작을 수 있다. 라운드 사이 잡힌 좌석이 남는 부하(`SeatHoldLoadTest`, K1)에서 효과가 클 것으로 본다.
