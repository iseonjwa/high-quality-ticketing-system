# 접수형 소비자(ISE-17) 머지 전 남은 확인 항목을 어떻게 풀 것인가 (트레이드오프와 추천)

ISE-17(PR #609, 접수형 좌석 선점 소비자) 리뷰에서 나온 확인 항목들의 해결 방안을 트레이드오프 관점에서 설명하고, 어느 쪽이 더 좋은 결과를 낼지 근거를 들어 달라.

## 자세히

### 배경: 두 가지 선점 방식
- **동기형**: HTTP 요청 안에서 바로 좌석을 잠그고 잡는다. 요청이 몰리면 HTTP 스레드 수만큼 DB 커넥션이 동시에 좌석을 다툰다.
- **접수형**: HTTP는 요청을 `seat_hold_requests`와 Outbox에 적고 202를 돌려준다. Kafka 소비자가 메시지를 하나씩 꺼내 좌석을 잡는다. 같은 구역 요청은 같은 메시지 키라 같은 파티션에 들어가고, 한 파티션은 한 번에 한 메시지씩 순서대로 처리된다.

이 차이가 아래 모든 판단의 바탕이다. 동기형의 문제는 "동시에 다투는 요청이 너무 많다"이고, 접수형의 문제는 "한 줄에 선 메시지가 앞 메시지 때문에 밀린다"(head-of-line blocking)다.

### 1. 선점 본체를 두 PR이 다르게 고친 문제

**상황**
- PR #609(ISE-17)는 `SyncSeatHoldService`의 선점 본체(매수 UPDATE → 좌석 UPDATE → 예매 INSERT)를 `SeatHolding`으로 떼어 동기형과 소비자가 함께 쓰게 했다.
- ISE-261(아직 커밋 전)은 같은 본체를 ADR 0061에 따라 고쳤다.
  - (가) 사전 거절: 이미 읽은 좌석 상태로 먼저 409를 낸다.
  - (나) 순서 변경: 다투지 않는 쓰기(예매·이력·멱등키)를 먼저 하고, 좌석 UPDATE를 트랜잭션 끝으로 옮긴다.
- 둘 다 `SyncSeatHoldService`를 고쳐 git 충돌이 나고, 내용상으로도 "(가)·(나)를 소비자에도 적용하나"를 정해야 한다.

**1-A. 사전 거절(가)을 소비자에도 넣을까**

| 안 | 얻는 것 | 잃는 것 |
|---|---|---|
| 넣는다 | 진 메시지가 매수·좌석 UPDATE를 하지 않는다 | 코드 몇 줄 |
| 넣지 않는다 | 변경 없음 | 진 메시지마다 쓰기 후 롤백, 새 트랜잭션 한 번 더 |

추천: 넣는다. 소비자에서 효과가 동기형보다 크다.
- 접수 단계에도 같은 검사가 있지만 오픈 순간에는 거의 걸러지지 않는다. 인기 좌석 하나에 1초 안에 100명이 요청하면, 접수 시점에는 그 좌석이 아직 아무에게도 잡히지 않았으므로 100건이 모두 통과한다. 소비자가 첫 메시지를 처리해야 비로소 좌석이 잡힌다. 그래서 나머지 99건은 소비자에서 걸러야 한다.
- 소비자는 한 파티션을 한 줄로 처리하므로 메시지 하나의 처리 시간이 곧 그 구역의 처리량이다. 진 메시지가 싸지면 같은 구역의 뒤 메시지가 그만큼 빨리 처리된다.
- 소비자에서는 사전 거절이 동기형보다 정확하다. 같은 파티션의 앞 메시지는 이미 커밋을 마쳤으므로 읽은 좌석 상태가 최신이다. 동기형에서는 아직 커밋 안 된 경쟁자가 있어 "빈 좌석으로 읽었는데 실제로는 질" 수 있다.
- 비슷한 효과를 동기형에서 이미 쟀다. 사전 거절을 넣자 인기 구역 쏠림(L7)에서 처리량이 65% 늘고 p95가 198ms에서 124ms로 줄었다(ADR 0062).
- 더 줄일 수도 있다. 사전 거절이면 아무것도 바꾸지 않았으므로 롤백하고 새 트랜잭션을 열 필요가 없다. 같은 트랜잭션에서 `REJECTED`와 처리 기록을 쓰면 진 메시지 한 건당 트랜잭션이 2개에서 1개로 준다. 효과는 측정 전 추정이다.

**1-B. 순서 변경(나)을 소비자에도 적용할까**

| 안 | 얻는 것 | 잃는 것 |
|---|---|---|
| 공용 본체에 넣어 둘 다 적용 | 본체가 하나라 두 모드가 어긋나지 않는다 | 소비자에서는 효과가 거의 없다 |
| 동기형에만 적용(본체 두 벌) | 소비자 코드 그대로 | 같은 일을 하는 코드가 두 벌이 되고, 다음 수정 때 한쪽만 고칠 위험 |

추천: 공용 본체에 넣는다. 효과가 아니라 유지보수 때문이다.
- 순서 변경의 목적은 "좌석 잠금을 쥔 시간을 줄여 같은 좌석을 기다리는 경쟁자를 덜 기다리게 하는 것"이다. 소비자에서는 같은 구역 경쟁자가 줄을 서 있어 동시에 기다리는 경쟁자가 거의 없다. 그래서 소비자 쪽 이득은 작다.
- 동기형에서도 이득이 측정으로 확인되지 않았다(ADR 0062: L7·L8 차이가 오차 안). 그래서 "효과가 있으니 넣는다"가 아니라 "본체를 두 벌로 나눌 만큼 다르지 않다"가 근거다.
- 비용도 작다. 순서 변경의 대가는 "질 요청이 INSERT를 더 하고 롤백한다"인데, 1-A의 사전 거절이 질 요청 대부분을 먼저 거른다.
- 구현: 동기형과 소비자 모두 "매수 → 예매·이력 → 요청 `HELD` 표시 → 좌석 UPDATE → 예매 좌석"으로 같은 순서를 쓸 수 있다. 소비자도 요청 행을 이미 잠그고 있어 `markHeld`를 좌석 UPDATE 앞에 둬도 된다. 그러면 `markHeld`까지 `SeatHolding` 안으로 넣어 호출하는 쪽 코드가 더 단순해진다.

**1-C. 무엇을 먼저 머지할까**

| 안 | 얻는 것 | 잃는 것 |
|---|---|---|
| ISE-17 먼저, ISE-261을 그 위에서 다시 맞춤 | 열린 PR을 고치지 않는다. ISE-261은 커밋 전이라 새 구조에 맞춰 바로 쓴다 | ISE-261 커밋이 #609 리뷰를 기다린다 |
| ISE-261 먼저, #609에서 본체를 다시 떼어 냄 | ISE-261이 먼저 dev에 들어간다 | 열린 PR #609를 크게 다시 쓰고 리뷰를 다시 받는다 |

추천: ISE-17 먼저.
- 다시 맞추는 양이 다르다. ISE-261이 본체에 준 변경은 `SyncSeatHoldService` 약 50줄이다. #609의 본체 분리는 main 코드 14개 파일에 걸친다. 작은 쪽을 큰 쪽 위로 옮기는 편이 실수할 곳이 적다.
- 검증이 겹친다. ISE-261의 동시성 테스트(C2·C3, `SeatHoldLockWaitTest`)가 공용 본체를 돌게 되므로, 한 번의 테스트로 두 모드의 본체를 함께 확인한다.
- 두 작업 모두 다음 주 배포 측정 전에 들어가야 하므로, 순서만 바뀔 뿐 측정 일정은 같다.

### 2. 소비자 잠금 시한: 100ms를 유지할까, 50ms로 맞출까

**잠금 시한이란**
PostgreSQL `lock_timeout`은 행 잠금을 이 시간 안에 못 얻으면 오류를 내고 포기하게 하는 설정이다. 포기하면 그 좌석이 곧 풀렸을 수도 있는데 "이미 선택된 좌석"으로 거절한다(거짓 거절). 오래 기다리면 거짓 거절은 줄지만 그동안 다른 일을 못 한다.

**동기형과 소비자는 "기다리는 비용"이 다르다**
- 동기형: 기다리는 요청마다 커넥션을 하나씩 쥔다. 몰리면 풀이 차서 상관없는 좌석 조회까지 실패한다(번짐). 트래픽에 비례해 커지는 비용이다.
- 소비자: 동시성이 2라 기다려도 커넥션은 최대 2개다. 번짐은 없다. 대신 기다리는 동안 그 스레드가 맡은 파티션이 모두 멈춘다. 파티션 6개를 스레드 2개가 나눠 맡으므로 한 스레드가 파티션 3개를 맡는다. 잠금 한 번에 100ms를 기다리면 구역 세 곳의 줄이 100ms 멈춘다.

**소비자가 만나는 잠금은 누가 쥐나**
같은 구역 경쟁자는 줄을 서 있어 동시에 잠그지 않는다. 소비자가 만나는 것은 줄 밖의 작업이다. 선점 만료 스케줄러, 취소, 결제 확정, 다른 구역 키로 들어온 섞인 요청이 여기에 해당한다.

| 안 | 얻는 것 | 잃는 것 |
|---|---|---|
| 100ms 유지 | 50~100ms 쥐는 잠금이 끝나기를 기다려 거짓 거절이 조금 준다 | 기다릴 때마다 파티션 3개가 최대 100ms 멈춘다. 좌석 여러 개 요청은 잠금마다 따로 시한이 걸려 몇 배로 늘 수 있다 |
| 50ms로 맞춤 | 멈춤이 절반. 두 모드가 같은 값이라 설명이 쉽다 | 50ms보다 오래 쥐다가 롤백하는 잠금이면 거짓 거절 |
| 더 길게(예: 200ms) | 거짓 거절 최소 | 멈춤이 가장 길다. 오픈 피크에 30초 시한 초과(TIMEOUT)가 늘 수 있다 |

추천: 50ms로 맞추고 설정 키(`seat-hold.consumer.lock-timeout`)는 그대로 둔다.
- 기다려서 살릴 수 있는 잠금은 대부분 수 ms짜리다. 동시성 테스트 C2(10명이 겹치는 좌석 4개를 500번 다툼)에서 성공한 선점 수가 500ms일 때 83건, 50ms일 때 78~92건으로 같은 범위였다(ADR 0061). 50ms를 넘겨 기다려도 더 살아나는 선점이 측정에서 보이지 않았다.
- 반대로 오래 쥔 잠금(C3, 2초 쥐고 있음)은 100ms든 50ms든 결국 거절된다. 그렇다면 더 기다린 시간은 멈춤 비용만 남긴다.
- 지금 PR의 근거("동기형 500ms보다 짧게")는 ISE-261로 동기형이 50ms가 되면 뒤집힌다. 100ms를 유지하려면 "소비자는 동기형보다 더 기다려야 한다"는 새 근거가 필요한데, 위 분석은 반대 방향을 가리킨다.
- 한계: C2·C3는 동기형 경로에서 잰 값이다. 소비자 경로에서 줄 밖 작업(특히 만료 스케줄러 일괄 처리)이 잠금을 얼마나 쥐는지는 재지 않았다. 배포 측정에서 `seathold.consumer.result{outcome=lock_timeout}`과 접수→처리 지연(`seathold.consumer.delay`)을 50ms 기준으로 보고, `lock_timeout` 비율이 눈에 띄면 그때 올린다. 설정값이라 재배포 없이 config-repo에서 바꿀 수 있다.

### 3. PR 브랜치가 dev보다 뒤처짐
- 방법은 둘이다. rebase는 이력이 깔끔하지만 force push가 필요하고 리뷰 중인 커밋이 바뀐다. merge는 병합 커밋이 하나 생기지만 리뷰 이력이 그대로다.
- 팀 규칙(`docs/guides/git-workflow.md`)이 rebase·force push를 금지하고 squash 머지가 기본이다. squash하면 병합 커밋도 사라지므로 merge의 단점이 없다. 고민할 거리가 없는 항목이다. 1-C에 따라 ISE-17을 먼저 머지한다면 지금 `git merge origin/dev` 후 build를 다시 돌린다.

### 4. Kafka 통합 테스트(`SeatHoldKafkaFlowTest`)를 CI에서 돌릴까
CI(`verifyWorkspace`)는 `compose.test.yml`의 PostgreSQL·Redis만 띄운다. Kafka가 없어 이 테스트는 환경 변수가 있을 때만 켜진다.

| 안 | 얻는 것 | 잃는 것 |
|---|---|---|
| A. 지금처럼 끄고 로컬 결과를 PR에 남김 | CI 변경 없음 | 누가 공통 재시도·DLQ 코드를 고쳐도 CI가 못 잡는다 |
| B. `compose.test.yml`에 Kafka를 더하고 CI에서 켬 | 배포와 같은 브로커(apache/kafka 4.1.1)로 매번 확인 | CI 시간 증가(브로커 기동 + DLQ 테스트만 약 7.6초), 시간 기다림이 있는 테스트라 가끔 흔들릴 수 있음 |
| C. 내장 Kafka(`spring-kafka-test`의 EmbeddedKafka) | Docker 없이 JVM 안에서 돎 | 실제 배포 브로커와 다르다. 의존성 추가 |

추천: 이 PR은 A, CI 편입(B)은 팀 제안 이슈로 따로 올린다.
- B의 가치는 이 PR만의 문제가 아니다. 재시도 1·2·4초와 DLQ 전송은 공통 모듈(`ConsumerErrorHandlers`)이 하고, 결제 쪽도 같은 코드를 쓴다. 공통 코드가 바뀌면 Kafka가 있는 테스트만 회귀를 잡는다. 그래서 장기적으로는 B가 낫다.
- 하지만 CI 구성은 팀 전체의 빌드 시간과 안정성을 바꾸는 공유 설정이다. 이 PR에 끼우면 리뷰 범위가 커지고 다른 팀원 PR까지 영향을 받는다. 따로 합의를 받는 것이 맞다(AGENTS.md 대전제 11).
- C는 배포 브로커와 달라, 이 테스트가 확인하려는 "실제 브로커에서의 재시도·DLQ·파티션 생성"을 그대로 보지 못한다.

### 5. 커넥션 풀 5개 중 소비자가 2개를 씀
필요한 커넥션 수는 대략 "초당 요청 수 × 요청 하나가 커넥션을 쥐는 시간"이다(리틀의 법칙).

| 안 | 얻는 것 | 잃는 것 |
|---|---|---|
| A. 그대로 두고 측정 | 다른 측정값(ADR 0062 상한 4개)이 그대로 유효 | 측정 전까지 부족한지 모른다 |
| B. 풀을 10개로 | 여유 | DB 연결 수 증가. ADR 0062의 동시 처리 상한(풀 5개 기준 4개·200ms)을 다시 재야 한다 |
| C. 소비자 동시성 1 | HTTP 몫 4개 | 접수형 처리량이 절반 |
| D. 소비자 전용 풀 분리 | HTTP와 완전히 격리 | DataSource 두 개 관리, 전체 연결 수 증가, 트랜잭션 설정 복잡 |

추천: A. 그리고 ISE-79에 합격 기준을 미리 적어 둔다.
- 소비자 몫은 트래픽이 아무리 몰려도 최대 2개로 묶여 있다. 문제는 "남은 3개로 HTTP가 버티느냐"다.
- 기본 모드(`mode: sync`)에서는 소비자가 할 일이 없어 커넥션을 쓰지 않는다. 접수형 모드에서는 무거운 선점이 HTTP에서 소비자로 옮겨 가고, HTTP는 짧은 INSERT(접수)와 짧은 SELECT(결과 폴링)만 한다. 커넥션을 쥐는 시간이 짧아지니 3개로 충분할 가능성이 높다. 다만 이것은 추정이다.
- B는 측정 근거 없이 다른 결정(ADR 0062 상한 값)을 무효로 만든다. D는 확실하지만 문제가 확인되기 전에 들이기에는 복잡하다.
- 합격 기준 예: 접수형 부하에서 Hikari 대기(`hikaricp_connections_pending`)가 0을 오래 넘지 않고, 커넥션 획득 실패(1초 시한)가 0건이고, 결과 폴링 p95가 동기형 좌석 조회 수준이다. 넘으면 D를 먼저 검토한다.

### 6. 배포 Kafka에 `seat-hold.request`가 이미 있을 수 있음
- Kafka는 기본으로 없는 토픽에 메시지가 오면 파티션 1개로 자동 생성한다(`auto.create.topics.enable` 기본값 true, compose에서 바꾸지 않음). 배포 Kafka는 볼륨이 있어 토픽이 재배포 뒤에도 남는다. ISE-16 릴레이가 배포에서 이미 돌았다면 파티션 1개짜리가 있을 수 있다.
- 앱이 뜨면 `KafkaAdmin`이 선언(6개)에 맞춰 늘린다. 파티션 수가 바뀌면 같은 키가 다른 파티션으로 가므로, 그 순간 처리 중인 메시지끼리만 순서가 흔들린다.

| 안 | 얻는 것 | 잃는 것 |
|---|---|---|
| A. 앱이 늘리게 둔다 | 손이 안 감 | 트래픽 중이면 순서가 잠깐 흔들린다 |
| B. 배포 전에 지우고 다시 만든다 | 처음부터 6개 | 수동 작업. 남은 메시지가 있으면 잃는다 |
| C. 배포 전에 확인하고 결정 | 상황에 맞춤 | 명령 한 번 |

추천: C. `kafka-topics.sh --describe --topic seat-hold.request`로 보고, 6개면 끝이다. 1개이고 Outbox PENDING과 소비자 지연(lag)이 0이면 A로 충분하다. 흔들릴 메시지가 없으므로 위험도 없다. 브로커 자동 생성을 끄는 것은 모든 서비스에 영향을 주는 공유 설정이라 이 작업 범위가 아니다.

## 면접 포인트
- "Kafka 소비자에서 DB 잠금 시한을 왜 짧게 뒀나요?" → 소비자는 한 파티션을 순서대로 처리하므로 기다리는 시간이 곧 뒤 메시지 전체의 지연이다. 한 스레드가 파티션 여러 개를 맡으면 그 배수로 커진다. 짧은 롤백 잠금은 50ms로도 기다려지는 것을 측정으로 확인했고, 오래 쥔 잠금은 더 기다려도 어차피 거절되므로 더 기다릴 이유가 없다.
- "접수 단계에서 이미 검사하는데 소비자에서 또 검사하는 이유는?" → 오픈 순간에는 같은 좌석 요청이 첫 처리 전에 한꺼번에 접수되어 접수 검사를 모두 통과한다. 진짜 거름망은 소비자이고, 소비자는 앞 메시지가 커밋을 마친 뒤 읽으므로 그 검사가 정확하다.
- "두 PR이 같은 코드를 다르게 고쳤을 때 어떻게 정리했나요?" → 다시 맞추는 양이 작은 쪽을 큰 쪽 위로 옮겼고, 효과가 아니라 "코드 두 벌의 유지 비용"을 근거로 본체를 하나로 유지했다.
