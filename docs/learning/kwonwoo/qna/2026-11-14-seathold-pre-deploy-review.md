# 배포 단계 측정 전에 좌석 선점 구조에서 더 개선할 것은 무엇인가 (시니어 관점 검토와 개선안)

## 질문
다음 주 배포 환경에서 측정하기 전에 여기서 더 개선할 수 있는 방안은 없나. 백엔드 시니어 개발자의 관점에서 좌석 선점의 전체 구조를 검토하고, 개선안마다 변경 내용과 손익, 예상 수치를 처음 보는 사람도 이해할 수 있게 써 달라.

## 짧은 답
기준 시점은 2026-11-14의 dev `0f69c1aa`에 ISE-261 미커밋 변경(잠금 대기 50ms, 사전 거절, 순서 변경, 동시 처리 상한)을 얹은 코드다.

정합성 뼈대는 바꿀 곳이 없다. 이번 검토에서 새로 찾은 것 중 가장 큰 것은 **접수형의 Outbox 릴레이가 같은 구역 메시지를 한 주기에 한 건만 보낸다**는 점이다. 접수형을 배포에서 잴 계획이라면 측정 전에 먼저 풀어야 한다. 나머지는 측정 결과를 해석할 수 있게 하는 준비와 작은 비용 절감이다.

| 순서 | 개선안 | 왜 측정 전인가 | 담당 | 크기 |
|---|---|---|---|---|
| 1 | 접수형 발행 경로: 직접 발행 모드 추가(또는 릴레이 완화 contract) | 지금 그대로 재면 접수형이 릴레이 한계만 보여 준다 | 선점(직접 발행) / 결제(릴레이) | 중 |
| 2 | 선점 동시 처리 상한과 계측 보강(좌석 UPDATE 시간, 상한 사용 중 수) | 상한 값을 정하고 병목이 잠금인지 풀인지 가르려면 필요 | 선점 | 소 |
| 3 | 커넥션 풀 크기를 ISE-237에서 먼저 정하기 | 상한 값(4개)과 소비자 몫이 풀 크기에 묶여 있다 | 효승(contract) | 소 |
| 4 | 캐시 사전 거절(P4c 읽기 메서드 contract, ISE-281) | 측정된 개선 폭이 가장 크다 | 효승 + 선점 | 소~중 |
| 5 | 만료 처리 속도 올리기 | 부하 뒤 좌석 회수가 늦으면 다음 측정 회차가 오염된다 | 선점 | 소 |
| 6 | 결제 토큰 서명을 트랜잭션 밖으로 | 성공 경로의 커넥션·좌석 잠금 시간을 줄인다. 비용이 거의 없다 | 선점 | 소 |
| 7 | 예매 좌석 다중 행 INSERT, 매수 반영 한 문장 | 배포에서 DB 왕복이 길게 나올 때만 | 선점(+공용 저장소) | 중 |

하지 않을 것: 입장 토큰 사전 조회 제거, 회차 정보 캐시, `SKIP LOCKED`, Redis 좌석 정본, 풀 크게 늘리기.

## 자세히

### 0. 지금 구조 한눈에 보기

**동기형 선점 한 건(성공, N석)의 DB 왕복**(`SyncSeatHoldService.holdInTransaction` → `SeatHolding.hold`)

- 입장 토큰이 붙은 요청(배포 경로) 기준으로 1석이면 커밋까지 왕복 14번, 4석이면 17번이다. 좌석 잠금을 쥔 구간은 "좌석 UPDATE + 예매 좌석 INSERT N번 + 토큰 서명 + 커밋"이다.
- 사전 거절로 끝나는 409는 1~4, 멱등키 재조회(`rejectHeldSeats`), 롤백으로 왕복 6번이고 잠금은 없다.
- 측정 참고값: Gateway를 우회한 K1-H 800명(풀 10)에서 서버 선점 평균 2.0ms, p99 6ms였다(`k6-contract-proposals.md` 5절). local에서는 선점 트랜잭션 자체가 병목이 아니었다.

**접수형 한 건의 흐름**: 접수 트랜잭션(멱등키·토큰·회차·좌석 조회, 요청 INSERT, Outbox INSERT) → Outbox 릴레이가 Kafka로 전송 → 소비자가 구역 파티션 순서대로 선점 → 결과 조회 API 폴링.

**배경 작업**: 선점 만료(5초마다 최대 100건), 접수형 30초 시한 정리(5초마다), Outbox 릴레이(500ms마다).

### 1. 접수형 발행 경로: Outbox 릴레이의 같은 키 한 건 제약

**상황**
- 공통 Outbox 릴레이(`common/.../OutboxRepository.claimNext`)는 같은 `message_key`의 PENDING 중 가장 오래된 한 건만 집는다. 앞 메시지가 실패한 채 뒤 메시지가 먼저 나가 순서가 뒤집히는 것을 막으려는 장치다. 결제 이벤트처럼 순서가 중요한 곳에는 맞는 설계다.
- 릴레이 한 주기(`OutboxRelayScheduler.relayRounds`)는 최대 20건(`batch-size`)씩 최대 10라운드를 돈다. 라운드에서 집은 수가 20보다 적으면 그 주기를 끝내고 500ms(`messaging.outbox.interval` 기본값) 뒤에 다음 주기를 시작한다.
- 접수형 선점의 메시지 키는 `회차:구역`이다(ADR 0056). 그래서 **한 구역의 메시지는 한 라운드에 한 건씩만 나간다.**

**예상 수치(코드 기준 계산, 미측정)**
- 밀린 구역이 20개보다 적으면 한 라운드에 집는 수가 20보다 적어 주기가 바로 끝난다. 구역당 전송은 **약 0.5초에 한 건, 곧 초당 약 2건**이다.
- 밀린 구역이 20개 이상이면 라운드가 이어져 한 주기에 구역당 최대 10건이다. 회차 좌석이 25구역(시드 기준 A~Y)이라 모든 구역에 고르게 몰려야 이 경우가 된다. 인기 구역 쏠림(L7)처럼 몇 구역에 몰리면 앞의 경우(초당 약 2건)다.
- 예: 인기 구역 하나에 1초 동안 1,000건이 접수되면, 30초 안에 소비자까지 가는 것은 약 60건이다. 나머지 약 940건은 처리 시작 전에 30초 시한이 지나 `REJECTED(TIMEOUT)`이 된다.

**선택지**

| 안 | 변경 | 얻는 것 | 잃는 것 |
|---|---|---|---|
| A. 접수형 직접 발행 모드 | 접수 트랜잭션 커밋 뒤 `KafkaTemplate`로 바로 보낸다. 설정으로 Outbox 방식과 고른다. seathold 모듈 안에서 끝난다 | 구역당 한계가 사라진다(프로듀서 전송 속도까지). 공통 모듈을 건드리지 않는다. ISE-18이 비교하려던 "접수형 직접 발행"이 이것이다 | 커밋 뒤 전송이 실패하거나 서버가 죽으면 메시지가 사라진다. 그 요청은 30초 시한 정리가 `TIMEOUT`으로 닫으므로 좌석·매수가 어긋나지는 않지만, 사용자는 30초를 기다린 뒤 다시 시도해야 한다 |
| B. 릴레이 완화(contract) | 토픽별 설정으로 같은 키를 한 라운드에 여러 건 보내게 한다. 같은 키는 id 순서로 보내고 앞 건이 실패하면 뒤 건을 멈춘다 | 전달 보장(Outbox)을 유지한 채 한계를 푼다 | 공통 모듈(결제 담당 안준현) 변경이다. 결제 이벤트에 영향이 없음을 그쪽에서 확인해야 한다 |
| C. 지금 그대로 재기 | 없음 | 측정 준비가 필요 없다 | 접수형 결과가 릴레이 한계만 보여 줘 동기형과 비교할 수 없다 |

**추천: A.** 담당 영역 안에서 이번 주에 끝낼 수 있고, 원래 계획(ISE-18의 세 가지 비교)에 들어 있던 경로다. 선점 요청은 30초 시한이라는 안전망이 있어 "최대 한 번 전달"을 받아들일 수 있다. 결제 이벤트처럼 잃으면 돈이 어긋나는 메시지와 다르다. B는 측정에서 직접 발행과 Outbox의 차이가 확인되면 근거와 함께 contract로 올린다.

- 구현 요지: 접수 트랜잭션은 그대로 두고 Outbox INSERT만 모드에 따라 뺀다. 커밋 뒤 전송하고 실패는 지표(`seathold.direct_publish.failed`)와 경고 로그로 남긴다. 같은 구역은 같은 키라 같은 파티션으로 가고, 한 프로듀서 안에서는 보낸 순서가 유지된다.
- 확인할 것: 소비자는 Outbox 경로와 같은 봉투(`SeatHoldRequestedMessageParser`)를 읽으므로 같은 형식으로 보내야 한다. 특히 `eventId`로 중복 소비를 거르므로(`processed_events`) 보내는 쪽이 이벤트마다 새 UUID를 만들어 넣어야 한다. 프로듀서는 `acks: all`, `enable.idempotence: true`(config-repo `application.yml`)라 재전송이 있어도 한 파티션 안의 순서가 유지된다.

### 2. 측정 전에 계측을 보강한다

**상황**
- 배포 측정에서 선점이 느리면 원인은 셋 중 하나다. 커넥션을 못 받았거나(풀), 좌석 잠금을 기다렸거나(잠금), CPU가 모자랐다. 지금 지표로는 Hikari 대기(`hikaricp_connections_pending`)와 결과 카운터(`seathold.result`, `seathold.consumer.result`)만 보여, 잠금 대기를 직접 볼 수 없다.
- 동시 처리 상한(`SeatHoldConcurrencyLimit`)은 거절 수(`seathold.concurrency.rejected`)만 센다. 상한 값을 정하려면 "지금 몇 자리를 쓰고 있나"와 "자리를 얼마나 기다렸나"가 필요하다.

**변경**
- 좌석 조건부 UPDATE(`holdAvailableSeats`) 한 문장의 소요 시간 Timer. 잠금을 기다리지 않으면 1ms 안쪽이고, 기다리면 최대 50ms까지 늘어나므로 이 분포가 곧 잠금 대기 분포다. SLO 버킷(ISE-277 방식)으로 둔다.
- 상한 사용 중 수 Gauge(`max - availablePermits`)와 자리 대기 시간 Timer.

**손익**
- 얻는 것: 배포 측정 한 번으로 병목이 풀인지 잠금인지 가를 수 있다. 상한 값을 "사용 중 수가 상한에 붙는 지점"으로 정할 수 있다.
- 잃는 것: Timer 기록 한 번은 보통 1µs보다 짧아(재지는 않았다) 선점 시간(ms 단위)에 비해 무시할 만하다. 시계열은 Timer 2개 × 버킷 수, Gauge 1개만큼 는다.

### 3. 커넥션 풀 크기를 측정 전에 정한다(ISE-237)
- 상황: reservation-service 풀은 근거 없이 들어간 5개다([학습 노트](2026-11-14-reservation-hikari-pool-5-origin.md)). ADR 0062의 동시 처리 상한(4개, 대기 200ms)과 접수형 소비자 몫(2개)이 이 값을 전제로 한다.
- 근거 수치(측정): K1-H 800명에서 풀 5는 커넥션 대기 최대 40건·p99 33ms, 풀 10은 대기 0·p99 6ms였고 풀 20·40은 10과 같았다.
- 변경: 코드 변경은 없다. ISE-237(효승 담당, Backlog)에 선점 쪽 근거를 보태고, 배포 측정 전에 값을 정해 달라고 요청한다.
- 손익: 풀을 10으로 정하면 상한 값을 다시 재야 한다. 정하지 않고 재면 상한·소비자 결과가 나중에 풀이 바뀌는 순간 무효가 된다.

### 4. 캐시 사전 거절(P4c 읽기 메서드 contract)
- 상황: P4c(1초 좌석 상태 캐시)는 dev에 있다(PR #605). 하지만 캐시가 `ScheduleSeatQueryService` 안의 `private` 필드라 선점 쪽에서 읽을 수 없다. ISE-205 댓글에서 약속한 contract 이슈는 아직 없다.
- 변경: 효승에게 읽기 메서드(예: `anyNotHoldable(scheduleId, seatIds)`)를 요청하는 contract 이슈를 올린다. 캐시가 비었거나 만료됐으면 `false`를 돌려줘 DB 판정으로 넘기게 한다. 선점 쪽은 트랜잭션을 열기 전에 이 메서드로 409를 낸다.
- 예상 수치(측정 브랜치 실측, 11/12): 4코어 Gateway 경유에서 409의 73~84%를 DB 전에 걸렀고, 선점 처리 시간이 47~95% 줄었다. 320명 단계 좌석 조회 성공률은 79.6%에서 99.9%로 올랐다. 잘못 거절한 409는 표본 407건 중 0건이었다.
- 지금의 사전 거절(DB에서 읽은 상태)과의 관계: 둘은 겹치지 않는다. 캐시는 트랜잭션을 열지 않고 걸린 요청만 같은 멱등키 재요청인지 PK로 한 번 본다(측정 브랜치 구현, 왕복 1번). 그래서 커밋된 지 1초가 넘은 선점을 지금의 왕복 6번 대신 1번으로 거른다. DB 사전 거절은 캐시가 놓친 최근 1초를 거른다.
- 손익: 최대 1초 낡은 캐시 때문에 그사이 풀린 좌석에 409를 줄 수 있다. 최종 판정은 DB 조건부 UPDATE라 중복 판매는 생기지 않는다.

### 5. 만료 처리 속도를 올린다
**상황**
- `SeatHoldExpiryScheduler`는 5초마다(`fixedDelay`) 최대 100건(`seathold.expiry.batch-size` 기본값, config-repo에 덮어쓰기 없음)을 한 건씩 트랜잭션으로 만료한다.
- 동시성 테스트 C6에서 두 인스턴스가 100건을 약 402ms에 만료했다. 스레드 하나가 건당 약 8ms를 쓴 셈이다(local).

**예상 수치(계산)**
- 지금 상한: 100건 ÷ (대기 5초 + 처리 약 0.8초) ≈ **초당 약 17건**.
- 예: 부하 측정에서 결제하지 않은 선점이 5,000건 남으면, 선점 5분이 지난 뒤 모두 회수하는 데 약 5분이 더 걸린다. 그동안 좌석은 HELD로 보여, 같은 회차로 바로 다음 측정을 돌리면 "이미 잡힌 좌석"이 섞여 결과가 오염된다.

**선택지**

| 안 | 변경 | 회수 속도(계산) | 잃는 것 |
|---|---|---|---|
| 지금 | 5초, 100건 | 약 17건/초 | |
| A | 주기를 1초로 | 100 ÷ 1.8초 ≈ 약 55건/초 | 커넥션 하나를 약 45% 시간 동안 쓴다 |
| B | 대상이 남아 있으면 쉬지 않고 계속 | 약 125건/초(건당 8ms) | 밀린 동안 커넥션 하나를 계속 쥔다. 풀 5에서 상한 4개를 켜면 좌석 조회 몫이 0이 된다 |

**추천: A.** 설정 한 줄(`seathold.expiry.interval: 1s`)로 3배 빨라지고, 커넥션을 쉬는 시간이 남는다. B는 풀이 10 이상으로 정해진 뒤에 검토한다.
- 대가: 만료 트랜잭션도 좌석 행을 잠근다. 다만 선점의 잠금 쿼리는 `status = 'AVAILABLE'`인 행만 잠근다. 만료가 아직 커밋하지 않은 좌석은 선점 쪽에서 HELD로 보여 기다리지 않고 건너뛴다(409). 그래서 만료 주기를 줄여도 선점이 만료를 기다리는 일은 거의 없고, 대신 막 풀리는 좌석을 그 순간 놓칠 수 있다. 같은 사용자의 매수 행은 둘 다 잠그므로 그 사용자의 선점과 만료가 겹치면 잠깐 기다린다.

### 6. 결제 토큰 서명을 트랜잭션 밖으로 옮긴다
- 상황: 동기형은 트랜잭션 안에서 결과를 만들며 결제 토큰을 서명한다(`SyncSeatHoldService` `results.withToken`). 이때 좌석 잠금과 커넥션을 쥐고 있다.
- 실측: 이 PC(32코어, JDK `SHA256withECDSA`, P-256)에서 서명 한 번이 약 0.11ms였다(2만 번 3회 평균). 배포 서버는 코어당 성능이 다르므로 다시 확인해야 한다.
- 변경: 트랜잭션은 예매를 돌려주고, 커밋 뒤에 `withToken`을 부른다. 같은 키 재요청 경로(`replay`)도 같은 방식으로 맞춘다.
- 예상 수치: 성공(201) 한 건당 커넥션·좌석 잠금 시간이 약 0.1ms 준다. 서버 선점 평균 2.0ms(K1-H) 기준 약 5%다. 201은 선점 응답의 13~23%라 전체 효과는 작다.
- 손익: 거의 공짜다. 다만 서명이 실패하면(키 오류) 지금은 트랜잭션이 롤백되지만, 옮기면 선점은 커밋되고 응답만 500이 된다. 사용자가 같은 멱등키로 다시 보내면 재응답 경로에서 토큰을 다시 받으므로 복구된다.

### 7. 배포에서 DB 왕복이 길게 나올 때만: 쓰기 문장 묶기
- 예매 좌석 다중 행 INSERT: 좌석 잠금 구간 안에 있는 예매 좌석 INSERT N번을 한 문장(`INSERT ... SELECT unnest(...)`)으로 바꾼다. 4석이면 잠금 구간 왕복이 6번에서 3번으로 준다. ID 전략(IDENTITY)은 바꾸지 않는다. 대가는 공용 저장소(`ReservationSeatRepository`, 효승·준현도 씀)를 건드리고, 부분 유니크 인덱스 위반을 `ActiveSeatConflictException`으로 바꾸는 처리를 다시 맞춰야 한다는 점이다.
- 매수 반영 한 문장: 지금은 "행 만들기(없으면)" + "조건부 UPDATE" 2문장이다. `INSERT ... ON CONFLICT (user_id, schedule_id) DO UPDATE SET held_count = ... WHERE held_count + :q <= :max`로 합치면 1문장이다. 성공·매수 초과 경로 모두 왕복 1번이 준다.
- 판단: local에서는 순서 변경(ADR 0062 2번)도 효과가 오차 안이었다. 왕복 하나가 컨테이너 네트워크에서 1ms보다 훨씬 짧으면 이 둘도 보이지 않을 것이다. 배포 측정에서 2번의 좌석 UPDATE Timer와 Zipkin 구간으로 왕복 시간이 길게 나오면 그때 넣는다.

### 하지 않을 것
| 안 | 끌리는 이유 | 하지 않는 이유 |
|---|---|---|
| 입장 토큰 사전 조회 제거 | 토큰이 붙은 요청에서 왕복 1번이 준다. 같은 토큰의 동시 요청은 요청 행의 부분 유니크 인덱스(`uq_seat_hold_requests_entry_token_jti`)가 어차피 막는다 | 조회를 빼면 "쓴 토큰 + 잡힌 좌석" 요청이 403 대신 409를 받는다. 코드가 따르는 ADR 0053 결정 2("다른 요청이 쓴 토큰이면 좌석을 잠그기 전에 거절")의 응답 순서가 바뀐다 |
| 회차 정보 캐시 | 모든 요청에서 왕복 1번이 준다 | 판매 기간·매수 한도가 바뀌어도 캐시 시간만큼 옛 값으로 판단한다. 얻는 왕복 하나에 비해 판단 오류의 비용이 크다 |
| `SKIP LOCKED` | 대기 0 | C2 성공이 약 1/3 줄었다(ADR 0061) |
| Redis 좌석 정본 | DB 잠금이 사라진다 | 이중 쓰기, 장애 때 정본이 흐려진다. 캐시 사전 거절이 같은 이점을 정본을 옮기지 않고 얻는다 |
| 풀 크게(20·40) | 대기가 줄 것 같다 | K1-H에서 10과 같았다 |

## 면접 포인트
- "Outbox를 썼는데 왜 직접 발행도 만들었나요?" → Outbox의 같은 키 순서 보장이 핫 구역에서 초당 약 2건 한계가 됐다. 선점 요청은 30초 시한이 남은 요청을 닫는 안전망이 있어 메시지 유실이 정합성 문제가 아니라 사용자 재시도 문제로 끝난다. 그래서 이 토픽만 전달 보장을 낮추고 처리량을 택했다. 결제 이벤트는 그대로 Outbox다.
- "측정 전에 무엇을 준비했나요?" → 느려졌을 때 원인을 가를 지표(잠금 대기 Timer, 상한 사용 중 수)를 먼저 넣었다. 수치를 보고 고칠 곳을 고르기 위해서다.
- 개선의 예상 효과는 "측정값", "측정에서 옮겨 온 값", "코드 기준 계산"을 나눠 말한다. 계산값은 배포 측정으로 확인할 대상이다.

## 재검토에서 고친 것
초안을 쓴 뒤 문장마다 코드·설정·기록에 다시 대조했다.
- 지표 이름: 초안의 `seathold.*.result`는 없는 이름이었다. 실제 이름 `seathold.result`, `seathold.consumer.result`로 고쳤다.
- 왕복 수: 입장 토큰 조회는 jti가 있을 때만 나간다(`SeatHoldRules.requireUnusedEntryToken`). 14·17번은 토큰이 붙은 요청 기준이라고 밝혔다.
- ADR 0053 인용: "좌석을 보기 전에"가 아니라 "좌석을 잠그기 전에"다. 코드 주석의 문구로 고쳤다.
- 만료와 선점의 충돌: 초안은 "막 풀리는 좌석을 두고 다툰다"고 썼다. 선점의 잠금 쿼리는 AVAILABLE 행만 잠그므로 만료가 커밋하기 전의 좌석은 기다리지 않고 건너뛴다. 실제로 둘이 같이 잠그는 것은 같은 사용자의 매수 행이다. 그렇게 고쳤다.
- 직접 발행: 소비자가 `eventId`로 중복을 거르므로 보내는 쪽이 이벤트 ID를 만들어야 한다는 점이 빠져 있었다. 프로듀서 순서 보장의 근거(`acks: all`, `enable.idempotence: true`)도 설정 파일에서 확인해 적었다.
- Timer 비용: 재지 않은 값이라 "재지는 않았다"를 붙였다.
- 캐시 사전 거절의 비용(11/14 추가 확인): 초안은 "왕복 0번"이라고 썼다. 측정 브랜치 `HeldSeatPreCheck`와 STEPS.md를 다시 보니 걸린 요청은 멱등키 PK 조회를 한 번 한다. "왕복 1번"으로 고쳤다.
- 확인만 하고 고치지 않은 것: 회차·좌석 조회가 연관 엔티티를 더 읽지 않는다(둘 다 `LAZY`). 만료·릴레이 주기는 config-repo와 앱 설정 어디에서도 덮어쓰지 않아 코드 기본값(5초·100건, 500ms)이 그대로다. 매수 테이블의 기본 키는 `(user_id, schedule_id)`라 `ON CONFLICT` 한 문장이 가능하다. 릴레이 라운드 종료 조건(`claimed < batchSize`), `MAX_ROUNDS = 10`, 같은 키 `NOT EXISTS`는 코드 그대로다.
