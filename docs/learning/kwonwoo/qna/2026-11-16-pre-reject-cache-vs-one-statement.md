# 캐시 사전 거절과 한 문장 사전 판정, 측정으로 보면 무엇이 나은가

## 질문
dev 최신화 뒤 "기존 코드가 dev보다 나은 점"을 다른 기기 에이전트가 정리해 줬다(정확성, 거절 사유 순서, 캐시로 아끼는 몫이 작다, 자동 배정에는 개선이 없다). 측정 결과로 보면 어떤가.

## 짧은 답
- 둘 다 남긴다. 캐시 판정을 앞에 두고, 캐시가 모르면 한 문장 사전 판정으로 간다.
- "캐시로 아끼는 몫이 작다"는 한 건 기준으로는 맞지만 결론은 틀렸다. 처리 한계는 한 건이 자리를 쥐는 시간에 반비례해서, 0.3ms 안팎을 줄인 것이 정상 3,000/s에서 의도 실패 5.5% → 0%로 나타났다.
- 정확성(1초 늦은 409)과 사유 순서 대가는 맞지만 작다. 이미 contracts.md 1-1에 적혀 있다.
- 자동 배정 지적은 대부분 맞다. 다만 "이력 저장·HELD 기록을 잠금 앞으로" 옮길 수는 없다. 줄일 수 있는 것은 잠금 뒤 좌석 재조회 1번이다.

## 자세히

### 왜 작은 절약이 큰 차이를 만드나
- 동시 처리 상한 4개 자리를 요청들이 돌려 쓴다. 처리 한계 ≈ 4 ÷ (한 건이 자리를 쥐는 시간).
- 끔: 1.53ms → 약 2,600/s. 켬: 1.07ms → 약 3,700/s(계산값).
- 도착이 3,000/s면 끔은 한계를 넘어 줄이 쌓이고(503 42.7%, 재시도까지 실패 5.5%), 켬은 한계 안이라 줄이 없다(503 5.5%, 실패 0%).
- 한계 아래(1,800·2,400/s)에서는 둘 다 실패가 없어 차이가 보이지 않는다. 그래서 "아끼는 몫"은 부하가 한계 근처일 때만 드러난다.

### 왜 왕복 수가 아니라 쿼리 무게인가
| | 끔(한 문장 사전 판정) | 켬(캐시가 잡힘이라 할 때) |
|---|---|---|
| 트랜잭션 | 쓰기 | 읽기 |
| 쿼리 | 좌석·회차 JOIN + 하위 쿼리 2개 | 멱등키 PK 조회 1개 |
| 끝 | 롤백 | 커밋 |
| DB 왕복 | 1번 | 1번 |

- 왕복 수가 같으니 네트워크가 느린 배포 환경에서 이점이 더 커진다고 단정할 수 없다. 배포에서 다시 본다.

### 정확성 대가의 크기
- 캐시는 최대 1초 늦다. 그사이 풀린 좌석(만료·결제 실패·취소)에 409를 줄 수 있다.
- 오픈 순간에는 좌석이 풀리기보다 잡히는 쪽이 압도적이다. 409를 받은 사용자는 다른 좌석을 고른다.
- 캐시는 거절에만 쓴다. "선점 가능"이라는 캐시를 믿고 잡지 않는다(최종 판정은 조건부 UPDATE). 그래서 중복 판매로 이어지지 않는다.

### 다른 AI의 분석을 받을 때
- 사실(코드가 무엇을 하나)과 판단(그래서 무엇이 낫나)을 나눠 본다. 이번에 사실은 대부분 맞았고, 판단 하나("아끼는 몫이 작다 → 하나만 남길 수도")가 측정과 달랐다.
- 판단은 같은 시점에 번갈아 잰 측정으로 정한다. 편차 범위가 겹치면 효과 없음이다.
