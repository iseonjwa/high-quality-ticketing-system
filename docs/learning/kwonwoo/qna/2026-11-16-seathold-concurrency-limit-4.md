# 선점 동시 처리 상한은 왜 4인가, 더 크게 두면 병렬 처리가 늘어 지표가 좋아지지 않나

## 질문
동시 처리 상한을 4로만 둔 이유는 무엇인가. 더 크게 두면 한 번에 더 많이 병렬로 처리해서 성능 지표가 좋아지지 않나.

## 짧은 답
- 상한 4는 따로 고른 값이 아니라 **커넥션 풀 5개에 묶인 값**이다. 풀 5개 중 4개를 선점에 주고 1개를 좌석 조회·요청 상태 조회 같은 다른 API 몫으로 남겼다(`seathold-structure-improvements.md` 7절).
- 실제로 DB에서 동시에 도는 선점 수는 상한이 아니라 **커넥션 수**가 정한다. 상한을 풀보다 크게 두면 병렬 처리는 늘지 않는다. 넘친 요청이 상한 앞(200ms, 공정 순서, 503)이 아니라 커넥션 풀 앞(1초, 실패 시 500)에서 기다리게 될 뿐이다. 그 줄에는 좌석 조회도 같이 서므로 조회까지 실패한다. 상한을 끄고 초당 600건을 넣었을 때 이것이 일어났다(타임아웃 57~76%, 조회 성공 29~47%).
- 그래서 병렬 처리를 늘리려면 **풀과 상한을 함께** 올려야 한다. 반복 2의 참고 측정에서 풀 6·상한 5는 정상 1,800/s 의도 실패를 22.5% → 9.4%로 줄였다. 풀 크기는 ISE-237(반효승) 범위라 넣지 않고 근거로만 남겼다.
- 한계도 있다. 풀 5에서 상한 5(다른 API 몫 없음)나 3과 비교한 측정은 없다. 4는 "다른 API 몫 1개"라는 추론으로 정했고, 측정은 "상한 끔 대 상한 4"만 했다.

## 자세히

### 상한이 하는 일
- `SeatHoldConcurrencyLimit`은 커넥션을 잡기 **전에** 선점 요청 수를 센다. 자리가 없으면 최대 200ms 기다리고, 대기 인원이 64명을 넘거나 200ms가 지나면 503으로 바로 돌려보낸다.
- 목적은 "많이 처리하기"가 아니라 **줄을 서버 밖으로 내보내기**다. 처리할 수 있는 양을 넘는 요청이 서버 안에서 몇 초씩 기다리다 타임아웃되고, 그 사이 사용자 모르게 좌석이 잡히는(유령 선점) 일을 막는다.

### 처리량은 무엇이 정하나
- 처리량 ≈ 동시에 처리하는 수 ÷ 한 건이 그 자리를 쥐는 시간.
- 반복 4 뒤 한 건이 자리를 쥐는 시간은 약 1.3ms(측정값, 대부분 409 경로)다. 상한 4면 계산상 초당 약 3,000건이다(4 ÷ 1.3ms, 계산값). 측정에서도 정상 2,000/s 의도 실패가 0%였다.
- 이 식의 "동시에 처리하는 수"는 상한과 커넥션 수 중 **작은 쪽**이다. 커넥션이 5개면 상한을 10으로 둬도 DB에서 동시에 도는 선점은 5개다.

### 상한을 풀보다 크게 두면 생기는 일
| 상한 | DB 동시 선점 | 넘친 요청이 기다리는 곳 | 좌석 조회 |
|---|---|---|---|
| 4 (풀 5) | 최대 4 | 상한 앞 200ms, 넘치면 503 | 커넥션 1개가 늘 남는다 |
| 5 (풀 5) | 최대 5 | 상한 앞 | 선점이 몰리면 남는 커넥션이 없다(측정 없음) |
| 6 이상 (풀 5) | 최대 5 (그대로) | 일부는 커넥션 풀 앞 1초, 실패하면 500 | 선점과 같은 줄에 선다 |
| 끔 | 최대 5 | 전부 커넥션 풀 앞 | 초당 600건에서 성공 29~47% |

- 커넥션 풀 앞에서 기다리는 요청은 Tomcat 스레드를 쥔 채 최대 1초를 기다린다. 1초를 넘기면 계약의 503이 아니라 500이 나간다(측정 문서 9절, 공통 예외 처리기 담당 확인 필요).
- 잠긴 좌석을 노린 요청은 잠금 대기(50ms, ADR 0061) 동안 커넥션을 쥔다. 상한이 크면 이런 요청이 커넥션을 다 차지할 수 있다. 잠금 장애 600/s에서 지금도 실패가 21%인 이유다.

### 풀까지 함께 늘리면
- 반복 2 참고 측정(풀 6·상한 5): 처리 한계가 상한 수에 비례해 약 25% 올랐다. 정상 1,800/s 의도 실패 22.5% → 9.4%. 잠금 장애 300/s에서는 503이 0이 됐다. 다만 배경 작업 부하가 없는 측정이고, 반복 3·4의 코드로는 다시 재야 한다.
- 무한히 늘릴 수는 없다. 풀이 커지면 DB에서 동시에 도는 쿼리가 늘어 CPU 경합·잠금 경합이 커진다. 배포 환경의 좌석 조회는 이미 postgres CPU를 많이 쓴다([커넥션 풀 5개의 근거](2026-11-14-reservation-hikari-pool-5-origin.md)). 그래서 값은 배포 환경에서 풀 크기(ISE-237)와 함께 잰다.

### 정리
- 상한을 키우는 것 자체는 병렬 처리를 늘리지 않는다. 커넥션 수가 천장이다.
- 상한은 "커넥션 수 - 다른 API 몫"으로 두고, 처리량을 올리려면 커넥션 수를 올리거나(ISE-237) 한 건이 자리를 쥐는 시간을 줄인다(반복 3·4: 3.6ms → 1.3ms).
