# AI 에이전트로 부하 테스트를 돌릴 때 토큰은 어디에 얼마나 드는가

## 질문
- 직전 토큰 사용량을 확인할 수 있나?
- (`/context`를 본 뒤) 방금 테스트를 돌릴 때 든 토큰량이 궁금하다.

맥락: 2026-11-09 Claude Code(Opus 5.5)에게 ISE-217 Q1-d 시나리오의 로컬 실행·원인 조사·스크립트 수정·Q1-c 확인을 맡긴 세션이다.

## 짧은 답
k6 실행 자체는 토큰을 쓰지 않는다. 토큰은 에이전트가 명령을 보내고, 결과를 읽고, 답을 쓰는 데만 든다. 이 세션의 테스트 부분은 AI 서버 호출 44번에 캐시 저장 약 9.2만, 캐시 읽기 약 433만, 출력 약 3.9만 토큰이었다. 대부분은 캐시 읽기다. 호출할 때마다 지금까지의 대화 전체를 다시 보내기 때문이다. 대화가 길수록, 확인 호출이 많을수록 늘어난다.

## 자세히

### 토큰의 종류
| 항목 | 뜻 | 요금 |
|---|---|---|
| 입력(input) | 캐시에 없어 새로 처리한 입력 | 기준 단가 |
| 캐시 저장(cache write) | 처음 보낸 부분을 캐시에 넣음. 다음 호출부터 캐시로 읽음 | 기준보다 조금 비쌈 |
| 캐시 읽기(cache read) | 이미 보낸 앞 대화를 캐시에서 다시 읽음 | 기준보다 훨씬 쌈 |
| 출력(output) | 모델이 쓴 답과 도구 호출 | 가장 비쌈 |

에이전트는 한 번의 답을 쓰는 동안에도 도구(명령 실행, 파일 읽기)를 부를 때마다 AI 서버를 다시 호출한다. 호출마다 시스템 지침, 도구 정의, 지금까지의 대화가 함께 간다. 그래서 한 호출의 캐시 읽기는 "그 시점의 대화 길이"와 같고, 한 단계의 캐시 읽기는 대략 "호출 수 × 대화 길이"가 된다.

### 이 세션의 실측
대화 기록 파일(`~/.claude/projects/<프로젝트>/<세션 id>.jsonl`)에는 assistant 메시지마다 `usage`(input_tokens, cache_creation_input_tokens, cache_read_input_tokens, output_tokens)가 남는다. 같은 메시지 id는 한 번만 세고, 사용자 메시지 단위로 묶어 합쳤다. 새 입력은 단계마다 수 토큰이라 표에서 뺐다(합계 88).

| 단계 | 호출 | 캐시 저장 | 캐시 읽기 | 출력 |
|---|---|---|---|---|
| 스택 기동, Q1-d 1차 실행, 원인 조사 | 14 | 50,525 | 956,476 | 9,754 |
| Q1-d 2차 실행 | 5 | 8,195 | 452,027 | 4,304 |
| 순간 속도(밀도) 설명, 노트 | 3 | 7,080 | 293,697 | 4,401 |
| Q1-d 3차 실행, sleep 탐침 | 7 | 9,848 | 761,028 | 8,524 |
| 스크립트 수정, 100명 실행, Q1-c, 기록 | 13 | 15,322 | 1,594,874 | 11,194 |
| 기록 검사 결과 확인 | 2 | 1,278 | 267,700 | 413 |
| 합계 | 44 | 약 9.2만 | 약 433만 | 약 3.9만 |

- 첫 단계의 캐시 저장(5만)이 큰 것은 시스템 지침·도구 정의·프로젝트 지침(AGENTS.md 등)을 처음 캐시에 넣었기 때문이다.
- 마지막 단계(13번 호출)가 가장 컸다. 대화가 이미 12~13만 토큰으로 길어진 뒤에 호출이 많았다.
- 40초 넘게 기다린 k6 실행도 출력을 `grep`·`sed`로 줄여 받았기 때문에 실행 하나당 늘어난 대화는 수천 토큰이었다.

세션 끝의 `/context`는 컨텍스트 137.7k / 1m(14%)였다. 이 값은 지금 대화가 한 번에 차지하는 크기이고, 위 합계(누적 사용량)와는 다른 숫자다.

### 도구 호출 횟수
같은 기록 파일에서 assistant 메시지의 `tool_use`를 셌다. 한 번의 AI 호출에서 도구를 여러 개 동시에 부르기도 해서 도구 호출 수(48)가 AI 호출 수(44)보다 많다.

| 단계 | 도구 호출 | 종류 | 그중 k6 실행 |
|---|---|---|---|
| 스택 기동, Q1-d 1차, 원인 조사 | 15 | Bash 14, Grep 1 | Q1-d 1번 |
| Q1-d 2차 | 5 | Bash 4, Write 1 | Q1-d 1번 |
| 밀도 설명, 노트 | 3 | Bash 1, Edit 2 | 없음 |
| Q1-d 3차, sleep 탐침 | 7 | Bash 6, Edit 1 | Q1-d 1번, 탐침 2번(각 호출에서 k6 2회) |
| 수정, 100명, Q1-c, 기록 | 17 | Bash 10, Edit 6, Write 1 | 탐침 1번, Q1-d 1번, Q1-c 1번 |
| 기록 검사 확인 | 1 | Bash 1 | 없음 |
| 합계 | 48 | Bash 36, Edit 9, Write 2, Grep 1 | 서버 측정 5번, 탐침 3번 |

Bash 36번 중 k6 실행은 8번이다. 나머지는 결과 CSV 집계, Redis 확인, Prometheus 차단기 지표 조회, 로그·설정 확인이다. Edit·Write 11번 중 스크립트 수정은 2번이고 나머지는 학습 노트와 판단 기록이다.

### 기다리는 동안 무엇을 했나
- k6 실행은 모두 앞에서(foreground) 한 번의 도구 호출로 돌렸다. 끝날 때까지 그 호출이 기다리고, 중간에 상태를 다시 묻는 반복 확인은 없었다. 회차 오픈까지 40초를 기다리는 일은 k6 안의 VU가 했다.
- 스택 기동은 `docker compose ... up -d --wait` 한 번이다. 건강 상태 대기는 compose가 했다.
- 반복 확인은 한 번 있었다. reservation-service·user-service가 healthy가 될 때까지 5초 간격 최대 40번 확인하는 셸 반복문이다. 한 번의 도구 호출 안에서 돌았고, 이미 healthy라 바로 끝났다.
- `sleep 3`이 한 번 있었다. 대기가 아니라 `redis-cli --latency`를 3초 동안 재게 하려는 것이었다.
- 기록 검사(`records-check.sh`)는 2분 제한을 넘겨 자동으로 백그라운드로 옮겨졌다. 끝날 때 알림을 받았고, 그 사이 확인을 반복하지 않았다.

셸 반복문이나 앞에서 기다리는 실행은 기다리는 동안 토큰을 쓰지 않는다. 토큰이 드는 것은 그 결과를 읽는 순간뿐이다. 반대로 "끝났나?"를 도구로 여러 번 묻는 방식은 확인할 때마다 대화 전체를 다시 읽으므로 비싸다.

### 컨텍스트 구성(`/context`)
세션 끝의 `/context`는 137.7k / 1m(14%)였다.

| 항목 | 토큰 | 설명 |
|---|---|---|
| 대화(Messages) | 96.8k | 주고받은 말과 도구 결과. 가장 크고 계속 늘어난다 |
| 기본 도구 정의 | 27.1k | Bash, Read, Edit 등 항상 불러오는 도구 설명 |
| 스킬 목록 | 5.3k | 32개 스킬의 한 줄 설명. 본문은 쓸 때만 읽는다 |
| 메모리 파일 | 4.1k | AGENTS.md 3.3k, CLAUDE.md 0.7k, CLAUDE.local.md 0.2k |
| 시스템 지침 | 2.8k | |
| MCP 서버 안내 | 1.6k | Linear 등 연결 서비스 사용 안내 |
| 남은 공간 | 829.3k | |
| 자동 압축 여유 | 33k | 이만큼 남으면 앞 대화를 요약해 줄인다 |

표에 "지연 로딩(deferred)" 도구(MCP 46.4k, 시스템 26k)가 함께 보이지만, 이름만 올라가 있고 쓸 때 불러온다. 실제로 차지하는 양은 0에 가깝다(`/context`에도 "99 tools · 0 tokens"로 나온다).

대화 96.8k 중 큰 몫은 도구 결과다. 1차 실행에서 진행 막대가 포함된 k6 출력 80줄을 그대로 받은 것이 대표적이다. 2차부터는 진행 막대를 걸러 줄였다.

### 줄이는 방법
- 결과 확인을 스크립트 하나로 모은다. 결과 CSV에서 상태별 연결·응답 시간을 한 번에 뽑는 스크립트를 쓰면 확인 호출 수가 준다.
- 도구 출력은 필요한 줄만 받는다. k6 진행 막대처럼 반복되는 줄은 걸러 낸다.
- 성격이 다른 작업(측정 실행과 문서 정리 등)은 새 세션에서 시작해 대화 길이를 짧게 유지한다.
- 공식 집계는 `/cost`(비용·토큰), 현재 컨텍스트 크기는 `/context`로 본다.

## 면접 포인트
- 에이전트의 토큰 비용은 "호출 수 × 대화 길이"로 커진다. 프롬프트 캐시가 반복 입력의 단가를 낮추지만 호출 수를 줄이는 것이 더 큰 효과다.
- 외부 도구(k6, Docker)가 하는 일은 토큰을 쓰지 않는다. 에이전트가 읽는 출력의 양만 토큰이 된다.
