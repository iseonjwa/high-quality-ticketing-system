# 대기열 폴링 수는 왜 계산값보다 많이 나오고, 폴링 간격은 어떻게 확인하는가

## 질문
- Q2(대기자 3,000명) 배포 측정에서 초당 폴링이 322건으로, 계산값 약 270건보다 많았다. 왜 그런가?
- 폴링 간격이 서버가 준 값의 ±10% 안인지 "추정"으로 확인했다는 것은 무슨 뜻인가?

## 짧은 답
서버는 앞쪽 대기자에게 더 짧은 간격을 준다. 계산값 270건은 3,000명 모두 약 11초마다 부른다고 본 값이라, 3~11초마다 부르는 앞쪽 500명의 몫이 빠졌다. 순번별 간격을 반영하면 초당 약 327건으로 실측과 맞는다. 폴링 간격은 k6 결과에 사용자별 시각이 없어 직접 재지 못했다. 대신 "서버가 준 간격 + 응답 시간 + 늦게 보낸 시간"으로 계산했다.

## 자세히

### 서버가 정하는 간격
`PollPolicy`는 다음 순서로 간격을 정한다(설정 `admit-per-second: 50`, `poll-min: 3s`, `poll-max: 10s`, `poll-jitter-ratio: 0.2`).

1. 예상 대기 = 순번 ÷ 50(올림). 1초에 50명씩 입장하기 때문이다.
2. 그 값을 3초 이상 10초 이하로 자른다(clamp).
3. 0~20%를 무작위로 더한다(지터). 모두가 같은 순간에 몰려 부르지 않게 한다.

```java
long base = Math.clamp(estimatedWaitSeconds * 1000, pollMin, pollMax);
long jitter = (long) (Math.random() * base * pollJitterRatio);
return base + jitter;
```

### 대기자 3,000명일 때 초당 폴링
| 순번 | 예상 대기 | 자른 값 | 지터 포함 간격 | 초당 폴링 |
|---|---|---|---|---|
| 1~150 | 0~3초 | 3초(최소) | 약 3.3초 | 150 ÷ 3.3 ≈ 45 |
| 151~500 | 3~10초 | 그대로 | 3.3~11초 | 사람마다 달라 합하면 ≈ 55 |
| 501~3,000 | 10초 이상 | 10초(최대) | 약 11초 | 2,500 ÷ 11 ≈ 227 |
| 합계 | | | | ≈ 327 |

151~500번 구간은 1/간격을 더한 값이다. 간격이 순번에 비례하므로 `50 ÷ 1.1 × ln(500/150)` ≈ 55다.

측정에서 서버가 준 간격 분포도 3초대 27,095건, 4~9초대 25,726건, 10~11초대 140,742건으로 이 구조와 맞았다. 대기자가 많아질수록 앞쪽 500명의 비중이 작아져 "대기자 수 ÷ 11"에 가까워진다. 명세의 2,700건(3만 명)은 그 근사다. 대기자가 적은 측정에서 명세 계산값을 그대로 쓰면 실측이 늘 많게 나온다.

### 폴링 간격 확인
명세 판정은 "실제 간격 중앙값이 서버가 준 값의 ±10% 안"이다. 같은 사용자가 앞 요청과 뒤 요청 사이에 실제로 얼마나 쉬었는지 보려면 요청마다 사용자와 ms 단위 시각이 필요하다. k6 raw CSV에는 둘 다 없다(시각은 초 단위, 사용자 태그 없음).

Q2 스크립트는 응답을 받은 순간부터 준 간격만큼 기다렸다가 다음 요청을 보낸다. 그래서 다음 식으로 계산했다.

```
실제 간격 = 서버가 준 간격 + 응답 시간 + 늦게 보낸 시간(poll_lateness)
          = 10,616ms      + 1.55ms   + 0ms               ≈ 10,618ms (+0.02%)
```

스크립트 동작을 근거로 한 계산이라 직접 잰 값은 아니다. 직접 재려면 폴링마다 사용자 번호와 ms 시각을 남기는 지표를 더해야 한다.

### 오류가 나면 계산이 깨진다
같은 날 대기자 10,000명 Q2에서는 첫 폴링(10초 동안 흩음, 초당 약 1,000건) 3초 만에 Gateway auth-redis 차단기가 열렸다. 오류를 받은 대기자는 3초 뒤 다시 부르므로 초당 폴링이 2,300~3,800건으로 불었다. 이때 초당 폴링 수와 간격은 서버가 준 간격이 아니라 재시도 규칙이 정한다.

## 면접 포인트
- 폴링 부하는 "대기자 수 ÷ 평균 간격"이 아니라 각 대기자의 1/간격을 더한 값이다. 간격이 순번에 따라 다르면 앞쪽 대기자가 부하를 더 만든다.
- 지터는 같은 간격을 받은 사용자들이 같은 순간에 몰리지 않게 흩는다. 평균 간격을 약 10% 늘리는 비용이 있다.
- 오류 뒤 재시도 간격이 짧고 오류 응답이 빠르면 재시도가 부하를 키워 보호 장치가 회복하지 못할 수 있다.
