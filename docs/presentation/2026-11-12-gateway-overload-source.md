# 발표 소스: Gateway 과부하를 측정으로 좁혀 간 기록 (11/9~11/12)

발표 자료를 만드는 사람이 가공할 원재료다. 장면마다 핵심 메시지 한 문장, 보여 줄 숫자, 그래프 데이터, 발표자 메모, 출처를 둔다. 자세한 흐름은 [트러블슈팅 서사 문서](../design/infra/gateway-overload-troubleshooting-story.md)(맨 위 "팀원용 3분 요약"), 측정 정본은 [open-peak-scenarios.md](../design/infra/open-peak-scenarios.md) 배포 서버 1~8차다.

담당: Gateway·측정 kangmin. 1~3차 측정은 대기열 담당(youngeun)이 했다.

## 0. 숫자를 쓸 때 지킬 것
- 모든 숫자는 배포 서버(EC2 `m7i.xlarge` 4 vCPU 한 대, 컨테이너 21개)에서 G1 부하(인증이 필요한 대기열 순번 조회 `GET /api/v1/schedules/{id}/queue/me`)로 쟀다. 발생기는 같은 VPC의 별도 EC2(k6)다.
- **% 변화는 같은 날 비교에만 쓴다.** 8차에서 같은 설정(요청 로그 끔)도 7차보다 서버 CPU가 6~9%p 낮게 나와, 날이 다르면 수치가 흔들린다는 것을 확인했다. 날이 다른 값은 "참고"로만 쓴다.
- 대부분 회차당 1회 측정이다. 8차만 같은 설정을 2회씩 쟀다. 같은 값을 두 번 잰 차이는 굿풋 약 5%였다(6차 L128).
- "굿풋"은 200 응답이면서 200ms 안에 끝난 요청 수/초다. "성공 처리량"(늦어도 성공한 수)과 다르다.
- "계산값"은 측정값으로 계산한 것이다. "추정"은 근거가 간접적인 것이다.

## 1. 용어 (화면 하단 주석용)
| 말 | 한 줄 풀이 |
|---|---|
| 차단기(서킷 브레이커) | 최근 호출의 실패·느린 호출 비율이 기준을 넘으면 일정 시간 호출을 막는 장치. Gateway의 `auth-redis`는 로그아웃 토큰 확인(Redis)을 감싼다 |
| 벌크헤드 | 동시에 실행할 수 있는 수를 세는 허가 카운터. 차면 바로 거절 |
| 동시 처리 수 상한 | Gateway 전체에서 처리 중인 요청 수를 세어 넘치면 바로 503을 주는 장치(부하 차단, load shedding) |
| 굿풋 | 200ms 안에 성공한 요청 수/초 |
| p95 | 요청 100개 중 95번째로 느린 응답 시간 |
| 리틀의 법칙 | 평균 처리 중 수 = 도착률 × 평균 머문 시간 |
| 작업 보존형 | 자리가 비면 다음 요청이 바로 채우는 방식. 남는 CPU를 놀리지 않는다 |

## 2. 장면

### 장면 1. 문제: 티켓 오픈 순간 Gateway가 먼저 무너진다
- **메시지**: 인증이 필요한 요청이 몰리면 Gateway가 세 가지 모양으로 무너졌다.
- **보여 줄 것**
  | 모양 | 숫자 | 측정 |
  |---|---|---|
  | Redis는 정상인데 인증 차단기가 열려 전체 503 | 2,000/s에서 201 428건 / 503 19,573건, Redis 지연 0.1~0.8ms | 1차(대기열 진입 Q1) |
  | CPU 포화 | 1,500/s 서버 CPU 93%, 2,000/s 굿풋 1,469/s·p95 435ms에서 정체 | 5차 0a |
  | Gateway OOM 강제 종료 | 768MiB 한도에서 3회 | 5차 0a |
- **발표자 메모**: 한 회차에 값 하나만 바꾸고, 바꾼 값·이유·전후 차이를 누적 표에 쌓는 방식으로 1~8차를 쟀다.

### 장면 2. 차단기는 무엇을 실패로 세야 하나
- **메시지**: 기준값보다 "무엇을 실패로 세나"가 먼저다.
- **보여 줄 것**: 벌크헤드 거절이 차단기 안쪽에서 "Redis 실패"로 세어지던 구조 → 집계에서 뺌. 결과 3,000/s까지 차단기 열림 0회, 거절 16,024건 모두 "무시" 집계, 실패 0.
- **발표자 메모**: 처음 가설 두 개(벌크헤드 크기 25 → 100, 느린 호출 기준 50 → 100ms)는 둘 다 틀렸다. 25와 100의 한도가 같다는 결과가 "크기가 아니라 구조"로 시선을 옮겼다.
- **출처**: [ADR 0050](../decisions/0050-gateway-auth-redis-breaker-bulkhead-split.md), TS-56

### 장면 3. 실패한 가설: 차단기를 예민하게 하면 CPU 포화를 막을까
- **메시지**: 실패한 가설도 측정으로 닫았고, 실패 이유가 다음 장치의 위치를 정했다.
- **보여 줄 것**: 느린 호출 기준 100 → 20ms로 낮춰도 2,500/s까지 열림 0회, 느린 호출 비율 최대 24%(열림 기준 80%). 차단기가 잰 호출 시간 평균 11~17ms 대 사용자 p95 878ms.
- **발표자 메모**: 기다림이 차단기가 재는 구간 밖(이벤트 루프·CPU 차례 대기)에 있었다. AI는 처음부터 "맨 앞 유입 제한"을 추천했고, 강민은 거부하고 차단기부터 실험했다. 결론은 같았지만 근거가 숫자가 됐다.
- **출처**: TS-57, [판단 기록(거부)](../ai-judgments/kangmin/2026-11-11-breaker-first-for-gateway-cpu-saturation.md)

### 장면 4. 메모리만 늘리면 죽는 대신 느려진다
- **메시지**: 자원을 늘리는 것은 실패의 모양만 바꾼다.
- **보여 줄 것**: Gateway 메모리 768 → 1,024MiB. OOM 3회 → 0회. 같은 부하에서 2,000/s p95 435 → 752ms, 굿풋 1,469 → 1,315/s.
- **발표자 메모**: 동시 요청을 더 받아 줄이 길어졌다. 메모리 예산과 동시 처리 수 상한은 함께 가야 한다.
- **출처**: TS-58

### 장면 5. 맨 앞 동시 처리 수 상한
- **메시지**: 리틀의 법칙으로 고른 값이 측정에서 맞았다.
- **그래프 데이터**(2,000/s, 같은 날 11/11. 막대 = 굿풋, 선 = p95)
  | 회차 | 상한 | 굿풋(/s) | p95(ms) |
  |---|---|---|---|
  | 0a | 없음 | 1,469 | 435 |
  | M1 | 없음(메모리만 증설) | 1,315 | 752 |
  | L32 | 32 | 1,575 | 49 |
  | **L64** | **64(운영 기본값)** | **1,696** | **87** |
  | L128b | 128 | 1,721 | 162 |
  | L500 | 500(대조군) | 1,304 | 571 |
- **변화**: 0a 대비 L64 굿풋 +15.5%, p95 −80%(같은 날, 배포는 다름). 메모리 511~540MiB로 평탄, OOM 0.
- **발표자 메모**: 굿풋이 멈춘 약 1,480/s에서 p95 200ms를 지키는 평균 처리 중 수를 계산하니 60~67이었다. 설계 세션 안은 500(p95를 평균 자리에 넣은 값)이었고, L500은 상한 없음과 같았다. 128은 굿풋이 1.5% 높지만 반복 측정 차이(5%) 안이고 p95가 두 배라 64를 유지했다.
- **출처**: TS-59, [판단 기록(64 유지)](../ai-judgments/kangmin/2026-11-11-keep-in-flight-limit-64.md)

### 장면 6. 거절에도 비용이 든다 → 거절 위치를 프레임워크 층으로 옮김
- **메시지**: 숫자의 이상함을 소스 코드로 따라가 구조를 찾았다.
- **그림 소스**(요청이 Gateway 안에서 지나는 층, Spring Boot 4.1.2 소스로 확인)
  | 순서 | 층 | 하는 일 | 거절 위치 |
  |---|---|---|---|
  | 0 | Netty | HTTP 해석 | |
  | 1 | HttpHandler 데코레이터 | 카운터 하나 | **개선 후(H1)** |
  | 2 | `HttpWebHandlerAdapter` | 요청 객체, 서버 관측(추적·지표) 시작 | |
  | 3 | 요청 로그 WebFilter | 요청 로그 한 줄 | |
  | 4 | 라우트 매칭 | 경로 조건 평가 | |
  | 5 | GlobalFilter -200 | 동시 처리 수 상한 | 개선 전 |
  | 6 | GlobalFilter -100 | 인증(JWT, Redis) | |
- **보여 줄 것**(2,500/s, 같은 날): 굿풋 1,608 → 1,814/s(+12.8%), p95 104 → 78ms(−25%). 서버 CPU는 ±1%p로 그대로.
- **발표자 메모**: "맨 앞 WebFilter"로 옮기면 될 줄 알았지만, Boot 4에서는 서버 관측이 WebFilter 체인 바깥 어댑터에서 시작된다. 그래서 프레임워크가 제공하는 더 바깥 연결점(HttpHandler 데코레이터)으로 옮겼다.
- **출처**: TS-59, [학습 노트](../learning/kangmin/qna/2026-11-11-gateway-httphandler-decorator-early-reject.md)

### 장면 7. 측정 지표의 함정과 R0
- **메시지**: 측정 설계도 검증 대상이다.
- **보여 줄 것**
  - 미리 정한 판정 지표(포화 구간의 "Gateway CPU ÷ 요청 수")는 거의 같았다(0.71 → 0.72ms). 서버 CPU 98~99%에서는 이 값이 비용이 아니라 "받은 CPU 몫 ÷ 처리량"이라 가설을 가리지 못한다.
  - 그래서 포화 전 구간에서 거절을 일부러 만드는 측정(R0, 상한 1과 1,000을 500·1,000/s로 비교)을 따로 설계했다.
  - R0 결과(8차): 받은 요청 한 건 1.06ms, 거절 한 건 0.02~0.08ms. **거절은 받은 요청의 2~8%.** 개선 전 거절은 받은 요청의 약 1/5(포화 구간 자료로 푼 추정)였다.
- **발표자 메모**: 전후 측정 방법이 달라 "몇 % 줄였다"고 말하지 않는다. "약 1/5에서 1/10 이하로"까지만 말한다. 거절이 싸져 남은 CPU는 상한이 받은 요청에 다시 쓰므로(작업 보존형) 이득은 서버 CPU가 아니라 굿풋으로 나타났다.
- **출처**: [학습 노트(거절 비용 전후)](../learning/kangmin/qna/2026-11-12-rejection-cost-before-after.md), 8차 절

### 장면 8. 비용은 코드 밖에 있었다: 요청 로그
- **메시지**: 프로세스 안 프로파일러는 프로세스 밖 비용을 보지 못한다.
- **보여 줄 것**
  - JVM 프로파일러(JFR)는 요청 로그를 Gateway CPU의 5.2%로 봤다.
  - 요청 로그를 끄자(7차, 같은 날): 서버 CPU 1,000/s 78 → 66%(−12%p), 1,500/s 93 → 85%(−8%p). **처음으로 90% 아래.** Gateway CPU는 거의 같고(114 → 111%), 로그 수집기 Alloy(22 → 14%)와 호스트 쪽이 줄었다.
  - 운영 반영: 실패·느린 요청만 남김(5xx, 끊긴 요청, 200ms 이상). 8차에서 같은 날 끔과 비교.
- **그래프 데이터**(8차, 같은 날·같은 배포, 두 회차 평균 서버 CPU)
  | 목표 | 운영 설정(problems) | 끔 | 차이 |
  |---|---|---|---|
  | 1,000/s | 59.6% | 56.7% | +2.9%p |
  | 1,500/s | 78.5% | 79.1% | −0.5%p |
  | 2,000/s | 90.6% | 90.1% | +0.5%p |
  | 2,500/s | 96.3% | 96.8% | −0.6%p |
- **발표자 메모**: 운영 설정이 끔과 같은 효과를 낸다. 1,000/s 차이는 30초 평균의 흔들림(약 2.5%p)과 크기가 같다. 실패한 요청은 traceId로 로그에서 찾고, 정상 요청은 추적(Zipkin)과 지표로 본다.
- **출처**: [ADR 0052](../decisions/0052-request-log-problems-only-in-operation.md), 7차·8차 절

### 장면 9. 지금 상태와 한계
- **메시지**: 한 대의 한도를 숫자로 말하고, 다음 수단을 비용과 함께 제시한다.
- **보여 줄 것**(8차, 같은 G1 부하)
  | 목표 | 굿풋 | p95 | 서버 CPU |
  |---|---|---|---|
  | 1,000/s | 약 1,000/s | 6~8ms | 약 57~60% |
  | 1,500/s | 약 1,490~1,498/s | 21~30ms | 약 79% |
  | 2,000/s | 약 1,937~1,954/s | 43~44ms | 약 90% |
  | 2,500/s | 약 2,237~2,275/s | 50~54ms | 약 96~97% |
- **누적 참고값**(날이 달라 %로 쓰지 않음): 2,000/s p95 435ms(5차) → 43~44ms(8차), 2,500/s 굿풋 1,608/s(6차 L64) → 약 2,240~2,275/s(8차), OOM 3회 → 0회.
- **한계**
  | 남은 것 | 못 한 이유 |
  |---|---|
  | 과부하(2,500/s)에서 서버 CPU 96~97% | 동시 처리 수 상한은 지연·메모리를 지키지만 CPU를 남기지 않는다(작업 보존형). 4 vCPU 한 대의 한도는 약 2,000~2,350/s(계산값), 목표 3,000/s는 약 5~6코어가 필요하다(계산값) |
  | 장비 분리·수평 확장(Gateway 별도 EC2, 여러 대 + 로드밸런서) | 비용과 일정. 4 vCPU 한 대가 프로젝트 전제(ADR 0047). 한 대 안에서 로드밸런서를 두면 CPU를 나눠 쓸 뿐이다 |
  | 요청률 상한 | 넘친 만큼 굿풋을 버린다 |
  | 요청 로그 공통 필터(서비스 쪽) | 모든 서비스에 걸리는 공유 설정이라 팀 합의(contract 이슈) 필요 |
  | 로그아웃 토큰 확인 메모리 캐시 | 로그아웃 반영 지연, 보안 결정이라 팀 합의 필요 |
- **거부한 대안**: 대기열 폴링 간격을 10 → 30초로 늘리면 폴링이 약 2,780 → 1,000/s로 준다(대기자 3만 명, 계산값). 강민은 "10초도 느리다"며 거부했다. 서버 부하를 사용자 경험으로 떠넘기지 않는다([판단 기록](../ai-judgments/kangmin/2026-11-12-reject-poll-max-30s.md)).

### 장면 10. AI와 결정이 갈린 지점 (AI 설계 검증 로그 후보)
| 시점 | AI 추천 | 강민 결정 | 결과 |
|---|---|---|---|
| 11/11 | CPU 포화는 맨 앞 유입 제한으로 | 거부. 차단기를 먼저 예민하게 실험 | 가설 실패를 숫자(느린 호출 24%)로 닫음 |
| 11/11 | 기본 상한 64 → 128 | 거부. 64 유지 | p95 절반, 굿풋 차이는 반복 변동 안 |
| 11/11 | Zipkin 힙·메모리 증설 | 거부. 스팬 근원(스케줄러 `evalsha`, 스팬의 87%)을 줄임 | 10만 건 차는 시간 약 40분 → 약 5시간(계산값) |
| 11/12 | 폴링 간격 30초 | 거부. 사용자 경험 우선 | 남은 수단을 효율·장비 분리로 좁힘 |
| 11/12 | 리뷰 뒤 머지, 측정은 다음 날 | 거부. 선조치 후보고로 당일 배포·측정 | 8차로 운영 반영 효과를 같은 날 확인 |

판단 기록 전체는 [AI 판단 색인](../ai-judgments/README.md)의 11/9~11/12 행이다.

## 3. 예상 질문
| 질문 | 답의 요지 |
|---|---|
| 차단기를 끄면 되지 않나 | Redis가 정말 멈추면 모든 요청이 시한만큼 기다린다. 끄지 않고 Redis 탓인 실패만 세게 했다 |
| 왜 64인가 | 리틀의 법칙 평균식으로 60~67. 32·128·500과 비교해 p95가 가장 균형 잡힌 값 |
| 상한을 낮추면 CPU가 내려가지 않나 | 32에서도 99%였다. 상한은 자리를 다시 채우는 작업 보존형이라 과부하에서 CPU를 남기지 않는다 |
| 로드밸런서를 두면 되지 않나 | 장비가 한 대면 CPU를 나눠 쓸 뿐이다. 장비를 늘려야 하고, 그것은 비용 문제다 |
| 요청 로그를 줄이면 장애 분석은 | 실패·느린 요청은 그대로 남는다. 정상 요청은 traceId로 Zipkin에서 본다 |
| 측정을 믿을 수 있나 | 발생기 한계를 무효 규칙(빠진 요청 1% 초과, 발생기 유휴 10% 미만)으로 걸렀고, 반복 변동과 날짜 차이를 함께 적었다. 측정 도구 오류(수집기의 PID)도 찾아 고쳤다 |
