# AI가 만든 코드를 어떻게 검증했나 (발표 한 장)

정본: [`docs/guides/ai-code-review.md`](../../guides/ai-code-review.md). 숫자는 2026-11-13 `origin/dev` 기준이다.

## 핵심 메시지
쓰는 AI와 검토하는 AI를 나누고, 지적마다 사람이 판단해 기록했다. 그리고 CI와 배포 환경이 한 번 더 걸렀다.

## 그림(다섯 겹)
```
L0 기준 고정      사람이 SA·ADR·계약을 정한다 ───────────── AI는 그 안에서 구현
L1 자기 검증      실패하는 테스트 → 구현 → 변이 확인 → 실제로 띄워 보기
L2 다른 눈 리뷰   작성(Sonnet·Claude) ≠ 검토(Opus 리뷰어·codex·다른 세션)
                  지적마다 수용·부분 수용·거부·보류 → docs/ai-judgments/
L3 CI 관문        verifyWorkspace(격리 DB·Redis, JUnit 1,833개) · records-check(비밀값·기록)
L4 배포 확인      롤백 · Loki·Grafana·Zipkin · k6 측정 · Slack 경보
```

## 숫자
| 항목 | 값 |
|---|---|
| AI 판단 기록(공통 표) | 170건: 수용 81, 부분 수용 31, **거부 55**, 보류 3 |
| 리뷰·테스트가 잡은 결함 사례 | 10건(Opus 리뷰 4, 그중 1건은 머지 뒤 후속 PR. CI·배포에서 4, 동시성 테스트 1, codex 교차 검토 1) |
| 테스트 | Java `@Test` 1,833개, 시스템 테스트 16개, 프론트 테스트 파일 101개 |
| GitHub PR 리뷰가 남은 PR | 313개 중 12개(한계로 같이 보인다) |

## 보여 줄 사례 두 개
1. **AI가 놓친 라이브러리 기본값을 다른 AI가 소스로 찾음**: 결제 DB가 멈추면 연결 생존 검사가 5초를 기다려 Gateway 3초 시한을 넘겼다. Opus 리뷰가 HikariCP 소스를 읽고 찾았고, 메인이 소스와 변이 확인으로 재현한 뒤 고쳤다. 재확인 3회 모두 2.0초에 503(PR #280).
2. **CI 초록이 운영 정상은 아니었다**: Gateway 생성자에 `@Autowired`가 없어 배포 서버에서 기동 실패. 단위 테스트는 `new`로 만들어 통과했다. 배포 롤백과 Loki로 찾았고, 빈 생성 경로를 보는 테스트를 더해 `@Autowired`를 빼면 실패하는 것을 확인했다(TS-53).

## 한계 (먼저 말한다)
- 리뷰 흔적이 PR보다 판단 기록·PR 본문에 있다. 승인 대신 CI를 관문으로 둔 팀 규칙의 대가다.
- AI 리뷰가 결함을 몇 개 줄였는지는 재지 않았다. 같은 계열 모델끼리 리뷰하면 같은 곳을 놓칠 수 있다.
- 4계층 의존 방향은 자동 검사(ArchUnit 등) 없이 AI 점검과 사람 판단으로 지켰다.

## 예상 질문
- **AI가 만든 테스트로 AI가 만든 코드를 검증하면 의미가 있나?** 테스트가 결함을 실제로 잡는지 변이 확인으로 본다. 고친 코드를 되돌리면 테스트가 실패해야 한다(PR #88 변이 7건, Gateway 동시 처리 상한 변이 6건).
- **리뷰 지적을 거부한 기준은?** 측정 오차 안의 차이, 판정할 수 없는 상태를 전제한 제안, 형식만 느는 분리, 운영과 다른 측정 조건이다. 거부는 모두 개별 기록으로 남겼다.
