# 사례 가안 2. 좌석 동시성: AI의 전제 검토는 테스트로 확인해 받고, 측정 도구 제안은 거부함

가안이다. 판단자(권우)가 내용과 숫자를 확인한 뒤 확정한다. 숫자 출처는 [`concurrency-results.md`](../../design/reservation/concurrency-results.md), [`k6-seathold-story.md`](../../design/reservation/k6-seathold-story.md), TS-65~68이다.

## 1. 해결하려던 작업
좌석 선점의 동시성 결함(1인 매수 한도, 멱등키, 잠금 대기, 만료 경합)을 고치고, 고친 효과와 비용을 숫자로 보이려 했다(ISE-79).

## 2. Claude Code 활용 방식
Linear 이슈와 설계 문서를 주고 단계(S0~S4)와 동시성 시나리오(C1~C7) 설계, 이슈 전제 검토를 맡겼다. 단계별 실측은 별도 worktree에서 하게 했다.

## 3. 채택·수정·기각 이유
| AI 제안 | 판단 | 이유 |
|---|---|---|
| "역순 데드락은 재현되기 어렵다", "멱등 결함의 증상은 500이 아니라 자기 요청 409다" | 수용 | 시나리오로 확인했다. 데드락은 기준선부터 0이었고, 멱등 결함은 자기 요청 409로 나타났다 |
| 같은 JVM 안의 JUnit으로 부하를 근사 측정 | **거부** | Gateway를 거치지 않고, 부하 생성기와 앱이 CPU를 나눠 써서 실제 병목 순위를 말할 수 없다. k6로 다시 재기로 했다 |

## 4. 빌드·테스트·API 검증 결과
- 동시성 시나리오(고치기 전 → 후): C4 같은 사용자 4탭 한도 초과 30/30라운드 → 0, C5 같은 멱등키 3연타의 자기 요청 409 60건 → 0, C6 만료 헛수고 100건 → 0, C3 잠금 대기 p50 2,034ms → 564ms.
- 회귀: `./gradlew :reservation-service:test --rerun` 263건 통과.
- k6(초당 50명 120초): 연타로 자기 요청 409를 받은 사람 2,416명 → 0명, 멀티 탭 한도 초과 293명 → 0명.
- JUnit 근사는 고친 뒤 처리량이 1,125 → 648 req/s로 줄었다고 보였지만(편차 큼), k6로 재니 선점 p95가 400명까지 5ms 이하로 넣기 전과 같았다. 정합성 수정의 비용이 측정에 보이지 않았다.

## 5. 팀이 직접 내린 MSA 설계 판단
잠금 순서를 예매 → 좌석 → 매수로 고정하고, 좌석은 조건부 UPDATE로 DB가 최종 판정하게 했다. 여러 인스턴스의 만료 처리는 `SKIP LOCKED`로 나눠 같은 건을 두 번 집지 않게 했다.

## 핵심 메시지
AI가 맞게 짚은 전제는 테스트로 확인했고, 측정 도구의 한계는 사람이 막았다. 그 결과 "정합성을 고치면 느려진다"는 걱정이 측정으로 지워졌다.

## 예상 질문
- **잠금 대기 목표를 1,000ms에서 1,500ms로 고친 것(TS-67)은 결과에 목표를 맞춘 것 아닌가?** 고친 뒤 최대값이 1,060~1,305ms였다. `lock_timeout`(500ms)은 문장 전체가 아니라 잠금 시도마다 걸리므로, 목표를 설정값이 아니라 그 동작에서 다시 끌어냈다는 근거를 같이 보인다(TS-67 "배운 점"). k6 측정은 로컬 PC에서 했다.
