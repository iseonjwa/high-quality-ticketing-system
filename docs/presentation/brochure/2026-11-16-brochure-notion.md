# 이선좌 : 빠른 손 아니어도 추첨으로, 선착순도 같은 좌석은 딱 한 명

〔그림: 2026-11-16-cover-banner.png〕

## 서비스/프로젝트 소개

이선좌는 기획사에게 위탁받아 콘서트 티켓을 파는 판매 대행 서비스입니다. 티켓 오픈 순간 수많은 사람이 같은 좌석을 노리는 상황을 서버가 어떻게 견디는지, 그리고 빠른 손이 아니어도 기회가 있는 예매를 어떻게 만들지에 집중했습니다.

| 문제 | 해법 | 결과 |
|---|---|---|
| 오픈 정각 접속 폭주 | 대기열(Redis Lua 번호표) + 초당 일정 인원 입장 + Gateway 맨 앞 동시 처리 상한 | 순번 조회 굿풋 1,304 → 1,696/s, p95 571 → 87ms(초당 2,000건, 상한 64, 회차마다 1회·반복 차이 약 5%) |
| 같은 좌석 동시 경합 | 좌석 ID 순 조건부 UPDATE로 일괄 선점, DB 부분 유니크 인덱스, 구역만 고르면 자동배정 | 모든 측정에서 중복 판매 0건. 별도로 사전 거절·직렬화 재사용·예열 묶음으로 선점 p95 219 → 38ms(각 2회 평균) |
| 결제와 예매의 불일치 | Kafka + Outbox + 멱등 처리, PG 결과를 모르면 UNKNOWN으로 재조회, 거절되면 보상 | 결제 거절 뒤 약 0.14초에 좌석 반환(배포 서버 시연 1건) |
| 빠른 손·매크로만 유리함 | 추첨 배분 + 빌링키 자동결제, 응모 1인 1~2매·회차 합계 4매 제한 | 당첨 약 2,000건 자동결제가 추첨 뒤 약 3분 50초 시점에 35%(전 1회) → 100%(후 2회) 완료, 처리 속도 약 2.9배 |

## 서비스/프로젝트 목표

목표 처리량을 숫자 하나로 정하지 않고, "틀리지 않는 것"을 먼저 고정한 뒤 한계를 측정으로 찾았습니다. 못 지킨 목표도 그대로 적습니다.

| 목표 | 기준 | 결과 | 판정 |
|---|---|---|---|
| 같은 좌석 동시 요청 | 1건만 성공, 중복 판매 0 | 모든 측정에서 중복 0, 확정 = 결제 승인 | 달성 |
| 추첨 자동결제 | 추첨 뒤 10분 안 95% | 100%(2회) | 달성 |
| 응모 마감 직전 몰림 | 초당 100건 p95 300ms 이하 | p95 5.0ms, 초당 800까지 503 0(데운 서버 기준) | 달성 |
| 추첨 중 일반 선점 간섭 | 선점 p95 증가 20% 이하 | +90%(11.06 → 21.0ms, 1회) | **미달** |
| 오픈 순간 대기열 진입 | 처리 못 한 오류 0(k6 임계값) | 현실 도착(오픈 직후 몰림)에서 남은 상한 거절의 약 87~88%가 대기열 진입. 균일 도착은 개선 뒤 임계값 통과(1회) | **미해결** |

- 오류 정의: 409(이미 선택된 좌석)는 정상 거절, 5xx·타임아웃만 오류

## 인프라 설계도

〔그림: 2026-11-11-system-architecture.png〕

- 요청은 nginx → API Gateway 한 곳으로 들어오고, Gateway가 동시 처리 상한 → JWT 검증 → 로그아웃 토큰 조회 → 입장 토큰 검증을 차례로 합니다
- 서비스: User, Reservation(공연·대기열·선점·예매·추첨 모듈러 모놀리스), Payment, Assistant(AI 상담), Mock PG
- 예매와 결제는 Kafka 토픽 `payment.command`·`payment.result`와 Outbox로 주고받고, 서비스마다 DB가 따로입니다
- CI/CD: GitHub Actions가 main 머지 때 이미지 9개를 커밋 SHA 태그로 GHCR에 올림 → Jenkins(별도 EC2)가 main을 폴링해 이미지가 올라오길 기다린 뒤 배포 EC2에 SSH로 `deploy.sh`(이미지 받기 → 헬스 대기 → 스모크) → 실패하면 직전 성공 커밋으로 되돌림, 성공하면 예열 → 시작·진행·결과를 슬랙에 알림
- 관측: Prometheus·Grafana, Zipkin, Loki·Alloy, Alertmanager → 슬랙
- 그림 기준일 11/11(자동배정·HTTPS 반영 전)

## 주요 기능

1. **대기열과 입장 토큰**: 계정당 1자리, Redis Lua로 번호표 발급, 초당 50명 입장. 입장 토큰은 좌석 선점에 성공한 순간 소모(재사용하면 403)
2. **좌석 선점·자동배정**: 매수 확인 → 좌석 ID 오름차순 조건부 UPDATE(전부 아니면 전부). 구역·매수만 고르면 서버가 `SKIP LOCKED`로 빈 좌석을 골라 줌. 5분 뒤 만료 스케줄러가 반환
3. **예매↔결제 SAGA(코레오그래피)**: 결제 거절 → Outbox → Kafka → 예매 `HELD → RELEASED`, 좌석·매수 원복. 결과: 거절 뒤 약 0.14초에 좌석 반환(배포 서버 시연 1건)
4. **결제 장애 대응**: PG는 DB 트랜잭션 밖에서 호출. 결과를 모르면 UNKNOWN → 간격을 늘리며 재조회 → 끝내 모르면 수동 확인. 예매 만료 뒤 승인되면 자동 환불
5. **추첨 자동결제**: 응모(1인 1응모) + 빌링키 등록 → 시드를 기록한 해시 정렬 추첨 → 자동 배정·자동결제 → 실패 시 예비자 승계. 결과: 10분 안 100%
6. **내부 AI 상담**: 규정 문서 키워드 검색 + Claude 출처 인용 답변. API 키가 없거나 장애면 검색 결과만 보여 줌

## 기술적 의사결정

### ① Gateway 과부하: 차단기와 bulkhead의 역할을 나누고, 과부하는 맨 앞 동시 처리 상한으로

- 배경: bulkhead 거절이 차단기 실패로 세어져 Redis가 정상인데도 차단기가 열렸습니다
- 선택지: 맨 앞 동시 처리 상한(AI 추천) / 기존 차단기를 예민하게 / 입구 요청률 제한
- 선택과 이유: 차단기는 Redis 장애만 세게 나눈 뒤, AI 추천은 일단 거부하고 차단기가 포화 전에 열리는지 먼저 실험했습니다. 열리지 않아(느린 호출 최대 24%, 기준 80%) AI가 낸 동시 처리 상한(64)을 받아들였고, 128 제안은 굿풋 차이 1.5%가 반복 변동(5%) 안이고 p95가 약 두 배라 거부했습니다
- 감수한 점: 과부하가 차단기 지표에 보이지 않아 거절 비율 경보 2개를 따로 둡니다. 섞인 흐름에서는 정상 요청도 상한에 걸립니다
- 다시 볼 조건: 피크 경보가 오픈마다 울리면 입구 요청률 제한(인스턴스 로컬)을 넣습니다. 장비나 Gateway 수가 바뀌면 리틀의 법칙으로 값을 다시 냅니다

### ② 입장 토큰은 좌석 선점에 성공한 순간 소모

- 배경: 10분짜리 무상태 토큰이라 "선점 → 만료 → 다시 선점"으로 좌석을 묶어 둘 수 있었습니다
- 선택지: 선점 성공 시 소모(채택, 팀 회의) / 선점 시 소모 + 1회 복원(AI 추천) / 결제 완료 시 소모 / 10분 자연 만료
- 선택과 이유: "입장 한 번 = 선점 한 번"으로 막고, 소모 확인은 DB 고유 인덱스가 해 Gateway 경로 비용이 늘지 않습니다
- 감수한 점: 결제에 실패한 사람은 대기열을 다시 섭니다
- 다시 볼 조건: 결제 시간 초과로 다시 줄을 서는 사람이 많다는 지표가 나오면 1회 복원안을 다시 봅니다

### ③ 예매↔결제는 오케스트레이션 대신 코레오그래피 SAGA

- 선택지: Reservation이 조정자가 되는 오케스트레이션(AI 권고) / 이벤트 코레오그래피
- 선택과 이유: 일반 예매 참여자가 예매·결제 2개라 결과 이벤트 구독으로 충분합니다. 결제 요청이 예매보다 먼저 오는 경합은 선점 뒤 발급하는 서명 결제 토큰으로 막습니다
- 감수한 점: 보상은 Kafka 이벤트로 따로 일어나 결제 트레이스에 이어 보이지 않아서, 예매 상태 이력(DB)과 이벤트 흐름도로 보완합니다
- 결과: 결제 거절 뒤 약 0.14초에 좌석 반환(배포 서버 시연 1건)
- 다시 볼 조건: 〔팀 확인: 원문에 없음〕

### ④ 자동결제는 소비자를 늘리고 전용 PG 허가 그룹을 둠

- 배경: 자동결제 10분 완료가 약 93%(3회 92.4~93.4%)로 기준(95%)에 못 미쳤습니다
- 선택지: 소비자만 증설 / 허가만 증설 / 전용 그룹만 / 소비자 3 + 전용 그룹 3(채택). 앞서 10/30에는 처음부터 전용 그룹을 두자는 AI 추천을 거부하고 공유로 시작해 문제부터 재현했습니다
- 선택과 이유: PG 지연 스윕으로 원인이 "소비자 1개의 직렬 대기"임을 확정했습니다(남은 허가 9/10). 결제 명령 파티션·소비자 3과 자동결제 전용 허가 그룹(3)을 함께 두었습니다. 일반 결제 허가 10 → 30은 결제 담당이 입장 속도 초당 50에 맞춰 정했습니다
- 감수한 점: PG 최대 동시 호출 수가 35로 늘고, 파티션을 늘리는 순간 결제 → 환불 순서가 뒤집힐 수 있어 랙 0일 때만 늘립니다
- 결과: 추첨 뒤 약 3분 50초에 전원 결제 완료(같은 시점 35% → 100%), 결제 완료 p95 약 613 → 208초(3.0배 빠름), 겹친 일반 결제 503 1,424건 → 0건. 판정 기준인 10분 안 완료는 약 93 → 100%(전 3회·후 2회, 503은 각 1회)
- 다시 볼 조건: 재측정에서 95%를 못 지키면 소비자·전용 허가를 4~6으로 올립니다. 환불이 자동결제 뒤에 밀리면 전용 토픽을 더합니다

### ⑤ AI 상담은 별도 서비스, 벡터 DB 대신 키워드 검색 + 출처 인용

- 선택지: pgvector RAG / LLM 없는 FAQ / 기존 서비스에 포함
- 선택과 이유: 예매·결제와 장애를 격리하고, API 키가 없어도 검색 모드로 동작합니다. 규정 문서가 수천 토큰이라 키워드 검색으로 충분하고, 벡터 DB를 쓰면 임베딩 키·메모리(+512MB)·구현 4~6일이 더 듭니다
- 감수한 점: 외부 API 의존과 비용(질문당 약 $0.0005, 추정)
- 다시 볼 조건: 문서가 수만 토큰 이상으로 늘거나 공연·내 예매 같은 동적 데이터를 넣게 되면 벡터 검색을 다시 봅니다

## 트러블슈팅

성능 전후 비교의 배포 수치는 **배포 EC2와 같은 VPC의 별도 부하 발생기**에서 쟀습니다. 좌석 선점 단계별 개선·동시성 검증·자동배정 쿼리 분석·추첨 실행 시간은 로컬 PC 측정입니다. 전후 비교는 같은 장비·같은 데이터·같은 부하로 맞췄습니다.

| 항목 | 값 |
|---|---|

## AI 활용 성과 및 회고

AI를 코드 생성기보다 "반대 의견을 내는 검토자"로 썼습니다. AI 제안마다 수용·거부를 기록했고, 성능 판단은 측정으로 닫았습니다. 아래 수치는 팀 측정 결과이고, AI는 제안과 구현을 맡았으며 채택은 측정으로 정했습니다.

| 지표 | 값 |
|---|---|
| AI 판단 기록(팀 공통 표) | 〔팀 확인: 등록 날 다시 셈〕 207건: 수용 98, 부분 수용 37, 거부 67, 보류 5(11/16 dev 기준) |
| 설계 검증 로그 | 11개 항목, 거부 5건(Queue 서비스 분리, 오케스트레이션, 응모 동기 처리 등), 부분 거부 2건 |

| AI 제안 | 우리 판단 | 근거 | 결과 |
|---|---|---|---|
| Gateway 맨 앞 동시 처리 상한(전역 유입 제한) | 일단 거부 → 차단기 먼저 실험 → 실패 → AI 추천 수용, 128은 거부 | 차단기가 포화 전에 열린다는 가설을 숫자로 닫으려고. 128은 굿풋 차이가 반복 변동 안 | 굿풋 1,304 → 1,696/s, p95 571 → 87ms |
| JUnit으로 부하 근사 | 거부 → k6로 측정 | Gateway를 거치지 않아 실제 부하가 아님 | "정합성 수정은 비용 없이 들어갔다"로 결론을 뒤집음(400명까지 p95 5ms 이하) |
| 자동결제 전용 허가 그룹을 처음부터 | 거부 → 공유로 시작해 문제를 재현 | 먼저 막으면 측정할 간섭이 없음 | 원인이 소비자 1개임을 확정 → 약 3분 50초에 전원 결제(같은 시점 35% → 100%), p95 3.0배 빠름 |
| 추첨 간섭 미달을 저트래픽 시간대 정책으로 갈음 | 거부 → 속도 상한 + 재측정 | 정한 기준을 정책으로 덮지 않음 | 재측정 전 |
| 개선 묶음 구현(사전 거절·직렬화 재사용·Kafka 헬스체크·예열 등) | 수용 → 같은 조건 2회 측정으로 비교 | 측정으로 채택 여부를 정함 | 선점 p95 219 → 38ms(2회 평균) |
