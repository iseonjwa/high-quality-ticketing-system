# 브로셔 재디자인 설계 (메인은 이미지, 상세는 하위 페이지)

- 날짜: 2026-11-16. 제출 11/18, 발표 11/19.
- 목표: 다른 조 상위 카드처럼 메인 페이지를 "그림과 큰 숫자"로 한눈에 읽히게 하고, 긴 글은 하위 페이지(서비스별 이야기 5개)로 옮긴다. 개선 폭은 "몇 배"로 크게 보이되, 숫자마다 조건을 작은 글씨로 단다(과장 금지는 그대로).
- 상태: 진행 중(11/16 강민 승인: 6절 추천안 그대로). 전수조사 5개 영역을 Sonnet 5.5로 동시 진행. 지시 방법과 심사 채점표는 [`2026-11-16-prompt-guide.md`](2026-11-16-prompt-guide.md).

## 1. 메인 페이지 새 배치 (11/16 강민: 글은 최소, 하위 페이지 썸네일 카드 위주로 열거)

다른 조 상위 브로셔처럼 메인은 "큰 그림 몇 장 + 썸네일 카드 묶음"으로 읽히게 한다. 템플릿 항목 제목은 남기되, 항목마다 본문은 1줄 이하이고 내용은 카드를 눌러 들어간 하위 페이지에서 펼친다.

| 메인 순서 | 템플릿 항목 | 메인에 놓는 것 | 카드(하위 페이지)로 보내는 것 |
|---|---|---|---|
| 0 | 커버·아이콘 | 커버 배너(1500×688), 앱 아이콘 | — |
| 1 | 한 줄 소개 | 한 줄 + 메인 이미지(커버 배너) | — |
| 2 | 소개·목표 | ★ **숫자로 보는 이선좌**(KPI 이미지 1장) | 카드 「서비스 소개와 목표 판정」 |
| 3 | 인프라 설계도 | 구조도 1장 | 카드 「인프라·배포 파이프라인」 |
| 4 | 주요 기능 | ★ 화면 흐름 1장(대기열 → 자동배정 → 결제 → 당첨) | 카드 「기능 상세」 |
| 5 | 적용 기술 | ★ 기술 로고 띠 1장 | 카드 「기술 선택 이유」 |
| 6 | 기술적 의사결정 | 카드 묶음(결정 5장, 썸네일마다 결정 한 줄) | 결정별 하위 페이지 |
| 7 | 트러블슈팅 | 카드 묶음(서비스별 이야기 5장, 썸네일에 대표 배수) + ★ 하이라이트 3장 | 서비스별 하위 페이지 |
| 8 | 알려진 한계 | 1줄 | 카드 「알려진 문제와 넘지 못한 한계」 |
| 9 | CONTRIBUTORS | 표(템플릿 요구) | — |
| 10 | AI 활용 | ★ 인포그래픽 1장 | 카드 「AI 판단 기록과 대표 사례」 |

- 카드 묶음은 Notion 인라인 갤러리 데이터베이스(카드 미리보기 = 페이지 커버). 카드 썸네일은 서비스별 이야기와 같은 틀(제목·한 줄·대표 숫자)로 만든다.
- 하위 페이지는 "읽는 문서"가 아니라 "펼쳐 보는 보고서": 맨 위에 그림 1장과 핵심 숫자 3개, 그 아래 단계 표·근거 그림·한계·예상 질문.

## 2. "몇 배"로 보일 숫자 후보 (원문 값으로 계산함)

전후가 같은 조건인 것만 고른다. 배수는 원문 값을 나눈 계산값이다.

| 후보 | 전 → 후 | 배수 | 조건(작은 글씨) | 근거 |
|---|---|---|---|---|
| Gateway 응답 p95 | 571 → 87ms | **6.6배 빠름** | 순번 조회 초당 2,000건, 상한 64, 1회 | gateway-overload-one-page |
| 좌석 선점 p95 | 219 → 38ms | **5.8배 빠름** | 3,000명 현실 도착, 각 2회 평균 | bottleneck-improvement-study 7-3 |
| 자동결제 같은 시각 완료율 | 35% → 100% | **약 3분 50초에 전부** | 전 1회 진행 조회, 후 2회 | numbers-and-measurement 3-3·3-5 |
| 자동결제 완료 p95 | 613 → 208초 | **3.0배 빠름** | 당첨 약 2,000건, 전 3회·후 2회 평균 | 같은 문서 |
| 일반 결제 승인 상한 | 초당 31.2 → 91.5 | **2.9배** | PG 300ms, 각 1회 | open-peak-scenarios PAY1 |
| 자동배정 DB CPU | 280% → 18.2% | **15배 감소** | 인덱스 누락 → 수정, 1회 | TS-72 |
| Kafka CPU 최대 | 228.8% → 15.8% | **14.5배 감소** | 헬스체크 교체 전후 | bottleneck-improvement-study 7-3 |
| 매진 직후 409 처리 시간 | −95% | **20배 빠름** | 320명, 측정 브랜치 1회 | bottleneck-improvement-study |
| 좌석 응답 직렬화 | 1,495 → 110ms | 13.6배 | **로컬 벤치 참고값**(배포 아님) | 같은 문서 |
| Gateway 강제 종료 | 3회 → 0회 | — | 메모리 1,024MiB + 상한 64 | TS-58 |
| DB 커넥션 대기 | 12~14 → 0 | — | 3,000명, 각 2회 | 7-3 |
| 중복 판매 | 0건 | — | 모든 측정 | 7-3, 3-6, F1 |

- 피할 것: 굿풋 1.3배처럼 작아 보이는 것은 하이라이트에서 빼고 하위 페이지에 둔다. 로컬 벤치(직렬화, Kafka 헬스체크 200~400배)는 대표 숫자로 쓰지 않는다.
- **메모리 숫자가 비어 있다.** "메모리 사용률을 얼마나 줄였나"는 원문에 감소율로 정리된 값이 없다. 후보는 ① Gateway 상한 전후 힙 피크(상한 값별 메모리 그림 `2026-11-13-safety-net-limit-summary`의 원자료), ② Gateway 강제 종료 3 → 0, ③ payment 메모리 부족 종료 하루 5회 → 수정 뒤 횟수, ④ Prometheus 카디널리티 71만으로 인한 OOM 이후 조치. ①·③은 원자료를 찾아야 한다(5절 P1).

## 3. 전후 하이라이트 이미지 3장 (드라마틱하게, 그러나 정직하게)

한 장 = 큰 배수 1개 + 전후 막대 또는 시계열 2개 + 근거 화면(Grafana) 작은 삽입 + 조건 한 줄.

| 장 | 큰 글씨 | 그림 | 근거 화면 |
|---|---|---|---|
| A. 입구 | "응답 6.6배 빠르게, 강제 종료 0회" | 상한 전후 p95 막대 + 처리 중 요청 시계열 | `performance/img/2026-11-15/inflight-122-123.png`, `2026-11-13-safety-net-limit-inflight.png` |
| B. 좌석 | "선점 5.8배 빠르게, DB 대기 0" | v1 대 v2 막대(있음) + DB 커넥션 대기 시계열 | `hikari-pending-122-123.png`, `host-cpu-122-123.png` |
| C. 추첨 | "3분 50초면 전원 결제 끝" | 같은 시각 누적 완료 곡선 전후 겹치기(전: 진행 조회 점, 후: 버킷) | `l2b-billing-vs-approve.png` |

- C의 누적 곡선은 원문 진행 조회 점(전)과 히스토그램 버킷(후)으로 그릴 수 있다. 같은 축 위에 두면 "전은 10분이 지나도 안 끝나고, 후는 3분대에 끝난다"가 그림으로 보인다.
- 근거 화면이 없는 숫자는 "측정값으로 그린 그림"이라고 각주에 밝힌다.

## 4. 이미지 품질과 모델 역할 분담

이미지는 지금처럼 코드(SVG)로 그린다. 숫자를 정확히 넣으려면 코드 렌더링이 맞고, 생성형 이미지 모델은 숫자·한글을 틀리게 그리기 쉽다. 품질이 아쉬운 부분은 "누가 그리느냐"와 "디자인 규칙"으로 푼다.

| 역할 | 맡길 곳 | 이유 | 산출물 |
|---|---|---|---|
| 숫자 확정·검수 | Sonnet 5.5 하위 에이전트(값싼 반복 대조) | 원문 대조는 반복 작업이고 지금까지 검수가 잘 잡았다 | 숫자 표, 문제 표 |
| 디자인 규칙 1장 | 메인 세션 | 색·글꼴·크기·여백·카드 규격을 먼저 고정해야 이미지가 한 벌로 보인다 | `design-kit.md` + 공통 SVG 부품 |
| 이미지 시안 | **모델 둘에게 같은 지시로 시안을 받아 비교**: Fable 5.2 하위 에이전트와 Opus 5.5 하위 에이전트(또는 Sonnet 5.5) | Opus 결과가 깔끔하지 않다는 판단이 있으니, 같은 지시서로 다른 모델 시안을 나란히 놓고 고른다 | 장마다 시안 2개 PNG |
| 배경 일러스트(선택) | 외부 이미지 모델(ChatGPT 이미지 등) | 무대 조명·관객 같은 분위기 그림만. 숫자·글자는 넣지 않고 그 위에 코드로 얹는다 | 배경 PNG |
| 레이아웃 미리보기(선택) | claude.ai 디자인 아티팩트 | Notion에 붙이기 전에 메인 페이지 전체를 한 화면에서 본다 | 미리보기 링크 |
| 최종 조립 | 메인 세션 | 숫자 출처와 하위 페이지 연결을 한곳에서 책임진다 | notion-paste.html |

지시서 형식(모델이 바뀌어도 같게): 목적 한 줄, 크기, 디자인 규칙 경로, 넣을 숫자와 조건(그대로 복사, 바꾸지 말 것), 근거 화면 경로, 금지(숫자 반올림·새 숫자·영문 문구), 산출 경로. 하위 에이전트 지시는 한국어 출력 규칙을 넣는다.

## 5. 작업 순서 (단계마다 확인 후 진행)

| 단계 | 할 일 | 담당 | 끝난 기준 |
|---|---|---|---|
| P0 | 6절 결정 | 강민 | 결정 기록 |
| P1 | 전수조사 5개 영역(A 발표·결정·TS, B 설계·SA·가이드, C AI 판단·학습, D 코드·측정·PR, E 개인 기록·세션·Linear) → 사실 원장 `census/` + 히어로 숫자·메모리 숫자 확정 | Sonnet 5.5 조사 에이전트 5개 | 원장 5개 + 통합 원장 |
| P2 | 디자인 규칙 1장 + 공통 부품 | 메인 | 규칙 문서, 견본 1장 |
| P3 | 이미지 7장 시안(KPI, 목표 판정, 화면 흐름, 기술 띠, 결정 카드, 하이라이트 A·B·C, AI 인포그래픽) | 시안 에이전트 2개(모델 비교) | 장마다 시안 2개 |
| P4 | 시안 고르기 → 다듬기 | 강민 → 메인 | 최종 PNG·SVG |
| P5 | 메인 본문 글 최소화, 상세는 하위 페이지로 이동 | 메인 | notion.md 새 판 |
| P6 | 숫자 검수 + 카드 크기 가독성 검수 | Sonnet 검수 에이전트 | 문제 0 또는 반영 |
| 상시 | **심사위원 에이전트**: P1 원장, P3 시안, P5 본문마다 만든 쪽과 다른 모델로 새로 띄워 채점표(prompt-guide 3절)로 심사 → 미달이면 고쳐 다시 심사(최대 3회) | Opus 5.5 또는 Fable 5.2(만든 쪽과 다르게) | 모든 기준 4점 이상, 정직성 5점 |
| P7 | 붙여 넣기 HTML 재생성 | 메인 | notion-paste.html |

예상: P1~P3를 병렬로 돌리면 반나절 안. 11/17 안에 P7까지 끝내야 11/18 제출이 여유 있다(계산이 아니라 추정).

## 6. 정할 것

| # | 질문 | 선택지 | 추천 |
|---|---|---|---|
| 1 | 이미지 시안을 어느 모델로 비교할까 | Fable 5.2 대 Opus 5.5 / Fable 5.2 대 Sonnet 5.5 / Fable 5.2 하나만 | Fable 대 Sonnet: Opus가 이미 아쉬웠으니 다른 둘을 비교 |
| 2 | 외부 이미지 모델로 배경 일러스트를 쓸까 | 쓴다(숫자 없는 배경만) / 안 쓴다 | 안 쓴다(시간·저작권·톤 맞추기 비용). 코드 그림으로 충분 |
| 3 | 근거 화면을 새로 찍을까 | 기존 Grafana 캡처만 / 배포 서버에서 새로 캡처 | 기존만. 새 캡처는 측정 모드가 필요하고 서버가 다시 뜬다 |
| 4 | 메모리 숫자가 원자료에 없으면 | 하이라이트에서 빼고 "강제 종료 3 → 0"만 / 원자료를 Prometheus에서 다시 뽑기 | 먼저 원자료 찾기(P1), 없으면 강제 종료 0회로 |
| 5 | 결정 카드 5장을 이미지로 할까, Notion 토글 글로 둘까 | 이미지 / 토글 | 이미지(한 줄씩) + 상세는 하위 페이지 |
