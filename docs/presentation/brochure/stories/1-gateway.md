# 01 Gateway: 입구가 먼저 무너졌다

> 4 vCPU 장비 한 대에서 모든 인증 요청이 Gateway 한 곳을 지납니다. 몰림이 오면 Gateway가 먼저 무너졌고, 고칠 때마다 무너지는 모양이 바뀌었습니다(차단기 오탐 → CPU 포화 → 메모리 부족 → 정상 요청 거절). 넘친 요청을 버리는 장치는 CPU를 만들어 내지 못한다는 것을 측정으로 배웠습니다.

## 측정 조건

| 항목 | 값 |
|---|---|
| 서버 | 배포 EC2 `m7i.xlarge`(4 vCPU) 1대, 컨테이너 21개 |
| 부하 발생기 | 같은 VPC의 별도 EC2, k6(발생기 사양은 1차 기록 기준 `c6i.xlarge`) |
| 시나리오 | 대기열 순번 조회 API(G1, 대기자 10,000명), 대기열·좌석·결제가 섞인 흐름(O1, 3,000명) |
| 굿풋 | 200 응답이면서 200ms 안에 끝난 요청/초. 느린 성공을 성공으로 세지 않으려고 처리량 대신 쓴다 |
| 반복 | 회차마다 1회(같은 값 반복 차이 약 5%). 11/16 비교는 각 2회 |

## 어떻게 발전했나

| 단계 | 처음 가정 | 시도와 측정 | 결과와 다음 행동 |
|---|---|---|---|
| 1. 차단기가 Redis 정상인데 열림(11/9~10) | 벌크헤드 25가 부족하다 / 느린 호출 50ms가 너무 낮다 | 벌크헤드·느린 호출 값을 바꿔 다시 잼. 데운 초당 2,000건에서 201이 428건, 503이 19,573건 | **두 가설 모두 틀림.** 차단기를 연 원인 대부분이 벌크헤드 거절이었다(거절이 차단기 안쪽에서 실패로 세어짐) |
| 2. "무엇을 실패로 세나"를 바꿈(11/10) | 집계 기준만 고치면 오탐이 사라진다 | 벌크헤드 거절을 차단기 집계에서 빼고, 창 10초·최소 500건, 벌크헤드 50 | 초당 3,000건까지 차단기 닫힘(거절 16,024건 모두 `ignored`). **성공했지만 한도가 CPU로 옮겨 감**(초당 2,300~2,470에서 멈춤, 서버 CPU 99%) → ADR 0050 |
| 3. 차단기를 예민하게(11/11) | AI는 맨 앞의 전역 유입 제한(동시 처리 수 기반)을 추천. 차단기가 포화 전에 열릴 수 있다고 보고 **AI 추천을 거부**하고 먼저 실험 | 느린 호출 기준 100 → 20ms | **가설 실패.** 열림 0회, 느린 호출 비율 최대 24%(기준 80%). 기다림은 차단기가 재는 구간 밖에 있었다(차단기 구간 10.7~16.5ms, 사용자 p95 878ms) |
| 4. 메모리만 늘림(11/11) | 메모리를 늘리면 강제 종료가 사라진다 | 768 → 1,024MiB | 강제 종료 3회 → 0회. 대신 초당 2,000건 p95 435 → 752ms. **"죽는 실패"가 "느려지는 실패"로 바뀜** |
| 5. 맨 앞 동시 처리 상한(11/11) | AI 추천안으로 돌아감. 리틀의 법칙으로 낸 60~67 근처가 맞다 | 상한 32·64·128·500을 초당 2,000건에서 비교 | 상한 500 굿풋 1,304/s·p95 571ms → **64에서 1,696/s·87ms**. 128 제안은 굿풋 차이 1.5%가 반복 변동 안이고 p95가 약 두 배(162ms)라 **거부** |
| 6. 거절 위치를 앞으로(11/11) | 거절도 관측·로그·라우트 매칭 비용을 낸다 | 거절을 HttpHandler 데코레이터로 옮김 | 초당 2,500건 굿풋 1,608 → 1,814/s, p95 104 → 78ms. 거절 한 건 비용은 받은 요청의 2~8%(별도 측정) |
| 7. 요청 로그(11/11~12) | 로그 한 줄이 비용이다 | 로그를 끈 측정 → 운영은 문제 요청만 남기는 모드 | 로그를 끈 측정에서 초당 1,000건 서버 CPU 78 → 66%, 초당 2,500건 굿풋 2,122/s. 줄어든 곳은 Gateway 밖(로그 수집기)이었다. 운영 모드는 11/12 별도 측정에서 끈 것과 비슷 |
| 8. 섞인 흐름에서 다시 봄(11/13~15) | 64는 순번 조회 한 API로 정한 값이다. 섞이면 맞나 | 3,000명 섞인 흐름에서 64 대 1000 | 64: 확정 1,973건, 503 1,150건이 모두 상한 거절(서버 오류 0). 1000: 확정 +9.0%지만 선점 p95 192 → 277ms, DB 커넥션 대기 10 → 22. **상한은 근본 조치가 아니라 줄을 어디에 세울지 고르는 손잡이** → 운영은 64 유지 |
| 9. 뒤쪽을 고친 뒤(11/16) | 뒤쪽이 빨라지면 입구 거절도 준다 | 개선 전 v1 대 개선 후 v2, 각 2회 | 남은 상한 거절의 약 87~88%가 오픈 순간의 대기열 진입 요청. 같은 코드에서 진입을 오픈 +1~11초에 고르게 편 실행(1회, 오픈 전 상세 조회 몰림 없음)은 상한 거절 0. **양보다 시점의 문제로 봄** |

## 감수한 것
- 넘친 요청은 503(Retry-After 3초)을 받습니다. 섞인 흐름에서는 좌석 조회·선점 요청도 상한에 걸립니다.
- 맨 앞에서 거절한 요청은 요청 로그와 추적 ID가 없고, 거절 수는 전용 지표로만 셉니다.
- 운영 로그는 실패·느린 요청만 남겨, 정상 요청은 추적 ID와 지표로만 봅니다.
- 차단기를 Redis 장애 전용으로 나눠, Redis가 실제로 느려질 때 감지가 늦어질 수 있습니다.
- 서버 부하를 줄이려고 순번 조회 간격을 30초로 늘리자는 AI 제안은 사용자 대기를 늘린다고 보고 거부했습니다. 그래서 요청 수를 줄이는 수단 하나를 쓰지 않았습니다.

## 알려진 문제와 개선 방향
| 문제 | 개선 방향(설계만, 측정 전) |
|---|---|
| 오픈 순간 대기열 진입이 상한에 막힘 | 오픈 전 사전 대기 등록, 진입 경로 분리, 연타 진입 합치기(팀 논의 중) |
| 상한 하나가 모든 경로에 같이 걸림 | 경로 묶음별·가중치 상한, 적응형 상한(AIMD 등) |
| 상한을 올리면 거절이 인증 Redis 벌크헤드로 옮겨 감 | 블랙리스트 로컬 캐시(로그아웃 즉시 반영 규칙 보완 필요) |
| 5초 표본 지표가 순간 최댓값을 놓침(1초 최대 216 대 5초 표본 89) | 구간 최댓값 게이지, 경로 태그 |
| 좌석 응답(약 845KB)이 압축 없이 Gateway를 지남 | 응답 축소·압축, 공연 상세 앞단 캐시(요청의 73.8%) |

## 넘지 못한 한계
- **장비 한 대**: 상한은 처리량을 늘리지 못하고 줄 세울 위치만 바꿉니다. 천장을 올리는 장비 분리·증설은 비용과 마감 때문에 미뤘습니다.
- **반복 부족**: 대부분 1회 측정입니다. 같은 설정(상한 1000)의 두 실행이 크게 달라(확정 대기 p95 1.84초 대 10.96초) 방향만 말합니다. 예열 뒤 다시 재지 못했습니다.
- **경로별·적응형 상한**: 새 의존성과 결정이 필요하고, 경로별 계산이 아직 없어 적용하지 못했습니다.

## 예상 질문
- **CPU가 여전히 98%인데 개선인가요?** 상한은 빈자리를 바로 다음 요청으로 채워 CPU를 남기지 않습니다. 대신 같은 CPU로 200ms 안에 끝나는 요청이 늘었습니다. CPU를 낮춘 것은 Gateway 밖의 로그 비용이었습니다.
- **왜 64인가요?** 리틀의 법칙으로 낸 60~67에서 골랐고, 128과의 굿풋 차이는 반복 변동 안이었으며 p95는 절반이었습니다. 다만 섞인 흐름에서는 정상 요청도 거절해, 값보다 "어디에 줄을 세울지"의 문제로 봅니다.
- **AI 추천을 거부한 이유는요?** 차단기 시간에 Gateway 대기가 섞인다는 측정 근거가 있어 먼저 실험했습니다. 실험 한 번으로 가설을 닫았고, 결론은 AI 추천과 같았지만 근거가 숫자가 됐습니다.
