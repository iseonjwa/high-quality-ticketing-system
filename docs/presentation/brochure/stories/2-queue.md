# 02 대기열: 줄은 공정하게, 순번 조회는 싸게

> 오픈 순간 몰리는 사람을 공정하게 줄 세우고, 뒤쪽이 감당할 속도로만 들여보내야 합니다. 동시에 가장 많이 불리는 순번 조회는 싸게 유지해야 합니다. 설계 단계에서 빈틈을 하나씩 막았고, 측정에서는 "대기열까지 온 요청은 정확했지만 줄에 들어오기 전 입구가 막힌다"는 것을 확인했습니다.

## 어떻게 발전했나

| 단계 | 고민 | 선택 | 결과와 대가 |
|---|---|---|---|
| 1. 순서 기준(10/26) | 진입 시각을 점수로 쓰면 같은 밀리초에서 순서를 못 가리고, 서버마다 시계가 다르다(대기열 담당 지적) | Redis `INCR` 번호표를 점수로 쓰고, 확인·발급·등록을 Lua 하나로 | 기준이 Redis 도착 순서 하나가 됨. 판정은 `번호표 <= 입장 커서` |
| 2. 입장 커서의 빈틈(10/27) | 인스턴스 중복 입장, 커서가 번호표를 앞지름, 토큰 재발급, 토큰 넘겨주기 | 마지막 입장 시각 기록, 커서 상한, 발급 기록, 토큰에 사용자 확인 | 대가: 키 2개와 메모리, 정리 작업 |
| 3. 조회가 상태를 바꿈(10/29) | 순번 조회 GET이 상태를 바꾸고 토큰을 주는 곳이 둘 | 토큰 API 분리, 대기·준비·입장 상태, 순번 조회는 읽기 전용, 다음 조회 시각 안내(3~10초 + 지터) | 조회를 복제본으로 나눌 수 있게 됨. 대가: API·상태·오류 코드 1개씩 추가 |
| 4. 첫 배포 측정(11/9) | 대기열 한도는 어디인가 | 배포 서버에서 진입·조회·입장 측정 | 3,000명 진입 통과, 입장 초당 50 유지. 대기열까지 온 요청은 정확했다(번호표 = 대기 인원 = 성공 응답 수). 10,000명은 Gateway 차단기가 먼저 열림 → **한계는 대기열이 아니라 입구** |
| 5. Redis 지연(11/11~12) | Redis 시한 초과가 500으로 나간다 | 대기열 예외로 바꿔 503 + Retry-After. 차단기 값은 Gateway와 맞추고 AI가 낸 느린 호출 50ms는 거부 | 사용자는 재시도 안내를 받음. 대기열에만 지연을 넣는 실험은 못 해 값은 근거 수준으로 정함 |
| 6. 입장 토큰 재사용(11/12~13) | 10분짜리 토큰으로 "선점 → 만료 → 다시 선점"을 반복할 수 있다 | 선점 성공 순간 소모(팀 결정), DB 고유 제약으로 확인 | 대가: 결제에 실패하면 다시 줄을 섬 |
| 7. 줄 맡아 두기(11/15) | 차례가 와도 오지 않는 사람이 자리를 막는다 | 차례 유효 1분, 준비 판정을 Lua 안으로(앱 판정 유지라는 AI 추천은 거부) | 대가: Redis 장애가 1분을 넘으면 직전에 차례가 온 사람이 맨 뒤로 감 |
| 8. 입장 속도를 바꾸면(11/15~16) | 동적 입장 속도로 오픈 장애가 줄까 | 개념 정리. 실제 사용자 행동을 흉내 낸 합성 데이터(Synthetic) 실행의 진입은 초당 최대 2,792건(균일 도착의 약 7.9배) | 남은 상한 거절의 약 87~88%는 줄에 들어오기 전 Gateway에서 남. 진입을 오픈 +1~11초에 고르게 편 실행(1회)은 상한 거절 0. **입장 속도보다 진입 시점의 문제로 봄** |

## 감수한 것
- 이탈을 감지하지 않습니다. 감지하려면 가장 많은 요청인 순번 조회가 쓰기가 되기 때문입니다. 떠난 사람 칸만큼 입장이 늦어집니다(1명당 1/50초, 계산값).
- 순번이 도착 순서라 화면을 거치지 않고 API를 직접 부르는 사람이 앞설 수 있습니다(보류).
- 판정 코드가 Lua 세 곳에 같은 조각으로 들어갑니다.
- 순번 조회 간격은 30초로 늘리는 안(사용자 대기 증가)도, 1~3초로 줄이는 실험(중단)도 반영하지 않아 3~10초 그대로입니다.

## 알려진 문제와 개선 방향
| 문제 | 개선 방향(설계만, 측정 전) |
|---|---|
| 입장 속도 50이 고정이고 되먹임이 없다. 두 회차가 같이 열리면 두 배가 들어온다 | 고정값 30·40·50 비교 → AIMD → 동시 입장 인원 상한 |
| 대기열이 매진을 모른다. 매진 뒤에도 초당 50명씩 입장시킨다(코드 확인) | 매진 신호를 대기열에 전파해 대기자를 내보냄. 1,500석 매진 측정을 계획함 |
| 오픈 순간 진입이 입구에서 막힌다 | 사전 대기 등록, 진입 경로 분리, 연타 진입 합치기(대기열 계약 변경이라 팀 논의 필요) |
| 순번 조회 반응이 최대 10초 늦다 | 예상 입장 시각 직전에 묻기, 밀어 주기(SSE), 최소 간격만 1초로 |

## 넘지 못한 한계
- **측정 미완료**: 입장 속도 비교, 조회 간격 1~3초 실험(예열 도중 중단), 매진 시나리오, 30,000명 진입은 재지 못했습니다.
- **담당 경계**: 동적 입장·사전 대기실은 대기열 계약을 바꾸는 일이라 설계안으로만 남았습니다.
- **대기 가능 인원은 계산값**: 초당 약 2,000건 × 11초 간격으로 약 22,000명을 버틴다는 계산만 있고 실제로 줄을 세워 재지 않았습니다.

## 예상 질문
- **진입 시각이 아니라 번호표로 정렬한 이유는요?** 같은 밀리초면 정렬이 사용자 ID 사전순이 되고 서버마다 시계가 다릅니다. Redis `INCR`은 겹치지 않고 기준이 하나입니다.
- **이탈을 감지하지 않은 이유는요?** 감지하려면 순번 조회가 쓰기가 됩니다. 1명당 1/50초 지연이라는 대가를 계산하고 받아들였고, 줄 맡아 두기는 차례 유효 1분으로 막았습니다.
- **입장 속도를 동적으로 바꾸면 오픈 장애가 사라지나요?** 아닙니다. 남은 거절 대부분이 줄에 들어오기 전 입구에서 나고, 진입을 오픈 뒤 약 10초에 고르게 편 실행(1회)은 거절이 0이었습니다.
