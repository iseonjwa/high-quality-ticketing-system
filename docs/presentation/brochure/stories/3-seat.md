# 03 좌석 선점: 같은 좌석은 한 명, 병목은 계속 옮겨 갔다

> 오픈 순간 같은 좌석·같은 사용자·같은 멱등키 요청이 동시에 옵니다. 중복 판매와 한도 초과는 DB가 막아야 하고, 그러면서도 장비 한 대에서 처리량을 내야 합니다. 한 곳을 풀 때마다 병목이 GC → 커넥션 → DB 조인 → 직렬화 → CPU → Gateway 입구로 옮겨 갔습니다.

## 어떻게 발전했나

| 단계 | 처음 가정 | 시도와 측정 | 결과와 다음 행동 |
|---|---|---|---|
| 1. 동시성 결함 재현(11/3) | 결함 4종이 실제로 재현되는가 | 수정 4단계를 하나씩 넣고 시나리오 7개 실행(JUnit, 로컬) | 매수 한도 초과 30/30라운드 → 0, 자기 요청 충돌 60 → 0. 역순 교착은 처음부터 0 |
| 2. 병목은 잠금인가(11/3) | 잠금 경합이 느림의 원인이다 | 커넥션 풀 5 대 20 | 풀 20이면 처리량 약 2배, 잠금 대기 세션은 최대 0~6개. **병목은 잠금이 아니라 커넥션** |
| 3. 정합성의 비용(11/3~4) | JUnit에서 처리량이 1,125 → 648 req/s로 줄었으니 비용이 크다 | AI는 JUnit으로 부하를 근사하자고 했지만 Gateway를 거치지 않는다는 이유로 **거부**하고 k6로 다시 잼 | 400명까지 선점 p95 5ms 이하로 같음. **"비용 없이 들어갔다"로 결론을 뒤집음** |
| 4. 하나씩 고치고 다시 재기(11/6~10) | 측정 전에 예상을 적고 한 가지만 바꾼다 | 초당 100명·15,000석·앞 10%에 70% 쏠림으로 6단계 | 좌석 조회 성공률 0.13 → 0.7 → 40.3 → 81.3 → 100%(p95 7ms) |
| 5. 좌석 배치를 Redis에 둘까 | 공유 캐시가 빠를 것이다 | 로컬 캐시와 같은 조건으로 비교 | Redis는 p95 7.0 → 38.3ms, 한계 640 → 160명으로 나빠짐. **기각** |
| 6. 부하 속 동시성 | 연타·멀티 탭에서도 막히나 | 연타·멀티 탭·잠금 주입 | 한도 초과 293명 → 0, 연타 자기 요청 409 2,416명 → 0(초당 50명·120초, 로컬) |
| 7. "한계는 부하 발생기"라고 판단(11/9~10) | 1,280명에서 멈춘 것은 k6 탓이다 | k6 메모리 2.5 → 6GiB | 같은 코드로 1,280명 100%. **잘못 읽었다고 정정** |
| 8. 409 한 건의 비용(11/11) | 이미 잡힌 좌석 거절도 트랜잭션 안 SQL 7~8문장을 쓴다 | 트랜잭션 전 사전 거절(1초 캐시) | 409의 73~84%를 트랜잭션 전에 거름. 매진 직후 320명 처리 시간 −95%, 잘못 거절 0/407(측정 브랜치, 각 1회) |
| 9. 상한을 풀면(11/15) | Gateway 상한만 풀면 확정이 는다 | 상한 1000·134 | 확정 +9.0%·+6.2%지만 선점 p95 192 → 277 → 435ms, DB 커넥션 대기 10 → 22 → 31. **줄이 DB 풀 앞으로 옮겨 갔을 뿐** |
| 10. 뒤쪽 비용 묶음(11/16) | 사전 거절·직렬화 재사용·예열로 뒤쪽을 가볍게 | 개선 전 v1 대 후 v2, 3,000명 현실 도착 각 2회 | 확정 평균 +10.7%, 선점 p95 −77~87%, DB 커넥션 대기 12~14 → 0, reservation CPU −33~49% |
| 11. 자동 배정(11/16) | 서버가 좌석을 고르면 충돌·재조회가 사라진다(흉내 실험 +33.7%) | `SKIP LOCKED` 자동 배정 API | **확정 433건, DB CPU 280%로 가정이 뒤집힘(인덱스 누락, 1회).** 인덱스가 없어 다른 회차 좌석 약 248만 행을 훑음 → 인덱스 3개로 쿼리 309~382ms → 0.04~0.21ms, 확정 2,248건, DB CPU 18.2% |

## 감수한 것
- 잠금 대기 상한 500ms는 잠금 시도마다 걸려 실제 상한이 약 1초입니다.
- 사전 거절은 1초 낡은 좌석 상태를 씁니다. 1초 안에 풀린 좌석도 409로 거절될 수 있습니다.
- 입장 토큰을 선점 순간 소모해, 결제에 실패한 사람은 다시 줄을 섭니다.
- 자동 배정은 사용자가 자리를 고르지 못하고 연석을 보장하지 않습니다. 배포 때 인덱스 생성이 좌석 쓰기를 14.1초 막았습니다.
- Redis 좌석 캐시를 버린 대신 배치 캐시를 인스턴스마다 둡니다.

## 알려진 문제와 개선 방향
| 문제 | 개선 방향 |
|---|---|
| 유령 선점: 클라이언트가 포기한 요청이 나중에 처리돼 아무도 모르는 좌석이 만료까지 묶임(잠긴 행 집중 실험에서 8~9건) | 요청 기한 전달, 서버 쪽 요청 시한 |
| 잠금 하나가 번짐(인기석을 잠근 동안 상관없는 좌석 조회 성공 53.5%, 재측정·로컬) | 커넥션을 잡기 전에 거절(선점 동시 처리 상한) |
| 만료 배치 100이면 적체(약 9,050건) | 배치 상한 1,000 또는 시간 상한 반복(1,000이면 57~269건) |
| 접수형(Kafka) 선점은 배포에서 재지 못함 | 동기형·접수형 비교 측정(진행 중) |
| 좌석 응답 약 845KB | 비트맵 응답, 구역 단위 조회, 압축(응답 계약 변경 필요) |

## 넘지 못한 한계
- **장비 한 대(4 vCPU)**: 로컬 32코어에서 본 "1,280명"은 CPU가 남아서 나온 값이라 배포에 그대로 쓸 수 없습니다. 배포 4코어로 묶으면 320명에서 실패가 시작됩니다.
- **한 번씩 잰 비교**: 풀 10 실험처럼 1회만 재 "방향만" 말한 결론이 많습니다.
- **계약 변경이 필요한 개선**: 비트맵·대안 좌석·압축은 다른 서비스와 프론트를 바꿔야 해 기간 안에 넣지 못했습니다.

## 예상 질문
- **정합성을 고치면 느려지지 않나요?** JUnit(같은 JVM)에서는 느려 보였지만 편차가 커서 단정하지 않았고, k6로 다시 재니 400명까지 p95 5ms 이하로 같았습니다.
- **흉내 실험 +33.7%는 왜 실제로 안 나왔나요?** 흉내는 서버가 좌석을 고르는 비용을 뺀 값이었고, 실제 구현은 인덱스가 없어 433건이었습니다. 고친 뒤에도 +2~4%인 것은 409 비용이 이미 줄었고 남은 병목이 입구라서입니다.
- **커넥션 풀을 왜 안 늘렸나요?** 풀 10에서 500은 사라졌지만 p95가 1.06 → 1.83초로 나빠져 CPU 쪽 문제로 읽었습니다(1회, 방향만). 풀은 원인이 아니라 증상이 드러나는 자리로 봅니다.
