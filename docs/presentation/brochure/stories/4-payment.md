# 04 결제: 결과를 모를 때, 돈은 한 번만

> PG는 DB 트랜잭션 밖에서 부르므로 "처리 중"이라는 중간 상태와 결과를 모르는 경우(UNKNOWN)가 생깁니다. 그래도 한 예매의 승인은 한 번이어야 하고, 장애가 환불 같은 돈 복구까지 막으면 안 됩니다. 예매와 DB가 다르니 보상(SAGA)과 대사로 서로를 맞춥니다.

## 어떻게 발전했나

| 단계 | 고민 | 선택 | 결과와 대가 |
|---|---|---|---|
| 1. PG 허가 시점(10/27~28) | 503 뒤에 쓸모없는 요청 행이 쌓이고, 승인 실패로 차단기가 열리면 환불도 막힌다 | PG 허가를 DB 쓰기 전에 얻고, 신규 승인과 복구 호출의 허가 그룹을 나눔 | 복구 호출이 신규 승인을 막지 않음. 처음 원안의 빈틈을 AI 교차 검토로 보완 |
| 2. 같은 키 재시도(10/27~28) | 처리 중인 결제를 다시 부르면 | 202 + 기존 결제 ID, 멱등 조회를 토큰 검증보다 먼저 | 409로 돌려주는 안은 기각 |
| 3. 거절된 결제 토큰 재사용 | "HELD가 아니면 모두 환불" 원안이 확정 티켓을 환불할 수 있다 | 결제 쪽은 거절·환불된 예매의 재승인을 409로 막고(조회 + 예매당 1건 고유 제약), 예매 쪽은 확정할 수 없는 승인만 환불하되 같은 결제의 재전달은 무시하는 두 겹 | 원안 개정 |
| 4. 환불 실패 | 실패한 환불을 모두 사람이 처리 | 먼저 저장하고 워커 한 곳에서만 PG 호출, 자동 복구 | "실패하면 바로 수동 확인" 원안은 거부 |
| 5. 대사(10/28 → 11/3) | 각 장치는 자기 실패만 본다 | 결제가 주체인 대사 8종, 기록과 알림만 | 닫히지 않는 알림을 막으려 금액·사용자 대조 규칙을 승인 건으로 한정 |
| 6. DB 멈춤(11/3) | DB가 멈추면 요청이 시한 없이 기다린다 | 연결 1초·문장 1.5초·소켓 2초 시한 | 새 한계: 첫 트랜잭션 커밋 응답이 유실될 수 있음 |
| 7. 응답 유실 처리(11/9) | 요청 상태를 재시도가 이어받아 승인하자(원안) | **거부.** 첫 트랜잭션 커밋 응답이 사라진 결제는 PG를 부르지 않고 "보내지 않음"으로 종결 | 돈은 안전(승인 0건). 대가: 그 예매로는 재결제 불가 |
| 8. 허가 수가 처리량을 정한다(11/12) | 허가 10이 한도다 | 배포 서버에서 허가 10 대 30, 대기 0 대 200ms | 허가 10: 초당 31.2에서 정체 → **허가 30: 초당 91.5**, DB 연결은 최대 3개. 대기 200ms는 처리 +7.7% 대신 승인 p50 309 → 491ms라 버림 |
| 9. 대사가 배포에서 실패(11/12) | 로컬(예매 몇 건)에서 통과했으니 된다 | 배포 | 변경 목록 약 1,460쪽이 상한 1,000을 넘어 회차마다 실패. 호출 수를 결제 쪽만 셌음 → 증분 읽기 + 회차당 예산 |
| 10. 보상이 실제로 도는가(11/14) | SAGA 보상 경로 확인 | 시연 패널로 결제 거절 1건 | **거절 기록 뒤 약 0.14초에 예매가 풀림**(좌석·매수 원복, 배포 서버 시연 1건) |
| 11. 정상 종료처럼 보이는 재시작(11/15~16) | `docker inspect`는 exit 0 | 커널 로그 대조 | 하루 5회 메모리 부족 종료. 원인: 힙 최대 + 힙 밖 메모리가 상한 768MiB를 넘는 구조, 계기는 대사가 7일치 약 19.5만 건을 메모리에 올리는 것 → 1,024MiB, 힙 밖 상한 |

- 1~6단계 결정(ADR 0016~0029)은 구현됐지만 문서 상태는 "제안"(SA 변경 요청 대기)입니다. 7단계(ADR 0048)와 재전달 무시(ADR 0027)는 채택입니다.

## 감수한 것
- 첫 트랜잭션의 커밋 응답이 유실되면 그 예매는 재결제할 수 없습니다.
- Gateway 3초 안에 결제 전체가 끝나지 않을 수 있어 504를 허용합니다.
- 허가 그룹이 셋이고 PG 최대 동시 호출은 35입니다. 실제 PG 한도는 확인하지 못했습니다.
- 대사는 기록과 알림만 하고, 최대 몇 분 늦게 압니다.

## 알려진 문제와 개선 방향
| 문제 | 개선 방향 |
|---|---|
| 느린 PG(1~2.5초) 측정을 하지 못해 허가 24~30 최종값 미확정 | 느린 PG(1~2.5초) 측정 뒤 확정 |
| 대사가 회차마다 7일치를 메모리에 올림 | 이어 읽기로 바꾸기(결제 담당 결정) |
| 첫 트랜잭션 응답 유실 | 지표가 0이 아니면 그 트랜잭션에만 긴 소켓 시한 |
| 대사·Mock PG 서명 수정의 배포 확인 | 배포 서버에서 다시 확인 |

## 넘지 못한 한계
- **Mock PG만 썼습니다.** 실제 PG의 동시 한도·승인 멱등·지연 편차는 확인하지 못했습니다. 원장도 메모리라 재배포마다 비었습니다.
- **결제 서비스 증설은 장비 한 대의 메모리 예산 밖**입니다.
- **k6의 일정한 도착은 실제(포아송)보다 낙관적**입니다.

## 예상 질문
- **결과를 모를 때 왜 재시도가 이어받아 승인하지 않나요?** 요청 상태에는 응답 유실·호출 중·승인 뒤 저장 실패·승인 뒤 중단이 섞여 있어, 이어받으면 승인이 두 번 갈 수 있습니다.
- **허가를 30으로 정한 근거는요?** 입장 초당 50 × PG p99 0.35초 × 여유 2 ≈ 35를 Erlang B로 검산했고, 배포 실측은 초당 31.2 → 91.5, DB 연결 최대 3개였습니다.
- **대사가 배포에서 왜 실패했나요?** 로컬은 몇 건이었고 호출 수를 한쪽만 셌습니다. "상한을 넘으면 실패" 구조가 영구 실패가 되어 증분 + 예산으로 바꿨습니다.
