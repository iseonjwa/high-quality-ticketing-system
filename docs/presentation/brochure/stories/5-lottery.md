# 05 추첨·자동결제: 빠른 손 아니어도, 당첨되면 결제까지

> 선착순 경쟁을 줄이려고 추첨 배분을 넣었습니다. 추첨 직후 자동결제 약 2,000건을 10분 안에 95% 끝내야 하고, 같은 PG·서버·DB를 쓰는 일반 결제와 일반 선점을 방해하면 안 됩니다. 배치형이라 문제가 숫자로 잘 드러나지 않아, 측정 시나리오를 설계보다 먼저 정했습니다.

## 어떻게 발전했나

| 단계 | 고민 | 선택·측정 | 결과와 다음 행동 |
|---|---|---|---|
| 1. 숫자부터(10/29) | 배치형이라 성과를 숫자로 보이기 어렵다 | 측정 시나리오 3개(응모 몰림, 자동결제 10분, 일반 선점 간섭)를 설계에 먼저 넣음 | 기준: 추첨 뒤 10분 안 95% 결제, 응모 초당 100건 p95 300ms, 선점 p95 증가 20% 이하 |
| 2. 추첨석 떼기(10/29~31) | 시간 순서에만 기대면 일반 선점이 추첨석을 잡는다 | S석 일부를 추첨 등급으로 미리 뗌. 미리 떼지 않는 AI 안은 거부 | 대가: 등급 칸이 가격과 판매 경로를 함께 뜻함 |
| 3. 우리 장애로 당첨을 잃지 않게(10/31) | 서버 장애로 당첨자가 자리를 잃으면 안 된다 | 사유별 분기: 보내지 못함은 1회 재시도, 결과 미수신은 30분 1회 연장 | 대가: 재시도 예매는 다른 좌석을 받을 수 있음 |
| 4. 처음부터 막을까(10/30~31) | AI는 자동결제 전용 허가 그룹을 처음부터 두자고 함 | **거부.** 먼저 막으면 측정할 간섭이 없다. 공유 기준선으로 문제부터 재현 | 측정으로 원인을 찾기로 함 |
| 5. 기준선(11/10) | 10분 95%를 지키나 | 배포 서버, 자동결제만 3회 | 93.1·92.4·93.4%(약 93%)로 **미달**, 처리 초당 약 3.2로 일정 |
| 6. 겹침(11/10) | 일반 결제와 겹치면 | 일반 결제 초당 20·30 | 초당 20 합격, 초당 30에서 일반 결제 503 9.5% |
| 7. 원인 확정(11/10) | 허가가 모자란가, 소비자가 느린가 | PG 지연 300·150·50ms 스윕 | 처리 초당 3.17·6.27·15.9로 지연에 반비례, 허가는 9/10 남음, CPU 17% → **소비자 1개가 PG 응답을 직렬로 기다린 것** |
| 8. 장애에서도 한 번만(11/11) | 결제 서버 강제 종료·Kafka 정지에도 이중 결제가 없나 | 장애 주입 3종 | PG 원장 승인 38 = DB 승인 38, 중복 0, 연장 1회 작동. 정체 경보는 10분 45초 뒤에야 울림 |
| 9. 개선(11/12~13) | 소비자와 허가를 함께 고친다 | 파티션·소비자 3 + 자동결제 전용 허가 3, 일반 결제 허가 10 → 30 | **추첨 뒤 약 3분 50초(229~231초) 시점 완료율 35.0% → 100%**(전: 3회차 진행 조회 707/2,019건, 후: 마지막 결제가 206~229초 버킷 안). 10분 안 100%(2회), 결제 완료 p95 약 610~616초 → 205~210초(계산값), 처리 초당 약 3.2 → 9.4(약 2.9배) |
| 10. 겹침 다시(11/15) | 일반 결제·선점 간섭이 사라졌나 | 일반 결제 초당 30과 겹친 실행, 일반 선점 초당 30과 겹친 실행 각 1회 | 일반 결제 503 9.5% → 0, 자동결제 100%. 그러나 추첨 직후 선점 p95 11.06 → 21.0ms(+90%)로 **기준(+20%) 미달** |
| 11. 미달을 어떻게(11/16) | AI는 "저트래픽 시간대에 추첨" 정책으로 갈음하자고 추천 | **거부.** 미달을 정책으로 덮지 않고 추첨 워커 속도 상한을 걸어 다시 재기로 함 | 구현·재측정 전 |

## 감수한 것
- 자동결제가 새 결제를 만들면서도 전용 허가 그룹을 써, 결제 허가 경계에 예외가 생겼습니다. PG 최대 동시 호출은 35입니다.
- 파티션을 늘리는 순간 같은 예매의 결제 → 환불 순서가 뒤집힐 수 있어, 소비자 랙 0일 때만 늘리고 그 시간대에는 배포하지 않습니다.
- 빌링키 암호 키를 잃으면 전원이 다시 등록해야 합니다(키 교체 절차 없음).
- 응모는 동기 INSERT 하나만 재서 유지했고 다른 방식과 비교하지 않았습니다(초당 100건 p95 5.0ms, 데운 서버에서 800까지 503 0).

## 알려진 문제와 개선 방향
| 문제 | 개선 방향 |
|---|---|
| 추첨 직후 선점 p95 +90%(기준 +20% 초과) | 추첨 워커 속도 상한 + 재측정. 넘으면 추첨 서비스 분리 근거(팀 판단) |
| 추첨 대량 처리가 2~3분 동안 DB CPU 200%대 | 영향 측정부터 |
| 예매 Outbox 정체 경보가 없어 장애 탐지에 10분 넘게 걸림 | 경보 범위 넓히기 |
| 추첨 실행 시간이 0.5초와 4.5초로 갈리는 원인 미확인 | 재현·분석 |

## 넘지 못한 한계
- **장비 한 대**: 추첨이 다른 회차 판매와 같은 CPU·DB를 나눕니다. 서비스 분리는 장비 결정과 함께 볼 일입니다.
- **Mock PG만 썼습니다.** 실제 빌링 응답 시간과 동시 한도는 확인하지 못했습니다.
- **간섭 측정은 1회**라 반복 변동을 모릅니다.

## 예상 질문
- **처음부터 전용 그룹을 두지 왜 공유로 시작했나요?** 먼저 막으면 측정할 간섭이 없습니다. 측정으로 원인이 허가가 아니라 소비자 1개임을 확정했고, 그룹만 나눴다면 해결되지 않았을 것이라는 근거가 생겼습니다.
- **허가를 키우면 되지 않았나요?** 자동결제 중 남은 허가가 9/10였습니다. 소비자가 1개라 허가를 키워도 그대로였습니다.
- **10ms 늘었을 뿐인데 왜 다시 재나요?** 정한 기준을 넘었기 때문입니다. AI는 정책으로 갈음하자고 했지만 미달을 덮지 않고 속도 상한을 걸어 다시 재기로 했습니다.
