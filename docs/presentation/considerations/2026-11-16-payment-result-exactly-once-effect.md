# 결제 결과를 놓치지도, 두 번 반영하지도 않기: 예매 ↔ 결제 이벤트

담당: 효승(예매 흐름) · 정본: ADR [0027](../../decisions/0027-reservation-payment-event-contract.md)·[0029](../../decisions/0029-payment-reservation-reconciliation.md)·[0022](../../decisions/0022-outbox-retry-and-retention.md), SA 8장 · 그림: [결제 거절 → 좌석 원복 SAGA](../architecture/2026-11-14-saga-payment-declined.md)

## 1. 문제

결제는 다른 서비스(payment-service)가 하고, 결과는 Kafka 이벤트(`payment.result`)로 온다. 예매 서비스는 이 결과로 예매를 확정하거나 좌석을 되돌린다. 여기서 세 가지가 잘못될 수 있다.

| 위험 | 사용자에게 생기는 일 |
|---|---|
| 결과를 **놓침**(처리 중 오류, DB 연결 실패) | 돈은 나갔는데 예매가 만료된다 |
| 결과를 **두 번 반영**(Kafka 재전달) | 티켓이 두 번 생기거나 환불이 두 번 요청된다 |
| 결과가 **늦게** 옴(선점 시간 만료 뒤 승인) | 이미 다른 사람에게 갈 수 있는 좌석에 확정이 붙는다 |

## 2. 선택지와 고른 것

| 고민 | 검토한 방법 | 고른 것과 이유 |
|---|---|---|
| 결과를 어떻게 받나 | 결제 서비스가 예매 API를 동기 호출 / 이벤트 | **이벤트(Choreography)**. 결제가 끝난 순간 예매 서비스가 느리거나 죽어 있어도 결과가 Kafka에 남는다(SA 14장 #3) |
| 두 번 반영 막기 | 이벤트 ID 처리 이력만 / 예매 상태로만 | **둘 다**. 처리 이력(`processed_events`)으로 같은 이벤트를 걸러 내고, 상태 전이는 "지금 HELD일 때만" 조건부 UPDATE로 한다. 같은 예매를 선점 만료 스케줄러도 바꾸기 때문이다 |
| 늦게 온 승인 | 받은 시각 기준 / PG 승인 시각 기준 | **PG 승인 시각(`approvedAt`)**. 선점 시간 안에 승인됐고 예매가 아직 HELD면 좌석은 다른 사람에게 가지 않았으니 확정한다. 만료 뒤 승인이면 확정하지 않고 환불을 요청한다 |
| 처리가 계속 실패하면 | 무한 재시도 / 버리기 / DLQ | **1·2·4초 재시도 → DLQ → 한 번 더 처리 → 실패하면 `dead_letters`에 OPEN**. 무한 재시도는 파티션 전체를 멈추고, 버리면 돈만 나간다 |
| 예매와 결제가 어긋나면 | 자동 수정 / 기록·알림 | **기록·알림(대사)**. 예매 서비스는 읽기 전용 내부 조회 API만 열고, 결제 서비스가 대조한다. 대사 오류가 데이터를 망가뜨리지 않게 MVP는 고치지 않는다 |
| 환불 요청 보내기 | 처리 중 바로 Kafka 전송 / Outbox | **Outbox**. 상태 전이와 환불 요청을 같은 트랜잭션에 쓰고, 릴레이가 나중에 보낸다. DB는 커밋됐는데 전송만 실패하는 틈이 없다 |

## 3. 예매 상태별 규칙(승인 이벤트 예)

| 예매 상태 | 처리 |
|---|---|
| HELD, 대조 통과, 선점 시간 안 승인 | CONFIRMED, 좌석별 티켓 |
| HELD, 선점 시간 뒤 승인 | EXPIRED, 좌석 반환, 환불 요청 |
| HELD, 사용자·금액 불일치 | 상태 유지, 환불 요청, 즉시 알림 |
| CONFIRMED, 같은 결제 | 아무것도 안 함(재전달) |
| CONFIRMED, 다른 결제 | 상태 유지, 중복 승인 환불 요청 |

거절 이벤트는 HELD면 좌석을 되돌린다(RELEASED). "이상"은 상태를 바꾸지 않고 `event=PAYMENT_RESULT_ANOMALY` 로그로 남겨 사람이 본다.

## 4. 결과

| 확인 | 결과 |
|---|---|
| 결제 거절 → 좌석 원복 | 화면·로그 캡처([SAGA 그림](../architecture/2026-11-14-saga-payment-declined.md), ISE-267) |
| DLQ 처리기 | AI 리뷰 지적 세 가지를 받아 고침: DB 연결 실패를 업무 실패로 보던 것, NUL 문자·긴 키로 저장이 실패해 파티션이 멈추던 것, 먼저 OPEN이 된 건이 닫히지 않던 것. 테스트 5개 → 9개([판단 기록](../../ai-judgments/hyoseung/2026-11-03-dlq-review-fixes-all-accepted.md)) |
| 대사 API | 결제 서비스가 부르는 읽기 전용 `/internal/reconciliation/reservations`(Gateway가 밖에서 막음, ISE-75) |

## 5. 포기한 것

- 이상 이벤트를 따로 격리하는 테이블은 두지 않았다. 정상 경로에서는 생기지 않아 로그와 알림으로 충분하다고 봤다.
- DLQ에서도 실패한 건은 자동으로 다시 보내지 않는다. OPEN으로 남고 운영자가 확인한다. 같은 이벤트가 뒤에 처리되면 RESOLVED로 닫힌다.
- 대사에서 어긋남을 찾아도 자동으로 고치지 않는다.

## 발표 한 줄

"정확히 한 번 전달"은 Kafka가 약속하지 않으므로, **같은 결과가 여러 번 와도 한 번만 반영되고(처리 이력 + 조건부 전이), 끝내 처리 못 한 결과는 사라지지 않게(DLQ + dead_letters + 대사)** 만들었다.
