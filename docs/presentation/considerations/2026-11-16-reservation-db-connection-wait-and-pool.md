# 예매 DB 커넥션: 오래 기다리지 않게(1초), 풀은 늘리지 않게(5)

담당: 효승(예매 흐름) · 정본: ISE-196(커넥션 대기 시한), ADR [0064](../../decisions/0064-reservation-db-pool-keep-5.md)(풀 크기), [`k6-overload-recovery.md`](../../design/reservation/k6-overload-recovery.md)

## 1. 문제

reservation-service는 좌석 조회·선점·응모·추첨·스케줄러·Kafka 소비자가 커넥션 풀 하나를 나눠 쓴다. 오픈 순간 몰리면 두 가지가 문제였다.

| 문제 | 측정에서 본 것 |
|---|---|
| 커넥션을 너무 오래 기다림(기본 30초) | Gateway는 3초에 포기했는데 서버는 그 요청을 끝까지 기다렸다 처리했다. 부하가 끝나고 340초가 지나도 연결 4,344개가 남아 회복하지 못했다 |
| 풀이 작아 보임(5개) | 선점과 섞인 오픈 피크(E2, Gateway 상한 1000)에서 커넥션 대기 115, 시한 초과 500 약 476건 |

## 2. 선택지와 고른 것

| 고민 | 검토한 방법 | 고른 것과 이유 |
|---|---|---|
| 얼마나 기다리나 | 30초 그대로 / 1초 / 스레드·연결 수도 함께 조정 | **1초(ISE-196)**. Gateway 3초 안에 실패 응답이 돌아가게 하는 값이다. 1초만으로 부하가 끝나고 10초 안에 회복했고, 사용자가 받은 좌석 조회 200이 7건에서 1,463건으로 늘었다. 스레드·연결 수를 함께 바꾼 시작값(연결 200)은 오히려 나빴다(각 3회) |
| 풀을 늘리나 | 10·20으로 늘리기 / 5 유지 | **5 유지(ADR 0064)**. 풀 10(X1, 상한 1000)에서 500은 사라졌지만 서버 CPU가 이미 차 있어 커넥션을 쥐는 시간이 두 배(16.5 → 33.2ms), 선점 p95가 1.06 → 1.83초로 나빠졌다(1회 측정이고 발생기 지연 판정이 무효인 실행이라 방향만 읽는다). 주된 근거는 개선 묶음 뒤 풀 5(상한 64)로 다시 재자 커넥션 대기가 0이었다는 점이다 |
| 무거운 쿼리가 풀을 바닥낼 때 | 풀 늘리기 / 쿼리 고치기 | **쿼리 고치기**. 인덱스 없는 자동 배정 쿼리가 한 건에 약 785ms 커넥션을 쥐자 상관없는 조회까지 500이 났고, 인덱스를 더하자 대기 0이 됐다(TS-72, 강민) |

## 3. 결과

| | 전 | 후 |
|---|---|---|
| 부하가 끝난 뒤 회복 | 340초 뒤에도 연결 4,344개 남음 | 10초 안 회복(시한 1초) |
| 오픈 피크 O1 커넥션 대기 최대(풀 5) | 12~39(개선 전, 시나리오마다 다름) | 0(개선 묶음 뒤) |

## 4. 포기한 것

- 순간적인 몰림에도 1초가 지나면 바로 실패한다. 지금은 500으로 나가고, 계약대로 503으로 바꿔 화면이 다시 시도하게 하는 일은 ISE-293에서 한다.
- 응모(L1)에서 풀의 몫은 아직 모른다. 11/10 풀 20 결과는 세 설정을 함께 바꾼 값이다.

## 발표 한 줄

커넥션이 모자랄 때 "더 많이"가 아니라 "더 짧게 쥐고, 오래 기다리지 않게" 했다. 풀을 키우면 이미 찬 CPU에서 모두 느려진다는 것을 측정으로 확인했다.
