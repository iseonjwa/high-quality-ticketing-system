이선좌 배포 파이프라인 · 2026-11-05 기준 · ADR 0044

main 머지에서 배포 서버까지

릴리스 PR(dev → main)을 머지하면 사람이 할 일은 끝난다. GitHub Actions가 이미지 8개를 만들어 GHCR에 올리고, Jenkins가 그 이미지를 배포 서버에 띄워 확인한 뒤 슬랙으로 결과를 알린다. 아래 노선도는 11/5 릴리스 #338(머지 커밋 ab274ab)이 지나간 길이다.

  • 사람이 하는 일: 릴리스 PR 머지 한 번
  • 커밋 SHA 하나가 이미지 태그, 배포 버전, 되돌림 기준이 된다
  • 확인에 실패하면 직전 버전으로 자동 되돌림
  • 슬랙 알림 세 번: 배포 준비 → 배포 중 → 결과

CI와 CD

CI는 합칠 때마다 자동으로 검사하는 일이고, CD는 검사를 통과한 결과물을 서버까지 옮기는 일이다. 이 프로젝트는 둘을 서로 다른 도구에 맡겼다.

Continuous Integration · 지속적 통합

CI: 합칠 때마다 자동 검사

여러 사람이 작은 변경을 자주 합치고, 합칠 때마다 빌드와 테스트를 자동으로 돌려 깨진 곳을 바로 찾는다. 여기서는 PR마다 GitHub Actions가 돈다.

  • build (필수): Java 21로 ./gradlew verifyWorkspace
  • records-check (필수): 학습·판단 기록 구조와 비밀값 흔적
  • frontend: frontend/가 바뀐 PR에서 포맷·린트·테스트·빌드
  • prometheus-rules: 알림 규칙이 바뀐 PR에서 문법·단위 테스트
  • images: Dockerfile 등이 바뀐 PR에서 빌드만
Continuous Delivery / Deployment

CD: 서버까지 옮기기

지속적 전달은 언제든 배포할 수 있는 결과물을 자동으로 만들어 두고, 배포 버튼은 사람이 누른다. 지속적 배포는 관문을 통과하면 사람 없이 운영 서버까지 올린다.

이 프로젝트는 main에 들어온 커밋을 자동으로 배포하므로 지속적 배포에 가깝다. main에 넣는 일(릴리스 PR 머지)은 배포 담당이 하므로, 그 머지가 사람이 쥔 유일한 스위치다.

ADR 0044 · 왜 둘로 나눴나

빌드는 Actions, 배포는 Jenkins

  • 배포 서버에서 빌드하면 앱 7개 Gradle 빌드가 5~10분과 메모리를 운영 서비스와 다툰다. 그래서 빌드는 GitHub 실행기에서 한다.
  • Jenkins는 같은 VPC의 별도 서버에서 사설 IP로 배포 서버에 SSH한다. 배포 서버 SSH를 인터넷에 열지 않는다.
  • 웹훅 대신 폴링이라 Jenkins도 외부에 열지 않는다. 대가로 최대 2분 늦게 시작한다.
  • main 머지가 곧 배포라, 시연·측정 중에는 머지를 멈춘다.

커밋 하나가 지나가는 길

가로줄 하나가 시스템 하나다. 검은 알약이 커밋이고, 정거장을 지날 때마다 아래 설명이 바뀐다. 실패한 경우는 위 버튼으로 바꿔 본다.

    슬랙에 오는 알림

    배포 한 번에 알림이 세 번 온다. 앞의 두 번은 남색 띠의 진행 알림(started 배포 준비, deploying 배포 중)이고, 마지막은 Jenkins가 정한 결과(RESULT)에 따라 띠 색과 제목이 달라진다. 이미지를 못 찾으면 배포 중 알림 없이 결과가 바로 온다. 서버 상태 칸이 "확인 필요"면 배포 담당이 서버에 들어가 본다.
