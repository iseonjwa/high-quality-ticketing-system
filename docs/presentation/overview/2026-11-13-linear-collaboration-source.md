# 발표 소스: Linear로 담당·상태·선후 관계를 보이게 한 협업 (10/26~)

발표 자료를 만드는 사람이 가공할 원재료다. 장면마다 핵심 메시지 한 문장, 보여 줄 것, 발표자 메모, 출처를 둔다. 협업 방식의 정본은 [git-workflow.md](../../guides/git-workflow.md) 6절(이슈·PR 메타데이터와 Linear 연동)과 [contract-issues.md](../../guides/contract-issues.md)다.

정리: kangmin(11/13). 이야기 흐름은 kangmin의 회고이고, 각 장면의 출처는 저장소 문서와 Linear 이슈다.

## 0. 표현과 숫자를 쓸 때 지킬 것
- "원천적으로 차단했다"는 쓰지 않는다. Linear는 두 사람이 같은 코드를 고치는 것 자체를 막지 못한다. 실제로 한 일은 **이슈마다 담당 1명을 두고, 작업을 시작하기 전에 담당과 상태를 확인해 겹침을 먼저 발견한 것**이다.
- 이슈 수는 ISE-1(10/26)~ISE-276(11/13)이다. 상태별 개수는 세지 않았다. 쓰려면 Linear에서 다시 센다.
- "GitHub만으로는 누가 무엇을 잡았는지 알기 어려웠다"는 팀원의 경험이다. 수치 근거는 없다.

## 1. 장면

### 장면 1. 문제: 공통부문을 여러 사람이 동시에 만들었다
- **메시지**: 공통부문(Gateway, 인프라, user)에 형식상 담당만 두다 보니 같은 영역을 여러 사람이 동시에 만들었다.
- **보여 줄 것**: 10/27 기준 구현 브랜치 5개가 각자 공통 응답·예외, 인증, 빌드·DB 테스트 방식을 따로 만들었다. 하나를 기준(준현 브랜치)으로 고르고 나머지 장점을 골라 옮겨 붙이는 통합 검토 문서가 필요했다.

  | 브랜치 | 각자 만든 것(요약) |
  |---|---|
  | 준현 | 회원·세션 인증, 공통 인가·감사, 앱 7개·CI |
  | 권우 | 응답·예외 API, `ok/created` |
  | 효승 | Servlet 자동 구성, Redis 설정 분리, Gateway 라우트 테스트 |
  | 강민 | version catalog·convention 플러그인, PostgreSQL Testcontainers·Flyway |
  | 영은 | 모듈 구성, package-info, Gateway 헤더 제거 |
- **발표자 메모**: 같은 패키지 안에서도 여러 사람이 동시에 작업했고, GitHub 이슈만으로는 이슈가 쌓일수록 누가 무엇을 잡고 있는지, 끝냈는지 알기 어려웠다.
- **출처**: [sa-review/2026-10-27-branch-integration/README.md](../../sa-review/2026-10-27-branch-integration/README.md) "브랜치별 장점과 기준 선택"

### 장면 2. 선택: Linear로 할 일을 관리하고 GitHub와 잇는다
- **메시지**: 할 일과 담당은 Linear, 코드와 PR은 GitHub에 두고 이슈 번호로 잇는다.
- **보여 줄 것**
  | 무엇 | 어디서 | 연결 방식 |
  |---|---|---|
  | 이슈(할 일·완료 기준·담당) | Linear | Linear 이슈가 GitHub 이슈로 동기화된다 |
  | 브랜치 | Git | `{type}/ISE-{번호}-{주제}`. 담당은 이슈에 있으므로 이름에 사람 이름을 넣지 않는다 |
  | PR | GitHub | 브랜치 이름이나 제목의 `ISE-번호`로 Linear 이슈에 PR이 붙고, 머지하면 이슈가 Done이 된다 |
- **발표자 메모**: 첫 이슈는 ISE-1 「공통 기반 및 인증 모듈 제작」(10/26)이다. 통합 회의(10/27) 뒤 후속 작업을 그 하위 이슈(ISE-2~4)로 나눴다.
- **Linear를 고른 이유**(kangmin 회고, 11/13)
  - GitHub 연동이 편했다. 이슈가 GitHub로 동기화되고, PR이 이슈에 자동으로 붙는다.
  - 브랜치 관리가 좋았다. 이슈마다 `ISE-번호`가 든 브랜치 이름을 바로 쓸 수 있다.
  - 가볍다.
  - 한 달 무료 패키지가 있어 이슈가 많아져도(11/13 기준 ISE-276까지) 관리에 큰 문제가 없었다.
- **확인 필요**: 무료 패키지의 정확한 이름·기간과 끝난 뒤의 이슈 수 한도는 확인하지 못했다. 숫자로 말하려면 발표 전에 Linear 설정의 요금제 화면으로 확인한다.
- **출처**: [git-workflow.md](../../guides/git-workflow.md) 5절(브랜치 이름), 6절(Linear 연동)

### 장면 3. 결과: 누가 맡았고, 끝냈고, 어디서 막혔는지 보인다
- **메시지**: 이슈마다 담당 1명과 상태가 있어 겹침과 막힘을 작업 전에 발견했다.
- **보여 줄 것**
  - 다른 영역에 생기는 일은 담당을 이슈 제목에 드러냈다. 추첨 때문에 좌석·예매·결제 코드에 생기는 일은 추첨 담당이 맡고 제목에 "(추첨 타 영역)"을 붙였다(ISE-83, ISE-88, ISE-89, ISE-96). 그 영역 담당은 합의·리뷰를 맡는다.
  - 서비스 간 접점은 라벨 `contract` 이슈로 상대 담당에게 배정하고, 받는 쪽은 작업 전에 자신에게 온 열린 `contract` 이슈를 확인한다. 10/30 결제 담당이 ISE-73~77로 처음 쓴 방식을 팀 규칙으로 정했다.
  - 11/8 남은 이슈 정리에서 서로의 상태를 기다리는 이슈를 찾아 풀었다. 끝난 이슈 닫기(ISE-135, ISE-71, ISE-29), 취소(ISE-176, ISE-26), 담당자 확인 요청(ISE-8, ISE-62, ISE-76), 한 서비스를 함께 맡은 두 담당이 합의해 일정을 정하게 한 것(ISE-189)이다.
- **발표자 메모**: "막았다"가 아니라 "먼저 봤다"로 말한다. 시작 전에 담당과 상태를 확인하는 습관이 장치보다 중요했다.
- **출처**: [판단 기록: 추첨 타 영역 담당](../../ai-judgments/kangmin/2026-10-31-lottery-cross-area-work-ownership.md), [contract-issues.md](../../guides/contract-issues.md), [판단 기록: 11/8 Linear 정리](../../ai-judgments/junhyun/2026-11-08-linear-cleanup-plan-feedback.md)

### 장면 4. 교착: 서로가 먼저 끝나야 하는 이슈를 쪼개서 풀었다
- **메시지**: 이슈가 꼬리를 물어 서로를 기다릴 때, 계약 하나에 정하는 담당 하나를 붙이도록 이슈를 쪼개 교착을 풀었다.
- **보여 줄 것**: ISE-19 「서비스 간 계약 4종 확정」(10/27 생성). M2(일반 예매 한 흐름 연결) 전에 서비스 사이의 약속을 먼저 고정해야 했다. 늦게 정하면 만드는 쪽과 쓰는 쪽 서비스를 모두 다시 고쳐야 한다(SA U1).

  | 하위 이슈 | 계약 | 형식을 정하는 담당 | 확인하는 쪽 |
  |---|---|---|---|
  | ISE-20 | 입장 토큰 claim | 대기열 | Gateway, 좌석 선점 |
  | ISE-21 | 좌석 선점 결과 형식 | 좌석 선점 | 예매 흐름 |
  | ISE-22 | 결제 토큰 claim | 예매 흐름 | 결제 |
  | ISE-23 | `payment.result` 이벤트 필드 | 결제 | 예매 흐름 |

  규칙: 형식을 소유한 담당이 정해 공유하고, 쓰는 쪽이 리뷰한다. 완료 기준은 "계약이 SA나 `docs/`에 표로 적혀 있고 관련 담당이 확인했다"이다. 11/1 하위 4개가 모두 Done이 됐다.
- **발표자 메모**
  - 쪼개기 전에는 "계약을 정해야 구현하고, 상대 구현을 봐야 계약을 정한다"는 식으로 서로를 기다렸다. 쪼갠 뒤에는 계약마다 누가 먼저 움직일지가 정해졌다.
  - 곁가지 교훈: 하위 이슈 하나의 PR이 상위 번호 브랜치로 머지되면서 ISE-19가 10/29 자동으로 Done이 됐다. 그때 입장 토큰 계약은 끝나지 않았다. 이후 "부분 완료로 자동 Done이 되면 다시 열지 않고 후속 이슈를 만들어 blocked by를 건다"는 규칙을 만들었다.
- **출처**: Linear ISE-19 본문(현황 정리 10/29, 마감 정리 11/1), [git-workflow.md](../../guides/git-workflow.md) 6-3절 "부분 완료로 자동 Done이 된 경우"

## 2. 예상 질문
| 질문 | 답의 재료 |
|---|---|
| 왜 GitHub Projects가 아니라 Linear인가 | GitHub 연동과 브랜치 관리가 편하고, 가볍고, 한 달 무료 패키지로 이슈 270여 개를 문제없이 관리했다(장면 2) |
| 무료 기간이 끝나면 어떻게 하나 | 확인 필요. 요금제 화면에서 기간과 한도를 확인한 뒤 답을 정한다 |
| Linear로 어떻게 중복 작업을 막았나 | 막은 것이 아니라 담당 1명·상태로 먼저 보이게 했다. 타 영역 일은 제목에 담당을 드러내고, 접점은 `contract` 이슈로 상대에게 배정했다(장면 3) |
| 교착을 어떻게 알아챘고 어떻게 풀었나 | ISE-19. 계약마다 형식을 정하는 담당을 붙여 하위 이슈 4개로 나눴다(장면 4) |
| 이슈 관리에 드는 비용은 없었나 | PR의 담당·라벨·마일스톤은 자동으로 채워지지 않아 직접 지정해야 했고, 11/2 팀 전체 GitHub PR·이슈 메타데이터를 한 번 일괄 정리했다(ISE-141, ISE-144) |
