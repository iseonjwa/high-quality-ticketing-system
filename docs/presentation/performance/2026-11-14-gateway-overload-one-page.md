# Gateway 과부하 개선 전·후 한 장 (발표용, 2026-11-14)

발제 "최적화 전·후 2회 이상, 개선 내역 1~3줄"의 Gateway 몫이다. 원천은 [Gateway 과부하 발표 소스](../2026-11-12-gateway-overload-source.md)(장면 5·6·8)와 [안전망 상한 소스](2026-11-13-safety-net-limit-source.md), 측정 정본은 [open-peak-scenarios.md](../../design/infra/open-peak-scenarios.md) 배포 서버 6~8차다.

## 결론

같은 4 vCPU 서버 한 대에서 장치를 하나씩 더해, 순번 조회 2,500/s의 굿풋(200ms 안에 성공한 요청 수/초)을 1,608/s에서 2,122/s로 올리고 1,000/s의 서버 CPU를 78%에서 66%로 낮췄다.

## 전·후 표

굿풋은 200 응답이면서 200ms 안에 끝난 요청 수/초, p95는 성공 응답 기준이다. 세 비교 모두 같은 날(2026-11-11 UTC) 같은 시나리오의 앞뒤 회차다.

| 개선 | 지표 | 전 | 후 | 원인(왜 달라졌나) | 치른 대가 | 조건 |
|---|---|---|---|---|---|---|
| 1. 맨 앞 동시 처리 수 상한 64 | 2,000/s 굿풋 / p95 | 1,304/s / 571ms(상한 500, 사실상 없음) | 1,696/s / 87ms | 넘친 요청을 일찍 503으로 돌려 받은 요청의 줄이 짧아졌다. 64는 리틀의 법칙(처리 중 수 = 도착률 × 머문 시간)으로 계산한 60~67에서 골랐다 | 넘친 요청은 503(2,000/s에서 상한 거절 8,715건). 서버 CPU는 그대로 98% | 6차 L500 → L64, 배포 `8b95fe68` 같음 |
| 2. 거절 위치를 HttpHandler 데코레이터로 앞당김(H1) | 2,500/s 굿풋 / p95 | 1,608/s / 104ms | 1,814/s / 78ms | 거절이 서버 관측·요청 로그·라우트 매칭을 거치지 않는다. 8차 R0에서 거절 한 건은 받은 요청 한 건의 2~8%(0.02~0.08ms 대 1.06ms)로 쟀다 | 서버 CPU는 99%로 그대로. 이득은 CPU가 아니라 굿풋으로 나타났다 | 6차 L64 → 7차 H1, 배포 `8b95fe68` → `1e9b1c75` |
| 3. 요청 로그를 실패·느린 요청만 남김(H2 → 운영 `problems`) | 1,000/s 서버 CPU, 2,500/s 굿풋 | 78%, 1,814/s | 66%, 2,122/s | 로그 한 줄마다 드는 비용이 Gateway 밖(로그 수집기 Alloy 22 → 14%, 호스트)에 있었다. JVM 프로파일러는 5.2%로만 봤다 | 정상 요청 로그가 없다. 정상 요청은 traceId로 Zipkin·지표에서 본다 | 7차 H1 → H2, 배포 `1e9b1c75` 같음. 운영 반영 확인은 8차(11/12) |

- 공통 조건: 배포 서버 EC2 `m7i.xlarge`(4 vCPU) 한 대, 발생기는 같은 VPC의 별도 EC2(k6). 시나리오 G1(대기열 순번 조회 `GET /api/v1/schedules/{id}/queue/me`), 대기자 10,000명, 목표 1,000·1,500·2,000·2,500/s 단계마다 30초, 웜업은 판정에서 뺐다.
- 반복: 회차당 1회. 같은 값을 두 번 잰 차이는 굿풋 약 5%(6차 L128)다. 개선 1·2·3의 굿풋 차이는 30%·13%·17%로 그보다 크다.
- 유효성: 모든 단계에서 빠진 요청 0건, 발생기 CPU 유휴 최소 16%(6차)·18%(7차). Gateway OOM 0건.
- 계산식(이 장에서 새로 낸 값): 개선 1의 굿풋 +30% = (1,696 − 1,304) ÷ 1,304, p95 −85% = (571 − 87) ÷ 571.

## 개선 내역

1. Gateway 맨 앞에 동시 처리 수 상한(64)을 두어 2,000/s p95를 571ms에서 87ms로 묶었다.
2. 상한 거절을 프레임워크 가장 바깥 연결점(HttpHandler 데코레이터)으로 옮겨 거절 비용을 받은 요청의 2~8%로 줄였다.
3. 요청 로그를 실패·느린 요청만 남기게 해 1,000/s 서버 CPU를 12%p 낮췄다.

## 이 장면이 증명하는 것

자원을 늘리지 않고, 한 번에 하나만 바꾸고 같은 날 앞뒤로 재서 개선마다 원인을 숫자로 분리했다.

## 예상 질문

| 질문 | 답 |
|---|---|
| 서버 CPU가 여전히 98~99%인데 개선인가 | 상한은 빈자리를 바로 다음 요청으로 채워(작업 보존형) CPU를 남기지 않는다. 대신 같은 CPU로 200ms 안에 끝내는 요청이 늘었다. CPU를 낮춘 것은 개선 3이다 |
| 왜 64인가 | 굿풋이 멈춘 약 1,480/s에서 p95 200ms를 지키는 평균 처리 중 수가 60~67(계산값)이다. 같은 날 32·128·500과 비교해 128은 굿풋이 1.5% 높지만 반복 변동 안이고 p95가 두 배라 64를 골랐다 |
| 실제 예매 흐름에서도 64가 맞나 | 아니다. 11/13 섞인 흐름(O1)에서는 64가 좌석 조회·결제에 자리를 내주며 순번 조회를 초당 94~245건 거절했고 확정 예매가 2,574건으로 512의 약 절반이었다. 그래서 상한을 메모리 안전망으로 올리는 쪽을 보고 있다([안전망 상한 소스](2026-11-13-safety-net-limit-source.md)) |

## 숫자 사용 주의

- % 변화는 같은 날 비교에만 쓴다. 8차에서 같은 설정도 7차보다 서버 CPU가 6~9%p 낮게 나와, 날이 다르면 수치가 흔들린다.
- 누적 값(5차 2,000/s p95 435ms → 8차 43~44ms)은 날이 달라 "참고"로만 말하고 %로 말하지 않는다.
- 개선 2의 거절 비용은 전후 측정 방법이 다르다(전은 포화 구간 자료로 푼 추정 약 1/5, 후는 R0 직접 측정). "약 1/5에서 1/10 이하로"까지만 말한다.
- G1(순번 조회 한 API) 숫자와 11/13 O1(섞인 흐름) 숫자를 한 표에 섞지 않는다.
- 운영 설정의 상한은 아직 64다(`config-repo/gateway.yml`). 512로 올릴지는 정하지 않았다.
