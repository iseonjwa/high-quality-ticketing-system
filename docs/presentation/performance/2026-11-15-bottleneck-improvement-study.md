## 0. 한 장 요약

### 병목 사슬

```
[입구 몰림]  대기열 진입 초당 최대: 균일 353 / Synthetic 2,792 (약 7.9배, 계산값)
     │
     ▼
[Gateway 동시 처리 상한 64]  요청 수만 센다. 1초 미만 순간 몰림에서 거절
     │   상한을 올리면 → 거절이 auth-redis bulkhead(50)로 옮겨 감 (B1 130건, B2 106건)
     ▼
[대기열 입장 초당 50]  뒤쪽 부하를 평평하게 만든다 (두 모드의 뒤쪽 유입 속도가 같다)
     │
     ▼
[좌석 쏠림]  균일: 사용자 70%가 앞 10% 좌석을 노림 → 409 약 48~50%
     │        409마다 830KB 좌석 재조회 + 재선점, 409도 SQL 약 7~8문장(권우 노트: 7개, 왕복 약 9번) 뒤 롤백
     ▼
[reservation]  CPU 0.29(4코어 전체 = 1) · DB 커넥션 풀 5 · Hikari 대기 10 → 22 → 31
     │        커넥션을 쥐는 시간이 평소 2~4ms(K1-H 로컬 측정·가정) → 약 25ms 이상으로 늘었다고 본다(계산값·추정)
     ▼
[호스트 CPU 포화]  4 vCPU 한 대에 앱 8개·DB 3개·Redis·Kafka·관측 도구. 최대 0.988~0.999
```

### 결론
Gateway 상한은 근본 조치가 아니라 **어디에 줄을 세울지 고르는 손잡이**다. 상한을 올리면 거절은 줄지만 같은 요청이 reservation DB 풀 앞에서 기다리고 지연이 는다. 처리량 천장은 호스트 CPU 포화와 reservation 처리 비용(409·재조회·직렬화)이 정하는 것으로 본다(추정). 풀 5가 원인인지 CPU가 원인인지는 3-2의 2번 실험(X1)으로 가른다(트러블슈팅 초안 4-2절).

### 1-3. 호스트 CPU가 최대인 순간의 몫
reservation 조사 5절. `process_cpu_usage`(JVM이 쓴 CPU, 4코어 전체 = 1)를 같은 5초 표본의 `system_cpu_usage`와 비교한 소급 집계다.

| 실행 | 호스트 | reservation | gateway | payment | user | JVM 합 | 나머지(DB·Kafka·Redis·Prometheus 등) |
|---|---|---|---|---|---|---|---|
| 균일 122 | 0.997 | 0.292 | 0.218 | 0.130 | 0.001 | 0.641 | 0.356 |
| 균일 132(상한 1000) | 0.988 | 0.188 | 0.241 | 0.114 | 0.001 | 0.544 | 0.444 |
| Synthetic 123 | 0.803 | 0.188 | 0.168 | 0.201 | 0.001 | 0.558 | 0.245 |

- 호스트 0.95 이상 표본 평균(122, 5표본): reservation 0.296, gateway 0.226, payment 0.131.
- reservation 최댓값은 0.359(122), 약 1.4코어(계산값).
- Gateway 최댓값(시점 무관)은 0.269~0.382, 1.08~1.53코어(계산값, Gateway 조사 4절). 위 표의 gateway 값과 다른 것은 "호스트 최대 시점"과 "실행 중 최댓값"의 차이다.
- 나머지 0.36~0.44의 내역은 확인 못 함(`container_*` 지표 없음).
- 포화는 오픈 뒤 짧은 구간뿐이다. 122에서 호스트 0.95 이상은 5/302 표본, 실행 평균 0.200이다. Hikari 대기 > 0은 2/302 표본(약 10초)이다.

## 2. 개선 후보 카드

### A. Gateway

#### A1. 통합 상한 하나의 한계와 1초 미만 순간 몰림
| 항목 | 내용 |
|---|---|
| 발견(코드) | 상한은 Gateway 전체에 `AtomicInteger` 하나이고 경로를 보지 않는다. 운영자 경로만 뺀다(`InFlightLimitHandlerDecorator.java:40`, `:85-93`). 자리는 응답 전송이 끝날 때까지 잡는다(`:25`, `:93`). 64는 대기열 순번 조회 한 경로(G1)의 체류 40~45ms × 1,480/s로 고른 값이다(`config-repo/gateway.yml:69-78`, `:71-72` 주석) |
| 발견(숫자) | 1-1 표. 30초 평균은 64 아래인데 거절 1,150. B1에서 1초 최대 216.2 대 표본 89(약 2.4배, 계산값). 5초 표본으로 고른 134는 순간 최대를 못 덮어 거절 358이 남았다 |
| 경로 분포(k6, 균일 64) | 503이 대기열 순번 조회 421, 예매 조회 286, 선점 168, 좌석 123, 결제 80, 입장 토큰 48, 진입 16, 공연 상세 8로 퍼졌다(진행 기록 264행) |

개선안 비교
| 안 | 장점 | 대가 |
|---|---|---|
| 1-A. 값만 올림(1초 최대 216에 여유, 예: 256) | 설정 한 줄, 오늘 잴 수 있다 | 줄이 DB 풀 앞으로 옮겨 간다(Hikari 대기 10 → 22~31). 진짜 폭주 때 힙이 커진다(5차 OOM 이력) |
| 1-B. 짧은 대기 줄(최대 N개, 최대 50~100ms 대기 뒤 처리) | 1초 미만 몰림을 흡수하고 상한 값은 유지 | 대기 요청도 메모리를 쓴다. 지연이 는다. 거절 비용이 조금 오른다(추정) |
| 1-C. 입구 요청률 제한(토큰 버킷) | 버스트 허용량을 값으로 표현 | 느린 요청이 쌓이는 것은 못 막는다. ADR 0050 "검토한 대안"이 미뤘다(`0050-...md:46`) |
| 1-D. 64 유지 + 좌석·선점 503 재시도 | 서버 변경 없음 | 거절이 사용자 지연으로 바뀐다. 시나리오·프론트 변경 |
| 2-A. 경로 묶음별 상한 | 무거운 경로가 가벼운 경로 자리를 뺏지 않는다 | 값이 묶음 수만큼 늘고 묶음마다 측정 필요. 전체 상한도 함께 둬야 한다 |
| 2-B. 가중치 상한(좌석 조회 w칸) | 메모리를 바이트에 가깝게 묶는다 | 가중치 근거가 응답 크기뿐, 설명이 어렵다 |
| 2-C. 적응형(AIMD) | 값 고르기 부담이 준다 | 재는 지연에 PG 300ms·전송 시간이 섞여 과부하 판별이 어렵다 |
| 2-D. 적응형(Gradient2, `com.netflix.concurrency-limits`) | 큐가 쌓이기 시작하는 순간을 잡는다 | 새 의존성·ADR. 짧은 피크에서는 수렴 전에 끝날 수 있다(추정). CPU 포화에서는 경로 구분이 흐려진다 |

| 적용 경로 | 내용 |
|---|---|
| 오늘 측정 모드 | 1-A만: `INFLIGHT_MAX`(`loadtest/deploy/compose.gateway-inflight.yml:26`). 3절 E1 |

| 인프라 | 없음 |

| 적용하지 못할 때의 예측 근거 | 계산 |
|---|---|
| 순간 몰림을 받으려면 | 리틀의 법칙 L = λW. B1의 1초 최대 216을 받으려면 상한 ≥ 216(계산값). k6 값이라 네트워크 왕복이 섞여 서버 실제 값은 더 작다(추정) |
| 64를 유지하면 | 같은 O1에서 매번 약 1,150~1,560건 거절, 그중 좌석·선점 몫은 `error`(균일 291 = 좌석 123 + 선점 168) |
| 경로별 합 | L = Σ λi·Wi. 결제 λ 30/s(가정)면 Mock PG 300ms 때문에 9칸을 상시 쓴다(계산값). 경로별 λ×W는 아직 계산하지 않았다 |

남은 한계: 어떤 값·방식이든 하류(DB 풀 5, 호스트 CPU)가 처리량 천장이다. 경로 격리는 "누가 거절되는지"를 바꿀 뿐 처리량을 늘리지 않는다.

#### A2. 830KB 좌석 응답 압축
| 항목 | 내용 |
|---|---|
| 발견 | 저장소 전체에 `server.compression` 설정이 없다. 압축은 프론트 nginx에만 있다(`frontend/nginx/default.conf:21-23`). k6는 Gateway 8080으로 직접 가므로 측정에서 830KB가 그대로 오간다(`compose.deploy.yml:8-9`, ADR 0046). 브라우저 경로도 Gateway→nginx 구간은 비압축이다 |
| 양(계산값) | 균일 122 좌석 조회 4,782건(서버 지표) × 0.83MB ≈ 4.0GB, 피크 94/s × 0.83MB ≈ 78MB/s ≈ 620Mbps(reservation 조사 2-1). 자동 배치 조사는 830KB × 4,781 ≈ 3.97GB(불일치: 분모 4,782 대 4,781, 아래 5절) |
| 이미 한 것 | P4d가 `sections` JSON 바이트를 1초 스냅숏마다 한 번 만든다(`docs/design/reservation/k6-p4d-review.md:7`) |

| 안 | 장점 | 대가 |

| 4-A. reservation에서 스냅숏마다 gzip 바이트를 한 번 만들어 캐시 | 압축 CPU가 초당 1번. Gateway·네트워크가 나르는 바이트가 준다(압축률 5~20배, 추정) | 좌석 담당 영역 코드. `serverTime`·`traceId`와 합치는 방식이 까다롭다 |
| 4-B. reservation `server.compression` | 설정만 | 요청마다 830KB 압축. 호스트 CPU 0.99에서 다른 서비스 몫을 뺏는다(추정) |
| 4-C. Gateway `server.compression` | 설정만, 모든 경로 | reservation→Gateway는 비압축 그대로, 압축 CPU가 Gateway에 얹힌다 |
| 4-D. 응답 줄이기(구역별 조회, 비트맵) | 근본 해결, 발생기 대역폭 문제도 해결 | API 계약 변경, 마감 내 어렵다(추정). B3 카드와 같다 |
| 4-E. `Cache-Control: max-age=1` 또는 ETag/304 | 409 뒤 재조회가 304로 끝난다 | 최대 1초 묵음(지금도 1초 공유라 변화 작음, 추정). k6가 캐시를 흉내 내야 측정에 보인다 |

| 적용 경로 | 내용 |
|---|---|
| 오늘 측정 모드 | 부하 없는 크기 확인만: `curl -s -o /dev/null -w '%{size_download}\n' -H 'Accept-Encoding: gzip' ...`(인증·입장 토큰 필요). 압축을 켜려면 새 덮어쓰기 파일 필요(PR로 덮어쓰기 파일 추가 필요). k6가 `Accept-Encoding`을 보내는지 먼저 확인 |
| 코드 변경 | 4-A 약 50~100줄 + 테스트(추정), 좌석 담당과 상의 |
| 인프라 | 없음 |

| 적용하지 못할 때의 예측 근거 | 계산 |
|---|---|
| 좌석 조회 한 건의 자리 점유 | 같은 VPC 1.5Gbps에서 830KB 전송만 약 4.4ms. 모바일 10Mbps면 약 0.66초로 대기열 조회 약 15건분(40~45ms 기준) 자리를 잡는다(모두 계산값) |
| 직접 메모리 | 128MB(`compose.deploy.yml:58`) ÷ 830KB ≈ 154건분(계산값). Netty가 응답 전체를 쥐는지는 확인 못 함 |

남은 한계: 좌석 응답 한 건의 Gateway CPU와 압축률을 재지 않았다. 이득 크기는 모두 추정이다.

#### A3. auth-redis bulkhead 50과 블랙리스트 조회
| 항목 | 내용 |
|---|---|
| 발견(코드) | 인증 요청마다 Redis `EXISTS auth:blacklist:<jti>` 한 번. TimeLimiter → 차단기 → bulkhead → 조회(`GatewayAuthenticationFilter.java:90-110`). 필터 시한 200ms(`gateway.yml:60`), bulkhead 동시 50·대기 0(`gateway.yml:100-105`). Redis 무응답이면 막는다(fail closed, ADR 0005:14) |
| 발견(숫자) | 상한을 올리자 503이 bulkhead 거절로 옮겨 갔다: 1000에서 130, 134에서 106, Synthetic(64)에서 48. Gateway Lettuce 최대 60 → 129 → 143ms. ADR 0050 측정에서 Redis 명령은 0.1~2ms였으므로 늘어난 시간은 Gateway·호스트 CPU 대기로 본다(추정) |

개선안 비교
| 안 | 장점 | 대가 |
|---|---|---|
| 3-A. bulkhead 50 → 100 | 오늘 잴 수 있다 | 11/10 G1에서 50이 100보다 p95가 좋았다(2,000/s 208 → 157ms, ADR 0050:34). 원인이 CPU 대기라 지연만 늘 수 있다(추정) |
| 3-B. jti별 "블랙리스트 아님"을 1~2초 로컬 캐시 | 같은 사용자의 연속 요청이 Redis를 덜 부른다 | 로그아웃이 최대 N초 늦게 반영된다. 팀 결정·ADR 필요(ADR 0005 보완) |
| 3-C. 로그아웃 이벤트로 로컬 차단 목록 유지 | 요청당 Redis 호출이 사라진다 | 이벤트 유실·재기동 대응, 서비스 간 접점(`contract` 이슈). 코드가 가장 크다 |
| 3-D. 같은 jti 동시 조회 묶기 | 정책 변화 없음 | 연타·다기기에만 이득, 효과 작음(추정) |

| 적용 경로 | 내용 |
|---|---|
| 오늘 측정 모드 | 3-A: `AUTH_BULKHEAD`(`compose.gateway-bulkhead.yml:56`). 이 파일과 `compose.gateway-inflight.yml`은 둘 다 `SPRING_APPLICATION_JSON`이라 함께 주면 뒤 파일만 남는다(`compose.gateway-inflight.yml:20`). 상한 1000 + bulkhead 100은 합친 파일이 필요하다(PR로 덮어쓰기 파일 추가 필요) |
| 코드 변경 | 3-B 약 40~60줄 + ADR(추정). 3-C 수백 줄 + 이벤트 계약(추정) |
| 인프라 | 없음 |

| 적용하지 못할 때의 예측 근거 | 계산 |
|---|---|
| bulkhead 최대 처리율 | 동시 50 ÷ 한 건 시간. 정상 1~7ms면 약 7,000~50,000/s. Lettuce 최대 129~143ms가 이어지는 순간에는 약 350~390/s(계산값, 최댓값으로 잡은 비관적 하한) |
| 상한을 더 올리면 | Gateway 동시 처리 증가 → CPU 대기 증가 → Lettuce 시간 증가로 bulkhead 거절이 남는다(추정) |

남은 한계: 3-B·3-C는 Redis 호출 비용만 없앤다. bulkhead가 찬 근본 원인(호스트 CPU 대기)은 그대로다. 요청당 Gateway CPU 중 Redis 몫은 확인 못 함.

### C. 좌석 자동 배치

| 항목 | 내용 |
|---|---|
| 발견 | 서버가 좌석을 고르는 사용자용 API는 없다. 서버가 고르는 코드는 추첨 배정 워커뿐이다. SA 5-1 MoSCoW **Could**에 "좌석 자동 배정"이 있고 설계 내용·ADR은 없다(`SA MASTER.md:415`(dev 기준)). A0 기준선은 이름과 달리 배정 API가 아니라 미리 나눠 둔 좌석으로 선점 처리량만 잰다 |
| 숫자(균일 122, 계산값) | 좌석 조회 4,904 = 첫 조회 3,000 + 409 뒤 재조회 1,904(409 2,298 − `gave_up` 394). Gateway 자리 점유 합: 좌석 조회 329s(4,904 × 67.1ms), 선점 254s(4,781 × 53.1ms), 결제 674s(2,053 × 328.4ms) |
| 핵심 변수 | 결제가 자리를 가장 오래 쓴다(PG 300ms). 좌석 조회+선점(583s)을 줄여도 확정이 늘면 결제 몫이 는다 |

| 기준 | A 구역·매수 지정 → 서버가 골라 선점 | B 서버 추천 → 사용자 확정 | C 409 응답에 대안 좌석 |
|---|---|---|---|

| 830KB 재조회 | 없음 | 화면 설계에 달림 | 없음 |
| 선점 트랜잭션 변경 | 있음(선택 쿼리, 멱등 비교) | 없음 | 실패 경로에 대안 계산 |

A안 동시성 선택지
| 방식 | 장점 | 대가 |
|---|---|---|
| A1. `FOR UPDATE SKIP LOCKED` + `LIMIT :n` + `RETURNING` | 잠금 대기·`lock_timeout` 409가 사라진다. 기존 조건부 UPDATE·인덱스·잠금 순서 유지, 저장소에 이미 쓰는 패턴 | 앞쪽 HELD 행을 매번 지나간다(구역당 평균 600석, 계산값). 2매 옆자리 미보장 |
| A2. Redis 좌석 풀 pop | DB 앞에서 경쟁 종료 | 상태가 두 곳, 되돌리기·대사 필요. 남은 기간에 맞지 않다(추정) |
| A3. 구역별 커서 | 앞 HELD 반복 스캔 감소 | 인스턴스 간 공유, 만료로 풀린 앞 좌석을 놓침 |

- 설계 판단이 필요한 곳: `seat_hold_requests.seat_ids`가 `BIGINT[] NOT NULL`이고 `claimRequest`가 좌석 잠금 전에 쓴다. `requireSameRequest`도 `seatIds`로 비교한다. 선택지는 (1) 빈 배열로 먼저 쓰고 재요청 비교를 구역·매수로(열 추가), (2) 좌석을 먼저 고르고 요청 행을 나중에(순서 변경)다. 어느 쪽이든 `contracts.md` 3절 멱등 규칙을 고친다.
- 2매 연석 이웃 계산은 `lottery.SeatAllocator`에 있지만 seathold가 가져오면 `lottery → seathold`와 순환이 생긴다(ADR 0034).

## 5. 확인 못 한 것과 입력 간 불일치

### 5-1. 확인 못 한 것(입력 문서에서 모음)
Gateway
- 좌석 응답 한 건의 Gateway CPU, 압축률, k6 `Accept-Encoding` 기본 동작과 압축 해제 뒤 본문 처리
- Netty 이벤트 루프 실제 스레드 수, Netty가 응답 전체를 직접 메모리에 쥐는지
- Gateway `http_server_requests`의 `uri` 태그 값
- 134 실행의 k6 1초 동시 수 최대, 오픈 순간 1초 Gateway 요청률과 경로 구성
- bulkhead 거절 응답의 `Retry-After` 헤더(인증 없는 몰림이라 받지 못함)
- 프론트의 좌석·선점 503 처리, 프론트·nginx의 `traceparent` 전송 여부
- 요청당 Gateway CPU 중 Redis 호출 몫, 8차 R0 1.06ms에서 더 줄일 여지
- A0가 Retry-After를 따르는지, A0 실행의 V1(1초 실행이라 10초 표본에 안 잡힘)

reservation
- 134의 획득 대기 1.009초 때 커넥션 획득 실패(500) 여부, B2 소급 파일(노트북에 없음)의 대기 > 0 표본 수

- PostgreSQL `max_connections` 실제 값(기본 100 추정), postgres-reservation 컨테이너 이름
- 호스트 CPU "나머지" 0.36~0.44의 내역(DB 몫)
- 대사 내부 API가 오픈 직후 20초 동안 초당 59로 도는 이유
- 실제 프런트의 예매 확정 폴링 간격
- 배포 서버의 직렬화 CPU(JFR)
- 접수형 모드에서 소비자가 대기 중 커넥션을 쓰지 않는지(추정만)

좌석 자동 배치
- 구역별 실제 좌석 수(평균 600은 계산값)
- `LIMIT`과 `FOR UPDATE SKIP LOCKED`가 하위 쿼리 안에 있을 때 PostgreSQL이 `LIMIT`을 채우려 더 읽는지
- B안(추천)에서 409가 줄어드는 정도
- 공통 오류 응답에 부가 데이터 칸이 있는지
- 국내 예매 사이트의 자동 배정 동작과 범위

측정·기타
- `gave_up` 394 → 587 증가 원인(M10)
- Grafana 캡처 실패 원인이 새로고침인지(M7)
- B2의 `gave_up`·`queue_wait` p95·서버 좌석 조회 p95·Gateway CPU 최대(진행 기록에 없음)
- B2 Synthetic(회차 135)·B2 A0 결과(트러블슈팅 초안 "채울 것")
- Synthetic `action_lateness` 8분 56초의 원인은 진행 기록 S1 시점에 "확인 못 함"이었고, 뒤에 트러블슈팅 초안 8절·세부 후보 M2에서 `browse_only` 예정 시각 문제로 설명됐다(31표본 = 31명 일치)
