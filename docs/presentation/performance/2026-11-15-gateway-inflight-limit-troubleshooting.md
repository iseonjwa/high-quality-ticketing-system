# Gateway 동시 처리 상한 64가 섞인 트래픽에서 정상 요청까지 거절한 문제 (11/15, ISE-230·ISE-264)

## 1. 문제: 무엇을 봤나
- 장면: 티켓 오픈 순간 3,000명이 대기열 → 좌석 조회 → 선점 → 결제로 몰리는 O1. 배포 서버 main `e109c11c`, Gateway 상한 64(운영값), Mock PG 승인 지연 300ms.
- 증상: 서버 오류는 0인데 503이 났다. 503 전부가 Gateway 맨 앞 동시 처리 상한의 거절이었다.

| 실행 | 확정 예매 | 503 | 상한 거절 증가(지표) | 처리 중 최댓값 | 처리 못 한 오류(`error`) |
|---|---|---|---|---|---|
| O1 균일(회차 122, 18:42~19:07 KST) | 1,973 / 3,000 | 1,150(0.96%) | 1,150 | 63 | 291(좌석 조회 503 123 + 선점 503 168) |
| O1 Synthetic(회차 123, 19:08~19:33) | 2,547 / 3,000 | 1,603(1.53%) | 1,555 + auth-redis bulkhead 48 | 13(스크레이프 표본) | 8 |
| A0 ×3(19:35~19:36) | 성공률 48.2·41.3·50.6% | 518·587·494 | 1,598 + bulkhead 1 | — | — |

- 판정: 측정 유효성(V1~V4)은 통과. 정합성 "처리 못 한 오류 0"과 A0 "오류율 1% 미만"은 어겼고 원인은 모두 이 상한이다(`synthetic-data.md` 5-0: 무효가 아니라 "원인 먼저").

## 2. 가설
- 상한은 Gateway 전체에 하나이고 **요청 수만 센다**. 좌석 조회(응답 약 830KB)·선점·결제(PG 300ms)처럼 자리를 오래 잡는 요청이 64칸을 채우면, 가벼운 대기열 순번 조회까지 거절된다(경로별 리틀의 법칙 합).
- 64는 대기열 순번 조회만 몰리는 G1에서 고른 값이다(체류 40~45ms × 굿풋, 11/11·11/13). 섞인 트래픽은 그 측정 범위 밖이었다(판단 기록 `docs/ai-judgments/kangmin/2026-11-13-in-flight-limit-as-safety-net-first.md`).
- 근거: 균일 2회차의 처리 중 최댓값 63 = 상한에 붙어 있었다. 거절이 좌석 조회·선점·확정 조회·결제에 고루 퍼졌다(균일). Synthetic은 도착이 흩어져 거절이 대기열 진입에 몰렸다.

## 4-2. 중간 해석(B1·B2 균일까지)
- 상한을 올리면 **병목이 뒤로 옮겨 간다.** Gateway가 거절하던 요청이 reservation DB 커넥션 풀(5개) 앞에서 줄을 선다(Hikari 대기 10 → 22~31). 호스트 CPU는 모든 실행에서 0.99 이상이다.
- 이득은 확정 +6~9%, 대가는 선점·결제·확정 지연 증가(최대 2.3배). Gateway 메모리는 어느 값에서도 문제가 아니었다(힙 40%).
- 134가 1000보다 지연이 나쁜 이유는 실행이 1회씩이라 가를 수 없다(반복 변동 모름).
- 따라서 Gateway 상한은 "근본 조치"가 아니라 **어디서 줄을 세울지 고르는 손잡이**다. 근본 원인은 대기열 뒤 좌석 충돌로 인한 재조회(균일 409 48%)와 reservation 쪽 처리 한도(DB 풀 5, CPU 포화)다.
