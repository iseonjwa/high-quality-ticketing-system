## 0. 한 페이지 요약

1. **문제**: 티켓 오픈 순간 3,000명이 몰리는 O1에서 서버 오류는 0인데 503이 났다. 균일 1,150건, Synthetic 1,603건 전부가 Gateway 맨 앞 동시 처리 상한 64(와 인증 Redis bulkhead)의 거절이었고, 확정 예매는 균일 1,973 / 3,000명에 그쳤다.
2. **가설**: 상한 64는 가벼운 순번 조회만 몰리는 측정(G1)에서 고른 값이라, 830KB 좌석 조회·선점·결제처럼 자리를 오래 잡는 요청이 섞이면 정상 요청까지 거절한다.
3. **실험**: 상한을 1000(B1)·134(B2)로 바꿔 같은 시나리오를 다시 쟀다. 거절은 줄고 확정이 +9.0%·+6.2%(계산값) 늘었지만, 같은 요청이 reservation DB 커넥션 풀(5개) 앞에서 기다려 선점 p95가 192 → 277 → 435ms, DB 커넥션 대기 최대가 10 → 22 → 31로 늘었다. 병목은 없어지지 않고 뒤로 옮겨 갔다.
4. **뒤집힌 가정**: 상한 1000을 같은 설정으로 한 번 더 재자(E2) 확정 대기 p95 1.84s → 10.96s, 선점 500 126건·예매 조회 500 342건이 나왔다. "상한을 올리면 낫다"는 한 번의 비교는 실행 변동 안에 있었다. 또 Synthetic이 균일보다 좋아 보인 것은 도착 모양이 아니라 좌석 쏠림(409 48% 대 12%) 차이였고, 전체 요청의 73.8%인 공연 상세 조회는 98.1%가 오픈 전에 나와 병목 순간에는 0건이었다.
5. **지금의 결론(해석)**: Gateway 상한은 근본 조치가 아니라 **어디에 줄을 세울지 고르는 손잡이**이고, 서버 오류(500)를 재시도할 수 있는 거절(503 + `Retry-After: 3`)로 바꾸는 안전망이다. 처리량 천장은 호스트 CPU 포화(0.99 이상)와 reservation 처리 비용으로 본다(추정).
6. **남은 것**: X1(풀 10)은 풀이 아니라 CPU 쪽으로 나왔고(방향만), AA는 확정 +33.7%, X2②는 효과가 변동에 묻혔다. 개선 6개(I1·I2·I3·I4·I5·I7)는 dev 머지까지 끝났고 배포 서버 효과는 아직 재지 않았다. v0 X2①·R·W, v1, v2 측정이 남았다.

## 3. 회고

### 3-1. 강민 회고(말 그대로)
> "공연 상세 조회가 실제 상황에 가까운 시나리오로 적용하면 가장 앞단에서 요청이 쏠릴 것이라는 걸 미리 대비하지 못하고 늦게 문제를 발견한 것도 내 잘못이라고 할 수 있겠다"

- 무엇을 놓쳤나: 측정 내내 요청의 73.8%가 공연 상세였는데, 그것을 오픈 뒤 병목만 보는 눈으로 읽었다. 실제 오픈에서는 사람들이 오픈 직전 상세 페이지를 연타하고, 정각 0~1초에 진입을 광클한다. AI가 짠 시나리오는 진입을 오픈 +1~11초로 고르게 흩고, 새로고침을 10~30초로 느슨하게 두어 이 쏠림을 약하게 만들었다.
- 그래서 바꾼 것
  - k6에 **현실 모드**를 더한다: 오픈 전 공연 상세 조회 몰림, 오픈 0~1초 진입 광클, 확정 조회를 프론트와 같은 1초 간격으로.
  - 공연 상세를 싸게 만든다: ISE-285 1단계(서비스 안 1초 값 객체 캐시, `serverTime`·판매 상태·`traceId`는 매 요청 계산).
  - 규모로 말할 때 "오픈 전에 먼저 무너지는 곳"으로 공연 상세를 첫 번째에 둔다([규모 비교](2026-11-15-scale-comparison.md) 2-1절).
