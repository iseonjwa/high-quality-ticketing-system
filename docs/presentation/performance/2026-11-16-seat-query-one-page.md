# 좌석 조회 개선 한 장: 실패 없이 받는 양 초당 5 → 200(40배)

담당: 효승 · 이슈 ISE-189(P4a·P4b·P4c), ISE-284 · 측정 정본: [`open-peak-scenarios.md`](../../design/infra/open-peak-scenarios.md) "배포 서버: S1 좌석 조회 3단계와 Gateway 상한 값"

## 왜 좌석 조회인가

오픈 순간 대기열을 통과한 모든 사용자가 가장 먼저 부르는 API다. 15,000석 회차 하나의 응답이 약 820KB이고, 좌석 상태는 계속 바뀐다. 개선 전에는 배포 서버에서 **초당 10건에 무너졌다.**

## 한 장 요약: 병목을 하나 풀면 다음 병목이 드러났다

| 단계 | 바꾼 것 | 실패 0 최대(초당) | 그때 막힌 곳 |
|---|---|---|---|
| 개선 전 | 엔티티로 읽어 응답 만들기 | **5** | 서비스 메모리·GC(객체 3만 개, 메모리 1.11/1.125GiB) |
| 1차 P4a(#377) | 필요한 열 8개만 DTO로 바로 읽기 | **40** | DB 조인·정렬(DB CPU 약 211%) |
| 2차 P4b(#534·#603) | 바뀌지 않는 좌석 배치(구역·열·번호·등급·가격)를 서비스 메모리에 캐시. 커넥션은 DB 읽는 동안만 쥐고, 첫 요청이 몰려도 DB는 한 번 | **100** | 커넥션 풀 5(대기 최대 196) |
| 3차 P4c(#605) | 바뀌는 값(선점 가능한 좌석 ID)을 회차마다 1초 캐시 | **200** | 응답 만들기·전달 CPU(DB CPU 1~2%, 커넥션 대기 0) |

조건: 배포 서버 m7i.xlarge(4 vCPU) 한 대, 회차 104(15,000석, 응답 약 820KB), 좌석 조회만 30초 × 3회, Gateway 상한 끔, 커넥션 풀 5·대기 시한 1초, 측정 전 `ANALYZE`. 11/12(개선 전·1·2차), 11/14(2차 보강·3차).

## 단계마다 무엇을 보고 다음을 골랐나

1. **개선 전 → 1차**: 처음에는 쿼리가 느리다고 봤지만, 같은 쿼리를 DTO로 읽으면 커넥션을 쥔 시간이 18~20ms였다. 원인은 트랜잭션 안에서 객체 3만 개를 만드는 동안 쥔 커넥션과 GC였다([트러블슈팅 TS-75](../troubleshooting/2026-11-16-seat-query-entity-connection-hold.md)).
2. **1차 → 2차**: DB CPU가 찼다(로컬 초당 200에서 postgres 최고 408%). 좌석 배치는 회차를 만든 뒤 바뀌지 않으니 매번 조인할 필요가 없다. 바뀌는 값(상태·회차 등급)은 캐시에 넣지 않아 무효화가 필요 없다. Redis 대신 서비스 메모리에 둔 이유는 세 가지다. 서버끼리 맞출 값이 없고, Redis는 요청마다 약 1MB(권우 님 측정에서는 1.3MB)를 받아 15,000개 객체를 다시 만들어야 하고(1차에서 줄인 일이 돌아온다), Gateway·대기열이 같이 쓰는 Redis에 부담을 주지 않는다(같은 조건 p95 7.0ms 대 38.3ms, ADR 0054). 로컬 초당 150에서 postgres CPU 평균 136% → 21%였다.
   - **2차 보강(#603), 같은 기능의 두 구현 합치기**: 권우 님 측정 브랜치에도 2차가 따로 있었다. 코드로 커넥션 쥐는 구간, 상태 쿼리, 캐시가 빈 순간 몰림을 항목별로 비교해 나은 쪽(커넥션은 DB 읽는 동안만, 몰려도 DB는 한 번)을 합쳤다. 처음엔 "성능도 낫다"고 봤지만 측정해 보니 처리량은 같았다. 그래서 성능 개선이 아니라 안정성 개선(몰릴 때 500 0)으로만 적었다.
3. **2차 → 3차**: 남은 DB 읽기는 "지금 잡을 수 있는 좌석"뿐인데, 초당 수백 번 같은 값을 읽었다. 1초 캐시로 회차마다 1초에 한 번만 읽는다. 최대 1초 낡은 좌석이 보일 수 있지만, 중복 판매는 선점의 조건부 UPDATE가 막는다(409 비율 76.6% → 76.9%로 거의 같음).

응답 JSON은 모든 단계에서 그대로다. 단계마다 응답 바이트를 비교해 같음을 확인했다.

## 측정하다 함께 찾은 것

| 발견 | 결과 |
|---|---|
| 새 회차에서만 4배 느림(낡은 통계로 Nested Loop) | 좌석 생성 직후 ANALYZE를 운영 코드로 넣음(ISE-284, [트러블슈팅](../troubleshooting/2026-11-16-stale-statistics-nested-loop.md)) |
| 큰 응답이 Gateway 동시 처리 자리를 잡아 다른 API까지 503 | 상한 64 유지, 대기열 입장 속도로 양을 묶음([트러블슈팅](../troubleshooting/2026-11-16-large-response-gateway-limit.md)) |
| 상한을 키우면? | 3차 초당 800에서 64·128·256 모두 30초 성공 약 8,900건으로 같고 p95만 0.36 → 0.8 → 2초 |

## 남은 한계(다음 병목)

- 3차 처리 한도는 초당 약 295건이다. DB가 아니라 820KB 응답을 만들고(서비스 약 220%) 전달하는(Gateway 230~280%) CPU가 4코어를 채웠다. 둘 중 어느 쪽이 큰지는 재지 않았다.
- 다음 수단은 응답 크기다(압축, 배치·상태 분리). 압축은 CPU와 맞바꾸고 배치·상태 분리는 화면도 바꿔야 해서 이번에는 하지 않았다.
- 측정·시연 시드는 11/16부터 1,500석이다(ADR 0060). 응답도 약 10분의 1로 줄어든다(계산값). 위 숫자는 모두 15,000석 기준이다.

## 예상 질문

- **왜 처음부터 캐시하지 않았나?** 개선 전 병목은 DB가 아니라 객체 생성과 커넥션 점유였다. 캐시부터 넣었으면 원인을 가린 채 메모리 문제를 키웠을 것이다. 병목이 DB로 옮겨 간 2차에서 캐시를 넣었다.
- **1초 낡은 상태는 괜찮은가?** 화면은 최대 1초 낡을 수 있지만 판매 판정은 선점이 DB에서 한다. 측정에서 409 비율 변화는 0.3%p였다.
- **서버를 늘리면?** 3차 한도는 한 대 4코어 CPU다. 서비스·Gateway를 나누거나 늘리면 오르겠지만 재지 않았다.
