# 좌석 조회 실패가 "차단기가 열려서"? 장치가 재는 구간을 확인해 원인을 가름

담당: 효승 · 정본: [TS-78](../../troubleshooting.md) · 차단기 자체의 개선: 강민(ISE-233, ADR 0050, TS-56)

## 1. 증상

11/10 배포 서버에서 좌석 조회를 재는 중 이런 순서가 보였다.

```
504(서비스 3초 시한) → 정확히 10초 동안 4ms짜리 503(차단기 OPEN) → 다시 504
```

503이 "차단기가 열려서"였으니 좌석 조회 실패의 원인도 차단기로 보일 수 있었다.

## 2. 원인: 장치가 무엇을 재는지부터 확인

| 확인한 것(라이브러리 소스) | 뜻 |
|---|---|
| 차단기는 Gateway의 Redis 확인(`auth:blacklist:<jti>`, 로그아웃된 토큰)만 잰다 | 서비스 호출(3초, 504)은 차단기가 재지 않는다 |
| 시간을 재는 시계가 Gateway다 | Gateway가 바쁘면(스레드·CPU·GC) Redis가 멀쩡해도 "느림"으로 셀 수 있다 |
| 11/11 정상 측정, 초당 50: 차단기 열림 0, 실패는 전부 504 | 실패의 원인은 차단기가 아니다 |
| 같은 때 커넥션 대기 최대 59~124 | 원인은 예매 DB 15,000행 조인·정렬과 커넥션 5개 앞의 줄 |

결론: 서비스가 먼저 무너지고, Gateway가 바빠져 차단기가 **뒤따라** 열린 것이다. 차단기 OPEN은 원인이 아니라 결과였다.

## 3. 해결

- 좌석 조회는 서비스 쪽(DB·커넥션)에서 풀었다([좌석 조회 개선 한 장](../performance/2026-11-16-seat-query-one-page.md)).
- 차단기 설정안(ISE-230)을 그대로 받지 않고 측정 설계 문제를 짚었다.
  - 시간 창 10초·최소 500건이면 초당 50건 미만은 판정을 안 해 전후 비교가 안 된다.
  - 한 측정에서 Gateway 설정과 DB 풀(5 → 20)을 함께 바꾸면 무엇이 효과를 냈는지 모른다.

## 4. 발표 한 줄

"차단기가 열렸다"는 추측 대신 차단기가 재는 구간을 소스로 확인하고, 차단기 상태와 커넥션 대기를 같은 시간축에 놓아 원인과 결과를 갈랐다.
