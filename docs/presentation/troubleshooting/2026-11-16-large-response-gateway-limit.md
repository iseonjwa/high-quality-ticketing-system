# 서비스는 17ms인데 Gateway가 503: 큰 응답이 동시 처리 자리를 잡음

담당: 효승 · 정본: [TS-77](../../troubleshooting.md) · 상한 결정의 배경: [Gateway 과부하 한 장](../performance/2026-11-14-gateway-overload-one-page.md)(강민)

## 1. 증상

11/12 로컬(노트북 1대), 2차 개선 뒤 좌석 조회(15,000석, 응답 약 820KB)를 Gateway 경유로 보냈다.

| 초당 | k6가 본 중앙값 | Gateway 처리 | 서비스 처리(중앙값) | 실패 |
|---|---|---|---|---|
| 200 | 18ms | 13ms | 10ms | 0 |
| 400 | 714ms | 22ms | 17ms | 0 |
| 500 | **2.35s** | 44ms | 17ms | **1.79%(172건)** |

실패는 상한 거절 카운터 +177과 맞았고, 상태 코드를 남긴 재실행에서 503 `GATEWAY_OVERLOADED` 100건(0.8%)을 확인했다. 서비스는 끝까지 빨랐고, 커넥션 대기 0, 인증 차단기 열림 0이었다. 그런데도 503이 났다.

## 2. 원인: 어떻게 찾았나

처음 해석(AI 포함)은 "노트북 한 대에서 k6와 서버가 같이 돌아 생긴 측정 환경 한계"였다. 그렇게 넘기지 않고 k6·Gateway·서비스 시간을 따로 재고 요청마다 상태 코드를 남겨 다시 봤다.

1. 재실행의 503 코드가 `GATEWAY_OVERLOADED`였다. Gateway 맨 앞 동시 처리 상한(64)의 거절이다. 이 거절은 요청 로그에 남지 않고 `gateway_in_flight_rejected_total`에만 남는다(재실행 거절 100건 = 카운터 +99).
2. 성공 요청을 쪼개 보니 첫 바이트까지 105ms, **본문 받기 1.73s**(p95 2.66s)였다.
3. 코드(`InFlightLimitHandlerDecorator`): 자리는 응답 마지막 조각을 넘길 때까지 잡힌다.

```
동시에 잡힌 자리 = 초당 요청 × 자리 잡는 시간
                 ≈ 500 × 1.73s  →  64를 훌쩍 넘는다
```

서버가 빨리 만들어도 받는 쪽이 느리면 큰 응답이 자리를 오래 잡는다. 이 상한은 Gateway 전체에 하나라, 좌석 조회가 자리를 차지하면 로그인·대기열·선점·결제도 503을 받는다.

## 3. 해결: 상한 값은 그대로, 들어오는 양과 응답 크기로 다룬다

배포 서버에서 상한 값을 바꿔 다시 쟀다(11/14).

| 상한(3차, 초당 800) | 30초 성공 | p95 |
|---|---|---|
| 64 | 약 8,800~9,100 | 0.35~0.36s |
| 128 | 약 8,800~8,900 | 0.79~0.84s |
| 256 | 약 8,900~9,100 | 1.89~2.11s |

- 상한을 키워도 성공은 같고(서버 CPU가 한도), 넘친 요청이 503 대신 줄을 서서 지연만 늘었다.
- 커넥션이 막히는 구간(2차 보강, 초당 200)에서는 64가 시한 초과 500을 약 2,000건에서 29~53건으로 줄이고 성공을 약 15% 늘렸다.
- 로컬에서는 256이 낫게 보였지만 배포 측정이 뒤집었다. 상한을 끈 쪽의 "실패 0"도 착시였다. k6 VU 400개가 느린 응답을 기다리느라 다 묶여 요청을 덜 보낸 것이고(회당 약 15,000건 못 보냄), 실제 처리는 같은 초당 약 290건이었다.
- 그래서 64를 유지한다. 큰 응답 위험은 대기열 입장 속도(초당 50명)가 양을 묶어 다룬다. 측정·시연 시드는 11/16부터 1,500석이라 응답도 약 10분의 1이다(계산값).

## 4. 발표 한 줄

서비스 지표만 보면 놓치는 503을, 거절 카운터와 "본문 받는 시간"으로 찾아 "동시 수 = 초당 × 자리 잡는 시간"으로 설명했다.
