# 좌석 조회가 초당 수십 건에 무너짐: 느린 쿼리가 아니라 "커넥션을 쥔 채 객체 3만 개 만들기"

담당: 효승 · 정본: [TS-75](../../troubleshooting.md) · 이어지는 개선: [좌석 조회 개선 한 장](../performance/2026-11-16-seat-query-one-page.md)

## 1. 증상

| 환경 | 부하 | 결과 |
|---|---|---|
| 로컬(노트북, Gateway 경유) | 좌석 조회 초당 50, 15,000석 회차 | p95 2.68s, Gateway 3초 시한 504 4건(서비스는 200) |
| 배포 서버(4코어) | 초당 10 | 500 2.6~7.0%, 서비스 메모리 1.11/1.125GiB. 실패 0으로 버틴 최대는 초당 5 |

좌석 조회는 오픈 직후 모든 사용자가 가장 먼저 부르는 API다. 이 상태로는 대기열이 초당 50명만 들여보내도 버티지 못한다.

## 2. 원인: 어떻게 찾았나

처음 가설은 "조인·정렬 쿼리가 느리다"였다. 지표를 같이 보니 아니었다.

| 본 것 | 값(로컬, 초당 50) | 뜻 |
|---|---|---|
| 커넥션을 쥔 시간 | 107ms(초당 30에서 74ms) | 쿼리만이 아니라 다른 일도 하는 동안 쥐고 있다 |
| 커넥션을 기다린 시간(풀 5) | 평균 1,377ms, 줄 최대 115 | 다음 요청이 커넥션을 못 받고 줄을 선다 |
| GC 멈춤 | 30초 중 8.3초 | 요청마다 큰 객체 묶음이 생긴다 |
| 같은 쿼리를 DTO로 읽을 때 쥔 시간 | 18~20ms | DB 쿼리 자체는 빠르다 |

원인은 `@Transactional` 안에서 회차 좌석과 공연장 좌석을 엔티티로 읽어 **객체 30,000개를 만드는 동안 커넥션을 쥔 것**이었다. 커넥션 풀이 5개라 쥐는 시간이 길어지면 바로 줄이 생기고, 객체가 많아 GC도 자주 멈췄다.

## 3. 해결

- 1차(PR #377): 엔티티 대신 화면에 필요한 열 8개만 DTO로 바로 읽는다. 응답 JSON은 그대로 두고 바이트 비교로 같음을 확인했다.
- 고르지 않은 것: 커넥션 풀 늘리기. 쥐는 시간이 그대로면 줄만 뒤로 밀린다.

## 4. 결과(로컬, 같은 조건 초당 50)

| | 전 | 후 |
|---|---|---|
| p95 | 2.68s | 40ms |
| 커넥션 대기 | 1.4초 | 0.01ms |
| GC 멈춤(30초 중) | 8.3초 | 0.18초 |

배포 서버에서는 실패 0 최대가 초당 5 → 40이 됐고, 2·3차 개선으로 200까지 올렸다(performance 한 장).

## 5. 발표 한 줄

"느리다"를 쿼리 탓으로 단정하지 않고 커넥션을 쥔 시간·대기·GC를 같이 봐서, 원인이 쿼리가 아니라 트랜잭션 안의 객체 생성이라는 것을 찾았다.
