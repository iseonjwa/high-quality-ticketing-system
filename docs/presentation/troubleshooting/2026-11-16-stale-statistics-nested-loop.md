# 같은 코드인데 새 회차에서만 4배 느림: 낡은 DB 통계와 Nested Loop

담당: 효승 · 정본: [TS-76](../../troubleshooting.md) · 이슈 ISE-284(PR #678)

## 1. 증상

| 날짜 | 회차 | 좌석 조회 초당 20 | DB CPU |
|---|---|---|---|
| 11/11 | 기존 회차 | 43ms, 실패 0 | 약 73% |
| 11/12 | **새로 만든 회차 104** | 중앙값 1.25s, **실패 40%**(커넥션 대기 1초 초과 500) | **약 310%** |

코드도 서버도 같았다. 다른 것은 회차뿐이었다.

## 2. 원인: 어떻게 찾았나

1. `pg_stat_activity`: 좌석 조회 4~5개가 동시에 0.07~0.6초씩 돌고 있었다. 혼자 돌리면 28ms다. 쿼리가 서로 CPU를 다투고 있었다.
2. 실행 계획: DB가 회차 104의 좌석 수를 **1행**으로 짐작하고 한 건씩 찾는 방식(Nested Loop)을 골랐다. 실제는 15,000행이었다(버퍼 약 46,000).
3. 통계: 회차 104는 마지막 자동 통계 갱신 뒤에 생겨 통계에 없었다.

왜 자동 갱신이 안 돌았나:

| | 값 |
|---|---|
| 자동 갱신 기준 | 바뀐 행 > 50 + 표 행 수 × 10% |
| `schedule_seats` 표 | 156만 행(측정 회차를 지우지 않아 쌓임) → 기준 약 15만 6천 행 |
| 새 회차 하나 | 15,000행(약 1%) → 기준에 못 닿음 |

운영도 지난 회차를 지우지 않으므로 측정만의 문제가 아니다. 오픈 직전에 만든 회차가 이 상태로 트래픽을 받는다.

## 3. 해결

- 그날: `ANALYZE schedule_seats`를 손으로 돌렸다. Hash Join으로 바뀌어 초당 20에서 42ms, p95 73ms, 실패 0, DB 약 67%가 됐다.
- 고친 것(ISE-284): 회차 좌석 생성 API가 좌석을 커밋한 직후 시스템이 `ANALYZE schedule_seats`를 돌린다. ANALYZE는 표본(약 3만 행)만 읽고 읽기·쓰기를 막지 않는다. 실패해도 좌석은 이미 만들어졌으니 성공으로 답하고 경고 로그만 남긴다.

| 검토한 방법 | 판단 |
|---|---|
| 좌석 생성 직후 ANALYZE | **채택**. 만든 즉시 통계가 맞는다 |
| 표별 자동 갱신 기준 낮추기 | 기각. 1분 주기만큼 늦고, 기준보다 작은 공연장은 안 돌고, 오픈 중 좌석 상태 변경으로 오히려 자주 돈다 |
| 같은 트랜잭션 안·커밋 직후 콜백에서 ANALYZE | 기각. 커밋 전이거나, 콜백이 원래 커넥션을 쥐고 있어 ANALYZE가 커밋되지 않는다. 생성 트랜잭션을 `ScheduleSeatCreator`로 떼고 커밋 뒤 따로 부른다 |

## 4. 결과

| 확인 | 결과 |
|---|---|
| 로컬 테스트 | 새 회차 추정 행 수 8 → 실제(1,500)에 가깝게 |
| 배포 서버(11/16, 표 259만 행) | 회차 생성 0.38초 뒤 통계 갱신, 실행 계획 Hash Join, ANALYZE 203ms |

측정 전에 손으로 돌리던 ANALYZE가 필요 없어졌다.

## 5. 발표 한 줄

"같은 코드, 다른 결과"를 실행 계획의 추정 행 수와 실제를 비교해 풀었고, 측정용 임시 조치(손 ANALYZE)를 운영 코드로 옮겼다.
