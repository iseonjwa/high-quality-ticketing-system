## 한눈에 보기

- **쓸모없이 분리된 서비스: Lottery.** 두 리뷰어 모두 Reservation에 병합해야 한다고 판정했다. 분리 근거가 SA 문서 자신의 진행 순서와 모순된다.
- **Queue는 의견이 갈렸다.** codex는 Reservation 내부 모듈로 강등(3개 구성), Claude는 조건부 유지(4개 구성). 종합 권고는 **4개 (User / Queue / Reservation+추첨 / Payment)**.
- **서비스 수보다 급한 문제 3가지**
  1. PG 타임아웃을 결제 실패로 취급하고 있다
  2. 발제 필수 항목이 P1(실제로는 마지막 주)에 몰려 있다
  3. 좌석 상태 전이 규칙이 없다

### Lottery를 병합해야 하는 이유 (두 리뷰어 공통)

- SA의 진행 순서가 "응모 기간 → 응모 마감 → 추첨·자동결제 → 일반 예매 오픈"이다. 추첨 처리와 실시간 선점은 시간이 겹치지 않으므로 격리할 대상이 없다.
- SA 스스로 응모 수요가 "응모 기간 전체로 분산되어 피크 트래픽이 줄어든다"고 썼다. "응모 기간 트래픽"을 분리 근거로 들기 어렵다.
- 무거운 작업은 분리해도 다른 서비스가 한다. 좌석 배정·발권은 Reservation이, 결제는 Payment가 맡는다.
- 비용은 크다. 3-서비스 추첨 SAGA, Lottery DB, 이벤트 계약 2쌍(Lottery↔Reservation, Lottery↔Payment)이 새로 생긴다. "예비 승계 중 이중 배정"도 한 DB 안이면 조건부 상태 전이로 끝나지만, 서비스를 나누면 분산 정합성 문제가 된다.
- *(종합 시 추가)* 운영자가 Lottery에서 "추첨 배정 좌석"을 정하는데, 좌석은 Reservation 소유다. 설정 단계부터 서비스 경계를 넘는 쓰기가 생긴다.
- 병합하면 추첨 자동결제가 일반 예매와 같은 결제 이벤트 계약(PaymentRequested / Completed / Failed)을 그대로 쓴다. 결제방식 필드(BILLING)만 추가하면 된다. 발제 필수 SAGA는 Reservation↔Payment 하나로 충족된다.
- 모노레포 규칙("서비스 모듈끼리 직접 의존 금지")과 충돌하지 않도록, lottery는 reservation-service 안의 패키지로 둔다고 명시한다.

### Queue 조건부 유지

- 두 리뷰어 모두 SA의 근거("순번 조회 폭주가 좌석 선점까지 번지지 않게 격리")가 절반만 맞다고 봤다.
  - Redis 하나를 Reservation(선점·캐시), Gateway(토큰 블랙리스트·요청 제한)와 같이 쓴다.
  - Queue가 죽으면 입장 토큰이 나오지 않아 예매도 멈춘다. 장애 격리가 성립하지 않는다.
- 그래도 4개를 권하는 이유: Queue는 분리 비용이 가장 낮다. DB가 없고, SAGA에 참여하지 않으며, Reservation은 Queue를 호출하지 않고 서명 토큰만 검증한다. "QPS가 가장 높은 폴링 엔드포인트를 따로 확장한다"와 "대기열 정책과 예매 정책은 바뀌는 이유가 다르다"는 실제로 성립한다.
- 유지 조건
  1. 나눈 이유를 "독립 확장 + 입장 관문"으로 바꿔 쓴다
  2. Queue 전용 Redis를 두거나, 두지 않으면 '격리' 주장을 뺀다
  3. 인스턴스가 여러 개일 때 입장 속도를 전역 카운터(Redis Lua)로 제어한다. 인스턴스마다 스케줄러가 돌면 입장 속도가 배가 된다
- 팀이 더 단순하게 가고 싶다면 codex 안(3개)도 타당하다. 발제 추천 구성(User / Product / Order)과 같은 규모다.

### AI 검증 로그 #0 수정 필요

- 지금 로그의 유일한 '거부' 사례 근거가 Lottery 분리 논리다. 발제상 "심사 시 AI 활용 부분도 … 랭킹에 반영"되므로 발표 때 가장 먼저 반박당할 지점이다.
- 4개로 바꾸면 이렇게 고쳐 쓸 수 있다: "3개 권고는 거부(근거: Queue는 독립 확장·입장 관문), 4개 절충안은 수용(근거: Lottery 분리 근거가 진행 순서와 모순)". 거부 사례와 수용 사례가 하나씩 남는다.

## Critical

### C1. PG 타임아웃은 실패가 아니라 "결과 모름"이다 (두 리뷰어 공통)

- 목표 표의 "결제 거절·**타임아웃**·선점 만료 시 좌석·예매·결제 상태가 자동 원복"은 위험하다. PG가 실제로는 승인했다면 돈은 빠져나갔는데 좌석은 다른 사람에게 팔린다. AI 프롬프트 #3에는 "PG 타임아웃(결과를 모름)"이라고 직접 적어 두어, 목표 표와 모순된다.
- 결제 상태에 UNKNOWN을 추가한다. 멱등키(reservationId)로 Mock PG에 결과를 조회해 승인·거절이 확정된 뒤에만 SAGA를 진행한다.
- Circuit Breaker OPEN(PG 호출 전 거절)은 안전하게 보상해도 된다. 호출 도중 타임아웃은 조회 대상이다.
- 결제 진행 중(PAYING)인 예매는 만료 스케줄러에서 제외하고 별도의 결제 마감 시한을 둔다. 만료 뒤 승인이 도착하면 보상은 "좌석 복구"가 아니라 "자동 환불"이다.
- Mock PG에 결제 조회 API, "승인 후 응답 유실" 모드, 멱등 승인·환불을 넣는다.
- 검증 기준 수정안: 거절·CB OPEN·만료는 원복한다. 타임아웃은 조회로 확정한다. 만료 뒤 승인은 자동 환불한다.
- 실제 PG사의 처리 방식은 [02-pg-timeout-handling.md](02-pg-timeout-handling.md) 참고.

### C2. 우선순위가 거꾸로 되어 있다 (두 리뷰어 공통)

- 발제 필수 항목(Kafka 비동기 접수, Outbox·멱등, Circuit Breaker, Grafana 대시보드, Synthetic Data, AWS 배포)이 P1에 있다. P1에 쓸 수 있는 시간은 사실상 트러블슈팅 기간(11/9~16, 6영업일)이다.
- 반대로 발제 필수가 아닌 빌링키 자동결제(F5-4·5), 추첨 흐름(F6), 취소·환불 SAGA(F4-6·F5-3)가 P0에 있다.
- 11/6 MVP 시연에서 발제는 "성능 Test & 배포", "AI 활용 현황 (설계 검증 로그, Synthetic Data 생성 현황)"을 확인한다. P1에 두면 시연에서 보여줄 수 없다.
- Kafka 비동기 접수는 API 계약을 바꾼다(동기 결과 → 접수 후 조회). 나중에 바꾸면 프론트, SAGA 시작점, 부하 스크립트가 함께 흔들린다.
  - 계약은 2차 SA API 명세에서 최종 형태로 정한다.
  - 구현은 동기 v1 → 비동기 v2로 간다. 이 과정이 그대로 발제가 원하는 "개선 전/후" 비교 스토리다.
- Outbox를 P1로 미루면 P0에서 KafkaTemplate 직접 발행으로 짠 SAGA 발행 경로를 서비스마다 다시 짜야 한다.
- 추첨은 P0인데 실패 시 좌석 반환(F6-6·7)은 P1이다. P0만으로는 결제에 실패한 당첨자의 좌석이 어디에도 속하지 않는다.
- **P0로 올릴 것**: 입장 토큰 검증 필터, PG 타임아웃 + Circuit Breaker, 결제 멱등·서버 금액 검증, Outbox 한 경로(Reservation→Payment) + 멱등 처리 테이블, Synthetic Data 1차본과 기준선 측정, 배포 1회
- **P1로 내릴 것**: 취소·환불 SAGA, 자동결제 재시도. 추첨은 일반 예매↔결제 SAGA가 동작한 뒤 성공 경로만 P0 후반에 둔다. 추첨을 P0에 두려면 실패 시 좌석 해제까지 P0로 함께 올린다.

### C3. 좌석 상태 규칙이 없다 (두 리뷰어 공통)

- 지금은 "원자적 선점 + DB 제약 이중 방어"라는 방향만 있다.
- `UNIQUE(seat_id)`로 막으면 취소·만료 뒤 같은 좌석을 다시 팔 수 없다. 대안은 두 가지다.
  - 부분 유니크 인덱스 `UNIQUE(schedule_id, seat_id) WHERE status IN ('HELD','PAYING','SOLD')`
  - `UPDATE … WHERE id IN (…) AND status='AVAILABLE'` 실행 후 영향 행 수가 요청 좌석 수와 같은지 검사
- 1인 최대 매수 안에서 여러 좌석을 고르므로 전부 성공하거나 전부 실패해야 한다. 사용자별 최대 매수도 동시 요청을 포함해 검증한다.
- Redis TTL(5분)과 DB 만료 시각이 따로 움직이면 한쪽만 풀린 상태가 생긴다. 정본은 DB로 두고, 만료는 DB 스케줄러(`FOR UPDATE SKIP LOCKED`)가 처리하면서 Redis 키도 지운다.
- 모든 상태 전이는 `WHERE status = 이전상태`를 붙인 조건부 UPDATE로 한다.

## Major

### M1. Kafka 비동기 접수 설계가 비어 있다 (두 리뷰어 공통)

자세한 설명은 [03-seat-hold-kafka-design.md](03-seat-hold-kafka-design.md) 참고.

- 파티션 키
  - 회차 ID: 인기 회차 하나가 한 파티션에 몰려 병렬 처리가 사라진다.
  - 좌석 ID: 한 요청에 좌석이 여러 개라 전부 성공/전부 실패의 원자성이 깨진다.
  - 결론: **Kafka 파티션 순서를 정합성 수단으로 쓰지 않는다.** 정합성은 Redis·DB가 지키고, 키(userId 또는 reservationId)는 부하 분산과 한 사용자의 순서 보장에만 쓴다. 발제 요구대로 "왜 그 파티션 수·키를 선택했는지" 한 줄로 기록한다.
- 결과 전달: 접수 응답 뒤 "처리 중 / 선점 성공 / 선점 실패"를 조회하는 API가 필요하다. 5분 선점 시간은 선점 확정 시점부터 센다.
- 발신 유실: 접수 API에는 DB 쓰기가 없어서 Outbox가 맞지 않는다. `acks=all` + idempotent producer로 보내고 send 결과를 확인한다. 실패하면 Redis 선점을 지우고 503을 반환한다.
- *(Claude 제안)* 혼합형: API에서 Redis Lua로 여러 좌석을 원자적으로 선점해 결과를 즉시 반환하고, 성공분만 Kafka에 적재하고, Consumer가 DB에 기록한다(DB 제약이 2차 방어). "선택 완료 버튼을 누를 때 선점"이라는 팀 결정과 잘 맞는다.

### M2. SAGA 방식과 결제 진입 경로가 정해지지 않았다 (Claude)

- Orchestration과 Choreography 중 무엇을 쓸지가 아직 AI 검증 질문으로만 남아 있다. 발제는 "어떤 방식을 선택했는지, 왜 선택했는지 한 줄로 기록"을 요구한다.
- 사용자가 어느 API로 결제를 요청하는지, Payment가 서버 측 금액 검증(H6)에 쓸 금액을 어디서 얻는지 없다. Payment가 결제 API를 직접 받으면 예매 생성 이벤트보다 결제 요청이 먼저 도착할 수 있다.
- 제안
  - Reservation을 오케스트레이터로 두고 예매 상태 머신에 SAGA 상태를 둔다: PENDING → PAYING → CONFIRMED(+티켓) / FAILED → 좌석 반환 / EXPIRED / CANCEL_REQUESTED → REFUNDED → CANCELLED
  - 사용자는 `POST /reservations/{id}/payment`를 호출한다. Reservation이 Outbox로 PaymentRequested(amount, idempotencyKey)를 발행하고, Payment는 이벤트에 담긴 금액만 신뢰한다.
  - 일반 예매와 추첨 자동결제가 같은 상태 머신을 쓴다.
- 취소 시 티켓 무효화(첫날 회의 목록에 있었음)가 SA에서 빠졌다. *(codex)*

### M3. MVP에서는 대기열과 매크로 방지를 우회할 수 있다 (두 리뷰어 공통)

- 토큰 발급(F3-3)은 P0인데 "입장 토큰 없는 예매 요청 차단"(H3)은 P1이다. MVP에서는 선점 API를 직접 호출할 수 있어서 "대기열 무조건 필요" 결정이 효력이 없다. 토큰 검증 필터는 서명 검증 하나라 비용이 작으니 P0로 올린다.
- "보안문자 → 프론트에서 처리": 매크로는 프론트를 거치지 않고 API를 직접 부른다. 보안문자는 대기열 진입 API에서 서버가 검증해야 한다. 일정이 부족하면 보안문자를 빼고 서버 측 중복 제한부터 구현한다.
- 서명 토큰은 무상태라 Queue는 누가 나갔는지 모른다. 그래서 "한 명 나가면 다음 사람 입장"은 불가능하고 일정한 속도로 입장시키는 방식만 된다. "초당 N명 입장, 토큰 TTL T → 동시 활성 인원 최대 N×T"를 문서화한다.
- 토큰 클레임에 userId·scheduleId·exp를 묶어 공유·재사용을 막는다.

### M4. 검증 기준을 판정할 수 없거나 당연히 참이다 (두 리뷰어 공통)

- "같은 좌석 동시 요청 중 1건만 성공"과 "오류율 0%에 근접"이 부딪친다. 경합 테스트에서는 실패가 정상이다. 409(업무상 거절)와 5xx·타임아웃(오류)을 구분해 정의한다.
- 접수 응답(202)의 처리량은 실제 처리량이 아니다. Consumer lag과 접수→확정 지연을 함께 기록한다.
- 발제 필수 설정인 "**1초 안에 모두 시작**"(Ramp-up 1)과 지표 "**요청 당 평균 응답 시간**"이 목표에서 빠졌다.
- "PG 장애 중에도 조회·대기열은 정상 동작"은 구조상 당연히 참이다(조회·대기열은 Payment를 거치지 않음). 의미 있는 기준으로 바꾼다: PG 장애 중에도 선점·예매 생성은 정상, 결제 요청은 CB OPEN으로 즉시 거절, 미결제 좌석은 만료로 반환, PG 복구 후 HALF_OPEN → CLOSED.
- "이벤트 유실 0건·중복 0건"은 측정 방법이 없다. 장애를 주입하고(커밋 직후 프로듀서 중단, 처리 중 Consumer kill, 같은 이벤트 재발행) outbox·처리 이력·예매 상태를 대사 쿼리로 맞춰 본다. 브로커 1대 구성의 브로커 유실은 범위 밖이라고 명시한다.
- 부하 테스트 실무
  - 가상 사용자 100명 모두에게 JWT와 입장 토큰이 필요하다. 테스트 프로파일에서 입장 속도 제한을 풀거나 토큰을 미리 발급한다.
  - 측정할 때마다 좌석 상태를 초기화하는 스크립트가 필요하다.
  - H1의 IP 단위 요청 제한이 JMeter의 단일 IP를 막지 않게 예외를 둔다.
  - *(종합 시 추가)* 1인 최대 매수 제한 때문에 한 사용자가 10회 선점하면 몇 번째부터는 업무상 거절이 난다. 좌석 수와 사용자 행동을 맞춘 시나리오가 필요하다.

### M5. 트랙 분담이 고르지 않다 (두 리뷰어 공통)

- 트랙 A의 담당이 "전부"라서 책임자가 없다. 그런데 Gateway 인증 필터와 docker-compose는 모든 트랙 P0의 선행 조건이다. "공통부분을 각자 구현해 보고 통합"은 9영업일 MVP에서 같은 일을 다섯 번 하는 셈이다.
- "최소한의 프론트엔드"는 확정됐지만 어느 트랙에도, 우선순위 표에도 없다. MVP 시연은 유저 시나리오를 실시간으로 보여주는 방식이라 프론트가 필요하다.
- 부담 쏠림
  - 트랙 D: Payment, Mock PG, H6·H7·H8에 더해 모든 트랙이 기다리는 Kafka 신뢰성 공통 모듈까지 맡는다.
  - 트랙 E: 개발 리드 업무에 가장 의존이 많은 3-서비스 추첨 SAGA까지 맡는다.
  - 트랙 B: Queue에 더해 Reservation 코드베이스의 F2·H2, 모든 서비스가 완성돼야 할 수 있는 H11 주관까지 맡는다.
- 제안
  - 트랙 A 책임자 1명을 정하고 10/29까지 "걷는 뼈대"를 만든다: compose 한 번으로 Gateway → 서비스 1개 → Kafka → Prometheus가 뜨는 상태.
  - 프론트 담당과 화면 범위(대기 화면, 좌석 배치도, 결과 화면)를 정한다.
  - Lottery 병합으로 트랙 E 범위가 줄면 리드가 트랙 A나 프론트 일부를 맡는다.
  - Kafka 공통 모듈은 트랙 C(발행·Outbox)와 트랙 D(멱등 소비·DLQ)가 나눠 첫 주 안에 낸다.
  - H11은 트랙 B가 시나리오·Synthetic·스크립트를, 대상 API 튜닝은 트랙 C가 맡는다.

### M6. 추첨 규칙에 빈칸이 많다 (두 리뷰어 공통)

- 예비 당첨자의 등급·매수가 당첨자와 다를 때 어떻게 승계하는지 없다.
- 좌석 자동 배정 시 연석 보장 여부가 없다.
- 결제 실패 유형(잔액 부족, 타임아웃, CB OPEN)별 재시도·승계 규칙이 없다. PG 장애로 승계가 멈추면 일반 예매 오픈 시각을 넘긴다.
- 응모 시 결제수단 등록 여부는 Payment 소유 데이터인데, 확인 방법이 없다.
- 추첨 재실행 시 새 당첨자가 생기지 않게 하는 규칙, 마감 직후 늦게 처리된 응모 처리가 없다. *(codex)*
- 1차 단순화 제안 *(Claude)*: 등급별 응모, 매수 1~2매 고정, 연석 미보장, 같은 등급·매수의 예비자에게만 승계, 실패 시 한 번 조회로 확정 후 승계, 승계 마감은 일반 오픈 30분 전.
- H9의 "응모 Kafka 비동기 접수"와 "자동결제 파티셔닝"은 과하다. SA 스스로 응모 수요가 분산된다고 썼다. 1인 1응모는 `UNIQUE(lottery_id, user_id)`로 충분하다.

### M7. Outbox·멱등·DLQ가 이름만 묶여 있다 (codex)

- Outbox는 각 서비스의 업무 변경과 같은 DB 트랜잭션에 들어가야 한다. Payment 담당이 공통 모듈을 만들어도 Reservation 트랜잭션에 자동 적용되지 않는다.
- Consumer의 중복 판정 기록과 업무 변경도 원자적으로 처리한다. 이벤트 ID뿐 아니라 결제·배정 같은 업무 식별자의 중복도 막는다.
- 재시도 횟수·간격, DLQ 확인 담당자, 재처리 방법을 정한다.
- 발제 요구는 유실 방지 "1개 이상의 기능 구현"이다. Outbox·DLQ 전부를 발제 필수로 해석할 필요는 없으니, 필요한 최소 경로부터 검증한다.
- PG 호출 동시 실행 수 제한이 필요하면 Circuit Breaker에 Bulkhead를 조합한다(CB는 동시 실행 수를 제한하지 않음).

## 팀원들과 논의할 부분

### 아키텍처

1. **서비스 구성**: 4개(User / Queue / Reservation+추첨 / Payment) vs 3개(Queue도 Reservation 모듈) vs 5개 유지

### 핵심 설계

5. **좌석 선점 방식**
   - v1(개선 전): DB 조건부 UPDATE vs 비관적 락
   - v2(개선 후): Redis Lua 즉시 선점 + Kafka → DB 기록(혼합형) vs 202 접수 + 결과 폴링
   - 선점 결과를 사용자에게 즉시 보여줄지, 접수 후 조회로 보여줄지
6. **Kafka 파티션 키·수**: userId / reservationId 중 무엇을 키로, 파티션 몇 개로 시작할지 (발제 권장 3개)
7. **SAGA 방식**: Orchestration(Reservation 조정자) vs Choreography, 결제 요청 진입점(Reservation 경유 vs Payment 직접)
8. **PG 타임아웃 정책**: UNKNOWN 상태 도입, 결과 조회 주기·최대 대기, 결제 진행 중 예매의 결제 마감 시한
9. **대기열 입장 정책**: 초당 입장 인원 N과 토큰 TTL, 토큰 유효 범위(좌석 선택까지 vs 결제까지)
10. **보안문자**: 서버 검증까지 구현할지, 일정상 빼고 서버 측 중복 제한만 할지
