M1은 하나의 질문으로 정리된다. **"발제가 요구하는 Kafka 비동기 접수를, 결과를 바로 알아야 하는 좌석 선점에 어떻게 맞출까?"**

## 1. 출발점: 발제 요구와 우리 UX가 부딪친다

발제의 [필수] 요구:

> API가 요청을 받으면 Kafka를 이용해 요청 데이터를 지정된 Topic에 적재하고 바로 응답을 반환한 뒤, 해당 Topic을 구독하는 Consumer가 요청을 처리하도록 구성해주세요.

요청을 받으면 일단 쌓아 두고 "접수했어요"라고 먼저 답한 뒤, 실제 처리는 나중에 하라는 뜻이다.

그런데 팀은 "선택 완료 버튼을 누를 때 선점"하기로 정했다. 사용자는 버튼을 누른 직후 **좌석을 잡았는지**를 알아야 결제로 넘어갈 수 있다. "접수했어요"만으로는 부족하다. 이 간극을 어떻게 메울지가 M1의 핵심이다.

## 2. 파티션 키: 왜 회차 ID도, 좌석 ID도 안 되나

Kafka 동작 세 가지:

- Topic은 여러 **파티션**으로 나뉜다. 예를 들어 3개.
- 메시지의 **키**가 같으면 항상 같은 파티션으로 간다.
- 한 파티션은 Consumer **하나**만 읽는다. 그래서 파티션 안에서는 순서대로 처리되고, 파티션끼리는 동시에 처리된다.

### 회차 ID를 키로 쓰면: 정확하지만 느리다

```
파티션 0: (비어 있음)                 ← Consumer 1 놀고 있음
파티션 1: [아이유 콘서트 요청 × 1000]  ← Consumer 2 혼자 처리
파티션 2: (비어 있음)                 ← Consumer 3 놀고 있음
```

티켓 오픈 때는 거의 모든 요청이 인기 회차 하나에 몰린다. 키가 같으니 전부 한 파티션으로 가고, Consumer 3개 중 1개만 일한다. 한 줄로 세워 처리하니 같은 좌석을 두 명에게 주는 일은 없지만, 처리량은 Consumer 하나의 속도에 묶인다. 파티션을 10개로 늘려도 결과는 같다.

### 좌석 ID를 키로 쓰면: 빠르지만 원자성이 깨진다

사용자 A가 A1, A2 두 좌석을 한 번에 골랐다고 하자.

**방법 ①: 좌석마다 메시지를 하나씩 보낸다**

```
A1 → 파티션 0 → 성공
A2 → 파티션 1 → 실패 (B가 먼저 잡음)
```

A는 좌석 하나만 잡은 어정쩡한 상태가 된다. "둘 다 잡거나 둘 다 놓치기"가 깨지고, 이미 잡은 A1을 되돌리는 보상 로직이 따로 필요해진다.

**방법 ②: 요청 하나로 보내고, 첫 좌석을 키로 쓴다**

```
사용자 A: {A1, A2} → 키 A1 → 파티션 0
사용자 B: {A2, A3} → 키 A2 → 파티션 1
```

두 요청이 모두 A2를 노리는데 서로 다른 파티션에서 **동시에** 처리된다. 순서 보장이 없으니 결국 DB 락 같은 다른 장치로 막아야 한다.

### 결론: 정합성은 Kafka 순서에 맡기지 않는다

| 역할 | 담당 |
| --- | --- |
| 같은 좌석을 두 명에게 주지 않기 (정합성) | Redis 원자 연산 + DB 조건부 UPDATE |
| 일을 고르게 나누기, 한 사용자의 이벤트 순서 지키기 | Kafka 파티션 키 = **userId** |

userId를 키로 쓰면 사용자들이 파티션 3개에 고르게 퍼진다. 같은 사용자의 "선점 → 결제 요청 → 취소"는 같은 파티션에서 순서대로 처리되므로, 취소가 선점보다 먼저 처리되는 사고도 막을 수 있다.

발제가 요구하는 "한 줄 근거" 예시:

> 파티션 3개: 로컬 단일 브로커, Reservation 1대 × Consumer concurrency 3. 키 userId: 정합성은 Redis·DB가 보장하므로 키는 균등 분산과 사용자 단위 순서 보장에만 쓴다.

## 3. 결과 전달: 순수 비동기로 가면 무엇이 필요하나

발제 예제를 그대로 따르면:

```
POST /seats/hold        → 202 { requestId: "r-123" }   (접수만 됨)
GET  /seat-holds/r-123  → PROCESSING                    (프론트가 0.5~1초마다 조회)
GET  /seat-holds/r-123  → HELD { expiresAt }  또는  FAILED { reason: "이미 선점된 좌석" }
```

**5분 타이머를 언제부터 셀지**가 중요하다. 버튼을 누른 시점부터 세면, Consumer가 밀려 30초 뒤에 처리됐을 때 사용자는 결제 시간 30초를 그냥 잃는다. 그래서 타이머는 **HELD가 확정된 시점부터** 센다.

## 4. 발신 유실: 202를 줬는데 메시지가 사라지는 문제

발제도 이 문제를 직접 짚는다.

> `kafkaTemplate.send()`는 결과를 기다리지 않고 바로 돌아오는 비동기 메서드입니다. … Kafka 적재가 실패해도 사용자는 이미 202(접수됨)를 받습니다.

Kafka가 잠깐 죽어 있으면 사용자는 "접수됨"을 받았는데 실제로는 아무것도 처리되지 않는다. 화면은 영원히 "처리 중"에 머문다.

**왜 Outbox로 해결이 안 되나**

- Outbox는 "DB 저장과 이벤트 발행을 한 트랜잭션으로 묶는" 패턴이다.
- 그런데 접수 API는 빠르게 응답하려고 일부러 DB에 쓰지 않는다. 묶을 DB 트랜잭션이 없다.
- 접수할 때 outbox 테이블에 쓰기 시작하면, 다시 DB가 병목이 되어 비동기로 바꾼 의미가 사라진다.

**대신 이렇게 한다**

| 설정 | 의미 |
| --- | --- |
| `acks=all` | 브로커가 "확실히 저장했다"고 답해야 성공으로 친다 |
| `enable.idempotence=true` | 프로듀서가 재시도해도 같은 메시지가 두 번 저장되지 않는다 |
| send 결과를 기다린 뒤 응답 | 저장 확인을 받은 다음에만 사용자에게 성공을 돌려준다 |

전송이 실패하면 Redis에 잡아 둔 좌석을 풀고 **503(잠시 후 다시 시도)**을 반환한다. 응답이 수 ms 늦어지는 대신, **"성공 응답 = Kafka에 확실히 들어감"**이 보장된다. 브로커가 1대라 디스크 자체가 날아가는 경우는 범위 밖이라고 명시해 둔다.

## 5. 혼합형: Redis에서 즉시 판정하고, DB 기록만 Kafka로 넘긴다

Claude 에이전트가 제안한 방식이고, 우리 UX에 가장 잘 맞는다.

```
[사용자] "선택 완료" {회차 7, 좌석 A1·A2}
   │
   ▼
[Reservation API]
   ① 입장 토큰 검증, 1인 최대 매수 확인
   ② Redis Lua: A1·A2가 모두 비어 있으면 둘 다 잡고, 하나라도 차 있으면 아무것도 안 잡음
        ├ 실패 → 409 "이미 선점된 좌석" (DB를 건드리지 않고 끝남)
        └ 성공 ↓
   ③ Kafka 전송 (키 = userId), 저장 확인을 기다림
        ├ 실패 → Redis 키 삭제, 503
        └ 성공 ↓
   ④ 200 { holdId, 좌석, expiresAt } ← 사용자는 여기서 바로 "선점 성공"을 봄
   │
   ▼ (비동기)
[Consumer]
   ⑤ DB에 예매(PENDING) 생성 + 좌석 상태 HELD로 조건부 UPDATE
        ├ 성공 → 끝
        └ DB 제약 위반 → 예매 FAILED 기록, Redis 키 해제
   │
   ▼
[결제 진입] 결제하기 전에 DB에 예매가 기록됐는지 확인 (아직이면 잠깐 "처리 중")
```

**② Redis Lua가 원자적인 이유.** Redis는 Lua 스크립트를 실행하는 동안 다른 명령을 끼워 넣지 않는다. 그래서 "전부 확인하고 전부 잡기"가 중간에 끊기지 않는다.

```lua
-- KEYS: hold:{회차}:{좌석} 목록, ARGV[1]: holdId, ARGV[2]: TTL(초)
for _, key in ipairs(KEYS) do
  if redis.call('EXISTS', key) == 1 then return 0 end  -- 하나라도 차 있으면 실패
end
for _, key in ipairs(KEYS) do
  redis.call('SET', key, ARGV[1], 'EX', ARGV[2])        -- 전부 잡기
end
return 1
```

**⑤ DB가 2차 방어인 이유.** Redis가 재시작되어 키를 잃는 등 예외 상황이 생기면 Redis 판정이 틀릴 수 있다. 그래서 DB에서 한 번 더 확인한다.

```sql
UPDATE seat SET status = 'HELD', hold_id = ?
WHERE schedule_id = 7 AND seat_id IN ('A1','A2') AND status = 'AVAILABLE';
-- 바뀐 행 수가 2가 아니면 롤백 → FAILED
```

**이 방식이 좋은 이유**

- 사용자는 버튼을 누르자마자 결과를 본다. UX가 동기 방식과 같다.
- 경합에서 지는 대부분의 요청은 Redis에서 바로 걸러진다. DB까지 가지 않으니 처리량이 오르는 지점이 바로 여기다.
- 느린 DB 쓰기는 Kafka 뒤로 빠지고, API는 "적재 후 즉시 응답"을 하므로 발제 요구도 충족한다.

**지켜야 할 규칙 두 가지**

1. **만료의 기준은 DB다.** Redis TTL을 DB 만료보다 조금 길게 잡는다(예: 5분 + 30초). DB 만료 스케줄러가 예매를 만료시킬 때 Redis 키도 지운다. Redis가 먼저 풀리면 다른 사람이 Redis에서는 성공하고 DB에서 실패하는 혼란이 생긴다.
2. **결제가 시작되면 Redis 키의 TTL을 없애거나 늘린다.** 결제 중에 좌석이 풀리면 안 되기 때문이다. C1의 "PAYING은 만료 대상에서 제외"와 같은 원칙이다.

## 6. 두 방식 비교와 발표 스토리

| | 순수 비동기 (202 + 조회) | 혼합형 (Redis 즉시 판정 + Kafka) |
| --- | --- | --- |
| 사용자가 결과를 아는 시점 | 폴링으로 몇백 ms~수 초 뒤 | 버튼 누르자마자 |
| 프론트 작업 | 폴링 화면 필요 | 일반 요청과 같음 |
| 정합성 | DB 하나가 보장 | Redis(1차) + DB(2차), 둘을 맞추는 규칙 필요 |
| 구현 난이도 | 낮음 | 중간 (Lua, Redis-DB 동기화) |
| 발제 요구 충족 | 충족 | 충족 |

부하 테스트의 개선 전/후 비교:

- **개선 전 (v1)**: API에서 DB 조건부 UPDATE를 동기로 처리한다. 모든 요청이 DB에 몰린다.
- **개선 후 (v2)**: 혼합형이다. 경합에서 진 요청은 Redis에서 끝나고, DB 쓰기는 Consumer가 나눠 처리한다.

이렇게 하면 발제가 원하는 "병목을 어떻게 찾고 무엇을 바꿨나"에 그대로 답할 수 있다. 2차 SA의 API 명세는 처음부터 v2 형태(`holdId`, `expiresAt` 반환)로 써 두면, v1에서 v2로 바꿀 때 프론트를 고칠 필요가 없다.
