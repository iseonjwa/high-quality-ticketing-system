## 2. 논의 사항

각 항목에 현재 상태, 선택지, 정리자의 추천을 적었다. 추천은 제안이며 팀 결정이 아니다. 결정되면 `docs/decisions/`에 기록한다.

### N1. v2 접수형의 상태 저장 (F6, F7)
- 현재: v2는 API가 DB 행을 만들지 않고 Kafka에 바로 발행하며(D4), 소비자가 결과 행을 만든다. 접수 후 소비 전, 또는 소비 실패 시 요청의 상태를 담을 곳이 없다. 이 구조는 D4(저장과 발행이 원자적이지 않은 문제)를 피하려고 택했다.
- 코멘트의 핵심: 실패를 누가 어떻게 알려 줄지가 비어 있고, 상태를 저장하지 않으면 재조회에서 판단할 수 없다.
- 선택지

| 안 | 내용 | 장점 | 단점 |
|---|---|---|---|
| (가) 현행 유지 | 소비자가 결과 행 생성. 접수 후 소비 전까지는 "알 수 없음" | v2 API 경로에 DB 쓰기가 없어 처리량 이점이 큼 | 실패·유실을 조회로 판별할 수 없음 |
| (나) 접수 행 + outbox | API가 `REQUESTED` 행과 outbox를 한 트랜잭션으로 INSERT, 릴레이가 발행 | 상태가 DB에 남고 D4도 해결됨 | API 경로에 INSERT가 생겨 v2의 이점이 줄어듦(줄어드는 정도는 측정 전) |
| (다) Redis에 접수 상태 저장 | TTL 키로 상태 기록 | 가볍다 | Redis는 기준 저장소가 아니라는 원칙과 충돌, 유실 시 다시 "알 수 없음" |

- 추천: (나). 상태를 판단할 수 없는 요청이 생기는 것이 정합성 쪽 피해가 더 크다. 선점 경합 자체는 INSERT 한 건이라 좌석 행 락 경합보다 가볍다. v2 재측정에서 (나)의 처리량을 (가)가 아닌 v1과 비교해 이점이 남는지 확인한다.
- 이 결정은 상태 머신의 `REQUESTED: DB 행 없음`, 4장 "D4" 문구, 결정 기록 #33·#50을 바꾼다. 담당 제안: 최권우(좌석 선점).

### N2. 결제·환불 상태 모델과 재확인 방식 (F1, F2, F3, F7)
- 현재: 결제 상태에 `REQUESTED`가 있으나 재조회 대상은 UNKNOWN뿐이다. 환불은 상태가 한 단계다.
- 결정할 것
  1. `REQUESTED`가 일정 시간(예: PG 응답 타임아웃 + 여유) 지나도 남은 경우를 재조회 대상에 넣을지.
  2. 환불 상태를 결제와 같은 구조로 둘지: 예) `REFUND_REQUESTED → REFUNDED | REFUND_FAILED | REFUND_UNKNOWN`. 별도 `refund` 테이블과 상태 이력을 둘지 결제 테이블 컬럼으로 둘지.
  3. 환불 멱등: 같은 예매에 환불 요청이 여러 번 와도 PG 환불은 한 번.
  4. 재확인 경로 분리: 몇 초 안에 끝날 재확인은 Kafka 재시도, 몇 분 이상 걸릴 재확인은 스케줄러.
  5. UNKNOWN의 종결: 6회 후에도 모르면 운영자 확인 상태(`NEEDS_MANUAL_CHECK`)로 명시하는지.
- 추천: 환불을 결제와 같은 구조(별도 `refund` + 이력)로 둔다. `REQUESTED` 경과 건과 UNKNOWN을 같은 스케줄러가 처리한다. 재확인은 짧은 간격 몇 회(Kafka 재시도) 후 몇 분 간격 스케줄러로 넘긴다. 담당 제안: 안준현(결제).
- 연결: `docs/sa-review/02-pg-timeout-handling.md`.

### N3. 결제 토큰 만료와 입장·결제 토큰 키 분리 (F4, F5)
- F4: 결제 토큰 유효 시간을 `선점 만료 − 여유`로 정할지. 여유는 PG 응답 타임아웃(2초)과 Gateway 요청 타임아웃(3초)을 합친 값 이상으로 잡는 것을 제안한다. 효과: 결제 승인이 만료 뒤에 도착하는 경우가 줄어 자동 환불(E8)이 안전망으로만 남는다. 비용: 사용자의 결제 가능 시간이 그만큼 줄어든다.
- F5: 입장 토큰과 결제 토큰이 같은 키와 비슷한 claim이면 한쪽 토큰으로 다른 쪽 검증을 통과할 수 있다. 선택지는 (가) 키를 분리, (나) 키는 같고 `aud`·`typ` claim을 검증에 필수로 포함, (다) 둘 다. 추천은 (다). 키를 분리하면 Gateway는 입장 토큰 검증 키만, Payment는 결제 토큰 검증 키만 갖게 되어 유출 범위도 줄어든다.
- 담당 제안: 반효승(결제 토큰 발급), 권영은(입장 토큰), 안준현(검증).

### N4. 선점 API의 버전 표기와 응답 형식 (F8, F9)
- F8: 선점 방식의 "v1(동기)/v2(접수)"와 경로의 `/api/v1`이 같은 표기라 혼동된다. 선택지는 (가) 선점 방식을 "동기형/접수형"이나 "sync/async"로 바꿔 부른다, (나) 경로 버전과 구분되게 방식 이름을 따로 둔다. 추천은 (가). 문서·코드·측정 결과의 표기를 한 번에 바꿀 수 있는 지금이 비용이 가장 낮다.
- F9: 선점 API는 같은 경로에서 201과 202를 방식에 따라 다르게 낸다. 🆕 응답 형식 통일 제안은 `status`/`code`/`data`를 고정하므로 틀은 맞는다. 남은 문제는 한 요청 형태에서 성공 결과가 둘이라는 점이다. 선택지는 (가) 방식 전환을 서버 설정으로 두고 클라이언트는 응답의 `data.status`로 분기, (나) 접수형을 별도 경로로 분리. 추천은 (가)지만, 클라이언트가 분기해야 한다는 점이 2차 가공에 해당하는지는 팀이 판단한다.
- 응답 형식 통일 제안 자체의 합의는 10/27 안건이다.

### N5. 선점 쿼리의 한도 초과와 행 없음 구분 (F11)
- 현재: `user_schedule_quota` 조건부 UPDATE가 0행이면 409 한도 초과로 응답한다. 0행은 "한도 초과"일 수도, 사용자·회차 행이 아직 없어서일 수도 있다.
- 선택지: (가) 선점 전에 `INSERT ... ON CONFLICT DO NOTHING`으로 행을 먼저 보장한 뒤 조건부 UPDATE, (나) UPDATE 0행이면 SELECT로 원인을 구분. 회차 오픈 시 모든 사용자의 행을 미리 만드는 방식은 사용자 수가 많아 제외한다.
- 추천: (가). (나)는 조회가 한 번 더 들고, 동시 요청 사이에서 판정이 어긋날 수 있다. 담당 제안: 최권우.

### N6. 레이스 컨디션 해결 방식의 근거 (F10)
- 현재 설계: 조건부 UPDATE + 부분 유니크 인덱스(DB가 기준). v2 접수형에서는 회차·구역 파티션 순차 처리가 락 경합을 줄이는 보조 수단이다.
- 코멘트가 후보로 든 분산락을 쓰지 않는 이유가 문서에 없다. 팀이 설명할 수 있어야 하는 항목(발표 질문 대비)이다.

| 방식 | 장점 | 단점 |
|---|---|---|
| 조건부 UPDATE + 부분 유니크 | 별도 인프라 없음, DB가 최종 방어, 락 만료 문제 없음 | 경합이 심하면 행 락 대기가 DB에 쌓임 |
| 분산락(Redis 등) | DB 접근 전에 경합을 거를 수 있음 | 락 획득·해제 왕복, 락 만료와 장애 시 정합성 위험, 결국 DB 제약이 필요 |
| Redis Lua 선점 | 한 번의 왕복으로 원자적 | Redis가 기준이 되면 유실 시 판정이 틀림. DB 2차 방어 필수 |

- 추천: 현 설계를 유지하고 위 비교를 결정 기록에 남긴다. 분산락은 DB 제약이 어차피 필요해 이중이 되고, 느려진 Redis가 선점 경로를 막을 수 있다(N8). Lua 선점은 `docs/sa-review/03-seat-hold-kafka-design.md`의 혼합형 안이므로 v2 설계와 함께 다룬다.
- F12 부분 유니크 ADR도 같이 쓴다.

### N7. 입장 판정 기준: ZRANK vs seq (F13)
- 현재: `admitted`와 비교할 값이 ZRANK(현재 몇 번째)인지 seq(받은 번호)인지 `(팀 확인)`.
- 코멘트: 현 구조(seq 카운터로 순번 발급)라면 seq가 맞다. 이탈한 사람이 줄에서 빠지면 ZRANK는 앞당겨지지만 `admitted`는 입장시킨 번호까지만 올라가므로 두 값이 어긋난다.
- 추천: seq 기준으로 확정하고 SA v2 14-8을 갱신한다. 담당 제안: 권영은. 결정만 내리면 되는 항목이라 10/27에 처리한다.

### N8. Redis 장애·느려짐 대응 (F16, F17, U7)
- 현재: Redis 장애 시 입장이 중단되고 Gateway의 로그아웃 확인·요청 제한도 멈춘다고만 적혀 있다.
- 결정할 것
  1. Gateway의 Redis 호출 타임아웃과 서킷 브레이커. 느려짐을 장애로 보는 기준(예: 타임아웃 N회 연속).
  2. 기능별 fail-open/closed. 아래는 초안이다.

| 기능 | 초안 | 이유 |
|---|---|---|
| 대기열 입장 | closed | 입장 속도 통제가 없으면 선점 API가 폭주를 그대로 받음 |
| 로그아웃 블랙리스트 확인 | 팀이 선택 | closed면 전 사용자 영향, open이면 로그아웃된 토큰이 유효 시간 동안 통과 |
| 사용자 요청 제한 | 로컬 제한으로 낮춘 open | 뒷단 보호는 유지하고 전체 중단은 피함 |
| 공연 정보 캐시 | open (DB로 대체 조회) | 캐시는 기준 저장소가 아님. 대체 조회 수는 제한 |

- 서킷 브레이커가 열려 있는 동안의 응답(예: 503과 재시도 안내)도 정해야 한다.
- 개념 설명: `docs/learning/junhyun/qna/2026-10-26-fail-open-fail-closed.md`.
- 담당 제안: 다 같이(U7), Gateway 설정은 공통 담당.

### N9. 외부 노출과 관리자 UI 접근 (F18, F19)
- 현재: 외부 공개 포트는 gateway(8080)와 grafana(3000). Kafka-UI(8085), Prometheus(9090), Zipkin(9411)은 공개하지 않는다고만 읽힌다.
- 결정할 것
  1. EC2 보안그룹 인바운드 규칙 표: 포트별로 허용 대상(전체 / 특정 IP / 차단)을 적는다.
  2. 어디서 요청을 막는지: 보안그룹(네트워크) → Gateway(JWT·입장 토큰·요청 제한) → 서비스(권한). 계층별 책임을 표로 적는다.
  3. 관리자 UI 접근 방식과 매뉴얼. 선택지는 (가) SSH 터널(로컬 포트 포워딩)만 허용, (나) 보안그룹에서 팀 IP만 허용, (다) 공개하되 인증. 추천은 (가): 외부에 열린 포트가 gateway 하나가 되어 규칙이 단순하다. grafana는 시연 때 보여 줘야 하므로 (나)를 시연 기간에만 적용하는 방안을 같이 검토한다.
- 담당 제안: 인프라 배포 담당(다 같이 · 10/29 이슈 소유자).

### N10. 숫자 기준의 근거와 EC2 메모리 예산 (F20, F21, F22, F23)
- 입장 토큰 TTL 10분과 초당 입장 50명: 문서의 식은 "최대 동시 입장 = N × T"이고 이것이 리틀의 법칙 `L = λ × W`(시스템 안의 평균 인원 = 도착률 × 체류 시간)과 같은 꼴이다. 값을 넣으면 50 × 600초 = 30,000명이다. 문서의 KSPO DOME 좌석 약 15,000석(회차당 `schedule_seat` 15,000행)보다 크다. T는 토큰 유효 상한이고 실제 체류 시간은 이보다 짧을 것이므로 30,000은 상한이지만, 상한이 좌석 수의 2배라는 점은 근거를 적을 때 짚어야 한다. 실제 체류 시간은 측정 전이라 미확인이다.
- EC2 메모리: 컨테이너 약 15개가 한 대에 올라간다. 서비스별 `-Xmx`(힙 상한)와 컨테이너 메모리 상한을 표로 만들고 합이 EC2 메모리의 70~80% 이하인지 확인한다. 힙 외 메모리(메타스페이스, 스레드 스택, 네이티브)가 있으므로 컨테이너 상한은 힙 상한보다 크게 잡는다. 수치는 측정 전이라 미확인이다. 담당 제안: 권영은(U10).
- 단일 인스턴스 한계(F21): 6장에 "EC2 1대 compose라 인스턴스 장애 시 전체가 중단된다. 서비스 단위 격리는 컨테이너 수준이고 운영이라면 다중 인스턴스"를 한계로 명시하는 것을 추천한다. 발표 질문에 먼저 답해 두는 효과가 있다.
- 숫자는 측정 후 수정한다는 합의(F23)는 🆕 측정 방식 제안(포화점 + 환경 기록표)과 함께 처리한다.
