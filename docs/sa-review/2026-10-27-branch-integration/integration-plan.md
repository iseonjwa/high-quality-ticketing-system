# 팀 결정 후 실행할 통합 계획

이 계획은 아직 실행하지 않았다. [D01~D12](team-decisions.md)의 팀 답변을 받은 뒤 범위를 확정하며, 현재 checkout·dev·원격 브랜치에는 적용하지 않는다.

## 시작 조건과 소유권

- 통합 담당 한 명이 통합 브랜치·커밋 순서·결정표를 관리한다. 공통 담당은 공개 API·감사, 인증 담당은 회원/세션, Gateway 담당은 토큰·라우트·신뢰 경계, 인프라/빌드 담당은 실행·저장소·CI를 검토한다.
- 기준 SHA와 최신 `origin/dev`·다섯 원격 브랜치를 다시 비교한다. 이 보고서 이후의 변경이 있으면 채택 범위에 영향 있는 차이만 재검토한다.
- 기존 작업·팀 기록을 보존하고 격리 작업 공간과 테스트 포트를 확보한다. 공유 Docker·DB·Redis를 중단하거나 테스트 데이터로 덮지 않는다.
- SA와 다른 선택은 팀이 결정한 상태·이유·비용을 정본 및 ADR에 반영한다. 이 검토 문서를 채택 확정 기록으로 소급 표시하지 않는다.

## 1. 통합 기준 마련

1. fresh `origin/dev`에서 `codex/common-auth-integration` 같은 전용 브랜치를 만든다. 실제 이름과 공간은 실행 시 확인한다.
2. 준현의 공통·인증·실행 기반을 기능 단위로 가져온다. 기준 브랜치의 문서·학습·판단 기록도 검토하고 보존하되 오래된 정책을 새 팀 결정으로 취급하지 않는다.
3. 첫 기준 상태에서 빌드·기존 테스트를 실행해 후속 이식 전 기준 결과를 남긴다. 알려진 결함·팀 정책 불일치는 다음 단계의 명시적 수정 대상으로 둔다.

다섯 브랜치를 통째로 연속 merge하는 방식은 권하지 않는다. [충돌 근거](git-conflicts.md)에 더해 서로 다른 이름의 타입·필터는 충돌 표시 없이 공존할 수 있다. Git상 충돌이 사라진 상태와 기능 통합 완료를 분리한다.

## 2. 계약과 기준 코드 정렬

1. D01·D02에 맞춰 패키지·모듈·Gradle group·의존 경계를 정렬한다. imports·컴포넌트 스캔·advice 범위·자동구성 파일·실행 스크립트·문서를 함께 확인한다.
2. D03·D04에 맞춰 응답/ErrorCode API, HTTP 상태·헤더, JWT 키 encoding·환경 변수·발급/검증 규약을 하나로 만든다.
3. D05·D06의 Redis 실패·warmup·세션·관리자 정책을 반영한다. 기존 Access 잔여 유효와 즉시 폐기 요구를 혼동하지 않는다.
4. D07·D08에 맞춰 헤더 제거·내부 접근·관리자 우선 라우트·알림·공개 method/path를 맞춘다.

정책 수정은 이름 변경과 별도 커밋으로 나누어 리뷰한다. 폐기할 중복 클래스를 삭제하기 전에 채택 기능과 테스트가 기준 코드에 남았는지 확인한다.

## 3. 다른 브랜치의 장점 선별 이식

| 출처 | 이식 범위 | 통합 방식 |
| --- | --- | --- |
| 효승 | trace advice·메서드 검증 errors·Redis 설정 분리·라우트/인증 테스트 | 기준 응답·패키지·장애 정책에 맞춘 패치로 옮긴다. JWT verifier·GlobalFilter를 중복 등록하지 않는다 |
| 권우 | 작은 성공 팩토리·의존성 전이 제한 | 필요한 API·의존 정책만 반영한다. 예외 handler와 Compose를 일괄 교체하지 않는다 |
| 강민 | PostgreSQL 통합 테스트·Config 입력 추적·서비스별 DB 계정 | 선택된 DB 버전·설정 변수·도구와 맞춘다. catalog/convention 전환은 D11에서 정한 후속 단계로 분리한다 |
| 영은 | 모듈/패키지 책임 설명·간결한 구성 | 채택 구조와 일치하는 설명만 보존한다. 미구현 Outbox를 기능으로 표시하지 않는다 |

각 패치에 원본 SHA·파일·채택 이유·변경된 의미를 기록한다. 통째 복사와 패턴 이식을 구분하며, 공통 공개 타입·설정의 정본은 하나만 남긴다.

## 4. 실행·저장소·문서 정렬

1. D09의 DB 계정·권한·볼륨·Redis 영속성과 D10의 Config/test 프로필을 환경 생성기·Compose·CI까지 맞춘다.
2. Dockerfile·healthcheck·실행 사용자·외부 bind·관리 9080·Prometheus 수집 주소를 한 실행 방식으로 검증한다.
3. 기록 README 충돌은 한쪽 버전 선택으로 덮지 않고 각 기록 링크를 보존한다. 철회·잠정·제안 상태를 그대로 구분한다.
4. [수정 체크리스트](team-decisions.md#정책-결정과-별도로-처리할-수정-체크리스트)를 마치고 실행 가이드·환경 변수 예시·모듈 사용 예를 실제 코드와 맞춘다. 비밀값은 기록하지 않는다.

## 5. 단계별 검증

아래는 향후 실행 기준이며 이번 조사에서 통과한 결과가 아니다. 명령은 채택된 모듈·패키지에 맞춰 갱신한다.

| 단계 | 실행·확인 범위 | 통과 기준 |
| --- | --- | --- |
| 공개 계약 | 공통 DTO/MVC/WebFlux·역할·JWT 단위/계약 테스트 | HTTP/body status·오류 필드·헤더·trace·용도별 토큰 거절·중복 빈·제외 범위가 일치한다 |
| 데이터·세션 | 격리 PostgreSQL/Redis에서 AuthIntegrationTest 20개 기존 사례와 정책 변경 회귀, 감사 JPA·Flyway | Refresh 동시 회전·잠금·변경/초기화·실패 복구·actor NULL을 실제 저장 결과로 확인한다 |
| 워크스페이스 | Java 21 `./gradlew verifyWorkspace --no-daemon`을 기준으로 채택 도구에 맞게 실행 | 전체 빌드·단위/통합 테스트·포트/환경·기록 검사가 통과한다 |
| 실제 스택 | `./gradlew :system-tests:systemTest -PredisFailure=true -PcoldStart=true --no-daemon`과 선택 정책에 맞춘 시나리오 | Config 누락·cold start·Redis 장애/복구·로그아웃 토큰·기동 정책을 실제 HTTP로 확인한다 |
| 경계·관측 | 전체 Compose에서 공개/보호/관리자/알림 라우트, 직접 서비스 접근, 위조 헤더, Prometheus | 올바른 대상·역할·노출과 실제 수집을 확인한다. mock 결과로 대체하지 않는다 |

Redis 영속성은 재시작 전후 Refresh·블랙리스트 상태로 확인한다. 테스트 종료 시 이번 작업이 만든 격리 자원만 정리한다. 부하·운영 용량·업무 SAGA/Outbox는 별도 범위이며 이 통합의 검증 결과로 주장하지 않는다.

## 6. dev PR과 완료 조건

1. 통합 담당은 최신 dev와 차이를 다시 확인하고 영역 담당의 리뷰를 받는다. 기능 기준·이식 항목·정책 결정·실행 결과·미검증 범위를 PR에 적는다.
2. dev로 직접 push하지 않고 통합 브랜치에서 dev 대상 PR을 만든다. 코드·환경·문서가 선택된 계약과 일치하는지 검토한다.
3. 필수 결정란에 미정이 없고, 중복 구현이 없으며, 단계별 검증이 통과하고 담당 리뷰가 끝나면 병합 가능한 상태로 본다. 실제 dev 병합은 팀의 승인 절차를 따른다.
4. 통합 후 각 팀원에게 새 공통 API·설정 변경·기존 브랜치 갱신 방법을 전달한다. Kotlin DSL/동적 수집 등 보류 항목은 별도 작업으로 남긴다.

## 롤백

통합 전 기존 브랜치와 고정 SHA를 보존한다. 패키지 정렬·정책 변경·선별 이식·도구 전환을 나눠 실패 단계를 식별하고 해당 변경만 되돌릴 수 있게 한다.

dev 반영 뒤 문제는 팀 절차에 따라 해당 통합 변경을 revert하고 재검증한다. 공유 브랜치의 강제 push는 사용하지 않는다. DB major 버전·볼륨 형식 변경은 코드 revert로 되돌아가지 않으므로 별도 전환에 백업·복구 검증을 요구하며, 기존 볼륨 삭제를 롤백 수단으로 삼지 않는다.
