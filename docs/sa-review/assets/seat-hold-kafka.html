3 · 결과 전달

순수 비동기라면 결과 조회 API가 필요하다

발제 예제를 그대로 따르면 접수와 결과 확인이 분리된다. 프론트는 결과가 나올 때까지 조회를 반복한다.

POST /seats/hold202 { requestId: "r-123" }접수만 됨
GET /seat-holds/r-123PROCESSING0.5~1초마다 다시 조회
GET /seat-holds/r-123HELD { expiresAt }
또는 FAILED { reason }결과 확정

5분 타이머는 언제부터 세나

Consumer가 밀려서 버튼을 누른 뒤 30초 만에 HELD가 확정됐다고 가정한다. 막대 길이는 실제 시간 비율 그대로다.

✗ 버튼 클릭부터 센다
결제에 쓸 수 있는 시간 4분 30초
✓ HELD 확정부터 센다
온전한 5분
클릭 HELD 5:00 5:30

빗금은 Consumer가 처리하는 동안 사용자가 모르는 사이 흘러간 30초다. 그래서 타이머는 HELD가 확정된 시점부터 센다.

4 · 발신 유실

202를 줬는데 메시지가 사라진다

kafkaTemplate.send()는 결과를 기다리지 않고 바로 돌아오는 비동기 메서드입니다. … Kafka 적재가 실패해도 사용자는 이미 202(접수됨)를 받습니다. — 발제문

send 결과를 기다리지 않을 때

유실
  • →API가 send()를 호출한다
  • ✓결과를 기다리지 않고 202를 돌려준다
  • ✗Kafka가 잠깐 죽어 있어서 메시지가 저장되지 않는다
  • ✗Consumer가 처리할 메시지가 없다
  • ✗사용자 화면은 영원히 처리 중…

저장 확인을 기다릴 때

권장
  • →API가 send()를 호출한다
  • →브로커의 저장 확인(ack)을 기다린다 (수 ms)
  • ✓확인을 받으면 그때 성공을 돌려준다
  • ✗실패하면 Redis에 잡아 둔 좌석을 풀고 503 "잠시 후 다시 시도"
  • ✓성공 응답 = Kafka에 확실히 들어감
프로듀서 설정의미
acks=all브로커가 "확실히 저장했다"고 답해야 성공으로 친다
enable.idempotence=true프로듀서가 재시도해도 같은 메시지가 두 번 저장되지 않는다
send 결과를 기다린 뒤 응답저장 확인을 받은 다음에만 사용자에게 성공을 돌려준다

왜 Outbox로는 안 되나

Outbox = DB 저장과 이벤트 발행을 한 트랜잭션으로 묶기 → 접수 API는 빠르게 응답하려고 DB에 쓰지 않음 → 묶을 트랜잭션이 없음

접수할 때 outbox 테이블에 쓰기 시작하면 다시 DB가 병목이 되어, 비동기로 바꾼 의미가 사라진다. Outbox는 Consumer 이후 단계(예매 → 결제 요청)에서 쓴다. 우리는 브로커가 1대라 디스크 자체가 날아가는 경우는 범위 밖이라고 명시한다.

5 · 혼합형 (Claude 에이전트 제안)

Redis에서 즉시 판정하고, DB 기록만 Kafka로 넘긴다

사용자는 버튼을 누르자마자 결과를 보고, 느린 DB 쓰기만 Kafka 뒤로 빠진다. 아래에서 상황을 고르면 그 경우에 실제로 지나가는 단계만 밝게 표시된다.

Redis에서 두 좌석을 모두 잡고, Kafka 저장 확인을 받은 뒤 바로 성공을 돌려준다. DB 기록은 Consumer가 뒤에서 처리한다.

③ Redis 1차 판정

Redis

Redis는 Lua 스크립트를 실행하는 동안 다른 명령을 끼워 넣지 않는다. 그래서 "전부 확인하고 전부 잡기"가 중간에 끊기지 않는다.

-- KEYS: hold:{회차}:{좌석} 목록
-- ARGV[1]: holdId, ARGV[2]: TTL(초)
for _, key in ipairs(KEYS) do
  if redis.call('EXISTS', key) == 1 then
    return 0  -- 하나라도 차 있으면 실패
  end
end
for _, key in ipairs(KEYS) do
  redis.call('SET', key, ARGV[1], 'EX', ARGV[2])
end
return 1

⑥ DB 2차 방어

Consumer · DB

Redis가 재시작되어 키를 잃는 등 Redis 판정이 틀릴 수 있다. DB가 한 번 더 확인하고, 최종 기준(정본)은 DB다.

UPDATE seat
   SET status = 'HELD', hold_id = ?
 WHERE schedule_id = 7
   AND seat_id IN ('A1', 'A2')
   AND status = 'AVAILABLE';

-- 바뀐 행 수가 2가 아니면 롤백 → FAILED

규칙 1 · 만료의 기준은 DB다

Redis TTL을 DB 만료보다 조금 길게 잡는다. DB 만료 스케줄러가 예매를 만료시킬 때 Redis 키도 함께 지운다.

DB 예매 상태 (HELD)
HELD · 만료 스케줄러가 기준
Redis 선점 키 (TTL)
선점 키
선점 확정 5:00 5:30

빗금은 30초 여유분이다. 실제로는 5:00에 스케줄러가 키를 지운다. 반대로 Redis가 먼저 풀리면, 다른 사람이 Redis에서는 성공하고 DB에서는 실패하는 혼란이 생긴다.

규칙 2 · 결제가 시작되면 Redis TTL을 없앤다

선점 확정 (HELD)→ 결제 시작 (PAYING)→ Redis 키 TTL 제거 PERSIST→ 결제 완료·실패 또는 결제 마감 시한→ 키 정리

결제 중에 좌석이 풀리면 안 되기 때문이다. C1의 "결제 진행 중(PAYING) 예매는 만료 대상에서 제외"와 같은 원칙이다.

개선 전 (v1)

API에서 DB 조건부 UPDATE를 동기로 처리한다. 경합에서 질 요청까지 모두 DB 커넥션을 쓴다. 이 상태로 기준선을 측정한다.

개선 후 (v2)

경합에서 진 요청은 Redis에서 끝나고, 이긴 요청의 DB 쓰기는 Consumer가 나눠 처리한다. "병목을 어떻게 찾고 무엇을 바꿨나"에 그대로 답할 수 있다.

2차 SA에서 할 일

API 명세는 처음부터 v2 형태(holdId, expiresAt 반환)로 쓴다. 그러면 v1에서 v2로 바꿀 때 프론트를 고칠 필요가 없다.
