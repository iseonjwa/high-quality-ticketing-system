# K1 단계 측정 기록 (측정 브랜치 `experiment/ISE-79-k6-steps`)

수정하지 않은 기본 코드에서 시작해, 측정에서 직면한 병목 하나를 고치고 다시 재는 순서로 쌓는다. 이 브랜치는 머지하지 않는다. 계획은 [k6-seathold-bottleneck-plan.md](../../docs/design/reservation/k6-seathold-bottleneck-plan.md) 3절이고, 결과는 단계가 끝날 때마다 그 문서 5절로 옮긴다.

## 규칙

- **한 단계 = 커밋 하나.** 코드로 고치는 단계는 코드를, 설정으로 고치는 단계(G1, R1, P1)는 `step-overlays.txt`에 덮어쓰기 한 줄을 더하는 커밋으로 넣는다. `git log`와 `git diff <앞 단계> <이 단계>`가 무엇을 바꿨는지의 기록이다.
- **직면한 것만 고친다.** 다음 단계는 앞 단계 측정에서 실제로 막힌 곳으로 정한다. 계획의 순서는 예상이고, 실측이 다르면 실측을 따르고 계획 문서에 이유를 적는다.
- **측정 전에 예상을 적는다.** 단계마다 아래 표의 "예상"을 먼저 채우고 잰 뒤 "실측"과 대조한다.
- **다른 이슈의 코드.** 이 브랜치에는 측정하려고 모든 단계를 쌓는다. 실제로 반영할 때는 이슈마다 따로 브랜치를 판다. 해당 단계는 P4(ISE-189, 반효승), R1(ISE-196), G1·P1(공유 설정, contract 이슈)이다. ISE-79 브랜치에는 선점 모듈 코드(S4, P3 등)와 측정 기록만 옮긴다.
- **기준 환경.** 배포 메모리(gateway 768MB, reservation-service 1,152MB), 선점 만료 스케줄러 끔, 60초 워밍업(초당 2명. 기본값 10명은 base 한계를 넘어 워밍업만으로 적체가 생겼다), 지표·GC 로그 켬, Gateway 인증 차단기 완화(느린 호출 판정 끔, 실패율 100%. 아래), k6 컨테이너 메모리 상한 2,560MB와 `GOMEMLIMIT=2GiB`, 측정 경로에 없는 컨테이너(grafana·loki·alloy·zipkin·kafka-ui·alertmanager·frontend) 멈춤, k6를 compose 네트워크에 붙여 Gateway 직접 호출(`http://gateway:8080`)(셋 다 P4b 재측정부터. 아래 "P4b 재측정 전 대책", "P4b 실측 2차", "P4b 실측 4차"). 나머지는 계획 문서 1-6절의 측정 기준을 따른다. 측정은 모두 local에서 하고, 배포 환경 성능 테스트는 나중에 따로 한다.

## 실행

워크트리 루트에서 Git Bash로 실행한다. 원래 저장소의 `.env`를 가리킨다. 먼저 기준 환경으로 전체 스택을 띄운다. `step-run.sh`는 reservation-service만 다시 띄우므로, 기준 환경 파일을 바꿨거나 원래 저장소에서 스택을 띄운 뒤에는 이 명령을 다시 실행한다.

```bash
K6=reservation-service/k6
docker compose --env-file ../../../.env -f compose.yml -f compose.local.yml -f $K6/compose.deploy-memory.yml   -f $K6/compose.b8-observe.yml -f $K6/compose.step-observe.yml -f $K6/compose.measure-gateway.yml up -d --build --wait

export ENV_FILE=../../../.env
bash reservation-service/k6/tools/step-run.sh base L   # 부하: 초당 100명 300초
bash reservation-service/k6/tools/step-run.sh base S   # 스트레스 5→320명 + 회복 120초
bash reservation-service/k6/tools/step-run.sh base H   # K1-H 스트레스 50→800명 + 회복 120초
```

- 회마다 지금 커밋으로 reservation-service를 다시 빌드해 새로 띄운다. 커밋되지 않은 코드·단계 설정이 있으면 멈춘다.
- 결과는 `results/step-<단계>-<종류>-<시각>-*`이다. k6 로그·요약·원자료, 회복 탐침, Prometheus 지표 CSV, GC 로그, 컨테이너 CPU와 잠금 대기 세션 수(`stats`), 대사(`invariants`), 조건(`meta`)이 남는다.
- 조건부 단계를 판단하는 회(P4c의 K1 S, P3의 K1-H S)에만 `OBSERVE_JFR=1`을 붙인다. JFR 녹화가 `results/*.jfr`로 남고, 로컬 JDK의 `jfr view hot-methods <파일>`로 본다. 꺼내려고 측정 뒤 reservation-service를 멈춘다.
- P5 근사 검증: base의 H 회 `metrics-summary.json`에서 `hold_time_s`와 `hikari_usage_s`가 20% 안인지 본다. 맞으면 이후 `hold_409_time_ratio`를 P5 판단에 쓴다.
- 대사가 0이 아니면 그 회의 처리량은 쓰지 않는다. 대사 위반이 나오면 그것이 S4(정합성 수정)를 넣을 근거다.
- 단계를 고르는 측정은 1회, 발표 비교점(기본, 각 묶음의 마지막 단계, 최종)은 3회 반복해 중앙값과 범위를 적는다.
- 끝나면 원래 저장소에서 `docker compose build reservation-service`로 이미지를 되돌린다. Compose 프로젝트 이름이 같아(`iseonjwa`) 이 브랜치 이미지가 원래 스택을 대신하기 때문이다.

**집계 정정 (2026-11-09):** k6 원자료(`*-raw.csv.gz`)의 `http_reqs` 행은 중복이 아니다(행 수가 summary의 `http_reqs` 수와 같다). 그런데 G1부터 P4b 4차까지 기록은 "두 줄씩 중복"으로 보고 건수를 2로 나눠 적었다. 그 건수를 실제 값으로 고쳤다. 비율(성공률, 단계별 %)은 분자와 분모가 함께 나뉘어 바뀌지 않는다. base 기록은 처음부터 나누지 않았다. 서버 지표(Prometheus)는 이 문제와 무관하다.

### base 예상

예비 측정(계획 문서 5-1·5-2·5-4절, 측정 방법이 바뀌기 전)에서 가져왔다.

- **L(초당 100명):** 좌석 조회가 거의 모두 실패한다(503·504). 선점 201은 0건에 가깝다. 컨테이너 메모리가 작아 JVM이 Serial GC를 고르고, Major GC가 이어져 서비스가 수 초 이상 멈춘다. Eureka 갱신이 끊겨 전체 503이 겹칠 수 있다.
- **S:** 오류 1% 미만으로 버틴 최대 속도는 초당 5명이다. 10명 단계에서 좌석 조회가 무너진다.
- **R:** 회복하지 못한다. 부하가 끝나도 Gateway가 포기한 요청을 서버가 계속 처리해 탐침이 10분 가까이 실패한다(B8).
- **H:** 예비 측정은 G1에서만 했다. Serial에서도 좌석 조회가 없으면 할당이 작아 초당 100~200명은 버틸 것으로 본다. 넘으면 커넥션 대기(풀 5)가 먼저 막는다.
- **대사:** 위반 0으로 예상한다. S1(매수 한도)·S2(멱등키)·S4(만료)의 결함은 같은 사용자의 동시 요청, 같은 멱등키 재전송, 만료 스케줄러 두 개에서 생기는데, K1에는 그 조건이 없다. 이 셋은 동시성 테스트로 직면한 결함으로 P1 앞에 넣고 비용만 잰다(계획 문서 3-4절).
- **잠금 대기:** S3(잠금 대기 상한)은 K1에서 직면할 수 있다. `stats`의 `lock_waits`가 처음 무너진 단계에서 풀의 절반(3개) 이상 이어지면 S3을 넣는다. base에서는 GC 정지와 커넥션 대기가 먼저 막아 거의 보이지 않을 것으로 본다.
- **다음 단계 예상:** G1(GC 정지) → R1(회복 실패) → P4a(좌석 조회가 커넥션을 붙잡음) 순서로 직면할 것으로 본다.

**H에서 직면한 것: Gateway 인증 차단기(`auth-redis`).** Gateway는 요청마다 Redis에서 로그아웃 토큰 여부를 확인하고, 이 호출에 차단기를 건다(`config-repo/gateway.yml`: 느린 호출 50ms, 비율 50%, 열림 10초. 호출 시한 100ms). 초당 100명 단계 30초째(부하 시작 90초)부터 즉시 503이 나왔다. Gateway CPU가 100~180%로 오르자 Redis 응답을 늦게 받아 느린 호출 비율이 90~100%가 되고 차단기가 열렸다. 열린 동안 인증이 필요한 요청은 모두 즉시 503이다(거절 약 6만 1천 건). Redis 컨테이너 CPU는 10% 아래였으므로 Redis가 아니라 Gateway 쪽 지연이다. 회복 탐침은 인증이 없는 공개 API라 200이었지만, 같은 시간 선점은 99%가 503이었다. Gateway는 다른 담당 영역이라 이 측정에서는 고치지 않는다.

**P5 근사 검증: 통과하지 못했다.** H 회에서 `hold_time_s` 1,412.8초, `hikari_usage_s` 268.0초로 20% 안이 아니다(약 5.3배). 선점 처리 시간의 약 5분의 1만 커넥션을 쥔 시간이라 `hold_409_time_ratio`(0.758)를 P5 판단에 그대로 쓸 수 없다. 이 차이 자체는 커넥션 밖 처리 시간이 크다는 신호라 P2 판단(JFR)에서 다시 본다.

**다음 단계:** K1(L·S)은 예상대로 G1(GC 정지)로 간다. K1-H는 Gateway 차단기가 reservation-service보다 먼저 막아, 선점 경로의 병목을 보려면 처리 방식을 정해야 한다.

**차단기 처리 (2026-11-07 결정):** 측정 환경에서만 느린 호출 판정을 끈다. 단계가 아니라 기준 환경이므로 base부터 모든 단계에 똑같이 얹는다. 선점 쪽 개선이 수치로 보이지 않으면 그 개선을 재는 의미가 없기 때문이다. 공유 설정에 반영할지는 Gateway 담당이 정한다.
- **조율 시점 (2026-11-07 결정):** 측정 중에는 contract 이슈를 올리지 않는다. 측정 환경에서만 쓰는 임시 덮어쓰기라 다른 서비스가 따라야 할 변경이 아니기 때문이다. 발견 내용은 측정이 모두 끝난 뒤 최종 수치와 함께 조율할 거리로 남긴다(계획 문서 6절 13번).
- 덮어쓰기: `compose.measure-gateway.yml`이 Gateway에 `k6measure` 프로필을 켜고, config-server가 `config-measure/`를 함께 읽게 한다. `config-measure/gateway-k6measure.yml`이 `slow-call-duration-threshold`를 50ms에서 100ms(호출 시한과 같음)로 올린다. 시한을 넘긴 호출은 어차피 실패로 세므로 느린 호출 판정만 사실상 꺼진다. "시한 초과·오류가 절반 이상이면 연다"는 보호는 남는다.
- `step-run.sh`는 Gateway가 `k6measure` 프로필로 떠 있지 않으면 멈춘다.
- base H는 이 환경에서 다시 잰다. 위 H 회는 공유 차단기 기준의 기록으로 남긴다. K1 L·S는 Gateway까지 부하가 가기 전에 reservation-service가 무너져 이 환경과 결과가 같다고 보고, 다시 재지 않는다. G1부터는 이 환경에서 잰다.

왜 회복하지 못했나: Gateway는 3초에 504를 돌려주지만 reservation-service는 그 요청을 계속 붙든다. 커넥션 5개 앞에서 최대 30초까지 기다리고, 커넥션을 얻으면 이미 버려진 좌석 조회를 약 1초씩 끝까지 처리한다. 부하가 끝나도 이렇게 밀린 요청을 다 치울 때까지 새 요청(탐침)이 뒤에 선다.

- **L:** 커넥션 대기가 1초 안으로 묶여, 대기 시한 초과 실패(500)가 대량으로 생긴다. 서버의 좌석 조회 처리량(초당 약 15건)은 G1과 비슷하다. 대신 처리된 요청이 3초 안에 끝나 클라이언트 좌석 조회 성공이 0.1%에서 약 10%로 오른다. 실패의 모양이 504(늦은 실패)에서 500(빠른 실패)으로 바뀐다. GC 정지 비율은 G1과 같다(약 25%). 대사 위반 0.
- **S:** 버틴 단계는 G1과 같다(10명까지). 20명 단계에서 커넥션 대기가 쌓이지 않고 수십 건 안에서 머물며, 실패는 대기 시한 초과로 바로 나온다. **부하가 끝나고 10~20초 안에 회복 탐침이 200이 된다**(G1은 3분 동안 504). 이번 단계의 판정 기준이다.
- **H:** R1과 무관하다고 보고 재지 않는다. 200명까지 커넥션 대기가 거의 없고, 400명부터는 Gateway가 먼저 막는다. 대기 시한 1초가 선점 경로를 바꾸는 것은 커넥션 대기가 1초를 넘을 때뿐이다.
- **다음 단계 예상:** 좌석 조회 한 건이 커넥션을 약 1초 쥐는 것이 남아 P4a(좌석 조회 DTO 프로젝션)로 간다.

**원인:** 서버가 빨라져 k6가 830KB 좌석 응답을 초당 더 많이 받게 됐다. k6는 응답을 문자열 검색으로만 다루지만(`JSON.parse` 안 함), 응답 본문을 가진 VU가 수백 개면 메모리가 GB 단위로 커진다. Docker VM 8GB를 서비스 전체(약 4GB)와 k6가 나눠 써서 VM 메모리가 바닥나 모든 컨테이너가 멈췄다. 서버의 한계가 아니라 부하 생성기의 한계다. 다시 재기 전에 k6 메모리를 묶는 방법을 정한다.

**P4b 재측정 전 대책 (2026-11-09 결정):** k6 컨테이너에 메모리 상한을 건다(`run.sh`의 `--memory 2560m --memory-swap 2560m`, `GOMEMLIMIT=2GiB`). Docker VM 메모리를 늘리는 안(`.wslconfig`)은 개인 PC 설정이라 팀원이 같은 조건을 만들기 어려워 고르지 않았다.
- 왜 이 값인가: 서비스 전체가 약 4GB를 쓰고 VM이 약 8GB라, k6에 2.5GB를 주면 VM에 1.5GB 안팎의 여유가 남는다. `GOMEMLIMIT`는 상한 근처에서 Go GC를 앞당겨 넘침을 늦춘다. 그래도 넘치면 k6 컨테이너만 OOM으로 죽고 서비스는 멈추지 않는다.
- 앞 단계와의 비교: P4a까지는 k6가 0.9GB 아래였으므로 상한이 그 회들의 조건을 바꾸지 않는다. 다시 재지 않는다.
- 판정: `meta`에 `k6_memory`·`k6_gomemlimit`·`k6_exit`가 남는다. `k6_exit=137`이면 k6가 상한에 닿아 죽은 회라 처리량을 쓰지 않고 부하 생성기 한계로 적는다. `stats`의 `k6-<단계>-<종류>-<시각>` 행으로 k6 메모리를 보고, 수집 간격이 15초를 넘는 구간이 있으면 그 회는 무효로 본다.

## 측정 기기 이동 (2026-11-09)

지금까지의 회는 모두 노트북 한 대(Intel i7-11800H, 호스트 메모리 16GB, Docker Desktop 29.4.0, Docker VM 16코어·7.6GiB)에서 쟀다. 호스트 메모리가 부족해 내부망 재측정이 끊겨(Claude Code가 백그라운드 작업을 회수함), 남은 측정은 다른 기기에서 한다.

- **기기가 바뀌면 절대 수치가 달라져 단계끼리 비교할 수 없다.** 컨테이너 메모리 상한은 같지만 CPU 상한이 없어 처리량이 기기를 따라간다. 그래서 새 기기에서 base부터 다시 잰다: base(L·S·H 3회), G1(L·S·H), R1(L·S), P4a(L·S), P4b(L·S). 그 뒤 P4c부터 이어 간다.
- 이 노트북에서 잰 회는 지우지 않고 "이전 기기 참고 기록"으로 둔다. 단계마다 직면한 병목의 종류(GC → 커넥션 → DB 조인 → Gateway)는 새 기기 결과로 다시 확인한다.
- `step-run.sh`가 `meta`에 `host_cpu`, `host_mem_kb`, `docker`(버전·OS·구조·VM 코어·VM 메모리)를 남긴다. 이 줄이 없는 회는 이 노트북에서 잰 회다.
- 새 기기의 Docker VM 메모리는 7.6GiB 이상, 가능하면 10GiB 이상으로 둔다.

이 노트북에서 끝난 내부망 재측정(임시 브랜치 `experiment/ISE-79-remeasure-net`, src는 `849435a`, 덮어쓰기 없음). 모두 수집 간격 15초 이내, 대사 위반 0이다. 자세히 분석하지 않았다.

"P4c가 클라이언트 수치를 떨어뜨렸다"는 해석은 거둔다. 1,280명의 한계가 reservation-service가 아니라 Gateway 인증 차단기라는 판단과 K1을 P4c에서 마친다는 결정은 그대로다. 오히려 차단기 때문에 1,280명 수치가 회마다 크게 흔들려, 이 단계로는 reservation-service 개선의 효과를 볼 수 없다는 근거가 더 분명해졌다.

### P4a 구현 대조 예상 (dev `a40b01d` 대 측정 브랜치 `50a365d`, 2026-11-10, 측정 전)

좌석 조회 담당이 dev에 넣은 P4a(`a40b01d`, ISE-189)와 측정 브랜치 P4a(`50a365d`, 코드는 `649139c`)를 같은 조건으로 잰다. dev 코드를 채택해도 되는지, 곧 두 구현의 성능 차이가 작은지 보는 것이 목적이다. 임시 브랜치 `experiment/ISE-79-p4a-compare`에서 잰다.

- **두 구현의 차이:** 둘 다 엔티티를 만들지 않고 공연장 좌석과 조인해 구역 → 열 → 번호 순으로 15,000행을 읽는다. 측정 브랜치는 네이티브 SQL로 7열을 읽고 선택 가능 여부를 SQL에서 계산해 `Object[]`를 행으로 옮긴다. dev는 JPQL 생성자 식으로 `ScheduleSeatRow` 8열(회차 좌석 등급·상태 포함)을 바로 만들고 선택 가능 여부를 자바에서 판단한다. 응답 DTO의 필드와 순서는 같다. `reservation-service/src/main`에서 두 커밋의 차이는 좌석 조회 파일 10개뿐이다.
- **조건:** src는 `649139c`(측정 브랜치 P4a)와, 그 위에 좌석 조회 파일만 `a40b01d`로 바꾼 것 두 가지다. 덮어쓰기는 P4a 단계와 같은 G1·R1이다(풀 5). 도구는 지금 측정 브랜치 그대로라 k6 상한이 6GiB다. 앞의 P4a 실측(2.5GiB)과 조건이 달라 측정 브랜치 P4a도 다시 잰다.
- **순서:** L을 측정 브랜치 → dev 순으로 번갈아 3회씩, 그 뒤 S(5~320명)를 1회씩 잰다. 번갈아 재서 시간에 따른 기기 상태 변화가 한쪽에만 쌓이지 않게 한다.
- **예상:** P4a 단계의 병목은 DB다(PostgreSQL CPU 약 4코어, 커넥션 5개가 모두 조인·정렬 쿼리에 묶임). 두 구현은 DB에 같은 일을 시키고 차이는 JVM에서 행을 만드는 방식뿐이다. 그래서 L 좌석 조회 성공률, 서버 좌석 조회 200 초당 건수, PostgreSQL CPU가 회 사이 편차 안에서 같을 것으로 본다.
- **"차이가 크지 않다"의 기준(측정 전에 정함):** 3회 중앙값으로 L 좌석 조회 성공률 차이 5%p 이내, 서버 좌석 조회 200 초당 건수 차이 10% 이내, S에서 버틴 단계(성공 99% 이상)가 같음.

### 동시성 부하 측정 예상 (K2 멀티 탭·연타, X 만료 켬, 2026-11-10, 측정 전)

K1은 같은 좌석 경쟁만 대량으로 만든다. 사용자가 요청을 하나씩 보내고 만료 스케줄러를 끈 채 재므로, S1·S2(같은 사용자 동시 요청)와 S3·S4(만료와 선점 경합)는 동시성 테스트(C1~C7)로만 확인했다. 이 결함이 부하 상태에서도 그대로 나오는지, 고친 뒤 사라지는지를 본다.

- **비교:** A는 P4c 코드에서 S1~S4만 뺀 것(src = `d3820f5`), B는 F(지금 src)다. 덮어쓰기는 둘 다 G1·R1·P1(풀 10)이다. 차이는 S1~S4뿐이다. 각 1회씩, A → B 순으로 잰다.
- **T (K2 멀티 탭, `BURST=tabs`):** 사용자 한 명이 고민 1~3초 뒤 탭 4개로 서로 다른 좌석 2석씩, 서로 다른 멱등키로 동시에 선점한다. 초당 50명 120초. 사용자마다 201로 잡은 좌석 수를 센다.
  - 예상 A: 한도(4매)를 넘겨 잡은 사용자(`over_limit`)가 나온다. C4에서는 30라운드 모두 넘었다. 부하 중에는 인기석 경쟁으로 일부 탭이 409를 받으므로 비율은 C4보다 낮을 것이다.
  - 예상 B: `over_limit` 0. 넘는 탭은 409 `PURCHASE_LIMIT_EXCEEDED`를 받는다.
- **D (K2 연타, `BURST=double`):** 같은 좌석·같은 멱등키로 3번 동시에 보낸다. 초당 50명 120초.
  - 예상 A: 한 요청만 201이고 나머지는 자기 요청 때문에 409 `SEAT_ALREADY_HELD`를 받는 사용자(`self_conflict`)가 대부분이다(C5: 201 30건, 409 60건).
  - 예상 B: `self_conflict` 0. 좌석을 잡은 사용자는 세 응답이 모두 같은 예매의 201(`same_201`)이다. 두 구현 모두 같은 키로 예매가 둘 생기는 경우(`duplicate`)는 0이다.

- **반영 제안:** `seathold.expiry.batch-size` 기본값을 100에서 1,000으로 올린다. 더 나은 방법은 주기 안에서 대상이 빌 때까지 처리하되 시간 상한(주기 길이)을 두는 것이다. 선점 만료는 내 영역(ISE-13)이라 feat 브랜치에서 고칠 수 있다.

### 잠긴 행 집중 스트레스 예상 (Z, 2026-11-10, 측정 전)

실제 티켓팅에서는 인기석에 요청이 몰리고, 그 행이 잠겨 있을 때도 요청이 계속 온다. 잠긴 행에 몰린 요청이 장애를 만드는지, 그 장애가 다른 API와 다른 서비스로 번지는지를 본다.

- **조건:** 별도 세션이 앞쪽 10석(인기석)을 부하 시작 10초 전부터 부하가 끝난 뒤 30초까지 `FOR UPDATE`로 쥔다. k6는 선점을 그 10석에만 보낸다(`HOT_RATIO=1`, 재시도 없음, 고민 0~0.2초). 도착률은 초당 10 → 20 → 40 → 80 → 160 → 320명이고 단계마다 60초다. 같은 시간에 구경꾼 요청 세 가지를 API마다 초당 10건씩 Gateway로 보낸다. 부하가 끝난 뒤 90초 동안도 이어 보낸다.
  - `by_concerts`: 같은 reservation-service의 공연 목록(같은 커넥션 풀, 잠금과 상관없음)
  - `by_user`: user-service 내 정보
  - `by_payment`: payment-service 신원 확인(local 전용)
- **비교:** A(S1~S4 전, `lock_timeout` 없음)와 B(F, S3 500ms). 덮어쓰기는 G1·R1·P1(풀 10). 각 1회.
- **예상 A:** 잠긴 좌석 선점은 잠금이 풀릴 때까지 커넥션을 쥔 채 기다린다. 첫 단계(초당 10명)에서 이미 풀 10개가 1~2초 안에 찬다. 그 뒤 reservation-service의 모든 DB 요청은 커넥션 대기 시한(1초) 초과로 500이 된다. 공연 목록도 실패한다. 기다리는 요청이 Tomcat 스레드(200개)도 채우면, DB를 쓰지 않는 요청도 응답을 받지 못할 것이다. 선점 클라이언트는 Gateway 시한(3초)에 504를 받는다.
- **예상 B:** 잠긴 좌석 선점은 500ms 뒤 409다. 커넥션 10개 ÷ 0.5초 = 초당 약 20건까지는 풀에 여유가 있어 공연 목록이 성공한다. 초당 40명 단계부터 풀이 차서 공연 목록 실패가 늘어날 것이다. 단계가 오를수록 A와 같아진다.
- **다른 서비스(user-service, payment-service):** Gateway는 논블로킹(WebFlux)이고 서비스마다 경로가 따로라, reservation-service가 무너져도 영향이 없을 것으로 본다. 다만 Gateway가 응답을 기다리는 reservation-service 요청이 수천 개로 쌓이면 Gateway의 메모리·커넥션 풀에 영향을 줄 수 있다. 이 부분이 번짐의 핵심 관찰 대상이다.
- **회복:** 잠금이 풀리면 A·B 모두 수십 초 안에 회복할 것이다.
- **판정에 쓸 값:** 단계별(그리고 부하 뒤) 구경꾼 API별 성공률과 p95, 선점 응답 분포, 커넥션 대기, 잠금 대기 세션, Tomcat 스레드, Gateway CPU·메모리.

### 잠긴 행 집중 1차 실측 (A `77d3647`, B `323d385`, 2026-11-10) — 잠금이 k6의 목표와 어긋남

**어긋남:** 잠금 세션이 ID가 작은 10석(3360001~3360010)을 잠갔다. k6의 좌석 목록은 응답 순서(구역 → 열 → 번호)이고 그 순서로 ID가 연속이 아니다(`K1-H 좌석 목록: 15000석, ID 비연속`). k6가 노린 10석은 3360001, 3360501, 3361001 … 3364501이라 **그중 1석(3360001)만 잠겼다.** 나머지 9석은 부하 초반에 팔렸고, 그 뒤 그 좌석 요청은 기다리지 않고 바로 409를 받았다. 그래서 이 회는 "인기석 요청의 약 10%가 잠긴 행으로 가는" 조건이다(B 선점 응답의 약 10%만 500ms 근처, 나머지는 3~7ms). 1차 잠금 장애 주입(K)도 같은 ID 순서로 잠갔으므로, 잠근 2,200석과 k6 인기 구역(응답 앞쪽 1,500석)이 얼마나 겹쳤는지는 미확인이다. 그 결과는 "인기 구역 근처를 잠갔을 때"로만 읽는다. 잠금 순서는 응답 순서로 고쳤다(`step-run.sh`).

### 측정 회고 뒤 세 측정 예상 (CPU 상한 F, 매진을 피한 스트레스 M, K 재측정, 2026-11-11, 측정 전)

측정 회고(학습 노트 `docs/learning/kwonwoo/qna/2026-11-11-k6-seathold-scenario-retrospective.md`)에서 고르기로 한 세 가지다. 모두 1회씩이다.

**1. CPU 상한 F (`compose.cpuset-4.yml`, F L·S)**
- **조건:** 서버 컨테이너 전체를 Docker VM의 0~3번 코어에 함께 묶는다(배포 서버 4 vCPU 한 대를 흉내 냄). k6는 `K6_CPUSET=4-15`로 다른 코어에 둔다. 코드는 F, 덮어쓰기는 G1·R1·P1이다. S 단계는 F 확장과 같은 5~1,280명이다. 다른 조건은 F 실측과 같다.
- **추정 근거:** F S 1,280명 단계(매진 뒤, 좌석 조회만)에서 reservation-service 6.5코어, Gateway 7.0코어, PostgreSQL 0.6코어를 썼다. 좌석 조회 한 건에 두 컨테이너가 합쳐 약 11ms의 CPU를 쓴 셈이다. 4코어면 이론 상한이 초당 약 360건이다. 매진 전 사용자 한 명은 좌석 조회를 평균 약 2.4번 한다(409 비율 약 77%, 재시도 최대 2번: 1 + 0.77 + 0.77²).
- **예상 L(초당 100명):** 매진 전 좌석 조회가 초당 약 240건으로 상한의 약 3분의 2다. 성공률은 95% 이상을 유지한다. 대신 p95가 7ms에서 수십~수백 ms로 오른다. 4코어가 거의 늘 바쁘다.
- **예상 S:** 80명까지 버티고, 160명(매진 전 좌석 조회 초당 약 380건)에서 실패가 생기기 시작한다. 320명 이상에서는 Gateway 시한(3초) 504가 늘어난다. 병목은 커넥션이 아니라 CPU다(reservation-service와 Gateway가 4코어를 나눠 씀, 커넥션 대기 거의 0). 이 결과가 맞으면 응답 직렬화를 줄이는 P4d가 4코어 환경에서는 효과를 낼 자리가 생긴다. 직렬화는 reservation-service CPU의 약 32%, 두 컨테이너 합의 약 15%다.

**2. 매진을 피한 스트레스 M (CPU 상한 없음, F)**
- **조건:** S와 같은 흐름과 단계(5~1,280명)다. 단계마다 새 회차를 쓰고 회차 하나에는 초당 100명까지만 보낸다(1,280명 단계는 회차 13개). 회차 하나는 초당 100명이면 약 190초에 매진되므로(F L) 60초 단계 안에서는 매진되지 않는다. 회차는 모두 31개다. CPU 상한은 걸지 않는다. 그래야 F S 확장과 차이가 "매진을 피했는지"뿐이다.
- **예상:** 사용자마다 좌석 조회 약 2.4번과 선점 약 2.4번을 한다. 1,280명 단계는 좌석 조회가 초당 약 3,000건이다. F S의 1,280명 단계는 매진 뒤라 초당 약 1,280건이었다. 같은 CPU 비용(약 11ms)이면 서버 두 컨테이너에만 약 33코어가 들어 VM(32코어, k6 포함)을 넘는다. 그래서 640명(좌석 조회 초당 약 1,500건)까지는 버티되 p95가 오르고, 1,280명에서 무너질 것이다. 병목은 CPU다. 선점(초당 약 3,000건)은 Gateway 우회 K1-H 800명(서버 초당 약 2,200건, 풀 10, 대기 0)보다 많아 커넥션 대기가 함께 생길 수 있다.
- 단계가 바뀔 때 새 회차들의 배치 캐시(P4b)를 처음 만드는 비용이 순간적으로 몰린다(1,280명 단계 시작에 회차 13개). 여러 공연이 함께 열리는 상황의 비용이기도 해서 따로 본다.
- 발표 문구 "초당 1,280명"을 조회와 선점이 섞인 한계로 바꾸는 근거가 된다.

**3. K 재측정 (응답 순서로 잠금, A·B, CPU 상한 없음)**
- **조건:** 1차 K와 같다(부하 30초 뒤 앞쪽 3,000석 중 선택 가능 좌석을 30초 잠금). 다른 점은 잠글 좌석을 좌석 ID 순서가 아니라 응답 순서(구역 → 열 → 번호)로 고른다는 것뿐이다(`754f116`에서 고친 도구). 이제 k6 인기 구역(응답 앞쪽 약 10%, 1,500석)이 모두 잠금 범위 안에 든다. A는 `experiment/ISE-79-concurrency-load-a4`(S1~S4 전), B는 F다.
- **예상:** 잠금이 걸린 뒤 인기 구역에서 아직 선택 가능한 좌석은 모두 잠긴 좌석이다. 사용자 약 70%가 그 구역을 고르므로, 선점의 대부분이 잠긴 행으로 간다(초당 수십~100건 이상). B도 풀 10개 ÷ 0.5초 = 초당 약 20건을 크게 넘는다. 그래서 잠금 중 좌석 조회 성공은 1차보다 낮아질 것이다. A는 25%보다 낮은 0~20%, B는 77.5%보다 크게 낮은 20~50%로 본다. 맞으면 "S3만으로는 인기 구역에 걸린 잠금의 번짐을 막지 못한다"가 되고, 커넥션을 잡기 전에 거절하는 장치의 근거가 더 강해진다.

CPU가 모자라 응답이 1초 넘게 걸리자 동시에 쥔 응답이 늘어 메모리가 찬 것으로 본다. - **P4d 판단에 주는 것:** 4코어에서는 160~320명에서 CPU가 거의 찼고, reservation-service가 그중 1.5~2.1코어를 썼다. 직렬화가 그 CPU의 약 32%라면 0.5~0.7코어를 덜어 준다. 다만 같은 구간에서 Gateway(1.3~1.7코어)와 Gateway 인증 차단기가 함께 한계에 닿았다. P4d만으로 한계 단계가 바뀔지는 이 1회로 말하기 어렵다. 배포 측정에서 다시 본다는 기존 결론(2안)을 유지하되, "local에서는 효과가 보이지 않는다"는 근거는 "CPU 상한에서는 CPU가 한계에 닿는다"로 바꾼다.

### Gateway OOMKilled 재현과 원인 확인 예상 (2026-11-11, 측정 전)

CPU 상한 S(`step-f-cpu4-S-20261111-133015`)의 1,280명 단계 끝에서 Gateway가 `OOMKilled`로 죽었다. 반복되는지와 무엇이 메모리를 채웠는지 확인한다.

- **조건:** CPU 상한 S와 같다(서버 0~3번 코어, k6 4~15번, 5~1,280명, Gateway `-Xms256m -Xmx512m`·Serial GC·768MiB). 관찰만 더한다(`compose.gateway-observe.yml`: GC 로그, NMT 요약, Netty 기동 로그). 매 회 Gateway를 새로 띄운다. 2회 잰다.
- **기록:** `tools/gateway_mem_sampler.py`가 1초마다 cgroup 메모리(anon·file·sock·kernel), java RSS·스레드, TCP 소켓 수와 보내기·받기 대기열 합을 남긴다. 5초마다 별도 JDK 컨테이너(`jcmd`, 코어 16번 이후)로 NMT 요약을 남긴다.
- **측정 전에 확인한 것(앞 분석 정정):** Netty 기동 로그가 `direct buffer constructor: unavailable`이다. 그래서 Netty는 JDK 직접 버퍼를 쓰고, 그 양은 `jvm_buffer_memory_used_bytes{id="direct"}`에 잡힌다. 앞 회 Prometheus(5초 간격)에서 직접 버퍼는 3~19MB였고, 커밋 힙은 죽기 2초 전까지 248MB로 그대로였다. 앞 분석의 "JVM 지표에 안 보이는 Netty 직접 메모리" 가설은 약해졌다. 마지막 수집에서 컨테이너는 770.9MiB, JVM이 보고한 커밋은 412MB라 약 360MB가 JVM 밖에 있다. Gateway의 GC는 Serial이었다(측정 덮어쓰기에 `-XX:+UseG1GC`가 없음. 배포는 G1).
- **가설과 가르는 값:**
  - A 힙 확장: GC 로그의 힙 용량이 커진다. NMT의 Java Heap committed가 커진다.
  - B 네이티브(JVM 안): NMT의 다른 영역(Other, Internal, Thread 등)이 커진다.
  - C 커널 소켓 버퍼: cgroup `sock`이 커지고 TCP 보내기 대기열 합이 커진다. NMT 합계는 그대로다.
- **예상:** 반복된다(2회 중 1회 이상). 원인은 C로 본다. 1,280명 단계에서 CPU가 모자라 응답 830KB를 클라이언트에 늦게 내보내는 동안, 보내지 못한 바이트가 커널 소켓 버퍼에 쌓여 Gateway cgroup에 잡힐 것이다.

- **원인(확인):** 1,280명 단계에서 830KB 좌석 응답이 짧은 시간에 몰려 두 곳에 동시에 쌓였다. 하나는 커널 소켓 받기 버퍼다. 받았지만 Gateway가 아직 읽지 않은 바이트로, `sock` 값과 TCP 받기 대기열 합이 같이 움직였고 최대 약 590MiB였다. 다른 하나는 JDK 직접 버퍼다. 읽었지만 아직 내보내지 못한 바이트로, NMT `Other`가 3MB에서 183MB로 올랐다. 보내기 대기열은 내내 0이었다. 클라이언트(k6)에 내보내는 쪽이 아니라 reservation-service에서 받는 쪽에 쌓였다는 뜻이다.
- **JVM 평시 크기:** anon 약 520MiB다(NMT 합계 약 470MB: 힙 256, 코드 62, 심볼 31, 클래스 14 등). 상한 768MiB까지 여유가 약 250MiB뿐이다. 그래서 응답이 몰리면 몇 초 안에 상한에 닿는다.
- **죽지 않은 이유:** 컨테이너가 메모리 상한만큼 스왑을 쓸 수 있다(`memory.swap.max` 768MiB, Docker 기본 `memswap = 2 × mem_limit`, Docker VM 스왑 4GiB). 커널은 상한에 닿으면 JVM 메모리를 스왑으로 내보내 자리를 만든다. oom2 기준 약 303MiB를 내보냈다(`pswpout` 77,611쪽). oom1에서 anon이 521에서 146MiB로, RSS가 540에서 165MiB로 떨어진 것이 이것이다. 대가로 Gateway가 크게 느려졌다. oom1에서 GC 멈춤 최대 6.9초, 1,280명 좌석 조회 p95 5.8초, 504 621건이 나왔다. 처음 회(`133015`)는 스왑으로도 자리를 만들지 못해 강제 종료된 것으로 본다. 그 회는 관찰 자료가 없어 그 순간의 구성은 미확인이다.
- **기각한 가설:** 힙 확장은 기각한다. 힙 용량이 GC 로그에서 247~252MB로 그대로였다. "JVM 지표에 안 보이는 Netty 직접 메모리"도 기각한다. Netty가 JDK 직접 버퍼를 쓰므로(`direct buffer constructor: unavailable`) NMT `Other`와 JDK 지표에 잡힌다. 앞 회 Prometheus(5초)가 3~19MB만 본 것은 몇 초짜리 급등을 놓쳤기 때문이다.
- **배포와 다른 점(미확인):** 배포 서버에 스왑이 있는지는 문서에 없어 확인하지 못했다. 스왑이 없으면 같은 상황에서 느려지는 대신 바로 강제 종료될 것으로 본다. 배포 Gateway는 G1(측정은 Serial)이라 JVM 평시 크기가 다를 수 있다.

### Gateway 차단기 시험 값 비교 예상 (2026-11-11, 측정 전)

강민·영은이 배포 서버에서 시험 중인 `auth-redis` 값(재측정 2회 값, `docs/design/infra/gateway-auth-redis-resilience.md` 5절)을 local에 넣고 운영 값과 비교한다. Gateway 메모리 문제를 강민에게 넘길 때 근거로 쓴다.

- **코드:** 측정 브랜치의 Gateway 코드는 ISE-230/233 이전이다. 필터 시한을 설정값으로 바꾸려면 ISE-233 코드가 필요해서 dev의 `gateway/src/main`, `config-repo/gateway.yml`, `loadtest/deploy/compose.gateway-bulkhead.yml`을 가져왔다(`common`은 reservation-service에도 영향을 주므로 가져오지 않았다). reservation-service 코드(F)는 그대로다.
- **비교:** 두 묶음 모두 `compose.gateway-bulkhead.yml`이 차단기 키 전부를 `SPRING_APPLICATION_JSON`으로 준다. 그래서 이 측정 브랜치의 k6measure 완화(느린 호출 100ms, 실패율 100%)는 덮인다(강민 확인: `SPRING_APPLICATION_JSON`이 config 서버 값보다 우선). 운영 묶음의 벌크헤드가 25로, 시험 묶음이 50으로 보이는지 지표로 확인한 뒤 판정한다.
  - **운영 값(P):** 환경변수 없음. 창 20건, 느린 호출 50ms·50%, 실패율 50%, 열림 10초, 필터 시한 100ms, Lettuce 100ms, 벌크헤드 25
  - **시험 값(T):** 시간 창 10초·최소 500건, 느린 호출 100ms·80%, 실패율 50%, 열림 5초·반열림 20, 필터 시한 200ms, Lettuce 300ms, 벌크헤드 50 + `BulkheadFullException` 무시
- **측정:** CPU 상한 S(4코어, 5~1,280명)와 매진을 피한 스트레스 M(상한 없음) 두 시나리오를 P·T로 1회씩, 모두 4회다. Gateway 메모리 관찰(`compose.gateway-observe.yml`, 1초 샘플러, NMT)을 함께 켠다. 회마다 Gateway를 새로 띄운다.
- **예상:**
  - P는 지금까지의 측정(k6measure 완화)보다 일찍 무너진다. CPU 상한 S 160명 단계에서 p95가 약 140ms였으므로, Redis 확인도 50ms를 자주 넘어 느린 호출로 차단기가 열릴 것이다. M은 320명 이하에서 열릴 수 있다.
  - T는 P보다 버틴다. 다만 503의 원인이 차단기 열림에서 벌크헤드 거절(`bulkhead_full`)로 바뀐다. CPU가 모자라 Redis 확인이 길어지면 동시 확인이 50을 넘기 때문이다.
  - **메모리:** T에서 인증을 통과하는 요청이 늘면 830KB 응답이 더 많이 동시에 지나간다. 그래서 CPU 상한 S의 Gateway 메모리 상한 도달(소켓 받기 버퍼 급등)이 P보다 잦거나 커질 수 있다. 차단기를 덜 민감하게 하면 메모리 위험이 커질 수 있다는 것이 이번 측정으로 확인할 핵심이다.
- **판정에 쓸 값:** 단계별 좌석 조회·선점 성공률과 p95, 503 원인별 수(`gateway_auth_redis_failures_total{cause}`, 차단기 상태 전환 로그), Gateway 메모리 최대·상한 도달 횟수(`memory.events max`)·스왑 아웃·`sock` 최대, Gateway CPU.

## k6로 직면하지 않는 결함의 확인 (2026-11-06)

S1·S2·S4의 결함은 K1에 그 조건(같은 사용자 동시 요청, 같은 멱등키 재전송, 만료 스케줄러 두 개)이 없어 k6로는 직면하지 않는다(계획 문서 3-4절). 그래서 base 코드(`3dfc750`, dev와 같은 선점 코드)에서 동시성 테스트로 결함이 실제로 있는지 확인했다. 테스트의 단언은 고친 뒤의 목표라 base에서는 실패가 정상이다.

```bash
SEATHOLD_CONCURRENCY=true ./gradlew :reservation-service:test --tests '*SeatHoldConcurrencyTest.C4*'   --tests '*SeatHoldConcurrencyTest.C5*' --tests '*SeatHoldConcurrencyTest.C6*' --rerun --no-daemon
```

| 수정 | 테스트 | base 결과 | 목표 | 판정 |
|---|---|---|---|---|
| S1 매수 한도 | C4 같은 사용자 탭 4개 × 30라운드 | 30라운드 모두 한도 초과, 최대 8매 보유 | 한도 초과 0, 최대 4매 | 결함 있음 |
| S2 멱등키 | C5 같은 멱등키 3연타 × 30라운드 | 201 30건, 자기 요청에 409 60건 | 90건 모두 같은 201 | 결함 있음 |
| S4 만료 | C6 만료 100건, 스케줄러 2개 | 헛수고 100건(다른 인스턴스가 처리한 건을 다시 집음), 1,494ms | 헛수고 0 | 결함 있음 |

수정 S1~S4는 ISE-79 브랜치에 수정마다 커밋으로 넣었다(S1 `5b2a9b4`, S2 `4eaa6d3`, S3 `3b9b0bf`, S4 `c307621`). 넣은 뒤 동시성 테스트는 C1·C2·C4·C5·C6·C7이 통과했다. C4는 한도 초과 0, C5는 90건 모두 201, C6은 헛수고 0이다. C3은 처음에 최대 1,099ms로 목표 1초를 넘었다. `lock_timeout`이 잠금 시도마다 걸려 실제 상한이 약 1초이기 때문이라 목표를 1,500ms로 고쳤고(`971eec2`), 다시 돌려 최대 1,128ms로 통과했다([concurrency-results.md](../../docs/design/reservation/concurrency-results.md) 4-3절). cherry-pick할 때 이 커밋도 S3 뒤에 함께 넣는다. 이 브랜치에는 P1 앞에서 같은 순서로 cherry-pick하고, S1·S2 뒤에 K1-H S를 한 번씩 잰다. S4는 만료 경로만 바꾸고 측정 중 만료 스케줄러가 꺼져 있어 재지 않는다. S3은 잠금 대기를 직면하면 그 자리에, 아니면 S1·S2와 함께 넣는다.

세 결과 모두 이전 측정의 S0 값([concurrency-results.md](../../docs/design/reservation/concurrency-results.md) 3절)과 같다. 결함은 지금 코드에도 그대로 있다.
