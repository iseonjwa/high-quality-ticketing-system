# K1 단계 측정 기록 (측정 브랜치 `experiment/ISE-79-k6-steps`)

수정하지 않은 기본 코드에서 시작해, 측정에서 직면한 병목 하나를 고치고 다시 재는 순서로 쌓는다. 이 브랜치는 머지하지 않는다. 계획은 [k6-seathold-bottleneck-plan.md](../../docs/design/reservation/k6-seathold-bottleneck-plan.md) 3절이고, 결과는 단계가 끝날 때마다 그 문서 5절로 옮긴다.

## 규칙

- **한 단계 = 커밋 하나.** 코드로 고치는 단계는 코드를, 설정으로 고치는 단계(G1, R1, P1)는 `step-overlays.txt`에 덮어쓰기 한 줄을 더하는 커밋으로 넣는다. `git log`와 `git diff <앞 단계> <이 단계>`가 무엇을 바꿨는지의 기록이다.
- **직면한 것만 고친다.** 다음 단계는 앞 단계 측정에서 실제로 막힌 곳으로 정한다. 계획의 순서는 예상이고, 실측이 다르면 실측을 따르고 계획 문서에 이유를 적는다.
- **측정 전에 예상을 적는다.** 단계마다 아래 표의 "예상"을 먼저 채우고 잰 뒤 "실측"과 대조한다.
- **다른 이슈의 코드.** 이 브랜치에는 측정하려고 모든 단계를 쌓는다. 실제로 반영할 때는 이슈마다 따로 브랜치를 판다. 해당 단계는 P4(ISE-189, 반효승), R1(ISE-196), G1·P1(공유 설정, contract 이슈)이다. ISE-79 브랜치에는 선점 모듈 코드(S4, P3 등)와 측정 기록만 옮긴다.
- **기준 환경.** 배포 메모리(gateway 768MB, reservation-service 1,152MB), 선점 만료 스케줄러 끔, 60초 워밍업(초당 2명. 기본값 10명은 base 한계를 넘어 워밍업만으로 적체가 생겼다), 지표·GC 로그 켬, Gateway 인증 차단기의 느린 호출 판정 끔(아래). 나머지는 계획 문서 1-6절의 측정 기준을 따른다. 측정은 모두 local에서 하고, 배포 환경 성능 테스트는 나중에 따로 한다.

## 실행

워크트리 루트에서 Git Bash로 실행한다. 원래 저장소의 `.env`를 가리킨다. 먼저 기준 환경으로 전체 스택을 띄운다. `step-run.sh`는 reservation-service만 다시 띄우므로, 기준 환경 파일을 바꿨거나 원래 저장소에서 스택을 띄운 뒤에는 이 명령을 다시 실행한다.

```bash
K6=reservation-service/k6
docker compose --env-file ../../../.env -f compose.yml -f compose.local.yml -f $K6/compose.deploy-memory.yml   -f $K6/compose.b8-observe.yml -f $K6/compose.step-observe.yml -f $K6/compose.measure-gateway.yml up -d --build --wait

export ENV_FILE=../../../.env
bash reservation-service/k6/tools/step-run.sh base L   # 부하: 초당 100명 300초
bash reservation-service/k6/tools/step-run.sh base S   # 스트레스 5→320명 + 회복 120초
bash reservation-service/k6/tools/step-run.sh base H   # K1-H 스트레스 50→800명 + 회복 120초
```

- 회마다 지금 커밋으로 reservation-service를 다시 빌드해 새로 띄운다. 커밋되지 않은 코드·단계 설정이 있으면 멈춘다.
- 결과는 `results/step-<단계>-<종류>-<시각>-*`이다. k6 로그·요약·원자료, 회복 탐침, Prometheus 지표 CSV, GC 로그, 컨테이너 CPU와 잠금 대기 세션 수(`stats`), 대사(`invariants`), 조건(`meta`)이 남는다.
- 조건부 단계를 판단하는 회(P4c의 K1 S, P3의 K1-H S)에만 `OBSERVE_JFR=1`을 붙인다. JFR 녹화가 `results/*.jfr`로 남고, 로컬 JDK의 `jfr view hot-methods <파일>`로 본다. 꺼내려고 측정 뒤 reservation-service를 멈춘다.
- P5 근사 검증: base의 H 회 `metrics-summary.json`에서 `hold_time_s`와 `hikari_usage_s`가 20% 안인지 본다. 맞으면 이후 `hold_409_time_ratio`를 P5 판단에 쓴다.
- 대사가 0이 아니면 그 회의 처리량은 쓰지 않는다. 대사 위반이 나오면 그것이 S4(정합성 수정)를 넣을 근거다.
- 단계를 고르는 측정은 1회, 발표 비교점(기본, 각 묶음의 마지막 단계, 최종)은 3회 반복해 중앙값과 범위를 적는다.
- 끝나면 원래 저장소에서 `docker compose build reservation-service`로 이미지를 되돌린다. Compose 프로젝트 이름이 같아(`iseonjwa`) 이 브랜치 이미지가 원래 스택을 대신하기 때문이다.

### base 예상

예비 측정(계획 문서 5-1·5-2·5-4절, 측정 방법이 바뀌기 전)에서 가져왔다.

- **L(초당 100명):** 좌석 조회가 거의 모두 실패한다(503·504). 선점 201은 0건에 가깝다. 컨테이너 메모리가 작아 JVM이 Serial GC를 고르고, Major GC가 이어져 서비스가 수 초 이상 멈춘다. Eureka 갱신이 끊겨 전체 503이 겹칠 수 있다.
- **S:** 오류 1% 미만으로 버틴 최대 속도는 초당 5명이다. 10명 단계에서 좌석 조회가 무너진다.
- **R:** 회복하지 못한다. 부하가 끝나도 Gateway가 포기한 요청을 서버가 계속 처리해 탐침이 10분 가까이 실패한다(B8).
- **H:** 예비 측정은 G1에서만 했다. Serial에서도 좌석 조회가 없으면 할당이 작아 초당 100~200명은 버틸 것으로 본다. 넘으면 커넥션 대기(풀 5)가 먼저 막는다.
- **대사:** 위반 0으로 예상한다. S1(매수 한도)·S2(멱등키)·S4(만료)의 결함은 같은 사용자의 동시 요청, 같은 멱등키 재전송, 만료 스케줄러 두 개에서 생기는데, K1에는 그 조건이 없다. 이 셋은 동시성 테스트로 직면한 결함으로 P1 앞에 넣고 비용만 잰다(계획 문서 3-4절).
- **잠금 대기:** S3(잠금 대기 상한)은 K1에서 직면할 수 있다. `stats`의 `lock_waits`가 처음 무너진 단계에서 풀의 절반(3개) 이상 이어지면 S3을 넣는다. base에서는 GC 정지와 커넥션 대기가 먼저 막아 거의 보이지 않을 것으로 본다.
- **다음 단계 예상:** G1(GC 정지) → R1(회복 실패) → P4a(좌석 조회가 커넥션을 붙잡음) 순서로 직면할 것으로 본다.

### base 실측 (2026-11-06)

결과 파일은 `results/step-base-{L,S,H}-*`다. 세 회 모두 GC는 Serial(JVM이 고름), 재시작 0, 대사 위반 0이다.

**측정 방법을 두 번 고쳤다.** 첫 S 회는 워밍업(k6 기본 초당 10명)이 base 한계를 넘어, 요청 스레드 200개와 커넥션 대기 197건이 찬 채로 측정이 시작됐다. 5명 단계부터 전부 504라 쓰지 않았다. 워밍업을 모든 단계에서 초당 2명으로 낮췄다(`1836e87`). 또 새로 띄운 직후 관리자 경로가 데워지지 않아 회차 생성이 실패해, 버리는 회차로 먼저 데운다(`da3f332`, `64b963e`). 측정 대상은 바꾸지 않았다.

**H에서 직면한 것: Gateway 인증 차단기(`auth-redis`).** Gateway는 요청마다 Redis에서 로그아웃 토큰 여부를 확인하고, 이 호출에 차단기를 건다(`config-repo/gateway.yml`: 느린 호출 50ms, 비율 50%, 열림 10초. 호출 시한 100ms). 초당 100명 단계 30초째(부하 시작 90초)부터 즉시 503이 나왔다. Gateway CPU가 100~180%로 오르자 Redis 응답을 늦게 받아 느린 호출 비율이 90~100%가 되고 차단기가 열렸다. 열린 동안 인증이 필요한 요청은 모두 즉시 503이다(거절 약 6만 1천 건). Redis 컨테이너 CPU는 10% 아래였으므로 Redis가 아니라 Gateway 쪽 지연이다. 회복 탐침은 인증이 없는 공개 API라 200이었지만, 같은 시간 선점은 99%가 503이었다. Gateway는 다른 담당 영역이라 이 측정에서는 고치지 않는다.

**P5 근사 검증: 통과하지 못했다.** H 회에서 `hold_time_s` 1,412.8초, `hikari_usage_s` 268.0초로 20% 안이 아니다(약 5.3배). 선점 처리 시간의 약 5분의 1만 커넥션을 쥔 시간이라 `hold_409_time_ratio`(0.758)를 P5 판단에 그대로 쓸 수 없다. 이 차이 자체는 커넥션 밖 처리 시간이 크다는 신호라 P2 판단(JFR)에서 다시 본다.

**다음 단계:** K1(L·S)은 예상대로 G1(GC 정지)로 간다. K1-H는 Gateway 차단기가 reservation-service보다 먼저 막아, 선점 경로의 병목을 보려면 처리 방식을 정해야 한다.

**차단기 처리 (2026-11-07 결정):** 측정 환경에서만 느린 호출 판정을 끈다. 단계가 아니라 기준 환경이므로 base부터 모든 단계에 똑같이 얹는다. 선점 쪽 개선이 수치로 보이지 않으면 그 개선을 재는 의미가 없기 때문이다. 발견 내용은 Gateway 담당에게 contract 이슈로 알리고, 공유 설정에 반영할지는 그쪽이 정한다.
- 덮어쓰기: `compose.measure-gateway.yml`이 Gateway에 `k6measure` 프로필을 켜고, config-server가 `config-measure/`를 함께 읽게 한다. `config-measure/gateway-k6measure.yml`이 `slow-call-duration-threshold`를 50ms에서 100ms(호출 시한과 같음)로 올린다. 시한을 넘긴 호출은 어차피 실패로 세므로 느린 호출 판정만 사실상 꺼진다. "시한 초과·오류가 절반 이상이면 연다"는 보호는 남는다.
- `step-run.sh`는 Gateway가 `k6measure` 프로필로 떠 있지 않으면 멈춘다.
- base H는 이 환경에서 다시 잰다. 위 H 회는 공유 차단기 기준의 기록으로 남긴다. K1 L·S는 Gateway까지 부하가 가기 전에 reservation-service가 무너져 이 환경과 결과가 같다고 보고, 다시 재지 않는다. G1부터는 이 환경에서 잰다.

| 회 | 예상 | 실측 | 대조 |
|---|---|---|---|
| H (차단기 완화) | 차단기가 느린 호출로 열리지 않아 부하가 reservation-service까지 간다. 100~200명에서 커넥션 5개가 차고 대기가 생긴다(선점 한 건이 DB 왕복 약 12~14번). 인기 구역 쏠림으로 잠금 대기 세션이 0보다 커진다(S3 직면 후보). 400명 이상에서는 Gateway CPU 포화로 Redis 호출이 시한 100ms를 넘겨 503(실패로 여는 차단기)이 다시 섞일 수 있다 | (측정 전) | |

## k6로 직면하지 않는 결함의 확인 (2026-11-06)

S1·S2·S4의 결함은 K1에 그 조건(같은 사용자 동시 요청, 같은 멱등키 재전송, 만료 스케줄러 두 개)이 없어 k6로는 직면하지 않는다(계획 문서 3-4절). 그래서 base 코드(`3dfc750`, dev와 같은 선점 코드)에서 동시성 테스트로 결함이 실제로 있는지 확인했다. 테스트의 단언은 고친 뒤의 목표라 base에서는 실패가 정상이다.

```bash
SEATHOLD_CONCURRENCY=true ./gradlew :reservation-service:test --tests '*SeatHoldConcurrencyTest.C4*'   --tests '*SeatHoldConcurrencyTest.C5*' --tests '*SeatHoldConcurrencyTest.C6*' --rerun --no-daemon
```

| 수정 | 테스트 | base 결과 | 목표 | 판정 |
|---|---|---|---|---|
| S1 매수 한도 | C4 같은 사용자 탭 4개 × 30라운드 | 30라운드 모두 한도 초과, 최대 8매 보유 | 한도 초과 0, 최대 4매 | 결함 있음 |
| S2 멱등키 | C5 같은 멱등키 3연타 × 30라운드 | 201 30건, 자기 요청에 409 60건 | 90건 모두 같은 201 | 결함 있음 |
| S4 만료 | C6 만료 100건, 스케줄러 2개 | 헛수고 100건(다른 인스턴스가 처리한 건을 다시 집음), 1,494ms | 헛수고 0 | 결함 있음 |

수정 S1~S4는 ISE-79 브랜치에 수정마다 커밋으로 넣었다(S1 `5b2a9b4`, S2 `4eaa6d3`, S3 `3b9b0bf`, S4 `c307621`). 넣은 뒤 동시성 테스트는 C1·C2·C4·C5·C6·C7이 통과했다. C4는 한도 초과 0, C5는 90건 모두 201, C6은 헛수고 0이다. C3은 처음에 최대 1,099ms로 목표 1초를 넘었다. `lock_timeout`이 잠금 시도마다 걸려 실제 상한이 약 1초이기 때문이라 목표를 1,500ms로 고쳤고(`971eec2`), 다시 돌려 최대 1,128ms로 통과했다([concurrency-results.md](../../docs/design/reservation/concurrency-results.md) 4-3절). cherry-pick할 때 이 커밋도 S3 뒤에 함께 넣는다. 이 브랜치에는 P1 앞에서 같은 순서로 cherry-pick하고, S1·S2 뒤에 K1-H S를 한 번씩 잰다. S4는 만료 경로만 바꾸고 측정 중 만료 스케줄러가 꺼져 있어 재지 않는다. S3은 잠금 대기를 직면하면 그 자리에, 아니면 S1·S2와 함께 넣는다.
